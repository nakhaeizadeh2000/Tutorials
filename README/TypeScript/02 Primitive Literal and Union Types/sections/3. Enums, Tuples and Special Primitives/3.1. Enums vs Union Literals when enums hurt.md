## 3.1. Enums vs Union Literals (when enums hurt)

### 1) **Tradeoff** (enum emit vs union)

**Definition** — `enum` is a TS-only feature that emits a real object at runtime; a union of literals (`"a" | "b"`) is purely type-level and erases to nothing.

```typescript
// enum — emits JS object
enum DirectionEnum { North, South, East, West }
// emits: var DirectionEnum; (function (D) { D[D["North"] = 0] = "North"; ... })(DirectionEnum || ...)

// union literal — zero emit
type Direction = "north" | "south" | "east" | "west"; // erases entirely
```

Tradeoff table:

| Aspect | `enum` | Union literal (`"a"\|"b"`) |
|--------|--------|-----------------------------|
| Runtime cost | object + reverse mapping (numeric) | zero |
| Tree-shake | poor — side-effectful IIFE | perfect |
| Interop | needs import, breaks `isolatedModules` for `const enum` | just `string` |
| Exhaustiveness | works with `never` | works with `never` |
| Declarations | single namespace | composable (`type T = A \| B`) |

**Modern guidance** (5.6 era): prefer union literals by default. Use `enum` only when you need *both* a runtime collection (`Object.values(DirectionEnum)`) and bidirectional mapping, and can tolerate emit.

### 2) **Bad** (ambient enums)

**Bad practices:**

- `const enum` across module boundaries — inlines values at use site but requires `isolatedModules: false` to cross-file inline correctly; with `isolatedModules: true` (required for `tsx`/`esbuild`/`swc`) it breaks or requires `preserveConstEnums`. See [10 3.1 Const Enum trap](<../../../10%20Migration%20Interop%20and%20Runtime%20Gaps/sections/3.%20Performance%20and%20Emit%20Gaps/3.1.%20Const%20Enum%20Erased%20Types%20and%20Perf%20Traps.md>).
- Ambient `declare enum` — type-only enum with no emit; confusing parity between `declare` and real `enum`.
- Numeric enum without explicit values — auto-increment reorders silently on insertion.

```typescript
// bad: const enum leaks across modules under isolatedModules
export const enum Status { Draft = 0, Published = 1 }
// in another file: import { Status } from "./status.js"; if (x === Status.Draft) → inlined 0 only whole-program

// good: erasable union — works in any transpiler
export type Status2 = "draft" | "published";
export const Status2 = {
  Draft: "draft" as const,
  Published: "published" as const,
} as const; // runtime object if needed, separate from type
type _Check = typeof Status2[keyof typeof Status2]; // "draft" | "published"

// numeric enum surprise
enum Bad { A, B, C } // A=0 B=1 C=2 — insert A2 between A and B shifts B/C values → DB breakage
enum Good { Draft = 1, Published = 2, Archived = 3 } // explicit
```

### 3) **Mentor** (prefer union literals)

**Mentor rule:** default to `type Role = "admin" | "member"` and review any `enum` PR as "explain why you need runtime object." The checklist:

- Do you iterate `Object.values(Role)` at runtime? If no → union.
- Do you need reverse mapping (`Role[0] === "North"`)? If no → union.
- Is this a library publishing types for consumers with `isolatedModules`? If yes → union (or `as const` object pattern above).

```typescript
// recommended pattern — single source, both type and value
const Role = { Admin: "admin", Member: "member", Guest: "guest" } as const;
type Role = typeof Role[keyof typeof Role]; // "admin" | "member" | "guest"

// exhaustive check still works
function describeRole(r: Role): string {
  switch (r) {
    case "admin": return "Admin";
    case "member": return "Member";
    case "guest": return "Guest";
    default: { const _ex: never = r; throw new Error("unhandled"); }
  }
}
```

### Common confusion

- "`enum` is type-only" — no, it emits. `type` and `interface` erase; `enum` does not.
- "`const enum` is zero-cost, always better" — only whole-program emit. With `isolatedModules`, it's a footgun; prefer union.

### Performance note

Union literals have no emitted helpers. Numeric enums emit IIFE + reverse map (extra bytes + startup parse cost). For hot paths with many enums, bundle size measurable.
