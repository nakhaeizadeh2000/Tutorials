## 1.2. Optional, Rest and Void

### 1) **Definition** (optional param vs overload)

**Definition:**

- `param?: T` — may be omitted at call site; inside function `param` is `T | undefined`.
- `...rest: T[]` / tuple rest `...rest: [string, number]` — variadic.
- `void` — function does *not use* its return value; caller should not rely on it. Contrast `undefined` (value) and `never` (doesn't return).

```typescript
function greet(name: string, title?: string): string {
  return title ? `${title} ${name}` : name;
}
greet("Ava"); // "Ava"
greet("Ava", "Dr."); // "Dr. Ava"
// title is string | undefined inside

function join(sep: string, ...parts: string[]): string {
  return parts.join(sep);
}
join("-", "a", "b", "c"); // "a-b-c"

// tuple rest for precise arity
type Args = [string, number, boolean?];
function call(...args: Args) {}
call("hi", 42); // ok
call("hi", 42, true); // ok
// call("hi"); // error — second required

// void vs undefined
function returnsVoid(): void { console.log("hi"); }
function returnsUndefined(): undefined { return undefined; }
let v: void = returnsVoid(); // caller's v is void — not useful to read
let u: undefined = returnsUndefined(); // explicit undefined value
```

Optional param vs overload: use overload only when *return type* changes with arity; otherwise optional param is simpler (see [2.1 Overloads](<../2.%20Overloads%20and%20Generics%20in%20Functions/2.1.%20Overload%20Signatures%20when%20overloads%20help.md>)).

### 2) **Example** (rest tuple types)

```typescript
// precise rest tuple: named + typed positions
type HandlerArgs = [event: "click", x: number, y: number] | [event: "key", key: string];
function emit(...args: HandlerArgs) {}
emit("click", 10, 20); // ok
emit("key", "Enter"); // ok
// emit("click", "x", 0) // error — second must be number

// infer helper for rest (advanced — used by ReturnType analogs)
type First<T extends unknown[]> = T extends [infer F, ...unknown[]] ? F : never;
type F = First<HandlerArgs>; // "click" | "key" (but shows distribution nuance — see 06)

// callback void trap
type Cb = (x: number) => void;
const cb: Cb = (x) => 42; // ok — returning value from void callback is allowed (caller ignores it)
// but inside, relying on return is wrong:
declare function doEach(cb: Cb): void;
// doEach((x) => 1) — return 1 is silently ignored; don't assign result of Cb call
```

---

### 3) **Bad** (void misused)

**Bad patterns:**

- Using `void` as "nothing" param: `(x: void)` — means "call with undefined" under `strict`. Use `()` or `param?: never` instead.
- Returning a meaningful value from a `void`-typed callback and expecting caller to use it (e.g., `forEach` return ignored).
- Marking *required* param as optional to avoid overload — loses caller guidance.

```typescript
// bad: callback returns value but typed void — silent discard
function forEachBad(arr: number[], cb: (x: number) => void): void {
  for (const x of arr) cb(x);
}
let sum = 0;
forEachBad([1,2], x => sum += x); // return ignored — ok
forEachBad([1,2], x => x * 2); // also ok (no error) but value 2*x thrown away — likely bug

// good: if caller's return matters, type it properly
function mapGood<T, U>(arr: T[], cb: (x: T) => U): U[] { return arr.map(cb); }

// bad: optional hides required
function createBad(name?: string): string { return name ?? "anon"; }
// createBad() // allowed — but was name truly optional? If not, error slips

// bad: : void param
declare function takesVoid(x: void): void;
// takesVoid("hi") // error
// use () => void for no-arg, or optional
```

**Common confusion** —

- "`void` and `undefined` same" — no. `void` is contextual "ignore return"; `undefined` is a concrete value. Function returning `void` can return anything; returning `undefined` must be code-path `undefined`.

**Performance note** — Types are erased (zero emit); checker cost dominates. For this feature, keep types shallow and measure `tsc --extendedDiagnostics` if checker slows.

**Mentor note** —

Teach `void` as "caller ignores return" not "function returns nothing." Demo: `() => 42` is assignable to `() => void` — a frequent interview question.
