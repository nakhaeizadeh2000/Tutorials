## 1.1. Function Type Expressions and Call Signatures

### 1) **Definition** ((x: string) => number)

**Definition** — A function type describes call shape. Forms:

- Type expression: `(x: string) => number`
- Call signature inside object/interface: `{ (x: string): number }` or `interface Fn { (x: string): number; prop: string }` (callable + properties).
- Method shorthand vs function property (affects `this` parameter).

```typescript
type Fn = (x: string) => number;
const f: Fn = (x) => x.length;

type CallableWithProp = {
  (x: string): number;
  description: string;
};
const tagged: CallableWithProp = Object.assign((x: string) => x.length, { description: "len" });

// interface call signature
interface Parser {
  (input: string): string[];
  delimiter: string;
}

// generic call signature
type Identity = <T>(x: T) => T;
const id: Identity = x => x;

// optional and rest in signature
type Variadic = (first: string, ...rest: number[]) => void;
```

### 2) **Context** (contextual typing)

Contextual typing infers parameter types from where the function is used:

```typescript
const nums = [1, 2, 3];
// callback param typed by array element type — no annotation needed
const doubled = nums.map(n => n * 2); // n inferred as number

// same for custom higher-order
function forEach<T>(arr: T[], fn: (item: T, i: number) => void): void {
  for (let i = 0; i < arr.length; i++) fn(arr[i], i);
}
forEach(["a", "b"], (item, i) => {
  item.toUpperCase(); // item inferred as string
  console.log(i.toFixed()); // i as number
});

// contextual this requires explicit this parameter (see 04 3.1)
```

### 3) **Mistake** (bivariance pitfall)

**Mistake — bivariant function parameters** (historical): function params are *bivariant* (accept wider *and* narrower) when `strictFunctionTypes: false`. With `strict: true` they are contravariant for non-method syntax (safe). Array methods and callbacks rely on this.

```typescript
// with strictFunctionTypes (strict: true), this correctly errors:
type Handler = (x: string | number) => void;
type StringHandler = (x: string) => void;
// const h: Handler = ((x: string) => {}) as StringHandler // error — string handler cannot handle number

// method syntax is bivariant (intended for built-in compat)
interface Array<T> {
  // method syntax — bivariant
  // strictFunctionTypes does not apply to method shorthand
}

// bad: misusing method vs property for callback
type Bad = {
  handle(x: string): void; // method — bivariant (lenient)
};
type Good = {
  handle: (x: string) => void; // property — strict contravariant
};

// bad: any in callback propagates
const bad = [1, 2].map((x: any) => x + 1); // loses inference
// good: let inference flow
const good = [1, 2].map(x => x + 1); // x inferred number
```

### Mentor note

Default to `type Fn = (...) => ...` for pure functions, interface call signature only when you need callable + properties (e.g., overloaded lib function with attached `mock`).

### Common confusion

- "`Function` type is fine for callbacks" — no. `Function` is untyped (like `any` for callables). Use specific signature.
