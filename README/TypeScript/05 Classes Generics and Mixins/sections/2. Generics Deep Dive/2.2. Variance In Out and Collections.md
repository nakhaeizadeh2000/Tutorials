## 2.2. Variance, In Out and Collections

### 1) **Concept** (invariance vs covariance)

**Definition** — Variance asks: if `Cat extends Animal`, is `Wrapper<Cat>` assignable to `Wrapper<Animal>`? TS 4.7 adds explicit `in`/`out` modifiers for precise checking.

- **Covariant** (`out T`) — wrapper produces `T`: `Wrapper<Cat>` → `Wrapper<Animal>` safe. Example: `ReadonlyArray<T>`.
- **Contravariant** (`in T`) — wrapper consumes `T`: `Wrapper<Animal>` → `Wrapper<Cat>` safe (callback params). Example: `(x: T) => void` with `strictFunctionTypes`.
- **Invariant** (`in out T`) — both produce + consume (mutable): `Array<T>` — *neither* direction safe. You need exact `T`.
- **Bivariant** — both directions unsafe (legacy method syntax in `strictFunctionTypes: false`).

```typescript
type Getter<out T> = { get(): T }; // covariant — getter produces T
let catGetter: Getter<{ kind: "cat"; meow(): void }> = { get: () => ({ kind: "cat", meow() {} }) };
let animalGetter: Getter<{ kind: string }> = catGetter; // ok — covariant

type Setter<in T> = { set(v: T): void }; // contravariant — setter consumes T
type Handler<in T> = (x: T) => void;
let animalHandler: Handler<{ kind: string }> = (x) => {};
let catHandler: Handler<{ kind: "cat" }> = animalHandler; // ok — contravariant? Actually Handler<Animal> can handle Cat (extra checks)

type Box<in out T> = { value: T; set(v: T): void }; // invariant — mutable
// Box<Cat> not assignable to Box<Animal> nor vice versa
```

### 2) **Example** (ReadonlyArray out)

```typescript
// classic example from Handbook:
// Mutable array is invariant
let cats: { kind: "cat" }[] = [{ kind: "cat" }];
let animals: { kind: string }[] = cats; // error if strict? Actually Array is invariant with variance annotations (TS 4.7+ strict)
// cats.push({ kind: "dog" }) via animals alias would corrupt cats — hence invariance

// Readonly is covariant — safe to widen
let roCats: readonly { kind: "cat" }[] = [{ kind: "cat" }];
let roAnimals: readonly { kind: string }[] = roCats; // ok — readonly out T is covariant

// Promise is covariant (produces T)
let pCat: Promise<{ kind: "cat" }> = Promise.resolve({ kind: "cat" });
let pAnimal: Promise<{ kind: string }> = pCat; // ok

// Function param is contravariant with strictFunctionTypes
type Cb<in T> = (x: T) => void;
declare let cbAnimal: Cb<{ kind: string }>;
declare let cbCat: Cb<{ kind: "cat" }>;
// cbCat vs cbAnimal direction shows contravariance (Animal handler can handle Cat)
```

Enable `--strict` (includes `strictFunctionTypes`) to see these distinctions; otherwise functions are bivariant.

### 3) **Expert** (in/out TS 4.7)

**Expert — TS 4.7 `in out`:**

- Annotate generic parameters when you own the type: `interface Emitter<in T> { on(handler: (x: T) => void): void }` signals "consumes T" — checker can then enforce covariance checks at call site.
- Omit annotation — TS infers variance from usage (property position). But explicit `in out` documents intent and catches drift when internals change.
- Library example:

```typescript
// explicit variance — library author
interface Producer<out T> { produce(): T; }
interface Consumer<in T> { consume(x: T): void; }
interface Store<in out T> { get(): T; set(x: T): void; } // invariant

// checks
declare let pCat2: Producer<{ kind: "cat" }>;
declare let pAnimal2: Producer<{ kind: string }>;
pAnimal2 = pCat2; // ok — covariant

declare let cAnimal: Consumer<{ kind: string }>;
declare let cCat: Consumer<{ kind: "cat" }>;
// cCat = cAnimal // ok — contravariant
```

### Mentor note

Default to `readonly` collections when you only read; covariance then makes subtyping work without casts. If a function takes `readonly T[]`, callers can pass `U[]` where `U extends T` — fewer `as` assertions in reviews.

### Common confusion

- "Array is covariant" — no, `Array` is invariant (mutable). `ReadonlyArray` is covariant.
- "`in out` changes runtime" — no, variance modifiers are type-only, erased.
