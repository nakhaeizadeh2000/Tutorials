## 2.2. Designing APIs with Types (when to generic)

### 1) **Guidance** (generic only if reused)

**Guidance — when to genericize:**

- **Generic** when API is *reused* across multiple types without losing precision (helper, container, combinator).
- **Concrete** when API is domain-specific (`User`/`Order`) — concrete signatures read better and error messages are shorter.

Decision table:

| Situation | Use | Why |
|-----------|-----|-----|
| `identity`, `Array.map`, `Promise.all` | generic | Must preserve caller's type |
| `getUser(id: string): Promise<User>` | concrete | Single domain shape |
| `createValidator<T extends string>()` that only ever called with `User` | concrete | Generic adds noise without value |
| `EventEmitter<T>` used for many event types | generic | Reuse |

```typescript
// good generic: preserves caller literal
function wrap<T>(v: T): { value: T } { return { value: v }; }
let a = wrap("hi"); // { value: string } inferred, a.value is string literal flow
let b = wrap(42);    // { value: number }

// bad generic: only one call site type — YAGNI
function getUserGeneric<T extends { name: string }>(user: T): T { return user; }
// simpler: function getUser(user: User): User

// good concrete for domain
type User = { id: string; name: string };
function greetUser(user: User): string { return `Hi ${user.name}`; }

// helper that's genuinely generic
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
```

### 2) **Example** (API shape)

```typescript
// API with fluent + type-safe builder
type Config = { timeout: number; retries: number; baseUrl: string };
type PartialConfig = Partial<Config>;
type Built<T extends PartialConfig> = T extends Required<Config> ? Config : PartialConfig;

class ApiBuilder<T extends PartialConfig> {
  constructor(private cfg: T) {}
  withTimeout(n: number): ApiBuilder<T & { timeout: number }> {
    return new ApiBuilder({ ...this.cfg, timeout: n } as T & { timeout: number });
  }
  build(): T extends Required<Config> ? Config : never {
    // runtime check that required fields present
    if (!("timeout" in this.cfg) || !("retries" in this.cfg) || !("baseUrl" in this.cfg)) {
      throw new Error("missing");
    }
    return this.cfg as T extends Required<Config> ? Config : never;
  }
}
let api = new ApiBuilder({}).withTimeout(1000); // T is still partial — build() type prevents calling too early

// overload vs generic for API ergonimcs (see 04)
function fetchApi(url: string): Promise<Config>;
function fetchApi(url: string, fallback: Config): Promise<Config>;
function fetchApi(url: string, fallback?: Config): Promise<Config> {
  return Promise.resolve(fallback ?? { timeout: 0, retries: 0, baseUrl: url });
}

// branded API id vs plain string (design safety)
type UserId = string & { __brand: "UserId" };
function loadUser(id: UserId): User { /* ... */ return { id, name: "Ava" }; }
// loadUser("plain"); // error — forces branded creation, great for public SDK
```

**Common confusion** —

- "Generic makes API more type-safe automatically" — only if constraint correct (`extends`). Wrong constraint gives `any`-like permissiveness.

**Performance note** —

Heavy generic API chains (`Builder<T & U & ...>`) stretch `tsc` check time. For internal high-churn APIs, prefer concrete + overload.

**Design note** —

Types are checked docs — not docs that drift. A well-typed builder prevents missing-config bug *before* `fetch` call, no runtime cost.

**Mentor note** —

Rule: "generic only if reused." In PR, ask: "how many call sites would benefit from this `T`?" If 1, make concrete; if 3+ with different `T`, keep generic.
