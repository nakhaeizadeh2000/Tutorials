## 1.2. Code Review Checklist (what to reject)

### 1) **Checklist** (any, !, as)

**Reject checklist (merge-blocking):**

- `any` without `// reason: ...` comment + tracking issue — require `unknown` + narrow. Lint `no-explicit-any: error`.
- `!` non-null assertion (`user!.email`) — reject unless secured by preceding guard; prefer `?.`/`??` or `if (user)`.
- `as` assertion across boundary (`JSON.parse(s) as User`, `x as string`) — require validator (`z.parse`) or guard (`isUser`).
- `@ts-ignore` / `@ts-expect-error` without `why` — require error code + linked ticket.
- `const enum` in lib code — require union literal.
- `namespace` in app code — require ESM.
- Missing `strict` handling: `arr[0]` used without `??`/guard when `noUncheckedIndexedAccess` would have flagged — require guard.

```typescript
// reject examples
let badAny: any = fetchUser(); // any — reject, use Promise<User> + unknown at fetch edge
let badAssert = JSON.parse(s) as User; // as — reject, use schema.parse
let badBang = user!.email; // ! — reject: if (user) or user?.email ?? fallback
// @ts-ignore — reject without comment

// good
import { UserSchema } from "./schema.js";
let goodUser: User = UserSchema.parse(JSON.parse(s));
let goodEmail = user?.email ?? "unknown";
```

Checklist file: `docs/CODE_REVIEW.md` or `CONTRIBUTING.md` entry with these bullets + link to this domain.

### 2) **Example** (PR comment)

Template comments to reuse:

```markdown
<!-- reject any -->
Any hides the checker. Please replace with `unknown` + guard or add // reason: integration with untyped lib X tracked in #123.

<!-- reject as -->
`as User` at line 42 is a boundary assertion. Please use `UserSchema.parse` or `isUser` guard — see [10 2.1 Zod bridge](../../../10%20Migration%20Interop%20and%20Runtime%20Gaps/sections/2.%20Interop%20and%20Boundaries/2.1.%20Zod%20Valibot%20and%20Runtime%20Validation%20TS%20erasure%20bridge.md).

<!-- reject ! -->
Non-null `!` assumes API never returns null. Prefer `value ?? fallback` or early return if null branch is expected.

<!-- reject const enum -->
`const enum` breaks isolatedModules with esbuild/swc — please switch to union literal `"draft"|"published"` + const object (see [02 3.1 Enums](../../../02%20Primitive%20Literal%20and%20Union%20Types/sections/3.%20Enums%20Tuples%20and%20Special%20Primitives/3.1.%20Enums%20vs%20Union%20Literals%20when%20enums%20hurt.md)).
```

Enforce via `danger.js`/`husky`? Prefer human, but also automate: `eslint --max-warnings=0` + `biome check` + `tsc --noEmit` in CI block before review.

### 3) **Mentor** (teach vs gatekeep)

**Mentor — gate vs teach:**

- Don't just block — add link to leaf that explains *why*. E.g., link to [02 3.1 Enums](<../../../02%20Primitive%20Literal%20and%20Union%20Types/sections/3.%20Enums%20Tuples%20and%20Special%20Primitives/3.1.%20Enums%20vs%20Union%20Literals%20when%20enums%20hurt.md>) when rejecting enum.
- Use `nit:` for style, `block:` for safety; separate correctness from taste.
- For `any` legitimate (legacy lib one-off), allow `// TODO(any): #123` with ticket.
- Track metrics: # of `any` per package trending down; celebrate when a team reaches `strict: true`.

### Common confusion

- "Strict checklist slows velocity" — measured effect is opposite post-adoption; track bug count before/after.

### Performance note

Rejecting `any` early avoids defensive runtime clones (`JSON.parse(JSON.stringify)`) introduced later to paper over type lies.
