## 1.1. Type Challenges and Whiteboard Patterns

### 1) **Challenge** (Pick impl)

**Whiteboard type challenges (expect to hand-write without IDE):**

```typescript
// implement Pick
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
type A = MyPick<{ a: string; b: number; c: boolean }, "a" | "c">; // {a: string; c: boolean}

// implement ReturnType
type MyReturn<T> = T extends (...args: unknown[]) => infer R ? R : never;
type R = MyReturn<() => string>; // string

// implement Partial
type MyPartial<T> = { [K in keyof T]?: T[K] };

// deep readonly (recursive)
type DeepReadonly<T> = T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } : T;
type DR = DeepReadonly<{ a: { b: string } }>; // { readonly a: { readonly b: string } }

// key remapping: get getters
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
type G = Getters<{ name: string }>; // { getName: () => string }
```

Interview expects you to *explain* distributive + infer while writing.

### 2) **Example** (live coding)

```typescript
// live exercise: exhaustive discriminated union handler
type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number };
function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "square": return s.s ** 2;
    default: {
      const _ex: never = s; // must add new branch when Shape grows
      throw new Error("unknown");
    }
  }
}

// live: generic constraint
function get<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
// what happens with T extends {id:string}? discuss

// live: branded id vs structural
type UserId = string & { __brand: "UserId" };
function takes(id: UserId) {}

```

Explain tradeoffs verbally as you type — interviewer scores reasoning over syntax.

### 3) **Mistake** (over-engineer)

**Common interview mistakes:**

- Jumping to complex utility (`DeepReadonly`) before simple (`Pick`) passes — start trivial, then layer.
- Missing `extends keyof T` constraint → `MyPick` accepts non-keys, no error.
- Forgetting distributivity trap (`Exclude` needs naked `T extends`).
- Over-engineering branded solution when simple literal discriminant suffices.

```typescript
// bad: over-engineered generic when simple will do
type Over<T extends string | number> = T extends string ? string[] : number[];
// Could be union param: (x: string | number) => (string[] | number[])

// good: simplest passing whiteboard answer
type SimpleExclude<T, U> = T extends U ? never : T;
type Test = SimpleExclude<"a"|"b"|1, string>; // 1
```

**Common confusion** —

- "Need to memorize lib.d.ts" — no, derive from `keyof` + `in` + `infer` patterns.

**Performance note** — Types are erased (zero emit); checker cost dominates. For this feature, keep types shallow and measure `tsc --extendedDiagnostics` if checker slows.

**Mentor note** —

In mock interviews, require candidates to state *definition* before writing code: "Pick is mapped over keys" — tests mental model, not memory.
