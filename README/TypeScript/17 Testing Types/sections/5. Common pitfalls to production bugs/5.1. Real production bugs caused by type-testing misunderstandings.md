## 5.1. Real production bugs caused by type-testing misunderstandings

### 1) **Snapshot-only type tests approved a widened public return** (hover text updated blindly, switches going non-exhaustive)

**Definition** — the incident: a library's `status()` returned `"paid" | "shipped"`; a refactor widened it to `string` (fetch normalization "simplifying" the type). The type-snapshot suite recorded hover text — the developer ran `--update`, snapshots went green. Three consumer services with exhaustive switches over the union went non-exhaustive silently (default branches swallowing `"paid"` refunds as "unknown" — revenue misclassified for 11 days).

**What problem it solves / history** — snapshot-update reflexes (bulk `--update` as conflict resolution — 3.1's warned pattern) approve semantic moves as text churn. `Equal` assertions would have broken (identity failing on widening — no update flag capable of approving it silently); the fix took one probe line, the incident took a quarter's revenue-review to untangle.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), `Equal` on every public return (3.1 discipline — snapshots never the primary gate); CI failing on snapshot `--update` flags (updates local, hunk-by-hunk, contract-justified). Post-incident rule adopted: widening a public return requires a major version + consumer-switch audit (baseline diffs per 3.2 part 3).

**Runnable example** — the widening that snapshots approve and assertions catch (good vs bad, `tsc --strict`):

```typescript
// good — Equal breaking on widening (the probe that would have paged)
export {}; // module marker (consistent module scope across fences)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
// pre-refactor contract: "paid" | "shipped" (probe pins it — widening breaks HERE, pre-merge)
function status(): "paid" | "shipped" { return "paid"; }
assertType<Equal<ReturnType<typeof status>, "paid" | "shipped">>(); // red after widening (no --update escape — deliberation forced)
console.log(status()); // paid — widening loud (major version + switch audit, or revert)
// bad — snapshot updated with the widening (hover text re-recorded — green suite, rotting consumers)
// fix — Equal primaries (snapshots advisory at most — contracts asserted semantically, never textually)
```

```typescript
// good — consumer switch staying exhaustive (downstream guard the probe protects)
function assertNever(x: never): never { throw new Error(`unreachable:${String(x)}`); }
type Order = "paid" | "shipped";
function label(o: Order): string {
  switch (o) {
    case "paid": return "P";
    case "shipped": return "S";
    default: return assertNever(o); // sink (widened inputs error HERE — see 07/3.2)
  }
}
console.log(label("shipped")); // S — exhaustiveness downstream (protected by the upstream probe — chain unbroken)
// bad — default-swallowing switches (default: return "unknown" — widened members misclassified silently for 11 days)
// fix — assertNever sinks everywhere (widening breaks consumers loudly — the 07 discipline as incident response)
```

**Common confusion** — "snapshots caught the change" — snapshots *recorded* the change (green after update — recording ≠ catching); assertions *judge* the change (red until deliberated). "one consumer audit suffices" — audits decay (new consumers monthly); probes persist (every merge re-audited automatically).

**Performance note** — `Equal` probes cost microseconds (incident cost: 11 days misclassified revenue + audit quarter — the cheapest-to-priciest ratio in this domain).

**Mentor note** — incident-review exhibit A for assertion-over-snapshot (show the green snapshot diff beside the red `Equal` diff — the room converts unanimously).

**Cross-links** — snapshot discipline → [3.1. Snapshot vs assertions](<../3. Type Tests in Practice/3.1. Testing generics and conditional types.md>); exhaustiveness sinks → [3.2. Exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>).

### 2) **`any`-cast mock hid a renamed required field across 40 call sites** (double silencing arity, production undefined)

**Definition** — the incident: `createOrder({ customerId, items })` renamed `customerId` → `customer` (domain language cleanup). The shared `mockOrders` double was `any`-typed (legacy convenience, lint-exempted "temporarily" 14 months prior). All 40 call-site tests passed (mock accepting both spellings — `any` swallowing arity). Production orders shipped `customerId: undefined` for 6 hours (validation defaulting missing customers to guest checkout — revenue unattributed, support queue flooded).

**What problem it solves / history** — `any` doubles (2.1 part 3's infection mechanics) decouple test outcomes from contract moves: renames, new required params, narrowed unions — all green, all broken. The rename itself was correct (domain language improved); the double made its migration unverifiable (40 sites "passing" with stale spellings).

**Modern guidance** — `typeof`-pin every shared double (2.1 — the rename breaking all 40 sites pre-merge, each fix mechanical); lint `no-explicit-any` on test/utils with zero exemptions (temporary exemptions fossilize — 1.3's fossil lesson restated); shared doubles reviewed as contracts (owner assigned, changes announced).

**Runnable example** — the rename that typed doubles catch (good vs bad, `tsc --strict`):

```typescript
// good — typeof-pinned double breaking on rename (40 reds pre-merge, each a one-line fix)
export {}; // module marker (consistent module scope across fences)
function createOrder(args: { customer: string; items: string[] }): string {
  return `order:${args.customer}:${args.items.length}`; // renamed (customerId → customer — domain cleanup)
}
const double: typeof createOrder = (args) => `mock:${args.customer}:${args.items.length}`; // pinned (stale spellings error HERE)
// double({ customerId: "c", items: [] }); // ❌ errors when uncommented (stale spelling — caught, not shipped)
console.log(double({ customer: "c", items: ["x"] })); // mock:c:1 — migration verified (all 40 sites fixed pre-merge)
// bad — any double (both spellings accepted — 40 greens, production undefined for 6 hours)
// fix — typeof pins on shared doubles (renames break tests first — migration as mechanical fixes, not incidents)
```

**Common confusion** — "shared doubles reduce maintenance" — *typed* shared doubles reduce maintenance (one pin, forty enforced fixes); *untyped* shared doubles defer maintenance to incidents (forty silent stalenesses). "lint exemptions for legacy doubles" — exemptions fossilize (14 months and counting — convert-then-fix per 1.3, never exempt-and-forget).

**Performance note** — `typeof` pins cost one query each (microseconds); the incident cost 6 hours unattributed revenue + support flood (exemption "convenience" priced accordingly).

**Mentor note** — exemption review quarterly: every `any`-exemption older than one quarter is a scheduled incident (convert it or own the postmortem in advance).

**Cross-links** — mock infection → [2.1. Typed mocks](<../2. Typed Test Doubles/2.1. Mocking functions with full type safety.md>); `any` mechanics → [2.1. any](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>).

### 3) **Missing `@ts-expect-error` probe let a rejected card shape back in** (validation bypass, fraud-review incident)

**Definition** — the incident: `parseCard` rejected 15-digit non-Luhn numbers (fraud rule, 2025). A 2026 "cleanup" widened the input to `string` (removing the branded `CardNumber` parameter — "simplification"). No negative probe existed (acceptance tests green on valid cards). Malformed numbers flowed to the processor for 3 days (soft-decline fees + fraud-review queue backlog — the bypass discovered by finance, not engineering).

**What problem it solves / history** — acceptance-only validation testing (happy paths green — rejections untested, see 4.1 part 2): every validation rule is a *rejection* rule (its value IS the no it says); untested nos evaporate under well-meaning loosenings. The branded parameter (04/3.2) encoded the rule; the missing probe failed to defend it.

**Modern guidance** — negative probe per validation branch (1.3 — the bypass breaking the build pre-merge); branded inputs for validated shapes (brand removal itself breaking probes — two-layer defense); finance-visible metrics on validation paths (decline rates alerting — observability beyond tests, see 20/production discipline).

**Runnable example** — the lock that would have held (good vs bad, `tsc --strict`):

```typescript
// good — branded input plus negative lock (two layers: type + probe)
export {}; // module marker (consistent module scope across fences)
declare const cardBrand: unique symbol;
type CardNumber = string & { readonly [cardBrand]: "CardNumber" };
function parseCard(raw: string): CardNumber | null {
  return /^\d{16}$/.test(raw) ? raw as CardNumber : null; // 16-digit rule (acceptance tested by behavior)
}
// lock illustration — in real test-d files: "@ts-expect-error — 15-digit shapes rejected" above parseCard("123456789012345" as CardNumber)
// (widening the parameter to string breaks the probe — bypass red pre-merge, never in production)
console.log(parseCard("1234567890123456") !== null); // true — acceptance proven (valid cards flow; rejections locked)
// bad — acceptance-only card tests (valid numbers green — 15-digit bypass re-admitted silently for 3 days)
// fix — negative probe per validation branch (every no a test — bypasses break builds, not queues)
```

**Common confusion** — "`as CardNumber` in tests defeats the brand" — test-time `as` constructs *fixtures* (known-valid values cast once — 15/parse discipline: fixtures parsed, not assumed); production paths never cast (factories validate). "fraud rules are backend concerns" — type-level rejection locks live wherever the signature lives (frontend or backend — the probe defends the contract, not the tier).

**Performance note** — negative probes cost one diagnostic each (microseconds); the incident cost 3 days processor fees + fraud-queue backlog (finance discovering engineering gaps — the most expensive notification channel).

**Mentor note** — validation PRs require the fraud/abuse lens in review ("which rejection does this loosen, and where is its probe?") — product-aware type review, not just shape review.

**Cross-links** — negative locks → [1.3. Negative tests](<../1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>); branded patterns → [3.2. Branded patterns](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>).

### 4) **Type tests excluded from CI passed locally, broke published types** (include-skipped test-d, shipped-any declarations)

**Definition** — the incident: `test-d/` matrices green locally (`tsd` passing on the author's machine), but CI ran `tsc --noEmit` over `src/` only (`tsconfig.include: ["src/**/*"]` with `test-d/` at root — include-skipped). A PR merged with a broken declaration (widened `Options` leaking `any` through a mapped type — 09/homomorphism loss). Published types resolved `any` for every consumer (downstream infection at scale — fixed by a patch release + apology post).

**What problem it solves / history** — check-vs-emit include mismatches (test files checked locally, skipped in CI — green-locally-red-nowhere): the gate that matters is CI's, not the laptop's. Include configuration (13/project scoping) silently scoping gates out of existence — the 13/7.1-adjacent class of config-vs-practice drift.

**Modern guidance** — `test-d/` inside the checked include (or a dedicated `tsconfig.test-d.json` extended + run in CI — explicit, reviewed); CI-vs-local parity checks (same commands locally and remotely — `package.json` scripts as the single source, never tribal flags); publish gates (`attw`/`publint` per 3.2) as backstops (broken declarations caught at pack even when test-d slips).

**Runnable example** — include parity (good vs bad, `tsc --strict`):

```typescript
// good — probes in the checked tree (CI evaluating what authors run)
export {}; // module marker (consistent module scope across fences)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
export interface Options { retries: number }
assertType<Equal<keyof Options, "retries">>(); // probe in-tree (include-covered — CI red on drift, like local)
// bad — test-d outside tsconfig.include (green laptop, blind CI — broken declarations shipping as patch surprises)
// fix — include parity (test-d in-tree or dedicated tsconfig run in CI — gates identical everywhere)
```

```jsonc
// good — script parity (one command, both places)
// package.json (labeled config doc — single source, never tribal flags):
// { "scripts": { "check": "tsc --noEmit && tsd && vitest run" } }
// CI: { "run": "npm run check" } (identical command — parity by construction, not by memory)
```

**Common confusion** — "CI mirrors local by default" — CI runs *scripts*, developers run *habits* (flags, file-scoped runs, IDE checks — parity requires shared scripts, not shared intentions). "packaging gates substitute for test-d" — gates backstop (catching slips); test-d prevents (catching drift at authoring) — both layers, different times. "include tweaks are trivial" — include tweaks scope *every gate* (one glob line enabling or deleting the whole static suite — review include diffs like gate diffs).

**Performance note** — include-parity costs nothing (configuration, not computation); the incident cost a patch release + apology post + downstream `any`-infection window (glob-line review neglected at six-figure cost).

**Mentor note** — onboarding task one: run `npm run check` locally and confirm it matches CI's command (parity verified by every newcomer — tribal flags die on contact with scripts).
