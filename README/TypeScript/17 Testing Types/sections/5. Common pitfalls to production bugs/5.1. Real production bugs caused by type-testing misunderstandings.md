## 5.1. Real production bugs caused by type-testing misunderstandings

The following are **synthetic failure cases**, not documented company incidents. They show how incomplete evidence can permit a defect to escape. The first, second and fourth cases use this domain's existing executed fixtures; the third adds a small branding test. No revenue loss, outage duration or number of affected services is claimed.

### 1) **Updating an expectation can approve the change under review**

Suppose an API promises an "a" | "b" result and a refactor widens its declaration to string. A test protecting that literal union should make the change visible. The [compile-time assertion fixture](<../1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) shows its precise return gate failing, while a broad string target still accepts the widened result. A consumer expecting the narrower union would also reject string; assignability is directional.

Updating a text snapshot to say string can approve that change. Updating an Equal expectation to string can do the same. The defect is unexamined acceptance of a changed contract, not an update mechanism unique to one kind of test. Review why the new result is intended, which consumers depend on the old result, and whether the compatibility policy permits it.

That fixture also proves the selected gate actually runs. It does not run a snapshot tool, and this case claims no measured snapshot failure. Choose a relation or displayed-text assertion according to the promised contract, as the [generic-test lesson](<../3. Type Tests in Practice/3.1. Testing generics and conditional types.md>) explains.

### 2) **A cast can hide a malformed mock reply from the compiler**

In the [actual typed-mock fixture](<../2. Typed Test Doubles/2.1. Mocking functions with full type safety.md>), the consumer expects a reply with name. Configuring displayName instead produces a checker failure. Casting that malformed reply as any makes checking pass; the runtime test still fails when the consumer tries to uppercase the missing name. The cast removed static evidence, not the runtime consequence.

A correctly typed but wrong name gives a different result: checking passes and the expected uppercase label fails. This demonstrates why a signature is useful but insufficient. Build fixtures with the intended checked types, keep important result assertions, and test real adapters for behavior the substitute does not model. Inspect an escape's purpose rather than assuming every any assertion is harmless or that no runtime test involving any can detect a defect.

### 3) **A branded input and its validating factory need different tests**

A brand can distinguish a validated identifier from a plain string in checked calls. The validation still depends on executable code. This deliberately small contract accepts strings consisting of T- followed by one or more ASCII digits. It proves no ticket existence, authorization or authenticity.

Use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. Create these files in an empty directory, omitting labels from JSON:

```typescript
// file: src/ticket.mts
declare const ticketBrand: unique symbol;
export type TicketId = string & { readonly [ticketBrand]: "TicketId" };
export function parseTicketId(raw: string): TicketId | null {
  return /^T-\d+$/.test(raw) ? raw as TicketId : null;
}
export function ticketLabel(id: TicketId): string { return `ticket:${id}`; }
```

```typescript
// file: test-d/ticket.test-d.mts
import { parseTicketId, ticketLabel } from "../src/ticket.mjs";
const parsed = parseTicketId("T-42");
if (parsed !== null) ticketLabel(parsed);
// @ts-expect-error -- a raw string has not passed the branded construction boundary.
ticketLabel("T-42");
```

```json
// file: tsconfig.check.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": [], "noEmit": true },
  "include": ["src/**/*.mts", "test-d/**/*.mts"]
}
```

```json
// file: tsconfig.build.json
{
  "extends": "./tsconfig.check.json",
  "compilerOptions": { "noEmit": false, "rootDir": "src", "outDir": "dist" },
  "include": ["src/**/*.mts"]
}
```

```javascript
// file: runtime.mjs
import assert from "node:assert/strict";
import { parseTicketId, ticketLabel } from "./dist/ticket.mjs";
const id = parseTicketId("T-42");
assert.notEqual(id, null);
assert.equal(ticketLabel(id), "ticket:T-42");
for (const raw of ["", "T-", "42", "T-x", "T-42x"]) {
  assert.equal(parseTicketId(raw), null);
}
console.log("ticket factory behavior passed");
```

Run `tsc -p tsconfig.check.json`, `tsc -p tsconfig.build.json` and `node runtime.mjs`. Both checks succeed and the consumer prints `ticket factory behavior passed`. The declared symbol is used only in a type; no missing runtime symbol is read.

Remove the directive temporarily: the raw call reports TS2345. Restore it, then widen ticketLabel's parameter to TicketId | string. The check now reports TS2578 because the static construction boundary admits a raw string. The factory's runtime tests still pass. Restore the parameter afterward.

For the opposite contrast, change only the factory regex to `/^.*$/`. The static suite still passes because the branded return annotation and rejected raw consumer call remain intact. The runtime malformed-input assertion fails. Restore the regex. A directive above a parser that already accepts string cannot assert that one malformed string literal is rejected at runtime.

Keep the assertion establishing the phantom brand localized after reviewed validation. A type assertion elsewhere can bypass that convention. The [branded-object owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) explains trusted construction and copying limits; [Josh Goldberg's branding article](https://www.learningtypescript.com/articles/branded-types) develops the domain-distinction trade-offs. This fixture tests the stated string-format rule, not a general authenticity system.

### 4) **A green command can omit the intended probe**

The [CI collector fixture](<../3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>) deliberately gives its type probe a false expectation. With test-d selected, check fails and the runtime suite passes. Removing test-d from include makes both commands green because that false expectation is no longer checked. The apparent repair removed evidence.

Compare the commands, selected files, compiler versions and installed inputs used locally and in CI. Sharing a script reduces accidental differences, but it cannot make different environments identical. For a package, preserve the [installed-artifact consumer tests](<../3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) as well. A declaration can resolve correctly while claiming the wrong semantic behavior; packaging tools do not infer every intended contract.

### 5) **Common confusion**

A string-format parser, a branded type and an expected-error probe are three different mechanisms. The parser executes validation, the brand records a trusted construction decision in types, and the negative probe checks that one raw typed call remains rejected. Breaking any one does not guarantee that every other test fails.

Likewise, a red test requires interpretation. A deliberately changed API may need revised expectations and compatibility work; an accidental change needs repair. Deleting the probe, changing its expected type or excluding its file can all make green without establishing the original promise.

### 6) **Performance note**

The brand and alias-only type reasoning erase; the parser's regex and runtime assertions still execute. The static suite also consumes compiler work. This lesson measures no per-probe cost, incident savings or production throughput. Choose useful contract boundaries and investigate actual suite cost if it becomes material.

### 7) **Mentor note**

Ask which command catches a widened ticketLabel input and which catches an overly permissive factory regex. Then show the excluded-probe case and ask what the green status actually establishes. A strong answer identifies each input and assertion without claiming the type checker proves runtime validation or a healthy package proves complete consumer compatibility.
