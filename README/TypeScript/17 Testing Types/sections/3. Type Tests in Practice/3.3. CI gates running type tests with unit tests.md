## 3.3. CI gates running type tests with unit tests

### 1) **Three-gate suite** (noEmit plus tsd-typecheck plus unit tests)

**Definition** — the *three gates*: (1) `tsc --noEmit` (whole-program check — inline pins, negative directives, matrices all evaluated); (2) `tsd` or `vitest --typecheck` (library-surface/packaging assertions — declarations + fluent probes); (3) unit tests (behavior — runners executing values). Separate CI jobs, separate signals: static drift vs surface drift vs logic bugs — each red gate routing to a different fix.

**What problem it solves / history** — single-gate pipelines (`npm test` running vitest only — types unchecked) ship red-statics green-behavior for weeks (drift compounding until a flag-day migration); or `tsc` lumped inside unit jobs (slow feedback — behavior results waiting on full-program checks). Split gates give fast behavior signals (seconds) alongside thorough static signals (tens of seconds) — each at its natural cadence.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), wire three jobs: `typecheck` (`tsc --noEmit`, blocking), `typetest` (`tsd` for packages / `vitest --typecheck` where fluent probes live, blocking), `unit` (vitest/jest, blocking). All three required for merge (no optional statics — optional gates are skipped gates). Cache `tsbuildinfo` per job (16/debugging discipline — no stale-incremental poisoning).

**Runnable example** — gate responsibilities, shown as labeled config docs plus a type fence (good vs bad):

```typescript
// good — typecheck gate covering inline pins (the cheapest gate catching the most drift)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
function discount(rate: number): number { return 1 - rate; }
assertType<Equal<ReturnType<typeof discount>, number>>(); // gate 1 (noEmit evaluates this — widening breaks the job)
console.log(discount(0.2)); // 0.8 — gate-1 coverage (inline pins live here, checked in seconds-to-tens-of-seconds)
// bad — typecheck optional (drift green for weeks — compounding until flag-day migrations)
// fix — three required gates (each red blocking merge — drift caught at authoring, always)
```

```jsonc
// good — pipeline shape (three jobs, three signals, all required)
// .github/workflows/check.yml (labeled config doc — jobs, not code):
// jobs: { typecheck: { run: "tsc --noEmit" }, typetest: { run: "tsd" }, unit: { run: "vitest run" } }
// required: [typecheck, typetest, unit] (branch protection — all three green to merge)
```

```typescript
// good — unit gate covering behavior (the gate statics cannot replace)
export function total(items: number[]): number { return items.reduce((a, b) => a + b, 0); }
console.log(total([1, 2, 3])); // 6 — gate-3 coverage (logic proven by execution — types prove shapes, tests prove values)
// bad — statics-only pipelines (shapes green, logic broken — types never executing values)
// fix — behavior gate beside static gates (three jobs — shapes AND values proven, every merge)
```

**Common confusion** — "typecheck subsumes typetest" — `noEmit` checks *sources*; `tsd`/packaging gates check *built declarations + resolution* (different artifacts — 3.2's gap restated). "unit covers types" — unit executes *values* (widened returns still behave — drift invisible); type gates evaluate *contracts* (drift loud). "three jobs cost too much CI" — jobs parallelize (wall-time ≈ slowest gate, not the sum — split gates often FASTER to green than lumped ones).

**Performance note** — `tsc --noEmit` dominates wall-time (tens of seconds — cacheable via `tsbuildinfo`, incremental-safe per 16/3.1); `tsd` adds seconds (test-d program); unit adds seconds (runner) — parallel jobs, total ≈ max, not sum.

**Mentor note** — onboarding demo: push a widened-return branch and watch gate 1 fail while gate 3 passes (the two-greens-one-red moment teaches gate separation permanently).

### 2) **Failure triage order** (type errors first, behavior second)

**Definition** — *triage order*: red gate 1 (typecheck) → fix statics first (contracts moved — behavior failures may be downstream symptoms); red gate 2 (typetest) → fix surface/packaging (declarations/resolution — consumer-facing); red gate 3 alone (unit, statics green) → fix logic (genuine behavior bug — shapes proven, values wrong). Order matters: fixing behavior under broken statics wastes cycles on symptoms.

**What problem it solves / history** — developers debugging unit failures for hours that were widened-type symptoms (mock shapes stale, narrowed branches unhandled — fixed in minutes once statics ran first). Triage order converts multi-hour symptom hunts into minute-level contract fixes (statics localize the move; behavior localizes the logic — each gate's failure read in its own terms).

**Modern guidance** — CI dashboards list gates in triage order (typecheck, typetest, unit — top-down reading = fix order); developer runbooks state it explicitly ("if typecheck is red, ignore unit failures until green"). Flaky-unit triage starts with floats (2.3 part 2) only after statics are green (order enforced, not suggested).

**Runnable example** — ordered reading (good vs bad, `tsc --strict`):

```typescript
// good — statics-first reading (contract move spotted before symptom hunting)
export interface Config { host: string; retries?: number }
function connect(cfg: Config): string { return `${cfg.host}:${cfg.retries ?? 3}`; }
console.log(connect({ host: "h" })); // h:3 — statics green here (failures elsewhere read as logic, confidently)
// bad — unit-first debugging under red statics (symptom hunts across suites — hours, ending at a one-line type move)
// fix — gate-1-green before gate-3-debug (order in the runbook — symptoms after contracts, always)
```

```typescript
// good — gate-3-alone means logic (shapes proven — the bug IS behavioral, hunt freely)
export function clamp(n: number, lo: number, hi: number): number {
  return Math.min(hi, Math.max(lo, n)); // logic bug hunt starts HERE (statics green — shapes excluded)
}
console.log(clamp(5, 0, 10)); // 5 — green statics licensing behavior hunts (exclusion by gate, not by hope)
// bad — assuming logic under red statics (hunting values while shapes lie — motion without progress)
// fix — triage order as habit (red 1 → contracts; red 2 → surface; red 3 alone → logic)
```

**Common confusion** — "all reds are equal" — reds differ by *layer* (contracts/surface/logic — different fixes, different owners); reading order encodes the layering. "triage order slows fixes" — order *shortens* fixes (symptom hunts skipped — net faster by hours per incident). "solo developers don't need runbooks" — solo developers need runbooks *most* (no colleague to suggest "did you check statics first?" at midnight).

**Performance note** — triage order costs nothing (reading sequence, not computation); symptom hunts under red statics cost hours (the most expensive activity in the pipeline — order deletes it).

**Mentor note** — postmortem template includes "triage order followed?" (process question first — order violations explain slow resolutions more often than technical difficulty).

### 3) **Baseline discipline for legacy** (error budgets shrinking, never growing)

**Definition** — *baselines* for legacy adoption: checked-in error budgets (`tsc` error counts per class, `tsd` known-failures, lint baselines — 13/4.1 triage + 16/2.1 tiers applied to test adoption): CI fails when counts *grow*, passes when they *hold-or-shrink*. Legacy code migrates incrementally (each PR shrinking the budget) without flag-day rewrites or permanently-red gates.

**What problem it solves / history** — legacy suites blocking type-test adoption ("200 errors — gates must stay optional until clean" — optional forever, drift compounding): baselines square the circle (gates required AND legacy tolerated — required-against-the-baseline, not required-clean). Each PR either shrinks the budget (progress) or holds it (neutral) — growth blocked (ratchet, not flag-day).

**Modern guidance** — record baselines per error class (nullability/any/variance — 13/4.1 classes, not raw totals — class-level budgets directing fixes); review budget-shrink PRs fast (reward progress); require justification for budget-touching PRs that merely hold (holding is allowed, growing is not). Sunset the baseline file when counts hit zero (ceremony — the ratchet's graduation).

**Runnable example** — ratchets in code and config (good vs bad, `tsc --strict`):

```typescript
// good — strict new code beside baselined legacy (ratchet: new files clean, legacy budgeted)
export function strictNew(input: string | null): string {
  return input ?? "default"; // strict (new code — nullability handled, no budget consumed)
}
console.log(strictNew(null)); // default — new-code bar (clean regardless of legacy budgets)
// bad — legacy budget cited for new debt ("the codebase has 200 errors, one more is fine" — ratchet inverted)
// fix — per-file strictness (new files excluded from baselines — budgets cover legacy ONLY)
```

```jsonc
// good — budget file shape (per-class counts, ratchet semantics)
// type-baseline.json (labeled config doc — CI compares, blocks growth):
// { "nullability": 41, "any": 87, "variance": 3, "updated": "2026-09-01" }
// CI rule: current[class] <= baseline[class] (grow → red; shrink → PR updates the file down)
```

```typescript
// good — graduation (budget zero → file deleted, gates fully clean)
export function graduated(x: string): string { return x.toUpperCase(); }
console.log(graduated("done")); // DONE — post-baseline normal (every PR clean — the ratchet's end state)
// bad — baselines kept at zero (dead files, confused newcomers — "what is this empty budget?")
// fix — delete at zero + celebrate (graduation PR — team signal that discipline compounded)
```

**Common confusion** — "baselines bless tech debt" — baselines *contain* debt (bounded, shrinking, visible) vs unbounded invisible debt (the alternative — baselines are honesty, not blessing). "per-class budgets overcomplicate" — raw totals hide class-shifts (nullability fixed, `any` grown — net zero, understanding negative); classes direct effort (fix the class, watch the number). "new code in baseline files" — new files never enter baselines (ratchet direction — legacy shrinks INTO the clean standard, clean never dilutes into legacy).

**Performance note** — baseline comparison is integer compares per class (milliseconds); the `tsc` run it gates dominates (unchanged — baselines add no check cost, only policy).

**Mentor note** — plot baseline counts per sprint (the downward slope IS the migration story — leadership-visible progress without flag-days; flat lines trigger staffing conversations, not surprise rewrites).
