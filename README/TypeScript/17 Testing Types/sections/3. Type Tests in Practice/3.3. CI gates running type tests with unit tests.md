## 3.3. CI gates running type tests with unit tests

A gate is a command whose failure the workflow treats as a failure. The useful question is which inputs it checks and which outcome it can establish. An ordinary compiler project can check source, test code and alias-only type assertions together. A special tool suite or an installed-package consumer adds a gate when it checks a distinct promised surface. A runtime suite supplies behavior evidence.

There is no mandatory number of tools or jobs. Make the commands explicit, select the intended files, preserve their exit status and prove that an intentional regression fails. This lesson runs a small local gate collector that can also be called by a continuous-integration (CI) runner. Hosted job scheduling and merge protection remain separate configuration.

### 1) **Run a complete local gate collector**

Start with the complete [typed-mock project](<../2. Typed Test Doubles/2.1. Mocking functions with full type safety.md>) and its four tests. Use Node 22.18.0, npm 11.13.0 and the pinned Vitest 5.0.5 / TypeScript 5.9.3 tool integration. The following extension was verified on Linux on 2026-10-17. Replace its manifest and tsconfig with these versions; omit file labels from JSON.

```json
// file: package.json
{
  "name": "typed-function-doubles",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "check": "tsc --noEmit",
    "test": "vitest run --maxWorkers=1",
    "verify": "node scripts/verify.mjs"
  },
  "devDependencies": { "@types/node": "22.18.0", "typescript": "5.9.3", "vitest": "5.0.5" }
}
```

```json
// file: tsconfig.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": ["node"] },
  "include": ["src/**/*.ts", "test/**/*.ts", "test-d/**/*.ts"]
}
```

```typescript
// file: test-d/gateway.test-d.ts
import type { fetchUser } from "../src/gateway.js";
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type GatewayResult = Expect<Equal<Awaited<ReturnType<typeof fetchUser>>, { name: string }>>;
```

```javascript
// file: scripts/verify.mjs
import { spawnSync } from "node:child_process";
let failed = false;
for (const script of ["check", "test"]) {
  const result = spawnSync("npm", ["run", script], { stdio: "inherit" });
  if (result.error) throw result.error;
  const status = result.status ?? 1;
  console.log(`${script} exit: ${status}`);
  if (status !== 0) failed = true;
}
process.exitCode = failed ? 1 : 0;
```

The collector runs both commands even if check fails, prints their statuses, and exits nonzero when either fails. It invokes the real tools; it does not infer success from a printed label. The alias-only test is selected by ordinary tsc and is not a Vitest runtime test. Confirm that selection with `npm run check -- --listFilesOnly`.

After the base project's initial installation has generated a lockfile, retain that reviewed file. Run:

```bash
npm exec --yes --package=npm@11.13.0 -- npm ci --include=dev
npm run verify
```

The collector prints `check exit: 0` and `test exit: 0` after four passing runtime tests, then exits 0. [npm ci](https://docs.npmjs.com/cli/v10/commands/npm-ci/) requires the lockfile and rejects dependency mismatches instead of refreshing it. Include dev explicitly because the compiler and test runner are development dependencies. A CI host must select the project directory and required Node version before these commands; this local verification does not configure a hosted workflow or branch protection.

### 2) **Prove each signal and diagnose its actual input**

Temporarily change the expected gateway shape in the type test to `{ displayName: string }`. Verify exits 1: check reports TS2344 and exit 2, while all four runtime tests pass. Restore it. Then change labelWith's return expression from `.name.toUpperCase()` to `.name`. Check still exits 0, while the uppercase behavior assertions fail and test exits 1. Combining both changes reports both failures and a final exit 1. Restore both files.

Now make only the type-test expectation wrong again, but remove test-d from include. Verify becomes green because the incorrect assertion is no longer selected. This is a selection defect, not a repaired type contract. Restore both the expectation and include. The [include reference](https://www.typescriptlang.org/tsconfig/include.html) explains how root file patterns participate in the project. Imported dependencies can still enter the program, so examine actual membership rather than inferring it from a folder name alone.

These results show why commands need clear responsibilities, but their failure sets can overlap. A compiler error and a runtime failure may share one cause; a green static suite may miss an untested declaration, an any escape or a runtime shape mismatch. Read the actual diagnostics and inputs before declaring an entire category of causes impossible. Investigate the failure that most directly explains the observed change; there is no universal rule to ignore all behavior failures until every static error is fixed.

For tool-specific checks, use the actual [tsd/Vitest type-testing commands](<../1. Type Assertions in Tests/1.2. tsd expect-type and type-testing libraries.md>). Their dedicated discovery and compiler integration differ from this alias-only suite. For a published package, build and pack before running the [installed-surface consumers](<./3.2. Testing declaration files and public API surface.md>) and [health checks](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.3. publint attw and package health checks.md>) against that artifact. Do not substitute a second source check for missing artifact evidence.

### 3) **Adopt gates without confusing a baseline with a proof**

An existing project may have known diagnostics while new work adopts stronger checks. A documented baseline can track the accepted exceptions, ownership and removal conditions. The ordinary tsc command does not automatically classify errors into a custom nullability/any/variance budget or tolerate selected diagnostics; such a policy needs an actual parser and comparison implementation, or an appropriate tool, with its own verification.

Counts alone do not establish that no new error appeared. For an illustrative baseline, suppose the two accepted diagnostics are A and B. If A is fixed and a new C appears, the total remains two. Even per-class counts can miss replacement within the same class. More useful comparison can retain diagnostic code, normalized path and relevant location/context, while handling line movement, duplicates and changed messages deliberately. Review the exceptions themselves alongside totals.

A simpler initial boundary can put selected migrated code in a clean checking project, provided its dependencies and omitted scope are clear. Excluding an old file is not a per-file strictness override, and importing it may bring it back into the program. Keep the uncovered contract visible and expand checks as work lands. A baseline and an intentionally narrower project are migration mechanisms; neither means the whole repository passes the new standard.

This fixture uses no diagnostic baseline. Its gate requires clean exits from both real commands. It also uses no incremental cache. Add project/tool-appropriate caching only after establishing the selected inputs and invalidation behavior; a cache filename is not a guarantee of correctness.

### 4) **Common confusion**

NoEmit controls emission, not whether a selected alias-only type test is checked. Conversely, normal Vitest runtime execution does not replace a compiler check. Test filenames, package scripts and tool discovery have different roles; verify them together.

A local nonzero command is useful only if the surrounding workflow preserves that failure. A CI job marked optional or a wrapper that discards its status changes the enforcement policy. Required merge checks must be configured and verified in the hosting system; none were created by this tutorial's local run.

### 5) **Performance note**

This collector runs its two steps sequentially and waits for both results. Parallel jobs may reduce some waiting but also repeat setup, compete for resources and depend on artifact ordering. This lesson measures no latency, dominant gate or speedup formula. Choose sequential, parallel or dependent work from actual inputs and feedback needs, and measure before adding caches or a large matrix.

### 6) **Mentor note**

Ask a learner to demonstrate a static-only failure, a behavior-only failure and the false green caused by excluding the probe. Have them show the command statuses and selected files. Then give them the A/B to B/C baseline example and ask why an unchanged count cannot prove that new work added no diagnostics.
