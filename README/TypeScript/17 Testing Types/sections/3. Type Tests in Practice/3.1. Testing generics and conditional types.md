## 3.1. Testing generics and conditional types

A generic type describes a family of results. Testing one instantiation does not test every legal input. Choose cases that expose the distinctions the helper promises: union distribution, an empty input, a readonly tuple, an unconstrained value or a rejected constraint. Explain each expected result before relying on a green compiler command.

The [conditional-type owner](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) teaches the mechanism in full. Here we build a selected regression suite for those promises. It uses **TypeScript 7.0.2**, verified 2026-10-17, with no runtime library or execution step.

### 1) **Build a compile-only matrix around meaningful differences**

Create these files in an empty directory. Omit the file label from JSON.

```typescript
// file: src/helpers.mts
export type NoString<T> = T extends string ? never : T;
export type WholeNoString<T> = [T] extends [string] ? never : T;
export type IsString<T> = T extends string ? true : false;
export type WholeIsString<T> = [T] extends [string] ? true : false;
export type Head<T> = T extends readonly [infer H, ...unknown[]] ? H : never;
export type First<T extends readonly unknown[]> = Head<T>;
export type Unpack<T> = T extends Promise<infer U> ? U : T;
```

```typescript
// file: test-d/helpers.test-d.mts
import type { NoString, WholeNoString, IsString, WholeIsString, Head, First, Unpack } from "../src/helpers.mjs";
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type IsAny<T> = 0 extends (1 & T) ? true : false;
type Cases = [
  Expect<Equal<NoString<"a">, never>>,
  Expect<Equal<NoString<1>, 1>>,
  Expect<Equal<NoString<"a" | 1>, 1>>,
  Expect<Equal<WholeNoString<"a" | 1>, "a" | 1>>,
  Expect<Equal<IsString<never>, never>>,
  Expect<Equal<WholeIsString<never>, true>>,
  Expect<Equal<Head<[1, 2]>, 1>>,
  Expect<Equal<Head<readonly [1, 2]>, 1>>,
  Expect<Equal<Head<[]>, never>>,
  Expect<Equal<Head<readonly number[]>, never>>,
  Expect<Equal<Head<[1] | [2]>, 1 | 2>>,
  Expect<Equal<Head<never>, never>>,
  Expect<Equal<Head<unknown>, never>>,
  Expect<Equal<Head<any>, unknown>>,
  Expect<Equal<keyof unknown, never>>,
  Expect<Equal<Unpack<Promise<number>>, number>>,
  Expect<Equal<Unpack<string>, string>>,
  Expect<IsAny<Unpack<any>>>,
  Expect<IsAny<Exclude<any, string>>>
];
// @ts-expect-error -- unknown does not satisfy First's array constraint.
type RejectedInput = First<unknown>;
```

```json
// file: tsconfig.check.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": [], "noEmit": true },
  "include": ["src/**/*.mts", "test-d/**/*.mts"]
}
```

Run `tsc -p tsconfig.check.json`. It succeeds without emitting JavaScript. Confirm selection with `tsc -p tsconfig.check.json --listFilesOnly`; both helpers.mts and helpers.test-d.mts participate. These are type aliases and an active constraint-rejection directive, not calls to an ambient function. The [assertion-mechanics lesson](<../1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) owns the comparison helper and its limitations.

NoString's naked type parameter distributes over the mixed union, removing only its string member. WholeNoString checks that union as a whole and retains it because the whole union does not fit string. These are different operations, so testing the mixed case matters more than repeating many single-number examples. The [primary conditional-type reference](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html) explains the underlying inference and distribution rules.

For a controlled regression, change NoString's implementation to `[T] extends [string] ? never : T`. The mixed-input expectation fails with TS2344. Restore it. Then remove readonly from Head's tuple pattern: the readonly tuple expectation fails. Restore it. Each failure connects a concrete implementation change to a promised result.

### 2) **Interpret boundary results instead of guessing them**

The Head pattern requires a tuple with at least one element. An arbitrary readonly number array might be empty, so it does not satisfy that pattern and the result is never. Supporting arbitrary arrays would require a different contract, such as an element type together with possible absence. It is not a reason to change the expected test result silently.

A naked conditional over never distributes over no members and produces never. Wrapping the checked side changes that behavior: WholeIsString<never> evaluates the whole assignability question and returns true. Do not generalize that every conditional with never must return never. The exact definition matters.

Unknown does not establish a nonempty tuple, so Head<unknown> is never; keyof unknown also has no known keys. Any has different behavior: this Head inference produces unknown, whereas Unpack<any> and Exclude<any, string> produce any. The IsAny predicate makes those latter expectations explicit. Exclude<any, string> is not never, and Unpack<any> does not invent a string-or-number union. These are compiler behaviors to verify, not results a team can choose by accepting a comment.

The First constraint also changes which inputs are legal. First<unknown> is rejected at the constraint; its negative probe tests that fact. Remove the directive temporarily to observe TS2344, then restore it. A useful matrix includes applicable legal boundaries and deliberate illegal inputs. It does not require an unconstrained never/unknown/any checklist for every generic regardless of its purpose.

[Axel Rauschmayer's type-testing chapter](https://exploringjs.com/ts/book/ch_testing-types.html) develops predicate/gate design and special-type cases. Reuse that reasoning while checking the behavior of the actual helper definition and compiler version in your project.

### 3) **Choose a type relation or a text snapshot for its intended contract**

A hover display is useful evidence about what an editor presents. A checked type relationship protects a different promise. Text can change because a tool displays an alias instead of expanding it, while a compatibility assertion still holds. Conversely, an assertion helper may distinguish two mutually assignable representations. Equal is not a universal semantic-equivalence oracle.

For example, `{ a: string } & { b: number }` and `{ a: string; b: number }` fit each other but the helper above distinguishes them. The [worked assertion owner](<../1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) tests that contrast. Use directional assignability when compatibility is the requirement, and a stricter comparison when its distinctions are intentional.

A diagnostic or documentation tool can reasonably test displayed text because presentation is part of its product. The [actual Twoslash fixture](<../../../16 Tooling Language Server and Ecosystem/sections/3. Debugging and Ecosystem/3.2. Playground twoslash and documentation snippets.md>) owns checked documentation queries and expected errors. This lesson does not run a snapshot tool. Review changes to expected types or text for their meaning; either kind of test can hide a regression if its expectation is blindly changed to match the new output.

### 4) **Common confusion**

Computing a type alias whose value is false is not automatically a failing test. Expect creates a constraint gate, and the selected project must actually check that file. A test-d name alone does neither. Likewise, alias-only predicates have no promised console output and need no ambient callable assertion.

Equal and IsAny are utilities with specific definitions. Read the assertion they make rather than treating a green gate as proof of every related property. For constrained helpers, distinguish an invalid instantiation from a valid instantiation whose result is never.

### 5) **Performance note**

The suite adds compiler work through its instantiations and comparison predicates. The cost depends on the helper and input structure; one probe is not necessarily one cheap conditional evaluation. This fixture measures no timing, universal per-case overhead or assertion-versus-snapshot speed comparison. Choose cases for explanatory value, then measure a real large suite before changing its layout or limiting useful coverage.

### 6) **Mentor note**

Ask the learner why the mixed union separates NoString from WholeNoString, why the readonly array differs from a nonempty tuple and why Head<any> differs from Unpack<any>. Have them demonstrate one regression and its failing gate, then restore it. A strong explanation identifies the specific type definition, selected input and tested relation instead of reciting a mandatory boundary quota.
