## 3.2. Testing declaration files and public API surface

A source-level test can bypass the files, entry points and declarations a consumer receives. A public-surface test imports the installed package through its supported names, under a stated compiler configuration. It checks selected promises about that resolved surface. Runtime tests then check what the installed JavaScript actually does.

Use **TypeScript 7.0.2**, **Node.js 20.20.2** and **npm 10.8.2**, verified 2026-10-17. First follow sections 1 and 2 of the complete [publishing fixture](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>). It builds calc-kit, packs its root and stats entry points, and installs the tarball into a separate consumer. Keep its producer, artifacts and consumer directories. No publication is needed.

### 1) **Probe declarations from an installed package**

Add these files beneath that consumer directory. Omit the file label from JSON.

```typescript
// file: consumer/test-d/esm.test-d.mts
import { add, format } from "calc-kit";
import { mean } from "calc-kit/stats";
// @ts-expect-error -- secret is not a named export of the package root.
import { secret } from "calc-kit";
// @ts-expect-error -- this physical file is not an exported package subpath.
import { secret as deepSecret } from "calc-kit/dist/secret.mjs";
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ESMContract = [
  Expect<Equal<Parameters<typeof add>, [number, number]>>,
  Expect<Equal<ReturnType<typeof add>, number>>,
  Expect<Equal<typeof format, "esm">>,
  Expect<Equal<Parameters<typeof mean>, [readonly number[]]>>,
  Expect<Equal<ReturnType<typeof mean>, number | undefined>>
];
```

```typescript
// file: consumer/test-d/cjs.test-d.cts
import api = require("calc-kit");
import stats = require("calc-kit/stats");
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type CJSContract = [
  Expect<Equal<Parameters<typeof api.add>, [number, number]>>,
  Expect<Equal<ReturnType<typeof api.add>, number>>,
  Expect<Equal<typeof api.format, "cjs">>,
  Expect<Equal<ReturnType<typeof stats.mean>, number | undefined>>
];
```

```json
// file: consumer/tsconfig.surface.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "moduleResolution": "nodenext", "types": [], "noEmit": true },
  "include": ["test-d/**/*.mts", "test-d/**/*.cts"]
}
```

From consumer, run `tsc -p tsconfig.surface.json`. It succeeds. Run it with `--listFilesOnly` to confirm that both static test files and the installed declarations participate. Add `--traceResolution` to inspect the selected .d.mts and .d.cts files for both entry points. The [module reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html#packagejson-exports) explains the conditions and extension substitution involved.

Remove each directive individually and rerun. The missing named export reports TS2305; the blocked subpath reports TS2307. Restore the directives. These are active checks. A missing module can also supply a diagnostic for the wrong reason, so retain positive imports and inspect the unsuppressed failures, as the [negative-test lesson](<../1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>) demonstrates.

Tuple parameter labels are not part of this helper's equality distinction. Rename add's left parameter to first and its body reference in both producer sources, rebuild, repack and install into a fresh consumer. These assertions still pass. Adding an optional third parameter instead changes Parameters<typeof add> and fails the strict tuple gates, even though the original two-argument consumers still check and run. Restore the original producer after each experiment.

### 2) **Check runtime and artifact boundaries separately**

The publishing owner already runs installed ESM and CommonJS consumers. Add this explicit ESM assertion file:

```javascript
// file: consumer/surface-runtime.mjs
import assert from "node:assert/strict";
import { add, format } from "calc-kit";
import { mean } from "calc-kit/stats";
assert.equal(format, "esm");
assert.equal(add(2, 3), 5);
assert.equal(mean([2, 4]), 3);
assert.equal(mean([]), undefined);
await assert.rejects(import("calc-kit/dist/secret.mjs"), { code: "ERR_PACKAGE_PATH_NOT_EXPORTED" });
console.log("installed surface behavior passed");
```

Run `node surface-runtime.mjs`. It prints `installed surface behavior passed`. The type suite remains compile-only; it does not execute the intentionally invalid imports. The blocked package subpath is an entry-point policy, not secrecy: the canonical tarball physically includes the secret file and a filesystem-relative import can still reach it.

For another controlled failure, expose that exact deep name in the producer's exports map:

```json
{
  "./dist/secret.mjs": { "types": "./dist/secret.d.mts", "default": "./dist/secret.mjs" }
}
```

This fragment adds a key inside exports; it does not replace package.json. Repack and install that variant in a fresh consumer. Its deep-import directive becomes unused (TS2578), and the runtime rejection assertion fails because the import now succeeds. Restoring the original metadata and repacking repairs that boundary. Use fresh consumers or deliberately replace the installed artifact; editing producer source alone cannot change a previously installed tarball.

The [package-health owner](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.3. publint attw and package health checks.md>) runs actual publint and attw commands on this package. Their configured analyses add evidence; they do not execute every consumer. Its missing-declaration example makes publint fail while the tested attw version prints an untyped-package message and exits 0. Its subtraction variant passes the compiler and both tools but fails the addition behavior assertion. Read the output, profile and tested artifact rather than interpreting an exit code as a universal proof.

This lesson's matrix covers the stated native compiler, Node runtime and entry points. Support for older compilers, bundlers, browser conditions or other configurations needs appropriate additional consumers. Package-name imports can still resolve source under project aliases or workspace mappings; inspect the actual resolved path before calling a test an installed-artifact test.

### 3) **Interpret baseline failures as evidence for a compatibility decision**

Keep useful released-consumer tests and contract assertions when checking a candidate artifact. A removed export, required new argument or widened return can break a consumer while the package's internal source remains valid. A strict representation assertion can also fail for a change that preserves a particular consumer use, as the optional-parameter experiment shows. Consumers that inspect Parameters may have different requirements from callers that only make a two-argument call.

A failing gate identifies a tested promise that changed. It does not enumerate every affected consumer or calculate the release version. [Semantic Versioning](https://semver.org/) distinguishes incompatible API changes from compatible additions and fixes. Apply that distinction to the declared support contract and actual consumer uses. A green sampled baseline can still miss a runtime bug or an unsupported configuration.

The [SemVer for TypeScript practical guide](https://www.semver-ts.org/3-practical-guidance.html) discusses public type surfaces, support commitments and compiler-dependent declaration compatibility. Use it as design guidance, with actual compiler tests for the combinations you promise. Review intentional changes, update expectations with an explanation and retain useful regression cases; do not equate every assertion edit with a major release or every green run with permission for a patch release.

### 4) **Common confusion**

Checking a package's own source, checking generated declarations and checking an installed tarball are different inputs. The compiler can read exports maps in a consumer program; tsc is not restricted to checking package source. Tool health checks and runtime assertions supplement that program rather than replacing it.

A negative internal-name probe protects one chosen boundary. It is not a requirement to list every private implementation symbol, and an export map does not reveal an API the author forgot to list. Define the public entry points and test representative supported uses alongside deliberate exclusions.

### 5) **Performance note**

Building, packing, installing and checking consumer programs adds real work. This fixture measures no universal number of seconds or fixed per-export cost. Reusing the same tarball across complementary checks keeps the input consistent; expanding the supported consumer matrix adds setup and maintenance. Choose that matrix from support commitments, not an invented timing budget.

### 6) **Mentor note**

Ask which files each command reads, why the hidden-name and deep-path probes differ, and why renaming a parameter label passes while adding an optional parameter fails the strict tuple assertion. Have the learner show the resolved declaration and one deliberately broken artifact. A sound answer distinguishes changed representation, compatibility for a particular use, packaging policy and runtime behavior.
