## 3.2. Testing declaration files and public API surface

### 1) **Public-surface probes** (import-from-package assertions pinning consumer names)

**Definition** — *surface probes* import from the package name (not relative paths) and assert the visible contract: `import { createApp } from "my-lib"` + `assertType<Equal<Parameters<typeof createApp>, [...]>>()` + `@ts-expect-error` on removed/internal names. They test what consumers can *name* (exports), with what *signatures* (parameters/returns), and what stays *hidden* (internals unimportable).

**What problem it solves / history** — packages break consumers without breaking themselves: an export renamed (unit tests updated alongside — green), a return widened (behavior tests indifferent), an internal helper accidentally exported (no test noticing the surface grew). Surface probes fail on all three (import errors, identity mismatches, unexpected-name availability) — consumer-equivalent verification without publishing.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), mirror the 12/3.3 publishing checklist with probes: every `exports`-map subpath gets an import probe; every public signature gets an `Equal` probe; every internal module gets a negative probe (unimportable from the package root). Run probes against built declarations (`tsc -b` output), not sources (declaration drift is the regression class).

**Runnable example** — consumer-view assertions (good vs bad, `tsc --strict`):

```typescript
// good — export-name probes (renames break HERE, pointing at the consumer view)
// consumer view simulated: the public barrel re-exports exactly the contract
export function createApp(name: string): { name: string } { return { name }; }
export type App = ReturnType<typeof createApp>;
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
assertType<Equal<Parameters<typeof createApp>, [name: string]>>(); // signature pinned (param renames break here)
assertType<Equal<App, { name: string }>>(); // return shape pinned (widening breaks here)
console.log(createApp("shop").name); // shop — surface probed (names + signatures, consumer-equivalent)
// bad — source-internal tests only (exports renamed freely — consumers discovering renames at upgrade)
// fix — barrel-level probes (import-from-package view tested — the consumer's compiler as the test oracle)
```

```typescript
// good — internal stays internal (unexported helpers unnameable — surface growth detected)
// internal helper (NOT exported from the barrel — negative probe below locks that in)
function hashInternal(s: string): string { return `h:${s}`; }
export function token(s: string): string { return hashInternal(s).toUpperCase(); }
// lock illustration — in real test-d files: import { hashInternal } from "my-lib" must ERROR (not exported)
// "@ts-expect-error — hashInternal is internal" above the import line (surface growth breaks the probe)
console.log(token("ab")); // H:AB — internals hidden (helpers used, not exported — growth intentional or not at all)
// bad — accidental exports unnoticed (helper exported "temporarily", consumers depending, removal now breaking)
// fix — negative probes per internal module (surface minimal by default — growth a deliberate PR)
```

**Common confusion** — "unit tests cover the surface" — unit tests import *relatively* (`../src/app` — internals reachable); consumers import *by package name* (barrel-filtered) — different views, different breakage. "probing against sources suffices" — declaration *emit* transforms the surface (stripped types, generated `.d.ts` — 12/3.1 derive-don't-declare); probe the *built* declarations (the artifact consumers compile against). "surface probes duplicate API docs" — docs describe intent; probes enforce names (docs rot silently, probes rot loudly).

**Performance note** — surface probes add one program over built declarations (seconds — CI scale); run them in the packaging job (after `tsc -b`, before `publint` — 16/2.3 gates adjacent, failures routed identically).

**Mentor note** — semver question per surface change: probe red + intentional → major (or documented minor, per policy); probe red + accidental → revert (the probe did its job — thank it in the PR).

### 2) **`attw`/publint as type tests** (packaging assertions beside unit assertions)

**Definition** — `attw` (are-the-types-wrong) resolves every `exports`-map condition per importer kind (node10/node16/bundler — 13/3.1 pairing matrix) and reports unresolvable/mismatched *types*; `publint` lints packaging coherence (missing `types` conditions, file inclusion, dual-shape hazards). Both are *type tests at the packaging layer*: green means consumers resolve declarations, red means shipped-any (the 5.1 unpublished-types incident class).

**What problem it solves / history** — `exports` mapping JS without `types` (or with wrong conditions) ships implicit-`any` to every consumer (their `tsc` resolving no declarations — downstream `any`-infection at scale, discovered post-publish). Unit tests never catch it (they run pre-pack); `tsc` never catches it (it checks sources, not the packed layout). `attw`+`publint` close the exact gap: consumer-equivalent resolution, verified pre-publish.

**Modern guidance** — run `attw --pack` + `publint` as blocking CI gates on the packed tarball (not the working tree — 12/3.3 triple-pipeline discipline); treat their failures like red type tests (same severity, same triage — see 3.3). Keep the 13/3.1 pairing table (module/moduleResolution per runtime) consistent with the tested matrix (untested pairings unshipped).

**Runnable example** — the resolution contract, shown as source-level equivalents (good vs bad, `tsc --strict`):

```typescript
// good — dual-shape coherence (the invariant attw verifies: both shapes serve identical types)
export interface Widget { id: string }
export function makeWidget(id: string): Widget { return { id }; }
// packaging rule illustrated: exports { ".": { types: "./dist/index.d.ts", import: "./dist/index.mjs", require: "./dist/index.cjs" } }
// (import-condition AND require-condition resolve declarations — attw checks every condition pair; tsc alone checks none)
console.log(makeWidget("w1").id); // w1 — shape served identically (both importers see Widget, never any)
// bad — types condition missing on one shape (CJS consumers resolving any — infection at scale, discovered post-publish)
// fix — attw --pack gate (every condition pair resolving declarations — verified, not hoped)
```

```typescript
// good — subpath coverage (every exports-map key probed — 12/3.3 gate restated as tests)
export const version = "1.0.0";
export function ping(): string { return "pong"; }
// subpath probes (test-d importing "my-lib/feature" per exports key — uncovered keys error at the probe)
console.log(ping()); // pong — subpaths enumerated (map keys == probe files — parity enforced in review)
// bad — root-only probes (subpath types broken — feature-import consumers resolving any)
// fix — probe per subpath (exports keys mirrored in test-d — the 3.1 matrix discipline at packaging layer)
```

**Common confusion** — "`tsc` passing means packaging is fine" — `tsc` checks *source programs* (no exports map involved); `attw` checks *packed resolution* (conditions × importers) — different artifacts, different oracles. "publint duplicates attw" — publint lints *coherence* (files/conditions/shapes); attw verifies *resolution* (importer-equivalent type loading) — complementary, both blocking. "gates only matter at publish" — gates run per PR (pack + check in CI — regressions caught at authoring, not at release).

**Performance note** — pack + attw + publint costs seconds per run (tarball I/O + resolution matrix — packaging-job scale); run on the release job AND on PRs touching `package.json`/`exports` (targeted, not every push — cost proportional to packaging-change frequency).

**Mentor note** — packaging-change PRs (exports, files, typesVersions) require the attw/publint logs pasted in the PR (evidence, not claims — same bar as test output).

### 3) **Breaking-change detection** (assertion diffs as semver signals)

**Definition** — *type-break detection*: `tsc` + `tsd`/surface probes run against the *previous* release's test-d files (or a checked-in API report — `attw`-style baselines): red assertions enumerate exactly which consumer-visible types moved (renames, widenings, new required params, removed exports). The diff *is* the semver verdict (any consumer-visible move → major, per policy).

**What problem it solves / history** — "minor" releases breaking consumers (renamed option, widened return collapsing exhaustiveness downstream — discovered at `npm update`, not at PR): behavior semver (tests green) diverging from type semver (contracts moved). Break detection unifies them: type moves fail the build with the moved name attached (reviewers deciding major-vs-revert with evidence, not memory).

**Modern guidance** — keep previous-release test-d files (or an `api-report.md` baseline — Microsoft's api-extractor pattern) in CI; diff on every PR (red = consumer-visible move — deliberate + major, or accidental + revert). Exempt explicitly-versioned beta tags (breaking allowed, still listed — transparency without blocking).

**Runnable example** — moves detected, verdicts routed (good vs bad, `tsc --strict`):

```typescript
// good — baseline pins the released contract (moves break HERE with the moved name attached)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
// baseline (v1 released): connect(host: string, port?: number)
function connect(host: string, port?: number): string { return `${host}:${port ?? 80}`; }
assertType<Equal<Parameters<typeof connect>, [host: string, port?: number]>>(); // baseline pinned (new required param breaks here → major-or-revert)
console.log(connect("h")); // h:80 — released contract enforced (consumer-visible moves loud by construction)
// bad — no baseline (port made required silently — consumers omitting it breaking at THEIR upgrade, not at OUR PR)
// fix — baseline assertions per public signature (every consumer-visible move a deliberate semver decision)
```

```typescript
// good — removal detected (deleted exports error at the probe — the removal listed, not silent)
export function kept(): string { return "kept"; }
// baseline probe for removed("x") would error: Cannot find name 'removed' (removal visible — major verdict, changelog entry)
// lock illustration — in real baselines: removed names stay listed until the major ships (history, not amnesia)
console.log(kept()); // kept — removals enumerated (each deletion a named, versioned decision)
// bad — silent removals (export deleted, no probe — consumers discovering at upgrade with a cryptic module error)
// fix — baseline retention (removed names error loudly — deletion diffs reviewed like feature diffs)
```

**Common confusion** — "semver checkers replace probes" — tools (api-extractor, attw diffs) *report* moves; probes *block* them (report without a gate is a newsletter). "all moves are major" — policy decides (additive optional params often minor; removals/narrowings usually major — the probe surfaces the move, policy sets the verdict). "baselines freeze design" — baselines freeze *unintentional* moves (intentional moves update the baseline in the same major PR — evolution with evidence).

**Performance note** — baseline checking reuses the type-test program (one extra include set — seconds); api-report diffs are text compares (milliseconds — cheapest gate in the pipeline).

**Mentor note** — release checklist: baseline green (no moves) → patch/minor; baseline red + reviewed moves → major with changelog entries per moved name (mechanical, auditable).
