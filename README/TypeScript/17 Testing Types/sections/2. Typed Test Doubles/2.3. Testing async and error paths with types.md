## 2.3. Testing async and error paths with types

An async test must own the operation's completion and assert the relevant outcome. TypeScript can check a fulfilled value's type or a Result union's branches, but Promise<T> has no rejection-type parameter. Testing an error class is a runtime assertion, not a static guarantee about everything the operation can reject with.

Use the complete project from [typed mocking](<./2.1. Mocking functions with full type safety.md>): Node 22.18.0, Vitest 5.0.5, TypeScript 5.9.3 for this compatible tool integration, its manifest, tsconfig and commands. Add the files below. Run `npm run check` and `npm run test`. Verified 2026-10-17. These are local function and timer tests, without network requests.

### 1) **Assert rejection behavior and Result branches**

```typescript
// file: src/outcomes.ts
export class ValidationError extends Error {
  constructor(message: string) { super(message); this.name = "ValidationError"; }
}
export async function save(input: string): Promise<string> {
  if (input === "") throw new ValidationError("empty");
  return `saved:${input}`;
}
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
export function divide(a: number, b: number): Result<number, "zero"> {
  return b === 0 ? { ok: false, error: "zero" } : { ok: true, value: a / b };
}
```

```typescript
// file: test/outcomes.test.ts
import { expect, test, vi } from "vitest";
import { divide, save, ValidationError } from "../src/outcomes.js";

test("save resolves or rejects with the specified runtime error class", async () => {
  await expect(save("x")).resolves.toBe("saved:x");
  await expect(save("")).rejects.toThrow(ValidationError);
});

test("Promise's fulfilled type does not constrain rejection reasons", async () => {
  const load = vi.fn<() => Promise<number>>().mockRejectedValue("offline");
  await expect(load()).rejects.toBe("offline");
});

test("Result branches expose their own payload types", () => {
  const success = divide(1, 2);
  if (!success.ok) throw new Error("expected success");
  const value: number = success.value;
  expect(value).toBe(0.5);
  const failure = divide(1, 0);
  if (failure.ok) throw new Error("expected zero error");
  const code: "zero" = failure.error;
  expect(code).toBe("zero");
  // failure.value; // Checking rejects access to the success-only field.
});
```

The class assertion fails if save throws an unrelated TypeError. It does not also assert the message; add a message or structured-field assertion when that detail is part of the contract. A bare rejection assertion can be enough when only rejection matters. Select class, identity, message or fields for the promise being tested rather than banning an assertion spelling universally.

The mock's rejected string is accepted by its configuration API and observed at runtime, despite its Promise<number> signature. Treat caught reasons as unknown until narrowed. For Result, explicit branch guards both reject an unexpected outcome and make the payload types available. An error-valued result and a rejected promise are different outcomes. The [error-as-value owner](<../../../15 Strictness Errors and Validation/sections/2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>) owns that design choice.

### 2) **Make test completion explicit**

Return or await promises whose results belong to the test. The [Vitest async guide](https://vitest.dev/guide/learn/async) explains how the returned test promise determines completion. The assertions above are awaited, so failures propagate into that promise.

For a deliberate runner failure, remove await from the save rejection assertion and rerun test. In this pinned version, Vitest reports the unawaited assertion and fails the test even though save rejects as expected. Restore await afterward. Do not infer that every detached task is automatically detected in every runner or that every missing await silently passes.

A floating operation may finish after its test, and an unhandled rejection may be reported separately by the runner. TypeScript accepts many discarded promises; a compiler check does not enforce general completion ownership. The [executed type-aware lint lesson](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>) demonstrates no-floating-promises with actual rule configuration. Its ignoreVoid option matters: writing void does not attach a rejection handler or wait for completion. Reuse that configuration deliberately for test files, with the correct selected files and compiler integration.

Awaiting does not require independent operations to run one at a time. Start work together and await its combined completion when concurrency is part of the scenario. Keep rejection handling, cleanup and ownership explicit rather than using detached work as accidental parallelism.

### 3) **Drive actual timers and cooperative cancellation**

The following helper waits for a short timer unless its supplied signal aborts. It propagates that signal's reason. It rejects immediately for pre-aborted input and clears its timer and listener on cancellation. On completion it removes the listener. This implements cancellation for this timer operation; a signal does not automatically stop arbitrary work.

```typescript
// file: src/wait.ts
export function wait(ms: number, signal: AbortSignal): Promise<void> {
  if (signal.aborted) return Promise.reject(signal.reason);
  return new Promise<void>((resolve, reject) => {
    const onAbort = (): void => {
      clearTimeout(timer);
      signal.removeEventListener("abort", onAbort);
      reject(signal.reason);
    };
    const timer = setTimeout(() => {
      signal.removeEventListener("abort", onAbort);
      resolve();
    }, ms);
    signal.addEventListener("abort", onAbort, { once: true });
  });
}
```

```typescript
// file: test/wait.test.ts
import { afterEach, beforeEach, expect, test, vi } from "vitest";
import { wait } from "../src/wait.js";

beforeEach(() => { vi.useFakeTimers(); });
afterEach(() => { vi.clearAllTimers(); vi.useRealTimers(); });

test("completes at the scheduled boundary", async () => {
  const controller = new AbortController();
  const remove = vi.spyOn(controller.signal, "removeEventListener");
  try {
    let completed = false;
    const pending = wait(50, controller.signal).then(() => { completed = true; });
    await vi.advanceTimersByTimeAsync(49);
    expect(completed).toBe(false);
    await vi.advanceTimersByTimeAsync(1);
    await pending;
    expect(completed).toBe(true);
    expect(vi.getTimerCount()).toBe(0);
    expect(remove).toHaveBeenCalledWith("abort", expect.any(Function));
  } finally { remove.mockRestore(); }
});

test("pre-aborted input schedules no timer", async () => {
  const controller = new AbortController();
  const reason = new Error("already cancelled");
  controller.abort(reason);
  await expect(wait(50, controller.signal)).rejects.toBe(reason);
  expect(vi.getTimerCount()).toBe(0);
});

test("abort during the wait rejects and releases the timer", async () => {
  const controller = new AbortController();
  const reason = new Error("cancelled during wait");
  const pending = wait(50, controller.signal);
  const rejection = expect(pending).rejects.toBe(reason);
  expect(vi.getTimerCount()).toBe(1);
  controller.abort(reason);
  await rejection;
  expect(vi.getTimerCount()).toBe(0);
});
```

With the four base-project tests, this extension passes ten tests. It controls the timer boundary at 49 and 50 milliseconds, asserts pre-abort and in-flight abort separately, and restores real timers after each test. It does not sleep for the scheduled duration. If you also added the previous spies/fakes lesson, those four extra tests remain independent.

Delete clearTimeout from onAbort and rerun: rejection still occurs, but the timer-count assertion fails. Restore it. Move the timer from ms to ms + 1 and the completion-boundary assertion fails. Fake timers help expose these local scheduling and resource mistakes. They do not certify real network cancellation, host scheduling latency or every possible race. See [Vitest's timer API](https://vitest.dev/api/vi#fake-timers) and the [tested Node AbortController reference](https://nodejs.org/download/release/v22.18.0/docs/api/globals.html#class-abortcontroller) for the underlying operations.

### 4) **Common confusion**

A Promise<number> may reject with a string, an Error or another value. A Result<number, E> models E in its returned value, but its implementation can still throw unexpectedly. Tests and callers need the correct boundary for each outcome.

Cancelling a Promise.race winner does not inherently cancel another operation. Here cancellation works because wait subscribes to the signal and releases its own resource. An injected now function also does not advance scheduled timers; choose a clock seam for reading time and a timer facility for scheduling behavior.

### 5) **Performance note**

Fake timers avoid the configured wall-clock delay for these tests, while advancing the virtual clock still runs callbacks and associated promise work. Large timer queues and loops consume real CPU and memory. This fixture measures no suite-speed ratio or fixed execution-time bound. Clear resources and restore mocked globals; use real integration tests when actual scheduler or I/O behavior is the property under review.

### 6) **Mentor note**

Ask why a rejected string checks under Promise<number>, which returned promise keeps each test alive and what releases the pending timer on abort. Have the learner remove cleanup and observe the specific failed assertion. A good explanation connects completion, rejection ownership and cleanup without claiming that typing or fake time makes every race impossible.
