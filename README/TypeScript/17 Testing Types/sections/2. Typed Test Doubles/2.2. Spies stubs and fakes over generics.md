## 2.2. Spies stubs and fakes over generics

A substitute's role explains what the test learns. A stub supplies selected answers, a spy records interactions, and a fake implements a useful slice of behavior, often with in-memory state. Framework names overlap with these roles: a Vitest spy can initially call the real method and later replace its implementation. A type annotation describes permitted calls and values; it does not prove behavioral fidelity.

This lesson extends the complete project in [typed mocking](<./2.1. Mocking functions with full type safety.md>). Keep its package.json, tsconfig.json and tests, using Node 22.18.0, Vitest 5.0.5 and the compatible TypeScript 5.9.3 checking integration. Add the files below and run `npm run check` and `npm run test`. Verified 2026-10-17. No external service is needed.

### 1) **Observe, override and restore an actual spy**

```typescript
// file: test/spy.test.ts
import { expect, test, vi } from "vitest";

test("call-through, replacement, clearing and restoration differ", () => {
  const account = {
    balance: 0,
    charge(amount: number): number { this.balance += amount; return this.balance; },
  };
  const original = account.charge;
  const spy = vi.spyOn(account, "charge");
  try {
    expect(account.charge(4)).toBe(4);
    expect(account.balance).toBe(4);
    expect(spy.mock.calls).toEqual([[4]]);
    spy.mockImplementation(() => 99);
    expect(account.charge(8)).toBe(99);
    expect(account.balance).toBe(4);
    spy.mockClear();
    expect(spy.mock.calls).toEqual([]);
    expect(account.charge(2)).toBe(99);
    expect(account.balance).toBe(4);
    // account.charge("4"); // Checking rejects a string amount.
  } finally {
    spy.mockRestore();
  }
  expect(account.charge).toBe(original);
  expect(account.charge(1)).toBe(5);
});
```

The initial call preserves both the receiver and the real balance update. After mockImplementation, the spy returns 99 without charging. mockClear removes recorded history and keeps that replacement. mockRestore restores the object's original method; the final call charges again. These are asserted outcomes, not merely printed call counts. The [mock API reference](https://vitest.dev/api/mock.html) documents the distinct operations.

Call-through also preserves real side effects. A spy on a payment adapter can still submit a payment unless you replace the implementation or use a controlled environment. Choose observation when the real behavior is appropriate for this test. Choose a substitute when the scenario requires controlled behavior. Neither is the default for every collaborator.

### 2) **Program answers with the intended key coverage**

```typescript
// file: test/stub.test.ts
import { expect, test } from "vitest";

test("finite answers are complete; open lookups need missing-key behavior", () => {
  type Region = "eu" | "us" | "ap";
  const rates: Record<Region, number> = { eu: 0.2, us: 0.08, ap: 0.1 };
  const rate = (region: Region): number => rates[region];
  expect(rate("eu")).toBe(0.2);
  expect(rate("ap")).toBe(0.1);
  const partial = new Map<Region, number>([["eu", 0.2]]);
  expect(partial.get("us")).toBeUndefined();
  const lookup = (key: string): number => new Map([["a", 1]]).get(key) ?? -1;
  expect(lookup("a")).toBe(1);
  expect(lookup("missing")).toBe(-1);
});
```

Remove the ap property from rates and run check: the finite Record requires that key. The Map accepts a partial set of Region keys, so its get result can be undefined. Its generic key type constrains admissible keys; it does not require an entry for each member. Choose a fallback, an explicit missing result or a throw according to the scenario, then assert that choice. The [collection selection lesson](<../../../10 Arrays Tuples and Collections/sections/3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>) owns the broader comparison.

Keep programmed answers close to the scenario they explain. A shared factory is reasonable when its defaults and isolation are explicit; a global mutable table can make unrelated tests affect one another. Sharing is a design choice with observable consequences, not an automatic defect.

### 3) **Give a generic fake an explicit behavioral contract**

Consider a store whose result distinguishes an absent key from a present value, including undefined. put replaces the existing value for a key, and each new store begins empty. This fake stores object references; it does not promise cloning or database transaction behavior.

```typescript
// file: src/store.ts
export type Lookup<T> = { found: false } | { found: true; value: T };
export interface Store<T> {
  get(id: string): Lookup<T>;
  put(id: string, value: T): void;
}
export class MemoryStore<T> implements Store<T> {
  private rows = new Map<string, { value: T }>();
  get(id: string): Lookup<T> {
    const entry = this.rows.get(id);
    return entry === undefined ? { found: false } : { found: true, value: entry.value };
  }
  put(id: string, value: T): void { this.rows.set(id, { value }); }
}
```

Wrapping each stored value preserves the difference between no Map entry and a stored undefined. The class-level T fixes one payload type per store instance. A Store<string> cannot accept a number merely because another instance stores numbers.

```typescript
// file: test/store.test.ts
import { expect, test } from "vitest";
import { MemoryStore, type Store } from "../src/store.js";

function storeContract(name: string, make: <T>() => Store<T>): void {
  test(`${name}: missing, put and replacement`, () => {
    const store = make<string>();
    expect(store.get("a")).toEqual({ found: false });
    store.put("a", "first");
    expect(store.get("a")).toEqual({ found: true, value: "first" });
    store.put("a", "second");
    expect(store.get("a")).toEqual({ found: true, value: "second" });
    expect(make<string>().get("a")).toEqual({ found: false });
    const numbers = make<number>();
    numbers.put("n", 7);
    expect(numbers.get("n")).toEqual({ found: true, value: 7 });
    // store.put("a", 123); // Checking rejects a number in this string store.
  });
  test(`${name}: present undefined differs from absent`, () => {
    const store = make<undefined>();
    store.put("a", undefined);
    expect(store.get("a")).toEqual({ found: true, value: undefined });
    expect(store.get("missing")).toEqual({ found: false });
  });
}
storeContract("memory", <T>() => new MemoryStore<T>());
```

The extended project now passes eight runtime tests and check. To expose the limit of implements, replace MemoryStore.get's body with `return { found: false };`. Check still succeeds: that is a legal Lookup<T>. The contract tests fail because put is no longer observable through get. Restore the implementation afterward.

A shared contract suite can check the same stated properties against another adapter. This run covers only the memory fake. A production-backed adapter needs its own setup and actual execution, and extra properties for its promised semantics. Passing a finite contract suite does not make divergence impossible. [Fowler's original article](https://martinfowler.com/articles/mocksArentStubs.html) helps distinguish state verification from interaction verification; here the store tests deliberately assert state through the interface.

### 4) **Common confusion**

A spy is not guaranteed to preserve behavior after configuration, and recording a call does not prove that the called operation produced the required outcome. In the account test, the replacement records calls without changing the balance. Assert the outcome the consumer needs as well as an interaction when that interaction is part of the contract.

A generic fake is checked for the chosen signatures, not automatically for persistence, concurrency, ordering or missing-value semantics. Define those promises before deciding what a useful contract suite should assert. Even undefined can be a valid T, which is why this store represents presence separately.

### 5) **Performance note**

Spies retain call history, and the memory store retains its rows for the lifetime of each instance. Fresh instances bound this fixture's state and keep tests independent. This example contains no timing or allocation benchmark and establishes no nanosecond overhead or universal constant-time bound for Map operations. A local fake avoids this fixture's need for external I/O; it does not measure the speed of a real adapter.

### 6) **Mentor note**

Ask what changes after clear versus restore, why a partially filled Map still checks and why the broken get implementation satisfies Store<T>. Then ask which extra properties a real database adapter would promise. A useful review identifies evidence already supplied and behavior still untested, rather than treating a compatible interface as a proof of equivalence.
