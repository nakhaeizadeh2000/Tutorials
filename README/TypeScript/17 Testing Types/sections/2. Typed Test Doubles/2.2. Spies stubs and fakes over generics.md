## 2.2. Spies stubs and fakes over generics

### 1) **Spies observing without replacing** (calls recorded, implementation kept)

**Definition** — a *spy* wraps the real implementation: same signature, same behavior, plus a recorded call list (`calls: Parameters<T>[]`). Unlike mocks (replacing behavior), spies *observe* it — assertions target interaction (called with what, how often, in which order) while behavior stays production-identical.

**What problem it solves / history** — reimplementing collaborators per test (hand-written behavior copies drifting from production logic) tests the copy, not the integration: green suites, broken wiring. Spies keep the real implementation (no behavior copy to drift) and assert only the interaction layer (arguments, counts, ordering) — the seam's contract without its reimplementation.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS; vitest 3.x), prefer `vi.spyOn(obj, "method")` (implementation preserved, types inferred from the object) over `vi.fn()` reimplementations; assert on `calls` arrays with typed matchers (argument tuples, not serialized strings). Spy *boundaries* (ports charged, emails queued), never pure computation (assert returns, not interactions).

**Runnable example** — spies keeping behavior, recording interaction (good vs bad, `tsc --strict`):

```typescript
// good — spy preserving behavior (real logic runs, calls recorded with types)
export {}; // module marker (top-level await below needs module scope)
type Charge = (amount: number, currency: "usd" | "eur") => string;
const realCharge: Charge = (amount, currency) => `${currency}:${amount}`;
const calls: Parameters<Charge>[] = [];
const spyCharge: Charge = (amount, currency) => { calls.push([amount, currency]); return realCharge(amount, currency); };
console.log(spyCharge(10, "usd")); // usd:10 — behavior identical (real impl runs); interaction recorded (args typed)
console.log(calls.length); // 1 — call count asserted (interaction layer tested, behavior un-duplicated)
// bad — reimplemented mock behavior (copy drifting from realCharge — suite tests the copy)
// fix — spy wrapping (real impl + recorded calls — no behavior copy to drift)
```

```typescript
// good — ordering assertions on typed tuples (sequence contracts pinned)
export {}; // module marker (consistent module scope across fences)
type Step = (name: string) => void;
const order: string[] = [];
const step: Step = (name) => { order.push(name); };
step("migrate"); step("seed"); step("verify");
console.log(order.join(",")); // migrate,seed,verify — ordering asserted (typed call log, not string-matching)
 // bad — asserting console output strings (brittle, untyped — formatting changes break interaction tests)
// fix — structured call logs (Parameters<T>[] arrays — order + args asserted structurally)
```

**Common confusion** — "spies and mocks are interchangeable" — spies *keep* behavior (assert interaction); mocks *replace* behavior (assert in isolation) — different questions (wiring vs logic). "spy everything" — spying pure functions couples tests to call counts (refactor-fragile); spy *side-effecting boundaries* (I/O, queues, charges), assert *returns* for pure logic. "calls arrays need a framework" — `calls.push` beside the wrapper suffices (frameworks add ergonomics, not capability).

**Performance note** — spies add one array push per call (nanoseconds — test-time only); production code untouched (zero runtime cost — spies live in test files).

**Mentor note** — review question per test double: "does this replace behavior or observe it?" — replaced behavior needs justification (nondeterminism, cost, unavailability); everything else should be a spy.

### 2) **Stubs with programmed answers** (per-case tables typed exhaustively)

**Definition** — a *stub* replaces behavior with programmed answers: a table `Map<Input, Output>` (or lookup function) returning canned responses per input. Typed stubs constrain both sides (input keys cover the domain, outputs satisfy the return type) — uncovered inputs error (exhaustive tables) or fall through explicitly (partial tables with a documented default).

**What problem it solves / history** — stubs returning `any` per case (each answer unchecked) let contract drift hide per branch: three of four cases still satisfy the return while the fourth silently widens. Exhaustively-typed tables break on the first stale answer (the table's value type disagrees — red at the row, not at the consumer).

**Modern guidance** — type answer tables as `Record<InputUnion, Output>` (exhaustiveness enforced — missing keys error) for finite domains; use `Map` + explicit fallback for open domains (documented default, tested default). Keep tables beside the test (reviewed with the behavior they serve), never in shared global fixtures (stale rows infecting unrelated suites).

**Runnable example** — exhaustive answer tables (good vs bad, `tsc --strict`):

```typescript
// good — Record table enforcing exhaustiveness (missing keys error at the table)
type Region = "eu" | "us" | "ap";
type TaxRate = (region: Region) => number;
const rates: Record<Region, number> = { eu: 0.2, us: 0.08, ap: 0.1 }; // exhaustive (drop a key — errors HERE)
const stubRate: TaxRate = (region) => rates[region];
console.log(stubRate("eu")); // 0.2 — answers programmed (per-case, typed, exhaustive)
// bad — partial table with silent undefined (missing key returns undefined at runtime — typed number lie)
// fix — Record over the input union (exhaustiveness enforced where answers are written)
```

```typescript
// good — open-domain stub with a tested default (fallback documented, fallback asserted)
function stubLookup(id: string): number {
  const table: Record<string, number> = { a: 1, b: 2 };
  return table[id] ?? -1; // explicit default (unknown ids → -1, asserted below)
}
console.log(stubLookup("zzz")); // -1 — default proven (unknown-input behavior specified, not accidental)
// bad — open table without default (undefined leaking as number — consumers crash on unknown inputs)
// fix — ?? default + assertion on the default (unknown inputs specified like known ones)
```

**Common confusion** — "stubs duplicate the spec" — stubs duplicate the *contract slice* under test (intentional, pinned); production implements the full contract (different scopes). "shared stub libraries save time" — shared stubs couple suites (one row change breaks ten files); per-test tables cost lines and save incidents. "exhaustive tables rot on union growth" — rotting *loudly* is the point (new member breaks every table — the growth TODO list, see 1.3).

**Performance note** — `Record` lookups are O(1) property access (identical to production maps — test-time only); exhaustive checking costs one mapped-type instantiation per table (negligible).

**Mentor note** — when a union grows, the red stub tables across suites *are* the migration checklist — assign them, don't silence them.

### 3) **Fakes carrying generic state** (in-memory substitutes proving contracts)

**Definition** — a *fake* is a working in-memory implementation of an interface (`FakeQueue`, `FakeRepo<T>`, `FixedClock`): real logic over ephemeral state, satisfying the same type as production. Generic fakes (`FakeStore<T>`) substitute whole *families* (any entity type) while enforcing the repository contract per instantiation.

**What problem it solves / history** — integration-only coverage (every test needing Postgres/Redis/queues — minutes per run, flakes per week) collapses suite velocity until developers stop running tests. Fakes restore unit speed (microseconds, deterministic) while proving contract compliance (the fake *implements* the interface — drift breaks the fake, see 2.1 part 2) — integration suites shrink to thin wiring checks.

**Modern guidance** — implement fakes against the *interface*, never the concrete class (depend on `Store<T>`, substitute `MemoryStore<T>`); keep fake logic minimal (happy paths + documented errors — full-fidelity simulation is a second production system). Test the fake against the contract suite once (shared `testStore(makeFake)` reused per implementation — fakes and production passing identical assertions).

**Runnable example** — generic in-memory fakes (good vs bad, `tsc --strict`):

```typescript
// good — generic fake proving the Store contract (any entity type, same semantics)
export {}; // module marker (consistent module scope across fences)
interface Store<T> { get(id: string): T | null; put(id: string, v: T): void }
class MemoryStore<T> implements Store<T> {
  private rows = new Map<string, T>();
  get(id: string): T | null { return this.rows.get(id) ?? null; }
  put(id: string, v: T): void { this.rows.set(id, v); }
}
const users: Store<{ name: string }> = new MemoryStore();
users.put("u1", { name: "ada" });
console.log(users.get("u1")?.name); // ada — fake working (real logic, ephemeral state, contract-proven)
// bad — mock-per-method for stateful seams (call-count assertions where state assertions belong — behavior untested)
// fix — fake the stateful seam (get/put semantics asserted through the interface, not around it)
```

```typescript
// good — contract suite shared across implementations (fake and production, identical assertions)
interface Counter { inc(): number }
function behavesLikeCounter(make: () => Counter): string {
  const c = make();
  const a = c.inc(); const b = c.inc();
  return b === a + 1 ? "ok" : "broken"; // contract property (monotonic +1 — implementation-agnostic)
}
class MemCounter implements Counter { private n = 0; inc(): number { return ++this.n; } }
console.log(behavesLikeCounter(() => new MemCounter())); // ok — contract suite (run against EVERY Store/Counter impl)
// bad — fake tested separately from production (divergent assertions — implementations drifting apart silently)
// fix — shared behavesLike suite (one contract, N implementations — divergence impossible)
```

**Common confusion** — "fakes are mocks with state" — fakes implement *semantics* (working logic — assert outcomes); mocks record *interactions* (assert calls) — different assertions, different failures. "contract suites double test cost" — contract suites run per implementation in milliseconds (fakes) + seconds (production) — divergence incidents cost postmortems. "generic fakes over-abstract" — `FakeStore<T>` abstracts over *entity types*, not over *seams* (one seam, many payloads — the 08 per-call-vs-per-value discipline applied to doubles).

**Performance note** — `Map`-backed fakes are O(1) per op (suite of thousands runs in milliseconds); production-backed equivalents cost network per op (seconds — the velocity gap fakes close).

**Mentor note** — the behavesLike pattern is the highest-leverage test abstraction most teams never adopt: one contract function, every implementation cited — introduce it at the second implementation, never the fifth.
