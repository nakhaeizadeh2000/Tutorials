## 2.1. Mocking functions with full type safety

A test double replaces a dependency with behavior the test controls. Its TypeScript signature should keep the dependency's input and output contract visible. That lets the checker reject a stale fixture or invalid call while runtime assertions test what the consumer actually does.

A compatible signature does not prove that a substitute behaves like the production dependency. A function returning the wrong user's name can still return a perfectly valid string. [Fowler's discussion of test doubles](https://martinfowler.com/articles/mocksArentStubs.html) distinguishes programmed answers, call observation and working substitutes; use those roles to decide what evidence the test needs.

### 1) **Run actual typed mock functions**

Use **Node.js 22.18.0**, **Vitest 5.0.5**, **TypeScript 5.9.3** for this tool integration and **npm 11.13.0** for installation, verified 2026-10-17. These pins reproduce the compatible JavaScript compiler integration; they do not replace the track's native compiler baseline. Create the following files in an empty directory. Omit file labels from JSON.

```json
// file: package.json
{
  "name": "typed-function-doubles",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": { "check": "tsc --noEmit", "test": "vitest run --maxWorkers=1" },
  "devDependencies": { "@types/node": "22.18.0", "typescript": "5.9.3", "vitest": "5.0.5" }
}
```

```json
// file: tsconfig.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": ["node"] },
  "include": ["src/**/*.ts", "test/**/*.ts"]
}
```

```typescript
// file: src/gateway.ts
export interface User { name: string }
export async function fetchUser(id: string): Promise<User> {
  return { name: `real:${id}` };
}
```

```typescript
// file: src/label.ts
import { fetchUser } from "./gateway.js";
export async function labelWith(id: string, lookup: typeof fetchUser): Promise<string> {
  return (await lookup(id)).name.toUpperCase();
}
export function label(id: string): Promise<string> {
  return labelWith(id, fetchUser);
}
```

```typescript
// file: test/injected.test.ts
import { expect, test, vi } from "vitest";
import { fetchUser } from "../src/gateway.js";
import { labelWith } from "../src/label.js";

test("typed mock supplies an answer and records the requested id", async () => {
  const lookup = vi.fn<typeof fetchUser>().mockResolvedValue({ name: "Ada" });
  await expect(labelWith("u1", lookup)).resolves.toBe("ADA");
  expect(lookup).toHaveBeenCalledExactlyOnceWith("u1");
  // lookup(123); // Checking rejects a number argument.
  // lookup.mockResolvedValue({ displayName: "Ada" }); // Checking rejects the wrong reply shape.
});

test("an implementation can provide inference without an explicit type argument", async () => {
  const lookup = vi.fn(async (id: string) => ({ name: id }));
  await expect(labelWith("u2", lookup)).resolves.toBe("U2");
  expect(lookup.mock.calls[0]?.[0]).toBe("u2");
});

test("separate injected substitutes stay local to their calls", async () => {
  const first: typeof fetchUser = async () => ({ name: "Ada" });
  const second: typeof fetchUser = async () => ({ name: "Lin" });
  await expect(labelWith("u1", first)).resolves.toBe("ADA");
  await expect(labelWith("u1", second)).resolves.toBe("LIN");
});
```

Run:

```bash
npm exec --yes --package=npm@11.13.0 -- npm install
npm run check
npm run test
```

Keep the generated lockfile. The [installation/tool lesson](<../1. Type Assertions in Tests/1.2. tsd expect-type and type-testing libraries.md>) explains the tested npm route and separate compiler integration. These runtime tests pass, and the checking command succeeds. Activate each invalid line independently and run check to observe a static failure; restore it afterward. Normal Vitest execution transforms TypeScript and runs assertions, so a passing runtime command alone does not establish a clean type check.

The explicit type argument connects the first mock to the production function. The second mock instead infers a checked signature from its implementation and is checked again at the injection boundary. That is also useful typing. An empty `vi.fn()` returns undefined until configured; it does not infer a dependency's contract from its variable name. See the [Vitest mock-function guide](https://vitest.dev/guide/learn/mock-functions) for the real APIs.

### 2) **Compare injection with an actual module replacement**

Injection passes the substitute directly to a consumer. It is easy to give two calls different dependencies without a shared mock registry. Module replacement is useful when testing code that imports its dependency directly. Add this test to the same project:

```typescript
// file: test/module.test.ts
import { expect, test, vi } from "vitest";
import { fetchUser } from "../src/gateway.js";
import { label } from "../src/label.js";

vi.mock(import("../src/gateway.js"), () => ({
  fetchUser: vi.fn<typeof fetchUser>().mockResolvedValue({ name: "Module" }),
}));

test("the imported consumer uses the replacement export", async () => {
  await expect(label("u3")).resolves.toBe("MODULE");
  expect(vi.mocked(fetchUser)).toHaveBeenCalledExactlyOnceWith("u3");
});
```

Both commands still pass, now with four runtime tests. The module-promise form gives the factory a checked module shape. Under the default module runner used here, Vitest hoists vi.mock before imports and the consumer receives the replacement. The factory's `typeof fetchUser` is a type query, so it does not read an uninitialized imported value. `vi.mocked` supplies mock-aware typing; it is not the operation that creates the replacement. The [vi API reference](https://vitest.dev/api/vi) explains hoisting, caching and import limitations.

Avoid closing a hoisted factory over an ordinary later-initialized variable. Construct its values inside the factory, or use the documented hoisted-value mechanism when shared setup is necessary. This example uses default per-file isolation; do not generalize its result to require-based imports, setup-file caches or disabled isolation without checking those conditions.

Choose the boundary that exposes the behavior clearly. A parameter seam can simplify tests; adding one everywhere has a design cost. A module mock can test an existing imported boundary without proving a need to redesign it. First-party versus third-party ownership alone does not settle that choice.

### 3) **Keep type compatibility separate from behavioral fidelity**

Change the first test's configured name from Ada to Wrong while retaining its ADA expectation. Check still passes because both names are strings; test fails because the observed label changes. The double's signature constrains the available values, not the real service's identity, persistence, ordering or failure semantics.

An any cast can hide even shape failures. For a deliberate runtime contrast, replace only that configured value with `{ displayName: "Ada" } as any`. Check accepts the escape hatch, while the awaited assertion fails when labelWith tries to uppercase the missing name. Restore the original fixture afterward. A passing test around an any value can still assert runtime behavior, but it has lost the static protection at that use.

Prefer checked fixture construction and narrowly justified escapes for intentional invalid-input tests. `no-explicit-any` reports written any syntax; it does not reject every inferred permissive library type or prove that all fixtures are valid. Rules concerning unsafe uses have separate requirements. Keep lint, checking and behavior evidence distinct.

### 4) **Common confusion**

A typed mock is not an implementation of the real service's complete behavior. It supplies a bounded scenario. Here the real gateway is intentionally tiny; no network, database or authentication integration was tested. Add appropriate real-boundary tests when a production dependency has those responsibilities.

Explicit generics are one way to preserve a signature. Inference, checked object construction and parameter compatibility can also do it. Inspect the resulting signature and the actual failure case instead of treating a bare vi.fn spelling as proof of a defect.

### 5) **Performance note**

Mock functions record calls and results, consuming runtime memory as they run. Module replacement also involves runner setup; injected substitutes execute their own code. This fixture measures no timing and supports no universal claim that one technique saves seconds or becomes cheaper after a particular number of tests. Use fresh local doubles or appropriate cleanup to keep state intentional, and profile a real suite before optimizing its setup.

### 6) **Mentor note**

Ask a learner to activate the wrong argument, wrong reply shape and correctly typed wrong name separately. They should identify which command fails and why. Then ask which operation actually replaces the module and why vi.mocked alone would not. Good answers distinguish signature checking, runner replacement, call observation and behavior assertions.
