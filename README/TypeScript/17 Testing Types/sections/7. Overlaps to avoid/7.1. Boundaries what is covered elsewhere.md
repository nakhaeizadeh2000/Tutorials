## 7.1. Boundaries — what is covered elsewhere

A type test asks whether a declaration permits or rejects a stated use. A runtime test executes code and observes its behavior. A package-consumer test also asks which declaration and implementation are available through an entry point. Choose the evidence from the public contract being defended. This map links the existing owners and uses their completed contrasts for practice.

### 2) **Generic semantics and meaningful probe rows**

[inference and NoInfer](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. A good row names the contract it defends: preserved literal evidence, selected union members, a whole-union condition, an empty case or a rejected input.

Select the assertion from the question. Assignability asks whether a value/type can satisfy a target; a chosen equality helper asks a stricter question about the resulting type. Neither is a runtime validator. Keep ordinary inputs and meaningful boundaries such as never, unknown or any explicit when they can change the transform's behavior. A list of hover strings is weaker evidence if a reviewer can update it without deciding whether the contract should change.

For recursive transformations, also state where the operation stops. [the verified recursive-object lesson](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.1. A passing shallow instantiation does not establish deeper behavior, and a cap that makes compilation succeed may deliberately stop transforming the remainder. Test that stated boundary rather than treating compile success as the entire outcome.

### 6) **Common confusion**

A compile-time assertion and a runtime assertion perform different work. Calling an ambient declaration can type-check and still fail because its implementation is absent. Dedicated tool processing and actual imported helpers need their declared setup; a comment saying type assertion is not that setup.

A green runtime test does not establish that a public type stayed precise. A green type test does not establish that the body computes the promised result. The executed lesson deliberately changes an expectation so runtime remains green while the type suite turns red. Keep both signals when both contracts matter.

Finally, testing source and testing a package entry point can resolve different artifacts. A fresh consumer can reveal a declaration omission that producer checking misses. Use the observed resolved surface rather than a hand-copied signature that can drift independently.

### 7) **Performance note**

This routing lesson has no direct performance effect. Type-test instantiations add checker work in programs that include them; runtime cases and package/tool gates perform their own work. Their cost depends on the assertions, program size, dependencies, cache conditions and job arrangement. No fresh type-test, suite or pipeline benchmark was run here.

Do not assign universal microsecond costs to a probe or assume parallel jobs always make pipeline duration equal to the longest task. Setup, scheduling and shared resources also matter. Measure the actual gates when their cost affects adoption, while preserving the semantic tests that defend a public contract. A removed failing row can make a command cheaper by discarding evidence rather than improving the implementation.

### 8) **Mentor note**

Require the tested contract, command, consumer and observed outcome. Use these completed contrasts:

1. **A snippet calls declare assertType and prints a passing label afterward.** Ask where the JavaScript implementation comes from. The executed type-testing lesson supplies real tooling and separates compile-only checks; a declared function alone cannot execute the assertion.
2. **Runtime stays green after a type expectation changes.** Identify the separate type-check gate. The Vitest fixture demonstrates a wrong type expectation failing its dedicated command while the runtime suite still passes, then restores the expectation.
3. **Source probes pass, but a consumer cannot find declarations.** Inspect packed files and entry-point resolution. The native migration assessment's malformed tarball reproduces the consumer failure while the runtime import succeeds.

For a generic matrix, ask which change should make each row fail and why. For async work, ask which operation owns completion and rejection. A sound review preserves evidence for the public outcome instead of accepting another assertion, copied signature or passing label without an executed check.
