## 1.2. tsd expect-type and type-testing libraries

A behavior test can pass while a declaration accepts the wrong inputs. Type tests make those static promises observable. This lesson uses real tools against complete small projects, then deliberately breaks a contract to prove which command detects it. The [hand-rolled assertion lesson](<./1.1. Expect Equal and compile-time type assertions.md>) owns the underlying equality mechanics.

Verified 2026-10-12: tsd 0.33.0, TypeScript 5.9.3 for the JavaScript compiler integrations, Vitest 5.0.4 and expect-type 1.4.0. The tsd commands were run on Node 20.20.2; the Vitest project was run on Node 22.18.0, which satisfies that version's engine requirement. These tool integrations use compatible compiler packages; a separate native TypeScript 7.0.2 check does not replace them. Preserve the generated lockfiles when repeating a fixture.

### 1) **`tsd` test files**

`tsd` checks assertions against a declaration surface. Its `expectType` tests type identity; `expectError` requires a diagnostic at an expression that should be rejected. The test file is processed by the tool, not executed as a behavior test. The [maintainer's documentation](https://github.com/tsdjs/tsd) describes that special processing and its declaration-file discovery.

Create `tsd-project` with the following four files, including the `src` and `test-d` directories. The declaration is built from a real implementation; the tests import the package root whose `types` entry points to that built surface.

`package.json`:

```json
{
  "name": "greeting-type-checks",
  "version": "1.0.0",
  "private": true,
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "test:types": "tsd"
  },
  "devDependencies": {
    "typescript": "5.9.3",
    "tsd": "0.33.0"
  }
}
```

`tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "commonjs",
    "types": [],
    "declaration": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": [
    "src/**/*.ts"
  ]
}
```

`src/index.ts`:

```typescript
export function greet(name: string): `hello ${string}` {
  return `hello ${name}`;
}
```

`test-d/index.test-d.ts`:

```typescript
import { expectType, expectError } from "tsd";
import { greet } from "..";
expectType<`hello ${string}`>(greet("Ada"));
expectError(greet(123));
```

In that directory run:

```bash
npm install
npm run build
npm run test:types
```

The build and type suite exit successfully. The suite does not print `hello Ada`: `greet("Ada")` is inspected statically. To observe the implementation separately, run `node -e 'console.log(require("./dist").greet("Ada"))'`; that consumer prints `hello Ada`.

Now change the implementation's parameter annotation to `name: string | number`, rebuild, and run the type suite. The happy-path return test still passes, but the negative assertion fails with `Expected an error, but found none.` Restoring `string` and rebuilding makes the suite pass. The solution preserves the intended rejected input; deleting the test would merely hide the changed contract.

Do not add these negative assertions to an ordinary `tsc` include set expecting identical results. For comparison, `npx tsc --strict --noEmit --module commonjs --target es2022 --skipLibCheck test-d/index.test-d.ts` reports TS2345 at `greet(123)`. That diagnostic is precisely what `tsd` expects to find and handle. Keep the source build and the tool-specific suite as separate commands.

The checked tsd dependency graph has an [unpatched braces advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) for deeply nested patterns. This fixture uses its fixed local test directory; review that dependency finding before adopting the tool in a workflow that accepts external patterns. The fluent project below provides another choice when a dependency policy excludes this tsd graph. Do not downgrade to the old version suggested by an automatic audit fix without validating its API and compiler support.

### 2) **`expect-type` fluent assertions**

A fluent assertion such as `.toEqualTypeOf<number>()` is checked by TypeScript. It does not compare runtime values. Vitest exposes `expectTypeOf` for this purpose and has a separate type-checking mode. Its [type-testing guide](https://vitest.dev/guide/testing-types) distinguishes that mode from normal execution; the [expect-type maintainer documentation](https://github.com/mmkal/expect-type) explains the fluent API and its limits.

Create a separate `vitest-project` using Node 22.18.0 and these files. The runtime test checks successful parsing and an actual throw; the `.test-d.ts` file checks the function signature.

`package.json`:

```json
{
  "name": "fluent-type-checks",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "vitest run",
    "test:types": "vitest run --typecheck.only"
  },
  "devDependencies": {
    "@types/node": "22.18.0",
    "expect-type": "1.4.0",
    "typescript": "5.9.3",
    "vitest": "5.0.4"
  }
}
```

`tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "types": [
      "node"
    ],
    "noEmit": true,
    "lib": [
      "es2022",
      "esnext.disposable",
      "dom"
    ]
  },
  "include": [
    "src/**/*.ts",
    "test/**/*.ts"
  ]
}
```

`vitest.config.mts`:

```typescript
import { defineConfig } from "vitest/config";
export default defineConfig({
  test: {
    maxWorkers: 1,
    typecheck: { tsconfig: "./tsconfig.json" },
  },
});
```

`src/parse.ts`:

```typescript
export function parseCount(raw: string): number {
  const value = Number(raw);
  if (Number.isNaN(value)) throw new Error("invalid number");
  return value;
}
```

`test/parse.test.ts`:

```typescript
import { expect, test } from "vitest";
import { parseCount } from "../src/parse.js";
test("parses a count", () => {
  expect(parseCount("7")).toBe(7);
  expect(() => parseCount("bad")).toThrow("invalid number");
});
```

`test/parse.test-d.ts`:

```typescript
import { expectTypeOf, test } from "vitest";
import { parseCount } from "../src/parse.js";
test("parseCount signature", () => {
  expectTypeOf(parseCount).parameter(0).toEqualTypeOf<string>();
  expectTypeOf(parseCount).returns.toEqualTypeOf<number>();
});
```

Run in that directory:

```bash
npm install
npm run test
npm run test:types
```

Each command succeeds. Ordinary `vitest run` executes the runtime test; `vitest run --typecheck.only` checks the dedicated type test without executing it. Type checking in the verified Vitest version is labeled experimental, so the pin matters. Node declarations and the disposable library in this configuration support the tool's declaration dependencies; they are not substitutes for installing a compatible runtime.

Change only the return expectation in `parse.test-d.ts` from `number` to `string`. `npm run test` still passes its behavior test, while `npm run test:types` fails the static expectation. Restoring `number` makes the type command pass again. This demonstrates why a green runtime suite alone cannot certify a static API contract.

For an independent compile-only probe, the same package also supports an actual import from `expect-type`:

`fluent.ts`:

```typescript
import { expectTypeOf } from "expect-type";
expectTypeOf<ReturnType<(raw: string) => number>>().toEqualTypeOf<number>();
```

Check it with `npx tsc --noEmit --strict --module nodenext --target es2022 fluent.ts`. It succeeds using the installed compiler. It has no promised console output. Changing the expected type to `string` produces a checker failure; calling an ambient hand-rolled assertion without an implementation would instead be a different runtime problem.

### 3) **Library vs hand-rolled choice**

Choose the test based on the contract under review and the commands your team can maintain. A package's generated declarations are a useful target for tsd. A project already using Vitest can keep behavior and dedicated fluent type tests nearby, with explicit commands for each. A small compile-only contract may be clearest as a type alias using `Expect<Equal<...>>`; it does not need a callable ambient function.

Prefer an identity assertion when widening would break the contract; use assignability when compatibility with a broader consumer type is the intended property. Neither is universally stronger for every API. Test rejection when rejection is deliberate, then add runtime checks for properties that types cannot express, such as actual parser behavior or business validation.

These fixtures are local tool demonstrations, not a complete package compatibility matrix. A production library should also verify its built consumers, export resolution and supported compiler/runtime combinations. The [public-surface lesson](<../3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) owns that broader boundary.

### 4) **Common confusion**

A declared assertion function can be useful in a compile-only file, but `declare` creates no implementation. Running a call to such a function can throw a `ReferenceError`; label the probe according to how it is checked. The real libraries above supply their APIs, and the type command determines whether the assertions hold.

Fluent calls also do not validate a value at runtime. In an ordinary executable test, expressions supplied as arguments still follow JavaScript evaluation rules. Dedicated type-test files are checked without being run; keep behavior assertions in runtime tests and avoid assuming a transform removes every type-related call or side effect.

### 5) **Performance note**

Type suites create checker work and may repeatedly analyze generated declarations. Runtime suites have a separate execution cost. This lesson verifies pass/fail behavior, without a timing benchmark or a universal assertion-count budget. Measure the actual project before splitting jobs, adding matrices or changing tools; parallel jobs can still contend for CPU and memory.

The test helpers should remain in test code. Their compile-time type reasoning is erased, but executable imports and argument expressions can still add runtime work if you place them in application code.

### 6) **Mentor note**

Ask a learner to widen `greet` and predict which tsd assertion fails. A good answer identifies the lost input rejection and explains why the valid string case still passes. Then ask them to fix a wrong fluent expectation while keeping runtime behavior unchanged; they should run the specific type command and show its failure first.

During review, ask for the actual command, tested compiler and observed output. A library-shaped equivalent or a commented negative call does not prove the library integration works. Review the contract and dependency choice together, rather than requiring every project to adopt the same suite.
