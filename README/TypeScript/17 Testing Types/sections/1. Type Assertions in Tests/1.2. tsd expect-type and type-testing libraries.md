## 1.2. tsd expect-type and type-testing libraries

### 1) **`tsd` test files** (test-d plus expectType plus expectError)

**Definition** — [`tsd`](https://github.com/SamVerschueren/tsd) is a CLI that type-checks a `test-d/` directory against your package's built declarations: `expectType<string>(value)` asserts the *exact* type (identity, like 1.1's `Equal`), `expectError(...)` asserts an expression *fails* checking (negative tests without `@ts-expect-error` comments). No test runner executes — `tsd` reports assertion failures as diagnostics, wired as a CI job beside `tsc`.

**What problem it solves / history** — library authors shipped widened/broken declarations for years with green unit tests (behavior tested, *types* untested — consumers discovered `any`-leaks and renamed exports). Hand-rolled `Equal` probes (1.1) work but scatter across `src/`; `tsd` standardizes the convention: one directory, two assertion functions, zero runtime — the type surface tested like an API contract.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), adopt `tsd` when you publish a package (consumers depend on declarations — test them); keep hand-rolled `Equal` for apps (no packaging boundary, no extra tool). Configure `tsd.directory` to `test-d`, and keep `test-d` inside `tsconfig.include` so plain `tsc --noEmit` also sees the files (double coverage, zero drift).

**Runnable example** — the `tsd` assertion vocabulary, shown as plain `tsc --strict` equivalents (good vs bad):

```typescript
// good — expectType asserts identity (the 1.1 Equal mechanic, library-spelled)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
declare function greet(name: string): `hello ${string}`;
assertType<Equal<ReturnType<typeof greet>, `hello ${string}`>>(); // identity (template-literal return pinned)
console.log(greet("ada")); // hello ada — tsd's expectType<string-template> expressed hand-rolled
// bad — expectAssignable-only suites (tsd's looser assertion passing on widened returns — same hole as 1.1's assignability probe)
// fix — default to expectType (identity); use expectAssignable only for intentional widening contracts
```

```typescript
// good — expectError locks rejected inputs (negative tests as first-class assertions)
function onlyPositive(n: number): number {
  if (n <= 0) throw new Error("must be positive");
  return n;
}
// expectError(onlyPositive("x")); // ❌ tsd form (string arg rejected — locked: accepting it later breaks the test)
console.log(onlyPositive(3)); // 3 — negative shape pinned (rejection is the contract, tested like acceptance)
 // bad — testing only happy paths (rejected shapes re-admitted silently — the 5.1 card-shape incident class)
// fix — one expectError per public validation rule (every rejection a pinned test)
```

```typescript
// good — test-d placement beside src (one directory, reviewed with the package)
// file layout (convention, not code): src/index.ts + test-d/index.test-d.ts (mirrored names — reviewers see both in one PR)
export function add(a: number, b: number): number { return a + b; }
console.log(add(1, 2)); // 3 — implementation and its type probes (mirrored files, single review unit)
// bad — type assertions scattered in src/ (implementation noise) or in distant misc/ (forgotten probes)
// fix — test-d/ mirror (bulk assertions grouped, mirrored names, CI-checked — see 1.1 part 3)
```

**Common confusion** — "`tsd` runs my tests" — `tsd` checks *types* (no runtime executes — `console.log` never fires under `tsd`); vitest/jest run *behavior* — different gates (see 3.3). "`expectError` and `@ts-expect-error` are identical" — same *intent* (negative lock), different *homes* (`tsd` API vs inline comments — 1.3 owns the comment form). "apps need `tsd`" — apps have no declaration consumers (no packaging boundary — hand-rolled `Equal` suffices; `tsd` pays off at package boundaries).

**Performance note** — `tsd` spins a full program over `test-d` + declarations (seconds, not milliseconds — CI-job scale, not save-scale); keep `test-d` matrices representative (union members × 3 edge types) so the job stays under a minute.

**Mentor note** — adoption threshold question: "does anyone `import` our declarations?" — yes → `tsd` this quarter; no → hand-rolled `Equal` (1.1) is enough. Review rule for packages: no PR changing `src/*.d.ts`-visible types merges without its `test-d` mirror updated.

### 2) **`expect-type` fluent assertions** (expectTypeOf with readable failures)

**Definition** — [`expect-type`](https://github.com/mmkal/expect-type) (bundled with vitest as `expectTypeOf`) offers a fluent API: `expectTypeOf(value).toEqualTypeOf<Expected>()` (identity), `.toMatchTypeOf<Pattern>()` (assignability), `.not` variants, `.parameter(n)`/`.returns` extractors for function parts. Failures render *both* types expanded (diffable), unlike bare `assertType` constraint errors.

**What problem it solves / history** — `assertType<Equal<A,B>>` failures read `Type 'false' does not satisfy the constraint 'true'` (true but useless — *which* side drifted needs hover archaeology). Fluent assertions print actual-vs-expected expansions inline (the drift visible in the terminal, no IDE needed) — failure-message quality deciding triage speed.

**Modern guidance** — use `expectTypeOf` inside vitest suites (`*.test.ts` — type assertions beside behavior assertions, one runner, one file); keep `tsd` for declaration-only packages without runtime tests. Prefer `toEqualTypeOf` (identity) by default; `toMatchTypeOf` only where widening is the documented contract.

**Runnable example** — fluent assertions as plain-`tsc` equivalents (good vs bad, `tsc --strict`):

```typescript
// good — toEqualTypeOf pins identity with a readable failure (hand-rolled equivalent below)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
const STATUSES = ["a", "b"] as const;
type Status = (typeof STATUSES)[number];
assertType<Equal<Status, "a" | "b">>(); // identity (as-const derivation pinned — widening breaks here)
console.log(STATUSES.length); // 2 — expectTypeOf(STATUSES).toEqualTypeOf<readonly ["a","b"]>() in fluent spelling
// bad — asserting the widened container (string[] — derivation drift invisible, tables desync)
// fix — assert the DERIVED union (the consumed contract), not the container (the source trivia)
```

```typescript
// good — parameter/returns extractors testing function parts (overload-aware in fluent form)
declare function assertType<T extends true>(): void;
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
function parse(raw: string): { ok: true; n: number } | { ok: false; err: string } {
  const n = Number(raw);
  return Number.isNaN(n) ? { ok: false, err: "nan" } : { ok: true, n };
}
assertType<Equal<Parameters<typeof parse>, [raw: string]>>(); // parameter part pinned
assertType<Equal<ReturnType<typeof parse>["ok"], boolean>>(); // discriminant part pinned
console.log(parse("3").ok); // true — .parameter(0).toEqualTypeOf<string>() + .returns matchers in fluent spelling
// bad — asserting only the full signature (parameter drift hidden inside a passing whole)
// fix — extractors per part (parameters, returns, awaited — each pinned, failures localized)
```

**Common confusion** — "fluent assertions execute at runtime" — `expectTypeOf` calls are *type-level* (vitest strips them from runtime semantics — they never assert values); value assertions (`toBe`) execute — same file, different universes (see 02 type-vs-value). "`.not` variants are redundant with negative tests" — `.not.toEqualTypeOf` pins *inequality* (related-but-distinct types staying distinct — branded IDs per 04/3.2); `@ts-expect-error` pins *rejection* (illegal code staying illegal) — different intents.

**Performance note** — fluent generics instantiate per assertion (heavier than bare `Equal` — expanded-type printing costs); fine at suite scale (hundreds), not inside hot production mapped types (test-only import — `import { expectTypeOf } from "expect-type"` in test files only).

**Mentor note** — teach the failure-message difference live: break a return type and show both errors side by side (`false`-constraint vs expanded diff) — developers choose readable failures forever after.

### 3) **Library vs hand-rolled choice** (two-line Equal vs test framework)

**Definition** — the decision table: *hand-rolled* (`Equal` + `assertType`, ~5 lines in a shared `test-utils.ts`) vs *`tsd`* (declaration-package convention, `test-d/` + CLI) vs *`expect-type`/vitest* (suites mixing behavior + type assertions). Cost axis: dependencies + config + CI jobs; benefit axis: message quality + convention + runner integration.

**What problem it solves / history** — teams cargo-cult `tsd` into apps (config + CI job testing no packaging boundary) or hand-roll fifty bespoke assertion helpers in a published SDK (inconsistent messages, no convention for contributors). The table routes by *boundary*: apps (no consumers of declarations) → hand-rolled; packages (declarations ARE the product) → `tsd` + `expect-type` where suites exist.

**Modern guidance** — apps: one shared `assertType` + `Equal` (+ `Extends`, `IsNever`) in test utils, inline pins + `test-d`-style matrices, `tsc --noEmit` gate only. Packages: `tsd` for `test-d/` surface probes + `expect-type` inside vitest suites + `attw`/publint gates (16/2.3) — three gates, each catching a distinct regression class (see 3.3).

**Runnable example** — the shared hand-rolled kit (good vs bad, `tsc --strict`):

```typescript
// good — one shared kit (four helpers covering 90% of type tests)
// file: test-utils.ts (shared OSHA kit — imported by every test-d file)
export type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
export declare function assertType<T extends true>(): void;
export type Extends<A, B> = A extends B ? true : false;
export type IsNever<T> = [T] extends [never] ? true : false;
console.log("kit-ready"); // kit-ready — five lines (every matrix below imports these, nothing else)
// bad — bespoke helpers per file (Equal2/Assert3/IsNevers — inconsistent semantics, contributor confusion)
// fix — single kit module (one definition of identity, imported everywhere — convention beats invention)
```

**Common confusion** — "more helpers means better tests" — four helpers (`Equal`, `Extends`, `IsNever`, `assertType`) cover identity/containment/emptiness/gating — everything else composes from them. "libraries obsolete hand-rolled" — libraries *package* the same tricks with nicer messages; the tricks (1.1) remain the mental model (debug any fluent failure by expanding to `Equal`).

**Performance note** — shared-kit imports add one module to each test program (negligible); `tsd`/`expect-type` add dependency install + resolution weight (justified at package boundaries, wasteful in apps).

**Mentor note** — onboarding order: hand-rolled `Equal` first (mechanics understood), fluent/`tsd` second (convenience appreciated) — convenience-before-mechanics produces developers who cannot read failure output.
