## 1.1. Expect Equal and compile-time type assertions

### 1) **`Equal<A, B>` identity check** (exact equality, not mere assignability)

**Definition** — `type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false` — the conditional-identity trick: two types are `Equal` only when mutually substitutable *including* `any`-vs-`unknown`, literal-vs-widened, and optional-vs-required distinctions that plain `extends` checks silently accept. Paired with `function assertType<T extends true>(): void` (call `assertType<Equal<Actual, Expected>>()` — drift errors at the call, pointing at the changed line).

**What problem it solves / history** — assignability tests (`const x: Expected = actualValue` — passes when `Actual` merely *fits inside* `Expected`) approve widening drift: a function returning `string` where it once returned `"a" | "b"` still assigns, and every downstream exhaustive switch goes quietly non-exhaustive. `Equal` closes the hole: identity fails on any widening, narrowing, or optionality change — the test breaks exactly when the contract moves.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), hand-roll `Equal` + `assertType` in apps (two lines, zero dependencies); reach for `expect-type`/`tsd` only for published packages (nicer messages, file conventions — see 1.2). Assert *public* return/parameter types at declaration boundaries, never every local.

**Runnable example** — identity catches what assignability hides (good vs bad, `tsc --strict`):

```typescript
// good — Equal catches widening drift (assignability would pass silently)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
function currentStatus(): "a" | "b" { return "a"; }
assertType<Equal<ReturnType<typeof currentStatus>, "a" | "b">>(); // compiles (identity holds)
console.log(currentStatus()); // a — contract pinned (widening to string breaks THIS line, loudly)
// bad — assignability probe passes after widening (const x: string = currentStatus() still fits — drift invisible)
// fix — Equal<Actual, Expected> (identity, not compatibility — widening errors at the assertion)
```

```typescript
// good — Equal distinguishes optional vs required (extends-checks conflate them)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
interface Opt { a?: string }
interface Req { a: string | undefined }
// assertType<Equal<Opt, Req>>(); // ❌ errors TS2344 (Type 'false' ... — proving Opt ≠ Req: optional-absence differs from explicit-undefined)
console.log("probe-shape"); // probe-shape — optional-vs-required differ (the commented line errors when uncommented)
// bad — { a?: string } vs { a: string | undefined } treated as "the same" (exactOptionalPropertyTypes off hides absence-vs-undefined — see 04/1.2)
// fix — Equal + exactOptionalPropertyTypes (both the assertion and the flag agree on absence semantics)
```

```typescript
// good — any-vs-unknown distinguished (the one hole bidirectional-assignability opens)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
assertType<Equal<string, string>>(); // compiles (sanity: identical types are Equal)
console.log("equal-ok"); // equal-ok — sanity probe (the machinery works before trusting it on real contracts)
// bad — Equal<any, unknown> assumed true (any is bidirectionally assignable — see 03/2.1 — but NOT identical)
// fix — trust the trick: Equal<any, unknown> is false (identity sees what assignability hides)
```

**Common confusion** — "`Equal` and `extends` checks are interchangeable" — `extends` proves *compatibility* (fits inside); `Equal` proves *identity* (same contract) — drift-catching needs identity. "`Equal` in value position works" — `assertType<...>` must be *called* (`assertType<Equal<A,B>>()`); bare `assertType<Equal<A,B>>` names the function without instantiating the constraint — no check happens. "assert every type" — assert *boundary* contracts (public returns, mapped outputs, conditional results); asserting locals couples tests to implementation trivia.

**Performance note** — `Equal` instantiates two conditional function types per assertion — trivial at test-file scale (dozens of probes add milliseconds); never place `Equal` inside hot mapped/conditional production types (assertion-only helper — test files excluded from emit via `tsconfig.include`).

**Mentor note** — teach the widening demo first (literal union → `string` passing an assignability probe, failing `Equal`): oneCompile-error moment converts skeptics permanently. Review rule: every public function returning a literal/union gets one `Equal` line beside it.

### 2) **`Expect<T extends true>` gate** (assertion positions erroring on drift)

**Definition** — `Expect` is the *consumer* half: `declare function assertType<T extends true>(): void` (or `type Expect<T extends true> = T`) — any `false` argument errors at the call (`Type 'false' does not satisfy the constraint 'true'`). Combined with `Equal`, `Extends`, `IsNever` utilities it turns arbitrary type predicates into compile-time tests: `assertType<Equal<A, B>>()`, `assertType<Extends<A, B>>()`.

**What problem it solves / history** — type predicates (`IsNever<T>`, `Extends<A,B>`) compute booleans nobody reads — without a *gate*, a `false` result sits in a hover nobody opens. `Expect`/`assertType` converts the boolean into a *diagnostic*: false becomes a red squiggle at a pinned line, in CI, blocking merge.

**Modern guidance** — prefer the call form `assertType<...>()` (error points at the assertion line with the tested expression in scope); use the alias form `type T1 = Expect<Equal<A, B>>` inside declaration probes where no runtime file exists (`*.test-d.ts` — see 1.2 and 3.2).

**Runnable example** — gates turning predicates into blocking tests (good vs bad, `tsc --strict`):

```typescript
// good — gate errors exactly on drift (false fails the constraint, pointing at the contract)
declare function assertType<T extends true>(): void;
type Extends<A, B> = A extends B ? true : false;
assertType<Extends<"a", string>>(); // compiles (literal extends widened — containment holds)
console.log("gate-ok"); // gate-ok — containment assertions (directional checks where identity is too strict)
// bad — computing Extends without gating (type X = Extends<...>; — false sits unread in a hover)
// fix — always terminate predicates in Expect/assertType (booleans unasserted are wishes, not tests)
```

```typescript
// good — IsNever probe locking exhaustiveness (07/3.2 sinks pinned as tests)
declare function assertType<T extends true>(): void;
type IsNever<T> = [T] extends [never] ? true : false;
assertType<IsNever<never>>(); // compiles (the sink shape, pinned — regressions error here)
console.log("never-ok"); // never-ok — sink probes (exhaustiveness machinery itself under test)
// bad — assuming the sink is never (refactors silently un-empty it — switches go non-exhaustive with no signal)
// fix — IsNever + assertType beside every assertNever helper (the 07 mechanic tested, not hoped)
```

**Common confusion** — "`Expect` needs a test runner" — `assertType` calls erase fully (no emit — see 01/2.1); `tsc --noEmit` *is* the runner (CI gate — see 3.3). "one gate per file suffices" — gate *per contract* (each public return/transform gets its line — coarse gates localize nothing).

**Performance note** — gates cost zero at runtime (erased calls); check-time cost equals the predicate inside (usually one conditional instantiation — negligible).

**Mentor note** — review check: every `Equal`/`Extends`/`IsNever` must terminate in `Expect`/`assertType` — a predicate without a gate is a comment with syntax highlighting.

### 3) **Where assertions live** (colocated test-d files vs inline probes)

**Definition** — two homes: *inline probes* (`assertType<...>()` beside the declaration — visible at the contract, noisy at scale) and *colocated `*.test-d.ts`* (one test file per module, e.g. `user.ts` → `user.test-d.ts` — assertions grouped, excluded from emit, run by `tsc --noEmit` over the project).

**What problem it solves / history** — inline-only probes rot into noise (contracts drowned in assertions); separate-only files drift from contracts (changed declarations, forgotten probes). The split that survives: one-line identity probes inline at *declaration* sites (the contract advertises its pin), exhaustive matrices (unions × never × optional × conditional branches) in `test-d` files (bulk without noise).

**Modern guidance** — inline: the single `Equal` on each public return/parameter; `test-d`: distribution matrices (every union member, `never`/`unknown`/`any` instantiations per 3.1), negative `@ts-expect-error` locks per 1.3, public-surface import probes per 3.2. Exclude `test-d` from emit but *include* in `tsc --noEmit` CI (the 5.1 incident class otherwise).

**Runnable example** — placement discipline (good vs bad, `tsc --strict`):

```typescript
// good — inline pin at the contract (one line, co-located, unmissable)
// file: user.ts (inline probe beside the declaration)
export interface User { id: string; role: "admin" | "user" }
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
assertType<Equal<User["role"], "admin" | "user">>(); // inline pin (contract advertises its lock)
console.log("pinned"); // pinned — declaration and assertion reviewed in one diff hunk
// bad — probes in a distant misc file (changed declarations, forgotten probes — drift windows)
// fix — inline pins for contracts, test-d matrices for branches (each where reviewers look)
```

**Common confusion** — "`test-d` files need a runner" — `tsc --noEmit` checks them (they are *type* tests — no runtime); runners (vitest) execute *behavior* tests — different gates (see 3.3). "exclude test files from tsconfig" — exclude from *emit*, include in *check* (`include: ["src"]` with `test-d` inside `src`, or explicit include — the 5.1 shipping-broken-types incident is this misconfiguration).

**Performance note** — test-d files add check-time linear in assertions (each `Equal` ~microseconds); keep matrices representative (union members × 3 edge types), not combinatorial (every tuple of everything).

**Mentor note** — file-review rule: a PR changing a public type without touching its inline pin or `test-d` matrix is incomplete — request changes, every time.
