## 1.1. Expect, Equal and compile-time type assertions

### 1) **Choose the relationship the test should protect**

A type test asks the compiler whether a relationship holds. Assignability answers a directional question: can this source type be used where a target is expected? A stricter comparison helper can detect distinctions that a broad target permits. Neither choice is universally better; match the assertion to the public contract.

For example, both a literal union and string fit a string target. That target is too broad to protect a promise to return only two status names. Assigning a string result to the literal union would instead fail. State the direction before claiming that assignability missed a widening.

We will use this commonly used comparison and a gate:

```typescript
// Illustration; the complete test file below defines these helpers.
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
```

Equal compares generic conditional-function representations. It distinguishes useful cases such as any versus unknown and a literal versus its widened primitive. It is a test utility, not a built-in equality operator or a proof that every behaviorally interchangeable representation has one canonical identity. Intersections and flattened object types can be mutually assignable while this helper reports false.

[Axel Rauschmayer's type-testing chapter](https://exploringjs.com/ts/book/ch_testing-types.html) develops predicates, gates, distribution and special-type cases. Its discussion also shows why equality definitions need deliberate choices. The [conditional-type reference](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html) supplies the underlying assignability and distribution rules. Use the helper's actual behavior on the types your contract needs.

### 2) **Run a complete compile-only suite**

Use **TypeScript 7.0.2** and **Node.js 20.20.2**. Create these files in an empty directory, omitting file labels from JSON:

```typescript
// file: src/status.mts
export function currentStatus(): "a" | "b" { return "a"; }
```

```typescript
// file: test-d/status.test-d.mts
import { currentStatus } from "../src/status.mjs";
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Fits<A, B> = [A] extends [B] ? true : false;
type StatusContract = Expect<Equal<ReturnType<typeof currentStatus>, "a" | "b">>;
type BroadTarget = Expect<Fits<ReturnType<typeof currentStatus>, string>>;
type SpecialTypes = Expect<Equal<Equal<any, unknown>, false>>;
type OptionalIsNotRequired = Expect<Equal<Equal<{ a?: string }, { a: string | undefined }>, false>>;
type OptionalDoesNotFitRequired = Expect<Equal<Fits<{ a?: string }, { a: string | undefined }>, false>>;
type Split = { a: string } & { b: number };
type Flat = { a: string; b: number };
type RepresentationCases = [
  Expect<Fits<Split, Flat>>, Expect<Fits<Flat, Split>>,
  Expect<Equal<Equal<Split, Flat>, false>>
];
// type WrongExpectation = Expect<false>; // TS2344.
// type OptionalAsRequired = Expect<Fits<{ a?: string }, { a: string | undefined }>>; // TS2344.
```

```json
// file: tsconfig.check.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": [], "noEmit": true },
  "include": ["src/**/*.mts", "test-d/**/*.mts"]
}
```

```json
// file: tsconfig.build.json
{
  "extends": "./tsconfig.check.json",
  "compilerOptions": { "noEmit": false, "rootDir": "src", "outDir": "dist" },
  "include": ["src/**/*.mts"]
}
```

Run `tsc -p tsconfig.check.json`. It succeeds without emitting JavaScript. Activate WrongExpectation or OptionalAsRequired individually to observe TS2344, then restore it. Optional absence and required presence already differ under ordinary strict checking; exactOptionalPropertyTypes additionally changes permitted present-undefined assignments. That flag is not required to make these two shapes different.

Now change currentStatus's return annotation to string. The precise StatusContract fails with TS2344, while BroadTarget still holds. Restore the literal union after the experiment. The gate makes a false result observable as a compiler error; computing a type alias whose result is false without constraining it is not itself a failing test.

Use `tsc -p tsconfig.check.json --listFilesOnly` to confirm the test file is selected. Run `tsc -p tsconfig.build.json` to emit only the selected source. The check/build split is explicit: a test-d directory or filename does not automatically create this policy for ordinary tsc. A runner may impose its own naming conventions. Excluding a file from the only checking project removes its assertions from that check, not merely from emission.

### 3) **Do not confuse erased types with executable expressions**

Type aliases disappear from JavaScript. A call to a declared function does not disappear merely because its declaration is ambient. For a deliberate failure demonstration, save this separate file outside the check project's selected roots:

```typescript
// file: unsafe.mts
declare function onlyTrue<T extends true>(): void;
onlyTrue<true>();
// onlyTrue<false>; // TS2344 even without calling: this is an instantiation expression.
```

Compile with `tsc --ignoreConfig --strict --target es2022 --module nodenext --outDir unsafe-dist unsafe.mts`, then inspect unsafe-dist/unsafe.mjs. The declaration and type argument disappear, but `onlyTrue();` remains. Running `node unsafe-dist/unsafe.mjs` exits with ReferenceError because no implementation exists. This is an intentional negative runtime example, not a test file to add to production output.

Uncomment the bare `onlyTrue<false>;` expression and compile with noEmit to observe TS2344. [Instantiation expressions](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#instantiation-expressions) specialize a generic value and check its type arguments without requiring a call. Calling is not what makes a generic constraint apply. Either value expression can also read or call a missing runtime value if emitted and executed.

Prefer type aliases for these compile-only predicates. An imported assertion library can supply real value implementations and richer diagnostics, but its static checks and runtime behavior remain separate promises. The [worked library-tool lesson](<./1.2. tsd expect-type and type-testing libraries.md>) demonstrates those actual tools rather than an undeclared runtime helper.

### 4) **Common confusion**

Expect checks a generic constraint; it does not implement an infallible truth oracle. Never is assignable to true, so `type Vacuous = Expect<never>` is accepted. Any also needs care. Define predicates that return meaningful true/false results for the relevant inputs, and test boundary cases rather than feeding arbitrary types into a gate and interpreting silence as proof.

Equal is not runtime deep equality and does not validate untrusted values. Nor is representation equality always the compatibility goal. The Split/Flat pair explains why a mutually assignable contract can fail this stricter helper. Choose assignability, a representation-sensitive assertion or a negative call test according to the change you want to detect.

### 5) **Performance note**

The alias-only suite is checked but not executed and its aliases add no emitted runtime operations. Type predicates still require compiler work; nested generic, union and conditional cases can have different costs. This fixture establishes results without a per-assertion timing or linear-scaling claim. Use representative contracts and measure a real suite before expanding large matrices.

### 6) **Mentor note**

Ask the learner why BroadTarget survives widening, why OptionalDoesNotFitRequired is false and why Split/Flat can fit both ways while Equal reports false. Then show the emitted ambient call and ask what executes. A strong answer separates the chosen static relation, the constraint gate, project selection and runtime implementation.
