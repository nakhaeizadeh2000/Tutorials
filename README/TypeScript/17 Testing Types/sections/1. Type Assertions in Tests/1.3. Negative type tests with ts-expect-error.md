## 1.3. Negative type tests with ts-expect-error

A positive type test checks an accepted relationship. A negative test checks an operation that should be rejected. With `@ts-expect-error`, a successful check means the following line produced a diagnostic that the directive suppressed. If that line becomes valid, the compiler reports TS2578 for the unused directive. This makes intentional rejection testable, with an important limit: the directive does not specify which diagnostic must occur.

The [TypeScript 3.9 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html) introduced this behavior and explain its difference from `@ts-ignore`. The examples below were checked with **TypeScript 7.0.2** and **Node.js 20.20.2**.

### 1) **Run an active rejection test**

Create these files in an empty directory. File labels identify their destination; omit the label from JSON. The check project includes both source and static tests. The build project selects only source, so it never executes intentionally invalid calls.

```typescript
// file: src/port.mts
export function toPort(value: number): number {
  const port = Number(value);
  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new RangeError("bad port");
  }
  return port;
}
```

```typescript
// file: test-d/port.test-d.mts
import { toPort } from "../src/port.mjs";
toPort(80);
toPort(0); // Accepted statically: 0 is a number. The runtime rejects it.
// @ts-expect-error -- callers must supply a number, not a numeric string.
toPort("80");
```

```json
// file: tsconfig.check.json
{
  "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": [], "noEmit": true },
  "include": ["src/**/*.mts", "test-d/**/*.mts"]
}
```

```json
// file: tsconfig.build.json
{
  "extends": "./tsconfig.check.json",
  "compilerOptions": { "noEmit": false, "rootDir": "src", "outDir": "dist" },
  "include": ["src/**/*.mts"]
}
```

Run `tsc -p tsconfig.check.json`. It succeeds. Remove the directive temporarily and rerun: TS2345 reports that string cannot flow to number. Restore it, then change the parameter to `value: number | string`. The implementation still checks, but the negative test now fails with TS2578. Restore the original signature. That failure is evidence of changed input acceptance; review whether the change is intended before editing the test.

A comment that quotes a directive, or a commented-out invalid call, tests nothing. Keep both the actual directive and its following operation active. `tsc -p tsconfig.check.json --listFilesOnly` confirms that the file participates in this check. A test-d filename alone does not select it for ordinary tsc.

### 2) **Check the reason for rejection and separate runtime rules**

Replace only the negative call with `toPrt("80")`, leaving its directive in place. The suite still succeeds: the unknown name supplies an error. Remove the directive and TS2552 exposes the typo and suggests toPort. Restore the correctly spelled call and directive afterward. A trailing explanation helps a reviewer, but TypeScript does not compare that text with the diagnostic or enforce a written error code. Keep negative expressions small and inspect their unsuppressed diagnostic when writing or changing them.

Nor does the directive validate a runtime policy. A number annotation admits 0, fractions and infinity. Putting an expected-error directive above `toPort(0)` would produce TS2578 rather than test the range check. Save this separate JavaScript consumer:

```javascript
// file: runtime.mjs
import assert from "node:assert/strict";
import { toPort } from "./dist/port.mjs";
assert.equal(toPort(80), 80);
for (const value of [0, 65536, 1.5, NaN, Infinity]) {
  assert.throws(() => toPort(value), RangeError);
}
console.log("port behavior passed");
```

Run `tsc -p tsconfig.build.json`, then `node runtime.mjs`. The output is `port behavior passed`. This checks actual numeric boundaries, separately from the static rejection of a string. The test-d file is not run. Removing a range check can break the behavior suite while leaving the static suite green; widening the parameter can break the static suite while leaving these behavior cases green.

`@ts-ignore` also suppresses following-line errors, but does not report an unused directive when that line becomes valid. For a rejection test, that loses the regression signal. Temporary compatibility code checked by several compiler versions can need different treatment: the release notes explicitly discuss a line that errors in one supported version but not another. Review suppression intent, supported versions and removal conditions instead of blindly converting every ignore. A lint rule can enforce a chosen comment policy; it cannot establish that a negative expression failed for its stated reason.

### 3) **Distinguish exhaustive handling from excluded input**

An exhaustive handler checks all members of its declared union. An outsider rejection checks the input boundary. They can complement each other, but they answer different questions. Add these files to the same project:

```typescript
// file: src/shipping.mts
export type ShipState = "paid" | "shipped";
function assertNever(value: never): never {
  throw new Error(`unexpected state: ${String(value)}`);
}
export function shippingLabel(state: ShipState): string {
  switch (state) {
    case "paid": return "P";
    case "shipped": return "S";
    default: return assertNever(state);
  }
}
```

```typescript
// file: test-d/shipping.test-d.mts
import { shippingLabel } from "../src/shipping.mjs";
shippingLabel("paid");
// @ts-expect-error -- refunded is outside this API's declared input union.
shippingLabel("refunded");
```

The check succeeds. Add `| "refunded"` to ShipState without changing the switch. The existing never sink reports TS2345 because a member remains; the outsider directive also becomes unused. The sink itself detects this future union growth. It does not require a second hand-maintained union list or an ambient assertion call.

Now handle refunded with its own return case. The sink is satisfied, while the outsider test still reports TS2578. If refunds are an intentional new input, update that test into an accepted-case test and verify its behavior. If admission was accidental, restore the input union. Different failures identify different contract decisions; there is no guarantee that a fixed number of probes must always fail together. The [exhaustiveness owner](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) explains control flow and runtime fallbacks in full.

### 4) **Common confusion**

An expected diagnostic is not a runtime throw, and suppression does not remove executable code. Running port.test-d.mts would reach the invalid numeric call even though its static suite passed. Keep a compile-only suite selected for checking and out of the runtime build, or intentionally wrap invalid-input behavior in a runtime assertion.

A green expected-error test also does not prove a particular error code or every rejected input. The typo experiment is the counterexample. Choose representative contract boundaries, inspect the actual diagnostic and combine static and behavior tests where their responsibilities differ.

### 5) **Performance note**

These suites add compiler work by checking source and test expressions. Directives do not establish a fixed per-test cost, and this lesson measures no timing or assertion-count budget. The separate build avoids executing the invalid calls; the directive itself does not provide that separation. Measure a growing suite before changing its project or CI layout.

### 6) **Mentor note**

Ask a learner to predict four changes: widening the port input, misspelling its name, deleting its range check and growing ShipState. They should identify the observed static or runtime signal and explain the typo's false positive. Review the actual selected file, command and unsuppressed diagnostic, not merely the presence of an expected-error comment.
