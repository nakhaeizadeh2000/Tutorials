## 1.3. Negative type tests with ts-expect-error

### 1) **`@ts-expect-error` as a lock** (rejected shapes pinned, re-admission breaks the test)

**Definition** — `// @ts-expect-error` suppresses the *next line's* type error — and errors itself (`Unused '@ts-expect-error' directive`) when the next line has *no* error. That inversion makes it a lock: the rejected call stays rejected (directive consumed, suite green); anyone loosening the signature re-admits the call (directive unused → suite red, pointing at the exact line).

**What problem it solves / history** — validation rules (`parseCard`, `toPort`, branded-ID factories) erode silently: a well-meaning `string` widening re-admits malformed input, unit tests still pass (behavior unchanged for valid inputs), production discovers the bypass (fraud queue, 5.1 incident class). Negative tests pin every rejection: the bypass breaks the build before review ends.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), place one `@ts-expect-error` probe per public rejection rule (invalid card shape, out-of-range port, unbranded ID into branded slot); keep a one-line comment stating *why* rejection is the contract (future readers distinguish intentional locks from accidental errors).

**Runnable example** — locks on rejected shapes (good vs bad, `tsc --strict`):

```typescript
// good — rejection pinned (loosening the signature breaks THIS line, loudly)
function toPort(n: number): number {
  if (!Number.isInteger(n) || n < 1 || n > 65535) throw new Error("bad port");
  return n;
}
// lock illustration — in real test-d files uncomment BOTH lines below to activate:
// "@ts-expect-error — string ports rejected" (contract: numeric ports only)
// const badPort = toPort("80"); // ❌ errors when active (string not assignable to number)
console.log(toPort(80)); // 80 — acceptance tested by behavior; rejection locked by the directive above
// bad — acceptance-only tests (toPort(80) === 80 green; toPort("80") re-admitted silently after a widening)
// fix — @ts-expect-error per rejection rule (every no a test, not a hope)
```

```typescript
// good — branded-ID slot locked (unbranded strings stay out — 04/3.2 mechanics under test)
declare const brand: unique symbol;
type UserId = string & { readonly [brand]: "UserId" };
function loadUser(id: UserId): string { return `user:${id}`; }
declare const someId: UserId;
// lock illustration — in real test-d files uncomment BOTH lines below to activate:
// "@ts-expect-error — raw strings rejected" (must pass through the validating factory)
// const badLoad = loadUser("u-1"); // ❌ errors when active (string not assignable to UserId)
console.log(loadUser(someId)); // user:… — branded acceptance flows; raw-string admission locked out
// bad — factory bypass untested (direct string calls compile after any signature loosening)
// fix — negative probe on every branded parameter (the brand's whole point, pinned)
```

```typescript
// good — unused-directive signal honored (stale locks removed, not feared)
// lock form in real test-d files: "@ts-expect-error" above the rejected call (if the call ever compiles, tsc reports UNUSED directive — the lock working)
console.log("locks-checked"); // locks-checked — CI runs tsc --noEmit (unused directives fail the gate — see 3.3)
// bad — deleting red directives to "fix CI" (removing the lock instead of the regression — review must catch)
// fix — red directive means EITHER intentional loosening (update contract + probe together) OR regression (revert) — never silent deletion
```

**Common confusion** — "commented-out code is the same" — commented code checks *nothing* (no directive, no unused-signal); `@ts-expect-error` *asserts present rejection* (removing the error breaks the build — active lock vs dead text). "negative tests slow the suite" — directives cost one diagnostic each (microseconds); the bypass incidents they prevent cost postmortems. "one negative test per file suffices" — per *rejection rule* (each validation branch gets its lock — matrices in test-d files, pins inline).

**Performance note** — directives add zero emit (comments) and one diagnostic slot each at check time (negligible); keep probes counted (rejection rules number in dozens, not thousands).

**Mentor note** — PR rule: a PR adding a validation branch without its `@ts-expect-error` probe is incomplete — the branch's rejection is untested. Teach the unused-directive error as *good news* (the lock firing, not noise).

### 2) **`@ts-ignore` vs `@ts-expect-error` discipline** (suppression vs testable lock)

**Definition** — `// @ts-ignore` suppresses next-line errors *unconditionally* (no error → silent no-op); `// @ts-expect-error` *requires* an error (no error → `Unused '@ts-expect-error' directive` error). One hides problems; the other tests that a problem exists — opposite semantics sharing a syntax family.

**What problem it solves / history** — `@ts-ignore` migrations ("suppress 200 errors, fix later") fossilize: fixes land, suppressions stay (silent no-ops hiding nothing, exempt from review), and new errors on the same lines vanish into pre-existing suppressions. `@ts-expect-error` self-cleans (fixed lines error as unused → removed in the same PR) and never masks new errors beyond its line.

**Modern guidance** — ban `@ts-ignore` in lint (`@typescript-eslint/ban-ts-comment` with `ts-ignore: true` — see 16/2.1 tiers); allow `@ts-expect-error` only with a trailing reason comment (`// @ts-expect-error — ports are numeric (see toPort)`). Migration strategy: convert each `@ts-ignore` to `@ts-expect-error` *before* fixing (converting surfaces already-fixed lines as unused — free progress).

**Runnable example** — discipline contrast (good vs bad, `tsc --strict`):

```typescript
// good — expect-error with a reason (self-cleaning, reviewable intent)
// lock form: "@ts-expect-error — numeric ports only" above the rejected call (reason attached: the contract, not just the suppression)
console.log("reasoned-lock"); // reasoned-lock — every lock carries its why (future loosening debates the reason)
// bad — bare @ts-ignore (no reason, no unused-signal — fossilizes past its usefulness)
// fix — ban-ts-comment for ts-ignore (lint-enforced) + reason comments on every expect-error (review-enforced)
```

```typescript
// good — migration conversion first (ts-ignore → ts-expect-error, then fix red lines)
function legacy(x: unknown): string {
  // migration form: "@ts-expect-error — legacy any-flow" above the next line (converting first: already-clean lines go red-unused immediately)
  if (typeof x === "string") return x;
  throw new Error("legacy");
}
console.log(legacy("ok")); // ok — conversion surfacing free progress (unused directives mark fixed lines)
// bad — fixing under ts-ignore (fixed lines stay suppressed — coverage unknown, regressions masked)
// fix — convert-then-fix (each fix deletes its directive — progress visible in the diff)
```

**Common confusion** — "they differ only in strictness" — they differ in *direction*: `ts-ignore` asserts nothing (masking); `ts-expect-error` asserts an error exists (testing) — different tools, not different strengths. "reason comments are noise" — reason-less locks get deleted as cruft during cleanups (the 5.1 bypass class re-enters); reasons survive cleanups (intent documented survives tidiness).

**Performance note** — both are comments (zero emit/check cost beyond the diagnostic slot); lint rule cost is per-file syntax scan (trivial — 16/2.1 tier math unaffected).

**Mentor note** — enable `ban-ts-comment` on day one of any strictness migration (13/3.3 sequencing): the rule converts suppression debt into a countable, shrinkable backlog.

### 3) **Exhaustiveness probes** (never-sink plus error-line assertions)

**Definition** — the 07/3.2 `assertNever` sink *plus* a negative probe: after the exhaustive switch, `assertType<IsNever<Remaining>>()` (positive: remainder is empty) and a `@ts-expect-error` call passing an unhandled member (negative: unhandled members stay unhandled). Together they test exhaustiveness from both sides — handled members flow, unhandled members error.

**What problem it solves / history** — switches grow members (`"refunded"` added to `"paid" | "shipped"`) while handlers lag: without probes, the new member falls into `default` (silent wrong behavior) or a non-`never` sink (no signal). Dual probes break the build at the handler (sink remainder non-never) *and* at the negative test (new member admitted nowhere) — the member cannot land without its handling.

**Modern guidance** — every discriminated-union handler gets both probes: `default: return assertNever(x)` (sink) + `assertType<IsNever<Exclude<...>>>` + one `@ts-expect-error` for a representative unhandled literal. When the union legitimately grows, update handler + probes in one PR (the red probes *are* the TODO list).

**Runnable example** — dual-probe exhaustiveness (good vs bad, `tsc --strict`):

```typescript
// good — sink plus remainder probe (both sides tested)
function assertNever(x: never): never { throw new Error(`unreachable:${String(x)}`); }
type IsNever<T> = [T] extends [never] ? true : false;
declare function assertType<T extends true>(): void;
type Order = "paid" | "shipped";
function label(o: Order): string {
  switch (o) {
    case "paid": return "P";
    case "shipped": return "S";
    default: return assertNever(o); // sink (new members break HERE)
  }
}
assertType<IsNever<Exclude<Order, "paid" | "shipped">>>(); // remainder empty (positive probe)
console.log(label("paid")); // P — exhaustiveness tested (sink + remainder + negative below)
// bad — sink without probes (assertNever present but remainder unchecked — sink bypassed via non-never default)
// fix — triple: sink + IsNever remainder + @ts-expect-error unhandled (no single point of silence)
```

```typescript
// good — negative probe for unhandled members (representative outsider stays out)
type ShipState = "paid" | "shipped";
function handleShip(s: ShipState): number { return s === "paid" ? 1 : 2; }
// lock illustration — in real test-d files uncomment BOTH lines below to activate:
// "@ts-expect-error — refunded is not a handled state" (adding it must update handler + probes together)
// const badHandle = handleShip("refunded"); // ❌ errors when active ("refunded" not assignable to ShipState)
console.log(handleShip("paid")); // 1 — outsider locked out (union growth forces handler work, loudly)
// bad — handler-only coverage (unhandled members untested — growth lands silently)
// fix — negative outsider probe per handler (growth breaks the probe before production notices)
```

**Common confusion** — "sink alone suffices" — sinks prove *current* handlers exhaustive; probes prove *future* growth handled (different times, both needed). "probes duplicate the switch" — probes duplicate the *member list* (cheap, one line) precisely so drift between list and handler errors (duplication as detection, not debt).

**Performance note** — `Exclude` + `IsNever` instantiate per probe (one conditional each — negligible); switches themselves unaffected (probes live outside the function).

**Mentor note** — demonstrate by adding a member live: watch all three probes fire (sink, remainder, negative) — the "cannot land without handling" moment teaches exhaustiveness-as-tests better than any diagram.
