## 4.1. Type-testing checklist — mental models mentors insist on

Review a type test as an argument: identify the promise, the selected input, the operation that checks it, the observed failure and the limit of that evidence. A green command is useful when those pieces agree. A familiar assertion spelling or a fixed number of jobs cannot supply the missing argument.

This checklist synthesizes the domain's worked fixtures. Follow their exact tool and runtime versions when reproducing a case. It introduces no additional runner, timing measurement or production incident.

### 1) **Choose the relation and make its result observable**

Start with what a consumer needs. Directional assignability can express that a result fits a supported target. A stricter comparison can protect a precise representation or literal union. State the direction: a string result does not fit an "a" | "b" target, while both types fit a broad string target. Assignability does not universally miss widening.

The [assertion owner](<../1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) demonstrates a precise gate failing after widening while the broad target still passes. It also shows mutually assignable intersection and flat-object types that its Equal helper distinguishes. That is a reason to choose the tested relation intentionally, not to require Equal on every public signature.

A computed false type is not itself a compiler failure. A constraint gate makes the result observable, and a selected compiler project must check it. Prefer alias-only gates for compile-only tests. An ambient declaration supplies no runtime implementation; its emitted call can fail with ReferenceError.

For generic helpers, select legal cases that expose promised differences, such as a mixed union or readonly tuple. The [generic matrix](<../3. Type Tests in Practice/3.1. Testing generics and conditional types.md>) tests those differences and its special-type results. Avoid a mandatory boundary quota that ignores the helper's constraints.

### 2) **Separate static rejection from runtime validation**

An active expected-error directive requires a diagnostic on its following line. It does not require the reason written in a trailing comment. The [negative-test fixture](<../1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>) demonstrates a misspelled callee making the suite pass for the wrong reason. Inspect the unsuppressed diagnostic when introducing or changing a negative test.

A number annotation admits 0 even when a port validator rejects it at runtime. Test string-versus-number admission statically and numeric range behavior with runtime assertions. One expected-error directive per validation branch would confuse those responsibilities. Choose representative rejected type operations and meaningful runtime boundaries instead.

When a directive becomes unused, decide whether acceptance changed intentionally. Restore a regression or update the contract and its tests together. Do not delete a failed probe solely to make CI green. For an exhaustive union handler, the existing never sink detects newly unhandled members; an outsider rejection tests a separate input-admission promise.

### 3) **Check substitutes' signatures and assert their behavior**

A double can acquire a checked signature through an explicit annotation, a generic argument, an implementation's inference or a checked injection boundary. The [actual mock fixture](<../2. Typed Test Doubles/2.1. Mocking functions with full type safety.md>) demonstrates both explicit and inferred signatures. It also shows a correctly typed wrong name passing check and failing its behavior test.

An any escape removes static protection at that use, but does not make a real runtime assertion incapable of failing. Review why an escape exists, what it bypasses and whether a checked fixture can replace it. A blanket grep is not a complete analysis of inferred permissive types or runtime coverage.

The [spy and generic-fake suite](<../2. Typed Test Doubles/2.2. Spies stubs and fakes over generics.md>) supplies useful contrasts: a spy initially calls through, an override changes behavior, clearing history keeps the override, and restoration returns the original method. Its store can satisfy the interface while a broken get method fails the shared behavior contract. Define the properties a fake models and preserve separate integration evidence for a real adapter.

### 4) **Connect each command to its actual boundary**

Use this table when reviewing the command list:

| Question | Evidence to inspect | What remains outside that evidence |
|---|---|---|
| Does the selected static relationship hold? | Compiler project, file membership, gate and deliberate failing variant | Unselected probes and runtime behavior |
| Does a tool-specific type suite work? | Actual [tsd or Vitest type-mode run](<../1. Type Assertions in Tests/1.2. tsd expect-type and type-testing libraries.md>), compatible compiler API and failure contrast | Other tool versions and ordinary runtime execution |
| Does async work complete and release resources? | [Awaited outcome, abort and timer assertions](<../2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) | Real network cancellation and host scheduling latency |
| What does a package consumer receive? | [Fresh installed-tarball imports](<../3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>), resolved declarations and supported runtime tests | Unpromised resolver/compiler combinations |
| Does the workflow preserve failures? | [Actual collector statuses](<../3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>) and surrounding job policy | Hosted merge protection that has not been configured or tested |

Some checks overlap and some need another check's artifact first. Choose their composition from those dependencies. Ordinary tsc can check source and alias-only tests in one selected project; a dedicated suite is useful when it checks another relevant boundary. No fixed three-job layout is required.

For migration baselines, inspect accepted diagnostic identities and omitted scope. An unchanged count can hide one fixed error and one new error. For package changes, a strict signature assertion is a signal to review compatibility, not an automatic semantic-version verdict.

### 5) **Common confusion**

A review can have all its commands green and still omit the important probe. The CI fixture demonstrates that removing test-d from include hides a deliberately false assertion. Check membership as well as status. The same reasoning applies to excluded entry points and narrowed tool profiles.

A compile-time promise and a runtime promise can also change independently. Promise<T> describes a fulfilled value, not every rejection reason. An installed package can resolve declarations correctly and still subtract where its contract requires addition. Decide what each assertion actually establishes.

### 6) **Performance note**

Type predicates consume compiler work; runtime doubles retain state; artifact checks build, pack and analyze files. Their cost depends on the actual suite and environment. These examples supply pass/fail evidence without a universal per-probe cost or parallel-job speed formula. Measure before choosing caches, job splits or matrix size, while keeping the relevant checks intact.

### 7) **Mentor note**

Use this review exercise: a pull request adds an optional third parameter, updates a strict Parameters assertion, and reports that existing calls pass. Ask whether this alone proves a breaking change or complete compatibility. A sound answer identifies the stricter representation change, checks supported call and reflective uses, and asks for the relevant consumer matrix. Then remove the type-test directory from the check and ask why green no longer supplies the same evidence.
