## 6.1. Common interview QA — testing types

### 1) **`Equal` vs assignability — what does each prove, and which catches drift?**

**Definition** — `Equal<A, B>` proves *identity* (mutual substitutability down to literals/optionality/`any`-vs-`unknown` — 1.1's conditional-identity trick); assignability (`A extends B`, or `const x: B = a`) proves *compatibility* (fits inside — widening allowed). Drift-catching needs identity (moves fail); compatibility checking needs assignability (intentional widening allowed).

**What problem it solves / history** — candidates (and suites) asserting assignability where identity belongs: widened returns passing, downstream switches rotting. The interview separates mechanical knowledge (writing both forms) from judgment (choosing per contract — identity default, containment deliberate with a reason comment).

**Modern guidance** — answer shape: define both, demo the widening (`"a"|"b"` → `string` passing assignability, failing `Equal`), state the default (identity) and the exception (documented widening contracts use `Extends` — 4.1 part 1). As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS).

**Runnable example** — the demo to whiteboard (good vs bad, `tsc --strict`):

```typescript
// good — widening visible under Equal, invisible under assignability (the interview demo)
export {}; // module marker (consistent module scope across fences)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
function current(): "a" | "b" { return "a"; } // widen this to string: assignability still green, Equal red
type CurrentReturn = ReturnType<typeof current>; // alias (no >>> closers — scanner-safe per 3.1 lesson)
assertType<Equal<CurrentReturn, "a" | "b">>(); // identity (widening breaks HERE)
console.log(current()); // a — identity demo (one widening, two verdicts — the whole lesson in four lines)
// bad — "assignability tests are type tests" (compatibility ≠ identity — drift invisible by construction)
// fix — Equal default (identity proves contracts; assignability proves compatibilities — different tools)
```

```typescript
// good — strong follow-up (optionality distinction — Equal sees what extends hides)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Extends<A, B> = A extends B ? true : false;
declare function assertType<T extends true>(): void;
interface Opt { a?: string }
assertType<Extends<{ a: string | undefined }, Opt>>(); // required-with-undefined fits optional (present-possibly-undefined satisfies absence-allowed — TRUE, pinned)
// assertType<Extends<Opt, { a: string | undefined }>>(); // ❌ errors when uncommented (absence ≠ explicitly-undefined without exactOptionalPropertyTypes — 04/1.2 matrix)
// lock illustration — the follow-up's point: even SENIORS must check (verdicts depend on flags — direction matters, memory lies)
console.log("follow-up"); // follow-up — optionality follow-up (flag-dependent verdicts — the deep cut)
// bad — asserting optionality verdicts from memory (flag-dependent — memory lies, compilers don't)
// fix — probe flag-dependent claims live (the interview move AND the engineering move — verify, don't recite)
```

**Common confusion** — "identity is always stricter" — identity is *differently* strict (exactOptionalPropertyTypes off: optional-vs-undefined verdicts surprise — strictness flag-dependent, see 04/1.2). "whiteboard Equal from memory" — interviewers accept the *idea* (conditional-identity) over the exact trick (nobody memorizes the double-arrow form — describe, then derive).

**Performance note** — interview demos cost one instantiation (nothing); production matrices stay representative (3.1 discipline — branch-changing classes only).

**Mentor note** — hiring signal: candidates choosing identity-by-default with reasoned exceptions outrank candidates reciting the `Equal` trick verbatim (judgment over memory, every time).

### 2) **`@ts-expect-error` vs `@ts-ignore` — which is testable, and why?**

**Definition** — `@ts-expect-error` *requires* a next-line error (unused → `TS2578` error — the directive tests rejection); `@ts-ignore` suppresses *unconditionally* (unused → silent no-op — the directive hides everything). Testable vs masking — opposite semantics (1.3 part 2).

**What problem it solves / history** — suppression fossilization (fixed lines staying suppressed — coverage unknown) vs self-cleaning locks (fixed lines erroring unused — progress visible). The interview probes migration judgment (convert-then-fix) and lint policy (`ban-ts-comment` — 16/2.1).

**Modern guidance** — answer shape: state the unused-signal difference, give the migration play (convert `@ts-ignore` → `@ts-expect-error` first — free progress surfacing), cite the lint rule (`ban-ts-comment` with `ts-ignore: true`). Reason comments on every lock (intent surviving cleanups).

**Runnable example** — the contrast to whiteboard (good vs bad, `tsc --strict`):

```typescript
// good — expect-error self-cleans (fixed lines go red-unused — progress visible in the diff)
export {}; // module marker (consistent module scope across fences)
function strictParse(raw: string): number {
  const n = Number(raw);
  if (Number.isNaN(n)) throw new Error("nan");
  return n;
}
// lock form: "@ts-expect-error — numeric strings only" above strictParse("abc" as never) in real test-d files
console.log(strictParse("42")); // 42 — locks self-maintaining (contract moves break probes — maintenance by redness)
// bad — ts-ignore fossilizing (suppressions outliving their errors — new errors masked on pre-suppressed lines)
// fix — ban-ts-comment (ts-ignore unrepresentable — locks only, forever)
```

**Common confusion** — "they're interchangeable strictness levels" — different *directions* (testing vs masking — not strengths). "reason comments are optional" — reason-less locks get cleanup-deleted (bypasses re-entering — 5.1 part 3's lesson restated).

**Performance note** — directives are comments (zero cost); fossilized suppressions cost coverage-unknown (unbounded — ban them).

**Mentor note** — follow-up: "how do you migrate 200 `@ts-ignore`s?" (convert-then-fix + per-class budgets per 3.3 part 3 — process answer, not just API answer).

**Cross-links** — lock discipline → [1.3. Negative tests](<../1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>); lint tiers → [2.1. typescript-eslint](<../../../16 Tooling Language Server and Ecosystem/sections/2. ### 3) **How do you mock a generic function without losing its signature?**

**Definition** — pin the double with the real signature: `const mock: typeof fn` (2.1 — monomorphic functions) or explicit instantiation `const mock: Fn<string>` / generic-preserving wrappers (generic functions — per-call inference retained via the generic annotation, not a concrete instantiation).

**What problem it solves / history** — `any`-mocks collapsing generic call sites (inference untested — wrong explicit arguments passing vacuously); concrete-instantiation mocks (`Fn<string>` used where `Fn<number>` needed — half the call sites untested). Signature-preserving doubles keep inference honest per call.

**Modern guidance** — answer shape: `typeof` pin first (exact signature, inference intact); explicit type arguments where the seam instantiates (`Repo<User>` fakes per entity — 2.2 part 3); `Record`-exhaustive answer tables for finite generic domains (2.2 part 2). Never `any`, never bare `vi.fn()` (2.1 lint tier).

**Runnable example** — generic doubles keeping inference (good vs bad, `tsc --strict`):

```typescript
// good — typeof pin preserving genericity (per-call inference intact through the double)
export {}; // module marker (consistent module scope across fences)
function first<T>(items: T[]): T | undefined { return items[0]; }
const double: typeof first = (items) => items[0]; // generic preserved (T inferred per call — not fixed)
console.log(double([1, 2])); // 1 — inference through doubles (genericity kept — call sites honestly checked)
console.log(double(["a"])); // a — second instantiation (same double, fresh inference — the generic contract tested)
// bad — concrete mock (T fixed to string — number call sites untested, inference collapsed)
// fix — typeof pins on generics (inference flows through — doubles transparent to type arguments)
```

**Common confusion** — "generics need generic mocks" — `typeof` pins *are* generic-preserving (the annotation carries the type parameters — no special machinery). "explicit arguments per call in tests" — let inference work (explicit args only where inference fails — 08/1.2's three situations, same rule in suites).

**Performance note** — generic doubles instantiate per call site (normal generic cost — test-time only); collapsed-concrete doubles cost coverage (untested instantiations — incidents).

**Mentor note** — live follow-up: "show a double that fixes `T` to `string` and tell me which call sites go untested" (concrete-vs-generic reasoning on the spot).

**Cross-links** — typed mocks → [2.1. Typed mocks](<../2. Typed Test Doubles/2.1. Mocking functions with full type safety.md>); inference control → [1.2. Inference](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>).

### 4) **Where do type tests run in CI — and what does each gate catch?**

**Definition** — three gates (3.3): `tsc --noEmit` (whole-program contracts — inline pins, directives, matrices), `tsd`/`vitest --typecheck` (surface + packaging — declarations, resolution), unit runners (behavior — values). Triage order: statics first (contracts), surface second (packaging), behavior last (logic).

**What problem it solves / history** — lumped/optional statics (drift compounding, symptom hunts under red statics). Split required gates give layered signals (each red routing to its fix — contracts vs surface vs logic).

**Modern guidance** — answer shape: name all three, state each gate's regression class with an example (widened return → gate 1; missing types-condition → gate 2; wrong total → gate 3), state triage order and why (symptoms after contracts). Baselines for legacy (ratchet — 3.3 part 3).

**Runnable example** — gate-to-regression mapping (good vs bad, `tsc --strict`):

```typescript
// good — gate-1 example (widened return breaking noEmit — contracts first)
export {}; // module marker (consistent module scope across fences)
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
function total(items: number[]): number { return items.reduce((a, b) => a + b, 0); }
assertType<Equal<ReturnType<typeof total>, number>>(); // gate 1 (shape pinned — widening breaks here)
console.log(total([1, 2])); // 3 — gate 3 (value proven — logic green beside statics green)
// bad — "CI runs tests" (which gates? which order? — vague answers hiding lumped pipelines)
// fix — three named gates + triage order (precision about layers — senior signal)
```

**Common confusion** — "more gates slow merging" — parallel gates wall-time ≈ max (often faster than lumped jobs — plus symptom-hunts deleted). "unit green means shippable" — unit green + statics red means contracts moved (shipping anyway = flag-day debt — gates block, deliberately).

**Performance note** — gate costs: noEmit (tens of seconds, cached), tsd (seconds), unit (seconds) — parallel (total ≈ slowest).

**Mentor note** — strongest close: "red type tests page like red unit tests" (severity parity — culture as configuration, 4.1 part 4).

**Cross-links** — gate composition → [3.3. CI gates](<../3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>); baseline ratchets → [3.3 part 3](<../3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>).

### 5) **When do hand-rolled assertions beat tsd/expect-type — and when don't they?**

**Definition** — the boundary rule (1.2 part 3): apps (no declaration consumers) → hand-rolled `Equal` + `assertType` (zero deps, mechanics visible); published packages (declarations ARE the product) → `tsd` (test-d convention) + `expect-type` (readable failures in suites) + `attw`/publint (packaging gates).

**What problem it solves / history** — cargo-culted `tsd` in apps (config + CI for no packaging boundary) vs fifty bespoke helpers in SDKs (no contributor convention, inconsistent messages). The interview probes cost-benefit judgment (dependencies + config + jobs vs messages + convention + integration).

**Modern guidance** — answer shape: state the consumer question ("does anyone import our declarations?"), route by answer (no → hand-rolled; yes → libraries), note the learning order (mechanics first via hand-rolled, convenience second — 1.2 mentor note). Failure-message quality as the tiebreaker at package scale (expanded diffs vs `false`-constraint — 1.2 part 2).

**Runnable example** — the shared kit vs library call (good vs bad, `tsc --strict`):

```typescript
// good — hand-rolled kit sufficing for apps (five lines, full coverage)
export type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
export declare function assertType<T extends true>(): void;
export type Extends<A, B> = A extends B ? true : false;
export type IsNever<T> = [T] extends [never] ? true : false;
assertType<Equal<string, string>>(); // sanity (kit verified — every matrix imports these four)
console.log("kit"); // kit — apps served (no packaging boundary — libraries adding cost without benefit)
// bad — "always use libraries" (deps + config + jobs for zero packaging boundary — cost without benefit)
// fix — consumer-question routing (boundary decides — apps hand-rolled, packages tooled)
```

**Common confusion** — "libraries obsolete hand-rolled" — libraries *package* the tricks (messages + convention); the tricks remain the mental model (fluent failures debugged by expanding to `Equal`). "more tooling signals seniority" — *appropriate* tooling signals seniority (restraint where boundaries absent — judgment over accumulation).

**Performance note** — kit imports cost one module (negligible); library stacks cost installs + resolution + CI jobs (justified at packaging boundaries only).

**Mentor note** — hiring signal: candidates asking "who consumes the declarations?" before recommending tooling (boundary-first reasoning — staff-level instinct).
