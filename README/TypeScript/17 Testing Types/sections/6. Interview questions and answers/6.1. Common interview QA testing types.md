## 6.1. Common interview QA — testing types

Use these questions to explain what a test establishes and where its evidence stops. A useful answer names the contract, chosen check, actual failing case and remaining limitation. The linked owners contain the complete tested fixtures and their version requirements; the answers here do not introduce another test runner.

### 1) **What do equality and assignability assertions establish?**

Assignability asks whether a source fits a target. A comparison helper asks its own stricter question about two type representations. Choose the relation the consumer contract needs. Neither is universally the correct default.

For a concrete follow-up, consider a return changing from "a" | "b" to string. Both results fit a broad string target, but string does not fit an "a" | "b" target. The [assertion fixture](<../1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) demonstrates a broad assignability gate surviving and a precise comparison gate failing. An answer that says assignability always permits widening omits the decisive target and direction.

Ask whether mutually assignable object types must pass the helper's Equal test. That owner shows an intersection and a flat shape that fit both ways yet compare false. It also shows optional absence differing from required presence. A good explanation gives the actual representation or flag-sensitive distinction instead of treating Equal as a universal identity operator.

### 2) **Why is expected-error useful, and what can fool it?**

An active @ts-expect-error directive suppresses diagnostics on the following line and reports TS2578 when none exists. @ts-ignore lacks that unused signal. That makes expected-error useful for a deliberate static rejection test, provided the intended operation is actually checked.

The [negative-test fixture](<../1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>) shows the limitation: misspelling the callee can supply a different diagnostic and leave the suite green. The reason comment is not matched against an error code. Inspect the unsuppressed failure and keep the expression focused.

Ask whether a number-typed port validator can reject 0 through a directive. Its parameter admits 0 statically, so the range rule needs a runtime assertion. Ask whether every ignore should be converted mechanically: compiler-version compatibility can make a line valid in one supported version and invalid in another. Review purpose and support conditions rather than reciting a blanket migration rule.

### 3) **How can a double preserve a generic contract?**

First distinguish the generic scope. A function generic per call must support the promised relationship for each call's type argument. A Store<T> instance fixes its payload type for that instance; it need not accept unrelated payloads on later calls. A string-only implementation is not a substitute for an arbitrary per-call generic merely because one test uses strings.

An annotation carrying the original generic function type can preserve that relationship when its implementation genuinely satisfies it. A framework's wrapper types need inspection too; do not assume every utility involving Parameters or ReturnType preserves every overload or input/output correlation. Choose a checked adapter or stateful fake when it makes the intended scenario clearer.

The [actual mock lesson](<../2. Typed Test Doubles/2.1. Mocking functions with full type safety.md>) demonstrates explicit and inferred signatures for its monomorphic seam. The [generic-fake fixture](<../2. Typed Test Doubles/2.2. Spies stubs and fakes over generics.md>) checks separate string, number and undefined stores. Follow up by asking why a get method that always returns absent still satisfies the interface: the missing property is behavioral fidelity, which its contract tests detect. For the underlying scope mechanics, use the [generic-scope owner](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>).

### 4) **Which checks belong in CI, and what does green mean?**

Start from the inputs. An ordinary compiler project can check source and selected alias-only assertions together. A dedicated tsd or Vitest type suite checks its tool-specific assertions. A fresh installed package consumer checks resolved declarations and entry points. Runtime tests check observed behavior. Add the checks your support contract requires and preserve their failures in the workflow; no fixed job count is necessary.

The [actual CI collector](<../3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>) runs compiler and runtime commands, then demonstrates static-only, behavior-only and combined failures. It also shows a false green after removing the type probe from include. Follow up by asking for selected files, resolved paths and exit statuses, not just a screenshot of green jobs.

For a package, the [installed-surface fixture](<../3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) tests actual ESM/CommonJS declarations and runtime behavior. Neither health-tool success nor a clean type suite certifies every consumer or logic path. Diagnose overlapping failures from their actual cause; static green does not rule out an untested or asserted-away shape defect.

### 5) **When should a project use assertion aliases, tsd or fluent tools?**

Choose by the property, diagnostics, contributor workflow and compatible compiler interface. A small alias-only suite can protect precise type relationships without a callable runtime helper. tsd is useful for a generated declaration surface and its special assertions. Fluent assertions can fit an existing test workflow, provided its actual type-checking mode runs. Installed-consumer and package-health checks answer additional artifact questions.

The [real tool fixtures](<../1. Type Assertions in Tests/1.2. tsd expect-type and type-testing libraries.md>) show these differences through actual commands and negative variants. An application can benefit from fluent type tests even without publishing declarations; a package can use aliases where they express a useful contract. The app/package label alone does not choose the entire stack.

Ask what happens if a team simply runs an ambient declared assertion call as JavaScript. Declare supplies no implementation, so the retained call can throw ReferenceError. Conversely, a real fluent API does not validate its arguments' values merely because TypeScript checks their types. Keep compile-only and runtime execution policies explicit.

### 6) **Common confusion**

A type-test failure is evidence that a tested relationship changed, not an automatic release-version verdict. The installed-surface lesson adds an optional parameter: the strict Parameters tuple assertion fails while existing two-argument calls still check and run. Review both supported calls and relevant reflective uses before deciding compatibility.

A brand also does not prove the factory's validation is correct. The [pitfall fixture](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by type-testing misunderstandings.md>) independently breaks branded input admission and runtime format checking. Different tests should expose those different changes.

### 7) **Performance note**

These answers justify checks from evidence rather than assumed cost. Generic instantiation, tool setup, recorded mock calls and artifact consumers have different workloads. The linked examples establish outcomes without a universal per-assertion time or parallel-job speedup. Explain measurement needs before proposing job splits, caches or a larger test matrix.

### 8) **Mentor note**

Ask for a prediction, one controlled change and the observed failure. Useful follow-ups include the typo false positive, the typed-but-wrong fake and the excluded probe. Assess whether the learner revises their explanation when the output contradicts a broad claim. Memorizing an equality trick or naming more tools does not replace identifying the checked contract and its limits.
