## 6.1. Common interview QA — objects interfaces and type aliases

These five questions test whether a learner can explain the resulting object contract, identify the evidence behind it and diagnose a meaningful failure. A short answer should state the rule and its conditions; a stronger answer can predict the probe's result and name the owner of the full explanation. Vocabulary or an operator preference alone is insufficient.

The complete probe uses TypeScript 7.0.2 and Node 20.20.2, checked 2026-10-13. The optional-mode comparison names its separate setting. No interview answer below claims a benchmark, live framework integration or a production incident.

### 1) **When does interface versus alias matter?**

Both can describe structural object contracts. Interface declarations can merge compatible members. An alias can name a primitive, union, tuple, mapped or conditional expression. An interface can extend a compatible computed object type, including a concrete utility result; using a utility does not automatically force every downstream name to be an alias.

There are also contextual assignability differences: a plain alias-shaped object may satisfy an implicit dictionary contract where a named interface with the same members does not. Treat the two spellings as overlapping capabilities, not a universal identity or a strict-versus-loose division. A fresh ambient alias declaration is legal; attempting to redeclare an existing alias is different from introducing a fresh name. The [interface/alias owner](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>) verifies those distinctions and intended extension points.

Follow-up: if two required/optional declarations disagree on modifiers, does merging soften the property? No. The tested merge reports a declaration conflict. The augmentation owner owns the full multi-file program and provider checks.

### 2) **Why can an extra member pass through a variable but fail in a fresh literal?**

An existing value can structurally satisfy a target that requires fewer members. A fresh literal at a checked creation site also receives an excess-property check. The literal error catches a likely mistake where data is authored; assigning a narrower type later does not remove extra runtime fields.

Do not extend that answer to a missing required member: a variable still cannot provide one that it lacks. Likewise, a spread's inherited members differ from directly written members, which can still trigger an excess-property error. An assertion bypasses evidence rather than making a typo intentional. The [shape owner](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) contains the fuller contrasts.

Follow-up: should the consumer always become wider to accept an extra field? Only when it actually needs that field. Otherwise correct a typo, expose the intended smaller view, or validate data at its boundary.

### 3) **How do extends and intersection differ on conflicts?**

Compatible object heritage and intersections can describe similar resulting requirements. Heritage rejects an incompatible member in the declaration. An intersection requires both contracts; a required string-and-number member becomes never, so ordinary construction fails later. Naming an interface or using extends does not supply nominal identity.

Optional conflicts also require a presence analysis. An omitted optional property can satisfy both sides even when incompatible present values cannot. In an optional-string/required-string-or-undefined intersection, explicit undefined is accepted under the default optional setting but rejected with exact optional properties. A required string refinement can extend an optional string parent legally. These are contract distinctions, not an unconditional operator rule. The [composition owner](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) demonstrates both modes.

Follow-up: is an `as never` value a valid proof that the required conflict has an ordinary inhabitant? No. The assertion bypasses the very requirement the question tests. Use a live type assertion for the resulting member and a rejected construction as evidence.

### 4) **What does a branded object protect, and what must happen after JSON?**

A phantom marker can make otherwise equal-shaped domain objects incompatible statically. A checked factory localizes the assertion and the invariant it claims. The marker is absent at runtime in this construction pattern; serialization does not transport TypeScript's proof. Parse the deserialized unknown value and reconstruct the needed contract. Ordinary parsing also does not construct a class instance.

Whole spread inference may retain an aggregate marker. A Pick of just id omits an unselected aggregate marker while retaining an id field's own brand. Decide whether the consumer needs a whole domain object, a branded scalar or a public projection. A class with a private member offers declaration-based instance compatibility plus runtime construction; ordinary private modifiers can be stripped in the tested setup. Parameter properties require transformation and fail erasableSyntaxOnly. The [branding owner](<../3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) verifies those facts.

Follow-up: does one construction assertion prove that validation is correct? No. A prefix check proves only the chosen prefix contract, and an incorrect predicate or arbitrary assertion can still bypass the intended discipline. Test malformed input and state the invariant.

### 5) **What does satisfies retain that an assertion may expose differently?**

Satisfies checks compatibility and retains contextual inference. In the Route probe, method remains get while path is string. Asserting Route exposes its broader method union; asserting a narrower target can instead narrow, so as does not always widen. A const assertion preserves the literal structure's readonly types but does not freeze the runtime object.

Choose an annotation when the exposed target contract is the intended API, satisfies when the checked source precision serves derivation, and an assertion only when its independent justification is clear. None parses unknown data. The [object-checks owner](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) demonstrates contextual inference, referenced mutable objects and actual branch evidence.

Follow-up: can Object.hasOwn replace a discriminant guard without additional proof? It checks own presence, but its boolean does not automatically narrow the demonstrated object union. An inherited User remains a User even when its own-email test is false; the predicate must match the contract being established.

export {};
interface Config { host: string }
interface Config { port?: number }
type ConfigAlias = { host: string; port?: number };
const config: Config = { host: "db", port: 5432 };
const alias: ConfigAlias = config;
interface HostOnly extends Omit<Config, "port"> { label: string }
const host: HostOnly = { host: "db", label: "primary" };
declare global { type TutorialObjectInterviewVersion = string }
const version: TutorialObjectInterviewVersion = "v1"; // fresh ambient alias, real initialized value
console.log(alias.host, host.label, version); // db primary v1

interface NameInterface { name: string }
type NameAlias = { name: string };
function dictionaryName(value: { [key: string]: string }): string | undefined { return value.name; }
const named: NameInterface = { name: "Ada" };
const namedAlias: NameAlias = named;
console.log(dictionaryName(namedAlias)); // Ada
// dictionaryName(named); // TS2345: interface lacks the implicit dictionary signature

type Point = { a: number; b: number };
function sum(point: Point): number { return point.a + point.b; }
const extra = { a: 1, b: 2, extra: 3 };
const point: Point = extra;
console.log(sum(point), Object.hasOwn(point, "extra")); // 3 true
// sum({ a: 1, b: 2, extra: 3 }); // TS2353: fresh literal
// const missing: Point = { a: 1 }; // TS2741

type Conflict = { age: number } & { age: string };
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ConflictAge = Expect<Equal<Conflict["age"], never>>;
interface Base { age: number }
// interface BadExt extends Base { age: string } // TS2430
// const badValue: Conflict = { age: 1 }; // TS2322
interface OptionalName { nickname?: string }
interface RequiredName extends OptionalName { nickname: string }
const required: RequiredName = { nickname: "ada" };
console.log(required.nickname); // ada

type UserId = { readonly value: string } & { readonly __brand: "UserId" };
type OrderId = { readonly value: string } & { readonly __brand: "OrderId" };
function makeUserId(raw: string): UserId {
  if (!/^u_[A-Za-z0-9]+$/.test(raw)) throw new Error("bad user id");
  return { value: raw } as UserId;
}
function userIdFromJson(raw: unknown): UserId {
  if (typeof raw !== "object" || raw === null || !("value" in raw)) throw new Error("bad object");
  const value: unknown = raw.value;
  if (typeof value !== "string") throw new Error("bad member");
  return makeUserId(value);
}
const uid = makeUserId("u_42");
// const swapped: OrderId = uid; // TS2322: marker mismatch
const decoded: unknown = JSON.parse(JSON.stringify(uid));
const restored = userIdFromJson(decoded);
console.log(restored.value, Object.hasOwn(restored, "__brand")); // u_42 false
try { userIdFromJson({ value: "o_1" }); }
catch (error) { console.log(error instanceof Error); } // true
class UserIdClass {
  private __brand!: void;
  readonly value: string;
  constructor(value: string) { this.value = value; }
}
const instance = new UserIdClass("u_1");
console.log(instance instanceof UserIdClass, decoded instanceof UserIdClass); // true false
// class Transforming { constructor(public value: string) {} } // TS1294 under erasableSyntaxOnly

type Route = { path: string; method: "get" | "post" };
const checked = { path: "/", method: "get" } satisfies Route;
const asserted = { path: "/", method: "get" } as Route;
type CheckedMethod = Expect<Equal<typeof checked.method, "get">>;
type CheckedPath = Expect<Equal<typeof checked.path, string>>;
type AssertedMethod = Expect<Equal<typeof asserted.method, "get" | "post">>;
console.log(checked.method, asserted.method); // get get
// const badMethod = { path: "/", method: "DELETE" } satisfies Route; // TS2322
// const tooNarrow: "get" = asserted.method; // TS2322
```

It prints the eight documented lines. The class is a runtime identity example rather than a validated id factory; the checked construction in this file is makeUserId. Four live equality assertions establish the conflict and Route results without executing ambient type-test stubs.

export {};
type Mixed = { nickname?: string } & { nickname: string | undefined };
const present: Mixed = { nickname: "ada" };
const explicitUndefined: Mixed = { nickname: undefined };
console.log(present.nickname, explicitUndefined.nickname); // ada undefined under default mode
```

This isolates the option that changes assignment; the runtime is not changing type semantics. ### 6) **Common confusion**

Interface merging, compatible computed heritage and fresh ambient names are distinct capabilities. Composition does not reopen an alias. A member named never is a static result, while an assertion claiming never supplies no runtime proof. Optional presence also cannot be summarized as all conflicts becoming unusable in the same way.

A phantom brand is not restored by a serializer. The domain parser must reconstruct the appropriate contract from received data, while a class constructor creates an instance. Choosing between those designs depends on the operations required, not a false ban on ordinary private modifiers or a brand-count quota.

### 7) **Performance note**

The type-only checks erase, while factories, serialization, reconstruction and class construction execute. These examples measure no checker time, symbol size, operand threshold or brand-count cost. An interview answer should distinguish the runtime operations from the erased type expression and describe the evidence needed for a performance comparison instead of inventing one.

### 8) **Mentor note**

Ask learners to predict each commented diagnostic before activating it individually with --noEmit. Require an explanation of the failure location and a remedy that preserves the intended contract. A good answer to dictionaryName identifies the named-interface assignability context; a good answer to the freshness call explains why the value still owns extra after assigning it to Point.

For the reconstruction question, replace decoded with an object carrying the wrong prefix. The compiler still accepts unknown at the parser boundary, but the runtime factory rejects it. Finally compare both optional-mode results. Grade the stated assumptions, observed outcome and owner link, rather than whether the learner recites a preferred operator or assertion count.
