## 6.1. Common interview QA — objects interfaces and type aliases

Five canonical interview loops for the object-type model — each still compiles under `tsc --strict` in its *bad* form. As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS). Junior reads `Q` → `A` → runnable; senior reads the trade-off tables, error-locus deltas, and mentor traps.

### 1) **interface vs type — when does it matter?** (merging, unions, mapped/conditional, primitives — the decision table)

**Q:** "When would you use `interface` vs `type` for an object? When does the choice actually matter?"

**Definition (question restated)** — Both `interface User { id: string }` and `type User = { id: string }` describe the same structural shape — extra members allowed, missing rejected — and both erase (zero emit, safe under `--erasableSyntaxOnly`). They are 90% interchangeable for plain object shapes. The choice matters where their *syntax powers diverge*: merging, naming non-object types, and type-level computation. See [1.3. Interfaces vs type aliases when to use which](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>).

**What interviewer probes** — (a) Do you know `interface` merges and `type` never does? (b) Can `interface` name a union/primitive/mapped/conditional? (c) When does `extends` vs `&` timing differ? (d) Does mapped/conditional/template-literal require `type`?

**A — Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

| Need | Prefer | Why |
|---|---|---|
| **Public, augmentable contract** (`Window`, `Express.Request`, plugin spine) — will be reopened via `declare global`/`declare module` | `interface` | Only `interface` merges; `type` redeclaring is `TS2300` |
| **Closed shape, no reopening needed** | either | 90% overlap — pick team convention, not correctness |
| **Union / primitive / tuple alias** (`type Id = string`, `type Status = "a" \| "b"`) | `type` | `interface` body must be a fixed member list — cannot name a union or primitive |
| **Mapped / conditional / template-literal / utility composition** (`Partial<T>`, `T extends U ? X : Y`, `` `on${string}` ``) | `type` | Type-level operators only on `type` aliases |
| **Heritage list that should error at declaration on conflict** | `interface extends` | `extends` reports `TS2430` at the declaration; `&` defers to `never` at use sites (see §3) |

Both spellings are erasable — `interface` vs `type` for *object shapes* never affects emit or `--erasableSyntaxOnly`; `enum`/`namespace` do — see [3.3. Choosing erasable syntax the zero-cost interop rule](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>).

**Runnable example** — what only one spelling can do (`tsc --strict` — error lines commented):

```typescript
// good — interface merges (only interface can be reopened)
interface Config { host: string; }
interface Config { port?: number; } // merges → { host: string; port?: number }
const cfg: Config = { host: "localhost", port: 5432 };
console.log(cfg.host); // localhost

// bad — type never merges
type Cfg2 = { host: string; };
// type Cfg2 = { port?: number; } // error TS2300: Duplicate identifier 'Cfg2'

// good — type can name union / primitive / tuple (interface cannot)
type Status = "idle" | "loading" | "done";
type UserId = string; // primitive alias — interface cannot do this
type Pair = [number, string];
const s: Status = "idle";
console.log(s); // idle

// good — type can compute: mapped / conditional / template literal
type ReadonlyDeep<T> = { readonly [K in keyof T]: ReadonlyDeep<T[K]> };
type IsString<T> = T extends string ? true : false;
type EventName = `on${Capitalize<string>}`; // "onClick" etc — type only
const _t: IsString<string> = true;
const _e: EventName = "onClick";
console.log(_t, _e); // true onClick

// bad — interface cannot compute the body (must be fixed members)
// interface BadMapped { [K in keyof Config]: string } // error — mapped only on type
// fix — derive type first, then extend if you need a nominal name:
type ConfigRO = ReadonlyDeep<Config>;
interface ConfigRONamed extends ConfigRO {} // ok — interface extends the computed type
console.log(cfg.port); // 5432
```

```typescript
// good — augmentation needs interface (module/global) — type cannot augment
// file: src/types/app.d.ts (shown inline — needs tsconfig include + import marker in real project)
declare global {
  interface Window { __APP_VERSION__?: string; }
}
export {}; // makes this file a module so declare global is legal
console.log(typeof window !== "undefined" ? window.__APP_VERSION__ : "node");

// bad — trying to augment with type
// declare global { type Window = { __APP_VERSION__: string } } // error — type cannot merge with interface Window
```

**Common confusion** — "`interface` is strict / `type` is loose" — false for object shapes: both use width subtyping and the same freshness lint. "`type` has runtime cost" — no, both erase. "`interface` can do mapped/conditional if I write it cleverly" — no; derive a `type` first then `interface Foo extends Mapped`. "`type` can merge like `interface` if I use `&`" — `&` composes, it does not reopen the same name — `type Foo = A & B` is a new alias, not a merge.

**Performance note** — for plain shapes `interface` and `type` intern to the same object type — checker cost identical, emit zero. Divergence costs only when `type` builds type-level computation: large `&` chains / mapped / conditional instantiate `O(n × depth)` with memoization, while `interface extends` is a flat member merge. No runtime difference — both erase. Measure with `tsc --extendedDiagnostics`.

**Mentor note** — ask "give me one example only `interface` can do and one only `type` can do" — correct: merge/augment vs union/mapped/conditional. Flag PRs that use `interface` for `type Status = "a" | "b"` — should be `type`. Gate: every public augmentable contract is `interface`; every composite/utility is `type`; require the answer to cite §2 semantics, not habit.

### 2) **Why does `{ a: 1, b: 2, extra: 3 }` error when passed directly but not via a variable?** (freshness, not structural failure)

**Q:** "Why does `fn({ a: 1, b: 2, extra: 3 })` error but `const v = { a: 1, b: 2, extra: 3 }; fn(v)` not — did structural typing break?"

**Definition (question restated)** — `{ a: 1, b: 2, extra: 3 }` **is** structurally assignable to `{ a: number; b: number }` — extra members are allowed via width subtyping (see [1.1. Structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>)). The direct-literal error `TS2353: Object literal may only specify known properties` is the *freshness* (excess property check) heuristic — a lint that fires only on fresh literals at typed assignment/call/return sites to catch typos, not a type rejection. See object-level treatment in [1.1. Object types structural shape and excess property checks](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) §§2–3 and canonical inventory in [1.2. Excess property checks and freshness](<../../../02 The Type System Core/sections/1. Structural typing/1.2. Excess property checks and freshness.md>).

**What interviewer probes** — (a) Do you know width subtyping allows extra? (b) Can you name the two freshness triggers vs two escapes? (c) Do you treat the error as lint vs assignability failure? (d) Can you seal without `as`?

**A — Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Two triggers** — fresh literal at an annotated assignment (`const p: Point = { a:1, b:2, extra:3 }`), fresh literal as call argument or `return` (`fn({ a:1, b:2, extra:3 })`, `return { a:1, b:2, extra:3 }` where target is `Point`) — both `TS2353`.
- **Two escapes that silence it** — stash through a variable/spread (`const v = { a:1, b:2, extra:3 }; const p: Point = v` / `{ ...v }`), or `as Target` (`{ a:1, b:2, extra:3 } as Point`) — both smuggle the typo past the lint.
- **Three correct seals** — `satisfies` at literal (`{ a:1, b:2 } satisfies Point` — checks + preserves literals), wider target (`Point & { extra?: number }`), or annotated binding (`const v: Point = { ... }` — typo caught where written). Never `as` a fresh literal to silence `TS2353` without a `// proof:` comment.

**Runnable example** — triggers vs escapes vs correct seals (`tsc --strict` — error lines commented so the fence compiles; uncomment one trigger line at a time to see the lint):

```typescript
// good — width subtyping: extra via variable is allowed (not a failure of structural typing)
type Point = { a: number; b: number };
function take(p: Point): void { console.log(p.a, p.b); }
const viaVar = { a: 1, b: 2, extra: 3 };
take(viaVar); // ok — freshness evaporated, width allows extra

// freshness triggers — uncomment to see TS2353 (lint, not assignability)
 // const badAssign: Point = { a: 1, b: 2, extra: 3 }; // error TS2353 — trigger 1: fresh literal at annotated assignment
 // take({ a: 1, b: 2, extra: 3 }); // error TS2353 — trigger 2: fresh literal as call argument
 // function make(): Point { return { a: 1, b: 2, extra: 3 }; } // error TS2353 — trigger 2: fresh literal as return

// escapes that hide a typo — bad (both silence the lint)
const leaky = { a: 1, b: 2, extraTypo: 3 }; // typo — no target yet → no freshness
take(leaky as Point); // bad escape via as — extraTypo rides through, Point contract satisfied but intent lost
const spread: Point = { ...leaky, a: 1 }; // bad escape via spread — freshness dropped
console.log(spread.a); // 1 — typo extraTypo leaked silently
```

```typescript
// good — correct seals that keep the lint and literal narrowness
type Point = { a: number; b: number };
type Route = { path: string; method: "get" | "post" };

// seal 1 — satisfies checks without widening (TS 4.9+, idiomatic 5.9 era)
const routeGood = { path: "/users", method: "get" } satisfies Route; // keeps "get" literal
type MethodOfGood = typeof routeGood.method; // "get" — preserved for keyof/T[K] derivation
const m: MethodOfGood = "get"; // ok
 // const typoFresh = { path: "/users", methd: "get" } satisfies Route; // error TS1360 — caught at literal

// seal 2 — wider target when extra is intentional
type LabeledPoint = Point & { label?: string };
function drawLabeled(p: LabeledPoint): void { console.log(p.a, p.b, p.label ?? ""); }
drawLabeled({ a: 1, b: 2, label: "origin" }); // fresh → checked against wider target → ok

// seal 3 — annotate the binding so typo caught where written
const opts: Point = { a: 1, b: 2 }; // checked at declaration
 // const optsBad: Point = { a: 1, b: 2, extra: 3 }; // error TS2353 at declaration — flagged where typo lives
console.log(routeGood.path, m, opts.a); // /users get 1
```

**Common confusion** — "Excess-property error means not assignable" — no, `const v = { a:1, b:2, extra:3 }; const p: Point = v` proves it *is* assignable. "Freshness applies through variables/spreads/generics" — it does not — only fresh literals at typed sites trigger. "Fix is `as Point`" — `as` disables the guard for that line and widens; prefer `satisfies` / wider target / annotated binding.

**Performance note** — freshness is `O(k)` over literal member count at check time — negligible, zero emit, zero allocation. The indirect cost is incident time: a typo `portt` that rides via `const v + as` ships and `port` stays `undefined` at runtime. Checker cost of `satisfies` vs `as` is identical (`O(members)` assignability check) — pick `satisfies` for correctness, not speed.

**Mentor note** — show the three-way demo in one block — `const p: Point = { a:1,b:2,extra:3 }` (error) vs `const v = {a:1,b:2,extra:3}; const p: Point = v` (silent) vs `const r = {a:1,b:2,extra:3} satisfies Point` (error again, literals kept) — ask "which rule explains each?" (answer: freshness lint vs width vs satisfies check). Gate: every `as Target` on a fresh literal needs a `// proof:` comment or must become `satisfies`.

### 3) **extends vs & — are they the same?** (error deltas, conflicting members, optional overrides — senior answer)

**Q:** "Is `interface B extends A` the same as `type B = A & { ... }`? When do they diverge?"

**Definition (question restated)** — Both compose object shapes: `interface B extends A { extra: string }` (*heritage* — `B` must refine `A`, each overlapping key must be a subtype) and `type B = A & { extra: string }` (*intersection* — a value must satisfy both sides, overlapping keys become `T & U`). They overlap ~90% and both erase, but they diverge on *conflicts* and optional overrides — `extends` errors at the *declaration* (`TS2430`), `&` puts `never` on the conflicting property and errors only at the *assignment*. See [2.1. Intersection vs extends composing object types](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>).

**What interviewer probes** — (a) Where does the diagnostic appear for a conflicting `age: number` vs `age: string`? (b) What is `number & string` on the property? (c) How do `age?: number` vs `age: number` interact under each operator? (d) When to prefer which for readability vs set-like composition?

**A — Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

| Scenario | `interface B extends A` | `type B = A & { ... }` | Senior verdict |
|---|---|---|---|
| Happy path — `A { a: string }` + `{ b: number }` | `interface B extends A { b: number }` — readable nominal chain | `type B = A & { b: number }` — set-like union | Either — prefer `extends` for 2–4 named parents, `&` for local combination |
| **Conflicting type** — `A { age: number }` vs `{ age: string }` | **error at declaration** `TS2430: Interface 'B' incorrectly extends interface 'A'` | **no declaration error** — `B["age"]` is `number & string = never` — error only when you assign a value to `age` | Public contract → `extends` (fail fast); local helper → `&` (deferred `never`) |
| **Optional vs required** — `A { nickname?: string }` vs `{ nickname: string \| undefined }` | reports `TS2430` when optionality incompatible in strict mode | computes `Mixed = Opt & Req` — `nickname: string \| undefined` (required-with-undefined) — models `exactOptionalPropertyTypes` split precisely | Need precise `?:` vs `\| undefined` modelling → `&` |
| **Primitive / union side** — branding `string & { __brand }` | **cannot** — `interface X extends string` invalid | **only `&` does this** | Branded primitives, `Record<...>` with utilities → `&` |
| Hover / instantiation | named heritage — hover stays named | inlined `&` expands — hover truncates past 4–5 operands | Long chains in public API → name intermediates + `extends` |

**Runnable example** — same conflict, different locus (`tsc --strict` — conflicting errors commented so fence compiles; uncomment one line at a time):

```typescript
// good — extends for readable chain (conflict error at declaration)
interface Route { path: string; method: "get" | "post"; }
interface Audited extends Route { createdAt: string; }
const okExt: Audited = { path: "/a", method: "get", createdAt: "2026-09-02" }; // ok
console.log(okExt.path); // /a

interface A { age: number; }
 // interface BadExt extends A { age: string; } // error TS2430 at declaration — preferred early signal for public contracts

// good — & for set-like / primitive / utility composition (& with conflicting age defers)
type Audited2 = Route & { createdAt: string };
const okAnd: Audited2 = { path: "/a", method: "post", createdAt: "2026-09-02" }; // ok
console.log(okAnd.method); // post

type BadAnd = A & { age: string }; // no declaration error — age becomes number & string = never
type BadAndAge = BadAnd["age"]; // never — tells you intersection is impossible for that key
const _checkNever: BadAndAge = undefined as unknown as never; // never has no inhabitant
console.log(_checkNever); // never witness — demonstrates empty set
```

```typescript
// good vs bad — optional edge (& can model the exact split, extends cannot)
type OptExact = { nickname?: string };
type ReqUndef = { nickname: string | undefined };
type MixedExact = OptExact & ReqUndef; // & models required-with-undefined precisely
const mixedOk: MixedExact = { nickname: "ada" }; // ok
const mixedUndef: MixedExact = { nickname: undefined }; // ok under default exact:false
console.log(mixedOk.nickname, mixedUndef.nickname); // ada undefined

// primitive side — only & can brand
type BrandedId = string & { readonly __brand: "UserId" };
function makeId(s: string): BrandedId { return s as BrandedId; }
const bid = makeId("u_1");
console.log(bid); // u_1

// bad — interface cannot intersect with primitive
 // interface X extends string {} // error — extends cannot intersect with string — must use type & instead
```

**Common confusion** — "`A & B` with conflicting `age` widens to `string | number`" — opposite — `&` requires both, so `number & string → never` (empty set); `|` widens. "Optional vs `| undefined` are sugar so operator shouldn't matter" — under `exactOptionalPropertyTypes` they differ and the two operators surface it differently. "`never` on the property means still usable if optional" — on a *required* conflicting key the intersection is uninhabitable; optional only sneaks past when the key can be missing. "Always use `&` — `extends` is legacy" — `extends` gives the earlier, more reviewable diagnostic for public contracts.

**Performance note** — both erase — zero emit/allocation/GC. Checker cost is one assignability walk per composition site — `O(members × operands)` — trivial for 2–5 operands. Very long `&` expansions (10+ operands spread across hundreds of files) inflate `instantiations` — visible in `tsc --extendedDiagnostics`; name intermediates (`type Mid = A & B`) rather than inlining giant `&` at call sites.

**Mentor note** — ask to trigger both errors with the same `age: number` vs `age: string` pair — once with `extends` (error at declaration) and once with `&` (error at assignment via `never`) — then "where do you want the reviewer to see the error?". Gate: public augmentable contracts use `interface extends`; branded/utility/union helpers use `type &`; answer `B["age"]` correctly as `never`.

### 4) **How do you model a branded UserId object?** (intersection + factory vs class private field)

**Q:** "We have `type UserId = { value: string }` and `type OrderId = { value: string }` — `ship(orderId)` accepts a `UserId` today. How do you make them incompatible without runtime cost? Compare intersection + factory vs class with `private` brand."

**Definition (question restated)** — Structural typing conflates two `{ value: string }` domains — both aliases erase and width allows the swap. A *brand* adds a checker-only phantom property via intersection — `type Branded = { value: string } & { readonly __brand: "UserId" }` or the `unique symbol` variant — so `UserId` is no longer assignable to `OrderId`. A *factory* is the single trusted site that does `as UserId` after validation; every other module receives `UserId`, never forges it. The competing construction is `class UserId { private __brand!: void; constructor(public value: string) {} }` — nominal via `private` member. See object-level patterns in [3.2. Branded and opaque object patterns for domain safety](<../3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) and primitive twin in [1.3. Nominal typing techniques](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>).

**What interviewer probes** — (a) Do you know intersection phantom vs `private` nominal? (b) Which erases vs emits? (c) How does `JSON.parse` round-trip? (d) When does `Pick`/`Omit` fracture? (e) `declare const` vs `const Symbol()` allocation?

**A — Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

| Approach | Construction | Emits? | JSON round-trip | Nominal via | When to pick |
|---|---|---|---|---|---|
| **Intersection + factory** | `type UserId = { value: string } & { readonly __brand: "UserId" }; function makeUserId(s: string): UserId` | **erases** — zero emit, safe under `--erasableSyntaxOnly` | `JSON.stringify/parse` round-trips — brand not a runtime key | phantom `__brand` property incompatibility | **Default for object wrappers** — aggregates (`User`, `Order`) at boundaries |
| **Intersection + `unique symbol` key** | `declare const Brand: unique symbol; type UserId = { value: string } & { readonly [Brand]: "UserId" }` | `declare const` erases; `const B = Symbol()` allocates heap | auto-omitted by `JSON.stringify` (symbols don't serialize) | never-colliding symbol key | Cross-team boundaries where `__brand` string might collide |
| **Class with `private` field** | `class UserId { private __brand!: void; constructor(public value: string) {} }` | **emits** (`class` + constructor) — not `erasableSyntaxOnly`-free; strict `private` brand breaks `JSON.parse` round-trip | `new UserId("u_1")` instance, but `JSON.parse('{"value":"u_1"}')` is *not* a `UserId` — needs `instanceof` + re-hydrate | `private` member declaration-site identity | Only when you also need runtime `instanceof`/methods on the wrapper |

Bounds: brand **~5–15 aggregates** at module boundaries (`User`, `Order`, `Session`, `Money`), not every leaf (`UserEmail`, `BrandedId` inside `User` fractures `Pick`/`Omit` and inflates `as` count) — see §3.2 cost vs safety.

**Runnable example** — intersection + factory (good, default) vs class `private` (emits + JSON hazard) vs `unique symbol` variant (`tsc --strict`):

```typescript
// good — intersection + factory (default, erasable, JSON-friendly)
type UserCore = { value: string };
type UserId = UserCore & { readonly __brand: "UserId" };
type OrderId = UserCore & { readonly __brand: "OrderId" };

function makeUserId(raw: string): UserId {
  if (!raw.startsWith("u_")) throw new Error(`bad user id: ${raw}`);
  return { value: raw } as UserId; // single trusted assertion per brand
}
function makeOrderId(raw: string): OrderId {
  if (!raw.startsWith("o_")) throw new Error(`bad order id: ${raw}`);
  return { value: raw } as OrderId;
}

function ship(orderId: OrderId): void { console.log(`ship ${orderId.value}`); }
const uid = makeUserId("u_42");
const oid = makeOrderId("o_99");
ship(oid); // ok
 // ship(uid); // error TS2322 — __brand mismatch — bug caught at compile time

// inside module — receive UserId, don't re-brand
function formatUserId(id: UserId): string { return id.value.toUpperCase(); }
console.log(formatUserId(uid)); // U_42

// projection via unbranded core — no brand friction
type PublicId = Pick<UserCore, "value">;
function toPublic(id: UserId): PublicId { return { value: id.value }; }
console.log(JSON.stringify(toPublic(uid))); // {"value":"u_42"} — brand never leaks
console.log(JSON.stringify(uid)); // {"value":"u_42"} — phantom not a runtime key

// boundary: JSON → validated then branded (never as UserId on raw)
function userIdFromJson(raw: unknown): UserId {
  if (typeof raw !== "object" || raw === null) throw new Error("bad json");
  const r = raw as { value: unknown };
  if (typeof r.value !== "string") throw new Error("bad shape");
  return makeUserId(r.value);
}
console.log(userIdFromJson({ value: "u_7" }).value); // u_7
```

```typescript
// reference — class private field alternative (nominal via private, but emits + JSON hazard)
class UserIdClass {
  private __brand!: void; // nominal — two classes with different private decls are incompatible
  constructor(public value: string) {}
  static make(raw: string): UserIdClass {
    if (!raw.startsWith("u_")) throw new Error(`bad user id: ${raw}`);
    return new UserIdClass(raw);
  }
}
class OrderIdClass {
  private __brand!: void;
  constructor(public value: string) {}
}

function shipClass(o: OrderIdClass): void { console.log(`ship class ${o.value}`); }
const uidC = UserIdClass.make("u_1");
const oidC = new OrderIdClass("o_1");
shipClass(oidC); // ok
 // shipClass(uidC); // error TS2345 — private brand mismatch (different declaration site)

// hazard — class brand needs re-hydration after JSON.parse; intersection does not
const parsed = JSON.parse('{"value":"u_1"}') as { value: string }; // plain object, not an instance
 // shipClass(parsed as unknown as OrderIdClass); // laundered — bypasses brand + constructor validation — bug
// class form must re-hydrate:
const rehydrated = UserIdClass.make((parsed as { value: string }).value); // validated again
console.log(rehydrated.value); // u_1
console.log(parsed instanceof UserIdClass); // false — plain object vs class instance
```

```typescript
// good — unique symbol brand variant (never collides, auto-omitted by JSON — erasable when declare const)
// type-only — zero runtime Symbol allocation:
declare const UserBrand: unique symbol;
type UserIdS = { value: string } & { readonly [UserBrand]: "UserId" };
type OrderIdS = { value: string } & { readonly [UserBrand]: "OrderId" }; // same symbol, different literal — still incompatible
function makeUserIdS(raw: string): UserIdS {
  if (!raw.startsWith("u_")) throw new Error(`bad user id: ${raw}`);
  return { value: raw } as UserIdS;
}
const uidS = makeUserIdS("u_7");
console.log(JSON.stringify(uidS)); // {"value":"u_7"} — symbol brand never stringifies

// contrast — const Symbol() DOES allocate (avoid for hot-path types)
const RuntimeBrand = Symbol("UserId"); // heap symbol — ~32–64 bytes, interned
type UserIdRuntime = { value: string } & { readonly [RuntimeBrand]: "UserId" }; // works but costs one symbol per module load
console.log(typeof RuntimeBrand); // symbol — runtime exists, unlike declare const

// bad — over-branding every leaf fractures composition
type BrandedId = string & { readonly __brand: "BrandedId" };
type OverUser = { id: BrandedId; email: string } & { readonly __brand: "OverUser" };
 // Pick<OverUser, "id">; // brand kept on leaf — composition forces extra as to reconstruct OverUser — prefer branding the aggregate only
```

**Common confusion** — "Brand must be a runtime property" — never — `JSON.stringify` omits `__brand`/`unique symbol`; `Object.keys` doesn't see it — checker-only. "`declare const Brand: unique symbol` allocates a `Symbol`" — `declare const` is type-only, zero allocation; `const Brand = Symbol()` allocates. "Factory is boilerplate — `as UserId` at call site is fine" — each `as` is a proof site that bypasses validation — centralize to one per brand. "Class `private` brand is type-only" — `class` emits and `private` brand requires re-hydration after `JSON.parse`; intersection round-trips as plain object. "Branding prevents `any`/`as` laundering" — it is discipline — `any` / `as unknown as UserId` still breaks it.

**Performance note** — intersection brand erases — zero emit/allocation/GC, checker adds one phantom-property check `O(1)` per assignment. `declare const ... unique symbol` also erases. Only `const B = Symbol()` allocates (~32–64 bytes, shape-initialized once). Over-branding (~40 leaf brands) inflates type-graph `O(brands)` per call site — `tsc --extendedDiagnostics` `instantiations` grows (8 brands ~2k, 40 brands ~8k, +10–15 ms) and hover on `Pick`/`Omit` truncates — budget brands like allocations.

**Mentor note** — draw the airlock: ingress (`JSON`/`DB`/`queue`) → `makeUserId`/`makeOrderId` → interior (`format`, `ship`, `toPublic` — receive `UserId`, never forge) → egress. Review gate: `grep -R "as UserId\|as OrderId\|__brand" --include="*.ts"` should return *only* factory lines; any hit outside `factories/` is laundering. Exercise: hand a PR with `ship(uid)` where `uid: UserId` was `as UserId` at the call site and ask to (a) move `as` into `makeUserId`, (b) add `userIdFromJson` boundary, (c) justify why leaf `BrandedEmail` is *not* added.

### 5) **satisfies vs as on an object literal** (preserved literal vs widened and silenced)

**Q:** "What's the difference between `const x = { method: \"get\" } satisfies Route` and `const x = { method: \"get\" } as Route`? When does it matter?"

**Definition (question restated)** — `satisfies Route` is a *check* — "check that this literal satisfies `Route`, keep its *inferred* literal type (`\"get\"`, not `string`)" — freshness/excess still errors at the literal site. `as Route` is an *assertion* — "treat this value as `Route` exactly — disable excess checks at the literal, *widen* literals (`\"get\"` → `string` or `\"get\" | \"post\"`), keep exactly `Route`". Counterpart `as const` narrows+readonly but alone does not validate the shape. See object-level sealing in [1.1. Object types structural shape and excess property checks](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) §3 and full `satisfies`/`as const`/narrowing system in [3.3. satisfies assertions and narrowing on object shapes](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) §§1–2; literal ground truth in [3.3. Literal types and const assertions](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>).

**What interviewer probes** — (a) Which preserves `typeof x.method` as `"get"` vs `"get" | "post"`? (b) Which catches a typo `methd` / excess `extra` at the literal? (c) Which erases vs which pretends to validate? (d) When to reach for `as const satisfies` vs bare `satisfies`?

**A — Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

| Need | Write | `typeof x.method` after | Typo `extra` at literal? | Downstream `keyof typeof`/`T[K]` |
|---|---|---|---|---|
| **Validate literal *and* keep its inferred literal** (route table, theme, test fixture) | `const x = { path: "/", method: "get" } satisfies Route` | `"get"` (literal preserved) | **errors `TS2353` at that line** | `typeof x.method` → `"get"` — derivation stays narrow |
| Widen intentionally when checker cannot see proof (validated `JSON.parse` after `zod`) | `JSON.parse(raw) as Route // proof: zod parsed above` | `Route["method"]` = `"get" \| "post"` (widened) | **silent** — excess/typo not reported | widened — less useful derivation |
| Deep `readonly` + literals (exported constant table) | `const x = { method: "get" } as const` or `as const satisfies Route` | `"get"` + `readonly` | `as const` alone **does not validate** shape; `as const satisfies Route` validates + keeps `readonly` | `typeof x` stays `readonly "get"` |
| Hide the proof (anti-pattern) | `{ path:"/", method:"DELETE" } as unknown as Route` | widened, lies | silent | compiles — runtime 405 |

Rule: is the **literal** the source of truth? → `satisfies` (or `as const satisfies` for frozen tables). Is the **consumer** genuinely wider than the literal? → widen the *consumer* (`Route & { extra?: unknown }`), not the literal. Every `as Target` on a literal needs a `// proof:` comment or must become `satisfies`.

**Runnable example** — `satisfies` preserves literal and catches excess; `as` widens, silences, and erases the literal (`tsc --strict` — error lines commented so fences compile):

```typescript
// good — satisfies checks Route while preserving "get" literal for derivation
type Route = { path: string; method: "get" | "post"; secure?: boolean };

const routeOk = { path: "/users", method: "get" } satisfies Route;
// routeOk.method is "get" (literal), not "get" | "post" — downstream keeps narrowness:
const methodOk: "get" = routeOk.method; // ok — literal preserved
type MethodOfOk = typeof routeOk["method"]; // "get" — not widened

// satisfies still catches typos and excess at the literal site:
 // const typo = { path: "/users", methd: "get" } satisfies Route; // error TS1360: does not exist in type 'Route'
 // const excess = { path: "/users", method: "get", extra: true } satisfies Route; // error TS2353: 'extra' does not exist

// good — as const satisfies when you also want deep readonly
const routeFrozen = { path: "/users", method: "get" } as const satisfies Route;
// routeFrozen.method is readonly "get"
console.log(routeOk.path, routeOk.method); // /users get
console.log(routeFrozen.method); // get

// derive from the satisfied literal — typeof capture keeps the literal because satisfies preserved it
type KeysOfRoute = keyof typeof routeOk; // "path" | "method"
const _k: KeysOfRoute = "path"; // ok
```

```typescript
// bad — as widens to exactly Route and silences the same mistakes (contrast with above)
type Route = { path: string; method: "get" | "post"; secure?: boolean };

const routeCast = { path: "/users", method: "get" } as Route;
// routeCast.method is "get" | "post" (widened) — literal identity lost:
 // const methodLost: "get" = routeCast.method; // error TS2322 — "get" | "post" not assignable to "get"
type MethodOfCast = typeof routeCast["method"]; // "get" | "post" — widened, less useful for derived tables
const _widened: MethodOfCast = "post"; // widened allows either — proof the literal was lost

// bad — as silences typos inside a nested object literal (freshness bypass):
const routeSilenced = { path: "/users", method: "get", extra: true } as Route; // ok at literal site — excess not reported
console.log(routeSilenced.path); // /users — bug: extra survived silenced and may be read later as valid config

// bad — double assertion launders an invalid shape:
const laundered = { path: "/users", method: "DELETE" } as unknown as Route; // compiles — runtime 405 later
console.log(laundered.method); // DELETE — checker silence, production mismatch
// fix — return to satisfies so the bad method errors where written:
 // const fixed = { path: "/users", method: "DELETE" } satisfies Route; // error TS2322: '"DELETE"' is not assignable to '"get" | "post"'
```

```typescript
// good — satisfies composes with object composition and as const satisfies
type Route = { path: string; method: "get" | "post" };
type Audited = { createdAt: string };
type RouteAudited = Route & Audited;

const auditedOk = { path: "/a", method: "post", createdAt: "2026-09-02" } satisfies RouteAudited;
const auditedMethod: "post" = auditedOk.method; // preserved through intersection

const auditedCast = { path: "/a", method: "post", createdAt: "2026-09-02" } as RouteAudited;
 // const auditedMethodLost: "post" = auditedCast.method; // error — widened through & as well

// good — exported table: validated + literals + readonly
type RouteTable = Record<string, Route>;
const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "post" },
} as const satisfies RouteTable;
type RouteKey = keyof typeof ROUTES; // "home" | "users" — derived because literals kept
console.log(auditedOk.createdAt, ROUTES.users.method); // 2026-09-02 post
```

**Common confusion** — "`satisfies` narrows the variable to `Route`" — no, `satisfies Route` keeps the source literal (`"get"`); `as Route` forces the variable to `Route`. "`satisfies` has runtime or emit cost" — none — both erase, zero emit; `satisfies` is not a validator (use `zod`/`valibot` at boundaries). "`as` is shorter so it's the same" — `as` disables excess checks and widens; `satisfies` keeps checks and literals. "`as const satisfies T` checks after widening" — it narrows first (`as const`) then checks (`satisfies`), so typo/excess still errors — order is `(x as const) satisfies T`. "`satisfies` alone gives `readonly`" — it does not — only `as const` adds `readonly`.

**Performance note** — `satisfies` and `as` both erase — zero emit/allocation/GC/dispatch. Checker cost of `satisfies` is one extra assignability check at the literal — `O(members)` (3–8 props) — trivial; `satisfies` can *reduce* downstream cost by preserving `"get"` vs branching over `"get" | "post"` generics. Hundreds of `as` launderings cost nothing in checker time but hide work that reappears as runtime incidents.

**Mentor note** — litmus: "is the literal the source of truth?" — *yes* → `satisfies T` at the literal (or `as const satisfies T` for frozen tables); *no, the consumer is truth* → widen the consumer (`& { extra?: ... }`) or annotate the binding. Review rule: every `as Target` on a literal carries a `// proof:` comment or is replaced — `grep -R " as [A-Z]" --include="*.ts" src/ | grep -v " as const"` should be near zero. Exercise: give three `as Route` literals — one must become `satisfies` (typo guard), one annotated `const r: Route` (variable is truth), one wider param — discuss why the same `as` was wrong three ways.
