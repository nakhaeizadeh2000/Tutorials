## 2.2. Declaration merging and module augmentation

Declaration merging combines compatible declarations with the same name in the same relevant scope. Module augmentation applies that mechanism to an existing module's declarations; global augmentation adds declarations to global scope. These operations change what the checker sees, while runtime values and behavior still need real implementations.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Create the project files shown below in a new directory. For the separate merges.ts and overloads.ts programs, use `tsc --ignoreConfig --strict --target es2022 --module commonjs --lib es2022,dom --outDir out FILE.ts`, then `node out/FILE.js`. The ignoreConfig option allows these standalone checks beside the project configuration. For an intentional rejection, activate only the indicated line and use the same flags with `--noEmit` instead of `--outDir out`.

### 1) **Compatible members, declaration spaces and additive overloads**

Two User interface declarations below contribute id and name to one contract. Required members remain required. A same-key redeclaration must have compatible declaration modifiers and the same member type in these examples: it cannot silently make title optional or change it from string to number.

Save `merges.ts`:

```typescript
export {};
interface User { id: string }
interface User { name: string }
const user: User = { id: "1", name: "Ada" };
console.log("merged:", user.id, user.name);
// const missing: User = { id: "2" }; // TS2741: both declarations contribute.
interface Contract { title: string }
// interface Contract { title?: string } // TS2687/TS2717: cannot weaken the member.
// interface Contract { title: number } // TS2717: incompatible type.

// An alias cannot be reopened; a same-named value is a different declaration space.
type Product = { id: string };
const Product = { category: "catalog" };
const product: Product = { id: "p1" };
console.log("different spaces:", product.id, Product.category);
// type Product = { name: string }; // TS2451 here: alias redeclared alongside the value.
type NamedProduct = Product & { name: string };
const named: NamedProduct = { id: "p2", name: "Widget" };
console.log("new contract:", named.name);
```

The output is `merged: 1 Ada`, `different spaces: p1 catalog` and `new contract: Widget`. Activate missing to observe TS2741. Activate the optional-title redeclaration to observe TS2687 and TS2717; the rejection remains with --exactOptionalPropertyTypes. Activate the numeric-title redeclaration to observe TS2717.

A type alias cannot be reopened, but a separate same-named value can coexist with it. In this specific Product example, activating the additional alias produces TS2451 diagnostics because the name also has a block-scoped value declaration. The [interfaces-versus-aliases owner](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>) separately demonstrates the usual alias-only TS2300 case. Diagnose the actual declarations rather than treating every same-name pair as an identical error.

[Declaration spaces](<../../../02 The Type System Core/sections/2. The type vs value separation/2.2. Declaration spaces type value and namespace.md>) owns the full permitted-pair table and actual namespace/class combination. Value-bearing namespace companions can modify runtime values; a namespace containing only types can erase. Neither namespace syntax nor same-name adjacency alone tells you that a runtime object was created.

Methods with the same name can contribute overloads. Adding a narrow overload does not remove an existing broad callable signature, as the [primary merge reference](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#merging-interfaces) describes.

Save `overloads.ts`:

```typescript
export {};
interface Response { json(body: unknown): void }
interface Response { json(body: { ok: true; data: string }): void }
const response: Response = { json(body: unknown): void { console.log(JSON.stringify(body)); } };
response.json({ completelyDifferent: 123 }); // Existing broad signature remains.

type Envelope = { ok: true; data: string } | { ok: false; error: string };
function sendEnvelope(body: Envelope): void { response.json(body); }
sendEnvelope({ ok: true, data: "Ada" });
// sendEnvelope({ completelyDifferent: 123 }); // TS2353: restricted wrapper.
```

The output is `{"completelyDifferent":123}` followed by `{"ok":true,"data":"Ada"}`. The first call is accepted through the original unknown signature. Uncomment the call through sendEnvelope to observe TS2353: that separate wrapper exposes the intentionally restricted Envelope contract. It supplies a checking boundary, not a runtime parser. External data still needs [runtime validation](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>); general overload design belongs in [callable types](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>).

### 2) **A complete module/global augmentation project**

This local project adds an optional label to an exported Session interface and declares a global version value with a separate runtime provider. The module augmentation affects consumers of this Session type throughout the checked program. It is not confined to the file containing the augmentation. The global declaration has wider visibility, but it still does not install a value.

Save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "erasableSyntaxOnly": true,
    "noEmitOnError": true,
    "target": "es2022",
    "module": "commonjs",
    "moduleDetection": "legacy",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src/**/*"]
}
```

The explicit legacy moduleDetection setting makes the import/export markers used by this exercise easy to observe. It is a declared fixture choice, rather than a universal application default; [module detection](https://www.typescriptlang.org/tsconfig/moduleDetection.html) has other modes. rootDir keeps output layout explicit, and noEmitOnError prevents a failing build from creating new outputs. A clean output directory remains relevant when testing a failure, as the [pipeline pitfalls owner](<../../../01 Fundamentals and Mental Model/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by misunderstanding fundamentals.md>) explains.

Save `src/store.ts`:

```typescript
export interface Session { id: string }
export function describe(session: Session): string { return session.id; }
```

Save `src/store-augmentation.d.ts`:

```typescript
import "./store.js";
declare module "./store.js" {
  interface Session { label?: string }
}
```

The import makes this file a module, and the matching specifier identifies the declaration to augment. This is an augmentation of an existing named interface, rather than a new ambient description of an untyped package. The [primary augmentation reference](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#module-augmentation) documents that distinction and the named-export restrictions.

Save `src/globals.d.ts`:

```typescript
export {};
declare global {
  // Introduces a type and describes a value provided separately by provider.ts.
  type TutorialVersion = string;
  var tutorialVersion: TutorialVersion | undefined;
}
```

The fresh TutorialVersion alias introduces a type name; it is not an attempt to reopen an alias. The var declaration describes an optional runtime value. Save its implementation in `src/provider.ts`:

```typescript
export {};
globalThis.tutorialVersion = "v1";
```

Save `src/app.ts`:

```typescript
import "./provider.js";
import { describe, type Session } from "./store.js";
const session: Session = { id: "s1", label: "Ada" };
console.log("augmented:", describe(session), session.label);
console.log("provided:", globalThis.tutorialVersion?.toUpperCase() ?? "missing");
// console.log(globalThis.tutorialVersoin); // TS7017: undeclared global property.
const locallyRequired: Session & { label: string } = { id: "s2", label: "Grace" };
console.log("local requirement:", locallyRequired.label.toUpperCase());
```

Run `tsc -p tsconfig.json`, then `node dist/app.js`. The output is `augmented: s1 Ada`, `provided: V1` and `local requirement: GRACE`. Run `tsc -p tsconfig.json --listFilesOnly`: both declaration files appear. That check establishes program inclusion; it does not prove the provider was executed.

For a contrasting runtime case, remove only the provider import from app.ts, rebuild and run in a fresh Node process. Checking still succeeds; the middle line becomes `provided: missing`. Restoring the import restores V1. The declaration cannot make its provider run. This example uses a real local module rather than claiming an Express/Hono/NestJS integration; application-oriented backend teaching retains its separate NestJS/Fastify route in the [root curriculum](<../../../../../README.md>).

### 3) **Diagnose inclusion, scope and presence separately**

Make these controlled changes one at a time, using `tsc -p tsconfig.json --noEmit` for failures, and restore the file after each check:

- Remove the import from store-augmentation.d.ts. The relative declaration becomes an invalid ambient module declaration (TS2436); the consumer also loses label and reports TS2353/TS2339.
- Remove export {} from globals.d.ts. Under this fixture, declare global is misplaced and produces TS2669; the global value references also lose their declaration.
- Activate tutorialVersoin. This undeclared global property access produces TS7017. Ordinary typed property access has checks independently of object-literal excess-property checking.
- Add `"exclude": ["src/store-augmentation.d.ts"]` to the configuration. Without another import/reference bringing that file into the program, the consumer loses label and checking reports TS2353/TS2339. Remove that exclusion to restore its declaration.

A newly added optional member is different from changing an existing required member to optional. The passing Session augmentation adds a new label. The rejected title merge from part 1 weakens an existing member. For a specific operation that truly requires label, the local Session intersection keeps that requirement visible; the initializer supplies it here. Untrusted input would need a checked construction path rather than an assertion.

Prefer a local subtype or wrapper when only one operation needs extra members. Use augmentation when changing the existing shared contract is intentional. Keep its target, program inclusion and provider reviewable, and rerun consumers when upgrading dependencies. Merging does not guarantee that future package versions remain compatible with your added members. File-scale placement and publishing belong in [module augmentation](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.2. Module augmentation at file scale.md>) and [global declarations](<../../../12 Modules Namespaces and Declaration Files/sections/2. Namespaces and Ambient Contexts/2.2. declare global and global augmentation.md>).

### 4) **Common confusion**

A module-scoped interface named like a global does not automatically augment that global. A declaration file can describe a missing provider. A narrow added overload leaves the broad overload callable, and an optional redeclaration cannot silently replace a required interface member. Distinguish a new declaration, a legal merge and a runtime implementation before drawing conclusions from similar names.

### 5) **Performance note**

The interfaces, aliases and declaration-file augmentations in this project erase. The provider assignment, initializers and response calls still execute. No checking/invalidation benchmark or latency threshold was measured, and consolidating augmentation files alone establishes no speed improvement. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a program-level cost investigation; choose scope primarily from the intended contract and visibility.

### 6) **Mentor note**

Have the learner predict the difference between removing an augmentation file and removing its runtime provider. A sound answer separates lost static members from a still-declared but absent value. Then show the broad response call and ask why another overload did not prohibit it. Finish with the rejected optional-title merge: the explanation must name the modifier conflict rather than invent a silent weakening mechanism.
