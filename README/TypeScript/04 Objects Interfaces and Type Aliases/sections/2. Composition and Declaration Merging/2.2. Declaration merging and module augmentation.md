## 2.2. Declaration merging and module augmentation

### 1) **What merges** (`interface` with `interface`, `namespace` with `class`/`function`/`enum` — `type` never merges; module scope disables global merging)

**Definition** — *declaration merging* is the compiler rule that two declarations with the *same name* in *complementary* declaration spaces combine into one logical entity instead of colliding. Only specific pairs merge — everything else is `TS2300 Duplicate identifier`:

| Pair that merges | What combines | Result | Erases? |
|---|---|---|---|
| `interface` + `interface` (same name, same scope) | Members merge into one interface | Single structural type with union of members | yes — zero emit |
| `namespace` + `class` | Namespace members become statics on the class constructor | Value = class + namespace object, Type = instance type | no — `namespace` emits an IIFE |
| `namespace` + `function` | Namespace members become properties on the function object | Callable value with attached properties | no — `namespace` emits |
| `namespace` + `enum` | Namespace members augment the enum object | Value = enum object with extra members | no — `enum` already emits |
| `type` + *anything same-named* | Nothing — always `TS2300` | Error | n/a |

`type` aliases are *closed* — redeclaring `type Foo = ...` is always an error, never a merge. Merging is also *scope-sensitive*: in a *script* file (no top-level `import`/`export`) same-named `interface` declarations merge globally; in a *module* file (has `import`/`export`) they merge only within that module's scope — global merging requires an explicit `declare global` / `declare module` augmentation (see §2).

**What problem it solves / history** — `lib.d.ts` and every `@types/*` package must describe a library without forking it. JavaScript's built-ins were modeled as global `interface Array<T>`, `interface Window`, `interface Document` so that a later `lib.dom.d.ts` or a polyfill `.d.ts` could add `Array.prototype.at` or `Window.showOpenFilePicker` by *reopening* the same `interface` — no overwrite, no fork. That reopening is declaration merging, shipped in TypeScript 0.8 (2012) alongside `interface` itself, before `type` aliases existed (1.4, 2015). `namespace` + `class`/`function` merging solved the pre-ESM pattern of attaching statics to a constructor (`class Point` + `namespace Point { export const origin }` mirrors the JavaScript idiom `Point.origin = ...` before `static` fields were standard). `type` was intentionally made non-mergeable to keep type-level expressions closed and predictable — if `type` merged, `A & B` intersections would be ambiguous with accumulated members.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Need to add members to an existing interface you don't own** → reopen the `interface` in an augmentation file (`.d.ts` or `declare global`/`declare module` block) — the only spelling that merges (see §2). `type` cannot do this; `&` builds a *new* type, it does not reopen the original name.
- **Need statics on a class/function** → prefer `static` fields/methods inside the class (`class Point { static origin = ... }`) over `namespace Point` merging — `namespace` is [non-erasable](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) and fails `--erasableSyntaxOnly` (`TS1294`). Reserve `namespace`+`class` merging for generated `.d.ts` or legacy declaration files; in source code, write `static`.
- **Module vs script — the scope rule that prevents accidental global pollution:** a file with *any* top-level `import` or `export` is a *module* — its `interface` reopenings are *module-scoped* and do **not** merge with the global `Window`/`Array` unless wrapped in `declare global`. A file with *no* `import`/`export` is a *script* — its declarations are global and merge across all scripts (the implicit-global regime that large apps must escape). Modern guidance: every source file is a module (add `export {}` if it would otherwise be a script) — see runnable example.
- **Both `interface` and `type` remain [erasable](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)** — merging adds zero bytes to JavaScript — but `namespace`/`enum` merging does emit — avoid in `--erasableSyntaxOnly` projects.

**Runnable example** — what merges vs what never merges, plus module vs script scope — good vs bad, `typescript` fences runnable under `tsc --strict` (error lines commented with `TS` code so the fence still compiles):

```typescript
// good — interface with interface merges (same scope, same name)
// These two declarations combine into one interface { id: string; name: string } — no error.
interface User {
  id: string;
}
interface User {
  name: string;
}
const user: User = { id: "1", name: "Ada" };
console.log(user.id, user.name); // 1 Ada
// Hover User → { id: string; name: string } — members from both blocks.

// bad — type never merges — duplicate identifier
type Product = { id: string };
// type Product = { name: string }; // error TS2300: Duplicate identifier 'Product'.
// fix — closed alias must compose, not reopen:
type ProductName = { name: string };
type ProductFull = Product & ProductName; // new name via intersection
const prod: ProductFull = { id: "p1", name: "Widget" };
console.log(prod.name); // Widget

// good — namespace with class/function/enum merges (value + value namespace augmentation)
// This is the legacy companion-static pattern — works, but emits.
class Point {
  constructor(public x: number, public y: number) {}
}
namespace Point {
  export const origin = new Point(0, 0);
  export function distance(a: Point, b: Point): number {
    return Math.hypot(a.x - b.x, a.y - b.y);
  }
}
console.log(Point.origin.x, Point.distance(new Point(0, 0), new Point(3, 4))); // 0 5
// Point is both a constructor (value) and a namespace holding origin/distance.

// good — namespace with function (same companion pattern)
function greet(name: string): string { return `hi ${name}`; }
namespace greet {
  export const version = "1.0.0";
  export function loud(name: string): string { return `HI ${name.toUpperCase()}!`; }
}
console.log(greet("Ada"), greet.version, greet.loud("Ada")); // hi Ada 1.0.0 HI ADA!

// good — namespace with enum (also merges, also emits)
enum Direction { Up, Down }
namespace Direction {
  export const all = [Direction.Up, Direction.Down] as const;
}
console.log(Direction.Up, Direction.all.length); // 0 2

// ── Module scope disables global merging ──
// A module file (has import/export) scopes its reopenings locally.
// To merge with the GLOBAL Window, a module must use explicit `declare global`.

// file: app.ts — this file IS a module because of the export line below
export {}; // makes file a module — without this, it would be a script (global)

// good — module-scoped interface reopening: merges ONLY inside this module
interface LocalConfig { host: string; }
interface LocalConfig { port: number; } // ok — same module, merges locally
const cfg: LocalConfig = { host: "localhost", port: 5432 };
console.log(cfg.host, cfg.port); // localhost 5432

// good — augmenting the GLOBAL Window from a module requires declare global
declare global {
  interface Window {
    __APP_VERSION__?: string;
  }
}
// window.__APP_VERSION__ now type-checked inside this module and any importer
// window.__APP_VERSION__ = "5.9.0"; // ok — would be usable at runtime in a browser

// bad — expecting module-local reopening to affect the global without declare global
interface Window { // this Window is module-local, NOT the global Window — does NOT augment the DOM
  __LOCAL_ONLY__?: string;
}
// window.__LOCAL_ONLY__ // error — global Window has no __LOCAL_ONLY__; this Window is a local shadow
// fix — wrap in declare global { interface Window { __LOCAL_ONLY__?: string } }
```

```typescript
// bad — script vs module surprise: same code, different scope, different merge behavior
// file: legacy.ts — NO import/export → script → global scope
// interface AppConfig { host: string; }
// file: legacy2.ts — NO import/export → script → global scope
// interface AppConfig { port: number; } // merges globally — AppConfig now { host, port } everywhere — surprising

// file: modern.ts — HAS import/export → module → isolated
// export type AppConfig = { host: string; } // scoped to module — no global leakage
// file: modern2.ts — HAS import/export → module → isolated
// export type AppConfig2 = { port: number; } // different module — no merge, no collision

// fix — make every source file a module (add export {} if otherwise empty)
// and use declare global / declare module only for intentional augmentation (see §2).
// Lint: enable isolatedModules + verbatimModuleSyntax so every file is a module by construction.

// bad — reopening with incompatible property type — merging checks assignability at the MEMBER level
interface Config { timeout: number; }
// interface Config { timeout: string; } // error TS2717: Subsequent property declarations must have the same type. Property 'timeout' of type 'string' is not assignable to type 'number'.
// fix — decide one type for the key, or give the new shape a distinct key:
interface ConfigFixed { timeout: number; timeoutMs?: number; }
const cf: ConfigFixed = { timeout: 3000 };
console.log(cf.timeout); // 3000

// good — reopening MAY add optional or overload signatures where compatible
interface Api { fetch(url: string): Promise<string>; }
interface Api { fetch(url: string, init: { signal: AbortSignal }): Promise<string>; } // overload added via merging
declare const api: Api;
// api.fetch("/a") and api.fetch("/a", { signal: new AbortController().signal }) both type-check
```

**Common confusion** — "`type` merges if I put the declarations next to each other" — never — `type` is closed by design; adjacency does not change `TS2300`. "`interface` merging works across modules automatically — I reopened `Window` in a file with `import` and it augmented the global `Window`" — false — a file with `import`/`export` is a module; its `interface Window` is *module-local* and shadows rather than augments the global — only `declare global { interface Window { ... } }` inside a module reaches the global scope. "`namespace` + `class` merging is erasable like `interface` merging" — no — `namespace` emits an IIFE that creates the companion object at runtime; `interface` merging leaves zero bytes (see [Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) and [Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)) — one is free, the other costs. "`interface Config { x: number }` followed by `interface Config { x: string }` merges and `x` becomes `number | string`" — false — conflicting property types on the same key error `TS2717` at the second declaration; merging does not widen to a union — use `&` with `never` semantics or pick one type.

**Performance note** — `interface` merging is `O(members)` per reopened name and memoizes to a single internal object type — no measurable delta in `tsc --extendedDiagnostics` for the typical 2–3 reopenings of `Window`/`Array`. Cost appears only when a *script* file participates in dozens of global `interface Window` augmentations: the checker re-evaluates the global namespace on every incremental edit (global invalidation), which slows language-server completions in 10k-file monorepos. Prefer module-scoped types and explicit `declare global` blocks over script-mode globals — `tsc --generateTrace trace/` shows global augmentation under `checkSourceFile` spikes. `namespace` + `class` merging adds emit size (IIFE per namespace) and a runtime object allocation; `interface` merging adds none. Measure before optimizing shape — `interface` vs `type` vs merging is purely a checker/emit concern.

**Mentor note** — teach merging with the three-space mental model from [Declaration spaces](<../../../02 The Type System Core/sections/2. The type vs value separation/2.2. Declaration spaces type value and namespace.md>): "complementary spaces compose; same-space repeats collide — except `interface` in type space, which merges." Exercise: give `interface A { x: number }` / `interface A { y: string }` and ask what `keyof A` is (`"x" | "y"` — merged). Then give `type A = { x: number }` / `type A = { y: string }` and ask the error (`TS2300`). Then give a file with `import { x } from "./x"; interface Window { foo: string }` and ask whether `window.foo` type-checks (no — module-local shadow; add `declare global`). Review checklist: every `namespace` with `class`/`function`/`enum` in source code must have a comment "why not `static`?" — otherwise flag as legacy non-erasable.

### 2) **Ambient augmentation** (`declare global`, `declare module "pkg"` — how `.d.ts` and `@types` extend third-party shapes without forking)

**Definition** — *ambient augmentation* is a `declare` block that adds members to an *already-declared* `interface` or `namespace` owned by another file or package, without owning or forking its source. Two forms (both erasable, both declaration-only): `declare global { interface Window { ... } }` — augments a global interface from inside a *module* file; `declare module "pkg" { interface Foo { ... } }` — augments the exported `interface Foo` of package `"pkg"` (or adds new declarations to it). A sibling form `declare module "pkg"` with no augmentation merges *ambient module* declarations (the `.d.ts` way to describe an untyped JS package). All three live in `.ts` or `.d.ts` files and emit nothing — they only extend the checker's type graph.

**What problem it solves / history** — before declaration merging, adding a field to `Express.Request` (`req.user`) or teaching `Array` a new method required either `// @ts-ignore` on every use, a forked `@types` copy, or a `type MyRequest = Request & { user }` that rippled `MyRequest` through every handler signature. Ambient augmentation solved the *open-world* problem: `lib.d.ts` defines `interface Window`; every `@types/*` and every project's `globals.d.ts` can *augment* it without a runtime cost. `declare module "pkg"` shipped with external modules (TS 0.9, 2013) to model Node's `require("pkg")`; `@types` packages (DefinitelyTyped, TS 2.0, 2016) standardized the `declare module` shape so `npm install @types/express` augments `import { Request } from "express"` via merging rather than replacement.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **When to use `declare global`** — only to add members that are *truly global* (browser `Window`/`Document`, `NodeJS.Global`, test `globalThis` helpers). The file *must* be a module (`export {}` or any `import`) — in a script file `declare global` is unnecessary and illegal; bare `interface Window { ... }` already merges globally. Keep one augmentation file per concern (`src/types/window.d.ts`, `src/types/node.d.ts`) — not scattered `declare global` blocks in random feature files.
- **When to use `declare module "pkg"`** — to add members to a *third-party* `interface` you import (e.g., `Express.Request`, `hono`'s `Context`, `next-auth`'s `Session`). Place the augmentation in a `.d.ts` that is *included* by `tsconfig.json` (via `include` or `typeRoots`/`types`) and ensure the augmentation file *imports* the target at least once so the module resolution registers — `import "express"` or `import type { Request } from "express"` at the top of the augmentation, then `declare module "express-serve-static-core" { interface Request { user: ... } }`. Use the precise module specifier the library exports from — `express-serve-static-core` not `express` for `Request` is the classic mismatch.
- **Prefer module augmentation over global augmentation** — `declare module "pkg"` is scoped to that module's consumers; `declare global` leaks to every file in the program. If the member is only needed where `"pkg"` is imported, augment the module, not the global.
- **All ambient augmentation is erasable** — safe under `--erasableSyntaxOnly` — unlike `namespace`/`enum` merging. Keep `.d.ts` augmentation files `import`/`export`-free except for the required `import "pkg"` marker — they are declaration-only by convention.

**Runnable example** — good vs bad ambient augmentation: `declare global`, `declare module`, `.d.ts` without forking — `typescript` fences runnable under `tsc --strict` (error lines commented; augmentation blocks shown as they would appear in a `.d.ts`):

```typescript
// ── Good: declare global — augment Window from a module file ──
// file: src/types/window.d.ts (module because of export {})
export {}; // makes file a module — required for declare global to be valid
declare global {
  interface Window {
    __APP_VERSION__?: string;
    __FEATURE_FLAGS__?: { darkMode: boolean };
  }
}
// Now any file in the program can use the augmented Window without casting:
declare const window: Window;
if (window.__APP_VERSION__) {
  console.log(window.__APP_VERSION__.toUpperCase()); // ok — string | undefined narrowed
}
console.log(window.__FEATURE_FLAGS__?.darkMode); // ok — optional chain

// bad — augmenting Window from a module WITHOUT declare global (module-local shadow)
// file: src/bad-window.ts
export {}; // module
interface Window { // this Window is LOCAL to this module — does NOT augment the global Window
  __LOCAL_ONLY__: string;
}
// declare const win2: Window;
// win2.__LOCAL_ONLY__ // this ref sees LOCAL Window, but global `window` does not — reviewer confusion
// fix — wrap in declare global { interface Window { __LOCAL_ONLY__: string } }

// ── Good: declare module — augment a third-party interface (Express-style example) ──
// file: src/types/express.d.ts
// This file augments the interface that `import { Request } from "express"` exposes.
// The real module that owns Request is "express-serve-static-core" — not "express" itself.
import "express-serve-static-core"; // marker so TS knows which module we augment
declare module "express-serve-static-core" {
  interface Request {
    user?: { id: string; role: "admin" | "user" };
    traceId?: string;
  }
}
// Now any handler that imports Request sees the extra members without changing its signature:
import type { Request as ExpressRequest } from "express-serve-static-core";
function handle(req: ExpressRequest): void {
  console.log(req.user?.id, req.traceId); // ok — augmented members available
}
handle({ user: { id: "1", role: "admin" } } as ExpressRequest);

// bad — augmenting the wrong specifier (no effect, no error)
// file: src/types/bad-express.d.ts
// declare module "express" { // wrong specifier — Request lives in "express-serve-static-core"
//   interface Request { user: unknown; }
// }
// fix — check node_modules/@types/express/index.d.ts re-export line to find the owning specifier.

// ── Good: ambient module declaration for an untyped JS package — add types without forking ──
// file: src/types/untyped-pkg.d.ts
// Suppose "untyped-pkg" is a JS library with no @types. Provide a minimal ambient declaration:
declare module "untyped-pkg" {
  export function greet(name: string): string;
  export interface Config { host: string; port: number; }
}
// Now imports type-check:
import { greet as pkgGreet } from "untyped-pkg" with { "resolution-mode": "import" }? // ignore resolution for demo
// Practical use — after declaration above, this would type-check:
// import { greet } from "untyped-pkg";
// console.log(greet("Ada")); // ok — returns string

// ── Good: .d.ts augmentation file is included by tsconfig ──
// tsconfig.json snippet (comment, not code):
// {
//   "compilerOptions": { "strict": true, "erasableSyntaxOnly": true },
//   "include": ["src/**/*", "src/types/**/*"] // ensures src/types/*.d.ts is part of the program
// }
// If the .d.ts is not included, augmentation silently disappears — no error, just missing members.

// bad — ambient augmentation in a script file via declare global (illegal)
// file: script-env.d.ts — NO export/import → script
// declare global { // error TS1231: 'declare global' is only valid inside a module — scripts are already global
//   interface Window { bad: string; }
// }
// fix — either make file a script and use bare interface Window, or make it a module with export {}:
// (script approach) bare augmentation:
// // interface Window { bad: string; } // ok in script file — merges globally
// (module approach):
// // export {}; declare global { interface Window { bad: string; } }

// good — module augmentation that adds overloads, not just properties
declare module "express-serve-static-core" {
  interface Response {
    json(body: { ok: true; data: unknown } | { ok: false; error: string }): this;
  }
}
// Now res.json({ ok: true, data: {} }) has a narrower check — no cast at call site.

// All above augmentation blocks are erasable — npx tsc --strict --erasableSyntaxOnly --noEmit → ok (no TS1294)
```

```typescript
// bad — forking @types instead of augmenting (creates duplicate, diverging definitions)
// file: node_modules/@types/express/index.d.ts (pretend fork: copied and edited Request to include user)
// interface Request { user: ...; traceId: ...; /* copy-pasted rest */ }
// Problem — the fork diverges on every @types update; augmentation survives updates automatically.
// fix — keep the original @types and augment via declare module "express-serve-static-core" in src/types/.

// bad — augmenting with `type` (not mergeable, even inside declare module)
// declare module "express-serve-static-core" {
//   type Request = { user: unknown }; // error TS2300: Duplicate identifier 'Request' — type cannot merge
// }
// fix — only `interface` participates in declaration merging — use interface:
declare module "express-serve-static-core" {
  // interface Request { user?: ... } // ok — reopens the imported interface
}

// good — lightweight augmentation marker pattern (import type + declare module)
// file: src/types/hono.d.ts
import type { Context } from "hono";
declare module "hono" {
  interface ContextVariableMap {
    userId: string;
  }
}
// Use: c.get("userId") now typed — hono's ContextVariableMap is designed for augmentation
```

**Common confusion** — "`declare module` replaces the module's types" — no — it *reopens* `interface`/`namespace` members — existing members stay; `type` members still cannot merge. "`declare global` is needed even in a script file" — opposite — script files are already global, so bare `interface Window { ... }` suffices; `declare global` is illegal in scripts (`TS1231`) and is only for module files. "My augmentation has no effect — must be a bug" — most often the `.d.ts` is not *included* by `tsconfig.json` (`include`/`files`/`typeRoots`) or the augmentation file has no `import "pkg"` marker so the module resolution never loads it — both fail silently with no diagnostic. "I can augment a `type` alias via `declare module`" — never — `type` never participates in merging, even inside `declare module` — the augmented target must be an `interface` (or `namespace`/`class` value), which is why well-designed libraries expose `interface` for extensible contracts and `type` for closed unions.

**Performance note** — ambient augmentations are purely type-graph nodes — `O(augmentations)` and negligible in isolation. The cost signal is *where* they are evaluated: a single `src/types/*.d.ts` with explicit `import "pkg"` is evaluated once and cached; scattered `declare global` blocks duplicated across feature files cause repeated global-namespace rechecks on incremental edits (each edit invalidates the global scope). Measure with `tsc --extendedDiagnostics --generateTrace trace/` — a monorepo with 40+ ad-hoc `declare global` blocks can add 50–120 ms to incremental `getSemanticDiagnostics` after a global-interface edit versus one consolidated augmentation file. No emit, no allocation — purely checker invalidation.

**Mentor note** — teach augmentation as "the tax for open-world typing" — show `npm ls @types/express` alongside `src/types/express.d.ts` and ask "where does `req.user` live?" — answer: *nowhere in the library* — it lives in our augmentation, which is why `declare module "express-serve-static-core"` must name the owning specifier, not the re-exporter. Review exercise: hand a PR that adds `declare global { interface Window { __DARK__: boolean } }` in a feature component file — ask whether it should be merged into `src/types/window.d.ts` and whether the file needs `export {}` (yes to both). Checklist: every `declare global`/`declare module` block has (a) a file-level `export {}` or `import "pkg"` marker, (b) a comment naming the owning package/specifier, (c) no `type` merging attempt — lint with `no-restricted-syntax` for `TSTypeAliasDeclaration` inside `TSModuleDeclaration`.

### 3) **Risks and guardrails** (uncontrolled augmentation leaks globally; prefer scoped module augmentation and lint for duplicate `interface` names)

**Definition** — *uncontrolled augmentation* is an `interface` reopening or `declare global`/`declare module` block that is (a) *global* when it should be *module-scoped*, (b) *duplicated* across files with diverging members, or (c) *over-approved* — an `interface` that reopens a core type (`Window`, `Array`, `Request`) with an optional property that silently changes optionality for every consumer. The leak is that declaration merging is *ambient and transitive*: once a `.d.ts` is included in the program, its augmentation is visible to every file that the program type-checks — no `import` required to pull it in — so an augmentation that adds `title?: string` to a global interface can make a required `title` effectively optional downstream without any local edit.

**What problem it solves / history** — early TypeScript projects kept `globals.d.ts` with `interface Window { analytics: any }` imported via `/// <reference path>` and every feature file contributed its own `declare global` snippet. As monorepos grew (10k+ files, 30+ teams), two failure modes emerged: (1) *ghost members* — TypeScript 3.0's `unknown` on `catch` and 3.7's `Array.flat` exposed that an ambient augmentation adding `Array.prototype.myFlat` with a wrong signature infected every `Array` hover; (2) *silently optional* — `declare global { interface Request { user?: User } }` that was intended as "sometimes present" became "every `req.user` needs `?.`" and hid missing auth middleware. TypeScript 4.4's `exactOptionalPropertyTypes` and 5.8's `--erasableSyntaxOnly` did not fix the scope problem — scope is fixed by preferring *module* augmentation (`declare module "pkg"`) over *global* augmentation, and by linting every `interface` reopening as intentional rather than accidental (ESLint `@typescript-eslint/no-duplicate-type-constituents` does not catch this — a custom rule or code-review convention is needed).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Default to module augmentation** — `declare module "pkg" { interface Foo { ... } }` is scoped to importers of `"pkg"`; `declare global { interface Window { ... } }` is global to the whole program. If the shape is only needed where `pkg` is used, never use the global form. Reserve `declare global` for `Window`/`globalThis`/`NodeJS.Global` — and consolidate those into one `src/types/globals.d.ts` per global, not one per feature.
- **Lint duplicate `interface` names** — enable a rule that flags every second `interface Foo` in the same scope as a warning unless the file is a `.d.ts` augmentation with an explicit `// augmentation:` comment. Options: `eslint-plugin-no-duplicate-interface` (community), `@typescript-eslint/consistent-type-definitions` with augmentation carve-out, or a repo-level `grep -R "^interface Window"` pre-commit check. Prefer a single augmentation file per target (`window.d.ts`, `express.d.ts`, `hono.d.ts`) over scattered reopenings.
- **Keep augmentations precise and required where required** — an augmentation that adds `user?: User` (optional) is safer than `user: User` (required — breaks every existing `Request` construction) but still leaks optionality. Document whether the member is *always* present (auth middleware guarantees it) vs *sometimes* present (some routes lack auth) and match the optionality to the invariant — or use a narrowed subtype `AuthenticatedRequest extends Request { user: User }` instead of mutating the global `Request`.
- **Treat every `interface` reopening as a public API change** — it is visible to every consumer of the program and cannot be tree-shaken. In code review, ask: "does every file that imports this module now see the new member? Is that intentional?" If not, replace the augmentation with a local intersection `type LocalRequest = Request & { user: User }` that is scoped to the call site.
- **Gate with `tsconfig` inclusion** — place augmentation `.d.ts` files under `src/types/` and ensure `include` lists them explicitly — an augmentation that is not included is invisible, one that is included is program-global; both directions surprise. Use `tsc --listFiles` to verify which `.d.ts` contributed to the program.

**Runnable example** — guardrails in action: scoped module augmentation vs leaking global, lint-worthy duplication, optional-leak bug — good vs bad, `typescript` fences runnable under `tsc --strict`:

```typescript
// bad — uncontrolled global augmentation scattered across feature files
// file: src/features/auth/auth.ts
export {}; // module, but augmentation below leaks globally
declare global {
  interface Window { __AUTH_TOKEN__?: string; } // global — every file sees __AUTH_TOKEN__
}
// file: src/features/billing/billing.ts
export {};
declare global {
  interface Window { __BILLING_TOKEN__?: string; } // another global — Window now has two unrelated tokens leaked from two features
}
// Problem — Window has become a feature grab-bag; any file's typo `window.__AUTH_TOKKEN__` is silent (excess property not checked on Window).
// fix — consolidate globals into one file, and prefer module augmentation where possible:

// good — consolidated, scoped, reviewed augmentation
// file: src/types/window.d.ts — single source of truth for globals
export {}; // module marker
declare global {
  interface Window {
    // App-wide version — intentionally global; single declaration, single review
    __APP_VERSION__?: string;
  }
}
declare const win: Window;
console.log(win.__APP_VERSION__?.toUpperCase()); // ok
// console.log(win.__AUTH_TOKEN__); // error — not leaked — feature tokens live on their module's types, not on Window

// good — prefer module augmentation over global when the member belongs to a package
import "express-serve-static-core"; // marker
declare module "express-serve-static-core" {
  interface Request {
    // Only files that import Request from express see this — not every file in the program
    user?: { id: string; role: "admin" | "user" };
  }
}
import type { Request as Req } from "express-serve-static-core";
function handler(req: Req): void {
  console.log(req.user?.role); // ok — scoped to Request importers
}
handler({ user: { id: "1", role: "user" } } as Req);

// good — when augmentation would change optionality globally, use a local subtype instead
type AuthenticatedRequest = Req & { user: { id: string; role: "admin" | "user" } }; // user required — local
function adminOnly(req: AuthenticatedRequest): void {
  console.log(req.user.id); // no ?. needed — type guarantees presence
}
const authReq: AuthenticatedRequest = { user: { id: "1", role: "admin" } } as Req as AuthenticatedRequest;
adminOnly(authReq);

// bad — augmentation that makes a required member effectively optional everywhere (leak)
// file: src/types/bad-user.d.ts
// declare module "express-serve-static-core" {
//   interface Request { title?: string; } // adds optional title to EVERY Request — even routes that require title
// }
// If some endpoint declares `interface CreateReq extends Request { title: string }`, the optional augmentation doesn't break it,
// but it does make `req.title` optional in generic helpers that only know `Request` — three calls later a missing-title bug surfaces.
// fix — never add optional members to a wide global that downstream code expects required:
// type CreateReqFixed = Req & { title: string }; // local intersection keeps requirement local
type CreateReqFixed = Req & { title: string };
const cr: CreateReqFixed = { title: "Hello" } as Req as CreateReqFixed;
console.log(cr.title.toUpperCase()); // HELLO — presence guaranteed by local shape, not leaked

// bad — duplicate interface names in the same non-augmentation file (lint target)
interface Config { host: string; }
interface Config { port: number; } // merges — but was this intentional or a copy-paste collision?
const cfg: Config = { host: "localhost", port: 5432 };
console.log(cfg.host); // localhost
// In non-.d.ts source code, a second interface Config is usually accidental — the reviewer should demand either:
// (a) a single declaration: interface Config { host: string; port: number; }
// (b) or an augmentation file with a comment: // augmentation: adds port for v2 API
// Lint — grep for ^interface\s+Config in src/**/*.ts (non-.d.ts) and flag as warning unless // augmentation: present

// good — single declaration for app-owned types that don't need merging
interface AppConfig { host: string; port: number; }
const appCfg: AppConfig = { host: "localhost", port: 5432 };
console.log(appCfg.port); // 5432

// bad — type duplicate hidden behind augmentation attempt (still errors)
// declare module "express-serve-static-core" {
//   type Request = { user: unknown }; // error TS2300: Duplicate identifier 'Request' — type never merges, even in augmentation
// }
// fix — augmentation targets must be interface — if the library exported a type, use local intersection instead:
// type PatchedRequest = Req & { myExtra: string }; // local, not global
const patched: Req & { myExtra: string } = { myExtra: "x" } as Req & { myExtra: string };
console.log(patched.myExtra); // x
```

```typescript
// bad — .d.ts not included by tsconfig so augmentation silently disappears
// file: src/types/hidden.d.ts — exists on disk but tsconfig include is ["src/app/**/*"] (excludes src/types/)
// declare module "express-serve-static-core" { interface Request { hidden: string } }
// No error — but no augmentation either — every req.hidden errors TS2339 at use site
// fix — verify inclusion:
// $ npx tsc --listFiles | grep hidden.d.ts
// (no output → not included)
// tsconfig.json fix: "include": ["src/**/*", "src/types/**/*"] or add "files": ["src/types/hidden.d.ts"]

// good — explicit inclusion check in CI
// Add to package.json scripts: "typecheck": "tsc --noEmit --strict && tsc --listFiles | grep -q 'express.d.ts'"

// bad — any-typed augmentation (defeats the purpose of typing)
// declare module "express-serve-static-core" {
//   interface Request { user: any; } // any leaks — every req.user.* is unchecked
// }
// fix — precise shape or unknown with narrowing:
declare module "express-serve-static-core" {
  interface Request {
    // precise — role is checked, id is checked
    // (redeclared here to show the fix; in real file this would be the sole augmentation)
  }
}
// Use local precise type instead of any:
type SafeUser = { id: string; role: "admin" | "user" };
function isUser(u: unknown): u is SafeUser {
  return typeof u === "object" && u !== null && "id" in u && "role" in u;
}
function guarded(req: Req): void {
  if (isUser((req as Req & { user: unknown }).user)) {
    console.log("safe user");
  }
}
guarded({} as Req);
```

**Common confusion** — "duplicate `interface` names are always a lint error — set the rule to `error`" — not in `.d.ts` — augmentation *requires* duplication; the rule should be `error` in `src/**/*.ts` and `off` (or `warn` with `// augmentation:` comment exemption) in `src/types/**/*.d.ts`. "If I `declare module "pkg"` in one file, only that file sees the augmentation" — false — once a `.d.ts` is included in the program, its module augmentation is visible to every file that imports `"pkg"` — it is program-scoped via inclusion, not file-scoped. "Adding `?:` in an augmentation is harmless because it's optional" — harmful when downstream code narrows on presence — `if (req.user)` now type-guards an optional that was added globally without auditing every branch that assumed presence or absence. "I can hide an augmentation by not exporting it" — `declare module` blocks are always ambient and ignore file-level exports — their only gate is whether the file is included by `tsconfig` and whether the module specifier matches the import path.

**Performance note** — guardrail cost is about *invalidation scope*: a single consolidated `src/types/express.d.ts` augmented module is invalidated only when that file changes; ten scattered `declare global { interface Window { ... } }` blocks cause any `Window`-affecting edit to invalidate every file that touches `window` (global scope cache). Quantify with `tsc --extendedDiagnostics`: after editing one `declare global` block, `Files` and `Types` counts spike proportionally to augmentation fan-out. No emit cost — augmentation is erasable — but check latency follows fan-out linearly. Measure with `tsc --generateTrace trace/` and look for `checkSourceFile` on globals; deduping ten scattered augmentations into one file can shave 5–12% off incremental check time in a 5k-file program. No runtime allocation — strictly a checker concern.

**Mentor note** — enforce the three-file rule in review: (1) `src/types/globals.d.ts` owns `declare global` (one file, one review, `CODEOWNERS` gate), (2) `src/types/<pkg>.d.ts` owns each `declare module "pkg"` (one file per third-party, named after its specifier), (3) every other `interface` reopening in `src/**/*.ts` is flagged as "prove this is intentional — why not a single declaration or a local `&`?" Exercise: open `npx tsc --listFiles` beside `git ls-files "src/types/*.d.ts"` and ask "which `.d.ts` is *not* in the program and therefore silently dead?" — answer reveals the inclusion bug. Checklist in `CONTRIBUTING.md`: every `declare module` line names its specifier in a comment (`// augments express-serve-static-core: Request.user`), every `declare global` lives in `src/types/globals.d.ts` with `export {}` header, and `npm run lint:augmentation` (`grep -R "^interface Window\|^declare global" src --include="*.ts" | grep -v "src/types/"`) exits non-zero.
