## 2.3. Type queries on objects — keyof, indexed access, and typeof capture

Type queries let you *derive* a type from another type or from a value — without re-declaring it. On object types they are the reflective trio that keeps a single source of truth: `keyof` lists the keys, `T[K]` reads the member type, and `typeof` (in type position) snapshots a value's shape. This leaf applies the primitive operators introduced in [2.3. Type queries](<../../../02 The Type System Core/sections/2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>) specifically to object shapes — and explains why every query erases to zero bytes.

---

### 1) **keyof and `T[K]` on object types** (`keyof {a:number,b:string}` → `"a"|"b"`; `T[keyof T]` as ad-hoc value union)

**Definition** — `keyof T` is a *type operator* that takes an object type `T` and produces a string/number/symbol literal union of its own property names. `T[K]` (indexed access) then reads the *type* of the property `K` in `T`. For `type O = { a: number; b: string }`, `keyof O` is `"a" | "b"` and `O["a"]` is `number`. Compose them — `T[keyof T]` — and you get the union of *all value types* in `T` (e.g., `number | string`) without naming a second type.

**What problem it solves / history** — before `keyof` (TS 2.1, late 2016) you duplicated. A route table `const ROUTES = { home: "/", users: "/users" }` needed a separate hand-written `type RouteKey = "home" | "users"` and a `type RouteVal = string`. Add a route, update two places — or forget the union and ship a typo. Generic helpers like `pluck(obj, key)` took `key: string` and returned `any`, because there was no way to say "`K` is a key of `T` and the result is `T[K]`". `keyof` + `T[K]` closed that gap with one constraint (`K extends keyof T`) and one indexed access. `T[keyof T]` then became the idiomatic "values of this object" without a mapped type or enum.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Need the key union of an object type** → `keyof T` — never duplicate a string union that `T` already declares. For `type User = { id: string; name: string }`, `keyof User` is always the truth, even after augmentation (merged `interface` members extend the union automatically).
- **Need the value union** → `T[keyof T]` — the cheapest ad-hoc "values" type. Use it for return types, config-value validators, and discriminant narrowing before reaching for `Object.values` (whose typed return is intentionally `unknown[]` without a helper).
- **Need a safe property reader** → `K extends keyof T` + `T[K]` — `function get<T, K extends keyof T>(obj: T, key: K): T[K]` preserves literal correlation (`get(user, "name")` is `string`, not `string | number`). Passing bare `string` loses that.
- **Object-specific edge** — with an index signature (`{ [k: string]: number; a: number }`), `keyof` widens toward `string | number` (string-like keys + number-coercible keys) — not just `"a"`. Model exact keys with `Record<"a"|"b", T>` when you need a closed key set (see [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>)).

**Runnable example** — `keyof` on a literal object, `T[K]` correlation, and ad-hoc value union — good vs bad (`tsc --strict` — error lines commented so the fence compiles):

```typescript
// good — keyof produces the exact key union; T[K] reads the member type
type Obj = { a: number; b: string };
type Keys = keyof Obj; // "a" | "b"
type AVal = Obj["a"];  // number
type BVal = Obj["b"];  // string

// good — T[keyof T] is the value union without a second declaration
type ObjValues = Obj[keyof Obj]; // number | string
const v1: ObjValues = 42;    // ok
const v2: ObjValues = "hi"; // ok
// const v3: ObjValues = true; // error TS2322: Type 'boolean' is not assignable to type 'string | number'.

// good — generic pluck keeps key ↔ value correlation via keyof + T[K]
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const obj: Obj = { a: 1, b: "x" };
const a = get(obj, "a"); // number — precise
const b = get(obj, "b"); // string — precise
console.log(a + 1, b.toUpperCase()); // 2 X

// good — config-shaped object: derive keys and values directly from the shape
const FEATURES = { darkMode: true, betaSearch: false, maxItems: 20 } as const;
type FeatureMap = typeof FEATURES; // (captured via typeof — §2) — { readonly darkMode: true; ... }
type FeatureKey = keyof FeatureMap; // "darkMode" | "betaSearch" | "maxItems"
type FeatureVal = FeatureMap[FeatureKey]; // true | false | 20 → boolean | 20 (true/false collapse to boolean unless as const)
type FeatureValStrict = FeatureMap[FeatureKey]; // with as const above, maxItems stays 20 (literal), booleans stay true/false literals via as const
console.log(a, b); // use to avoid unused warning

// bad — accepting string loses the correlation and widens to the value union
function getLoose(obj: Obj, key: string): Obj[keyof Obj] {
  // key could be any string — no guarantee it is "a" | "b"; caller loses literal return type
  // Also needs an assertion inside because string is not keyof Obj:
  return (obj as Record<string, Obj[keyof Obj]>)[key];
}
const loose = getLoose(obj, "a"); // type number | string — lost that "a" → number
// fix — constrain K extends keyof Obj as in get() above

// bad — duplicating the union by hand — drifts when Obj changes
type HandKeys = "a" | "b"; // duplicate of keyof Obj — add c: boolean to Obj and this type lies
// fix — type HandKeys = keyof Obj — single source of truth

// bad — keyof on an open dictionary widens immediately
type Dict = { [key: string]: number; id: number };
type DictKeys = keyof Dict; // string | number — not "id" literal; index signature floods the union
// fix — when exact keys matter, use Record<"id", number> or a closed mapped type, not an index signature
```

```typescript
// bad — indexing with a bare string without a keyof constraint defeats the check
type User = { id: string; name: string };
function read(user: User, key: string) {
  // return user[key]; // error TS7053: Element implicitly has an 'any' type because expression of type 'string' can't be used to index type 'User'.
  return (user as Record<string, string>)[key]; // assertion silences — but runtime key may be "email" and returns undefined silently
}
// good — constrain and return T[K] so the wrong key is a checker error, not a runtime undefined
function readSafe<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const user: User = { id: "1", name: "Ada" };
const userName = readSafe(user, "name"); // string
// readSafe(user, "email"); // error TS2345: Argument of type '"email"' is not assignable to parameter of type 'keyof User'.
console.log(userName.toUpperCase()); // ADA

// good — optional members: T[keyof T] includes undefined at the value level only when optionality permits it
type Opt = { a: string; b?: number };
type OptKeys = keyof Opt; // "a" | "b"
type OptVals = Opt[keyof Opt]; // string | number | undefined — b contributes number | undefined
const okOpt: OptVals = undefined; // ok — from optional b
console.log(okOpt);
```

**Common confusion** — "`keyof` includes `toString` and prototype members" — no, `keyof {a:number}` is `"a"` only; prototype keys appear only if `T` actually declares them (e.g., `keyof string` includes `"length"` because `String` declares it). "`keyof` always gives string literals" — numeric keys (`{ 0: string }`) contribute `number`, and `unique symbol` keys contribute the symbol type; `keyof { [k: number]: string }` is `number`. "`T[K]` creates a runtime object" — it reads a *type*, erased (see §3); it never allocates. "`T[keyof T]` loses optionality/readonly" — `T[keyof T]` is a *value-type* union; optionality affects assignability of the container, but the value union itself always includes the possibly-`undefined` branch when `?:` members are present. "`keyof` on a merged interface is stale after augmentation" — the union updates automatically: adding `interface User { avatar: string }` augments `keyof User` to include `"avatar"` without touching the `keyof` line (see [2.2. Declaration merging and module augmentation](<./2.2. Declaration merging and module augmentation.md>)).

**Performance note** — `keyof` and `T[K]` are `O(members)` type-graph nodes with no runtime cost. The cost appears only when the *resulting union* is huge: `type V = BigObj[keyof BigObj]` over a 200-property generated type expands to a 200-member union that every assignment branches over (`O(N)` per check, hover becomes a 200-way `|` list). For generated or API-derived objects with >50 keys, *name* the intermediate (`type BigKeys = keyof BigObj; type BigVals = BigObj[BigKeys]`) rather than inlining `BigObj[keyof BigObj]` at every call site — it memoizes the expansion and shortens diagnostics/hover. No allocation, no GC — purely checker time. Measure with `tsc --extendedDiagnostics` and `tsc --generateTrace trace/`.

**Mentor note** — teach `keyof`/`T[K]` as the smallest DRY loop: write one object shape, derive everything. Exercise: give `type User = { id: string; name: string; role: "admin" | "user" }` and ask for (a) the key union and (b) the value union *without* writing a new literal — they should reach `keyof User` and `User[keyof User]`. Then add `email?: string` and ask how `User[keyof User]` changes (adds `| undefined`). Review checklist: every function that takes `(obj, key)` as `string` must be challenged — "why not `K extends keyof T` + `T[K]`?" — and every duplicated key union (`type K = "a" | "b"`) must point at `keyof Shape` instead. Pair with [3.3. Literal types and const assertions](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>) when literals narrow the value union.

### 2) **`typeof` value capture** (`const cfg = { host: "localhost" } as const; type Cfg = typeof cfg` — snapshot the shape without duplicating it)

**Definition** — `typeof` in *type position* (`type T = typeof value`) is a **type query** — it *captures* the static type the checker inferred for `value` and reuses it as a type, without re-declaring the shape. In *value position* (`if (typeof x === "string")`) it is the JavaScript runtime operator. The object lesson is `const cfg = { host: "localhost", port: 5432 } as const; type Cfg = typeof cfg` — one initializer is the single source; `Cfg` is `{ readonly host: "localhost"; readonly port: 5432 }` (with `as const`) or `{ host: string; port: number }` without it — never a duplicated `interface` that drifts.

**What problem it solves / history** — pre-`as const` (TS 3.4, 2019) teams wrote every config twice: a value and a parallel `interface Cfg { host: string; port: number }`. Adding a field meant updating both; widening meant the type said `string` while the value held `"localhost"` (precision lost). `typeof` queries existed from the earliest releases, but without `as const` they captured *widened* types (`{ host: string }`) — useful for shape, useless for literal precision. `as const` + `typeof` closed that gap: the initializer's literals are frozen *before* capture, so `typeof cfg` preserves `"localhost"` (not `string`) and `5432` (not `number`) plus `readonly`. Combined with `keyof`/`T[K]` it round-trips values to types for config tables, route tables, and discriminants — zero runtime cost.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Need a derived type from a value you already declare** → `type T = typeof value` — never re-type the shape. One edit point (`cfg`) updates both runtime and type.
- **Need literal identity preserved** → pair with `as const` (or `satisfies` when validating shape while keeping literals — see [03 3.3](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>)). Without `as const`, `typeof { host: "localhost" }` is `{ host: string }` — the literal narrows to its base (widening, see [03 3.2](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>)).
- **`const` alone does not preserve object-property literals** — `const cfg = { host: "localhost" }` still widens `host` to `string` (property is mutable `let`-like). `as const` is what narrows *and* marks `readonly`. Use `as const satisfies Shape` when you need both validation and literal capture.
- **Capture respects the inferred modifiers** — `typeof` captured from a `let`-initialized or non-`as const` object will reflect wider, mutable members; capture right after the `as const` declaration, not after mutations or widening reassignments.

| You write | Captured `typeof` | Literal? | `readonly`? |
|---|---|---|---|
| `const cfg = { host: "localhost" }` | `{ host: string }` | no — widened | no |
| `const cfg = { host: "localhost" } as const` | `{ readonly host: "localhost" }` | yes | yes (deep) |
| `const cfg = { host: "localhost" } as const satisfies { host: string }` | same as above, but shape validated | yes | yes |
| `let cfg = { host: "localhost" }` | `{ host: string }` (reassignable base) | no | no |

**Runnable example** — snapshot with `as const` vs losing literals without it — good vs bad (`tsc --strict` — error lines commented):

```typescript
// good — as const + typeof: literal-accurate snapshot, single source of truth
const cfg = { host: "localhost", port: 5432, debug: false } as const;
type Cfg = typeof cfg; // { readonly host: "localhost"; readonly port: 5432; readonly debug: false }
type CfgKeys = keyof Cfg; // "host" | "port" | "debug"
type CfgVals = Cfg[CfgKeys]; // "localhost" | 5432 | false — literals, not string | number | boolean

function getCfg<K extends keyof Cfg>(key: K): Cfg[K] {
  return cfg[key];
}
const host = getCfg("host"); // "localhost" (literal) — not string
const port = getCfg("port"); // 5432 (literal)
console.log(host.toUpperCase(), port + 1); // LOCALHOST 5433

// good — derive dependent unions from the snapshot without duplicating
const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "get" },
  createUser: { path: "/users", method: "post" },
} as const;
type Routes = typeof ROUTES;
type RouteKey = keyof Routes; // "home" | "users" | "createUser"
type RouteMethod = Routes[RouteKey]["method"]; // "get" | "post" — union of all methods
const m: RouteMethod = "get"; // ok
// const bad: RouteMethod = "delete"; // error TS2322: Type '"delete"' is not assignable to type '"get" | "post"'.
console.log(m);

// bad — missing as const: widened capture loses literal precision — host is string, not "localhost"
const cfgWidened = { host: "localhost", port: 5432 }; // widens: { host: string; port: number }
type CfgWidened = typeof cfgWidened; // { host: string; port: number } — less precise than Cfg
type HostWidened = CfgWidened["host"]; // string — lost "localhost"
type HostPrecise = Cfg["host"];       // "localhost" — kept
// function narrow requires literal:
function connect(host: "localhost"): void { console.log(`connect ${host}`); }
connect(host); // ok — host is "localhost" (precise capture)
// connect((cfgWidened as CfgWidened).host); // error TS2345: Argument of type 'string' is not assignable to parameter of type '"localhost"'.
// The fix for widened is to capture from the as const source, not to cast back — redeclare with as const or satisfies.

// bad — annotating the variable widens away the literal even though you wrote a literal value
const cfgAnnotated: { host: string; port: number } = { host: "localhost", port: 5432 };
type CfgAnnotated = typeof cfgAnnotated; // { host: string; port: number } — annotation widened before capture
// fix — leave inference to as const, or use satisfies to check without widening:
const cfgChecked = { host: "localhost", port: 5432 } as const satisfies { host: string; port: number };
type CfgChecked = typeof cfgChecked; // { readonly host: "localhost"; ... } — checked AND literal

// bad — capturing a let binding that will be reassigned: inferred as wider base
let mutableCfg = { host: "localhost", port: 5432 } as const;
// mutableCfg = { host: "remote", port: 80 } as const; // reassigning still typed as const snapshot until reassigned — let widens intent
type MutableCfg = typeof mutableCfg; // still the as const literal shape — but let signals "will be reassigned", so prefer const + typeof
// fix — always capture from const when literal identity matters
```

```typescript
// good — nested objects: as const narrows deeply, typeof captures the deep literal types
const THEME = {
  colors: { primary: "#0ea5e9", secondary: "#8b5cf6" },
  spacing: { sm: 4, md: 8, lg: 16 },
} as const;
type Theme = typeof THEME;
type ColorKey = keyof Theme["colors"]; // "primary" | "secondary"
type SpacingVal = Theme["spacing"][keyof Theme["spacing"]]; // 4 | 8 | 16 — literals, not number
const spacing: SpacingVal = 8; // ok
// const badSpacing: SpacingVal = 10; // error TS2322: Type '10' is not assignable to type '4 | 8 | 16'.
console.log(spacing);

// bad — capture before as const (order matters — query captures the static type at that point)
const raw = { mode: "fast" }; // widens to { mode: string }
type Raw = typeof raw; // { mode: string }
// const rawConst = { mode: "fast" } as const;
// type RawConst = typeof rawConst; // { readonly mode: "fast" } — precise
// fix — declare as const first, then typeof — never snapshot the widened intermediate
type Fixed = typeof raw extends { mode: string } ? "widened captured" : "ok";
const _proof: Fixed = "widened captured"; // raw was widened — demonstrates the cost
console.log(_proof);
```

**Common confusion** — "`typeof cfg` runs `typeof` at runtime" — opposite — in type position it is a *static* query (erased). The runtime `typeof` is `if (typeof x === "string")` — position decides. "`as const` changes the runtime object" — `as const` is a type assertion — runtime object is identical to plain `const` (same values, same prototype); only the static type narrows and gains `readonly`. "`const` alone preserves object literals" — `const cfg = { method: "get" }` still widens `method` to `string` — properties are mutable slots even under `const` — only `as const` narrows them. "`typeof` snapshot validates the shape" — `typeof` captures *whatever* you wrote — if the initializer is wrong, the snapshot is wrong. Validate with `satisfies` first (`{ host: "localhost" } satisfies Config`), then `typeof`. "`typeof` of a function captures its return type directly" — `typeof fn` is the function type; `ReturnType<typeof fn>` is the return.

**Performance note** — `as const` + `typeof` adds no runtime allocation — `as const` is an erased assertion and `typeof` capture expands only the inferred type graph. The checker cost is the size of the captured type: a 200-key `as const` config object produces a 200-member literal-mapped type, which is cheap at capture but can bloat every `keyof typeof CONFIG` hover downstream. Keep config objects cohesive — split a 200-key flat `CONFIG` into namespaced sub-objects (`CONFIG.db`, `CONFIG.api`) so each `keyof typeof CONFIG.db` is a 20-member union, not a 200-member one. Deep `as const` literals can also stringify long union hovers; name intermediates (`type DbConfig = typeof CONFIG.db`).

**Mentor note** — demo the widening trap with a one-line hover check: declare `const a = { method: "get" }` and `const b = { method: "get" } as const` side-by-side, hover each, ask "which one's `typeof` gives `"get"` vs `string`?" — the aha that `const` ≠ literal lock. In review, flag every `type X = typeof somePlainObject` where `somePlainObject` lacks `as const` or `satisfies` — ask whether literal capture was intended. When the answer is "shape only", make the intent explicit with a comment (`// shape-only capture — literals intentionally widened`). Pair with [3.3. Literal types and const assertions](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>) for `satisfies` nuance.

### 3) **Why queries erase** (like every type operator, they leave no emit — bridging value and type spaces with zero runtime cost)

**Definition** — *every* type query — `typeof` (type query), `keyof`, `T[K]`, mapped (`{[K in keyof T]: ...}`), conditional, template-literal — is a **type operator**: it runs in the checker, contributes to a static type, and **erases** (leaves zero bytes in emitted `.js`). The emitted JavaScript keeps only the *value* the query read from. `const cfg = { host: "localhost" } as const; type Cfg = typeof cfg; type K = keyof Cfg; type V = Cfg[K]` — after `tsc`, the runtime sees only `const cfg = { host: "localhost" }` — `Cfg`, `K`, `V`, and `as const` are gone.

**What problem it solves / history** — without type operators, every abstraction had a runtime tax. Pre-2016 the only way to list keys was a runtime `Object.keys` array and a parallel hand-maintained `type Keys = "a" | "b"` — two artifacts, one checker-checked, one runtime-checked, always risking drift. `enum` (the most notorious non-erasable construct) emitted a bidirectional `IIFE` object precisely because it tried to be *both* a type and a value with one declaration — the handbook's migration from `enum` to `as const` + `typeof`/`keyof`/`T[K]` (TS 3.4+) exists to remove that emit. TS 5.8 formalized the distinction with `--erasableSyntaxOnly` (and `--isolatedDeclarations` for parallel emit): `interface`, `type`, `typeof` queries, `keyof`, `T[K]` all pass; `enum`/`namespace`/`parameter properties` fail with `TS1294` — see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) and [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>). The modern story is: model in types *for free*, ship only values — native stripping (`node --experimental-strip-types` as of Node 22.12) can run the file by stripping *annotations only*, because queries never needed a transform.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Treat every query as a zero-cost abstraction** — derive `keyof typeof TABLE`, `T[keyof T]`, `typeof cfg` freely; they never add runtime branches, allocations, or dispatch. Prefer them over any runtime mirror (`Object.keys(x) as ("a"|"b")[]` is a lie the checker cannot verify).
- **Keep erasable syntax when you bridge spaces** — `const TABLE = { idle: 0, done: 1 } as const; type Key = keyof typeof TABLE; type Val = typeof TABLE[Key]` is `erasableSyntaxOnly`-clean — `node --experimental-strip-types` runs it, `tsc --erasableSyntaxOnly` passes, and Deno/Bun strip it. `enum TABLE { idle, done }` is not — it requires emit and blocks stripping — prefer the erasable trio (see the enum-to-literal migration in [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).
- **Grounding rule: types never branch at runtime** — a type query cannot answer a runtime question. `type K = keyof typeof userInput` does not *validate* `userInput` at runtime — it captures the static type (often `string`) — use a runtime validator (`zod`, `valibot`, or an `in`/`hasOwnProperty` guard) at boundaries (see [2.2. Static vs runtime](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>)).
- **`&`/`|`/`extends` on query results also erase** — `type Augmented = Cfg & { port: string }` that produces `never` on a conflict is a *checker* phenomenon — runtime never sees `never`; it just never constructs a valid value (see [2.1. Intersection vs extends](<./2.1. Intersection vs extends composing object types.md>)).

What is erased vs what survives (object-query edition):

| You write | Erased? | Survives as `.js` |
|---|---|---|
| `type Cfg = typeof cfg` | yes | — (gone) |
| `type K = keyof Cfg` | yes | — |
| `type V = Cfg[K]` / `T[keyof T]` | yes | — |
| `as const` / `satisfies` / `as` | yes | — |
| `interface` / `type` alias | yes | — |
| `const cfg = { ... }` | no (value) | `const cfg = { ... }` — runtime object |
| `enum` / legacy `namespace` | no (requires IIFE emit) | `var E = ...` — emitted wrapper |

**Runnable example** — emitted JavaScript proves zero trace — good vs bad (`tsc --strict` + `--erasableSyntaxOnly` — error lines commented):

```typescript
// good — every query erases; .js is just the value (single source of truth, zero cost)
const STATUS_MAP = { pending: 0, done: 1, failed: 2 } as const;
type StatusMap = typeof STATUS_MAP; // { readonly pending: 0; ... } — erased
type StatusKey = keyof StatusMap;   // "pending" | "done" | "failed" — erased
type StatusVal = StatusMap[StatusKey]; // 0 | 1 | 2 — erased (T[keyof T])

// Usage is also erased when it is a type annotation; runtime call keeps only values:
function handle(key: StatusKey): StatusVal {
  return STATUS_MAP[key]; // value-level indexing — emits as STATUS_MAP[key]
}
console.log(handle("done")); // 1
// After: npx tsc --target es2022 --module esnext
// emit → const STATUS_MAP = { pending: 0, done: 1, failed: 2 };
//         function handle(key) { return STATUS_MAP[key]; }
```

**Common confusion** — "`keyof`/`typeof`/`T[K]` ship as runtime helpers" — they don't — grep the emitted `.js`: only values (`const cfg = ...`) remain; types are comments for the checker. "`as const` emits `Object.freeze`" — `as const` is purely a type narrowing + `readonly` marker — runtime mutation (`(cfg as any).host = "x"`) still succeeds — for runtime freeze add `Object.freeze(cfg)` separately ([1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>)). "`enum` erases like queries" — `enum` emits an IIFE object — the entire reason to migrate to `as const` objects + `typeof`/`keyof`/`T[K]` is to get back to zero emit. "`T[K]` distributes at runtime like a `switch`" — it never runs — it is a static member-type read; runtime dispatch still needs `if`/`switch`/`in` guards.

**Performance note** — the performance dividend of erasure is *negative* cost (less code to parse, less I/O, smaller bundle) plus the *checker* dividend of unconstrained use — because queries add no dispatch, you can be generous without measuring. The only measurable number is the *lack* of cost: stripping-only startup (`node --experimental-strip-types`) cold-starts ~20–40% faster than transform execution on 500-file projects because no AST rewrite fires — every `as const` + `typeof` + `keyof` + `T[K]` line is a no-op (see [3.2. Executing TypeScript](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>)). The counterpart cost is language-server hover size — a `typeof CONFIG` that captures a 300-key `as const` object produces a 300-line tooltip — split `CONFIG` into namespaces to keep hover latency low (guide in [2.3. Type queries](<../../../02 The Type System Core/sections/2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>)).

**Mentor note** — close the "two universes" story from [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>): "value space is what ships; type space is the proof you erased — queries are the typed bridge." Demo by compiling a single file with `npx tsc --target es2022 --outDir /tmp/out` and `cat /tmp/out/demo.js` — students see every query vanish. Review checklist: every derived `type X = typeof Y` must answer "is `Y` declared `as const` when literals matter?" — and every consumption of `X` must answer "is there a runtime guard when `X` meets untrusted input?" — because the query is a *static* mirror, not a *runtime* validator. Bonus exercise: ask to rewrite a project's single remaining `enum` as `const E = { A: "A", B: "B" } as const; type E = typeof E[keyof typeof E]` and run `npx tsc --erasableSyntaxOnly` before/after — the failing `TS1294` disappears, which is the concrete signal that the bridge is now zero-cost.
