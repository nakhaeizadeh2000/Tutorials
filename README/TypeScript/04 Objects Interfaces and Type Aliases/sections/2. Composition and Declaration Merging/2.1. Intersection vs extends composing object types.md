## 2.1. Intersection vs `extends` — composing object types

### 1) **Two composition operators** (`interface B extends A` vs `type B = A & { extra }` — similar results, different error reporting and assignability edges)

**Definition** — two spellings compose one object shape from others: `interface Admin extends User { role: string }` declares a *heritage clause* — `Admin` must contain every member of `User` plus `role` — and `type Admin = User & { role: string }` computes a *set intersection* — a value satisfies `Admin` only if it satisfies both `User` and `{ role: string }` simultaneously. For non-conflicting plain object shapes both produce an identical required-member set and both erase completely at emit (see [Type erasure — what survives compilation](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)) — the difference lives in *when* conflicts are diagnosed and *how* the resulting type is displayed.

**What problem it solves / history** — `interface extends` shipped with TypeScript 0.8 (2012) as the nominal-looking heritage syntax for class/interface hierarchies and for augmenting `lib.d.ts` — `interface Array<T>` could `extend` without forking the global type, and conflicts were rejected *at the declaration* (`TS2430` — incompatible override). `type` with `&` arrived in 1.6 (2015) as the set-theoretic operator that can combine *any* types — objects, unions, primitives, branded intersections — but it cannot merge — redeclaring `type X = ...` is always `TS2300` ([1.3. Interfaces vs type aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). Two operators were needed because one owns *declaration-site hierarchy* (lintable at the heritage clause, cheap to intern) and the other owns *expression-site composition* (composable anywhere, supports non-object operands). Before `&`, the only way to add a property to a closed shape was to reopen the `interface` — which broke module boundaries.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Need heritage among plain object shapes with early conflict errors** → `interface B extends A` — incompatible overrides fail *at the interface line* (fast triage, reviewer sees `TS2430` on the clause, not three calls later). Readable `extends` chains double as documentation: `interface AuditedAdmin extends Admin, Audited {}` names the lineage.
- **Need composition with non-objects, unions, primitives, mapped/conditional, or ad-hoc one-off combinations** → `type B = A & { extra }` — only `&` accepts those operands (`string & { __brand }`, `A & Partial<B>`, `A & Record<string, unknown>`).
- **Both remain erasable** — neither triggers `TS1294` under `--erasableSyntaxOnly` (see [Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)); the choice is about diagnostics and expressiveness, not emit. Like all object types, both participate structurally — `type X = A & B` is assignable to `A` and to `B` iff its members satisfy each (see [Structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>)).
- **Rule of thumb** — exported contracts expected to grow via heritage → `interface extends`; internal computed shapes or cross-kind composition → `type &`.

**Runnable example** — same shape, two operators — identical success, different failure timing (good vs bad, `tsc --strict` — error lines commented with `TS` code so the fence still compiles):

```typescript
// good — interface extends: heritage clause, conflict checked at declaration
interface User {
  id: string;
  name: string;
}
interface Admin extends User {
  role: "admin";
  department: string;
}
const admin: Admin = { id: "1", name: "Ada", role: "admin", department: "eng" };
console.log(admin.id, admin.role); // 1 admin

// good — type intersection: set-like composition, same resulting shape
type UserT = { id: string; name: string };
type AdminT = UserT & { role: "admin"; department: string };
const adminT: AdminT = { id: "2", name: "Grace", role: "admin", department: "eng" };
console.log(adminT.id, adminT.role); // 2 admin

// good — both flow structurally to narrower consumers (width-agnostic)
function greet(u: User): string { return `hi ${u.name}`; }
greet(admin);  // ok — Admin ≤ User (interface lineage)
greet(adminT); // ok — AdminT ≤ User (intersection still has every member of User)

// bad — extends reports conflict AT the declaration (TS2430)
interface Base { age: number; }
 // interface BadExtends extends Base { age: string } // error TS2430: Interface 'BadExtends' incorrectly extends interface 'Base'. Types of property 'age' are incompatible. Type 'string' is not assignable to type 'number'.

// good — & defers the conflict: it computes the overlapping property as never, checked at USE sites
type BadIntersection = Base & { age: string };
// type of BadIntersection['age'] is never (= number & string) — declaration itself does NOT error
// const bad: BadIntersection = { age: "3" }; // error TS2322: Type 'string' is not assignable to type 'never'.
// const bad2: BadIntersection = { age: 3 };   // error TS2322: Type 'number' is not assignable to type 'never'.
// no value can satisfy age: never — every construction fails, but the diagnostic appears at the value, not at the type alias line

// good — & shines where extends cannot: union / primitive operands
type BrandedId = string & { readonly __brand: "UserId" }; // intersection with primitive — only & can do this
function takeBranded(id: BrandedId): void { console.log(id); }
// takeBranded("raw"); // error — string lacks brand member
takeBranded("raw" as BrandedId); // ok via factory (branding pattern — see 04 3.2 textual forward)

// good — reassignable intersections for ad-hoc widening at the call site
type WithMeta = Admin & { label?: string }; // extra not in heritage; ad-hoc
const withMeta: WithMeta = { id: "3", name: "Linus", role: "admin", department: "eng", label: "on-call" };
console.log(withMeta.label); // on-call

// All above are erasable — npx tsc --strict --erasableSyntaxOnly --noEmit → ok
```

```typescript
// bad — reaching for & where extends would have caught the typo one line earlier (diagnostic-cost counterpart)
type Config = { host: string; port: number };
type ExtendedConfig = Config & { port: string }; // no error HERE — bug hides until someone builds ExtendedConfig
// const c: ExtendedConfig = { host: "localhost", port: 5432 }; // error at USE — reviewer must trace back to the & line
// fix — when both operands are plain object shapes and conflict is accidental, prefer interface heritage so the typo fails at the clause:
// interface ExtendedConfigI extends Config { port: string } // error TS2430 at THIS line — immediate, local
```

**Common confusion** — "`extends` and `&` are interchangeable aliases" — false for errors: `extends` fails fast at the declaration (`TS2430`), `&` computes `never` on conflicts and fails at every *use* site — different fix location and different reviewer workflow. "`&` merges like `interface` reopening" — no: `&` builds a new anonymous set; only `interface` reopening merges members into the same global declaration (see [1.3. Interfaces vs type aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). "`interface B extends A` creates nominal identity" — no — it is still structural: `type C = A & B` with the same members is assignable to `B` and vice versa; heritage is documentation plus early checking, not a runtime brand.

**Performance note** — for plain non-conflicting object shapes both operators are `O(members)` and intern to the same internal object type — no measurable delta in `tsc --extendedDiagnostics`. The delta appears only with conflicting members or large unions: `extends` is a flat member-merge that the checker can reject without instantiating an intersection (`never`) branch; `&` must compute `never` on the overlap and retain it in the type graph, which adds instantiation cost proportional to `conflicts × depth`. No runtime cost — both erase to zero bytes, no allocation, no dispatch, no GC. Measure with `tsc --extendedDiagnostics` and `tsc --generateTrace trace/` before optimizing spelling; prefer naming an intermediate (`type Mid = A & B`) over inlining a giant `A & B & C & D` at every call site.

**Mentor note** — demo the diagnostic split in one editor pane: place `interface Bad extends Base { age: string }` (red squiggle on the clause) next to `type Bad = Base & { age: string }` (red squiggle only when constructing) — students feel *why* the choice matters for review latency. Review checklist: every `A & { prop: T }` where `A` already declares `prop` must have a comment explaining that `prop: never` is intentional (branding, narrowing) — otherwise convert to `extends` so the error is local. Exercise: given `interface ApiResponse { data: string }` / `type CacheMixin = { cached: boolean }`, ask whether `interface Enriched extends ApiResponse, CacheMixin` and `type Enriched = ApiResponse & CacheMixin` differ — answer: *no* for non-conflicting shapes — then add `data: number` to `CacheMixin` and ask where the error appears.

### 2) **When they disagree** (conflicting property types, optional vs required overrides, intersection with primitives/union members)

**Definition** — they *disagree* exactly where the language semantics diverge: (a) **conflicting required property types** — `extends` rejects incompatible overrides at the declaration, `&` collapses the property to `never`; (b) **optional-vs-required on the same key** — `extends` requires the derived property to be *assignable* to the base (optional may widen to required with compatible type, incompatible type still fails), while `&` computes the intersection member-wise and the resulting optionality follows set semantics, often producing `T & undefined` or `never`; (c) **intersection with primitives / union members** — `extends` cannot name those operands at all (`interface X extends string` is `TS2320` / `TS2689`), only `&` can (`string & { __brand }`, `A & (B | C)` distributes).

**What problem it solves / history** — TypeScript needed two answers to "what if two parents disagree on the same key?" — heritage (`extends`) models *refinement* — a subtype narrows or keeps the parent's contract, so narrowing `age: number` to `age: string` is rejected immediately as "does not refine" (heritage is a subtype check). Intersection (`&`) models *set conjunction* — a value must satisfy *both* — so `number & string` is the empty set `never` (no value is both). The split mirrors two use cases added years apart: `extends` from 0.8 for interface hierarchies, `exactOptionalPropertyTypes` (4.4) and branded intersections (`string & { __brand }`) which *need* `&` with primitives to encode phantom members that `extends` cannot express.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Conflicting required types → prefer `extends` for plain objects** — the early `TS2430` is a better local signal than a `never` that errors at every construction site and in hover (`age: never` reads as opaque). Reserve `&`-producing-`never` for intentional narrowing that is documented (branding).
- **Optional vs required → know the matrix and pick the operator that preserves intent:**

| Base | Derived clause | `extends` | `&` |
|---|---|---|---|
| `name: string` | `name?: string` | error `TS2430` — optional not assignable to required | `string & (string | undefined)` effectively — still requires `string` because intersection requires both; optionality collapses |
| `name?: string` | `name: string` | ok — required refines optional (subtype may require more) | `{name?: string} & {name: string}` → `{name: string}` — required wins, same result |
| `name?: string` | `name?: number` | error `TS2430` — incompatible even though both optional | `never` on `name` — both optional but types disjoint |
| `name?: string` (with `exactOptionalPropertyTypes: true`) vs `name: string | undefined` | deliberate via `&` | see runnable — `T | undefined` vs `?:` differ under exact optionality (see [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) and [null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)) |

- **Need `string & Brand` / `A & (B|C)` / distribution** → `&` exclusively; `extends` cannot list a primitive or union as a parent. Intersections with primitives produce branded nominal-like types; with unions they *distribute* — `({a:string} & ( {b:string} | {c:string}))` → `({a:string}&{b:string}) | ({a:string}&{c:string})` — which `extends` cannot express without helper interfaces.

**Runnable example** — three disagreement regimes — good vs bad, `tsc --strict` (and `--exactOptionalPropertyTypes` where noted — flagged lines marked):

```typescript
// ── Regime 1: conflicting required property types ──

// bad — extends catches conflict at declaration (preferred for plain objects)
interface Base { id: string; age: number; }
// interface ConflictExtends extends Base { age: string } // error TS2430: 'age' string not assignable to number — local

// good — & defers: type of Bad['age'] becomes never — every value fails, hover shows 'never'
type Bad = Base & { age: string }; // ok at declaration — age is number & string → never
type AgeOfBad = Bad["age"]; // never — hover reveals the collapse
// const bad1: Bad = { id: "1", age: "3" }; // error TS2322: string not assignable to never
// const bad2: Bad = { id: "1", age: 3 };   // error TS2322: number not assignable to never — no value helps
// fix — decide which shape is truth; rename or narrow compatibly:
interface BaseFixed { id: string; age: number; }
interface DerivedFixed extends BaseFixed { age: number; verified: boolean; } // ok — keeps number
const fixed: DerivedFixed = { id: "1", age: 30, verified: true };
console.log(fixed.age); // 30

// ── Regime 2: optional vs required overrides ──

interface OptBase { nickname?: string; } // optional string
interface ReqDerived extends OptBase { nickname: string; } // ok — required refines optional (demands more)
const reqD: ReqDerived = { nickname: "Ada" };
console.log(reqD.nickname.toUpperCase()); // ADA — narrowing benefits from required

 // interface OptDerived extends OptBase { nickname?: number } // error TS2430 — type mismatch even though both optional
type OptConflict = OptBase & { nickname?: number }; // ok at declaration — nickname is (string | undefined) & (number | undefined) → never-like
// const oc: OptConflict = { nickname: "hi" }; // error — "hi" not assignable to never-flavored intersection

// optional widening requires type compatibility — string ⊆ string | undefined is ok, string ⊆ number is not
interface OptString extends OptBase { nickname?: string | undefined; } // ok — wider optional is compatible
type OptStringT = OptBase & { nickname?: string | undefined }; // ok — same via &

// exactOptionalPropertyTypes sharpens regime 2: ? vs | undefined diverge (see 04 1.2)
// Under exactOptionalPropertyTypes:true, { nickname?: string } means key may be absent but NOT present-with-undefined
// while { nickname: string | undefined } requires key present (possibly undefined). Intersection under exact flag
// can produce { nickname?: string } & { nickname: string | undefined } where the second demands presence — subtle.
type ExactOpt = { nickname?: string }; // absent ok, present must be string (when exact flag on)
type ExactReqUndef = { nickname: string | undefined }; // present required, may be undefined
type MixedExact = ExactOpt & ExactReqUndef; // requires key present (from second) and string when present (from first)
const mixedOk: MixedExact = { nickname: "hi" }; // ok
const mixedUndef: MixedExact = { nickname: undefined }; // ok when exact flag off; errors when exactOptionalPropertyTypes:true because ExactOpt disallows present-with-undefined
console.log(mixedOk.nickname, mixedUndef.nickname); // hi undefined
// rule — enable exactOptionalPropertyTypes and model missing vs null vs undefined distinctly (see 03 1.3)

// ── Regime 3: intersection with primitives and union members (only & can do this) ──

// good — intersection with primitive: branded type (nominal-like on top of structural)
// Only & can name a primitive operand; extends cannot (interface X extends string → TS2320)
type UserId = string & { readonly __brand: unique symbol };
function makeUserId(raw: string): UserId { return raw as UserId; } // factory proves validation
function takeUserId(id: UserId): void { console.log(`user:${id}`); }
const uid = makeUserId("u-42");
takeUserId(uid); // ok
// takeUserId("u-42"); // error — string not assignable to UserId (lacks brand) — nominal separation recovered structurally

// good — intersection distributes over unions (set-algebra needed for narrowing)
type A = { kind: "a"; a: string };
type B = { kind: "b"; b: number };
type C = { a: string } & (A | B); // distributes → ({a:string}&A) | ({a:string}&B)
declare function handle(x: C): void;
// handle({ kind: "a", a: "hi" }); // ok — satisfies A branch
// handle({ kind: "b", a: "hi", b: 1 }); // ok — satisfies B branch
console.log("C distributes — hover C to see union of intersections");

// bad — trying to express primitive/union composition with extends (not expressible)
// interface BadExtendsString extends string { extra: string } // error TS2320: An interface can only extend an object type or intersection of object types with statically known members. ('string' is a primitive)
// type BadUnionAlias = A | B;
// interface BadExtendsUnion extends BadUnionAlias { extra: string } // error TS2320 / TS2689
// fix — express as type with &:
type GoodExtendsUnion = (A | B) & { extra: string }; // ok — adds extra to either branch
const goodUnion: GoodExtendsUnion = { kind: "a", a: "hi", extra: "meta" };
console.log(goodUnion.extra); // meta

// good — intersection with index-signature-like open shape
type WithMeta = { id: string } & Record<string, unknown>; // & with Record — flexible carrier
const carrier: WithMeta = { id: "1", debug: true, hits: 3 };
console.log(carrier.id, carrier.debug); // 1 true
```

```typescript
// bad — silent never that ships: intersection with incompatible optional looked innocent but is uninhabitable
type BaseOpts = { timeout?: number; retries?: number };
type Override = BaseOpts & { timeout?: string }; // no declaration error — timeout is number & string → never
// The bug — every caller that sets timeout fails with a 'never' message that never points at the & line:
 // const opts: Override = { timeout: 3000 }; // error: Type 'number' not assignable to type 'never'
 // const opts2: Override = { timeout: "3s" }; // error: Type 'string' not assignable to type 'never'
 // const opts3: Override = {};                 // ok — optional absent avoids the never check — but setting the key is impossible
// fix — catch at declaration with extends, then fix the model:
interface BaseOptsI { timeout?: number; retries?: number; }
// interface OverrideI extends BaseOptsI { timeout?: string } // error TS2430 at THIS line — local, actionable
// correct model — choose ONE type for the key or make them distinct keys:
type OverrideFixed = BaseOpts & { timeoutMs?: number }; // new key, no conflict
const optsFixed: OverrideFixed = { timeout: 3000, timeoutMs: 3000 };
console.log(optsFixed.timeout); // 3000
```

**Common confusion** — "`A & B` with conflicting `age` gives a wider `age: string | number`" — opposite — `&` requires *both* (`number & string → never`, the empty set), while `|` would widen. "`optional` vs `| undefined` are the same so `extends` vs `&` shouldn't differ on optionality" — under `exactOptionalPropertyTypes` they differ (missing vs present-with-`undefined`) and the two operators surface that difference differently — see the `MixedExact` demo above and [03 1.3 discussion of `exactOptionalPropertyTypes`](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>). "`never` on the property means the type is still usable — just avoid that property" — no — `never` on a required key makes the whole intersection *almost* uninhabitable for objects that include that key; absence only sneaks past when the key is optional.

**Performance note** — disagreement regimes dominate checker cost: an intersection with `n` conflicting keys instantiates `n` `never` intersections and retains them in the type cache, so hover/`quickInfo` must render `never` for each — `O(n)` type-graph growth. A 20-key `A & B` with 5 conflicts can show 2–3× the `checker time` of the equivalent `interface extends` that failed fast (measured via `tsc --extendedDiagnostics`). Primitives/union distribution adds multiplicative branches: `X & (A | B | C | D)` expands to a 4-member union of intersections — `O(branches × members)` — which can blow up language-server completions. No runtime cost — disagreement is purely a checker phenomenon; emit is unaffected (intersections erase). Guideline — keep distribution explicit (`type U = (A & Extra) | (B & Extra) | ...`) when unions exceed 8 branches so reviewers see the branch count.

**Mentor note** — teach regime 2 with a table on the whiteboard and regime 3 with a live hover: show `Bad["age"]` tooltip as `never` and ask "what value inhabits `never`?" — answer: *none* — cements that `&` is set conjunction, not "merge and pick one". Review exercise: paste a PR with `type Config = Base & { timeout?: string }` where `Base` already has `timeout?: number` — ask which review comment is correct: (a) "not an error at the line" → wrong mental model, (b) "`timeout` is `never`" → correct, (c) "use `extends` to fail at the clause" → correct fix for plain-object refinement. Checklist: every `&` with overlapping keys needs either a `// intentionally never — branding` comment or a linter rule (`@typescript-eslint/no-redundant-type-constituents` / custom rule flagging `T & { sameKey: Incompatible }`) — otherwise convert to `extends` for early failure.

### 3) **Readability trade-off** (`extends` chains read like inheritance; intersections read like set union — error messages differ at scale)

**Definition** — readability here is *how fast a reviewer locates intent and fault*: an `extends` chain `interface C extends B { x: string }` reads like inheritance — parent names are a heritage clause, hover shows `interface C` with flat members, and errors point at the `extends` keyword with "`C` incorrectly extends `B`". An intersection `type C = B & { x: string }` reads like set union — operands are an expression, hover shows `type C = B & { x: string }` (or an expanded `B & C & D & E` chain), and conflicts surface only where `C` is used, with "`never` is not assignable to ..." or a long `B & C & D` expansion. Same members, different narrative and diagnostic path.

**What problem it solves / history** — before mapped/conditional types (pre-2.1) most teams read every composition as inheritance — a `User` *is-a* `Entity` — and `interface extends` mirrored that mental model. After 2.8+ utility types (`Partial`, `Pick`, `Omit`, `Record`) most compositions are *set-algebra expressions* — `type PublicUser = Omit<User, "password"> & { displayName: string }` — which cannot be spelled as heritage without helper interfaces, and whose hover naturally expands as a union of intersections. The two readings persist because one serves *contracts* (stable lineage) and the other *computed shapes* (transient expressions). The handbook (5.9 era) treats both as peer — the trade-off is diagnostic locality and hover cost, not correctness.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Public API / domain lineage (auth, billing, `Window` augmentation)** → `extends` — chain reads top-down (`AuditedAdmin extends Admin, Audited, Timestamped`), hover is a single named interface with flattened members, `extends` conflict errors point *at the interface* — one click to fix. Audit with `npx tsc --noEmit --pretty` — inheritance errors are one-line.
- **Ad-hoc / utility / computed (Omit/Pick/Record, `string & Brand`)** → `&` — expression reads left-to-right as "also has", hover preserves the operand names until expanded — useful when tracing which mixin contributed a key. But long `A & B & C & D & E & F & Record<...>` chains expand to a 4-line hover that hides which operand owns `__brand`, `debug`, or `cached` — at that point *name the intermediate*: `type Audited = Admin & Timestamped; type Visible = Audited & { visible: boolean }` — named aliases memoize in the language server and shorten errors from `... & ... & ... & Record<string,unknown> not assignable` to `Audited not assignable`.
- **Hover budget** — keep any single `type = ... & ...` expression to ≤3 operands on one line; beyond that extract a named type. Keep any single `interface extends A, B, C` heritage to ≤4 parents; beyond that introduce an aggregate parent (`interface Aggregate extends A, B, C {}`).
- **Error-message budget** — when reviewers consistently see "`never` on `timeout` not assignable ..." three calls away from the `&`, convert the conflicting pair to `extends` so the next reviewer sees `TS2430` at the clause. Measure with `tsc --extendedDiagnostics` — giant `&` hovers are a leading cause of "hover lag" in 10k-file monorepos (server expands every operand on hover).

| Composition | Reads as | Hover at scale | Error location | When to choose |
|---|---|---|---|---|
| `interface C extends A, B` | lineage — "is-a" | `interface C` — flat members | at `extends` clause (`TS2430`) | stable domain hierarchy, public contracts |
| `type C = A & B` | set — "also satisfies" | `type C = A & B` — expanded operands | at use site (`never` / excess on `C`) | ad-hoc, utility, primitive/union operands |
| `type C = A & B & C & D` (4+) | noisy set | 4-line `&` chain — slow | at every construction | name an intermediate instead |
| `interface C extends A&B` | mixed | flat + `&` inside heritage | at `extends` but hover still noisy | avoid — pick one idiom per declaration |

All four erase — readability is purely a checker/hover/CI concern (no emit, no runtime).

**Runnable example** — reading and debugging at scale — good vs bad, `tsc --strict`:

```typescript
// good — extends chain reads as lineage; conflict fails AT the clause (local)
interface Entity { id: string; createdAt: number; }
interface User extends Entity { name: string; }
interface AuditedUser extends User { auditedBy: string; verified: boolean; }
// Hover AuditedUser → { id, createdAt, name, auditedBy, verified } — flat, named heritage visible in clause.
// Add a conflict — diagnostic is immediate and points at the heritage keyword:
// interface BadAudited extends User { name: number } // error TS2430 at 'extends User' — one-line fix radius.

// good — & chain reads as set; NOMINATE intermediates to keep hovers short
type EntityT = { id: string; createdAt: number };
type UserT = EntityT & { name: string };
type AuditedT = UserT & { auditedBy: string; verified: boolean };
// Hover AuditedT → UserT & { auditedBy ... } — two operands, still readable.

// bad — giant anonymous intersection: hover becomes 5-operand expansion, error message lists the whole chain
type Giant = EntityT & { name: string } & { auditedBy: string } & { visible: boolean } & Record<string, unknown>;
declare const giant: Giant;
// console.log(giant.visible); // hover Giant → "EntityT & {name} & {auditedBy} & {visible} & Record..." — 5-line expansion in CI output
// fix — name intermediates so errors name the intermediate, not the expansion:
type NamedAudited = AuditedT & { visible: boolean };
type NamedGiant = NamedAudited & Record<string, unknown>; // now hover NamedGiant → NamedAudited & Record — 2 operands
const namedGiant: NamedGiant = { id: "1", createdAt: Date.now(), name: "Ada", auditedBy: "ops", verified: true, visible: true, extra: 1 };
console.log(namedGiant.visible, namedGiant.extra); // true 1

// bad — & conflict at scale: error appears at USE, three calls away from the & line
type BaseFlags = { debug?: boolean; verbose?: boolean };
type FlagsWithString = BaseFlags & { debug?: string }; // no error here — debug is boolean & string → never
function configure(flags: FlagsWithString): void { console.log(flags.debug); }
// configure({ debug: true });   // error TS2322 at CALL site: 'boolean' not assignable to 'never' — far from the & definition
// configure({ debug: "on" });   // error TS2322: 'string' not assignable to 'never' — same distance
// Good — extends fails at declaration, fixing radius is one line:
// interface FlagsBad extends BaseFlags { debug?: string } // error TS2430 at 'extends BaseFlags' — local, same file as definition
// Fix — rename or narrow compatibly:
type FlagsFixed = BaseFlags & { debugLevel?: string }; // distinct key — no conflict, readable intent
const flagsOk: FlagsFixed = { debug: true, debugLevel: "verbose" };
console.log(flagsOk.debug, flagsOk.debugLevel); // true verbose

// good — & required where extends cannot name the operand: utility composition reads as set expression (idiomatic &)
type PublicUser = Omit<{ id: string; name: string; password: string }, "password"> & { displayName: string };
const pub: PublicUser = { id: "1", name: "Ada", displayName: "adal" };
console.log(pub.displayName); // adal — & with Omit is the only spelling; heritage cannot spell Omit

// good — deep hover budget demo: prefer interface lineage for stable API, & for transient computed shape
interface ApiEntity { id: string; }
interface ApiUser extends ApiEntity { email: string; } // lineage — reviewer sees is-a
type RequestShape = ApiUser & { traceId: string; cached?: boolean }; // transient request — ad-hoc & is idiomatic
const reqShape: RequestShape = { id: "1", email: "a@b.co", traceId: "t-1" };
console.log(reqShape.traceId); // t-1
```

```typescript
// bad — mixing idioms in one declaration breeds noisy hovers and split error sites
type EntityT = { id: string; createdAt: number };
type UserT = EntityT & { name: string };
interface Mixed extends EntityT { extra: string } // heritage wrapping an intersection operand — hover mixes flat + & expansion
// Alternative that reads worse than splitting:
// type AlsoMixed = EntityT & UserT & { extra: string } // redundant: UserT already includes EntityT — redundant constituent
// fix — pick ONE idiom per declaration: lineage for lineage, set for set
interface Entity { id: string; createdAt: number; }
interface CleanLineage extends Entity { extra: string } // lineage — flat
type CleanSet = EntityT & { extra: string }            // set — 2 operands, no redundancy
const clean1: CleanLineage = { id: "1", createdAt: 0, extra: "x" };
const clean2: CleanSet = { id: "2", createdAt: 0, extra: "x" };
console.log(clean1.extra, clean2.extra); // x x
```

**Common confusion** — "long `A & B & C & D` is more explicit than named intermediates" — explicitness at the cost of hover that wraps past the editor gutter and error messages that list every operand — reviewers grep for `never` instead of reading the clause. "`interface` hover is always shorter" — only when heritage is flat; `interface X extends A & B & C` reintroduces the same `&` expansion inside the clause — compose as a *pure* lineage or a *pure* set, not a hybrid. "`Record<string, unknown>` with `&` is free" — `& Record<string, unknown>` on a closed shape makes the intersection *open* (`string`-keyed) and widens future excess-property leniency — see [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) — use `&` with dictionaries deliberately.

**Performance note** — readability and performance align: each unnamed `&` operand is a distinct type node the server must expand on hover and on error formatting — `O(operands × members)` per diagnostic. A 6-operand `A & B & C & D & E & F` hover can cost 30–80 ms of server `quickInfo` time (measured via `tsc --generateTrace` → `trace.json` hover latency) and 2× the `tsc --extendedDiagnostics` checker time of the equivalent 6-parent `interface extends A,B,C,D,E,F` that the checker interns as one flat member table. Naming intermediates (`type Mid = A & B`) cuts both hover length and error-text length because the server memoizes the alias — same emit (none). Rule — when `tsc --generateTrace` shows a `&` alias as a top `time`-ranked symbol, split it.

**Mentor note** — in code review, enforce a hover-budget lint: flag any `type X = A & B & C & D` with ≥4 operands or any `interface X extends A, B, C, D, E` with ≥5 parents — require a named intermediate (`type Audited = A & B`) and a code comment naming what `Audited` *means* (domain language, not just `A_and_B`). Exercise: show `tsc --extendedDiagnostics` for a file with a 7-operand `&` vs the same shape split into two named intermediates — time drops 10–15% and hover shrinks from 5 lines to 1 — makes the abstract budget concrete. Checklist: every `& Record<string, unknown>` has a comment "open dictionary intentionally — index signature trade-offs reviewed in [1.2](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>)" — otherwise flag as overly permissive.
