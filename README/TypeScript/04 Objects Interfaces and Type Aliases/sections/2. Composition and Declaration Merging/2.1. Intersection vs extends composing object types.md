## 2.1. Intersection vs extends — composing object types

An extends clause declares an object contract that must be compatible with its parents. An intersection A & B requires a value to satisfy both operands. With compatible object members they can describe the same usable shape, but conflicts and the kinds of permitted parents make the choice meaningful.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Save each named file in a new directory without a tsconfig.json. Run `tsc --strict --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir out FILE.ts`, then `node out/FILE.js`. Substitute composition, conflicts, optional, optional-undefined or branches. For a rejection, uncomment only the indicated line and use the same flags with `--noEmit` instead of `--outDir out`. Exact-optional comparisons add `--exactOptionalPropertyTypes` explicitly; strict alone does not enable that option.

### 1) **Compatible composition and legal heritage**

The PublicUser interface below can extend this Omit result because its members are statically known. PublicUserT expresses the same added displayName member through an intersection. Neither syntax choice makes the value nominal or creates an object at runtime.

Save `composition.ts`:

```typescript
export {};
type User = { id: string; name: string; password: string };
interface PublicUser extends Omit<User, "password"> { displayName: string }
type PublicUserT = Omit<User, "password"> & { displayName: string };
const user: PublicUser = { id: "1", name: "Ada", displayName: "adal" };
const alias: PublicUserT = user;
console.log("public:", alias.name, alias.displayName, "password" in alias);

type Audited = { auditedBy: string };
interface AuditedUser extends PublicUser, Audited {}
type PublicAndAudited = PublicUser & Audited;
interface NamedParent extends PublicAndAudited {}
const audited: AuditedUser = { ...user, auditedBy: "ops" };
const named: NamedParent = audited;
console.log("same value:", named === audited, named.auditedBy);
// interface InvalidSyntax extends PublicUser & Audited {} // TS1005: invalid syntax.
```

The output is `public: Ada adal false` and `same value: true ops`. The first object has no password because its initializer did not provide one. Omit does not delete properties from runtime data. Constructing a public response from a private record still requires deliberate value-level selection.

A comma-separated heritage list is valid. Extending the named PublicAndAudited intersection is valid here too. By contrast, uncommenting the direct PublicUser & Audited heritage syntax produces two TS1005 parser errors. Fix the syntax with the named parent or the comma-separated list; there is no general prohibition on mixing a concrete type alias with interface heritage.

Choose from the actual parent contract rather than a rule that utilities require intersection. The [Object Types reference](https://www.typescriptlang.org/docs/handbook/2/objects.html#interface-extension-vs-intersection) compares extension and intersection; [interfaces versus aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>) covers their other capabilities. Detailed Omit and mapped-type mechanics belong in [transformations](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>).

### 2) **Required conflicts, optional conflicts and compatible refinement**

An interface cannot refine age: number with age: string. An intersection instead retains both requirements. For the required property in the following example, the live equality check confirms that Conflict["age"] is never. Assigning an ordinary numeric age cannot satisfy it.

Save `conflicts.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
interface Base { age: number }
// interface BadHeritage extends Base { age: string } // TS2430 at declaration.
type Conflict = Base & { age: string };
type ImpossibleAge = Expect<Equal<Conflict["age"], never>>;
// const bad: Conflict = { age: 30 }; // TS2322 at construction.

type Narrow = { age: number } & { age: 18 | 21 };
const adult: Narrow = { age: 21 };
console.log("compatible refinement:", adult.age);

// If the string is an alternate representation, give it a different key.
interface FormattedAge extends Base { ageLabel: string }
const formatted: FormattedAge = { age: 30, ageLabel: "30 years" };
console.log("distinct keys:", formatted.age, formatted.ageLabel);
```

The output is `compatible refinement: 21` and `distinct keys: 30 30 years`. Uncomment BadHeritage to observe TS2430 at the declaration. Uncomment bad instead to observe TS2322 at the construction: number cannot satisfy the conflicting property's never type. The remedy is to decide the intended contract. A compatible literal refinement works; distinct keys work when the number and its formatted label represent different information. An assertion would conceal that decision.

Optional conflicts require separate reasoning about presence, present values and reading. If both operands allow omission, an empty object can satisfy both. That does not make a string or number value acceptable at the conflicting key.

Save `optional.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type OptionalConflict = { nickname?: string } & { nickname?: number };
const empty: OptionalConflict = {};
type ReadResult = Expect<Equal<OptionalConflict["nickname"], undefined>>;
console.log("omitted:", Object.hasOwn(empty, "nickname"), empty.nickname);
// const text: OptionalConflict = { nickname: "Ada" }; // rejected in both modes.
// const numeric: OptionalConflict = { nickname: 1 }; // rejected in both modes.

interface OptionalName { nickname?: string }
interface RequiredName extends OptionalName { nickname: string }
type AlsoRequired = OptionalName & { nickname: string };
const name: RequiredName = { nickname: "Ada" };
const same: AlsoRequired = name;
console.log("required:", same.nickname.toUpperCase());
// const missing: AlsoRequired = {}; // TS2322: nickname is required.
// interface WrongOptional extends OptionalName { nickname?: number } // TS2430.
```

With the default exact-optional setting, this compiles and prints `omitted: false undefined` and `required: ADA`. Check this same file with --exactOptionalPropertyTypes: it still succeeds, including the equality assertion that reading the optional conflict yields undefined. Activate text or numeric individually: both are rejected with TS2322 in both modes. The default-mode diagnostic names undefined; the exact-mode diagnostic names never for the attempted present value. The property read remains undefined because absence remains possible.

The compatible RequiredName refinement is accepted, and AlsoRequired similarly demands nickname through its required operand. Uncomment missing to observe TS2322 for absence. Uncomment WrongOptional to observe TS2430: an optional number does not refine optional string. Making both properties optional does not resolve their incompatible present values.

Save the following separate `optional-undefined.ts` to compare explicit undefined:

```typescript
export {};
type OptionalConflict = { nickname?: string } & { nickname?: number };
const present: OptionalConflict = { nickname: undefined };
type Mixed = { nickname?: string } & { nickname: string | undefined };
const mixed: Mixed = { nickname: undefined };
console.log("explicit undefined:", Object.hasOwn(present, "nickname"), present.nickname);
console.log("required undefined:", Object.hasOwn(mixed, "nickname"), mixed.nickname);
```

With the default setting, it prints `explicit undefined: true undefined` and `required undefined: true undefined`. Check it with --exactOptionalPropertyTypes and both assignments fail with TS2375. This is a checking-mode change, rather than a change in JavaScript object presence. Do not run stale emitted output to infer that a rejected exact-mode assignment was accepted.

| Contract in these probes | Exact optional off | Exact optional on |
|---|---|---|
| Conflicting optional string and number, omitted key | Accepted; read type undefined | Accepted; read type undefined |
| Same conflict, explicit undefined | Accepted | Rejected |
| Same conflict, present string or number | Rejected | Rejected |
| Optional string intersected with required string | Key required, string accepted | Key required, string accepted |
| Optional string intersected with required string-or-undefined, explicit undefined | Accepted | Rejected |

The [exact-optional reference](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html) establishes the missing-versus-explicit-undefined distinction. The intersection results above are checked directly. The [modifier owner](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) develops presence, readonly and dictionary behavior; this lesson adds the composition consequences.

### 3) **Expression composition, review intent and debugging**

An intersection can add a requirement to each branch of a union. An interface cannot extend a union parent whose members are not statically known as one object contract. That restriction differs from the accepted Omit example.

Save `branches.ts`:

```typescript
export {};
type Payment = { kind: "paid"; amount: number } | { kind: "failed"; message: string };
type AuditedPayment = Payment & { traceId: string };
function describe(payment: AuditedPayment): string {
  const detail = payment.kind === "paid" ? payment.amount.toFixed(2) : payment.message;
  return `${payment.traceId}: ${detail}`;
}
console.log(describe({ kind: "paid", amount: 12, traceId: "t1" }));
console.log(describe({ kind: "failed", message: "declined", traceId: "t2" }));
// interface BadParent extends Payment { traceId: string } // TS2312: union parent.
```

The output is `t1: 12.00` and `t2: declined`. Each alternative must also carry traceId, and the discriminator selects the branch-specific detail. Uncomment BadParent to observe TS2312. The [union/intersection owner](<../../../07 Unions Intersections and Narrowing/sections/2. Intersection Types/2.3. Unions and intersections distributive behavior and primitive intersections.md>) owns the full algebra and primitive intersections used by brands. Those type operators do not create validators.

For compatible object parents, extends offers a useful declaration-site compatibility check. Use an intersection when the expression itself captures the intended conjunction, including union or primitive operands. Name an intermediate when it communicates a coherent concept or makes a failing contract easier to locate. Parent count alone is not a reason to split a definition, and neither form guarantees a particular editor hover layout.

As a review exercise, consider optional timeout: number combined with optional timeout: string. Predict an empty object, an explicitly undefined key and each present value under both flag settings before checking them. The answer follows the optional-conflict probe: omission passes both, explicit undefined passes only with exact optional off, and both concrete present values fail. If milliseconds and formatted duration are different pieces of data, use distinct keys; if they are alternatives, redesign the contract deliberately rather than pretending intersection overwrites the old property.

### 4) **Common confusion**

Intersection means both requirements, rather than union or last-write-wins object spread. It does not reopen an existing declaration. A required conflicting member and a conflicting optional member have different usable cases: the latter may be omitted. Finally, a utility result is not automatically an illegal heritage parent; inspect whether the parent has statically known object members and use legal syntax.

### 5) **Performance note**

These declarations and type-equality probes erase. Object initializers, spread and function calls still execute. The compiler team's [performance guidance](https://github.com/microsoft/TypeScript/wiki/Performance#preferring-interfaces-over-intersections) identifies composition choices worth investigating, with codebase-dependent exceptions. No checker speed, hover latency or operand-count threshold was measured here. Use the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before attributing a cost to a particular composition, and preserve the contract when trying a different representation.

### 6) **Mentor note**

Ask where the incompatible age contract fails under each operator and why a numeric initializer cannot repair the intersection. Then require three separate answers for an optional conflict: can the key be omitted, which present values pass, and what is read? A sound answer names the exact-optional setting and predicts the observed diagnostics. Finish by asking why extends Omit succeeds while direct extends A & B fails: parent semantics and grammar are distinct questions.
