## 4.1. Objects interfaces checklist — mental models mentors insist on

An object-type review should explain what the consumer requires, where unexpected fields are checked, how absence is represented, and which construction establishes a domain invariant. The four checks below connect those questions. Use the worked synthesis to test a decision rather than relying on a count of assertions, brands or type operators.

The examples use TypeScript 7.0.2 and Node 20.20.2, checked 2026-10-13. Save the named files in a directory without tsconfig.json. The synthesis command uses strict checking, exact optional properties and erasable syntax; the separate optional-mode file intentionally compares two compiler settings.

### 1) **Review the required shape and the literal's checking site**

An extra property on an existing value can be harmless when the consumer needs a smaller shape. Assigning it does not delete the extra property. A fresh object literal written at a typed assignment, call, return or satisfies check can instead report an excess property. That check catches likely mistakes where the object is authored; it does not make every value an exact object.

A spread is not a blanket escape. Inherited fields from the spread and directly written fields are checked differently: a directly written typo can still be rejected. The [object-shape owner](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) runs that contrast in full. Review the specific origin of a suspicious field before recommending a remedy.

If an extra field is intentional, give the consumer a contract that names it and actually uses it. If it is a typo, fix the spelling at the creation site. If a value comes from outside the program, parse it; freshness and satisfies do not inspect unknown runtime data. An assertion can bypass a check but supplies no evidence for the object it claims.

### 2) **Separate absence, explicit undefined and the wire representation**

Ask whether a key may be omitted, what values it may hold when present, and what the receiver observes after serialization. With exactOptionalPropertyTypes enabled, `title?: string` permits omission but rejects an explicit undefined value; `title: string | undefined` requires a key; `title?: string | undefined` permits both. Reading an optional member can still produce undefined. The flag affects the assignment contract, not JSON's behavior.

JSON.stringify omits an object member whose value is undefined. Therefore a required undefined-valued key in memory need not be present on the wire. A required nullable wire member can express an explicit null, provided that the receiving protocol defines it that way. Choose the type from the protocol; neither optional nor null is universally preferable. The [modifier owner](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) gives the fuller mode and runtime matrix.

Save `optional-modes.ts`:

```typescript
export {};
type Optional = { title?: string };
type RequiredUndefined = { title: string | undefined };
type OptionalUndefined = { title?: string | undefined };
const missing: Optional = {};
const explicit: Optional = { title: undefined }; // accepts by default, rejects with exact optional properties
const required: RequiredUndefined = { title: undefined };
const flexible: OptionalUndefined = { title: undefined };
console.log(Object.hasOwn(missing, "title"), Object.hasOwn(required, "title")); // false true
console.log(JSON.stringify(explicit), JSON.stringify(required), JSON.stringify(flexible)); // {} {} {}
// const requiredMissing: RequiredUndefined = {}; // TS2741: key is required
```

Run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir dist optional-modes.ts`, then `node dist/optional-modes.js`. Both succeed with the shown outputs. Check the same source using `--exactOptionalPropertyTypes --noEmit` instead of `--outDir dist`: TS2375 rejects explicit. Adding `| undefined` to its optional value contract permits that deliberate presence. It does not preserve the key in JSON.

### 3) **Choose composition by its resulting contract and error location**

Interface heritage and intersection composition both describe requirements that compatible values must satisfy. Interface names and extends do not by themselves create nominal identity. A compatible utility result such as Omit can be an interface parent; utilities are not categorically restricted to intersections.

A conflicting required member can fail early in an interface declaration or become never in an intersection, with a later construction failure. An optional conflict has a separate presence question: omission may satisfy both sides. The [composition owner](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) demonstrates the exact-optional distinctions. Do not insert `as never` to manufacture an impossible value merely to make a synthesis compile.

Review the result: which fields are required, which overlapping types remain compatible, and where a meaningful error appears. Prefer a named contract when it improves comprehension or is an intended extension point. Use a union/intersection or mapped expression when that is the relationship required. A measured checking problem may motivate another representation; an arbitrary parent/operand quota is not evidence.

### 4) **Connect the brand to a checked construction and a real consumer**

Use a brand when two structurally compatible values must carry different meanings. A factory can check the intended invariant and localize a construction assertion. A readonly phantom marker is not a runtime authentication property, and the compiler does not prove the factory's validation logic. Test malformed inputs and name what the factory actually establishes.

An aggregate brand protects the whole-object contract. A projection can intentionally omit it while a selected field retains its own brand. Whole spread inference can preserve the static marker; a function boundary alone does not remove it. Class-private identity is also compatible with the tested erasable syntax when the class avoids transforming syntax. The [branding owner](<../3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) verifies those contrasts; choose a design from the operation's requirements.

Save `synthesis.ts`. This combines the four review decisions in one small local operation. No network, database or framework is involved.

```typescript
export {};
type Route = { path: string; method: "get" | "post" };
type RouteTable = Record<string, Route>;
interface Timestamped { createdAt: string }
type AuditedRoute = Route & Timestamped;
interface AuditedRouteExt extends AuditedRoute { auditedBy: string }
interface PublicRoute extends Omit<Route, "method"> { title: string }
const publicRoute: PublicRoute = { path: "/", title: "Home" };

type ThemeTokens = {
  colors: { primary: string; background: string };
  spacing: { sm: number; md: number; lg: number };
  radii: readonly ("none" | "sm" | "md")[];
  debugLabel?: string;
};
const THEME = {
  colors: { primary: "#0ea5e9", background: "#ffffff" },
  spacing: { sm: 4, md: 8, lg: 16 },
  radii: ["none", "sm", "md"],
} as const satisfies ThemeTokens;
const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "post" },
} as const satisfies RouteTable;
type Radius = typeof THEME.radii[number];
type RouteKey = keyof typeof ROUTES;
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Keys = Expect<Equal<RouteKey, "home" | "users">>;
type Radii = Expect<Equal<Radius, "none" | "sm" | "md">>;
type HomeMethod = Expect<Equal<typeof ROUTES.home.method, "get">>;
type Conflict = { age: number } & { age: string };
type ConflictMember = Expect<Equal<Conflict["age"], never>>;

type UserCore = { readonly id: string; readonly email: string };
type User = UserCore & { readonly __brand: "User" };
function makeUser(id: string, email: string): User {
  if (!/^u_[A-Za-z0-9]+$/.test(id)) throw new Error("bad user id");
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email)) throw new Error("bad email shape");
  return { id, email } as User;
}
function userFromJson(raw: unknown): User {
  if (typeof raw !== "object" || raw === null || Array.isArray(raw)) throw new Error("bad object");
  if (!("id" in raw) || !("email" in raw)) throw new Error("missing member");
  const id: unknown = raw.id;
  const email: unknown = raw.email;
  if (typeof id !== "string" || typeof email !== "string") throw new Error("bad member");
  return makeUser(id, email);
}
function auditedFor(user: User, route: Route): AuditedRouteExt {
  return { ...route, createdAt: "2026-10-13T00:00:00Z", auditedBy: user.id };
}
const alice = userFromJson({ id: "u_42", email: "alice@example.com" });
const audited = auditedFor(alice, ROUTES.home);
console.log(`${alice.email} (${alice.id})`); // alice@example.com (u_42)
console.log(audited.path, audited.auditedBy, publicRoute.title); // / u_42 Home
console.log(THEME.colors.primary, ROUTES.users.method); // #0ea5e9 post
console.log(Object.hasOwn(alice, "__brand")); // false
let rejected = 0;
for (const raw of [null, {}, { id: "o_1", email: "a@b.co" }, { id: "u_1", email: 1 }]) {
  try { userFromJson(raw); } catch { rejected++; }
}
console.log(rejected); // 4

// Uncomment one negative at a time and recheck with --noEmit.
// const badFresh: Route = { path: "/x", method: "get", extra: true }; // TS2353
// const badOpt: ThemeTokens = { ...THEME, debugLabel: undefined }; // TS2375 in exact mode
// interface BadExt extends AuditedRoute { path: number } // TS2430
// const badConflict: Conflict = { age: 1 }; // TS2322: number cannot satisfy never
// type OrderRef = { id: string } & { readonly __brand: "Order" };
// const wrongDomain: OrderRef = alice; // TS2322: marker mismatch
```

Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist synthesis.ts`, then `node dist/synthesis.js`. The five output lines are shown in the comments. The four live type probes establish the derived keys, radius union, literal method and conflicting member without pretending to execute a runtime type-test function.

The fixed timestamp keeps the exercise reproducible. The checked User has only the declared prefix and small email-shape evidence; it does not prove deliverability or ownership. auditedFor needs no assertion because its returned literal already has the required members. The malformed inputs test that construction checks execute. Freshness, optionality, composition and marker errors are separate negative cases; inspect the actual diagnostic before deciding the remedy.

### 5) **Common confusion**

A type that accepts a value does not remove its extra keys, serialize it or validate its origin. Required undefined-valued members can disappear in JSON even while the object in memory has the key. Likewise, deriving RouteKey needs the actual key set, but not every key derivation requires as const; its benefit here is preserving member values and readonly literal structure.

A brand construction assertion should state the evidence it relies on. Finding one assertion in a factory is not proof that its validator is correct, and finding more than one assertion is not automatically proof of a defect. Trace the invariant and the consumers. Treat text searches as discovery aids, not an enforceable substitute for compiler checks, runtime tests or review.

### 6) **Performance note**

Object types, mapped queries, phantom brands and satisfies checks erase. The synthesized program still constructs objects, validates strings, copies a route and prints results. JSON serialization also executes. No checker-node arithmetic, brand-count budget, hover threshold or timing comparison was measured for this checklist. If checking or validation is expensive in a real application, use a reproducible workload and the measurement owner before choosing a representation.

### 7) **Mentor note**

Uncomment one negative probe, predict the diagnostic and explain why it appears at that location. A good solution repairs the required relationship: remove an unintended extra field, choose deliberate optional semantics, resolve conflicting types, or pass a correctly constructed domain value. Adding an assertion should not be the reflexive fix.

For the optional-mode exercise, ask why exact checking rejects explicit while JSON.stringify loses the key from required. The answer must distinguish the compiler assignment from the serializer. For the branding exercise, remove the id-prefix check and rerun malformed inputs. The compiler can remain green while the rejected count changes; the factory's evidence needs the runtime check. Finally, have learners explain why PublicRoute can extend Omit and why AuditedRouteExt remains structural. The existing owner lessons supply the fuller explanations.
