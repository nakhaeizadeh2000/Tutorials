## 4.1. Objects interfaces checklist — mental models mentors insist on

Four questions every reviewer should answer before approving an object-type change — shape vs name, optionality spelling, lightest composition operator, and where the brand is proved. As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS). This leaf distills [Domain 04](<../../README.md>) into a checkable list — full treatments live in §1–§3; this leaf only synthesizes the decision.

| # | Check (mental model) | If you cannot answer, block the PR |
|---|---|---|
| 1 | **Shape not name governs assignability** — freshness is the exception | Name two freshness triggers and two escapes without looking |
| 2 | **Optionality has three spellings** — `?:`, `\| undefined`, both — `exactOptionalPropertyTypes` changes the matrix | State which of `{ title: undefined }` vs `{}` each spelling allows under `exactOptionalPropertyTypes:true` |
| 3 | **Compose with the lightest operator** — `extends` for nominal chains, `&` for set-like composition | Read the error (`TS2430` vs `never` on property) and justify your operator |
| 4 | **Brand at boundaries, not every leaf** — factories prove the brand once, callers carry it | Point to the single `as Brand` per brand and its validator |

### 1) **Shape not name governs assignability** (freshness is the exception — know its two triggers and two escapes)

**Definition** — TypeScript checks object types *structurally*: `type Point = { x: number; y: number }` accepts any value with at least `x` and `y` both `number` — extra members are allowed (width subtyping), name is ignored. The alias or `interface` name is erased — two separately declared `{ id: string }` shapes are the *same* type. *Freshness* (excess property check) is the narrow lint exception — a fresh literal written directly at a typed site that carries an unknown key is flagged even though it is structurally assignable.

**What problem it solves / history** — JavaScript objects are open bags — `draw({ x: 1, y: 2, color: "red" })` reads only `x`/`y`; a nominal system would reject `color` and force a wrapper class for every ad-hoc shape. TypeScript chose structural subtyping from 0.8 so JS idioms stay idiomatic. Bare structural acceptance then let typos through — `connect({ host: "localhost", portt: 5432 })` where `Options = { host: string; port?: number }` passed width — `portt` was just "extra" and shipped with `port === undefined`. Freshness (TS 1.6 era) was added as a pragmatic exception: flag excess on *literals at the call site* where typos are most likely, leave variable flow untouched.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Default to structural acceptance** — `ColoredPoint ≤ Point` is correct; do not fight width subtyping by writing exact-type wrappers — let `draw(colours)` pass.
- **Two freshness triggers to know** — (1) *fresh literal at an annotated assignment* — `const p: Point = { x: 1, y: 2, z: 3 }`; (2) *fresh literal as a call argument or return value* — `draw({ x: 1, y: 2, z: 3 })` / `return { x: 1, y: 2, z: 3 }` when the target is `Point`. Both report `TS2353: Object literal may only specify known properties`.
- **Two escapes that silence freshness** — (1) *stash through a variable or spread* — `const v = { x: 1, y: 2, z: 3 }; const p: Point = v` / `{ ...v, x: 1 }` — literal is no longer fresh; (2) *assert with `as`* — `const p = { x: 1, y: 2, z: 3 } as Point` — disables the check for that line. Both smuggle the typo past the lint.
- **Correct seal (not escape)** — keep the literal fresh and prove intent with `satisfies`, a wider target, or an annotated binding — see [1.1. Object types structural shape](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) §3 decision table. Never `as` a fresh literal to silence `TS2353` without a `// proof:` comment.

**Runnable example** — triggers vs escapes vs correct seal (`tsc --strict` — error lines commented so the fence compiles):

```typescript
// good — structural assignability: extra through a variable is allowed (width)
type Point = { x: number; y: number };
type ColoredPoint = { x: number; y: number; color: string };
function draw(p: Point): void { console.log(`(${p.x}, ${p.y})`); }
const rich: ColoredPoint = { x: 10, y: 20, color: "red" };
draw(rich); // ok — ColoredPoint has superset of Point → structurally assignable

// freshness triggers — uncomment to see the lint (not a structural failure)
 // const badAssign: Point = { x: 1, y: 2, z: 3 }; // error TS2353 — trigger 1: fresh literal at annotated assignment
 // draw({ x: 1, y: 2, z: 3 }); // error TS2353 — trigger 2: fresh literal as call argument
 // function makePoint(): Point { return { x: 1, y: 2, z: 3 }; } // error TS2353 — trigger 2: fresh literal as return

// escapes that hide the typo — bad (silent via variable and via as)
const leaky = { host: "localhost", portt: 5432 }; // typo — no target yet → no freshness
type Options = { host: string; port?: number };
function connect(o: Options): void { console.log(o.host, o.port); }
connect(leaky as Options); // bad escape 2 — as silences; port stays undefined at runtime
const spread: Options = { ...leaky, host: "localhost" }; // bad escape 1 — spread drops freshness
console.log(spread.port); // undefined — bug shipped
```

```typescript
// good — correct seals that keep the lint and the literals
type Point = { x: number; y: number };
type Route = { path: string; method: "get" | "post" };

// seal 1 — satisfies checks without widening (TS 4.9+, idiomatic 5.9 era)
const routeGood = { path: "/users", method: "get" } satisfies Route; // checks Route, keeps "get" literal
type MethodOfGood = typeof routeGood.method; // "get" — preserved
const m: MethodOfGood = "get"; // ok
 // const typo = { path: "/users", methd: "get" } satisfies Route; // error TS1360 — caught at literal

// seal 2 — wider target when extra is intentional
type LabeledPoint = Point & { label?: string };
function drawLabeled(p: LabeledPoint): void { console.log(p.x, p.y, p.label ?? ""); }
drawLabeled({ x: 1, y: 2, label: "origin" }); // fresh → checked against wider target → ok

// seal 3 — annotate the binding so the typo is caught where written
type Options = { host: string; port?: number };
const optsGood: Options = { host: "localhost", port: 5432 }; // checked at declaration
 // const optsBad: Options = { host: "localhost", portt: 5432 }; // error TS2353 at declaration
connect(optsGood);
function connect(o: Options): void { console.log(o.host, o.port); }
console.log(routeGood.path, m); // /users get
```

**Common confusion** — "Excess property error means not assignable" — no — it *is* assignable; the error is a literal-site lint, not a type rejection — `const v = { x: 1, y: 2, z: 3 }; const p: Point = v` proves it. "Freshness applies through variables/spreads/generics" — it does not — only fresh literals at typed assignment/call/return trigger. "I should `as Target` to silence `TS2353`" — that disables the typo guard for that line forever — prefer `satisfies` / wider target / annotated binding.

**Performance note** — freshness check is `O(k)` over literal member count — negligible checker cost. Structure checks are `O(n × depth)` compile-time only — object types erase with zero emit, zero allocation, zero dispatch. Indirect cost: many stashed intermediates to dodge freshness inflate distinct literal types in the language-server graph — small, visible only in 10k-file traces (`tsc --extendedDiagnostics`).

**Mentor note** — open every object-type review with the three-way demo — `const p: Point = { x: 1, y: 2, z: 3 }` (error) vs `const v = { ... }; const p: Point = v` (silent) vs `const r = { ... } satisfies Point` (error again, literals kept) — ask "which rule explains each?". Gate: every `as Target` on a literal needs a `// proof:` comment or must become `satisfies`.

### 2) **Optionality has three spellings** (`?:`, `| undefined`, both — `exactOptionalPropertyTypes` changes the matrix)

**Definition** — three distinct property modifiers control absence vs presence-with-`undefined`: (1) `prop?: T` — *optional* — key may be missing (`"prop" in obj === false`); (2) `prop: T | undefined` — *required-undefined* — key must be present, value may be `undefined` (`"prop" in obj === true` even when `undefined`); (3) `prop?: T | undefined` — *optional + explicit undefined* — key may be missing **or** present as `undefined`/`T`. Under default `exactOptionalPropertyTypes: false` case 1 silently admits `{ prop: undefined }`; under `exactOptionalPropertyTypes: true` (TS 4.4+, stricter) it does not.

**What problem it solves / history** — before `strictNullChecks` (TS 2.0) every property implicitly included `undefined`, so missing vs `undefined`-valued vs `null` were indistinguishable and `{ search: undefined }` serializing to `{}` while `{ search: null }` serializes to `{"search":null}` shipped as one bug. `?` historically meant "missing **or** `undefined`-valued" — hiding the wire distinction. `exactOptionalPropertyTypes: true` (TS 4.4) was added to make the third question checkable: *may the key be present with `undefined` as a value?* — new codebases enable it to surface missing-vs-`undefined` confusion at assignment instead of at `fetch`.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Ask three questions before choosing a spelling** — can the key be missing? can it be `undefined` when present? can it be `null`? Require the author to answer all three at the API boundary.
- **Use this matrix at review** — enabled by `exactOptionalPropertyTypes: true`; default (`false`) is noted where it differs:

| Spelling | `{}` (missing) | `{ prop: undefined }` | `JSON.stringify` of `{ prop: undefined }` | Narrowing |
|---|---|---|---|---|
| `prop?: T` | allowed | **error when `exact: true`**; allowed by default (`false`) | `{} ` — key stripped | `"prop" in obj` checks presence; `obj.prop !== undefined` checks value |
| `prop: T \| undefined` | error (required) | allowed (present) | `{} ` — still stripped, but `in` is `true` | presence always `true` — check value |
| `prop?: T \| undefined` | allowed | allowed | `{} ` | need both `in` and value checks if protocol distinguishes |
| `prop: T \| null` | error | error (not `null`) | `{"prop":null}` — `null` preserved | `obj.prop !== null` |

- **Model wire types exactly as sent** — if the server expects the key always, use `search: string | null` or `string | undefined` with key present; if the server tolerates missing, use `search?: string`. Convert at the boundary — `function toWire(c: Client): Wire { return { search: c.search ?? null }; }` — never leak `undefined`-valued into `fetch` body without deciding the spelling.
- **Enable `exactOptionalPropertyTypes: true` on new services** once the team can articulate why `{ prop: undefined }` differs from `{}` after `JSON.stringify` / `Object.keys` / `in`. Keep it off on legacy codebases until audit passes — see [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) §1 for the migration note.

**Runnable example** — three spellings, matrix demo, and `exactOptionalPropertyTypes` boundary (`tsc --strict` — `exactOptionalPropertyTypes` error lines commented for default compile; enable `exactOptionalPropertyTypes:true` to see them fire):

```typescript
// good — three spellings and their assignability (tsc --strict, exactOptionalPropertyTypes:false by default)
type OptOnly = { title?: string };                // missing allowed; { title: undefined } allowed by default
type ReqUndef = { title: string | undefined };    // key required, may be undefined
type OptOrUndef = { title?: string | undefined }; // missing allowed, explicit undefined also allowed
type ReqNull = { title: string | null };          // key required, may be null (wire-preserved)

const a: OptOnly = {}; // ok — missing
const b: OptOnly = { title: undefined }; // ok under default exact:false — see next fence for true
const c: ReqUndef = { title: undefined }; // ok — present-with-undefined required
 // const d: ReqUndef = {}; // error TS2741 — property title is missing (required)
const e: OptOrUndef = {}; // ok
const f: OptOrUndef = { title: undefined }; // ok
const g: ReqNull = { title: null }; // ok — null preserved by JSON.stringify

// exactOptionalPropertyTypes:true difference — same OptOnly now rejects explicit undefined:
 // type ExactStrict = { title?: string }; // with exactOptionalPropertyTypes:true, { title: undefined } would error here
type ExactExplicit = { title?: string | undefined }; // explicit form stays allowed
const h: ExactExplicit = { title: undefined }; // ok even with exact:true

// wire observable — why the spelling matters after serialization
console.log(JSON.stringify({ note: undefined } as unknown as { note?: string })); // {} — stripped
console.log(JSON.stringify({ note: null })); // {"note":null} — preserved
console.log(JSON.stringify({})); // {} — same as undefined-valued, different from null
console.log(a, b, c, e, f, g, h); // values exist — serialization stripped undefined keys
```

```typescript
// bad — requiring undefined at call sites vs optional, and vice versa (fix by choosing the consumer spelling)
type ReqUndef = { title: string | undefined };
type OptOnly2 = { title?: string };

// bad — optional passed where required-undefined expected
 // function requiresUndef(x: ReqUndef): void { console.log(x.title?.toUpperCase()); }
 // const opt: OptOnly2 = {}; // requiresUndef(opt); // error TS2345 — {} missing required title (even though title may be undefined, key must be present)

// good — model the boundary and convert: ensure key when required
function requiresUndefGood(x: ReqUndef): void { console.log(x.title?.toUpperCase()); }
const opt2: OptOnly2 = { title: "hi" };
requiresUndefGood({ title: opt2.title }); // explicit key — ok (value may be undefined)
requiresUndefGood({ title: undefined }); // ok

// bad — narrowing confusion: "in" vs "!== undefined" interchangeability
type Local = { note?: string | undefined };
const v: Local = { note: undefined };
if ("note" in v) {
  // v.note is still string | undefined — "in" alone doesn't make it required after the branch on some TS versions
  console.log(v.note?.toUpperCase()); // must still guard the value
}
console.log(requiresUndefGood);
```

**Common confusion** — "`prop?: T` is sugar for `prop: T | undefined`" — false under `exactOptionalPropertyTypes: true` and observably false after `JSON.stringify`/`Object.keys`/`in`. "`in` and `!== undefined` are interchangeable" — `in` tests presence, `!== undefined` tests value — with `prop?: T | undefined` you need both if the protocol distinguishes missing from `undefined`-valued. "Optional is always the right default for nullable APIs" — if the wire expects `{"note":null}`, use `| null` with required key, not `?`.

**Performance note** — optionality is compile-time only — all three spellings erase to the same emit (`{}` or `{ prop: value }`) — zero allocation/runtime dispatch. Checker cost is one assignability check per optional property (`O(members)` per literal) — trivial; `exactOptionalPropertyTypes` adds one extra present-with-`undefined` check per site — still `O(1)`. The real cost is the re-serialize bug: inconsistent `?` vs `| undefined` across client/server causes a `400` or silent key strip — measure not cycles but `fetch` `4xx` rate after enabling the flag.

**Mentor note** — run the `JSON.stringify` triple — `JSON.stringify({})` vs `JSON.stringify({ note: undefined })` vs `JSON.stringify({ note: null })` — ask which two produce `{}` (first two) — then ask which spelling each case demands. Require every external-data type (`fetch` JSON, `localStorage`, query params) to state its `?` vs `| null` vs `| undefined` choice in a comment or boundary helper. Gate: flip `exactOptionalPropertyTypes:true` in CI for new services and demand `prop?: T | undefined` wherever `undefined`-valued is intentional.

### 3) **Compose with the lightest operator** (`extends` for nominal chains, `&` for set-like composition — read the error message to decide)

**Definition** — two operators build larger object shapes: `interface B extends A { extra: string }` — *heritage* — `B` must refine `A` (each overlapping key must be a subtype); and `type B = A & { extra: string }` — *intersection* — a value must satisfy *both* sides (overlapping keys become `T & U`). Both erase (safe under `--erasableSyntaxOnly`) and overlap ~90%, but they diverge on conflicts: `extends` errors `TS2430` at the declaration ("does not correctly extend"), `&` keeps the declaration and puts `never` on the conflicting property — the error moves to the *assignment*.

**What problem it solves / history** — sharing members across object types is daily — `Route` + `Audited`, `Point` + `LabeledPoint`. `extends` (TS 0.8) modeled hierarchies — a subtype narrows the parent's contract, so `age: number → age: string` is rejected as non-refining. `&` (added later) modeled conjunction — a value must satisfy both, so `number & string → never` (no value is both). Branded intersections (`string & { __brand }`) and primitive/union composition *require* `&` — `extends` cannot intersect with primitives — while long nominal chains read better as `extends`. Teams that defaulted to one operator hit either unreadable hops (`extends` chains that required hover invalidation) or late `never` errors (`&` conflicts only at assignment).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Readable nominal chain (2–4 named parents, no conflicts) → `extends`** — `interface Audited extends Route, Timestamped {}` — declaration-time error `TS2430` catches conflicts early, hierarchy is navigable.
- **Set-like combination, primitive/union side, or computed helper (`Omit`/`Pick`/`Record`) → `&`** — `type User = UserCore & { __brand: "User" }`, `type RouteAudited = Route & Audited`, `type MixedExact = { nickname?: string } & { nickname: string | undefined }` — only `&` can intersect with primitives and `| undefined` edges.
- **When the hover truncates or every consumer needs alias-go-to-definition → prefer named `extends`**, when the literal is local and errors at assignment are informative → `&` is fine — hover cost is `O(extends depth)` vs `O(& operands)` but both trivial until 10+ operands.
- **Conflict rule** — `interface Bad extends A { age: string }` where `A` has `age: number` → error at declaration `TS2430`; `type Bad = A & { age: string }` → `Bad["age"]` is `number & string = never` — inhabitable only by missing (`age?`). Read the error locus to decide: *early at the declaration* → `extends` told you; *late at a value* → `&` built an impossible property.

**Runnable example** — happy path, conflicting regimes, and readability split (`tsc --strict` — conflicting errors commented so fence compiles; uncomment one error line at a time to see the locus):

```typescript
// good — extends for readable nominal chain (conflicts error at declaration)
interface Route { path: string; method: "get" | "post"; }
interface Timestamped { createdAt: string; }
interface RouteAuditedExt extends Route { createdAt: string; }
const okExt: RouteAuditedExt = { path: "/a", method: "get", createdAt: "2026-09-02" }; // ok

interface A { age: number; }
 // interface BadExt extends A { age: string; } // error TS2430: Interface 'BadExt' incorrectly extends interface 'A' — Types of property 'age' are incompatible
console.log(okExt.path); // /a

// good — & for set-like / primitive / utility composition
type Audited = { createdAt: string; };
type RouteAuditedAnd = Route & Audited;
const okAnd: RouteAuditedAnd = { path: "/a", method: "post", createdAt: "2026-09-02" }; // ok
type RouteTable = Record<string, Route>;
type AuditedTable = RouteTable & { _audited: true }; // & with utility — only & can do this directly
console.log(okAnd.method); // post
```

```typescript
// good vs bad — conflicting property: never on the leaf vs widened to never silently
type A2 = { age: number };
 // interface BadExt2 extends A2 { age: string; } // error TS2430 at declaration — preferred for early signal
type BadAnd2 = A2 & { age: string }; // no declaration error — age becomes number & string = never
 // const badVal2: BadAnd2 = { age: 30 as unknown as number & string }; // age: never — every concrete assignment errors at the value site
type BadAnd2Age = BadAnd2["age"]; // never — tells you the intersection is impossible for this key
const _checkNever: BadAnd2Age = undefined as unknown as never; // never has no inhabitant except never itself
console.log(_checkNever); // never inhabitable — demonstrates empty set

// optionality edge under exactOptionalPropertyTypes semantics (& can model the exact split, extends cannot)
type OptExact = { nickname?: string }; // missing allowed; present-with-undefined depends on exact flag
type ReqUndefOpt = { nickname: string | undefined }; // required-with-undefined
type MixedExact = OptExact & ReqUndefOpt; // required-with-undefined when both sides considered — & models presence vs missing precisely
const mixedOk: MixedExact = { nickname: "ada" }; // ok
const mixedUndef: MixedExact = { nickname: undefined }; // ok by default exact:false; errors under exactOptionalPropertyTypes:true (see 1.2)
console.log(mixedOk.nickname, mixedUndef.nickname); // ada undefined

// primitive/ union side — only & can express branding (extends cannot intersect with string)
type BrandedId = string & { readonly __brand: "UserId" };
function makeId(s: string): BrandedId { return s as BrandedId; }
const bid = makeId("u_1");
console.log(bid); // u_1 — string at runtime, branded at check time

// bad — using extends where & is required (conceptual): interface X extends string — not valid syntax
 // interface X extends string {} // error — extends on interfaces cannot intersect with primitives
```

**Common confusion** — "`A & B` with conflicting `age` widens to `string | number`" — opposite — `&` requires both (`number & string → never`, empty set); `|` would widen. "Optional vs `| undefined` are the same so the operator shouldn't matter" — under `exactOptionalPropertyTypes` they differ and the two operators surface it differently (see `MixedExact` demo). "`never` on the property means still usable" — `never` on a *required* conflicting key makes the whole intersection almost uninhabitable for objects that include that key; absence only sneaks past when optional. "Always use `&` — `extends` is legacy" — `extends` gives early `TS2430` at the declaration, which is preferable for public contracts; reserve `&` for local combination and primitive/unit helpers.

**Performance note** — both operators erase — zero emit/allocation/GC/dispatch. Checker cost is one assignability walk per composition site — `O(members × operands)` compile-time only — trivial for 2–5 operands. Very long chains (10+ `extends` parents or `&` operands on a single type that is spread across hundreds of files) inflate instantiation count — visible in `tsc --extendedDiagnostics` `instantiations` — split into named intermediates (`type UserCore = ...; type User = UserCore & Brand`) when diagnostics show type-check time spiking; naming also avoids hover truncation.

**Mentor note** — ask the student to trigger both conflict errors — write the same `age: string` vs `age: number` pair once with `extends` (error at declaration) and once with `&` (error at assignment via `never`) — then ask "where do you want the reviewer to see the error?" — public contract → `extends` (fail fast); local combination → `&`. Exercise: given `interface A { age: number }` and `type B = A & { age: string }`, ask for `B["age"]` — correct answer `never`. Gate: every public augmentable contract uses `interface` + `extends`; every branded/utility/union helper uses `type` + `&`.

### 4) **Brand at boundaries, not every leaf** (factories prove brand once; callers carry it without re-asserting)

**Definition** — a *brand* adds a type-only phantom property via intersection — `type User = { id: string } & { readonly __brand: "User" }` or `declare const UserBrand: unique symbol; type UserS = { id: string } & { readonly [UserBrand]: "User" }` — that makes two structurally identical `{ id: string }` domains incompatible while remaining identical at runtime. A *factory* — `function makeUser(id, email): User` — is the single trusted site that does `as User` after validation; every other module receives `User`, never forges it. The `unique symbol` key variant guarantees no two brands accidentally share the same string literal and auto-omits from `JSON.stringify`.

**What problem it solves / history** — backends mix `User.id`, `Order.id`, `Session.id` that are all `string` or `{ id: string }` underneath — `ship(order: Order)` happily accepted a `User` because alias names erase and freshness doesn't fire on shared `{ id }` width. Primitive brands (`string & { __brand }`) existed early (TS 2.x), but object wrappers carry audit fields (`createdAt`, `kind`) and need object-level nominal recovery. `class private __brand` gave nominality but broke `JSON.parse` round-trips and emitted non-erasably; the intersection phantom pattern won because it erases and strips. Early teams then branded *every* leaf (`UserId`, `UserEmail`, `OverUser`) and fractured composition — `Pick`/`Omit` stripped the brand, `&` on two `__brand` literals conflicted, and tests laundered via `as` to avoid fixtures — the correction (TS 4.9–5.9, `erasableSyntaxOnly` era) was to treat branding like validation: one aggregate brand at module boundaries, unbranded `Core` inside.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Brand ~5–15 aggregates, not every leaf** — typical set: `User`, `Order`, `Session`, `Money`, `Percent`, `TenantId`/`OrgId` — roughly one per "if swapped, on-call pages". The aggregate brands (`User = UserCore & { __brand }`); its `email` field stays plain `string` unless email-swap itself pages.
- **Validate at the factory, brand once per boundary crossing** — `POST /users`, `JSON.parse`, `db.rowToUser`, `queue.consumeOrder` each call `makeUser`/`makeOrder` — inner helpers `formatUser(user: User): string`, `total(order: Order): number` just *receive* `User`/`Order`.
- **Keep unbranded cores for projection** — `type UserCore = { id: string; email: string }; type User = UserCore & { readonly __brand: "User" }; type PublicUser = Pick<UserCore, "id">` — `Pick`/`Omit`/`Partial` on `UserCore` never touches the phantom.
- **Hide every `as Brand` behind the factory** — `as User` count should equal factory count (1 per brand); audit via `grep -R "as User"`. Keep the brand `readonly` and never store it at runtime (`user.__brand = ...` leaks to persistence).
- **Pick the brand key by collision risk** — `__brand: "User"` for app code with 5–15 brands; `declare const UserBrand: unique symbol; [UserBrand]` for cross-team boundaries or when ambient augmentation might touch `__brand` — both are type-only (zero runtime allocation) when `declare const`; `const B = Symbol()` *does* allocate a heap symbol.

**Runnable example** — bounded branding good vs over-branding fracture and projection (`tsc --strict` — error lines commented):

```typescript
// good — brand the aggregate at the boundary, compose on unbranded core
type UserCore = { id: string; email: string };
type User = UserCore & { readonly __brand: "User" };
type OrderCore = { id: string; totalCents: number };
type Order = OrderCore & { readonly __brand: "Order" };

function makeUser(id: string, email: string): User {
  if (!id.startsWith("u_")) throw new Error(`bad user id: ${id}`);
  if (!email.includes("@")) throw new Error(`bad email: ${email}`);
  return { id, email } as User; // single trusted assertion per brand
}
function makeOrder(id: string, totalCents: number): Order {
  if (!id.startsWith("o_")) throw new Error(`bad order id: ${id}`);
  return { id, totalCents } as Order;
}

function notify(user: User): void { console.log(`notify ${user.email}`); }
function ship(order: Order): void { console.log(`ship ${order.id} ${order.totalCents}c`); }
const alice = makeUser("u_42", "alice@example.com");
const order99 = makeOrder("o_99", 4999);
notify(alice); // ok
ship(order99); // ok
 // ship(alice); // error TS2322: Type 'User' is not assignable to type 'Order' — __brand mismatches

// inside module — receive User, don't re-brand
function formatUser(u: User): string { return `${u.email} (${u.id})`; }
console.log(formatUser(alice)); // alice@example.com (u_42)

// projection via UNBRANDED core — no brand friction
type PublicUser = Pick<UserCore, "id">;
function toPublic(u: User): PublicUser { return { id: u.id }; }
console.log(toPublic(alice).id); // u_42
console.log(JSON.stringify(alice)); // {"id":"u_42","email":"alice@example.com"} — no brand key leaks (erases)
```

```typescript
// bad — over-branding every leaf fractures composition (self-contained for isolated check)
type UserCore = { id: string; email: string };
type User = UserCore & { readonly __brand: "User" };
function makeUser(id: string, email: string): User {
  if (!id.startsWith("u_")) throw new Error("bad id");
  return { id, email } as User;
}

type BrandedId = string & { readonly __brand: "BrandedId" };
type BrandedEmail = string & { readonly __brand: "BrandedEmail" };
type OverUser = { id: BrandedId; email: BrandedEmail } & { readonly __brand: "OverUser" };
function makeBrandedId(s: string): BrandedId { if (!s.startsWith("u_")) throw new Error("bad"); return s as BrandedId; }
function makeBrandedEmail(s: string): BrandedEmail { if (!s.includes("@")) throw new Error("bad"); return s as BrandedEmail; }
function makeOverUser(id: string, email: string): OverUser {
  return { id: makeBrandedId(id), email: makeBrandedEmail(email) } as OverUser;
}
const over = makeOverUser("u_1", "a@b.co");

// fracture — clone/build of OverUser needs extra as (laundering pressure)
function cloneOver(u: OverUser): OverUser {
  return { id: u.id, email: u.email } as OverUser; // extra as — audit count grows
}
console.log(cloneOver(over).id); // u_1

// fracture — JSON.parse must go through factory, not as User on raw
 // const raw = JSON.parse('{"id":"u_1","email":"not-an-email"}') as User; // bad — no validation
function userFromJson(raw: unknown): User {
  if (typeof raw !== "object" || raw === null) throw new Error("bad json");
  const r = raw as { id: unknown; email: unknown };
  if (typeof r.id !== "string" || typeof r.email !== "string") throw new Error("bad shape");
  return makeUser(r.id, r.email); // validated then branded — single assertion site reused
}
console.log(userFromJson({ id: "u_99", email: "ok@example.com" }).id); // u_99

// unique symbol brand variant — never collides, auto-omitted by JSON (type-only — no runtime Symbol needed)
declare const UserBrand: unique symbol;
type UserS = { id: string; email: string } & { readonly [UserBrand]: "User" };
function makeUserS(id: string, email: string): UserS {
  if (!id.startsWith("u_")) throw new Error("bad id");
  return { id, email } as UserS;
}
const aliceS = makeUserS("u_7", "a@b.co");
console.log(JSON.stringify(aliceS)); // {"id":"u_7","email":"a@b.co"} — symbol brand never stringifies
```

**Common confusion** — "The brand must be a runtime property" — it never is — `JSON.stringify(user)` omits it; `Object.keys(user)` doesn't see it — checker-only. "Factory is boilerplate — `as User` at call site is fine" — each `as` is a proof site that bypasses validation — centralize to one. "`unique symbol` always allocates a runtime `Symbol`" — `declare const Brand: unique symbol` is type-only, zero allocation; `const Brand = Symbol()` allocates per module. "Branding prevents `any`/`as` laundering" — it is discipline, not a vault — `any` / `as unknown as User` still break it.

**Performance note** — every brand erases — zero emit/allocation/GC/dispatch — checker adds one phantom property check (`__brand`) per assignment — `O(1)` per branded edge. `declare const B: unique symbol; & { readonly [B]: "User" }` also emits nothing. Only `const B = Symbol()` allocates (~32–64 bytes, interned). Over-branding (~40 leaf brands) inflates type-graph cost `O(brands)` per call site — visible in `tsc --extendedDiagnostics` `instantiations` (example: 8 brands ~2k, 40 brands ~8k, +10–15 ms) and in truncated hover on `Pick`/`Omit` — budget brands like allocations.

**Mentor note** — draw the airlock diagram — ingress (`JSON`/`DB`/`queue`) → `makeUser` → *unboxed interior* (`format`, `total`, `toPublic`) → egress — "the factory is the airlock — dirt stays outside". In review ask: "if we swapped this object's brand, would prod notice within one hour?" — *yes* → brand at airlock; *no* → leave it `UserCore`. Exercise: hand a PR that adds `type Comment = { id: string } & { __brand: "Comment" }` with three leaf brands inside and ask to (a) count `as` sites, (b) rewrite to one aggregate brand on `CommentCore`, (c) write the `commentFromJson` boundary. Gate: every brand PR adds a factory + a boundary call site + a test-fixture helper in the same commit, or block as "brand without airlock".

### 5) **Runnable synthesis** (one config that exercises all four checks)

The single file below is the review gate: if all four mental models are internalized, it compiles; if any is violated, `tsc --strict` errors at the violation site.

```typescript
// synthesis: shape + optionality + composition + branding — tsc --strict should exit 0
// compile: npx tsc synthesis.ts --strict

// 1 — shape not name: Config is by shape; freshness catches typos at the literal
type Route = { path: string; method: "get" | "post" };
type RouteTable = Record<string, Route>;

// 3 — compose with the lightest operator:
//   extends for nominal chain, & for set-like + branded + utility combination
interface Timestamped { createdAt: string; }
type AuditedRoute = Route & Timestamped; // & — set-like combination
interface AuditedRouteExt extends AuditedRoute { auditedBy: string; } // extends — nominal chain on the result

// 2 — optionality has three spellings — model missing vs present-with-undefined vs required:
type ThemeTokens = {
  colors: { primary: string; background: string };
  spacing: { sm: number; md: number; lg: number };
  radii: readonly ("none" | "sm" | "md")[];
  // optional key that may be missing; with exactOptionalPropertyTypes:true, explicit undefined needs `?: string | undefined`
  debugLabel?: string;
};

// 4 — brand at the boundary, not every leaf — one factory per aggregate, carry inward
type UserCore = { id: string; email: string };
type User = UserCore & { readonly __brand: "User" };
function makeUser(id: string, email: string): User {
  if (!id.startsWith("u_")) throw new Error(`bad user id: ${id}`);
  if (!email.includes("@")) throw new Error(`bad email: ${email}`);
  return { id, email } as User; // single trusted assertion site
}
function formatUser(u: User): string { return `${u.email} (${u.id})`; } // receives User — no re-brand

// Seal the config literal with as const satisfies — validates shape, preserves literals, deep readonly:
const THEME = {
  colors: { primary: "#0ea5e9", background: "#ffffff" },
  spacing: { sm: 4, md: 8, lg: 16 },
  radii: ["none", "sm", "md"] as const,
} as const satisfies ThemeTokens;

const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "post" },
} as const satisfies RouteTable;

// Derived types from as const literals — only possible because we kept literals:
type PrimaryColor = typeof THEME.colors.primary; // "#0ea5e9"
type Radius = typeof THEME.radii[number]; // "none" | "sm" | "md"
type RouteKey = keyof typeof ROUTES; // "home" | "users"

// Boundary: JSON → validated User (brand once)
function userFromJson(raw: unknown): User {
  if (typeof raw !== "object" || raw === null) throw new Error("bad json");
  const r = raw as { id: unknown; email: unknown };
  if (typeof r.id !== "string" || typeof r.email !== "string") throw new Error("bad shape");

}

// Composition consumes the branded + optional + satisfies pieces together:
function auditedFor(user: User, route: Route): AuditedRouteExt {
  return { ...route, createdAt: new Date().toISOString(), auditedBy: user.id } as AuditedRouteExt;
}

// Verify each check at the call site:

console.log(audited.path, audited.auditedBy); // / u_42
console.log(THEME.colors.primary satisfies PrimaryColor); // #0ea5e9 — primary kept literal
const _radiusOk: Radius = "sm"; // ok — literal union from as const
console.log(_radiusOk); // sm
```
