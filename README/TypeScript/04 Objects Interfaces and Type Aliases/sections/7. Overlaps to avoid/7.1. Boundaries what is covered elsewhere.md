## 7.1. Boundaries — what is covered elsewhere

> As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS, 22 Maintenance LTS) — this domain owns the *static object-type model* (structural shape, optional/`readonly`, index signatures, `interface` vs `type`, `&`/`extends`, declaration merging, `keyof`/`T[K]`/`typeof` capture). Everything that needs runtime execution, call signatures, or type-level computation is owned elsewhere — one line + link, not a re-explanation (DRY — [PROMPT.md:5](<../../../../PROMPT.md>)).

### 1) **JavaScript runtime mechanics** (descriptors, prototype, enumeration) — [JavaScript 06 Objects in Depth](<../../../../JavaScript/06 Objects in Depth/README.md>)

**Definition** — runtime object mechanics are how the engine stores properties at execution: descriptor attributes (`value`/`writable`/`enumerable`/`configurable`, `get`/`set`), `[[Prototype]]` linkage, and enumeration order (`for-in` vs `Object.keys` vs `Reflect.ownKeys`). This domain describes the *static shape* `{ id: string; readonly name?: string }`; JavaScript 06 describes what `defineProperty`, `freeze`, and prototype walks *do* at runtime.

**Why this domain stops here** — TypeScript erases object-type syntax entirely (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)). `readonly` blocks a *checker* write but emits no `freeze`; index signatures do not install an enumerability filter. Re-teaching `getOwnPropertyDescriptor`, `setPrototypeOf` deoptimization, or `for-in` chain walk here would duplicate JS 06 and invite the false mental model that a type annotation changes emit.

**Modern guidance** — model shape with `type`/`interface` and `readonly`/`?` here; enforce runtime guarantees with `Object.freeze`/`seal`/`defineProperty` there. Review JS 06 when a bug report mentions silent sloppy-mode mutation, prototype pollution via `__proto__`, or shallow-copy surprise — those are runtime, not type, fixes.

**Runnable example** — `readonly` is checker-only; `freeze` is runtime — good vs bad ( `tsc --strict` — error lines commented):

```typescript
// good — static guarantee (this domain) — checker blocks, no emit
type User = { readonly id: string; name: string };
const u: User = { id: "a1", name: "Ada" };
// u.id = "b2"; // error TS2540 — checker only
console.log(u.id); // a1

// good — runtime guarantee (JS 06) — engine blocks, no type needed
const raw = { id: "a1" };
Object.freeze(raw);
console.log(Object.isFrozen(raw)); // true
// (raw as { id: string }).id = "b2"; // sloppy: silent no-op; strict: TypeError — see JS 06 5.1

// bad — assuming readonly implies frozen (mixing domains)
type Config = { readonly host: string; nested: { port: number } };
const cfg: Config = { host: "localhost", nested: { port: 5432 } };
// cfg.host = "other"; // blocked — checker
cfg.nested.port = 9999; // allowed — readonly is shallow, nested still mutable
console.log(cfg.nested.port); // 9999 — runtime not frozen
```

**Common confusion** — "`readonly` freezes the object" — no — `readonly` erases, `Object.freeze` (shallow) is the runtime complement — see [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>). "`enumerable: false` is the same as an index signature" — no — enumerability gates `for-in`/`keys`/spread, index signatures widen the *static* dictionary type.

**Performance note** — object-type checking is `O(members × depth)` and erases — zero runtime cost. Runtime descriptor installation (`defineProperty` with `enumerable: false`) and `freeze` add hidden-class and extensibility checks that survive to execution — measure with `Object.getOwnPropertyDescriptor` and `isFrozen` guards, not type-level hunches.

**Mentor note** — in review, flag `readonly` without `freeze` when the PR promises runtime immutability ("API contract: must not mutate") — require an `Object.freeze` call or an explicit "checker-only" comment. Demo `getOwnPropertyDescriptor` on a `readonly` property to prove no descriptor change.

**Cross-links** — runtime descriptors, order, `for-in`, utilities, freeze/seal → [JavaScript 06 Objects in Depth](<../../../../JavaScript/06 Objects in Depth/README.md>) (especially [2.1 Data vs accessor descriptors](<../../../../JavaScript/06 Objects in Depth/sections/2. Properties and descriptors/2.1. Data vs accessor descriptors and attribute defaults.md>), [2.3 Enumerability](<../../../../JavaScript/06 Objects in Depth/sections/2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>), [5.1 Prevent extensions seal freeze](<../../../../JavaScript/06 Objects in Depth/sections/5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>)); static shape/freshness this domain owns → [1.1. Object types structural shape](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>); `readonly` without `freeze` → [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>); erasure → [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. ### 2) **Unions, intersections, and narrowing** (type-level composition, `in`/`is` guards, discriminant unions) — [07 Unions, Intersections and Narrowing](<../07 Unions Intersections and Narrowing/README.md>) (textual forward until that domain lands; live for JS-side `in` mechanics in [JavaScript 06 Objects in Depth](<../../../../JavaScript/06 Objects in Depth/README.md>))

**Definition** — unions (`A | B`), intersections at union scale (`A & B` over unions), and control-flow narrowing (`in`, `typeof`, discriminant `===`, user predicates `x is T`, exhaustive `never` switches) are the *logic* that refines a broad object union to one branch. This domain touches `&`/`extends` only as *object-shape* composition (see [2.1. Intersection vs extends](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>)) and `in`/`typeof` only as the *object-pairing* preview (see [3.3. satisfies assertions and narrowing on object shapes](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>)).

**Why this domain stops here** — full `in`/`is` guard theory, discriminant-union modeling (`kind`/`type`/`status` with literal values), closed vs open unions, and distributivity of `&` over `|` belong to 07. Re-teaching them here would duplicate 07's formalism and pull object-shape leaves into logic-leaves.

**Modern guidance** — define object branches here (`type Circle = { kind: "circle"; radius: number }`); narrow them there (`if (s.kind === "circle")` or `if ("radius" in s)` with `switch`+`never` default). Keep `satisfies`/`as const` on the literal (see [3.3. satisfies assertions](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>)) so the discriminant stays literal for 07's equality check.

**Runnable example** — shape defined here, narrowing owned by 07 — good vs bad (`tsc --strict`):

```typescript
// good — shapes defined in this domain; narrowing delegated to 07
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;

function areaGood(s: Shape): number {
  if (s.kind === "circle") return Math.PI * s.radius ** 2; // discriminant — owned by 07
  return s.side ** 2; // else is Square — narrowed
}

// bad — branch-specific access without narrowing (compile error, not runtime)
function areaBad(s: Shape): number {
  // return Math.PI * s.radius ** 2; // error TS2339: 'radius' not on Square — narrow first
  if ("radius" in s) return Math.PI * s.radius ** 2; // fallback "in" guard — also owned by 07
  return s.side ** 2;
}

console.log(areaGood({ kind: "circle", radius: 2 }).toFixed(1)); // 12.6
console.log(areaBad({ kind: "square", side: 3 })); // 9

// good — keep discriminant literal with satisfies so 07 check stays precise
const c = { kind: "circle", radius: 2 } satisfies Shape; // kind is "circle", not string
type KindOfC = typeof c.kind; // "circle" — literal preserved for 07 narrowing
console.log(c.kind); // circle — value, while KindOfC is the preserved literal type
```

**Common confusion** — "`A & B` is the same as `extends` for narrowing" — `extends` composes object shapes; `&` over unions distributes (`(A|B) & C` → `(A&C)|(B&C)`) — narrowing a distributed union is 07 logic. "`in` narrows exactly like discriminant `===`" — `in` keeps members that *could* have the key (imprecise on optional `?` members); discriminant `kind === "..."` is exact — prefer `kind` for modelled unions.

**Performance note** — object-shape composition (`&`/`extends`) costs one checker walk over members; union narrowing costs one control-flow fork per branch (`O(branches)`). Wide unions (>30 members) with repeated `in` probes inflate `check time` linearly — narrow once to a discriminant and `switch` (07 pattern) rather than probing `"a" in x || "b" in x` at every use site; measure `tsc --extendedDiagnostics`.

**Mentor note** — flag any PR that re-implements discriminant narrowing with manual `"prop" in obj` chains when a `kind` literal already exists — redirect to 07's `switch`+`never` exhaustive form. Exercise: add a new `Triangle` variant to `Shape` and watch the `default: never` site error if `switch` missed it — the breakage teaches why modelling beats ad-hoc probing.

**Cross-links** — object composition here → [2.1. Intersection vs extends](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>); literal/narrowness pairing → [3.3. satisfies assertions and narrowing](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>); structural freshness feeding discriminants → [1.1. Object types structural shape](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>); full unions/narrowing/predicates → [07 Unions, Intersections and Narrowing](<../07 Unions Intersections and Narrowing/README.md>) textual; runtime `in`/`hasOwn` mechanics → [JavaScript 06 Objects in Depth](<../../../../JavaScript/06 Objects in Depth/README.md>).

### 3) **Functions and classes** (callable signatures, methods, accessors) — [05 Functions and Callable Types](<../05 Functions and Callable Types/README.md>) + [06 Classes and Object-Oriented Types](<../06 Classes and Object-Oriented Types/README.md>) (textual forwards)

**Definition** — callable signatures (`{ (x: string): number }`, `(x: string) => number`), method shorthand (`{ m(): void }` vs `{ m: () => void }`), getters/setters, and class field/accessor typing (`public`/`private`/`#`, `abstract`, `implements`) are the *behavioral* side of objects. This domain covers *data* shapes (`{ id: string; readonly name?: string }`) and treats callables as leaf boundaries.

**Why this domain stops here** — `this` parameter, overloads, generic call signatures, `this` as receiver, private field erasure, and `super` dispatch are owned by 05/06. Teaching `call`/`bind` receiver rules or accessor variance inside object-shape leaves would duplicate 05/06 and conflate "object has a method" with "function is a subtype".

**Modern guidance** — type data objects here; type callable members with the lightest form that survives review. Prefer property-arrow `onClick: (e: Event) => void` for callback-like members (preserves `this` via arrow) and method shorthand `save(): void` for object-identity methods — full trade-off and `strictFunctionTypes` on methods vs properties lives in 05; class-backed brands vs structural brands in 06.

**Runnable example** — data shape here, callable/class there — good vs bad (`tsc --strict`):

```typescript
// good — data shape (this domain)
type UserData = { id: string; name: string };
const data: UserData = { id: "u_1", name: "Ada" };
console.log(data.id); // u_1

// good — callable signature owned by 05 (method vs property arrow — see 05)
type Service = {
  get(id: string): UserData;           // method shorthand — owned by 05
  onUpdate: (u: UserData) => void;     // property arrow — owned by 05
};
const svc: Service = {
  get(id) { return { id, name: "Ada" }; },
  onUpdate(u) { console.log(u.name); },
};
svc.onUpdate(svc.get("u_1")); // Ada

// bad — modelling a class with private state as a plain object shape (loses encapsulation)
type BadUser = { id: string; _secret: string }; // exposes interior — use class with #secret in 06
// fix — keep data interface here, behavior in 06 (brand via private field vs & { __brand })
```

**Common confusion** — "`method` and `arrow property` are identical for objects" — `m(): void` is bivariant in `strictFunctionTypes` for methods (JS `this` compatibility), `m: () => void` is checked strictly — see 05. "`implements` makes a class structurally fit" — `implements` only checks; structural fit is still shape-based (see [1.1. Object types](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>)).

**Performance note** — method vs arrow choice affects runtime allocation (arrow per-instance, method on prototype) but both erase at type level. Prefer method on prototype for hot objects; arrow for callbacks that must capture `this` without `bind` — measure instance count, not type-check time.

**Mentor note** — in object review, flag any `interface` that mixes 5+ method members with 1 data field — split into data `type` (this domain) + service `interface` (05) — SOLID single-responsibility. Redirect `get set` accessor questions to 06.

**Cross-links** — data shape/freshness → [1.1. Object types](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>); `interface` vs `type` for callable members → [1.3. Interfaces vs type aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>); composition helpers → [2.1. Intersection vs extends](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>); callable/method/overload/`this` → [05 Functions and Callable Types](<../05 Functions and Callable Types/README.md>) textual; class fields/accessors/brands → [06 Classes and Object-Oriented Types](<../06 Classes and Object-Oriented Types/README.md>) textual.

### 4) **Generics / utility-type transformations** (mapped, conditional, `infer`, template literals building object shapes) — [08 Generics Deep Dive](<../08 Generics Deep Dive/README.md>) + [09 Utility Types and Type Transformations](<../09 Utility Types and Type Transformations/README.md>) (textual forwards)

**Definition** — type-level computation on object shapes: mapped types (`{ [K in keyof T]: V }`), conditional types (`T extends U ? X : Y`), `infer` extraction, `keyof`/`typeof` synthesis at generic scale, and template literal types (`` `on${Capitalize<K>}` ``) that *build* new object keys. This domain owns only the *primitive* operators `keyof T` / `T[K]` / `typeof` capture for derivation (see [2.3. Type queries on objects](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>)); 08/09 own the combinators.

**Why this domain stops here** — `Partial`/`Pick`/`Omit`/`Record`, `Exclude`/`Extract`/`ReturnType`, recursive `DeepPartial`, and `--isolatedDeclarations` parallel emit are 08/09's catalog. Teaching them here would duplicate 09 and pull recursion/variance theory (08) into shape leaves.

**Modern guidance** — derive unions/keys with `keyof`/`T[K]`/`typeof` here; transform shapes there. Prefer standard utilities (`Record`, `Pick`, `Omit`) over hand-rolled mapped types — they carry intent and better hover. When a helper must stay erasable, keep it in a type-only module (see [01 Fundamentals 3.3 Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

**Runnable example** — queries here, transformations there — good vs bad (`tsc --strict`):

```typescript
// good — queries owned by this domain (2.3)
const ROUTES = { home: { path: "/", method: "get" }, users: { path: "/users", method: "post" } } as const;
type RouteTable = typeof ROUTES;
type RouteKey = keyof RouteTable; // "home" | "users" — this domain
type MethodOf<K extends RouteKey> = RouteTable[K]["method"]; // "get" | "post" via indexed access — this domain
const m: MethodOf<"home"> = "get";
console.log(m); // get

// bad — hand-rolling Pick/Omit that duplicates 09 utilities
type HandRolledPick<T, K extends keyof T> = { [P in K]: T[P] }; // ok but duplicates Pick<T,K> — use Pick
type GoodPick = Pick<RouteTable["home"], "path">; // prefer standard — owned by 09
console.log((null as unknown as GoodPick).path === undefined ? "pick" : "pick");

// good — transformation owned by 09 (preview — full treatment there)
type PartialRoutes = Partial<RouteTable>; // mapped over object — see 09
console.log(Object.keys(ROUTES).length); // 2

//  conditional + infer owned by 08/09 — textual forward
// type UnwrapPromise<T> = T extends Promise<infer U> ? U : T; // see 08/09
```

**Common confusion** — "`keyof` is a utility type" — `keyof`/`T[K]`/`typeof` are primitive operators (this domain, [2.3. Type queries](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>)); `Pick`/`Omit`/`Record` are library mapped/conditional types (09). "`as const` is a mapped type" — `as const` is a const assertion (see [3.3. satisfies assertions and narrowing](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>)), not a mapped type. "Utility types emit" — all erase — zero emit.

**Performance note** — `keyof`/`T[K]` are `O(members)` and trivial. Mapped/conditional/`infer` over large object unions (e.g., `DeepPartial` on a 100-key config) can dominate `check time` via instantiation count — split into `theme/colors.ts` + `theme/spacing.ts` and measure `tsc --extendedDiagnostics` `instantiations` before blaming object-shape leaves.

**Mentor note** — flag copy-pasted `{ [K in keyof T]: T[K] }` as "use `Pick`/`Partial`/`Record`" — intent signal > cleverness. Demo hover truncation on a 150-key `as const` table to justify module split.

**Cross-links** — `keyof`/`T[K]`/`typeof` queries → [2.3. Type queries on objects](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>); `readonly`/optional modifiers on queries → [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>); `satisfies`/`as const` preserving literals for queries → [3.3. satisfies assertions and narrowing](<../3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>); recursive shapes paired with utilities → [3.1. Recursive object types](<../3. Advanced Object Types/3.1. ### 5) **Configuration deep dive** (`exactOptionalPropertyTypes`, `strictNullChecks`, `erasableSyntaxOnly`) — [13 Configuration and Compiler Options](<../13 Configuration and Compiler Options/README.md>) (textual forward)

**Definition** — `tsconfig` flags that change how object types are checked or emitted: `strictNullChecks` (nullable optionals), `exactOptionalPropertyTypes` (`prop?: T` vs `prop?: T | undefined`), `erasableSyntaxOnly` (bans `enum`/`namespace`/parameter properties), `noImplicitAny`/`strict` family, and `isolatedDeclarations` for parallel emit.

**Why this domain stops here** — this domain *uses* flags to explain semantics (e.g., optional matrix in [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>), erasable note in [1.3. Interfaces vs type aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)); 13 owns the per-flag trade-off, `extends` composition, project references graph, and the 5.9→6.0 default delta. Duplicating the flag matrix here would drift.

**Modern guidance** — assume `strict: true` baseline (as of TS 5.9 era). Enable `exactOptionalPropertyTypes` when `undefined` vs absent matters (API payloads where missing ≠ `undefined`); keep `erasableSyntaxOnly: true` for native Node 22.12+ stripping / `isolatedDeclarations` compatibility — both `interface` and `type` stay erasable (see [1.3. Interfaces vs type aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). Full `extends` + monorepo advice lives in 13.

**Runnable example** — flag semantics preview — good vs bad (`tsc --strict` — `exactOptionalPropertyTypes` line only errors with that flag):

```typescript
// good — exactOptionalPropertyTypes changes optional contract (preview — deep dive in 13)
type Opts = { title?: string }; // with exactOptionalPropertyTypes:true, undefined requires | undefined
const ok1: Opts = {}; // ok — absent allowed
const ok2: Opts = { title: "hi" }; // ok
// const bad: Opts = { title: undefined }; // error TS2375 with exactOptionalPropertyTypes:true — needs title?: string | undefined
console.log(ok1, ok2);

// good — strictNullChecks (part of strict) — optional narrowing owned by 1.2, flag catalog in 13
type User = { nickname?: string };
function greet(u: User): string {
  if (u.nickname !== undefined) return `hi ${u.nickname}`; // narrowed
  return "hi";
}
console.log(greet({})); // hi

// bad — assuming absence and undefined are interchangeable in payloads without the flag
function send(payload: { token?: string }): void {
  // JSON.stringify({ token: undefined }) omits key; { } also omits — but
  // with exactOptionalPropertyTypes:true checker distinguishes — see 1.2 and 13
  console.log(JSON.stringify(payload)); // {} when token absent vs undefined
}
send({}); // ok
```

**Common confusion** — "`exactOptionalPropertyTypes` is covered by `strict`" — it is *not* in `strict` (as of 5.9) — it is opt-in. "`erasableSyntaxOnly` bans `interface`/`type`" — no — both erase; it bans `enum`/`namespace`/parameter properties. "`strictNullChecks` fixes optional vs `| undefined`" — `strictNullChecks` gates nullability; `exactOptionalPropertyTypes` refines optionality — they stack.

**Performance note** — flags do not emit but change check cost: `exactOptionalPropertyTypes` adds one assignability branch per optional property (`O(optionals)`); `isolatedDeclarations` (13) adds parallel emit passes — measure `tsc --extendedDiagnostics` per-flag rather than assuming "stricter = slower".

**Mentor note** — require a one-line comment on every non-default flag in `tsconfig.json` explaining the *object-shape* reason (`exactOptionalPropertyTypes` — payload absent vs undefined). In review, flag `enum` in new code when `erasableSyntaxOnly` is on — suggest literal union + `as const satisfies`.
