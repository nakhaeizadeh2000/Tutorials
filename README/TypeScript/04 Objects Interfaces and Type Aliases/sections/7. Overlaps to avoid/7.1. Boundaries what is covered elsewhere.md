## 7.1. Boundaries — what is covered elsewhere

This domain owns static object shapes: required/optional/readonly members, index signatures, interface/type choices, composition, merging and object queries. Related runtime and type-system topics have other owners. Use this page to locate the next explanation and to diagnose which layer a failing example exercises.

The track's checked baseline is TypeScript 7.0.2. Current configuration/tool migration belongs in the [7.0 learning route](<../../../25 Update TypeScript 7.0/sections/6. ### 3) **Functions, receivers and classes**

An object can declare `onClick: () => void`, but this is a function **type expression**, not an arrow implementation. A normal method body can satisfy that property type and still depend on its runtime receiver. Method/property spelling matters for variance checks; it does not itself install lexical this capture. The primary [function reference](https://www.typescriptlang.org/docs/handbook/2/functions.html#declaring-this-in-a-function) distinguishes function types and receiver typing.

Save `receiver.ts` in a new directory without a `tsconfig.json`:

```typescript
export {};
type Service = { name: string; onClick: () => void };
const service: Service = {
  name: "Ada",
  onClick() { console.log("receiver:", this.name); }
};
service.onClick(); // receiver: Ada
const detached = service.onClick;
try {
  detached();
} catch (error: unknown) {
  console.log("detached:", error instanceof TypeError ? "TypeError" : "other");
}
const bound = service.onClick.bind(service);
bound(); // receiver: Ada
```

Run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir out receiver.ts`, then `node out/receiver.js`. Both exit 0; the output is `receiver: Ada`, `detached: TypeError` and `receiver: Ada`. The ordinary call supplies service as receiver. The detached call lacks it, and the deliberate catch makes the failure observable. Bind supplies service for the later call. Compiler acceptance of the function-valued property did not guarantee detached-call safety.

Go to [this parameters and capture](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) for the full receiver topic and [callback variance](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) for assignment rules. For constructor/instance relationships and class encapsulation, use [Classes and Object-Oriented Types](<../../../06 Classes and Object-Oriented Types/README.md>). Choose an actual arrow, bound function or explicit receiver contract according to the caller's behavior, rather than assuming the erased type chooses an implementation.

### 4) **Queries, generics and utilities**

`typeof`, `keyof` and indexed access capture information from an object here. Reusable generic inference belongs in [Generics Deep Dive](<../../../08 Generics Deep Dive/README.md>); mapped/conditional utility construction belongs in [Utility Types and Type Transformations](<../../../09 Utility Types and Type Transformations/README.md>). A short use of Pick can introduce the boundary without rebuilding its mapped-type definition.

Save `queries.ts` beside the first file:

```typescript
export {};
const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "post" }
} as const;
type RouteTable = typeof ROUTES;
type RouteKey = keyof RouteTable;
type MethodOf<K extends RouteKey> = RouteTable[K]["method"];
const method: MethodOf<"home"> = "get";
console.log("method:", method); // get

type GoodPick = Pick<RouteTable["home"], "path">;
const picked: GoodPick = { path: ROUTES.home.path };
console.log("picked:", picked.path); // /
console.log("route count:", Object.keys(ROUTES).length); // 2
```

Use the same compile command with queries.ts, then run `node out/queries.js`. Both exit 0 and print `method: get`, `picked: /` and `route count: 2`. The query describes the existing table; picked is a separate initialized object satisfying the Pick-shaped contract. A type assertion of null would not create that object. Treat source data, a derived type and a constructed value as separate steps.

The full [object query lesson](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>) owns the local operators. Utility selection belongs in [standard utility reasoning](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>). Declaration emission options are configuration topics, rather than part of the utility catalog.

### 6) **Route a debugging question**

| Observed problem | Start with | Why |
|---|---|---|
| A typed readonly view observes a changed ID | 04/1.2, then JavaScript integrity | Identify the alias and runtime mutation policy. |
| A detached callback cannot read this.name | 05 receiver/capture | The implementation and call site determine the receiver. |
| Pick-shaped data is null at runtime | The value producer, then boundary validation | A type expression or assertion does not initialize or parse data. |
| A Route union rejects branch-only member access | 07 narrowing | Establish which variant reaches that access. |
| Checking succeeds but an emitter/tool fails | 13 configuration and 25 tool compatibility | The checking and consuming interfaces have different contracts. |

Practice explaining each route in a sentence. The table identifies the owner, but a complete diagnosis still needs the actual failing input, command and output. Use existing explanations for full mechanics and add only the application needed by the current lesson.

### 7) **Common confusion**

The same arrow-shaped syntax appears in a function type and an executable arrow, but only the latter chooses lexical capture. A type query describes a value without producing it. A runtime requirement can need both a checked contract and implementation work, even when their full explanations live in different domains. Ownership links prevent duplicated teaching; they do not require splitting a coherent fix merely because it crosses layers.

### 8) **Performance note**

The function property type and utility/query expressions erase. Allocation and receiver behavior depend on the actual method, closure or bound-function implementation. Bind executes here; no timing or allocation benchmark was measured. Object.freeze and prototype operations also need runtime evidence, while checker performance belongs in the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>). Heading ownership or type spelling alone cannot establish a cost.

### 9) **Mentor note**

Ask the learner to name the layer before proposing a fix: static assignment, control-flow evidence, runtime receiver, value construction, or tool consumption. Use the two programs to challenge an answer that attributes capture to a type or treats Pick as a constructor. A useful review comment includes the relevant owner link and the immediate reason, so the learner can follow it without guessing a prerequisite chain.
