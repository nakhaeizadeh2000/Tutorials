## 1.3. Interfaces vs type aliases — when to use which

### 1) **What overlaps** (both can describe object shapes, both erase, both participate structurally — 90% interchangeable)

**Definition** — `interface` and `type` are two spellings for the same core job — naming an object shape that the checker validates structurally and the emitter erases. `interface User { id: string; name: string }` and `type User = { id: string; name: string }` both say "any value with at least `id: string` and `name: string` satisfies me" — extra members allowed, missing members rejected — and both disappear from emitted JavaScript (see [Type erasure — what survives compilation](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)). For plain object shapes with required/optional/`readonly` members, they are 90% interchangeable.

**What problem it solves / history** — TypeScript shipped with `interface` from 0.8 (2012) as the nominal-looking way to describe object contracts — `class` already used `implements Interface` and declaration merging was needed for ambient `lib.d.ts` augmentation (adding `Array.prototype` members, `Window` extensions). `type` aliases arrived in 1.4 (2015) to name *any* type — not just objects — including unions, primitives, tuples, and later mapped/conditional/template-literal types. The overlap is intentional: both were given structural object syntax so teams could pick one without relearning shape semantics — the divergence (§2) exists only where one spelling enables syntax the other cannot.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), treat `interface` and `type` as **identical for object-shape assignability** — choose on the §2/§3 criteria, not on "which checks stricter" (neither is stricter for shapes). Both are [erasable](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) — safe under `--erasableSyntaxOnly` and native Node stripping — unlike `enum`/`namespace`. When a reviewer asks "why `interface` vs `type` here?" the answer should cite §2/§3, not habit.

**Runnable example** — same shape, two spellings — identical checking, identical erasure (good vs bad, `tsc --strict` + `--erasableSyntaxOnly` ok):

```typescript
// good — interface spelling for a plain object shape
interface UserI {
  id: string;
  name: string;
  nickname?: string;
  readonly createdAt: number;
}
const u1: UserI = { id: "1", name: "Ada", createdAt: Date.now() };
console.log(u1.name); // Ada

// good — type spelling for the same shape — checker treats them identically
type UserT = {
  id: string;
  name: string;
  nickname?: string;
  readonly createdAt: number;
};
const u2: UserT = { id: "2", name: "Grace", createdAt: Date.now() };
console.log(u2.name); // Grace

// good — structural assignability ignores the spelling — interoperable
const fromI: UserT = u1; // ok — UserI ≤ UserT (shape, not name)
const fromT: UserI = u2; // ok — UserT ≤ UserI
console.log(fromI.id, fromT.id); // 1 2

// good — both support optional / readonly / call signatures in the same way
interface ServiceI {
  host: string;
  connect(port?: number): void;
}
type ServiceT = {
  host: string;
  connect(port?: number): void;
};
const svcI: ServiceI = { host: "localhost", connect() {} };
const svcT: ServiceT = svcI; // ok — interchangeable
console.log(svcT.host); // localhost

// good — both erase — no emit, safe under --erasableSyntaxOnly
// npx tsc --strict --erasableSyntaxOnly --noEmit → ok (no TS1294)
// npx tsc --emitDeclarationOnly → both produce .d.ts, .js contains only: const u1 = { ... }

// bad — assuming one spelling changes assignability or runtime
type BrandedId = string;
// interface BrandedId2 { value: string } // different shape — not comparable to string
function deleteUser(id: BrandedId): void { console.log(id); }
declare let raw: string;
// deleteUser(raw as unknown as { value: string }); // error — shape mismatch, not spelling
deleteUser(raw); // ok — alias is still string; spelling didn't add nominal protection
// for true nominal separation use branding (see 3.2), not interface-vs-type
```

```typescript
// bad — mixing "which is stricter?" myth — excessive type annotation hides interchangeability
interface PointI { x: number; y: number }
type PointT = { x: number; y: number };
const p: PointI = { x: 1, y: 2, extra: 99 } as PointI; // bad — 'as' silences freshness regardless of spelling
// fix — keep literal fresh so either spelling catches the typo:
// const p2: PointI = { x: 1, y: 2, extra: 99 }; // error TS2353 — excess caught (freshness), not spelling
// const p3: PointT = { x: 1, y: 2, extra: 99 }; // error TS2353 — same error with type alias
console.log(p.x); // 1
```

**Common confusion** — "`interface` is strict / `type` is loose (or vice versa)" — false for object shapes: both use the same structural rule (width subtyping) and the same freshness heuristic on literals. "`type` has runtime cost / emit" — no: `type` aliases erase exactly like `interface` (both are `TS1294`-free under `--erasableSyntaxOnly`; contrast `enum`). "`interface` is always faster for the checker" — not for plain shapes; the checker interns both to the same internal object type (see Performance note).

**Performance note** — for plain object shapes (≤20 members, no conditional/mapped wrapping), `interface` vs `type` has **no measurable difference** in `tsc --extendedDiagnostics` — both produce one object-type symbol and erase to zero bytes. The emitter cost is zero; the checker cost is `O(members)` per assignability check regardless of spelling. No allocation, no GC, no JIT dispatch — strictly compile-time. Measure before optimizing spelling; the delta only appears at scale with the diverging features (§2).

**Mentor note** — demo interchangeability in one slide: define `interface A {x:number}` / `type B = {x:number}`, show `const a: A = {x:1}`, `const b: B = a` compiles both ways — the "aha" that spelling does not create nominal identity. Review check: any PR comment that says "change `type` to `interface` for performance" on a plain shape must cite a diagnostic (`--extendedDiagnostics`) — otherwise close as style nit. Exercise: give `interface User {id:string}` / `type User2 = {id:string}` and ask whether `User` is assignable to `User2` — answer: *yes*, structurally — then ask how to make them *not* assignable (branding, not spelling).

### 2) **What diverges** (interface merges and extends nominally; type aliases compose via `&`/`|`, support mapped/conditional/template-literal operators, and can name any type)

**Definition** — the overlap ends where syntax diverges: `interface` is an **open, nominally declared** shape — it can be *reopened* (declaration merging) and it *extends* other interfaces with a heritage clause; `type` is a **closed, expression-based** alias — it can name *any* type (object, union, primitive, tuple, mapped, conditional, template literal) and *composes* via `&` (intersection) and `|` (union), but it never merges and it composes only through type operators.

| Capability | `interface` | `type` alias |
|---|---|---|
| Describe object shape | yes | yes |
| Reopen / declaration merge (same name twice) | yes — merges members | no — `Duplicate identifier` |
| Heritage (`extends`) | `interface B extends A` (nominal list) | no — use `&` instead |
| Intersection `&` / union `|` | no (cannot `interface U = A \| B`) | yes — `type U = A \| B` |
| Mapped types `{[K in keyof T]: ...}` | no | yes |
| Conditional `T extends U ? X : Y` / `infer` | no | yes |
| Template-literal `type Key = \`on${string}\`` | no | yes |
| Name a non-object (primitive, tuple, union) | no | yes |
| Augment via `declare module` / `declare global` | yes (classic `.d.ts` augmentation) | no |

**What problem it solves / history** — merging exists because `lib.d.ts` and `@types` must *augment* ambient shapes without forking — `interface Array<T> { at(index:number): T | undefined }` added `Array.at` in TS 4.6 by merging into the global `Array` interface; `type` could not do that without overwriting. Conversely, `type` operators (`&`, `|`, mapped, conditional, template literal) were added (TS 2.1 mapped, 2.8 conditional, 4.1 template literal) as *type-level functions* — they needed expression syntax, which `interface` bodies don't support. The split is deliberate: `interface` owns *declaration-site extensibility*, `type` owns *composition-site expressiveness*.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- Need **ambient augmentation** or a **public contract that downstream `.d.ts` consumers may extend** → `interface` (and lint duplicate interface names as intentional, not accidental — see [2.2. Declaration merging](<../2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>)).
- Need **union, intersection with non-objects, mapped, conditional, template-literal, or `infer`** → `type` — these operators are *only* valid on type aliases (an `interface` body that tries `{[K in keyof T]: T[K]}` errors `TS2427`/`TS2526`).
- Need **heritage with conflict detection at declaration** → `interface extends` (errors early on incompatible overrides); **set-like composition** → `type &` (conflicts become `never` on the property, checked at use sites — semantics differ, see [2.1. Intersection vs extends](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>)).
- Both remain erasable — the choice is about syntax power, not emit.

**Runnable example** — each divergence with good vs bad, `tsc --strict` + `--erasableSyntaxOnly` ok (error lines commented with `TS` code so the fence still compiles):

```typescript
// --- Divergence 1: declaration merging — only interface merges ---

// good — interface merging intended (ambient augmentation / same-file reopen)
interface User {
  id: string;
}
interface User { // ok — merges into one User { id: string; name: string }
  name: string;
}
const user: User = { id: "1", name: "Ada" };
console.log(user.name); // Ada

// bad — type alias cannot merge — duplicate identifier
type Product = { id: string };
// type Product = { name: string }; // error TS2300: Duplicate identifier 'Product'
// fix — compose with & instead (new name, closed):
type ProductName = { name: string };
type ProductFull = Product & ProductName;
const prod: ProductFull = { id: "p1", name: "Widget" };
console.log(prod.name); // Widget

// good — augmentation of a third-party/global shape requires interface (in a module file)
export {}; // make this file a module so declare global is valid
declare global {
  interface Window {
    __APP_VERSION__?: string;
  }
}
// window.__APP_VERSION__ now type-checked — 'type Window = ...' inside declare global would error

// --- Divergence 2: extends (interface) vs & (type) ---

interface Animal { kind: string; age: number }
interface Dog extends Animal { bark(): void } // ok — heritage clause, conflict checked at declaration
const dog: Dog = { kind: "dog", age: 3, bark() { console.log("woof"); } };
dog.bark();

type AnimalT = { kind: string; age: number };
type DogT = AnimalT & { bark(): void }; // ok — set-like intersection, same result via operator
const dogT: DogT = { kind: "dog", age: 3, bark() { console.log("woof"); } };
dogT.bark();

// bad — conflicting property: extends errors at declaration, & produces never at use
// interface BadDog extends Animal { age: string } // error TS2430: 'age' string not assignable to number — caught early
type BadDogT = AnimalT & { age: string }; // ok at declaration — age is number & string → never
// const bad: BadDogT = { kind: "dog", age: "3", bark(){} }; // error — age: never → no value satisfies
declare const badExample: BadDogT;
// badExample.age; // never — unusable; 'extends' would have flagged earlier

// --- Divergence 3: mapped / conditional / template-literal — only type ---

// good — mapped type (Readonly, Partial, Pick) — only on type alias
type Point = { x: number; y: number };
type ReadonlyPoint = { readonly [K in keyof Point]: Point[K] }; // ok
const rp: ReadonlyPoint = { x: 1, y: 2 };
// rp.x = 9; // error TS2540 — readonly via mapped type

// bad — interface cannot be mapped
// interface ReadonlyPointI { readonly [K in keyof Point]: Point[K] } // error TS2428/TS2526: interface cannot use mapped syntax
// fix — derive as type, optionally extend interface from it:
interface ReadonlyPointI extends ReadonlyPoint {} // ok — interface can extend a mapped type
const rp2: ReadonlyPointI = { x: 1, y: 2 };
console.log(rp2.x, rp.x); // 1 1

// good — conditional + template-literal — only on type alias
type EventName = `on${Capitalize<string>}`;
type Handler = { [K in EventName]?: () => void }; // ok — patterned keys
const h: Handler = { onClick() { console.log("click"); } };
h.onClick?.();

// good — type can name any type (union, primitive alias, tuple), interface cannot
type Status = "idle" | "loading" | "done"; // union
type Id = string;                           // primitive alias
type Pair = [number, string];               // tuple
// interface StatusI = "idle" | "loading"  // error TS2427 — interface cannot represent union
// interface IdI = string                  // error — interface must be object shape
const s: Status = "idle";
console.log(s, ([1, "a"] as Pair)[1]); // idle a

// --- Divergence 4: union — only type ---

interface Circle { kind: "circle"; radius: number }
interface Square { kind: "square"; side: number }
// interface Shape = Circle | Square // error — interface cannot be union
type Shape = Circle | Square; // ok
function area(shape: Shape): number {
  return shape.kind === "circle" ? Math.PI * shape.radius ** 2 : shape.side ** 2;
}
console.log(area({ kind: "circle", radius: 3 })); // 28.27...

// All above spans are erasable — npx tsc --strict --erasableSyntaxOnly --noEmit → ok
```

**Common confusion** — "`type A = B & C` and `interface A extends B, C` are identical" — almost: `extends` checks conflicts *at the declaration* (incompatible `age: string` vs `age: number` errors immediately), `&` computes `never` on the conflicting property and errors only at the *use* site — different diagnostic timing and fix path. "`interface` can do mapped/conditional types" — no; the body must be a fixed member list, not a type-level function — derive a `type` first, then `interface Foo extends MappedType` if you need a nominal name. "`type` can merge like `interface`" — never — redeclaring `type Foo = ...` is always `TS2300`; reach for `&` or rename. "`interface` is legacy, `type` is modern" — both are modern (TS 5.9 handbook treats them as peer spellings); choosing on recency rather than §2 semantics is cargo-culting.

**Performance note** — divergence has real checker cost: **large intersections / mapped / conditional chains on `type` aliases instantiate type-level computation** (`O(n × depth)` plus memoization), while **interface heritage is a flat member-merge** that the checker interns more cheaply. A 50-member `type Deep = A & B & C & D` with conflicting optionals can be slower than `interface Deep extends A, B, C, D {}` because `&` must compute `never` intersections on conflicts; conversely, deeply mapped `type DeepPartial<T> = { [K in keyof T]?: DeepPartial<T[K]> }` recursed to depth >4 dominates check time in 10k-file monorepos regardless of spelling (depth is the cost, not the keyword). No runtime difference — both erase. Measure with `tsc --extendedDiagnostics` and `tsc --generateTrace trace/` — optimize by naming intermediates (`type Mid = A & B`) rather than inlining giant `&` at call sites.

**Mentor note** — teach the table as a decision tree, not a preference poll: "does this shape need to be *reopened* by another file?" → `interface`; "does it need `|`, mapped, conditional, or template-literal?" → `type`; else either (pick the team default and be consistent). Review exercise: hand a PR that tries `interface Handlers { [K in EventName]: () => void }` — ask the student to diagnose the error (`TS2526`), fix to `type Handlers = { [K in EventName]: ... }`, then discuss why the fix erases identically. Checklist item: every global/ambient augmentation files is `interface`-only — grep for `declare global { type` or `declare module { type` and flag as bad.

### 3) **Team rule of thumb** (public, augmentable contracts → `interface`; composite, utility, or union shapes → `type` — with `erasableSyntaxOnly` both safe)

**Definition** — a *team rule* is a deterministic, lintable convention that removes "which spelling?" bikeshedding: **public or augmentable contracts → `interface`; composite / utility / union shapes → `type`**. A third line handles the tie-breaker: when neither divergence matters, **pick the team default and be consistent within a file/module** — and verify that both remain erasable under `--erasableSyntaxOnly`.

| Situation | Use | Why (trade-off, not dogma) |
|---|---|---|
| Exported public API, library boundary, `lib.d.ts` / `components` contract | `interface` | Consumers may `declare module "lib" { interface Props { extra?: T } }` to augment; `type` would force a breaking `&` at every consumer. Readable `extends` errors at declaration (faster triage). |
| Domain object that *other teams augment* (`Window`, `Express.Request`, `Array`) | `interface` | Only `interface` participates in declaration merging / `declare global` / `declare module` — `type` cannot. |
| Union, intersection with non-object, mapped, conditional, template-literal, `infer`, tuple, primitive alias | `type` | Only `type` supports these operators — `interface` body is fixed members only. |
| Utility wrapping (`Partial<T>`, `Readonly<T>`, `Pick<T,K>`, `Omit<T,K>`, `DeepPartial`) | `type` (=`type PartialUser = Partial<User>`) | Utilities are mapped/conditional — they require `type`. Wrap the result again with `interface` only if you need a nominal name to `extend`. |
| Internal helper, no augmentation need, plain shape | either (team default, consistent per file) | No technical delta — pick one and lint for consistency. |
| Recursive object shape (`Tree`, `LinkedList`) | prefer `interface` | `interface Node { value: T; next: Node | null }` is more readable and marginally faster than `type Node = { value: T; next: Node | null }` at depth >5 (see 3.1). |

**What problem it solves / history** — without a rule, PRs churn on spelling — half the team writes `type Props = { ... }`, half writes `interface Props { ... }`, and reviewers re-litigate taste each time. Worse, the *wrong* spelling for the job creates refactoring cost later: a `type`-based public API that suddenly needs augmentation requires a breaking rename to `interface`; a utility-heavy domain modeled with `interface` forces `type Wrapper = ...` shims anyway. The TypeScript handbook itself has oscillated (older guides said "prefer `interface` for objects") — modern guidance (TS 5.9 handbook) explicitly calls them peers and advises deciding on *augmentation vs composition* rather than seniority. The rule above is that advice made lintable.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), adopt this enforceable convention:

1. **Default to `interface` for exported object shapes at module boundaries** — they read as "this contract may be extended" and give better `extends` diagnostics when conflicts appear.
2. **Default to `type` for everything that *computes* a shape** — unions, `&` compositions, mapped wrappers, conditional branches, template-literal keys, and utility aliases. If a line contains `|`, `&`, `in keyof`, `extends ?`, `` `on${string}` ``, or `infer`, it must be a `type`.
3. **For the remaining overlap (internal plain objects), pick one default and enforce it** — e.g., `@typescript-eslint/consistent-type-definitions` with `["error", "interface"]` for objects and allow `type` only for the operator cases above (or the inverse — consistency matters more than which you pick).
4. **Both spellings are erasable** — add `npx tsc --erasableSyntaxOnly --noEmit` in CI and `node --experimental-strip-types src/**/*.ts` probe; neither `interface` nor `type` should ever trip `TS1294` (unlike `enum`). Document that guarantee in `CONTRIBUTING.md` so new hires don't reintroduce `enum`/`namespace`.

All three bullet tools from [1.1. Object types — sealing the leak](<./1.1. Object types structural shape and excess property checks.md>) (`satisfies`, annotated binding, wider target) work identically with either spelling — `satisfies Interface` vs `satisfies Type` — so the rule never needs a `satisfies`-specific carve-out.

**Runnable example** — rule applied to real shapes — good vs bad, `tsc --strict` + `--erasableSyntaxOnly` ok:

```typescript
// good — public contract → interface (augmentable by consumers)
export interface AppProps {
  title: string;
  theme: "light" | "dark";
}
// consumer can augment without forking:
// declare module "./props" { interface AppProps { debug?: boolean } }

// good — composite / utility → type (operator needed)
type Status = "idle" | "loading" | "done"; // union needs type
type PartialProps = Partial<AppProps>;       // mapped utility needs type
type PropsOrError = AppProps | { error: string }; // union needs type
type HandlerKeys = `on${Capitalize<string>}`; // template literal needs type
type Handlers = Record<HandlerKeys, () => void>; // mapped needs type
type PropsWithId = AppProps & { id: string }; // intersection needs type (or interface extends)

// good — recursive shape → prefer interface (readability + checker intern)
interface TreeNode {
  value: number;
  left: TreeNode | null;
  right: TreeNode | null;
}
const leaf: TreeNode = { value: 1, left: null, right: null };
console.log(leaf.value); // 1

// contrast — type works but harder to read at recursion depth >3
type TreeNodeT = { value: number; left: TreeNodeT | null; right: TreeNodeT | null };
const leafT: TreeNodeT = { value: 1, left: null, right: null };
console.log(leafT.value); // 1

// good — utility + interface bridge (derive as type, name as interface when augmentation needed)
type BaseProps = Partial<AppProps> & { id: string }; // computed → type
interface AugmentedProps extends BaseProps { // named → interface for augmentation
  analytics?: boolean;
}
const ap: AugmentedProps = { id: "1", title: "Hi", theme: "light" };
console.log(ap.id); // 1

// good — internal helper with no augmentation need → either is fine; be consistent per file
// (this file chose 'type' as default for internal — that's the team decision, not a technical mandate)
type InternalCache = { url: string; hits: number };
const cache: InternalCache = { url: "/api", hits: 12 };
console.log(cache.hits); // 12

// bad — public union modeled as interface (breaks the rule, won't compile as written)
// interface BadShape { kind: "circle"; radius: number } | { kind: "square"; side: number } // syntax error
// fix — public shape that is a union must be a type:
type Shape = { kind: "circle"; radius: number } | { kind: "square"; side: number };
function area(s: Shape): number { return s.kind === "circle" ? Math.PI * s.radius ** 2 : s.side ** 2; }
console.log(area({ kind: "circle", radius: 2 })); // ~12.56

// bad — augmentable public API as type (blocks consumers, forces breaking & at call sites)
export type LockedProps = { title: string; theme: string };
// declare module "./locked" { type LockedProps = LockedProps & { debug: boolean } } // error TS2300 — type cannot merge
// fix — export as interface if augmentation is expected:
// export interface PublicProps { title: string; theme: string }

// bad — internal plain shape mixing spellings in one module (style churn)
// interface A { x: number } // good — pick one
// type A2 = { x: number }  // bad — two spellings for same internal pattern in same file
// fix — configure @typescript-eslint/consistent-type-definitions and let the linter decide

// erasable proof — all above pass --erasableSyntaxOnly (no TS1294)
// npx tsc --strict --erasableSyntaxOnly --noEmit → ok
// node --experimental-strip-types app.ts → runs (only values remain)
```

**Common confusion** — "we should always use `type` (or always `interface`) everywhere for consistency" — consistency matters *within* a module, but a single-spelling rule breaks the two cases that *require* a specific syntax (augmentation needs `interface`; `| `/mapped/conditional needs `type`). Enforce "consistent *where interchangeable*, specific *where divergent*". "`interface` merges are spooky magic — avoid all interfaces" — merging only happens for same-named `interface` in the same global scope or inside `declare module`/`declare global` — in normal `import`/`export` module files, two `interface Foo` in the same file merge intentionally, but cross-file merging requires an explicit `declare` — so accidental global leakage is rare when `verbatimModuleSyntax`/`isolatedModules` is on. "If both erase, why does `erasableSyntaxOnly` matter?" — it matters because `enum`/`namespace` (the *other* object-like declarations) do *not* erase cleanly — the rule guarantees the codebase stays on the erasable pair.

**Performance note** — the rule itself has zero runtime cost — both spellings erase. The *indirect* performance win is reducing `&`-heavy internal helpers that were written as `type` chains because "we always use type" — a single `interface` with `extends` for a plain chain of 4+ shapes can shave 5–10% off `tsc` check time in hot files (measured via `--extendedDiagnostics` + `--generateTrace`), while a single `type` that wraps a mapped utility is mandatory anyway. No GC/JIT effect — object types never shape the emitted JS. Choose for checker diagnostics (interfaces give earlier `extends` errors) and for augmentation need; micro-optimize only when traces show a leaf type dominating check time.

**Mentor note** — make the rule lintable and teachable, not tribal: add `@typescript-eslint/consistent-type-definitions` (or `biome` equivalent) with `interface` for object-shaped exports and `type` for operators — then in review, the CI message *is* the teaching. Onboard with a 5-minute exercise: give `type User = { id: string }` that's exported and ask "what happens when consumer needs `declare module` to add `avatar?`" — answer: blocked (must be `interface`), which is the single story that anchors the whole matrix. Review checklist: every exported object type at a `src/api`, `src/components`, `src/types` boundary is `interface` unless its definition contains `|`, `&` with non-object, `in keyof`, `extends ?`, or template-literal — in which case it *must* be `type` (and the `interface` bridge pattern is documented). Close with the erasable guarantee: "if `tsc --erasableSyntaxOnly` passes, your choice here will never break native stripping."
