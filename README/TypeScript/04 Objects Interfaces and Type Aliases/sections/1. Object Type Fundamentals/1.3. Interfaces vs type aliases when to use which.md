## 1.3. Interfaces vs type aliases — when to use which

An interface names an object contract. A type alias gives a name to a type expression, which may describe an object, union, primitive or computed type. For an ordinary object contract, both often work. Choose by the capabilities and intended extension points of the API, then check the actual assignment target.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Save each named file in a new directory without a tsconfig.json. Run `tsc --strict --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir out FILE.ts`, then `node out/FILE.js`. Substitute shapes, dictionaries, declarations or choices. To observe a rejection, uncomment only the indicated line and use the same compiler flags with `--noEmit` instead of `--outDir out`.

### 1) **Shared structural behavior and the dictionary exception**

Matching members allow the UserI and UserT values below to flow in both directions. The assignment preserves object identity; it does not construct a new User instance. Neither the interface name nor the alias creates nominal separation. A plain alias for string also accepts an ordinary string without validating its meaning.

Save `shapes.ts`:

```typescript
export {};
interface UserI { id: string; name: string; readonly createdAt: number }
type UserT = { id: string; name: string; readonly createdAt: number };
const ada: UserI = { id: "1", name: "Ada", createdAt: 0 };
const grace: UserT = { id: "2", name: "Grace", createdAt: 0 };
const fromInterface: UserT = ada;
const fromAlias: UserI = grace;
console.log("names:", fromInterface.name, fromAlias.name);
console.log("same object:", fromInterface === ada);
// const missing: UserT = { id: "3", createdAt: 0 };
// const extra: UserI = { id: "3", name: "Lin", createdAt: 0, typo: true };

type UserId = string;
const raw: string = "unvalidated-id";
function printId(id: UserId): void { console.log("id:", id); }
printId(raw); // A plain alias supplies no domain validation or brand.
```

The output is `names: Ada Grace`, `same object: true` and `id: unvalidated-id`. Uncomment missing to observe TS2741, or extra to observe TS2353. The first fails because a required member is absent; the second invokes a creation-site excess-property check. These distinctions are explained in [object shape and freshness](<./1.1. Object types structural shape and excess property checks.md>). A domain ID needs a deliberate construction/validation contract, as taught in [branding](<../3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>).

Structural compatibility between these two object shapes does not guarantee identical assignability to every other target. An open string dictionary is a useful counterexample.

Save `dictionaries.ts`:

```typescript
export {};
interface NameI { name: string }
type NameT = { name: string };
const i: NameI = { name: "Ada" };
const t: NameT = { name: "Grace" };
function values(dictionary: Record<string, string>): string {
  return Object.values(dictionary).join(",");
}
console.log("alias dictionary:", values(t));
// console.log(values(i)); // TS2345: NameI lacks the string index signature.

// A dictionary contract is appropriate when arbitrary string keys are intended.
interface NameDictionary { [key: string]: string; name: string }
const dictionary: NameDictionary = { name: "Ada", city: "London" };
console.log("explicit dictionary:", values(dictionary));

// Otherwise describe only what the consumer needs; both spellings satisfy it.
function upperName(person: { name: string }): string {
  return person.name.toUpperCase();
}
console.log("named consumer:", upperName(i), upperName(t));
```

The output is `alias dictionary: Grace`, `explicit dictionary: Ada,London` and `named consumer: ADA GRACE`. Uncomment values(i) to observe TS2345. In this case the object alias is accepted by Record<string, string>, while the interface lacks the required string index signature. The compiler's [maintainer discussion](https://github.com/microsoft/TypeScript/issues/15300) connects this implicit-index distinction to interfaces being reopenable; its historical explanation is corroborated here with the current compiler.

Choose the remedy from the consumer's operation. If arbitrary string keys genuinely belong to the contract, declare a compatible index signature. If the function needs only name, accepting a named member avoids imposing a dictionary contract on every caller. Replacing the rejected call with an assertion would hide that design question. The [index-signature owner](<./1.2. Optional readonly and index signatures.md>) covers missing lookups and compatible named members.

### 2) **Reopening an interface differs from introducing a fresh type**

Compatible interface declarations with the same name in the same scope contribute to one interface. An alias cannot be reopened this way. Create a new alias when composing a closed definition with additional members.

Ambient context adds another question: are we introducing a fresh type name or adding to an existing declaration? A fresh alias in declare global is legal in the following module. It does not become mergeable just because it is global. The [declaration-file deep dive](https://www.typescriptlang.org/docs/handbook/declaration-files/deep-dive.html) distinguishes introducing names from combining declarations.

Save `declarations.ts`:

```typescript
export {};
interface Preferences { theme: "light" | "dark" }
interface Preferences { compact?: boolean }
const preferences: Preferences = { theme: "dark", compact: true };
console.log("merged:", preferences.theme, preferences.compact);

type ClosedPreferences = { theme: "light" | "dark" };
// type ClosedPreferences = { compact?: boolean }; // TS2300: cannot reopen an alias.
type CompactPreferences = ClosedPreferences & { compact?: boolean };
const compact: CompactPreferences = { theme: "light" };
console.log("new alias:", compact.theme);

declare global {
  // This introduces a fresh type name; it does not merge an existing alias.
  type TutorialFreshLabel = string;
  interface TutorialPreferences { theme: "light" | "dark" }
  interface TutorialPreferences { compact?: boolean }
  // type TutorialFreshLabel = number; // TS2300: duplicate type name.
}
const label: TutorialFreshLabel = "Ada";
const globalContract: TutorialPreferences = { theme: "light", compact: false };
console.log("global types:", label, globalContract.theme, globalContract.compact);
```

The output is `merged: dark true`, `new alias: light` and `global types: Ada light false`. Uncomment either alias redeclaration separately to observe TS2300. The accepted TutorialFreshLabel declaration introduces a type; the rejected redeclaration attempts to reuse that same alias name. TutorialPreferences demonstrates a compatible interface merge in the same global block.

All runtime values are initialized here. The global declarations describe types; they install no global object, browser property or validation function. If an ambient declaration describes a runtime value, its provider must exist independently. File placement, module augmentation restrictions and real providers belong in [declaration merging and augmentation](<../2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) and the [file-scale global owner](<../../../12 Modules Namespaces and Declaration Files/sections/2. Namespaces and Ambient Contexts/2.2. declare global and global augmentation.md>). The fresh-global case is not a license to add arbitrary exports to any module augmentation.

### 3) **Choose the feature before applying a team convention**

Use interface when intentionally supporting compatible declaration merging. Use a type alias to name a union, primitive, tuple or type expression. For ordinary objects that need neither special capability, a consistent team convention is reasonable. Exporting a plain object alone does not establish that downstream augmentation is a supported extension mechanism.

An interface extends clause creates a structural object contract. A matching literal satisfies it without a class declaration or nominal identity. A computed type can also serve as a parent when its members are statically known; the mapped bridge below has that property. A union instead describes alternative possibilities and is naturally named with a type alias.

Save `choices.ts`:

```typescript
export {};
interface Point { x: number; y: number }
interface LocatedPoint extends Point { label: string }
const point: LocatedPoint = { x: 1, y: 2, label: "origin-ish" };
console.log("structural extension:", point.label, point.x, point.y);

type FrozenPoint = { readonly [K in keyof Point]: Point[K] };
interface NamedFrozenPoint extends FrozenPoint { label: string }
const frozenView: NamedFrozenPoint = { x: 1, y: 2, label: "view" };
// frozenView.x = 9; // TS2540: a readonly member through this view.
console.log("mapped bridge:", frozenView.label, frozenView.x);

type Outcome = { ok: true; point: Point } | { ok: false; message: string };
function describe(outcome: Outcome): string {
  return outcome.ok ? `${outcome.point.x},${outcome.point.y}` : outcome.message;
}
console.log("union:", describe({ ok: true, point }));
```

The output is `structural extension: origin-ish 1 2`, `mapped bridge: view 1` and `union: 1,2`. Uncomment the write through frozenView to observe TS2540. The mapped type creates a readonly view, rather than freezing the object. Direct mapped syntax belongs to the type expression; the interface can reuse this concrete result. Full mapped/conditional/template-literal techniques live in [type transformations](<../../../09 Utility Types and Type Transformations/README.md>), while [composition](<../2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) compares conflict handling.

The [current Handbook](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#differences-between-type-aliases-and-interfaces) presents the shared model and the reopening difference. Paweł Grzybek's original [comparison](https://pawelgrzybek.com/typescript-interface-vs-type/) provides a useful capability-first teaching sequence and explicitly corrects its older recursion discussion. Its preference for public interfaces is a convention to evaluate, rather than a requirement for every exported object.

For review practice, choose a spelling for an extensible preferences contract, a success-or-failure result and an internal coordinate object. A sound answer chooses interface for intended merging, type for the union and either consistent spelling for the coordinate object. If the coordinate API unexpectedly rejects a dictionary assignment, inspect that specific target rather than claiming the spellings are identical everywhere.

### 4) **Common confusion**

Open declaration merging does not make an interface nominal. A closed alias is still structural, rather than a sealed runtime object. Fresh ambient aliases and alias redeclarations are different operations. Finally, both names can describe the same ordinary members while behaving differently at an implicit-index assignment boundary; keep the target type in the explanation.

### 5) **Performance note**

These type declarations erase; the emitted programs contain the initialized objects, calls and output operations. The dictionary example still enumerates values and joins strings. No checker or runtime speed comparison was measured here, so member counts and recursion depths are not optimization thresholds. Complex composition deserves investigation with the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>), while a keyword change alone establishes no measured benefit.

### 6) **Mentor note**

Ask the learner to predict the mutual User assignments, then the two dictionary calls. A useful explanation identifies the different target contract instead of repeating that everything is structural. Next, compare the passing fresh global alias with the rejected redeclaration and ask what value declare global created. The answer is none in this program: every observed value comes from an initializer.
