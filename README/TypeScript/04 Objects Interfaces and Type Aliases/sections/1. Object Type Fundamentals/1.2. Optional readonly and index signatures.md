## 1.2. Optional readonly and index signatures

### 1) **Optional members** (`prop?: T` vs `prop: T | undefined` — assignability, `exactOptionalPropertyTypes`, and narrowing)

**Definition** — `prop?: T` marks a property as *optional* — the key may be absent (`{}` is valid, `"prop" in obj` is `false`). It does **not** automatically mean `prop: T | undefined` (key must be present, value may be `undefined`). Under default settings the two overlap; under `--exactOptionalPropertyTypes` they diverge — the distinction that decides whether `JSON.stringify` strips the key or preserves it. All three are object-level modifiers; full `null` vs `undefined` semantics live in [1.3. null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>).

**What problem it solves / history** — before `strictNullChecks` (TS 2.0, 2016) every property implicitly included `undefined`, so missing vs `undefined`-valued vs `null` were indistinguishable and typos like `portt: 5432` silently produced `{}` with `undefined`. `strictNullChecks` forced `| undefined` to be explicit. `?` was always the shorthand for "may be missing", but it historically *also* admitted `undefined` as a value — hiding wire bugs where `{ search: undefined }` serializes to `{}` while `{ search: null }` serializes to `{"search":null}`. `exactOptionalPropertyTypes` (TS 4.4, opt-in stricter) was added to make that distinction checkable at call sites.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), use this table:

| Declaration | Key may be missing? | Value may be `undefined` when present? | `JSON.stringify` |
|---|---|---|---|
| `prop?: T` | yes | only if default (`exactOptionalPropertyTypes: false`); **no** when `true` | missing → stripped |
| `prop?: T \| undefined` | yes | yes (both modes) | `undefined`-valued → stripped anyway |
| `prop: T \| undefined` | no (`{}` error) | yes | key present, value `undefined` → stripped |
| `prop: T \| null` | no | no (only `null`) | `null` → `{"prop":null}` preserved |
| `prop?: T \| null` | yes | via `?` | either missing or explicit `null` |

- Default to `prop?: T` for optional input (caller may omit).
- Write `prop: T | null` when the domain requires an explicit empty placeholder (DB nullable column, API `null`).
- Enable `exactOptionalPropertyTypes: true` on new codebases once the team can articulate missing vs `undefined`-valued — it surfaces the wire bug at assignment instead of at `fetch`. Model wire types exactly as sent.

**Runnable example** — assignability, `exactOptionalPropertyTypes`, and narrowing (good vs bad, `tsc --strict` — `exactOptionalPropertyTypes` lines commented where they would error under that flag):

```typescript
// good — optional means "may be missing"
type User = { id: string; nickname?: string; age: number | undefined };

const u1: User = { id: "1", age: undefined };          // ok — nickname missing, age present as undefined
const u2: User = { id: "2", nickname: "Ada", age: 30 }; // ok — both present
console.log("in" in u1, "nickname" in u1); // false — key absent

// narrowing — "in" tests presence, truthiness/!== undefined tests value
function greeting(u: User): string {
  if ("nickname" in u && u.nickname !== undefined) return `hi ${u.nickname}`;
  if (u.age !== undefined) return `age ${u.age}`;
  return "hi there";
}
console.log(greeting(u1)); // hi there
console.log(greeting(u2)); // hi Ada

// good — optional chaining + nullish coalescing narrow without assertions
function displayName(u: User): string {
  return u.nickname ?? "(no nickname)";
}
console.log(displayName(u1)); // (no nickname)

// exactOptionalPropertyTypes difference — default false admits undefined, true does not
type Config = { title?: string };
const okDefault: Config = { title: undefined }; // ok with default exactOptionalPropertyTypes:false
// with --exactOptionalPropertyTypes:true this line errors:
// const errorsWhenExact: Config = { title: undefined }; // error TS2322: Type 'undefined' not assignable to type 'string'
// fix when exact — include undefined explicitly:
type ConfigExact = { title?: string | undefined };
const okExact: ConfigExact = { title: undefined }; // ok even with exactOptionalPropertyTypes:true
const alsoOk: ConfigExact = {};                    // ok — missing still allowed
console.log(okDefault, okExact, alsoOk);

// bad — conflating optional with required | undefined over a JSON boundary
type Wire = { note: string | null };     // server expects key always present
type Local = { note?: string };          // local model optional
function toWire(local: Local): Wire {
  return { note: local.note ?? null };   // good — convert missing → null at boundary
}
console.log(JSON.stringify({} as Local));                              // {} — missing stripped
console.log(JSON.stringify({ note: undefined } as unknown as Local)); // {} — undefined stripped too (unknown cast keeps --exactOptionalPropertyTypes demo compilable)
console.log(JSON.stringify(toWire({})));                               // {"note":null} — explicit null preserved
```

```typescript
// bad — assuming optional property is always present
type Opts = { host: string; port?: number };
function connectBad(o: Opts): void {
  // const p: number = o.port; // error TS2322/TS18048: 'port' is number | undefined
  const p = o.port!; // bad — non-null assertion silences checker; throws if caller omitted port
  console.log(p.toFixed());
}

// good — narrow before use
function connectGood(o: Opts): void {
  if (o.port !== undefined) console.log(o.port.toFixed()); // ok — narrowed to number
  else console.log(`${o.host}:default`);
}
connectGood({ host: "localhost" });       // localhost:default
connectGood({ host: "localhost", port: 5432 }); // 5432

// bad — explicit undefined vs missing matters after spread/keys
type Config2 = { title?: string };
const withUndef = { title: undefined } as Config2;
console.log(Object.keys(withUndef)); // ["title"] — key exists even though value undefined
console.log(Object.keys({} as Config2)); // [] — key absent
// with exactOptionalPropertyTypes:true the first assignment would be flagged — choose the spelling the consumer expects
```

**Common confusion** — "`prop?: T` is sugar for `prop: T | undefined`" — false under `exactOptionalPropertyTypes: true` and observably false after `JSON.stringify` / `Object.keys` / `"prop" in obj`. "`in` and `!== undefined` are interchangeable" — `in` tests *presence* (`"k" in obj`), `!== undefined` tests *value*; with `prop?: string | undefined` you need both if the protocol distinguishes missing from `undefined`-valued. "`optional` is always the right default for nullable APIs" — if the server expects `{"note":null}`, use `| null` with required key, not `?`.

**Performance note** — optional members add one union branch to control-flow analysis — negligible. The cost is *human* and *wire* — each optional key doubles the states callers must handle. Deep optional trees (`DeepPartial<Config>` with 50+ optionals) widen checker work linearly; keep optional nesting shallow and validate at boundaries with a schema (`zod` / `valibot`) that produces a concrete required shape after parsing — one validation at entry saves thousands of `!== undefined` checks downstream. No runtime emit — `?` erases.

**Mentor note** — teach "three questions at the property": can the key be missing? can it be `undefined` when present? can it be `null`? Require the student to answer all three before choosing a spelling. Review checklist: every external-data type (`fetch` JSON, `localStorage`, query params) distinguishes `?` vs `| null` vs `| undefined` consistently; flip on `exactOptionalPropertyTypes` in CI for new services and demand `prop?: T | undefined` where `undefined`-valued is intentional. Exercise: given `type Req = { search?: string }` and `type Wire = { search: string | null }`, ask students to write `toWire` and explain why `JSON.stringify` produces different payloads for `{}` vs `{ search: undefined }` vs `{ search: null }`.

### 2) **readonly at the type level** (prevents *type-checked* writes but emits no runtime freeze — contrast with `Object.freeze`)

**Definition** — `readonly prop: T` (or `readonly T[]` / `Readonly<T>`) tells the checker "assignments to this property through this type are errors". It is a *compile-time* lens — the emitted JavaScript has no `writable: false` descriptor, no `Object.freeze`, no runtime guard. Mutations via a mutable alias, a type assertion, or plain JavaScript still succeed — unlike [`Object.freeze`](<../../../../JavaScript/06 Objects in Depth/sections/5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>) which installs non-writable descriptors at runtime (and is shallow).

**What problem it solves / history** — object properties in TypeScript are mutable by default (mirroring JavaScript). Without `readonly`, every function that receives `Config` can reassign `config.port`, making "config is constant after load" unenforceable and forcing defensive copies. `readonly` (since TS 2.0) lets interfaces express intent — "this field is read through this view" — without paying a runtime cost. It predates `as const` (TS 3.4) which adds *deep* literal+readonly for finite config objects; `readonly` remains the per-property, shallow counterpart.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

| Goal | Type-level (`readonly`) | Runtime (`Object.freeze` / `deepFreeze`) | Use when |
|---|---|---|---|
| Prevent accidental write in typed code | yes — `c.id = "x"` → error TS2540 | no | Public APIs, function params, returned views |
| Prevent runtime mutation from JS / `as any` / another realm | no — erased | yes — throws in strict, silent in sloppy | Module-level constants, enum maps, shared default configs |
| Shallow vs deep | shallow — nested objects still mutable unless also `readonly` | shallow by default — need recursive `deepFreeze` | Mark every level `readonly` or `as const` for deep intent |

- Use `readonly` on object/array properties that are *logically* immutable after construction (`id`, `createdAt`, injected `Config`). Use `readonly T[]` / `ReadonlyArray<T>` for covariant-safe array views (see [3.1. Covariance](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>)).
- For module constants, combine both: `type` is `readonly`, *value* is frozen — `const METHODS = { GET: "GET" } as const satisfies Record<string,string>; Object.freeze(METHODS);` — checker + runtime agree.
- Remember `readonly` is shallow — `readonly meta: { retries: number }` prevents `c.meta = {...}` but not `c.meta.retries = 9`; write `readonly meta: { readonly retries: number }` or `as const` for deep.
- Both `readonly` and `interface`/`type` are [erasable](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) — safe under `--erasableSyntaxOnly`.

**Runnable example** — type-level prevention vs runtime freeze (good vs bad, `tsc --strict`):

```typescript
// good — readonly prevents type-checked writes; shallow by design
type Config = { readonly id: string; readonly tags: readonly string[]; meta: { retries: number } };
type DeepConfig = { readonly meta: { readonly retries: number } };

const cfg: Config = { id: "a1", tags: ["web"], meta: { retries: 3 } };
// cfg.id = "b2"; // error TS2540: Cannot assign to 'id' because it is a read-only property
// cfg.tags.push("api"); // error — push does not exist on readonly string[]
cfg.meta.retries = 9; // ok — meta itself is mutable, inner is mutable (shallow surprise)
console.log(cfg.meta.retries); // 9

const deep: DeepConfig = { meta: { retries: 3 } };
// deep.meta.retries = 9; // error TS2540 — now inner is also readonly
console.log(deep.meta.retries); // 3

// readonly on function params — communicate "I won't mutate your array"
function total(xs: readonly number[]): number { return xs.reduce((a, b) => a + b, 0); }
const nums: readonly number[] = [1, 2, 3];
console.log(total(nums)); // 6
// total as (xs: number[]) => void would allow mutation — readonly view is covenant
```

```typescript
// good — combining type-level readonly with runtime freeze for constants
const HTTP_METHODS = { GET: "GET", POST: "POST" } as const; // type: { readonly GET: "GET"; readonly POST: "POST" }
Object.freeze(HTTP_METHODS);
// (HTTP_METHODS as { GET: string }).GET = "get"; // runtime write — sloppy silent, strict TypeError; type-checked write already blocked
console.log(Object.isFrozen(HTTP_METHODS)); // true
console.log(HTTP_METHODS.GET); // GET

// bad — relying on readonly alone for security / cross-realm safety
type Token = { readonly value: string };
const tok: Token = { value: "secret" };
const mutableAlias = tok as { value: string }; // escape via assertion
mutableAlias.value = "hacked"; // ok — readonly was only a view
console.log(tok.value); // hacked — mutation landed via alias
// also erased — no descriptor:
// console.log(Object.getOwnPropertyDescriptor(tok, "value")?.writable); // true — still writable at runtime
// fix — freeze the value that must not change at runtime:
const frozenTok = Object.freeze({ value: "secret" } as const);
console.log(Object.getOwnPropertyDescriptor(frozenTok, "value")?.writable); // false
// (frozenTok as { value: string }).value = "x"; // strict throws, sloppy silent ignored
console.log(frozenTok.value); // secret

// good — as const for deep readonly literals vs readonly per-property
const theme = { colors: { primary: "#000" } } as const; // deep readonly + literal "#000"
// theme.colors.primary = "#fff"; // error — deep readonly
console.log(theme.colors.primary); // #000
```

**Common confusion** — "`readonly` is `Object.freeze`" — no: `readonly` is type-only and erased; `freeze` is runtime and shallow — you need both for constants that cross an untyped boundary. "`readonly` is deep" — shallow; every nested level needs its own `readonly` or a deep `as const` / `ReadonlyDeep` utility. "`readonly T[]` is the same as `T[]`" — no: `readonly T[]` is covariant-safe (`Dog[]` → `readonly Animal[]` ok), `T[]` is unsoundly covariant (see [3.3. Unsound spots](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)). "`as const` does the runtime freeze" — it does not; `as const` is also type-only — pair with `Object.freeze` if you need runtime immutability.

**Performance note** — `readonly` has zero emit, zero allocation, zero GC — it is purely a checker gate. At runtime the object is identical to its mutable counterpart. `Object.freeze` *does* have runtime cost — per-object descriptor walk plus a shape-transition that makes engines treat the object as non-extensible (faster reads, slower future writes — engines optimize for "shape never changes"). Freeze constants at module load (linear startup cost, justified); never freeze per-request state bags in hot paths — each write then branches on `IsFrozen`.

**Mentor note** — demo the two-layer test in one file: `cfg.id = "x"` fails the checker (`tsc` error), then show `Object.getOwnPropertyDescriptor(cfg,"id").writable` is still `true` and `(cfg as any).id = "x"` succeeds — the "aha" that `readonly` is not a lock. Review rule: every exported constant object that is conceptually an enum/map is *both* `as const` (type) and `Object.freeze` (runtime) — add a CI grep for `export const.*= {` without trailing `as const` or `freeze`. Exercise: give `type State = { readonly items: readonly Item[]; meta: { count: number } }` and ask what `state.meta.count = 2` does — answer: compiles (shallow), which is the bug to fix with `readonly meta: { readonly count: number }`.

### 3) **Index signatures** (`[key: string]: T` — the open-ended dictionary escape; why mapped types and `Record` are usually safer)

**Definition** — an index signature `[key: string]: T` (or `[key: number]: T`, `[key: symbol]: T`) says "any string key is allowed and its value is `T`" — plus any explicitly declared members, which must be compatible with `T`. It models an unbounded dictionary (`cache: { [url: string]: Response }`). `Record<string, T>` is the mapped-type alias for the same shape; template-literal `Record<`prefix_${string}`, T>` narrows the key pattern. Both are erasable.

**What problem it solves / history** — JavaScript objects are used as maps (`const scores: any = {}; scores[username] = 42`). Before `Map` (ES2015) and before mapped types (TS 2.1), index signatures were the only way to type dictionaries. They remain the escape hatch for truly open-ended bags (plugin registries, `localStorage` wrappers, parsed JSON with unknown keys). The hazard is openness — once you add `[key: string]: T`, *every* known property must satisfy `T`, and the type loses exactness — excess-property typo guards weaken and autocomplete degrades.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

| Need | Prefer | Why |
|---|---|---|
| Finite known keys (`"get" \| "post"`, `"id" \| "name"`) | `type M = "get" \| "post"; Record<M, Handler>` or `{ get: Handler; post: Handler }` | Retains exactness, typo-checked, autocomplete |
| Open bag with uniform values | `Record<string, number>` (= `{ [k: string]: number }`) — narrowest that fits | `Record` reads as "dictionary" intent |
| Open bag with mixed known + extra | Intersection: `type T = { id: string; name: string } & Record<string, unknown>` | Known props keep their types, extra is bounded |
| Constrained keys (`on_`, `data-`) | `Record<\`on${string}\`, Handler>` (TS 4.4+ template literal index) | Pattern-checked keys |

- Do not mix incompatible known members into an index signature — `type Bad = { [k: string]: number; name: string }` → error: `string` not assignable to `number`. Either make the known member compatible (`name: number`) or use intersection (`{ name: string } & Record<string, number>` — where known `name` stays `string` via intersection merging).
- Prefer `Map<K,V>` at runtime for non-string keys, iteration order guarantees, and no prototype pollution (`__proto__` key in a plain dict is dangerous); use index signatures only when the value *is* a plain JSON object.
- For finite-key objects, `as const` + `typeof` or `satisfies` preserves literal keys better than `[key: string]`.

**Runnable example** — open dictionary vs safer `Record` / intersection (good vs bad, `tsc --strict`):

```typescript
// good — Record<string, T> for a uniform dictionary (open bag)
type Scores = Record<string, number>;
const scores: Scores = { alice: 42, bob: 17 };
scores["carol"] = 99; // any string key ok
console.log(scores["alice"]); // 42
console.log(Object.entries(scores).length); // 3

// bad — index signature swallows known-property mismatch
// type Bad = { [key: string]: number; name: string }; // error TS2411: 'string' not assignable to 'number' — every key must be number
// fix — keep known props typed via intersection
type NamedScores = { name: string } & Record<string, number | string>;
const named: NamedScores = { name: "leaderboard", alice: 42, bob: 17 };
console.log(named.name.toUpperCase()); // LEADERBOARD — name stays string, extra keys are number|string

// good — intersection widens extra without contaminating known props
type Config = { host: string; port: number } & Record<string, unknown>;
const cfg: Config = { host: "localhost", port: 5432, debug: true, retries: 3 };
console.log(cfg.debug); // true — extra allowed but bounded to unknown

// bad — index signature disables excess-property typo guard for open bags
type Dict = { [key: string]: number };
const dict: Dict = { alcie: 42 }; // no error — typo "alcie" silently accepted (any key is valid)
// fix — for finite keys, use exact shape + satisfies (typo caught)
type ExactScores = { alice: number; bob: number };
const exact = { alice: 42, bob: 17 } satisfies ExactScores;
// const typoExact = { alcie: 42, bob: 17 } satisfies ExactScores; // error TS1360 — typo caught

// good — template-literal Record for patterned keys (TS 4.4+)
type Handlers = Record<`on${string}`, () => void>;
const handlers: Handlers = { onClick: () => console.log("click"), onHover: () => console.log("hover") };
handlers.onClick();
// handlers.click = () => {}; // error — "click" does not match `on${string}`

// good — prefer Map at runtime for non-string keys / prototype safety
const byId = new Map<string, number>([["alice", 42]]);
byId.set("__proto__", 1); // safe — Map key, not prototype pollution
console.log(byId.get("__proto__")); // 1
const dictProto: Record<string, number> = {};
// (dictProto as Record<string, number>)["__proto__"] = 1; // bad — pollutes prototype if using plain object as map
```

```typescript
// bad — numeric vs string index nuance
type NumDict = { [key: number]: string };
// NumDict accepts string keys too (numbers coerce to strings), but checker treats them as numeric index:
// const nd: NumDict = { 0: "a", hello: "b" }; // hello is string key — allowed via JS but not checked as number index
// fix — be explicit about which dictionary you mean:
type StringDict = Record<string, string>;
type NumberArray = { [index: number]: string; length: number }; // array-like
const arrLike: NumberArray = { 0: "a", 1: "b", length: 2 };
console.log(arrLike[0]); // a

// good — readonly index signature for immutable view
type ReadonlyDict = { readonly [key: string]: number };
const ro: ReadonlyDict = { a: 1, b: 2 };
// ro["a"] = 9; // error TS2540 — readonly index
console.log(ro["a"]); // 1
```

**Common confusion** — "`Record<string, T>` and `{ [k: string]: T }` differ" — almost identical; `Record` is `type Record<K,T> = { [P in K]: T }` (mapped type), so `Record<string,T>` *is* an index signature. Difference is readability and that `Record` composes with unions/template literals. "Index signatures are exact / catch typos" — they do the opposite — any key is valid, so typos are invisible; use an exact object type with `satisfies` for finite keys. "Numeric index `[n: number]: T` only allows numeric keys" — at runtime all keys are strings/symbols; the numeric index is a checker-level view (arrays are `number`-indexed but also have `length: number` which must be compatible). "`Map` and `Record<string,T>` are interchangeable" — `Map` preserves key types (including objects), has size/iteration, and avoids `__proto__` pollution; `Record` is a plain object with string keys and prototype chain.

**Performance note** — index signatures widen the type to "all strings → T", which disables excess-property checks and broadens assignability — checker does less per-property validation (marginally faster for huge literals) but you lose the typo guard. No runtime allocation difference — both erase to plain objects. The real cost is downstream — iterating an open `Record<string, T>` forces `Object.entries` to be `(string, T)[]` with no key narrowing; iterating `Map` or a finite-key object lets the checker keep literal key unions, enabling better narrowing and often fewer runtime `in` checks.

**Mentor note** — ask "is the key set *finite and known at author time* or *open and user-supplied*?" — finite → exact object type + `satisfies`; open uniform → `Record<string, T>`; open with known spine → intersection `Known & Record<string, unknown>`; patterned → template-literal `Record`. Review flag: any `[key: string]: any` — replace `any` with `unknown` and bound the value. Exercise: give `type User = { name: string; [k: string]: string }` and ask why `name: string` is required to be compatible — because `name` must satisfy the index signature; fix is `& Record<string, unknown>` if `name` should stay `string` while extra stays bounded. Also show `Object.keys(dict).includes("__proto__")` pollution demo to motivate `Map` for user-supplied keys.
