## 1.2. Optional readonly and index signatures

Object contracts answer three different questions: may a key be omitted, may this view write a member, and which keys may appear? Those static permissions do not determine serialization or change an object's prototype. This lesson separates the contracts from the runtime operations that consume them.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Save each named file in a new directory without a `tsconfig.json`. For the four runtime files, run `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --target es2022 --module commonjs --lib es2022,dom --outDir out FILE.ts`, followed by `node out/FILE.js`. Replace FILE with optional, readonly, dictionaries or prototypes. All four compile and run as shown. The separate optional-mode file is checked with `--noEmit` in both flag modes.

### 1) **Optional members: assignment, presence and serialization**

`note?: string` permits an omitted key. `note: string | undefined` requires the key while permitting undefined as its value. Under strict checking, reading either can produce undefined. With [exactOptionalPropertyTypes](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html), an optional property admits an explicitly undefined value only if its declared union includes undefined.

The following table concerns **assignment** under strictNullChecks. The value T here excludes null and undefined.

| Declaration | May omit key? | Present undefined, exact off | Present undefined, exact on | Present null? |
|---|---|---|---|---|
| `note?: T` | yes | yes | no | no |
| `note?: T \| undefined` | yes | yes | yes | no |
| `note: T \| undefined` | no | yes | yes | no |
| `note: T \| null` | no | no | no | yes |
| `note?: T \| null` | yes | yes | no | yes |
| `note?: T \| null \| undefined` | yes | yes | yes | yes |

Save `optional-mode.ts` to compare both modes:

```typescript
export {};
type Text = { note?: string };
type Maybe = { note?: string | null };
type Explicit = { note?: string | null | undefined };
const absent: Maybe = {};
const nullValue: Maybe = { note: null };
const explicit: Explicit = { note: undefined };
const textUndefined: Text = { note: undefined };
const nullableUndefined: Maybe = { note: undefined };
```

`tsc --strict --noEmit optional-mode.ts` succeeds. Add `--exactOptionalPropertyTypes` and the last two assignments report TS2375; the omitted key, explicit null and union explicitly including undefined remain accepted. The flag changes checking rather than installing a runtime rule.

Save `optional.ts` for presence and serialization observations:

```typescript
export {};
type Optional = { note?: string | undefined };
type RequiredUndefined = { note: string | undefined };
type Nullable = { note?: string | null };
const missing: Optional = {};
const present: RequiredUndefined = { note: undefined };
const nullable: Nullable = { note: null };
console.log("presence:", "note" in missing, "note" in present); // false true
console.log("own keys:", Object.keys(missing).length, Object.keys(present).length); // 0 1
console.log("JSON:", JSON.stringify(missing), JSON.stringify(present)); // {} {}
console.log("null:", JSON.stringify(nullable)); // {"note":null}
function display(value: Optional): string {
  return value.note !== undefined ? value.note.toUpperCase() : "empty";
}
console.log("display:", display(missing), display({ note: "Ada" })); // empty ADA
function toWire(value: Optional): { note: string | null } {
  return { note: value.note ?? null };
}
console.log("wire:", JSON.stringify(toWire(missing))); // {"note":null}
// const absent: RequiredUndefined = {}; // uncomment: TS2741
```

The output distinguishes presence (`false true`) and own-key count (`0 1`), while both objects serialize as `{}`. Null serializes as `{"note":null}`. An undefined-valued object property is omitted by [JSON serialization](https://tc39.es/ecma262/multipage/structured-data.html#sec-json.stringify), even when its TypeScript declaration requires the key. Optionality does not change that algorithm. The display function checks the value before using its string method; the final toWire operation deliberately constructs a required null placeholder. See the [verified wire example](<../../../03 Basic Types and Annotations/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by basic type misunderstandings.md>) for a serialized receiving check.

Uncomment absent and check with `--noEmit` to observe TS2741: a required undefined-capable property must still be supplied. Choose omitted, null or explicit undefined according to the consumer's contract; a non-null assertion does not create a missing value.

### 2) **Readonly is a view; freeze is a runtime operation**

A readonly property blocks assignments through that typed view. It does not remove mutable aliases or recursively mark nested members readonly. The [Object Types reference](https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties) explains aliasing and shallow permissions.

Save `readonly.ts`:

```typescript
export {};
type View = { readonly id: string; readonly meta: { count: number } };
const mutable = { id: "a1", meta: { count: 1 } };
const view: View = mutable;
// view.id = "b2"; // uncomment: TS2540
mutable.id = "b2";
view.meta.count = 2;
console.log("view:", view.id, view.meta.count); // b2 2
console.log("descriptor:", Object.getOwnPropertyDescriptor(view, "id")?.writable); // true

const frozen = Object.freeze({ id: "a1", meta: { count: 1 } });
frozen.meta.count = 2; // nested object is still mutable
console.log("freeze:", Object.isFrozen(frozen), Object.isFrozen(frozen.meta)); // true false
try {
  (frozen as { id: string }).id = "b2"; // deliberately bypass static readonly
} catch (error: unknown) {
  console.log("write:", error instanceof TypeError ? "TypeError" : "other");
}
console.log("frozen values:", frozen.id, frozen.meta.count); // a1 2
```

The output is `view: b2 2`, `descriptor: true`, `freeze: true false`, `write: TypeError` and `frozen values: a1 2`. A mutable alias changes the ID observed through the readonly view, and the nested count remains writable. Uncomment the write through view to observe TS2540. That rejection concerns the typed access path.

Object.freeze acts on the actual outer object: the deliberate assertion escape still encounters a strict-mode runtime TypeError when changing its frozen ID. The nested object remains unfrozen and its count changes. Use readonly to state typed access intent, and choose runtime freezing when the value's mutation policy requires it. Neither readonly nor as const promises runtime freezing or a detached immutable snapshot. Full runtime integrity mechanics belong in the [JavaScript freeze owner](<../../../../JavaScript/06 Objects in Depth/sections/5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>).

### 3) **Index signatures and compatible known members**

`Record<string, number>` permits an open string-keyed numeric dictionary. It does not promise that each possible key has actually been stored. [noUncheckedIndexedAccess](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html) adds undefined to undeclared indexed reads; these examples enable it and check absent values before using them.

A string index signature also constrains known string-named members. Intersecting `{ name: string }` with a numeric dictionary keeps both requirements, so a string name does not become valid by changing the syntax to an intersection. Either permit an agreed broader value union or put numeric entries under a separate scores property. The [index-signature reference](https://www.typescriptlang.org/docs/handbook/2/objects.html#index-signatures) explains this named-member constraint.

Save `dictionaries.ts`:

```typescript
export {};
type Scores = Record<string, number>;
const scores: Scores = { alice: 42, bob: 17 };
scores["carol"] = 99;
console.log("scores:", scores["alice"], scores["missing"]); // 42 undefined
const candidate = scores["missing"];
console.log("checked read:", candidate === undefined ? "absent" : candidate.toFixed());

type NamedScores = { name: string } & Record<string, string | number>;
const named: NamedScores = { name: "leaderboard", alice: 42 };
console.log("name:", named.name.toUpperCase()); // LEADERBOARD
const nested: { name: string; scores: Scores } = {
  name: "leaderboard", scores: { alice: 42 }
};
console.log("nested:", nested.scores["alice"]); // 42
// const incompatible: { name: string } & Record<string, number> = { name: "leaderboard", alice: 42 }; // TS2322

const finite = { alice: 42, bob: 17 } satisfies Record<"alice" | "bob", number>;
console.log("finite:", finite.bob); // 17
// const typo = { alcie: 42, bob: 17 } satisfies Record<"alice" | "bob", number>; // TS2561
const arrayLike: { [index: number]: string; length: number } = { 0: "a", length: 1 };
console.log("array-like:", arrayLike[0], arrayLike.length); // a 1
const handlers: Record<`on${string}`, () => void> = { onClick: () => console.log("click") };
handlers["onClick"]?.(); // indexed lookup may be absent under the chosen flag
```

The outputs show the missing lookup as undefined, a checked absent result, the typed name `LEADERBOARD`, numeric nested scores, finite bob value 17, array-like `a 1` and click. Uncomment incompatible to get TS2322; uncomment typo to get TS2561. The finite Record requires alice and bob instead of accepting any spelling. A numeric index signature can coexist with the nonnumeric length property; it constrains numeric indexes rather than every string-named field. The handler key pattern allows on-prefixed names, but an arbitrary indexed read may still be absent.

Prefer a finite contract for known fields. For an open bag, choose the value type and absence handling deliberately. The full mapped-type catalog belongs in [utility types](<../../../09 Utility Types and Type Transformations/README.md>); runtime collection design belongs in [collections](<../../../10 Arrays Tuples and Collections/README.md>).

### 4) **Dictionary keys and prototype behavior**

A plain object may inherit the legacy __proto__ accessor. On the tested Node runtime, assigning number 1 through that accessor changes neither the prototype nor the own keys. Assigning an object does change that particular dictionary's prototype. This follows the [legacy setter algorithm](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-set-object.prototype.__proto__): a value other than an object or null returns without mutation. Observe prototype identity and own-property presence separately.

Save `prototypes.ts`:

```typescript
export {};
const numeric: Record<string, number> = {};
const before = Object.getPrototypeOf(numeric);
numeric["__proto__"] = 1;
console.log("numeric:", Object.getPrototypeOf(numeric) === before, Object.keys(numeric).length); // true 0

const ordinary: Record<string, unknown> = {};
const inherited = { marker: true };
ordinary["__proto__"] = inherited;
console.log("object:", Object.getPrototypeOf(ordinary) === inherited,
  Object.hasOwn(ordinary, "marker"), ordinary["marker"]); // true false true
console.log("own proto key:", Object.hasOwn(ordinary, "__proto__")); // false

const noPrototype: Record<string, number> = Object.create(null);
noPrototype["__proto__"] = 1;
console.log("null prototype:", Object.getPrototypeOf(noPrototype) === null,
  Object.hasOwn(noPrototype, "__proto__"), noPrototype["__proto__"]); // true true 1
const map = new Map<string, number>();
map.set("__proto__", 1);
console.log("Map:", map.get("__proto__")); // 1
```

The five lines are `numeric: true 0`, `object: true false true`, `own proto key: false`, `null prototype: true true 1` and `Map: 1`. The changed ordinary dictionary inherits marker but does not own it. This fixture changes only that local object's prototype; it does not change Object.prototype or demonstrate a complete production exploit. Object.keys alone cannot establish which prototype changed.

For arbitrary dictionary keys, Map keeps entries separate from object property lookup. A null-prototype object also avoids this inherited accessor but remains an object with string/symbol property keys and its own serialization rules. Choose the representation for those semantics; an erased Record declaration selects neither. The original [prototype-less dictionary explanation](https://javascript.info/prototype-methods) supplies a useful before/after comparison, corroborated here with direct identity checks. The [JavaScript prototype owner](<../../../../JavaScript/06 Objects in Depth/sections/3. Prototype linkage intro/3.1. The prototype chain getPrototypeOf setPrototypeOf and Object.create.md>) owns the full runtime mechanics.

### 5) **Common confusion**

An undefined-capable required property can disappear from JSON, a readonly view can observe mutation through another alias, and an open numeric dictionary can still return undefined for a missing key. These are different contracts. Ask separately whether the key must exist, what values are permitted, who can write, and which runtime object was created. A prototype claim needs a prototype observation, rather than an inference from an empty key list.

### 6) **Performance note**

Optional and readonly modifiers and index signatures are erased; they emit no serializer, freeze or dictionary allocation. The examples' JSON conversion, object freezing and collection operations do execute. No speed comparison or engine optimization was measured. Choose the needed mutation/key/serialization behavior first, then measure relevant workloads before claiming that freezing or replacing a collection improves performance.

Finally, repair the incompatible NamedScores design and describe why the numeric prototype assignment differs from the object assignment. Require both a contract explanation and an observed result.
