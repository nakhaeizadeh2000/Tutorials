## 1.1. Object types — structural shape and excess property checks

### 1) **Structural shape** (an object type is a set of required members — assignability by shape, width subtyping)

**Definition** — an object type like `{ x: number; y: number }` is a *contract* that says "any value with at least `x` and `y` (both `number`) satisfies me" — extra members are ignored, missing or mismatched members are rejected. TypeScript compares *shapes*, not declaration names — this is [structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>), and object types erase completely at emit (see [Type erasure — what survives compilation](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**What problem it solves / history** — JavaScript objects are open-ended bags — `{ x: 1, y: 2, color: "red" }` is created without declaring a nominal class, and functions consume only what they read (`function draw(p: {x:number; y:number})` reads `x`/`y` and ignores `color`). A nominal system (Java/C# style — "only `Point` instances count as `Point`") would reject that extra `color` and force ceremony for every ad-hoc shape. TypeScript chose structural subtyping from day one so JS idioms stay idiomatic — width subtyping (`{x,y,color} ≤ {x,y}`) is the rule, not the exception.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), model object shapes with plain object types, `type` aliases, or `interface` — all three participate identically in structural checks (when to prefer which is owned by [1.3. Interfaces vs type aliases](<../1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). Treat extra members as *allowed by default* — do not fight width subtyping; rely on the freshness lint (§2 below) for typo-catching, not on structural rejection.

**Runnable example** — width and depth by shape (good vs bad, `tsc --strict`):

```typescript
// good — width subtyping lets rich values flow into narrow consumers
type Point = { x: number; y: number };
type ColoredPoint = { x: number; y: number; color: string };

function draw(p: Point): void {
  console.log(`(${p.x}, ${p.y})`);
}

const rich: ColoredPoint = { x: 10, y: 20, color: "red" };
draw(rich); // ok — ColoredPoint has superset of Point's members → ColoredPoint ≤ Point

// Through a variable — extra members are silent (no freshness)
const withExtra = { x: 1, y: 2, z: 3, label: "origin" };
const p1: Point = withExtra; // ok — width subtyping

// Depth — nested members checked recursively
type Config = { server: { host: string } };
type RichConfig = { server: { host: string; port: number } };
declare let richCfg: RichConfig;
const cfg: Config = richCfg; // ok — inner { host, port } ≤ { host }

// bad — assuming nominal protection that doesn't exist
type UserId = string;
type OrderId = string;
function deleteUser(id: UserId): void {}
declare let oid: OrderId;
deleteUser(oid); // compiles — aliases are the same shape (string); structural alias ≠ nominal brand

// bad — expecting width to be rejected at the call site via literal
// draw({ x: 1, y: 2, color: "red" }); // would be ok via shape, but FRESH literal triggers
// the extra "excess property" lint (§2) — not a structural failure. Don't confuse the two.
```

```typescript
// bad — depth mismatch IS a structural failure (not width, not freshness)
type A = { inner: { value: string } };
type B = { inner: { value: number } };
declare let b: B;
// const a: A = b; // error TS2322: number not assignable to string — deep member incompatible
```

**Common confusion** — "extra members should be an error" — only for *fresh* literals (see §2); through a variable or spread, extra members are invisible to the checker by design. "Two interfaces with the same members are different types" — no, they are interchangeable structurally; use branding ([1.3. Nominal typing techniques](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)) when you need nominal separation. "`implements` makes the shape fit" — `implements` only *checks* satisfaction; removing it does not change assignability.

**Performance note** — structural checks are O(n × depth) over member count — trivial for typical object types (<20 members). Deeply nested `DeepPartial<LargeConfig>` with recursion depth >5 or 50+ member object literals can dominate checker time because each depth layer re-walks the shape. Cost is compile-time only — after erasure there is zero runtime overhead (object types leave no emit, no allocation, no dispatch table). Measure `tsc --extendedDiagnostics` on your project; prefer `Pick`/`Omit` composition that names intermediates over giant inline literals when diagnostics show type-check time spiking.

**Mentor note** — teach with the question "is source *assignable* to target?" — answer by member-wise containment, not by `extends` lookup. Review exercise: give two unrelated `class Dog { name: string }` / `class Cat { name: string }` and ask if `Dog` is assignable to `{ name: string }` — correct answer is *yes* (structural), which reframes `class` as a shape factory, not a nominal type. Check that students can articulate why `draw({ x: 1, y: 2, z: 3 } as Point)` silences a guard (§3 warns against it).

### 2) **Freshness at the literal** (fresh literal direct vs via variable — the excess-property heuristic)

**Definition** — *freshness* (excess property check) is an extra lint that fires *only* when a fresh object literal — `{ ... }` written directly at an assignment, call argument, or `return` — is checked against a target type. If the literal contains a property the target does not declare, the checker reports `Object literal may only specify known properties` — even though the literal *is* structurally assignable (see §1). The heuristic exists to catch typos, not to enforce nominal exactness.

**What problem it solves / history** — without freshness, `connect({ host: "localhost", portt: 5432 })` where `Options = { host: string; port?: number }` would silently pass — `portt` is an extra member, width subtyping says "extra is ok", so the typo `portt` ships and `port` stays `undefined` at runtime. Freshness was added early (TypeScript 1.6 era) as a pragmatic exception: flag excess on *literals at the call site* where typos are most likely, while leaving variable-flow (where excess is often intentional) untouched.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), treat freshness as a *warning*, not a soundness proof — it catches the common case (fresh literal typo) and evaporates everywhere else. Do not rely on it for safety-critical validation; use `exactOptionalPropertyTypes` and runtime validators at boundaries instead. When freshness fires, fix the typo — do not reflexively `as` the literal away (see §3 for correct escapes).

**Runnable example** — when freshness triggers vs evaporates (good vs bad, `tsc --strict`):

```typescript
type Point = { x: number; y: number };
type Options = { host: string; port?: number };
function connect(opts: Options): void {
  console.log(opts.host, opts.port);
}

// good — fresh literal with typo is CAUGHT
// connect({ host: "localhost", portt: 5432 }); // error TS2353: 'portt' does not exist in type 'Options' — typo caught!

// freshness evaporates through an intermediate variable — excess becomes silent (width subtyping)
const optsViaVar = { host: "localhost", portt: 5432 }; // no target yet → no check
connect(optsViaVar as Options); // bad — no error here; typo survives (port stays undefined at runtime)
console.log((optsViaVar as Options).port); // undefined — bug shipped three calls later

// spread also drops freshness — the result is no longer a fresh literal
const base = { host: "localhost", portt: 5432 };
const spread: Options = { ...base, host: "localhost" }; // ok — spread is not fresh → no excess check

// assertion disables freshness for that line
const asserted: Point = { x: 1, y: 2, z: 99 } as Point; // bad — silenced the typo guard

// good — keep the literal fresh when you WANT the guard
const good1: Point = { x: 1, y: 2 }; // fresh → checked → ok
connect({ host: "localhost", port: 5432 }); // fresh → checked → ok

// good — when excess is INTENTIONAL, type the intermediate variable instead of asserting the literal
const typedVar: Options = { host: "localhost", port: 5432 }; // annotation checks the variable itself
connect(typedVar); // ok — excess never entered, no lint needed

// fresh return also re-triggers — useful diagnostic anchor
function makeOpts(): Options {
  return { host: "localhost", port: 5432 }; // fresh return → checked → ok
  // return { host: "localhost", portt: 5432 }; // would error here too — fix at the source
}
```

```typescript
// bad — canonical production leak: freshness bypass via variable + 'as' hides a typo until runtime
type Theme = { primary: string; secondary?: string };
function applyTheme(t: Theme): void {
  // reads t.primary / t.secondary — typo'd 'seconday' is never read
  console.log(t.primary, t.secondary);
}
const config = { primary: "#000", seconday: "#fff" }; // typo — no freshness yet
applyTheme(config as Theme); // no error — 'seconday' silently ignored, secondary undefined at runtime
// fix — avoid 'as' on literals; type the variable or keep literal fresh:
// const configFixed: Theme = { primary: "#000", secondary: "#fff" }; // error flags typo immediately
// applyTheme({ primary: "#000", secondary: "#fff" }); // fresh → flagged if typo
```

**Common confusion** — "excess property error means my object is not assignable" — no, it *is* assignable; the error is a heuristic lint for literals, not a type-system rejection (the same members via a variable are assignable). "Freshness applies everywhere" — only literals at assignment/call/return sites; variables, spreads, `as` assertions, and generic-constrained passes bypass it. "I should always `as Target` to silence the error" — that silences the typo guard for that line and every future typo on that line; prefer the §3 escapes that preserve checking.

**Performance note** — freshness checking is O(k) over literal member count — negligible. The performance cost is indirect: workarounds that materialize many intermediate variables to dodge freshness increase the number of distinct literal types in the hover/type graph, which can bloat language-server memory in large codebases — still small, but visible in 10k-file monorepos. No runtime cost — freshness is purely a checker heuristic and erases entirely.

**Mentor note** — demo the three-way comparison in one block — fresh literal → error, variable → silent, `as` → silent — side-by-side. Students who see all three stop treating "excess property" as nominal-vs-structural and recognize it as a literal-site lint. Review check: given `const x = { a: 1, b: 2, typoC: 3 }; f(x)` ask whether `f` sees the typo — answer is *no* (no freshness). Exercise: have them fix a leaked `portt` by typing the intermediate variable (`const opts: Options = ...`) rather than adding `as`.

### 3) **Sealing the leak** (when to use `satisfies`, a wider target, or an explicit annotation — keep literals honest without widening callers)

**Definition** — "sealing the leak" means choosing a fix that keeps the freshness typo guard *and* preserves literal narrowness for callers — instead of smuggling excess through a stale variable or silencing it with `as`. Three idiomatic tools — `satisfies`, a wider target type, and an explicit annotation on the binding — each seal a different leak shape.

**What problem it solves / history** — the two naïve fixes both hurt: (1) routing a literal through an untyped variable drops freshness (typo leaks), and (2) `as Target` widens the literal to exactly `Target` and disables checking (typo and literal information both lost). `satisfies` (added TS 4.9, idiomatic as of 5.9 era) was introduced precisely for this gap — it *checks* that the literal satisfies `Target` while *preserving* the source's literal types for downstream inference. The wider-target and explicit-annotation patterns predate it and remain correct for their own shapes.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to this decision table:

| Leak shape | Fix | Why |
|---|---|---|
| Config / route table literal where callers should keep literals (`"get"` not `string`) | `const route = { method: "get" } satisfies Route` | Checks `Route`, preserves `"get"` literal — no widening, no `as` |
| Caller intentionally carries extra members to a narrow consumer | Pass via typed variable or widen the consumer's param (`Point & Record<string, unknown>`) — do not add excess to the target globally | Keeps structural flow honest; documents intent |
| Intermediate variable that should itself be validated | `const opts: Options = { host, port }` — annotate the binding | Typo caught at the binding, not three calls later |

- Use `satisfies` when the *literal* is the source of truth and you want checking without losing its inferred type (route configs, theme objects, test fixtures, `as const` alternatives).
- Use a wider target (`Options & { debug?: boolean }` or `Point & { label?: string }`) when the consumer genuinely accepts extra — widen the narrow consumer explicitly rather than weakening the literal site.
- Use an explicit annotation on the *variable* when the variable is the source of truth — the annotation re-enables checking that freshness would have provided.

All three erase — `satisfies`, annotations, and `&` on types leave no emit (erasable — safe under `--erasableSyntaxOnly`).

**Runnable example** — three seals, each with a bad counterpart (good vs bad, `tsc --strict`):

```typescript
// --- Seal 1: satisfies — check without widening (TS 4.9+, idiomatic 5.9 era) ---
type Route = { path: string; method: "get" | "post" };

// bad — 'as' widens and silences: literal becomes Route, "get" widens to string, typo not caught
const routeBad = { path: "/users", method: "get", extra: true } as Route; // no error — extra smuggled, literal lost
// typeof routeBad.method is string (widened) — downstream switch on "get"|"post" loses exhaustiveness

// bad — untyped variable leaks freshness, typo survives
const routeLeaky = { path: "/users", methd: "get" }; // typo 'methd' — no target yet → no error
// const _check: Route = routeLeaky; // would error, but you forgot to add it

// good — satisfies checks Route while preserving literal narrowness
const routeGood = { path: "/users", method: "get" } satisfies Route; // checks → ok, method stays "get"
type MethodOfGood = typeof routeGood.method; // "get" — preserved for discriminated narrowing

// good — satisfies still CATCHES typos/excess at the literal site
// const routeTypo = { path: "/users", methd: "get" } satisfies Route; // error TS1360: 'methd' not in Route
// const routeExcess = { path: "/users", method: "get", extra: true } satisfies Route; // error TS2353

// good — as const + satisfies for deep readonly config (alternative when you want readonly + literals)
const routeFrozen = { path: "/users", method: "get" } as const satisfies Route; // readonly "get"

// --- Seal 2: wider target — consumer honestly accepts extra ---
type Point = { x: number; y: number };

// bad — consumer is narrow but caller silently carries extra via variable; intent is undocumented
const labeledPoint = { x: 1, y: 2, label: "origin" };
function drawNarrow(p: Point): void { console.log(p.x, p.y); }
drawNarrow(labeledPoint); // ok via width — but future reader can't tell if extra is intentional

// good — widen the CONSUMER when extra is intentional and documented
type LabeledPoint = Point & { label?: string };
function drawLabeled(p: LabeledPoint): void {
  console.log(p.x, p.y, p.label ?? "");
}
drawLabeled({ x: 1, y: 2, label: "origin" }); // fresh literal → checked against LabeledPoint → ok
drawLabeled({ x: 1, y: 2 }); // also ok — label is optional
// drawLabeled({ x: 1, y: 2, extra: true }); // error — still catches unintended excess

// --- Seal 3: explicit annotation on the binding — validate the variable itself ---
type Options = { host: string; port?: number };
function connect(opts: Options): void {}

// bad — untyped binding + 'as' at call site moves the check away from the typo
const optsLeaky = { host: "localhost", portt: 5432 }; // no check here
connect(optsLeaky as Options); // no error here either — bug shipped

// good — annotate the binding; typo caught where it is written
const optsGood: Options = { host: "localhost", port: 5432 }; // ok — checked at declaration
connect(optsGood);
// const optsBad: Options = { host: "localhost", portt: 5432 }; // error TS2353 at declaration — caught early

// good — keep literal fresh at the call site when there is no intermediate variable
connect({ host: "localhost", port: 5432 }); // fresh → checked → ok
```

**Common confusion** — "`satisfies` changes the variable's type to `Target`" — no, `satisfies Target` keeps the *source* literal type and only checks assignability; `as Target` forces the variable to `Target` and widens away literals. "`satisfies` has runtime cost or emit" — none — it erases like every annotation; it is not a validator (use `zod`/`valibot` at boundaries for runtime checks). "Wider target means `any`" — no, widen with `& { extra?: T }` or a specific union — never `any`/`unknown` — so excess is still bounded.

**Performance note** — all three seals are checker-only — zero runtime allocation, zero dispatch, zero GC. `satisfies` can *reduce* checker work versus `as` chains because it preserves literal types that enable contextual narrowing without extra generic instantiation. The only measurable cost is a slightly larger type graph when many literals each retain distinct literal unions via `satisfies` — still negligible; measure `tsc --extendedDiagnostics` if you retain thousands of route literals in one file, and split into modules if check time grows.

**Mentor note** — teach the decision as "where is the source of truth?" — if the literal is the truth, `satisfies` at the literal site; if the consumer genuinely accepts more, widen the consumer; if the variable is the truth, annotate the variable. Review checklist: every `as Target` on a literal must have a comment explaining what proof the checker cannot see — otherwise replace with `satisfies Target` (typo guard) or an annotated binding (early failure). Exercise: give a PR with three `as Route` literals and ask students to convert each to the correct seal — one becomes `satisfies`, one becomes an annotated `const`, one requires widening the function param — discuss why the same syntax (`as`) was wrong in three different ways.
