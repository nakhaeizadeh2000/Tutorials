## 1.1. Object types — structural shape and excess property checks

An object contract describes the members a consumer needs. A drawing function can accept a colored point without using its color, while a connection configuration should catch a misspelled port. Structural compatibility and excess-property checks address those different needs. This lesson applies the [core assignability model](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>) to complete object examples.

Examples were checked with TypeScript 7.0.2 and run with Node 20.20.2 on 2026-10-13. Save the three named files in a new directory without a `tsconfig.json`. For each file, run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir out FILE.ts`, then `node out/FILE.js`, replacing FILE with its name. All three programs compile and run successfully as shown. Test intentional errors separately with `tsc --strict --noEmit FILE.ts` after uncommenting only the indicated line.

### 1) **Structural shape and real values**

`Point` requires numeric x and y. A variable with those members and an additional color can satisfy it. Nested members must also satisfy their own contracts: a numeric host fails even though the outer property is still named server. [Type compatibility](https://www.typescriptlang.org/docs/handbook/type-compatibility.html) describes this recursive comparison.

Save `shapes.ts`:

```typescript
export {};
type Point = { x: number; y: number };
type ColoredPoint = Point & { color: string };
function draw(point: Point): void {
  console.log(`point: ${point.x}, ${point.y}`);
}
const rich: ColoredPoint = { x: 10, y: 20, color: "red" };
draw(rich);
const withExtra = { x: 1, y: 2, z: 3 };
const narrow: Point = withExtra;
console.log("same object:", narrow === withExtra, "z" in narrow); // true true

type Config = { server: { host: string } };
type RichConfig = { server: { host: string; port: number } };
const richConfig: RichConfig = { server: { host: "localhost", port: 5432 } };
const config: Config = richConfig;
console.log("nested:", config.server.host, richConfig.server.port); // localhost 5432
// const wrong: Config = { server: { host: 123 } }; // uncomment: TS2322

type UserId = string;
type OrderId = string;
function recordUserDeletion(id: UserId): string { return `accepted: ${id}`; }
const orderId: OrderId = "order-1";
console.log(recordUserDeletion(orderId)); // accepted: order-1
// The example records a string; it does not delete an external resource.
```

The output is `point: 10, 20`, `same object: true true`, `nested: localhost 5432` and `accepted: order-1`. Assigning to Point changes the checker view without cloning the object or stripping z. The nested configuration is initialized, so its property read has a real runtime value. The ID aliases both mean string, so the recorder accepts the order ID; their names alone provide no distinction. Use a [brand](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>) when the distinction belongs in the contract.

Uncomment the wrong-host line to observe TS2322. This is incompatible member typing rather than an extra-member complaint. An ambient `declare` would describe a value supplied elsewhere, so it is inappropriate as a substitute for these runtime initializers.

### 2) **Where excess-property checks apply**

A directly written object literal checked against Options catches the portt typo. Passing the richer variable succeeds because it has the required host; the optional port can be absent. That distinction is documented in [Object Types](https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks). The consumer reads port, so the typo produces the fallback 80.

Spread needs a more precise prediction: portt inherited from the spread passes in this example, while portt explicitly written alongside the spread is checked and rejected. Adding a spread does not disable every excess-property check in the resulting literal.

Save `freshness.ts`:

```typescript
export {};
type Options = { host: string; port?: number };
function connect(options: Options): void {
  console.log(options.host, options.port ?? 80);
}
const viaVariable = { host: "localhost", portt: 5432 };
connect(viaVariable); // localhost 80: portt is never read
const inherited: Options = { ...viaVariable, host: "localhost" };
connect(inherited); // localhost 80: spread copied the typo
// const written: Options = { ...viaVariable, portt: 1234 }; // uncomment: TS2561
// connect({ host: "localhost", portt: 5432 }); // uncomment: TS2561

const checked: Options = { host: "localhost", port: 5432 };
connect(checked); // localhost 5432
const checkedLiteral = { host: "localhost", port: 5432 } satisfies Options;
connect(checkedLiteral); // localhost 5432
// const typo = { host: "localhost", portt: 5432 } satisfies Options; // TS2561
```

The four output lines are `localhost 80`, `localhost 80`, `localhost 5432` and `localhost 5432`. Uncomment the written, direct-call or satisfies-typo line separately: each reports TS2561 on this compiler, suggesting port. The annotation and satisfies expression catch mistakes where the good literal is created; the later call receives a correctly named port.

Fix the spelling or adjust the contract if the property is genuinely supported. Routing through a variable simply to remove an error hides evidence of a bug. These checks concern declared program structure; external data still needs a [runtime boundary check](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>). `exactOptionalPropertyTypes` refines optional assignments but does not validate incoming objects.

### 3) **Choosing an annotation, satisfies or a broader contract**

An annotation makes Route the binding's declared contract. An assertion tells the checker to treat the expression as Route, without proving its fields at runtime. `satisfies` checks the expression against Route without replacing the resulting expression type with Route; contextual typing still participates. Here, asserted.method and annotated.method have the finite union `"get" | "post"`, while checked.method has the singleton `"get"`. Neither of the first two is an arbitrary string. The path property in the satisfies result is still string, so this is not a universal literal-preservation rule. [TypeScript 4.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator) introduces the operator; the live equality probes below check this particular result.

Save `contracts.ts`:

```typescript
export {};
type Route = { path: string; method: "get" | "post" };
const asserted = { path: "/users", method: "get", extra: true } as Route;
const checked = { path: "/users", method: "get" } satisfies Route;
const annotated: Route = { path: "/users", method: "get" };
const readonlyRoute = { path: "/users", method: "get" } as const satisfies Route;
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type AssertedMethod = Expect<Equal<typeof asserted.method, "get" | "post">>;
type CheckedMethod = Expect<Equal<typeof checked.method, "get">>;
type AnnotatedMethod = Expect<Equal<typeof annotated.method, "get" | "post">>;
type CheckedPath = Expect<Equal<typeof checked.path, string>>;
console.log("methods:", asserted.method, checked.method, annotated.method); // get get get
console.log("assertion retained:", "extra" in asserted); // true
console.log("runtime frozen:", Object.isFrozen(readonlyRoute)); // false
// const exact: "get" = asserted.method; // uncomment: TS2322
// const excess = { path: "/users", method: "get", extra: true } satisfies Route; // TS2353

type Point = { x: number; y: number };
type LabeledPoint = Point & { label?: string };
function drawLabeled(point: LabeledPoint): void {
  console.log("label:", point.label ?? "unlabeled");
}
drawLabeled({ x: 1, y: 2, label: "origin" }); // label: origin
drawLabeled({ x: 1, y: 2 }); // label: unlabeled
```

The output is `methods: get get get`, `assertion retained: true`, `runtime frozen: false`, `label: origin` and `label: unlabeled`. The equality assertions compile, distinguishing static precision from unchanged runtime strings. Uncomment exact to see TS2322 because the asserted union cannot satisfy a singleton target. Uncomment excess to see TS2353 at the checked literal. The assertion retained the extra runtime field rather than removing it; `as const` added a readonly contract rather than a runtime freeze.

Use an annotation when callers should see the declared contract; use satisfies when checking the local expression and retaining its inferred detail serves later code. Give a consumer a broader contract when it actually reads an additional member, as drawLabeled does. A consumer that only reads x and y can continue accepting richer variables through structural typing; it does not need every caller's incidental fields in its signature. The original [Learning TypeScript explanation](https://www.learningtypescript.com/articles/the-satisfies-operator) provides a useful annotation-versus-inference comparison; verify the exact properties for your own target.

### 4) **Common confusion**

A narrow type view leaves the original object intact. A spread can carry unchecked inherited extras while directly written members still receive checks. An assertion to a union can lose singleton precision while preserving that union, and satisfies is a compile-time check rather than a parser. In each case, distinguish what the checker knows from the data the consumer actually reads.

### 5) **Performance note**

Object type declarations, assertions and satisfies checks do not add runtime validation. The examples still allocate their ordinary objects, and object spread creates a new object containing copied properties. That copy differs from the reference assignment in shapes.ts. No checking-time complexity formula, member-count threshold or speed comparison is established here. If a real type graph is slow, follow the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before choosing a remedy.

### 6) **Mentor note**

Ask the learner to predict the two port defaults, then add an explicitly written portt beside the spread. A sound explanation identifies which member was copied and which was checked. Next ask what changes when as Route becomes satisfies Route: the target union and singleton differ statically, while both initial runtime strings remain get. Have the learner choose an annotation, satisfies or LabeledPoint for a new configuration and justify the consumer's actual needs.
