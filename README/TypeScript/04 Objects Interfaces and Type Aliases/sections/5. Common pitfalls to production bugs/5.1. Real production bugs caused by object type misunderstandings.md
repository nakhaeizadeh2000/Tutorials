## 5.1. Real production bugs caused by object type misunderstandings

Four incidents that shipped to production from object-type misconceptions — each still compiles under `tsc --strict` in its *bad* form and is caught only by the *good* form next to it. As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS) all object-type syntax below is erasable and costs nothing at emit — the bugs cost incidents, not bytes.

---

### 1) **Freshness escape via `as`** (excess property smuggled into a narrower target and surfacing three calls later)

**Definition** — *freshness* (excess-property check) is the checker lint that fires only on a fresh literal written directly at a typed assignment, call argument, or `return` — `const p: Point = { x: 1, y: 2, z: 3 }` errors `TS2353` even though `{ x, y, z }` is structurally assignable to `Point`. `as Target` disables that lint for the line it appears on and forces the value to `Target` — extra, typo'd, or misspelled keys ride through silently and are read as `undefined` three calls later.

**What problem it solves / history** — JavaScript objects are width-subtyped — `{ x, y, color }` flows into `{ x, y }` by design (see [1.1. Object types structural shape and excess property checks](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>)). Without freshness, `connect({ host: "db", portt: 5432 })` for `Options = { host: string; port?: number }` would pass — `portt` is just "extra" — and `port` would be `undefined` at runtime. Freshness (TS 1.6 era) added the literal-site lint to catch that typo, but left variable flow untouched so intentional width still works. `as` was the escape that laundered the same typo — `const v = { host, portt: 5432 }; connect(v as Options)` — and `satisfies` (TS 4.9, idiomatic as of 5.9 era) was introduced precisely to say "check without widening and without silencing".

**Modern guidance** — as of TypeScript 5.9 era:

- **Never `as Target` a fresh or near-fresh literal** — keep the literal fresh (`connect({ host, port: 5432 })`) or type the binding (`const opts: Options = { host, port: 5432 }`) so freshness fires where the typo is written.
- **Literal is the source of truth** → `satisfies Target` — `const payload = { currency: "USD", amount: 100 } satisfies Payment` checks `Payment`, preserves `"USD"` literal for discriminant narrowing, and still errors on `curency`.
- **Consumer honestly accepts extra** → widen the consumer (`Point & { label?: string }`) — document intent instead of silencing the literal.
- **Boundary that needs validation** → `zod`/`valibot` then `satisfies` — `as` never replaces a runtime parse.

**Runnable example** — incident: checkout `curency` typo laundered by `as`, surfaced three calls later at Stripe (`tsc --strict` — error lines commented so the fence compiles):

```typescript
// bad — freshness escape via as: typo rides to Stripe, three calls later as undefined
type Payment = { userId: string; amount: number; currency: "USD" | "EUR" };

function toStripe(p: Payment): string {
  // invariant: currency is always present — downstream trusts Payment
  if (p.currency !== "USD" && p.currency !== "EUR") throw new Error(`unsupported currency: ${p.currency}`);
  return `${p.amount} ${p.currency}`;
}
function charge(p: Payment): string {
  return toStripe(p); // call 2 — still typed as Payment
}
function checkoutBad(rawUserId: string): string {
  // incident: typo curency — no freshness because `as unknown as Payment` silences the literal site
  const payload = { userId: rawUserId, amount: 100, curency: "USD" } as unknown as Payment; // ok — double assert launders: excess not reported, curency kept, currency missing
  return charge(payload); // call 3 — throws 'unsupported currency: undefined' in production
}
console.log(checkoutBad("u_1")); // throws at runtime — bug shipped

// good — keep freshness: satisfies checks and preserves literal, typo caught at the literal line
function checkoutGood(rawUserId: string): string {
  const payload = { userId: rawUserId, amount: 100, currency: "USD" } satisfies Payment; // checks Payment, keeps "USD" literal
  // const typo = { userId: rawUserId, amount: 100, curency: "USD" } satisfies Payment; // error TS2353: 'curency' does not exist in type 'Payment'
  return charge(payload); // ok — currency is "USD"
}
console.log(checkoutGood("u_1")); // 100 USD

// good — alternatives that also seal: annotate the binding or keep literal fresh at the call site
const optsTyped: Payment = { userId: "u_2", amount: 50, currency: "EUR" }; // error flags curency here, not three calls later
// const optsTypo: Payment = { userId: "u_2", amount: 50, curency: "EUR" }; // error TS2353 at declaration
console.log(charge(optsTyped)); // 50 EUR
console.log(charge({ userId: "u_3", amount: 10, currency: "USD" })); // fresh literal at call — freshness fires
```

```typescript
// good — spread also drops freshness: type the spread source, don't as the result
type Theme = { primary: string; secondary?: string };
function applyTheme(t: Theme): void { console.log(t.primary, t.secondary); }

const rawTheme = { primary: "#000", seconday: "#fff" }; // typo — no target yet → no freshness
// applyTheme(rawTheme as Theme); // bad — laundered, secondary undefined at runtime

// good — satisfies on the literal before spread, or annotate the source
const themeFixed = { primary: "#000", secondary: "#fff" } satisfies Theme;
applyTheme({ ...themeFixed, primary: "#111" }); // spread of a checked source — still honest
// const themeTypo = { primary: "#000", seconday: "#fff" } satisfies Theme; // error TS2353 — caught
console.log(themeFixed.secondary); // #fff
```

**Common confusion** — "excess-property error means not assignable" — it is assignable; the error is a literal-site lint, not a structural rejection — `const v = { x: 1, y: 2, z: 3 }; const p: Point = v` proves width still allows it. "`as` is the same as `satisfies` but shorter" — `as` disables excess checks and widens (`"USD"` → `string`); `satisfies` keeps both checks and literals. "Routing through a variable proves the object is clean" — the variable *removes* the lint; only a typed binding or fresh literal proves it.

**Performance note** — freshness is one checker pass over literal members — `O(k)` for `k` keys, compile-time only, zero emit, zero allocation, zero dispatch. `as` and `satisfies` both erase — zero runtime cost. Indirect cost is incident time: one `as` on a literal that hides a typo costs a Stripe 500 or DB-misconnect — measure `grep -R " as Payment" --include="*.ts" | wc -l` before measuring microseconds.

**Mentor note** — demo the three-way comparison in one reviewer exercise: `const p: Payment = { userId: "u", amount: 1, curency: "USD" }` (error) vs `const v = { userId: "u", amount: 1, curency: "USD" }; const p: Payment = v` (silent) vs `const r = { userId: "u", amount: 1, curency: "USD" } as Payment` (silent) vs `const ok = { userId: "u", amount: 1, currency: "USD" } satisfies Payment` (error on typo, literal kept). Require every `as Target` on a literal in PRs to carry `// proof:` or be replaced — `grep -R " as [A-Z]" --include="*.ts" src/ | grep -v " as const"` should be near zero.

### 2) **`readonly` without `freeze`** (`readonly` silenced a write at compile time but the runtime mutation still landed)

**Definition** — `readonly prop: T` (or `readonly T[]`, `Readonly<T>`, `as const`) is a *type-level* lens — the checker errors on `cfg.port = 9` through a `readonly` view, but the emitted JavaScript has no `writable: false` descriptor. At runtime the object is still a plain mutable bag — a mutable alias, an `as` cast, `(cfg as any).port = 9`, or plain JavaScript in another bundle mutates it — unlike `Object.freeze` which installs non-writable, non-configurable descriptors (shallow) and, in strict mode, throws on write.

**What problem it solves / history** — object properties are mutable by default, mirroring JavaScript. `readonly` (TS 2.0) let interfaces express "this field is read through this view" without paying a runtime cost — `interface Config { readonly id: string }` enforces intent after construction. `as const` (TS 3.4) added deep `readonly` + literal for config tables. Neither added a runtime fence — `Object.freeze` (ES5.1, 2009) is the runtime counterpart, shallow by default. Teams that treated `readonly` as a lock shipped shared default configs (`DEFAULTS`) that were cloned by reference and mutated through an untyped helper — every tenant after the first saw the first tenant's overrides.

**Modern guidance** — as of TypeScript 5.9 era:

| Need | Checker (`readonly`) | Runtime (`Object.freeze` / `deepFreeze`) | Pair them? |
|---|---|---|---|
| Prevent accidental write in typed code | yes — `c.id = "x"` → `TS2540` | no — erased | for API params and return views |
| Prevent mutation from JS / `as any` / cross-bundle | no — `(c as any).id = "x"` succeeds | yes — strict throws, sloppy silent-no-op | for module constants and shared defaults |
| Deep intent (nested `meta.retries`) | per-property `readonly` or `as const` on the literal | recursive `deepFreeze` helper | mark every level `readonly` or `as const` + freeze once |

- **Public view that must not be reassigned** → `readonly` on the type.
- **Module constant / shared default / tenant config that must not drift at runtime** → `as const` on the literal **plus** `Object.freeze` (or deep-freeze) on the value — checker + runtime agree. Both remain erasable-safe (`--erasableSyntaxOnly`).
- **`readonly` is shallow** — `readonly meta: { retries: number }` blocks `c.meta = {...}` but not `c.meta.retries = 9`; write `readonly meta: { readonly retries: number }` or `as const`.

**Runnable example** — incident: `DEFAULTS` marked `readonly` but mutated through a helper alias, poisoning every request after the first (`tsc --strict`):

```typescript
// incident — readonly silenced the direct write, but alias + runtime still mutated the shared default
type Config = { readonly apiUrl: string; readonly tags: readonly string[]; meta: { retries: number } };
type DeepConfig = { readonly meta: { readonly retries: number } };

const DEFAULTS: Config = { apiUrl: "https://api.prod", tags: ["web"], meta: { retries: 3 } };
// DEFAULTS.apiUrl = "https://api.evil"; // error TS2540 — checker blocks direct write (good)
console.log(Object.getOwnPropertyDescriptor(DEFAULTS, "apiUrl")?.writable); // true — still writable at runtime!

// bad — escape through mutable alias (single extra `as` bypasses the view)
const alias = DEFAULTS as { apiUrl: string; tags: string[]; meta: { retries: number } };
alias.apiUrl = "https://api.evil"; // ok — alias is mutable
console.log(DEFAULTS.apiUrl); // https://api.evil — mutation landed, every tenant after this sees evil url

// bad — shallow readonly: nested mutation not blocked
DEFAULTS.meta.retries = 99; // ok — meta itself is mutable (shallow surprise)
console.log(DEFAULTS.meta.retries); // 99 — poisoned

// shallow inner not enough:
const deep: DeepConfig = { meta: { retries: 3 } };
// deep.meta.retries = 99; // error TS2540 — inner readonly now blocks
console.log(deep.meta.retries); // 3

// any also bypasses:
(DEFAULTS as any).apiUrl = "https://api.prod"; // restore for demo — any bypasses checker
console.log(DEFAULTS.apiUrl); // https://api.prod — checker never saw the write
```

```typescript
// good — pair type-level readonly with runtime freeze for shared constants
const FROZEN_DEFAULTS = { apiUrl: "https://api.prod", tags: ["web"] } as const;
Object.freeze(FROZEN_DEFAULTS);
console.log(Object.isFrozen(FROZEN_DEFAULTS)); // true
console.log(Object.getOwnPropertyDescriptor(FROZEN_DEFAULTS, "apiUrl")?.writable); // false
// (FROZEN_DEFAULTS as { apiUrl: string }).apiUrl = "x"; // strict: TypeError: Cannot assign to read only property; sloppy: silent no-op
console.log(FROZEN_DEFAULTS.apiUrl); // https://api.prod — runtime fence held

// good — factory never exposes the frozen default by reference; returns a shallow copy
function getDefaults(): { apiUrl: string; tags: readonly string[] } {
  return { ...FROZEN_DEFAULTS, tags: [...FROZEN_DEFAULTS.tags] };
}
const a = getDefaults();
(a as { apiUrl: string }).apiUrl = "https://tenant-a"; // mutates the copy, not the frozen source
console.log(FROZEN_DEFAULTS.apiUrl); // https://api.prod — source untouched
console.log(a.apiUrl); // https://tenant-a

// good — as const for deep literals + deepFreeze helper when nesting matters
const THEME = { colors: { primary: "#000" } } as const; // deep readonly
// THEME.colors.primary = "#fff"; // error TS2540 — deep readonly blocks
console.log(THEME.colors.primary); // #000
function deepFreeze<T extends object>(o: T): T {
  Object.freeze(o);
  for (const v of Object.values(o)) if (v && typeof v === "object") deepFreeze(v as object);
  return o;
}
const deepFrozen = deepFreeze({ meta: { retries: 3 } } as const);
console.log(Object.isFrozen(deepFrozen.meta)); // true
```

**Common confusion** — "`readonly` is `Object.freeze`" — `readonly` erases, `freeze` installs descriptors; need both for constants that cross an untyped boundary. "`readonly` is deep" — shallow; every nested level needs its own `readonly` or `as const` / `ReadonlyDeep`. "`as const` does the runtime freeze" — type-only as well; pair with `Object.freeze`. "`Object.freeze` is deep" — shallow by default; use recursive helper for nested bags.

**Performance note** — `readonly` has zero emit, zero allocation, zero GC, zero dispatch — purely a checker gate. `Object.freeze` has runtime cost — per-object descriptor walk plus an engine shape transition to non-extensible (faster reads, slower future writes — engines optimize for "shape never changes"). Freeze module constants once at load (linear startup cost, justified); never freeze per-request bags in a hot path — each future write then branches on `IsFrozen`. Checker cost of `readonly` is one assignability check per write site; `freeze` cost is one-time `O(members)` per frozen object.

**Mentor note** — run the two-layer demo live: `cfg.apiUrl = "x"` fails the checker, then show `Object.getOwnPropertyDescriptor(cfg, "apiUrl").writable === true` and `(cfg as any).apiUrl = "x"` succeeds — the "aha" that `readonly` is not a lock. PR gate: every `export const DEFAULTS = { ... }` that is conceptually a constant is *both* `as const` (type) and `Object.freeze` (runtime) — add CI `grep -R "export const.*= {" --include="*.ts" src/ | grep -v "as const" | grep -v "freeze"` as a lint. Exercise: give `type State = { readonly items: readonly Item[]; meta: { count: number } }` and ask what `state.meta.count = 2` does — answer: compiles (shallow), which is the bug to fix.

### 3) **Index signature widens exactness** (dictionary type accepted unknown keys and bypassed discriminant checks)

**Definition** — an index signature `[key: string]: T` (or `Record<string, T>` — the mapped-type alias for the same shape) means "any string key is allowed with value `T`" plus any explicit members, which must be compatible with `T`. The type becomes *open* — excess-property typo guards weaken, autocomplete degrades, `keyof` widens toward `string`, and a `kind` discriminant that should be `"click" | "hover"` collapses to `string` so `"clikc"` and `"CLICK"` are accepted.

**What problem it solves / history** — before `Map` (ES2015) and mapped types (TS 2.1), index signatures were the only way to type dictionaries — `const cache: { [url: string]: Response }`. Template-literal `Record<`on${string}`, Handler>` (TS 4.4) and `satisfies` with exact finite shapes are the modern replacements for *closed* key sets. Index signatures remain correct for *truly* open bags — plugin registries, parsed JSON with unknown keys — but became the default for finite shapes by habit, swallowing typos like `alcie` / `onClikc`.

**Modern guidance** — as of TypeScript 5.9 era:

| Key set | Prefer | Why |
|---|---|---|
| Finite known keys (`"alice"`, `"onClick"`, `"click"`) | `{ alice: number; bob: number }` or `Record<"alice" | "bob", number>` + `satisfies` | Exact — typo `alcie` / `onClikc` errors `TS2353` / `TS1360` |
| Open bag, uniform values | `Record<string, number>` — narrowest that fits | Reads as "dictionary" intent, still open deliberately |
| Open bag with known spine + extras | `type T = { id: string } & Record<string, unknown>` | Known props stay typed, extra bounded to `unknown` |
| Constrained pattern (`on*`) | `Record<`on${string}`, Handler>` | Pattern-checked keys |
| Runtime map, non-string / `__proto__`-safe | `Map<string, T>` | No prototype pollution, preserves key types |

- Do not mix incompatible known members into an index signature — `type Bad = { [k: string]: number; name: string }` errors `TS2411`; use intersection `& Record<...>` when `name` should stay `string` while extra is `number | string`.
- For discriminant unions, keep `kind` as a *literal union* (`kind: "click" | "hover"`) without an index signature; a `[key: string]: unknown` on the union floods the discriminant to `string`.

**Runnable example** — incident: dictionary + discriminant widened by index signature; typos `alcie` and `clikc` bypassed checks, good fix restores exactness (`tsc --strict`):

```typescript
// bad — index signature swallows typos: any key is valid, discriminant widens to string
type ScoresDict = { [key: string]: number };
const scoresBad: ScoresDict = { alcie: 42, bob: 17 }; // ok — typo alcie accepted (any key valid)
console.log(scoresBad["alcie"]); // 42 — bug: leaderboard misses alice

// bad — index signature on event floods the discriminant: "clikc" accepted, exhaustive switch broken
type LooseEvent = { kind: string; [key: string]: unknown; x?: number; y?: number };
function handleLoose(e: LooseEvent): string {
  if (e.kind === "click") return `click ${e.x}`;
  if (e.kind === "hover") return "hover";
  return `unknown ${e.kind}`; // now reachable — "clikc" falls here, no checker error
}
console.log(handleLoose({ kind: "clikc", x: 10 })); // unknown clikc — typo shipped, should have been click branch

// bad — keyof floods too: not "alice" | "bob"
type Dict = { [key: string]: number; id: number };
type DictKeys = keyof Dict; // string | number — not "id" literal
const _k: DictKeys = "anyStringIsOk"; // accepted — exactness lost
console.log(_k);

// good — finite keys + satisfies keeps exactness and discriminant narrow
type ExactScores = { alice: number; bob: number };
const scoresGood = { alice: 42, bob: 17 } satisfies ExactScores;
type ScoreKeys = keyof typeof scoresGood; // "alice" | "bob" — literal union preserved
const kGood: ScoreKeys = "alice"; // ok — typo would error
// const typoExact = { alcie: 42, bob: 17 } satisfies ExactScores; // error TS2353 — typo caught
console.log(scoresGood.alice, kGood); // 42 alice

// good — discriminated union with literal discriminant, exhaustive, no index signature
type Click = { kind: "click"; x: number };
type Hover = { kind: "hover"; y: number };
type AppEvent = Click | Hover;
function handleExact(e: AppEvent): string {
  switch (e.kind) {
    case "click": return `click ${e.x}`; // narrowed to Click
    case "hover": return `hover ${e.y}`;
    default: { const _ex: never = e; return _ex; } // exhaustiveness — adding a variant forces a case
  }
}
// const badEvent: AppEvent = { kind: "clikc", x: 10 }; // error TS2322 — "clikc" not in "click" | "hover"
console.log(handleExact({ kind: "click", x: 10 })); // click 10

// good — open bag with known spine via intersection (keeps id typed, extra bounded)
type NamedScores = { name: string } & Record<string, number | string>;
const named: NamedScores = { name: "leaderboard", alice: 42, bob: 17 };
console.log(named.name.toUpperCase()); // LEADERBOARD

// good — patterned keys with template-literal Record
type Handlers = Record<`on${string}`, () => void>;
const handlers: Handlers = { onClick: () => console.log("click"), onHover: () => console.log("hover") };
handlers.onClick();
// handlers.click = () => {}; // error — "click" doesn't match `on${string}`
console.log(Object.keys(handlers).length); // 2

// good — Map for user-supplied keys (no __proto__ pollution)
const byId = new Map<string, number>([["alice", 42]]);
byId.set("__proto__", 1); // safe — Map key, not prototype
console.log(byId.get("__proto__")); // 1
```

**Common confusion** — "`Record<string, T>` and `{ [k: string]: T }` differ" — `Record<string, T>` *is* the index signature via `{ [P in K]: T }`; difference is readability and template-literal composition. "Index signatures are exact / catch typos" — opposite — any key is valid, so typos are invisible; use exact object type + `satisfies` for finite keys. "`kind: string` with an index signature is still a discriminant" — widened to `string` — never exhaustive; keep `kind: "click" | "hover"` without the signature. "`Map` and `Record<string, T>` are interchangeable" — `Map` preserves key types (including objects), has `size`/iteration, avoids `__proto__` pollution; `Record` is a plain object with string keys and prototype chain.

**Performance note** — index signatures widen `keyof` to `string | number` and disable per-property excess checks — checker does *less* per-property validation (marginally faster for huge literals) but forces downstream `Object.entries` to `(string, T)[]` with no key narrowing, so every consumer pays with `in` checks and broader control-flow sets. An open `Record<string, unknown>` iterated in a hot loop boxes to `(string, unknown)[]` and defeats literal-key narrowing; a closed `Record<"alice" | "bob", number>` keeps keys as a union and enables direct property loads (`O(1)`). Measure `tsc --extendedDiagnostics` `instantiations` if a file with a large dictionary dominates check time — split finite vs open bags to shrink the graph.

**Mentor note** — ask "is the key set *finite and known at author time* or *open and user-supplied*?" — finite → exact object type + `satisfies`; open uniform → `Record<string, T>`; spine + extra → `Known & Record<string, unknown>`; patterned → template-literal `Record`. Review flag: any `[key: string]: any` — replace `any` with `unknown` and bound the value. Exercise: give `type User = { name: string; [k: string]: string }` and ask why `"bob"`-style typo is hidden and why `name: string` must be compatible with the index — fix is `{ name: string } & Record<string, unknown>` if `name` should stay `string` while extra stays bounded.

### 4) **Merged interface collision** (ambient augmentation added an optional property that made a required property effectively optional across the app)

**Definition** — *declaration merging* lets two `interface` blocks with the same name in the same scope combine into one logical type — members union, `keyof` widens, `never` on conflicts (`TS2717`) is the guard. *Ambient augmentation* (`declare global { interface Window { ... } }`, `declare module "pkg" { interface Request { ... } }`) does the same across files — once a `.d.ts` is included in `tsconfig.json`, its augmentation is visible to every file in the program with no `import` required. A collision is when a second declaration reopens a core type with an overlapping key whose optionality or type widens the original — `interface User { email: string }` (required) merged with `interface User { email?: string }` (optional) makes `email` `string | undefined` everywhere the program checks it — `user.email.toLowerCase()` that was safe now throws.

**What problem it solves / history** — `lib.d.ts` models built-ins as `interface Window`, `interface Array<T>` precisely so later `lib.dom.d.ts` or a polyfill can add `Array.prototype.at` by reopening `Array` without forking (TS 0.8). `@types/*` (TS 2.0) does the same for `Express.Request`. The hazard grew with monorepos: feature teams each contributed a `declare global` snippet (`Window.__AUTH_TOKEN__`, `Window.__BILLING_TOKEN__`), and a shared `User` contract gained an optional `email?` augmentation for "guest" flow — the augmentation lived in one `src/types/guest.d.ts`, but every handler that trusted `user.email: string` now needs `?.` or a guard. TypeScript 4.4's `exactOptionalPropertyTypes` did not fix scope — scope is fixed by *where* the augmentation lives and whether it should have been a local intersection instead.

**Modern guidance** — as of TypeScript 5.9 era:

- **Default to module augmentation, not global** — `declare module "pkg" { interface Request { ... } }` is scoped to importers of `"pkg"`; `declare global` leaks to every file. If the shape is only needed where `pkg` is used, never use the global form. Consolidate `declare global` into one `src/types/globals.d.ts` per global behind `CODEOWNERS`.
- **Never add `?:` to a wide contract that downstream expects required** — `User.email?: string` on the global `User` makes *every* `user.email` optional. Model the variant locally: `type GuestUser = Omit<User, "email"> & { email?: string }` or `type AuthenticatedUser = User & { email: string }` scoped to the handler that proves it.
- **Treat every interface reopening as a public API change** — `grep -R "^interface User" --include="*.ts" --include="*.d.ts" src/ | grep -v "src/types/"` should be empty unless the file has `// augmentation:` comment.
- **Gate inclusion** — `tsconfig.json` `include: ["src/**/*", "src/types/**/*"]` — run `npx tsc --listFiles | grep "guest.d.ts"` to verify which `.d.ts` contributed — an included augmentation is program-global, an omitted one is silently dead; both surprise.
- **Lint duplicates** — `error` on second `interface Foo` inside `src/**/*.ts`; `off` (or `warn` with `// augmentation:` exemption) inside `src/types/**/*.d.ts`.

**Runnable example** — incident: global `User` required `email`, guest augmentation added `email?`, every handler broke silently; local intersection keeps the requirement scoped (`tsc --strict` — error lines commented so the fence compiles, uncomment one at a time to see the locus):

```typescript
// incident — global User is required; augmentation collides and widens to optional program-wide
interface User {
  id: string;
  email: string; // invariant: every User has an email — handlers call user.email.toLowerCase()
}
function sendWelcome(u: User): string {
  return u.email.toLowerCase(); // safe before augmentation — checker proves email is string
}
const alice: User = { id: "u_1", email: "ALICE@EXAMPLE.COM" };
console.log(sendWelcome(alice)); // alice@example.com

// bad — ambient-style augmentation that reopens User with email? — same pattern as declare global/module
// In production this lived in src/types/guest.d.ts as a second file:
//   interface User { email?: string; } // merges — User now { id: string; email?: string } — email becomes string | undefined everywhere
// In a single-file demo that merge would be `error TS2687: All declarations of 'email' must have identical modifiers.`
// Simulate the merged effect via a local alias so the fence still compiles under tsc --strict:
type UserAfterAugmentation = Omit<User, "email"> & { email?: string }; // what every consumer now sees program-wide
// After merge, the same handler is now UNSAFE but still compiles until strictNullChecks surfaces:
function sendWelcomeAfter(u: UserAfterAugmentation): string {
  // return u.email.toLowerCase(); // error TS18048: 'u.email' is possibly 'undefined' — was safe before merge
  return (u.email ?? "fallback@example.com").toLowerCase(); // now every caller pays ?. or ?? — required became effectively optional
}
const guest: UserAfterAugmentation = { id: "g_1" }; // ok after merge — guest without email now inhabits the widened User
console.log(sendWelcomeAfter(guest)); // fallback@example.com — silent widening changed the domain

// type-level witness — before merge: keyof User = "id" | "email" (both required); after: still "id" | "email" but email is optional
type UserEmail = UserAfterAugmentation["email"]; // string | undefined — was string before merge
const _checkEmail: UserEmail = undefined as unknown as UserEmail;
console.log(_checkEmail); // undefined — demonstrates optional leak

// bad — conflicting type on same key errors at the second declaration (TS2717), not at use
// interface User { email: number; } // error TS2717: Subsequent property declarations must have the same type — checker does catch type conflicts, but not optionality widens

// good — keep the global contract closed; model the variant locally with intersection / Omit — no global leak
interface AppUser { id: string; email: string; } // closed — never reopened globally
type GuestUser = Omit<AppUser, "email"> & { email?: string }; // guest variant — local
type AuthenticatedUser = AppUser & { email: string }; // stronger guarantee — also local (redundant with AppUser, but illustrates pattern)
function sendWelcomeApp(u: AppUser): string { return u.email.toLowerCase(); } // safe — AppUser still requires email
function sendWelcomeGuest(u: GuestUser): string { return (u.email ?? "guest@example.com").toLowerCase(); } // scoped optional
const appAlice: AppUser = { id: "u_2", email: "alice@example.com" };
const guestBob: GuestUser = { id: "g_2" }; // ok — guest may omit email
console.log(sendWelcomeApp(appAlice)); // alice@example.com
console.log(sendWelcomeGuest(guestBob)); // guest@example.com

// good — when you MUST augment a third-party module, scope to the module, not the global
// file: src/types/express.d.ts (shown inline — real file needs `import "express-serve-static-core"` marker + tsconfig include)
// declare module "express-serve-static-core" { interface Request { user?: { id: string } } } — scoped to Request importers
// file: src/types/globals.d.ts — single global for Window, CODEOWNERS-gated
// export {}; declare global { interface Window { __APP_VERSION__?: string } } — one file, one review
type RequestLike = { url: string }; // stand-in for express Request
type RequestWithUser = RequestLike & { user: { id: string } }; // local, not global
type GuestRequestLike = Omit<RequestWithUser, "user"> & { user?: { id: string } }; // local optional variant
function handler(req: RequestWithUser): void { console.log(req.user.id); } // requires user
function guestHandler(req: GuestRequestLike): void { console.log(req.user?.id ?? "anon"); }
handler({ url: "/a", user: { id: "u_9" } });
guestHandler({ url: "/g" });
console.log("augmentation scoped");

// bad — .d.ts not included by tsconfig: augmentation silently dead — verify with tsc --listFiles
// tsconfig.json fix: "include": ["src/**/*", "src/types/**/*"]
```

**Common confusion** — "`type` merges like `interface` if I put them nearby" — never — `type` is closed (`TS2300`); only `interface` (and `namespace` + `class`/`function`/`enum`) merges. "`declare global` is needed even in a script file" — opposite — script files are already global; `declare global` is illegal in scripts (`TS1231`) and only for modules. "Duplicate `interface` names are always a lint error" — not in `.d.ts` — augmentation *requires* duplication; rule should be `error` in `src/**/*.ts` and `off` in `src/types/**/*.d.ts`. "My `declare module "pkg"` had no effect — must be a bug" — most often file not included by `tsconfig` `include`/`files` or missing `import "pkg"` marker — both fail silently. "Adding `?:` in an augmentation is harmless because it's optional" — harmful when downstream narrows on presence — `if (req.user)` now guards an optional that was added globally without auditing every branch.

**Performance note** — `interface` merging is `O(members)` per reopened name and memoizes to a single internal object type — negligible for 2–3 reopenings of `Window`/`User`. Cost appears when a *script* file or many scattered `declare global` blocks participate: the checker re-evaluates the global namespace on every incremental edit (global invalidation), slowing completions in 10k-file monorepos. One consolidated `src/types/*.d.ts` with explicit `import "pkg"` is evaluated once and cached; ten scattered blocks cause repeated global rechecks — `tsc --extendedDiagnostics --generateTrace trace/` shows the spike under `checkSourceFile`. Deduping ten scattered augmentations into one file can shave 5–12% off incremental check time — no emit cost (merging is erasable), but check latency follows fan-out linearly.

**Mentor note** — enforce the three-file rule in review: (1) `src/types/globals.d.ts` owns `declare global` (one file, `CODEOWNERS` gate), (2) `src/types/<pkg>.d.ts` owns each `declare module "pkg"` (one file per third-party, named after its specifier), (3) every other `interface` reopening in `src/**/*.ts` is flagged "prove this is intentional — why not a single declaration or a local `&`?" Exercise: open `npx tsc --listFiles` beside `git ls-files "src/types/*.d.ts"` and ask "which `.d.ts` is *not* in the program and therefore silently dead?" — answer reveals the inclusion bug. Checklist in `CONTRIBUTING.md`: every `declare module` line names its specifier (`// augments express-serve-static-core: Request.user`), every `declare global` lives in `src/types/globals.d.ts` with `export {}` header, and `npm run lint:augmentation` (`grep -R "^interface Window\|^declare global" src --include="*.ts" | grep -v "src/types/"`) exits non-zero.
