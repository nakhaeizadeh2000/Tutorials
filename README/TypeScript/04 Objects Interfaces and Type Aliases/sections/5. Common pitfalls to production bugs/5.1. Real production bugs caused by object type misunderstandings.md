## 5.1. Real production bugs caused by object type misunderstandings

A mistaken object contract can conceal missing fields, shared mutation or an overly broad key domain. Declaration conflicts can instead stop checking before any consumer runs. This lesson demonstrates those failure mechanisms in local reproductions; it does not claim that these examples came from recorded production incidents or exercised a payment provider.

Examples use TypeScript 7.0.2 and Node 20.20.2, checked 2026-10-13. Save each named fence in a directory without tsconfig.json. For positive examples run `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. Intentional runtime failures are caught so each program reaches its remedy. Keep commented compiler failures inert until checking them individually with `--noEmit`.

### 1) **An assertion bypasses evidence rather than fixing a missing field**

A required field must exist with the right value type. Merely storing an object in a variable does not supply a missing currency, and a failed check should not be repaired by asserting the object into Payment. A double assertion can bypass the missing proof, leaving the downstream operation to encounter undefined.

Save `freshness.ts`:

```typescript
export {};
type Payment = { userId: string; amount: number; currency: "USD" | "EUR" };
function toProcessor(payment: Payment): string {
  if (payment.currency !== "USD" && payment.currency !== "EUR") {
    throw new Error(`unsupported currency: ${payment.currency}`);
  }
  return `${payment.amount} ${payment.currency}`;
}
function charge(payment: Payment): string { return toProcessor(payment); }
const raw = { userId: "u_1", amount: 100, curency: "USD" };
// const missing: Payment = raw; // TS2741: currency is missing even through a variable
const asserted = raw as unknown as Payment;
try { console.log(charge(asserted)); }
catch (error) { console.log(error instanceof Error && error.message); }
// unsupported currency: undefined
const checked = { userId: "u_1", amount: 100, currency: "USD" } satisfies Payment;
console.log(charge(checked)); // 100 USD
// const typo = { userId: "u_1", amount: 100, curency: "USD" } satisfies Payment; // TS2561

type Options = { host: string; port?: number };
const leaky = { host: "db", portt: 5432 }; // optional port is absent; another key exists
const throughVariable: Options = leaky;
const throughSpread: Options = { ...leaky };
console.log(throughVariable.port, throughSpread.port); // undefined undefined
// const writtenTypo: Options = { ...leaky, portt: 5432 }; // TS2561: directly written field
const fixed = { host: "db", port: 5432 } satisfies Options;
console.log(fixed.port); // 5432
```

The required-currency and optional-port cases fail for different reasons. Required currency is structurally missing, so even the variable assignment is rejected. Optional port may be omitted, so the unrelated portt can travel through an existing value without violating the required shape. Directly writing the typo in a checked literal surfaces the creation-site error. The [object-shape owner](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) explains the written-versus-inherited spread distinction.

Choose the fix from the origin: correct an authored typo, name an intentional extra member in the consuming contract, or parse unknown external data. Neither an assertion nor satisfies supplies runtime validation of incoming payloads. The local processor here checks only its currency domain and formats an amount; a real monetary boundary needs its own complete amount/user/authorization policy.

### 2) **A readonly view does not freeze shared defaults**

Readonly rejects a write through that static view. It does not alter the object's runtime property descriptors or make a shared reference into a copy. Another mutable view can still change ordinary data. Object.freeze provides a shallow runtime integrity policy; it does not automatically freeze referenced children.

Save `integrity.ts`:

```typescript
export {};
type Config = { apiUrl: string; tags: string[]; meta: { retries: number } };
const mutable: Config = { apiUrl: "https://api.example", tags: ["web"], meta: { retries: 3 } };
const defaults: Readonly<Config> = mutable;
// defaults.apiUrl = "x"; // TS2540: rejected through this view
console.log(Object.getOwnPropertyDescriptor(defaults, "apiUrl")?.writable); // true
mutable.apiUrl = "https://tenant.example";
defaults.meta.retries = 99; // top-level readonly does not make the nested member readonly
console.log(defaults.apiUrl, defaults.meta.retries); // https://tenant.example 99

const frozen = Object.freeze({ apiUrl: "https://api.example", meta: { retries: 3 } });
const forcedMutable = frozen as { apiUrl: string; meta: { retries: number } };
try { forcedMutable.apiUrl = "changed"; }
catch (error) { console.log(error instanceof TypeError); } // true in this strict emitted program
forcedMutable.meta.retries = 4; // the child was not frozen
console.log(Object.isFrozen(frozen), Object.isFrozen(frozen.meta), frozen.meta.retries); // true false 4

function getDefaults(): Config {
  return { apiUrl: frozen.apiUrl, tags: ["web"], meta: { retries: 3 } };
}
const first = getDefaults();
const second = getDefaults();
first.tags.push("tenant");
first.meta.retries = 8;
console.log(second.tags.join(","), second.meta.retries); // web 3: selected nested values are fresh
```

The factory constructs fresh arrays and nested metadata for this specific shape. A top-level spread alone would retain their references. Decide which values may be shared and which need independent ownership before calling a copy a remedy. If runtime immutability is required at additional levels, apply a policy designed for those data types; a generic deep-freeze fragment is not a substitute for considering cycles, accessors, Maps or other objects. The runtime object's owner is the JavaScript integrity lesson, while the [modifier owner](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) explains the static views.

### 3) **Open keys do not automatically broaden explicit member types**

An open number dictionary accepts alcie because any string key is allowed. A closed score-key contract can reject that spelling. Separately, declaring kind as string allows any string value; an index signature does not cause that explicit declaration. A compatible named kind literal union remains a literal union alongside `[key: string]: unknown`.

Save `dictionaries.ts`:

```typescript
export {};
const scoresBad: Record<string, number> = { alcie: 42, bob: 17 };
console.log(scoresBad["alice"], scoresBad["alcie"]); // undefined 42
const scoresGood = { alice: 42, bob: 17 } satisfies Record<"alice" | "bob", number>;
console.log(scoresGood.alice); // 42
// const scoreTypo = { alcie: 42, bob: 17 } satisfies Record<"alice" | "bob", number>; // TS2561

type LooseEvent = { kind: string; [key: string]: unknown };
const loose: LooseEvent = { kind: "clikc", x: 10 };
console.log(loose.kind); // clikc: permitted by kind: string

type Tagged = { kind: "click" | "hover"; [key: string]: unknown };
const tagged: Tagged = { kind: "click", extra: 1 };
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Kind = Expect<Equal<Tagged["kind"], "click" | "hover">>;
console.log(tagged.kind, tagged.extra); // click 1
// const kindTypo: Tagged = { kind: "clikc" }; // TS2820: named member stayed literal-valued

type AppEvent =
  | { kind: "click"; x: number; [key: string]: unknown }
  | { kind: "hover"; y: number; [key: string]: unknown };
function handle(event: AppEvent): string {
  switch (event.kind) {
    case "click": return `click ${event.x}`;
    case "hover": return `hover ${event.y}`;
    default: { const complete: never = event; return complete; }
  }
}
console.log(handle({ kind: "hover", y: 2, extra: "retained" })); // hover 2
// const missingPayload: AppEvent = { kind: "click" }; // TS2322: required x is missing

// Named members must also be compatible with the index value domain.
type NamedScores = { name: string } & Record<string, number | string>;
const named: NamedScores = { name: "leaderboard", alice: 42 };
console.log(named.name.toUpperCase()); // LEADERBOARD
```

The first named-member probe preserves kind even with open extra keys. That single Tagged type does not establish a relationship between kind and payload fields. AppEvent adds the relationship with separate branches, so the switch can access the appropriate required number even while each branch permits unrelated extra keys. Open extras can be correct for the model; reject or filter them separately if your boundary needs a closed runtime representation.

Missing dictionary reads are optional under the demonstrated noUncheckedIndexedAccess setting. The compiler still does not inspect external data, and an annotation neither guarantees own runtime keys nor sanitizes their representation. The [index/member owner](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) owns compatible named members; the [query owner](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>) owns static keys versus enumeration. Use the existing union owner for the full narrowing model.

### 4) **A conflicting merge is rejected; a local guest contract is a deliberate alternative**

Two declarations of the same interface can add compatible members. They cannot silently change a required email into an optional one. Mismatched modifiers produce TS2687, with the type conflict also producing TS2717 in the tested setup. Modeling a local Guest type with Omit and an optional email is a different action: it does not mutate the original User type.

Save `merging.ts`:

```typescript
export {};
interface User { id: string; email: string }
// interface User { email?: string } // TS2687/TS2717: conflicting declarations
function welcome(user: User): string { return user.email.toLowerCase(); }
const alice: User = { id: "u_1", email: "ALICE@EXAMPLE.COM" };
console.log(welcome(alice)); // alice@example.com
// const missingEmail: User = { id: "g_1" }; // TS2741: original requirement remains

type Guest = Omit<User, "email"> & { email?: string };
function guestWelcome(guest: Guest): string {
  return (guest.email ?? "guest@example.com").toLowerCase();
}
const guest: Guest = { id: "g_1" };
console.log(guestWelcome(guest), welcome(alice)); // guest@example.com alice@example.com

// Additive merging is allowed when the new member is compatible.
interface LocalConfig { host: string }
interface LocalConfig { port?: number }
const config: LocalConfig = { host: "db" };
console.log(config.host, config.port); // db undefined
```

Uncomment the conflicting User declaration and run the negative check in either exact-optional mode. Both reject it; the flag does not make the conflict legal. Restore the comment before execution. To obtain a guest variant, use a local contract that states which operation accepts omission, and adapt the handler accordingly. Do not present that alias as a simulation of a successful merge.

For real module/global augmentation, verify inclusion, the legal file markers and the runtime provider separately. Removing an augmentation file can create downstream missing-member errors; omitting a runtime provider can leave checking green while execution lacks its value. A script/module marker mistake can itself be a compiler error. The [complete augmentation owner](<../2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) executes those different cases. Adding declarations supplies no implementation, and a text-search rule or chosen directory cannot prove that the program includes the correct files.

### 5) **Common confusion**

A variable can carry extra members but cannot supply a missing required one. A readonly view can reject direct writes while a mutable alias changes the shared object. An open key domain can accept a misspelled key while an explicit member still rejects a misspelled value. Name the particular contract before diagnosing a failure.

An incompatible interface merge does not quietly soften the original property. A local variant may permit omission intentionally, which is why its consumers require different handling. None of these static choices validates an unknown payload or establishes a runtime provider.

### 6) **Performance note**

Annotations and type operators erase. Currency checks, object construction, copying, freezing, lookup and formatting still execute. Fresh nested values avoid shared mutation here at the cost of constructing those values; shallow freezing applies runtime integrity only to the targeted object. No universal engine-read speedup, per-property checker formula, brand-count budget or incremental percentage was measured. Choose semantics first and measure the actual copying/validation/checking workload when its cost matters.

### 7) **Mentor note**

Give learners the four positive files and ask them to predict where each negative belongs: missing data, a checked literal, a readonly view, a named literal member, or a merge declaration. A sound explanation identifies the runtime consequence as well as the static diagnostic.

For a controlled variation, replace the fresh tags array in getDefaults with one shared array and predict why changing first also changes second. Then explain why a User with omitted email cannot be justified by the Guest alias. Finally add an extra key to the valid Tagged value and separately change kind to clikc: open keys permit the first edit, while the named literal contract rejects the second. Review the resulting contract rather than banning all index signatures or all declarations of the same interface name.
