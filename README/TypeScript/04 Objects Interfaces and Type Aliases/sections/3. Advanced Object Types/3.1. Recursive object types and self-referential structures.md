## 3.1. Recursive object types and self-referential structures

A recursive type names itself, directly or through another declaration, to describe repeated structure. A comment can contain replies that are themselves comments; a tree can contain smaller trees. The declaration describes allowed relationships. It does not allocate children or determine how a runtime traversal terminates.

These examples were checked with TypeScript 7.0.2 and executed as emitted JavaScript with Node 20.20.2 on 2026-10-13. Save each fence in the named file in a directory without a tsconfig. Run `tsc --strict --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. Replace `FILE` with the shown name. Intentional error lines stay commented until the negative exercise.

### 1) **Self-reference and legal recursive structures**

`Tree.children` describes another array of the same shape. An empty children array represents a leaf. A linked list instead uses `null` to end its chain. Both an interface and an object type alias can describe these structures; their names do not make otherwise equal shapes incompatible.

Recursive array aliases are also valid. `type RecursiveArray = RecursiveArray[]` describes arrays whose elements are more such arrays, including an empty array. A union can add scalar leaves. These patterns differ from `type Loop = Loop`, which contributes no usable structure and is rejected with TS2456. The [3.7 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#more-recursive-type-aliases) explain the historical relaxation for array and tuple aliases; the examples here establish the current checked behavior.

Save `shapes.ts`:

```typescript
export {};
interface Tree { value: number; children: Tree[] }
type TreeAlias = { value: number; children: TreeAlias[] };
const leaf: Tree = { value: 1, children: [] };
const root: Tree = { value: 2, children: [leaf, { value: 3, children: [] }] };
const sameShape: TreeAlias = root;
console.log(root.children.length, sameShape === root); // 2 true

interface Linked<T> { value: T; next: Linked<T> | null }
const list: Linked<string> = { value: "a", next: { value: "b", next: null } };
console.log(list.next?.value); // b

type RecursiveArray = RecursiveArray[];
type ArrayOrText = ArrayOrText[] | string;
const empty: RecursiveArray = [];
const nested: RecursiveArray = [[], [[]]];
const text: ArrayOrText = ["leaf", ["nested"]];
console.log(empty.length, nested.length, Array.isArray(text)); // 0 2 true

type JSONValue = string | number | boolean | null | JSONValue[] | { [key: string]: JSONValue };
const doc: JSONValue = { user: { name: "Ada", tags: ["admin"], meta: null } };
console.log(typeof doc); // object

// type Loop = Loop; // TS2456: direct circular alias
// const missing: Tree = { value: 1 }; // TS2741: children is required
```

The first output also shows that assigning the root to another recursive shape keeps the same object. Types do not clone it. JSONValue models a static JSON-like value space; annotating external input with it is not a parser and does not establish serializability of a cyclic graph. Use the existing boundary-validation owner for unknown inputs.

### 2) **Mutual recursion and finite cyclic graphs**

Mutual recursion forms a cycle between declarations: Category references Team and Team references Category. Self-recursion has an edge back to the same declaration. Draw those edges before classifying a model; simply using two type names does not establish mutual recursion.

A type without a `null` leaf can still have a finite runtime inhabitant. One allocated object can point to itself. Two allocated objects can point to each other. Following `next` forever would revisit those objects, rather than allocate infinitely many more. This separates a graph's finite size from an unbounded traversal.

Save `cycles.ts`:

```typescript
export {};
type NoBase = { next: NoBase };
class SelfCycle { next: SelfCycle = this }
const self: NoBase = new SelfCycle();
console.log(self.next === self); // true: one object

interface NodeA { b: NodeB }
interface NodeB { a: NodeA }
class A implements NodeA {
  b: B;
  constructor() { this.b = new B(this); }
}
class B implements NodeB {
  a: A;
  constructor(a: A) { this.a = a; }
}
const pair: NodeA = new A();
console.log(pair.b.a === pair); // true: two objects

interface Category { name: string; parent: Category | null; teams: Team[] }
interface Team { label: string; category: Category }
const engineering: Category = { name: "eng", parent: null, teams: [] };
const backend: Team = { label: "backend", category: engineering };
engineering.teams.push(backend);
console.log(backend.category.teams[0] === backend); // true: also cyclic

interface DocTree { title: string; children: DocForest }
type DocForest = DocTree[];
const forest: DocForest = [{ title: "root", children: [{ title: "leaf", children: [] }] }];
console.log(forest[0].children.length); // 1: an acyclic mutual structure

// type BareA = BareB; // TS2456
// type BareB = BareA; // TS2456
```

The Category example contains a cycle even though it has `parent: null` and an initially empty teams array. A terminating option in the type permits some acyclic values; it does not require every value to be acyclic. Choose the runtime policy deliberately: reject cycles for a strict tree, revisit each distinct node once for a graph, or stop at an explicit traversal limit.

For spelling, use an interface when a named object contract and intended merging fit your API. Use an alias when you need a union, tuple or transformation. Neither spelling supplies cycle detection, runtime validation or a universal speed advantage. See the existing interface-versus-alias comparison for its actual capability differences.

### 3) **Separate type-transform caps from runtime traversal limits**

A recursive mapped transform computes a new type from member types. A depth parameter can stop that transform, but the stop branch determines the result. Returning `T` leaves the remaining structure unchanged. It does not reject a deep value and does not issue TS2589 merely because the local cap was reached.

Save `cap.ts`. This preserves the previous example's five-step boundary so the consequence is visible. Its name now describes a capped readonly view rather than suggesting a runtime freeze or mutual recursion.

```typescript
export {};
type Leaf = string | number | boolean | null;
type CappedReadonlyView<T, D extends unknown[] = []> =
  D["length"] extends 5 ? T :
  T extends Leaf ? T :
  T extends Map<infer K, infer V> ? Map<K, CappedReadonlyView<V, [...D, unknown]>> :
  T extends (infer E)[] ? CappedReadonlyView<E, [...D, unknown]>[] :
  T extends object ? { readonly [K in keyof T]: CappedReadonlyView<T[K], [...D, unknown]> } : T;
type Nested = { a: { b: { c: { d: { e: { f: string } } } } } };
const view: CappedReadonlyView<Nested> = { a: { b: { c: { d: { e: { f: "hi" } } } } } };
// view.a.b.c.d.e = { f: "replaced" }; // TS2540: e lies inside the transformed region
view.a.b.c.d.e.f = "changed"; // accepted: depth-five remainder is returned unchanged
console.log(view.a.b.c.d.e.f); // changed
console.log(Object.isFrozen(view)); // false

type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Remainder = Expect<Equal<CappedReadonlyView<Nested>["a"]["b"]["c"]["d"]["e"], { f: string }>>;

const numbers: CappedReadonlyView<number[]> = [1];
numbers.push(2); // this array branch remains a mutable array
const table: CappedReadonlyView<Map<string, { value: number }>> = new Map();
table.set("item", { value: 1 }); // this Map branch retains set
console.log(numbers.length, table.size); // 2 1
```

At depth zero the outer object's property `a` becomes readonly. Each descent adds one element to D. At depth four, `e` becomes readonly; at depth five its value `{ f: string }` is returned unchanged. The live equality check confirms that remainder. The array and Map branches recurse into values while retaining mutable containers. This is a limited teaching transform, not a complete DeepReadonly library: callable and built-in leaf policies belong to the linked deep-transform lesson. Readonly annotations also do not call Object.freeze.

Uncomment the `e` replacement and run the same compiler command with `--noEmit`: TS2540 rejects it. Restore the comment before running the positive file. For the separate declaration failure, save `export {}; type Loop = Loop;` as `bare.ts` and check it with `--noEmit`: TS2456. Neither test is a measurement of the compiler's expansion limit. A reproducible TS2589 example and measurement workflow live in the budget owner.

Runtime limits concern actual visits and accepted data. Save `traversal.ts`:

```typescript
export {};
interface ChainNode { label: string; next: ChainNode | null }
function visitChain(start: ChainNode | null, maxNodes: number): string[] {
  const seen = new Set<ChainNode>();
  const labels: string[] = [];
  let current = start;
  while (current !== null && !seen.has(current)) {
    if (seen.size >= maxNodes) throw new RangeError("node budget exceeded");
    seen.add(current);
    labels.push(current.label);
    current = current.next;
  }
  return labels;
}
const first: ChainNode = { label: "a", next: null };
const second: ChainNode = { label: "b", next: first };
first.next = second;
console.log(visitChain(first, 2).join(",")); // a,b: stops on repeated identity
try { visitChain(first, 1); }
catch (error) { console.log(error instanceof RangeError); } // true

interface ThreadComment { text: string; replies: ThreadComment[] }
function countStrictTree(root: ThreadComment, maxDepth: number, maxNodes: number): number {
  const stack = [{ node: root, depth: 0 }];
  const seen = new Set<ThreadComment>();
  while (stack.length > 0) {
    const item = stack.pop();
    if (item === undefined) break;
    if (seen.has(item.node)) throw new Error("repeated node identity");
    if (item.depth > maxDepth) throw new RangeError("depth budget exceeded");
    if (seen.size >= maxNodes) throw new RangeError("node budget exceeded");
    seen.add(item.node);
    for (const reply of item.node.replies) stack.push({ node: reply, depth: item.depth + 1 });
  }
  return seen.size;
}
const thread: ThreadComment = { text: "root", replies: [{ text: "reply", replies: [] }] };
console.log(countStrictTree(thread, 1, 2)); // 2
try { countStrictTree(thread, 0, 2); }
catch (error) { console.log(error instanceof RangeError); } // true
const loop: ThreadComment = { text: "loop", replies: [] };
loop.replies.push(loop);
try { countStrictTree(loop, 10, 10); }
catch (error) { console.log(error instanceof Error && error.message); } // repeated node identity
```

The chain permits cycles and records each distinct node once. The strict-tree visitor rejects repeated identity, including both cycles and a child shared by two parents. That policy is stricter than merely rejecting cycles, so use it only when the data must form a tree. Root depth is zero; a child has depth one. The chosen limits are small exercise inputs, not recommended production defaults. A node budget also bounds wide input that could pass a depth-only rule.

Both functions accept already typed values. They are traversal-policy demonstrations, not validators of arbitrary unknown objects, getters, proxies or array contents. Validate and construct trusted input first. The iterative tree visitor avoids recursive function calls, but it still allocates a stack and a visited set. A type-level cap of five has no required relationship to these runtime limits.

### 4) **Common confusion**

A recursive declaration creates no runtime graph. A graph without a null leaf can contain finitely many objects and cyclic references. Conversely, allowing null does not guarantee that every constructed graph eventually reaches it. Termination is a property of the traversal and the actual graph.

A circular alias error, a missing required child, and TS2589 are different failures. Identify the failing declaration, value construction or type computation before applying a remedy. A cap that returns T changes the deepest transformed contract; it does not make arbitrary recursive code safe or prove a payload depth.

### 5) **Performance note**

Recursive types and mapped computations erase. Their checking work does not become a runtime recursion loop. No compiler timing, type-node formula or editor benchmark was measured for these examples; use the measurement owner for those claims. Wide unions and member relationships can matter as well as depth, so choosing an interface or a small cap is not a universal performance guarantee.

The visitors execute ordinary JavaScript. The chain stores one set entry and one label per distinct visited node. The strict-tree visitor stores visited identities and pending children, so wide input can use substantial memory. Iteration avoids the recursive call stack but does not remove that work. Select limits from your application's accepted data and operation budget, separately from a type transform's semantics.

### 6) **Mentor note**

Ask learners to predict `self.next === self`, then explain how one object satisfies a type with no leaf branch. Next uncomment the cap's e assignment while leaving f's write active. A sound answer identifies the stop branch and explains why one assignment fails while the other passes.

For dependency classification, give these definitions as a prose exercise: `Expr = { kind: "lit"; value: number } | { kind: "bin"; left: Expr; right: Expr }` and `Stmt = { kind: "expr"; expr: Expr } | { kind: "block"; stmts: Stmt[] }`. Expr→Expr and Stmt→Stmt are self-recursive; Stmt→Expr is a one-way dependency. Expr never references Stmt, so the pair is not mutually recursive. Contrast it with NodeA→NodeB→NodeA in cycles.ts. Finally, ask whether a shared child should pass countStrictTree. It fails by the explicit identity policy; a graph visitor would need a different contract.
