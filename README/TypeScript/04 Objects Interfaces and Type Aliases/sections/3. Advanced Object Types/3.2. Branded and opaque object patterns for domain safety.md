## 3.2. Branded and opaque object patterns for domain safety

Two object types can have the same members yet represent different domains. A user reference and an order reference might both contain an id string. When passing one in place of the other would be a mistake, an extra static brand can distinguish them. This lesson applies the primitive-brand idea to whole objects and examines what factories, copies, projections and classes actually preserve.

Examples were checked with TypeScript 7.0.2 and emitted JavaScript executed with Node 20.20.2 on 2026-10-13. Save each fence under its stated filename in a directory without a tsconfig. Run `tsc --strict --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. Keep intentional error lines commented for the positive run. The class example also ran directly on Node 22.18.0 using the command below.

### 1) **Establish the structural collision before adding a brand**

TypeScript compares the members required by the target, rather than treating distinct alias names as distinct domain identities. With two `{ id: string }` types, an order reference can reach a user-only operation. But a User containing email cannot satisfy an Order that requires totalCents unless it also supplies that member. The [compatibility reference](https://www.typescriptlang.org/docs/handbook/type-compatibility.html) explains required-member comparison.

Save `shapes.ts`:

```typescript
export {};
type UserRef = { id: string };
type OrderRef = { id: string };
function deleteUser(user: UserRef): string { return `user lookup ${user.id}`; }
const order: OrderRef = { id: "o_99" };
console.log(deleteUser(order)); // user lookup o_99: accepted equal shape, wrong domain

// A different required shape already has protection without a brand.
type User = { id: string; email: string };
type Order = { id: string; totalCents: number };
function shipOrder(value: Order): string { return `order ${value.id} ${value.totalCents}`; }
const user: User = { id: "u_42", email: "alice@example.com" };
const realOrder: Order = { id: "o_99", totalCents: 4999 };
console.log(shipOrder(realOrder)); // order o_99 4999
// shipOrder(user); // TS2741: required totalCents is missing

const asserted = user as unknown as Order;
console.log(asserted.totalCents); // undefined: assertion created no member
```

This code performs local formatting only; it does not delete records or call a service. The first line demonstrates a genuine domain mix-up that structure permits. The last line demonstrates a deliberate assertion bypassing a different, existing check. Adding a brand cannot prevent an author from using `any`, an unchecked assertion or a lying predicate to bypass checking again.

### 2) **A checked factory supplies evidence for a phantom brand**

A phantom member participates in static compatibility but is intentionally absent from the constructed runtime value. `User & { readonly __brand: "User" }` and the corresponding Order brand have incompatible marker types. A factory validates the required contract and makes a localized assertion after that validation. TypeScript does not prove that the factory's checks establish the meaning of the brand, so those checks need review and malformed-input tests.

Save `factories.ts`:

```typescript
export {};
type UserCore = { readonly id: string; readonly email: string };
type OrderCore = { readonly id: string; readonly totalCents: number };
type User = UserCore & { readonly __brand: "User" };
type Order = OrderCore & { readonly __brand: "Order" };
function makeUser(id: string, email: string): User {
  if (!/^u_[A-Za-z0-9]+$/.test(id)) throw new Error("bad user id");
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email)) throw new Error("bad email shape");
  return { id, email } as User;
}
function makeOrder(id: string, totalCents: number): Order {
  if (!/^o_[A-Za-z0-9]+$/.test(id)) throw new Error("bad order id");
  if (!Number.isSafeInteger(totalCents) || totalCents < 0) throw new Error("bad total");
  return { id, totalCents } as Order;
}
function userFromJson(raw: unknown): User {
  if (typeof raw !== "object" || raw === null || Array.isArray(raw)) throw new Error("bad object");
  if (!("id" in raw) || !("email" in raw)) throw new Error("missing member");
  // Read once before checking and copying the accepted primitive values.
  const id: unknown = raw.id;
  const email: unknown = raw.email;
  if (typeof id !== "string" || typeof email !== "string") throw new Error("bad member");
  return makeUser(id, email);
}
const alice = userFromJson({ id: "u_42", email: "alice@example.com" });
const purchase = makeOrder("o_99", 4999);
console.log(alice.id, purchase.totalCents); // u_42 4999
console.log(Object.hasOwn(alice, "__brand"), JSON.stringify(alice));
// false {"id":"u_42","email":"alice@example.com"}

const badUsers: unknown[] = [null, [], {}, { id: 1, email: "a@b.co" },
  { id: "o_1", email: "a@b.co" }, { id: "u_1", email: "missing-at" }];
let rejectedUsers = 0;
for (const raw of badUsers) {
  try { userFromJson(raw); } catch { rejectedUsers++; }
}
console.log(rejectedUsers); // 6
let rejectedOrders = 0;
for (const total of [-1, NaN, Infinity, 1.5, Number.MAX_SAFE_INTEGER + 1]) {
  try { makeOrder("o_1", total); } catch { rejectedOrders++; }
}
console.log(rejectedOrders); // 5

// const unproved: User = { id: "u_1", email: "a@b.co" }; // TS2322: missing brand
// makeOrder("o_1", "4999"); // TS2345: string is not a number
```

The prefix and email checks are deliberately small exercise contracts. An email-like shape does not prove deliverability, ownership or account existence. The total check establishes safe non-negative integer cents, not authorization to buy anything. userFromJson creates a new object from checked primitive values, so replacing fields in the input afterward does not replace its fields. Readonly is a static view; this example does not freeze the output or protect it against unchecked mutation. A brand records a trusted construction decision, not an immutable runtime certificate.

Keep construction and parsing near the domain that owns the invariant. Callers that already hold a trusted branded value need not rerun the parser for formatting. Re-enter validation when new untrusted data arrives or a transformation changes the invariant. A branded type assertion at an arbitrary call site would conceal precisely the decision this boundary is intended to make visible.

A symbol-key brand can avoid two independently declared markers sharing the same string key and literal. The symbol declarations below are used only in type positions; no runtime reads of them occur. Save `symbols.ts`:

```typescript
export {};
declare const UserBrand: unique symbol;
declare const OrderBrand: unique symbol;
type UserRef = { readonly id: string } & { readonly [UserBrand]: "Ref" };
type OrderRef = { readonly id: string } & { readonly [OrderBrand]: "Ref" };
function makeUserRef(id: string): UserRef {
  if (!/^u_[A-Za-z0-9]+$/.test(id)) throw new Error("bad user id");
  return { id } as UserRef;
}
function makeOrderRef(id: string): OrderRef {
  if (!/^o_[A-Za-z0-9]+$/.test(id)) throw new Error("bad order id");
  return { id } as OrderRef;
}
function lookupUser(value: UserRef): string { return value.id; }
const user = makeUserRef("u_1");
const order = makeOrderRef("o_1");
console.log(lookupUser(user)); // u_1
console.log(Object.keys(user).join(","), JSON.stringify(order)); // id {"id":"o_1"}
// lookupUser(order); // TS2345: different required symbol marker
```

No symbol property was attached to either object. That absence explains their runtime shape; it is separate from JSON's rules for actual symbol properties. A type-only declaration also does not create a runtime value: trying to read UserBrand would require a real provider. Export a branded type and its construction API when consumers need it; an unexported key makes accidental typed forgery harder but does not prevent explicit assertions.

### 3) **Copies and projections preserve different parts of the contract**

A whole spread can preserve the brand in its inferred type even when no marker exists as an own runtime property. A function boundary does not automatically remove it. An explicit field projection omits an aggregate marker; a return annotation can also expose a deliberately unbranded view. Pick selects keys, so a brand on a selected field can survive while an unselected brand on the whole object does not.

Save `projections.ts`. Its two construction assertions supply known valid fixtures for examining static transformations; use checked factories at real input boundaries.

```typescript
export {};
type UserCore = { id: string; email: string };
type User = UserCore & { readonly __brand: "User" };
const user = { id: "u_1", email: "a@b.co" } as User;
function clone(value: User) { return { ...value }; }
const copy: User = clone(user); // inferred return retains the brand
console.log(copy.id, Object.hasOwn(copy, "__brand")); // u_1 false

function project(value: User) { return { id: value.id, email: value.email }; }
const projected = project(user);
function coreView(value: User): UserCore { return { ...value }; }
const exposedCore = coreView(user);
console.log(projected.email, exposedCore.id); // a@b.co u_1
// const lostByProjection: User = projected; // TS2322: missing aggregate marker
// const lostByContract: User = exposedCore; // TS2322: public view omits marker

type Id = string & { readonly __brand: "Id" };
type OverUser = { id: Id; email: string } & { readonly __brand: "OverUser" };
const over = { id: "u_2" as Id, email: "b@c.co" } as OverUser;
type OverPick = Pick<OverUser, "id">;
const picked: OverPick = { id: over.id };
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type SelectedKeys = Expect<Equal<keyof OverPick, "id">>;
type FieldBrand = Expect<Equal<OverPick["id"], Id>>;
type Projection = Expect<Equal<typeof projected, UserCore>>;
type InferredBrand = Expect<Equal<typeof copy["__brand"], "User">>;
console.log(picked.id, Object.hasOwn(picked, "__brand")); // u_2 false
// const badId: Id = "u_3"; // TS2322: plain string lacks the field brand
```

A core projection is useful for a public response or a partial update. It does not claim to be the whole branded aggregate, so it need not be asserted back to User. If a helper must return User, decide whether its transformation preserves the invariant or whether it must reconstruct through the factory. A spread's inferred brand alone is not proof that editing a data member preserved the intended domain rule.

Choose the level that the operation needs. An aggregate brand protects a function receiving the aggregate, while a field brand can protect a function receiving only the id. Using both can be justified when both contracts matter. There is no useful universal brand-count quota; evaluate the mix-up each marker prevents and the construction/projection work it introduces. [Learning TypeScript's branding discussion](https://www.learningtypescript.com/articles/branded-types) develops these trade-offs and the limits of assertions and predicates; local probes here verify the object-specific behavior.

### 4) **Class-private identity is another design with runtime construction**

Private members from different class declarations can distinguish otherwise similar instance shapes. Classes also provide runtime constructors and methods. The ordinary private modifier in the following example is accepted by erasableSyntaxOnly and was stripped by the tested Node runtime. Parameter properties are a different syntax that needs transformation. The [syntax-gate reference](https://www.typescriptlang.org/tsconfig/erasableSyntaxOnly.html) names that restriction.

Save `classes.ts`:

```typescript
export {};
class UserClass {
  private __brand!: void;
  readonly id: string;
  constructor(id: string) { this.id = id; }
}
class OrderClass {
  private __brand!: void;
  readonly id: string;
  constructor(id: string) { this.id = id; }
}
const user = new UserClass("u_1");
const order = new OrderClass("o_1");
console.log(user.id, user instanceof UserClass); // u_1 true
console.log(Object.hasOwn(user, "__brand")); // true: ordinary class field exists here
console.log(order.id); // o_1
// const wrong: UserClass = order; // TS2322: private members have separate declarations
// const plain: UserClass = { id: "u_1" }; // TS2741: private member is missing
// class NeedsTransform { constructor(public id: string) {} } // TS1294 under erasableSyntaxOnly
```

Run `npm exec --yes --package=node@22.18.0 -- node classes.ts`: it prints the same three lines as emitted execution. The private TypeScript modifier restricts static access; it is not JavaScript `#private` runtime privacy. With these class fields and target, the emitted object owns an undefined __brand field. These classes demonstrate identity and construction, not validated ids; add a checked constructor or factory if the domain requires validation.

Choose a class when runtime behavior, constructor identity or encapsulation is part of the model. A phantom brand can suit plain data construction when a runtime wrapper is unnecessary. JSON parsing reconstructs plain data rather than an instance, so re-establish the appropriate contract at that boundary for either design. Source syntax support and runtime representation are separate questions; neither choice is universally preferable.

### 5) **Common confusion**

A brand's phantom member is not automatically present at runtime. Static key queries and spread inference can mention it while Object.hasOwn reports false. Do not read the phantom to authenticate a value. The class-field example intentionally has a different representation.

Pick does not retain every aggregate requirement and does not erase every field brand. Inspect the chosen keys and each selected member's type. Likewise, alias names cannot fix equal-shape compatibility, while missing required members already produce a diagnostic without branding.

### 6) **Performance note**

Phantom marker types and assertions erase. The factories still execute checks and allocate the returned objects; spreads and projections still copy values. A type-only symbol declaration creates no runtime Symbol call. Class construction also creates runtime instances. No brand-count benchmark, checker-complexity formula, symbol-size measurement or speed comparison was run here. Choose marker granularity from correctness and API needs, then measure actual validation/copying or checker costs if they matter to the application.

### 7) **Mentor note**

Ask why shapes.ts accepts the equal-shape reference but rejects the uncommented shipOrder(user). A sound answer separates domain meaning from required-member structure and identifies the assertion bypass. Next ask why clone(user) retains a brand while project(user) does not. Require a prediction about both the static marker and Object.hasOwn, then run the examples.

For a review exercise, change the malformed email in factories.ts to a value that passes its small regex and ask what it proves. It establishes only the declared shape, not ownership or delivery. Finally propose a function that accepts user.id alone: learners should explain why an aggregate-only marker does not protect that scalar call and justify a field brand if distinguishing the id domain is necessary.
