## 3.2. Branded and opaque object patterns for domain safety

Object-level branding recovers nominal safety inside a structural type system — two `{ id: string }` objects that *look* identical become incompatible when each carries a phantom brand. This leaf shows why plain structural objects conflate domain identities, how to brand an object type with `& { __brand }` and a `unique symbol` variant, and where the cost outweighs the safety so you brand at boundaries, not every leaf.

---

### 1) **Why object branding matters** (two `{ id: string }` shapes that must not mix — `User` vs `Order` — structural typing alone conflates them)

**Definition** — *object branding* is a type-only tag that makes two structurally identical object shapes — e.g., `type User = { id: string }` and `type Order = { id: string }` — *incompatible* to the checker while remaining identical at runtime. Without a brand, TypeScript's structural rule says "same members → same type" — a `User` object flows into an `Order` slot and vice versa. With a brand, one phantom member participates in the check and breaks that symmetry.

**What problem it solves / history** — every backend mixes IDs that are all `string` or all `{ id: string }` underneath: `User.id`, `Order.id`, `Session.id`, `PaymentIntent.id`. In plain JavaScript that never mattered — you checked at runtime or paid with a swapped lookup. TypeScript inherited structural typing from day one (it made JS object literals ergonomic), so `type User = { id: string }` / `type Order = { id: string }` were *aliases of the same shape* — `declare function ship(order: Order)` happily accepted a `User`. Freshness (see [1.1. Object types structural shape](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>)) does not help — `User` and `Order` have the same width, so no excess fires. The primitive-level answer existed early — `type UserId = string & { __brand: "UserId" }` (see [1.3. Nominal typing techniques](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)) — but object wrappers `{ id: string }` are preferred when the domain carries more than a bare scalar (audit fields, `createdAt`, `kind`), and they need the same nominal recovery at the *object* level. True `opaque type User = { id: string }` remains a proposal as of the TypeScript 5.9 era — not stable — so intersection branding is the pragmatic mechanism.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Need to keep `User` and `Order` objects from mixing** → brand at least one member difference into the shape — the checker then rejects cross-assignment. Leave unbranded objects for genuinely *generic* carriers (`{ id: string }` as a pagination cursor) — brand only when swapping would be a production incident.
- **Keep the brand object-level, not field-level, when the object carries behavior** — `type User = { id: string; email: string } & { __brand: "User" }` brands the whole aggregate; field-level `UserId = string & { __brand }` brands the scalar (see [1.3. Nominal typing techniques](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)) — choose based on whether callers pass `user.id` or `user`.
- **Do not rely on class `private` for this** — `class User { private __brand!: void; id: string }` recovers nominality via private identity but is non-erasable, non-structural for plain data, and breaks `JSON.parse` round-trips — prefer intersection brands for data objects that cross network/storage boundaries.
- **Pair the model with §2 and §3** — this section proves *why*; [§2 below](#2-object-level-branding-type-user--id-string----brand-user--branded-factories-hide-the-assertion-unique-symbol-key-variant) shows *how*; [§3 below](#3-cost-vs-safety-every-branded-value-needs-a-validated-factory-over-branding-fractures-composition--brand-at-module-boundaries-not-every-leaf) bounds *how much*.

**Runnable example** — structural conflation on `{ id: string }` — bad (silent swap) vs the diagnostic you *want* (`tsc --strict` — error lines commented so the fence compiles):

```typescript
// bad — two domain objects with the same shape conflate structurally
type User = { id: string; email: string };
type Order = { id: string; totalCents: number };

function shipOrder(order: Order): void {
  console.log(`shipping order ${order.id} for ${order.totalCents}c`);
}

const alice: User = { id: "u_42", email: "alice@example.com" };
const orderA: Order = { id: "o_99", totalCents: 4999 };

// No error today — both have { id: string } — the swap ships to the wrong record:
shipOrder(alice as unknown as Order); // forced via cast — but without cast:
declare let anyUser: User;
declare let anyOrder: Order;
// Structural test with only { id: string } subset collapses entirely:
type UserIdOnly = { id: string };
type OrderIdOnly = { id: string };
declare let uidOnly: UserIdOnly;
declare let oidOnly: OrderIdOnly;
const conflated1: UserIdOnly = oidOnly; // ok — bug: Order id accepted as User id
const conflated2: OrderIdOnly = uidOnly; // ok — reverse also ok
console.log(conflated1.id, conflated2.id); // same string shape, no checker help

// What you WANT the checker to do (will be achieved with branding in §2):
// shipOrder(alice); // should error TS2322 — User is not assignable to Order
// const bad: Order = alice; // should error — missing totalCents AND brand (but today only missing totalCents matters)

// Extra members don't save you — width subtyping allows superset → subset:
type RichUser = { id: string; email: string; role: "admin" };
const richAlice: RichUser = { id: "u_42", email: "alice@example.com", role: "admin" };
const asUser: User = richAlice; // ok — extra role ignored structurally
console.log(asUser.email); // alice@example.com
```

```typescript
type UserUnbranded = { id: string };

}

deleteUserUnbranded(orderUnbranded); // ok — structural alias collapses nominal intent — ships 404 or deletes wrong user

// Even distinct type aliases don't help — alias name is erased:

type OrderIdAlias = string;
function deleteUserByString(id: UserIdAlias): void { console.log(id); }

// Fix for objects → §2 below (intersection brand on the object itself)
```

**Common confusion** — "`type User = { id: string }` and `type Order = { id: string }` are different types because the names differ" — no — aliases are erased; the checker compares `{ id: string }` to `{ id: string }` and finds them identical (see [1.1. Structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>)). "`extends` or `interface` makes it nominal" — `interface User { id: string }` / `interface Order { id: string }` still conflate — `interface` only becomes nominal via `private`/`protected` members, whichPlain data objects should not use. "Extra fields prevent mixing" — only when the target *requires* a field the source lacks — `Order` with `totalCents` vs `User` with `email` still conflates on the shared `{ id: string }` projection. "`OrderId = string` branded in one place protects `{ id: OrderId }`" — partially — the field is branded, but `User = { id: string }` without the branded field still interoperates on the raw string — brand the object *or* brand the shared field type consistently.

**Performance note** — the structural conflation itself has no runtime cost — it is a missing checker error, not extra code. Two distinct `{ id: string }` aliases allocate one object-type node each and compare in `O(members)` (`1` member here) — trivial. The cost is *incident* cost: a swapped `User`/`Order` at runtime still allocates the same `{ id }` object and takes the same `O(1)` property access — you lose time debugging, not cycles. Measure the cure in §2 — it adds zero emit.

**Mentor note** — open with the `User` vs `Order` story from your own incident log — ask "what would the compiler have needed to reject this?" — let the group discover that structural equality *is* the bug. Teach the diagnostic phrase: "same shape, different meaning → needs a brand". Review gate: any PR that introduces a second `{ id: string }` domain type without a brand or a comment `// intentionally shared id shape — generic cursor` is flagged "conflation risk" — require the author to state whether the two id spaces must stay disjoint.

### 2) **Object-level branding** (`type User = { id: string } & { __brand: "User" }`; branded factories hide the assertion; `unique symbol` key variant)

**Definition** — an *object-level brand* adds a phantom property via intersection that exists only in the type graph: `type User = { id: string } & { readonly __brand: "User" }` or the stronger `type User = { id: string } & { readonly [Brand]: "User" }` where `Brand` is a `unique symbol` key. At runtime a `User` is just `{ id: "u_42" }`; at check time the extra `__brand` member makes `User` incompatible with `Order = { id: string } & { __brand: "Order" }`. A *factory* — `function makeUser(id: string): User` — is the single trusted site that performs `as User` after validation; every other module *receives* `User`, never forges it. The `unique symbol` variant guarantees no two brands accidentally share the same string literal.

**What problem it solves / history** — intersection branding for primitives (`string & { __brand }`) landed early (TS 2.x) but object-level branding needed community convergence: a `class` with `private __brand` gave nominality via private identity but imposed construction via `new` and broke plain-data `JSON.parse` round-trips; `enum`-based tags were non-erasable and failed under `erasableSyntaxOnly`. The `__brand` intersection pattern (plain `string` literal, later `unique symbol` key) won because it is *erasable*, *strip-friendly*, and *structural where it matters*: `{ id: string }` stays the runtime shape, the brand only participates in assignment checks. Factories emerged as the discipline answer to "who may `as Brand`?" — one validator per domain concept, audit-able via `grep as User`. The `unique symbol`-key form (`declare const UserBrand: unique symbol; type User = { id: string } & { readonly [UserBrand]: "User" }`) grew after `unique symbol` became a first-class type in domain 02 (see [1.2. bigint and symbol](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.2. bigint and symbol the ES-era primitives.md>)) — it prevents the subtle bug where two brands both pick `__brand` + `"Id"` and still collide on the literal member.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Brand the object when the domain travels as an object** — `type User = { id: string; email: string } & { readonly __brand: "User" }`; `type Order = { id: string; totalCents: number } & { readonly __brand: "Order" }` — callers pass `user`, not `user.id`. When only the scalar crosses boundaries, brand the scalar (primitive pattern in [1.3. Nominal typing techniques](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)) and keep `{ id: UserId }` narrow.
- **Hide every `as Brand` behind a factory that validates** — `makeUser`, `makeOrder` are the only sites that may `as User`/`as Order` — they validate the raw `id` shape (`startsWith("u_")`, `uuid` regex, DB lookup) before asserting. Count `as User` sites — should be ≤ `makeUser` call count; audit via grep.
- **Pick the brand key by collision risk** — `{ __brand: "User" }` is sufficient for app code with 5–15 brands; `unique symbol` key (`[UserBrand]: void` or `[Brand]: "User"`) is the review-mandated form when (a) two teams author brands independently, (b) the object also flows through `JSON.stringify` (symbol keys auto-omit — no leak), or (c) ambient augmentation might touch `__brand`. The `unique symbol` brand has *zero* runtime allocation when used as `& { readonly [UserBrand]: "User" }` on an object (type-only); only `const UserBrand = Symbol("User")` allocates a runtime symbol — use `declare const UserBrand: unique symbol` to stay type-only.
- **Keep the brand `readonly`** — `readonly __brand` / `readonly [UserBrand]` prevents accidental reassignment in type space and documents "phantom — never written at runtime".
- **Do not store the brand at runtime** — never `user.__brand = "User"` — the field is type-only; a runtime value would survive `JSON.stringify`, leak to storage, and require migration of persisted documents.

**Runnable example** — string-literal brand, factory with validation, `unique symbol` key variant, and the unvalidated `as` bad path (`tsc --strict` — error lines commented):

```typescript
// good — object-level branding with string-literal phantom + validated factory
type User = { id: string; email: string } & { readonly __brand: "User" };
type Order = { id: string; totalCents: number } & { readonly __brand: "Order" };

function makeUser(id: string, email: string): User {
  if (!id.startsWith("u_")) throw new Error(`bad user id: ${id}`);
  if (!email.includes("@")) throw new Error(`bad email: ${email}`);
  // single trusted assertion per brand — audit this line
  return { id, email } as User;
}
function makeOrder(id: string, totalCents: number): Order {
  if (!id.startsWith("o_")) throw new Error(`bad order id: ${id}`);
  if (!Number.isInteger(totalCents) || totalCents < 0) throw new Error("bad total");
  return { id, totalCents } as Order;
}

function ship(order: Order): void { console.log(`ship ${order.id} ${order.totalCents}c`); }
function notify(user: User): void { console.log(`notify ${user.email}`); }

const alice = makeUser("u_42", "alice@example.com");
const order99 = makeOrder("o_99", 4999);
ship(order99);   // ok
notify(alice);   // ok
// ship(alice);  // error TS2322: Type 'User' is not assignable to type 'Order' — __brand mismatches
// notify(order99); // error TS2322: Type 'Order' is not assignable to type 'User'

// bad — forging a brand without the factory (validation skipped, brand laundered)
const forged = { id: "o_steal", email: "alice@example.com" } as User; // bad — no makeUser validation, audit misses
notify(forged); // compiles, but forged came from unchecked JSON — runtime email may be attacker-controlled
// fix — never `as User` outside makeUser; force JSON through the factory:
// function userFromJson(raw: unknown): User {
//   if (typeof raw !== "object" || raw === null) throw new Error("bad json");
//   const r = raw as { id: unknown; email: unknown };
//   if (typeof r.id !== "string" || typeof r.email !== "string") throw new Error("bad shape");
//   return makeUser(r.id, r.email); // validated then branded — single assertion site
// }

// emit check — branding erases (npx tsc file.ts --target es2022 --strict):
// function makeUser(id, email) { ... return { id, email }; } — no __brand remains
console.log(JSON.stringify(alice)); // {"id":"u_42","email":"alice@example.com"} — no brand key leaks
```

```typescript
// good — unique symbol key variant — no string-key collision, auto-omitted by JSON
declare const UserBrand: unique symbol;
declare const OrderBrand: unique symbol;

type UserS = { id: string; email: string } & { readonly [UserBrand]: "User" };
type OrderS = { id: string; totalCents: number } & { readonly [OrderBrand]: "Order" };

function makeUserS(id: string, email: string): UserS {
  if (!id.startsWith("u_")) throw new Error("bad id");
  return { id, email } as UserS; // type-only brand — no runtime UserBrand allocation needed (declare const)
}
function makeOrderS(id: string, totalCents: number): OrderS {
  if (!id.startsWith("o_")) throw new Error("bad id");
  return { id, totalCents } as OrderS;
}
declare function shipS(o: OrderS): void;
const aliceS = makeUserS("u_7", "a@b.co");
const orderS = makeOrderS("o_8", 100);
// shipS(aliceS); // error TS2322 — [UserBrand] vs [OrderBrand] distinct symbols
console.log(JSON.stringify(aliceS)); // {"id":"u_7","email":"a@b.co"} — symbol brand never stringifies

// bad — runtime symbol allocation when you meant type-only (import cost, GC note — see Performance)
const RuntimeBrand = Symbol("User"); // allocates a runtime symbol object
type UserR = { id: string } & { readonly [RuntimeBrand]: "User" }; // brand key is a runtime symbol value
// JSON.stringify still omits symbol keys, but you now carry a runtime Symbol per module — prefer declare const when possible
console.log(typeof RuntimeBrand); // symbol — exists at runtime, contrast declare const above which emits nothing

// good — branded factory composes with satisfies / literal preservation (see 3.3)
type Route = { path: string; method: "get" | "post" };
const route = { path: "/users", method: "get" as const } satisfies Route;
console.log(route.method); // get — satisfies keeps literal narrowness, branding would add __brand on domain carriers if needed
```

```typescript
// good — branding survives structural spread only when you re-brand (brand is not auto-copied)
type BrandedUser = { id: string } & { readonly __brand: "User" };
function makeBrandedUser(id: string): BrandedUser {
  if (!id.startsWith("u_")) throw new Error("bad");
  return { id } as BrandedUser;
}
const bu = makeBrandedUser("u_1");
const copy = { ...bu }; // spread produces { id: string; __brand: "User" } structurally? — brand is phantom, no runtime key, but type carries it in this scope
const stillBranded: BrandedUser = copy; // ok — spread preserved the phantom in the type graph here
// Across a function boundary the brand would be lost without the typed return — always return the branded type from helpers
function cloneUser(u: BrandedUser): BrandedUser {
  return { id: u.id } as BrandedUser; // must re-brand — { id: u.id } alone is { id: string }
}
console.log(cloneUser(bu).id); // u_1
```

**Common confusion** — "The brand must be a runtime property" — no — `type User = { id: string } & { __brand: "User" }` never creates `__brand` at runtime; `JSON.stringify(user)` omits it; the checker sees it but `Object.keys(user)` does not. "String literal brand collides silently" — only if two domains pick the same literal *and* the same key name — `"User"` vs `"Order"` never collides; two modules both branding `"Id"` on `__brand` *would* still be compatible — `unique symbol` prevents that. "Factory is boilerplate — I can `as User` at the call site" — each `as` is a proof site that bypasses validation — centralizing to `makeUser` collapses `N` proofs to one. "`declare const Brand: unique symbol` needs no runtime Symbol" — correct — it is type-only; `const Brand = Symbol()` *does* allocate (see Performance). "Branding prevents `any`/`as` laundering" — branding is a *discipline*, not a vault — `any`, `as unknown as User`, and lying type predicates still break it.

**Performance note** — `string & { __brand }` on primitives and `{ id: string } & { __brand }` on objects both erase to the underlying shape — zero emit, zero allocation, zero GC, zero dispatch — the checker adds one property check (`__brand`) per assignment — `O(1)` per branded edge. The `unique symbol` type-only form (`declare const B: unique symbol; & { readonly [B]: "User" }`) also emits nothing — no `Symbol()` call. Only `const B = Symbol("User")` allocates a heap symbol (one per module evaluation, ~32–64 bytes, interned by the engine, `JSON.stringify` ignores it). Checker cost stays negligible for 5–15 brands; prefer `string`-literal brands for app code and reserve type-only `unique symbol` for cross-team boundaries — the type graph cost is identical (`one phantom property`).

**Mentor note** — enforce the factory rule mechanically: `eslint` `no-restricted-syntax` for `as User` / `as Order` outside `factories/*.ts`, or a `grep -R "as User" --include="*.ts" | grep -v factories` CI step — allowlist only `makeUser`. Pair the lesson with a live `grep` demo — run the query on the current codebase and count stray assertions — the reaction is visceral. Exercise: give `const raw = JSON.parse(payload) as { id: string }` and ask to produce `BrandedUser` — correct answer routes through `makeUser(raw.id, raw.email)` after `typeof` checks, not `as BrandedUser` at the parse site. Review checklist: every brand has (a) one `declare const Brand: unique symbol` or `__brand` literal, (b) one `makeX` factory with validation + single `as`, (c) zero other `as X` in the codebase.

### 3) **Cost vs safety** (every branded value needs a validated factory; over-branding fractures composition — brand at module boundaries, not every leaf)

**Definition** — *cost vs safety* is the trade-off that a branded object is *opaque* at every creation site — no literal `{ id: "u_1" }` is a valid `User` without passing the factory's validation and `as` — and that every extra brand partitions the type graph. *Over-branding* is branding every leaf property, intermediate shape, or transient `{ id }` even though the swap would not cause an incident — it fractures composition (`Pick`/`Omit`/spread loses the brand, `&` intersections multiply, hover noise grows) for no safety gain. The rule is: **brand at module boundaries, not every leaf** — validate and brand once when data enters the system; carry the brand inward without re-asserting.

**What problem it solves / history** — early adopters branded *everything*: `UserId`, `UserEmail`, `UserName`, `OrderId`, `OrderTotal`, `MoneyCents`, `MoneyDollars`, `CurrencyCode`, `Percentage` — a 300-file app gained ~40 brands. Two things broke: (1) composition — `type PublicUser = Pick<User, "id" | "email">` stripped the brand (the `Pick` target has no `__brand`), so every helper that returned a projection had to re-brand (`return { id: u.id, email: u.email } as User` — wrong) or stay `PublicUser` (leak); intersections `A & B` where `A` and `B` each carried `__brand` reported conflicting `__brand` literals on merges; (2) boundary cost — every test fixture `makeUser` needed a valid `id` prefix, every story, every `JSON.parse` mock — reviewers started laundering via `as User` to avoid fixtures, which defeated the point. The community correction (handbooks circa TS 4.9–5.9, `erasableSyntaxOnly` era) was to treat branding like validation: one validated entry per domain aggregate, unbranded inside the module, branded at public exports. The remaining `opaque type` proposal would have formalized boundary-only opacity — until it ships, the team convention does.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Brand ~5–15 aggregates, not every leaf** — typical set: `User`, `Order`, `Session`, `Money`, `Percent` + `TenantId`/`OrgId` — roughly one per "if we swapped these the on-call would page". A `User` object brands the *aggregate*; its `email` field inside stays `string` unless email-swap itself pages on-call.
- **Validate at the factory, brand once per boundary crossing** — `POST /users`, `JSON.parse`, `db.rowToUser`, `queue.consumeOrder` each call `makeUser`/`makeOrder` — inner helpers `formatUser(user: User): string`, `total(order: Order): number` just *receive* `User`/`Order` — never re-validate or re-brand.
- **Keep unbranded shapes for composition** — derive public/projection shapes from the unbranded core when you must project:
  ```typescript
  type UserCore = { id: string; email: string };
  type User = UserCore & { readonly __brand: "User" }; // branded public
  type PublicUser = Pick<UserCore, "id">; // unbranded projection — no brand friction
  ```
  Project via `UserCore`, export `User` — `Pick`/`Omit`/`Partial` on `UserCore` never touches the brand.
- **Structure factories as validators** — throw or `Result<User, ValidationError>` — callers learn that `makeUser` *proves* the `u_` prefix / `uuid` / non-empty email. For `unknown` ingress (network, storage) parse with `zod`/`valibot` then `makeUser` — never `as User` on raw `unknown`.
- **Lint the boundary** — custom rule or `grep` count: `as User` sites should equal factory sites (1 per brand). Any extra `as` is a laundering attempt — block the PR.

| Situation | Brand? | Why |
|---|---|---|
| Public export `User` / `Order` that crosses API/storage/queue | Yes — `User & { __brand }` via `makeUser` | Swap = incident — pay the factory cost once |
| Internal leaf `{ id: string }` inside a single function | No — `UserCore` or plain `{ id: string }` | No boundary — branding just fractures the local `Pick` |
| Transient projection `Pick<User, "id">` / `Omit<Order, "totalCents">` | No — derive from `UserCore`/`OrderCore` | Branded `Pick` strips/loses the brand — rebuild cost |
| Scalar that crosses teams (`cents`, `percent`, `tenantId`) | Field-level brand (see [1.3. Nominal typing techniques](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)) | Scalar swap pages — brand the unit, not every carrier |
| Mass test fixtures (100+ literals) | Brand via one `makeUser` loop, not 100 `as User` | Keep assertion sites auditable — generate fixtures through factory |

Both brand and core erase — no emit difference (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**Runnable example** — boundary branding good, leaf over-branding and projection fracture bad (`tsc --strict` — error lines commented):

```typescript
// good — brand the aggregate at the boundary, compose on the unbranded core
type UserCore = { id: string; email: string };
type User = UserCore & { readonly __brand: "User" };
type OrderCore = { id: string; totalCents: number };
type Order = OrderCore & { readonly __brand: "Order" };

function makeUser(id: string, email: string): User {
  if (!id.startsWith("u_")) throw new Error("bad user id");
  if (!email.includes("@")) throw new Error("bad email");
  return { id, email } as User;
}
function makeOrder(id: string, totalCents: number): Order {
  if (!id.startsWith("o_")) throw new Error("bad order id");
  return { id, totalCents } as Order;
}

  if (typeof raw !== "object" || raw === null) throw new Error("bad json");

  if (typeof r.id !== "string" || typeof r.email !== "string") throw new Error("bad shape");
  return makeUser(r.id, r.email); // single brand site — audit here
}

function lifetimeValue(orders: Order[]): number {
  return orders.reduce((sum, o) => sum + o.totalCents, 0);
}
```

**Common confusion** — "More brands = more safety" — up to ~15, yes; past that composition cost dominates and teams launder via `as` to avoid factories — net safety drops. "`Pick<User, 'id'>` keeps the brand" — `Pick` copies listed keys — if `__brand` is not listed it is dropped; if it is listed via `Pick<User, 'id' | '__brand'>` you carry phantom noise to callers that never needed it. "`as User` in tests is harmless" — it seeds unchecked literals that drift from factory validation — the next refactor changes the `u_` prefix rule and only factory-built tests fail — `as`-built tests stay green while production breaks. "`opaque type` already exists" — not stable as of TS 5.9 era — the proposal `opaque type User = { id: string }` would give boundary-only opacity without intersection tricks, but until it ships the factory pattern is the contract. "I should brand numbers like `totalCents` on every math helper" — brand the `Money` *aggregate* (`{ cents: number } & { __brand: "Money" }`) at the currency boundary; inside `centsToDollars` arithmetic, plain `number` composes without brand friction — validate at conversion, not every `+`.

**Performance note** — cost is checker graph, not runtime. One branded object (`User`) adds one phantom property node per assignment check — still `O(1)`. Forty leaf-level brands on a single module's locals inflate the type graph to ~40 extra property checks per helper that touches them — `O(brands)` per call site — visible in `tsc --extendedDiagnostics` `instantiations` count (e.g., 300-file app with 8 brands: ~2k instantiations; same app branded at every leaf — 40 brands — ~8k instantiations, +10–15 ms check time). Runtime remains zero — every brand erases — but language-server hover on `Pick`/`Omit` of heavily branded objects expands each `& { __brand }` and truncates. Over-branding's `clone` that does `as OverUser` per derived shape also pressures the checker to re-validate the intersection — measure with `tsc --generateTrace trace/` and budget brands like allocations: brand only what would page.

**Mentor note** — draw the boundary diagram: ingress (`JSON`/`DB`/`queue`) → `makeUser`/`makeOrder` → *unboxed* interior (`format`, `total`, `toPublic`) → egress — tell students "the factory is the airlock — dirt stays outside". In review, ask: "if we swapped this object's brand, would prod notice within one hour?" — *yes* → brand at the airlock; *no* → leave it `UserCore`. Exercise: hand a PR that introduces `type Comment = { id: string; postId: string; authorId: string } & { __brand: "Comment" }` with three leaf brands inside and ask to (a) count `as` sites, (b) rewrite to one aggregate brand on `CommentCore`, and (c) write the `commentFromJson` boundary that calls `makeComment`. Gate: any PR that adds a brand must add a factory + a boundary call site + a test-fixture helper in the same commit — otherwise block as "brand without airlock".
