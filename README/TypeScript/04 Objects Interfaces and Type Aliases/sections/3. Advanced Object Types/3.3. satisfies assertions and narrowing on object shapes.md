## 3.3. satisfies assertions and narrowing on object shapes

When building an object, choose which information its type should expose. When consuming an object union, establish which branch is available before reading a branch-specific member. Those are related tasks, but a checked literal, an assertion and a runtime presence test provide different evidence.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Save each named file in a new directory without tsconfig.json. For positive examples run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. Keep intentional failures commented until the negative exercise. The optional-property contrast specifies a separate default-mode check.

### 1) **Choose a checked source, exposed contract or assertion**

An annotation exposes the declared target type. A satisfies check verifies compatibility while retaining the expression's inferred type, including contextual information supplied by the target. An assertion asks the compiler to treat the expression as the asserted type; it is not a validator. An assertion can widen or narrow depending on that target. It does not universally turn literals into string.

Save `contracts.ts`:

```typescript
export {};
type Route = { path: string; method: "get" | "post" };
const annotated: Route = { path: "/users", method: "get" };
const checked = { path: "/users", method: "get" } satisfies Route;
const asserted = { path: "/users", method: "get" } as Route;
const literal = "get" as "get"; // an assertion can expose a narrower target too

type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type CheckedMethod = Expect<Equal<typeof checked.method, "get">>;
type CheckedPath = Expect<Equal<typeof checked.path, string>>;
type AnnotatedMethod = Expect<Equal<typeof annotated.method, "get" | "post">>;
type AssertedMethod = Expect<Equal<typeof asserted.method, "get" | "post">>;
type NarrowAssertion = Expect<Equal<typeof literal, "get">>;
console.log(checked.path, checked.method); // /users get
console.log(annotated.method, asserted.method, literal); // get get get

const excessAccepted = { path: "/a", method: "get", extra: true } as Route;
const wrong = { path: "/a", method: "DELETE" } as unknown as Route;
console.log(Object.hasOwn(excessAccepted, "extra"), wrong.method); // true DELETE
// const excessChecked = { path: "/a", method: "get", extra: true } satisfies Route; // TS2353
// const wrongChecked = { path: "/a", method: "DELETE" } satisfies Route; // TS2322
// const tooNarrow: "get" = asserted.method; // TS2322: exposed union is wider
```

The checked method retains get because the target provides a literal-union context; the path is still string. Therefore satisfies is not a promise that every value stays a singleton literal or that every expression would infer exactly the same type without context. The live checks establish these particular results. The runtime outputs also show that erased assertions neither remove extra data nor change DELETE into a legal method.

Use satisfies when the source's checked precision serves later derivation. Use a broader annotated contract when clients must see that contract, including permitted mutations. Use an assertion when independently justified information is unavailable to the checker, and make the justification reviewable. For unknown input, obtain the evidence by parsing; do not assert a type merely to suppress its missing proof. The [4.9 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator) introduce the check; the object-shape owner explains its creation-site excess checks.

### 2) **Const assertions describe literal structure without freezing it**

A const assertion preserves literal values and marks the literal's properties readonly; nested literal arrays become readonly tuples. It is useful when a table's actual values are part of its type contract. It does not freeze objects at runtime, and a referenced mutable object is not recursively converted into an immutable object by placing its reference inside a const-asserted literal.

Save `tables.ts`:

```typescript
export {};
type Route = { path: string; method: "get" | "post" };
const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "post" },
} as const satisfies Record<string, Route>;
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Keys = Expect<Equal<keyof typeof ROUTES, "home" | "users">>;
type HomePath = Expect<Equal<typeof ROUTES.home.path, "/">>;
console.log(ROUTES.home.path, ROUTES.users.method); // / post
// ROUTES.home.method = "post"; // TS2540: readonly member

const shared = { count: 1 };
const view = { shared, nested: { count: 1 } } as const;
view.shared.count = 2; // referenced mutable object's member remains mutable
console.log(view.shared.count, view.nested.count); // 2 1
console.log(Object.isFrozen(view), Object.isFrozen(view.nested)); // false false
// view.nested.count = 2; // TS2540: this nested literal's member is readonly

Object.freeze(view);
console.log(Object.isFrozen(view), Object.isFrozen(view.nested)); // true false
shared.count = 3; // shallow freeze does not freeze the referenced object
console.log(view.shared.count); // 3
```

The combined assertion/check validates the table values and retains their literal/readonly type. It is a good fit for this table because editing an entry is not part of the intended API. A builder needing to change get to post can instead expose Route for that mutable slot; a mutable property inferred as only get still rejects post for its value type. Readonly and accepted value range are independent questions.

The runtime freeze operation is separate and shallow. Use the existing integrity owner for deeper runtime policies rather than assuming `as const satisfies` supplies them. Deriving only a key union does not require const assertions in every case; choose the retained member precision that the consumer actually needs.

### 3) **Narrow a declared object union with actual branch evidence**

A declared union can already supply a discriminant. Circle and Square below each have a required kind with a distinct literal value, so equality or switch narrowing selects a branch. The [2.0 tagged-union notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-0.html#tagged-union-types) demonstrate this mechanism before const assertions and satisfies existed. Those newer features can help construct a suitable literal; they are not prerequisites for union narrowing.

Save `branches.ts`:

```typescript
export {};
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default: { const complete: never = shape; return complete; }
  }
}
console.log(area({ kind: "circle", radius: 4 }).toFixed(1), area({ kind: "square", side: 5 })); // 50.3 25
function broadCheck(shape: Shape): void {
  if (typeof shape.kind === "string") {
    // shape.radius; // TS2339: both branch tags are strings
    console.log(shape.kind);
  }
}
broadCheck({ kind: "square", side: 5 }); // square

// A presence test can narrow a declared union whose members differ by key.
type UserObj = { id: string; email: string };
type OrderObj = { id: string; totalCents: number };
type Entity = UserObj | OrderObj;
function describe(entity: Entity): string {
  if ("email" in entity) return `user ${entity.email}`;
  return `order ${entity.totalCents}c`;
}
class InheritedUser {
  id = "u_1";
  get email(): string { return "a@b.co"; }
}
const inherited: UserObj = new InheritedUser();
console.log(describe(inherited)); // user a@b.co
console.log("email" in inherited, Object.hasOwn(inherited, "email")); // true false
function ownBoolean(entity: Entity): boolean {
  if (Object.hasOwn(entity, "email")) {
    // entity.email; // TS2339: the own-property boolean did not narrow Entity
  }
  if (entity.hasOwnProperty("email")) {
    // entity.email; // TS2339 here too
  }
  return Object.hasOwn(entity, "email");
}
console.log(ownBoolean(inherited)); // false: does not turn this UserObj into OrderObj
```

The in operator checks the prototype chain as well as own properties. The typed inherited User is therefore correctly described as a User. Its lack of an own email is a different fact. Object.hasOwn and hasOwnProperty return boolean in this compiler's installed declarations and do not automatically narrow this Entity union; the rejected accesses make that limitation visible. Do not cast the false branch to Order merely because the own email check failed.

Presence alone also cannot prove an arbitrary unknown value's whole domain shape. The in branch here starts from the declared Entity contract. At an input boundary, validate the member's value and all other required fields. A justified custom predicate may communicate the result to the checker, but the compiler trusts its declaration; the implementation still needs evidence for both success and failure.

Save `presence.ts` for a small own-email value contract, rather than claiming to prove a whole User:

```typescript
export {};
function ownEmail(raw: unknown): string | undefined {
  if (typeof raw !== "object" || raw === null || Array.isArray(raw)) return undefined;
  if (!("email" in raw) || !Object.hasOwn(raw, "email")) return undefined;
  const value: unknown = raw.email;
  return typeof value === "string" ? value : undefined;
}
console.log(ownEmail({ email: "a@b.co" })); // a@b.co
console.log(ownEmail({ email: 42 }), ownEmail(null)); // undefined undefined
class Inherited { get email(): string { return "inherited@b.co"; } }
console.log(ownEmail(new Inherited()), ownEmail({})); // undefined undefined

type Contact = { id: string; email?: string } | { id: string; phone?: string };
function contactEmail(contact: Contact): string | undefined {
  if ("email" in contact) {
    const present: string = contact.email; // accepted with exactOptionalPropertyTypes
    return present;
  }
  // contact.phone; // TS2339: an email-shaped member can also omit email
  return undefined;
}
console.log(contactEmail({ id: "u", email: "a@b.co" }), contactEmail({ id: "u" })); // a@b.co undefined
```

For `email?: string`, the exact-optional contract excludes an explicitly undefined value when that property is present. The positive in branch can read string with that option enabled. Recheck presence.ts using the same compiler flags but omit `--exactOptionalPropertyTypes` and add `--noEmit`: TS2322 rejects present because the default contract also permits a present undefined value. With `email?: string | undefined`, guard the value in either mode. The false presence branch can still contain a member that omitted its optional email; it is not necessarily the phone branch. The modifier owner gives the full optional matrix.

The ownEmail function establishes only an own string-valued email member. It accepts no claim about id, account ownership or email validity, and it does not harden property access against arbitrary getters/proxies. Use the fuller parsing owner when a complete domain value is required.

### 4) **Common confusion**

Satisfies checks compatibility; it does not run a parser, freeze a value or preserve every property as a literal. Asserting Route exposes Route rather than necessarily preserving the initial get member. A const assertion changes the literal's static view, while Object.freeze changes a runtime object's integrity.

An own-property test answers a different question from a discriminant or in guard on a declared union. A boolean method does not acquire a predicate return type merely because its name sounds like a guard. Optional members can remain in more than one control-flow branch; consider the exact-optional setting and the property's value contract before accessing a value.

### 5) **Performance note**

The type operators erase. The in, typeof, equality, Object.hasOwn and Object.freeze expressions still execute as JavaScript. There is no measured checker-complexity formula, universal property-probe timing or union-size threshold in these examples. Guard according to the contract you need, then measure real hot paths if their runtime work matters. An own-property check may reject data a prototype-aware model accepts; a speed preference cannot decide that semantic policy.

Ask which contract each value in contracts.ts exposes and why checked.path is string even though checked.method is get. Require the live probes rather than an untested hover claim. Next predict whether view.shared.count can change and whether shallow freeze freezes view.nested.

For narrowing, remove the comments from the own-boolean accesses and explain TS2339. Replacing them with a cast hides the missing inference instead of establishing the branch's shape.
