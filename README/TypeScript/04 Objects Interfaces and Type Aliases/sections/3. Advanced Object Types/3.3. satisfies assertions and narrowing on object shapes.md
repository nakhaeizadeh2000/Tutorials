## 3.3. satisfies assertions and narrowing on object shapes

`satisfies`, `as`, and `as const` are the three value-site assertions that pair with object types — and `in` / `typeof` / `hasOwnProperty` are the three narrowing tools that refine an object union back to a single shape. This leaf ties them together for object shapes: when `satisfies` keeps literal narrowness while checking, when `as const` adds deep `readonly` for config tables, and which narrowing test to reach for in everyday object-union code — with the full discriminated-union system deferred to domain 07.

---

### 1) **satisfies vs as on objects** (satisfies checks shape while preserving literal narrowness; as widens and silences)

**Definition** — `satisfies T` is a *checker-only* constraint — "check that this literal satisfies `T`, but keep its *inferred* literal type" — while `as T` is an *assertion* — "treat this value as `T` exactly, disable the excess-property freshness check, and *widen* away literal identity". For objects: `{ path: "/users", method: "get" } satisfies Route` checks `Route` and preserves `"get"` as `"get"`; the same literal `as Route` widens `method` to `"get" | "post"` and silences an excess or typo inside the literal.

**What problem it solves / history** — before TS 4.9 there were two bad escapes for a literal that should satisfy an object target. Routing a fresh literal through an untyped variable dropped freshness (typo/excess leaked), and `as Target` disabled checking at the literal site and forced the variable to `Target` — downstream callers lost literal narrowness that `keyof`/`typeof` and route-table helpers needed. `as` also laundered unsound payloads (`as unknown as Target`). `satisfies` (added TS 4.9, idiomatic as of the TypeScript 5.9 era) was introduced precisely to say "validate the shape *here* without widening the source" — it runs the same excess-property / assignability check as a fresh assignment but leaves the source's literal union intact for the next inference step. The primitive/literal ground truth is established in [3.3. Literal types and const assertions](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>) and the object-level sealing cases in [1.1. Object types structural shape](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) — this section covers the object-shaped consequences.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Need a config/route/theme literal validated without losing its inferred literals** → `satisfies` at the literal site — `const route = { path: "/users", method: "get" } satisfies Route` — `route.method` stays `"get"`, typos/excess (`methd`, `extra`) still error `TS1360`/`TS2353` at that line, and hover shows the narrowed literal for `typeof` capture (see [2.3. Type queries on objects](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>)).
- **Need to narrow or widen intentionally when the checker cannot see the proof** → `as` *with a comment* explaining the invisible proof — e.g., `JSON.parse(raw) as Route` after a `zod` parse — otherwise block `as` in review.
- **Need both readonly and literal preservation on an object table** → `as const satisfies T` (see §2 below) — `satisfies` checks, `as const` narrows+freezes the type graph — the two compose.
- **`satisfies` never replaces runtime validation** — it is still erased (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)) and has no emit — ingress from network/storage still goes through `zod`/`valibot` first.

**Runnable example** — `satisfies` preserves literal and catches excess; `as` widens, silences, and erases the literal (`tsc --strict` — error lines commented so the fence compiles):

```typescript
// good — satisfies checks Route while preserving "get" literal
type Route = { path: string; method: "get" | "post"; secure?: boolean };

const routeOk = { path: "/users", method: "get" } satisfies Route;
// routeOk.method is "get" (literal), not "get" | "post" — downstream keeps narrowness:
const methodOk: "get" = routeOk.method; // ok — literal preserved

// satisfies still catches typos and excess at the literal site:
 // const typo = { path: "/users", methd: "get" } satisfies Route; // error TS1360: 'methd' does not exist in type 'Route'
 // const excess = { path: "/users", method: "get", extra: true } satisfies Route; // error TS2353: 'extra' does not exist

// good — as const satisfies when you also want deep readonly (see §2 for why)
const routeFrozen = { path: "/users", method: "get" } as const satisfies Route;
// routeFrozen.method is readonly "get"

// derive from the satisfied literal — typeof capture keeps the literal because satisfies preserved it
type MethodOfOk = typeof routeOk["method"]; // "get" — not widened

console.log(routeOk.path, routeOk.method); // /users get
console.log(routeFrozen.method); // get
```

```typescript
// bad — as widens to exactly Route and silences the same mistakes (contrast with above)
type Route = { path: string; method: "get" | "post"; secure?: boolean };

const routeCast = { path: "/users", method: "get" } as Route;
// routeCast.method is "get" | "post" (widened) — literal identity lost:
 // const methodLost: "get" = routeCast.method; // error TS2322: Type '"get" | "post"' is not assignable to type '"get"'

type MethodOfCast = typeof routeCast["method"]; // "get" | "post" — widened, less useful for derived tables

// bad — as silences typos inside a nested object literal (freshness bypass):
const routeSilenced = { path: "/users", method: "get", extra: true } as Route; // ok at literal site — excess not reported
console.log(routeSilenced.path); // /users — bug: extra survived silenced and may be read later as valid config

// bad — double assertion launders an invalid shape:
const laundered = { path: "/users", method: "DELETE" } as unknown as Route; // compiles — runtime 405 later
console.log(laundered.method); // DELETE — checker silence, production mismatch
// fix — return to satisfies so the bad method errors where written:
 // const fixed = { path: "/users", method: "DELETE" } satisfies Route; // error TS2322: '"DELETE"' is not assignable to '"get" | "post"'
```

```typescript
// good — satisfies composes with object composition (extends/&); as does too but hides literal
type Route = { path: string; method: "get" | "post"; secure?: boolean };
type Audited = { createdAt: string };
type RouteAudited = Route & Audited;

const auditedOk = { path: "/a", method: "post", createdAt: "2026-09-02" } satisfies RouteAudited;
const auditedMethod: "post" = auditedOk.method; // preserved through intersection

const auditedCast = { path: "/a", method: "post", createdAt: "2026-09-02" } as RouteAudited;
 // const auditedMethodLost: "post" = auditedCast.method; // error — widened through & as well

console.log(auditedOk.createdAt); // 2026-09-02

// sealing note — the same three seals from 1.1 still apply; satisfies is the literal-site seal:
 // wider-target and annotated-binding are the other two — see [1.1. Object types structural shape](<../1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>)
```

**Common confusion** — "`satisfies` narrows the variable to `T`" — no — `satisfies T` does *not* change the variable's type to `T`; it checks assignability to `T` and keeps the source literal (`"get"`). `as T` *does* force the variable to `T`. "`satisfies` has runtime or emit cost" — none — it erases like every annotation (safe under `--erasableSyntaxOnly`). "`as` is the same as `satisfies` but shorter" — `as` disables freshness/excess checks at the literal and widens; `satisfies` preserves both checks *and* literals. "`as unknown as T` is okay for JSON" — it bypasses every shape check; validate first (`zod`/`valibot`) then `satisfies` or a typed factory. "`satisfies` alone makes the object `readonly`" — it does not — only `as const` adds `readonly` (see §2).

**Performance note** — `satisfies` and `as` both erase — zero emit, zero allocation, zero GC, zero dispatch. The checker cost of `satisfies` is one extra assignability check at the literal site — `O(members)` on the object, usually 3–8 properties — trivial. `satisfies` can *reduce* downstream checker work: preserving `"get"` avoids instantiating a generic that would branch over `"get" | "post"`. Hundreds of `as` launderings do not cost checker time but hide assignability work that reappears as runtime bugs — measure not speed but incident count.

**Mentor note** — teach the litmus: "is the literal the source of truth?" — *yes* → `satisfies T` at the literal; *no, the consumer is the truth* → widen the consumer (`& { extra?: ... }`) or annotate the binding. Pair with a PR exercise: give three `as Route` literals and ask to convert one to `satisfies`, one to an annotated `const route: Route`, one to a wider param — discuss why the same `as` was wrong three ways. In review, require every `as Target` on a literal to carry a `// proof:` comment or be replaced — `grep -R " as [A-Z]" --include="*.ts"` should return mostly `as const`.

### 2) **as const on objects** (deep readonly + literal types for config/theme/route tables — when to use over satisfies)

**Definition** — `as const` is a *const assertion* that makes every property in the literal `readonly` and narrows every value position to its *literal type*: `{ retry: 3, mode: "fast" } as const` becomes `{ readonly retry: 3; readonly mode: "fast" }` (not `{ retry: number; mode: string }`). The `readonly` is shallow in the *type syntax* but deep in effect on object literals — nested objects and arrays inside also become `readonly` with literal elements. Unlike `satisfies`, it does **not** by itself validate against a target shape — it just refines what you wrote.

**What problem it solves / history** — config/theme/route tables were first written as mutable widened objects: `const theme = { colors: { primary: "#0ea5e9" }, spacing: [4,8] }` inferred `colors: { primary: string }` and `spacing: number[]` — literal identity (`"#0ea5e9"` vs `string`, `4` vs `number`) was lost, `keyof typeof theme` still worked but `typeof theme.spacing[number]` collapsed to `number` and `Theme["colors"]["primary"]` was not a usable literal union. Teams either annotated the whole table (`const theme: Theme = {...}`) and lost derivation, or sprinkled `as Theme` and widened callers. `as const` (TS 3.4) solved the literal+`readonly` half; `satisfies` (TS 4.9) solved the validation half; `as const satisfies T` (idiomatic as of TS 5.9 era) composes them — check the shape *and* keep literals *and* mark readonly — the table is both validated and derivation-ready for `keyof`/`T[K]`/`typeof` (see [2.3. Type queries on objects](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>)). This leaf focuses on the object-table consequences; the primitive/tuple ground truth lives in [3.3. Literal types and const assertions](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Object table whose *literals* are the API** (route table, theme tokens, feature-flag map where `keyof` and `value` unions are derived) → `as const` (or `as const satisfies Shape` when a shape target exists). `const ROUTES = { home: { path: "/", method: "get" } } as const` gives `typeof ROUTES["home"]["method"]` = `"get"` and prevents accidental reassignment in type space.
- **Object literal that must stay *mutable* but still preserve narrowness for callers** → `satisfies` alone — `const route = { path: "/users", method: "get" } satisfies Route` keeps `"get"` but leaves the property mutable so callers that *do* mutate (test shims, builder pattern) are not blocked.
- **Need both — validated + readonly + literal** → `as const satisfies T` — evaluation order is `(... as const) satisfies T` — the literal narrows first (good), then is checked against `T` (typo/excess still errors). Use this for exported `THEME`/`ROUTES` constants; keep builder interiors `satisfies`-only.
- **`as const` is type-level only** — runtime mutation is still possible via `any`/index — pair with `Object.freeze` when the *runtime* promise matters (see [1.2. Optional readonly and index signatures](<../1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) — `readonly` without `freeze` is checker-only).

**Runnable example** — `as const` deep `readonly` + literals for a route table vs `satisfies`-only mutable vs combined `as const satisfies` validated — good vs bad (`tsc --strict` — error lines commented):

```typescript
// good — as const gives deep readonly + literals, perfect for derivation via typeof/keyof
const THEME = {
  colors: { primary: "#0ea5e9", background: "#ffffff" },
  spacing: { sm: 4, md: 8, lg: 16 },
  radii: ["none", "sm", "md"] as const, // inner as const already, outer would also cover
} as const;

type Theme = typeof THEME;
// Theme["colors"]["primary"] is "#0ea5e9" (literal), not string — derivation preserved
type Primary = Theme["colors"]["primary"]; // "#0ea5e9"
const primaryOk: Primary = "#0ea5e9"; // ok — literal
 // const primaryBad: Primary = "#ff0000"; // error — not the literal

type Radius = Theme["radii"][number]; // "none" | "sm" | "md" — union from as const tuple
const r: Radius = "sm"; // ok

 // THEME.colors.primary = "#000"; // error TS2540: Cannot assign to 'primary' because it is a read-only property.
 // THEME.spacing.sm = 99; // error TS2540 — deep readonly (object inside object)

console.log(THEME.colors.primary); // #0ea5e9
console.log(THEME.radii.length); // 3
```

```typescript
  users: { path: "/users", method: "post" },

routesChecked.home.method = "get"; // ok — mutable (no readonly); different literal would error: "post" not in "get"
// routesChecked.home.method = "DELETE"; // error — "DELETE" not in literal "get" — demonstrates literal lock from satisfies

  home: { path: "/", method: "get" },
  users: { path: "/users", method: "post" },
} as const;
type ConstMethod = typeof routesConst["home"]["method"]; // "get" — also literal + readonly
 // routesConst.home.method = "post"; // error TS2540 — readonly (as const)

  home: { path: "/", method: "get" },
```

```typescript
}
const base: Route = { path: "/a", method: "get" };
console.log(withSecure(base).secure); // true

// bad — editing a readonly derived value without the mapped modifier
 // function mutate(table: typeof ROUTES): void { table.home.method = "post"; } // error TS2540 — readonly table entry
// fix — accept MutableRoute inside the mutating helper, not typeof ROUTES directly
```

**Common confusion** — "`as const` makes the object immutable at runtime" — it makes *types* `readonly`; runtime mutation via `(x as any).k = v` still lands — add `Object.freeze` (shallow) or deep-freeze helper when you promise runtime immutability. "`const x = { method: \"get\" }` preserves the literal" — no — `const` alone still widens object-property literals (`method: string`); only `as const` narrows them (see [2.3. Type queries on objects](<../2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>) and the `typeof` trapping note). "`as const satisfies T` checks after widening" — it narrows first (`as const`) then checks (`satisfies`), so typo/excess still errors — the order is `(x as const) satisfies T`, not widen-then-check. "`satisfies` alone already gives `readonly`" — it does not — `satisfies` preserves mutability; `as const` adds `readonly`. "I must pick one: either `as const` *or* `satisfies`" — compose — `as const satisfies T` is idiomatic for exported tables; use `satisfies` alone inside mutable builders.

**Performance note** — `as const` erases — zero emit, zero allocation, zero GC — the literal and `readonly` are checker-only. The checker cost is one traversal of the literal's value positions (members × depth) to literalize — negligible for route/theme tables with 20–50 entries. Very large `as const` tables (hundreds of keys with nested objects) inflate the hover/type display more than check time — hover starts truncating past ~100 keys — split into `theme/colors.ts` / `theme/spacing.ts` if hover or `tsc --extendedDiagnostics` `instantiations` grows. `as const satisfies` costs the same as `as const` + one `satisfies` assignability check — still `O(members)`.

**Mentor note** — demo the widening trap side-by-side: `const a = { method: "get" }` vs `const b = { method: "get" } as const` — hover both and ask which gives `typeof` literal `"get"` (answer: `b`). Review rule: every exported constant table (`THEME`, `ROUTES`, `FEATURES`) that is consumed via `keyof typeof`/`T[K]` must be `as const` (or `as const satisfies`) — flag bare `const table = {...}` without either as "derivation-lost". Exercise: give `const routes = { home: { path: "/" } }` and ask to (a) derive `type RouteKey = keyof typeof routes`, (b) make `method` a literal union, then (c) add `satisfies RouteTable` so a typo `methd` errors at the literal — correct answer lands on `as const satisfies RouteTable`. Pair with `Object.freeze` when the table crosses a trust boundary.

### 3) **Narrowing object unions** (in, typeof on discriminant, hasOwnProperty — the narrowing tools that pair with object types; full discriminated-union treatment in 07)

**Definition** — *narrowing an object union* is letting the checker eliminate branches of a union of object shapes (`A | B`) inside a control-flow branch. Three tools pair directly with object types: (1) the **`in` operator** — `"prop" in obj` tests whether an object has a given property key; (2) **`typeof` on a discriminant** — `typeof obj.kind === "string"` or the stricter `obj.kind === "circle"` equality narrowing on a common literal-typed property; (3) **`hasOwnProperty` / `Object.hasOwn`** — `obj.hasOwnProperty("radius")` or `Object.hasOwn(obj, "radius")` (ES2022) as the own-property variant. All three are *type guards* — after the `if`, the checker narrows `obj` to the branch that could have the tested property/value.

**What problem it solves / history** — a union of object shapes `type Shape = { kind: "circle"; radius: number } | { kind: "square"; side: number }` carries *either* shape at runtime, but the checker must prove which member it holds before allowing member access (`shape.radius` is unsafe on `square`). Early TypeScript relied on plain `if ("radius" in shape)` and user-defined predicates (`function isCircle(...): ... is Circle`). `typeof` narrowing on a discriminant (`shape.kind === "circle"`) grew as literal types became central (blocked until `satisfies`/`as const` could keep `kind` literal — see §§1–2). `hasOwnProperty` narrowing support arrived incrementally (TS 5.5 refined `hasOwnProperty` as a guard in some patterns; `Object.hasOwn` is the `ES2022` static form) — not every `hasOwnProperty` call narrows without a predicate wrapper, so `in` remains the most reliable built-in object-property guard. Full discriminant-union theory — common property, exhaustive `never`, `switch` on the discriminant — is owned by [07 Unions, Intersections and Narrowing](<../../07 Unions Intersections and Narrowing/README.md>) (textual forward until that domain lands); this section covers only the *object-type pairing* you need alongside domains 01–04.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS):

- **Union branches distinguished by a shared literal property (`kind`, `type`, `status`)** → narrow on that discriminant with equality — `if (shape.kind === "circle")` or `switch (shape.kind)` — the checker eliminates every branch whose discriminant literal cannot match (see exhaustive pattern in Runnable). This is the preferred narrow for modelled unions — conjunction with `satisfies`/`as const` keeps `kind` literal so the check stays precise.
- **Union branches distinguished by *different* property names (`radius` vs `side`, `email` vs `totalCents`)** → narrow with `"prop" in obj` — `if ("radius" in shape) { shape.radius }` — the checker keeps only members that *could* have `radius` (one caution below — `in` is less precise on optional members). Guard against inherited properties in security-sensitive code — use `Object.hasOwn`/`hasOwnProperty` when the prototype matters.
- **Need own-property only (prototype-carrying objects, `Object.create`)** → `Object.hasOwn(obj, "prop")` or `obj.hasOwnProperty("prop")` — note: plain `hasOwnProperty` narrowing requires TS 5.5+ and may need a predicate wrapper in some `strict` configurations — `in` is the fallback that always narrows on object unions.
- **`typeof` *on the object's discriminant value*** — `if (typeof shape.kind === "string")` — rarely narrows a union by itself (both branches have `kind: string`); narrow by value equality instead: `shape.kind === "circle"`. Use `typeof` to guard a *non-discriminant* field first — `if (typeof point.x === "number")` — then access object members.
- **After narrowing, avoid re-widening via `any`/`as`** — a narrowed `Circle` stays `Circle` until an `as` widens it; do not cast away the narrowed branch to reuse a helper typed for the wider union without proving the discriminant again at the call site.

**Runnable example** — `in`, `Object.hasOwn`, and discriminant `===`/`switch` narrowing on object unions — good vs bad (`tsc --strict` — error lines commented):

```typescript
// good — discriminant equality narrowing (preferred for modelled unions — exhaustive switch, never on default)
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Triangle = { kind: "triangle"; base: number; height: number };
type Shape = Circle | Square | Triangle;

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2; // narrowed to Circle — radius allowed
    case "square": return shape.side ** 2;               // narrowed to Square
    case "triangle": return 0.5 * shape.base * shape.height;
    default: {
      const _ex: never = shape; // exhaustiveness via never — see 07 for full system
      return _ex;
    }
  }
}

const c: Shape = { kind: "circle", radius: 4 } as const satisfies Shape; // kind stays "circle" — as const + satisfies
const s: Shape = { kind: "square", side: 5 } satisfies Shape;
console.log(area(c).toFixed(1), area(s)); // 50.3 25
```

```typescript
// good — "prop" in obj narrowing for property-name-distinguished unions; hasOwnProperty / Object.hasOwn as own-property form
type UserObj = { id: string; email: string };
type OrderObj = { id: string; totalCents: number };
type Entity = UserObj | OrderObj; // no shared discriminant — distinguish by member name

function describe(e: Entity): string {
  // "email" in e keeps only members that could have email (UserObj) — narrows the union
  if ("email" in e) {
    return `user ${e.email}`; // narrowed to UserObj — email allowed, totalCents not
    // e.totalCents; // error TS2339: Property 'totalCents' does not exist on type 'UserObj'
  } else {
    return `order ${e.totalCents}c`; // else branch — only OrderObj remains
  }
}

// good — own-property narrowing (use when prototype pollution matters)
function describeOwn(e: Entity): string {
  // Object.hasOwn is the ES2022 static form — own property only, not inherited
  if (Object.hasOwn(e, "email")) {
    // In TS 5.9 this narrows similarly to "in" for many object-union shapes; on older configs use a predicate wrapper
    return `own user ${(e as UserObj).email}`; // hasOwn narrowing may need assertion on older toolchains — prefer "in" when the chain is plain objects
  }
  return `own order ${(e as OrderObj).totalCents}c`;
}

// good — typeof on a discriminant's value is equality, not typeof the kind string
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Triangle = { kind: "triangle"; base: number; height: number };
type Shape = Circle | Square | Triangle;
const c: Shape = { kind: "circle", radius: 4 } satisfies Shape;

function isCircle(shape: Shape): shape is Circle {
  return shape.kind === "circle"; // user-defined predicate narrowing via value equality — the companion to in/typeof on objects
}
function areaViaPredicate(shape: Shape): number {
  if (isCircle(shape)) return Math.PI * shape.radius ** 2; // narrowed via predicate
  if (shape.kind === "square") return shape.side ** 2; // direct equality narrowing — cheapest
  return 0.5 * (shape as Triangle).base * (shape as Triangle).height; // last branch (exhaustive would use switch+never)
}

console.log(describe({ id: "u_1", email: "a@b.co" })); // user a@b.co
console.log(describeOwn({ id: "o_1", totalCents: 999 })); // own order 999c
console.log(isCircle(c)); // true
```

**Common confusion** — "`in` always narrows exactly" — `in` narrows to "members that *could* have the key" — on optional keys (`email?: string`) and on excess-carrying intermediates it can leave both branches, so model with a required discriminant (`kind`) instead. "`hasOwnProperty` narrows exactly like `in`" — in TS 5.9 era `in` is the most reliable built-in; `hasOwnProperty` narrows in some patterns (TS 5.5+) but may require a predicate wrapper — prefer `in` for plain `type`-union narrowing and `Object.hasOwn` only when prototype exclusion matters. "`typeof obj === \"object\"` narrows the union" — `typeof` on the *object itself* yields `"object"` for every branch — useless; narrow on `typeof obj.kind` or `obj.kind === "..."` instead. "Discriminant must be `kind`" — any common required property with literal-typed values is a discriminant — `type`, `status`, `role` all work — see [07 Unions, Intersections and Narrowing](<../../07 Unions Intersections and Narrowing/README.md>). "`in` checks own properties only" — `in` checks both own and inherited — use `Object.hasOwn` to exclude the prototype chain.

**Performance note** — all three narrowing forms are *control-flow analysis*, not emitted type tests — `in` emits one `in` operation (`O(1)` `HasProperty`), `typeof` emits one `typeof`, `hasOwn` emits one call — no allocations beyond the test value; after narrowing, member access is a direct property load (`O(1)`). Checker cost is one flow-analysis fork per `if` — each branch tracks a narrowed type set — `O(branches)`; deep `switch` on a discriminant with 20 cases costs ~20 narrowed sets per function — still negligible. Very wide unions (>30 members) with repeated `in` probes in a tight loop cost checker graph linear in `cases × probes` — prefer narrowing once to a discriminant and `switch` to the exhaustive form (see 07) rather than probing `"a" in x || "b" in x || ...` at every use site. Measure with `tsc --extendedDiagnostics` if a file with a large object union dominates `check time`.

**Mentor note** — teach object narrowing in three steps: (1) show the unsafe access error without a guard, (2) fix it with `"radius" in shape`, (3) replace with `shape.kind === "circle"` once the discriminant exists and explain why `kind` is more precise than probing member names — follow with a `switch` + `never` default that *forces* exhaustiveness when a new `kind` is added. Review checklist: every function that touches `Shape | UserObj | ...` must narrow before member access — flag bare `shape.radius` as "unnarrowed union". Pair with a live breakage demo — add a new `Pentagon` variant to `Shape` and watch the `default: never` site error (`TS2322: Type 'Pentagon' is not assignable to type 'never'`) if the `switch` missed it — the reaction teaches why discriminant modeling beats ad-hoc `in` probes. Flag `"in"` on optional (`?`) discriminants — require the property to be `required` before review.
