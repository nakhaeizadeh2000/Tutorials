## 4.1. Performance checklist — mental models mentors insist on

### 1) **Measure a successful, equivalent workload**

Before optimizing, name the problem: a slow batch check, declaration build, watch update or editor request. Record the actual compiler/provider, inputs, options, dependencies and relevant cache state. A fast erroring build is not an equivalent successful check, and a file-count change can mean coverage disappeared. Use [actual diagnostics and native traces](<../1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) to separate program membership, aggregate counters, traced work and elapsed measurements.

A useful review question is: “What did this command actually finish?” For example, the worked recursion comparison first reports TS2589, then a passing alternative. Comparing their counters can inform diagnosis, but the failed run did not establish the intended type contract. A replacement must pass semantic probes as well as complete checking. Branch counts in a type expression are not measured instantiation counts, and a trace span does not by itself prove a runtime or editor bottleneck.

Keep instrumented investigation separate from ordinary elapsed runs. Decide how much evidence a change needs from its purpose and risk. A small correctness fix need not acquire a quarterly tracing ceremony or an arbitrary set of performance artifacts. A claimed speed improvement does need comparable observations and their limits.

### 2) **Choose boundaries from dependencies and consumer contracts**

Separate projects when different outputs, hosts, settings, ownership or frequently co-edited code justify a boundary. Change frequency can inform that decision but cannot replace the dependency graph. The [three-project reference exercise](<../2. Project References and Builds/2.1. Composite partitioning and references architecture.md>) checks two consumers of a shared provider. Its body-only change preserves declaration bytes while changing both consumers' runtime behavior. An unchanged type surface therefore does not remove the need for behavioral checks.

Ask which graph a proposed boundary controls. References establish build dependencies; static import rules constrain particular import forms; package exports describe supported resolution entries. None is a general proof of architectural privacy, acyclic runtime initialization or correct behavior. The [boundary-rule exercise](<../3. Scaling Patterns/3.1. Codebase partitioning boundaries layers and barrels.md>) demonstrates both a dynamic import outside a static rule's coverage and a named-re-export cycle that fails at runtime.

Do not split solely because a team or file count crosses a fixed threshold. More projects can repeat shared dependency work and add configuration or artifact management. Explain the intended benefit, preserve real imports and outputs, then measure the workload the split was meant to improve.

### 3) **Use budgets as investigation gates**

A budget needs a defined successful command, compiler version, program and measured quantity. The [worked instantiation gate](<../1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) rejects compiler failures and missing counters before applying a threshold. Its aggregate count is not a per-property cost formula. A change in compiler or inputs can change the baseline without a source regression.

When a budget fails, inspect what changed and preserve accepted/rejected contracts while comparing candidates. A capped recursive transform can reduce recursion by changing the contract beyond its cap; that is a design decision to teach and test, not a free equivalent optimization. A legitimate feature may justify a documented budget adjustment. Automatically shrinking ceilings or rejecting all growth can discourage necessary work without improving the user's experience.

For editor programs, [inspect roots and imports](<../3. Scaling Patterns/3.3. Editor performance at scale budgets and tuning.md>) before treating a file ceiling as a diagnosis. Excluded dependencies can still enter through imports, while unrelated excluded files can remain unchecked. Counts locate changes; actual request evidence establishes whether the intended operation improved.

### 4) **Verify state, artifacts and task selection separately**

An incremental build's exit status, its retained state and the artifacts a consumer starts are separate evidence. The [cache exercise](<../2. Project References and Builds/2.2. Incremental builds and tsbuildinfo discipline.md>) observes a successful unchanged build after app JavaScript has been deleted, followed by a runtime failure. Force rebuilding restores that known output. The same exercise shows an obsolete sentinel surviving force and known-output clean; explicitly removing fixture-owned output/cache directories before rebuilding removes it.

Therefore `--force` is not synonymous with removing all old outputs, and deleting build information is not a universal repair. Define which input identity and complete artifact set a cache restores, keep writers isolated, and run checks on the consumed output. A fresh build comparison is useful evidence; it does not prove that every difference was caused by cache corruption.

Affected selection also needs a truthful graph and task map. The [actual collector](<../2. Project References and Builds/2.3. Solution builds and CI orchestration with tsc b.md>) shows a missing dependency edge allowing a scoped run to pass while full selection catches a consumer regression. Full selection covers more registered tasks; it cannot reveal a behavior no test checks. Choose broader verification from shared-input changes and coverage risk. A nightly schedule alone supplies no completeness proof, and no hosted cache or schedule was configured by these local exercises.

### 5) **Common confusion**

A smaller count can accompany weaker checking. A green build can coexist with missing runtime output. Stable declarations can accompany changed behavior. These are different failure modes, so attach the appropriate observation to each conclusion instead of treating “green” as one universal contract.

Type-only conversion likewise needs runtime judgment. [The installed declaration package](<../3. Scaling Patterns/3.2. Type-only boundaries import type bulk and erasable scale.md>) works with a whole-statement type import but fails when an inline type-only specifier leaves an empty runtime import. A syntax gate cannot replace checking the emitted graph and required initialization.

### 6) **Performance note**

This checklist introduces no new benchmark or executable fixture. It synthesizes the linked measured and behavioral exercises. No fixed instrumentation overhead, project speed multiplier, editor latency, cache payoff or savings estimate follows from the checklist itself. Record overhead and variability where they affect a real comparison, and evaluate operational complexity alongside any measured improvement.

### 7) **Mentor note**

Give a learner three observations: a lower instantiation count from an erroring run, a green incremental build with missing JavaScript, and a stable declaration after changed provider behavior. Ask what each observation establishes and which next check is needed. Strong answers request successful semantic probes, actual artifact execution and relevant consumer behavior respectively.

For a proposed optimization, ask the learner to identify the preserved contract, the measured workload and a plausible counterexample. Reward a bounded conclusion that survives those checks. Avoid substituting a slogan, file threshold or mandatory cadence for that reasoning.
