## 2.3. Solution builds and CI orchestration with tsc b

### 1) **`tsc -b` orchestration** (topological builds, force-dry semantics, solution files)

**Definition** — `tsc -b` (build mode): reads `references` graphs (topological order — leaves before apps, skips up-to-date projects via `.tsbuildinfo` comparison), `--force` (rebuild ignoring up-to-date checks — truth mode), `--dry` (print order without building — ordering proof per 2.1 part 3), `--verbose` (up-to-date reasoning logged — cache decisions evidenced). *Solution files*: root `tsconfig.json` with `files: []` + `references` only (orchestration without sources — the graph's entry point).

**What problem it solves / history** — unordered multi-project builds (scripts compiling apps before leaves — declaration-missing failures, `tsc -p` per project in hand-maintained order — order rotting as graphs evolve): `tsc -b` deriving order from the graph (topology computed, not maintained — order correct by construction at any graph size).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), solution-file per repo root (orchestration entry — `files: []`, references only); `tsc -b` as the single build command (local + CI — order derived, up-to-date-skipping free); `--dry` in reference-PR reviews (ordering evidenced — graph changes reviewed like code changes per 2.1).

**Runnable example** — orchestration derived (good vs bad, `tsc --strict`):

```text
// good — solution file and build commands (order derived — topology, not maintenance)
// tsconfig.json (labeled config doc — solution): { "files": [], "references": [{ "path": "./leaves" }, { "path": "./apps" }] }
// $ tsc -b (labeled CLI doc — topological build, up-to-date skipped)
// $ tsc -b --dry (labeled CLI doc — ordering proof for reference PRs)
// $ tsc -b --force (labeled CLI doc — truth mode, nightly schedules per 2.2 part 3)
```

```typescript
// good — up-to-date skipping (clean projects untouched — no-op builds in seconds)
// (edit apps/view.ts → tsc -b rechecks apps only — leaves up-to-date-skipped via .tsbuildinfo comparison)
export {}; // module marker (consistent module scope across fences)
export function viewTitle(t: string): string { return `title:${t}`; } // app edit (subgraph rebuilt — leaves skipped, CI fast-path per 2.2)
console.log(viewTitle("home")); // title:home — orchestration paying (order derived — up-to-date skipping free)
// bad — hand-ordered build scripts (tsc -p leaves && tsc -p apps — order rotting as graphs evolve, new projects unbuilt)
// fix — tsc -b (topology derived — order correct at any graph size, forever)
```

**Common confusion** — "`tsc -b` equals `tsc -p` per project" — `-b` adds *ordering + up-to-date skipping* (graph-aware — `-p` per project rechecking everything, every time). "`--force` in CI always" — `--force` *disables* caching (truth slow — nightly cadence per 2.2, not per-PR; PRs incremental-fast). "solution files compile" — solution files reference *only* (`files: []` — orchestration without sources; sources living in referenced projects).

**Performance note** — no-op `tsc -b` seconds (up-to-date checks — CI fast-path); full `-b` ∝ changed subgraphs (topology bounding work — order derived AND minimal).

**Mentor note** — build-command review: single `tsc -b` (one command — hand-ordered scripts rejected as graph-rot).

**Cross-links** — DAG hygiene → [2.1. References architecture](<./2.1. Composite partitioning and references architecture.md>); cache contracts → [2.2. Incremental builds](<./2.2. Incremental builds and tsbuildinfo discipline.md>).

### 2) **CI job topology** (per-project jobs vs solution builds, caching, localization)

**Definition** — two topologies: *solution builds* (one job, `tsc -b` whole graph — simple, cache-shared, failures localized by project output); *per-project jobs* (matrix over projects — parallel, cache-per-project per 2.2 keys, failures isolated per job). Choice inputs: graph size (small → solution; large → matrix), cache efficiency (shared vs keyed), failure routing (log-grep vs job-red).

**What problem it solves / history** — single-job megabuilds at scale (30-minute `tsc -b` blocking all merges — unrelated projects' failures blocking unrelated PRs): per-project matrices parallelizing (leaves-jobs + apps-jobs concurrent — failures isolated, merges unblocked except by owned partitions).

**Modern guidance** — solution builds under ~5 projects (simplicity winning — one job, shared cache); per-project matrices above (parallelism + isolation — caches keyed per 2.2, failures routed per owner); hybrid common (leaves-matrix + apps-solution — stable cached aggressively, churning built together).

**Runnable example** — topology chosen (good vs bad, `tsc --strict`):

```text
// good — matrix topology sketch (parallel, cached per project, failures isolated)
// .github/workflows/build.yml (labeled config doc — matrix over projects):
// jobs: { build: { strategy: { matrix: { project: [leaves, apps] } },
//   steps: [restore-cache(key: hash(lockfile, ts-version, matrix.project)),
//           run: "tsc -b packages/${{ matrix.project }}"] } }
// (failures isolated per job — merges blocked only by owned partitions)
```

```typescript
// good — failure localization (project-scoped errors — owners notified, others unblocked)
export {}; // module marker (consistent module scope across fences)
export function leafHealthy(): string { return "leaves-green"; } // leaves job (isolated — apps failures never blocking leaves merges)
console.log(leafHealthy()); // leaves-green — isolation paying (failures routed — velocity unblocked except by ownership)
// bad — megabuild failures blocking all (unrelated reds holding unrelated merges — velocity taxed by strangers)
// fix — matrices past scale (parallel + isolated — topology matched to graph size)
```

**Common confusion** — "matrices always faster" — matrices add *job overhead* (runners, cache restores — small graphs slower parallelized; threshold ~5 projects measured, not assumed). "caches shared across matrix" — caches keyed per project (shared caches colliding per 2.2 — keying avoiding corruption). "solution builds don't scale" — solution builds scale to medium (up-to-date skipping — `-b` no-ops fast; matrices past genuine need).

**Performance note** — matrix wall-time ≈ slowest project (parallel — overhead per job ~30–60s runners + cache; small graphs net-slower parallelized).

**Mentor note** — topology review: project count + wall-time justifying (matrices evidenced, not defaulted — simplicity until measurement says otherwise).

**Cross-links** — cache keys → [2.2. Incremental builds](<./2.2. Incremental builds and tsbuildinfo discipline.md>); gate composition → [3.3. CI gates](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>).

### 3) **Affected-only verification** (changed-project testing, full-suite schedules)

**Definition** — *affected-only*: type tests/lint/unit scoped to changed projects + dependents (reference graph selecting suites — PRs verifying subgraphs, not repos); *full-suite schedules* (nightly/weekly whole-repo verification — cross-cutting regressions caught on cadence, see 2.2 clean schedules + 17/3.3 baselines). Combined: fast PRs (affected) + true repos (scheduled) — velocity with truth, same duality as incremental-vs-clean.

**What problem it solves / history** — full-suite-per-PR at scale (40-minute pipelines per typo-fix — velocity throttled, developers batching changes to amortize CI — batches compounding review burden): affected-only restoring fast PRs (subgraph suites in minutes — full truth on schedule, not per keystroke).

**Modern guidance** — scope PR verification via reference graph (changed + dependents — `tsc -b` affected logic extended to tests/lint); schedule full suites nightly (cross-cutting truth — cadence per 2.2); alert on affected-green/full-red divergence (scoping gaps caught — affected logic fixed, not widened blindly).

**Runnable example** — scoped verification (good vs bad, `tsc --strict`):

```text
// good — affected selection sketch (subgraph suites — fast PRs, scheduled truth)
// PR (leaves/user.ts changed) → verify: leaves + apps(dependents) (labeled doc — graph-selected suites)
// nightly → verify: ALL (labeled doc — full truth on cadence, cross-cutting regressions caught)
// (affected-green + full-red → scoping gap alerted — selection fixed with evidence)
```

```typescript
// good — dependent-aware test placement (suites beside their projects — selection natural)
// file: apps/user.test.ts adjacent to apps/user.ts (co-located — graph selection finding suites by proximity)
// (changed leaves/user.ts → leaves suites + apps suites (dependents) — verification following references)
export function userLabel(id: string): string { return `user:${id}`; } // tested beside (suites co-located — affected selection trivially correct)
console.log(userLabel("u1")); // user:u1 — co-location paying (suites following code — selection by proximity, not registries)
// bad — central test registries (suites decoupled from projects — affected selection requiring maintained mappings, rotting)
// fix — co-located suites (proximity selecting — graph + filesystem agreeing, mappings unnecessary)
```

**Common confusion** — "affected-only misses regressions" — full schedules catching cross-cutting (nightly truth — affected for velocity, scheduled for completeness; missing schedules, not scoping, causing misses). "scoping needs tooling" — scoping needs *co-location* (suites beside code — graph selection trivial; registries needing tooling is the smell). "full suites per PR are safer" — full suites per PR *throttle* (batching changes — bigger, riskier merges; safety from speed + schedules, not from per-PR exhaustiveness).

**Performance note** — affected suites minutes (subgraphs — PR velocity); full suites tens-of-minutes nightly (amortized truth — cadence-priced, not PR-priced).

**Mentor note** — pipeline metric: PR-pipeline p50 (affected speed) + nightly-full red rate (truth health) — two numbers, velocity with truth evidenced.

**Cross-links** — co-location → part 2's proximity principle (same leaf — selection by filesystem); baseline schedules → [3.3. CI gates](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>).
