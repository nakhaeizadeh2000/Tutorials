## 2.3. Solution builds and CI orchestration with tsc b

Build ordering, test selection and final job status are separate responsibilities. TypeScript build mode follows project references and decides what needs building. It does not automatically discover and run a project's lint, type-test or runtime suites. A verification job must select those operations and preserve their outcomes.

Use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. Extend the complete [three-project fixture](<./2.1. Composite partitioning and references architecture.md>) and the [fresh-output helper](<./2.2. Incremental builds and tsbuildinfo discipline.md>). This page executes a local, provider-neutral collector. It does not create a hosted workflow, configure branch protection or install Nx.

### 1) **Use build mode for the graph it actually knows**

The fixture's root solution has files: [] and references its consumers. `tsc -b` discovers their referenced core project and orders required work. A regular project check does not orchestrate dependency builds, but it can itself be incremental when configured that way. Do not equate every -p invocation with a full uncached check.

The [reference handbook](https://www.typescriptlang.org/docs/handbook/project-references.html) distinguishes build, dry, force and clean. The preceding owners actually test those distinctions: dry can overlook a source error, force can retain obsolete files, and a retained up-to-date state can coexist with missing JavaScript. A successful plan or skipped build is not a substitute for the required artifact and consumer checks.

The collector below passes selected projects to **one build invocation**, so build mode handles their shared dependency graph. It only runs runtime consumers if that build succeeds. This ordering matters because the tests load emitted files: after a failed build, testing old output as if it represented current source would be misleading. Independent checks that do not require that artifact can follow a different dependency policy, as the [actual gate-composition owner](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>) demonstrates.

### 2) **Compute a small affected closure and name its checks**

For this fixture only, the caller supplies changed project names. The collector reads the three strict JSON configurations, follows directory references and adds reverse dependents. A core change selects core, app and admin; an app change selects app. Build mode may still visit core as app's prerequisite, even though only app's runtime check was selected.

The project-to-runtime-check registry is explicit. The tests are not discovered merely because files are nearby. Core has no separate runtime entry test here; its behavior is exercised through the two consumers. This is a small educational selector for these three projects, not a general tsconfig/JSONC parser, Git diff mapper, dynamic-import analyzer or complete workspace task graph.

Save:

```javascript
// file: ci.mjs
import { readFileSync, writeFileSync } from "node:fs";
import { resolve } from "node:path";
import { spawnSync } from "node:child_process";
const projects = ["core", "app", "admin"];
const checks = {
  app: { entry: "app/dist/main.mjs", expected: "user:u1" },
  admin: { entry: "admin/dist/main.mjs", expected: "user:admin" },
};
const report = { changed: process.argv.slice(2), selected: [], steps: [] };
function command(label, executable, args, expected) {
  const result = spawnSync(executable, args, { encoding: "utf8", timeout: 30000 });
  const ok = !result.error && result.status === 0 &&
    (expected === undefined || result.stdout.trim() === expected);
  const step = { label, executable, args, status: result.status, ok,
    stdout: result.stdout, stderr: result.stderr, error: result.error?.message };
  report.steps.push(step);
  return ok;
}
try {
  const byConfig = new Map(projects.map(name => [resolve(name, "tsconfig.json"), name]));
  const dependents = new Map(projects.map(name => [name, []]));
  for (const project of projects) {
    const config = JSON.parse(readFileSync(project + "/tsconfig.json", "utf8"));
    for (const reference of config.references ?? []) {
      const dependency = byConfig.get(resolve(project, reference.path, "tsconfig.json"));
      if (!dependency) throw new Error("unmodeled reference from " + project);
      dependents.get(dependency).push(project);
    }
  }
  const changed = report.changed.length ? report.changed : ["all"];
  if (changed.includes("all") && changed.length !== 1) throw new Error("all must stand alone");
  if (changed[0] !== "all" && changed.some(name => !projects.includes(name))) {
    throw new Error("unknown changed project");
  }
  const selected = new Set(changed[0] === "all" ? projects : changed);
  const pending = [...selected];
  while (pending.length) {
    for (const consumer of dependents.get(pending.shift())) {
      if (!selected.has(consumer)) { selected.add(consumer); pending.push(consumer); }
    }
  }
  report.selected = projects.filter(name => selected.has(name));
  const built = command("build", "tsc", ["-b", ...report.selected, "--verbose"]);
  if (built) {
    for (const name of report.selected) {
      const check = checks[name];
      if (check) command("runtime:" + name, process.execPath, [check.entry], check.expected);
    }
  }
  process.exitCode = report.steps.every(step => step.ok) ? 0 : 1;
} catch (error) {
  report.error = String(error);
  process.exitCode = 1;
} finally {
  writeFileSync("ci-results.json", JSON.stringify(report, null, 2));
  console.log(JSON.stringify({ selected: report.selected,
    outcomes: report.steps.map(step => [step.label, step.ok]), error: report.error }));
}
```

Run `node fresh.mjs`, then `node ci.mjs app`, `node ci.mjs core` and `node ci.mjs all`. Each positive invocation exits zero. Inspect ci-results.json after each command: app selects one runtime entry, while core and all select both. The report retains actual compiler/runtime status and output. A runtime program can exit zero with the wrong printed value; the collector then marks its expected-output contract false and exits unsuccessfully.

Change core's label implementation to return `wrong:${user.id}` while preserving its declared string return. Run `node ci.mjs core`: the build passes, both runtime contracts fail, and the collector exits one. Restore the original implementation. Now change its returned expression to number 123: the actual build reports TS2322, the collector exits one and **no runtime steps execute**. Restore the original and rerun the full collector.

These contrasts establish the collector's dependency and status behavior. They do not replace a real test suite; the printed label is simply this fixture's explicit small runtime contract.

### 3) **Expose what affected selection can miss**

The graph must represent the dependencies relevant to each task, and the supplied changed set must be accurate. For a concrete counterexample, temporarily remove admin's reference to core while retaining its direct import of the built artifact. Change core's body so app's u1 result remains correct but admin's result is wrong. The [configuration owner](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.2. declaration composite project references.md>) explains why an available physical declaration can still resolve without that reference.

Now `node ci.mjs core` selects core and app; its chosen runtime check passes and the collector can exit zero. `node ci.mjs all` also checks admin and detects the wrong output. The omitted graph edge caused incomplete task selection; co-location did not repair it. Restore the edge and implementation, rebuild, and run the full collector again. This is a deliberately broken dependency model, not proof that a nightly job makes incomplete PR selection safe.

Shared configuration, generated inputs, compiler/dependency changes and other cross-project effects need a broader selection policy. Use all for them in this small exercise; the script does not automatically classify changed files. Real systems also need a correct comparison base and head, file-to-project ownership and task-specific dependency rules. [Nx's affected-task guide](https://nx.dev/docs/features/ci-features/affected) explicitly separates changed-file detection, graph dependents and dependency-update policy. It is useful design input; none of its commands is executed by this fixture.

Full verification can reveal a discrepancy with a scoped run. Investigate the change set, graph, selected tasks and artifacts before deciding the remedy. A schedule only runs the checks it is configured to run; it does not establish completeness or bound detection time by itself. Choose required PR/full checks and any additional cadence from the actual release needs, with honest limits on what each covers.

### 4) **Choose job topology from dependencies and resources**

A single solution job is straightforward for this fixture. Multiple isolated jobs can be useful for different hosts, ownership or long-running independent suites. Project count alone does not determine the right topology. A matrix that runs tsc -b app and tsc -b admin in a shared checkout can send both invocations into core's outputs/build information; keying the jobs by their top-level names does not isolate that shared dependency.

Use isolated job workspaces and complete artifact contracts, or order shared tasks so dependent jobs consume the intended build. A task orchestrator can model those dependencies explicitly. Compiler build success does not automatically run lint or runtime tests, and job ownership does not automatically change which statuses block a merge. Those are workflow and repository settings that this page does not configure.

Compare actual runner startup, available parallel resources, repeated dependency work and artifact transfer before claiming a matrix improves elapsed time. A dependency chain can constrain parallelism, while splitting jobs can duplicate work. Avoid a universal slowest-project formula or fixed runner-overhead estimate.

### 5) **Common confusion**

Build mode's affected or up-to-date decisions are not an affected-test runner. The collector implements its own reverse graph selection and explicit runtime registry. Nearby tests, omitted dependencies and a guessed Git base are independent inputs to completeness.

A build failure and a behavioral failure require different evidence. The collector refuses to run emitted-output tests after a failed build, yet detects a type-correct wrong implementation after a successful one. A green scoped report only covers its selected tasks, just as the missing-edge counterexample shows.

### 6) **Performance note**

This fixture verifies selection, prerequisites, status propagation and failure contrasts. It does not benchmark pipeline time, remote cache behavior or parallel job savings. Preserve correctness and artifact identity when comparing topologies. Fewer executed tasks can mean justified reuse or a missing dependency; wall time alone cannot distinguish them.

### 7) **Mentor note**

Give the learner a green core-scoped report after admin's reference edge is removed. Ask which runtime task was selected, which import still exists and why the full run disagrees. A sound answer repairs the model or selection input rather than raising a timing budget or relying on a future scheduled job. Then introduce a compiler error and confirm that the collector reports failure without running stale emitted artifacts.
