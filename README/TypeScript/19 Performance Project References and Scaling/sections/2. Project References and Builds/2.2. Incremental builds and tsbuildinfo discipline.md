## 2.2. Incremental builds and tsbuildinfo discipline

Incremental build information records compiler state for reuse. It is neither executable output nor a certificate that the expected artifact set exists. Keep source/configuration, the compiler invocation, cached state and emitted files consistent before interpreting a successful fast build.

Use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. Begin with the complete scratch fixture from [reference architecture](<./2.1. Composite partitioning and references architecture.md>), including core, app, admin and verify.mjs, restored to its original user: implementation. This page adds a finite cache/output exercise; it does not configure hosted CI caching or claim a speed improvement.

### 1) **Separate build information from generated outputs**

The [incremental option](https://www.typescriptlang.org/tsconfig/incremental.html) saves project-graph information to disk. The JavaScript runtime does not use that .tsbuildinfo file. Its internal format belongs to the compiler; do not edit it as an application contract or assume portability across compiler versions. [tsBuildInfoFile](https://www.typescriptlang.org/tsconfig/tsBuildInfoFile.html) makes the location explicit, while its default depends on other output/root options.

The reused fixture gives each project a separate file in cache and separate generated dist directories. These files describe work state; they do not contain a deployable copy of every emitted module. In the exercised 7.0.2 build, deleting app/dist/main.mjs while retaining build information lets an ordinary unchanged solution build report up to date with exit zero. The missing JavaScript stays missing, and running the entry point fails. A forced build recreates it. Test the exact compiler/workflow instead of assuming an output-only deletion creates a fresh build.

Compiler state can also retain diagnostics. The exercise introduces a source type error, builds twice and requires TS2322 both times. Incremental does not mean caching only successful checks or automatically hiding earlier errors. Conversely, a successful prior build's old output can remain after a failed check under noEmitOnError. Do not run that file as evidence that the current source passed.

The [historical output-cleanup discussion](https://github.com/microsoft/TypeScript/issues/36648) raises the same practical distinction for removed/renamed files and links an earlier missing-output report. That report concerns TypeScript 3.7.5; the current fixture supplies this lesson's native 7.0.2 observation. A historical issue is a useful question to reproduce, not proof of every modern cache behavior.

### 2) **Use force and cleanup for their actual purposes**

Force treats projects as needing a rebuild. It does not delete arbitrary files from their output directories. Build mode's clean removes known outputs, which also does not mean recursively clearing unrelated files. The exercise writes an obsolete.txt sentinel, verifies that it survives force and known-output clean, then performs an explicitly owned fresh-output rebuild that removes it.

Save the following fresh.mjs **only inside this scratch fixture**. Its listed dist directories and cache are generated outputs owned by these examples. Do not point it at source, user files or a real project's output location without first establishing that ownership.

```javascript
// file: fresh.mjs
import assert from "node:assert/strict";
import { existsSync, rmSync } from "node:fs";
import { spawnSync } from "node:child_process";
for (const project of ["core", "app", "admin"]) {
  assert.ok(existsSync(project + "/tsconfig.json"), "run from the complete scratch fixture");
}
for (const generated of ["core/dist", "app/dist", "admin/dist", "cache"]) {
  rmSync(generated, { recursive: true, force: true });
}
const build = spawnSync("tsc", ["-b", "--verbose"], { encoding: "utf8", timeout: 30000 });
if (build.error) throw build.error;
process.stdout.write(build.stdout);
process.stderr.write(build.stderr);
if (build.status !== 0) process.exit(build.status ?? 1);
```

Run `node fresh.mjs` to recreate both state and emitted artifacts. This means fresh *project outputs and build information*, not flushed operating-system caches or a clean package installation. The [native measurement owner](<../../../25 Update TypeScript 7.0/sections/3. Native Build and Watch/3.1. Native builds watch and measurement.md>) defines those states when timing them.

A difference after force or cache deletion is evidence to investigate. It does not by itself establish that the cache was corrupted, that the source is correct, or that deleting state is the permanent repair. Compare exact inputs, selected configuration, compiler version, dependency installation and expected artifacts. The preceding architecture fixture even observes consumer-state reuse after an invalid configuration edit; explicitly checking that consumer exposes the error.

Save and run `node exercise.mjs`:

```javascript
// file: exercise.mjs
import assert from "node:assert/strict";
import { readFileSync, writeFileSync, existsSync, unlinkSync } from "node:fs";
import { spawnSync } from "node:child_process";
const sourcePath = "app/src/main.mts";
const original = readFileSync(sourcePath, "utf8");
const records = [];
function run(label, executable, args, failureCode) {
  const result = spawnSync(executable, args, { encoding: "utf8", timeout: 30000 });
  assert.ifError(result.error);
  const output = result.stdout + result.stderr;
  records.push({ label, executable, args, status: result.status, output });
  if (failureCode) {
    assert.notEqual(result.status, 0, label);
    assert.ok(output.includes(failureCode), output);
  } else { assert.equal(result.status, 0, output); }
}
const compiler = (label, args, failureCode) => run(label, "tsc", args, failureCode);
const node = (label, args, failureCode) => run(label, process.execPath, args, failureCode);
try {
  node("fresh baseline", ["fresh.mjs"]);
  node("baseline runtime", ["verify.mjs"]);
  for (const project of ["core", "app", "admin"]) {
    assert.ok(existsSync("cache/" + project + ".tsbuildinfo"));
  }
  unlinkSync("app/dist/main.mjs");
  compiler("missing output with retained state", ["-b", "--verbose"]);
  assert.equal(existsSync("app/dist/main.mjs"), false);
  node("missing runtime artifact", ["app/dist/main.mjs"], "MODULE_NOT_FOUND");
  compiler("force restores expected output", ["-b", "--force", "--verbose"]);
  node("restored runtime", ["verify.mjs"]);
  const previousOutput = readFileSync("app/dist/main.mjs", "utf8");
  assert.ok(original.includes('id: "u1"'));
  writeFileSync(sourcePath, original.replace('id: "u1"', "id: 123"));
  compiler("new type error", ["-b", "--verbose"], "TS2322");
  compiler("repeated type error", ["-b", "--verbose"], "TS2322");
  assert.equal(readFileSync("app/dist/main.mjs", "utf8"), previousOutput);
  writeFileSync(sourcePath, original);
  compiler("restored source", ["-b", "--verbose"]);
  node("restored consumer behavior", ["verify.mjs"]);
  writeFileSync("app/dist/obsolete.txt", "old output sentinel");
  compiler("force keeps unrelated output", ["-b", "--force"]);
  assert.equal(existsSync("app/dist/obsolete.txt"), true);
  compiler("clean known outputs", ["-b", "--clean"]);
  assert.equal(existsSync("app/dist/obsolete.txt"), true);
  assert.equal(existsSync("app/dist/main.mjs"), false);
  node("fresh owned-output rebuild", ["fresh.mjs"]);
  assert.equal(existsSync("app/dist/obsolete.txt"), false);
  node("fresh runtime consumers", ["verify.mjs"]);
  console.log("missing outputs, repeated diagnostics and fresh artifacts verified");
} finally {
  writeFileSync(sourcePath, original);
  writeFileSync("cache-exercise-results.json", JSON.stringify(records, null, 2));
}
```

The final message means the missing-output, diagnostic, sentinel and runtime assertions passed. The JSON retains each actual child command's status and output. The source is restored even if an assertion fails; a failed run can still leave generated artifacts requiring the fresh rebuild. As a deliberate mutation, change the missing-output expectation from false to true: the exercise detects the mistaken assumption. Restore it before continuing.

### 3) **Match execution mode and cache policy to the workflow**

| Mechanism | What it retains or orchestrates | Evidence needed |
|---|---|---|
| Incremental one-shot check/build | A new process reuses saved disk state where applicable | Initial, unchanged and edited success/error cases; required outputs |
| Watch | A long-running process observes edits and retains working state | Actual edit → diagnostic → correction transitions, plus termination |
| Solution build mode | Dependency ordering and up-to-date decisions across referenced projects | Graph, statuses, artifact set and relevant consumers |

These mechanisms can combine: a solution build can watch, and an incremental program can save state across processes. Watch is not synonymous with disk caching, and plain watch does not by itself promise the same .tsbuildinfo policy as an incremental configuration. Its feedback is not guaranteed to be instant. The [finite native watch experiment](<../../../25 Update TypeScript 7.0/sections/3. Native Build and Watch/3.1. Native builds watch and measurement.md>) actually executes startup, introduced TS2322, restored success and process cleanup; this page does not rerun that watch test.

A one-shot verification job usually needs a command that exits. A job intentionally testing a watcher can legitimately start one if it controls its lifetime and checks the relevant transitions. Choose commands from that purpose rather than rejecting every watch flag in CI or prescribing build mode for every repository.

Give concurrent writers separate output and build-information paths or serialize them. Restoring a cache is a performance tactic that still needs an input and artifact contract. Compiler version, options, source/generated inputs, dependency installation, output layout and other environment-relevant inputs can matter. A key hashing only a lockfile, version and tsconfig does not prove that every restored file corresponds to the current work. Restoring .tsbuildinfo without its expected outputs is the concrete mismatch this fixture tests.

Generated build information is normally ignored in source control and rebuilt or restored as part of a documented workflow. If a repository deliberately versions build artifacts, define how its metadata and outputs stay consistent instead of treating a blanket never-commit rule as reproducibility proof. A fresh verification job can reveal a discrepancy; choose its trigger and cadence from the workload and risk. No universal nightly/weekly schedule or promise of a 24-hour detection window follows from a compiler flag.

### 4) **Common confusion**

A compiler exit status and an executable artifact are separate checks. Retained build information does not recreate a deleted file in the observed unchanged build, while a failed source check can leave an older executable present. Both cases require inspecting the artifact the consumer will actually load.

Force rebuilds; clean removes known outputs; deleting a fixture's owned output directories removes the sentinel too. None establishes the cause of every prior discrepancy. Persist the failing inputs and command evidence before drawing a conclusion about invalidation or cache corruption.

### 5) **Performance note**

Reuse can reduce repeated work, but this exercise measures no speed ratio, storage size or per-edge cost. Fresh outputs, unchanged invocations, edits and a running watcher are different states. Time comparable successful work with the measurement owner, and verify artifacts and behavior alongside status. A missing or failed build cannot win a meaningful benchmark by doing less work.

### 6) **Mentor note**

Ask why the ordinary build exits zero after main.mjs is deleted, then why a later failed source check still leaves main.mjs on disk. A sound explanation distinguishes saved checking state, expected output ownership and the file the runtime loads. Have the learner predict the sentinel's fate under force, known-output clean and fresh.mjs, then confirm each observation from cache-exercise-results.json.
