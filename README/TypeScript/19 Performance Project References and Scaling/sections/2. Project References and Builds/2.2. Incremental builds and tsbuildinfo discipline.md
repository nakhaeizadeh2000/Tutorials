## 2.2. Incremental builds and tsbuildinfo discipline

### 1) **`.tsbuildinfo` contracts** (invalidation triggers, affected graphs, staleness)

**Definition** — `.tsbuildinfo` records program shape (file versions, signatures, dependency graph — the checker's memory): *invalidation triggers* (file content changes, `tsconfig` edits, TS version bumps — shape changes invalidating affected subgraphs); *affected graphs* (changed files + dependents rechecked — rest served from cache); *staleness* (cache disagreeing with sources — 16/3.1 + 17/5.1 poisoning classes: week-old declarations served downstream).

**What problem it solves / history** — full rechecks per save (minutes × hundreds of saves — developer velocity throttled by redundant verification): incremental caching converting rechecks into affected-subgraph work (edited file + dependents — seconds, proportional to change scope like 2.1 partitioning).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable `incremental` on apps (local speed — cache beside `outDir`); never commit `.tsbuildinfo` (generated — `.gitignore` + CI-cached per 2.3 job topology); treat staleness as cache-bug-class (symptoms: phantom errors, stale declarations — `tsc -b --force` distinguishing cache bugs from real ones in one command).

**Runnable example** — cache contracts (good vs bad, `tsc --strict`):

```typescript
// good — affected-subgraph thinking (edited files + dependents rechecked — rest cached)
// (edit leaves/user.ts → leaves + apps rechecked; edit apps/view.ts → apps only — invalidation proportional to dependence)
// file: apps/view.ts (churning — daily edits rechecking apps-subgraph, leaves served from .tsbuildinfo)
export function viewName(name: string): string { return `view:${name}`; } // app edit (subgraph recheck — seconds, not minutes)
console.log(viewName("home")); // view:home — incremental speed (change-scope work — velocity unthrottled by redundancy)
// bad — incremental disabled "for correctness" (full rechecks per save — minutes × hundreds of saves, velocity throttled)
// fix — incremental on + staleness runbook (speed with truth — cache bugs diagnosed via --force, not feared)
```

```jsonc
// good — cache configuration (gitignored locally, cached in CI — contracts declared)
// tsconfig.app.json (labeled config doc): { "compilerOptions": { "incremental": true, "tsBuildInfoFile": ".cache/app.tsbuildinfo" } }
// .gitignore (labeled config doc): .cache/ + *.tsbuildinfo (generated — never committed, CI-cached per content hash)
```

**Common confusion** — "incremental hides errors" — incremental *caches verified results* (same errors, less recomputation — staleness the exception class, diagnosed via `--force`, see 16/3.1). "caches commit for reproducibility" — caches *poison* reproducibility (machine-specific absolute paths — gitignored + CI-rebuilt; reproducibility from clean builds per part 3 schedules). "version bumps reuse caches" — version changes invalidate (checker internals differing — caches keyed per TS version, see 2.3 job keys).

**Performance note** — incremental rechecks ∝ affected subgraph (seconds vs minutes — 10×–50× on large repos); cache size MBs (`.tsbuildinfo` per project — disk-cheap, gitignored).

**Mentor note** — "is it a cache bug?" triage: `tsc -b --force` (reproduces clean → cache bug, delete cache; persists → real error — one command distinguishing in seconds).

### 2) **Incremental vs watch vs build modes** (per-workflow selection, cache locations)

**Definition** — three modes: `--incremental` (single `tsc` runs reusing `.tsbuildinfo` — CI/local one-shots); `--watch` (long-lived process, in-memory + disk cache — local development, instant re-emit); `tsc -b` (references-aware orchestration — topological order, per-project up-to-date checks — monorepos + CI per 2.3). Cache locations: beside output (default), `tsBuildInfoFile` (custom — per-job paths in CI avoiding collisions).

**What problem it solves / history** — one-mode-fits-all (`tsc` full per save locally — minutes; `--watch` in CI — processes never exiting): mode-per-workflow matching speed to context (watch locally — instant; incremental one-shots in CI jobs — cached; `-b` for graphs — ordered).

**Modern guidance** — local dev: `--watch` (instant feedback — process lifetime = session); CI jobs: `tsc -b` (ordered, cached per 2.3 topology); one-shot scripts: `--incremental` (single runs with memory — no watch processes in pipelines). Per-job `tsBuildInfoFile` paths in CI (collisions avoided — job-keyed cache dirs).

**Runnable example** — modes matched (good vs bad, `tsc --strict`):

```text
// good — mode per workflow (watch locally, -b in CI, incremental one-shots — speed matched to context)
// local:  $ tsc -b --watch (labeled CLI doc — session-long process, instant re-emit per save)
// CI:     $ tsc -b (labeled CLI doc — ordered one-shot, caches restored per 2.3 job keys)
// script: $ tsc --incremental --noEmit (labeled CLI doc — single run with memory, exits cleanly)
```

```typescript
// good — watch-friendly code (save-safe edits — incremental rechecks proportional, see part 1 contracts)
export {}; // module marker (consistent module scope across fences)
export function priced(kind: "std" | "pro"): number { return kind === "pro" ? 20 : 10; } // edited often (watch re-emitting in milliseconds — mode matched to workflow)
console.log(priced("pro")); // 20 — local speed (watch process — feedback instant, velocity unthrottled)
// bad — watch in CI (processes never exiting — pipelines hanging on persistent watchers)
// fix — mode per workflow (watch sessions, -b pipelines — contexts differing, modes differing)
```

**Common confusion** — "watch is always fastest" — watch fastest *locally* (warm process); in CI watch never exits (hanging pipelines — mode matched to context, not to speed alone). "incremental equals watch" — incremental persists *to disk* (cold starts warm via cache); watch persists *in memory* (warm only while running — complementary, not identical). "cache locations irrelevant" — colliding `tsBuildInfoFile` paths corrupt concurrent jobs (per-job dirs — collisions as cache-bug class).

**Performance note** — watch re-emit milliseconds-to-seconds (warm — local velocity); `-b` up-to-date checks skip clean projects entirely (seconds for no-op builds — CI fast-path).

**Mentor note** — pipeline review: watch flags in CI configs are hangs (grep `--watch` in workflows — present means broken).

### 3) **Cache poisoning prevention** (clean schedules, hash keys, gitignore-plus-CI-cache)

**Definition** — *poisoning*: stale caches served as truth (week-old declarations downstream per 17/5.1 part 4 + 16/3.1 — incremental-only CI drifting from sources). Prevention triad: *clean schedules* (nightly/weekly `tsc -b --force` full verification — truth reconciled on a cadence); *hash keys* (CI caches keyed by lockfile + TS version + tsconfig content — key changes busting stale entries); *gitignore-plus-CI-cache* (never committed, always restorable — caches ephemeral by policy).

**What problem it solves / history** — incremental-only CI green on stale (sources moved, caches un-busted — broken declarations shipping as patch surprises per 17/5.1): clean schedules reconciling truth (poisoning windows bounded by cadence — nightly catching what incrementals miss).

**Modern guidance** — key CI caches on `(lockfile, TS version, tsconfig hash)` (bust on shape change — stale entries unreachable); schedule `--force` full builds (nightly for active repos — truth cadence; weekly minimum); alert on clean-vs-incremental divergence (scheduled clean red while incremental green = poisoning caught — the metric proving the schedule's worth).

**Runnable example** — poisoning bounded (good vs bad, `tsc --strict`):

```text
// good — cache keys and clean schedules (stale unreachable, truth cadenced)
// CI cache key (labeled config doc): key = hash(package-lock.json, typescript-version, tsconfig**)
// schedule (labeled config doc): nightly `tsc -b --force` (truth reconciled — poisoning windows ≤24h, divergence alerting)
// (incremental green + clean red → poisoning caught — the schedule proving its worth per run)
```

```typescript
// good — version-keyed thinking (TS bumps busting caches — shape changes invalidating structurally)
export {}; // module marker (consistent module scope across fences)
export const CACHE_KEY_PARTS = ["lockfile", "ts-version", "tsconfig"] as const; // key anatomy (shape changes busting — stale unreachable by construction)
console.log(CACHE_KEY_PARTS.join("+")); // lockfile+ts-version+tsconfig — keys declared (bust conditions reviewed, not hoped)
// bad — static cache keys ("tsbuildinfo-v1" forever — version bumps reusing stale shapes, poisoning unbounded)
// fix — content-hash keys (shape changes busting — staleness structurally unreachable)
```

**Common confusion** — "clean schedules waste CI" — clean builds cost minutes nightly (poisoning costing releases — insurance arithmetic overwhelmingly favorable). "force flags fix poisoning" — `--force` *diagnoses* (clean truth revealed); keys + schedules *prevent* (stale unreachable + windows bounded — diagnosis vs prevention layered). "poisoning is rare" — poisoning is *silent* (rarity unmeasurable without clean schedules — absence of evidence ≠ evidence of absence; schedules producing the evidence).

**Performance note** — clean schedules minutes-per-night (amortized — insurance, not overhead); key hashing milliseconds (content hashes — bust precision free).

**Mentor note** — CI-review: cache keys quoted on sight (unkeyed caches rejected — staleness-by-default unmergeable).
