## 2.1. Composite partitioning and references architecture

A project boundary separates checking and build units. A reference tells build mode about a dependency between those units. Useful boundaries usually reflect coherent responsibilities, supported hosts, outputs and dependencies; change patterns can inform the decision, but rarely changing code is not automatically a separate project.

This lesson extends the complete [two-project configuration fixture](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.2. declaration composite project references.md>) with a second consumer. Use its exact base/core/app files in a fresh directory, then add or replace the three files below. The environment is **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. No monorepo manager or additional dependency is required.

### 1) **Choose boundaries from work and dependencies**

The existing app and the new admin project both consume core. Their reference arrows point from consumer to dependency: app → core and admin → core. Build mode must make core's required outputs available before those consumers. A separate solution config lists the consumers without adding another source program.

```json
// file: admin/tsconfig.json
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src", "outDir": "dist",
    "tsBuildInfoFile": "../cache/admin.tsbuildinfo"
  },
  "include": ["src/**/*.mts"],
  "references": [{ "path": "../core" }]
}
```

```typescript
// file: admin/src/main.mts
import { label } from "../../core/dist/index.mjs";
console.log(label({ id: "admin" }));
```

```json
// file: tsconfig.json
{ "files": [], "references": [{ "path": "./app" }, { "path": "./admin" }] }
```

Run `tsc -b --dry --verbose` on the fresh fixture. It reports planned work without creating the missing JavaScript outputs. Then run `tsc -b --verbose`, `node app/dist/main.mjs` and `node admin/dist/main.mjs`. The outputs are user:u1 and user:admin. Repeat the build without edits and inspect its up-to-date messages. These are build-state observations, not a measured speedup.

A team may split browser and server code because they need different libraries, or isolate a public package because it needs its own output and release contract. Files commonly edited together may belong together even if another grouping sounds more stable. The [performance guide's project discussion](https://github.com/microsoft/TypeScript/wiki/Performance#using-project-references) considers edit cohesion and repeated shared dependency work. Its empirical project-count guidance is not a threshold for the current native compiler or a rule about team size. There is no required minimum of three boxes, fixed 3–7 split, engineer count or file-count trigger.

Start with a dependency drawing and a concrete problem: excessive program size, incompatible host settings, unclear output ownership or measured rebuild work. Check whether the proposed split addresses it. Projects also need configuration, declarations, graph maintenance and repeated library work; more boundaries are not automatically better.

### 2) **Observe declarations and implementations separately**

Run `tsc -p app --noEmit --listFilesOnly` and the same command for admin. Each includes core/dist/index.d.mts and the appropriate consumer source, while excluding core/src/index.mts. Each program also includes standard-library declarations. This verifies the artifact boundary in this fixture; it does not mean every workspace import or editor request always skips all dependency sources.

Composite establishes constraints needed by referenced projects. The base configuration explicitly enables declaration output, declaration maps and noEmitOnError. A referenced project with composite disabled is rejected when its consumers are checked. If experimenting after an earlier successful build, use `tsc -b --force` or check the consumer directly so an up-to-date decision cannot reuse its prior state. The tested ordinary incremental run reused consumer state after this configuration edit; forcing the checks exposed TS6306. A composite project with declaration disabled is also a configuration error; it does not silently switch downstream checking to source implementations. The [project-reference handbook](https://www.typescriptlang.org/docs/handbook/project-references.html) explains composite's file-set, root and declaration constraints.

Now change only core's label body from user: to member:, keeping its parameter and return annotations unchanged. Build again and run both consumers. They print member:u1 and member:admin even though the public declaration text and consumer JavaScript text can remain identical. Runtime imports load the new implementation. The build log identifies which work was rebuilt or reused; do not infer a universal invalidation rule from whether the declaration changed.

Restore user: and rebuild before continuing. For an actual public-signature change, the configuration owner already tests adding a required argument and observing the downstream diagnostic. Keep runtime behavior checks beside checking/build-state observations, since stable declarations cannot establish an unchanged implementation contract.

Save this consumer to assert the current two runtime entry points:

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { spawnSync } from "node:child_process";
const prefix = process.argv[2] ?? "user";
for (const [path, id] of [["app/dist/main.mjs", "u1"], ["admin/dist/main.mjs", "admin"]]) {
  const result = spawnSync(process.execPath, [path], { encoding: "utf8", timeout: 5000 });
  assert.ifError(result.error);
  assert.equal(result.status, 0, result.stderr);
  assert.equal(result.stdout.trim(), prefix + ":" + id);
}
console.log("both reference consumers passed");
```

Run `node verify.mjs` for the original body and `node verify.mjs member` during the edited-body check. A failed compiler/build is still a failed baseline even if an older output happens to run. The harness verifies entry-point behavior; it does not inspect every possible consumer or editor navigation action.

Declaration maps point supported tools toward source files. They do not include those sources automatically or guarantee that a consumer's editor can find them. The configuration owner inspects the map and the [actual navigation fixture](<../../../16 Tooling Language Server and Ecosystem/sections/1. Language Server in Practice/1.1. Navigation go to definition find references.md>) separately executes native language-server queries. Do not call map generation an editor performance or UI verification result.

### 3) **Test the reference graph without confusing it with import policy**

Temporarily add a references entry to core/tsconfig.json pointing to ../admin. The graph now contains core → admin → core. Run `tsc -b --dry --verbose`: TS6202 reports a circular project-reference graph. This is a finite diagnostic, not a release-day compiler deadlock. Remove the added edge and rerun the actual build.

A successful dry run establishes planned graph/build work, not successful type checking, emission or runtime behavior. As a second contrast, change app's id value from a string to a number. Dry mode can report its plan without diagnosing that source error; an actual build reports TS2322. Restore the source and build again before running the positive consumer.

References also do not form a general import allow-list. With built outputs present, the canonical configuration fixture checks a direct core declaration import after removing the consumer's reference, and checks a direct physical import of an internal output. Those observations explain why packaging, architecture rules and runtime module cycles need their own controls. The [partitioning/layer owner](<../3. Scaling Patterns/3.1. Codebase partitioning boundaries layers and barrels.md>) develops that policy; path mappings alone are not a blanket ban on other imports.

[Nx's first-hand package-management comparison](https://nx.dev/blog/managing-ts-packages-in-monorepos) usefully separates package-manager linking from project references. A package can resolve through workspace/package metadata while references organize source build work. Our fixture instead uses explicit relative artifacts, so neither package installation nor an import-rewriting tool is implied. An external prebuilt dependency need not have a local source-project reference twin.

For a genuine build performance claim, compare matching fresh, unchanged and edited states using the [native measurement owner](<../../../25 Update TypeScript 7.0/sections/3. Native Build and Watch/3.1. Native builds watch and measurement.md>). Adding a boundary is a design change with a hypothesis to verify, not proof that downstream time is proportional only to declaration text or that every application edit checks just the app.

### 4) **Common confusion**

Project references, source imports, emitted runtime imports and package dependency metadata describe related but distinct graphs. Acyclic project references do not prove that emitted modules contain no cycle or that every architectural layer rule is enforced. A small declaration can also contain an expensive relationship; its byte size does not determine checking time.

Build mode orders dependencies and manages up-to-date work. A regular project check does not build dependencies automatically. Dry mode avoids building altogether. Keep the intended command visible before interpreting its success.

### 5) **Performance note**

The fixture observes declaration consumption, fresh/unchanged/body-edit states and finite graph errors. It does not measure latency, memory improvement, a cost per edge or editor work. Shared libraries can appear in multiple checking programs, and declarations, maps and build information need storage and processing. Measure the actual source graph, consumer work and machine constraints before refining the split.
