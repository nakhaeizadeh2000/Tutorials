## 5.1. Real production bugs caused by scaling misunderstandings

The failure patterns below can affect production build and startup paths. Their evidence here consists of **local reproductions in the linked complete fixtures**, not reported customer incidents. No outage duration, large-repository timing improvement or hosted-cache failure was measured. Follow each fixture for its files, pinned environment, commands and deliberate negative cases.

### 1) **A lower count is mistaken for a valid optimization**

A recursive type can hit TS2589 before completing the requested contract. A shorter erroring run or a lower aggregate instantiation count does not establish a successful replacement. In the [recursion and budget exercise](<../1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>), the failing form reports fewer instantiations than the passing accumulator form. The important difference is that the alternative completes its semantic checks. A deliberately incorrect `never` result is also rejected by a reverse-direction type probe; a one-way assignability observation would miss it.

Diagnose this failure by preserving the compiler's exit status and exact diagnostic, then checking the intended accepted and rejected types. Only compare performance of completed, suitably equivalent work. A depth cap may be useful, but it changes what the transform promises beyond the boundary. The exercise verifies that deeper required fields remain required at its chosen cap. Describe that contract instead of calling the cap a transparent speed fix.

For generated or broad object types, avoid estimating instantiations by multiplying source keys, conditional branches and call sites. The [mapped/conditional alternatives](<../1. Check-Time Performance/1.3. Hot-spot discipline mapped conditional and union cost.md>) demonstrate an additional hazard: a rewritten mapping can lose readonly/optional behavior or widen a variant relationship. Preserve these contracts before measuring a candidate. These local examples do not establish a linear checker complexity formula or a particular generated API's cost.

### 2) **A reference cycle is confused with a hung runtime import**

A project-reference cycle prevents dependency ordering. In the [three-project reference exercise](<../2. Project References and Builds/2.1. Composite partitioning and references architecture.md>), adding the reverse reference creates a finite TS6202 failure, including during dry planning. The observed process does not deadlock. Inspect and repair the reference graph; move genuinely shared contracts to a suitable dependency or redesign the relationship, rather than hiding the cycle with an alias.

Dry planning can reveal this structural problem, but it does not type-check every source. The same exercise deliberately puts a number where the provider promises a string: dry planning exits successfully, while the real build reports TS2322. Keep the actual build as a source gate.

A runtime import cycle is a separate graph and failure. It can exist within a single configured project and pass the type checker. Do not diagnose it from project-reference arrows alone. The next startup case supplies an actual import graph and error.

### 3) **Green incremental status is mistaken for complete current artifacts**

The [cache/output exercise](<../2. Project References and Builds/2.2. Incremental builds and tsbuildinfo discipline.md>) first builds and runs two consumers. It then removes the app's JavaScript while retaining build information. In the tested native 7.0.2 run, the ordinary build exits 0 as up to date, but starting the app fails because its entry file is missing. A forced build regenerates that known output and restores the consumer checks.

That observation supports an artifact-availability diagnosis for this fixture. It does not imply that incremental builds always ignore deleted files, or that every disagreement is a compiler cache defect. Preserve the exact sources, configuration, compiler, cache and output state before comparing runs. The same fixture repeats a source error and observes TS2322 again with the previous JavaScript still present; build state is not a certificate of success, and old output is not a valid fallback test of a failed build.

An additional obsolete sentinel survives both force and known-output clean. Removing the explicitly owned output/cache directories before a fresh rebuild removes it. Consequently force is not a complete output cleanup, and a small cache-key list cannot prove all relevant inputs were represented. Define the restored artifact set, avoid competing writers and run consumers from the actual output. Choose broader verification from risk and shared input changes; no schedule by itself certifies the tests or graph are complete.

### 4) **A curated barrel is treated as cycle prevention**

The [boundary exercise](<../3. Scaling Patterns/3.1. Codebase partitioning boundaries layers and barrels.md>) contains a barrel using explicit named re-exports. Its cycle passes checking and the configured lint rule, then fails on Node initialization with ReferenceError because a binding is read before initialization. No wildcard export is needed. Curation makes a public surface easier to review, but it does not remove import edges or prove safe initialization.

Trace the runtime path and identify the early read. A useful repair can move a shared value into an independent module, pass it through an explicit parameter, or change the dependency direction. Choose a design that preserves the intended contract, then run the actual entry after the change. Merely replacing `export *` with a named list would leave this demonstrated cycle intact.

Inspect the scope of any proposed lint backstop. The fixture's `no-restricted-imports` configuration checks particular static paths; an explicit dynamic import passes that rule and loads the outer module. It is not a general resolved-graph cycle detector. An installed consumer or startup test adds evidence about the path it executes, while unexecuted configurations and branches remain outside that observation. Do not promise all cycles are caught because a single lint command is green.

### 5) **Common confusion**

Different green results answer different questions. Dry planning is about build planning; a completed build checks/emits its selected programs; a runtime entry test checks particular artifact behavior. A lower counter, declaration file or curated export list is not a substitute for the others.

A shared provider's declarations can remain byte-identical while its behavior changes, as the reference fixture demonstrates. Task selection based on an incomplete dependency graph can then omit a consumer: the [affected collector](<../2. Project References and Builds/2.3. Solution builds and CI orchestration with tsc b.md>) reproduces a scoped green result and a full-selection consumer failure. Full selection still depends on the registered assertions; it is broader evidence, not proof of all behavior.

### 6) **Performance note**

These cases establish local correctness and artifact failures. They provide no measured large-repository speedup, outage cost, fixed per-key complexity or universal cache payoff. Use [comparable successful measurements](<../1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) to evaluate an optimization after preserving its relevant contracts. A faster gate that omits a necessary consumer or exits before completing checking has changed the work being measured.

### 7) **Mentor note**

Ask the learner to pair each symptom with the graph or artifact it concerns: TS6202, a missing emitted entry, a runtime initialization ReferenceError and an erroring type recursion. Then ask for a concrete next observation before accepting a cause. Strong answers inspect the reference graph, actual output, import initialization and completed type contract respectively.

For a proposed prevention, ask what it still misses. Good answers mention dry-run source coverage, static-rule scope, unregistered task contracts and obsolete artifacts. Require the actual fixture outcome instead of an invented production history or a guaranteed recovery time.
