## 3.2. Type-only boundaries import type bulk and erasable scale

### 1) **Convert imports while preserving initialization**

At a package boundary, ask two questions separately: does the checker need a declaration, and must the running program evaluate its module? A whole-statement `import type` answers only the first. Under `verbatimModuleSyntax`, `import { type Task }` removes the specifier but retains an empty runtime import. The [complete import graph](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) demonstrates both forms with observable module evaluation. The [compiler reference](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html) documents that distinction.

Before a bulk conversion, identify initialization such as registration performed when a dependency loads. Keep required initialization as an explicit side-effect import from a real runtime module, and use a separate type import for declarations. Do not add such an import to a declarations-only package: there is no implementation to execute. A codemod or lint fix can produce syntactically valid imports while removing behavior the application relied on. The [actual organize-imports experiment](<../../../16 Tooling Language Server and Ecosystem/sections/1. Language Server in Practice/1.2. Rename refactorings and code actions.md>) shows registration disappearing and an explicit side-effect import restoring it.

Convert a coherent package or application boundary, inspect the emitted imports, and execute its actual entry points and relevant initialization contracts. A green checker proves neither retained side effects nor absence of runtime cycles through remaining value imports. An imported type can come from a package that also ships JavaScript; this statement's erasure does not require extracting the type into a new package.

### 2) **Use syntax gates within an execution contract**

`isolatedModules`, `verbatimModuleSyntax` and `erasableSyntaxOnly` constrain different source constructs. They help make type removal and imports predictable; they do not implement a loader, install runtime APIs or prove every transformer accepts the same program. The [trio owner](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) contains a complete checked source/output graph and intentional failures. Keep that execution contract when changing a partition's toolchain: source versus output extensions, module format, package resolution, supported JavaScript syntax, dependencies and host APIs still matter.

An enum or runtime namespace may require transformation where a chosen stripping path cannot support it. That is a constraint on that path, not proof that the entire repository must use one emitter. Conversely, a namespace containing only types or an ambient declaration is not equivalent to a runtime namespace. Declaration files describe a provider; they do not create its values. Choosing `emitDeclarationOnly` for a package containing functions does not provide their implementation. Use the [declaration authoring experiment](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>) for that failure, and [separate checking and emission](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.2. declaration composite project references.md>) for pipeline design.

### 3) **Consume an actual declarations-only package**

A declarations-only package can publish shared static contracts without a runtime entry. Extract one when independent ownership, release coordination and consumer needs justify package maintenance. Consumer count alone supplies no universal threshold. Runtime validators, constructors and error classes require implementations; an interface describing them does not supply those implementations or validate incoming data.

This exercise uses TypeScript **7.0.2**, Node **20.20.2** and npm **10.8.2**, verified 2026-10-17. It packs a local declarations-only package, installs the tarball into a separate consumer, and executes emitted JavaScript. It does not publish anything or test native TypeScript execution. Start in a disposable directory with `contracts` and `consumer/src` directories. Save `contracts/package.json`:

```json
{
  "name": "@lesson/task-contracts",
  "version": "1.0.0",
  "type": "module",
  "files": ["index.d.mts"],
  "exports": {".": {"types": "./index.d.mts"}}
}
```

Save `contracts/index.d.mts`:

```typescript
export interface Task { id: string; state: "queued" | "done" }
export type TaskId = Task["id"];
```

These declarations intentionally export no constructor, validator or function. `TaskId` is a string alias, not a nominal identity check. The export map has a typing condition and no runtime condition. [Node's package documentation](https://github.com/nodejs/node/blob/v20.20.2/doc/api/packages.md#community-conditions-definitions) identifies `types` as a condition for typing systems, ignored by Node by default.

Save `consumer/package.json`:

```json
{"name":"task-consumer","version":"1.0.0","private":true,"type":"module"}
```

Save `consumer/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true
  },
  "include": ["src/**/*.mts"]
}
```

The DOM library supplies the console declaration here; it does not install a browser. Save `consumer/src/main.mts`:

```typescript
import type { Task, TaskId } from "@lesson/task-contracts";
const id: TaskId = "task:1";
const task: Task = { id, state: "queued" };
if (task.state !== "queued") throw new Error("unexpected task state");
console.log(task.id, task.state);
```

Run from the disposable root:

```bash
npm pack ./contracts --pack-destination .
npm install --prefix ./consumer --ignore-scripts --no-audit --no-fund ./lesson-task-contracts-1.0.0.tgz
tsc --version
tsc -p consumer/tsconfig.json
node consumer/dist/main.mjs
```

All commands exit 0; the final command prints `task:1 queued`. Inspect the tarball: it contains package.json and index.d.mts. Inspect `consumer/dist/main.mjs`: there is no import from the package. The consumer supplied its own task object, and the checker resolved its contract from the installed declaration. Node therefore needs no runtime entry for this statement.

Now change only the first line of main.mts to:

```typescript
import { type Task, type TaskId } from "@lesson/task-contracts";
```

Rebuild and run with the same commands. Checking/emission exits 0, but execution exits 1 with `ERR_PACKAGE_PATH_NOT_EXPORTED`: `import {} from "@lesson/task-contracts"` remains, and the package exposes no applicable runtime entry. Restore the whole-statement type import, rebuild and run; the original result returns. This is an import-form failure, not evidence that the declarations failed to install.

For an independent static failure, remove `state` from the task initializer. The compiler exits 1 with TS2741 because Task requires it. Restore it. Then try `console.log(Task)` as a separate change: checking exits 1 with TS2693 because an interface supplies no runtime Task value. Restore, build and run again. `noEmitOnError` prevents a new erroneous output; do not execute an old dist file as proof that an erroring build worked.

### 4) **Common confusion**

A package that has no JavaScript entry and a type-only import from a JavaScript package are different arrangements. Both can support erased imports, but only the latter also has an implementation available through its configured runtime exports. Neither arrangement automatically removes all runtime paths to another dependency.

A declaration package still needs consumer checks. The installed compile/run contrast above tests package layout, resolution and the consumer's emitted graph. More substantial surfaces may need dedicated type tests and supported module-mode fixtures. `tsd` is one possible tool, not a requirement imposed by the word “types.” A package with implementations also needs the relevant runtime contracts; declaration generation does not discharge them.

### 5) **Performance note**

The successful consumer emits no runtime dependency on this package. Its checker still loads and checks the types, and packaging adds release and dependency-management work. This exercise measured no bundle size, checking speed or editor latency. Syntax gates do not imply wall time divided by workers, a fixed transformer speedup or identical behavior through untested tools. Measure the actual pipeline before using a performance claim to justify extraction.

### 6) **Mentor note**

Ask the learner why the first consumer runs despite the absent runtime export, then why the inline form fails even though checking succeeds. A sound answer follows the actual emitted import and separates type resolution from Node's runtime resolution.

For a bulk-import review, ask which entry point would reveal lost registration and which import deliberately retains it. For an extraction proposal, require a consumer contract and an ownership/release reason, rather than counting consumers. Have the learner identify which exported names need real implementations before accepting a declaration-only build.
