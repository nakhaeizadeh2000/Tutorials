## 3.2. Type-only boundaries import type bulk and erasable scale

### 1) **`import type` bulk conversion** (type-traffic stating, emit independence at scale)

**Definition** — *bulk conversion*: migrating type-only imports to `import type` across partitions (verbatim-safe traffic per 12/1.2 + 13/2.2 — emit independence: transpilers dropping imports without cross-file knowledge). Scale effect: per-file transpilability (esbuild/swc/Node-stripping per partition — no type-aware bundler passes), cycle-risk reduction (type imports erasable — runtime cycles unaffected by type edges).

**What problem it solves / history** — mixed value/type imports blocking isolated transpilers (`isolatedModules` errors per file — 13/2.1 demands; single-file pipelines stalling on guessing): stated traffic converting guessing into declarations (per-file transpile safety — build parallelism by construction, see 13/2.1–2.3 trio standard).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enforce `consistent-type-imports` (lint — 16/2.1 tiers; new code stated, legacy converted per 13/4.1 triage); `verbatimModuleSyntax` on new partitions (guessing ends — stated-or-error, see 12/1.2); convert bulk per partition (codemods + review — traffic stated where reviewers see it).

**Runnable example** — stated traffic (good vs bad, `tsc --strict`):

```typescript
// good — type-only aliasing (stated traffic — emit independence demonstrated locally)
export {}; // module marker (consistent module scope across fences)
interface LocalUser { id: string } // local contract (import type { User } from "./domain" in real partitions — stated, erasable)
type AdminView = Pick<LocalUser, "id">; // type-only use (erasable — transpilers dropping, no runtime edge)
declare const v: AdminView;
console.log(v.id); // id — stated traffic (emit-independent — per-file transpile safety at partition scale)
// bad — mixed imports for types (import { User } — value-position type traffic, guessing required, isolated transpilers stalling)
// fix — import type bulk (stated — emit independence by declaration, per partition)
```

```typescript
// good — verbatim-safe re-exports (type barrels erasable — runtime cycles unaffected)
export {}; // module marker (consistent module scope across fences)
interface Contract { id: string } // barrel content (export type { Contract } in real barrels — stated re-export)
export type ContractAlias = Contract; // type-only export (erasable — barrel carrying no runtime edge)
declare const c: ContractAlias;
console.log(c.id); // id — erasable barrels (type traffic stated — cycle-risk reduced structurally)
// bad — value re-exports of types (export { User } — runtime edge for type traffic, cycles + emit coupling)
// fix — export type (barrels erasable — type edges never cycling runtime)
```

**Common confusion** — "`import type` changes semantics" — `import type` *states* existing semantics (type-only traffic already erasable — stating removing guesswork, changing nothing else). "bulk conversion risks behavior" — conversion tooling (`consistent-type-imports --fix`) provably behavior-preserving (erasable traffic — value edges untouched; tests confirming per 17/3.3 gates). "verbatimModuleSyntax only for libraries" — verbatim benefits *partitions* (per-file transpile safety — monorepos gaining build parallelism, see 13/2.2 triage).

**Performance note** — stated traffic enabling isolated transpilation (per-file parallelism — build wall-time ÷ workers; unstated traffic serializing through type-aware passes).

**Mentor note** — conversion PRs: codemod + full gates (mechanical diffs, green suites — review sampling, not line-reading).

### 2) **Erasable-syntax enforcement** (trio standard at partition scale, transpiler freedom)

**Definition** — *trio enforcement* (13/2.3 standard scaled): `isolatedModules` + `verbatimModuleSyntax` + `erasableSyntaxOnly` on every partition (per-file transpilability — any transpiler per partition, esbuild/swc/Node-native interchangeable). Scale effect: build-tool freedom (partitions choosing transpilers independently — migrations incremental, never flag-days).

**What problem it solves / history** — transpiler lock-in (one non-erasable `enum` forcing whole-repo `tsc` — 01/3.3's zero-cost rule violated once, taxing every build): trio enforcement deleting the class (non-erasable syntax unrepresentable — transpiler choice free per partition forever).

**Modern guidance** — trio flags on all partitions (new: day one; legacy: 13/4.1 triage conversion); per-partition transpiler choice (esbuild for apps, `tsc` for leaves needing declarations — horses for courses); CI trio gate (flags verified per project — violations red pre-merge, see 13/4.1 checklist).

**Runnable example** — transpiler freedom (good vs bad, `tsc --strict`):

```typescript
```typescript
// good — trio-clean partition code (any transpiler — freedom by construction)
export {}; // module marker (consistent module scope across fences)
type Status = "active" | "suspended"; // union, not enum (erasable — 11/2.3 decision rule restated at partition scale; import type { Status } from "./domain" in real partitions)
interface Account { id: string; status: Status } // interface + union (trio-clean — esbuild/swc/stripping interchangeable)
declare const a: Account;
console.log(a.status); // active? — trio freedom (syntax erasable — transpiler choice per partition, forever)
// bad — enum in shared partitions (one enum forcing tsc everywhere — transpiler lock-in from a single declaration)
// fix — trio enforcement (non-erasable unrepresentable — freedom by flag, not by vigilance)
```

```typescript
// good — namespace-free organization (modules, not namespaces — 12/2.1 avoid-rule at scale)
export {}; // module marker (consistent module scope across fences)
export const helper = "x"; // module scope (file-organized — erasable, transpilable anywhere)
console.log(helper); // x — modules organizing (no namespace emit — trio-clean by construction)
// bad — namespaces in libraries (compiles under tsc but fails --erasableSyntaxOnly and isolated transpilers — lock-in + merge surprises per 12/2.1)
// fix — modules (file-scoped — organization without runtime cost or transpiler lock-in)
```

**Common confusion** — "trio slows development" — trio *constrains syntax* (enums/namespaces/guessed imports — each replaceable with erasable equivalents per 01/3.3 inventory; friction only where lock-in lurked). "per-partition transpilers fragment builds" — fragmentation *isolates* risk (one partition migrating at a time — flag-days deleted, the 13/2.3 compounding argument). "namespaces organize large code" — modules + barrels organize (namespaces adding merge semantics + emit — cost without benefit at trio scale).

**Performance note** — isolated transpilation 10×–100× faster than `tsc` emit (per-file parallelism — wall-time ÷ workers; trio the enabler, transpilers the engine).

**Mentor note** — trio-PR review: non-erasable syntax blocked like `any` (same severity — lock-in prevented at authoring, not migrated later).

### 3) **Type-only packages** (d.ts-only partitions, contracts versioned independently)

**Definition** — *type-only packages*: partitions emitting only declarations (`.d.ts` + `package.json` `types` — zero runtime: interfaces, branded IDs, API shapes, error taxonomies — versioned independently, consumed by many runtimes). Use cases: shared domain contracts (frontend + backend + workers — one versioned truth), API schemas (client/server codegen inputs), design-token types.

**What problem it solves / history** — runtime-coupled contracts (domain types bundled with server code — frontend importing server bundles for three interfaces, versioning locked to deploys): type-only packages decoupling versioning (contracts releasing independently — consumers upgrading types without redeploying runtimes).

**Modern guidance** — extract shared contracts past 2 consumers (threshold — duplication vs package overhead); version semantically (breaking moves major per 17/3.2 baselines — contracts ARE the product); test surfaces with `tsd` (17/3.2 probes — declaration packages tested like libraries).

**Runnable example** — zero-runtime contracts (good vs bad, `tsc --strict`):

```typescript
// good — contracts versioned independently (zero runtime — many consumers, one truth)
export {}; // module marker (consistent module scope across fences)
export interface Money { cents: number; currency: "USD" | "EUR" } // contract (versioned — frontend + backend + workers consuming one truth)
export type OrderId = string & { readonly __brand: "OrderId" }; // branded (nominal safety — 04/3.2 pattern at package scale)
declare const m: Money;
console.log(m.cents); // cents — independent versioning (contracts releasing without runtime deploys)
// bad — contracts bundled with server runtime (frontend importing server bundles for interfaces — versioning locked to deploys)
// fix — type-only packages past 2 consumers (decoupling versioning — thresholds, not vibes)
```

**Common confusion** — "type packages need runtime tests" — type packages need *surface* tests (`tsd` probes per 17/3.2 — declarations the product, assertions the suite). "versioning types is overkill" — consumers pinning versions need semver signals (breaking moves major — 17/3.2 baselines evidencing; unversioned contracts breaking silently). "duplication simpler than packages" — duplication diverging (3 copies drifting — 2 consumers the threshold where packages win).

**Performance note** — type-only packages zero runtime cost (declarations erased — 01/2.1; check-time shared like all imports — budgeted per 1.2 like every partition).

**Mentor note** — extraction review: consumer count justifying (2+ consumers — threshold met; versioning + tsd probes attached in the same PR).
