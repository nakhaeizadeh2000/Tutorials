## 3.3. Editor performance at scale budgets and tuning

### 1) **Inspect the actual program before setting a budget**

A slow completion, hover and project-wide diagnostic request are different workloads. Record the operation, document state, service/provider version, effective configuration and loaded projects before changing settings. A batch file count helps investigate membership; it does not measure an editor request. The [language-service debugging owner](<../../../16 Tooling Language Server and Ecosystem/sections/3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) demonstrates actual native diagnostic requests and a green disk check alongside an erroneous unsaved buffer.

`include` and `exclude` control root-file discovery. Imports can bring excluded files into the dependency graph. `types` controls automatic inclusion of ambient type packages; it does not forbid explicit type imports. `maxNodeModuleJsDepth` addresses JavaScript discovery in node_modules when JavaScript is allowed, not every declaration dependency or every large program. The [compiler performance guide](https://github.com/microsoft/TypeScript/wiki/Performance#configuring-tsconfigjson-or-jsconfigjson) motivates inspecting file selection and ambient inclusion. Treat its historical implementation advice as a starting hypothesis, not proof about every native service request.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. This complete disposable fixture demonstrates membership and checking, not editor latency. Create `src`, `generated` and `contracts`, then save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": ".",
    "outDir": "dist",
    "noEmitOnError": true
  },
  "include": ["src/**/*.mts"],
  "exclude": ["generated", "dist", "node_modules"]
}
```

Save `contracts/shape.d.mts`:

```typescript
export interface Label { text: string }
```

Save `generated/label.mts`:

```typescript
export const generatedLabel = "generated";
```

Save `generated/unused.mts`:

```typescript
export const invalid: number = "wrong";
```

Save `src/main.mts`:

```typescript
import type { Label } from "../contracts/shape.mjs";
import { generatedLabel } from "../generated/label.mjs";
const label: Label = { text: generatedLabel };
console.log(label.text);
```

The output-extension specifiers match the emitted-only Node execution path. Run:

```bash
tsc -p tsconfig.json --showConfig
tsc -p tsconfig.json --listFilesOnly
tsc -p tsconfig.json --explainFiles
tsc -p tsconfig.json
node dist/src/main.mjs
```

All commands exit 0; runtime prints `generated`. The root configuration selects main.mts, while the complete file list also includes generated/label.mts, contracts/shape.d.mts and standard library declarations. explainFiles identifies the two explicit import paths. generated/unused.mts is absent. Therefore a green check has not validated that unimported file. The declared rootDir allows both source and generated input paths; it is not an import permission boundary.

Add `import "../generated/unused.mjs";` to main.mts. Checking now exits 1 with TS2322 in the excluded directory, and listFilesOnly includes unused.mts. Restore main. For another contrast, remove the generated import and initialize label.text with `"local"`. The generated implementation disappears from the file list, while shape.d.mts remains despite `types: []`. Restore the original, compile and run to recover `generated`.

Use such evidence to fix accidental roots or imports. Importing declarations from a referenced package's emitted directory can be intentional, as the [reference architecture](<../2. Project References and Builds/2.1. Composite partitioning and references architecture.md>) demonstrates. A blanket rule that every dist import doubles a program would reject valid boundaries.

### 2) **Treat reference redirects as a provider-specific experiment**

The [disableSourceOfProjectReferenceRedirect option](https://www.typescriptlang.org/tsconfig/disableSourceOfProjectReferenceRedirect.html) selects declaration boundaries instead of source-based reference behavior in supporting project services. It is not a per-edge “stable dependency” label or a guarantee that an editor loads no upstream sources. Establish the actual provider's support, then compare the same definition or completion request with the setting changed in the consuming configuration.

Have the referenced declaration artifacts available when the selected path needs them. Declaration maps can relate emitted declarations to source locations, but successful emission of a .d.mts.map does not prove that the editor resolves its source paths or displays the desired target. Verify navigation with the actual client, artifacts and source availability. A CLI list showing referenced declarations proves that batch program's membership; it does not prove a language service's redirect behavior or latency.

The fixture above does not test redirects or an editor UI. The [native navigation exercise](<../../../16 Tooling Language Server and Ecosystem/sections/1. Language Server in Practice/1.1. Navigation go to definition find references.md>) and debugging owner explain the actual requests already verified. Preserve that distinction when proposing a new provider-specific experiment.

### 3) **Distinguish configured projects from service processes**

A tsconfig describes a project, not a command to launch one dedicated server process. Multiple projects can be handled by a service; a multi-root workspace alone does not prove process isolation, independent restarts or preserved warm state elsewhere. Identify the editor integration and inspect its actual processes and project/request evidence before making those claims. Native TypeScript 7's LSP provider also differs from the historical Node tsserver integration; settings and logs must match the selected provider.

A useful team runbook starts with reproducing a named operation and preserving a small relevant trace or log. Check saved versus open content, project ownership and configuration loading. Then change one plausible cause, repeat the operation, and record the result. Restarting a service is a valid experiment or recovery action, but it changes process state and project loading. The symptom disappearing does not establish cache corruption. Deleting .tsbuildinfo affects build state, not automatically a running editor's memory; [incremental artifact discipline](<../2. Project References and Builds/2.2. Incremental builds and tsbuildinfo discipline.md>) owns that separate problem.

Set project or response budgets from representative workloads and agreed user expectations. Preserve correctness and useful navigation while testing changes. No universal file ceiling distinguishes legitimate feature growth from accidental inclusion; a count can trigger investigation without deciding the remedy.

### 4) **Common confusion**

An excluded file can still be checked through an import, as the intentional failure demonstrates. Conversely, a green project can leave an unrelated excluded implementation entirely unchecked. Removing files from a program may reduce work by abandoning coverage, so compare the intended contract as well as the count.

A declaration map is a navigation artifact, not a guarantee of identical editor behavior. A project is a configuration unit, not necessarily a process isolation unit. Neither a green CLI command nor restarting a server proves that a specific interactive operation meets its response target.

### 5) **Performance note**

Program membership and type relationships can affect service work, but no timing or memory benchmark was run here. Removing accidental inputs is a candidate improvement; fixed superlinear speedups, universal file thresholds and negligible multi-process overhead are unsupported. Multiple projects can repeat checking of shared dependencies. Compare the same operation, document and cold/warm state through the actual provider, and keep diagnostic/profiling overhead distinct from normal execution.

### 6) **Mentor note**

Show the excluded generated directory and ask whether label.mts and unused.mts are checked. A sound answer traces imports and distinguishes root discovery from dependency closure. Then ask what the green result says about unused.mts: nothing about its correctness until it belongs to a checked program.

For an editor complaint, require the exact slow operation and provider before accepting a configuration change. Ask the learner what observation would demonstrate improved navigation or responsiveness, and what evidence would distinguish a changed input from a stale diagnostic. Reject a process-isolation explanation based only on the number of tsconfig files.
