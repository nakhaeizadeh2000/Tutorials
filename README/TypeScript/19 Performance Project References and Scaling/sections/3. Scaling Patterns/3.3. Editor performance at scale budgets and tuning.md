## 3.3. Editor performance at scale budgets and tuning

### 1) **Program-size budgets** (file symbol ceilings, include scoping, node depth)

**Definition** — *program budgets*: ceilings on editor-program size (files/symbols per `tsserver` project — responsiveness degrading superlinearly past thresholds): controls — `include` scoping (sources only, no build output/dist — the #1 program-bloat cause), `maxNodeModuleJsDepth` (JS-in-`node_modules` traversal depth — deep traversal exploding programs), `types` scoping (`@types` allowlisting — unused globals unloaded).

**What problem it solves / history** — 50k-file editor programs (dist/ + node_modules-JS + all @types loaded — completions in seconds, hovers timing out): scoping restoring programs to sources (thousands, not tens of thousands — responsiveness returning without hardware upgrades, see 16/3.1 triage this leaf budgets for).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), scope `include` to sources (exclude dist/build/coverage — bloat class #1); set `maxNodeModuleJsDepth: 0`–1 unless JS-navigation needed (depth class #2); allowlist `types` per project (node/jest/vitest as needed — unused globals unloaded, class #3). Budget: files-per-project ceilings in CI (growth loud — programs staying scoped).

**Runnable example** — scoped programs, shown as labeled config docs plus a type fence (good vs bad, `tsc --strict`):

```jsonc
// good — scoped program (sources only — bloat classes excluded by configuration)
// tsconfig.app.json (labeled config doc): {
//   "include": ["src"], "exclude": ["dist", "build", "coverage"],
//   "compilerOptions": { "maxNodeModuleJsDepth": 0, "types": ["node"] } }
// (3 bloat classes excluded: outputs, deep-JS, unused-globals — programs scoped to sources)
```

```typescript
// good — scoped imports (sources importing sources — program boundaries respected)
export {}; // module marker (consistent module scope across fences)
export interface ScopedApi { version: string } // source contract (include-scoped — editor program containing sources, not outputs)
declare const api: ScopedApi;
console.log(api.version); // version — scoped programs (thousands of files — completions instant, hovers immediate)
// bad — dist imports in sources (build outputs imported — programs doubling with generated files, bloat class #1)
// fix — source-only imports (outputs never imported — boundaries respected, programs scoped)
```

**Common confusion** — "exclude slows nothing" — `exclude` *defines* program membership with `include` (unscoped includes pulling dist — exclusion the fix, not an optimization). "more @types is safer" — each `@types` package loads globals (programs bloating per package — allowlisting loading only needed globals). "budgets block features" — budgets block *bloat* (scoped growth updating ceilings with traces — features shipping with evidence per 1.1).

**Performance note** — scoping effects superlinear (50k→5k files — completions seconds→milliseconds; program size dominating tsserver latency per 16/3.1 profiles).

**Mentor note** — editor-complaint triage step zero: program file count (unscoped programs diagnosed in seconds — scoping before hardware, always).

### 2) **`disableSourceOfProjectReferenceRedirect` triage** (declaration-redirect tradeoffs)

**Definition** — *redirect*: with project references, tsserver by default loads upstream *sources* (not declarations — navigation jumping to `.ts` implementations, at the cost of larger programs); `disableSourceOfProjectReferenceRedirect: true` flips to *declarations* (programs smaller — navigation landing on `.d.ts` stubs, `declarationMap` restoring jumps per 2.1 part 2). Tradeoff: responsiveness (declarations — small programs) vs navigation fidelity (sources — implementation jumps).

**What problem it solves / history** — reference-monorepo editors crawling (upstream sources inflating every downstream program — 2.1's emit-once speed applying to builds but editors loading sources anyway): redirect triage choosing per project (huge stable leaves → declarations; churning neighbors → sources — responsiveness where stable, fidelity where editing).

**Modern guidance** — default sources (fidelity first — navigation to implementations, 16/1.1 workflows intact); flip to declarations for huge-stable upstreams (leaves rarely edited — programs slashed, navigation via `declarationMap`); measure per project (16/3.1 responsiveness triage — program sizes before/after, latency evidenced).

**Runnable example** — redirect choice (good vs bad, `tsc --strict`):

```jsonc
// good — per-project redirect triage (sources by default, declarations for huge-stable leaves)
// tsconfig.app.json (labeled config doc): { "extends": "./base", "references": [{ "path": "../leaves" }] }
// tsconfig.huge-stable.json (labeled config doc): { "compilerOptions": { "disableSourceOfProjectReferenceRedirect": true } }
// (leaves program slashed — navigation via declarationMap per 2.1; apps keeping source fidelity)
```

```typescript
// good — declarationMap preserving navigation (redirect without fidelity loss — jumps through declarations to sources)
export {}; // module marker (consistent module scope across fences)
export function leafFn(n: number): number { return n * 2; } // leaf impl (declarationMap linking — navigation landing here via the .d.ts stub)
console.log(leafFn(21)); // 42 — maps preserving (redirect triaged — responsiveness gained, fidelity kept via maps)
// bad — redirect without maps (navigation landing on .d.ts stubs — implementations unreachable, debugging via emitted guesses)
// fix — declarationMap with redirect (triaged pair — programs small AND navigation faithful)
```

**Common confusion** — "redirect always faster" — redirect shrinks programs using *stable* upstreams (churning upstreams re-emitting declarations constantly — redirect churning caches, net slower; triage per stability, see 2.1 change-rate). "maps cost performance" — maps cost emit bytes (sourcemap-adjacent — check-time unaffected; navigation fidelity for disk space, always worth it). "one setting per repo" — per-*project* triage (stability varying — huge-stable redirected, churning sourced; blanket settings mistriaging half the graph).

**Performance note** — redirect effects ∝ upstream source size (huge leaves slashed 10× — programs; churning neighbors unaffected-or-worse — triage measured per 16/3.1).

**Mentor note** — editor-perf review per reference: "sources or declarations?" (stability deciding — huge-stable redirected with maps; rest sourced).

### 3) **Multi-project editor setup** (per-partition tsservers, solution loading, restart runbooks)

**Definition** — *multi-project editing*: editors hosting one `tsserver` per partition (VS Code multi-root / `typescript.tsserver` per `tsconfig` — fault isolation: one sick project never slowing others) + *solution-aware loading* (solution file orienting — editors discovering the graph, not globbing blindly) + *restart runbooks* (documented recovery: reload window → restart TS server → clear editor cache → report with traces — 16/3.1 debugging operationalized per team).

**What problem it solves / history** — single-server monorepos (one tsserver for 50k files — sick-file stalls freezing all editing, restarts losing all warmth): partitioning isolating faults (sick project restarts alone — others warm, editing continuing) + runbooks standardizing recovery (restart folklore replaced by ordered steps with evidence collection).

**Modern guidance** — one tsserver per reference partition (fault isolation — editors configured per tsconfig, not per repo root); solution file at root (graph discovery — editors loading partitions, not globs); runbook in CONTRIBUTING (reload → restart-server → clear-cache → trace-and-report — ordered recovery, 16/3.1 evidence attached on escalation).

**Runnable example** — isolated editing (good vs bad, `tsc --strict`):

```text
// good — restart runbook (ordered recovery — folklore replaced by steps with evidence)
// CONTRIBUTING.md excerpt (labeled doc — team runbook):
// 1. Cmd/Ctrl+Shift+P → "Reload Window" (fastest — transient stalls)
// 2. "TypeScript: Restart TS Server" (project-scoped — sick partition restarting alone)
// 3. Clear editor TS cache + restart (staleness per 2.2 — cache bugs distinguished)
// 4. Attach trace (16/3.1 evidence — escalation with numbers, not adjectives)
```

```typescript
// good — partition-scoped editing (faults isolated — sick files stalling one server, not all)
export {}; // module marker (consistent module scope across fences)
export function partitionFn(s: string): string { return s.trim(); } // partition code (server-scoped — stalls contained per partition, editing continuing elsewhere)
console.log(partitionFn("  x ")); // x — isolation paying (faults partitioned — velocity unblocked except by ownership)
// bad — root-glob editor config (one server, whole repo — sick files freezing all editing, restarts losing all warmth)
// fix — per-partition servers (isolation — faults contained, warmth preserved)
```

**Common confusion** — "more servers use more memory" — servers sized by *partition* (sum ≈ monolith — isolation free-ish; sick-partition restarts saving more warmth than extra processes cost). "runbooks insult seniors" — runbooks *accelerate* seniors (ordered steps skipping folklore — evidence collection built in, escalations pre-triaged). "solution files are build-only" — solution files *orient* editors (graph discovery — loading partitions deliberately, the 2.3 orchestration file doubling as editor config).

**Performance note** — partition servers ∝ partition programs (sum comparable — isolation's price ~process overhead, trivial vs stall costs); runbooks saving hours per incident (ordered recovery vs folklore flailing).

**Mentor note** — onboarding: runbook exercised day one (restart drill — recovery practiced before needed, evidence habits formed early).
