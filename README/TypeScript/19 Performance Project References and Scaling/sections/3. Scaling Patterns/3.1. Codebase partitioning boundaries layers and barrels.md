## 3.1. Codebase partitioning boundaries layers and barrels

A boundary is a chosen dependency rule, not a property inferred from folder names. Separate the intended module relationship from what TypeScript resolution, a lint rule, a project reference and the runtime each enforce. A useful design makes those decisions visible and tests the rules that matter.

Use **TypeScript 7.0.2** for the compiler CLI and **Node.js 20.20.2**, verified 2026-10-17. This fixture also pins ESLint 10.12.0 and its TypeScript parser 8.71.1. The parser uses the separately installed TypeScript 6.0.3 JavaScript API; it does not replace the native 7.0.2 compiler. Run tsc directly as the verified global CLI, outside npm scripts, and confirm its version. The rule used here is a static-import restriction, not a type-aware lint service.

### 1) **State a dependency rule and execute its actual check**

This small policy lets app code use domain contracts and operations. Domain files must not statically import the named app or infra paths. The policy is useful when those modules represent responsibilities that should remain independent; it does not prove that changing domain code cannot affect consumers or that every application should have these exact layers.

Save the files in a fresh directory, omitting file-label comments from JSON:

```json
// file: package.json
{
  "private": true,
  "type": "module",
  "devDependencies": {
    "eslint": "10.12.0",
    "@typescript-eslint/parser": "8.71.1",
    "typescript": "6.0.3"
  }
}
```

```json
// file: tsconfig.json
{
  "compilerOptions": {
    "strict": true, "target": "ES2022", "module": "NodeNext",
    "lib": ["ES2022", "DOM"], "types": [],
    "rootDir": "src", "outDir": "dist", "noEmitOnError": true,
    "paths": { "#domain": ["./src/domain/index.mts"] }
  },
  "include": ["src/**/*.mts"]
}
```

```javascript
// file: eslint.config.mjs
import tsParser from "@typescript-eslint/parser";
export default [
  {
    files: ["src/**/*.mts"],
    languageOptions: { parser: tsParser, sourceType: "module" },
  },
  {
    files: ["src/domain/**/*.mts"],
    rules: {
      "no-restricted-imports": ["error", {
        patterns: [{ group: ["../app/*", "../infra/*"],
          message: "Domain must not depend on these outer paths." }],
      }],
    },
  },
];
```

```typescript
// file: src/domain/user.mts
export interface User { id: string }
export function userLabel(user: User): string { return "user:" + user.id; }
// export async function loadOuter() { return import("../infra/config.mjs"); }
// file: src/domain/index.mts
export { userLabel } from "./user.mjs";
export type { User } from "./user.mjs";
// file: src/app/view.mts
import { userLabel, type User } from "../domain/index.mjs";
export interface View { user: User; caption: string }
export function describe(view: View): string { return userLabel(view.user) + ":" + view.caption; }
// file: src/infra/config.mts
export const prefix = "infra";
// file: src/main.mts
import { describe } from "./app/view.mjs";
console.log(describe({ user: { id: "u1" }, caption: "home" }));
```

Run npm install, `tsc --version`, `tsc -p tsconfig.json`, `node_modules/.bin/eslint src` and `node dist/main.mjs`. The CLI version must be 7.0.2; compilation and lint pass, and the main entry prints user:u1:home. The selected parser dependencies are deliberately compatible JavaScript tools, as explained in the [actual tooling owner](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>).

For a deliberate boundary violation, add `import { prefix } from "../infra/config.mjs";` to user.mts and use prefix instead of the string user in its return expression. The compiler accepts the program, but ESLint reports no-restricted-imports. The paths setting supplies a resolution mapping for #domain; it is not an allow-list forbidding other relative imports and does not itself rewrite emitted specifiers. The example uses relative runtime imports, so no runtime alias implementation is implied.

Restore userLabel. Now activate the commented loadOuter function. Both compilation and this lint rule pass: the [core rule documentation](https://eslint.org/docs/latest/rules/no-restricted-imports) explicitly limits it to static imports. This is a counterexample to the claim that one pattern rule proves all layer dependencies are absent. Restore the comment afterward. A broader policy needs tools and tests that model its actual specifier forms, resolved paths, dynamic loading and type-only edges as appropriate.

### 2) **Curate a public surface without assuming acyclic evaluation**

The domain barrel names userLabel and User deliberately. This makes its intended API reviewable; it does not by itself hide every physical module, enforce a package export map or prove freedom from cycles. An internal module can import a specific owner file when that avoids an unnecessary public-barrel dependency. Whether an external consumer may use a deep package path is a separate supported-exports decision.

Explicit named re-exports can form cycles too. Add this intentionally failing runtime graph to the same source tree:

```typescript
// file: src/cycle/a.mts
export { b } from "./b.mjs";
export const a = "a";
// file: src/cycle/b.mts
import { a } from "./a.mjs";
export const b: string = a + "b";
```

Rebuild and rerun lint. Both pass because this restriction is not a cycle analyzer. Loading dist/cycle/a.mjs fails: evaluation enters b, which reads a before a's const initialization. The cycle uses a named re-export, so replacing stars with curated names is not a general cycle repair. Some cycles are benign under their actual initialization; this particular read is not.

Save the consumer below and run `node verify.mjs` after building all files. It checks both the valid entry and the intentional cycle failure:

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { spawnSync } from "node:child_process";
const main = spawnSync(process.execPath, ["dist/main.mjs"], { encoding: "utf8", timeout: 5000 });
assert.ifError(main.error);
assert.equal(main.status, 0, main.stderr);
assert.equal(main.stdout.trim(), "user:u1:home");
const cycle = spawnSync(process.execPath,
  ["--input-type=module", "-e", 'await import("./dist/cycle/a.mjs")'],
  { encoding: "utf8", timeout: 5000 });
assert.ifError(cycle.error);
assert.equal(cycle.status, 1);
assert.match(cycle.stderr, /ReferenceError/);
console.log("valid layered entry and named-cycle failure observed");
```

The [module-forms owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.1. import and export forms named default star re-export.md>) develops named/default/star bindings, ambiguity and evaluation. Keep those mechanics there; this example adds the architectural distinction between a curated surface and an actual dependency cycle. Import-graph analysis and runtime entry checks should address the graph the application loads, rather than declaring every barrel unsafe or every curated barrel safe.

### 3) **Define contract checks at the boundary that consumers use**

A public type describes accepted inputs and outputs, while a runtime implementation must satisfy the promised behavior. The View interface in the fixture does not construct a view, validate an external payload or prove that describe returns the intended string. The main entry constructs a real object and the consumer checks its actual result.

A fake implementing an interface likewise proves only the checked structural relationship. The [executed generic-fake contract suite](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.2. Spies stubs and fakes over generics.md>) demonstrates a type-correct fake whose behavior fails. Use shared behavioral checks where useful and acknowledge which implementations were exercised; divergence is not impossible merely because implements appears in the class.

For packages, the [installed declaration-surface tests](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) and [packed-package owner](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) test consumer entry points and blocked deep paths. A local barrel import does not certify the installed tarball or every semantic compatibility promise. A reference edge does not make that package boundary private either; the [reference fixture](<../2. Project References and Builds/2.1. Composite partitioning and references architecture.md>) separates those graphs.

Choose boundaries and tests from the dependencies and contracts that exist, rather than requiring a fake, adapter or three artifacts for every seam. A plain function can provide an appropriate boundary; decorator-driven dependency injection is not a prerequisite for this TypeScript module exercise. Measure the actual graph before attributing a checking or runtime improvement to the layer labels.

### 4) **Common confusion**

Paths maps specifiers; it does not ban arbitrary other imports. The shown lint rule matches selected static spellings within selected domain files; a pass does not certify an entire resolved architecture. Type-only dependency rules and runtime dependency rules may intentionally differ.

Curated names express API intent, while evaluation follows actual module edges. A cycle can arise with explicit names, and a public barrel can re-export types whose statements erase. Trace the particular runtime edges and initialization reads before diagnosing a startup failure.

### 5) **Performance note**

The fixture verifies imports, a real lint diagnostic and runtime behavior. It measures no check-time gain, bundle size, invalidation scope or cycle-analysis latency. Linting itself performs work, and runtime wrappers, factories and closures are executable rather than erased types. Broader or narrower boundaries can alter the graph and repeated checking; use the [measurement protocol](<../1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before claiming a speed benefit.

### 6) **Mentor note**

Ask a learner why the forbidden relative import compiles despite paths, then why dynamic import escapes this static-only rule. A sound answer states the intended policy and the precise coverage of the checker. Next load the named-re-export cycle and identify the read before initialization. Finally, distinguish the View type check, expected runtime output and an installed package's supported exports: each requires its own evidence.
