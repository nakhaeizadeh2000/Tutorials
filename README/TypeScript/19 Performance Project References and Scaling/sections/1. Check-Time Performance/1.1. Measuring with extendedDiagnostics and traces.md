## 1.1. Measuring with extendedDiagnostics and traces

Start with the operation that feels slow: a fresh CLI check, a build after one edit, an editor request, or emitted application code. They have different inputs, state and measurements. Compiler diagnostics can explain a checking workload, but cannot measure application latency or certify editor responsiveness.

This complete fixture uses **TypeScript 7.0.2**, **@typescript/analyze-trace 0.11.1**, **Node.js 20.20.2** and npm 10.8.2 on Linux, verified 2026-10-17. It demonstrates collecting and inspecting actual diagnostics and traces. The source is intentionally small: this is not an optimization benchmark or a claim about a production hot spot.

### 1) **Establish the checking program before interpreting counters**

The [primary performance guide](https://github.com/microsoft/TypeScript/wiki/Performance#extendeddiagnostics) explains diagnostic fields and checking phases. The exact output depends on the implementation and version. In this native compiler, the fixture reports Files, Lines, Identifiers, Symbols, Types, Instantiations, Memory used, Memory allocs and phase times. It does not report an assignability cache hit rate. Do not invent one from an older screenshot or turn a cache size into a percentage.

Files and lines describe the selected program, including its standard library. Unexpected growth can reveal an unintended inclusion or dependency. Types and instantiations describe checker work across that program; a mapped type over three properties does not imply exactly three reported instantiations. Repeated aliases also do not prove a particular cache hit or one-time computation. Check time is a compiler-reported phase time, not the external elapsed time of the entire command. Parallel or nested work prevents simply adding every duration into an exclusive wall-clock total.

Create a fresh directory and save:

```json
// file: package.json
{
  "private": true,
  "type": "module",
  "devDependencies": {
    "typescript": "7.0.2",
    "@typescript/analyze-trace": "0.11.1"
  }
}
```

```json
// file: tsconfig.json
{
  "compilerOptions": {
    "strict": true, "target": "ES2022", "module": "NodeNext",
    "lib": ["ES2022"], "types": [], "incremental": false, "noEmit": true
  },
  "files": ["sample.mts"]
}
```

```typescript
// file: sample.mts
export interface Config { label: string; retries: number; enabled: boolean }
export type ReadonlyConfig = { readonly [K in keyof Config]: Config[K] };
export const config: ReadonlyConfig = { label: "ready", retries: 2, enabled: true };
type Expect<T extends true> = T;
type Keys = Expect<keyof ReadonlyConfig extends "label" | "retries" | "enabled" ? true : false>;
// config.retries = 3;
```

Run npm install, then `node_modules/.bin/tsc --version` to confirm 7.0.2. Run `node_modules/.bin/tsc -p tsconfig.json --listFilesOnly` and inspect the source plus bundled libraries. Run `node_modules/.bin/tsc -p tsconfig.json --extendedDiagnostics > diagnostics.txt`. The selected source passes; noEmit produces no application output. Uncomment the assignment and rerun: TS2540 must fail the check even though diagnostics can still print counters. Restore it before treating the report as a successful baseline.

A small counter from a failed check is not an improvement over completed checking. The [instantiation-budget owner](<./1.2. Instantiation budgets and TS2589 carve-outs.md>) reproduces a failing expansion with fewer instantiations than its successful replacement. Use that complete budget implementation when a package needs a counter gate; this page does not pretend that a JSON budget file enforces itself.

### 2) **Generate a trace and follow its actual file mapping**

Run `node_modules/.bin/tsc -p tsconfig.json --generateTrace trace`, then `node_modules/.bin/analyze-trace trace --skipMillis 0 --forceMillis 0 --color false`. The [maintainer's analyzer guide](https://github.com/microsoft/typescript-analyze-trace#usage) describes this CLI and its thresholds. Zero thresholds here expose even tiny file spans for an inspection exercise; they are not recommended production alert settings. The output includes the project and file-check observations. Default thresholds may hide this small fixture entirely.

The native trace generated here includes trace.json, legend.json and multiple checker-specific type files. Read legend entries to associate checker IDs with their typesPath; do not assume every run produces one types.json or a fixed checker count. The fixture below validates those associations and locates actual checkSourceFile events for sample.mts.

The [performance-tracing guide](https://github.com/microsoft/TypeScript/wiki/Performance-Tracing) explains wall duration, self time and nested events, while warning that formats can change and tracing affects durations unevenly. Its older single-Main-thread screenshots are not a complete native parallel trace model. An inclusive file span can contain expensive nested work; summing overlapping thread or parent/child spans double-counts time. A wide span is an investigation candidate, not proof that the named file is bad or that changing its syntax preserves the API.

A trace can be loaded into a compatible trace viewer for manual inspection, but this lesson verifies generated JSON and actual analyzer output rather than claiming a browser UI session. Keep the source, compiler, configuration and trace together: moving files or changing the program after capture can make attribution misleading. A useful investigation reduces the observed expensive case and tests a candidate change against its required types and behavior.

For native profiling, also run `node_modules/.bin/tsc -p tsconfig.json --pprofDir profiles`. This compiler prints paths to CPU and memory .pb.gz artifacts. Those are pprof artifacts, distinct from the older JavaScript compiler's V8 CPU profile. The verification below checks their presence and gzip readability; it does not analyze samples, open a pprof viewer, or claim that a tiny CPU capture contains useful statistical detail.

Save:

```javascript
// file: inspect.mjs
import assert from "node:assert/strict";
import { readFileSync, readdirSync, existsSync } from "node:fs";
import { gunzipSync } from "node:zlib";
const diagnostics = readFileSync("diagnostics.txt", "utf8");
for (const field of ["Files", "Types", "Instantiations"]) {
  const match = new RegExp("^" + field + ":\\s+(\\d+)$", "m").exec(diagnostics);
  assert.ok(match, "missing " + field);
  assert.ok(Number(match[1]) > 0);
}
const legend = JSON.parse(readFileSync("trace/legend.json", "utf8"));
assert.ok(Array.isArray(legend) && legend.length > 0);
const traceFiles = new Set();
for (const entry of legend) {
  assert.equal(typeof entry.checkerId, "number");
  assert.ok(entry.configFilePath.endsWith("tsconfig.json"));
  assert.ok(existsSync(entry.typesPath));
  assert.ok(Array.isArray(JSON.parse(readFileSync(entry.typesPath, "utf8"))));
  traceFiles.add(entry.tracePath);
}
const sourceChecks = [];
for (const file of traceFiles) {
  const events = JSON.parse(readFileSync(file, "utf8"));
  sourceChecks.push(...events.filter(event => event.name === "checkSourceFile" &&
    event.args?.path?.endsWith("sample.mts")));
}
assert.ok(sourceChecks.length > 0, "sample must actually be checked in the trace");
for (const kind of ["cpuprofile", "memprofile"]) {
  const profile = readdirSync("profiles").find(name => name.endsWith("-" + kind + ".pb.gz"));
  assert.ok(profile, "missing " + kind);
  assert.ok(gunzipSync(readFileSync("profiles/" + profile)).length > 0);
}
console.log("diagnostics, checker trace mappings and compressed profiles verified");
```

Run `node inspect.mjs`. It validates real files, rather than printing an assertion that tracing happened. Deliberately replace sample.mts in the event filter with absent.mts: the assertion fails because that source was not checked. Restore it. This script intentionally depends on the observed 7.0.2 layout for the exercise; adapt it when a compiler's trace schema changes.

### 3) **Measure elapsed commands separately from an instrumented trace**

Save the following simple repeated-check collector. It starts a fresh compiler process each time with incremental reuse disabled by the published configuration. The interval includes process launch and the compiler invocation. It does not isolate CPU time, flush operating-system caches, measure native peak RSS, or determine editor latency.

```javascript
// file: measure.mjs
import { performance } from "node:perf_hooks";
import { spawnSync } from "node:child_process";
import { writeFileSync } from "node:fs";
const samples = [];
for (let trial = 1; trial <= 3; trial++) {
  const start = performance.now();
  const result = spawnSync("node_modules/.bin/tsc", ["-p", "tsconfig.json"], {
    encoding: "utf8", timeout: 30000,
  });
  const wallMilliseconds = performance.now() - start;
  if (result.error || result.status !== 0) {
    throw result.error ?? new Error(result.stdout + result.stderr);
  }
  samples.push({ trial, wallMilliseconds });
}
writeFileSync("measurements.json", JSON.stringify(samples, null, 2));
console.log(samples);
```

Run `node measure.mjs`. It saves three successful uninstrumented command durations without claiming a ranking or a speedup. Three tiny-process samples are an exploratory record; startup and machine noise can dominate. For a meaningful before/after comparison, retain inputs and options, separate fresh/incremental/edited states, vary order when appropriate, and use enough representative samples for the decision.

The [complete native build/watch experiment](<../../../25 Update TypeScript 7.0/sections/3. Native Build and Watch/3.1. Native builds watch and measurement.md>) owns a fuller two-version comparison, source edits, emitted-consumer assertions, external wall/RSS measurement and finite watch transitions. It explains why measuring the npm launcher's memory may identify the wrong process. [Pashalis Laoutaris's first-hand benchmark account](https://laoutaris.org/blog/typescript-benchmark/) reports that same measurement mistake and skipped-work pitfalls; its Windows ratios are not predictions for this fixture.

For an optimization proposal, state the user-visible operation, the measured bottleneck and the contract that must remain equivalent. Try a candidate change, rerun correctness checks, compare matching measurements and inspect remaining uncertainty. An unexpected counter movement can teach something even when elapsed time improves. A neutral performance result can still accompany a justified readability fix; simply label that motivation honestly instead of inventing a speed claim.

### 4) **Common confusion**

Counters, internal phase durations, external wall time and process memory are different quantities. A lower instantiation count cannot certify a faster build, and a successful CLI check cannot certify an editor query. Removing a public union member may make checking easier by changing the API; that is not an equivalent optimization.

A trace helps locate work but does not guarantee a fixed proportion of the code owns a fixed proportion of cost. Even analyzer output requires context, especially with tiny spans and parallel checking. Retain the source and reduce the actual expensive relationship before replacing it based on an abstract rule about mapped types or aliases.

### 5) **Performance note**

Diagnostics, tracing, profiling and artifact I/O can change the workload. This lesson does not measure their overhead or prescribe a universal always-on policy. Use uninstrumented runs for the elapsed operation comparison, and targeted captures to explain a suspected bottleneck. Native and JavaScript compiler counters are implementation-dependent; compare versions with a common external instrument and matched work, as the update experiment does.

### 6) **Mentor note**

Hand a learner two reports: one fails TS2540 quickly, the other checks successfully with more instantiations. Ask which is a valid baseline and why. Then ask them to point from sample.mts to its trace event and checker-specific type file. A sound answer follows actual compiler output, distinguishes exclusive from inclusive work, and asks for matching-state elapsed measurements before claiming an optimization.
