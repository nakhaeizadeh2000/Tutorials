## 1.2. Instantiation budgets and TS2589 carve-outs

### 1) **Instantiation counting**

An instantiation counter describes compiler work while applying generic types. It is not a count of source lines, runtime operations, or mapped keys. Conditional distribution, repeated relationships, library checking and implementation reuse all affect the total. “Branches × members × keys” can suggest where growth might occur, but it is not a formula for the reported counter or check time.

Use a pinned compiler, fixed inputs and fixed options to compare changes. The [TypeScript performance guide](https://github.com/microsoft/TypeScript/wiki/Performance) explains the diagnostics workflow; the [measurement owner](<./1.1. Measuring with extendedDiagnostics and traces.md>) develops the broader investigation. A team budget is a review threshold based on its own baseline, not a limit built into the language.

The following fixture uses TypeScript 7.0.2, reverified on 2026-10-17. Create `before` and `after` directories. Save the same `tsconfig.json` in each:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "commonjs",
    "types": [],
    "lib": [
      "es2022"
    ],
    "noEmit": true
  },
  "files": [
    "example.ts"
  ]
}
```

Save this as `before/example.ts`:

```typescript
export {};
type Chars<S extends string> = S extends `${infer C}${infer Rest}` ? C | Chars<Rest> : never;
type Letters = Chars<"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa">;
```

Save this as `after/example.ts`:

```typescript
export {};
type Chars<S extends string, Acc extends string = never> = S extends `${infer C}${infer Rest}` ? Chars<Rest, Acc | C> : Acc;
type Letters = Chars<"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa">;
type Expect<T extends true> = T;
type Check = Expect<Letters extends "a" ? true : false>;
type NonEmpty = Expect<"a" extends Letters ? true : false>;
```

The input is 60 ASCII `a` characters. The first version retains a pending union operation at each recursive step. The second carries accumulated characters as an argument and returns the recursive result directly. `Expect` constrains its argument at compile time; it declares no pretend runtime assertion function. With this input, the expected character union is `"a"`. The two directional checks exclude both extra members and an empty never result. A one-way Letters extends "a" check alone would accept never; change the accumulator's final Acc to never to see the second check reject that regression.

From the parent directory, run these independently:

```sh
tsc -p before/tsconfig.json --extendedDiagnostics > before/diagnostics.txt
tsc -p after/tsconfig.json --extendedDiagnostics > after/diagnostics.txt
```

The first command is intentionally unsuccessful with TS2589. The second passes. Observed counters were:

| Fixture, compiler 7.0.2 | Result | Types | Instantiations |
|---|---|---:|---:|
| Same config, source reduced to `export {}; type Letters = "a";` | Pass | 6,278 | 1,998 |
| Recursive union version | TS2589 | 6,339 | 2,558 |
| Accumulator version plus the shown checks | Pass | 6,349 | 2,686 |

The library contributes work even to the baseline. The passing version's counter is greater than the failing version's: the latter stopped before completing its task. That comparison proves successful checking of this input, not a speedup. Compiler releases, libraries and even extra probes can change counters. Repeat measurements on your actual workload before drawing a performance conclusion.

### 2) **TS2589 diagnosis and bounded transforms**

TS2589 says the checker reached an internal safeguard while expanding a type. A finite input can trigger it; it does not prove an infinite runtime loop. Different expansion shapes encounter different limits. The [4.5 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-5.html) explain why some conditional types benefit from tail-recursion elimination. Avoid turning a historical implementation threshold into a universal supported depth contract.

There is no supported `instantiationDepth` option in the checked 7.0.2 compiler: attempting it produces TS5023. The [request for configurable depth limits](https://github.com/microsoft/TypeScript/issues/46180) is a declined suggestion, not documentation of an available flag.

Choose a remedy that preserves the intended API. An accumulator can remove intermediate type construction, as above. A recursion cap can deliberately stop transforming deeper values. A carve-out can preserve a type such as `Date` that should be treated as a complete value rather than a bag of recursively optional methods. A narrower input contract can avoid transforming unrelated parts of a model. None is a universal first step; first reproduce the failing input and define the required result.

Save this separate example as `cap.ts` in the parent directory:

```typescript
export {};
type CappedPartial<T, Seen extends 0[] = []> = Seen["length"] extends 2 ? T
  : T extends Date | ((...args: never[]) => unknown) ? T
  : T extends object ? { [K in keyof T]?: CappedPartial<T[K], [...Seen, 0]> }
  : T;
interface Org { name: string; created: Date; child?: Org; }
const patch: CappedPartial<Org> = {
  created: new Date("2026-01-01T00:00:00Z"),
  child: { child: { name: "required at depth two", created: new Date(0) } }
};
console.log(patch.created?.toISOString());
console.log(patch.child?.child?.name);
```

Run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir dist cap.ts`, then `node dist/cap.js`. It prints `2026-01-01T00:00:00.000Z` and `required at depth two`. At the cap, the transform returns `T`, so deeper objects keep their original required members. Remove the deepest `name` property and recheck: TS2741 reports that it is missing. This is a contract change that callers need to understand, not a performance switch with identical semantics.

The cap limits this utility's own descent. It does not bound all other type computations, eliminate wide unions, or guarantee that every input avoids TS2589. The [deep-transform owner](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) owns the fuller array/collection/leaf design decisions.

### 3) **Budgeting per boundary**

Once checking passes, save diagnostics from the same package and compiler configuration. Establish a threshold from representative measurements, and keep correctness checks as a separate prerequisite. A counter ceiling can reveal growth early, but it cannot explain which file caused that growth. Investigate meaningful changes with the measurement tools before redesigning an API.

For this small fixture only, save `budget.json` as:

```json
{ "maxInstantiations": 3000 }
```

Save `budget.cjs`:

```javascript
const fs = require("node:fs");
const report = fs.readFileSync(process.argv[2], "utf8");
const budget = JSON.parse(fs.readFileSync(process.argv[3], "utf8"));
const match = /^Instantiations:\s+(\d+)$/m.exec(report);
if (!match || !Number.isInteger(budget.maxInstantiations)) {
  throw new Error("missing counter or invalid budget");
}
const count = Number(match[1]);
if (count > budget.maxInstantiations) {
  console.error(`Instantiations ${count} exceeds ${budget.maxInstantiations}`);
  process.exit(1);
}
console.log(`Instantiations ${count} within ${budget.maxInstantiations}`);
```

With Node 20.20.2, run:

```sh
tsc -p after/tsconfig.json --extendedDiagnostics > after/diagnostics.txt && node budget.cjs after/diagnostics.txt budget.json
```

The observed message is `Instantiations 2686 within 3000`. Lower the threshold to 2000 and rerun; the budget script exits unsuccessfully with `Instantiations 2686 exceeds 2000`. Missing counters also fail instead of silently becoming zero. The `&&` matters: a failed compiler run must not be accepted merely because it reports a small counter. These numbers are exercise thresholds, not recommended ceilings for real packages.

Pin the compiler and record included libraries, files and checking options beside the baseline. Treat a compiler upgrade as a new measurement context. For multiple packages, gather each package's results separately; shared dependencies and different included declarations can prevent direct comparisons. Explain justified growth rather than increasing every ceiling until CI passes.

### 4) **Common confusion**

A lower counter does not necessarily mean a faster or better implementation. The failing fixture reports less work precisely because checking failed. Counts also do not map one-to-one to recursive calls or keys in your source. Use them as investigation signals with correctness, timings and reproducible inputs.

A recursion cap changes what a transform promises. The deepest required `name` in `cap.ts` is the consequence of stopping with identity. Raising a local budget ceiling does not raise a compiler safeguard.

### 5) **Performance note**

All these type utilities erase, so their conditional-type work occurs in the checker. The cap example's JavaScript only constructs the shown values and prints them. A shallow cap can still traverse many properties or distribute over many members; its work is not constant merely because depth is bounded. The tiny observed check times varied across runs and do not support a ranking. For an operational performance claim, measure repeated runs with comparable inputs and disclose cache/toolchain conditions.

### 6) **Mentor note**

Give learners the two recursion versions and ask why the higher-counter version is the successful one. They should distinguish completed checking from early failure and explain the accumulator's removal of a pending operation. Then remove the deepest `name` from the cap example. A sound review explains the changed contract before recommending the cap. Finally, lower the exercise budget and ask which evidence would justify restoring it. A threshold change needs a reason and a baseline, not an invented compiler flag.
