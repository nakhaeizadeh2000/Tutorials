## 6.1. Common interview QA — performance project references and scaling

These questions assess explanations and diagnosis. The linked lessons contain complete verified projects; the answers below do not claim a new benchmark or executable test.

### 1) **How would you investigate a slow TypeScript check?**

First identify the executable/version, intended program, successful result and operation being measured. Inspect effective configuration and actual membership, then use aggregate diagnostics to characterize the work. Collect a supported trace or profile to investigate a specific hypothesis. Compare elapsed runs separately from instrumented runs, with relevant inputs and cache conditions recorded. A native pprof artifact and a legacy V8 profile are different formats; the command must match the compiler. The [measurement exercise](<../1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) establishes those actual native artifacts and limits.

A good optimization answer preserves the accepted and rejected contracts before comparing costs. Naming a type, narrowing a transform's purpose or redesigning recursion can be candidates, but none guarantees a fixed speedup. Source syntax does not supply an instantiation formula.

**Follow-up:** a failing TS2589 form reports fewer instantiations than the passing replacement. Which is better? The count alone cannot decide. The erroring form did not complete the intended check; the replacement must first pass semantic probes. If it introduces a depth cap, explain the changed boundary contract. The [recursion exercise](<../1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) demonstrates these distinctions, including a probe that rejects an accidental never result.

### 2) **When are project references useful?**

They express dependencies between configured projects and support ordered builds with declaration boundaries. Different outputs, host settings, package ownership, frequently co-edited code and measured program cost can justify a split. Team size and file count do not establish a universal threshold. Shared dependencies can still incur repeated work across consumers, and extra boundaries add configuration and artifact management.

Explain the actual graph and execution path. Composite projects have constraints; disabling declarations does not simply make a referencing consumer transparently fall back to arbitrary source. A reference cycle produces a graph diagnostic, while an import cycle can pass checking and fail during module initialization. Build references also do not constitute an import allow-list.

**Follow-up:** a provider's function body changes but its emitted declaration stays identical. Can consumer tests be skipped? The [three-project exercise](<../2. Project References and Builds/2.1. Composite partitioning and references architecture.md>) changes both consumer outputs behind that stable declaration. Behavior can change independently of the static API, so relevant behavior tests still matter. Selection must use a truthful graph and appropriate task contracts, not declaration bytes alone.

### 3) **What does a green incremental build establish?**

It establishes the result of that invocation over its selected programs and retained state. Also check that the consumer's required artifacts exist and execute the intended behavior. A green build is not a universal certificate for every source, previous output or runtime path.

The [cache exercise](<../2. Project References and Builds/2.2. Incremental builds and tsbuildinfo discipline.md>) removes emitted app JavaScript while retaining build state: the observed ordinary build exits 0, then startup fails. Force regenerates the known output, but an obsolete sentinel survives force and known-output clean. An explicitly owned fresh-output rebuild removes it. These outcomes separate forced work from complete cleanup.

**Follow-up:** incremental is green and a fresh workspace is red. Is cache corruption proved? No. Compare compiler, sources, dependencies, configuration, environment, task selection and artifact restoration first. The difference is a diagnostic clue. Nor does a nightly full command prove all behavior is tested: the [affected collector](<../2. Project References and Builds/2.3. Solution builds and CI orchestration with tsc b.md>) shows missing-edge selection failure, while full selection still depends on its registered assertions.

### 4) **How would you diagnose a slow editor operation?**

Name the operation and identify the actual provider, editor integration, open document and project. Compare the input with a batch check without assuming they represent the same state. The [service debugging exercise](<../../../16 Tooling Language Server and Ecosystem/sections/3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) obtains TS2322 for an unsaved changed buffer while the unchanged disk file compiles successfully. Both observations are consistent.

Inspect roots and imported dependencies when membership is a plausible cause. A configured project is not necessarily a separate server process. Multi-root workspaces and multiple tsconfigs alone do not establish independent restarts or fault isolation. Treat project-reference redirect options as provider-specific experiments; available declaration maps do not prove navigation succeeds in the client.

**Follow-up:** generated is excluded, but importing a generated file reports its error. Is exclusion broken? No. Root discovery and dependency closure are different. The [membership fixture](<../3. Scaling Patterns/3.3. Editor performance at scale budgets and tuning.md>) checks an imported excluded file while leaving an unrelated invalid excluded file unchecked. Measure the same editor request after a justified change; a lower file count or restart alone is not a latency result or cause diagnosis.

### 5) **What belongs in a declarations-only package?**

Static contracts such as interfaces and type aliases can be published without JavaScript implementations. Constructors, validators and runtime functions cannot be supplied by their declarations alone. Extract contracts when independent ownership/release coordination and consumer needs justify the overhead; a fixed consumer count is insufficient. A type-only import can also consume declarations from a package that ships JavaScript, so extraction is not required merely to erase one import.

The [installed-package exercise](<../3. Scaling Patterns/3.2. Type-only boundaries import type bulk and erasable scale.md>) packs a package with only a types export condition. Its whole-statement type import disappears, and the emitted consumer runs using its own constructed object. Dedicated type-test tools can add useful contract checks, but installed package resolution and the actual consumer graph also need evidence.

**Follow-up:** replacing that import with inline type-only specifiers still checks. Will execution succeed? Under the tested verbatim syntax it leaves an empty import. Node then tries runtime package resolution and fails because no runtime export is offered. Explain the emitted edge rather than treating every type-marked specifier as whole-statement erasure. During bulk conversions, retain necessary initialization through an explicit import from a real implementation module.

### 6) **Common confusion**

A familiar command or threshold is not a sufficient explanation. Answers should identify the contract, observation and limit: counters concern completed compiler work, references concern configured build dependencies, entry tests concern particular artifacts, and language-service results concern actual documents and requests.

A bounded counterexample strengthens an answer. For example, named re-exports can still form a runtime initialization cycle, and a static import rule can omit dynamic-import coverage. Mentioning these limits does not make checking or curation useless; it identifies which additional evidence is needed.

### 7) **Performance note**

These are reasoning questions, not performance measurements. No fixed worker scaling, partition multiplier, instrumentation overhead, file-count latency curve or cache payoff was established here. Use representative successful workloads to compare an improvement, and explain any changed contracts or coverage. Do not rank a candidate's experience by whether they recite one prescribed knob order.

### 8) **Mentor note**

Give one follow-up at a time and ask the learner to predict the observed result before revealing it. A sound answer traces program membership, emitted imports, actual artifact paths or dependency/task graphs. If an answer is too broad, ask for the observation that would falsify it.

Assess the reasoning needed for the role rather than command memorization. An honest “I would compare these inputs before diagnosing a cache bug” is stronger than a confident unsupported cause. Ask the learner to explain a repair and its remaining limits after diagnosing the failure.
