## 6.1. Common interview QA — performance project references and scaling

### 1) **How do you find what's slow in `tsc` — and what do you do about it?**

**Definition** — the workflow (1.1): diagnostics (`--extendedDiagnostics` — `Instantiations`/`Types`/`Check time` counters) → traces (`--generateTrace` — widest bars first) → fixes (carve-outs per 09/3.1, caps per 1.2, splits per 1.3, budgets per 1.2 part 3) → verification (re-trace, deltas evidencing). Numbers routing, folklore ignored.

**What problem it solves / history** — superstition-optimization (unmeasured refactors churning code for ±2%): the interview probes measurement discipline (counters → bars → fixes → proof — science, not folklore).

**Modern guidance** — answer shape: name the two commands, state the reading order (counters first, bars second), give one fix per hot-spot class (mapped → carve; deep → cap; union → split; growth → budget), close with verification (re-trace deltas). As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS).

**Runnable example** — the workflow as code (good vs bad, `tsc --strict`):

```typescript
// good — counted fix (arithmetic stated — numbers routing effort to the measured 5%)
export {}; // module marker (consistent module scope across fences)
type Pick2<T, K extends keyof T> = { [P in K]: T[P] }; // K-scoped (instantiations = |K| — counted fix, budgeted breadth)
interface Big { a: string; b: number; c: boolean; d: string }
type Small = Pick2<Big, "a">; // 1 instantiation (scoped — the fix shape: breadth declared, counters flat)
declare const s: Small;
console.log(s.a); // a — measured fixes (arithmetic stated — verification via diagnostics, not hope)
// bad — "split files for speed" (unmeasured folklore — files innocent, instantiations guilty)
// fix — counters → bars → fixes → proof (workflow, not vibes — science as the senior signal)
```

**Common confusion** — "experience replaces measurement" — experience *hypothesizes* (fast guesses); measurement *verdicts* (counters confirming — seniors measuring too, faster). "one tool suffices" — diagnostics quantify (what kind), traces localize (where) — complementary per 1.1.

**Performance note** — workflow overhead diagnostics-negligible + traces-targeted (cost proportional to insight — always worth it past slow-CI pain).

**Mentor note** — hiring signal: candidates opening with commands (tools first — practitioners); candidates opening with opinions (folklore first — skeptics until numbers appear).

### 2) **When do project references pay off — and what breaks without them?**

**Definition** — the threshold answer (2.1): references paying at 3+ engineers/2k+ files (whole-program costs biting — affected-subgraph checks via declarations); without them: edit latency = repo size (rechecks redundant), CI verifying unchanged code (velocity throttled), no build ordering (hand-maintained sequences rotting). Hygiene triple: DAG + composite + maps (order, speed, navigation).

**What problem it solves / history** — premature partitioning (40 micro-projects day one — overhead dwarfing savings) vs monolithic loyalty (10k files unpartitioned — minutes per save): the interview probes threshold judgment (measured splits, not vibes).

**Modern guidance** — answer shape: state thresholds (3 engineers/2k files), describe DAG direction (change-rate — stable leaves, churning apps), name the hygiene triple (DAG + composite + declarationMap), note coarse-first (3–7 projects — splits measured per 1.1).

**Runnable example** — threshold thinking (good vs bad, `tsc --strict`):

```typescript
// good — coarse partitions (3–7 projects — splits measured, overhead proportional)
export {}; // module marker (consistent module scope across fences)
export interface LeafContract { id: string } // leaf (stable — emitted once, downstream reading declarations)
export function useLeaf(c: LeafContract): string { return c.id; } // app composing (churning — subgraph rechecks only)
console.log(useLeaf({ id: "x" })); // x — coarse layering (thresholds met — partitioning paying, overhead proportional)
// bad — "references everywhere day one" (overhead without measurement — orchestration taxing trivial repos)
// fix — thresholds (3 engineers/2k files — splits scheduled, not defaulted)
```

**Common confusion** — "references are paperwork" — references are *cache boundaries* (invalidation scoped — structure, not paperwork per 4.1 part 2). "monorepos require references" — small monorepos compiling whole-program fine (thresholds deciding — requirements earned by scale).

**Performance note** — partitioned rechecks seconds (subgraphs); monolithic minutes (whole programs — threshold crossed where delta exceeds overhead).

**Mentor note** — follow-up: "draw your last reference graph" (DAG drawn — direction arrows mandatory; cycles discussed as prevented, not hypothetical).

### 3) **Incremental vs clean builds — when do you trust each, and how do you verify?**

**Definition** — the duality answer (2.2): incremental trusted for *speed* (affected subgraphs — PRs fast, watch instant); clean trusted for *truth* (full verification — nightly `--force` schedules); verification = divergence alerting (incremental-green + clean-red = poisoning caught — 2.2 part 3 metric). Hash keys + gitignore making caches honest (shape changes busting, never committed).

**What problem it solves / history** — speed-vs-truth false choice (incremental-only poisoning per 17/5.1; clean-only throttling): the interview probes duality thinking (both halves tooled — fast PRs + true repos, structurally).

**Modern guidance** — answer shape: modes per workflow (watch local, `-b` CI, incremental one-shots — 2.2 part 2), honesty triad (hash keys + gitignore + schedules — 2.2 part 3), triage command (`--force` distinguishing cache bugs from real ones in seconds).

**Runnable example** — duality tooled (good vs bad, `tsc --strict`):

```typescript
// good — cache-bug triage (force distinguishing — seconds, not sprints)
export {}; // module marker (consistent module scope across fences)
export function suspect(): string { return "verified-clean"; } // phantom-error suspect (force-run deciding — cache bug or real, one command)
console.log(suspect()); // verified-clean — triage instant (--force distinguishing — folklore debugging replaced by procedure)
// bad — "incremental is unreliable, disable it" (full rechecks per save — velocity throttled over diagnosable cache bugs)
// fix — duality (fast + true — incremental speed, scheduled truth, force triage)
```

**Common confusion** — "clean builds are the only truth" — clean builds are *scheduled* truth (nightly — PR truth from affected verification per 2.3 part 3; per-PR exhaustiveness throttling velocity). "caches always poison" — keyed caches + schedules bounding windows ≤24h (poisoning managed, not feared — 2.2 triad).

**Performance note** — incremental seconds (PRs); clean minutes nightly (amortized insurance — 2.2 arithmetic).

**Mentor note** — on-call answer: "incremental green + clean red means poisoning" (triage instant — cache bugs distinguished procedurally).

### 4) **How do you keep editors fast on huge repos — in what order?**

**Definition** — the triage order (3.3 + 16/3.1): (1) scope programs (`include` sources-only, exclude outputs — bloat #1); (2) trim globals (`types` allowlist, `maxNodeModuleJsDepth` — bloat #2–3); (3) triage redirects (`disableSourceOfProjectReferenceRedirect` for huge-stable — programs slashed); (4) partition servers (per-reference tsservers — faults isolated); (5) budget programs (ceilings in CI — growth loud). Order matters: scoping before tuning (bloat removed before knobs turned).

**What problem it solves / history** — hardware-first responses (bigger laptops for 50k-file programs — bloat unaddressed, latency returning with growth): ordered triage fixing causes (scoping → trimming → redirecting → partitioning → budgeting — each step measured per 16/3.1).

**Modern guidance** — answer shape: recite the five steps in order, justify ordering (bloat removal before knob tuning — causes before symptoms), cite measurement (program sizes before/after per step — 16/3.1 evidence).

**Runnable example** — ordered triage (good vs bad, `tsc --strict`):

```jsonc
// good — scoping first (bloat removed — knobs tuned after, never before)
// tsconfig.app.json (labeled config doc): { "include": ["src"], "exclude": ["dist", "build"],
//   "compilerOptions": { "maxNodeModuleJsDepth": 0, "types": ["node"] } }
// (steps 1–2 applied — programs scoped to sources before any redirect/partition tuning)
```

```typescript
// good — scoped program editing (thousands of files — completions instant after scoping)
export {}; // module marker (consistent module scope across fences)
export function scopedEdit(s: string): string { return s.trim(); } // sourced code (scoped program — responsiveness restored by configuration, not hardware)
console.log(scopedEdit("  y ")); // y — ordered triage (scoping first — causes fixed, symptoms gone)
// bad — "buy bigger laptops" (hardware for bloat — latency returning with growth, causes unaddressed)
// fix — five-step order (scope → trim → redirect → partition → budget — causes before symptoms, measured throughout)
```

**Common confusion** — "restart fixes slowness" — restarts clear *symptoms* (warmth lost — scoping fixing causes; runbooks ordering reload → restart → trace per 3.3 part 3). "one knob suffices" — knobs tune *scoped* programs (unscoped programs overwhelming every knob — order structural, not preferential).

**Performance note** — scoping superlinear (50k→5k files — seconds→milliseconds); knobs linear-marginal (redirects/partitioning — meaningful only post-scoping).

**Mentor note** — triage grading: ordered five (staff — causes sequenced); knob-first (junior — symptoms tuned, bloat kept).

### 5) **What belongs in a type-only package — and why separate it?**

**Definition** — the extraction answer (3.2 part 3): contents (domain contracts, branded IDs, API shapes, error taxonomies — zero runtime: interfaces + literal unions + brands); threshold (2+ consumers — duplication vs package overhead); versioning (semver — breaking moves major per 17/3.2 baselines); testing (`tsd` surface probes — declarations the product).

**What problem it solves / history** — runtime-coupled contracts (frontends importing server bundles for interfaces — versioning locked to deploys): separation decoupling versioning (contracts releasing independently — consumers upgrading types without redeploying runtimes).

**Modern guidance** — answer shape: list contents (contracts/IDs/shapes/taxonomies), state threshold (2 consumers), describe versioning (semver + baselines), name testing (`tsd` probes — 17/3.2).

**Runnable example** — zero-runtime extraction (good vs bad, `tsc --strict`):

```typescript
// good — contract package shape (zero runtime — versioned independently, consumed widely)
export {}; // module marker (consistent module scope across fences)
export interface Event { kind: string; at: string } // contract (shared — frontend + backend + workers, one versioned truth)
export type EventKind = "click" | "view"; // taxonomy (literal union — 11/2.3 decision rule at package scale)
declare const e: Event;
console.log(e.kind); // kind — extraction paying (consumers upgrading types without runtime deploys)
// bad — "types ride with implementations" (versioning locked — contract moves shipping with runtime deploys, consumers forced along)
// fix — type-only past 2 consumers (thresholds — decoupling versioning where sharing demands it)
```

**Common confusion** — "packages for three interfaces overkill" — overkill below 2 consumers (duplication cheaper); necessary above (drift costing more — threshold economics, not absolutes). "types need no semver" — pinned consumers needing signals (breaking moves major — baselines evidencing per 17/3.2).

**Performance note** — zero runtime (erased — 01/2.1); check-time shared like all imports (budgeted per 1.2 — partitions equal under ceilings).

**Mentor note** — extraction bar: consumers + versioning + probes in one PR (threshold met, semver attached, surfaces tested — complete extraction, not a files move).
