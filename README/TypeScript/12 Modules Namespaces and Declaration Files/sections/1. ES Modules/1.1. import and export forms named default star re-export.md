## 1.1. `import` and `export` forms — named, default, star, re-export

### 1) **Named vs default vs namespace imports** (explicitness, convention, weight)

**Definition** — named imports (`import { read } from "./fsx"`) bind specific exports by name (refactor-safe, tree-shakeable); default imports (`import cfg from "./config"`) bind one conventional export (terse, single-per-module); namespace imports (`import * as U from "./utils"`) bind the whole module object (convenient grouping, heaviest bundle/reference weight). All three read the same module record — the form documents *how much* of it the importer needs.

**What problem it solves / history** — default-heavy codebases (`export default` everywhere) lost rename-refactoring (defaults import under any local name — `import cfg` vs `import config` for the same export drifted per file) and grep-ability (finding all users of an export meant searching every possible local alias). Named-by-default convention restored both: one export name everywhere, renameable once with the IDE, searchable by construction.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to named exports/imports (explicit, refactorable, tree-shaken per symbol); reserve default exports for single-purpose modules with one obvious consumer shape (Next.js pages, plugin entries, config files); use `import *` for utility namespaces with many members consumed together — never as a laziness shortcut for one import.

**Runnable example** — forms compared across two files (`tsc --strict --module nodenext`; multi-file fences verified as a set):

```typescript
// file: shapes.ts
export interface Circle { kind: "circle"; r: number }
export function area(c: Circle): number { return Math.PI * c.r ** 2; }
export default function describe(c: Circle): string { return `circle r=${c.r}`; }
// file: main.ts
import { area, type Circle } from "./shapes.js";
import describe from "./shapes.js";
import * as S from "./shapes.js";
const c: Circle = { kind: "circle", r: 2 };
console.log(area(c).toFixed(2), describe(c), S.area(c).toFixed(2)); // 12.57 circle r=2 12.57
```

```typescript
// file: config.ts
export const port = 3000;
// file: app.ts
import { port } from "./config.js"; // named: one name everywhere (rename-safe)
// import cfgPort from "./config.js"; // error TS1192: no default export (caught — defaults must exist)
// fix — named imports for multi-export modules; default only where the module declares one
console.log(port); // 3000
```

```typescript
// file: utils.ts
export function a(): string { return "a"; }
export function b(): string { return "b"; }
// file: use.ts
import * as U from "./utils.js"; // namespace: many members, one prefix (grouped use)
console.log(U.a() + U.b()); // ab — U carries the whole record (weight: entire module referenced)
```

**Common confusion** — "`import *` imports the types too" — imports the module *record* (values + types as members: `S.Circle` as a type works) — but tree-shakers keep the whole record reachable (weight), unlike named imports (per-symbol shaking). "default exports rename freely, so they're flexible" — rename-freedom *is* the refactoring hazard (same export, N local names across files — grep dies). "named and default can share a name" — `export default function Foo` + `export { Foo }` collide confusingly — one form per module's primary export, documented in the contributing guide.

**Performance note** — named imports tree-shake per symbol (unused exports dropped by bundlers); namespace imports pin the whole record (bundlers keep everything reachable through `U`); defaults shake as one unit. Form choice has measurable bundle effects past library scale — default-named, shake-per-symbol, namespace only for genuinely grouped consumption.

**Mentor note** — rename one default export and count the files that *don't* update (every importer keeps its stale alias — the refactoring hazard made visible). Exercise: convert one default-heavy folder to named exports and delete the alias drift — grep-ability restored in one PR. Review gate: new `export default` requires a comment naming why named doesn't fit.

### 2) **Re-export barrels** (public-surface curation vs blast radius)

**Definition** — barrels (`index.ts` with `export { X } from "./x"`, `export * from "./y"`) curate a package's public surface behind one import path (`import { X } from "@org/lib"` instead of deep paths). `export *` re-exports everything (convenient, conflict-prone); explicit `export { X }` lists curate (verbose, conflict-proof, self-documenting).

**What problem it solves / history** — deep imports (`@org/lib/dist/x/y/z`) coupled consumers to internal layouts (every refactor broke import paths) and scattered the public contract (no single file stating "this is the API"). Barrels centralized the surface: internals move freely behind a stable index — at the price of barrel *cycles* (`a/index` ↔ `b/index` re-export ping-pong initializing to `undefined` — see 5.1 promise 1) and widened initial evaluation.

**Modern guidance** — as of TypeScript 5.9 era, barrel per package (explicit `export { … }` lists — never `export *` across internal boundaries where name collisions hide); no barrels *inside* packages for intra-package traffic (relative imports stay direct — barrels compose the public surface, not the internal graph); document the barrel as the API contract (reviewed like any public interface).

**Runnable example** — curated surface, direct internals (multi-file set):

```typescript
// file: circle.ts
export interface Circle { r: number }
// file: area.ts
import type { Circle } from "./circle.js";
export function area(c: Circle): number { return Math.PI * c.r ** 2; }
// file: index.ts
export type { Circle } from "./circle.js";
export { area } from "./area.js"; // explicit list: public surface stated once
// file: app.ts
import { area, type Circle } from "./index.js"; // stable path (internals free to move)
const c: Circle = { r: 1 };
console.log(area(c).toFixed(2)); // 3.14 — barrel resolved, surface stable
```

```typescript
// file: geo.ts
export interface Box { w: number }
// file: inner.ts
import type { Box } from "./geo.js"; // direct relative import (no barrel for internals)
export function wide(b: Box): boolean { return b.w > 10; }
const ok: boolean = wide({ w: 12 });
console.log(ok); // true — internal traffic bypasses the barrel (no cycle surface)
// bad — ./inner importing from ./index (which re-exports ./inner): cycle surface grows per file
```

```typescript
// file: api.ts
export function v1(): string { return "v1"; }
export function v2(): string { return "v2"; }
// file: pub.ts
export { v1, v2 } from "./api.js"; // explicit: collisions impossible, surface reviewable
// file: use2.ts
import { v1 } from "./pub.js";
console.log(v1()); // v1 — curated path (compare export *-from-api: silent on collisions)
// bad — export * from "./api.js" + export * from "./legacy.js" (both export `v1`): last wins silently
```

**Common confusion** — "barrels are free organization" — barrels add evaluation edges (every barrel hop executes an intermediate module) and cycle surface (each `export *` widens the initialization graph) — free for small packages, load-order-relevant past dozens of modules. "`export *` and explicit lists are equivalent" — `export *` skips `default` exports (silent omission!) and resolves name collisions by shadowing order (silent winner) — explicit lists error on neither because the author states each name. "deep imports are always bad" — deep imports *into other packages'* internals are bad (coupling); relative imports *within* a package are the healthy default (no cycle surface added).

**Performance note** — barrels add module-record hops per re-export (evaluation order + memory per intermediate record — trivial singly, measurable across hundreds of barrel-chained modules in startup profiles); `export *` defeats per-symbol tree-shaking at the barrel boundary (bundlers keep everything reachable). Explicit lists + direct internals optimize both axes simultaneously.

**Mentor note** — draw the import graph with and without barrels (star topology through index vs mesh of relatives) and ask "where can a cycle hide?" (barrel hops — each re-export is an edge reviewers stop seeing). Exercise: delete one intra-package barrel hop (import direct) and show the graph edge vanishing — cycle surface made visible, then reduced.

### 3) **Export forms and live bindings** (read-only views, not copies)

**Definition** — `export const x = 1` / `export function f` / `export { x }` / `export default …` all create *live bindings*: importers read the exporter's *current* value (updated `let` exports re-read fresh), but cannot *write* through the import (`import { x }; x = 2` errors — imports are read-only views). Reassignment happens only in the defining module; importers observe.

**What problem it solves / history** — CommonJS copies (`const { x } = require(…)` snapshots the value at require time — later exporter updates invisible) made live configuration (feature flags flipped at runtime, registries populated post-import) silently stale — importers read frozen snapshots while exporters moved on. ESM live bindings keep importers current by construction: `config.flag` flipped in the definer reads flipped everywhere, with no re-import protocol.

**Modern guidance** — as of TypeScript 5.9 era, rely on live bindings for intentionally-mutable shared state (flags, registries — updated in the definer, observed everywhere); prefer function-call reads (`getFlag()`) over mutable-export reads where update timing matters (explicit call beats implicit freshness); never assign through imports (read-only views — the error is the feature, directing writes to the owner).

**Runnable example** — liveness observed across the import (multi-file set):

```typescript
// file: flags.ts
export let debug = false;
export function enable(): void { debug = true; } // writes happen HERE (owner)
// file: app2.ts
import { debug, enable } from "./flags.js";
console.log(debug); // false — current value at read time
enable();
console.log(debug); // true — live binding re-read (no re-import needed)
// debug = false; // error TS2540: cannot assign to import (read-only view — writes belong to flags.ts)
```

```typescript
// file: reg.ts
export const registry = new Map<string, number>(); // mutable OBJECT, stable binding
// file: use3.ts
import { registry } from "./reg.js";
registry.set("a", 1); // legal — mutating the object (binding itself never reassigned)
console.log(registry.size); // 1 — live object shared (contrast: reassigning `registry = …` here errors)
// bad — expecting snapshot semantics (CJS habit): importers observing STALE values never happens in ESM
```

```typescript
// file: counter.ts
export let n = 0;
export function bump(): number { return ++n; }
// file: watch.ts
import { n, bump } from "./counter.js";
console.log(n, bump(), n); // 0 1 1 — reads track the owner's writes (liveness demonstrated)
// bad — import { n }; n = 5 (TS2540: read-only view — the error directing writes to counter.ts)
```

**Common confusion** — "live bindings mean mutable imports" — bindings are read-only *views* over live *values*: observe anything, assign nothing — mutation happens through owned functions or object methods, never through the import binding. "live bindings cost per-read overhead" — direct memory reads (same as local `let` after bundling/linking) — liveness is a linking semantic, not a getter call. "CJS destructured requires behave the same" — `require` snapshots (copy at call time); ESM binds (view for all time) — migrating CJS→ESM flips staleness assumptions silently (audit flag/registry reads during migration).

**Performance note** — live bindings compile to direct references (bundlers resolve to the same variable — zero indirection); namespace-object access (`ns.x`) adds one property hop per read (negligible except ultra-hot loops — destructure to locals there).

**Mentor note** — flip the flag and re-read without re-importing — liveness demonstrated beats liveness described. Exercise: find one CJS-migrated module assuming snapshot semantics (stale-flag reads) and convert to live-binding reads — the staleness class deleted by migration done right. Review gate: assignments to imports (TS2540) are never silenced with casts — reroute writes to owner functions.
