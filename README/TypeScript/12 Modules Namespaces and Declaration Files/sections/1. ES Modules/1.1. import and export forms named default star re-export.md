## 1.1. `import` and `export` forms — named, default, star, re-export

### 1) **Named, default and namespace views of a module**

An export makes a binding available to another module. A named import selects an export by its public name; a default import selects the export named `default`; a namespace import provides property access to the module's runtime exports. These are ways to address a module's API, not instructions to copy its source into the importing file.

Use TypeScript **7.0.2** and Node **20.20.2** for the emitted ESM examples in parts 1–3, verified 2026-10-15. Each fence is a separate project in an otherwise empty directory without a tsconfig. Split it at the `// file:` markers. The `.mts` extension makes the sources ES modules. Source specifiers name the emitted `.mjs` files: the checker resolves them to the corresponding `.mts` sources; Node runs the output. Native execution of these source graphs is a different contract, covered in [source versus emitted imports](<./1.2. import type and verbatimModuleSyntax erasable imports.md>).

```typescript
// file: shapes.mts
export interface Circle { radius: number }
export function area(circle: Circle): number {
  return Math.PI * circle.radius ** 2;
}
export default function describe(circle: Circle): string {
  return `circle r=${circle.radius}`;
}
// file: dual.mts
export default function Foo(): string { return "value"; }
export { Foo };
// file: forms.mts
import describe, { area as circleArea, type Circle } from "./shapes.mjs";
import * as Shapes from "./shapes.mjs";
import Default, { Foo } from "./dual.mjs";
const circle: Circle = { radius: 2 };
console.log(circleArea(circle).toFixed(2), describe(circle));
console.log(Shapes.area === circleArea, Shapes.default === describe);
console.log(Default === Foo, Foo());
```

Build and execute:

```bash
tsc --strict --target es2022 --module nodenext --lib es2022,dom --noEmitOnError --outDir dist forms.mts
node dist/forms.mjs
```

Both commands exit 0. Output is `12.57 circle r=2`, `true true`, then `true value`. `area as circleArea` changes the local name, so named imports also allow aliases. The namespace exposes the default as `Shapes.default`. Circle is a checker type and is absent from the runtime namespace. The final line proves that a function may legally be exported both as default and under its name; redundant API names are a design choice, not a collision.

Named exports make a multi-operation API explicit. A default export can suit a single primary operation or a framework's entry-point contract. A namespace prefix can clarify grouped operations. Choose a project convention for consistency, but do not promise that a spelling alone guarantees editor rename behavior or smaller bundles. An editor can track default imports, and a bundler may analyze static namespace accesses. Check the actual tool and resulting artifact when that matters.

### 2) **Re-export barrels curate public names**

A barrel is a module that re-exports other modules' bindings. An explicit list documents the public surface; `export *` forwards named exports except `default`. A re-export does not introduce a local variable in the barrel. Import a value separately if the barrel's own code needs to call it.

Here is an intentional failure, in a fresh directory:

```typescript
// file: left.mts
export const duplicate = "left";
export default function primary(): string { return "primary"; }
// file: right.mts
export const duplicate = "right";
// file: barrel.mts
export * from "./left.mjs";
export * from "./right.mjs";
// file: consumer.mts
import { duplicate } from "./barrel.mjs";
console.log(duplicate);
```

Run the same build command as above with `consumer.mts` as the entry. It fails with TS2308, exit 1 with `--noEmitOnError`, and produces no output graph. For this isolated experiment only, replace that flag with `--noEmitOnError false`; the compiler exits 2 while emitting files. Running `node dist/consumer.mjs` then exits 1 with a conflicting-star-export SyntaxError. This is an observed failure from deliberately unsuccessful compilation, not a deployable build.

The two stars lead to distinct bindings with the same public name. Neither wins by appearing last. The specification's [ResolveExport algorithm](https://tc39.es/ecma262/2026/multipage/ecmascript-language-scripts-and-modules.html#sec-source-text-module-records-resolveexport) detects this ambiguity. Multiple routes to the *same* binding are a different case.

Repair the graph by replacing the entire contents of barrel.mts with the following, then rebuild with `--noEmitOnError` and run the consumer again:

```typescript
export { duplicate } from "./left.mjs";
export { duplicate as legacyDuplicate } from "./right.mjs";
export { default as primary } from "./left.mjs";
```

The build and execution exit 0; the consumer prints `left`. Changing its import to `legacyDuplicate` prints `right`. `primary` is forwarded explicitly because a star would omit the original default. An alternative API may retain stars and explicitly select the intended duplicate, but spelling out the public names is often easier to review.

A public barrel can let internal files move behind a stable consumer path. Internal code can import the owning file directly to avoid routing through an unnecessarily broad public graph. Neither pattern guarantees freedom from cycles. Ordinary re-export dependencies participate in module evaluation, even when the barrel has no meaningful body. Trace actual edges and initialization reads when diagnosing a cycle; do not assume every cycle fails or every failure is an `undefined` value. The [module pitfalls owner](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by module misunderstandings.md>) is the route for that diagnosis.

### 3) **A live exported binding differs from a captured expression value**

An imported binding is read-only in the importing module. It can still expose changes made by the exporting module. The important question is *which binding was exported*. A default expression such as `export default count` evaluates count and initializes a separate default binding. Later reassignment of the local count does not replace that captured value. `export { count as default }` instead exports the local binding under the default name.

Run this fresh project:

```typescript
// file: captured.mts
let count = 1;
export { count };
export default count;
export function bump(): void { count++; }
export const registry = new Map<string, number>();
// file: live.mts
let count = 1;
export { count, count as default };
export function bump(): void { count++; }
// file: watch.mts
import captured, { count, bump, registry } from "./captured.mjs";
import liveDefault, { count as liveCount, bump as bumpLive } from "./live.mjs";
import * as Captured from "./captured.mjs";
const { count: copiedCount } = Captured;
console.log(count, captured, liveCount, liveDefault);
bump();
bumpLive();
console.log(count, captured, liveCount, liveDefault, copiedCount);
registry.set("jobs", 2);
console.log(registry.get("jobs"));
// count = 9; // Activate separately: TS2632, cannot assign to an import.
```

Build with the part 1 command, substituting `watch.mts`, then run `node dist/watch.mjs`. Both exit 0; output is `1 1 1 1`, `2 1 2 2 1`, then `2`. The named count and binding-alias default observe the increments; the expression default and destructured local retain their initial primitive values. Destructuring is an ordinary read into a new local, whereas static import braces select bindings. Activate the last line and check with `--noEmit`; it fails, exit 1. Restore it before building.

The Map's contents can change even though its imported binding cannot be reassigned. Capturing an object as a default expression also retains the object identity; it does not freeze that object. Conversely, replacing the exporter's local with another object would not replace a default expression's earlier captured object.

Named default function and class *declarations* have their own binding rules; do not classify `export default function Foo` as the same form as `export default someExpression`. Part 1 demonstrates the legal function case. The specification's [export mappings and semantics](https://tc39.es/ecma262/2026/multipage/ecmascript-language-scripts-and-modules.html#sec-exports) distinguish these forms. [Jake Archibald's original comparison](https://jakearchibald.com/2021/export-default-thing-vs-thing-as-default/) is useful further reading for the expression/alias distinction. The explanation applies to ESM itself, rather than a rule that every CommonJS access is a snapshot; see the [interop owner](<./1.3. export equals and interop with CommonJS.md>) for that separate system.

### 4) **Deferred evaluation has a separate support contract**

`import defer * as feature from "./feature.js"` is proposal syntax for deferring synchronous module evaluation until the deferred namespace is accessed. It is namespace-only. Ordinary loading/linking still happens ahead of use; it is not a guarantee to avoid fetching the module. The [TC39 proposal](https://github.com/tc39/proposal-defer-import-eval) was **Stage 3** when checked on 2026-10-15, so this is an optional, tool-gated example rather than a portable stable-runtime default. The proposal also eagerly evaluates asynchronous dependencies and their dependencies; “all transitive work waits” is too broad, especially with top-level await.

TypeScript added syntax support in 5.9. Its [release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-9.html#support-for-import-defer) explain that TypeScript preserves this syntax instead of implementing it. The following project uses **TypeScript 7.0.2**, **Node 22.18.0** and the explicitly pinned Babel transform below. Use Node 22.18.0 for every Node/npm command in this part; check `node --version` first. No native deferred-evaluation support is claimed for this runtime.

In a new directory, save package.json:

```json
{
  "private": true,
  "type": "module",
  "devDependencies": {
    "@babel/core": "8.0.7",
    "@babel/cli": "8.0.6",
    "@babel/plugin-proposal-import-defer": "8.0.1",
    "@babel/plugin-transform-modules-commonjs": "8.0.1"
  }
}
```

Save tsconfig.json. `bundler` resolution and preserved ES module output describe this transform pipeline, not direct Node loading:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "esnext",
    "moduleResolution": "bundler",
    "lib": ["es2022", "dom"],
    "types": [],
    "verbatimModuleSyntax": true,
    "noEmitOnError": true,
    "rootDir": "src",
    "outDir": "esm"
  },
  "include": ["src/**/*.ts"]
}
```

Create src and these files:

```typescript
// file: src/feature.ts
console.log("feature evaluated");
export const value: number = 42;
// file: src/eager.ts
import * as feature from "./feature.js";
console.log("entry started");
console.log(feature.value);
// file: src/deferred.ts
import defer * as feature from "./feature.js";
console.log("entry started");
console.log(feature.value);
console.log(feature.value);
// file: src/unused.ts
import defer * as feature from "./feature.js";
console.log("feature skipped");
// file: src/fallback.ts
console.log("entry started");
async function useFeature(enabled: boolean): Promise<void> {
  if (!enabled) { console.log("feature skipped"); return; }
  console.log("before request");
  const feature = await import("./feature.js");
  console.log(feature.value);
}
async function main(): Promise<void> {
  await useFeature(false);
  await useFeature(true);
}
void main();
```

Save babel.config.json:

```json
{
  "plugins": [
    "@babel/plugin-proposal-import-defer",
    "@babel/plugin-transform-modules-commonjs"
  ]
}
```

Check, emit and observe the unsupported native path:

```bash
npm install
tsc -p tsconfig.json --noEmit
tsc -p tsconfig.json
node esm/eager.js
node esm/deferred.js
```

Installation and both compiler commands exit 0. The eager entry prints `feature evaluated`, `entry started`, then `42`. The deferred entry **fails to parse**, exit 1, with SyntaxError; its body never runs. Inspect esm/deferred.js: `import defer` remains. The same native failure was also observed on Node 20.20.2. An unsupported parser does not leave the import inert; it rejects the entry. These are version-specific observations, not a claim about every Node release or browser.

For the supported **transformed CommonJS** path, run:

```bash
npx --no-install babel esm --out-dir cjs --extensions .js
node --input-type=commonjs -e 'require("node:fs").writeFileSync("cjs/package.json", JSON.stringify({type:"commonjs"}))'
node cjs/eager.js
node cjs/deferred.js
node cjs/unused.js
node esm/fallback.js
```

All six commands exit 0. The nested package.json marks Babel's `.js` output as CommonJS despite the outer ESM package. Run entries separately so a previous evaluation cannot hide initialization:

| Entry | Observed output in order |
|---|---|
| cjs/eager.js | `feature evaluated`, `entry started`, `42` |
| cjs/deferred.js | `entry started`, `feature evaluated`, `42`, `42` |
| cjs/unused.js | `feature skipped` |
| esm/fallback.js | `entry started`, `feature skipped`, `before request`, `feature evaluated`, `42` |

The deferred property's first access triggers initialization; the second does not repeat it. The unused entry does not initialize feature. [Babel's plugin documentation](https://babeljs.io/docs/babel-plugin-proposal-import-defer) states that this transform uses deferred require calls and requires CommonJS transformation. Inspect cjs/deferred.js to see that deferred require path. This synchronous, acyclic example verifies that particular tool path, not native ESM graph preloading, asynchronous-dependency handling or every proposal edge case. Keep that distinction when deciding whether a transform suits a real graph.

For a meaningful checker failure, change the deferred import to `import defer { value } from "./feature.js"`; `tsc -p tsconfig.json --noEmit` rejects it. A default-defer import is rejected too. Restore the namespace form. Setting `module` to es2022 also rejects deferred imports; select a supporting module mode for the compiler and a separately supporting runtime/transform for execution. The current compiler also accepts `preserve`; neither mode supplies a runtime implementation.

The dynamic `import()` alternative runs without the defer transform. It returns a promise and loads/evaluates when the enabled branch requests it. Its caller must handle asynchronous completion; replacing a synchronous deferred-property access with it changes the API. It also evaluates the module on import completion rather than waiting for the first namespace property read. For an application that can accept that boundary, this is an explicit alternative, not a transparent polyfill. The [JavaScript dynamic-import lesson](<../../../../JavaScript/14 Modules and Code Organization/sections/4. Dynamic import and meta/4.1. Dynamic import async loading and code splitting.md>) owns the broader loading and code-splitting concepts.

### 5) **Common confusion**

Default is an export name, not a statement that the module has no named exports. Import aliases are allowed for both forms. Namespace imports expose runtime exports; TypeScript can also resolve qualified types from an imported module, but those types are not runtime properties to enumerate or execute.

A barrel with ambiguous stars does not choose the last definition. A default expression does not track every reassignment of the expression's source variable. Neither rule is repaired by changing import names: fix the exporting module's public bindings. A deferred import is a runtime dependency with delayed evaluation under its supported execution contract; it does not erase like `import type`.

### 6) **Performance note**

Imports and re-exports define dependency relationships. A bundler may remove unused exports when its analysis and side-effect assumptions allow it; named, default, namespace and star spelling alone do not determine retained bytes. This lesson measured no bundle size or lookup timings. Do not replace a live namespace read with a destructured local as a speculative speed improvement: part 3 shows that it changes observed state.

Deferred evaluation can move initialization work from startup to first use; it does not remove that work when the feature is used. Required registration side effects may happen too late if deferred. Dynamic import adds an asynchronous loading boundary. Profile startup and first-use latency on the actual graph and target before choosing either approach. The Babel logs prove ordering in this small graph, not a speedup or native preload savings.

### 7) **Mentor note**

Have the learner predict the five values on watch's second line and identify the binding or local read behind each one. A sound explanation distinguishes exported local bindings, the captured default expression and destructuring; “ESM is always live” is not precise enough.

Next, ask them to repair the ambiguous barrel without losing the right-hand operation. Renaming its public binding should be an intentional API decision. For defer, ask for four pieces of evidence: compiler acceptance, preserved output, the unsupported native failure and the successful declared transform. Finally, have them explain why changing the fallback to return a number synchronously cannot be achieved merely by deleting await. This exposes the loading/API trade-off without making unmeasured performance promises.
