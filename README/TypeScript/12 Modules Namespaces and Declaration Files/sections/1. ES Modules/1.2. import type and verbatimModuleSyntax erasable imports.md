## 1.2. `import type` and `verbatimModuleSyntax` — erasable imports

### 1) **`import type` traffic** (type-only imports erase fully)

**Definition** — `import type { User } from "./models"` imports *only the type*: the entire statement (and the module dependency, if nothing else imports values) vanishes at emit — no runtime `require`/`import`, no bundler weight, no circular-import edge. Plain `import { User }` (used as a type only) *may* elide under `importsNotUsedAsValues` heuristics — but elision is guesswork the flag makes unnecessary.

**What problem it solves / history** — type-only imports through value syntax (`import { User } …` used solely in annotations) created phantom runtime dependencies: bundlers included unneeded modules (weight), circular type references became circular *runtime* edges (import-time `undefined` crashes — see 5.1 promise 1's barrel cycle class), and syntax-only transpilers had to *infer* erasability per import (occasionally wrong). `import type` (TS 3.8) states erasability explicitly — no inference, no edge, no weight.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write `import type` for every type-only import (interfaces, type aliases, `typeof`-query inputs used purely statically); reserve plain `import` for values (functions, classes, consts, enums). Mixed needs split across two statements (`import { run } …; import type { Cfg } …`) — one line per universe, each honest about its emit.

**Runnable example** — type traffic leaves no runtime trace (multi-file sets):

```typescript
// file: models.ts
export interface User { id: string }
export const VERSION = 3;
// file: service.ts
import type { User } from "./models.js"; // erased fully (no runtime edge to models.js)
export function nameOf(u: User): string { return u.id.toUpperCase(); }
// file: app4.ts
import { nameOf } from "./service.js";
import { VERSION } from "./models.js"; // value import (runtime edge — VERSION exists)
console.log(nameOf({ id: "u1" }), VERSION); // U1 3 — service.js carries no models.js weight
```

```typescript
// file: shapes2.ts
export interface Box { w: number }
export function area2(b: Box): number { return b.w ** 2; }
// file: calc.ts
import { area2 } from "./shapes2.js";
import type { Box } from "./shapes2.js"; // split: value + type traffic stated separately
const b: Box = { w: 4 };
console.log(area2(b).toFixed(0)); // 16 — bundler sees one value edge (area2), zero type edges
// bad — import { area2, Box } ... (single value-syntax import: bundler keeps the whole shapes2.js record reachable)
```

```typescript
// file: reg4.ts
export interface Handler { (at: number): void }
export const handlers = new Map<string, Handler>();
// file: dispatch.ts
import type { Handler } from "./reg4.js"; // zero-weight: dispatch.js never loads reg4.js at runtime
export function make(h: Handler): Handler { return h; }
// file: boot.ts
import { handlers } from "./reg4.js"; // the ONE value edge (pays weight deliberately)
import { make } from "./dispatch.js";
handlers.set("a", make((at) => console.log(at)));
console.log(handlers.size); // 1 — weight paid once (boot), never via dispatch
```

**Common confusion** — "`import type` changes what's imported" — identical *type* bindings (same names, same checking); only emit differs (erased vs possibly-emitted) — semantics preserved, weight removed. "elision already handles this" — `importsNotUsedAsValues` *guesses* from usage (correct usually, wrong across re-exports/isolated declarations); `import type` *declares* (always right, toolchain-independent). "`import type` breaks circular type references" — *fixes* them (type-space cycles are legal — values never load, so no runtime cycle exists to break).

**Performance note** — erased imports cost zero bytes and zero load edges (bundlers skip them entirely); value imports of types-only modules cost the module's evaluation (side effects run, graph grows). At scale (hundreds of type-only cross-imports), `import type` discipline measurably shrinks bundles and shortens startup — the cheapest bundle diet available.

**Mentor note** — bundle-diff one value-imported types module converted to `import type` (module vanishes from the chunk) — weight made visible in bytes. Exercise: grep `import {` for type-only names project-wide and convert (each conversion deletes a runtime edge); enable the lint (`consistent-type-imports`) so the discipline holds. Review gate: type-only names in value imports fail review.

### 2) **`verbatimModuleSyntax` enforcement** (the compiler stops guessing)

**Definition** — `verbatimModuleSyntax: true` (TS 5.0) disables import elision *heuristics*: type-only names in value imports *error* (`TS1484: … must be imported with import type`), `export =` interop narrows, and emit preserves import statements verbatim (bundlers/strippers see exactly what the author wrote). The compiler stops guessing erasability — authors state it, the flag enforces the statement.

**What problem it solves / history** — elision heuristics (`importsNotUsedAsValues: remove`) silently *changed meaning* across toolchains (tsc elided, esbuild preserved — same source, different runtime graphs; side-effect imports dropped by one pipeline, kept by another). `verbatimModuleSyntax` makes emit *predictable*: what you write is what every toolchain processes — type traffic via `import type` (erased everywhere identically), value traffic via `import` (kept everywhere identically).

**Modern guidance** — as of TypeScript 5.9 era, enable `verbatimModuleSyntax` in every strict tsconfig (with `isolatedModules` — the predictable-emit pair); fix each TS1484 by converting to `import type` (never by widening to value imports — the error *is* the erasability audit). Pair with `--erasableSyntaxOnly` where adopted (the erasable trio — see [2.2. erasableSyntaxOnly](<../../../11 Enums and Literal Types/sections/2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>) in 11).

**Runnable example** — guessing ends, stating begins (multi-file sets; TS1484 demo as commented error):

```typescript
// file: types5.ts
export interface Cfg { host: string }
// file: good.ts
import type { Cfg } from "./types5.js"; // stated erasable (passes under verbatimModuleSyntax)
export function hostOf(c: Cfg): string { return c.host.toUpperCase(); }
// file: use5.ts
import { hostOf } from "./good.js";
console.log(hostOf({ host: "h" })); // H — zero type edges in emit, identical on every toolchain
```

```typescript
// file: types6.ts
export interface Opts { retries: number }
// file: bad6.ts
// import { Opts } from "./types6.js"; // error TS1484 under verbatimModuleSyntax (type-only name in value import)
// fix — import type { Opts } (state erasability; the flag rewards stating, punishes guessing)
import type { Opts } from "./types6.js";
export function tries(o: Opts): string { return `tries=${o.retries}`; }
// file: use6.ts
import { tries } from "./bad6.js";
console.log(tries({ retries: 3 })); // tries=3 — converted import, predictable emit
```

```typescript
// file: side.ts
console.log("side effect ran");
export const V = 1;
// file: keep.ts
import "./side.js"; // side-effect import (no bindings — kept verbatim under every setting)
import { V } from "./side.js";
console.log(V); // side effect ran \n 1 — verbatimModuleSyntax never elides binding-less imports
// bad — import { V } ... used ONLY as a type under elision heuristics: side effect silently dropped by tsc, kept by esbuild (pipeline divergence)
// fix — import type { V }?? NO (V is a value!) — the discipline cuts both ways: values via import (kept), types via import type (erased)
```

**Common confusion** — "the flag changes checking" — emit-only (same types, same errors, different `.js`) — enable mid-project safely (only *new* TS1484 errors appear, each a stating-fix). "`export =` breaks under the flag" — narrows (only `export =` with `import = require()` pairing — see [1.3. export equals](<./1.3. export equals and interop with CommonJS.md>)) — interop forms keep working through their sanctioned syntax. "verbatim slows builds" — removes heuristic passes (marginally faster emit logic); the cost is authoring precision (stating per import), paid once per declaration.

**Performance note** — predictable emit means bundlers skip re-analysis (import statements mean exactly what they say — no cross-toolchain divergence to reconcile); `import type` edges vanish from graphs (smaller bundles, faster startup — same dividend as promise 1, now enforced).

**Mentor note** — enable the flag on a Friday and triage TS1484s Monday (each a type-only import masquerading as value traffic — the audit the codebase needed). Rule: TS1484 fixes convert to `import type` (stating); "fixing" by using the name as a value is fraud against the flag — review accordingly.

### 3) **Erasable import discipline** (the trio: `import type` + `verbatimModuleSyntax` + stripping-safe syntax)

**Definition** — the complete discipline: every type-only import written `import type` (stated), `verbatimModuleSyntax: true` enforcing the statement (no guessing), and `--erasableSyntaxOnly`-clean syntax elsewhere (no enums/namespaces — see domain 11) — together making *every file* safely processable by syntax-only toolchains (Node stripping, esbuild, swc, Babel) with byte-identical semantics to `tsc` emit.

**What problem it solves / history** — partial adoption (type imports stated but enums present; flags on but `export =` scattered) left *some* files toolchain-locked — the ones nobody remembered, discovered when Node-stripping or esbuild choked mid-migration. The trio as a *project standard* (linted + flagged + verified in CI across tsc/esbuild/stripping) makes erasability a property of the repo, not of the files someone remembered.

**Modern guidance** — as of TypeScript 5.9 era, standardize the trio in new projects (tsconfig flags + `consistent-type-imports` lint + CI job running tests under both `tsc`-emit and a stripping runner); migrate legacy projects per-directory (new code trio-clean, legacy exempted with dated TODOs). Verify with dual-pipeline CI (same tests, two runtimes — divergence fails the build, not the customer).

**Runnable example** — trio-clean module (multi-file sets):

```typescript
// file: domain.ts
export interface Order { id: string; total: number }
export function totalOf(o: Order): number { return o.total; }
// file: shop.ts
import { totalOf } from "./domain.js";
import type { Order } from "./domain.js"; // trio: stated type traffic (verbatimModuleSyntax-honest)
export function checkout(o: Order): string { return `pay ${totalOf(o).toFixed(2)}`; }
// file: main7.ts
import { checkout } from "./shop.js";
console.log(checkout({ id: "o1", total: 9 })); // pay 9.00 — stripping-safe on every toolchain
```

```typescript
// file: kit.ts
export interface Kit { sku: string }
export const KIT_VERSION = 7;
// file: store.ts
import type { Kit } from "./kit.js";
import { KIT_VERSION } from "./kit.js"; // split traffic: types erased, values kept (each honest)
export function label(k: Kit): string { return `${k.sku}@v${KIT_VERSION}`; }
// file: main8.ts
import { label } from "./store.js";
console.log(label({ sku: "k" })); // k@v7 — dual-pipeline CI (tsc + stripping) passes identically
// bad — import { Kit, KIT_VERSION } (single value-syntax import: verbatimModuleSyntax errors TS1484 on Kit)
```

```typescript
// file: cfg9.ts
export interface Cfg9 { host: string }
// file: net.ts
import type { Cfg9 } from "./cfg9.js";
export function url(c: Cfg9): string { return `https://${c.host}`; }
// file: main9.ts
import { url } from "./net.js";
console.log(url({ host: "x.io" })); // https://x.io — no enums, no namespaces, stated imports: trio-clean
// bad — same shape with enum-based status + value-imported types (two trio violations, two toolchain locks)
```

**Common confusion** — "trio discipline slows feature work" — per-declaration stating (seconds) vs toolchain migration quarters (months) — the trio front-loads trivial decisions to avoid back-loaded rewrites. "dual-pipeline CI doubles costs" — stripping runners execute in milliseconds (no typecheck — checking still runs once under tsc); the second pipeline pays startup-speed verification for near-zero CI time. "legacy code must convert immediately" — per-directory adoption (new trio-clean, legacy dated-TODO) compounds quarterly — flag-day conversion is the anti-pattern the trio exists to prevent.

**Performance note** — trio-clean repos start fastest under stripping runtimes (no transpile decisions per file — syntax deletes mechanically) and bundle smallest (type edges absent from graphs) — the performance story *is* the erasability story, measured in startup milliseconds and bundle bytes.

**Mentor note** — run the test suite under both pipelines in CI this quarter (same tests, tsc-emit + node-stripping) — divergence failures are the trio audit automated. Exercise: trio-convert one directory (flags + imports + enum migration per domain 11) and measure bundle + startup deltas — numbers sell standards better than rules.
