## 1.2. `import type` and `verbatimModuleSyntax` — erasable imports

### 1) **Type-only traffic and runtime dependencies**

An imported name can be needed by the checker without being needed by the running program. `import type` states that distinction: the entire statement is removed from emitted JavaScript. A value import supplies a runtime binding, while a side-effect import such as `import "./setup.mts"` deliberately evaluates a module without supplying a local binding.

[Josh Goldberg's original explanation](https://typescripteslint.com/blog/consistent-type-imports-and-exports-why-and-how/) uses side-effectful modules to motivate explicit type imports. A syntax-only processor cannot discover whether an unmarked imported name is an interface by inspecting the importing file alone. That practical question is more useful than treating every import conversion as a guaranteed bundle optimization.

There are two related forms with different consequences under `verbatimModuleSyntax`:

| Source form | Emitted import behavior | Use |
|---|---|---|
| `import type { User } from "./dep.mts"` | Whole statement disappears. | A checker dependency with no runtime dependency from this statement. |
| `import { greet, type User } from "./dep.mts"` | Value import remains; type specifier disappears. | Both value and type use from the same module. |
| `import { type User } from "./dep.mts"` | Empty `import {}` remains. | Module still evaluates; prefer top-level `import type` when that is unintended. |
| `import "./dep.mts"` | Side-effect import remains. | Intentional initialization with no local binding. |

A retained specifier's relative extension can also change when extension rewriting is enabled. The [verbatimModuleSyntax reference](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html) documents type removal and the empty-import case. The following actual graph makes the distinction visible.

### 2) **A complete checked and executed module graph**

Use TypeScript **7.0.2**, Node **20.20.2** for emitted JavaScript, and Node **22.18.0** for native source execution, verified 2026-10-13. Create a disposable directory with `src` inside it. Save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": [
      "es2022",
      "dom"
    ],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true,
    "rewriteRelativeImportExtensions": true
  },
  "include": [
    "src/**/*.mts"
  ]
}
```

The `.mts` files are explicitly ESM. These flags enforce distinct syntax/import restrictions; they do not configure Node's loader. The [trio configuration lesson](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) owns their full contracts. Here, `rewriteRelativeImportExtensions` lets a relative source specifier naming `.mts` become `.mjs` in emitted output.

Save `src/dep.mts`:

```typescript
console.log("dependency evaluated");
export interface User { name: string }
export const VERSION = 1;
export function greet(user: User): string { return `hello ${user.name}`; }
```

Save `src/app.mts`:

```typescript
import { greet, VERSION } from "./dep.mts";
import type { User } from "./dep.mts";
const user: User = { name: "Ada" };
console.log(greet(user), VERSION);
```

Save `src/type-only.mts`:

```typescript
import type { User, VERSION } from "./dep.mts";
type Version = typeof VERSION;
const version: Version = 1;
const user: User = { name: "Ada" };
console.log("type-only entry", user.name, version);
```

The type-only import can name VERSION for the checker query `typeof VERSION`. It supplies no runtime VERSION binding; the local variable `version` supplies the value printed here. A type-only imported class can similarly name an instance type, while construction requires a value import. Full type/value-space reasoning lives in [type queries](<../../../02 The Type System Core/sections/2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>).

Save `src/inline.mts`:

```typescript
import { type User } from "./dep.mts";
const user: User = { name: "Ada" };
console.log("inline entry", user.name);
```

Run each entry in a separate process so prior module evaluation cannot hide an import edge:

```bash
tsc --version
tsc -p tsconfig.json --noEmit
tsc -p tsconfig.json
node dist/app.mjs
node dist/type-only.mjs
node dist/inline.mjs
npm exec --yes --package=node@22.18.0 -- node src/app.mts
npm exec --yes --package=node@22.18.0 -- node src/type-only.mts
npm exec --yes --package=node@22.18.0 -- node src/inline.mts
```

All checks and executions exit 0. Both execution paths produce the same per-entry observations:

| Entry | Output |
|---|---|
| app | `dependency evaluated`, then `hello Ada 1` |
| type-only | `type-only entry Ada 1` |
| inline | `dependency evaluated`, then `inline entry Ada` |

Inspect `dist/type-only.mjs`: its type import is absent. Inspect `dist/inline.mjs`: `import {} from "./dep.mjs"` remains. Inspect `dist/app.mjs`: greet/VERSION are imported as values, while the separate User import is absent. The type-only entry never evaluates dep; the other two entries do. The app's value import still loads dep even though its User import disappears.

### 3) **Source and emitted import strategies**

This graph deliberately names relative source files with `.mts`. Native Node can locate those files. The [extension-rewrite option](https://www.typescriptlang.org/tsconfig/rewriteRelativeImportExtensions.html) changes supported relative TypeScript extensions in emitted imports, so the JavaScript graph locates `.mjs` output. Node itself does not read that compiler setting or rewrite paths according to it. [Node's TypeScript documentation](https://nodejs.org/docs/latest-v22.x/api/typescript.html) explains the source loader's module and type-import rules.

An emitted-only application can instead use output extensions in its source specifiers under a matching resolution configuration. That is a different execution contract. A checker can resolve a `.mjs` specifier to its `.mts` source counterpart, while Node's source loader still looks for the named `.mjs` file. Do not assume that file exists beside the source. Compiler `paths` aliases and package specifiers also need their real runtime arrangements; this relative-extension option is not a general alias resolver.

**Practice 1 — an unmarked type import:** change only `import type { User }` in app to `import { User }`. `tsc -p tsconfig.json --noEmit` reports TS1484, exit 1. For a controlled comparison, build this modified source with:

```bash
tsc -p tsconfig.json --verbatimModuleSyntax false --outDir dist-elided
node dist-elided/app.mjs
npm exec --yes --package=node@22.18.0 -- node src/app.mts
```

The first two commands exit 0; emitted code prints `dependency evaluated` and `hello Ada 1`. The native source execution exits 1 because dep does not provide a runtime export named User. Compiler elision repaired the runtime import in one path; source stripping could not infer the missing marker. Restore `import type`; disabling the flag was an experiment, not the fix.

**Practice 2 — an output extension in a source graph:** change only the app's value-import specifier to `./dep.mjs`. Keep its type import unchanged. The checker still exits 0. Native source execution exits 1 with ERR_MODULE_NOT_FOUND because `src/dep.mjs` is absent. Restore `./dep.mts`, rebuild, and run the emitted app; both commands exit 0 with the original output. This exposes a resolution failure which the syntax gates cannot prevent.

When migrating imports, first identify which graph is deployed. State type traffic explicitly, keep necessary initialization as an intentional runtime import, check with the relevant flags, then execute the actual entry points. Mixed value/type imports are valid when the type specifiers are marked; splitting them into two lines is a style choice except where whole-statement erasure affects the module edge. Do not convert a value binding that is needed at runtime into a type-only binding.

### 4) **Common confusion**

`import type` does not mean the exported declaration must itself be type-only. VERSION above is a value whose type can be queried without loading its module. What matters is whether the importing program needs a runtime binding. Conversely, a type-only binding cannot supply a runtime constructor or function.

Removing one import statement does not remove every path to a module. The app still evaluates dep through greet/VERSION. A type-only cycle creates no runtime edges from those statements; remaining value imports can still form a runtime cycle. Neither verbatimModuleSyntax nor erasableSyntaxOnly proves that a whole program executes identically through every toolchain. This lesson verified two declared paths, with purposeful failures for their boundaries.

### 5) **Performance note**

A whole-statement type import contributes no emitted runtime import. Its absence can avoid module evaluation if no other runtime edge loads that module. The checker still resolves the types. Bundle size and startup effects depend on the remaining graph, side effects, bundler behavior and target; no bundle or timing benchmark was run here. Inline-only imports may retain evaluation as observed, so inspect emitted imports rather than estimating savings from the number of type specifiers. Do not remove required initialization as an optimization.

### 6) **Mentor note**

Ask the learner to predict which fresh-process entries print `dependency evaluated`, then explain the emitted imports. A correct answer distinguishes removal of a type specifier from removal of an entire statement and notices the app's remaining value edge.

During review, ask which artifact the deployment starts and whether its import targets exist. Have the learner diagnose TS1484 and ERR_MODULE_NOT_FOUND separately: one needs explicit type traffic, the other needs an import strategy matching the execution graph. Neither is solved by asserting a value's type. For a side-effectful dependency, require the reason to retain or omit evaluation before applying a project-wide import rewrite.
