## 1.3. export equals and interop with CommonJS

CommonJS exposes the value assigned to module.exports. That value can be a function, class, primitive or object with properties. Export equals models that whole value in TypeScript. An ES default export is instead a named export slot; transforming it to CommonJS does not automatically replace module.exports with the exported function.

Consumer syntax also depends on the compiler mode and actual loader. Import equals can emit a real require call or a createRequire bridge; a default import may be transformed with a helper or remain native ESM syntax. It is not enough to call all of them equivalent whole-record bindings.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, with a separate Node.js 22.18.0 comparison, verified 2026-10-16. Create a fresh directory without tsconfig.json or package dependencies. Save the named files below there; split multi-file fences at their file markers. The .cts and .mts extensions make the intended module kinds explicit. No Node type package is needed by these sources. All execution here runs emitted JavaScript.

### 1) **Model a callable CommonJS export and its properties**

Save legacy.cts:

```typescript
function connect(url: string): string { return `connected ${url}`; }
namespace connect {
  export interface Options { url: string }
  export const version = 1;
}
export = connect;
// export const extra = 2; // TS2309: cannot add a separate top-level export beside export equals
```

Save cjs.cts:

```typescript
import connect = require("./legacy.cjs");
import defaultConnect from "./legacy.cjs";
import * as space from "./legacy.cjs";
import { version } from "./legacy.cjs";
const options: connect.Options = { url: "db://x" };
console.log(connect(options.url), defaultConnect(options.url), version);
console.log(connect === defaultConnect, typeof space, space.version, typeof space.default);
// connect(42); // TS2345
// space("db://x"); // TS2349: namespace object is not callable
```

Build with `tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --declaration --noEmitOnError --outDir out cjs.cts`, then run `node out/cjs.cjs`. The output is `connected db://x connected db://x 1`, then `true object 1 function`.

Inspect out/legacy.cjs: it assigns module.exports = connect. Its namespace adds version to that function. Inspect out/legacy.d.cts: it describes the callable value, Options and version, ending with export = connect. The merged namespace exposes a type and property on the exported entity; it does not create a separate top-level export alongside export equals. [Declaration merging](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) owns the full merge rules.

In out/cjs.cjs, the import-equals binding uses require directly. The default and namespace imports use interop helpers in this tested transform; the named import becomes a property access on the required value. Both callable bindings refer to the same function, while space is an object view. A CommonJS-exported function can have named properties, so consuming a property is not inherently invalid or untyped.

### 2) **Compare native ESM loading with the transformed consumer**

Save esm.mts:

```typescript
import connect from "./legacy.cjs";
import paired = require("./legacy.cjs");
console.log(connect("esm"), paired("paired"), connect.version, connect === paired);
```

Build with the part 1 command, substituting esm.mts, then run `node out/esm.mjs`. It prints `connected esm connected paired 1 true`. Inspect its output: the default import remains native ESM syntax, while import equals uses a generated import of createRequire from the built-in "module" specifier and a runtime require. This bridge is supported in this NodeNext ESM mode; import equals is neither erased compile-time-only syntax nor legal under every module configuration.

Now save named.mts:

```typescript
import { version } from "./legacy.cjs";
console.log(version);
```

It builds successfully with the same command, but `node out/named.mjs` exits 1 with a SyntaxError saying named export version was not found. Node statically analyzes CommonJS source to discover some named exports; it does not simply expose every property that eventually appears on module.exports. The namespace-generated function property in this fixture is not detected. The checker can describe that property while native linking still fails. The native default import in esm.mts accesses the actual whole value, so connect.version works.

These results were also observed with Node 22.18.0. With the system Node 20.20.2, invoke the comparison as `npm exec --yes --package=node@22.18.0 -- node out/esm.mjs` and substitute cjs.cjs or named.mjs. [Node's CommonJS namespace contract](https://nodejs.org/download/release/v22.18.0/docs/api/esm.html#commonjs-namespaces) distinguishes the default value from heuristic named exports. Do not turn this one missing name into a claim that no CommonJS named import works; explicit export assignments may be detected.

### 3) **Inspect the shape produced by a transformed default export**

Save these three files:

```typescript
// file: defaulted.cts
export default function greet(): string { return "hello"; }
// file: default-cjs.cts
import greet from "./defaulted.cjs";
console.log(greet());
// file: default-esm.mts
import loaded from "./defaulted.cjs";
console.log(typeof loaded, typeof loaded.default, loaded.default());
// loaded(); // TS2349 under this NodeNext module model
```

Build with the part 1 command, substituting `default-cjs.cts default-esm.mts`, then run both emitted entries. The CommonJS consumer prints `hello`; the native ESM consumer prints `object function hello`. Inspect out/defaulted.cjs: the compiler sets an __esModule marker and assigns the function to exports.default, not directly to module.exports. The transformed default consumer recognizes that marker. Node's native default import instead supplies the entire CommonJS export object, so the callable function is loaded.default. This is the [double-default distinction](https://www.typescriptlang.org/docs/handbook/modules/appendices/esm-cjs-interop.html#no-__esmodule-detection-the-double-default-problem).

[Andrew Branch's original analysis](https://blog.andrewbran.ch/default-exports-in-commonjs-libraries/) explains the export/declaration mismatch caused by combining an ESM default with a raw module.exports overwrite. Model the intended whole CommonJS export with export equals when that is the contract. Do not add two inconsistent export mechanisms just to make one consumer pass. Changing the public shape is an API migration that needs tests for existing consumers.

On TypeScript 7.0.2, explicitly adding `--esModuleInterop false --noEmit` to the part 1 check reports TS5108: this false setting has been removed. Older [option documentation](https://www.typescriptlang.org/tsconfig/esModuleInterop.html) explains the helper transformation and a historical on/off comparison; its default-false premise is not the baseline tested here. AllowSyntheticDefaultImports concerns checker acceptance, not installation of a runtime wrapper by itself. Nor does a TypeScript setting reconfigure Node's native loader. Inspect whether the actual output is CommonJS helper code or preserved ESM before explaining an interop result.

VerbatimModuleSyntax adds a separate authoring restriction: adding it to the cjs.cts build rejects its ESM value-import forms rather than silently rewriting them. Import equals and export equals remain useful CommonJS spellings in that mode, but both are rejected by erasableSyntaxOnly. They need transformation, so they are not the native stripping solution. [Type-only imports](<./1.2. import type and verbatimModuleSyntax erasable imports.md>) owns whole-statement erasure and retained import edges.

### 4) **Require an ESM namespace only under a supported runtime contract**

Import equals does not inherently discard named-export types. Save this separate pair:

```typescript
// file: esm-api.mts
export const version = 7;
export default function greet(): string { return "hello"; }
// file: require-esm.cts
import api = require("./esm-api.mjs");
console.log(api.version, api.default());
// api.missing; // TS2339
```

Build with the part 1 command, substituting require-esm.cts, then run `node out/require-esm.cjs`. It prints `7 hello` on both Node 20.20.2 and Node 22.18.0. In this tested NodeNext/runtime pair, require can load this synchronous ESM graph, and the binding has its typed namespace members. Do not generalize an older ERR_REQUIRE_ESM rule to these runtimes or assume every older compiler module mode models the same capability.

Now add `await Promise.resolve();` at the end of esm-api.mts. The NodeNext build still succeeds, but both runtime executions fail with ERR_REQUIRE_ASYNC_MODULE. Restore the synchronous fixture. For an asynchronous ESM graph, replace the require consumer with this asynchronous entry and rebuild:

```typescript
// file: dynamic.cts
async function main(): Promise<void> {
  const api = await import("./esm-api.mjs");
  console.log(api.version, api.default());
}
void main();
```

With the top-level await restored in esm-api.mts, dynamic.cjs runs and prints `7 hello` on both runtimes. It waits for module evaluation; changing a synchronous API to this form changes the caller's completion contract. Node's [require support](https://nodejs.org/download/release/v22.18.0/docs/api/esm.html#require) is limited to synchronous ESM graphs, and the [dynamic-import owner](<../../../../JavaScript/14 Modules and Code Organization/sections/4. Dynamic import and meta/4.1. Dynamic import async loading and code splitting.md>) explains the broader asynchronous loading model.

### 5) **Common confusion**

A whole CommonJS export can still contain properties. An ESM namespace exposes named bindings, while a native default import from CommonJS exposes its module.exports value. A transformed default export can therefore require another default property access under native ESM. These are runtime shapes, not interchangeable labels for one record.

Import equals retains checking for the resolved module and can create runtime loading work. It is not valid in every module mode, and its success does not prove that a require target has no asynchronous dependency. Conversely, a native named import may fail despite the checker describing the property. Verify the actual consumer format and loader, not only the library declaration.

### 6) **Performance note**

The tested CommonJS consumer retains helper code; the import-equals consumer retains require, and the ESM bridge creates a require function. All can load and evaluate dependencies. This lesson measured shape, checking and evaluation success, not timing or bundle size. There is no universal identical-emit, zero-runtime-work or hot-path recommendation based solely on import spelling. Choose the correct contract before measuring the actual consumer artifact.

### 7) **Mentor note**

Ask the learner what require returns, what native default import binds and what the declaration describes for each provider. A strong answer distinguishes legacy.cjs's callable value from defaulted.cjs's object with a default property. Then ask them to explain why named.mjs and require-esm with top-level await fail at different runtime stages despite passing checking.
