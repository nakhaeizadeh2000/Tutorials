## 1.3. `export =` and interop with CommonJS

### 1) **`export =` for CommonJS equivalence** (single `module.exports =` modeling)

**Definition** — `export = Foo` declares the module's *entire export* is one entity (modeling `module.exports = Foo` in CommonJS): importers take the whole thing (`import Foo = require(…)`), not members of it. The form exists for interop with un-migrated CJS (single-function packages, class-per-module libraries) — new ESM-first code never needs it.

**What problem it solves / history** — CJS single-export packages (`module.exports = connect`) had no ES equivalent (ES `export default` is *not* identical — default is a *named slot* called `default`; CJS overwrite replaces the *whole record*). `export =` models the overwrite exactly: one entity out, consumed whole — interop without reshaping either side's semantics.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write `export =` only when modeling an un-migrated CJS single export (library shims, `@types` for legacy packages); write ESM (`export`/`export default`) everywhere you own. Never mix `export =` with other exports in one file (the form *is* the whole export — siblings error).

**Runnable example** — whole-record export modeled exactly (multi-file sets, `--module commonjs`):

```typescript
// file: connect.ts
function connect(url: string): string { return `connected ${url}`; }
export = connect; // the module IS connect (models module.exports = connect)
// file: use10.ts
import connect = require("./connect.js");
console.log(connect("db://x")); // connected db://x — whole entity consumed whole
```

```typescript
// file: config11.ts
class Config { constructor(public host: string) {} }
export = Config; // single-class module (legacy library shape)
// file: use11.ts
import Config = require("./config11.js");
const c = new Config("h");
console.log(c.host.toUpperCase()); // H — class consumed whole (new + methods intact)
```

```typescript
// file: single.ts
const VERSION = 7;
export = VERSION; // single-value export (CJS constant-module shape)
// file: use12.ts
import VERSION = require("./single.js");
console.log(VERSION.toFixed(0)); // 7 — value consumed whole (literal type preserved)
// bad — export = alongside other exports (siblings error: the form IS the whole export)
// export = VERSION; export const X = 1; // error TS2309 — export assignment cannot have siblings
```

**Common confusion** — "`export =` equals `export default`" — default is a *slot* (`{ default: Foo }` record shape — interop needs `esModuleInterop` synthesis); `export =` *is* the record (no slot, no synthesis needed) — different shapes, different consumption syntax. "`export =` works in ESM output" — CJS/AMD/UMD only (TS1203 under ESM settings) — the form belongs to the interop world, not greenfield ESM. "migrating means renaming to default" — migration means *reshaping* (default slot + named members) with consumer updates — mechanical but semantic, not textual.

**Performance note** — interop form has zero runtime cost beyond the CJS linkage it models (same `require` graph, same evaluation) — the cost of *not* modeling it is mistyped imports (default-vs-record confusion) that surface as `undefined`-is-not-a-function at customer load.

**Mentor note** — draw the two shapes (`{ default: F }` vs `F`) and ask which `require` returns for each (`{default}` wrapper vs bare `F`) — interop confusion evaporates once the record shapes are visible. Exercise: convert one `export =` shim to ESM dual-shape (default + named) and update its consumers — the consumer diff *is* the interop lesson.

### 2) **`import = require()` pairing** (consuming `export =` from TS)

**Definition** — `import Foo = require("./foo")` is the sanctioned consumer of `export =` (and of untyped CJS generally): binds the whole record in one statement, works under every module setting, and types through `@types`/shims when present. Plain `import Foo from` on an `export =` shape errors without `esModuleInterop` (next promise) — the pairing syntax never needs the flag.

**What problem it solves / history** — `import Foo from "./cjs"` on `export =` shapes failed differently per flag (error without interop, synthetic default with it) — behavior depending on tsconfig rather than source made reviews guess. `import = require()` behaves identically under every setting (whole-record binding, always) — the form whose meaning never depends on flags, preferred wherever `export =` shapes are consumed.

**Modern guidance** — as of TypeScript 5.9 era, consume `export =` shapes with `import = require()` (stable across all module/resolution settings); consume ESM with `import`/`import type` (modern forms for modern shapes). Never mix the pairings (`import = require()` of ESM-named exports loses named checking — each shape keeps its syntax).

**Runnable example** — pairing stable across settings (multi-file sets, `--module commonjs`):

```typescript
// file: legacy.ts
function legacy(a: number, b: number): number { return a + b; }
export = legacy;
// file: con.ts
import legacy = require("./legacy.js"); // sanctioned pairing (no flag needed, every setting)
console.log(legacy(2, 3).toFixed(0)); // 5 — whole-record binding, typed end to end
```

```typescript
// file: greets.ts
export = function greet(name: string): string { return `hi ${name}`; }; // export = of anonymous-shaped value
// file: con2.ts
import greet = require("./greets.js");
console.log(greet("ada").toUpperCase()); // HI ADA — anonymous shape, named binding locally
// bad — import greet from "./greets.js" (default-slot import of a whole-record export: TS1259 without esModuleInterop)
// fix — import = require(): the pairing whose meaning never depends on flags
```

```typescript
// file: versioned.ts
const API_V = 2;
export = API_V;
// file: con3.ts
import API_V = require("./versioned.js");
console.log(API_V.toFixed(0)); // 2 — literal type preserved through the pairing
// bad — const { API_V } = require("./versioned.js") (untyped require: any — checking surrendered)
// fix — import = require(): typed whole-record binding (checking kept, flags irrelevant)
```

**Common confusion** — "`import = require()` is legacy and banned" — sanctioned (not deprecated) for `export =` consumption — bans apply to *new* `export =` authoring, never to consuming legacy shapes correctly. "the pairing works for ESM too" — technically compiles for some shapes but loses named-export checking (whole-record binding over a multi-export record) — ESM shapes deserve `import` syntax. "`require` calls execute at import time" — `import = require()` is *compile-time* module syntax (elided/preserved like imports, never a runtime `require()` call expression) — no dynamic-require semantics sneak in.

**Performance note** — identical emit to equivalent `import` forms (same module record linkage) — pairing choice is purely a checking/portability decision with zero runtime delta.

**Mentor note** — toggle `esModuleInterop` on/off around a plain-`import`-of-`export =` and watch behavior flip (error vs synthetic default) — then show `import = require()` stable across both — flag-independence demonstrated, not asserted. Rule: `export =` shapes pair with `import = require()`; ESM shapes pair with `import` — mismatched pairings fail review.

### 3) **Interop defaults and `esModuleInterop`** (synthetic defaults for CJS consumers)

**Definition** — `esModuleInterop: true` synthesizes a `default` slot for CJS records lacking one (`module.exports = Foo` importable as `import Foo from` — helper `__importDefault` wraps non-ESM records at runtime). Without the flag, default-importing a whole-record CJS shape errors (TS1259 — the honest refusal); with it, the helper bridges (convenience with a runtime wrapper per import).

**What problem it solves / history** — pre-flag interop forced the pairing syntax on every CJS import (verbose across migration-era codebases mixing ESM-TS with CJS deps) — `import React from "react"` (CJS single-record) errored without interop, confusing every newcomer. The flag (TS 2.7) made idiomatic default imports *work* over CJS shapes — at the cost of per-import helper code and flag-dependent meaning (the trade the previous promise avoids via pairing).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable `esModuleInterop` in application tsconfigs (idiomatic imports over the CJS ecosystem — React, Express-era libs, legacy utils); keep it *off* (or irrelevant) in library code compiled to clean ESM (helpers pollute emitted code consumers didn't ask for). Version note (verified with `tsc --version` → 7.0.2 in this repo's toolchain: interop is default-on and `false` was removed — behavior always bridged; on TS 5.x toolchains the flag still governs). Prefer `import = require()` at the specific `export =` boundaries even with bridging on (flag-independent meaning where it matters most).

**Runnable example** — flag bridges, pairing doesn't need it (multi-file sets):

```typescript
// file: cjsish.ts
function build(n: number): number[] { return Array.from({ length: n }, (_, i) => i); }
export = build; // whole-record shape (CJS-style single export)
// file: withflag.ts
import build from "./cjsish.js"; // compiles (bridged default: esModuleInterop on TS 5.x, default-on since TS 7)
console.log(build(3).join(",")); // 0,1,2 — idiomatic default import over a CJS shape
// file: noflag.ts
import build2 = require("./cjsish.js"); // compiles WITHOUT the flag (pairing needs nothing)
console.log(build2(2).length); // 2 — flag-independent consumption of the same shape
```

```typescript
// file: named10.ts
export const alpha = "a";
export const beta = "b";
// file: use10b.ts
import { alpha } from "./named10.js"; // named imports need no flag on any shape (ESM-native)
console.log(alpha.toUpperCase(), betaSafe());
function betaSafe(): string { return "b".toUpperCase(); } // (helper kept local; imports stay named)
console.log("named-ok"); // named-ok — flags govern defaults, never named bindings
// bad — default-importing a named-only ESM module (no default slot exists — flag can't synthesize intent)
// import whatever from "./named10.js"; // error TS1192 (no default export — flag-independent refusal)
```

```typescript
// file: dual.ts
export function run(): string { return "ran"; }
export default { run }; // dual shape: default slot AND named member (library-compatible both ways)
// file: useDual.ts
import bundle, { run } from "./dual.js"; // both forms, one statement (ESM-native dual consumption)
console.log(bundle.run(), run()); // ran ran — dual shapes serve both import styles without flags
// bad — dual-shaping CJS whole-record exports (consumers split across two idioms for one entity)
// fix — migrate CJS shapes to dual ESM (default + named) once; flag bridges only the transition
```

**Common confusion** — "the flag fixes all interop" — fixes *default-position* interop (one slot synthesized); named imports of CJS-named shapes need `@types`/shims regardless (no flag invents member types). "helpers are free" — `__importDefault`/`__importStar` wrappers emit per importing file (bytes × importers — trivial singly, measurable across hundreds of CJS imports; `import = require()` emits none of it). "new code needs the flag off for purity" — applications consuming the CJS ecosystem need it *on* (idiomatic imports); purity concerns belong to library *emit* (clean ESM out), not application *consumption*.

**Performance note** — helper wrappers cost bytes per importing file (one helper call each) + one indirection per default access (negligible at runtime; visible in bundles past hundreds of CJS imports). `import = require()` and named ESM imports emit zero helpers — prefer them on hot paths and in libraries.

**Mentor note** — toggle the flag around a default-import-of-CJS and watch error-vs-wrapper (TS1259 vs `__importDefault` in emit) — flag-dependent meaning made visible in two compiles. Rule: applications on (idiomatic ecosystem imports); libraries emit clean (no helper pollution); `export =` boundaries pair explicitly regardless.
