## 6.1. Common interview QA — modules, namespaces and declaration files

### 1) **Named vs default vs `import *` — which to prefer, and what does each cost?** (explicitness, convention, weight)

**Definition** — named (`import { a }` — explicit, refactor-safe, per-symbol tree-shaken); default (`import d` — terse, single-per-module, rename-drifting); namespace (`import * as N` — grouped, whole-record weight, no per-symbol shaking). Prefer named by default; default for single-purpose modules (pages, plugins, factories); namespace for genuinely grouped multi-member consumption.

**What problem it solves / history** — interviewers ask this to test organization judgment beyond syntax: candidates who add costs (refactorability, grep-ability, bundle weight) to each form reason about codebases, not just compilers — named-by-default with reasons beats personal-preference answers.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer named-first plus the three costs (rename-drift for defaults, record-weight for namespaces, explicitness dividends for named), then volunteer the lint (`array-type`-analogous import conventions + `consistent-type-imports`). Full treatment in [1.1. import and export forms](<../1. ES Modules/1.1. import and export forms named default star re-export.md>).

**Runnable example** — three forms, three costs (multi-file sets):

```typescript
// file: lib83.ts
export function alpha(): string { return "a"; }
export function beta(): string { return "b"; }
export default function main(): string { return alpha() + beta(); }
// file: app83.ts
import { alpha } from "./lib83.js"; // named (explicit, shakeable)
import main from "./lib83.js"; // default (terse, single)
import * as L from "./lib83.js"; // namespace (grouped, whole-record weight)
console.log(alpha(), main(), L.beta()); // a ab b — three forms, three cost profiles
```

```typescript
// file: drift.ts
export default function compute(): number { return 1; }
// file: app84.ts
import compute from "./drift.js";
import calc from "./drift.js"; // SAME export, second alias (rename-drift: grep for users finds neither reliably)
console.log(compute().toFixed(0), calc().toFixed(0)); // 1 1 — works, ungreppable (named exports prevent this)
// bad — default-heavy folders (every file its own alias dialect for shared exports)
```

```typescript
// file: heavy.ts
export function x1(): string { return "1"; }
export function x2(): string { return "2"; }
export function x3(): string { return "3"; }
// file: app85.ts
import { x1 } from "./heavy.js"; // named: bundler drops x2/x3 (per-symbol shaking)
console.log(x1()); // 1 — shakeable import (namespace import would pin all three)
// bad — import * as H (whole record reachable: x2/x3 ship unused)
```

**Common confusion** — "defaults are simpler for consumers" — simpler to *write* once, costlier to *maintain* (rename drift, grep death, single-unit shaking) — simplicity measured across the codebase lifetime, not the import line. "namespaces organize large APIs" — barrels + named imports organize without record-weight (namespace objects are grouping with costs; explicit barrels are grouping without them).

**Performance note** — named per-symbol shaking (smallest bundles); defaults shake as one unit; namespaces pin whole records — form choice has measurable bundle effects past library scale.

**Mentor note** — strong answers volunteer costs unprompted (refactor/grep/weight); probe with "what breaks when the team renames a default export?" (nothing compiles red — aliases persist stale) when candidates stop at syntax. Hiring signal: cost-aware import choices predict codebase stewardship.

**Cross-links** — forms → [1.1. import and export forms](<../1. ES Modules/1.1. import and export forms named default star re-export.md>); class exports → [1.1. Class duality](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>) (in 06).

### 2) **What does `import type` guarantee that plain `import` doesn't — and what enforces it?** (erasure + enforcement)

**Definition** — `import type` guarantees *full erasure* (zero bytes, zero load edges, zero bundler weight — toolchain-independent) where plain `import` of type-only names merely *may* elide (heuristics guessing per toolchain — correct usually, divergent occasionally). `verbatimModuleSyntax` enforces the distinction (TS1484 on guessing); dual-pipeline CI verifies it (tsc + stripping agree).

**What problem it solves / history** — value-syntax type imports created phantom runtime edges (weight, circular-load crashes, toolchain-divergent graphs) that `import type` deletes by construction — interviewers probe whether candidates know *both* halves (the guarantee *and* its enforcement), separating users (write it sometimes) from stewards (enforce it repo-wide).

**Modern guidance** — as of TypeScript 5.9 era, answer guarantee-first (erasure: bytes/edges/weight all zero, every toolchain), enforcement-second (`verbatimModuleSyntax` + lint + dual CI), elision-contrast third (heuristics guess, declarations state). Full treatment in [1.2. import type](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>).

**Runnable example** — stated vs guessed (multi-file sets):

```typescript
// file: t86.ts
export interface Item86 { sku: string }
// file: svc86.ts
import type { Item86 } from "./t86.js"; // stated (erased on every toolchain identically)
export function label86(i: Item86): string { return i.sku.toUpperCase(); }
// file: app86.ts
import { label86 } from "./svc86.js";
console.log(label86({ sku: "k" })); // K — zero type edges in emit (guaranteed, not guessed)
```

```typescript
// file: t87.ts
export interface Cfg87 { host: string }
// file: svc87.ts
// import { Cfg87 } from "./t87.js"; // error TS1484 under verbatimModuleSyntax (guessing refused)
import type { Cfg87 } from "./t87.js"; // stating (the flag rewards stating, punishes guessing)
export function host87(c: Cfg87): string { return c.host; }
// file: app87.ts
import { host87 } from "./svc87.js";
console.log(host87({ host: "h" })); // h — enforcement converted a habit into compiler behavior
// bad — elision-reliant imports (correct under tsc, divergent under esbuild — toolchain roulette)
```

```typescript
// file: a88.ts
import type { B88 } from "./b88.js"; // type-space cycle half (erased — never loads)
export interface A88 { b?: B88 }
// file: b88.ts
import type { A88 } from "./a88.js";
export interface B88 { a?: A88 }
console.log("cycle-free-by-erasure"); // compiles AND loads (no runtime cycle exists to break)
// bad — value-syntax type cycle (runtime edges circle: import-time undefined under some loaders)
```

**Common confusion** — "elision equals import type" — elision *guesses from usage* (drifts when usage evolves type-only; diverges across toolchains); `import type` *declares* (stable across edits and toolchains). "the flag is bureaucratic" — TS1484 *is* the erasability audit automated (each error a phantom edge deleted) — bureaucracy that compiles away incidents. "small repos don't need enforcement" — enforcement scales with zero human steps (hope scales with forgetting) — install at birth, not after incidents.

**Performance note** — erased edges zero everything (bytes/loads/graph); enforced discipline compounds (every import honest from authorship — no audit quarters needed).

**Mentor note** — ask "what enforces it?" after every correct `import type` answer — guarantee-without-enforcement is convention (decays); with enforcement it's compiler behavior (compounds). Hiring signal: enforcement answers (flag + lint + dual CI) predict stewardship.

**Cross-links** — type imports → [1.2. import type](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>); type/value spaces → [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>) (in 02).

### 3) **When is a namespace still the right tool — and what replaces it elsewhere?** (corners vs default)

**Definition** — namespaces survive in three corners: ambient foreign declarations (`.d.ts` mirrors — no emit, pure description), generated single-file output (codegen IIFE scopes — tool output, not hand code), deliberately non-erasable grouping with recorded reasons. Everywhere else (application source): ES modules (file scope, explicit imports, tree-shakeable, erasable).

**What problem it solves / history** — namespace absolutism ("never") deleted ambient/generated necessities; namespace nostalgia ("always worked") kept application grouping paying IIFE + erasure + shaking taxes. The corners-plus-default rule routes each case in seconds: corners recorded, application migrated — judgment concentrated, not spread.

**Modern guidance** — as of TypeScript 5.9 era, answer corners-first (ambient/generated/recorded — one example each), default-second (modules everywhere else), migration-third (namespace → module + barrel per directory, tests green). Full treatment in [2.1. Namespaces](<../2. Namespaces and Ambient Contexts/2.1. Namespaces organization and when to avoid.md>).

**Runnable example** — corner stays, habit migrates (multi-file sets):

```typescript
// file: app89.d.ts
declare namespace Foreign89 { const V: number } // corner (ambient foreign): stays, commented
// file: app89.ts
/// <reference path="./app89.d.ts" />
console.log("foreign-corner"); // foreign truth needs SOME typed home (this one)
// bad — namespace App { ... } in application source (IIFE + un-erasable + un-shakeable for module-doable grouping)
```

```typescript
// file: mod90.ts
export function twice(n: number): number { return n * 2; } // migrated (file scope groups)
// file: app90.ts
import { twice } from "./mod90.js";
console.log(twice(21).toFixed(0)); // 42 — identical behavior, erasable, shakeable (migration dividend)
// bad — export namespace Util { export function twice ... } (triple tax for zero unique benefit)
```

```typescript
// file: nested91.ts
export namespace Outer91 { export namespace Inner91 { export const X = 1; } } // deep nesting (dot-spelunking replaces graphs)
// file: app91.ts
import { Outer91 } from "./nested91.js";
console.log(Outer91.Inner91.X.toFixed(0)); // 1 — works; module paths (outer/inner files + imports) scale better
// bad — 4-level application namespaces as architecture (tangles where graphs compose)
// fix — one-module-per-concern + barrels (composition over dot-paths)
```

**Common confusion** — "lint bans ambient namespaces" — `no-namespace` allows `declare namespace` (foreign description survives by design) — configure, don't blanket-ban. "migration changes behavior" — values preserved (same functions, new paths) — only grouping changes. "cross-file merging works in modules" — exported namespaces are file-scoped (no cross-file merge inside modules!); merging works for global/ambient namespaces — the most surprising namespace fact, worth stating unprompted.

**Performance note** — migrated namespaces delete IIFEs (bytes + evaluation) and unlock per-symbol shaking — dividends compound per directory (measure bundle deltas per migration PR).

**Mentor note** — strong answers volunteer the non-merge surprise (exported namespaces don't merge across module files) unprompted — probe with "do same-named namespaces merge across files?" when candidates stop at corners. Hiring signal: merge-truth answers predict debugging skill, not just rule recall.

**Cross-links** — namespaces → [2.1. Namespaces](<../2. Namespaces and Ambient Contexts/2.1. Namespaces organization and when to avoid.md>); merging → [2.2. Declaration merging](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) (in 04).

### 4) **`declare module "pkg"` vs real `.d.ts` — which wins, and when do you delete the shim?** (resolution + deletion)

**Definition** — resolution order: bundled `pkg/*.d.ts` → `@types/pkg` → `paths` mappings → ambient `declare module` shims (first hit wins, silently). Real types always beat shims; shims serve only until arrival. Delete the shim the release upstream types land (green tsc post-deletion = clean handoff; new errors = masked drift surfacing productively — fix sites, never restore the shim).

**What problem it solves / history** — parallel maintenance (shim + real types coexisting) split truth visibly-shim vs invisibly-real (readers trusted the stale visible, checker used the real — worst-of-both debugging); never-deleting shims masked drift through upgrades (v1 shapes checking v2 calls). Deletion-on-arrival keeps one truth per package permanently — the cheapest invariant in dependency typing.

**Modern guidance** — as of TypeScript 5.9 era, answer order-first (bundled → @types → paths → shim), deletion-second (arrival = deletion PR + green-or-drift-triage), pinning-third (version + issue on every shim meanwhile). Full treatment in [2.3. Ambient modules](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>).

**Runnable example** — order decides, deletion cleans (multi-file sets):

```typescript
// file: shim92.d.ts
// targets fake-lib92@^1.0 (issue #92: delete when upstream ships types)
declare module "fake-lib92" {
  export function get(id: string): string; // pinned v1 truth (dated, linked, minimal)
}
// file: app92.ts
/// <reference path="./shim92.d.ts" />
import { get } from "fake-lib92";
console.log(get("a").toUpperCase()); // checked against pinned truth (bump → re-verify this file)
// upstream ships types → DELETE shim92.d.ts → green means agreement (single truth restored)
```

```typescript
// file: shim93.d.ts
// targets fake-lib93@^1.0 — STALE (upstream v2 changed get(id) to get(id, opts); shim still v1)
declare module "fake-lib93" {
  export function get(id: string): string; // fiction post-upgrade (v2 calls checked against v1 shapes)
}
// file: app93.ts
/// <reference path="./shim93.d.ts" />
import { get } from "fake-lib93";
console.log(get("a").length); // compiles against fiction (runtime v2 behaves differently — incident brewing)
// fix — re-verify on bump (extend-or-delete with diff evidence) or delete on arrival (real types surface drift as errors)
```

```typescript
// file: order94.ts
export const resOrder = ["bundled-dts", "at-types", "paths", "ambient-shim"] as const; // priority, memorized
console.log(resOrder.join(" > ")); // bundled-dts > at-types > paths > ambient-shim — first hit wins silently
// bad — editing the shim when real types exist (changes nothing — shim unconsumed; edit real source or reconfigure)
// fix — ls types/shims/ + npm outdated quarterly (arrivals = deletion PRs, pre-triaged)
```

**Common confusion** — "keeping shims is harmless backup" — harmless while agreeing (then redundant); harmful once drifting (visible-shim vs invisible-real split-brain debugging). "deletion risks breakage" — deletion *reveals* (errors = masked drift — productive); breakage pre-existed (masked). "order is configurable" — fixed priority (configurable *inputs*, never the *order*).

**Performance note** — deleted shims simplify resolution (one fewer candidate tier per import — trivially faster); single-truth debugging (one declaration per package, always the consulted one) is the real dividend.

**Mentor note** — ask "which wins — shim or bundled types?" before "when do you delete?" (order first, deletion second — sequence matters). Exercise: delete one long-kept shim and triage resulting errors (masked-drift receipt). Rule: shims carry TODO + issue + version pin, or fail review.

### 5) **What must a published package wire for types — and how do you verify it?** (wiring + proof)

**Definition** — wiring: generated declarations current + `exports` mapped per subpath with `types` conditions + top-level `types` fallback + support policy stated (`typesVersions` justified or absent deliberately). Proof: regenerate-diff clean + per-subpath strict smoke imports + triple-pipeline execution (tsc + bundler + stripping) — four gates from [3.3. Publishing types](<../3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>), automated and blocking.

**What problem it solves / history** — untyped-subpath releases (consumer `any`-infection), stale-declaration releases (fulfillment gaps), pipeline-specific releases (tsc-green/esbuild-red) each shipped green CI and broke consumers — hope-based releasing. Gate-based releasing converts each class into a blocking check: emit-current, mapped, triple-smoked, policy-stated — proof before publish, every release.

**Modern guidance** — as of TypeScript 5.9 era, answer wiring-first (four components), proof-second (four gates, automated), versioning-third (checklist grows with incident history — same playbook as 11's enum stamp). Full treatment in [3.3. Publishing types](<../3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>).

**Runnable example** — wired and proven (multi-file sets):

```typescript
// file: lib95.ts
export function total95(xs: number[]): number { return xs.reduce((a, b) => a + b, 0); }
// file: con95.ts
import { total95 } from "./lib95.js";
console.log(total95([1, 2]).toFixed(0)); // 3 — smoke import (same file, three pipelines in CI)
// tsc: typecheck — bundler: bundle (no const-enum/namespace traps) — stripping: execute (erasable syntax)
```

```typescript
// file: sub96.ts
export function feat96(): string { return "f"; }
// file: con96.ts
import { feat96 } from "./sub96.js"; // per-subpath smoke (every public path imported under strict tsc per release)
console.log(feat96().toUpperCase()); // F — subpath matrix: minutes per release, zero consumer infections
// bad — tsc-only CI (pipeline-specific breakage ships to bundler/stripping consumers undetected)
```

```typescript
// file: pol97.ts
export const rel = { minTS: "5.0", smoke: ["tsc", "esbuild", "strip"] } as const; // stated policy (auditable)
// file: con97.ts
import { rel } from "./pol97.js";
console.log(rel.smoke.join("+")); // tsc+esbuild+strip — gates named, run, blocking (not hoped)
// bad — unstated policy (minimum unknown, pipelines assumed — three unknowns compounding into release roulette)
```

**Common confusion** — "gates slow releases" — seconds automated (parallel emit + smoke) vs days per incident — automation inverts the speed argument permanently. "small packages skip gates" — gates scale with zero human steps (hope scales with forgetting) — install at birth. "green CI equals gates passing" — green means *configured* gates passed (audit presence, not color).

**Performance note** — gate runtime seconds (parallelizable); incident cost days + trust — cheapest release insurance in typed-package practice.

**Mentor note** — strong answers name all four gates unprompted (emit-current, mapped, triple-smoke, policy-stated); probe with "how do you verify subpaths?" (strict smoke matrix) when candidates stop at `types`. Hiring signal: proof-based releasing predicts stewardship.
