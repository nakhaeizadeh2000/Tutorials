## 6.1. Common interview QA — modules, namespaces and declaration files

Strong answers separate language semantics, compiler resolution and the actual
build or loader. Use the questions below to explain a decision and propose an
observable check. The small probes use TypeScript 7.0.2 and Node 20.20.2 in a
fresh directory without a tsconfig; bundling explicitly uses esbuild 0.28.2.

### 1) **How do named, default and namespace imports differ?**

A named import selects an exported name and may rename its local binding. A
default import selects the export named `default` with a chosen local name. A
namespace import supplies a namespace view of the module's exports. None of
these spellings alone establishes a bundle-size ranking or prevents aliases.

```typescript
// file: lib.mts
export function alpha(): string { return "__alpha__"; }
export function beta(): string { return "__beta__"; }
export default alpha;
// file: aliases.mts
import { alpha as first } from "./lib.mjs";
import main from "./lib.mjs";
import anotherName from "./lib.mjs";
import * as Lib from "./lib.mjs";
console.log(first === main, main === anotherName, Lib.default === first);
console.log(Lib.beta());
// file: static.mts
import * as Lib from "./lib.mjs";
console.log(Lib.alpha());
// file: reflected.mts
import * as Lib from "./lib.mjs";
console.log(Object.keys(Lib).sort().join(","));
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist aliases.mts static.mts reflected.mts
node dist/aliases.mjs
npm exec --yes --package=esbuild@0.28.2 -- esbuild static.mts --bundle --platform=node --format=esm --outfile=static-bundle.mjs
node static-bundle.mjs
npm exec --yes --package=esbuild@0.28.2 -- esbuild reflected.mts --bundle --platform=node --format=esm --outfile=reflected-bundle.mjs
node reflected-bundle.mjs
```

Aliases prints `true true true`, then `__beta__`. The static bundle prints
`__alpha__` and omits beta's unused implementation. The reflected bundle prints
`alpha,beta,default` and retains beta. Inspect the bundle text to find the
`__beta__` marker. A statically accessed namespace import therefore does not
necessarily retain every export. Reflection on the namespace requires more of
the exported surface in this example. The [esbuild tree-shaking reference](https://esbuild.github.io/api/#tree-shaking)
documents static namespace access and conservative side-effect analysis.

Choose an API convention for discoverability and consistency. Explain the actual
exports, uses, side effects and supported bundler before claiming a size benefit.
Both named and default imports can be locally aliased; refactoring behavior also
depends on editor support and the operation requested. The [import-forms owner](<../1. ES Modules/1.1. import and export forms named default star re-export.md>)
develops live bindings, captured defaults and barrels.

### 2) **What does import type establish, and what does verbatim checking add?**

A whole-statement type import supplies checker names without supplying runtime
bindings from that statement; TypeScript removes it from JavaScript output.
With `verbatimModuleSyntax`, marked type specifiers disappear while the remaining
runtime import syntax is preserved, subject to supported extension rewriting.
An inline-only `import { type Config }` can leave `import {}` and still evaluate
the dependency. An unmarked import of an interface is rejected with TS1484 under
this flag. The [official reference](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html)
shows these distinctions.

Follow-up: does this make a whole program cycle-free? No. Other value imports can
still create a cycle. Does it guarantee source execution succeeds? No. The loader
must still locate retained imports, and erased types do not install providers.
The [type-import project](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>)
checks emitted and native-source graphs and deliberately exposes a missing
output-extension target. The [module checkpoint](<../4. Important points to remember/4.1. Modules checklist mental models mentors insist on.md>)
asks the reader to predict fresh-process initialization for three entry points.

A good answer names the deployed artifact and inspects emitted imports. It does
not claim that every successful import-marker change saves bytes or that all
processors behave identically. If initialization matters, retain an intentional
runtime dependency rather than relying on an interface import to load code.

### 3) **Do same-named namespaces merge across files?**

First ask which declarations they belong to. Ordinary exported namespaces in two
different external modules are different exports and runtime objects. Global
script fragments can contribute to a shared namespace. An intentional module
augmentation can also extend an existing exported namespace's declarations;
“exported namespaces never merge across files” misses that distinct case.

This small augmentation extends the Config interface inside one module's Group.
It does not add a runtime label to the Group object:

```typescript
// file: group.mts
export namespace Group {
  export interface Config { enabled: boolean }
  export const version = 1;
}
// file: extend.mts
import "./group.mjs";
declare module "./group.mjs" {
  namespace Group { interface Config { label?: string } }
}
// file: use-group.mts
import "./extend.mjs";
import { Group } from "./group.mjs";
const config: Group.Config = { enabled: true, label: "local" };
console.log(Group.version, config.label, Object.hasOwn(Group, "label"));
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist group.mts extend.mts use-group.mts
node dist/use-group.mjs
```

The output is `1 local false`. Config is a checker interface; the config variable
is an ordinary object supplied by the consumer. Removing the extend import from
use-group and checking only use-group excludes the augmentation and rejects the
extra `label` property. Merely making an augmentation file a root input restores
its program-wide effect, even without importing it from that consumer.

This example intentionally includes a value-bearing namespace; it is rejected
by `erasableSyntaxOnly`. Prefer ordinary module exports for new application code
unless a concrete namespace contract is needed. Use the [namespace lesson](<../2. Namespaces and Ambient Contexts/2.1. Namespaces organization and when to avoid.md>)
for object identity, shared scripts and ambient providers, and [module augmentation](<../3. Declaration Files in Practice/3.2. Module augmentation at file scale.md>)
for declaration inclusion versus runtime loading. Migration must preserve the
required behavior; replacing a grouping syntax is not an identity guarantee.

### 4) **Does an ambient shim always lose to bundled declarations?**

No fixed priority list answers this. An included script-level `declare module
"pkg"` declares an ambient module; a module-scoped declaration of an existing
module can instead augment it. Resolver mode, metadata, mappings and declaration
inclusion affect which API the checker uses. A trace may locate a package file
while an included ambient declaration still supplies the consumer's effective
API. No declaration creates the implementation it describes.

Use the [ambient-module project](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>):
an included string shim lets a call check against a numeric JavaScript provider,
then that provider throws. Checking without the shim exposes the wrong call.
The augmentation variant retains existing overloads, which still does not make
new declared behavior exist in JavaScript. A good diagnosis inspects the included
declarations and actually runs the provider.

When upstream types arrive, test removing a redundant shim and compare the
resulting contract. A deliberate local augmentation may still be necessary.
Neither “keep every shim” nor “delete every shim immediately” replaces this check.

### 5) **What evidence supports a typed package release?**

State the supported compilers, resolvers, module formats and runtime entry points.
Build fresh artifacts, inspect a local tarball and install it into a separate
consumer. Check the consumer against the packed declarations and execute its
actual runtime imports. Cover documented public subpaths. For dual formats, verify
module-kind matching declarations and the relevant import/require conditions.

The [publishing project](<../3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
contains the complete package, consumers and observed negative checks. Missing
an explicit `types` condition can still resolve adjacent declarations; excluding
declarations from the tarball causes its strict consumers to report TS7016.
An unmapped package subpath is a different resolution failure. Top-level `types`
is not an unconditional recovery path after `exports` blocks an import.

Follow-up: does `typesVersions` establish old-compiler compatibility when modern
exports are used? The resolver can ignore it when reading `exports`; versioned
`types@...` conditions serve that path. Also test caller inference, not just
parsing: the legacy identity signature in the publishing project accepts older
syntax but loses fresh-array tuple inference without an explicit const argument.

Bundler and native-source tests are additional evidence for supported paths,
not a universal three-pipeline certificate. A Node source consumer outside
node_modules importing built JavaScript does not demonstrate that shipping raw
TypeScript dependencies works. A green build only covers the checks it ran.

### 6) **Common confusion**

A module namespace import is not a TypeScript `namespace` declaration. The former
views module exports; the latter can introduce an emitted grouping object or an
erased declaration context depending on its form. Likewise, extending an
interface inside a namespace does not create a matching runtime property.

Import spelling alone does not determine bundle size or load safety. The static
and reflected examples use the same namespace import form with different retained
exports. Determine which values are observed and when before estimating costs.

### 7) **Performance note**

The two bundles demonstrate declaration retention for esbuild 0.28.2, not a timing
benchmark or a universal optimization ranking. Side effects, reflection, module
format and build configuration affect removal. Type declarations and type-only
statements add no runtime validation, while the checker still processes them.
The runtime Group object remains in the namespace probe. No namespace migration,
compiler-speed or release-duration savings were measured.

### 8) **Mentor note**

Ask candidates to predict the alias identities, the two bundle contents and the
augmentation's `hasOwn` result, then explain the observations. Follow a correct
answer with a changed condition: namespace reflection, omitted augmentation or
missing packed declarations. A useful explanation identifies the boundary that
changed and a check that could refute the proposed diagnosis.

Prefer that evidence to memorized resolution ladders or a mandatory number of
CI gates. Keep the full implementation details in the linked owners; use this
interview checkpoint to assess whether the learner can connect them.
