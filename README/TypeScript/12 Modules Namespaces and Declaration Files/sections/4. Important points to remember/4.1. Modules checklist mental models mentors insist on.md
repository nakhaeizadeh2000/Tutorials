## 4.1. Modules checklist — mental models mentors insist on

A useful module review follows the program from source declarations to the
artifact that actually runs. Keep four questions connected: which names are
needed by the checker, which imports evaluate code, which external implementation
supplies ambient values, and which files a consumer receives?

This checkpoint integrates the preceding lessons with one small application.
Use TypeScript 7.0.2 and Node 20.20.2 in a fresh directory without a tsconfig.
Native source checks below explicitly use Node 22.18.0. No external runtime
package is needed.

### 1) **State the graph and its initialization contract**

Save these files. `contracts.mts` exports a type and has a visible side effect so
we can observe whether a runtime edge reaches it. The ambient declaration names
an optional global supplied by our setup module; it does not create that value.

```typescript
// file: contracts.mts
console.log("contract module evaluated");
export interface Config { mode: "dev" | "prod" }
// file: globals.d.ts
export {};
declare global { var __REVIEW_BUILD: string | undefined; }
// file: setup.mts
/// <reference path="./globals.d.ts" />
globalThis.__REVIEW_BUILD = "build42";
console.log("setup evaluated");
export {};
// file: service.mts
/// <reference path="./globals.d.ts" />
import type { Config } from "./contracts.mts";
export function describe(config: Config): string {
  return `${config.mode}:${globalThis.__REVIEW_BUILD ?? "missing"}`;
}
// file: app.mts
import "./setup.mts";
import { describe } from "./service.mts";
import type { Config } from "./contracts.mts";
const config: Config = { mode: "prod" };
console.log(describe(config));
// file: no-setup.mts
import { describe } from "./service.mts";
console.log(describe({ mode: "prod" }));
// file: inline.mts
import { type Config } from "./contracts.mts";
const config: Config = { mode: "dev" };
console.log("inline", config.mode);
```

The top-level `import type` statements supply no runtime dependency on contracts.
The bare setup import deliberately requests initialization. Under
`verbatimModuleSyntax`, the inline-only import in `inline.mts` becomes an empty
runtime import, so contracts still evaluates. A mixed import containing runtime
values and marked type specifiers is also legal; splitting every such import
into separate lines is not a correctness requirement. The
[verbatimModuleSyntax reference](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html)
documents these distinctions.

### 2) **Check the source and execute the intended artifact**

The `.mts` extensions explicitly select ESM. Relative source extensions are
rewritten for emitted JavaScript. Run each entry in a fresh process so previous
initialization cannot conceal a missing import:

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --verbatimModuleSyntax --erasableSyntaxOnly --rewriteRelativeImportExtensions --noEmitOnError --outDir dist app.mts no-setup.mts inline.mts
node dist/app.mjs
node dist/no-setup.mjs
node dist/inline.mjs
npm exec --yes --package=node@22.18.0 -- node app.mts
npm exec --yes --package=node@22.18.0 -- node no-setup.mts
npm exec --yes --package=node@22.18.0 -- node inline.mts
```

Both execution paths give these per-entry results:

| Entry | Output | Reason |
|---|---|---|
| app | `setup evaluated`, then `prod:build42` | Its setup import executes the provider. |
| no-setup | `prod:missing` | A declaration remains visible, but the provider never runs. |
| inline | `contract module evaluated`, then `inline dev` | Its retained empty import evaluates contracts. |

Inspect `dist/service.mjs`: the type import disappears while the function and
global read remain. Inspect `dist/inline.mjs`: the empty import names
`./contracts.mjs`. Neither the ambient global declaration nor the syntax flags
install setup. Here the missing provider has an explicit fallback; declaring the
global as an unconditional string would merely hide that possibility from callers.

For practice, change only app's `import type { Config }` to `import { Config }`.
The same checker command rejects it with TS1484. Restore the marker. Then try
`console.log(Config)` with the type-only import restored: it rejects this
interface-as-value use with TS2693. These diagnostics ask different questions:
how an import is marked and whether the referenced declaration has a value.

### 3) **Review changes against their real boundaries**

Type-only imports remove those statements' runtime edges. They do not prove that
the whole program has no value cycle: another value or side-effect import may
still connect the modules. Inspect the remaining graph and its initialization
requirements before applying a bulk import rewrite. The [type-import owner](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>)
develops source/output failures and the separate syntax restrictions.

Prefer explicit module dependencies for ordinary application code. A legacy
namespace can still embody shared-script assembly, a runtime grouping object or
an ambient description. Migrating it can change object identity, property
behavior, global scope and load order. Check those observed contracts rather than
assuming that a new module path preserves everything. The [namespace owner](<../2. Namespaces and Ambient Contexts/2.1. Namespaces organization and when to avoid.md>)
compares actual objects and shared-script loading; it owns the migration mechanics.

For an ambient declaration, identify the provider, the file that includes the
declaration and the code that loads the provider. If upstream declarations arrive,
remove a redundant shim in a controlled check and compare the selected API and
runtime behavior. Some local augmentations remain necessary. Mere arrival of a
new `.d.ts` is not evidence that every local declaration can be deleted. Follow
[ambient modules](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>)
and [augmentation scope](<../3. Declaration Files in Practice/3.2. Module augmentation at file scale.md>)
for the distinct replacement and augmentation cases.

For a library release, check the installed packed artifact rather than this
application's source graph. The [publishing project](<../3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
builds both module formats, installs a tarball and tests declarations, public
subpaths, runtime exports and compiler-version selection. Select additional
bundler or native-source checks from the support promise. Passing one checker,
one bundler and one runtime still establishes only those tested combinations.

### 4) **Common confusion**

An erasable program can still fail because an import names a missing file or an
initialization module was omitted. A type-only dependency still matters to the
checker even though its emitted import disappears. Conversely, writing a type
specifier inside an otherwise retained statement need not remove evaluation.
The three fresh-process entries above make these distinctions observable.

Generated declarations also remain descriptions. They can preserve an asserted
runtime lie, and a tarball can omit them altogether. Source checking, declaration
agreement, package contents and runtime behavior require appropriate evidence;
none is a synonym for the others.

### 5) **Performance note**

The removed type imports add no emitted runtime edge from those statements.
Required initialization still executes, and the checker still resolves the type
dependencies. This example measures no timing, bundle size or namespace migration
savings. A namespace's emitted code and a bundler's retention depend on its form,
usage and configuration. Preserve required behavior first, then measure the
actual build or startup problem rather than counting import lines.

### 6) **Mentor note**

Ask the learner to predict all three outputs before running them. If they expect
contracts to print from app, inspect its emitted imports. If they expect build42
from no-setup, ask which runtime edge installs that global. A sound answer follows
the executed graph and separates it from declaration inclusion.

Then give a release whose source gate passes but whose installed consumer fails.
Ask for the resolved declaration path and packed file list before accepting a
new assertion or shim. This tests whether the learner can transfer the graph
model to a package boundary rather than memorize a fixed number of release gates.
