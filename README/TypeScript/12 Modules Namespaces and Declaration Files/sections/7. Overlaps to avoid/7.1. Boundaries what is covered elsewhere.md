## 7.1. Boundaries — what is covered elsewhere

A module question can be about a declaration's meaning, the files visible to the checker, or the JavaScript loaded by a runtime. Identify the failing operation first. A missing export diagnostic, an absent runtime method and a broken emitted import can appear near the same import statement while needing different evidence. This lesson routes those questions to their existing owners; its practice uses observations from the linked worked lessons.

### 1) **Merging rules and file placement**

[declaration merging](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) owns compatible declarations, member conflicts and additive overloads. This domain applies those rules to [global augmentation](<../2. Namespaces and Ambient Contexts/2.2. declare global and global augmentation.md>), [ambient module declarations](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>) and [module augmentation at file scale](<../3. Declaration Files in Practice/3.2. Module augmentation at file scale.md>). Start with the declaration rule when two interface members disagree. Start with program inclusion and module identity when an otherwise valid augmentation is not visible to its consumer.

For example, adding a route to an interface can change what an object literal must satisfy. It does not install a runtime function. The complete merging project separates an included augmentation from the provider that supplies the described value. A checker-visible declaration with no provider can still leave the running consumer without that value. Diagnose these as two obligations: the declaration must participate in the checked program, and the required implementation must participate in the executed program.

A `declare module` block also needs the intended role. A declaration describing an untyped module and an augmentation of an existing module answer different questions. Use the ambient and augmentation owners to inspect file context, imports and target identity. Avoid replacing an unresolved import with an expansive `any` shim before establishing what the consumer actually loads; that can hide the mismatch rather than resolve it.

### 2) **Erasure and the executed module graph**

Use [type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) and [erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) to decide which syntax remains after processing. Use [execution paths](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) to choose a supported runner. Then apply [type imports and the executed source/output graph](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) to the graph that is actually executed. Syntax restrictions and import markers supply useful checks, but they do not prove that every runtime can locate every retained import.

The worked import lesson runs source `.mts` and emitted `.mjs` entry points under declared versions. An output-extension specifier can pass checking while failing native source resolution because the output file is absent beside the source. That observation tells you to inspect the consumed artifact and its destinations. It is not a reason to cast the imported value or disable unrelated strictness checks.

Whole-statement type imports and inline type specifiers also have different observed evaluation effects. The owner shows a whole `import type` disappearing and an inline-only import retaining an empty runtime import. A remaining value edge can still evaluate the dependency. Choose whether initialization is required before rewriting imports, then inspect the emitted graph and run the intended entry points. Do not infer universal startup or bundle savings from an import count.

### 3) **Declaration meaning and imported bindings**

[type and value spaces](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>) and [declaration spaces](<../../../02 The Type System Core/sections/2. The type vs value separation/2.2. Declaration spaces type value and namespace.md>) explain what a name can mean. [the type-query lesson](<../../../02 The Type System Core/sections/2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>) explains how a value's type can be captured without creating another runtime value. [class duality](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>) applies that distinction to a class's instance type and constructor value. Here, [import and export forms](<../1. ES Modules/1.1. import and export forms named default star re-export.md>) and [type imports and the executed source/output graph](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) carry the relevant bindings across files.

Ask what the importing code needs to do. An annotation can need a class's instance type while `new` needs its constructor value. A type-only import can support a checker query about an exported value without supplying that value to execution; the worked VERSION example prints a separate local value. The import form must support the operation, not merely resemble the export's spelling.

When a value import already supplies the class used for construction and annotation, a second aliased type import may serve readability or naming, but it is not automatically required. Conversely, an annotation-only consumer can state its dependency with `import type`. Keep the full space table in its owner and use this distinction to explain the actual imported operation. For `export =` or CommonJS consumption, follow [CommonJS interop](<../1. ES Modules/1.3. export equals and interop with CommonJS.md>) with its declared module mode instead of extending an ESM assumption to every package.

### 4) **Generics and queries across files**

Importing a generic declaration does not change the question its parameters answer. Use [generic scope](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>) to distinguish per-call and fixed container choices, [generic constraints](<../../../08 Generics Deep Dive/sections/2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) to justify the members a body can use, and [inference and NoInfer](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) when competing inputs or widened sources affect the inferred type. File placement belongs here; those relationships belong to their generic owners.

For an imported function whose return changes, deriving a consumer type from that declaration can avoid a hand-maintained copy of its signature. Follow [infer extraction](<../../../08 Generics Deep Dive/sections/2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) and [function and async utility pipelines](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>) for the extraction and unwrapping operations. Such a query still describes the declaration available to the checker. It cannot repair a stale declaration file or validate data returned by an incompatible implementation. Route those failures to declaration synchronization or [runtime boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) according to the failed operation.

Likewise, a producer/consumer assignment remains a variance question when its interface is imported. [the variance lesson](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.1. Variance in out annotations and generic positions.md>) owns the relevant positions and annotation limits. Do not redeclare a weaker local interface merely to make an assignment pass. Preserve the intended public contract and reproduce the source-to-target direction. Avoid claims that imports add no compiler cost or guarantee a particular cache entry; investigate an actual performance problem with measurements.

### 6) **Common confusion**

A declaration describes an implementation; it does not create one. An augmentation visible to the checker and a provider loaded by the runtime are separate pieces of evidence. A missing runtime function is therefore not resolved merely by making its property visible in a declaration file.

An erased type import removes that statement's runtime dependency, not every possible route to the module. An inline-only import may retain evaluation, and another value import can still load the same dependency. Inspect the graph before predicting initialization or cycles. A checker acceptance also does not prove runtime resolution: the source/output extension contrast provides a concrete counterexample.

Finally, importing a type does not turn its structural or generic relationship into a different type-system rule. Determine which declaration the checker resolved and then use the relevant shape, query or generic owner. Keep file resolution and assignment reasoning connected without treating them as interchangeable explanations.

### 7) **Performance note**

This routing lesson has no direct effect on runtime or compiler performance. A fully erased import statement contributes no runtime import from that statement, while retained dependencies can cause module evaluation. Startup and bundle effects depend on the remaining graph, side effects, build tools and runtime; this lesson contains no timing or bundle measurement.

Type-only dependencies can still require checker resolution and declaration processing. Generic and merging cost cannot be estimated reliably from the number of import statements or an assumed shared cache. Use [compiler measurement](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for observed diagnostics and traces, then [measured instantiation budgets](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) when type expansion is the identified problem. Repeated prose would create maintenance work; it would not itself add runtime checks to the learner's program.

### 8) **Mentor note**

Ask the learner to name the failing operation, choose its owner and describe the next observable check. Use these cases with the linked lessons' actual evidence:

1. **The checker sees a newly declared global function, but the consumer reports it missing.** Inspect the provider and its load path as well as declaration inclusion. The merging project removes the provider without removing the checker declaration, demonstrating why a declaration is not installation.
2. **An import passes checking but native source execution reports ERR_MODULE_NOT_FOUND.** Identify whether source or emitted JavaScript is executed and inspect the named file. The import owner reproduces an output-extension specifier whose output is absent beside the source. A sound answer chooses a consistent source/output import strategy and reruns that graph.
3. **The library's source gate passes, but the fresh consumer cannot find declarations.** Inspect the built tarball and its package entry points before changing the consumer's types. The native migration assessment reproduces a tarball missing declaration files while its runtime import still succeeds.

A good explanation includes both the owner and why its evidence addresses this operation. Redirect an answer that merely proposes another assertion, another flag or an `any` shim. For a tool crash, add which compiler interface it imports; for malformed external data, require a runtime parser. This keeps the review focused on a reproducible contract rather than a universal toolchain slogan.
