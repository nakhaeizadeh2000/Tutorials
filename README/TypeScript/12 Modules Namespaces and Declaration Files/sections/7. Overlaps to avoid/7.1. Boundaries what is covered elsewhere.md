### 1) **Declaration merging mechanics** (interface merging, class/namespace rules, augmentation examples) — [04 Objects, Interfaces and Type Aliases](<../../../04 Objects Interfaces and Type Aliases/README.md>)

**What problem it solves / history** — 04 owns "what merges with what?"; 12 owns "where do merges live at file scale (ambient files, augmentation files, globals)?" — mechanics vs placement, composed at every `declare module` block (04's rules deciding legality, 12's placement deciding blast radius).

**Modern guidance** — for merge legality (can X merge with Y? what conflicts?) start at 04/2.2; for merge placement (ambient vs local, shim vs augmentation, global vs module) stay here ([2.2. declare global](<../2. Namespaces and Ambient Contexts/2.2. declare global and global augmentation.md>), [2.3. Ambient modules](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>), [3.2. Module augmentation](<../3. Declaration Files in Practice/3.2. Module augmentation at file scale.md>)).

**Runnable example** — 04 rules, 12 placement (multi-file sets):

```typescript
// file: base98.ts
export interface Cfg98 { host: string } // 04 owns whether interfaces merge (yes, same-named)
// file: aug98.ts
import "./base98.js"; // side-effect attachment (12 owns placement: attach before augmenting)
declare module "./base98.js" {
  interface Cfg98 { port?: number } // 04 rules allow (identical-kind merge); 12 placement scopes it
}
// file: app98.ts
import type { Cfg98 } from "./base98.js";
const c: Cfg98 = { host: "h" }; // merged surface usable (mechanics 04, placement 12, composed)
console.log(c.host.toUpperCase()); // H — rule (04) plus placement (12) in one augmentation
```

```typescript
// file: standalone.ts
export interface Solo { a: string } // merge mechanics question? → 04/2.2 (not here)
// file: app99.ts
import type { Solo } from "./standalone.js";
const s: Solo = { a: "x" };
console.log(s.a); // x — placement questions (ambient? local? global?) → 12 (this domain)
// bad — asking 12 whether type aliases merge (04 owns the answer: never — use interfaces)
```

```typescript
// file: dual100.ts
export function f(): string { return "f"; }
// file: app100.ts

console.log(f().toUpperCase()); // F — no merging involved (mechanics and placement both trivial here)
// bad — merging where composition fits better (namespaces/interfaces merged for grouping that modules+imports express)
// fix — 04 decides legality, 12 decides placement, both defer to modules where modules fit (see 2.1 promise 3)
```

**Common confusion** — "12 replaces 04/2.2" — 12 *applies* merging at file scale; the legality table (what merges, conflict rules) stays in 04 — application vs reference differ. "augmentation examples live in both" — 04's examples teach *mechanics* (small, focused); 12's teach *practice* (blast radius, versioning, exits) — same syntax, different lessons.

**Performance note** — no overlap means no duplicated guidance — mechanics (04) and placement (12) each measure their own costs (merge caching vs resolution tiers).

**Mentor note** — route "can X merge?" to 04 and "where should this merge live?" here — the question's verb (can vs where) picks the domain, every time.

**What problem it solves / history** — 01 owns "which syntax survives stripping?"; 12 owns "how do imports stay stripping-safe?" — inventory vs application, composed at every `import type` (01's rule justifying, 12's form implementing).

**Modern guidance** — for flag semantics and pipeline behavior start at 01/3.2–3.3; for import-level erasability stay here ([1.2. import type](<../1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>)).

**Runnable example** — 01 inventory, 12 application (multi-file sets):

```typescript

// file: app101.ts

```

```typescript
// file: pipe.ts
export function runPipe(): string { return "ran"; } // pipeline-agnostic code (runs under tsc/bundlers/stripping alike)
// file: app102.ts
```

**Common confusion** — "12 owns erasability" — 12 *applies* the inventory to imports; the inventory (all features) and pipelines (all toolchains) stay in 01 — application vs reference differ. "trio-clean is 12-specific" — the trio spans 01 (flags), 11 (enums), and 12 (imports) — 12 owns its third, references the rest.

**Performance note** — stripping runtimes start fastest on trio-clean code (01 guidance); import-type discipline shrinks bundles (12 guidance) — layers compose without double-counting.

**Mentor note** — read 01's inventory first (which features erase), then 12's import discipline (how traffic stays erasable) — reference before application, the same order as mechanism-before-application elsewhere.

### 3) **Type-vs-value spaces and class duality** (dual universes, dual exports, queries) — [02 The Type System Core](<../../../02 The Type System Core/README.md>) + [06 Classes and Object-Oriented Types](<../../../06 Classes and Object-Oriented Types/README.md>)

**Definition** — dual universes (type space vs value space — why `import type` and value imports differ fundamentally) live in [02/2.1](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>); class dual exports (instance type + constructor value in one declaration) live in [06/1.1](<../../../06 Classes and Object-Oriented Types/sections/1. Class as type and value duality instance vs constructor.md>) — this domain *moved* both across file boundaries (type/value imports, dual class re-exports) without re-teaching duality itself.

**What problem it solves / history** — 02/06 own "what lives in which universe?"; 12 owns "how do universes travel between files?" (`import type` vs `import`, `export type` vs `export`, dual re-exports) — ontology vs transport, composed at every cross-file type reference.

**Modern guidance** — for universe questions (is X a type or value? can it be `typeof`-queried?) start at 02/2.1–2.3; for class duality (instance vs constructor exports) start at 06/1.1; for file transport stay here (1.1–1.2 import/export forms).

**Runnable example** — 02 ontology, 06 duality, 12 transport (multi-file sets):

```typescript
// file: dual104.ts
export class Widget { constructor(public w: number) {} } // 06: dual declaration (type + value in one)
// file: app104.ts
import { Widget } from "./dual104.js"; // 12: value transport (constructor crosses files)
import type { Widget as WType } from "./dual104.js"; // 12: type transport (instance type crosses separately)
const w: WType = new Widget(3);
console.log(w.w.toFixed(0)); // 3 — duality (06) transported per universe (12) per ontology (02)
```

```typescript
// file: q105.ts
export const SIZE = 4;
export type Size = typeof SIZE; // 02: typeof-query bridging value to type (same-file ontology)
// file: app105.ts
import { SIZE } from "./q105.js";
import type { Size } from "./q105.js"; // 12: each universe transported by its own syntax
const s: Size = SIZE;
console.log(s.toFixed(0)); // 4 — query (02) transported (12), universes matched throughout
// bad — import { Size } (value-syntax import of a pure type: TS1484 under verbatimModuleSyntax)
```

```typescript
// file: spaces.ts
export interface Iface { a: string } // type-space only (erases fully)
export const VAL = 1; // value-space only (persists fully)
// file: app106.ts
import type { Iface } from "./spaces.js";
import { VAL } from "./spaces.js"; // universe-matched traffic (02 ontology → 12 transport, mechanically)
// fix — mismatched traffic (import { Iface } under verbatim: TS1484; import type { VAL }: TS1361-ish refusal)
console.log(VAL.toFixed(0)); // 1 — matched universes, zero guessing
```

**Common confusion** — "12 replaces 02/2.x" — 12 *transports* across files; 02 *defines* the universes (spaces, queries, duality of meaning) — transport vs ontology differ. "dual imports are redundant" — value and type bindings serve different positions (constructor calls vs annotations) — importing both is precision, not duplication (each universe explicitly sourced).

**Performance note** — universe-matched traffic erases maximally (types vanish, values persist minimally) — the bundle/startup dividend of getting transport right, measured per 1.2's guidance.

**Mentor note** — ask "type or value?" (02) before "import or import type?" (12) — ontology before transport, every time. Exercise: classify ten cross-file names by universe, then fix their import syntax — ontology drill with transport payoff.

**Cross-links** — type/value spaces → [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. ### 4) **Generic inference over imported types** (constraints, `infer`, variance across boundaries) — [08 Generics Deep Dive](<../../../08 Generics Deep Dive/README.md>)

**Definition** — type-parameter mechanics (sites, inference, constraints, defaults, `infer` extraction, `in`/`out` variance, recursion) live in 08 — this domain *imported* generic types (constraints referencing imported interfaces, `infer` over imported function types, variance across package boundaries) without re-teaching any mechanic.

**What problem it solves / history** — 08 owns "how do parameters behave?"; 12 owns "how do parameterized types cross files?" (imported constraints, generic re-exports, variance-safe public generics) — mechanics vs transport, composed at every generic boundary crossing a file edge.

**Modern guidance** — for parameter questions (scope, constraint design, variance annotation) start at the relevant 08 leaf; for cross-file generic transport stay here (import constraints by name, re-export generic aliases explicitly, annotate variance on public interfaces per 08/3.1).

**Runnable example** — 08 mechanics, 12 transport (multi-file sets):

```typescript
// file: constraints107.ts
export interface Named { name: string } // constraint source (08 mechanics apply to it elsewhere)
// file: greeters.ts
import type { Named } from "./constraints107.js"; // 12: constraint transported by name
export function greet<T extends Named>(x: T): string { return x.name.toUpperCase(); } // 08: mechanic applied
// file: app107.ts
import { greet } from "./greeters.js";
console.log(greet({ name: "ada", extra: 1 })); // ADA — transported constraint (12) constraining inference (08)
```

```typescript
// file: fns108.ts
export function fetchAge(id: string): Promise<number> { void id; return Promise.resolve(36); }
// file: meta108.ts
import type { fetchAge } from "./fns108.js"; // 12: function type transported (typeof-queryable)
export type Age = Awaited<ReturnType<typeof fetchAge>>; // 08/09: infer pipeline over the imported type
// file: app108.ts
import type { Age } from "./meta108.js";
const a: Age = 36;
console.log(a.toFixed(0)); // 36 — transport (12) feeding extraction (08) feeding use
// bad — re-deriving fetchAge's signature locally (mirror drift: source evolves, mirror rots)
```

```typescript
// file: sources.ts
export interface Source<out T> { read(): T } // 08: variance annotated (producer contract)
// file: app109.ts
import type { Source } from "./sources.js"; // 12: generic interface transported (variance travels with it)
const s: Source<string> = { read: () => "hi" };
console.log(s.read().toUpperCase()); // HI — annotated variance (08) crossing files (12) intact
// bad — widening imported generics to any at boundaries (variance/container precision surrendered per crossing)
```

**Common confusion** — "imported generics re-instantiate" — transported *declarations* instantiate at *use* (same caching, same variance — files don't reset generics). "variance needs redeclaration per file" — variance annotates the *declaration* (08/3.1) once; importers inherit it with the type — transport preserves, never re-declares. "constraints must be local" — imported constraints work identically (name resolution crosses files transparently) — locality is organizational, never semantic.

**Performance note** — generic instantiation caches program-wide (transported or local — one entry per argument tuple); cross-file generics cost nothing beyond same-file (names resolve once, cache shared).

**Mentor note** — trace one generic from declaration file through import to instantiation (three files, one parameter) — transport transparency made visible. Rule: generic questions route to 08 (mechanics), transport questions stay here (12).
