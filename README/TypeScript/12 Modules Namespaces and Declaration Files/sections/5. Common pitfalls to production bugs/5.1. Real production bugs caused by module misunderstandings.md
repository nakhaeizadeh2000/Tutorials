## 5.1. Module failure modes reproduced locally

A module problem can appear during checking, package resolution or evaluation.
Reproduce the failing entry point before changing import syntax. These are local
experiments, not reports of particular production incidents. Use TypeScript
7.0.2 and Node 20.20.2 in fresh directories without a tsconfig. The bundler
comparison explicitly uses esbuild 0.28.2.

### 1) **A barrel cycle with different entry-point outcomes**

Save these three files in `cycle`. Base exports a factory that needs Admin, and
Admin extends Base. Both files import through the public barrel, creating a
runtime loop. The type checker accepts this graph.

```typescript
// file: cycle/base.mts
import { Admin } from "./index.mjs";
export class Base { kind(): string { return "base"; } }
export function createAdmin(): Admin { return new Admin(); }
// file: cycle/admin.mts
import { Base } from "./index.mjs";
export class Admin extends Base { override kind(): string { return "admin"; } }
// file: cycle/index.mts
export { Base, createAdmin } from "./base.mjs";
export { Admin } from "./admin.mjs";
```

Run from `cycle`, with each entry in a fresh Node process:

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist base.mts admin.mts index.mts
node --input-type=module -e 'import {createAdmin} from "./dist/index.mjs"; console.log(createAdmin().kind())'
# Expected failure:
node --input-type=module -e 'import {createAdmin} from "./dist/base.mjs"; console.log(createAdmin().kind())'
```

The barrel entry prints `admin`. Starting from base instead throws
`ReferenceError: Cannot access 'Base' before initialization`. From that entry,
base must evaluate its barrel dependency, which reaches admin while base's class
binding is still uninitialized. Evaluating `extends Base` reads that binding too
early. From the barrel entry, base finishes defining its class before admin
needs it. Merely defining createAdmin does not call its body.

This is not a general claim that every cycle fails or that every entry-order
change causes a failure. The eager read and this graph explain these results.
It is also not necessarily an `undefined` property: native ESM class bindings
have an uninitialized state before evaluation reaches their declaration.

For a CommonJS comparison, copy the three source files into a fresh `cjs`
directory, change their extensions to `.ts` and every `.mjs` specifier to `.js`.
Compile and run there:

```sh
tsc --strict --target es2022 --module commonjs --verbatimModuleSyntax false --noEmitOnError --outDir dist base.ts admin.ts index.ts
node -e 'const {createAdmin}=require("./dist/index.js"); console.log(createAdmin().kind())'
# Expected failure:
node -e 'const {createAdmin}=require("./dist/base.js"); console.log(createAdmin().kind())'
```

The first prints `admin`; the second throws `TypeError: Class extends value
undefined`. This emitted CommonJS graph encounters an unfinished export object,
whereas the ESM graph reads an uninitialized binding. Diagnose the loader and
output that actually failed rather than transplanting an error message from
another module system. Node documents the [unfinished-export behavior](https://nodejs.org/api/modules.html#cycles) of CommonJS cycles; the commands above verify it under the declared Node 20 baseline.

### 2) **Break the loop rather than rename the imports**

In a separate `repaired` directory, move the factory out of base. The composition
module may depend on Admin; Base no longer depends on its subclass or barrel.

```typescript
// file: repaired/base.mts
export class Base { kind(): string { return "base"; } }
// file: repaired/admin.mts
import { Base } from "./base.mjs";
export class Admin extends Base { override kind(): string { return "admin"; } }
// file: repaired/factory.mts
import { Admin } from "./admin.mjs";
export function createAdmin(): Admin { return new Admin(); }
// file: repaired/index.mts
export { Base } from "./base.mjs";
export { Admin } from "./admin.mjs";
export { createAdmin } from "./factory.mjs";
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist base.mts admin.mts factory.mts index.mts
node --input-type=module -e 'import {createAdmin} from "./dist/index.mjs"; console.log(createAdmin().kind())'
node --input-type=module -e 'import {createAdmin} from "./dist/factory.mjs"; console.log(createAdmin().kind())'
```

Both print `admin`. Direct imports make these dependencies easier to see, but
they do not inherently prevent cycles. Keeping Base's import of Admin while
changing it to a direct file import would still leave a value loop. Here the
repair changes the dependency direction by extracting composition. An interface
and type-only dependency are alternatives when no runtime class reference is
needed; an `extends` expression still needs an actual constructor.

### 3) **An erased import does not perform plugin registration**

Save these files in `registration`. Setup registers a handler while its module
body evaluates. The app imports only its interface using unmarked syntax; the
registry itself has a separate value import.

```typescript
// file: registration/registry.mts
export const handlers = new Map<string, () => string>();
// file: registration/setup.mts
import { handlers } from "./registry.mjs";
handlers.set("alpha", () => "ready");
export interface Plugin { name: string }
// file: registration/app.mts
import { Plugin } from "./setup.mjs";
import { handlers } from "./registry.mjs";
const plugin: Plugin = { name: "alpha" };
console.log(handlers.has(plugin.name), handlers.get(plugin.name)?.() ?? "missing");
```

Run from `registration`. Disabling verbatim mode here is an experiment exposing
elision, not the proposed application configuration:

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --verbatimModuleSyntax false --noEmitOnError --outDir dist app.mts
node dist/app.mjs
npm exec --yes --package=esbuild@0.28.2 -- esbuild app.mts --bundle --platform=node --format=esm --outfile=bundle.mjs
node bundle.mjs
# Expected checker failure TS1484:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --verbatimModuleSyntax --noEmit app.mts
```

Both emitted and bundled executions print `false missing`: both tested processors
remove this type-only import. There is no demonstrated tsc-versus-esbuild
registration difference here. Enabling verbatim checking instead reports the
unmarked interface import. The [official option reference](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html)
explains why elision can remove a module's side effects.

Repair app by replacing its first import with these two statements:

```typescript
import "./setup.mjs";
import type { Plugin } from "./setup.mjs";
```

Rebuild with `--verbatimModuleSyntax` enabled, run the emitted app, then repeat
the bundle and run. Both print `true ready`. Changing only the original import
to `import type` still prints `false missing`: stating type traffic correctly
does not request initialization. A necessary bare import states that request.
Bundler side-effect metadata and optimization can also affect retention, so test
the supported build configuration rather than promising retention under every
possible tool setting.

### 4) **Separate declaration, package and provider failures**

Two other failures need different evidence from a cycle or missing registration:

| Symptom | Reproduction and next check |
|---|---|
| Calls check against a local shim but fail against the real package | The [ambient-module project](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>) includes a wrong string signature over a numeric implementation. Check declaration context, inclusion and provider behavior; do not assume bundled types always override an included ambient module. |
| Source checks but an installed public subpath lacks declarations | The [packed-package project](<../3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) packs a JavaScript-only variant, installs it and gets TS7016 from strict consumers. Inspect the tarball and resolved declaration path. |

Use those owners' complete fixtures to reproduce the failures. A local relative
source import does not test an installed package's export map. Missing an explicit
`types` condition is not sufficient evidence of missing declarations: the packed
project also checks adjacent declaration substitution successfully. An unmapped
package subpath instead fails package resolution. Adding a blanket ambient shim
can hide missing types without fixing either the package or implementation.

When replacing a local shim with upstream types, remove it in a controlled
consumer check and compare accepted calls and real runtime results. When an
augmentation is still required, retain its deliberate additions. Neither a
lockfile nor a version comment verifies a handwritten API contract.

### 5) **Common confusion**

A barrel participates in the graph even when it contains only re-exports. The
problem above is an eager constructor read in a loop, not the presence of an
index filename. The checker resolving all declarations does not mean that their
runtime bindings have finished initialization.

A type-only import and a side-effect import answer different questions. Marking
Plugin correctly fixes the syntax diagnostic; loading setup fixes registration.
Likewise, suppressing TS7016 does not add declarations to a tarball. Choose the
repair for the observed failing operation.

### 6) **Performance note**

These experiments establish outputs and failures, not startup timings or CI cost.
Removing a required initialization edge can appear to save evaluation while
breaking behavior. Type-only statements erase but still require checker work.
Cycles and barrels do not have a fixed byte, memory or latency penalty derived
from their count; measure the actual graph and build when performance is at issue.

### 7) **Mentor note**

Have the learner draw base, admin and the barrel as a dependency graph, then mark
the `extends` read. Ask why one entry passes and the other fails in fresh
processes. Accept an explanation that follows evaluation and initialization;
redirect a blanket “barrels are bad” answer toward the actual loop.

For registration, ask them to fix TS1484 and recover `true ready` as separate
steps. For packaging, ask which artifact the consumer checks. A useful regression
check asserts the intended behavior at the failed boundary instead of merely
checking that compilation finishes.
