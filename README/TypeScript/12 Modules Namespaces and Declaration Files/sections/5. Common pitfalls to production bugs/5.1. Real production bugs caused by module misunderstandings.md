## 5.1. Real production bugs caused by module misunderstandings

### 1) **Barrel re-export cycle crashed at import time** (`export *` ping-pong, `undefined` extended)

**Definition** — two barrels (`users/index` re-exporting `./roles`, `roles/index` re-exporting `../users`) formed an initialization cycle: `class Admin extends Base` evaluated while `Base` (mid-cycle, uninitialized) was still `undefined` — `TypeError: Class extends value undefined` at import time, crashing 100% of loads that touched either barrel first. The cycle was invisible in source (each file imported from a *barrel*, never directly) — only the initialization graph looped.

**What problem it solves / history** — barrel-everywhere conventions (`export *` per directory, all traffic through indexes) maximized cycle surface: every re-export an edge reviewers stopped seeing, every barrel a hub concentrating edges. The crash passed CI (test import order happened to initialize safely) and failed production (entry order differed) — order-dependent initialization, the worst kind of green-to-red gap.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), barrel per package surface only (explicit lists, never `export *` across internal boundaries); intra-package traffic imports relatively (direct files, no index hops); break base/derived cycles by depending on abstractions (interfaces via `import type` — type-space cycles are free — never value cycles). Detect with circular-dependency lint (`import/no-cycle`) in CI.

**Runnable example** — cycle vs direct graph (multi-file sets; cycle demo kept importable-safe):

```typescript
// file: base71.ts
export class Base { kind(): string { return "base"; } } // leaf (no imports — cycle impossible here)
// file: admin71.ts
import { Base } from "./base71.js"; // DIRECT import (not via barrel — no cycle surface added)
export class Admin extends Base { override kind(): string { return "admin"; } }
const a = new Admin();
console.log(a.kind()); // admin — direct graph: evaluation order follows imports exactly
```

```typescript
// file: roles72.ts
export class Role { constructor(public name: string) {} }
// file: users72.ts
import { Role } from "./roles72.js"; // direct (users → roles, one edge, acyclic)
export class User {
  constructor(public role: Role) {}
}
// file: app72.ts
import { User } from "./users72.js";
import { Role } from "./roles72.js";
console.log(new User(new Role("admin")).role.name.toUpperCase()); // ADMIN — acyclic by construction
// bad — users/index.ts: export * from "./users72"; roles/index.ts: export * from "./roles72" + users importing roles VIA roles/index (ping-pong: undefined Base at evaluation — order-dependent crash)
// fix — direct relative imports intra-package (barrels compose the PUBLIC surface only)
```

```typescript
// file: iface73.ts
export interface Shape { area(): number } // abstraction (type-only — cycle-free by construction)
// file: impl73.ts
import type { Shape } from "./iface73.js"; // type-space edge (erased — never participates in cycles)
export class Square implements Shape { constructor(public s: number) {} area(): number { return this.s ** 2; } }
// file: app73.ts
import { Square } from "./impl73.js";
console.log(new Square(3).area().toFixed(0)); // 9 — depend on abstractions (import type) to break value cycles
// bad — impl importing concrete factory from consumer module (value cycle: evaluation order decides crash-or-luck)
// fix — interface in the middle (type edge both ways legal), values flowing one way
```

**Common confusion** — "cycles crash deterministically" — crash depends on *entry order* (which module evaluates first — test entry vs production entry differ, hence green CI + red prod). "TypeScript detects cycles" — type-checks fine (types resolve regardless of evaluation order); *bundlers* warn (`import/no-cycle` lint, esbuild/vite cycle warnings) — enable the tooling, don't expect the checker. "barrels caused it, delete all barrels" — barrels *concentrate* edges (hubs); cycles need *loops* (A→B→A through barrels or direct) — keep package-surface barrels (explicit lists), delete intra-package barrel hops.

**Performance note** — cycles don't just risk crashes (partially-initialized live bindings read as `undefined` *without* throwing in property positions — silent corruption); acyclic graphs evaluate once per module in static order (predictable startup). `import type` edges cost zero evaluation (erased — cycle-free by construction).

**Mentor note** — reorder two test imports to flip entry order and watch green↔red flip (order-dependence demonstrated, not theorized). Exercise: run `import/no-cycle` on the repo and triage each loop (direct-import rewrite or interface extraction per loop) — the cycle backlog made countable. Gate: new barrel-to-barrel edges fail review.

### 2) **Stripped type import executed a side effect that never ran** (value import elided as type-only)

**Definition** — `import { init } from "./setup"` where `init` was used *only in type positions* got elided under `importsNotUsedAsValues` heuristics (tsc judged it type-only and deleted the import) — but `./setup`'s module body *registered* the plugin as a side effect of evaluation. Production (tsc-emit) skipped registration (import deleted → module never loaded); tests (esbuild, preserving the import) registered fine — behavior diverging by toolchain, green tests, broken prod.

**What problem it solves / history** — elision heuristics decide emit from *usage analysis* (used as type → delete import) while side effects live in *module evaluation* (deleted import = skipped body) — the two concerns collide exactly when a value import is consumed type-only *but* its module must load. `verbatimModuleSyntax` + explicit side-effect imports (`import "./setup"`) separate the concerns: types via `import type` (always erased), loading via bare imports (always kept) — no guessing on either axis.

**Modern guidance** — as of TypeScript 5.9 era, import registration/side-effect modules with bare `import "./setup"` (kept verbatim under every setting); import their *types* with `import type` (erased everywhere); enable `verbatimModuleSyntax` so the compiler (not heuristics) arbitrates. Never rely on value imports for side effects *and* types simultaneously (one statement, two jobs — the collision this incident classes).

**Runnable example** — loading separated from typing (multi-file sets):

```typescript
// file: setup74.ts
console.log("setup evaluated");
export interface Plugin { name: string }
// file: app74.ts
import "./setup74.js"; // BARE import (side effect kept verbatim — registration runs on every toolchain)
import type { Plugin } from "./setup74.js"; // type traffic (erased — zero weight, zero guessing)
const p: Plugin = { name: "x" };
console.log(p.name.toUpperCase()); // X (+ "setup evaluated" printed exactly once, everywhere)
// bad — import { Plugin } from "./setup74.js" (used type-only → elided by tsc heuristics → setup never evaluates → registration skipped silently in prod, kept under esbuild)
```

```typescript
// file: setup75.ts
export const registry: string[] = [];
console.log("registry module loaded");
// file: app75.ts
import "./setup75.js"; // kept (verbatim — evaluation guaranteed regardless of usage analysis)
import type {} from "./setup75.js"; // (no types needed here — bare import alone states "load me")
import { registry } from "./setup75.js"; // value use (also keeps — belt and suspenders, both honest)
registry.push("a");
console.log(registry.length); // 1 — module evaluated (bare import guarantees, value use reinforces)
// bad — type-only consumption of a side-effect module (elision deletes the load the app needed)
```

```typescript
// file: setup76.ts
export interface Cfg76 { v: number }
// file: app76.ts
import type { Cfg76 } from "./setup76.js"; // pure types, no side effects in setup76 (erasure total and safe)
const c: Cfg76 = { v: 1 };
console.log(c.v.toFixed(0)); // 1 — side-effect-free modules erase cleanly (the safe case, stated explicitly)
// bad — assuming side-effect-freedom (one console.log added later to setup76 silently changes elision behavior under heuristics)
// fix — verbatimModuleSyntax: stated imports never reinterpret when module bodies evolve
```

**Common confusion** — "side-effect imports are code smell" — registration/plugin/polyfill modules *are* side effects by design (their evaluation *is* the API) — bare imports state the design honestly. "bundlers handle this automatically" — bundlers preserve what tsc *emits* (elided imports never reach the bundler — the toolchain split *is* the incident; verbatim emit unifies it). "one import can serve both jobs" — value+type dual-use imports are exactly what heuristics misjudge (usage evolves type-only over time — elision flips silently on an unrelated edit).

**Performance note** — bare imports cost the module's evaluation (intended — registration runs); `import type` costs zero (erased) — stating both separately pays each cost exactly once, visibly. Heuristic elision "saved" the evaluation cost by *breaking* the app — the most expensive optimization in this domain's ledger.

**Mentor note** — delete a bare side-effect import and watch registration vanish (then restore it) — load-vs-type separation in one deletion. Exercise: grep value imports used type-only in modules with side effects (the elision-risk set) and split each into bare + `import type` — the at-risk list is the incident backlog, pre-triaged.

### 3) **Ambient shim hid a real breaking update** (v1 shapes pinned, v2 runtime arrived unchecked)

**Definition** — a `declare module "api-lib"` shim (hand-typed v1: `get(id): string`) stayed after the library shipped v2 (`get(id, opts)` + real bundled types) — resolution kept consulting… no wait, real types *beat* shims (see 2.3 promise 3). The incident variant is worse: the package shipped *no* types (untyped v2), so the v1 shim stayed authoritative — every v2 call checked against v1 shapes (new required `opts` invisible, changed returns unmodeled) while runtime behaved v2 — full checking against a fiction.

**What problem it solves / history** — shims pin *a version's* truth without versioning (no range, no checksum, no expiry — a v1 photograph consulted during v2). Dependency bumps never re-examined shims (lockfile changed, `.d.ts` didn't — no tool links the two). The fix links them procedurally: shim files carry version pins + upstream issues, and dep-bump checklists include shim re-verification (bump → read shim → still true? → keep, else extend-or-delete).

**Modern guidance** — as of TypeScript 5.9 era, pin every shim (`// targets api-lib@^1.4 (issue #…, re-verify on bump)`); re-verify shims on every dependency bump (diff runtime behavior notes vs shim signatures — 10 minutes per bump); prefer upstream types the release they land (delete shim, fix surfaced drift — the honest signal from 2.3 promise 3). Never bump major versions without reading the shim directory (the review step that would have caught this class entirely).

**Runnable example** — pinned shims, verified bumps (multi-file sets):

```typescript
// file: shim77.d.ts
// targets fake-api@^1.0 (issue #7: re-verify on every bump — upstream may ship types or break shapes)
declare module "fake-api" {
  export function get(id: string): string; // v1 truth (pinned, dated, linked)
}
// file: app77.ts
/// <reference path="./shim77.d.ts" />
import { get } from "fake-api";
console.log(get("a").toUpperCase()); // checked against PINNED v1 truth (bump to v2 → re-verify this file first)
// bad — unpinned shim (no version, no issue, no owner: v2 arrives, v1 shapes check v2 calls, nobody re-examines)
```

```typescript
// file: shim78.d.ts
// targets fake-api2@^2.0 — VERIFIED post-bump (v2 added opts; shim extended deliberately, still no upstream types)
declare module "fake-api2" {
  export function get(id: string, opts?: { raw: boolean }): string; // extended on bump (documented drift tracking)
}
// file: app78.ts
/// <reference path="./shim78.d.ts" />
import { get } from "fake-api2";
console.log(get("a", { raw: true }).toLowerCase()); // v2 shape checked (bump discipline working)
// bad — bump without reading shims (lockfile v2, declarations v1: every call checked against fiction — zero diagnostics)
```

```typescript
// file: shim79.d.ts
// targets fake-api3@^3.0 — upstream SHIPPED types in 3.0 (DELETE this file — real beats shim per 2.3 promise 3)
// (file deleted on upgrade — shown here as documentation of the deletion event, not as live text)
// file: app79.ts
console.log("shim-deleted-post-arrival"); // consumers now check against bundled real types (single truth restored)
// bad — keeping shim79 "just in case" (parallel truths: readers trust visible-shim, checker uses invisible-real — worst-of-both debugging)
// fix — delete on arrival (green tsc post-deletion = clean handoff; errors = masked drift surfacing productively)
```

**Common confusion** — "lockfiles cover shims" — lockfiles pin *code* (resolved versions); shims pin *beliefs about code* (hand-typed shapes) — beliefs need their own pins (version comments + issues) because no tool derives them. "bump CI catches drift" — CI checks *against the shim* (fiction self-consistent — green by construction); drift surfaces only via runtime failures or contract tests (the missing verification layer shims need). "deleting shims risks breakage" — deletion *reveals* (errors = drift masked — fix sites productively); breakage pre-existed (masked).

**Performance note** — shim audits cost minutes per bump (read + verify + extend-or-delete); un-audited shims cost v1-checked-v2-call incidents (days + customer impact) — highest-ROI minutes in dependency maintenance.

**Mentor note** — `ls types/shims/` beside `npm outdated` quarterly (each outdated entry with a shim = a verification task, pre-triaged). Exercise: bump one shimmed dep and re-verify its shim *before* merging (extend-or-delete with the diff as evidence) — the discipline in one PR.

### 4) **Missing `exports` types entry resolved to `any` for consumers** (untyped subpath, downstream infection)

**Definition** — a published subpath (`lib/stats`) with JS emit but no `types` condition (and no top-level `types` covering it) resolved consumer imports to *implicit `any`* (untyped module — `noImplicitAny` errors at the import, or worse, silent `any` where suppressed) — every downstream use unchecked, every consumer codebase infected through one missing map entry.

**What problem it solves / history** — `exports`-without-`types` (JS mapped, declarations forgotten) shipped "working" packages whose consumers lost checking on exactly the new subpaths (the feature the release advertised). Consumer `skipLibCheck`-adjacent suppressions and `declare module` workarounds then *localized* the infection permanently (workarounds outliving the fix). The publishing checklist (3.3 promise 3: mapped + smoke per subpath) prevents the class at the source.

**Modern guidance** — as of TypeScript 5.9 era, map `types` per exported subpath (no untyped public paths — the checklist gate); smoke-consume every subpath in release CI (tsc strict import per subpath — untyped paths fail the gate, not the customer); treat consumer `any`-reports on subpaths as P0 packaging bugs (checking lost at the boundary infects unbounded downstream code).

**Runnable example** — mapped subpaths check, unmapped infect (multi-file sets):

```typescript
// file: stats80.ts
export function mean(xs: number[]): number { return xs.reduce((a, b) => a + b, 0) / (xs.length || 1); }
// file: con80.ts
import { mean } from "./stats80.js"; // mapped-subpath equivalent (types travel with the path)
console.log(mean([1, 2, 3]).toFixed(0)); // 2 — checked import (types condition present in the map)
// bad — ./dist-stats-unmapped.js (JS emit, no types condition: consumer import resolves implicit any)
// fix — types per subpath (checklist gate 2): no public path without a types entry, ever
```

```typescript
// file: feat81.ts
export function feat(): string { return "f"; }
// file: con81.ts
import { feat } from "./feat81.js";
console.log(feat().toUpperCase()); // F — new-subpath smoke import (gate: every release imports every subpath under strict tsc)
// bad — releasing a subpath its own CI never imports (types missing/rotten — discovered by consumers, reported as any-bugs)
// fix — subpath smoke matrix (one strict import per public path per release — minutes of CI, zero consumer infections)
```

```typescript
// file: legacy82.ts
export const LEGACY = 1;
// file: con82.ts
import { LEGACY } from "./legacy82.js";
console.log(LEGACY.toFixed(0)); // 1 — legacy subpath WITH types (mapped deliberately, supported explicitly)
// bad — legacy subpath WITHOUT types (kept importable for compat, unchecked forever — infection vector with tenure)
// fix — type it (cheap — declarations exist) or remove it from exports (breaking, versioned honestly): never untyped-and-public
```

**Common confusion** — "`skipLibCheck` covers this" — `skipLibCheck` skips *checking declarations*, not *missing* ones (untyped subpath still resolves `any` — the flag is irrelevant to absent types). "consumers can declare the subpath themselves" — pushing packaging work onto every consumer (N shims for one missing entry — commons tragedy with extra steps). "deep filesystem imports work around it" — unmapped deep paths bypass encapsulation (support contracts on internals — the 3.3 promise-1 violation that compounds).

**Performance note** — typed subpaths check per import (cached once per consumer program); `any`-resolved subpaths skip checks (faster compile, unbounded incident surface) — speed-vs-safety inverted destructively; always choose checking.

**Mentor note** — import one unmapped subpath under strict tsc and read the implicit-`any` error (or worse, the silence where suppressed) — packaging bugs made visible in one import. Gate: release CI imports every public subpath under strict (the subpath smoke matrix — minutes per release, zero consumer infections).
