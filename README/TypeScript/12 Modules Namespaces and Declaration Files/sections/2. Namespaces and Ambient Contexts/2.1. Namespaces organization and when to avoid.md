## 2.1. Namespaces organization and when to avoid

A TypeScript namespace groups exported names under a qualified name. Its runtime declarations can produce an ordinary object and initialization code. A namespace containing only types, or an ambient namespace describing a provider, has a different output contract. The file's scope also matters: same-named namespaces in two separate modules do not merge merely because both files are loaded.

For new application organization, file modules usually give a clearer dependency graph without another wrapper. Namespaces can still describe global APIs or attach related declarations to an exported entity. Choose from the public shape, loader and existing consumers rather than assuming every namespace emits or every replacement is behavior-identical.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Create separate fresh directories for each named project below, with no tsconfig.json or dependencies. Split the fences at file markers. Native type-only source execution additionally uses Node.js 22.18.0. The classic-script example explicitly simulates a shared script context through Node's vm API; it is not a browser integration test.

### 1) **A namespace inside one module stays inside that module**

Save this ESM project:

```typescript
// file: left.mts
export namespace Geo {
  export interface Point { x: number }
  export function origin(): Point { return { x: 0 }; }
  export namespace Units { export const scale = 1; }
}
// file: right.mts
export namespace Geo { export const tag = "right"; }
// file: view.mts
import { Geo as Left } from "./left.mjs";
import { Geo as Right } from "./right.mjs";
const point: Left.Point = Left.origin();
console.log(point.x, Right.tag, Left.Units.scale);
console.log(Object.is(Left, Right), Object.hasOwn(Left, "tag"), Object.isExtensible(Left));
// console.log(Left.tag); // TS2339
```

Run `tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir out view.mts`, then `node out/view.mjs`. Output is `0 right 1`, then `false false true`. Geo in left and Geo in right are separate exported objects. A side-effect import of right would evaluate it but would not add tag to Left. An assertion claiming that Left has tag would change only checking; an actual property read still yields undefined.

Inspect out/left.mjs: Geo and Units have initialization code; Point erases. This implementation fails --erasableSyntaxOnly with TS1294. Same-scope merging has separate declaration-compatibility rules in the [merging owner](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>). Do not infer it from matching identifier text in unrelated modules.

For a file-module alternative, save flat.mts and flat-view.mts in the same project:

```typescript
// file: flat.mts
export interface Point { x: number }
export function origin(): Point { return { x: 0 }; }
export const Units = { scale: 1 };
// file: flat-view.mts
import * as Geo from "./flat.mjs";
const point: Geo.Point = Geo.origin();
console.log(point.x, Geo.Units.scale, Object.isExtensible(Geo));
```

Build with the same command, substituting flat-view.mts, then run its emitted .mjs file. Output is `0 1 false`, and the project passes --erasableSyntaxOnly. Namespace import gives a qualified module view without a TypeScript runtime namespace declaration. The functions and Units object still exist. Its module namespace is non-extensible, unlike the ordinary Geo object in the first program. A real migration must also review imports, identity, augmentation, enumeration and initialization; matching origin's output alone does not prove all consumers equivalent. The [Handbook module comparison](https://www.typescriptlang.org/docs/handbook/namespaces-and-modules.html) explains why a redundant wrapper is often unnecessary.

### 2) **Global script merging needs a shared execution context**

In a separate classic project, save these three files. They have no import/export statement at the file level:

```typescript
// file: part-a.ts
namespace Shared { export const A = "a"; }
// file: part-b.ts
/// <reference path="./part-a.ts" />
namespace Shared { export const B = A + "b"; }
// file: app.ts
/// <reference path="./part-b.ts" />
console.log(Shared.A, Shared.B);
```

Build with `tsc --strict --target es2022 --module commonjs --moduleDetection legacy --outDir scripts app.ts`. The explicit legacy detection keeps these import-free files as scripts. The reference directives include their dependencies for checking/emission; they are not emitted require calls. Inspect scripts/part-a.js and part-b.js: each uses a Shared variable in its surrounding script scope.

Save classic-run.cjs:

```javascript
const fs = require("node:fs");
const vm = require("node:vm");
const context = vm.createContext({ console });
for (const filename of process.argv.slice(2)) {
  vm.runInContext(fs.readFileSync(filename, "utf8"), context, { filename });
}
```

Run `node classic-run.cjs scripts/part-a.js scripts/part-b.js scripts/app.js`: it prints `a ab`. The harness evaluates the emitted files in order in one shared context, so their namespace fragments update the same object. Running part-b before part-a instead prints `a undefinedb`: B read the not-yet-initialized A while constructing its value. Running `node scripts/app.js` alone fails with ReferenceError, since the reference comment did not load the other scripts.

Do not replace this harness with three unrelated require calls and assume the variables share a scope. CommonJS wraps files separately. Classic browser script tags can provide shared script scope but require the corresponding actual loading/order arrangement. This local vm experiment models that scope/order issue only. The [namespace reference](https://www.typescriptlang.org/docs/handbook/namespaces.html#splitting-across-files) describes multi-file script assembly; older outFile recipes and module modes need their own compiler-version support check.

### 3) **Type-only and ambient namespaces do not install runtime objects**

In a new types project, save type-only.mts:

```typescript
export namespace Shapes { export interface Point { x: number } }
const point: Shapes.Point = { x: 2 };
console.log(point.x);
// console.log(Shapes); // TS2708: cannot use this type-only namespace as a value
```

Build with `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --outDir out type-only.mts`, then run `node out/type-only.mjs`: it prints 2. Inspect its output: no Shapes initialization exists. Native Node 22.18.0 also runs type-only.mts directly and prints 2; invoke it as `npm exec --yes --package=node@22.18.0 -- node type-only.mts` when the system runtime is Node 20. The gate distinguishes runtime namespaces from type-only ones.

In the same project, save vendor.d.ts and ambient.mts:

```typescript
// file: vendor.d.ts
declare namespace Vendor {
  const VERSION: "1.0";
  function ready(): boolean;
}
// file: ambient.mts
/// <reference path="./vendor.d.ts" />
const declared: "1.0" = Vendor.VERSION;
console.log(declared, Vendor.ready());
```

Save provider.cjs as the actual implementation:

```javascript
globalThis.Vendor = Object.freeze({ VERSION: "1.0", ready: () => true });
```

Build ambient.mts with the same command. The check passes and emits its consumer, but `node out/ambient.mjs` fails with ReferenceError because Vendor is absent. Run `node --require ./provider.cjs out/ambient.mjs`: the preload installs the global and the output is `1.0 true`. The ambient namespace described the contract; the JavaScript preload supplied the value. It did not make the implementation correct by itself. The [global augmentation lesson](<./2.2. declare global and global augmentation.md>) owns project inclusion and global-provider placement; [ambient modules](<./2.3. Ambient modules declare module wildcards.md>) describes imported-module declarations instead.

### 4) **Choose grouping without promising a mechanical migration**

Prefer direct file exports when the file already supplies the intended organization and consumers need no additional namespace object. This makes runtime imports visible and works with tools that erase types. Use an ambient namespace to describe an actual grouped global or a merged namespace to model a callable value with related types/properties when that is the API. The [CommonJS callable fixture](<../1. ES Modules/1.3. export equals and interop with CommonJS.md>) demonstrates the latter case.

A namespace-to-module migration can change global names, object identity, property mutability and load order, as well as import paths. Review the actual contract before deleting wrappers or replacing script assembly. Do not assume either that every namespace is forbidden or that wrapping every module is useful. An application can adopt a lint convention, but its exact allowances and exceptions are project policy, not a language guarantee or a measure of correctness by declaration count.

Practice: add an exported const C = B + "c" in part-c.ts with a reference to part-b.ts, then reference part-c from app.ts and print Shared.C. Rebuild and load a, b, c, app in that order; C must be abc. Loading c before b can still type-check but produces a wrong initialized value. Explain why a checking dependency and runtime order are separate in this script setup, then choose explicit modules if the application should stop depending on shared script assembly.

### 5) **Common confusion**

Export inside a namespace exposes a member of that namespace; export at file level makes a module binding. Identically named module-local namespaces are not one global object. Triple-slash inclusion makes a file visible to the checker but does not implement its runtime loader.

A type-only namespace erases, while a runtime namespace needs transformation. A declare namespace also erases, but its described provider may still be required by executed code. A module namespace import is a different runtime object from a TypeScript namespace implementation even when their qualified access looks similar.

### 6) **Performance note**

Runtime namespace fragments execute initialization; type-only and ambient descriptions erase. Ordinary module exports and retained objects can also perform runtime work. No experiment here measures bundle size, tree shaking or startup time, and no universal rule says every namespace defeats every bundler's analysis. The vm harness deliberately creates a shared context for an order demonstration; it is not a performance comparison with module loading.

### 7) **Mentor note**

Ask the learner to predict whether Left acquires Right's tag, whether the type-only namespace exists at runtime and whether a reference comment loads part-a. Require the output or exception before discussing a migration. A strong answer identifies scope, emitted initialization and the actual provider separately, then tests the contract the migration intends to preserve.
