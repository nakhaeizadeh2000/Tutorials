## 2.1. Namespaces — organization and when to avoid

### 1) **What namespaces provide** (dot-grouped values + types in one scope)

**Definition** — `namespace Geo { export interface Point {…}; export function dist(…)… }` groups values *and* types under one dotted scope (`Geo.Point`, `Geo.dist`) — the pre-ES-module organization unit (TS 1.x `module` keyword, renamed `namespace` in TS 1.5). Namespaces emit IIFE objects (`var Geo; (function(Geo){…})(Geo || {})`) — real runtime grouping, unlike pure types.

**What problem it solves / history** — pre-module TypeScript (and its `--outFile` single-bundle era) had no file-based modules — `<script>`-concatenated code needed collision-free grouping without a loader. Namespaces provided it: dot-scoped globals assembled across files via triple-slash references, merged by the compiler into one bundle. ES modules (file scope + import graph + bundlers) solved the same problems better — namespaces stayed for the corners modules can't serve (next promise + ambient declarations).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write application code as ES modules (file scope, explicit imports — no `namespace`); keep namespaces for: ambient declarations (`.d.ts` grouping of foreign globals), generated single-file bundles (codegen emitting one IIFE scope), and deliberate non-erasable grouping (with a recorded reason — namespaces fail `--erasableSyntaxOnly` like enums). New `namespace` in application source fails review by default.

**Runnable example** — namespace grouping vs module equivalent (multi-file sets, nodenext):

```typescript
// file: geo.ts
export namespace Geo {
  export interface Point { x: number }
  export function origin(): Point { return { x: 0 }; }
}
// file: app13.ts
import { Geo } from "./geo.js"; // namespace imported as ONE binding (dot access inside)
console.log(Geo.origin().x.toFixed(0)); // 0 — grouped values + types under Geo
```

```typescript
// file: shapes14.ts
export interface Point { x: number }
export function origin(): Point { return { x: 0 }; } // module equivalent: file IS the scope
// file: app14.ts
import { origin, type Point } from "./shapes14.js";
const p: Point = origin();
console.log(p.x.toFixed(0)); // 0 — same grouping via file scope + named imports (preferred)
// bad — namespace wrapping an ES module file (double scoping: file scope AND Geo scope, zero benefit)
```

```typescript
// file: ambient15.d.ts
declare namespace Vendor { const VERSION: string; function init(): void } // ambient: describes foreign global (no emit)
// file: app15.ts
/// <reference path="./ambient15.d.ts" />
console.log("vendor-namespace-declared"); // ambient namespace consumed without import (foreign truth)
// bad — namespace for ordinary application grouping (emits IIFE; un-erasable; un-tree-shakeable)
```

**Common confusion** — "namespaces and modules interchange" — namespaces group *within* a scope (mergeable, dot-accessed, emitted as objects); modules *are* scopes (file-bound, imported explicitly, tree-shakeable) — different organization axes for different eras. "namespaces are just types" — namespaces emit runtime objects (values live under them) — unlike interfaces, they cost bytes and break erasure. "triple-slash references are imports" — legacy assembly (pre-bundler file ordering) — modern code uses `import` (graph-based, cycle-checked); references survive for ambient/global assembly only.

**Performance note** — namespace IIFEs cost one object + closure per namespace (bytes + startup evaluation) — trivial singly, measurable across hundreds of generated namespaces (prefer flat ESM there). Tree-shakers cannot penetrate namespace objects (whole-namespace retention) — another reason application code stays modular.

**Mentor note** — emit-compare a namespace vs its module equivalent (`tsc` both, diff `.js` — IIFE object vs plain exports) — organization cost made visible in bytes. Rule: new `namespace` in application source fails review; ambient/generated namespaces carry comments naming their corner.

### 2) **Nest, merge, and split across files** (the legacy composition toolkit)

**Definition** — namespaces nest (`A.B.C` dot paths), merge (same-named `namespace N` blocks in one or many files combine members — the oldest declaration-merging form), and split across files (triple-slash-ordered assembly into one scope). Merging spans values, types, and nested namespaces uniformly — the most permissive merge in the language (interfaces merge types only; namespaces merge everything).

**What problem it solves / history** — giant pre-module libraries (jQuery-era `.d.ts` files, single-bundle applications) needed many authors/files contributing to one scope (`MyLib.ajax`, `MyLib.Widget`, `MyLib.version` from dozens of files) without a loader — namespace merging *is* that composition: each file augments the shared scope, the compiler (or `--outFile` concatenation) assembles the whole. Modules replaced the mechanism (import graphs compose better); the pattern survives in ambient declarations for foreign globals.

**Modern guidance** — as of TypeScript 5.9 era, merge namespaces only in ambient declarations (foreign-global mirrors split across `.d.ts` files) and generated bundles (codegen emitting augmentable scopes); never split application namespaces across files (each split is an invisible dependency edge — import graphs make edges explicit). Prefer one-module-per-concern with re-export barrels over namespace splitting for owned code.

**Runnable example** — merge across files, then the module equivalent (multi-file sets):

```typescript
// file: lib-a.ts
export namespace Lib { export const A = "a"; }
// file: lib-b.ts
export namespace Lib { export const B = "b"; } // same-named: merges with lib-a's Lib
// file: app16.ts
import { Lib } from "./lib-a.js";
import "./lib-b.js"; // side-effect import loads the augmenting file (merge needs BOTH evaluated)
console.log(Lib.A, (Lib as unknown as { B: string }).B); // a b — merged across files (B via assertion: cross-file merge is module-scoped, see confusion)
// bad — relying on cross-file namespace merge inside modules (each file's Lib is FILE-scoped: no real merge!)
// fix — single module exporting the whole scope, or ambient merging for foreign globals (below)
```

```typescript
// file: foreign.d.ts
declare namespace Foreign { const V: number }
declare namespace Foreign { function f(): string } // ambient merge: two blocks, one foreign scope (legal + normal)
// file: app17.ts
/// <reference path="./foreign.d.ts" />
console.log("foreign-merged"); // ambient merging is THE surviving use (foreign truth, split declarations)
// bad — application logic split across same-named namespaces per file (invisible edges, un-greppable assembly)
```

```typescript
// file: nested.ts
export namespace Outer { export namespace Inner { export const X = 1; } } // nesting: dot paths in one scope
// file: app18.ts
import { Outer } from "./nested.js";
console.log(Outer.Inner.X.toFixed(0)); // 1 — nested access (prefer module paths: outer/inner files + imports)
// bad — 4-level namespace nesting as application architecture (dot-path spelunking replaces import graphs)
```

**Common confusion** — "namespaces merge across module files" — *exported* namespaces are file-scoped (each file's `Lib` is distinct — no cross-file merge inside modules!); merging works for *global* (non-module) namespaces and ambient declarations — the distinction decides whether splitting works at all. "triple-slash assembly is importing" — ordering, not importing (no bindings created — files share global scope; modules create bindings per import). "nested namespaces equal nested modules" — nesting dots one scope (flat lookup `A.B.C`); nested modules compose graphs (each file independent, imported explicitly) — graphs scale, dots tangle.

**Performance note** — merged namespaces emit per-file IIFE fragments (`(function(Lib){…})(Lib || {})` — merge-at-runtime pattern) — each fragment evaluates at load (startup cost per contributing file); module graphs evaluate once per module with static ordering. Prefer module composition for load-order clarity.

**Mentor note** — demonstrate the non-merge (two files' exported `Lib` staying distinct) — the single most surprising namespace fact, worth one live demo. Rule: split namespaces means ambient-foreign or generated — application splits fail review with "use modules + barrel" as the fix.

### 3) **When to avoid** (modules win — the three surviving corners)

**Definition** — avoid namespaces in application source (modules do everything: scope, sharing, tree-shaking, erasability — better on every axis). Three surviving corners: (1) ambient declarations (foreign-global mirrors — no emit, pure description); (2) generated single-file bundles (codegen emitting one IIFE scope — tool output, not hand code); (3) deliberately non-erasable grouping with a recorded reason (rare — needs dot-grouped runtime values *and* rejects modules for documented cause).

**What problem it solves / history** — namespace-by-habit codebases paid the triple tax (IIFE bytes, un-erasability blocking toolchain adoption, un-tree-shakeable retention) for organization modules provide free — each namespace a small permanent cost with zero unique benefit in application code. The avoid-by-default rule with three named corners concentrates namespaces where they earn their costs and deletes them everywhere else.

**Modern guidance** — as of TypeScript 5.9 era, lint new application namespaces out (`no-namespace` rule on); record reasons on the three corners (ambient: "foreign truth"; generated: "tool output"; deliberate: dated justification + revisit). Migrate legacy application namespaces per directory (namespace → module + barrel, one directory per PR — mechanical, reviewable).

**Runnable example** — corner vs habit (multi-file sets):

```typescript
// file: legacy19.ts
export namespace Util { export function twice(n: number): number { return n * 2; } } // habit (migrate me)
// file: app19.ts
import { Util } from "./legacy19.js";
console.log(Util.twice(21).toFixed(0)); // 42 — works, but costs IIFE + erasure + shaking (migrate to module)
// fix — export function twice (module scope): same grouping, zero namespace costs
```

```typescript
// file: migrated.ts
export function twice(n: number): number { return n * 2; } // migrated: file scope does the grouping
// file: app20.ts
import { twice } from "./migrated.js";
console.log(twice(21).toFixed(0)); // 42 — identical behavior, erasable, shakeable (the migration dividend)
// bad — namespace kept "for consistency" (consistency with a costlier past is not a reason)
```

```typescript
// file: corner.d.ts
declare namespace IntlPoly { function format(n: number): string } // corner 1 (ambient foreign): stays, commented
// file: app21.ts
/// <reference path="./corner.d.ts" />
console.log("ambient-corner-kept"); // recorded reason (foreign truth) beats the default rule (the stamp working)
// bad — deleting ambient namespaces "for uniformity" (foreign truth needs SOME typed home)
```

**Common confusion** — "lint bans all namespaces" — `no-namespace` by default *allows* `declare namespace` (ambient) — the rule targets application grouping, not foreign description (configure, don't blanket-ban). "migration changes behavior" — namespace-to-module migration preserves values (same functions, new import paths) — only the grouping mechanism changes (IIFE object → module record). "small namespaces are harmless" — harmless singly, habitual collectively (each a precedent for the next — defaults compound like interest, in both directions).

**Performance note** — each migrated namespace deletes its IIFE (bytes + evaluation) and unlocks per-symbol shaking for its members — migration dividends compound per directory (measure bundle deltas per migration PR).

**Mentor note** — migrate one directory live (namespace → module + barrel, tests green throughout) — mechanical, reviewable, dividend-visible. Metric: application-namespace count per quarter (falling = default working). Celebrate deletions — culture follows measured behavior (same playbook as 11's enum stamp).
