## 2.3. Ambient modules declare module wildcards

An ambient module declaration describes an imported module to the checker. It supplies neither a runtime package nor an asset loader. Its context matters: a declare module block in a script-style declaration file declares a module; the same syntax in an external module can augment a resolved module instead. A shorthand declaration without a body supplies any, not an empty export contract.

The examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Create separate fresh directories for the package, assets and shorthand projects. No tsconfig.json is used. Each named source is complete; split multi-file fences at their file markers. Only the assets project installs the pinned esbuild dependency described below. All packages in the first project are local fixtures, not downloaded libraries.

### 1) **Observe an included ambient declaration hiding bundled types**

In the package project, create node_modules/calc-mini and save its package.json:

```json
{
  "name": "calc-mini",
  "version": "1.0.0",
  "main": "./index.cjs",
  "types": "./index.d.cts"
}
```

Save node_modules/calc-mini/index.d.cts:

```typescript
export function add(a: number, b: number): number;
```

Save node_modules/calc-mini/index.cjs:

```javascript
exports.add = (a, b) => {
  if (typeof a !== "number" || typeof b !== "number") throw new TypeError("numeric arguments required");
  return a + b;
};
```

Now save the deliberately incorrect shim and caller at the project root:

```typescript
// file: shim.d.ts
declare module "calc-mini" {
  export function add(a: string, b: string): string;
}
// file: bad.cts
import calc = require("calc-mini");
const text: string = calc.add("2", "3");
console.log(text);
```

Run `tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir out bad.cts shim.d.ts`. Checking succeeds even though the installed fixture already has a numeric declaration. Running `node out/bad.cjs` deliberately exits 1 with TypeError: numeric arguments required. The included script-style ambient module described a different API and hid the bundled declaration's effective contract for this call. It was not silently ignored just because a real .d.cts existed.

Check again with the same flags plus --noEmit and only bad.cts as input, leaving shim.d.ts out of the program. The caller now fails with TS2322 and TS2345: the actual declaration returns number and requires numeric arguments. Physical presence of a shim is different from including it. A tsconfig that includes all declaration files could make the unwanted ambient declaration active again.

Save good.cts:

```typescript
import calc = require("calc-mini");
const total: number = calc.add(2, 3);
console.log(total, typeof total);
// calc.add("2", "3"); // TS2345 without the incorrect shim in the program
// calc.subtract(3, 2); // TS2339: not declared by the fixture
```

Build only good.cts with the original flags and run out/good.cjs: it prints `5 number`. If the runtime package directory is temporarily moved out of node_modules, a consumer checked using an ambient description can still build, but execution fails with MODULE_NOT_FOUND. Restore the directory before continuing. A shim does not install that provider.

When a dependency gains types, remove or deliberately reconcile the old shim and run consumer checks. Do not assume a fixed bundled-types, @types, paths, ambient priority ladder. Resolution depends on the selected mode, package metadata, mappings and declaration context. TraceResolution can show resolved paths, but also inspect the actual accepted signatures. The [module reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html#ambient-modules) explains declaration context and program inclusion; [module configuration](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>) owns the broader resolver model.

### 2) **A module augmentation extends the resolved module instead**

Still in the package project, exclude shim.d.ts and save augment.d.ts and both.cts:

```typescript
// file: augment.d.ts
import "calc-mini";
declare module "calc-mini" {
  export function add(a: string, b: string): string;
}
// file: both.cts
import calc = require("calc-mini");
console.log(calc.add(2, 3), calc.add("2", "3"));
```

Build with the same flags, selecting both.cts and augment.d.ts. Both calls now check: the import makes augment.d.ts an external module, and its declaration adds an overload alongside the resolved numeric one. Running the current provider still throws TypeError for the strings. Augmentation added no JavaScript implementation.

For this deliberate API extension, replace index.cjs with the following implementation and run the emitted both.cjs again in a fresh process:

```javascript
exports.add = (a, b) => {
  if (typeof a === "number" && typeof b === "number") return a + b;
  if (typeof a === "string" && typeof b === "string") return a + b;
  throw new TypeError("matching numeric or string arguments required");
};
```

It prints `5 23`. The runtime provider now supports both declared overloads. This is a local demonstration, not permission to claim a third-party package supports an invented overload. The [merging owner](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) owns compatibility and implementation responsibilities. Importing a helper type at the top level of a file can change its ambient declaration into an augmentation; import it inside the declaration body when the file must remain script-style ambient instead.

### 3) **Verify wildcard declarations against an actual loader**

In a fresh assets project, run `npm install --ignore-scripts --save-exact esbuild@0.28.2`. Save message.txt containing hello and panel.module.css containing this CSS:

```css
.button { color: red; }
```

Save assets.d.ts and assets.ts:

```typescript
// file: assets.d.ts
declare module "*.txt" {
  const message: string;
  export default message;
}
declare module "*.module.css" {
  const classes: Readonly<Record<string, string>>;
  export default classes;
}
// file: assets.ts
import message from "./message.txt";
import classes from "./panel.module.css";
console.log(message.trim(), typeof classes.button, classes.missing === undefined);
// const absent: string = classes.missing; // TS2322 under noUncheckedIndexedAccess
```

Check with `tsc --strict --noUncheckedIndexedAccess --erasableSyntaxOnly --target es2022 --module preserve --moduleResolution bundler --noEmit assets.ts assets.d.ts`. Then bundle with `./node_modules/.bin/esbuild assets.ts --bundle --platform=node --format=cjs --loader:.txt=text --loader:.css=local-css --outfile=dist/assets.cjs` and run `node dist/assets.cjs`. The output is `hello string true`.

The text loader supplied a string. The local-css loader supplied a class-name mapping and emitted a CSS sidecar, dist/assets.css. Generated class names are implementation details, so the example checks their type rather than hard-coding a name. This Node execution verifies imported values, not browser styling; an application must arrange to load the emitted CSS too. [The esbuild CSS documentation](https://esbuild.github.io/content-types/#css-modules) explains that loader and the separate CSS artifact.

Change only the text import to ./absent.txt. The wildcard still permits it at checking time, but bundling fails because that file does not exist. Restore the filename. A wildcard matches import specifier text; it does not verify filesystem existence or loader support.

For another deliberate mismatch, change the txt declaration's default to `{ text: string }` and the consumer to message.text.trim(). Checking then succeeds, but bundling with the same text loader still produces a primitive string and execution throws TypeError. Restore both the declaration and consumer. The declaration must match the selected loader contract; it cannot configure that loader. Image URLs, SVG components, worker constructors and CSS side-effect imports can have different contracts even when a project treats them all as assets.

### 4) **Distinguish shorthand any from an explicit empty module**

This separate shorthand project is a checking-only experiment, with no runtime CSS loader or file. Save loose.d.ts and use.ts:

```typescript
// file: loose.d.ts
declare module "*.css";
// file: use.ts
import styles from "./not-a-real-file.css";
const count: number = styles.missing.deep();
console.log(count);
```

Run `tsc --strict --target es2022 --module preserve --moduleResolution bundler --noEmit use.ts loose.d.ts`: it passes. The arbitrary default binding and deep call are any, not a validated side-effect-only contract. The [shorthand module reference](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-0.html#shorthand-ambient-module-declarations) states that any behavior; the current compiler probe verifies it still applies here.

Replace loose.d.ts with `declare module "*.css" {}` and check again. The access styles.missing is rejected with TS2339 in this module mode. Replacing use.ts with only `import "./not-a-real-file.css";` passes against that empty declaration. Neither form supplies the missing CSS file or a loader. Use a shaped declaration when an imported value really exists, an explicit appropriate declaration for a side-effect loader, or the consuming framework's maintained declarations when they accurately describe its configured pipeline.

### 5) **Common confusion**

An ambient module can actively hide a package's effective type surface; it is not always the last fallback behind every physical declaration. A top-level import can instead make the same block an augmentation. Inspect inclusion and context before deciding which signatures the consumer is checking.

A wildcard neither checks that a matching file exists nor transforms it. A shorthand declaration grants any; empty braces provide a different checker surface. Good declarations need actual provider/loader evidence, and a TODO comment alone cannot make a false signature correct.

### 6) **Performance note**

Declarations erase. Actual package loading, arithmetic, asset bundling, generated mappings and any loaded CSS remain separate work. No experiment here measures resolver timing, pattern-match counts, bundle-size savings or a fixed candidate-priority cost. Removing stale declarations can clarify the effective contract, but a successful deletion is not a performance measurement.

### 7) **Mentor note**

Have the learner predict which add calls check with the global shim, with no shim and with the imported augmentation. Then run the unchanged numeric provider before extending its implementation. A strong answer separates module resolution/context, accepted signatures and actual runtime support. For assets, require both a checker result and a loader result; the missing txt file is a direct counterexample to treating a wildcard as validation.
