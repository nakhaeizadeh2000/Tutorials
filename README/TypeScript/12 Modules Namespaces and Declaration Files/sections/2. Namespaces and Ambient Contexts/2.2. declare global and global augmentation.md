## 2.2. declare global and global augmentation

Declare global lets a module contribute declarations to the compiler program's global scope. It does not install a runtime value or make a file visible to every TypeScript program on disk. Three separate obligations remain: include the declaration, load the provider where needed and check externally supplied values when their shape is not guaranteed.

The examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. The browser project was also executed in Google Chrome 151.0.7922.173. Use separate fresh directories for the Node and browser projects below. Neither needs package dependencies. The DOM library supplies checker names such as Window; it does not install window in Node.

### 1) **Include the augmentation in the checked program**

In the Node project, save globals.d.ts:

```typescript
export {};
declare global {
  var __APP_CONFIG: unknown;
  var __LEGACY_INIT: unknown;
  interface Window { appMode?: "dark" | "light" }
}
```

Export {} makes this declaration file a module; the global block then contributes its declarations outside that module's local scope. A script-style .d.ts can instead declare globals directly. Do not remove the module marker while retaining a top-level declare global wrapper: checking that script file reports TS2669. The [global-modifying module template](https://www.typescriptlang.org/docs/handbook/declaration-files/templates/global-modifying-module-d-ts.html) shows the module-marker pattern. Such a provider can be imported or preloaded; global does not mean its implementation is inherently non-importable.

Save app.mts:

```typescript
/// <reference path="./globals.d.ts" />
export interface Settings { mode: "dev" | "prod"; beta: boolean }
export function parseSettings(raw: unknown): Settings {
  if (typeof raw === "object" && raw !== null &&
      "mode" in raw && (raw.mode === "dev" || raw.mode === "prod") &&
      "beta" in raw && typeof raw.beta === "boolean") {
    return { mode: raw.mode, beta: raw.beta };
  }
  return { mode: "dev", beta: false };
}
const settings = parseSettings(globalThis.__APP_CONFIG);
console.log(settings.mode, settings.beta);
const initialize = globalThis.__LEGACY_INIT;
if (typeof initialize === "function") initialize();
try { console.log(window?.appMode ?? "light"); }
catch (error) { console.log(error instanceof ReferenceError); }
console.log(typeof window === "undefined" ? "light" : window.appMode ?? "light");
// window.appMode = "sepia"; // TS2322
// globalThis.__APP_CONFG; // Rejected: misspelled global property
```

Build with `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --lib es2022,dom --outDir out app.mts`, then run `node out/app.mjs`. Output is `dev false`, `true` and `light`. The reference includes globals.d.ts in this checking program. A tsconfig include list, an imported declaration-bearing package or another supported inclusion route could do that job instead. Merely leaving a declaration somewhere on disk is not enough; removing this reference from an otherwise unconnected entry makes its custom globals fail checking.

The unknown configuration remains untrusted until the actual comparisons return a Settings value. Missing or invalid input deliberately selects a development fallback in this example; a production application may need a fail-fast policy instead. The custom hook is called only when its runtime value is callable. Its declaration alone establishes neither presence nor implementation.

Window is absent in Node. Optional chaining still evaluates that root name before it can test its value, so window?.appMode throws the caught ReferenceError. The typeof guard avoids the unresolved read. [Optional chaining's root-name rule](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Optional_chaining#description) distinguishes an absent binding from a declared binding holding undefined. Reading an absent property through the existing globalThis object is another situation: globalThis.__APP_CONFIG produces undefined here and the parser handles it.

### 2) **Run the actual provider and validate its input**

Save provider.cjs in the Node project:

```javascript
globalThis.__APP_CONFIG = {
  mode: process.env.APP_MODE,
  beta: process.env.BETA_FLAG === "1"
};
globalThis.__LEGACY_INIT = () => console.log("initialized");
```

Run `APP_MODE=prod BETA_FLAG=1 node --require ./provider.cjs out/app.mjs`. Output is `prod true`, `initialized`, `true` and `light`. Node's [preload option](https://nodejs.org/download/release/v20.20.2/docs/api/cli.html#-r---require-module) executes this JavaScript provider before the entry. No replacement declaration for Node's process object was required.

Change APP_MODE to staging: the provider still runs, but output starts with `dev false` because staging is outside the parser's admitted values. An ambient ProcessEnv property typed as dev | prod would not validate the operating system's supplied string or make it present. Model uncertain inputs honestly and check them before relying on the narrower application type.

A shared global is mutable process state. A wrapper can centralize access and a pure parser can accept an explicit test input, but neither automatically restores state between tests or makes concurrent tests independent. Prefer explicit parameters or imported values when the API allows them. Where a global provider is required, document its load order and absent/invalid policy, then isolate tests through deliberate setup/cleanup or separate processes.

### 3) **Separate Window members from global object and lexical bindings**

In the separate browser project, save browser-globals.d.ts and browser.ts:

```typescript
// file: browser-globals.d.ts
export {};
declare global {
  interface Window { appMode?: "dark" | "light" }
  var APP_FLAGS: { beta: boolean } | undefined;
  const BUILD_ID: string;
  let LEXICAL_ID: string;
}
// file: browser.ts
/// <reference path="./browser-globals.d.ts" />
const result = document.getElementById("result");
if (result === null) throw new Error("missing result element");
try {
result.textContent = [
  window.appMode, globalThis.APP_FLAGS?.beta ?? false, BUILD_ID, LEXICAL_ID,
  Object.hasOwn(globalThis, "APP_FLAGS"), Object.hasOwn(globalThis, "BUILD_ID"),
  Object.hasOwn(globalThis, "LEXICAL_ID")
].join(" ");
} catch (error) { result.textContent = error instanceof ReferenceError ? "ReferenceError" : "unexpected error"; }
// window.appMode = "sepia"; // TS2322
// globalThis.appMode; // Rejected: this Window member did not declare a global variable
// globalThis.BUILD_ID; // Rejected: lexical binding is not a declared globalThis property
```

Compile with `tsc --strict --erasableSyntaxOnly --target es2022 --module commonjs --moduleDetection legacy --lib es2022,dom --outDir out browser.ts`. The entry has no import/export statement and is emitted as a classic script, despite the declaration file being a module. Save index.html beside it:

```html
<!doctype html>
<meta charset="utf-8">
<title>Global declarations and their provider</title>
<pre id="result">waiting</pre>
<script id="provider">
var APP_FLAGS = { beta: true };
const BUILD_ID = "build42";
let LEXICAL_ID = "lexical";
window.appMode = "dark";
</script>
<script src="./out/browser.js"></script>
```

Open index.html in a browser. The rendered result is `dark true build42 lexical true false false`. APP_FLAGS is supplied by a top-level var in a classic script, while BUILD_ID and LEXICAL_ID are top-level lexical bindings. They are readable by the later script but are not properties of globalThis. [The lexical declaration reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/let#description) explains that distinction. An ambient var versus ambient const or let is therefore meaningful, not a spelling preference.

Window augmentation types window.appMode, but does not itself declare a global variable appMode or type globalThis.appMode. Declaring a new interface named GlobalThis is not the general way to install global variable properties either. Match the actual provider form, and distinguish Window members, global variables and lexical globals instead of describing them as one interface-merge mechanism.

Delete only the provider script block and reload: the result becomes ReferenceError through the consumer's catch. BUILD_ID was declared as a required checker binding, but no runtime provider exists. The consumer's catch makes the deliberate failure visible; it does not repair the missing global. A real third-party script or server template would need its own loading and validation contract. This page demonstrates a local provider, not an external analytics integration.

### 4) **Review global contracts and test state deliberately**

An augmentation affects uses in the compiler program that includes it. Conflicting property declarations can fail merging; a declaration may also be perfectly consistent while describing an unavailable or incorrect runtime provider. [Declaration merging](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) owns compatibility rules, while [declaration authoring](<../3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>) owns implementation/declaration agreement.

Adding an any index signature to Window can hide misspellings far beyond the intended flag. Prefer the actual property shape and keep unknown external values unknown until checked. Narrow required declarations are appropriate only when their provider and initialization guarantee warrant them; optional or unknown forms are often more honest. A central file can make ownership clear, but no language rule requires every augmentation in one physical file or a mandatory review date.

Practice in app.mts: assign a prod/true object to globalThis.__APP_CONFIG and parse it into first. Replace the global with a dev/false object and parse it into second. Printing first.mode, second.mode and Object.is(first, second) must give `prod dev false`. The first parsed result is an ordinary snapshot of the selected primitive fields; it does not react to replacing the global. Explain why callers must decide when to read again and why test state still needs restoration or process isolation.

### 5) **Common confusion**

A declaration's visibility, a runtime binding's presence and a value's validity are separate. A custom global can pass checking and fail at execution; a present global can still contain invalid data. Including DOM types does not make Node a DOM runtime, and optional chaining does not guard an unresolved root name.

A Window interface member does not automatically become a declared globalThis property. Ambient const and let model lexical bindings, while var can model a global object property. Match the real provider and the module/script context rather than assuming one declaration form covers all hosts.

### 6) **Performance note**

Global declarations erase, but provider initialization, property reads, parser comparisons, snapshots and hook calls remain. These examples measure no global-access latency, wrapper overhead, checker cost or test-speed gain. Centralizing access is useful for understanding dependencies; it does not remove runtime work or prove parallel test safety.

### 7) **Mentor note**

Ask the learner to remove the declaration reference, then restore it and remove the provider. The first change should fail checking; the second should expose the runtime policy. Next ask why the browser lexical names can be read while hasOwn is false, and why Node's window optional chain throws. A strong answer names the separate compiler and host contracts instead of adding an assertion.
