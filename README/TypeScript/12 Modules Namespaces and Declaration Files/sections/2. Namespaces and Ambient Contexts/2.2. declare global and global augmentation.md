## 2.2. `declare global` and global augmentation

### 1) **`declare global` in modules** (adding to global scope from a module file)

**Definition** — inside any *module* file (one with imports/exports), `declare global { interface Window { … } }` (or `var …`, `function …`) augments the global scope: the declaration is visible everywhere without imports. The `declare global` wrapper is required precisely *because* modules are scoped — it marks the deliberate escape from file scope to shared scope.

**What problem it solves / history** — environment-provided globals (feature flags injected by the server, `window.analytics` from a third-party script, `process.env` typings) had nowhere typed to live in a modules-only codebase — `any`-casts at every use, or ambient script files breaking the module build. `declare global` houses them in one typed, reviewable location (conventionally `globals.d.ts` or `env.d.ts`) consumed implicitly everywhere.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), centralize globals in one `globals.d.ts` (or `vite-env.d.ts`/`next-env.d.ts` framework equivalents); type each global narrowly (literal/union, never `any`); fence with a lint rule (`no-restricted-syntax` on new `declare global` blocks outside the file, or review convention). Every global needs a comment naming its *provider* (which script/env/runtime injects it).

**Runnable example** — typed globals, one home (multi-file sets):

```typescript
// file: globals.d.ts
export {}; // module marker (makes declare global legal in this file)
declare global {
  interface Window { appFlags: { beta: boolean } }
  const BUILD_ID: string; // injected by the server template (provider documented here)
}
// file: app22.ts
/// <reference path="./globals.d.ts" />
console.log(window.appFlags.beta, BUILD_ID.length); // typed everywhere, imported nowhere
// window.appFlags = 42; // error TS2322 — global shape enforced at every use site
```

```typescript
// file: env.d.ts
export {};
declare global {
  namespace NodeJS { interface ProcessEnv { readonly APP_ENV: "dev" | "prod" } }
  // minimal process value declaration (self-contained: no @types/node needed for this demo)
  var process: { env: NodeJS.ProcessEnv };
}
// file: app23.ts
/// <reference path="./env.d.ts" />
const env: "dev" | "prod" = process.env.APP_ENV; // narrowed (not string|undefined)
console.log(env.toUpperCase()); // DEV — env access typed once, consumed safely
// bad — process.env.APP_ENV as string (per-use casts; provider contract restated per file)
```

```typescript
// file: third.d.ts
export {};
declare global {
  function analytics(event: string, props?: Record<string, string>): void; // third-party script global
}
// file: app24.ts
/// <reference path="./third.d.ts" />
analytics("page_view"); // typed call (script tag loads it at runtime; types describe it here)
// analytics(42); // error TS2345 — global function signature enforced like any other
// bad — (window as any).analytics("x") (untyped escape hiding at every call site)
```

**Common confusion** — "`declare global` works in scripts" — scripts *are* global scope (no wrapper needed — top-level `interface Window` augments directly); `declare global` exists *for modules* (explicit escape from file scope). "globals need importing" — visible without imports (that's the point *and* the hazard — implicit coupling, hence the single-file fence). "ambient globals validate providers" — types describe, never verify (a missing script tag still crashes at runtime — types narrow the *contract*, runtime owns the *presence*).

**Performance note** — zero emit (declarations erase); global access compiles to direct property reads (same as any global). The cost axis is coupling (implicit dependencies invisible in import graphs) — fenced by convention, not by tooling.

**Mentor note** — `grep declare global` quarterly and demand a provider comment per block (orphaned globals — provider long removed — are dead coupling to delete). Exercise: convert three `(window as any)` escapes to one `globals.d.ts` block and count the casts deleted — centralization dividend in one diff.

### 2) **Augmenting `Window`/`globalThis`** (third-party globals, environment flags)

**Definition** — `interface Window { … }` merging (global scope) adds properties to the DOM `Window` type; `globalThis` augmentation covers non-DOM runtimes (workers, Node 22+ global scope). Both follow interface-merging rules (see 04/2.2) — declarations combine, conflicts must be identical or error. Environment flags (`appFlags`, `BUILD_ID`), polyfill gaps, and script-injected APIs are the legitimate residents.

**What problem it solves / history** — `window.myFlag` (injected by A/B infrastructure) typed `any`-via-`Window` index or errored (`Property 'myFlag' does not exist`) — teams chose between per-use casts (noise + drift) and index-signature widening (`[key: string]: any` on Window — type-safety surrendered *globally* for one flag). Targeted augmentation types exactly the injected surface: known flags checked, unknown access still errors.

**Modern guidance** — as of TypeScript 5.9 era, augment narrowly per flag (`appFlags: { beta: boolean }` — not `[key: string]: unknown` blankets); prefer `globalThis` over `window` in isomorphic code (workers lack `window`); type injected functions with full signatures (params + returns — the script's contract, transcribed once). Never widen `Window` with index signatures to admit one flag (global type-safety for local convenience — the worst trade in this domain).

**Runnable example** — narrow augmentation, no blankets (multi-file sets):

```typescript
// file: flags25.d.ts
export {};
declare global {
  interface Window { appMode: "dark" | "light" } // narrow: union, not string, never any
}
// file: app25.ts
/// <reference path="./flags25.d.ts" />
function theme(): string { return window.appMode === "dark" ? "D" : "L"; }
console.log(theme()); // D or L — exhaustive over the union (narrowing works on globals)
// window.appMode = "sepia"; // error TS2322 — injected contract enforced (would be silent under blankets)
```

```typescript
// file: worker26.d.ts
export {};
declare global {
  var workerId: number; // globalThis-scoped (workers + main thread alike)
}
// file: app26.ts
/// <reference path="./worker26.d.ts" />
console.log(globalThis.workerId?.toFixed(0) ?? "unset"); // isomorphic access (no window assumed)
// bad — window.workerId in a worker (ReferenceError at runtime — window undefined outside DOM)
```

```typescript
// file: poly27.d.ts
export {};
declare global {
  interface Window { __perfMark?: (label: string) => number } // optional: vendor-hook-may-exist shape
}
// file: app27.ts
/// <reference path="./poly27.d.ts" />
window.__perfMark?.("boot"); // optional-call (presence checked per use)
// bad — interface Window { [key: string]: any } (blanket: every window typo compiles globally, forever)
// fix — per-flag narrow fields: known surface checked, unknown access still errors
```

**Common confusion** — "`var` vs `let` in declare global" — ambient globals use `var` (or bare `function`/interface merging) — `let`/`const` ambient declarations have different scoping semantics pedantically; `var` is the documented ambient-global form. "`globalThis` augmentation differs from `Window`" — same merging mechanics, different scope object (DOM `window` vs universal `globalThis`) — isomorphic code prefers `globalThis`. "optional (`?`) globals are non-committal" — honest (polyfill-may-exist, script-may-load) — `?.` at uses is the contract working, not hedging.

**Performance note** — zero emit; global reads are direct property accesses (same as any global). Narrow unions enable exhaustiveness over globals (fewer branches than `string`-typed flags) — precision dividends, not costs.

**Mentor note** — show the blanket (`[key: string]: any` on Window) beside narrow augmentation and typo-test both (`window.appModde` — silent vs error) — global type-safety surrendered vs kept in one typo. Gate: `Window` index-signature widening fails review unconditionally.

### 3) **Why globals are a last resort** (implicit coupling, collisions, test pollution)

**Definition** — every global is an *implicit* dependency (invisible in import graphs), a *collision* surface (two libraries' `init()` globals merge-or-clash), and a *test* hazard (suite order determines global state — flaky by construction). The review bar: exhaust imports, parameters, and context-passing first; reach for `declare global` only when the provider is genuinely ambient (scripts, env, runtime injections no import can name).

**What problem it solves / history** — global-first codebases (namespaced globals per feature, `window.store` state, ambient helpers) hit three walls in sequence: collisions (two teams' `format()` merged signatures erroring), untestability (suites leaking global state — order-dependent green/red), and un-traceability (no import graph — "who sets this?" answered by grep, not go-to-definition). Modules + explicit imports solve all three structurally; globals remain for the provider-ambient remainder only.

**Modern guidance** — as of TypeScript 5.9 era, justify each global with the provider test ("which non-importable runtime/script/env provides this?") — no provider, no global (use imports). Isolate global reads behind functions (`getFlags(): Flags` — one auditable read site, mockable in tests) instead of scattering `window.x` across features. Sunset globals whose providers gain module APIs (script → npm package migration deletes the declaration).

**Runnable example** — isolated reads, justified globals (multi-file sets):

```typescript
// file: g28.d.ts
export {};
declare global {
  var __APP_FLAGS: { beta: boolean } | undefined; // provider: server template (documented, sole global)
}
// file: flags28.ts
/// <reference path="./g28.d.ts" />
export function isBeta(): boolean { return globalThis.__APP_FLAGS?.beta ?? false; } // ONE read site (mockable)
// file: app28.ts
import { isBeta } from "./flags28.js";
console.log(isBeta() ? "beta" : "stable"); // stable — features import the function, never the global
// bad — window.__APP_FLAGS?.beta scattered across 40 features (40 implicit couplings, unmockable, ungreppable)
```

```typescript
// file: g29.d.ts
export {};
declare global {
  function __legacyInit(): void; // provider: vendored script (sunset when npm migration lands)
}
// file: boot29.ts
/// <reference path="./g29.d.ts" />
export function boot(): string {
  if (typeof __legacyInit === "function") __legacyInit(); // guarded (script may not have loaded)
  return "booted";
}
// file: app29.ts
import { boot } from "./boot29.js";
console.log(boot()); // booted — guarded global read, isolated in boot (testable via typeof branch)
// bad — unguarded __legacyInit() at module top-level (ReferenceError when the script tag is missing)
```

```typescript
// file: g30.d.ts
export {};
declare global {
  interface Window { __theme: string }
}
// file: theme30.ts
/// <reference path="./g30.d.ts" />
export function theme(): string { return window.__theme ?? "light"; } // isolated + defaulted
// file: app30.ts
import { theme } from "./theme30.js";
console.log(theme().toUpperCase()); // LIGHT — default covers absent provider (tests never set globals)
// bad — direct window.__theme reads per component (untestable without global setup/teardown per suite)
```

**Common confusion** — "one global is harmless" — harmless singly, precedent-setting collectively (each unreviewed global licenses the next — defaults compound). "isolation wrappers are ceremony" — wrappers are *the* test seam (mock `isBeta`, not `globalThis`) plus the sunset point (one file to delete on migration) — ceremony with two payoffs. "typeof-guards are paranoia" — script tags fail (ad-blockers, CSP, CDN outages) — guarded reads degrade; unguarded reads crash (see 5.1-adjacent robustness reasoning).

**Performance note** — indirect reads (function call per access) cost one call frame vs direct global reads — negligible except ultra-hot loops (hoist to locals there). Test-isolation dividends (no global setup/teardown per suite — parallel-safe suites) dwarf micro-costs.

**Mentor note** — `grep -r "window\." src | wc -l` before/after isolating globals (40 scattered reads → 3 audited functions) — coupling made countable. Rule: new `declare global` blocks name their provider + sunset condition, or fail review; direct global reads outside isolating functions fail review.
