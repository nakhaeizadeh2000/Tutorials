## 3.3. Publishing types — exports map and typesVersions

A package release has two related contracts: the JavaScript a loader executes and
the declarations a compiler checks. Testing the source directory does not prove
that either contract survived packaging. This lesson builds a package, installs
its local tarball into a separate consumer and observes both contracts.

The examples use TypeScript 7.0.2, Node 20.20.2 and npm 10.8.2. Historical compiler
checks explicitly use TypeScript 5.0.4 and 4.9.5. These older compilers illustrate
declaration compatibility; they are not the track's current baseline. All packages
are local fixtures. Nothing here requires `npm publish`.

### 1) **Build two module formats with matching declarations**

Create sibling `producer`, `consumer` and `artifacts` directories. In `producer`,
create this metadata and the five source files below. `import` and `require`
conditions choose different runtime files. Each branch also supplies declarations
with the corresponding module kind: `.d.mts` for ESM and `.d.cts` for CommonJS.
Put `types` before the runtime condition at the same level.

```json
// file: producer/package.json
{
  "name": "calc-kit",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "types": "./dist/index.d.cts",
  "files": ["dist"],
  "exports": {
    ".": {
      "import": { "types": "./dist/index.d.mts", "default": "./dist/index.mjs" },
      "require": { "types": "./dist/index.d.cts", "default": "./dist/index.cjs" }
    },
    "./stats": {
      "import": { "types": "./dist/stats.d.mts", "default": "./dist/stats.mjs" },
      "require": { "types": "./dist/stats.d.cts", "default": "./dist/stats.cjs" }
    }
  }
}
```

Remove the `// file:` label when saving JSON. It identifies the destination and is
not part of JSON syntax. Top-level `main` and `types` serve consumers that use
those legacy fields; they do not provide an unconditional fallback after a modern
resolver rejects an `exports` entry. The [module reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html#packagejson-exports)
explains which package fields each resolution mode reads.

```typescript
// file: producer/src/index.mts
export function add(left: number, right: number): number { return left + right; }
export const format = "esm";
// file: producer/src/index.cts
export function add(left: number, right: number): number { return left + right; }
export const format = "cjs";
```

```typescript
// file: producer/src/stats.mts
export function mean(values: readonly number[]): number | undefined {
  return values.length === 0 ? undefined : values.reduce((sum, n) => sum + n, 0) / values.length;
}
// file: producer/src/stats.cts
export function mean(values: readonly number[]): number | undefined {
  return values.length === 0 ? undefined : values.reduce((sum, n) => sum + n, 0) / values.length;
}
// file: producer/src/secret.mts
export const secret = "internal";
```

Run these commands from `producer`. The explicit input list keeps this fixture
independent of any parent project's configuration.

```sh
mkdir -p ../artifacts
# TypeScript 7.0.2:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --declaration --noEmitOnError --rootDir src --outDir dist src/index.mts src/index.cts src/stats.mts src/stats.cts src/secret.mts
npm pack --ignore-scripts --json --pack-destination ../artifacts
```

The tarball is `artifacts/calc-kit-1.0.0.tgz`. The pack result lists the files
actually included: five JavaScript files and five declarations, plus package
metadata. Inspect that list rather than assuming that generated files were packed.
The two source implementations are deliberately tiny and duplicated to expose
routing. A real build can generate both formats from one implementation, but must
still check that its declarations match the resulting exports. The [TypeScript
4.7 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#ecmascript-module-support-in-nodejs)
explain why a dual package needs declarations for each module kind.

### 2) **Check and execute consumers of the installed tarball**

Create `consumer/package.json` and the two consumers below. Install the tarball
from `consumer`, using the exact output filename reported by `npm pack`.

```json
// file: consumer/package.json
{ "name": "calc-consumer", "version": "1.0.0", "private": true }
```

```typescript
// file: consumer/esm.mts
import { add, format } from "calc-kit";
import { mean } from "calc-kit/stats";
const selected: "esm" = format;
console.log(selected, add(2, 3), mean([2, 4]), mean([]));
// file: consumer/cjs.cts
import api = require("calc-kit");
import stats = require("calc-kit/stats");
const selected: "cjs" = api.format;
console.log(selected, api.add(2, 3), stats.mean([2, 4]), stats.mean([]));
```

```sh
npm install --ignore-scripts --no-audit --no-fund --package-lock=false ../artifacts/calc-kit-1.0.0.tgz
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist esm.mts cjs.cts
node dist/esm.mjs
node dist/cjs.cjs
# Inspect declaration resolution without emitting again:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit --traceResolution esm.mts cjs.cts
```

The two runtime lines are `esm 5 3 undefined` and `cjs 5 3 undefined`.
The trace resolves root and `stats` imports to `.d.mts` for the ESM consumer and
`.d.cts` for the CommonJS consumer. The literal assignments check the selected
branch as well as the shared numeric API. Deliberately route the import branch
to `index.d.cts`: `selected: "esm"` then fails even though `add` has the same shape.
Testing only `add(2, 3)` would miss that declaration-routing mistake.

`calc-kit/dist/secret.mjs` is not an exported package subpath. A consumer import
of that name fails type resolution, and a native Node import throws
`ERR_PACKAGE_PATH_NOT_EXPORTED`. This is package-name encapsulation, not a
security boundary. The file exists in this tarball, so a relative filesystem
import such as `./node_modules/calc-kit/dist/secret.mjs` from the consumer root
still loads it. Node documents this [encapsulation limit](https://nodejs.org/download/release/v20.20.2/docs/api/packages.html#main-entry-point-export).
Exclude genuinely unwanted files from the tarball itself.

An explicit `types` condition makes declaration routing clear, but its absence
does not automatically mean `any`. In this fixture, replacing each nested branch
with just its runtime path still lets TypeScript find the adjacent matching
`.d.mts` or `.d.cts` through extension substitution. Conversely, packing only the
JavaScript files leaves the declarations absent: these strict consumers fail
with TS7016. Missing declarations, blocked subpaths and intentionally permissive
ambient shims are different failures; diagnose the actual resolver output.

### 3) **Serve declarations to different compiler versions**

A minimum supported compiler is part of a library's contract. A declaration that
uses `const` type parameters cannot be parsed by TypeScript 4.9.5. One possible
compatibility strategy is a separate declaration tree. Another is a higher
minimum compiler version or a conservative declaration shared by all consumers.
A successful package installation does not parse declarations; a subsequent
compiler invocation discovers incompatible syntax.

For a small independent experiment, create `version-consumer/node_modules/version-kit`
with this metadata and the three declaration files below. This manually installed
fixture isolates declaration selection; it does not replace the tarball test above.

```json
// file: version-consumer/node_modules/version-kit/package.json
{
  "name": "version-kit", "version": "1.0.0",
  "main": "./index.cjs", "types": "./index.d.ts",
  "typesVersions": {
    ">=5.0": { "*": ["modern/*"] },
    "*": { "*": ["legacy/*"] }
  }
}
```

```javascript
// file: version-consumer/node_modules/version-kit/index.cjs
exports.identity = value => value;
```

```typescript
// file: version-consumer/node_modules/version-kit/index.d.ts
export declare function identity<T extends readonly string[]>(value: T): T;
// file: version-consumer/node_modules/version-kit/legacy/index.d.ts
export declare function identity<T extends readonly string[]>(value: T): T;
// file: version-consumer/node_modules/version-kit/modern/index.d.ts
export declare function identity<const T extends readonly string[]>(value: T): T;
// file: version-consumer/pair.cts
import { identity } from "version-kit";
const inferred = identity(["get", "post"]);
const pair: readonly ["get", "post"] = inferred;
console.log(pair.join(","));
```

From `version-consumer`, compare the compilers. Use `--traceResolution` on any
command to inspect the selected declaration path.

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir dist pair.cts
node dist/pair.cjs
npm exec --yes --package=typescript@5.0.4 -- tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit pair.cts
# Expected failure TS2322: the legacy signature infers string[], not the tuple.
npm exec --yes --package=typescript@4.9.5 -- tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit pair.cts
```

The intermediate `inferred` binding keeps the tuple annotation from supplying
context to the generic call. TypeScript 7.0.2 and 5.0.4 select `modern/index.d.ts`; 4.9.5 selects
`legacy/index.d.ts`. The mapping replaces the matched `index.d.ts` path relative
to the package directory, so `modern/*` means `modern/index.d.ts` here, not
`dist/modern/index.d.ts`. Matching version ranges are considered in metadata
order; place the specific range before the catch-all.

The runtime prints `get,post`. Older syntax compatibility does not guarantee
identical inference. Change the argument to `identity(["get", "post"] as const)`:
all three compilers accept the tuple assignment and the runtime remains the same.
This is a useful compatibility test because it checks a type relationship that
matters to callers, not just whether a declaration parses.

Now add this `exports` field to the same package metadata, retaining the existing
`typesVersions` field:

```json
{
  "exports": {
    ".": { "types": "./index.d.ts", "default": "./index.cjs" }
  }
}
```

These NodeNext checks now read `exports` and ignore `typesVersions`. With the
original argument lacking `as const`, even TypeScript 7.0.2 rejects the tuple
assignment: the export points at the broad root signature. For modern export-map
resolution, replace that field with versioned type conditions:

```json
{
  "exports": {
    ".": {
      "types@>=5.0": "./modern/index.d.ts",
      "types": "./legacy/index.d.ts",
      "default": "./index.cjs"
    }
  }
}
```

TypeScript 7.0.2 and 5.0.4 again accept the original tuple test. TypeScript 4.9.5
uses the legacy declaration and accepts the `as const` variant. Node selects the
runtime `default` branch and still executes `index.cjs`. The
[module reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html#packagejson-typesversions)
covers both versioned type conditions and the cases where `typesVersions` is
ignored. Test every claimed resolver/compiler combination rather than assuming
one metadata field covers all of them.

### 4) **Choose release checks from the supported consumer contract**

For `calc-kit`, the actual release evidence is the generated file list, the local
tarball contents, strict declaration checks and runtime execution from the fresh
consumer. Add a negative check for omitted declarations and an intentional
public-subpath import. Keep build outputs fresh so stale files cannot conceal a
missing build step. Generated declarations describe the source compiler's view;
they do not validate an asserted runtime lie, as the previous authoring lesson
shows.

If bundler consumers are supported, run the installed package through a pinned
bundler as well. For example, from `consumer`, esbuild 0.28.2 can bundle this ESM
consumer and execute the resulting bundle:

```sh
npm exec --yes --package=esbuild@0.28.2 -- esbuild esm.mts --bundle --platform=node --format=esm --outfile=bundle.mjs
node bundle.mjs
```

The result is `esm 5 3 undefined`. This verifies that bundler's chosen branches
and transformation for this package. It does not establish every browser target,
loader or compiler option. If native TypeScript source consumers are supported,
Node 22.18.0 also runs this particular `esm.mts` from the consumer directory:

```sh
npm exec --yes --package=node@22.18.0 -- node esm.mts
```

That source file sits outside `node_modules` and imports the package's built
JavaScript. This test does not establish support for shipping TypeScript source
inside dependencies or for syntax such as the CommonJS consumer's `import =`.
Native execution and type checking remain separate checks.

### 5) **Common confusion**

There is no universal lookup ladder that always falls from export conditions to
top-level `types`, then community types, then ambient declarations. Resolution
mode, importer format, conditions, package metadata and program declarations all
matter. Use a minimal failing consumer and `--traceResolution` to identify the
actual path. A declaration shim can make a missing implementation type-check;
it cannot install a runtime package.

A module format and an API shape are also different. The sentinel `format`
exports expose a wrongly selected declaration branch here. Real packages may
have identical shapes in both builds and still require the correct module-kind
declarations and supported-runtime tests.

### 6) **Performance note**

Declarations and `typesVersions` do not add runtime validation or execute
JavaScript. Export conditions affect file selection, but this lesson has not
measured resolution speed, bundle size or startup latency. Their primary benefit
here is a clear and testable consumer contract. Supporting additional compiler
and runtime combinations increases build and maintenance work; choose that
matrix from actual support commitments rather than an invented timing formula.

### 7) **Mentor note**

Give a learner the correctly built producer and a tarball missing its declarations.
Ask why a source-directory check passes while the fresh strict consumer fails.
A sound answer inspects the packed files and resolved path before changing types.
Then ask whether the legacy `identity` signature preserves the modern inference:
the tuple test demonstrates why syntax compatibility and caller precision need
separate evidence.
