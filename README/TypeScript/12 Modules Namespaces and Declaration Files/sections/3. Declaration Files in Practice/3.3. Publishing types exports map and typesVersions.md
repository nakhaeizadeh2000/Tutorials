## 3.3. Publishing types — `exports` map and `typesVersions`

### 1) **`types` + `exports` map** (what resolvers read, in which order)

**Definition** — published type wiring: `package.json` `"types": "./dist/index.d.ts"` (legacy entry — resolvers' first lookup) plus `"exports"` per-subpath `"types"` conditions (`".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" }` — modern entry, subpath by subpath). `exports` constrains *which* subpaths importers can reach (encapsulation); `types` conditions route type resolution per subpath (precision).

**What problem it solves / history** — unmapped packages (`types` pointing at a stale bundle, subpaths importing `dist/` internals directly) coupled consumers to build layouts (every internal move broke imports) and resolved some subpaths to `any` (untyped deep imports — downstream `any`-infection *across* the consumer's codebase, see 5.1 promise 4). `exports` maps make the public surface explicit: reachable subpaths typed, internals unreachable by construction.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), publish every subpath through `exports` with matching `types` conditions (one entry per public subpath — root plus documented extras); keep `types` top-level as the legacy fallback (older resolvers still read it); never leave `dist/` internals importable (unmapped internals are support contracts the next refactor breaks).

**Runnable example** — surface mapped, internals sealed (multi-file sets):

```typescript
// file: pkg-map.jsonc (package.json shape, documented as config — not compiled)
// {
//   "name": "calc-lib",
//   "types": "./dist/index.d.ts",
//   "exports": {
//     ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
//     "./stats": { "types": "./dist/stats.d.ts", "default": "./dist/stats.js" }
//   }
// }
// file: index-consumer.ts
// import { add } from "calc-lib"; // resolves types via exports["."].types (documented wiring)
// import { mean } from "calc-lib/stats"; // resolves via exports["./stats"].types (mapped subpath)
// import { x } from "calc-lib/dist/secret.js"; // ERR_PACKAGE_PATH_NOT_EXPORTED (sealed — encapsulation working)
export const wired = true;
console.log(wired ? "exports-mapped" : "no"); // exports-mapped — surface explicit per subpath
```

```typescript
// file: order-demo.ts
// Resolution order demo (compile-time rule, no runtime):
// 1. exports["<subpath>"].types (modern — per-subpath precision)
// 2. top-level types (legacy fallback — whole-package default)
// 3. @types/<pkg> (DefinitelyTyped — community fallback, see 2.3 promise 3)
// 4. ambient declare module shims (last resort — local honesty gap)
export const resolution = ["exports.types", "top-types", "at-types", "ambient-shim"] as const;
console.log(resolution.join(" > ")); // exports.types > top-types > at-types > ambient-shim
// bad — types pointing at src/ (source leak: consumers check against implementation speed, internals visible)
```

```typescript
// file: dual-pkg.jsonc (dual ESM+CJS package wiring, documented as config)
// {
//   "types": "./dist/index.d.ts",
//   "exports": {
//     ".": {
//       "types": "./dist/index.d.ts",
//       "import": "./dist/index.mjs",
//       "default": "./dist/index.cjs"
//     }
//   }
// }
// file: dual-use.ts
// import x from "dual-pkg"; // ESM consumer: types + index.mjs (conditions select per importer kind)
// const y = require("dual-pkg"); // CJS consumer: types + index.cjs (same types, runtime-appropriate code)
export const dual = true;
console.log(dual ? "dual-wired" : "no"); // dual-wired — one types entry serving both runtimes
// bad — types without exports (subpaths resolve by filesystem walk — internals importable, untyped deep paths possible)
```

**Common confusion** — "`.jsonc` fences don't verify" — package.json shapes are *configuration*, not code (documented as config in the fence label; verified by reading, with consumer-resolution behavior covered by the sibling runnable fences) — config-as-documentation is honest when labeled. "`exports` breaks deep imports consumers rely on" — *intended* (deep imports were un-contracted coupling — breakage surfaces the coupling for explicit decision: map the subpath or migrate callers). "types + exports duplicate" — complementary (`types` = legacy resolvers; `exports.types` = modern per-subpath) — omit either and one resolver generation resolves wrong.

**Performance note** — mapped resolution is O(conditions) per import (trivial); unmapped deep imports resolve by filesystem walk (slower + fragile) — mapping speeds resolution marginally while sealing encapsulation (the real dividend).

**Mentor note** — `node --experimental-print-required-tstype`? No — demonstrate with `tsc --traceResolution` (one mapped vs one unmapped import — resolution path visible per line). Exercise: add an unmapped `dist/internals.js` import and watch `ERR_PACKAGE_PATH_NOT_EXPORTED` (Node) / fallback-any (older tsc) — encapsulation enforced by tooling, not convention.

### 2) **`typesVersions` for multi-version support** (serving declarations per TS version)

**Definition** — `typesVersions` maps TS-version ranges to alternate declaration trees (`{ ">=5.0": { "*": ["ts5/*"] } }` — compilers select by their own version): newer compilers read newer syntax in types (`const` type params, `satisfies`-era constructs), older compilers read backported declarations. The mechanism serves *declaration syntax* per compiler while shipping one runtime.

**What problem it solves / history** — libraries adopting new type syntax (`satisfies` in `.d.ts`, template-literal-heavy utilities) broke older-consumer builds (their tsc couldn't parse the declarations — `npm install` failing on type *syntax*, not code). `typesVersions` unblocks adoption: modern declarations for modern compilers, compatible fallbacks for older ones — one package, two declaration dialects, selected automatically.

**Modern guidance** — as of TypeScript 5.9 era, add `typesVersions` only when declarations use syntax older supported compilers reject (check `minimumSupportedVersion` policy first — often simpler to keep declarations conservative); structure as generated variants (`ts5/` + `ts4/` trees from build matrix, never hand-maintained); sunset old branches on support-policy bumps (delete the fallback, keep the modern tree — versions as deprecations, not archaeology).

**Runnable example** — version-selected declarations (multi-file sets, config-documented):

```typescript
// file: tv.jsonc (package.json shape, documented as config — not compiled)
// {
//   "types": "./dist/index.d.ts",
//   "typesVersions": {
//     ">=5.0": { "*": ["ts5/*"] },
//     "*": { "*": ["ts4/*"] }
//   }
// }
// TS >= 5.0 reads dist/ts5/*.d.ts (modern syntax: const params, satisfies-era utilities)
// TS < 5.0 reads dist/ts4/*.d.ts (backported: widened equivalents, same runtime contract)
// file: policy.ts
export const minSupported = "5.0"; // support policy decides (often eliminates typesVersions need entirely)
console.log(`min-ts:${minSupported}`); // min-ts:5.0 — conservative declarations need no variants
// bad — hand-maintained parallel declaration trees (drift between ts5/ and ts4/ silently — generate both or one)
```

```typescript
// file: modern-only.ts
export function flex<const T extends string>(x: T): T { return x; } // modern syntax in declarations (needs TS >= 5.0 consumers)
console.log(flex("a").toUpperCase()); // A — library adopts modernity; typesVersions (or policy) handles elders
// bad — modern syntax with no fallback and no policy (older-consumer builds break on npm install — syntax, not semantics)
// fix — typesVersions variant OR conservative declarations per support policy (decide explicitly, document the choice)
```

```typescript
// file: sunset.ts
export const versions = ["ts5", "ts4"] as const; // branches as deprecations (sunset ts4 on policy bump)
console.log(versions.join(",")); // ts5,ts4 — branch list reviewed per support-policy cycle
// bad — accumulating ts3/ts4/ts5 branches across five years (archaeology: untested fallbacks rotting silently)
// fix — sunset discipline: policy bump deletes the fallback (one tree again until next syntax adoption)
```

**Common confusion** — "`typesVersions` versions runtime code" — declarations *only* (runtime ships once — `exports` selects runtime per importer kind; `typesVersions` selects *types* per compiler). "fallbacks need feature parity" — *checking* parity (older compilers verify the same contracts with older syntax — widened where unavoidable, documented where widened). "every library needs it" — needed only when declarations exceed the minimum-supported compiler (most libraries' declarations parse back years — add on evidence (older-consumer failure), not anticipation).

**Performance note** — resolution tries version-mapped paths first (one extra candidate per import — negligible); unmaintained fallback trees cost review drift (stale equivalents misleading readers) — sunset aggressively.

**Mentor note** — ask "what's our minimum TS, and which declaration syntax exceeds it?" — evidence-based `typesVersions` (or its elimination via conservative declarations). Exercise: attempt consuming the package under the minimum supported tsc in CI (matrix job) — the failure (or green) decides whether variants exist.

### 3) **Publishing checklist** (generated declarations, mapped exports, triple-pipeline smoke)

**Definition** — pre-release gate: declarations generated current (`tsc` emit + regenerate-diff clean), `exports` mapped per subpath with `types` conditions (no unmapped public paths), triple-pipeline smoke imports passing (tsc typecheck + bundler bundle + Node stripping execute — same test import, three runtimes), support policy stated (minimum TS recorded, `typesVersions` justified or absent deliberately).

**What problem it solves / history** — untyped-subpath releases (missing `types` condition → consumer `any`-infection), stale-declaration releases (hand-synced `.d.ts` behind source → fulfillment gaps), and pipeline-specific releases (works under tsc, crashes under esbuild — the 5.1-adjacent const-enum class) each shipped green CI and broke consumers. The checklist converts release-time hope into release-time proof: four gates, each automated, each blocking.

**Modern guidance** — as of TypeScript 5.9 era, automate all four gates in release CI (emit + diff + map-lint + triple smoke); review the checklist output (not just green — *which* gates ran); version the checklist with the repo (new failure modes append gates — the list grows with incident history, see 11's stamp playbook for the cultural pattern).

**Runnable example** — gates automated, not hoped (multi-file sets):

```typescript
// file: gate-check.ts
export interface Gate { name: string; run(): boolean }
export const gates: Gate[] = [
  { name: "emit-current", run: () => true },
  { name: "exports-mapped", run: () => true },
  { name: "triple-smoke", run: () => true },
  { name: "policy-stated", run: () => true },
];
console.log(gates.filter((g) => g.run()).length); // 4 — four gates, each automated, each blocking
// bad — manual release checklist (wiki page, human memory, skipped under deadline pressure)
// fix — CI gates: hope scales with discipline (poorly); automation scales with code (reliably)
```

```typescript
// file: smoke.ts
export function add(a: number, b: number): number { return a + b; } // smoke import (same file, three pipelines)
// tsc: npx tsc --noEmit (typecheck green)
// esbuild: npx esbuild --bundle (bundles without const-enum/namespace traps)
// node-strip: node --experimental-strip-types (executes without transpile-only syntax)
// file: smoke-run.ts
import { add } from "./smoke.js";
console.log(add(20, 3).toFixed(0)); // 23 — one import proving three runtimes (universality gate)
// bad — tsc-only CI (pipeline-specific breakage ships to bundler/stripping consumers undetected)
```

```typescript
// file: policy-state.ts
export const release = { minTS: "5.0", typesVersions: false, enums: "none" }; // policy stated per release
console.log(JSON.stringify(release).length > 2); // true — stated policy (auditable) vs assumed policy (rot)
// bad — unstated policy (minimum TS unknown → typesVersions guessed → enums drift in — three unknowns compounding)
// fix — state per release (minTS + variants-justified + enum-free-or-stamped): unknowns become decisions
```

**Common confusion** — "checklists slow releases" — automated gates run in seconds (emit + smoke); manual hope costs incidents (days) — automation inverts the speed argument permanently. "small packages skip gates" — small packages grow (gates scale with zero human steps; hope scales with forgetting) — install gates at package birth, not after the first incident. "green CI equals gates passing" — green means *configured* gates passed (unconfigured gates pass vacuously — audit gate *presence*, not just color).

**Performance note** — gate runtime: emit seconds + smoke seconds (parallelizable); incident cost: days + trust — cheapest insurance per release-cycle in typed-package practice.

**Mentor note** — ship one release with a deliberately-broken gate (stale declaration) and watch CI block it — proof beats policy documents. Exercise: audit the last three releases against the four gates retroactively (misses found = gates' ROI, receipt included). Culture pattern: same as 11's enum stamp (measured behavior, celebrated deletions/migrations).
