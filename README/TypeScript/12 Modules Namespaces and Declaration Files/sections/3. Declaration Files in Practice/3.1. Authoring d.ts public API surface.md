## 3.1. Authoring d.ts public API surface

A declaration file describes the API the checker presents to consumers. It contains no executable implementation, but it may need non-exported supporting types, helper signatures or private-member markers to express exported contracts. Generation derives a declaration from the checked source; it does not prove that assertions are true or that a separate JavaScript transform/published package matches it.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Create a fresh directory with src and app subdirectories, no tsconfig.json and no dependencies. The .mts sources produce explicit ESM .mjs runtime files and .d.mts declarations. The consumer below imports the built lib artifact, so its checking boundary is the generated declaration rather than a direct source import.

### 1) **Generate the runtime and declaration artifacts**

Save src/api.mts. ClaimedNumber deliberately includes an unsafe assertion so that generation's limits can be observed later.

```typescript
interface InternalUser { id: string }
function double(value: number): number { return value * 2; }
export const twice: typeof double = double;
export function makeUser(id: string): InternalUser { return { id }; }
export const VERSION = "1.0";
export class Session {
  #id: string;
  constructor(id: string) { this.#id = id; }
  value(): string { return this.#id; }
}
export function claimedNumber(): number { return "oops" as unknown as number; }
```

Run `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --declaration --declarationMap --noEmitOnError --rootDir src --outDir lib src/api.mts`. It exits 0 and produces lib/api.mjs, lib/api.d.mts and lib/api.d.mts.map. The [declaration option](https://www.typescriptlang.org/tsconfig/declaration.html) describes the generated type artifact; .d.mts corresponds to this explicit ESM source.

Inspect lib/api.d.mts. InternalUser and double appear because exported declarations refer to them. Session contains a #private marker, its constructor and the value signature; no method implementation remains. VERSION uses a literal initializer spelling that describes its literal type. The file ends with an export marker and its declaration-map comment. These supporting declarations are not all additional named exports that consumers may import. Their presence serves the exported API's type relationships and private compatibility.

A declaration can therefore contain more names than the module's importable export list. Conversely, exporting a helper from the source intentionally exposes it even if its name or comment says internal; generation does not make API-design decisions for the author. Public documentation comments and deprecation guidance can also belong in declarations. Review the consumer contract, not just a count of declarations or added lines.

### 2) **Consume the generated API and its actual JavaScript**

Save app/consumer.mts:

```typescript
import { VERSION, twice, makeUser, Session, claimedNumber } from "../lib/api.mjs";
type User = ReturnType<typeof makeUser>;
const user: User = makeUser("u_1");
const session = new Session(user.id);
const promised: number = claimedNumber();
console.log(VERSION, twice(21), user.id, session.value());
console.log(typeof promised, promised);
// import { InternalUser } from "../lib/api.mjs"; // TS2459: locally declared, not exported
// import { double } from "../lib/api.mjs"; // TS2459
// new Session(123); // TS2345
```

Build with `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist app/consumer.mts`, then run `node dist/consumer.mjs`. Output is `1.0 42 u_1 u_1`, then `string oops`. Both commands exit 0. The lib import resolves to lib/api.d.mts for checking and lib/api.mjs at runtime. To inspect the checking input, add --listFiles with --noEmit to the consumer command: it lists the generated declaration, not src/api.mts.

ReturnType lets the consumer use the returned shape without importing InternalUser by name. The marked private-name imports are rejected; importing the original source path would not grant access to its unexported declarations either. Test internal behavior through the public contract or design an intentional internal testable module boundary, rather than assuming a source import bypasses exports.

The claimed number is actually a string. The double assertion instructed the checker to trust a false relationship, and the generated declaration faithfully publishes that trusted number promise. Remove the assertion from claimedNumber and check the library with --noEmit: returning oops as number fails with TS2322. Replace its body with `return 42;`, rebuild the library and run the consumer again. The final line becomes `number 42`, while its declaration still says claimedNumber(): number. A runtime repair can leave the public type declaration unchanged.

This is why generation is useful but not a runtime certificate. [Assertions and unknown values](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) own the trust boundary. If another tool emits JavaScript or rewrites exports, test that actual result too; [CommonJS interop](<../1. ES Modules/1.3. export equals and interop with CommonJS.md>) demonstrates export-shape differences. Generation does not automatically eliminate either unsafe assertions or a mismatched published artifact.

### 3) **Separate declaration-only output from a runtime provider**

Use a new empty types directory. Repeat the library build with --emitDeclarationOnly and --outDir types. It creates api.d.mts and its map, but no api.mjs. [EmitDeclarationOnly](https://www.typescriptlang.org/tsconfig/emitDeclarationOnly.html) is useful when another build supplies JavaScript or when only types are intended; it is not a runtime implementation mode.

Save app/types-only.mts:

```typescript
import { twice } from "../types/api.mjs";
console.log(twice(2));
```

Compile it with the consumer command, substituting app/types-only.mts. Checking passes through types/api.d.mts, but running dist/types-only.mjs fails with ERR_MODULE_NOT_FOUND because types/api.mjs does not exist. A type-only import could use a declaration without a runtime edge; this value import cannot. Do not accidentally let an old JavaScript file in an output directory conceal the missing provider.

Declaration maps are separate from JavaScript source maps. Inspect api.d.mts.map: its sources point back to src/api.mts relative to the map. Editors can use that information for source navigation, as the [declarationMap reference](https://www.typescriptlang.org/tsconfig/declarationMap.html) explains. The map does not embed the runtime implementation or guarantee that a consumer has those source files. This lesson inspected the actual map; no editor-navigation behavior was tested.

### 4) **Write a declaration deliberately when generation is not the source of truth**

Handwritten declarations can accurately describe existing JavaScript, foreign providers, loader contracts or a curated public boundary. They still need consumer checking and runtime agreement. When source generation owns an artifact, fix the source/configuration or intentional declaration-build step and regenerate rather than silently editing an output file that the next build will overwrite.

For a checking-only syntax example, save forms.d.mts:

```typescript
export declare const VERSION = "1.0";
export interface Options { debug?: boolean }
export declare function label(options: Options): string;
// export declare function wrong(): string { return "x"; } // TS1183: implementation in an ambient context
// export declare const invalid = { value: 1 }; // TS1254: this ambient const initializer is not a permitted literal form
```

Check with `tsc --strict --target es2022 --module nodenext --noEmit forms.d.mts`. The uncommented file passes, but it creates no VERSION or label implementation. Activate one negative at a time and check again to observe the stated rejection. Literal initializer syntax in an ambient constant declaration differs from an executable object initializer or function body. The [global/module provider examples](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>) show why a valid declaration still needs the promised runtime artifact.

Practice against the built boundary: add `export function triple(value: number): number { return value * 3; }` to src/api.mts. Before rebuilding lib, a consumer import of triple from ../lib/api.mjs must fail with TS2305 against the old declaration. Rebuild, add the import and print triple(3); it must produce 9. This tests generation and consumer inclusion, rather than merely compiling a source import. An unsuccessful build may leave previous output files present, so do not treat stale files as evidence that the new build passed.

A declaration diff can also change without adding a named export. Rename the private double helper and its typeof reference consistently, rebuild and inspect the supporting name change. The consumer behavior stays the same. Review exports, required argument/return shapes and supporting compatibility instead of assuming every added declaration line is a new public entry point. [Testing declaration consumers](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) owns the deeper package/type-test workflow.

### 5) **Common confusion**

Declaration generation does not mean only exported names appear as textual declarations. Supporting types and private markers can be necessary without making their names importable. A declaration also can legally use certain literal initializer syntax while still supplying no runtime value.

A generated contract can preserve a false asserted promise. Conversely, a correct runtime change can leave the declaration unchanged. Test the declarations consumers actually resolve and the JavaScript they actually load; a direct source import is a different checking boundary.

### 6) **Performance note**

Declaration files omit implementation bodies, while generation and maps add build artifacts and work. This lesson measured no consumer speedup, emit overhead, CI duration or complexity formula. Export spelling in a declaration does not determine a bundler's retained JavaScript; actual exports, graph usage and side effects matter. Choose generation and publication arrangements from the required artifacts, then measure the real workload if cost matters.

### 7) **Mentor note**

Ask the learner why double appears in api.d.mts but cannot be imported, then why promised prints string even though its declaration says number. Require them to locate the generated declaration in the consumer's file list. A strong answer distinguishes supporting type text, named exports, trusted assertions and the actual runtime file.
