## 3.2. Module augmentation at file scale

A module augmentation contributes declarations to an existing resolved module. Once included in a compiler program, its changes are visible to other consumers of that module in the program, even when the block sits inside a feature file. Moving the block into a .d.ts file does not change it from a private view into a shared view; program inclusion was already the relevant boundary.

Runtime changes follow a different graph. A declaration can describe an existing capability, or accompany actual patch code, but it never installs that code by itself. This lesson applies the [merging mechanics](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) to real files, consumers and loading order.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Create a fresh directory without tsconfig.json or dependencies. The only package is the local fixture below. Split multi-file fences at file markers. All TypeScript checks use `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext`, followed by the entry files and either --outDir out or --noEmit. Run each JavaScript entry in a fresh Node process.

### 1) **Create a package with one supported option missing from its types**

Create node_modules/client-mini and save its package.json:

```json
{
  "name": "client-mini",
  "version": "1.0.0",
  "main": "./index.cjs",
  "types": "./index.d.cts"
}
```

Save node_modules/client-mini/index.d.cts:

```typescript
export interface Options { host: string }
export function connect(options: Options): string;
export class Client { send(text: string): string }
```

Save node_modules/client-mini/index.cjs:

```javascript
exports.connect = options => `${options.host}:${options.retries ?? 0}`;
exports.Client = class Client {
  send(text) { return `sent:${text}`; }
};
```

The implementation already reads retries, but the declaration omits it. Client has send and deliberately has no ping method. These are independent gaps with different runtime requirements.

Save feature.mts and neighbor.mts at the project root:

```typescript
// file: feature.mts
export {};
declare module "client-mini" {
  interface Options { retries?: number }
}
// file: neighbor.mts
import { connect } from "client-mini";
console.log(connect({ host: "neighbor", retries: 2 }));
```

Check neighbor.mts alone with --noEmit: it fails with TS2353 because Options has no retries property. Now check or build `neighbor.mts feature.mts` together. Both files pass, and `node out/neighbor.mjs` prints `neighbor:2`. Neighbor imports no feature module. The augmentation's presence in the checking program affected its view anyway; no runtime patch was needed because this option already existed in the implementation.

Export {} makes feature.mts an external module. A top-level import could also establish that context; it need not specifically be an import of the augmented package. The declaration target is resolved from the augmenting file's location, and its base declarations must participate in the program. In this example neighbor's import brings them in. Checking feature.mts alone reports TS2664 on this baseline; adding `import "client-mini";` to feature makes that independent check work. The explicit package import is a useful inclusion step, while export {} alone only establishes module context. A script-style ambient declaration has different behavior, demonstrated in [ambient modules](<../2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>). Do not classify one form as a feature-local view and another as a globally shared package view. Separate compiler programs can have different included declarations, but that is a program/configuration boundary, not containment inside a block's source file.

### 2) **Keep a runtime patch in the entry's actual dependency graph**

Save patch.mts, use-client.mts and boot.mts:

```typescript
// file: patch.mts
import { Client } from "client-mini";
declare module "client-mini" {
  interface Client { ping(): string }
}
Client.prototype.ping = function(this: Client): string { return this.send("ping"); };
console.log("patch installed");
// file: use-client.mts
import { Client } from "client-mini";
console.log(new Client().ping());
// file: boot.mts
import "./patch.mjs";
import "./use-client.mjs";
```

Build `use-client.mts patch.mts` with --outDir out. The check passes because both files are included. Running `node out/use-client.mjs` alone nevertheless exits 1 with TypeError: ping is not a function. The compiler saw the augmented instance contract, but Node never loaded patch.mjs. Merely emitting or type-checking a patch file is not an initialization edge.

Build boot.mts and run `node out/boot.mjs`. It prints `patch installed`, then `sent:ping`. The entry's dependency graph now evaluates the installation before the consumer in this acyclic graph. Reverse boot's two imports and rebuild: the consumer executes first and throws before the patch installs. Restore the correct order. An application should make its initialization dependencies clear; do not generalize this small ordering experiment into a guarantee for arbitrary cyclic or asynchronous graphs.

The [Handbook augmentation example](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#module-augmentation) likewise separates an interface merge from prototype implementation and the consumer's import of that implementation. A runtime addition is therefore not automatically a reason augmentation is forbidden; it needs real code, a compatible target, loading evidence and an ownership decision. Avoid claiming that a declaration-only extension supplies the behavior.

If you own the consuming API and need no patched method, an explicit wrapper is another design. Save wrapper.mts:

```typescript
import { Client } from "client-mini";
function ping(client: Client): string { return client.send("ping"); }
console.log(ping(new Client()));
```

Build wrapper.mts alone and run out/wrapper.mjs: it prints `sent:ping` without loading a patch. Its behavior is explicit at the call site and it leaves the package's prototype unchanged. A wrapper, an upstream implementation change, a maintained patch or a fork have different compatibility and maintenance implications. Choose from the actual capability and control you need rather than a mandatory four-exit rule.

### 3) **Review type changes and upstream handoff as contracts**

Adding a required member to an augmented interface is legal, but can break existing constructions. Add tenant: string alongside retries in feature.mts. The interface declaration itself merges; neighbor's existing call now fails with TS2741 because tenant is missing. Supplying tenant makes the call check again, but this fixture's runtime does not use that field. Introduce such a requirement only when the intended contract warrants it, not because an optional-only rule is part of the language.

Changing an already-declared property to an incompatible type is a different case. Adding host: number to the same Options augmentation conflicts with the original host: string and reports TS2717. Full merge compatibility belongs in the canonical owner; this distinction is enough to review whether a proposed patch adds a requirement or contradicts an existing declaration.

For an upstream-fix simulation, restore the original feature.mts and add retries?: number to the fixture's bundled Options declaration. Neighbor now checks alone. Including feature.mts still succeeds because the duplicate property agrees, but it is redundant. Exclude the obsolete augmentation and run the consumer: neighbor:2 remains. That successful handoff establishes agreement for this fixture, not that all upstream changes automatically make every augmentation safe to delete.

If a later bundled declaration changes retries to string while the old augmentation still says number, the conflict can be exposed by checking both; hiding diagnostics or adding casts would conceal the disagreement. Inspect the installed version, actual implementation, effective declarations and consumer uses before changing the patch. Keep enough context to revisit it when upstream changes; an issue link is useful when available, but no particular comment format proves compatibility.

### 4) **Common confusion**

A declaration block in a module affects the resolved module's consumers throughout the checking program. It is not private to the file containing it. A .d.ts file is not inherently global either: imports/exports and module detection determine its context, while the project's included files determine whether it participates.

Type inclusion and runtime loading are separate. The use-client build passes with patch.mts present, yet its standalone runtime fails. Boot supplies the missing loading edge. The options augmentation needs no runtime patch because retries was already supported; the method augmentation needs one because ping was absent.

### 5) **Performance note**

Type-only augmentations erase. The prototype assignment, wrapper function, package evaluation and dependency loading remain. These examples measure no merge-cache cost, wrapper timing or runtime speedup. A declaration's file placement is a checking/ownership choice; it is not a reliable performance ranking or a substitute for testing initialization.

### 6) **Mentor note**

Have the learner check neighbor alone and then with feature, without changing neighbor's imports. Ask why the checking result changes. Next build use-client with patch but execute it alone; require an explanation of the missing runtime edge before accepting a type assertion as a fix. A strong answer can propose the explicit wrapper when patching the shared class is unnecessary.
