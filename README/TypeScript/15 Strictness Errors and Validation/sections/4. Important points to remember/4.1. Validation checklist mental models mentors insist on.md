## 4.1. Validation checklist — mental models mentors insist on

### 1) **Identify the guarantee and its consumer**

A good review starts with a concrete promise: which inputs are accepted, what representation is returned, what happens on failure and who observes the outcome. “Validated,” “safe” and “strict” are incomplete descriptions unless the implementation and consumer support the intended guarantee. This checklist synthesizes the worked lessons on **TypeScript 7.0.2** and **Node.js 20.20.2**; it adds no separate host or performance verification.

| Review question | Evidence to look for | A claim that needs correction |
|---|---|---|
| What does the check establish? | A precise condition, shape or normalization rule and malformed-input cases | A truthiness check proves every required value, or a number check proves a finite integer range |
| Who chooses failure behavior? | The actual branch, throw, returned failure or awaited rejection and its consumer | User input must always use predicates, or every expected failure must use Result |
| Does the signature match execution? | Correct predicate false cases, assertion bodies and callback behavior | A predicate cannot throw, an assertion is automatically correct, or Result prevents exceptions |
| Is the output representation suitable? | A distinct success/failure tag, meaningful payload and consumer narrowing | Any array can serve as an error discriminator for a generic parser |
| How long does the evidence last? | Ownership, mutation rules and current policy assumptions | Readonly annotations or an earlier successful parse make every later action valid |
| Which integration was checked? | Exact runtime, flags, dependencies and observed outcomes | A local mapping function proves an HTTP server, worker or monitoring integration |

Predicates and assertions both affect control-flow information. Their important application difference is how the caller uses a verdict versus successful continuation. An assertion can be appropriate for an input API whose consumer expects and handles that failure; a local explicit branch can enforce an invariant too. For the complete false-branch and continuation examples, use [1.2](<../1. Assertion Functions/1.2. Type predicates vs assertions caller vs thrower.md>). Do not turn a useful convention into a language-enforced division between recoverable input and programmer mistakes.

### 2) **Walk one proposed boundary through failure**

Suppose a change claims that returning Result makes a message handler exception-free, a readonly parsed User remains valid indefinitely, and calling a reporter means every failure was recorded. These promises need separate evidence.

First, follow a failed result to its consumer. The [Result example](<../2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>) shows an ignored result that compiles. It also shows callbacks and a Result-returning function throwing the original Error. The review must identify who narrows, propagates, defaults or adapts the returned failure, and which other exception channel remains. A default that discards an important missing-record error may be a product-policy mistake even when it is type-correct.

Next, inspect completion ownership. The [containment example](<../2. Error Values and Hierarchies/2.3. Never-throw boundaries and error budgets.md>) distinguishes a synchronous adapter holding a rejected promise from an asynchronous adapter that awaits it. Its reporter can fail synchronously or reject, and the caller receives that outcome separately. Repair a handler's claim by connecting the operation and reporter to observed completion, then defining what to do when reporting fails. A test that only confirms a fallback string cannot establish durable reporting or safe recovery after a fatal process exception.

Finally, inspect the data's lifetime. The [architecture example](<../3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) mutates a previously valid age through an alias. Its readonly view sees the invalid value. A separately owned frozen flat snapshot protects those particular fields, but a changed business-policy decision still needs current evidence. Choose ownership and representation deliberately; rechecking changed policy is not the same as repeating an unchanged shape check in every helper.

The resulting review asks for precise repairs, not one blanket prohibition: handle the modeled failure, specify the remaining exception policy, observe reporter completion and define validity assumptions. If the boundary deliberately drops an event or substitutes a default, explain what the consumer sees and which information is lost.

### 3) **Select checks that can falsify the promise**

A useful malformed-input matrix varies one relevant condition at a time. Reuse canonical examples instead of copying incomplete parsers into each caller.

| Promise under review | A discriminating check | What its result establishes |
|---|---|---|
| Required fields are parsed honestly | Wrong types, missing fields, arrays-as-objects and the declared accessor/inheritance policy | Whether the parser implements its accepted input contract |
| Collections retain meaning | Empty arrays, nested successful arrays, a sparse input and a bad later element | Whether success is distinguishable and invalid batches trigger actions prematurely |
| Schema types follow runtime behavior | Distinct input/output types, a required-field evolution and omitted versus explicit undefined keys | Which type projection and runtime presence policy the pinned schema implements |
| Diagnostics preserve the original | Same-object rethrow, wrapped cause, non-Error cause and a cycle | The implemented identity/stack/reporting limits, not universal reporter behavior |
| Failures are observed | Synchronous throw, promise rejection, reporter failure and a connected pending operation | Which completion paths the tested boundary actually owns |

The [hand-written parser](<../3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>) and [schema lesson](<../3. Schema Validation in Practice/3.2. Schema objects and inferred types.md>) deliberately have different reflective-input policies. Neither the presence of a schema library nor absence of assertions proves the intended requirements were checked. For example, a custom schema callback can claim the wrong output type without any downstream cast.

Run compile-time negative cases when the promise concerns a static contract, and execute failures when it concerns runtime behavior. Keep the distinction visible: accepting a source file, emitting JavaScript, running a local fixture and testing a real host integration establish different facts. Record commands, versions and actual outcomes. Do not count an unexecuted prediction or a successful link scan as verification of the teaching claim.

### 4) **Common confusion**

A check can be valid without proving everything a caller needs. A parser can establish shape while leaving authorization or current business state undecided. A readonly view can communicate intent while another reference still mutates the object. A returned error can be well modeled while the function or reporter still throws.

A downstream assertion deserves a specific justification, especially if it bypasses a failure branch. Its mere presence is not proof that a parser lied, and its absence is not proof of completeness. Review the implementation, input cases, consumer and evidence lifetime together.

### 5) **Performance note**

A checklist has no direct runtime effect. The chosen implementation may perform repeated traversal, copying, normalization, result allocation, stack collection or awaited reporting. Avoid unnecessary repeated checks when the same evidence remains valid, but do not remove checks for a new boundary or changed state merely to reduce a count. Compare representative workloads and retained data if cost affects the design. This synthesis adds no timing, allocation-rate or compiler-instantiation measurement.

### 6) **Mentor note**

Give the learner a boundary's signature and ask for its accepted input, success representation, failure consumer and validity lifetime. Then reveal an ignored result, a rejecting reporter or a mutable alias and ask which claim changes. A strong review proposes a falsifying check and a targeted repair, and explains which host behavior remains unverified. “No casts,” “uses Zod” and “compiled under strict” are useful observations, not completion criteria by themselves.
