## 2.3. Never-throw boundaries and error budgets

### 1) **Never-throw function contracts** (pure computation + handlers that must not propagate)

**Definition** — never-throw positions: pure computation consumed widely (formatters, mappers, comparators — throwing would poison every pipeline), event/callback handlers the runtime must survive (UI handlers, message consumers, timer callbacks — uncaught throws crash loops/processes), and `noUncheckedIndexedAccess`-style total functions (defined for every input — no invalid state to throw on). Contract: these functions *handle internally* (try/catch → fallback/log/report) and *never propagate* — enforced by review + tests (throw-injection tests proving containment).

**What problem it solves / history** — throws escaping never-throw positions crashed event loops (one handler's throw killing a UI thread's dispatch), poisoned `Promise.all` batches (one rejection failing ten parallel fetches), and broke `Array.map` pipelines (throwing mapper aborting whole transforms mid-array). Explicit never-throw contracts (documented + tested via throw-injection) convert these from incident classes to reviewed guarantees.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), mark never-throw positions (`// never-throws: catches internally, returns fallback` — documented contract); implement with internal try/catch → fallback/report (never bare); test by throw-injection (mock inner to throw — verify containment + fallback, not just happy paths). Reserve `throws` for programmer-error boundaries (invariants — see 1.1) and expected-failure Results (see 2.1).

**Runnable example** — containment contracts (good vs bad, `tsc --strict`):

```typescript
// good — event handler contains (internal try/catch → fallback + report — never propagates)
function onMessage(raw: string): string {
  try {
    const data = JSON.parse(raw) as { text?: unknown }; // may throw (malformed input — expected failure inside)
    return typeof data.text === "string" ? data.text.toUpperCase() : "empty";
  } catch (e) {
    console.log("message dropped"); // reported (observability preserved — containment isn't silence)
    return "empty"; // fallback (contract honored — handler never throws into the dispatcher)
  }
}
console.log(onMessage('{"text":"hi"}'), onMessage("{bad")); // HI empty — malformed input contained (dispatcher survives)
// bad — throwing handler (one malformed message crashing the dispatch loop — availability incident per bad input)
// fix — never-throw handlers (internal containment + fallback + report — contract documented, throw-injected in tests)
```

```typescript
// good — pure mapper total over inputs (defined for every element — no throw path exists)
function safe(n: unknown): string {
  if (typeof n === "number") return n.toFixed(0); // narrowed (numbers format)
  return "nan"; // total (every other input maps to a fallback — function defined on all inputs)
}
console.log(["a", 1, null].map(safe).join(",")); // nan,1,nan — map never aborts (totality by construction)
// bad — throwing mapper (one bad element aborting the whole transform — partial outputs, unclear state)
// fix — total mappers (fallback per kind — transform completes fully, invalid elements mapped honestly)
```

```typescript
// good — throw-injection tests prove containment (mock inner to throw — verify fallback, not just happy paths)
function contained(fn: () => string): string {
  try {
    return fn();
  } catch {
    return "fallback"; // contained (throw injected in tests → fallback verified — contract proven, not hoped)
  }
}
function boom(): string { throw new Error("x"); } // throw-injected double (test seam — inner failure simulated)
console.log(contained(() => "ok"), contained(boom)); // ok fallback — containment proven (both branches tested)
// bad — happy-path-only tests for never-throw contracts (containment unproven — first real throw tests it in production)
// fix — throw-injection suites (mock inners to throw per never-throw function — containment verified per contract)
```

**Common confusion** — "never-throw means infallible" — means *containing* (failures handled internally → fallbacks/reports — fallibility acknowledged, propagation refused). "containment hides bugs" — containment *reports* (logged + fallback) vs swallowing (silent) — report-every-containment distinguishes (observability preserved). "all functions should be never-throw" — programmer-error boundaries *must* throw (invariants — see 1.1); expected failures *return* Results (see 2.1) — never-throw contracts cover handlers/totals, not everything.

**Performance note** — try/catch costs nothing when untaken (zero-cost in modern JITs — setup free); thrown-and-caught costs stack capture per incident (exceptional by design — containment paths run rarely by construction). Never-throw contracts cost nothing steady-state (branches taken normally, catches dormant).

**Mentor note** — throw-inject one never-throw handler live (mock inner → verify fallback — containment proven in one test). Exercise: mark three never-throw positions and write throw-injection tests per contract (containment verified, not hoped). Review gate: throwing handlers/totals fail review (contain + fallback + report — contract documented).

### 2) **Error budgets per boundary** (which throws cross, which convert to values)

**Definition** — per-boundary policy stating *which* errors cross as throws (programmer bugs → crash reporting with stacks) and *which* convert to values (expected failures → Results/defaults at the boundary): API handlers (client errors → 4xx responses, never throws; server bugs → 500 throws + reports); library surfaces (typed throws documented per function vs Result returns); CLI entry points (exit codes per category — 0/1/2 mapped, never raw throws to users).

**What problem it solves / history** — unbudgeted boundaries threw everything (validation rejects crashing with stack traces users can't act on) or returned everything (programmer bugs flowing as `null` into distant crashes) — uniform handling mismatching both categories. Budgets assign per boundary: throws cross *programmer-error* boundaries (crash reporting consumes); values cross *expected-failure* boundaries (callers handle) — each boundary independently right, reviewably so.

**Modern guidance** — as of TypeScript 5.9 era, budget per boundary (API/library/CLI/worker — documented: throws-X/returns-Y per boundary); convert at the boundary (throws→responses inside handlers, never leaking; values→throws never — direction fixed); review budgets per boundary change (new error kind → budget decision recorded, not defaulted).

**Runnable example** — budgets per boundary (good vs bad, `tsc --strict`):

```typescript
// good — API boundary budget (client errors → responses; server bugs → throws + reports)
type ApiResult = { status: number; body: string };
function handleRequest(valid: boolean): ApiResult {
  if (!valid) return { status: 400, body: "bad request" }; // expected failure → VALUE (caller responds, never throws)
  return { status: 200, body: "ok" }; // success value (boundary converts — throws never cross to users)
}
console.log(handleRequest(false).status, handleRequest(true).status); // 400 200 — budgeted boundary (values for clients)
// bad — throw new Error("bad request") (client errors as exceptions — 500s for 400-situations, stack traces to users)
// fix — budget (expected→values at user boundaries; bugs→throws with reporting — per-boundary policy, documented)
```

```typescript
// good — CLI exit codes per category (0/1/2 mapped — never raw throws to terminals)
function cli(args: string[]): number {
  if (args.length === 0) return 2; // usage error → exit 2 (documented code — scripts branch on it)
  return 0; // success → exit 0 (categories mapped — terminals receive codes, not stacks)
}
console.log(cli([]), cli(["x"])); // 2 0 — budgeted exits (codes per category — automation-friendly)
// bad — uncaught throws as CLI errors (stack traces to terminals — users reading internals, scripts unable to branch)
// fix — exit-code mapping at CLI boundaries (categories → codes — terminals receive contracts, not crashes)
```

```typescript
// good — library surfaces document throw-vs-return per function (callers never guess)
function divide2(a: number, b: number): number { // throws on b === 0 (programmer error — documented below)
  if (b === 0) throw new Error("divide by zero (validate inputs before calling)"); // bug contract (fail-fast named)
  return a / b;
}
/** Returns undefined on missing keys (expected absence — value contract). */
function lookup2<K, V>(m: Map<K, V>, k: K): V | undefined {
  return m.get(k); // expected-absence contract (JSDoc states — callers handle, never guess)
}
console.log(divide2(6, 3).toFixed(0), lookup2(new Map([["a", 1]]), "zzz") ?? "miss"); // 2 miss — per-function contracts (throw vs return documented)
// bad — undocumented mixed surfaces (some functions throw misses, some return null — callers try/catch AND null-check defensively)
// fix — JSDoc per function (throws-X / returns-Y stated — discipline visible at every signature)
```

**Common confusion** — "budgets are bureaucratic" — one line per boundary (throws-X/returns-Y — seconds to write, permanent caller clarity). "uniform handling is simpler" — uniform *mishandles* half the categories (throws for expected (crashes) or values for bugs (corruption) — simplicity theater). "budgets never change" — new error kinds trigger budget review (recorded decision per kind — budgets evolve with understanding, explicitly).

**Performance note** — budgeted boundaries cost nothing steady-state (branches taken normally); unbudgeted boundaries cost incidents (500s for 400s, corruption for bugs — unbounded). Budgeting is pure incident prevention with zero runtime profile.

**Mentor note** — audit one boundary for both halves (throws documented? returns documented? mixed?) — half-budgeted boundaries are the incident queue, self-triaged. Exercise: write budget lines for three boundaries (API/library/CLI — throws-X/returns-Y each) and verify callers match (consumers reading the budget, not guessing). Review gate: undocumented throw-vs-return surfaces fail review.

### 3) **Top-level handling architecture** (one uncaught handler per runtime)

**Definition** — each runtime gets one uncaught-error handler: Node (`process.on("uncaughtException"/"unhandledRejection")` → log + report + graceful shutdown/restart); browsers (`window.onerror`/`unhandledrejection` → report + degraded UI); workers (parent-port error channel + restart policy). Handlers *report and degrade* (observability + continuity) — never resume normal operation blindly (unknown state post-uncaught).

**What problem it solves / history** — unhandled errors crashed processes silently (no logs — exit codes only), left browsers white-screened (no degradation — dead UI, no report), and lost in-flight work without trace (handlers absent — failures invisible *and* destructive). Top-level handlers convert unknown failures into *reported* degradation (logged, reported, restarted/degraded explicitly — worst case handled by design, not discovered in reviews).

**Modern guidance** — as of TypeScript 5.9 era, install one handler per runtime entry (Node main, worker bootstrap, browser shell — each logging + reporting + degrading); report with full causality (`cause` chains per 2.2 promise 3 — complete diagnostics, not top messages); degrade explicitly (restart policies, fallback UI, queued-work preservation — continuity designed, not hoped). Test handlers by fault-injection (throw in staging — verify report + degradation, not just absence of crash).

**Runnable example** — handlers per runtime (good vs bad, `tsc --strict`):

```typescript
// good — handler shape (report + degrade — one per runtime entry, tested by fault-injection)
interface Report { error: string; causes: string[] }
function report(e: unknown): Report {
  const chains: string[] = []; // cause-walk (see 2.2 promise 3 — full causality, not top messages)
  let cur: unknown = e;
  while (cur instanceof Error) {
    chains.push(cur.message);
    cur = (cur as { cause?: unknown }).cause;
  }
  return { error: chains[0] ?? "unknown", causes: chains.slice(1) }; // structured report (loggable, alertable, testable)
}
console.log(JSON.stringify(report(new Error("x")))); // {"error":"x","causes":[]} — report shape (handlers share it)
// bad — console.error(e) per catch (unstructured logs — ungreppable, unalertable, untestable as units)
// fix — shared report() (structured diagnostics — handlers identical across runtimes, tested once)
```

```typescript
// good — degraded operation (fallback serving while reporting — continuity by design)
function degraded<T>(fallback: T): T {
  return fallback; // continuity (fallback values serve — availability degraded gracefully; reporting happens at the handler layer, sampled)
}
console.log(degraded("cache"), degraded(0)); // cache 0 — degraded serving (continuity by design; sampled logging at handlers, not per call)
// bad — crash-only handling (process exits on first uncaught — availability zero during the failure window, state lost)
// fix — degrade-then-restart (serve fallbacks now, restart cleanly after — continuity + hygiene composed)
```

```typescript
// good — fault-injection tests prove handlers (throw in staging — verify report + degradation)
// (handler contract: report(e) structured + degraded(fallback) serving — both unit-tested below)
interface Report { error: string; causes: string[] } // re-declared: fences compile standalone (minimal shapes)
function report(e: unknown): Report {
  void e;
  return { error: "x", causes: [] };
}
function degraded<T>(fallback: T): T {
  return fallback;
}
function handled(fn: () => string): string {
  try {
    return fn();
  } catch (e) {
    const r = report(e); // reported (structured — test asserts shape + causes)
    void r;
    return degraded("fallback"); // degraded (continuity — test asserts fallback served)
  }
}
function fails(): string { throw new Error("boom"); } // fault-injected double (test seam — inner failure simulated)
console.log(handled(() => "ok"), handled(fails)); // ok fallback — handler proven (both branches tested — happy + fault paths)
// bad — untested handlers (first real failure tests the handler in production — worst moment, least information)
// fix — fault-injection suites (throw per handler path — report + degradation verified, not hoped)
```

**Common confusion** — "handlers resume normal operation" — handlers *degrade* (fallback serving + restart scheduling — unknown post-uncaught state never trusted for normal operation). "one handler covers all runtimes" — per-*entry* handlers (Node main, worker bootstrap, browser shell — each runtime's failure modes differ; shared `report()` shape, per-entry installation). "degradation hides incidents" — degradation *reports* (logged + alerted with full causality) while serving (availability preserved) — hidden incidents come from *unreported* degradation, never from reported fallbacks.

**Performance note** — handlers run on uncaught paths only (exceptional by definition — zero steady cost); cause-walking logs cost O(depth) per report (errors only); fallback serving costs normal-path values (availability preserved at fallback quality — degraded, not down).

**Mentor note** — fault-inject staging quarterly (throw per handler path — report + degradation verified, not hoped). Exercise: write one handler per runtime entry (Node/worker/browser shapes) sharing `report()` — coverage complete per entry, logic shared. Review gate: runtime entries without uncaught handlers fail review; untested handlers fail review.
