## 2.3. Never-throw boundaries and error budgets

### 1) **Specify which failures a boundary contains**

A boundary is a place where one caller hands responsibility to another component: a request handler invokes application code, a dispatcher invokes a callback, or a command invokes a library. A containment policy says which failures become returned values, which propagate, and who reports or recovers from them. “Never throw” is an implementation promise under stated conditions, not a TypeScript function-type feature.

Neither a Result return type nor `noUncheckedIndexedAccess` proves exception freedom. A synchronous function can throw despite its declared return type. A function can also return a promise successfully and have that promise reject later. Pure computations, array callbacks and framework handlers do not all need the same failure policy; choose the behavior their consumer expects.

This lesson uses **TypeScript 7.0.2** with emitted ES2022 modules on **Node.js 20.20.2**. Save the following two TypeScript files in an empty directory without a `tsconfig.json`. Compile with `tsc --strict --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist boundary.mts demo.mts`, then run `node dist/demo.mjs`. No dependencies or server are involved.

The small Attempt union is a local application of the [Result contract](<./2.1. Error as value Result Ok Err patterns.md>). `attempt` converts synchronous callback exceptions. `attemptAsync` awaits the callback's completion, so it also converts rejections. These helpers preserve the caught value as `unknown`; classification needs evidence rather than a cast.

```typescript
// file: boundary.mts
export type Attempt<Value> = { ok: true; value: Value } | { ok: false; error: unknown };
export function attempt<Value>(work: () => Value): Attempt<Value> {
  try { return { ok: true, value: work() }; }
  catch (error) { return { ok: false, error }; }
}
export async function attemptAsync<Value>(
  work: () => Value | PromiseLike<Value>,
): Promise<Attempt<Value>> {
  try { return { ok: true, value: await work() }; }
  catch (error) { return { ok: false, error }; }
}
export type Delivery =
  | { kind: "delivered"; value: string }
  | { kind: "dropped"; error: unknown; report: Attempt<void> };
export async function deliver(
  work: () => string | PromiseLike<string>,
  report: (error: unknown) => void | PromiseLike<void>,
): Promise<Delivery> {
  const outcome = await attemptAsync(work);
  if (outcome.ok) return { kind: "delivered", value: outcome.value };
  const reported = await attemptAsync(() => report(outcome.error));
  return { kind: "dropped", error: outcome.error, report: reported };
}
```

The caller receives both the original failure and the reporting outcome. A reporter that fails does not replace the original error or become a claim that reporting succeeded. This example uses the word “dropped” for a deliberate local event policy; it does not implement a queue acknowledgment, retry, transaction rollback or persistent incident record.

### 2) **Observe synchronous throws, rejections and reporter failures**

```typescript
// file: demo.mts
import { attempt, attemptAsync, deliver, type Attempt } from "./boundary.mjs";
const failure = new Error("operation failed");
const sinkFailure = new Error("reporter failed");
let reports = 0;
const record = (_error: unknown): void => { reports++; };
const throwOperation = (): string => { throw failure; };
const throwReporter = (_error: unknown): void => { reports++; throw sinkFailure; };
const rejectReporter = async (_error: unknown): Promise<void> => { reports++; throw sinkFailure; };
const cases: [string, () => string | PromiseLike<string>, (error: unknown) => void | PromiseLike<void>][] = [
  ["success", () => "ready", record],
  ["sync", throwOperation, record],
  ["rejection", () => Promise.reject(failure), record],
  ["report-sync", throwOperation, throwReporter],
  ["report-async", () => Promise.reject(failure), rejectReporter],
];
for (const [label, work, report] of cases) {
  const outcome = await deliver(work, report);
  if (outcome.kind === "delivered") console.log(label, outcome.kind, outcome.value);
  else {
    console.log(label, outcome.kind, outcome.error === failure, outcome.report.ok);
    if (!outcome.report.ok) console.log("report error preserved", outcome.report.error === sinkFailure);
  }
}
console.log("report attempts", reports);
const later = attempt(() => Promise.reject(failure));
console.log("sync adapter returned promise", later.ok);
if (later.ok) {
  try { await later.value; }
  catch (error) { console.log("caller caught later rejection", error === failure); }
}
const asynchronous = await attemptAsync(() => Promise.reject(failure));
console.log("async adapter returned failure", !asynchronous.ok && asynchronous.error === failure);
const purported = (): Attempt<string> => { throw failure; };
try { purported(); }
catch (error) { console.log("signature permits throw", error === failure); }
// const payload: string = asynchronous.value; // TS2339: narrow the returned Attempt.
// const immediate: Attempt<string> = deliver(() => "x", record); // TS2322: await completion first.
```

Expected output:

```text
success delivered ready
sync dropped true true
rejection dropped true true
report-sync dropped true false
report error preserved true
report-async dropped true false
report error preserved true
report attempts 4
sync adapter returned promise true
caller caught later rejection true
async adapter returned failure true
signature permits throw true
```

Success does not call the reporter. Both operation failure modes reach reporting, and both reporter failure modes are visible separately. `attempt` returns a successful result holding a promise before that promise's rejection is observed; the caller explicitly catches it. `attemptAsync` instead returns a failed Attempt after awaiting the rejected operation. Removing the `await` inside that helper would change the contract.

The contained work must be connected to the returned completion. Starting a timer or an independent promise and then returning success does not make that detached work part of the helper's catch. A hanging operation or reporter also prevents `deliver` from finishing; this implementation has no timeout, cancellation or retry policy. It handles ordinary exceptions and rejections of the supplied callbacks, not process termination or resource exhaustion.

Sometimes a framework expects a rejected promise or a thrown exception and has its own boundary that translates it. Adapting a failed Result into a throw can therefore be appropriate. The adaptation must retain useful context and have an observing consumer. There is no universal one-way rule requiring every expected failure to return a value or every bug to escape as a throw. Catching everything and calling it a recoverable fallback can hide failures the application cannot safely recover from.

### 3) **Separate local recovery from fatal process diagnostics**

A handled failure inside a request or task can have a known recovery policy. A Node exception that has escaped to the process level has a different scope. [Node's process documentation](https://nodejs.org/download/release/v20.20.2/docs/api/process.html#warning-using-uncaughtexception-correctly) advises shutdown rather than resuming normal work after an uncaught exception. A process-level diagnostic hook is not evidence that continuing to serve cached responses is safe.

Use a separate disposable process to observe fatal behavior. Save this JavaScript as `fatal.mjs`; it uses built-in modules and needs no TypeScript Node typings. Run `node --unhandled-rejections=strict fatal.mjs throw` and, separately, `node --unhandled-rejections=strict fatal.mjs reject`. Both commands intentionally exit with code 1 in this environment.

```javascript
// file: fatal.mjs
import { writeSync } from "node:fs";
process.on("uncaughtExceptionMonitor", (error, origin) => {
  writeSync(2, "monitor:" + origin + ":" + error.message + "\n");
});
setTimeout(() => {
  if (process.argv[2] === "reject") {
    void Promise.reject(new Error("fatal-rejection"));
  } else {
    throw new Error("fatal-throw");
  }
}, 0);
```

The first command prints `monitor:uncaughtException:fatal-throw` to standard error, followed by Node's fatal diagnostic. The second prints `monitor:unhandledRejection:fatal-rejection`, followed by a fatal diagnostic. Paths and stack frames vary. `uncaughtExceptionMonitor` observes these failures without overriding Node's default exit behavior. This example does not install an `uncaughtException` recovery listener. Its synchronous diagnostic write is also best effort, not a guarantee of durable remote reporting.

Default rejection behavior can depend on runtime flags and installed listeners, so the commands make the rejection mode explicit. Browser event handling, worker supervision, application shutdown, external restart and a framework's request exception handling require their own integration tests. This isolated process check establishes none of those integrations, nor a mandatory count of global handlers.

Finally, a **service error budget** is a quantitative reliability allowance tied to a service-level objective over a measurement window. It is not the list of exceptions a function permits. [Google's SRE explanation](https://sre.google/sre-book/embracing-risk/) gives the reliability meaning. Exception handling can affect measured success, but merely returning a fallback does not prove an operation met its promised service outcome. Define success and measure it before claiming budget compliance; this lesson measures no deployed service objective.

### 4) **Common confusion**

A catch surrounding a call only sees failures that occur within its observed execution. Returning a promise from a synchronous try is different from awaiting that promise inside the try. Calling a reporting callback is also different from awaiting its result and checking whether it succeeded.

“Never throw” does not mean infallible, necessarily quick, terminating or safe after an unrelated fatal process failure. Name the caller, connected completion, conversion policy and reporting limits. Use “error budget” for a measured reliability allowance, and “boundary policy” for the choice between propagation, returned errors and recovery.

### 5) **Performance note**

The policy itself is documentation, while its implementation performs branches, constructs result objects and may await work and reporting. Awaiting the reporter can delay completion, and a reporter without a completion bound can delay it indefinitely. The example reports callback attempts and outcomes, not timings or the cost of try/catch. No zero-overhead, JIT behavior, throughput or incident-prevention rate was measured. Reuse the Error lesson for construction/stack costs rather than attributing them to throwing alone.

### 6) **Mentor note**

Ask which callback failures each adapter observes, then predict the successful Attempt that contains a rejected promise. Make the reporter reject and check that the original and reporter errors both survive. Ask what a detached timer changes and why a process-level monitor cannot turn an unknown fatal state into validated local recovery. A sound review identifies actual completion ownership and reports exactly which local and host checks ran.
