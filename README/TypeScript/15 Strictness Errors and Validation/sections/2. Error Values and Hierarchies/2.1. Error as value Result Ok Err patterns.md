## 2.1. Error as value — `Result`, `Ok`, `Err` patterns

### 1) **`Result<T, E>` shape** (discriminated failure typed into signatures)

**Definition** — `type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }` — every fallible operation returns *either* success *or* typed failure (never throws for expected cases, never `null` for errors). Consumers narrow on `ok` (discriminant — see 07/1.2): `if (r.ok) ... value ... else ... error ...` — exhaustiveness enforced, unhandled errors unrepresentable.

**What problem it solves / history** — thrown errors for *expected* failures (missing records, validation rejects, network timeouts) forced `try/catch` at every call site (or uncaught rejections crashing processes — see 5.1 promise 2) while *hiding* failure modes from signatures (`getUser(id): User` — throws undocumented NotFound). Result types *declare* failure (callers see `Result<User, NotFound>` and handle both branches — the signature is the complete contract, success and failure alike).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), return Results for expected failures (lookups, parsing, validation, I/O with known failure modes); throw for programmer errors (invariant violations, unreachable branches — see 1.1/1.2's decision rule); keep `E` precise (string-literal unions or error classes per failure kind — never `unknown`-shaped errors that force re-narrowing per consumer).

**Runnable example** — failure declared, both branches handled (good vs bad, `tsc --strict`):

```typescript
// good — Result declares failure (both branches handled, exhaustiveness enforced)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
type NotFound = { kind: "missing"; id: string };
function find(names: Map<string, string>, id: string): Result<string, NotFound> {
  const v = names.get(id);
  return v === undefined ? { ok: false, error: { kind: "missing", id } } : { ok: true, value: v };
}
const db = new Map([["u1", "Ada"]]);
const r = find(db, "u2");
console.log(r.ok ? r.value.toUpperCase() : `missing:${r.error.id}`); // missing:u2 — handled branch (narrowed by ok)
// const v2 = find(db, "u1"); if (v2.ok) console.log(v2.value); // narrowed value (error branch excluded by discriminant)
```

```typescript
// good — helpers keep Results composable without throwing mid-chain (see promise 2 for map/andThen)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone
function fullName(first: string | undefined, last: string | undefined): Result<string, string> {
  if (first === undefined) return { ok: false, error: "missing first" }; // typed failure (string error kind here)
  if (last === undefined) return { ok: false, error: "missing last" };
  return { ok: true, value: `${first} ${last}` }; // success shape (both inputs proven present)
}
const f = fullName("a", undefined);
console.log(f.ok ? f.value.toUpperCase() : f.error); // missing last — failure value (not a throw — composable downstream)
// bad — throw new Error("missing last") (expected absence as exception — callers try/catch per call or crash)
// fix — Result returns (expected failures compose; throws reserved for programmer errors per 1.2's rule)
```

```typescript
// good — precise E per failure kind (consumers narrow errors, not just successes)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone
type Validation = { kind: "short"; min: number } | { kind: "blank" };
function checkName(s: string): Result<string, Validation> {
  if (s === "") return { ok: false, error: { kind: "blank" } };
  if (s.length < 2) return { ok: false, error: { kind: "short", min: 2 } };
  return { ok: true, value: s };
}
const c = checkName("x");
if (!c.ok && c.error.kind === "short") console.log(`min:${c.error.min}`); // min:2 — error narrowed (kind discriminant on E too)
// bad — Result<string, string> everywhere (error strings unparseable — consumers string-match failure kinds — fragile, untestable)
// fix — precise E (literal unions/classes per kind — errors narrow like values do)
```

**Common confusion** — "Results replace try/catch" — Results replace *expected-failure* throws (lookups, parsing, validation); *programmer-error* throws stay (invariants, unreachable — see 1.1). "Result helpers (map/andThen) complicate" — helpers *remove* nesting (`andThen` chains read top-down vs nested `if (!r.ok) return r` ladders) — learn two helpers, delete ten ladders. "`E` should be `Error`" — `E` should be *precise* (literal unions for kinds, classes for rich errors — `Error`-typed E forces `instanceof` chains per consumer; precise E narrows by discriminant).

**Performance note** — Result objects allocate per call (one small object — same as thrown-error allocation *without* the stack-capture cost; throws are expensive precisely because of stacks). Success-path overhead: one discriminant check per consumption (branch-predictable, negligible). Results are *cheaper* than throws on failure paths (no stack capture) and marginally costlier on success paths (one wrapper object — measure past millions/sec before caring).

**Mentor note** — convert one throwing lookup to Result live (signature gains the failure branch, call sites gain handling, tests gain the error case) — declared-failure value in one refactor. Exercise: classify five throwing functions (expected-failure → Result; programmer-error → keep throwing) — decision per function, documented. Review gate: throwing expected failures fails review (Results declare); returning programmer errors fails review (invariants throw).

### 2) **Chaining without throwing** (`map`/`andThen`/`unwrapOr` helpers)

**Definition** — Result combinators: `map(r, f)` transforms successes (failures pass through untouched); `andThen(r, f)` chains fallible steps (each step's failure short-circuits the rest — no nesting); `unwrapOr(r, fallback)` extracts with default (boundary exit from Result-land to values). Three helpers replacing every `if (!x.ok) return x` ladder with top-down pipelines.

**What problem it solves / history** — manual Result plumbing (`const a = step1(); if (!a.ok) return a; const b = step2(a.value); if (!b.ok) return b; …` — ladder growing per step, error paths dominating happy paths visually) punished Result adoption (verbose vs throwing one-liners). Combinators restore parity: `andThen(andThen(parse(raw), validate), save)` reads top-down like the happy path *is* the whole program — failures short-circuit invisibly but precisely.

**Modern guidance** — as of TypeScript 5.9 era, chain multi-step fallible pipelines with `andThen` (parse → validate → save reading top-down); transform successes with `map` (single-step value changes); exit with `unwrapOr`/`match` at boundaries (Results convert to values/responses once — never leak `Result` across API boundaries unhandled). Keep helpers in one utils module (tested once — combinator laws verified, not hoped).

**Runnable example** — pipelines read top-down (good vs bad, `tsc --strict`):

```typescript
// good — andThen chains fallible steps (failures short-circuit invisibly but precisely)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone
function andThen<T, U, E>(r: Result<T, E>, f: (v: T) => Result<U, E>): Result<U, E> {
  return r.ok ? f(r.value) : r; // failure passes through untouched (short-circuit without nesting)
}
function parseNum(s: string): Result<number, string> {
  const n = Number(s);
  return Number.isNaN(n) ? { ok: false, error: `bad:${s}` } : { ok: true, value: n };
}
function double(n: number): Result<number, string> { return { ok: true, value: n * 2 }; }
const chained = andThen(andThen(parseNum("21"), double), double);
console.log(chained.ok ? chained.value.toFixed(0) : chained.error); // 84 — three steps, zero nesting (failures short-circuit)
// bad — ladder plumbing (if-ok ladders growing per step — error paths dominating happy paths visually)
// fix — andThen (pipelines read top-down — happy path IS the program text; failures short-circuit precisely)
```

```typescript
// good — map transforms successes (failures flow through untouched — no branch at the call site)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone
function map<T, U, E>(r: Result<T, E>, f: (v: T) => U): Result<U, E> {
  return r.ok ? { ok: true, value: f(r.value) } : r; // success transformed (failure untouched — no handling needed here)
}
function parseNum(s: string): Result<number, string> { // re-declared: fences compile standalone
  const n = Number(s);
  return Number.isNaN(n) ? { ok: false, error: `bad:${s}` } : { ok: true, value: n };
}
const m = map(parseNum("10"), (n) => n + 1);
console.log(m.ok ? m.value.toFixed(0) : m.error); // 11 — transformed success (failure would flow through identically)
// bad — if (r.ok) { ...f(r.value)... } else { return r } per transformation (ladder per map — combinator deleted)
// fix — map (single-step transforms without branches — failures pass through by construction)
```

```typescript
// good — unwrapOr exits Result-land at boundaries (defaults documented at the exit, not scattered)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone
function unwrapOr<T, E>(r: Result<T, E>, fallback: T): T {
  return r.ok ? r.value : fallback; // exit (Result converts to values once — boundaries only, never mid-pipeline)
}
function parseNum(s: string): Result<number, string> { // re-declared: fences compile standalone
  const n = Number(s);
  return Number.isNaN(n) ? { ok: false, error: `bad:${s}` } : { ok: true, value: n };
}
console.log(unwrapOr(parseNum("oops"), 0).toFixed(0), unwrapOr(parseNum("5"), 0).toFixed(0)); // 0 5 — exits with documented defaults
// bad — leaking Result across API boundaries (consumers unwrap per use — failure handling scattered per caller)
// fix — unwrapOr/match at boundaries (convert once — downstream flows trusted values, never Results)
```

**Common confusion** — "combinators obscure control flow" — combinators *linearize* it (top-down pipeline vs nested ladders — failures short-circuit invisibly *but precisely*, each step's error preserved). "helpers need a library (never hand-roll)" — three 3-line helpers, tested once (laws: map-identity, andThen-associativity — verified, not hoped); libraries (neverthrow et al.) add ecosystem weight justified past threshold use. "unwrapOr hides failures" — unwrapOr *documents defaults at exits* (fallback visible at the boundary — failures handled once, loudly, where values resume).

**Performance note** — combinators allocate per step (one closure + one Result object — same as manual ladders; abstraction without overhead). Short-circuiting skips downstream steps on failure (faster failure paths than ladder equivalents checking per step — negligible either way; readability is the dividend, not speed).

Review gate: `if (!r.ok) return r` ladders past 2 steps fail review (andThen chains).

### 3) **Throw vs return discipline** (programmer errors throw; expected failures return)

**Definition** — the boundary rule: *programmer errors* (invariant violations, unreachable branches, misuse of internal APIs — caller did something no valid program does) → `throw` (fail-fast, named, crash-reportable). *Expected failures* (missing records, invalid input, timeouts, conflicts — valid programs encounter these routinely) → `return` Results (typed, composable, handled per call site). Mixed discipline (throwing lookups, returning invariant violations) mismatches both halves.

**What problem it solves / history** — undisciplined error styles (throwing `NotFound` (expected — every lookup site try/catches or crashes) alongside returning `null` for programmer misuse (bugs flowing as values into distant crashes)) forced callers to guess per function (try/catch? null-check? both?) — each guess wrong half the time, incidents split evenly between uncaught throws and unchecked nulls. Discipline makes the style *predictable from the category*: expected→Result, bug→throw, always.

**Modern guidance** — as of TypeScript 5.9 era, classify per function (expected-failure → Result return; programmer-error → named throw; genuinely uncertain → Result (safer default — callers handle; throws surprise)); document the discipline per module boundary (public APIs state throw-vs-return in JSDoc — callers never guess); never `throw` across trust boundaries to users (400-responses via Results; 500s reserved for bugs).

**Runnable example** — discipline per category (good vs bad, `tsc --strict`):

```typescript
// good — expected failure returns (lookup miss is routine — typed, handled, composable)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone
function lookup(ids: Map<string, string>, id: string): Result<string, { kind: "missing" }> {
  const v = ids.get(id);
  return v === undefined ? { ok: false, error: { kind: "missing" } } : { ok: true, value: v }; // expected (misses happen — returned)
}
const db2 = new Map([["a", "A"]]);
const found = lookup(db2, "zzz");
console.log(found.ok ? found.value : "not-found"); // not-found — routine miss (handled per call site, never thrown)
// bad — throw new Error("missing") on lookup miss (expected absence as exception — callers try/catch per lookup or crash)
// fix — Result returns (misses compose; throws reserved for bugs — discipline per category, predictable per function)
```

```typescript
// good — programmer error throws (invariant violated — no valid program continues this path)
function divide(a: number, b: number): number {
  if (b === 0) throw new Error("divide by zero (programmer error — validate inputs before calling)"); // bug (caller violated contract — fail-fast named)
  return a / b;
}
console.log(divide(6, 3).toFixed(0)); // 2 — valid call (invalid calls throw loudly — never silently return NaN/Infinity)
// bad — return NaN on zero-divide (bug flowing as a value — NaN poisons downstream arithmetic silently for pages)
// fix — throw programmer errors (fail-fast named — bugs crash loudly at cause, never flow as values)
```

```typescript
// good — mixed API documented per function (callers never guess throw-vs-return)
function parsePort2(raw: string): number | undefined { // undefined-return for expected absence (documented choice below)
  const n = Number(raw);
  return Number.isNaN(n) ? undefined : n; // expected failure as undefined (lightweight Result — documented discipline)
}
console.log(parsePort2("x") ?? "bad-port", parsePort2("80")); // bad-port 80 — documented discipline (JSDoc states undefined-means-invalid — callers handle, never guess)
// bad — undocumented mixed style (some functions throw misses, some return null — callers try/catch AND null-check everything, defensively bloated)
// fix — per-function documentation (JSDoc states throw-vs-return — discipline visible at every signature)
```

**Common confusion** — "Results everywhere (never throw)" — programmer errors *must* throw (returning bugs as values flows corruption downstream — fail-fast exists because some paths have no valid continuation). "throws everywhere (simpler)" — expected failures as throws force try/catch per call (ceremony) or crash on routine misses (incidents) — simplicity theater. "async changes the rule" — async *transports* identically (rejected promises ≈ throws; `Result`-valued resolutions ≈ returns — same categories, same discipline, different syntax — see domain 18).

**Performance note** — throws cost stack capture per throw (expensive — reserved for exceptional programmer errors); Results cost one wrapper object per call (cheap — routine failures stay cheap). Discipline aligns cost with frequency (cheap paths cheap, exceptional paths exceptional) — economics favoring correctness automatically.
