## 2.1. Error as value — `Result`, `Ok`, `Err` patterns

### 1) **Model returned success and failure explicitly**

A Result is a discriminated union describing a returned success or failure. The success variant carries a value; the failure variant carries an error value. Callers narrow on the tag before using the corresponding payload. This makes modeled failures visible in a signature, but TypeScript does not force every result to be consumed and the signature does not prohibit thrown exceptions.

This lesson uses **TypeScript 7.0.2** and emitted modules on **Node.js 20.20.2**. Save the two files below in an empty directory without a `tsconfig.json`. There are no package dependencies. Compile with `tsc --strict --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist result.mts demo.mts`, then run `node dist/demo.mjs`.

The lowercase `ok` and `err` factories construct the variants. `map` changes a successful value, `andThen` runs another fallible step, and a failure short-circuits either helper. Different steps can contribute different error types, so `andThen` returns their union.

```typescript
// file: result.mts
export type Result<Value, Failure> =
  | { ok: true; value: Value }
  | { ok: false; error: Failure };
export function ok<Value>(value: Value): Result<Value, never> { return { ok: true, value }; }
export function err<Failure>(error: Failure): Result<never, Failure> { return { ok: false, error }; }
export function map<Value, Next, Failure>(
  result: Result<Value, Failure>, transform: (value: Value) => Next,
): Result<Next, Failure> {
  return result.ok ? ok(transform(result.value)) : result;
}
export function andThen<Value, Next, FirstFailure, NextFailure>(
  result: Result<Value, FirstFailure>, next: (value: Value) => Result<Next, NextFailure>,
): Result<Next, FirstFailure | NextFailure> {
  return result.ok ? next(result.value) : result;
}
export function unwrapOr<Value, Failure>(result: Result<Value, Failure>, fallback: Value): Value {
  return result.ok ? result.value : fallback;
}
export function unwrapOrElse<Value, Failure>(
  result: Result<Value, Failure>, fallback: (error: Failure) => Value,
): Value {
  return result.ok ? result.value : fallback(result.error);
}
```

These helpers deliberately call callbacks directly. They do not wrap callback exceptions into `Err`. This is also a useful distinction to inspect in a real library: the [neverthrow source](https://github.com/supermacro/neverthrow/blob/master/src/result.ts) separates map/andThen callback application from explicit exception-conversion facilities. Its [documentation](https://github.com/supermacro/neverthrow) separately describes lint support for requiring consumption. This lesson runs its own small implementation, not that package or plugin.

### 2) **Trace short-circuiting, error unions and defaults**

The application accepts an ASCII decimal digit string representing an integer port from 1 through 65535. Empty strings, spaces, signs, fractional notation and `Infinity` do not meet that grammar. This is an explicit application contract; `Number(raw)` alone would accept or coerce more inputs. A second step looks up a label in a local map. No network connection or server is involved.

```typescript
// file: demo.mts
import { ok, err, map, andThen, unwrapOr, unwrapOrElse, type Result } from "./result.mjs";
type ParseFailure = { kind: "syntax"; raw: string } | { kind: "range"; raw: string };
type Missing = { kind: "missing"; port: number };
type Failure = ParseFailure | Missing;
function parsePort(raw: string): Result<number, ParseFailure> {
  if (!/^[0-9]+$/.test(raw)) return err({ kind: "syntax", raw });
  const value = Number(raw);
  if (!Number.isInteger(value) || value < 1 || value > 65535) return err({ kind: "range", raw });
  return ok(value);
}
const labels = new Map<number, string>([[80, "http"], [443, "https"]]);
let lookups = 0;
let transforms = 0;
function lookup(port: number): Result<string, Missing> {
  lookups++;
  const value = labels.get(port);
  return value === undefined ? err({ kind: "missing", port }) : ok(value);
}
function resolve(raw: string): Result<string, Failure> { return andThen(parsePort(raw), lookup); }
function describe(result: Result<string, Failure>): string {
  if (result.ok) return result.value;
  return result.error.kind === "missing" ? "missing:" + result.error.port : result.error.kind;
}
for (const raw of ["80", "x", "70000", "8080", "", "Infinity"]) {
  const result = map(resolve(raw), label => { transforms++; return label.toUpperCase(); });
  console.log(JSON.stringify(raw), describe(result));
}
console.log("calls", lookups, transforms);
const failed = err<Missing>({ kind: "missing", port: 9 });
const passedThrough = map(failed, () => { throw new Error("must not run on failure"); });
console.log("same failure", passedThrough === failed);
let fallbackCalls = 0;
function fallback(): number { fallbackCalls++; return 0; }
const eager = unwrapOr(ok(5), fallback());
const lazySuccess = unwrapOrElse(ok(5), () => fallback());
const lazyFailure = unwrapOrElse<number, Missing>(failed, () => fallback());
console.log("defaults", eager, lazySuccess, lazyFailure, fallbackCalls);
const failure = new Error("callback failed");
const declared = (): Result<number, never> => { throw failure; };
for (const invoke of [
  () => map(ok(1), () => { throw failure; }),
  () => andThen(ok(1), () => { throw failure; }),
  declared,
]) {
  try { invoke(); }
  catch (error) { console.log("throw channel", error === failure); }
}
resolve("8080"); // Legal to ignore this returned failure under these compiler settings.
console.log("ignored result", lookups);
// const unguarded = resolve("80").value; // TS2339: narrow on ok before selecting the payload.
// const onlySyntax: Result<string, { kind: "syntax"; raw: string }> = resolve("80"); // TS2322: range and missing remain possible.
```

Expected output:

```text
"80" HTTP
"x" syntax
"70000" range
"8080" missing:8080
"" syntax
"Infinity" syntax
calls 2 1
same failure true
defaults 5 5 0 2
throw channel true
throw channel true
throw channel true
ignored result 3
```

Only the two syntactically and numerically valid inputs reach `lookup`, and only the successful lookup reaches the uppercase transformation. The parser's syntax/range errors and lookup's missing error remain distinct. Checking only the success output would miss whether the earlier failures actually skip those steps.

This helper implementation returns the same failure object on the short-circuited path. That is an observed implementation choice, not a promise of every Result library. By contrast, mapping a success constructs an `ok` wrapper for the transformed value. A simple early-return sequence can express the same application policy; a helper chain is useful when it makes composition easier to follow, not because nested helper calls are automatically clearer or faster.

`fallback()` is evaluated before `unwrapOr` runs, even when the result is successful. `unwrapOrElse` receives a callback and invokes it only for failure. The counter is two: one eager success fallback and one lazy failure fallback. Choosing a default can discard useful failure information, so decide whether the caller should instead report or propagate that error value.

### 3) **Document the throw channel and the boundary contract**

The two callback invocations and the function declared to return `Result<number, never>` all throw the original Error. A Result return type describes values returned normally; it is not an exception-free function type. A callback, getter, assertion or called dependency can still throw unless an implementation deliberately handles it. An asynchronous boundary adds promise completion/rejection concerns rather than removing this distinction.

Use precise error variants when a caller needs to distinguish modeled cases. `unknown` can still be an honest type for an unexpected value caught before classification; using it is not inherently a failed design. Translate to a narrower domain error only with the evidence and policy needed for that boundary. [Error classes](<./2.2. Custom error classes cause and stacks.md>) and [never-throw boundary practice](<./2.3. Never-throw boundaries and error budgets.md>) own those later decisions.

Results can be returned through public APIs when that is the documented protocol. A caller may inspect, propagate, match, default, or adapt them to a different interface. Returning `null` for an intentional optional absence, or throwing through an API whose caller expects and handles exceptions, can also be appropriate. “Expected failure” and “programmer bug” are useful questions about handling responsibility, not language-enforced rules assigning one syntax to every case.

This project intentionally handles each modeled error in its display consumer, while its ignored call demonstrates that the compiler does not require consumption. Separate linting or API conventions can enforce stronger discipline. None of those checks proves the input contract of a deserialized Result from another process; that value still needs boundary validation.

### 4) **Common confusion**

A tagged union makes the two returned shapes distinct, but does not make ignored results or thrown exceptions unrepresentable. Narrowing on `ok` protects access to the corresponding payload in checked code; it does not prove the function's body cannot throw or that an unchecked incoming object has this shape.

`map` transforms a success into a value wrapped by this helper, while `andThen` expects its callback to return another Result and combines error types. Neither helper here catches exceptions. Also, passing a fallback value is different from passing a fallback factory: JavaScript evaluates ordinary arguments eagerly.

### 5) **Performance note**

The counters demonstrate skipped callback work. They do not establish a latency improvement. This implementation allocates an `ok` result on a mapped success, returns the existing failure on a short circuit, and invokes supplied callbacks directly. It does not allocate a new closure simply because a helper is called; callback allocation depends on the caller's expression. Error creation, stack access, wrapper objects and failure frequency vary by implementation. No universal Result-versus-throw ranking, allocation quantity or throughput threshold was measured.

### 6) **Mentor note**

Ask the learner to predict lookup and transformation counts for the six inputs. Then replace `unwrapOrElse` with `unwrapOr(..., fallback())` and identify when fallback work happens. Finish by explaining why the declared Result function can still throw and why the ignored call compiles. A sound design identifies the modeled error union, exception policy and owner that consumes or propagates each outcome.
