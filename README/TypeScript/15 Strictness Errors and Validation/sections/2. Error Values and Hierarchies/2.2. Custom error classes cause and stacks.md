## 2.2. Custom error classes — `cause` and stacks

### 1) **Extending `Error` correctly** (name, message, cause chaining)

**Definition** — `class AppError extends Error { constructor(message: string, options?: { cause?: unknown }) { super(message, options); this.name = "AppError"; } }` — set `name` (distinguishes in logs/traces), pass `cause` (ES2022 `ErrorOptions` — causal chain preserved), keep prototype intact (extending builtins works post-ES2015 targets; `Object.setPrototypeOf` fix only for pre-ES2015 emit). `instanceof` narrows subclasses reliably when construction goes through the subclass constructor.

**What problem it solves / history** — stringly errors (`throw "oops"`, `throw new Error("x")` everywhere undifferentiated) forced message-matching in handlers (`e.message.includes("not found")` — fragile, untestable, locale-hostile). Typed error classes make failure *kinds* checkable (`instanceof NotFound` — structured dispatch, exhaustive handling, tested branches) while `cause` preserves the causal chain that stringly errors flattened.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), extend `Error` per domain failure family (one base + specific subclasses — hierarchy depth 2, never deeper); set `name` explicitly (log/stack readability); chain `cause` on wrap (context added per layer — causality readable end to end); target ES2022+ (prototype chain correct without fixes — legacy emit needs the `setPrototypeOf` workaround, documented where it lingers).

**Runnable example** — typed errors with causes (good vs bad, `tsc --strict`):

```typescript
// good — named error with cause chain (kind checkable, causality preserved)
class AppError extends Error {
  constructor(message: string, options?: { cause?: unknown }) {
    super(message, options); // cause chained (ES2022 ErrorOptions — stack + causality together)
    this.name = "AppError"; // named (logs/traces distinguish — default "Error" tells nothing)
  }
}
function fail(): string {
  try {
    throw new Error("disk full");
  } catch (e) {
    throw new AppError("save failed", { cause: e }); // wrapped with context (cause preserved — not replaced)
  }
}
try {
  fail();
} catch (e) {
  console.log(e instanceof AppError, (e as Error).message); // true save failed — kind narrowed, message named
}
// bad — throw "save failed" (stringly: un-narrowable, un-chainable, untestable by kind)
// fix — AppError + cause (kinds narrow via instanceof; causes preserve causality — structured errors throughout)
```

```typescript

  }

  if (e instanceof Fatal) return "abort"; // narrowed (kind-specific escalation)
  if (e instanceof AppError) return "report"; // base narrowed (family fallback — never default-swallow)
  return "unknown"; // non-AppError (foreign throws — logged + rethrown upstream, never misclassified)
}
console.log(handle(new Retriable("x")), handle(new Fatal("y")), handle(42)); // retry abort unknown — dispatched per kind
// bad — message-matching dispatch (e.message.includes("retry") — fragile, untestable, locale-hostile)
// fix — class hierarchy + instanceof (kinds checkable — dispatch structured, branches tested)
```

```typescript

    super(message, options);

  }

  try {
    JSON.parse("{bad");
    return "ok";
  } catch (e) {

  }

```

**Common confusion** — "subclassing Error breaks instanceof" — true only for pre-ES2015 emit targets (prototype chain fix via `Object.setPrototypeOf(this, new.target.prototype)` — legacy workaround, documented where targets linger); ES2015+ targets subclass cleanly. "`name` assignment is cosmetic" — `name` appears in stacks/traces/logs (unnamed errors all read "Error" — triage-hostile); naming is incident-response infrastructure. "cause chains bloat errors" — one reference per wrap (causality graph, lazily inspected — zero cost until read, complete context when needed).

**Performance note** — throw + stack capture costs microseconds per throw (exceptional paths only — errors thrown at expected-failure rates indicate miscategorization per 1.2/2.1 discipline, not performance design). `cause` adds one reference per wrap (negligible); unthrown error *construction* (for Results) skips stacks entirely where stacks don't serve.

**Mentor note** — `console.log(err.stack)` with and without `cause` (flat trace vs causal chain — diagnostics depth in one option). Review gate: `throw "..."` stringly throws fail review; causeless wraps fail review.

### 2) **Domain error hierarchies** (status-carrying classes narrowing via `instanceof`)

**Definition** — `HttpError(status)` → `NotFoundError(404)` / `ValidationError(422, fields)` / `AuthError(401)` — status-carrying classes: constructors take domain payloads (missing id, field errors, required scopes), `status` drives HTTP mapping in one place, `instanceof` narrows handlers per kind (retryable? user-facing? loggable? — answered per class, not per message).

**What problem it solves / history** — flat `Error` + status-code juggling (`err.statusCode === 404` with `any`-shaped extras — untyped payloads, string-matched kinds, exhaustiveness impossible) scattered HTTP semantics across handlers (each mapping codes to responses independently — drift per handler). Hierarchies centralize: status + payload + handling-strategy per class (one place per kind, `instanceof`-dispatched everywhere).

**Modern guidance** — as of TypeScript 5.9 era, model HTTP/API failures as 2-level hierarchies (base with `status` + specific subclasses with payloads — depth 2, never deeper); map status→response once (middleware reading `err.status` — uniform translation); narrow handlers per kind (`instanceof ValidationError` → 422 body with fields; `instanceof AuthError` → 401 challenge). Never status-code-switch on `any`-shaped errors (untyped dispatch — hierarchy or Result, never message/property sniffing).

**Runnable example** — hierarchy dispatches uniformly (good vs bad, `tsc --strict`):

```typescript
// good — 2-level hierarchy (status + payloads per kind, dispatched via instanceof)
class HttpError extends Error {
  constructor(public status: number, message: string, options?: { cause?: unknown }) {
    super(message, options);
    this.name = "HttpError"; // family name (base catchable — kind dispatch via subclasses)
  }
}
class NotFoundError extends HttpError {
  constructor(public id: string) { super(404, `missing:${id}`); this.name = "NotFoundError"; } // payload typed (id carried, not interpolated away)
}
function toResponse(e: unknown): string {
  if (e instanceof NotFoundError) return `404:${e.id}`; // narrowed (payload available — typed handling)
  if (e instanceof HttpError) return `${e.status}`; // family fallback (status-mapped uniformly)
  return "500"; // foreign (non-hierarchy throws — 500 + report, never misclassified)
}
console.log(toResponse(new NotFoundError("u1")), toResponse(new Error("x"))); // 404:u1 500 — dispatched per kind
// bad — (err as any).statusCode === 404 (untyped dispatch — payloads any-shaped, kinds string-matched, exhaustiveness impossible)
// fix — hierarchy (status + payload per class — instanceof dispatch, tested branches, uniform mapping)
```


**Common confusion** — "hierarchies deeper than 2 help" — depth 3+ (HttpError → ClientError → NotFoundError) adds navigation without precision (handlers narrow to leaves or base — middle layers unused); depth 2 (family + kinds) covers status-mapping + payload-carrying fully. "status on every error" — transport status belongs to *boundary* errors (HTTP/API — mapped to responses); domain errors carry *domain* payloads (no status — mapped at the boundary adapter, not the domain). "instanceof fails across realms/bundles" — duplicate class identities (dual packages, worker boundary serialization) break `instanceof` — use `code`/`kind` discriminants for cross-realm errors (structural, not nominal, across isolation boundaries).

**Performance note** — subclass construction costs one extra prototype link per hierarchy level (negligible); `instanceof` walks chains per check (shallow hierarchies — trivial); status mapping O(1) per error (vs message-matching scans — hierarchy dispatch is faster *and* safer).

### 3) **`cause` chains for diagnostics** (context per layer, stacks intact)

**Definition** — `throw new AppError("save failed", { cause: original })` at every wrap boundary (repository → service → handler — each layer adding its context while preserving the original): stacks compose (each throw captures its layer), causes chain (root retrievable via `cause` walk), logs render full causality (`message` + `cause.message` recursively). Unwrapped rethrows (`throw e` bare) preserve stacks but add no context — wrap where context exists, rethrow where it doesn't.

**What problem it solves / history** — context-free rethrows (`catch (e) { throw e; }` — stacks preserved, causality flat) and message-flattening wraps (`throw new Error(\`save: ${e.message}\`)` — context added, causality *destroyed* (original stack/type discarded)) each lost half the diagnostics. `cause` chains keep both: layer messages (what each layer was doing) + original stacks/types (what actually failed) — complete causality, zero trade-offs.

**Modern guidance** — as of TypeScript 5.9 era, wrap with `cause` at every layer boundary that adds context (repository/service/handler — context per layer, original preserved); rethrow bare where no context exists (no wrapping theater — `catch { throw }` without cause adds nothing, remove it); log recursively (`cause` walk in error reporters — full chain in logs, not just the top message).

**Runnable example** — causality composed per layer (good vs bad, `tsc --strict`):

```typescript
// good — cause per layer (context added, original preserved — full chain readable)
class AppError extends Error {
  constructor(message: string, options?: { cause?: unknown }) {
    super(message, options);
    this.name = "AppError"; // re-declared: fences compile standalone (minimal AppError per fence needing it)
  }
}
function readFile(): string {
  try {
    JSON.parse("{bad");
    return "ok";
  } catch (e) {
    throw new AppError("config unreadable", { cause: e }); // layer context (what) + original (why)
  }
}
function boot(): string {
  try {
    return readFile();
  } catch (e) {
    throw new AppError("boot failed", { cause: e }); // second layer (each boundary adds context, preserves chain)
  }
}
try {
  boot();
} catch (e) {
  const err = e as AppError;
  console.log(err.message, err.cause instanceof AppError); // boot failed true — chain intact (layer messages + preserved originals)
}
// bad — message-flattening wraps (new Error(`boot: ${e.message}`) — context added, causality/type/stack destroyed)
// fix — cause chains (context per layer via message; causality via cause — both halves, every wrap)
```

```typescript

  }

  try {
    return readFile();
  } catch (e) {
    throw new AppError("boot failed", { cause: e });
  }
}
function chain(e: unknown): string[] {
  const out: string[] = [];
  let cur: unknown = e;
  while (cur instanceof Error) {
    out.push(cur.message); // layer message (each boundary's context, in order)
    cur = (cur as { cause?: unknown }).cause; // walk (cause chain traversed — depth-bounded by construction)
  }
  return out;
}
try {
  boot();
} catch (e) {
  console.log(chain(e).join(" <- ")); // boot failed <- config unreadable <- Expected property name... — full chain (causality readable end to end)
}
// bad — top-message-only logging (err.message — root causes invisible; incidents debugged from headlines)
// fix — cause-walking reporters (one shared chain() in logging infra — full causality per error, automatically)
```

```typescript
    return readFile();
  } catch (e) {
    throw e; // no context to add (rethrow bare — stack preserved, no theater wrap)
  }
}
try {
  console.log(pass());
} catch {
  console.log("rethrown-clean"); // rethrown-clean — bare rethrow (honest pass-through, zero decoration)
}
// bad — catch (e) { throw new Error("failed"); } (context-free rewrapping — original type/stack discarded for a generic message)
// fix — bare rethrow (no context → no wrap) or cause-wrap (context → wrap with cause) — never context-free rewrapping
```

**Common confusion** — "`cause` needs Error causes" — `cause?: unknown` accepts anything (strings, objects, undefined — causal data, not necessarily Errors; reporters handle non-Error causes defensively). "deep chains confuse logs" — chains *order* causality (outermost context first, root last — readable top-down); flat messages *hide* it (single message blending layers). "wrapping every layer is verbose" — wrap where *context exists* (repository/service/handler boundaries with something to add); bare-rethrow elsewhere — per-boundary judgment, not blanket wrapping.

**Performance note** — cause references cost one pointer per wrap (negligible); chain-walking logs cost O(depth) per error report (errors only — exceptional paths); stack capture dominates (per throw regardless of cause — chains add context, not cost).
