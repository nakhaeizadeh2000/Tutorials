## 2.2. Custom error classes — `cause` and stacks

### 1) **Give failures useful identity and payloads**

A custom Error class gives a locally constructed failure an identity that a caller can inspect with `instanceof`. Its fields carry facts needed for handling, while its message explains what happened. The `name` improves diagnostic presentation; setting a name does not establish class identity. Extend Error when consumers need its diagnostic behavior, and add subclasses when they enable a meaningful handling distinction.

This lesson uses **TypeScript 7.0.2**, an ES2022 target and emitted modules on **Node.js 20.20.2**. Save the next two TypeScript files together in an empty directory without a `tsconfig.json`. Compile with `tsc --strict --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist errors.mts demo.mts`, then run `node dist/demo.mjs`. No package dependencies are needed.

The Error constructor accepts `ErrorOptions`, whose optional `cause` can be any value. Pass those options to `super` so a wrapper can retain the original cause. ES2022 output uses native class inheritance on this runtime; no prototype repair is needed for this example. Compiler library declarations describe APIs to the checker and do not install them into an older runtime.

```typescript
// file: errors.mts
export class AppError extends Error {
  readonly code: string;
  constructor(code: string, message: string, options?: ErrorOptions) {
    super(message, options);
    this.name = "AppError";
    this.code = code;
  }
}
export class NotFoundError extends AppError {
  readonly id: string;
  constructor(id: string, options?: ErrorOptions) {
    super("NOT_FOUND", "record unavailable", options);
    this.name = "NotFoundError";
    this.id = id;
  }
}
export type Reply = { status: number; body: string };
export function toReply(error: unknown): Reply {
  if (error instanceof NotFoundError) return { status: 404, body: "missing:" + error.id };
  return { status: 500, body: "operation failed" };
}
export function causeNames(value: unknown, limit = 4): string[] {
  if (!Number.isInteger(limit) || limit < 1) throw new RangeError("positive integer limit required");
  const names: string[] = [];
  const seen = new Set<Error>();
  while (true) {
    if (!(value instanceof Error)) {
      names.push("[non-Error:" + typeof value + "]");
      return names;
    }
    if (seen.has(value)) { names.push("[cycle]"); return names; }
    if (seen.size === limit) { names.push("[limit]"); return names; }
    seen.add(value);
    names.push(value.name);
    if (!Object.hasOwn(value, "cause")) return names;
    value = value.cause;
  }
}
```

`NotFoundError` carries a domain identifier. The separate `toReply` adapter chooses a transport representation; the domain class does not need an HTTP status field. This pure function is a local mapping demonstration, not a running HTTP server or framework exception filter. An application can instead define a transport-specific error family if that is its intended abstraction.

The mapper deliberately returns a generic response for every other input. In a real request boundary, the owning handler must also decide how to record the internal failure. Sending complete messages, stacks or causes to clients can expose internal details. The generic fallback here does not claim that a reporting system ran.

### 2) **Distinguish construction, rethrowing and wrapping**

An Error in Node captures its creation location even if it is never thrown. Throwing the same object elsewhere does not create a new Error or move its recorded creation site. A wrapper creates a separate error and retains the original object through `cause`; the two errors have separate stack strings. [Node's Error documentation](https://nodejs.org/download/release/v20.20.2/docs/api/errors.html#class-error) and the [V8 stack trace API](https://v8.dev/docs/stack-trace-api) explain creation-time collection and formatting on access.

```typescript
// file: demo.mts
import { AppError, NotFoundError, toReply, causeNames } from "./errors.mjs";
function createRoot(): Error { return new Error("disk full"); }
const root = createRoot(); // Created without throwing.
const originalStack = root.stack;
console.log("unthrown stack", originalStack?.includes("createRoot") === true);
try { throw root; }
catch (error) {
  console.log("rethrow", error === root, error instanceof Error && error.stack === originalStack);
}
const config = new AppError("CONFIG", "config unreadable", { cause: root });
const outer = new AppError("BOOT", "boot failed", { cause: config });
console.log("causes", outer.cause === config, config.cause === root);
console.log("chain", causeNames(outer).join(" -> "));
console.log("stack head", outer.stack?.split("\n")[0]);
console.log("separate stack", outer.stack?.includes("disk full") === true);
console.log("unknown cause", causeNames(new Error("opaque", { cause: 0 })).join(" -> "));
console.log("absent cause", Object.hasOwn(new Error("none"), "cause"));
console.log("undefined cause", Object.hasOwn(new Error("present", { cause: undefined }), "cause"));
const loop = new Error("loop");
loop.cause = loop;
console.log("cycle", causeNames(loop).join(" -> "));
console.log("bounded", causeNames(outer, 1).join(" -> "));
const missing = new NotFoundError("u1");
console.log("identity", missing instanceof NotFoundError, missing instanceof AppError, missing instanceof Error);
console.log("name only", new Error("x", { cause: "NotFoundError" }) instanceof NotFoundError);
for (const error of [missing, outer, 42]) {
  const reply = toReply(error);
  console.log("reply", reply.status, reply.body);
}
class ConflictError extends AppError {}
const conflict = new ConflictError("CONFLICT", "version changed");
console.log("new subclass", conflict instanceof AppError, toReply(conflict).status);
console.log("JSON", JSON.stringify(new Error("hidden", { cause: root })));
console.log("custom JSON", Object.keys(JSON.parse(JSON.stringify(missing))).sort().join(","));
// console.log(outer.cause.message); // TS18046: cause needs evidence before property access.
// const unhandled: never = conflict; // TS2322: a new subclass is not an impossible value.
```

Expected output:

```text
unthrown stack true
rethrow true true
causes true true
chain AppError -> AppError -> Error
stack head AppError: boot failed
separate stack false
unknown cause Error -> [non-Error:number]
absent cause false
undefined cause true
cycle Error -> [cycle]
bounded AppError -> [limit]
identity true true true
name only false
reply 404 missing:u1
reply 500 operation failed
reply 500 operation failed
new subclass true 500
JSON {}
custom JSON code,id,name
```

The original error is still accessible by identity. Reading the outer stack alone does not expose its cause's message in this fixture. A console or monitoring tool may inspect causes separately; that presentation is different from the `.stack` string. Check the actual reporter rather than assuming that storing a cause automatically makes every output include it.

The base class is open to new subclasses, as the new ConflictError demonstrates. An `instanceof` chain over a few known classes is therefore not automatically exhaustive. If a closed set of modeled cases is the contract, use an explicit union with suitable discriminants and an exhaustiveness check. Hierarchy depth follows useful shared behavior and handling responsibilities; there is no language rule requiring exactly two levels.

### 3) **Preserve diagnostics within explicit limits**

Wrap when you have meaningful context to add, using a cause if retaining the original is appropriate. When passing a failure through unchanged, `throw error` preserves its identity; a catch that only rethrows is usually unnecessary. Constructing a new Error from only the old message discards the original object from that new error. Retaining a cause also retains its reachable data, so choose what a long-lived report stores and what a client sees.

`causeNames` is a small diagnostic walk over trusted, local Error objects with ordinary properties. It includes non-Error causes by type, detects repeated Error objects and caps the number of Error nodes. A present `undefined` cause differs from having no own cause property. It does not coerce arbitrary causes into strings. It intentionally does not inspect inherited causes or enumerate arbitrary payloads. It is not a safe serializer for hostile proxies, getters, foreign realms, AggregateError collections or arbitrary graphs; those need a separately specified reporting protocol.

JSON encoding is another boundary. The ordinary Error in the example produces `{}` because its relevant built-in properties are not enumerable. This custom class also assigns enumerable fields, so its JSON contains `code`, `id` and `name` but loses the Error prototype, message and cause. Neither output is a complete diagnostic record. Define and validate an explicit wire representation if another process needs structured error information.

For a separate runtime identity demonstration, save this JavaScript as `identity.mjs` and run `node identity.mjs` on the same Node version. It uses Node's built-in VM module, with no TypeScript package typings required.

```javascript
// file: identity.mjs
import { runInNewContext } from "node:vm";
const foreign = runInNewContext('new Error("foreign")');
console.log("foreign", foreign instanceof Error, foreign.name);
class First extends Error {}
class Second extends Error {}
const original = new First("local");
original.name = "Second";
console.log("duplicate identity", original instanceof First, original instanceof Second);
const copy = JSON.parse(JSON.stringify({ code: "NOT_FOUND", id: "u1" }));
console.log("wire", copy instanceof First, copy.code);
```

Expected output is `foreign false Error`, `duplicate identity true false` and `wire false NOT_FOUND`. The VM Error has a different constructor/prototype chain, changing `name` does not change identity, and JSON data is not an instance of a custom Error. For cross-boundary handling, read a documented code and validate its required payload; merely receiving a familiar code string does not prove authenticity. The [class compatibility lesson](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) owns the separate distinction between structural assignability and runtime ancestry.

### 4) **Common confusion**

`name`, a TypeScript class annotation and `instanceof` answer different questions: presentation, checked compatibility and a runtime identity test. An open class family does not become a closed union because today's handler recognizes its current subclasses.

A cause is a separate stored value, not text automatically appended to every stack. It can be non-Error, absent, explicitly undefined or cyclic. A diagnostic walker must state which cases it handles rather than assuming that every chain ends with an Error having no cause.

### 5) **Performance note**

Error construction in this Node/V8 environment collects stack information; formatting the stack string occurs on access. Returning an unthrown Error inside a Result does not remove construction-time stack work. Retaining a cause keeps the referenced object reachable. This walker stores at most its configured number of Error nodes plus one stop marker; its cap bounds ordinary node visits, not execution time of arbitrary property access. No throw latency, class-versus-message dispatch ranking or universal allocation cost was measured. Use an application's real workload before choosing a representation for performance reasons.

### 6) **Mentor note**

Ask the learner where `root.stack` points before and after the throw, then why `outer.stack` differs from its cause's stack. Add a new subclass and identify which mapper branch handles it. Finally, walk a self-cycle and a numeric cause, explaining the stopping policy and why this helper is not an arbitrary-object serializer. A sound answer separates domain handling, transport mapping, runtime identity and diagnostic presentation.
