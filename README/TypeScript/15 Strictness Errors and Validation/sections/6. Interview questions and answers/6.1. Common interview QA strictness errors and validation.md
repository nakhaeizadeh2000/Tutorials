## 6.1. Common interview QA — strictness, errors and validation

### 1) **`x is T` vs `asserts x is T` — which narrows, for whom, and what happens on failure?** (caller vs thrower)

**Definition** — `x is T` (predicate): returns `boolean`; narrows the *caller's* flow (inside `if`, `filter`, ternaries — `false` continues normally elsewhere). `asserts x is T` (assertion): returns `void`; narrows *past the call* (no branch remains — failure *throws*, never returns normally). Same narrowing power, opposite failure semantics: recoverable-false vs halting-throw.

**What problem it solves / history** — interviewers ask this to test narrowing judgment beyond syntax: candidates who add *failure semantics* (false-continues vs throws-exits) and *placement* (predicates for recoverable filtering; assertions for invariants) show production decision-making; syntax-only answers (`is` returns boolean, `asserts` returns void) show vocabulary without judgment.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer mechanics-first (caller-narrowing vs thrower-narrowing), failure-second (false-continues vs throws-exits), placement-third (recoverable → predicates; invariants → assertions; user input → parse, never assert). Full treatment in [1.2. Predicates vs assertions](<./1.2. Type predicates vs assertions caller vs thrower.md>).

**Runnable example** — both forms, both failures (good vs bad, `tsc --strict`):

```typescript
// good — predicate: false continues elsewhere (recoverable filtering, no throw)
function isLong(s: string): s is string {
  return s.length > 3; // boolean claim (caller branches — false path normal, handled inline)
}
const names = ["ab", "abcd"];
console.log(names.filter(isLong).map((s) => s.toUpperCase()).join(",")); // ABCD — caller narrowed (filter path, recoverable)
// bad — asserting filterable input (assert(isLong(x)) per element — recoverable absence escalated to throws)
// fix — predicates for recoverable (filter/find/default); assertions for invariants (must-hold-or-crash)
```

```typescript
// good — assertion: failure throws, success narrows unconditionally (no branch remains)
function assertLong(s: string): asserts s is string {
  if (s.length <= 3) throw new Error("too short (invariant — cannot proceed)"); // thrower (failure exits — no false path)
}
function use(s: string): string {
  assertLong(s); // enforced (throws for short) + narrowed (string proven — no branch remaining)
  return s.toUpperCase(); // narrowed unconditionally (assertion did both jobs — enforcement + proof)
}
console.log(use("abcd")); // ABCD — fused (one call, two guarantees — half-enforcement impossible)
// bad — if (!isLong(s)) throw ... per site (predicate + manual throw — check and enforcement split, drift per site)
// fix — asserts x is T (fused: enforcement and narrowing travel together, message named once)
```

```typescript
// good — failure semantics compared directly (false-continues vs throws-exits, same input)
function decide(s: string): string {
  const isLong = (x: string): x is string => x.length > 3; // re-declared inline: fences compile standalone (minimal predicate)
  if (isLong(s)) return `long:${s}`; // predicate branch (false continues below — recoverable)
  return "short"; // false path normal (handled inline — no throw, no crash, no incident)
}
console.log(decide("ab"), decide("abcde")); // short long:abcde — predicate failures continue (recoverable by design)
// bad — assertLong("ab") in user paths (recoverable input throwing — 500s for 400-situations, crash by category error)
// fix — per-site decisions (recoverable → predicate; invariant → assertion — tools matched to categories, documented)
```

**Common confusion** — "assertions return narrowed values" — return `void` (narrowing delivered via control-flow effect, not return values). "predicates throw on false" — return `false` (caller branches — throwing would make them assertions; the distinction *is* the failure semantic). "one form suffices with discipline" — fused assertions can't filter (no boolean to branch on); predicates can't enforce (no throw on failure) — complementary tools, never substitutes.

**Performance note** — predicates cost branches per use (callers branch — expected); assertions cost branches per call + throws on violation (exceptional — fail-fast economics). Decision quality affects incidents, never steady-state speed.

**Mentor note** — strong answers lead with failure semantics (false-continues vs throws-exits) unprompted — probe with "what happens on failure?" when candidates stop at signatures. Follow-up: "user input — which form?" (neither directly — parse/narrow; predicates for recoverable handling, assertions never). Hiring signal: failure-semantic answers predict production judgment.

**Cross-links** — decision rule → [1.2. Predicates vs assertions](<./1.2. Type predicates vs assertions caller vs thrower.md>); assertion shapes → [1.1. Assertion signatures](<./1.1. Assertion signatures asserts condition and asserts x is T.md>).

### 2) **When do you return `Result` vs throw — and how do callers handle each?** (expected vs bugs)

**Definition** — return `Result<T, E>` (or optionals) for *expected* failures (missing records, invalid input, timeouts — valid programs encounter routinely; callers narrow/handle per site); `throw` named errors for *programmer* errors (invariant violations, unreachable branches, contract misuse — no valid continuation exists). Callers handle Results (branch/compose/default) and let throws propagate to crash reporting (fail-fast with stacks).

**What problem it solves / history** — undisciplined error styles force callers to guess per function (try/catch? null-check? both?) — each guess wrong half the time (uncaught throws crashing routine misses; unchecked nulls corrupting on bugs). Discipline makes style predictable from category: expected→Result, bug→throw, documented per signature — callers never guess.

**Modern guidance** — as of TypeScript 5.9 era, answer category-first (expected vs programmer-error), handling-second (narrow/compose/default vs propagate-to-crash-reporting), documentation-third (JSDoc states throw-vs-return per public signature). Full treatment in [2.1. Error as value](<./2.1. Error as value Result Ok Err patterns.md>).

**Runnable example** — categories handled per kind (good vs bad, `tsc --strict`):

```typescript
// good — expected miss returns (routine absence — typed, handled, composable)
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }; // re-declared: fences compile standalone (minimal shape)
function lookup(ids: Map<string, string>, id: string): Result<string, { kind: "missing" }> {
  const v = ids.get(id);
  return v === undefined ? { ok: false, error: { kind: "missing" } } : { ok: true, value: v }; // expected (misses happen — returned)
}
const f = lookup(new Map([["a", "A"]]), "zzz");
console.log(f.ok ? f.value : "not-found"); // not-found — routine miss (handled per call site, never thrown)
// bad — throw new Error("missing") on lookup miss (expected absence as exception — callers try/catch per lookup or crash)
// fix — Result returns (misses compose; throws reserved for bugs — discipline per category, predictable per function)
```

```typescript
// good — programmer error throws (contract violated — no valid continuation exists)
function divide(a: number, b: number): number {
  if (b === 0) throw new Error("divide by zero (validate inputs before calling)"); // bug (caller violated contract — fail-fast named)
  return a / b;
}
console.log(divide(6, 3).toFixed(0)); // 2 — valid call (invalid calls throw loudly — never silently NaN)
// bad — return NaN on zero-divide (bug flowing as a value — NaN poisons downstream arithmetic silently for pages)
// fix — throw programmer errors (fail-fast named — bugs crash loudly at cause, never flow as values)
```

```typescript
// good — per-function documentation (callers read throw-vs-return — never guess)
// (divide throws programmer errors (documented above); lookup returns expected failures (documented above) — discipline visible per signature)
function documented(): string { return "throws-X/returns-Y stated per public function (JSDoc — callers never guess)"; }
console.log(documented()); // discipline stated (per-function contracts — predictable error handling repo-wide)
// bad — undocumented mixed surfaces (some functions throw misses, some return null — callers try/catch AND null-check defensively)
// fix — JSDoc per function (throws-X / returns-Y stated — discipline visible at every signature)
```

**Common confusion** — "Results everywhere (never throw)" — programmer errors *must* throw (returning bugs flows corruption — fail-fast exists because some paths lack valid continuations). "throws everywhere (simpler)" — expected failures as throws force try/catch per call (ceremony) or crash routine misses (incidents). "async changes the rule" — async *transports* identically (rejections ≈ throws; Result-resolutions ≈ returns — same categories — see domain 18).

**Performance note** — throws cost stack capture per throw (exceptional paths only — reserved for bugs by design); Results cost one wrapper object per call (routine failures stay cheap). Discipline aligns cost with frequency automatically.

**Mentor note** — classify ten throwing/returning functions live (expected→Result? bug→throw? mixed→document?) — decision drill transferring in under an hour. Follow-up: "async lookup miss — reject or Result-value?" (Result-valued resolution — same category, async transport). Hiring signal: category-first answers predict production judgment.

### 3) **Parse vs validate — what's the difference, and where does each run?** (production vs verification)

**Definition** — *parsing* converts unknown→typed (produces new values: `parseUser(raw): User | Errors` — input `unknown`, output proven); *validating* checks typed→verdict (verifies existing values: `isValid(user): boolean` — input already typed, output a claim). Parse at unknown boundaries (network/storage/env/CLI); validate untrusted-typed values (third-party payloads bypassing parsers); trust proven-typed values (no re-validation tax downstream).

**What problem it solves / history** — validate-everything codebases re-checked proven values (defense distributed, coverage unprovable) while unparsed unknowns flowed beside them (the actual gaps unexamined); parse-nothing codebases `as`-cast ingestion (assertion without evidence at every boundary). Parse-don't-validate inverts both: unknown parsed once (trust created), typed trusted (no tax), untrusted-typed guarded (narrow exception, explicitly).

**Modern guidance** — as of TypeScript 5.9 era, answer production-first (parsing *creates* trust from unknown — boundaries), verification-second (validating *checks* unclear-typed values — foreign producers), trust-third (proven values flow un-revalidated — re-validation is a parser-bug smell). Full treatment in [3.3. Parse boundaries](<../3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>).

**Runnable example** — production vs verification (good vs bad, `tsc --strict`):

```typescript
// good — parse produces (unknown → typed-or-errors — trust created once at the boundary)
interface Item { sku: string } // re-declared: fences compile standalone (minimal shape)
function parseItem(raw: unknown): Item | string {
  if (typeof raw !== "object" || raw === null) return "not-object"; // error channel (typed failure — see 2.1 Results)
  const r = raw as Record<string, unknown>;
  if (typeof r["sku"] !== "string") return "bad-sku";
  return { sku: r["sku"] }; // proven Item (consumers trust — zero downstream checks)
}
const it = parseItem({ sku: "a" });
console.log(typeof it === "string" ? it : it.sku.toUpperCase()); // A — produced trust (consumers narrow, never re-validate)
// bad — validating parsed output (if (!isValid(it)) throw — re-checking proven values while raw inputs flow unvalidated elsewhere)
// fix — parse unknown once (trust created); trust typed values (no re-validation tax on proven data)
```

```typescript
// good — validation for untrusted-typed values (foreign producers bypassing parsers — narrow exception, explicitly)
interface Item { sku: string } // re-declared: fences compile standalone (minimal shape)
function isItem(x: unknown): x is Item { // predicate guard (narrowing check for values of unclear provenance)
  if (typeof x !== "object" || x === null) return false;
  return typeof (x as Record<string, unknown>)["sku"] === "string";
}
const ext: unknown = { sku: "b" }; // unvalidated producer (third-party callback — provenance unclear)
if (isItem(ext)) console.log(ext.sku.toUpperCase()); // B — guard narrows (validation where parsing didn't run)
// bad — parseUser(raw) then isValid(user) then use (parse + validate + trust — triple handling, one redundant layer)
// fix — parse OR validate per boundary (unknown→parse; unclear-typed→guard; proven-typed→trust — exactly one layer each)
```

```typescript
// good — trusted pipelines flow un-revalidated (no tax on proven data — re-validation is a parser-bug smell)
interface Ticket { id: string } // re-declared: fences compile standalone (minimal shape)
function use(t: Ticket): string { return t.id.toUpperCase(); } // trusts (no guards — parser proved upstream, consumer flows)
console.log(use({ id: "t" })); // T — trusted pipeline (zero re-validation tax — trust spent freely where earned)
// bad — use() re-validating (proven data re-checked per consumer — defense distributed, coverage unprovable)
// fix — parse-once (boundary proves once — downstream trusts unconditionally; re-validation signals parser gaps)
```

**Common confusion** — "validation subsumes parsing" — validation *assumes* typed inputs (checks values already shaped); parsing *produces* them from unknown (creates shape) — unvalidated-unknown validated (not parsed) stays unknown-typed (casts downstream — the lie). "parsed values need periodic re-validation" — parsed values are *immutable-or-tracked* (frozen configs, validated DTOs — re-validation signals mutability bugs, not diligence). "guards duplicate parsers" — guards narrow *unclear-typed* values (third-party payloads, legacy producers); parsers produce from *unknown* — complementary layers (parse at owned boundaries, guard at foreign ones).

**Performance note** — parsing costs per-field checks once per boundary (vs per-use re-validation — N× savings downstream); guards cost per foreign value (bounded by foreign-producer surface); trust costs zero checks (unconditional flow — fastest possible consumption).

**Mentor note** — label one boundary "parse" and one "validate" live (unknown→typed production vs typed→checked verification — vocabulary in one labeling exercise). Follow-up: "parsed output needs re-checking?" (no — re-validation is a parser-bug smell; fix parsers, not consumers). Hiring signal: production-vs-verification vocabulary predicts boundary judgment.

**Cross-links** — hand parsers → [3.1. Hand-rolled schemas](<../3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>); parse boundaries → [3.3. Parse boundaries](<../3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>).

### 4) **Why is `catch { return default }` dangerous — and what belongs in catch blocks?** (narrow, handle, rethrow)

**Definition** — undifferentiated catches (`catch { return default }` — every throwable defaulted identically) blend *expected* failures (timeouts, missing keys — correctly defaulted) with *bugs* (TypeErrors from typos — incorrectly defaulted, masked for months). What belongs: narrow (`instanceof` per kind), handle expected (default/retry/degrade with logging), rethrow bugs (fail-fast named — never defaulted).

**What problem it solves / history** — blended catches masked a typo-throwing bug for months (TypeError defaulted alongside timeouts — green metrics, wrong behavior — discovered only in a rewrite exposing the dead path). Narrowed catches (`instanceof` dispatch: expected→handle, bug→rethrow, unknown→report+rethrow) preserve the distinction structurally — masking rendered impossible, not merely discouraged.

**Modern guidance** — as of TypeScript 5.9 era, narrow every catch (`instanceof` per kind — expected handled, bugs rethrown, unknown reported+rethrown); default expected failures explicitly (logged defaults — routines visible, not hidden); rethrow programmer errors unconditionally (fail-fast named — masking bugs as defaults is the months-long-hiding incident class). Full treatment in [5.1. Production bugs](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by validation misunderstandings.md>) promise 3.

**Runnable example** — narrowed catches, rethrown bugs (good vs bad, `tsc --strict`):

```typescript
// good — kinds dispatched (expected defaulted, bugs rethrown — never blended)
function load(key: string): string {
  try {
    if (key === "") throw new Error("empty-key"); // expected failure (routine — handled below as default)
    return `v:${key}`;
  } catch (e) {
    if (e instanceof TypeError) throw e; // BUG rethrown (typos/coding errors surface loudly — never defaulted)
    console.log(`load failed`); // expected logged (routines reported, not hidden)
    return "default"; // expected defaulted (routines degrade gracefully — bugs never reach here)
  }
}
console.log(load(""), load("a")); // default v:a — kinds dispatched (expected defaulted, bugs would rethrow)
// bad — catch { return "default"; } (undifferentiated: typos defaulted alongside timeouts — bugs masked for months)
// fix — instanceof dispatch (expected handled, bugs rethrown — categories never blended, masking structurally impossible)
```

```typescript
// good — toError normalizer shared (narrowing vocabulary centralized — see 13/1.2 full treatment)
function toError(e: unknown): Error { // re-declared: fences compile standalone (shared normalizer sketch)
  return e instanceof Error ? e : new Error(String(e));
}
function strict(code: number): string {
  try {
    if (code < 0) throw new RangeError("negative"); // programmer error (contract violated — fail-fast named)
    return `ok:${code}`;
  } catch (e) {
    if (e instanceof RangeError) throw e; // rethrown (bugs propagate — stacks intact, cause chains composable)
    return "fallback"; // non-Range errors (unexpected shapes — defaulted cautiously... simplified: rethrow unknown too in prod)
  }
}
console.log(strict(5)); // ok:5 — bugs rethrown (loud), routines defaulted (graceful) — separated structurally
// bad — catch (e) { return "fallback"; } (RangeError swallowed — contract violations masked as routine fallbacks)
// fix — rethrow bugs (fail-fast named — masking bugs as defaults is the months-long-hiding incident class)
```

```typescript
// good — validation errors handled, programmer errors escalated (per-kind policy in one catch)
class ValidationError extends Error {
  constructor(public field: string) {
    super(`bad:${field}`);
    this.name = "ValidationError"; // kind named (expected-failure family — handled, not escalated)
  }
}
function save(field: string): string {
  try {
    if (field === "") throw new ValidationError("name"); // expected (user data — handled below as 422-style default)
    return `saved:${field}`;
  } catch (e) {
    if (e instanceof ValidationError) return `invalid:${e.field}`; // expected handled (user-facing default — no escalation)
    throw e; // bugs escalated (non-validation errors propagate — crash reporting consumes, never defaults)
  }
}
console.log(save(""), save("x")); // invalid:name saved:x — per-kind policy (expected defaulted, bugs escalated — never blended)
// bad — catch { return "saved?" } (bugs saved as successes — corrupted state wearing valid shapes downstream)
// fix — kind dispatch (ValidationError handled; everything else rethrown — blending structurally impossible)
```

**Common confusion** — "catch-all is defensive" — catch-all *without narrowing* defends nothing (bugs and routines blended — masking bugs while handling routines); defensive catching narrows first, defaults second, rethrows third. "rethrowing loses context" — bare `throw e` preserves stacks fully (add `cause` where layer context exists per 2.2 promise 3 — rethrow is preservation, not loss). "narrowed catches are verbose" — three branches per catch (expected/bug/unknown — the complete taxonomy) vs one blended branch (incomplete by construction — verbosity that covers vs terseness that masks).

**Performance note** — `instanceof` per catch (shallow hierarchies — trivial); rethrows cost stack capture per bug (exceptional — bugs exceptional by definition); blended catches cost incidents (months-hidden bugs — unbounded). Narrowing is free correctness.

**Mentor note** — plant a typo inside a blended-catch try block (TypeError defaulted silently for months — then narrow the catch and watch it surface) — masking demonstrated, not theorized. Follow-up: "which errors does this catch *expect*?" (named kinds listed — unexpected kinds rethrown by rule). Hiring signal: narrow-first catch answers predict production judgment.

### 5) **How do you type an `unknown` API response with zero `as` casts?** (parse pipeline, no assertions)

**Definition** — zero-cast pipeline: `unknown` response → guard/parse per field (narrowing with `typeof`/`instanceof`/`in` — evidence per check) → narrowed typed value flowing un-asserted (no `as` anywhere downstream — parser proved everything consumers need). Cast count zero is the *metric* of parser completeness (grep-able, countable, trending to zero, held by review).

**What problem it solves / history** — `as`-cast API ingestion (`fetchUser() as User` — assertion without evidence; malformed payloads crashing downstream confidently) made every API boundary a lie agreed upon by both sides (producer unvalidated, consumer trusting). Zero-cast pipelines convert the lie into a contract: unknown in, evidence per field, narrowed types out — malformed payloads surface as error *values* at the boundary, never as crashes downstream.

**Modern guidance** — as of TypeScript 5.9 era, parse API responses field-by-field (`typeof` per primitive, `in` per shape, combinators per 3.1–3.2 for scale); return unions (`T | ParseError[]` — failures as values, composable); flow narrowed values un-asserted (zero `as` downstream — cast demand diagnoses parser gaps, fixed at the parser). Treat each downstream `as` as a filed ticket against the parser (demand-driven completeness — grep quarterly).

**Runnable example** — zero casts, full evidence (good vs bad, `tsc --strict`):

```typescript
// good — field-by-field evidence (no cast anywhere — parser proves everything consumers need)
interface Profile { name: string; age: number } // re-declared: fences compile standalone (minimal shape)
function parseProfile(raw: unknown): Profile | string {
  if (typeof raw !== "object" || raw === null) return "not-object"; // error channel (typed failure — see 2.1 Results)
  const r = raw as Record<string, unknown>; // single contained cast (evidence-gathering — see 3.1 full pattern)
  if (typeof r["name"] !== "string") return "bad-name";
  if (typeof r["age"] !== "number") return "bad-age";
  return { name: r["name"], age: r["age"] }; // proven Profile (narrowed per field — consumers trust structurally)
}
const pr = parseProfile({ name: "a", age: 1 });
console.log(typeof pr === "string" ? pr : pr.name.toUpperCase()); // A — narrowed (no cast downstream, ever)
// bad — fetchProfile() as Profile (assertion without evidence — malformed payloads crashing downstream confidently)
// fix — parse pipeline (evidence per field — unparseable input cannot reach typed consumers, structurally)
```

```typescript
// good — combinator reuse at API scale (shared primitives — no per-endpoint re-derivation)
function pStr(x: unknown): string | undefined { // re-declared: fences compile standalone (minimal primitive)
  return typeof x === "string" ? x : undefined;
}
function parsePair(raw: unknown): [string, string] | undefined {
  if (typeof raw !== "object" || raw === null) return undefined; // boundary honesty (non-objects rejected, not cast)
  const r = raw as Record<string, unknown>;
  const a = pStr(r["a"]); // shared primitive (tested once — reused per endpoint, never re-derived)
  const b = pStr(r["b"]);
  return a === undefined || b === undefined ? undefined : [a, b]; // proven pair (combinators composed — evidence per field)
}
const pp = parsePair({ a: "x", b: "y" });
console.log(pp === undefined ? "bad" : pp.join("+").toUpperCase()); // X+Y — combinators reused (primitives shared, shapes composed)
// bad — per-endpoint typeof chains (N endpoints × M fields of hand-rolled checks — drift per copy, untested per unit)
// fix — shared primitives + combinators (3.1's kit or 3.2's objects — tested once, composed everywhere)
```

```typescript
// good — cast-demand metric tracked (grep count trending to zero — parser completeness measured, not hoped)
function demand(): string { return "grep-as-downstream-of-parse (count → 0 — completeness proven by absence of demand)"; }
console.log(demand()); // metric stated (quarterly grep — demand falling means parsers completing; flat means gaps accepted)
// bad — cast demand ignored (parsers frozen incomplete — consumers casting forever, gaps permanent by neglect)
// fix — demand-driven completeness (each cast a parser ticket — fix parsers until grep is empty, then keep it empty)
```

**Common confusion** — "zero-cast is asymptotic" — zero-cast is *measurable* (grep count — trending to zero quarterly, held at zero by review). "contained casts violate zero-cast" — contained *evidence-gathering* casts (`raw as Record` *before* per-field narrowing) differ from *laundering* casts (`raw as Profile` *instead of* narrowing) — position relative to evidence decides honesty. "APIs guarantee shapes" — backends *version* (v2 payloads to v1 parsers — shape drift across deploys); frontend parsing is the contract check (drift surfaces as error values, not crashes).

**Performance note** — parsing costs per-field checks once per response (trivial vs network latency); `as`-casts cost zero checks (and unbounded incident surface). Parse-once economics at every API boundary.

**Mentor note** — feed one malformed payload through `as`-cast vs parse paths (confident crash vs error value — honesty demonstrated in one input). Follow-up: "how do you know the parser is complete?" (cast-demand grep at zero — completeness measured, not hoped). Hiring signal: evidence-per-field answers predict boundary judgment.
