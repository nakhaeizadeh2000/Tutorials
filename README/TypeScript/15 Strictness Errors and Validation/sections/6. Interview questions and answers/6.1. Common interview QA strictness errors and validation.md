## 6.1. Common interview QA — strictness, errors and validation

### 1) **How do predicates and assertions change caller information?**

A type predicate such as `value is User` provides control-flow information when its boolean result is used in a suitable branch or filter. An assertion signature such as `asserts value is User` describes what the checker may assume after a normally returning call. Both concern the caller's information. Neither signature verifies its own implementation or makes the function incapable of throwing.

A useful answer separates the signature, the implementation and the failure policy. In this domain's examples, a predicate returns false for a rejected value and an assertion throws on failure. Those are implemented behaviors, not proof that every predicate is exception-free or that assertions can only be used for programmer bugs. The consumer's protocol determines whether a branch, returned error or handled exception is appropriate.

Follow-up: would a check for a nonempty string be an honest `value is string` predicate over `string | null`? Not if it returns false for an empty string: that false branch would incorrectly exclude strings. Use a boolean selection criterion, an actual refined representation, or a predicate that describes the full string membership test. The [predicate/assertion comparison](<../1. Assertion Functions/1.2. Type predicates vs assertions caller vs thrower.md>) runs this counterexample and its repair.

### 2) **What does Result guarantee, and when would you throw instead?**

Result models values returned normally as success or failure. Its error variants help callers distinguish modeled cases and compose fallible steps. The consumer still has to inspect, propagate, default or adapt the result. TypeScript does not require a returned result to be consumed, and a Result-returning function can still throw. An async function returning a promise of Result also needs a policy for rejection.

Choose the interface the consumer can use correctly. Returned errors can make routine alternatives explicit. Throwing can fit an API whose callers already expect an exception and have a responsible handling boundary. Distinguishing expected conditions from bugs is useful design reasoning, but does not assign one language construct to every possible case. A default may intentionally discard information; document that consequence.

Follow-up: what happens if a `map` callback throws, and what if a fallback value is computed eagerly? In [2.1's executed implementation](<../2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>), the callback exception escapes, while `unwrapOr` receives a fallback already evaluated by JavaScript. Its lazy counterpart invokes the fallback callback only when needed. Explain these implementation choices before generalizing to a particular library.

### 3) **What does “parse, don't validate” preserve, and when is another check justified?**

The design goal is to preserve learned information in the representation supplied to a consumer. A parser can produce a normalized User or a stronger collection type, with an explicit failure path. The distinction is not that validators accept typed inputs while parsers accept unknown inputs. Both can inspect input, and a type guard can preserve information in the caller's narrowed flow.

Another check may be justified after deserialization, mutation, a schema/version transition, a new trust boundary or a change in business policy. Repeating the same unchanged shape check in every helper may add little; checking a different or invalidated guarantee is meaningful. “Exactly once” and “never revalidate” omit the assumptions that make earlier evidence usable.

Follow-up: a parsed User has a number age and is later viewed as readonly. Can another alias set its age to `-1`? Yes in the [architecture example](<../3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>): the number type does not encode the parser's range, and the readonly view does not freeze other references. Its owned frozen flat snapshot protects those fields, while current business policy still requires a separate decision. Ordinary structural User values can also be constructed without this parser.

### 4) **When is a broad catch appropriate, and what can reporting change?**

A catch should implement the boundary's stated recovery or adaptation policy. A universal fallback can turn a significant dependency failure into an apparently normal value. A narrow operation and a documented error case make recovery easier to justify. When the failure is outside that policy, propagate, adapt or report it according to the owning caller rather than silently pretending it succeeded.

Error classes and codes help apply an API contract, but a TypeError is not universally a programmer bug and a different Error is not automatically safe to default. A library may deliberately use a built-in error for an invalid argument. The [pitfalls lesson](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by validation misunderstandings.md>) compares a broad fallback with a specified MissingRecord fallback and preserves the other original failure by identity.

Follow-up: does attaching `.catch(report)` finish failure ownership? Not if the callback throws or returns a rejected promise: the returned completion then needs handling. The [containment example](<../2. Error Values and Hierarchies/2.3. Never-throw boundaries and error budgets.md>) awaits operation and reporter outcomes separately. A local recovery result also does not establish that normal work is safe after an unrelated fatal Node exception; its isolated host checks preserve fatal exit behavior.

### 5) **How do you give an unknown API value a useful type and verify the result?**

Specify the accepted representation first: required fields, numeric rules, missing versus undefined, extra fields, getters/inheritance, collection density and transformations. Then execute a parser or appropriate guard, preserve a distinguishable failure, and narrow before using its success payload. A cast of decoded JSON to User supplies no runtime field checks. JSON syntax success is also different from application-shape success.

[3.1's complete parser](<../3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>) demonstrates an assertion-free consumer and explicit own-data/dense-array rules. [3.2's pinned schema example](<../3. Schema Validation in Practice/3.2. Schema objects and inferred types.md>) derives string input and numeric output types and demonstrates different reflective-input policies. Type inference avoids a separately maintained output interface, but a dishonest custom schema callback can still return an invalid value with a confident type.

Follow-up: what evidence supports the guarantee? Use compiler probes for forbidden assignments, executed malformed-input cases for parser behavior, and integration tests for the actual HTTP/framework/storage boundary. Record exact versions, flags and outcomes. A zero-cast grep result, schema-library name or strict compilation pass does not prove complete validation. These answers synthesize the domain's TypeScript 7.0.2 and Node.js 20.20.2 checks; they add no new host integration or benchmark.

### 6) **Common confusion**

A strong answer explains what a construct promises and what its implementation must do. Predicates can throw; assertion bodies can lie; Result values can be ignored; schema inference can describe incorrect custom code. Runtime outcomes and compiler information are connected through trusted implementation, not automatically identical.

Shape validity, mutation control, completion ownership and current authorization/business decisions are separate guarantees. An answer that calls all of them “validated once” cannot explain what happens when one dependency changes.

### 7) **Performance note**

These interview questions have no direct runtime effect. Concrete choices can change traversal, copies, result objects, stack collection, reporting latency and retained cache data. The domain's examples establish behavior rather than a universal speed ranking. Explain which work a design performs, then request or produce a representative measurement when a performance claim matters. No fixed throw latency, free catch handling or schema-instantiation cost follows from the syntax alone.

### 8) **Mentor note**

Begin with one signature, ask for a failure prediction, then change one condition: an empty string, an ignored result, a rejecting reporter, a mutable alias or an overlapping union branch. Ask the learner to identify a suitable compiler or runtime check and state what remains unverified. Evaluate the causal explanation and repair rather than memorized categories, cast counts or claims about hiring performance.
