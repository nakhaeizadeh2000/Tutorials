## 5.1. Real production bugs caused by validation misunderstandings

### 1) **Treat these as reproduced failure modes**

The cases below reconstruct mistakes relevant to production code: unchecked payloads, lost reporting failures, broad fallback policies and stale decisions. They are local demonstrations, not accounts of identified production incidents. No outage duration, lost-request count, benchmark or deployed security outcome is claimed.

Use **TypeScript 7.0.2** and emitted ES2022 modules on **Node.js 20.20.2**. Reuse `parser.mts` from [3.1](<../3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>) and `boundary.mts` from [2.3](<../2. Error Values and Hierarchies/2.3. Never-throw boundaries and error budgets.md>), then save `pitfalls.mts` below beside them in a directory without a `tsconfig.json`. Compile with `tsc --strict --noUncheckedIndexedAccess --exactOptionalPropertyTypes --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist parser.mts boundary.mts pitfalls.mts`, then run `node dist/pitfalls.mjs`. There are no package dependencies or external services.

### 2) **Observe payload, reporting and fallback failures**

```typescript
// file: pitfalls.mts
import { parseJsonUsers, type User } from "./parser.mjs";
import { deliver } from "./boundary.mjs";
function unsafeName(text: string): string {
  const user = JSON.parse(text) as User; // Deliberately bad: no User checks were executed.
  return user.name.toUpperCase();
}
for (const [label, text] of [["shape", '{"error":"offline"}'], ["syntax", "{bad"]] as const) {
  try { unsafeName(text); }
  catch (error) { console.log(label, error instanceof TypeError, error instanceof SyntaxError); }
}
for (const text of ['[{"name":"Ada","age":37}]', '[{"error":"offline"}]', "{bad"]) {
  const result = parseJsonUsers(text);
  console.log("parsed", result.ok ? result.value.map(user => user.name.toUpperCase()).join(",")
    : result.issues.map(issue => issue.code).join(","));
}
const operationError = new Error("job failed");
const reportingError = new Error("report failed");
const secondary = Promise.reject(operationError).catch(() => { throw reportingError; });
try { await secondary; }
catch (error) { console.log("catch created rejection", error === reportingError); }
const observed = await deliver(() => Promise.reject(operationError), async () => { throw reportingError; });
console.log("separate outcomes", observed.kind === "dropped" && observed.error === operationError,
  observed.kind === "dropped" && !observed.report.ok && observed.report.error === reportingError);
class MissingRecord extends Error {}
function broad(work: () => string): string {
  try { return work(); }
  catch { return "fallback"; }
}
function specified(work: () => string): string {
  try { return work(); }
  catch (error) {
    if (error instanceof MissingRecord) return "fallback";
    throw error;
  }
}
const unexpected = new TypeError("dependency failed");
console.log("masked", broad(() => { throw unexpected; }));
console.log("expected", specified(() => { throw new MissingRecord("absent"); }));
try { specified(() => { throw unexpected; }); }
catch (error) { console.log("unhandled by this policy", error === unexpected); }
let revision = 0;
let permitted = true;
const idOnly = new Map<string, boolean>();
const versioned = new Map<string, { revision: number; permitted: boolean }>();
function stale(): boolean {
  const hit = idOnly.get("u1");
  if (hit !== undefined) return hit;
  idOnly.set("u1", permitted);
  return permitted;
}
function currentVersion(): boolean {
  const hit = versioned.get("u1");
  if (hit?.revision === revision) return hit.permitted;
  versioned.set("u1", { revision, permitted });
  return permitted;
}
function changePolicy(next: boolean): void { permitted = next; revision++; }
console.log("before change", stale(), currentVersion());
changePolicy(false);
console.log("after change", stale(), currentVersion(), permitted);
console.log("cache entries", idOnly.size, versioned.size);
```

Expected output:

```text
shape true false
syntax false true
parsed ADA
parsed missing,missing
parsed json-syntax
catch created rejection true
separate outcomes true true
masked fallback
expected fallback
unhandled by this policy true
before change true true
after change true false false
cache entries 1 1
```

The first mistake confuses JSON syntax with an application shape. Valid JSON containing an error object passes decoding and reaches a TypeError in the unchecked consumer. Invalid JSON instead fails during decoding. The repaired path uses the canonical parser and handles both kinds of failure. This is local text ingestion; it does not test HTTP status handling, response reading or a fetch integration.

The next mistake assumes that attaching a rejection handler finishes ownership of failure. Here the handler itself throws, so the promise returned by `.catch` rejects with the reporting error. The demonstration observes that promise immediately to avoid an unhandled rejection. The repaired `deliver` helper awaits both callbacks and retains both failure values. `void` alone would neither catch a rejection nor report it. Actual fatal Node behavior is tested separately in the [boundary lesson](<../2. Error Values and Hierarchies/2.3. Never-throw boundaries and error budgets.md>).

### 3) **Make fallback and freshness policies specific**

The broad fallback changes the unexpected dependency failure into an ordinary string. Whether that is appropriate depends on the boundary's explicit recovery policy; a log statement alone would not establish successful recovery. The more specific wrapper handles only its documented MissingRecord case and rethrows the same other value. Its caller can then decide how to report, adapt or terminate that path.

Do not infer that every TypeError is a programmer bug, every RangeError must crash, or every Error outside a class family is safe to default. A library can deliberately use a built-in error for rejected arguments. Error identity helps apply a known API contract; the constructor name does not establish a universal handling category. Keep the protected operation narrow enough that the classification means what the consumer intends.

The last case isolates cache freshness. An ID-only key keeps returning the old true decision after the policy changes. The version-aware map recomputes because the tracked revision changed. It retains one entry for the one fixed subject in this example. Correctness depends on every relevant policy update using the revision protocol; merely adding a version field is insufficient if a dependency can change without updating it.

This is a synchronous, in-memory invalidation demonstration. It omits authenticated subjects, resources, actions, tenants, distributed invalidation, concurrent updates and an atomic check-and-act operation. A request-scoped cache can also become stale within the request if its underlying state changes. A short TTL defines a possible staleness window rather than automatically satisfying a revocation requirement.

Caching a verdict is not inherently forbidden. Its key, dependency versions, invalidation and accepted freshness window must support the decision's actual contract. For permissions, [OWASP's authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) calls for correct checks on each request and for the relevant object/functionality. This toy map proves no authorization integration. Use an authoritative, tested protocol for the real application, and keep full cache mechanics in the [memoization owner](<../../../14 Decorators and Metadata/sections/3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>).

### 4) **Common confusion**

Catching an exception and returning a familiar fallback can hide its significance. Narrowing an error helps only when that distinction matches the invoked API's documented behavior. A logger or rejection callback can fail too, and the returned completion still needs an owner.

“Validated earlier,” “cached per request” and “short TTL” each leave lifetime questions unanswered. Name what can change, who changes it and how the consumer sees that change. Parsing shape and making a current permission decision are separate operations.

### 5) **Performance note**

The examples observe failures, decisions and entry counts, not speed. Parsing traverses the declared fields and creates outputs/issues; reporting awaits completion; caches retain entries and perform lookups. Recomputing a decision may be cheap or involve remote work, while a cache adds invalidation and consistency costs. No microsecond-versus-millisecond comparison, identical handled/floating-promise overhead or free correctness claim was measured. Choose performance work after the required recovery and freshness semantics are clear.

### 6) **Mentor note**

Ask the learner which line fails for valid JSON with the wrong shape and which fails for invalid JSON. Then make the reporter reject and identify the two distinct failure values. Finally, remove the revision update and predict the cached decision after the change. A strong repair explains the specific consumer, the fallback policy, the invalidation assumption and which real integration still needs testing.
