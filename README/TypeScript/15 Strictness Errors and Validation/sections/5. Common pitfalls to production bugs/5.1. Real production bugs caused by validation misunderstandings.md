## 5.1. Real production bugs caused by validation misunderstandings

### 1) **Blind `as User` on fetch results crashed on malformed payloads** (assertion without evidence)

**Definition** — a `fetchUser(id)` helper returning `JSON.parse(await res.text()) as User` (assertion without evidence — malformed/partial/error payloads blessed as `User`) crashed profile pages (`user.name.toUpperCase()` on `undefined` — `TypeError` with confident types, green CI) whenever the API returned error-shaped JSON (`{ error: … }` parsed "successfully" into the `User` lie).

**What problem it solves / history** — `as`-cast ingestion treats parsing as *already done* (JSON parsed = User proven — conflating deserialization with validation). Parse functions (see 3.1) treat parsing as *the work* (unknown → `User | Errors` — evidence per field). The incident class vanishes where parse replaces cast: malformed payloads surface as error *values* at the boundary, never as crashes downstream.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), parse every fetch result (hand-rolled per 3.1 or schema per 3.2 — `User | ParseError[]`, never `as User`); narrow before use (union checks, `ok` discriminants — zero casts downstream); treat downstream `as` on fetched data as parser-bug reports (narrow the parser until demand vanishes).

**Runnable example** — parse replaces cast (good vs bad, `tsc --strict`):

```typescript
// good — parsed fetch (malformed payloads surface as values, never crashes)
interface User { name: string }
type PErr = { path: string; reason: string }; // re-declared: fences compile standalone (minimal error shape)
function parseUser(body: unknown): User | PErr[] {
  if (typeof body !== "object" || body === null) return [{ path: "", reason: "not-object" }];
  const r = body as Record<string, unknown>; // single contained cast (evidence-gathering — see 3.1 full pattern)
  if (typeof r["name"] !== "string") return [{ path: "name", reason: "want-string" }];
  return { name: r["name"] }; // proven User (consumers narrow, never cast)
}
const good = parseUser(JSON.parse('{"name":"a"}'));
const bad = parseUser(JSON.parse('{"error":"x"}'));
console.log(Array.isArray(good) ? "err" : good.name.toUpperCase(), Array.isArray(bad) ? bad[0]?.path : "ok"); // A name — valid flows, malformed lists
// bad — JSON.parse(text) as User (assertion without evidence — error-shaped payloads blessed as User, crashing downstream)
// fix — parseUser (evidence-backed narrowing — contained casts inside, zero casts outside, errors as values)
```


**Common confusion** — "try/catch covers malformed payloads" — try/catch covers *syntax* errors (`JSON.parse` throwing on invalid JSON — exceptional); *shape* errors (valid JSON, wrong shape — `{"error":"x"}`) need *parsing* (values, not exceptions — expected failures per 2.1 discipline). "backend guarantees shapes" — backends *version* (v2 payloads to v1 parsers — shape drift across deploys); frontend parsing is the contract check (drift surfaces as error values, not crashes). "one `as` is harmless" — one `as` *per boundary* compounds per boundary (every ingestion a lie — incidents distribute across all of them).

**Performance note** — parsing costs per-field checks once per fetch (trivial vs network latency); `as`-casts cost zero checks (and unbounded incident surface). Parse-once economics at every fetch boundary.

**Mentor note** — feed one error-shaped payload through `as`-cast vs parse paths (confident crash vs error list — honesty demonstrated in one input). Exercise: convert three `as`-cast fetches to parse functions and delete downstream defensive checks the casts required (honesty upstream deletes paranoia downstream). Review gate: `as` on fetched/parsed values fails review (parse, don't assert).

### 2) **Swallowed async errors in fire-and-forget handlers crashed the process** (floating promises)

**Definition** — fire-and-forget `handler()` calls without `await`/`catch`/`.then(onErr)` (floating promises — rejections unobserved): one handler's rejection became an `unhandledRejection` crashing the Node process (all in-flight work lost for one background task's error). Sync-equivalent code (`try/catch` around direct calls) would have contained it; async fire-and-forget without handling contains nothing.

**What problem it solves / history** — `async` handlers *look* synchronous (same `try/catch` shapes nearby in code) while *behaving* asynchronously (rejections escape to process-level handlers, not local catches — unless awaited/caught explicitly). Linters (`no-floating-promises`) exist precisely because reviewers can't see floaters (no `await` keyword *missing* is invisible — the absence of syntax as the bug). Full async treatment lands in domain 18; this promise records the incident class with its immediate discipline.

**Modern guidance** — as of TypeScript 5.9 era, `await` or `.catch()` every promise (no floating promises — lint `no-floating-promises` as error, not warning); handle fire-and-forget explicitly (`void run().catch(report)` — the `void` marks intent, `.catch` handles rejection); install process-level backstops (`unhandledRejection` → log + graceful degradation — see 2.3 promise 3) as backstops, never as primary handling.

**Runnable example** — handled floats, never bare (good vs bad, `tsc --strict`):

```typescript
// good — explicit handling on every float (void marks intent, catch handles rejection)
async function job(ok: boolean): Promise<string> {
  if (!ok) throw new Error("job failed"); // rejection possible (async failures are values-in-flight — handled below)
  return "done";
}
void job(true).then(
  (v) => console.log(v), // fulfilled branch (handled — success consumed explicitly)
  (e) => console.log(`caught:${e instanceof Error ? e.message : "?"}`), // rejected branch (handled — no float, no crash)
);
// bad — job(false); (floating promise — rejection unobserved → unhandledRejection → process crash in production)
// fix — void + branches (intent marked, rejection handled — no promise floats, ever)
```

```typescript
// good — awaited handlers in async contexts (rejections flow into local try/catch — sync-equivalent containment)
export {}; // module marker for top-level await in this runnable snippet
async function job(ok: boolean): Promise<string> { // re-declared: fences compile standalone (minimal async shape)
  if (!ok) throw new Error("job failed");
  return "done";
}
async function handle(): Promise<string> {
  try {
    return await job(true); // awaited (rejection lands in this catch — local containment, sync-shaped reasoning)
  } catch {
    return "fallback"; // contained (never-throw handler contract per 2.3 promise 1 — fallback served)
  }
}
console.log(await handle()); // done — awaited (rejections contained locally — no process-level involvement)
// bad — job(true); return "started"; (fire-and-forget without catch — rejection floats past the handler's lifetime)
// fix — await (containment by construction) or void+.catch (explicit float handling) — never bare floats
```

```typescript
// good — backstop handler for the truly unexpected (process-level safety net, not primary handling)
function backstop(e: unknown): string {
  const msg = e instanceof Error ? e.message : String(e); // narrowed report (structured — see 2.3 promise 3's report shape)
  return `reported:${msg}`; // backstop reports (log + alert in production — degradation path, not silence)
}
console.log(backstop(new Error("x"))); // reported:x — backstop shape (installed per runtime entry — last resort, tested by fault-injection)
// bad — no backstop (first unhandled rejection crashes the process with default logging — worst diagnostics at the worst moment)
// fix — backstop per entry (report + degrade — 2.3 promise 3's architecture; primary handling stays per-promise)
```

**Common confusion** — "`void` suppresses errors" — `void` marks *intent* (fire-and-forget deliberately); handling comes from `.catch`/branches (intent without handling is still floating — `void job()` alone crashes identically). "top-level await fixes floats" — `await` *contains* (rejection lands locally); un-awaited top-level expressions still float (top-level position changes nothing about handling). "backstops replace handling" — backstops catch *unknown* failures (last resort); known async work handles explicitly (primary handling per promise — backstops never substitute).

**Performance note** — handled vs floating identical runtime (one branch per settlement either way); unhandled rejections cost process crashes (unbounded — all in-flight work lost per float). Lint costs nothing steady-state (static analysis); incidents cost availability.

**Mentor note** — remove one `.catch` and crash a dev process via unhandledRejection (float-to-crash in one deletion — handling proven load-bearing). Exercise: enable `no-floating-promises` and fix each error (await/catch per float — the at-risk list is the incident backlog, pre-triaged). Review gate: floating promises fail review unconditionally; `void` without `.catch`/branches fails review.

### 3) **Over-broad catch narrowed nothing and masked a bug for months** (swallowing vs handling)

**Definition** — `catch { return fallback; }` (or `catch (e) { log(e); return default; }` without narrowing) handling *every* throwable identically: expected failures (network timeouts — correctly defaulted) *and* programmer bugs (TypeErrors from typos — incorrectly defaulted) flowing through one recovery path. The bug hid for months (typo throwing per call, default masking per call — green metrics, wrong behavior) until a rewrite exposed the dead code path.

**What problem it solves / history** — undifferentiated catches (`catch` → default, regardless of error kind) conflate *expected* failures (handle: default/retry/degrade) with *bugs* (rethrow/report/crash loudly). Narrowed catches (`instanceof` dispatch per kind — expected handled, bugs rethrown) preserve the distinction: routines degrade gracefully, bugs surface loudly — each category handled per its nature, never blended.

**Modern guidance** — as of TypeScript 5.9 era, narrow catch bindings (`instanceof` per kind — expected → handle; bug → rethrow/report); rethrow programmer errors (TypeError/ReferenceError/RangeError from own code — bugs, not data); log-and-default expected failures (network/parse/user-input — routines, not incidents). See 1.2's `toError` normalizer + 2.2's hierarchy dispatch for the full toolkit.

**Runnable example** — narrowed catches, rethrown bugs (good vs bad, `tsc --strict`):

```typescript
// good — kinds dispatched (expected handled, bugs rethrown — never blended)
function toError(e: unknown): Error { // re-declared: fences compile standalone (shared normalizer sketch)
  return e instanceof Error ? e : new Error(String(e));
}
function load(key: string): string {
  try {
    if (key === "") throw new Error("empty-key"); // expected failure (routine — handled below as default)
    return `v:${key}`;
  } catch (e) {
    if (e instanceof TypeError) throw e; // BUG rethrown (typos/coding errors surface loudly — never defaulted)
    console.log(`load failed: ${toError(e).message}`); // expected logged (routines reported, not hidden)
    return "default"; // expected defaulted (routines degrade gracefully — bugs never reach here)
  }
}
console.log(load(""), load("a")); // default v:a — kinds dispatched (expected defaulted, bugs would rethrow)
// bad — catch { return "default"; } (undifferentiated: typos defaulted alongside timeouts — bugs masked for months)
// fix — instanceof dispatch (expected handled, bugs rethrown — categories never blended, masking structurally impossible)
```

```typescript
// good — rethrow preserves stacks (original error propagates with cause chain intact — see 2.2 promise 3)
function strict(code: number): string {
  try {
    if (code < 0) throw new RangeError("negative"); // programmer error (contract violated — fail-fast named)
    return `ok:${code}`;
  } catch (e) {
    if (e instanceof RangeError) throw e; // rethrown (bugs propagate — stacks intact, cause chains composable)
    return "fallback"; // non-Range errors (unexpected shapes — defaulted cautiously with logging below... simplified: rethrow unknown too in prod)
  }
}
console.log(strict(5)); // ok:5 — bugs rethrown (loud), routines defaulted (graceful) — categories separated structurally
// bad — catch (e) { return "fallback"; } (RangeError swallowed — contract violations masked as routine fallbacks)
// fix — rethrow bugs (fail-fast named — masking bugs as defaults is the months-long-hiding incident class)
```

```typescript
// good — validation errors handled, programmer errors escalated (per-kind policy in one catch)
class ValidationError extends Error {
  constructor(public field: string) {
    super(`bad:${field}`);
    this.name = "ValidationError"; // kind named (expected-failure family — handled, not escalated)
  }
}
function save(field: string): string {
  try {
    if (field === "") throw new ValidationError("name"); // expected (user data — handled below as 422-style default)
    return `saved:${field}`;
  } catch (e) {
    if (e instanceof ValidationError) return `invalid:${e.field}`; // expected handled (user-facing default — no escalation)
    throw e; // bugs escalated (non-validation errors propagate — crash reporting consumes, never defaults)
  }
}
console.log(save(""), save("x")); // invalid:name saved:x — per-kind policy (expected defaulted, bugs escalated — never blended)
// bad — catch { return "saved?" } (bugs saved as successes — corrupted state wearing valid shapes downstream)
// fix — kind dispatch (ValidationError handled; everything else rethrown — blending structurally impossible)
```

**Common confusion** — "catch-all is defensive" — catch-all *without narrowing* defends nothing (bugs and routines blended — masking bugs while handling routines; defensive catching narrows first, defaults second, rethrows third). "rethrowing loses context" — bare `throw e` preserves stacks fully (add `cause` where layer context exists per 2.2 promise 3 — rethrow is preservation, not loss). "narrowed catches are verbose" — three branches per catch (expected/bug/unknown — the complete taxonomy) vs one blended branch (incomplete by construction — verbosity that covers vs terseness that masks).

**Performance note** — `instanceof` per catch (shallow hierarchies — trivial); rethrows cost stack capture per bug (exceptional — bugs exceptional by definition); blended catches cost incidents (months-hidden bugs — unbounded). Narrowing is free correctness.

**Mentor note** — plant a typo inside a blended-catch try block (TypeError defaulted silently for months — then narrow the catch and watch it surface) — masking demonstrated, not theorized. Exercise: narrow three blended catches (expected/bug/unknown branches each) — masking deleted per conversion. Review gate: undifferentiated `catch { return default }` fails review (narrow-first, always).

### 4) **Validated-once cached verdict served stale permissions after role change** (correctness caching)

**Definition** — an `isAdmin(user)` verdict cached per user-id (memoized authorization — first check stored, subsequent checks skipped) served *stale* permissions after role revocation (demoted admin operating with cached admin rights for the cache TTL — authorization bypass via correctness caching). Correctness verdicts (authorization, validation, eligibility) depend on *mutable* state — caching them freezes decisions while reality moves.

**What problem it solves / history** — memoization applied to *correctness* (permission checks, validation verdicts, eligibility gates — verdicts over mutable world-state) instead of *computation* (pure deterministic functions — same args, same result, forever). Cached correctness goes stale on world-change (role revoked, config updated, clock advanced) while cached computation never does (pure functions don't observe the world). The rule: memoize computations (see 14/3.2), re-evaluate verdicts (every time, cheaply).

**Modern guidance** — as of TypeScript 5.9 era, never cache authorization/validation/eligibility verdicts (re-evaluate per decision — cheap checks, current world); memoize pure computations only (deterministic, side-effect-free, world-independent — see 14/3.2's bounds discipline); scope caches to request lifetimes where freshness windows exist (per-request memo — bounded staleness by construction, never cross-request correctness caching).

**Runnable example** — verdicts fresh, computations cached (good vs bad, `tsc --strict`):

```typescript
// good — authorization re-evaluated per decision (cheap check, current world — never cached)
interface Acct { id: string; roles: string[] }
function canAdmin(a: Acct): boolean {
  return a.roles.includes("admin"); // evaluated per call (world-current — role changes effective immediately)
}
const acc: Acct = { id: "u", roles: ["admin"] };
console.log(canAdmin(acc)); // true — fresh verdict (revocation effective next call, no TTL gap)
// (revoke: acc.roles = []; canAdmin(acc) === false — immediate (no cached verdict to expire))
acc.roles = [];
console.log(canAdmin(acc)); // false — revocation effective (re-evaluation per decision — correctness never stale)
// bad — memoized canAdmin per user-id (first verdict cached — demoted admins operating until TTL expiry — authorization bypass)
// fix — re-evaluate verdicts (cheap checks per decision); memoize computations (pure functions per 14/3.2)
```

```typescript
// good — request-scoped caching (bounded staleness by construction — per-request memo, never cross-request verdicts)
function perRequest(): { checked: Set<string> } {
  return { checked: new Set() }; // scope object (request lifetime — discarded after, freshness bounded structurally)
}
const scope = perRequest();
scope.checked.add("u1");
console.log(scope.checked.has("u1"), scope.checked.size); // true 1 — scoped memo (request dies → cache dies — staleness impossible across requests)
// bad — global verdict cache (cross-request correctness caching — user A's verdict serving user B's request eventually)
// fix — request scopes (freshness bounded by construction — scopes die with requests, verdicts never outlive their world)
```

```typescript
// good — computation memoized, verdicts re-evaluated (each cached per its nature — purity vs world-dependence distinguished)
function expensive(n: number): number { return n * n; } // pure computation (memoizable — same args, same result, forever)
const memo = new Map<number, number>(); // computation cache (safe: purity verified — world-independent)
function calc(n: number): number {
  const hit = memo.get(n);
  if (hit !== undefined) return hit; // cached computation (purity-guaranteed fresh — no world to go stale)
  const out = expensive(n);
  memo.set(n, out);
  return out;
}
console.log(calc(7).toFixed(0), calc(7).toFixed(0)); // 49 49 — memoized computation (verdicts elsewhere re-evaluated per decision)
// bad — memoizing canAdmin (verdict over mutable roles — cached correctness going stale on world-change — authorization bypass class)
// fix — memoize computations (pure, world-independent — see 14/3.2 bounds); re-evaluate verdicts (world-dependent — every decision fresh)
```

**Common confusion** — "caching verdicts is an optimization" — caching *computations* optimizes (same result guaranteed); caching *verdicts* corrupts (world moves, verdicts freeze — authorization bypass, stale eligibility, expired validation). "short TTLs make verdict caching safe" — TTLs bound *staleness windows* (still wrong within the window — demoted admin operating for TTL seconds — bounded bypass, still bypass). "re-evaluation is wasteful" — verdict checks cost microseconds (role-membership, field-presence — trivial vs request handling); verdict caching saves microseconds while risking authorization — worst trade in this domain.

**Performance note** — verdict re-evaluation costs microseconds per decision (membership checks, field reads — trivial); computation memoization saves milliseconds+ per hit (recomputation avoided — the legitimate cache); verdict caching saves microseconds while risking bypass (never worth it — re-evaluate, always).

**Mentor note** — revoke a role mid-session against cached vs fresh verdicts (stale admin powers vs immediate demotion — bypass demonstrated, not theorized). Exercise: find one cached verdict (memoized authorization/validation/eligibility) and convert to per-decision evaluation (bypass deleted per conversion). Review gate: memoized correctness verdicts fail review unconditionally (computations memoize; verdicts re-evaluate).
