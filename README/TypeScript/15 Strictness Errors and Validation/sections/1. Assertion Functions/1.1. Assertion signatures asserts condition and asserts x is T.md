## 1.1. Assertion signatures — `asserts condition` and `asserts x is T`

### 1) **Assert the particular condition you need**

An assertion signature tells TypeScript what it may assume after a function returns normally. Its implementation must justify that claim. `asserts condition` communicates the supplied condition; `asserts value is T` communicates a type refinement. Neither signature inserts a runtime check automatically. The [TypeScript introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#assertion-functions) models this successful continuation.

This lesson applies those mechanics to a small shared helper module and callers with an explicit failure policy. Predicate inference and callable-context details remain in [05/3.3](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>), and union-specific narrowing remains in [07/3.3](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>).

Use **TypeScript 7.0.2** and emitted modules on **Node.js 20.20.2**. Save the three files below in an empty directory without a `tsconfig.json`. No package dependencies are needed. Compile and run:

```bash
tsc --strict --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist assertions.mts cases.mts trust.mts
node dist/cases.mjs
node dist/trust.mjs
```

The module provides condition, nullish and unreachable-path helpers. It also contains one application-specific configuration assertion. Keeping that domain helper beside its configuration module would be equally reasonable; a single global utility file is not required.

```typescript
// file: assertions.mts
export function assert(condition: unknown, message: string): asserts condition {
  if (!condition) throw new Error(message);
}
export function assertDefined<Value>(value: Value, name: string): asserts value is NonNullable<Value> {
  if (value === null || value === undefined) throw new Error(`missing:${name}`);
}
export function assertNever(value: never): never {
  void value;
  throw new Error("unhandled mode");
}
export interface Config { host: string; port: number }
export function assertConfig(value: unknown): asserts value is Config {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new Error("config object required");
  }
  if (!("host" in value) || typeof value.host !== "string" || value.host.length === 0) {
    throw new Error("nonempty host required");
  }
  if (!("port" in value) || typeof value.port !== "number" ||
      !Number.isInteger(value.port) || value.port < 1 || value.port > 65535) {
    throw new Error("port must be an integer from 1 to 65535");
  }
}
```

The nullish helper rejects only `null` and `undefined`. It preserves `0`, `false` and an empty string. The condition helper can express something narrower or different: `assert(value !== null, ...)` excludes `null` but leaves a possible `undefined`. A truthiness check of `value` itself would answer a different question.

The original [Marius Schulz walkthrough](https://mariusschulz.com/blog/assertion-functions-in-typescript) usefully compares a non-null assertion operator, an inline check and a reusable helper. The operator erases while the latter two execute checks. Its historical spelling of `NonNullable` is not needed here; the current compiler's utility type and the runtime comparison define this example's contract.

### 2) **Check a shape before advertising its type**

The configuration helper first establishes an object, then checks both fields. Merely finding a `port` property would not prove a number. This implementation additionally enforces a nonempty host and integer port range; those semantic constraints are stronger than the plain interface expresses. It permits inherited properties and extra keys and does not clone or freeze the object. A stricter own-property or parsing policy belongs to the actual boundary's contract.

```typescript
// file: cases.mts
import { assert, assertDefined, assertNever, assertConfig } from "./assertions.mjs";
type Value = string | number | boolean | null | undefined;
function onlyNotNull(value: Value): string {
  assert(value !== null, "null rejected");
  const stillMaybeUndefined: string | number | boolean | undefined = value;
  // const required: string | number | boolean = value; // TS2322: undefined remains possible
  return String(stillMaybeUndefined);
}
function renderDefined(value: Value): string {
  assertDefined(value, "value");
  const defined: string | number | boolean = value;
  return String(defined);
}
function readPort(value: unknown): string {
  assertConfig(value);
  return value.host.toUpperCase() + ":" + value.port.toFixed(0);
}
function attempt(label: string, action: () => unknown): void {
  try { console.log(label, action()); }
  catch (error) { console.log(label, error instanceof Error ? error.message : "unexpected failure"); }
}
console.log("condition", onlyNotNull(undefined), onlyNotNull(0), JSON.stringify(onlyNotNull("")));
console.log("defined", JSON.stringify([renderDefined(0), renderDefined(false), renderDefined("")]));
attempt("null condition", () => onlyNotNull(null));
attempt("nullish", () => renderDefined(undefined));
console.log("config", readPort({ host: "api", port: 80 }));
for (const input of [null, { host: "api", port: "80" }, { host: "api", port: NaN }, { host: "", port: 80 }]) {
  attempt("bad config", () => readPort(input));
}
type Mode = "dev" | "prod";
function describeMode(mode: Mode): string {
  switch (mode) {
    case "dev": return "development";
    case "prod": return "production";
    default: return assertNever(mode);
  }
}
console.log("modes", describeMode("dev"), describeMode("prod"));
attempt("untyped invocation", () => Reflect.apply(describeMode, undefined, ["other"]));
```

Expected output:

```text
condition undefined 0 ""
defined ["0","false",""]
null condition null rejected
nullish missing:value
config API:80
bad config config object required
bad config port must be an integer from 1 to 65535
bad config port must be an integer from 1 to 65535
bad config nonempty host required
modes development production
untyped invocation unhandled mode
```

These callers deliberately catch helper failures and report them locally. An assertion may validate unknown input when a throwing API and its caller's handling policy fit. It need not crash the process. A parser returning a failure value may instead fit a form or batch operation that needs structured recoverable errors. [Predicate versus assertion choice](<./1.2. Type predicates vs assertions caller vs thrower.md>) and [Result](<../2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>) own those broader decisions.

The `never` parameter checks that the switch has covered its declared union. It does not validate arbitrary untyped input before the call. The `Reflect.apply` demonstration deliberately bypasses the ordinary typed call boundary and reaches the real throw. Extend Mode with `"test"` in an isolated copy: the old default call to `assertNever(mode)` is rejected until the new case is handled. [The exhaustiveness owner](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) explains that mechanism in full.

### 3) **Test helper behavior and preserve its assumptions**

Shared helpers can give repeated checks a consistent contract and useful failure names. They do not become correct because they are centralized, and checking their declarations does not verify their logical claims. Exercise invalid values and the caller operation that should have become safe, as well as valid inputs. A local `if (...) throw` is also valid when it makes a one-off condition clearer.

The next example shows two distinct limits. A dishonest assertion can return normally for an invalid input. An honest assertion can check a mutable object whose state later changes. The checker does not automatically invalidate every previous refinement after a reflective write.

```typescript
// file: trust.mts
import { assertConfig } from "./assertions.mjs";
function dishonest(value: unknown): asserts value is string { void value; }
function useDishonest(value: unknown): string {
  dishonest(value);
  return value.toUpperCase();
}
try { useDishonest(42); }
catch (error) { console.log("dishonest", error instanceof TypeError); } // dishonest true
const config: unknown = { host: "api", port: 80 };
assertConfig(config);
Reflect.set(config, "port", "changed");
try { console.log(config.port.toFixed(0)); }
catch (error) { console.log("mutation", error instanceof TypeError); } // mutation true
```

Both files compile under the stated strict options. The dishonest helper's body contains no validation, yet its signature refines its caller. In the second case, the initial check was honest; later mutation breaks the assumption. Preserve ownership or produce an appropriately isolated parsed value when subsequent code must rely on stable state. A signature alone neither freezes an object nor proves that unrelated code cannot mutate it.

For a shared library, review the advertised predicate, implementation, thrown failure and caller's error policy together. Tests are evidence about selected cases, not a proof that every future helper implementation or new domain shape remains correct. Keep failures close to their real requirement, and avoid including unnecessary sensitive values in diagnostic messages.

### 4) **Common confusion**

The condition `value !== null` is not the same as `value` being truthy or non-nullish. A nullish assertion intentionally accepts other falsy values. An assertion signature is also different from `as Config` or postfix `!`: the functions shown execute checks, while those operators do not insert them.

TypeScript trusts a declared assertion's successful-return claim. It does not prove that the body rejects every counterexample. Ordinary void helpers, assertion-call target typing and predicate behavior have their own rules in the callable owner. Finally, shape validation does not establish a user's identity, authorization or any untested domain capability merely because the interface was named `Admin`.

### 5) **Performance note**

The assertion annotations erase, but calls, comparisons, property reads and throws remain. `assertConfig` executes several checks; there is no universal one-branch cost for every assertion. Replacing a local check with a shared helper changes organization and may introduce a call; no faster/equal-runtime or inlining result was measured here. Removing required checks to save assumed nanoseconds would also remove their runtime enforcement. Measure the actual path if assertion cost matters.

### 6) **Mentor note**

Ask the learner to predict the condition and nullish outputs for undefined, zero and the empty string. Then give a malformed port and identify the check that rejects it before `toFixed`. Remove that check and compare the resulting failure location. A sound review distinguishes the signature's promise, the body's evidence, the caller's failure policy and the mutation assumptions after return.
