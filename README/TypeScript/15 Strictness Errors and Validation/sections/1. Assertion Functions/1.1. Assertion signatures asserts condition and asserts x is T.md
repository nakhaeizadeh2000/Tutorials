## 1.1. Assertion signatures — `asserts condition` and `asserts x is T`

### 1) **`asserts condition` shape** (throwing guards proving truthiness downstream)

**Definition** — `function assertDefined<T>(x: T | null | undefined): asserts x is NonNullable<T>` … more precisely the *condition* form: `function assert(cond: unknown, msg?: string): asserts cond` — after `assert(x !== null)`, the checker treats `x` as truthy-narrowed (excludes `null`/`undefined`/`false`/`0`/`""` per the condition's shape). Failure *throws* (never returns normally) — callers proceed unconditionally after the call, narrowed by the proven condition.

**What problem it solves / history** — manual invariant checks (`if (x == null) throw new Error(…)` — 5 lines per boundary, inconsistent messages, narrowing that *happened* to work via control flow) scattered ad-hoc guards that reviewers couldn't distinguish from business branches. Assertion functions name the pattern: one shared `assert`/`assertDefined` per codebase (tested once, messaged consistently), with checker-enforced narrowing downstream (the call *proves*, not merely checks).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), centralize `assert`, `assertDefined`, and `assertNever` in one utils module (shared narrowing vocabulary — tested once, messaged consistently); assert *invariants* (conditions that must hold or the program cannot proceed — non-null configs, initialized singletons, unreachable branches); never assert *expected* failures (user input, network absence — those narrow via predicates/unions, not throws).

**Runnable example** — invariants proven, not branched (good vs bad, `tsc --strict`):

```typescript
// good — shared assertion library (one vocabulary, tested once, messaged consistently)
function assert(cond: unknown, msg = "assertion failed"): asserts cond {
  if (!cond) throw new Error(msg); // throws (never returns normally on failure — callers proceed narrowed)
}
function assertDefined<T>(x: T | null | undefined, name: string): asserts x is NonNullable<T> {
  if (x === null || x === undefined) throw new Error(`missing:${name}`); // named failures (diagnosable)
}
const maybe: string | null = "hi";
assertDefined(maybe, "maybe");
console.log(maybe.toUpperCase()); // HI — narrowed (NonNullable<string> after the assertion, no branch in sight)
// bad — ad-hoc invariant branches per call site (5 lines each, inconsistent messages, narrowing by accident)
// fix — assert/assertDefined/assertNever (named, shared, tested — narrowing by contract)
```

```typescript
// good — config invariants asserted once at startup (fail-fast with named errors)
interface Cfg { host: string; port?: number }
function assertDefined<T>(x: T | null | undefined, name: string): asserts x is NonNullable<T> { // re-declared: fences compile standalone
  if (x === null || x === undefined) throw new Error(`missing:${name}`);
}
function loadConfig(raw: Partial<Cfg>): Cfg {
  assertDefined(raw.host, "CFG.host"); // invariant (cannot proceed without host — throw with a name)
  return { host: raw.host, port: raw.port ?? 80 }; // narrowed host (string — proven, not cast)
}
console.log(loadConfig({ host: "h" }).host.toUpperCase()); // H — startup invariants (fail-fast, diagnosable)
// bad — if (!raw.host) return {} as Cfg (lies downstream — unconfigured server booting with casted emptiness)
// fix — assertDefined (throw named errors at the boundary — unconfigured never boots)
```

```typescript
// good — assertNever closing exhaustive switches (unreachable proven, additions break loudly)
function assertNever(x: never): never { throw new Error(`unreachable:${String(x)}`); }
type Ev = "a" | "b";
function handle(e: Ev): number {
  switch (e) {
    case "a": return 1;
    case "b": return 2;
    default: return assertNever(e); // never here IFF all members cased (new member breaks HERE — see 07/3.2)
  }
}
console.log(handle("a")); // 1 — exhaustiveness proven (shared helper — same vocabulary as assertDefined above)
// bad — default: throw new Error("unknown") (untyped throw — no never-proof, additions silent)
// fix — assertNever (never-typed parameter proves unreachability — additions error at the sink)
```

**Common confusion** — "assertions validate input" — assertions enforce *invariants* (must-hold-or-crash); *input* validation narrows recoverably (predicates/unions — see 1.2) — crashing on user input is a bug, crashing on violated invariants is the design. "asserted code can't fail" — asserted *conditions* hold past the call (or the call threw — no third outcome); downstream logic still needs its own correctness (narrowing proves types, not logic). "assertion messages don't matter" — named messages (`missing:CFG.host`) diagnose; generic ones (`assertion failed`) puzzle at 3am — message quality is incident-response quality.

**Performance note** — assertions cost one branch per call (negligible); failed assertions throw (exceptional by design — stack capture costs, paid only when invariants actually break). Shared helpers vs ad-hoc branches: identical runtime, centralized messages.

**Mentor note** — delete one `assertDefined` and watch downstream narrowings collapse (property reads erroring — proof-by-absence of the assertion's value). Exercise: convert five ad-hoc invariant branches to shared assertions and count message-consistency improvements (diagnosability in one diff). Review gate: ad-hoc `if (x == null) throw` branches fail review (shared assertions — one vocabulary).

### 2) **`asserts x is T` shape** (throwing type-guards narrowing to full types)

**Definition** — `function assertIsAdmin(x: User): asserts x is Admin` — on success narrows `x` to the *full type* `T` (not just non-null); on failure throws. Unlike predicates (`x is T` returning boolean — caller branches), assertions *transfer control*: after the call, no branch remains (the failure path exited via throw). Full-type narrowing (not truthiness) is what distinguishes the `is T` form from bare `asserts condition`.

**What problem it solves / history** — role/capability checks (`if (!isAdmin(u)) throw …` — predicate plus manual throw per site, message drift, narrowing via the `if` rather than the check) split enforcement across two statements that reviewers had to verify *together* (predicate correct? throw present? message useful?). Assertion form fuses them: one call enforces *and* narrows (capability proven downstream, failure named at the throw).

**Modern guidance** — as of TypeScript 5.9 era, write `asserts x is T` for capability/role/shape enforcement (admin checks, parsed-shape confirmations, state-machine transitions); keep predicates for recoverable filtering (`filter`/`find`/optional handling — see 1.2). Name failures after the *required capability* (`expected admin, got user` — not `assertion failed`).

**Runnable example** — enforcement fusing check + narrow (good vs bad, `tsc --strict`):

```typescript
// good — capability asserted once (check + narrow fused, message named)
interface User { id: string }
interface Admin extends User { level: number }
function assertAdmin(x: User): asserts x is Admin {
  if (!("level" in x)) throw new Error(`expected admin, got user:${x.id}`); // named failure (diagnosable)
}
function wipe(u: User): string {
  assertAdmin(u); // enforced (throws for non-admins) + narrowed (Admin downstream — no branch)
  return `wiped by L${u.level}`; // level proven (no cast, no optional chain — assertion did both jobs)
}
console.log(wipe({ id: "u", level: 3 } as Admin)); // wiped by L3 — fused enforcement (one call, two guarantees)
// bad — predicate + manual throw per site (two statements verified together — drift per site: predicate right, throw missing?)
// fix — asserts x is T (fused: enforcement and narrowing travel together, message named once)
```

```typescript
// good — parsed-shape confirmation (unknown → proven type via assertion, no cast downstream)
interface Cfg2 { host: string; port: number }
function assertCfg(x: unknown): asserts x is Cfg2 {
  if (typeof x !== "object" || x === null) throw new Error("cfg must be object");
  const r = x as Record<string, unknown>; // single contained cast (evidence-gathering, not laundering)
  if (typeof r["host"] !== "string" || typeof r["port"] !== "number") throw new Error("cfg shape invalid");
}
const raw: unknown = JSON.parse('{"host":"h","port":1}');
assertCfg(raw); // proven (Cfg2 downstream — zero casts after this line, ever)
console.log(raw.host.toUpperCase(), raw.port.toFixed(0)); // H 1 — assertion discharged unknown honestly
// bad — as Cfg2 on parsed JSON (assertion without evidence — malformed payloads crash downstream with confident types)
// fix — assertCfg (evidence-backed narrowing — one contained cast inside, zero casts outside)
```

```typescript
// good — state-machine transition guards (illegal transitions throw with state names)
type St = "idle" | "running";
function assertRunning(s: St): asserts s is "running" {
  if (s !== "running") throw new Error(`need running, got ${s}`); // literal narrowing (asserts s is "running" — precise)
}
function haltMachine(s: St): string {
  assertRunning(s); // enforced (throws for idle) + narrowed ("running" — literal proven)
  return `stopped-from-${s}`; // s: "running" (no widening — assertion preserved the literal)
}
console.log(haltMachine("running")); // stopped-from-running — transition guard (fused enforcement, literal precision)
// bad — if (s !== "running") return "noop" (silent no-op on illegal transition — state bugs hide as successful no-ops)
// fix — assert (illegal transitions throw named errors — state machines fail loudly, never silently)
```

**Common confusion** — "assertions return booleans" — return `void` (control-flow effect only — the *narrowing* is the return value, delivered via the type system). "asserts-narrowing works across function boundaries automatically" — narrows *after the call in the caller's flow* (like predicates — flow-sensitive, scope-limited; aliased references need re-assertion). "assertion libraries replace validation" — assertions enforce *invariants* (must-hold); validation *parses* unknown (see 3.1–3.3 — different inputs: proven-context vs unknown-boundary).

**Performance note** — one branch per assertion (negligible); throws exceptional (stack capture on violation only). Fused check+narrow costs less than predicate+throw pairs (one call vs two statements) at identical runtime.

**Mentor note** — convert one predicate+throw pair to `asserts x is T` live (two statements → one call, message named once) — fusion made visible in one edit. Exercise: audit capability checks for unfused pairs (predicate right, throw missing/drifted — each a half-enforced invariant). Review gate: capability checks as predicate+manual-throw fail review (fused assertions — enforcement and narrowing travel together).

### 3) **Assertion libraries** (shared `assert`/`assertDefined`/`assertNever` per codebase)

**Definition** — one utils module exporting the narrowing vocabulary (`assert`, `assertDefined`, `assertNever`, plus domain `assertAdmin`-style guards): tested once (throw paths verified), messaged consistently (named failures per helper), imported everywhere (no ad-hoc invariant branches). The library *is* the codebase's proof vocabulary — every invariant speaks it, reviewers read it fluently.

**What problem it solves / history** — per-file assertion helpers (`assert1`, `checkNotNull`, `invariant` × 12 spellings — same semantics, different messages, untested throw paths) fragmented the proof vocabulary (reviewers re-learning each file's dialect; throw paths never covered by tests). One library centralizes: semantics once, messages consistent, throw paths unit-tested (assertions that *themselves* never fail testing are untested code paths like any other).

**Modern guidance** — as of TypeScript 5.9 era, ship `assert`/`assertDefined`/`assertNever` in shared utils from project start (three functions, full coverage of invariant shapes); add domain guards beside them (`assertAdmin`, `assertConfigured` — named failures per domain); test throw paths (each helper's failure branch asserted in unit tests — untested throws are untested code). Ban ad-hoc invariant branches (the library covers all three shapes — bare `if-throw` duplicates it).

**Runnable example** — one vocabulary, tested once (good vs bad, `tsc --strict`):

```typescript
// good — library (three shapes covering all invariants — tested once, used everywhere)
function assert(c: unknown, msg: string): asserts c { if (!c) throw new Error(msg); }
function assertDef<T>(x: T | null | undefined, name: string): asserts x is NonNullable<T> {
  if (x === null || x === undefined) throw new Error(`missing:${name}`);
}
function assertNev(x: never): never { throw new Error(`unreachable:${String(x)}`); }
const v: string | null = "x";
assertDef(v, "v");
console.log(v.toUpperCase()); // X — library vocabulary (narrowed via shared, tested helpers)
// bad — per-file assert1/checkNotNull/invariant dialects (same semantics × N spellings — reviewers re-learning per file)
// fix — one utils module (semantics once, messages consistent, throw paths unit-tested)
```

```typescript
// good — throw paths tested (assertions themselves under test — untested throws are untested code)
function assert(c: unknown, msg: string): asserts c { // re-declared: fences compile standalone
  if (!c) throw new Error(msg);
}
function isFailure(fn: () => void): boolean {
  try {
    fn();
    return false; // no throw (assertion passed — returns normally)
  } catch {
    return true; // threw (assertion fired — failure branch verified)
  }
}
console.log(isFailure(() => assert(false, "x")), isFailure(() => assert(true, "x"))); // true false — throw paths tested (both branches covered)
// bad — untested assertion helpers (throw paths never executed — first real violation tests the helper in production)
// fix — unit-test each helper's failure branch (isFailure-style harnesses — one test per helper, permanent)
```

```typescript
// good — domain guards beside the core three (named failures per domain, same vocabulary)
interface Svc { ready: boolean }
function assertReady(s: Svc): asserts s is Svc & { ready: true } {
  if (!s.ready) throw new Error("service not ready"); // domain invariant (named failure — diagnosable per domain)
}
const svc: Svc = { ready: true };
assertReady(svc);
console.log(svc.ready ? "go" : "stop"); // go — domain guard (core vocabulary extended, not duplicated)
// bad — if (!svc.ready) throw new Error("not ready") per call site (ad-hoc branches — message drift per site, narrowing by accident)
// fix — assertReady (named, shared, tested — domain invariants speak the library vocabulary)
```

**Common confusion** — "three helpers cover everything" — cover *shapes* (condition / definedness / unreachability + domain extensions) — exotic invariants (temporal, cross-object) still need bespoke asserts *in the library* (new vocabulary entries, tested, named — never ad-hoc at call sites). "testing throws is optional" — throw paths are *code paths* (untested throws fail first use in production — usually the worst moment: invariant violations during incidents). "library asserts slow hot paths" — one branch per call (nanoseconds — hot loops avoid per-iteration asserts by hoisting invariants out, same as any check).

**Performance note** — shared vs ad-hoc identical runtime (one branch each); library wins on testability (throw paths tested once) and messages (consistent diagnostics — incident-response quality, not speed).

**Mentor note** — `grep -c "throw new Error" src | sort` before/after centralizing (ad-hoc throws → library calls — vocabulary consolidation countable). Exercise: write throw-path tests for three existing helpers (isFailure harness — 10 minutes, permanent). Review gate: ad-hoc invariant `if-throw` branches fail review (library vocabulary — one dialect per codebase).
