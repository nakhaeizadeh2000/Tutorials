## 1.3. `satisfies` as a validation gate

### 1) **Use a compile-time gate for source declarations**

`satisfies` checks whether an expression's type is assignable to a target. It does not install a runtime validator, convert an incoming value, or universally make object types exact. The expression retains its resulting source view rather than being replaced by the complete target view. The target also supplies contextual typing, so it can affect inference.

The [4.9 introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator) motivates checked source tables. The [maintainer's contextual-typing explanation](https://github.com/microsoft/TypeScript/issues/55189) clarifies why “without changing the type” must not be interpreted as “cannot affect inference.” Full object checking lives in [04/3.3](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>); this lesson applies it to a curated table and a runtime boundary.

Use **TypeScript 7.0.2** and emitted modules on **Node.js 20.20.2**. Save the two files below in an empty directory without a `tsconfig.json`. Compile with `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist tables.mts runtime.mts`, then run `node dist/tables.mjs` and `node dist/runtime.mjs`.

```typescript
// file: tables.mts
type Name = "home" | "users";
interface Route { method: "get" | "post"; path: string }
const table = {
  home: { method: "get", path: "/" },
  users: { method: "post", path: "/users" }
} as const satisfies Record<Name, Route>;
function request(name: Name): string {
  return table[name].method.toUpperCase() + " " + table[name].path;
}
console.log(request("home"), request("users")); // GET / POST /users
const contextual = { method: "get", path: "/" } satisfies Route;
const literalMethod: "get" = contextual.method;
contextual.path = "changed";
const flexible: Route = { method: "get", path: "/" };
flexible.method = "post";
console.log(literalMethod, contextual.path, flexible.method); // get changed post
const existing = { method: "get" as const, path: "/", extra: true };
const retained = existing satisfies Route;
console.log("nonfresh extra", retained.extra); // nonfresh extra true
const open = { dark: "black", dakr: "black" } satisfies Record<string, string>;
console.log("open keys", Object.keys(open).join(",")); // open keys dark,dakr
console.log("frozen", Object.isFrozen(table), Object.isFrozen(table.home)); // frozen false false
console.log("runtime write", Reflect.set(table.home, "path", "/changed"), table.home.path);
// runtime write true /changed: readonly source view is not runtime freezing
// contextual.method = "post"; // Rejected: inferred method is get, not the full union.
// const literalPath: "/" = contextual.path; // Rejected: this property is string.
// table.home.path = "/other"; // Rejected: readonly source view.
// const extra = { method: "get", path: "/", extra: true } satisfies Route; // Rejected fresh extra key.
// const reversed = ({ method: "get", path: "/" } satisfies Route) as const; // TS1355.
```

The const snapshot retains exact path/method literals and readonly properties, which serve a consumer deriving from this particular table. `contextual` retains the method literal through its target union, while its `path` is a mutable string. The explicit annotation on `flexible` is useful when later code should select another permitted method. Maximum literal precision is not always the desired update contract; [09/3.3](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.3. satisfies and as const preserving literals through transforms.md>) demonstrates that trade-off through transforms.

A const assertion must apply to a supported literal expression. Applying it to the whole satisfies expression is rejected with TS1355; it is not another legal order that merely checks at different precision. When a literal snapshot and compatibility check both serve the consumer, `as const satisfies` expresses that choice. It remains optional when broader mutable state is intended.

### 2) **Let the target express the intended keys**

`Record<Name, Route>` requires the independently declared `home` and `users` entries. On this fresh literal, misspelling a key or omitting a required key is rejected. `Record<string, string>` permits arbitrary string keys, so it accepts `dakr`. Deriving a key union from that source would faithfully include the typo; derivation cannot identify the spelling the author meant.

The nonfresh `existing` object also passes the Route check while keeping `extra`. Structural compatibility does not require removing additional properties, and freshness checks are not a universal exact-object guarantee. Changing the source from an existing variable to a fresh literal can change the excess-property diagnostic without changing those runtime properties. The canonical object-checking owner covers that mechanism.

Exercises in isolated copies:

- Change the table key `users` to `userz`. The finite target rejects the fresh unexpected key.
- Remove `users` entirely. The compatibility check reports the missing required entry.
- Change `home.method` to `"gett"`. The method union rejects that value; this is a value mismatch, not an excess-key error.
- Change the target to `Record<string, Route>` and rename `users` to `userz`. That target accepts the spelling. The old `request(name: Name)` implementation must then address the missing `users` property; a broader table target does not fix the consumer.

These are checks of source compatibility and consumer contracts. They do not prove routing, register handlers, parse HTTP requests or freeze the table. The reflective write is deliberate evidence that the runtime object remains mutable despite its readonly view. No HTTP/framework integration is run here.

### 3) **Keep runtime validation at the incoming boundary**

`JSON.parse` returns `any` on this baseline. Applying `satisfies Config` to that unchecked value does not cause its fields to be checked at runtime. Giving the incoming value an `unknown` view instead forces code to gather evidence before using it.

```typescript
// file: runtime.mts
interface Config { port: number }
const raw = JSON.parse('{"port":"bad"}'); // any from the library declaration
const checked = raw satisfies Config;
console.log("same value", checked === raw); // same value true
try { console.log(checked.port.toFixed(0)); }
catch (error) { console.log("unchecked", error instanceof TypeError); } // unchecked true
const incoming: unknown = JSON.parse('{"port":"bad"}');
function readConfig(value: unknown): Config {
  if (typeof value !== "object" || value === null || !("port" in value) ||
      typeof value.port !== "number" || !Number.isInteger(value.port) ||
      value.port < 1 || value.port > 65535) {
    throw new Error("invalid port");
  }
  return { port: value.port };
}
console.log("parsed", readConfig({ port: 80 }).port); // parsed 80
try { readConfig(incoming); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected failure"); }
// invalid port
// const unproved = incoming satisfies Config; // TS1360: unknown is not established as Config.
// const incompatible = { port: "bad" } as Config; // TS2352: this direct assertion is also rejected.
```

The actual reader checks its port requirement and returns a new object containing the accepted field. The `satisfies` expression itself returns the original value after its compile-time role erases. An `as` assertion can hide mismatches in some relationships, but it is not true that every direct contradictory assertion is accepted. Here the marked assertion is rejected; using `any` or an additional escape can bypass such checks without implementing a conversion.

Choose an annotation when a published variable or API should expose the target contract, `satisfies` when a compatibility check and resulting source view fit, and an assertion only for a justified limitation of what the checker can establish. A redundant `as number` after an ordinary numeric guard supplies no missing runtime evidence. None of these spellings replaces the executable checks at an incoming boundary. [Assertion helpers](<./1.1. Assertion signatures asserts condition and asserts x is T.md>) and [schema parsers](<../3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>) own those implementations in more depth.

### 4) **Common confusion**

A compile-time gate can reject a fresh typo only when its target constrains that spelling. It cannot infer a closed key set from `Record<string, ...>` or strip extras from an already compatible object. A checked declaration is not a full runtime validator, and `any` can make the compatibility operation accept data whose fields are wrong.

Satisfies also supplies context rather than promising all literal properties stay fixed or all inference stays unchanged. A const assertion provides a particular literal/readonly view, not a frozen object. An annotation can intentionally expose a broader usable contract. Pick the view the consumer needs and inspect the actual result.

### 5) **Performance note**

The operators and annotations erase; the table, parser, property reads, reflective write and thrown failures execute. Removing a source-only check can leave this emitted JavaScript unchanged, but it also removes that compiler diagnostic. This lesson measures no checking cost, cached derivation, faster switch, startup cost or parser throughput. Retaining a useful source contract is a correctness/design choice, not evidence of a performance improvement.

### 6) **Mentor note**

Have the learner predict which of a fresh extra key, a nonfresh extra key and an open dictionary spelling will pass. Then ask why the JSON value still fails after `satisfies Config` and which line in `readConfig` supplies the actual evidence. A sound explanation distinguishes target compatibility, contextual inference, source precision and runtime checking without calling every annotation a widening defect or every table typo-proof.
