## 1.2. Type predicates vs assertions — caller vs thrower

### 1) **A predicate gives the caller a branch**

A type predicate relates a boolean result to a parameter's type. The caller can use its true and false outcomes in control flow, or pass it to a compatible operation such as `filter`. An assertion signature instead describes successful continuation after a call. **Both can narrow the caller**; “caller vs thrower” is a failure-policy comparison, not a claim that assertion narrowing occurs only inside the helper.

This lesson uses **TypeScript 7.0.2** and emitted modules on **Node.js 20.20.2**. The [callable owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) explains predicate inference and assertion-call context. Here we choose and test a consumer's policy without repeating the complete mechanics.

Save the complete fence below as `choices.mts` in an empty directory without a `tsconfig.json`. Compile with `tsc --strict --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist choices.mts`, then run `node dist/choices.mjs`.

The service input is a trusted discriminated union: a ready service has `run`, and an offline service has a reason. A tag check can select its ready alternative because that relationship is already in the input contract. A broad object with `state: string` would not establish the same payload relationship, and an unknown payload needs its actual fields checked before being treated as this union.

```typescript
// file: choices.mts
type Ready = { state: "ready"; run(): string };
type Offline = { state: "offline"; reason: string };
type Service = Ready | Offline;
function isReady(service: Service): service is Ready { return service.state === "ready"; }
const ready: Ready = { state: "ready", run: () => "ran" };
const offline: Offline = { state: "offline", reason: "maintenance" };
const services: Service[] = [ready, offline];
const selected: Ready[] = services.filter(isReady);
const inferred: Ready[] = services.filter(service => service.state === "ready");
function booleanOnly(service: Service): boolean { return service.state === "ready"; }
const booleanSelected = services.filter(booleanOnly);
console.log("selected", selected.map(service => service.run()).join(","), inferred.length, booleanSelected.length);
function preview(service: Service): string {
  return isReady(service) ? service.run() : "offline:" + service.reason;
}
function assertReady(service: Service): asserts service is Ready {
  if (!isReady(service)) throw new Error("service unavailable:" + service.reason);
}
function runRequired(service: Service): string {
  assertReady(service);
  return service.run();
}
console.log("preview", preview(ready), preview(offline));
console.log("required", runRequired(ready));
try { runRequired(offline); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected failure"); }
function isNonEmptyBad(value: string | null): value is string {
  return value !== null && value !== "";
}
function inspectRejected(value: string | null): void {
  if (!isNonEmptyBad(value)) {
    const believedNull: null = value;
    console.log("bad exclusion", believedNull === null, typeof believedNull);
  }
}
inspectRejected("");
function nonEmpty(value: string | null): boolean { return value !== null && value !== ""; }
function selectText(value: string | null): string {
  if (value === null) return "absent";
  return nonEmpty(value) ? value.toUpperCase() : "empty";
}
console.log("selection", selectText("Ada"), selectText(""), selectText(null));
const names = ["ab", "abcd"];
const longNames: string[] = names.filter(name => name.length > 3);
console.log("long", longNames.join(","));
function mayThrow(value: unknown): value is string {
  if (value === "stop") throw new Error("predicate policy failure");
  return typeof value === "string";
}
try { mayThrow("stop"); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected failure"); }
// const wrong: Ready[] = booleanSelected; // TS2322: boolean-only publication leaves Service[]
// function afterBoolean(service: Service): string { if (booleanOnly(service)) return service.run(); return "off"; } // TS2339
```

Expected output:

```text
selected ran 1 1
preview ran offline:maintenance
required ran
service unavailable:maintenance
bad exclusion false string
selection ADA empty absent
long abcd
predicate policy failure
```

The explicit predicate and eligible inferred callback both produce `Ready[]`. Since TypeScript 5.5, eligible functions can have a predicate inferred; an explicit `is` annotation is not the only way a filter can narrow. The [primary release explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates) describes the conditions. Publishing `booleanOnly` with a boolean return omits that predicate contract, even though its runtime selection is the same.

### 2) **The false outcome must support the excluded type**

`isNonEmptyBad` has a useful true case: a value it accepts is a string. Its false claim is wrong. An empty string is rejected, yet the caller excludes the entire `string` alternative and accepts `const believedNull: null = value`. The output `false string` exposes the mismatch between that view and the actual rejected value. A test that checks only the filtered positive array would miss this problem.

The [original false-branch analysis](https://effectivetypescript.com/2024/02/27/type-guards/) explains this two-sided contract. Its pre-5.5 example of an inline filter failing to narrow is historical; the current compiler supports the eligible inferred callback above. Its proposed future guard syntax is not a feature used by this lesson.

Use an ordinary boolean for a selection criterion that rejects some values within the advertised target type. `nonEmpty` answers whether a string has content without promising that false excludes every string. `selectText` first checks null directly, then makes the content decision. The long-name filter also needs no special type predicate: its input is already `string[]`, and filtering by length does not establish a new type alternative.

An explicit predicate is a trusted contract. TypeScript does not prove that its body has the promised true/false relationship. Checking `kind === "admin"` on an input whose contract is merely `{ kind: string }` would similarly not prove that `level` exists or is numeric. Validate unknown shapes in their [own boundary owner](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>), or use a trusted union whose variant members actually contain the required fields.

### 3) **Choose continuation and failure handling at the call site**

`preview` can show an offline reason, so branching is useful. `runRequired` needs a ready service for this operation, so its assertion stops that continuation when the condition fails. The surrounding caller catches and reports the error. That is a throwing API with a local handling policy, not an inevitable process crash.

The assertion reuses the predicate's check and supplies a named failure. A direct `if (!isReady(service)) throw ...` at a one-off call site would also be valid. Extract a helper when a shared invariant or diagnostic policy makes it easier to review. Neither splitting nor combining the two operations proves the implementation correct by itself.

The deliberately throwing `mayThrow` shows another distinction: a predicate's declared boolean result does not promise an exception-free implementation. It describes the type relationship when that result is returned. Consumers of callbacks still need to know whether their implementations can throw. Similarly, an assertion signature does not verify its runtime body; [1.1](<./1.1. Assertion signatures asserts condition and asserts x is T.md>) executes dishonest and post-check mutation cases.

Choose a predicate when a boolean and type distinction suit the caller, an assertion when successful continuation is the intended interface, or a parser/Result when the consumer needs a value with detailed modeled errors. A throwing parser can also be appropriate when its caller handles that contract. Avoid rules that all user input must never throw, every invariant must use a shared assertion, or a type category alone decides an HTTP response. The actual boundary owns recovery and reporting.

These examples operate synchronously on trusted service values. They do not test readiness over time, race-free access, a real service health check or server error handling. If state can change between a check and use, the ownership/synchronization contract needs separate treatment; a predicate or assertion annotation does not lock the state.

### 4) **Common confusion**

Predicate and assertion signatures both convey information to callers. The former supports branching on its boolean; the latter communicates a postcondition after normal return. Neither verifies an honest body, prevents unrelated exceptions, or guarantees that previously checked mutable state stays valid.

A value test can be useful without being a type predicate. Nonempty, long, finite or in-range conditions need a target type that accurately represents their distinction before false can safely exclude it. An explicit boolean can be the correct contract. Conversely, a current inferred predicate can narrow without a handwritten `is`, so do not add casts based on older filter behavior.

### 5) **Performance note**

The signatures erase; checks, function calls, filtering and throws execute. The two filter examples select the same item, while one publishes a narrower type through a different signature. That does not establish equal or different speed. A filter materializes a selected array; the assertion path performs its check and may construct an error. No timing, allocation quantity or failure-rate threshold was measured. Choose the correct consumer contract first, then measure an actual hot path if needed.

### 6) **Mentor note**

Ask why the two type-narrowing filters and boolean-only filter have the same runtime count but different published element views. Then supply the empty string to the bad predicate and explain `false string` in its rejected branch. Finally compare `preview` and `runRequired` on the same offline input: a sound answer explains the caller's continuation and handling policy instead of equating a throw with a crashed application.
