## 7.1. Boundaries — what is covered elsewhere

Validation work connects a value's declared type, the runtime check that establishes it and the caller's response to failure. Keep those responsibilities visible. A narrowing signature, a strict option and a test suite can contribute evidence, but each addresses a different obligation. This map routes questions to their existing owners rather than repeating their examples.

### 1) **Narrowing mechanics and failure choices**

[the verified guard/assertion lesson](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) owns explicit/inferred predicates, assertions and their caller effects. [built-in union narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) and [union exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) own control-flow checks and remaining static alternatives. This domain applies those mechanisms in [predicate and assertion choices](<../1. Assertion Functions/1.2. Type predicates vs assertions caller vs thrower.md>), [composing parsers](<../3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>) and [boundary parsing](<../3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) according to the boundary and its failure contract.

Start with what the caller needs. A predicate lets the caller branch on the tested property; an assertion checks a condition or value and rejects a failing case according to its body. A parser returns the value and error representation the application intends to consume. Choose the form from that behavior, then inspect whether its checks justify every required member of the resulting type.

An explicit predicate is not automatically a proved validator. The verified guard lesson executes dishonest true and false outcomes that compile but lead callers into invalid member operations. Its condition assertion also shows that a successful asserted discriminant can narrow a union. Refer to those observations when diagnosing caller narrowing; use the parser owners for the full boundary design. Do not use a never sink as validation of arbitrary unknown input.

[strictness configuration](<../../../13 Configuration and Compiler Options/sections/1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>) and [index and optional-property settings](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>) own option selection and migration. [the bounded syntax-gate lesson](<../../../13 Configuration and Compiler Options/sections/2. This domain applies those settings to validation code, while [the worked version upgrade](<../../../20 Production Checklist Migration and Interoperability/sections/2. Migration Playbooks/2.2. Establish which files, declarations, compiler version and settings the check uses before comparing diagnostics. Then explain the failing operation: an optional-property assignment, an unchecked index read and an unknown member access have different contracts. A suppression or asserted cast can silence a useful check without changing the underlying value.

Strictness also does not execute a parser or supply a runtime schema. Review both the checked signature and the invoked body. When a code example uses additional syntax such as parameter properties or decorators, state its actual processing path rather than labeling every validation example erasable by construction. A configured syntax gate and a runtime boundary test should remain separate results.

### 3) **Special types, absence and error values**

[the checked unknown lesson](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>), [the any escape hatch](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>) and [never and void](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>) own the special types. [null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>) and [the verified object-modifier lesson](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) own absence and property contracts. This domain owns [Result-valued errors](<../2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>), [custom errors and causes](<../2. Error Values and Hierarchies/2.2. Custom error classes cause and stacks.md>) and [never-throw boundary design](<../2. Error Values and Hierarchies/2.3. Never-throw boundaries and error budgets.md>) for expressing failure and deciding how it crosses a boundary.

Unknown asks for evidence before using a member. Any permits operations without that evidence, including mistaken ones. Never can express a remaining static alternative that should be impossible. Those distinctions help design a parser's input and a caller's branch handling; they do not turn an arbitrary assertion into a check or prevent every runtime failure.

Choose null, undefined, a missing property or an error result according to the public contract. The verified object-modifier lesson observes different in-memory presence states and JSON omission of undefined. If data crosses serialization, validate what the receiving side actually observes. A local required property whose value is undefined need not survive as a present JSON property.

Error values and thrown failures also need deliberate consumers. A Result branch makes a stated failure visible in the type, but a function called inside that branch can still throw unless its behavior is controlled. Follow the error and containment owners for the boundary's implementation and tests instead of reading a Result annotation as a universal never-throw guarantee.

### 5) **Async completion and error ownership**

[the verified return/completion lesson](<../../../05 Functions and Callable Types/sections/1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) has a controlled example in which a void callback host accepts an async function but returns before that task completes. It contrasts an awaiting host that owns completion and propagates a controlled rejection. Use that owner when a callback appears successful while its work is still running.

[Promise state and value types](<../../../18 Async Types and Standard Library/sections/1. Promise Types/1.1. Promise states and the Promise type anatomy.md>) and [async return contracts](<../../../18 Async Types and Standard Library/sections/1. Promise Types/1.3. async function return-type contracts.md>) own Promise and async result contracts. [the cancellation-contract lesson](<../../../18 Async Types and Standard Library/sections/2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>) owns explicit cancellation requirements. The boundary here decides which failures are returned, propagated or handled; the async owners explain how those values and rejections travel. Returning a Result inside a Promise and rejecting that Promise are separate outcomes that callers must handle according to the API.

A try/catch around starting an async operation does not by itself await the returned Promise. Identify who observes completion and rejection. Explicitly discarding a value with void does not handle its rejection. For deliberately independent work, supply the intended error handler and lifecycle arrangement, then test it. For request-owned work, await or return the relevant operation so the caller can observe its completion. Do not assert a universal process outcome without the declared host behavior and an actual run.

### 6) **Common confusion**

A narrowed type records what the checker now permits. A predicate or assertion body must still justify that permission. Test false outcomes as well as true ones; an incorrectly narrow false branch can be unsafe too. An asserted discriminant condition can narrow, while a plain void helper does not acquire an assertion signature merely because its implementation checks something.

Rule metadata describes intended checks; a validator performs them. A cache of earlier success can also become stale when the checked value changes. Decide which mutation and ownership boundaries the contract permits rather than assuming that parsing once makes every later mutation harmless.

Void is an ignored callback result view, not a promise of synchronous completion. The return lesson's task gate exposes the difference. A Result resolution and a rejection also require different handling; classify the observed outcome before selecting a fallback or suppression.

### 7) **Performance note**

This routing lesson has no direct performance effect. Predicate bodies, parsers, error construction, wrapper calls and async scheduling can perform real work. Their cost depends on the checks, data volume, copying, error reporting and host. No latency, allocation or async timing benchmark was run here.

Erased types and strict settings do not add runtime validation by themselves. Scheduling and validation costs need measurements of the actual operation; neither handling nor validation is universally cost-free or negligible beside I/O. If repeated validation appears expensive, measure the actual boundary and understand mutation before caching a verdict. Use [compiler measurement](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for checker work and a runtime measurement for parser or handler cost.

### 8) **Mentor note**

Ask for the failed operation, its contract, the next check and the owner. Use these cases from the linked verified lessons:

1. **An explicit predicate compiles but malformed input later throws.** Compare the body with every required member and test both outcomes. The checked unknown and guard lessons show why checker trust does not prove the predicate.
2. **A declared property is present as undefined locally but missing after JSON transport.** Inspect the serialized value and the receiving contract. The object-modifier lesson observes omission and distinguishes it from null or required presence.
3. **A void callback host returns before saving completes.** Identify the host's completion contract. The verified return lesson holds the task behind a gate, observes early host return and contrasts awaiting completion with an owned rejection path.

Require a remedy and an observable check, not merely another assertion, catch-all fallback or stricter-sounding annotation. For mutable data, ask what can invalidate earlier evidence. For async work, ask who receives failure and when. Keep the full parser/tool/async implementations in their owners while using the appropriate evidence at the current boundary.
