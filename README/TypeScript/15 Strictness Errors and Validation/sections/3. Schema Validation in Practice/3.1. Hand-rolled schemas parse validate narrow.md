## 3.1. Hand-rolled schemas — parse, validate, narrow

### 1) **Return evidence and a distinguishable failure**

A boundary parser checks an incoming representation and returns either a usable value or located issues. The useful guarantee comes from its actual checks and output construction. A return annotation alone does not establish correctness. Start with the application contract, including which values are accepted, transformed, rejected or omitted.

This lesson's User has a trimmed, nonempty name and an integer age from 0 through 130. These are example application rules, not universal rules for names or ages. Inputs must be ordinary data objects with their own data properties; arrays, inherited-only fields and accessors are rejected. Extra fields are ignored when constructing the new output. Arrays must have an own data element at every index. Proxies and concurrently changing or hostile reflective objects are outside this example's trust model.

Use **TypeScript 7.0.2** and emitted ES2022 modules on **Node.js 20.20.2**. Save `parser.mts` and `demo.mts` below in an empty directory without a `tsconfig.json`. Compile with `tsc --strict --noUncheckedIndexedAccess --exactOptionalPropertyTypes --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist parser.mts demo.mts`, then run `node dist/demo.mjs`. No packages are required.

A tagged result keeps success and failure distinct even when the successful value is itself an array. With `Value | Issue[]`, a generic consumer cannot distinguish a successful array from an issue array merely by calling `Array.isArray`. An empty array makes that ambiguity especially visible. The `ok` tag below has one meaning across primitives, objects and arrays.

```typescript
// file: parser.mts
export type Path = readonly (string | number)[];
export type Issue = { path: Path; code: string };
export type Parsed<Value> =
  | { ok: true; value: Value }
  | { ok: false; issues: Issue[] };
export type Parser<Value> = (input: unknown, path?: Path) => Parsed<Value>;
export type User = { name: string; age: number };
function failure(path: Path, code: string): Parsed<never> {
  return { ok: false, issues: [{ path, code }] };
}
function ownData(input: object, key: PropertyKey, path: Path): Parsed<unknown> {
  const descriptor = Object.getOwnPropertyDescriptor(input, key);
  if (descriptor === undefined) return failure(path, "missing");
  if (!("value" in descriptor)) return failure(path, "data-property-required");
  const value: unknown = descriptor.value;
  return { ok: true, value };
}
export const parseName: Parser<string> = (input, path = []) => {
  if (typeof input !== "string") return failure(path, "string-required");
  const value = input.trim();
  return value.length === 0 ? failure(path, "nonempty-required") : { ok: true, value };
};
export const parseAge: Parser<number> = (input, path = []) => {
  if (typeof input !== "number" || !Number.isInteger(input)) return failure(path, "integer-required");
  if (input < 0 || input > 130) return failure(path, "age-range");
  return { ok: true, value: input };
};
export const parseUser: Parser<User> = (input, path = []) => {
  if (typeof input !== "object" || input === null || Array.isArray(input)) return failure(path, "object-required");
  const namePath = [...path, "name"];
  const agePath = [...path, "age"];
  const rawName = ownData(input, "name", namePath);
  const rawAge = ownData(input, "age", agePath);
  const name = rawName.ok ? parseName(rawName.value, namePath) : rawName;
  const age = rawAge.ok ? parseAge(rawAge.value, agePath) : rawAge;
  if (!name.ok || !age.ok) {
    return { ok: false, issues: [...(!name.ok ? name.issues : []), ...(!age.ok ? age.issues : [])] };
  }
  return { ok: true, value: { name: name.value, age: age.value } };
};
export function parseArray<Value>(input: unknown, parse: Parser<Value>, path: Path = []): Parsed<Value[]> {
  if (!Array.isArray(input)) return failure(path, "array-required");
  const values: Value[] = [];
  const issues: Issue[] = [];
  for (let index = 0; index < input.length; index++) {
    const itemPath = [...path, index];
    const raw = ownData(input, String(index), itemPath);
    const item = raw.ok ? parse(raw.value, itemPath) : raw;
    if (item.ok) values.push(item.value);
    else issues.push(...item.issues);
  }
  return issues.length > 0 ? { ok: false, issues } : { ok: true, value: values };
}
export function parseJsonUsers(text: string): Parsed<User[]> {
  let input: unknown;
  try { input = JSON.parse(text); }
  catch { return failure([], "json-syntax"); }
  return parseArray(input, parseUser);
}
```

The property descriptor check rejects accessors without evaluating their getter. Reading its built-in `value` field into an `unknown` local prevents that library field's permissive type from becoming unchecked application data. The primitive parser then provides the actual evidence. This policy differs from accepting inherited fields or ordinary getter reads; neither policy follows automatically from the TypeScript object type.

`parseUser` combines independently checked fields. Only the branch where both results succeed constructs a User. It does not treat an empty issues list as an implicit compiler proof that previously read unknown fields are strings or numbers. The generic array parser similarly appends only successful values, retains indexed issues and returns no partial success when any element fails.

### 2) **Compose and vary the inputs**

```typescript
// file: demo.mts
import { parseName, parseAge, parseUser, parseArray, parseJsonUsers, type Parsed, type User } from "./parser.mjs";
function summary<Value>(result: Parsed<Value>): string {
  return result.ok ? JSON.stringify(result.value)
    : result.issues.map(issue => (issue.path.join(".") || "$") + ":" + issue.code).join(",");
}
console.log("valid", summary(parseUser({ name: " Ada ", age: 37, extra: true })));
console.log("invalid", summary(parseUser({ name: 7, age: NaN })));
console.log("array-object", summary(parseUser([])));
console.log("missing", summary(parseUser({ name: "Ada" })));
console.log("range", summary(parseUser({ name: " ", age: 131 })));
console.log("list", summary(parseArray([{ name: " A ", age: 0 }, { name: false, age: Infinity }], parseUser)));
const sparse = new Array<unknown>(2);
sparse[1] = { name: "Ada", age: 37 };
console.log("sparse", summary(parseArray(sparse, parseUser)));
console.log("nested", summary(parseArray([[" A "], []], (value, path) => parseArray(value, parseName, path))));
console.log("empty", summary(parseArray([], parseUser)));
console.log("inherited", summary(parseUser(Object.create({ name: "Ada", age: 37 }))));
let getterCalls = 0;
const accessor = { get name() { getterCalls++; return "Ada"; }, age: 37 };
console.log("accessor", summary(parseUser(accessor)), getterCalls);
console.log("json", summary(parseJsonUsers('[{"name":" Ada ","age":37}]')));
console.log("bad-json", summary(parseJsonUsers("{bad")));
const source = { name: " Ada ", age: 37 };
const parsed = parseUser(source);
source.name = "changed";
if (parsed.ok) console.log("snapshot", parsed.value.name, parsed.value === source);
console.log("primitives", summary(parseAge(0)), summary(parseAge(130)), summary(parseName(" X ")));
// const unguarded: User = parseUser({}); // TS2322: Parsed<User> is not a User.
// const payload = parseUser({}).value; // TS2339: check ok before selecting value.
```

Expected output:

```text
valid {"name":"Ada","age":37}
invalid name:string-required,age:integer-required
array-object $:object-required
missing age:missing
range name:nonempty-required,age:age-range
list 1.name:string-required,1.age:integer-required
sparse 0:missing
nested [["A"],[]]
empty []
inherited name:missing,age:missing
accessor name:data-property-required 0
json [{"name":"Ada","age":37}]
bad-json $:json-syntax
snapshot Ada false
primitives 0 130 "X"
```

The array loop visits every numeric position, including the hole at zero. Using an iterator such as `forEach` without a separate density check would skip holes and could accept fewer elements than the input length suggests. The nested result is a successful array of arrays; its shape is data rather than an error signal because success is indicated by `ok`.

Name normalization produces a different string, and object construction drops the extra field. Changing the source afterward does not change this flat output. These are observable properties of this parser, not guarantees of every function named `parse`. If a later parser keeps a nested reference, mutating that referenced object may still change the output. Copying is not freezing or authorization.

JSON decoding first checks text syntax. Its result is deliberately held as `unknown` before User-array parsing checks the application shape. The syntax branch here returns a public issue code and does not retain the original SyntaxError; choose a separate diagnostic policy if its details are needed. Neither JSON syntax success nor a static cast establishes that a value meets the User contract.

### 3) **Use the narrowed output within its contract**

After checking `ok`, pass `result.value` to a consumer needing User. On failure, display, propagate or adapt its located issues according to the owning boundary. Skipping the result check with `as User` suppresses the distinction between a successful value and failure. The repair is to handle the result, not to assert its success.

That specific mistake does not justify a universal ban on assertions anywhere after parsing. A contained assertion may bridge a generic implementation limitation or represent separate evidence; review its justification independently. Conversely, a parser without assertions can still have a wrong predicate or omit an important rule. Code review and malformed-input execution remain necessary.

The useful parse-versus-validate distinction concerns preserving learned information in the returned representation. It is not a rule that validators accept only typed inputs while parsers accept only unknown inputs. [Alexis King's original explanation](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) develops the representation idea and allows multiple parsing passes. In TypeScript, ordinary object types are structurally constructible and mutable; User does not statically encode the age range or prevent a caller from constructing an invalid value. Opaque constructors, ownership rules or later checks may be needed for stronger guarantees.

A library can provide reusable schemas and error infrastructure. For example, [Zod's basic usage documentation](https://zod.dev/basics) separates a throwing parse method from a tagged safe-parse result. This lesson executes its own functions and does not certify a Zod installation or identical policy. The [next lesson](<./3.2. Schema objects and inferred types.md>) owns schema objects and inferred output types.

### 4) **Common confusion**

`Array.isArray` can distinguish an object success from an error array in one narrowly defined parser. It cannot distinguish arbitrary successful arrays from issue arrays in a generic parser. A discriminant works independently of the payload type.

A number type check admits `NaN` and infinities. This age parser explicitly requires an integer and a range. Checking an object's existence also does not establish that its required properties are own data fields; the example states and tests that additional policy.

### 5) **Performance note**

This implementation visits every declared array position, reads required descriptors, trims names, creates output objects and accumulates all reported issues. Work therefore depends on array lengths and string lengths, not only on successful items. Huge sparse arrays can still cause a long scan. This teaching parser has no input-size or issue-count budget; applications should specify such limits for their input sources. Returning on the first issue reduces diagnostic work but provides different feedback. No claim that parsing is always negligible beside I/O, faster than inline checks or free after JIT optimization was measured.

### 6) **Mentor note**

Ask the learner to predict the nested-array and sparse-array results before running them. Remove one field check and feed its malformed value to a consumer; then explain what the declared User type failed to prove. Finish by identifying extra-field, getter, copying and size-limit policies. A strong review checks the accepted input language, resulting representation, issue locations and ownership rather than counting casts or requiring a library after a fixed number of shapes.
