## 3.3. Parse, don't validate — at boundaries

### 1) **Parse vs validate distinction** (production vs verification, different inputs)

**Definition** — *parsing* converts unknown→typed (produces new values: `parseUser(raw): User | Errors` — input `unknown`, output proven); *validating* checks typed→boolean/void (verifies existing values: `isValid(user)` — input already typed, output a verdict). Alexis King's distinction (Parse, don't validate): parsing *creates* trust (unknown becomes typed once); validation *assumes* trust (typed values re-checked redundantly — or worse, untyped values "validated" without ever becoming typed).

**What problem it solves / history** — validate-typed-values codebases (`if (!isValid(user)) throw` on already-`User`-typed data — re-verifying what types already prove, while `any`-shaped inputs flowed unvalidated beside them) spent checking budgets on proven values and skipped unknown inputs entirely (validation theater: thorough where unnecessary, absent where needed). Parse-don't-validate inverts the spend: unknown parsed once (trust created), typed values trusted (no re-validation tax).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), parse at unknown boundaries (network/storage/env/CLI — unknown→typed production, see promise 3's inventory); validate *untrusted-typed* values only (external `User`-typed payloads from unvalidated producers — narrow trust gaps, not proven types); never validate your own parsed output (parser proved it — re-checking is theater; fix the parser if untrusted).

**Runnable example** — production vs verification (good vs bad, `tsc --strict`):

```typescript
// good — parse produces (unknown → typed-or-errors — trust created once at the boundary)
interface Item { sku: string; qty: number }
type PErr = { path: string; reason: string };
function parseItem(raw: unknown): Item | PErr[] {
  if (typeof raw !== "object" || raw === null) return [{ path: "", reason: "not-object" }];
  const r = raw as Record<string, unknown>; // single contained cast (evidence-gathering — see 3.1 full pattern)
  if (typeof r["sku"] !== "string") return [{ path: "sku", reason: "want-string" }];
  if (typeof r["qty"] !== "number") return [{ path: "qty", reason: "want-number" }];
  return { sku: r["sku"] as string, qty: r["qty"] as number }; // produced (typed value — trust created here)
}
const it = parseItem({ sku: "a", qty: 2 });
console.log(Array.isArray(it) ? it.length : it.sku.toUpperCase()); // A — produced trust (consumers narrow, never re-validate)
// bad — validating parsed output (if (!isValid(it)) throw — re-checking proven values while raw inputs flow unvalidated elsewhere)
// fix — parse unknown once (trust created); trust typed values (no re-validation tax on proven data)
```

```typescript
// good — validation reserved for untrusted-typed values (external producers bypassing parsers)
interface Item { sku: string; qty: number } // re-declared: fences compile standalone (minimal shape)
function isItem(x: unknown): x is Item { // predicate guard (narrowing check for values of unclear provenance)
  if (typeof x !== "object" || x === null) return false;
  const r = x as Record<string, unknown>;
  return typeof r["sku"] === "string" && typeof r["qty"] === "number";
}
const extPayload: unknown = { sku: "b", qty: 3 }; // unvalidated producer (third-party callback payload — provenance unclear)
if (isItem(extPayload)) console.log(extPayload.sku.toUpperCase()); // B — guard narrows (validation where parsing didn't run)
// bad — parseUser(raw) then isValid(user) then use (parse + validate + trust — triple handling, one redundant layer)
// fix — parse OR validate per boundary (unknown→parse; unclear-typed→guard; proven-typed→trust — exactly one layer each)
```

```typescript
// good — unvalidated-typed inputs guarded (the narrow exception proving the parse-first rule)
interface Item { sku: string; qty: number } // re-declared: fences compile standalone (minimal shape)
function isItem(x: unknown): x is Item { // re-declared: fences compile standalone (minimal guard)
  if (typeof x !== "object" || x === null) return false;
  const r = x as Record<string, unknown>;
  return typeof r["sku"] === "string" && typeof r["qty"] === "number";
}
function total(items: Item[]): number { // typed signature (trusts callers — correct INSIDE parsed pipelines)
  return items.reduce((a, b) => a + b.qty, 0);
}
function totalGuarded(raw: unknown): number { // boundary entry (parses — unknown handled once, here)
  const parsed = Array.isArray(raw) ? raw : [];
  let sum = 0;
  for (const x of parsed) {
    if (isItem(x)) sum += x.qty; // guard (boundary values of unclear provenance — narrowed per element)
  }
  return sum;
}
console.log(total([{ sku: "a", qty: 1 }]).toFixed(0), totalGuarded([{ sku: "b", qty: 2 }]).toFixed(0)); // 1 2 — parsed pipelines trust (total), boundaries guard (totalGuarded)
// bad — total() re-validating each item (proven-typed inputs re-checked per call — validation tax on trusted data)
// fix — parse at boundaries (guard once), trust inside pipelines (no re-validation tax on proven values)
```

**Common confusion** — "validation subsumes parsing" — validation *assumes* typed inputs (checks values already shaped); parsing *produces* them from unknown (creates shape) — unvalidated-unknown validated (not parsed) stays unknown-typed (casts downstream — the lie). "parsed values need periodic re-validation" — parsed values are *immutable-or-tracked* (frozen configs, validated DTOs — re-validation signals mutability bugs, not diligence; fix the mutation). "guards duplicate parsers" — guards narrow *unclear-typed* values (third-party payloads, legacy untyped producers); parsers produce from *unknown* — complementary layers (parse at owned boundaries, guard at foreign ones).

**Performance note** — parsing costs per-field checks once per boundary (trivial vs I/O); re-validation taxes every use of proven data (distributed waste — N checks for one proof); guards cost per foreign value (bounded by foreign-producer surface). Parse-once economics dominate: prove once, trust downstream.

**Mentor note** — label one boundary "parse" and one "validate" live (unknown→typed production vs typed→checked verification — vocabulary in one labeling exercise). Exercise: delete re-validation of parsed outputs across one module (narrow-only downstream — trust restored per deletion). Review gate: validation of parser-produced values fails review (trust proven data); unvalidated unknown flows fail review (parse at boundaries).

### 2) **Boundary inventory** (every unknown-entry enumerated and parsed)

**Definition** — boundary inventory: every unknown-entry enumerated (network handlers, file reads, env access, CLI args, worker messages, `postMessage`, third-party callbacks, `JSON.parse` sites — each listed), each with a parser (hand-rolled per 3.1 or schema-object per 3.2 — no bare `as`, no implicit `any`), verified by audit (grep `JSON.parse` + `as ` + `process.env` + `unknown` quarterly — uncovered entries triaged).

**What problem it solves / history** — un-inventoried boundaries (the `JSON.parse` in a util nobody remembered, `location.search` parsed inline, `worker.onmessage` cast per handler) flowed `any`/`as`-shaped data beside fully-parsed main paths — incidents clustering at *forgotten* entries (the parsed 90% stayed green; the unlisted 10% crashed quarterly). Inventories make forgotten entries impossible (listed or nonexistent — audit proves completeness, not hope).

**Modern guidance** — as of TypeScript 5.9 era, enumerate boundaries in one doc/table per project (entry → parser → type — three columns, reviewed quarterly); parse each with shared combinators (3.1's kit or 3.2's objects — no ad-hoc per-boundary validators); audit via grep patterns (`JSON.parse`, `as `, `process.env[`, `onmessage`, `unknown` casts — uncovered entries fail the audit, not production).

**Runnable example** — inventory enumerated, entries parsed (good vs bad, `tsc --strict`):

```typescript
// good — env boundary parsed (entry listed, parser shared, type derived)
function parseEnv(raw: Record<string, string | undefined>): { port: number } | string {
  const p = raw["PORT"];
  if (p === undefined) return { port: 80 }; // absent → default (documented behavior, not silent)
  const n = Number(p);
  return Number.isNaN(n) ? "bad-port" : { port: n }; // parsed-or-error (unknown discharged at the entry)
}
const env: Record<string, string | undefined> = { PORT: "8080" };
const cfg = parseEnv(env);
console.log(typeof cfg === "string" ? cfg : cfg.port.toFixed(0)); // 8080 — env entry parsed (inventory row complete)
// bad — Number(process.env["PORT"]) inline per file (unparsed env reads scattered — NaN flowing as port silently)
// fix — parseEnv (one entry, shared parser, derived type — inventory row complete, audited quarterly)
```

```typescript
// good — CLI boundary parsed (args array → structured options or usage error)
function parseArgs(args: string[]): { verbose: boolean } | string {
  const verbose = args.includes("--verbose"); // flag parsed (known flags enumerated — unknown flags rejected below)
  const unknownFlags = args.filter((a) => a.startsWith("--") && a !== "--verbose");
  return unknownFlags.length > 0 ? `unknown:${unknownFlags.join(",")}` : { verbose }; // parsed-or-error (boundary honest)
}
const cli = parseArgs(["--verbose"]);
console.log(typeof cli === "string" ? cli : cli.verbose); // true — CLI entry parsed (inventory row complete)
// bad — args[2] === "--verbose" positional reads (order-coupled, unvalidated, undiscoverable — every flag a new index bug)
// fix — parseArgs (structured options or usage error — boundary parsed once, consumed typed everywhere)
```

```typescript
// good — worker message boundary parsed (onmessage payloads narrowed per message kind)
type Msg = { kind: "ping" } | { kind: "count"; n: number };
function parseMsg(raw: unknown): Msg | undefined {
  if (typeof raw !== "object" || raw === null) return undefined; // non-object rejected (boundary honest)
  const r = raw as Record<string, unknown>;
  if (r["kind"] === "ping") return { kind: "ping" };
  if (r["kind"] === "count" && typeof r["n"] === "number") return { kind: "count", n: r["n"] };
  return undefined; // unknown kind rejected (exhaustiveness at the boundary — new kinds error loudly, not silently)
}
const pm = parseMsg({ kind: "count", n: 3 });
console.log(pm !== undefined && pm.kind === "count" ? pm.n.toFixed(0) : "bad"); // 3 — narrowed before property access (unions don't chain ?. across members)
// bad — (e.data as Msg) per handler (assertion without evidence — malformed messages crashing workers confidently)
// fix — parseMsg (narrowed per kind — malformed rejected, new kinds error loudly via exhaustive-ish rejection)
```

**Common confusion** — "inventory is documentation overhead" — one table (entry → parser → type per boundary — minutes to write, quarters of relevance); un-inventoried boundaries cost incidents (each forgotten entry a crash class). "small projects need no inventory" — small projects have *few* boundaries (inventory trivially complete — cheapest when small; impossible to retrofit during incidents). "parsing everything slows startup" — parsing costs per-boundary field checks (microseconds vs I/O-bound startup — measured per boundary, never assumed).

**Performance note** — boundary parsing costs field checks once per entry (trivial vs network/disk); unparsed `as`-flows cost incidents (unbounded); inventory audits cost grep minutes quarterly. Parse-once economics at every entry.

**Mentor note** — grep the four patterns live (`JSON.parse`, ` as `, `process.env[`, `onmessage`) and triage each hit (parsed? inventoried? or incident-queued?) — audit made tangible in one command. Exercise: inventory one project's boundaries fully (table per entry) and parse the top three unparsed (incidents pre-triaged by audit). Review gate: new unknown entries without parsers fail review (inventory grows with the codebase, never lags it).

### 3) **Parse-once architecture** (unknown crosses inward once — trusted downstream)

**Definition** — parse-once: unknown crosses each trust boundary *exactly once* (parsed at entry → typed values flow inward, never re-parsed, never re-validated downstream); re-validation downstream signals *either* a second boundary (parse there too — nested trust domains) *or* a trust bug (parsed data distrusted — fix the parser's output type, not the consumer's paranoia). Downstream code trusts parsed types unconditionally (no `as`, no re-guards, no defensive `?.` on proven-present fields).

**What problem it solves / history** — re-validating pipelines (parsed `User` re-checked per function — `if (!u.name) throw` scattered downstream of honest parsers) taxed every consumer for parser distrust (defense distributed, coverage unprovable — which check covers which field? nobody knew) while *actual* gaps (unparsed entries elsewhere) stayed open. Parse-once concentrates trust (parser proves → consumers trust → gaps visible as *unparsed entries*, fixable at exactly one place each).

**Modern guidance** — as of TypeScript 5.9 era, parse at each trust boundary once (owned entries per inventory); trust parsed values downstream unconditionally (no re-validation, no defensive narrowing on proven fields); treat downstream `as`/re-guards as parser-bug reports (narrow the parser's output type until consumers need nothing — demand diagnoses parser gaps). Nested trust domains parse per domain (service boundary + module boundary each parse — different trusts, different parsers).

**Runnable example** — trust flows inward un-revalidated (good vs bad, `tsc --strict`):

```typescript
// good — parsed once at entry (downstream trusts unconditionally — no re-validation tax)
interface Ticket { id: string; qty: number }
function parseTicket(raw: unknown): Ticket | undefined {
  if (typeof raw !== "object" || raw === null) return undefined; // boundary parse (unknown discharged once, here)
  const r = raw as Record<string, unknown>;
  if (typeof r["id"] !== "string" || typeof r["qty"] !== "number") return undefined;
  return { id: r["id"], qty: r["qty"] }; // proven Ticket (consumers trust — zero downstream checks)
}
function total(t: Ticket): number { return t.qty * 10; } // trusts (no guards — parser proved, consumer flows)
const tk = parseTicket({ id: "t", qty: 2 });
console.log(tk === undefined ? "bad" : total(tk).toFixed(0)); // 20 — parse-once (boundary proves, pipeline trusts)
// bad — total() re-validating (if (!t.qty) throw — proven data re-checked per consumer — distrust distributed, coverage unprovable)
// fix — parse-once (boundary proves once — downstream trusts unconditionally; re-validation is a parser-bug smell)
```

```typescript
// good — nested domains parse per domain (service boundary + module boundary — different trusts, different parsers)
function parseOuter(raw: unknown): { inner: unknown } | undefined {
  if (typeof raw !== "object" || raw === null) return undefined; // outer trust domain (service boundary)
  return { inner: (raw as Record<string, unknown>)["data"] }; // inner still unknown (nested domain — parsed separately, honestly)
}
interface Ticket { id: string; qty: number } // re-declared: fences compile standalone (minimal shape)
function parseInner(raw: unknown): Ticket | undefined {
  if (typeof raw !== "object" || raw === null) return undefined; // inner trust domain (module boundary — separate parse)
  const r = raw as Record<string, unknown>;
  if (typeof r["id"] !== "string" || typeof r["qty"] !== "number") return undefined;
  return { id: r["id"], qty: r["qty"] };
}const outer = parseOuter({ data: { id: "x", qty: 1 } });
const inner = outer === undefined ? undefined : parseInner(outer.inner); // composed parses (each domain proves its own)
console.log(inner === undefined ? "bad" : inner.id.toUpperCase()); // X — nested trust (per-domain parsers, composed explicitly)
// bad — outer parser reaching into inner shapes (trust domains conflated — inner evolution breaks outer parser silently)
// fix — per-domain parsers composed (each trust proves its own — boundaries explicit, evolution isolated)
```

```typescript
// good — downstream as-casts treated as parser bugs (demand diagnoses gaps — fix parsers, not call sites)
function parseId(raw: unknown): string | undefined {
  return typeof raw === "string" ? raw : undefined; // narrow parser (proven output — consumers cast nothing)
}
const id = parseId("u1");
console.log(id?.toUpperCase() ?? "bad"); // U1 — narrowed use (no cast — parser proved everything needed)
// bad — id as string post-parse (cast demand = parser gap (proven insufficiently) — call-site casts compound per consumer)
// fix — narrow parser output types until cast demand hits zero (demand-driven parser completeness — grep as-downstream-of-parse)
```

**Common confusion** — "trusting downstream is naive" — trusting *parsed* downstream is engineered (parser proved per field — trust earned once, spent freely); trusting *unparsed* is naive (the actual bug — inventory catches it). "nested parsing duplicates work" — nested domains have *different* trusts (service vs module boundaries — each parses its own; shared sub-parsers compose without duplicating per-field logic). "re-validation is defense in depth" — defense-in-depth applies to *independent* mechanisms (validation + authz + rate-limiting); re-validation duplicates the *same* mechanism (parser checked twice — second check proves nothing new, costs readability).

**Performance note** — parse-once costs per-field checks once per boundary (vs per-use re-validation — N× savings downstream); downstream trust costs zero checks (unconditional flow — fastest possible consumption); nested parses cost per domain (bounded by domain count — explicit, reviewable).

**Mentor note** — grep `as` downstream of parse calls (each a parser-bug ticket — fix parsers until grep is empty). Exercise: delete re-validation across one parsed pipeline (narrow-only downstream — trust restored per deletion). Review gate: `as`/re-guards on parsed values fail review (narrow parsers until demand vanishes); unparsed unknown flows fail review (inventory + parse at boundaries).
