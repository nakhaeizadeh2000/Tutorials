## 3.3. Parse, don't validate — at boundaries

### 1) **Preserve learned information before using input**

The point of “parse, don't validate” is to preserve useful information in the representation passed to the next function. A check that returns only a verdict can leave every consumer responsible for remembering what it proved. A parser can instead return the value needed by the consumer, or a failure that must be handled before using that value.

This is a design distinction, not a language rule that parsers accept `unknown` and validators accept only already typed data. A type guard can inspect unknown data and narrow the caller. A parser can accept typed strings or arrays and produce a stronger representation. [Alexis King's original article](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) explains information preservation and explicitly allows multiple parsing passes. In TypeScript, implementation trust, mutation and structural construction limit what a type can prove.

The following local application uses **TypeScript 7.0.2** and emitted ES2022 modules on **Node.js 20.20.2**. Reuse the complete `parser.mts` file from [3.1's worked parser](<./3.1. Hand-rolled schemas parse validate narrow.md>) and save `architecture.mts` below beside it in a directory without a `tsconfig.json`. That parser trims names, checks an integer age range, rejects non-data properties and returns copied User objects with tagged failures. Compile with `tsc --strict --noUncheckedIndexedAccess --exactOptionalPropertyTypes --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist parser.mts architecture.mts`, then run `node dist/architecture.mjs`. No dependencies, network or persistent store are used.

```typescript
// file: architecture.mts
import { parseJsonUsers, parseUser, type Parsed, type User } from "./parser.mjs";
const applied: string[] = [];
function greeting(user: Readonly<User>): string { return "hi " + user.name.toUpperCase(); }
function importBatch(text: string): Parsed<number> {
  const parsed = parseJsonUsers(text);
  if (!parsed.ok) return parsed;
  const messages = parsed.value.map(greeting);
  applied.push(...messages); // Local memory only, after the whole input has passed parsing.
  return { ok: true, value: messages.length };
}
console.log("bad batch", importBatch('[{"name":"Ada","age":37},{"name":"Lin","age":"40"}]').ok, applied.length);
console.log("wrong root", importBatch('{"name":"Ada","age":37}').ok, applied.length);
const accepted = importBatch('[{"name":" Ada ","age":37},{"name":"Lin","age":40}]');
console.log("accepted", accepted.ok ? accepted.value : "failed", applied.join(","));
const checked = parseUser({ name: "Ada", age: 37 });
if (!checked.ok) throw new Error("fixture should parse");
const readOnlyView: Readonly<User> = checked.value;
const mutableAlias: User = checked.value;
mutableAlias.age = -1; // Legal number assignment; it invalidates the parser's age rule.
console.log("mutable refinement", readOnlyView.age, parseUser(checked.value).ok);
const restored = parseUser({ name: "Ada", age: 37 });
if (!restored.ok) throw new Error("fixture should parse");
const snapshot: Readonly<User> = Object.freeze({ ...restored.value });
restored.value.age = -1;
console.log("owned snapshot", snapshot.age, Reflect.set(snapshot, "age", -1), parseUser(snapshot).ok);
const fabricated: User = { name: "", age: 500 }; // Structurally compatible, not valid under this parser.
console.log("structural construction", parseUser(fabricated).ok);
function readCache(text: string): Parsed<User> {
  let input: unknown;
  try { input = JSON.parse(text); }
  catch { return { ok: false, issues: [{ path: [], code: "json-syntax" }] }; }
  return parseUser(input);
}
console.log("cache", readCache(JSON.stringify(snapshot)).ok, readCache('{"name":"Ada","age":"37"}').ok);
const allowedNames = new Set(["Ada"]); // A changing local business policy, not an authentication system.
function permittedNow(user: Readonly<User>): boolean { return allowedNames.has(user.name); }
const earlierDecision = permittedNow(snapshot);
allowedNames.delete("Ada");
console.log("current policy", earlierDecision, permittedNow(snapshot), parseUser(snapshot).ok);
// snapshot.age = 0; // TS2540: readonly prevents this checked assignment.
// const unchecked: User[] = parseJsonUsers("[]"); // TS2322: handle the tagged result.
```

Expected output:

```text
bad batch false 0
wrong root false 0
accepted 2 hi ADA,hi LIN
mutable refinement -1 false
owned snapshot 37 false true
structural construction false
cache true false
current policy true false true
```

The invalid second item rejects the batch before any messages are applied. Filtering invalid items and treating the remainder as a successful import would be a different contract that needs to report dropped items explicitly. A non-array root also fails, instead of silently becoming an empty successful batch. This example proves the validation-before-action ordering in memory, not transactional behavior for an external service or database.

### 2) **State how long the evidence remains valid**

The age rule is stronger than User's `number` property. Assigning `-1` through the mutable alias compiles, and the readonly view observes the changed value. An annotation does not freeze an object or force all other references to be readonly. The [TypeScript object documentation](https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties) makes that aliasing distinction explicit.

The separate frozen snapshot preserves its flat primitive fields after mutation of the earlier object, and the attempted reflective write returns false. This is a specific ownership choice for this representation. A shallow freeze would not recursively freeze new nested objects, maps or external state. Keep the detailed [readonly and mutation rules](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) in their owner rather than treating every parsed value as immutable by convention.

`fabricated` illustrates another limit: callers can construct an ordinary structural User without running this parser. If an API needs to distinguish parser-produced values from arbitrary structurally compatible objects, choose an encapsulated or opaque construction protocol and test it. A brand or private constructor can restrict checked construction; it still needs a correct runtime implementation and clear escape-hatch limits.

Decoding a cache record creates a new boundary. A previously valid object being serialized does not prove that today's stored bytes, producer, schema version or decoded value meet the current contract. The example checks a valid round trip and a malformed cache record, using the same canonical parser rather than a duplicate field checklist.

The changing allowed-name set is independent of User's shape. The old decision was true, the current decision is false, and the frozen User still parses successfully. Rechecking current business policy is not redundant shape validation. Real authorization and concurrent state changes require an authoritative decision/operation protocol; this local set does not implement one.

### 3) **Inventory real entry points and failure owners**

For each project entry, identify the producer, representation, parser, failure owner and effects that must wait. A useful inventory might include these rows:

| Entry | Representation to inspect | Decision to document |
|---|---|---|
| HTTP body or third-party callback | Decoded data with an unproven application shape | Limits, accepted schema, response/report owner and authorization policy |
| Stored record or cache | Bytes plus schema/version context | Decode/migrate/parse behavior and what happens to incompatible records |
| Environment or command line | Strings, missing values and a declared grammar | Defaults versus invalid input, supported flags and process exit ownership |
| Worker or message channel | A message envelope and payload | Version/kind checks, action ownership and retry/acknowledgment behavior |

These are design prompts, not claims that this lesson exercised those host integrations. For example, an environment port parser needs to distinguish an absent value from an empty string and enforce the supported numeric grammar/range; `Number(raw)` followed only by a NaN check is insufficient. [The Result lesson](<../2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>) runs a concrete port grammar. A CLI parser must also define positional arguments, duplicates and unsupported options; finding `--verbose` alone is not a complete CLI contract.

Searches for decoding, casts, environment access and message registration can help discover candidates. They do not prove inventory completeness: wrappers, generated adapters, plugin entry points and dependencies can hide the actual source. Trace data and effects through the relevant integration and run malformed-input checks there. An inventory is maintained evidence, not a guarantee created by a table or a quarterly grep.

Within a stable owned representation, avoid repeating identical checks in every helper without a reason. Recheck or refine when evidence can change: mutation, deserialization, version migration, a new trust boundary or a different business rule. Some algorithms also need staged parsing before selecting a branch-specific representation. The goal is justified evidence at each use, not an exact-once count enforced independently of the data's lifetime.

### 4) **Common confusion**

A successfully parsed shape is not proof that every future value is valid, every structurally compatible caller used the parser, or current business policy permits an action. Each claim needs its own evidence and lifetime assumptions.

Checking the same unchanged flat snapshot twice may add no useful information. Checking changed state, a newly decoded record or a stronger branch-specific condition can add essential information. Classify the guarantee being checked before calling a second check redundant.

### 5) **Performance note**

The example constructs parsed arrays/objects and all messages before applying them, so peak retained memory includes both representations during the import. It does not stream or limit batch size. Snapshot copying and freezing add work, while reparsing stored records performs their checks again. Whether to avoid that work depends on provenance, mutation and the required guarantee. No universal N-times saving, microsecond estimate or I/O-dominance result was measured. Resource budgets and representative workloads belong in the actual integration's design and tests.

### 6) **Mentor note**

Ask what must happen before the first item action in a batch, then show the invalid second item. After a successful parse, mutate the age through another reference and explain why the readonly view sees it. Finally, compare reparsing a cache record with checking the changed allowed-name policy. A good review names each guarantee, the event that can invalidate it, the owner who checks it and the observed integration evidence.
