## 3.2. Schema objects and inferred types

### 1) **Define an executed schema and infer its output**

A schema object is a runtime value describing how to accept, reject or transform input. A schema library can also expose the corresponding TypeScript types. Deriving a type from that value removes a separately maintained interface for the same representation. It does not prove that the schema implements the intended business rules or that custom callbacks are correct.

An interface containing fields such as `{ kind: "str" }` can describe a schema's shape, but an interface is erased. Without an actual schema value and parser implementation, it validates nothing. This lesson uses an executed library example; [3.1](<./3.1. Hand-rolled schemas parse validate narrow.md>) owns the small hand-written parser and its different input policies.

The example uses **TypeScript 7.0.2**, **Zod 4.6.7** and emitted ES2022 modules on **Node.js 20.20.2**. In a new empty directory, run `npm init --yes`, then `npm install --save-exact zod@4.6.7`. Save the three files below there, without a `tsconfig.json`. Compile with `tsc --strict --noUncheckedIndexedAccess --exactOptionalPropertyTypes --verbatimModuleSyntax --erasableSyntaxOnly --target es2022 --module nodenext --moduleResolution nodenext --outDir dist schema.mts demo.mts limits.mts`. Run `node dist/demo.mjs` and `node dist/limits.mjs` separately.

```typescript
// file: schema.mts
import * as z from "zod";
export const PortNumber = z.number().int().min(1).max(65535);
export const PortText = z.string().regex(/^[0-9]+$/).transform(Number).pipe(PortNumber);
export const AppSchema = z.object({
  label: z.string().trim().min(1),
  port: PortText,
  tags: z.array(z.string().trim().min(1)),
  mode: z.union([z.literal("dev"), z.literal("prod")]),
  nick: z.string().optional(),
  note: z.string().exactOptional(),
});
export type AppInput = z.input<typeof AppSchema>;
export type App = z.output<typeof AppSchema>;
export type InferredApp = z.infer<typeof AppSchema>;
```

`AppInput` has a string port, while `App` has a number port. `z.infer` extracts the output type too. The grammar check happens before numeric conversion, then the number schema enforces an integer port from 1 through 65535. A name for the input type documents expected pre-transformation data; the runtime parser still accepts `unknown` and checks it. [Zod's basic usage guide](https://zod.dev/basics) explains input/output inference and the tagged safe-parse result.

The label and tag strings are trimmed. `mode` accepts two literal values. `nick` accepts omission or an explicit `undefined`; it rejects `null`. In this pinned version, `note` uses `exactOptional` to accept omission while rejecting explicit `undefined`. The distinction also appears in the inferred property types under the compiler flag used here. These are schema decisions rather than automatic consequences of naming a property optional.

### 2) **Observe composition, optional presence and union order**

```typescript
// file: demo.mts
import * as z from "zod";
import { AppSchema, PortNumber, type AppInput, type App } from "./schema.mjs";
const source: AppInput = { label: " API ", port: "8080", tags: [" x "], mode: "dev" };
const result = AppSchema.safeParse({ ...source, extra: true });
if (!result.success) throw result.error;
const app: App = result.data;
console.log("parsed", JSON.stringify(app));
console.log("representations", typeof source.port, typeof app.port);
console.log("copies", Object.is(app, source), app.tags === source.tags);
const invalid = AppSchema.safeParse({ ...source, port: "", tags: ["ok", 2], mode: "other" });
if (!invalid.success) console.log("issues", invalid.error.issues.map(issue => issue.path.join(".") + ":" + issue.code).join(","));
for (const [label, value] of [
  ["absent", source],
  ["nick-undefined", { ...source, nick: undefined }],
  ["nick-null", { ...source, nick: null }],
  ["note-undefined", { ...source, note: undefined }],
] as const) {
  const parsed = AppSchema.safeParse(value);
  console.log(label, parsed.success, parsed.success && Object.hasOwn(parsed.data, "nick"));
}
console.log("unknown key policies",
  z.object({ label: z.string() }).safeParse({ label: "A", extra: 1 }).success,
  z.strictObject({ label: z.string() }).safeParse({ label: "A", extra: 1 }).success,
  "extra" in z.looseObject({ label: z.string() }).parse({ label: "A", extra: 1 }));
const short = z.object({ label: z.string() });
const detailed = z.object({ label: z.string(), age: z.number() });
const both = { label: "A", age: 1 };
console.log("union first", JSON.stringify(z.union([short, detailed]).parse(both)));
console.log("union reversed", JSON.stringify(z.union([detailed, short]).parse(both)));
const arbitrary: App["port"] = 70000;
console.log("number type versus rule", arbitrary, PortNumber.safeParse(arbitrary).success);
const Extended = AppSchema.extend({ region: z.enum(["eu", "us"]) });
console.log("evolved", Extended.safeParse(source).success, Extended.safeParse({ ...source, region: "eu" }).success);
// const inputPort: number = source.port; // TS2322: input port is a string.
// const outputPort: string = app.port; // TS2322: output port is a number.
// const exact: App = { ...app, note: undefined }; // TS2375: absent-only optional note does not accept undefined.
// const evolved: z.output<typeof Extended> = app; // TS2741: region is now required.
```

Expected output:

```text
parsed {"label":"API","port":8080,"tags":["x"],"mode":"dev"}
representations string number
copies false false
issues port:invalid_format,tags.1:invalid_type,mode:invalid_union
absent true false
nick-undefined true true
nick-null false false
note-undefined false false
unknown key policies true false true
union first {"label":"A"}
union reversed {"label":"A","age":1}
number type versus rule 70000 false
evolved false true
```

The object schema strips `extra` by default. `strictObject` rejects unknown keys, while `looseObject` retains them in this example. With overlapping union branches, the first successful branch determines the returned representation: the short object branch drops `age`, but the detailed branch retains it when tried first. A TypeScript union does not itself express that parsing precedence. The [schema API reference](https://zod.dev/api) documents these runtime policies.

The successful output has new object and array identities in this concrete example; this is not a promise of deep copying arbitrary opaque values or custom transform results. `nick: undefined` is retained as a present property even though omission is also valid. `exactOptional` imposes a different presence contract for `note`. On the type side, a number port still permits `70000`; the integer/range rule is executed by the schema and is not encoded in the ordinary `number` type.

Adding required `region` changes the extended runtime schema and its inferred type. The original schema remains a different value. This avoids one particular mirror between the extended output type and schema, but callers, tests, documentation and external contracts may still need changes. “One schema definition” does not mean a schema change has no migration work.

### 3) **Evaluate implementation trust and library trade-offs**

```typescript
// file: limits.mts
import * as z from "zod";
import { AppSchema } from "./schema.mjs";
const source = { label: "A", port: "80", tags: [], mode: "dev" };
console.log("inherited fields", AppSchema.safeParse(Object.create(source)).success);
let getterCalls = 0;
const input = { ...source, get label() { getterCalls++; return "A"; } };
console.log("getter", AppSchema.safeParse(input).success, getterCalls);
console.log("sparse policies", z.array(z.string()).safeParse(new Array(1)).success,
  z.array(z.unknown()).safeParse(new Array(1)).success);
const failure = new Error("custom transform failed");
try { z.string().transform(() => { throw failure; }).safeParse("x"); }
catch (error) { console.log("callback exception", error === failure); }
const dishonest = z.custom<string>(() => true);
const claimed: string = dishonest.parse(42);
try { claimed.toUpperCase(); }
catch (error) { console.log("dishonest schema", error instanceof TypeError); }
const asynchronous = z.string().refine(async value => value === "known");
try { asynchronous.safeParse("known"); }
catch (error) { console.log("sync call to async schema", error instanceof Error); }
console.log("async rejection as issues", (await asynchronous.safeParseAsync("missing")).success);
```

Expected output:

```text
inherited fields true
getter true 1
sparse policies false true
callback exception true
dishonest schema true
sync call to async schema true
async rejection as issues false
```

These checks expose policy differences from 3.1's parser. This library example accepts inherited required fields and reads the getter. A string element schema rejects a hole as an invalid element, while an unknown element schema admits its undefined value here. Do not infer an own-data or dense-input requirement merely from the word “schema”; test and enforce the application's actual boundary contract.

`safeParse` turns recognized validation failures into a result. It does not catch the thrown custom transform in this example. A dishonest custom check also produces a claimed string that fails at runtime, so type inference cannot rescue an incorrect schema implementation. Async checks require the corresponding async parsing API. This refinement runs a local callback only; no database, network or uniqueness transaction is involved.

Choose a library or a small owned parser according to requirements and maintenance responsibility. Compare issue quality, transformations, async support, schema reuse, dependency/bundle impact and measured runtime/checker work on representative inputs. There is no rule to adopt after three shapes, no universal fixed bundle size, and no automatic faster implementation. A small parser can be appropriate indefinitely; a library can also be worthwhile for a single important boundary. [Valibot's inference guide](https://valibot.dev/guides/infer-types/) offers another documented input/output model, but this lesson executes only the pinned Zod dependency.

### 4) **Common confusion**

A schema interface is a type description; a schema object plus its parser is executable behavior. Deriving an output type removes a duplicated description, not errors in the implementation or requirements. Ordinary inferred strings/numbers do not encode every normalization or range guarantee.

A TypeScript union permits values assignable to its members; a runtime union parser selects a branch and may transform its output. Optional undefined, absent-only optional and nullable values are separate contracts. Likewise, safe parsing is different from exception containment for arbitrary callback code.

### 5) **Performance note**

Type extraction is erased at runtime, while checking its generic types consumes compiler work. There is no guaranteed one-instantiation, cached-once cost per schema. Runtime work depends on traversal, copying, transforms, issue creation and how many union alternatives are tried. The example measures outcomes and identities, not throughput, compilation time or bundle size. Release benchmark results apply to their named versions, workloads and environments; they do not establish a ranking for this application's boundaries. Reuse schema values when practical, then measure the actual workload if cost matters.

### 6) **Mentor note**

Have the learner predict the input and output port types, then reverse the union branches and explain the lost or retained `age` field. Compare missing `nick`, present undefined `nick` and present undefined `note`. Finish by explaining why the dishonest schema compiles and why a thrown transform escapes safe parsing. A strong review connects each inferred guarantee to executed code, tested input policies and the consumer's representation.
