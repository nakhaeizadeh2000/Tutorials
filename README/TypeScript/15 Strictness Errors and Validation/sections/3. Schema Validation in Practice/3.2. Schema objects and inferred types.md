## 3.2. Schema objects and inferred types

### 1) **Schema-first typing** (validators defined, types derived — single source)

**Definition** — schema-first: define runtime validators (`Str`, `Num`, `Obj({...})` combinator objects), then *derive* static types from them (`type User = Infer<typeof UserSchema>` via indexed-access extraction) — one definition serving runtime checks *and* static checking, drift impossible by construction (the type *is* the schema's projection, never a parallel declaration).

**What problem it solves / history** — parallel type+validator declarations (`interface User {…}` beside `userSchema = {…}` — hand-mirrored, drifting on every field change: type gains `email`, schema forgets it — validated data missing fields the types promise) made every schema evolution a two-file edit with silent half-completion. Schema-first typing deletes the mirror: validators defined once, types derived mechanically — evolution edits one definition, both worlds follow.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), derive types from schemas at boundaries (single source per shape — validators defined, `Infer<>` projected); keep hand-written interfaces for *non-validated* internals (domain logic shapes that never cross unknown — direct declaration, no schema overhead); adopt Zod/Valibot where ecosystems matter (error messages, async refinements, community schemas — see promise 3).

**Runnable example** — single source, both worlds (good vs bad, `tsc --strict`):

```typescript
// good — schema defined once (validators), type derived mechanically (no mirror to drift)
interface FieldStr { kind: "str" }
interface FieldNum { kind: "num" }
type Field = FieldStr | FieldNum;
type InferField<F> = F extends { kind: "str" } ? string : F extends { kind: "num" } ? number : never;
interface UserSchema { name: FieldStr; age: FieldNum }
type User = { [K in keyof UserSchema]: InferField<UserSchema[K]> }; // { name: string; age: number } — derived (never listed)
const u: User = { name: "a", age: 1 };
console.log(u.name.toUpperCase(), u.age.toFixed(0)); // A 1 — type projected from schema (single source, both worlds)
// bad — interface User {...} beside userSchema = {...} (hand-mirrored — type gains email, schema forgets it — validated data missing promised fields)
// fix — schema-first (validators defined, types derived — evolution edits one definition, both worlds follow)
```

```typescript
// good — validator functions paired with derived types (runtime + static composed per shape)
function vStr(x: unknown): x is string { return typeof x === "string"; } // runtime half (type predicate — see 1.2)
function vNum(x: unknown): x is number { return typeof x === "number"; }
type VStr = { check: typeof vStr; type: string }; // schema record pairing validator with its proven type
const strSchema: VStr = { check: vStr, type: "s" };
const raw: unknown = "hi";
if (strSchema.check(raw)) console.log(raw.toUpperCase()); // HI — validator + type traveling together (single source)
// bad — validators returning boolean (untyped verdicts — callers narrow manually per site, claim untethered from test)
// fix — predicate validators (x is T claims — narrowing fused with testing, see 1.2's full treatment)
```

```typescript
// good — evolution edits one definition (schema change propagates to types mechanically)
interface F2Str { kind: "s" }
interface Schema2 { title: F2Str }
type Infer2<F> = F extends { kind: "s" } ? string : never;
type T2 = { [K in keyof Schema2]: Infer2<Schema2[K]> }; // { title: string } — add a field to Schema2, T2 follows (no mirror edit)
// const t: T2 = { title: "x" }; // (derivation proven by use below — single source, both worlds)
const t2: T2 = { title: "x" };
console.log(t2.title.toUpperCase()); // X — evolved once (schema edit → type follows — drift structurally impossible)
// bad — editing interface + schema + tests + docs per field (four files per field — three forgotten eventually)
// fix — schema-first (one definition edited — types, validators, and derivations follow mechanically)
```

**Common confusion** — "derivation obscures types" — hover shows the *projected* type (`{ name: string; age: number }` — readable, navigable to the schema source) — indirection with provenance beats duplication without it. "hand-rolled schemas rival Zod" — hand-rolled teach the *pattern* (define-once, derive-always); Zod/Valibot add *ecosystems* (messages, refinements, performance, community schemas) — pattern first (this leaf), library per thresholds (promise 3). "all types should derive from schemas" — *boundary* types derive (validated shapes crossing unknown); *internal* logic types declare directly (no validation overhead where no unknown crosses).

**Performance note** — derivation costs one mapped-type instantiation per shape (cached once — trivial); validation costs per-field checks per boundary (same as hand-written validators — single source doesn't change check complexity, only maintenance). Zod adds parse overhead per call (measured per boundary — adopt past hand-rolled complexity thresholds, not before).

**Mentor note** — evolve one schema live (add `email` field — type follows with zero additional edits) beside a mirrored pair (interface + schema edited separately, one forgotten) — single-source vs mirror in one field addition. Exercise: convert one mirrored interface+schema pair to schema-first and delete the mirror — drift vectors deleted per conversion. Review gate: hand-mirrored type+validator pairs fail review (single source per shape).

### 2) **Object, array, union, optional combinators** (hand-rolled kit mirroring Zod's shape)

**Definition** — minimal combinator kit: `str`/`num`/`bool` primitives (unknown→typed-or-error per 3.1 promise 2's shapes), `object(fields)` (field-map composition with path-tagged errors), `array(el)` (element parser mapped with index tags), `union(...options)` (first-match with collected errors), `optional(parser)` (absent→undefined, present→parsed — see 3.1 promise 2). Same architecture as Zod/Valibot (combinators + inference) minus ecosystems — the pattern libraries productize.

**What problem it solves / history** — ad-hoc boundary checks (`typeof` chains per endpoint, hand-rolled per form — N validators with N styles, untested per unit, unshared per shape) duplicated primitive logic everywhere (string-checks written dozens of times, each subtly different). Combinator kits centralize primitives (tested once per type) and compose shapes declaratively (objects/arrays/unions from shared parts — new shapes assemble, never re-derive).

**Modern guidance** — as of TypeScript 5.9 era, build the kit once per codebase (primitives + 4 combinators, tested per unit — truth tables per primitive, composition per combinator); compose boundary shapes declaratively (object/array/union/optional over shared primitives); graduate to Zod/Valibot when kit limits hit (rich error messages, async refinements, string formats (email/uuid), performance-tuned parsing — see promise 3).

**Runnable example** — kit composed declaratively (good vs bad, `tsc --strict`):

```typescript
// good — union combinator (first-match with collected errors — alternatives tried in order)
type PE = { path: string; reason: string }; // re-declared: fences compile standalone (minimal error shape)
type Parser<T> = (x: unknown, path: string) => T | PE[];
function pStr(x: unknown, path: string): string | PE[] {
  return typeof x === "string" ? x : [{ path, reason: "want-string" }];
}
function pNum(x: unknown, path: string): number | PE[] {
  return typeof x === "number" ? x : [{ path, reason: "want-number" }];
}
function pUnion(options: Parser<unknown>[], x: unknown, path: string): unknown | PE[] {
  const errs: PE[] = [];
  for (const o of options) {
    const r = o(x, path);
    if (!Array.isArray(r)) return r; // first match wins (alternatives tried in order — documented precedence)
    errs.push(...(r as PE[]));
  }
  return errs; // all failed: collected errors (every alternative's verdict — diagnosable, not just first-failure)
}
const u1 = pUnion([pStr, pNum], "a", "v");
const u2 = pUnion([pStr, pNum], true, "v");
console.log(typeof u1 === "string" ? u1.toUpperCase() : "err", Array.isArray(u2) ? u2.map((e) => (e as PE).reason).join(",") : "ok"); // A want-string,want-number — match wins; failures collect
// bad — if/else type ladders per union (alternatives hand-chained per site — precedence implicit, errors first-failure-only)
// fix — pUnion (ordered alternatives, collected errors — union parsing as a combinator, tested once)
```

```typescript
// good — object combinator over field parsers (path-tagged errors per field — forms render completely)
type PE = { path: string; reason: string }; // re-declared: fences compile standalone (minimal error shape)
function pStr(x: unknown, path: string): string | PE[] {
  return typeof x === "string" ? x : [{ path, reason: "want-string" }];
}
function pObj2(fields: Record<string, (x: unknown, path: string) => unknown | PE[]>, raw: unknown): Record<string, unknown> | PE[] {
  if (typeof raw !== "object" || raw === null) return [{ path: "", reason: "not-object" }];
  const r = raw as Record<string, unknown>;
  const out: Record<string, unknown> = {};
  const errs: PE[] = [];
  for (const [k, parse] of Object.entries(fields)) {
    const v = parse(r[k], k); // per-field parse (path-tagged — locators, not just messages)
    if (Array.isArray(v)) errs.push(...(v as PE[]));
    else out[k] = v;
  }
  return errs.length > 0 ? errs : out; // complete errors (every field verified per parse — no sequential discovery)
}
const o2 = pObj2({ name: pStr }, { name: "x" });
console.log(Array.isArray(o2) ? "errs" : (o2["name"] as string).toUpperCase()); // X — object composed (field parsers shared, errors located)
// bad — monolithic per-shape validators (200-line functions × create/update/patch variants — drift per copy)
// fix — pObj2 over shared field parsers (shapes declare field maps — compositions, not implementations)
```

```typescript
// good — array + optional combinators (element/index tagging + absent-vs-invalid distinction)
type PE = { path: string; reason: string }; // re-declared: fences compile standalone (minimal error shape)
function pStr(x: unknown, path: string): string | PE[] {
  return typeof x === "string" ? x : [{ path, reason: "want-string" }];
}
function pArr2<T>(parse: (x: unknown, path: string) => T | PE[], xs: unknown): T[] | PE[] {
  if (!Array.isArray(xs)) return [{ path: "", reason: "want-array" }];
  const out: T[] = [];
  const errs: PE[] = [];
  xs.forEach((x, i) => {
    const r = parse(x, `[${i}]`); // index-tagged (locators per element — forms highlight precisely)
    if (Array.isArray(r)) errs.push(...(r as PE[]));
    else out.push(r);
  });
  return errs.length > 0 ? errs : out;
}
console.log(JSON.stringify(pArr2(pStr, ["a", 1]))); // [{"path":"[1]","reason":"want-string"}] — located element errors (not partial results)
// bad — JSON.parse + as Shape[] (assertion without evidence — malformed elements crash downstream confidently)
// fix — element parsers + index tags (evidence per element — locators precisely where forms highlight)
```

**Common confusion** — "combinators over-engineer simple shapes" — primitives pay off at 3+ shapes (shared string/number checks vs triplicated `typeof` chains — threshold low, returns immediate). "union order doesn't matter" — first-match wins (overlapping alternatives resolve by *position* — order documents precedence; collected errors cover all-failed diagnostics). "optional combinator equals nullable" — optional handles *absence* (`undefined` → skip); nullable handles *null values* (explicit null → validate-or-reject per schema) — different inputs (missing vs null), different combinators.

**Performance note** — combinators cost per-field function calls (vs inline `typeof` chains — negligible indirection per boundary parse); shared primitives JIT-optimize hot (one function per type, called often); error-list allocation per failure (boundaries only — forms/APIs handle lists routinely).

**Mentor note** — build one combinator live (union with collected errors) and test all branches (first-match, second-match, all-fail — three behaviors, one function). Exercise: replace two monolithic validators with kit compositions and delete the duplicated primitives (deduplication made visible per primitive). Review gate: monolithic per-shape validators fail review past 3 shapes (combinator kit by then).

### 3) **When to adopt a library** (hand-rolled thresholds vs Zod/Valibot ecosystems)

**Definition** — adoption thresholds: error-message quality (hand-rolled string codes vs Zod's structured issues with paths/unions expected-received), async refinements (DB-existence checks, uniqueness queries — async validation hand-rolled awkwardly), string formats (email/uuid/url/datetime validators — reimplementing badly vs importing), performance-tuned parsing (large-payload throughput, JIT-friendly internals), ecosystem schemas (shared OpenAPI-derived validators, community types). Below thresholds: hand-rolled kit (zero deps, full control). Above any: library (ecosystem weight justified).

**What problem it solves / history** — hand-rolled maximalism (reimplementing email regexes, async refinement chains, i18n error catalogs — hundreds of lines reproducing library features badly) and library-by-default (Zod for three string checks — dependency + bundle weight + learning curve for kit-trivial shapes) both misjudge by ideology. Thresholds decide empirically: complexity present → library; absent → kit — reviewed per growth stage, not per preference.

**Modern guidance** — as of TypeScript 5.9 era, stay hand-rolled while shapes stay simple (primitives + objects + unions + optionals cover most internal boundaries); adopt Zod/Valibot at the first threshold crossed (formats/async/messages/performance/ecosystem — one trigger suffices with documented reason); migrate incrementally (new boundaries on the library, legacy kit shapes migrating opportunistically — strangler adoption, never flag-day rewrites).

**Runnable example** — thresholds decided (good vs bad, `tsc --strict`):

```typescript
// good — hand-rolled suffices here (primitives + object, sync, simple messages — below every threshold)
function isEmailLike(s: string): boolean { return s.includes("@"); } // format check proportionate to need (no email-RFC regex — pragmatic)
console.log(isEmailLike("a@b"), isEmailLike("nope")); // true false — threshold assessment (formats simple → kit serves)
// bad — Zod for three string checks (dependency + bundle + learning curve for kit-trivial shapes — ecosystem weight unjustified)
// fix — thresholds (formats/async/messages/performance/ecosystem — adopt past any, hand-roll below all)
```

```typescript
// good — library-shaped need identified honestly (async refinement — hand-rolled awkwardly, library natively)
interface Check { email: string }
function checkSync(c: Check): string[] {
  return c.email.includes("@") ? [] : ["email:format"]; // sync subset (hand-rolled serves — no async here)
}
console.log(checkSync({ email: "x" }).join(","), checkSync({ email: "a@b" }).length); // email:format 0 — sync shapes stay kit (async would trigger library evaluation)
// bad — hand-rolled async refinement chains (promise-plumbed validators reimplementing library primitives badly)
// fix — library at async threshold (DB checks, uniqueness queries — async validation is Zod/Valibot home territory)
```

```typescript
// good — migration strangler pattern (new boundaries library, legacy kit opportunistically — incremental, never flag-day)
function legacyKit(x: unknown): string | undefined {
  return typeof x === "string" ? x : undefined; // existing kit (serves — untouched until thresholds demand)
}
console.log(legacyKit("s")?.toUpperCase() ?? "bad"); // S — strangler (new shapes evaluate library adoption; legacy migrates per threshold crossed)
// bad — flag-day library rewrite (all validators converted in one PR — behavior churn + review impossibility + regression risk)
// fix — strangler adoption (new on library past thresholds, legacy opportunistically — incremental, reviewable, revertible)
```

**Common confusion** — "libraries are always better" — better past thresholds (formats/async/messages/performance/ecosystem); below thresholds they're weight without payoff (dependency + bundle + learning for kit-trivial shapes). "hand-rolled can't infer types" — hand-rolled *can* (indexed-access derivation per promise 1 — weaker than Zod's `z.infer` generics, sufficient for internal shapes). "migration must complete" — strangler *converges* opportunistically (new library, legacy per-threshold — permanent coexistence where kit still serves is fine, not failure).

**Performance note** — hand-rolled parsing minimal overhead (direct checks, no abstraction); Zod adds parse pipeline costs (schema traversal + issue allocation — measured per boundary, justified past thresholds); bundle weight (Zod ~10kb+ min — hand-rolled zero). Thresholds are performance-informed (large-payload throughput is an explicit trigger).

**Mentor note** — score one boundary against all five thresholds live (formats? async? messages? performance? ecosystem? — all-no stays kit, any-yes evaluates library). Exercise: identify the repo's most complex hand-rolled validator and score it (past-threshold → library spike with measurements; below → documented kit decision). Review gate: library adoption without threshold evidence fails review (weight needs justification); hand-rolled past thresholds fails review (reimplementation theater).
