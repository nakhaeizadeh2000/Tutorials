## 1.3. Generic scope — per-call vs per-value and declaration sites

### 1) **Per-call scope** (function `<T>` is fresh on every invocation)

**Definition** — a type parameter declared on a function belongs to that *call*: each invocation re-instantiates `<T>` from its own arguments, and nothing carries over to the next call. `map(users, toId)` with `T = User` and `map(orders, toId)` with `T = Order` are independent instantiations sharing one implementation.

**What problem it solves / history** — per-call scope lets one helper serve every element type without a registry of specializations — the pre-generics alternative was overload lists (`mapStrings`, `mapNumbers`) or `any`-typed helpers that returned `any[]` and pushed the cast onto every caller. Fresh-per-call inference keeps the call chain precise: the mapper's return flows into the result array element type with no annotation at either end.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to per-call generics for transformations — `map<T, U>(xs: T[], f: (x: T) => U): U[]`, `pick<T, K extends keyof T>(obj: T, key: K): T[K]`. Declare the parameter on the function (not the module, not a wider interface) so each call re-solves independently; multiple parameters (`<T, U>`) stay independent unless a constraint links them (`U extends T`).

**Runnable example** — fresh `T` per call (good vs bad, `tsc --strict`):

```typescript
// good — one map, every element type, precise results
function map<T, U>(xs: T[], f: (x: T) => U): U[] { return xs.map(f); }
const names = map([{ n: "a" }, { n: "b" }], (u) => u.n); // string[]
const lens = map(["a", "bb"], (s) => s.length); // number[] — independent T, U
console.log(names[0]?.toUpperCase(), lens[0]?.toFixed(0)); // A 1

// good — key lookup threads T through K without widening
function pick<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
const user = { id: "u1", age: 30 };
console.log(pick(user, "age").toFixed(0)); // 30 — T[K] = number, not string | number

// bad — any helper forces every caller to re-prove the type
function mapBad(xs: any[], f: (x: any) => any): any[] { return xs.map(f); }
const r = mapBad(["a"], (s) => s.length); // any[] — autocomplete dead, errors silent
// console.log(r[0].toFixed(0)); // compiles via any, crashes when mapper returns a string
// fix — map<T, U>: the relationship (not just the values) is checked
```

**Common confusion** — "calling with `string` locks `T` for later calls" — no cross-call memory; each call instantiates independently (unlike a per-value container, next promise). "`<T, U>` must relate" — they are independent unless constrained; `map<T, U>` allows any `U` for any `T`, which is exactly why the mapper (not the input) determines `U`. "fewer parameters is always better" — two precise parameters beat one `any`; the cost is zero at emit.

**Performance note** — per-call generics emit one function regardless of call count — 100 instantiations share the same `.js`. Check cost is per call site but local (argument types are already computed); the IDE cost is hover text, not memory — long inferred instantiations (`Pick<BigConfig, "a" | "b" | …>`) render slowly in tooltips but check fast.

**Mentor note** — show two consecutive `map` calls with different `T` on one screen and ask "what is `T` right now?" — answer is "whichever call you point at." That breaks the variable mental model (one slot, one value) and installs the parameter model (a template re-stamped per call). Exercise: convert `mapBad` to `map<T, U>` and watch `r[0].toFixed` become an error when the mapper returns a string.

### 2) **Per-value scope** (container `<T>` is fixed for the value's lifetime)

**Definition** — a type parameter declared on an interface, type alias, or class is fixed when the *value* is created and shared by every member: `const box: Box<string>` fixes `T = string` for `box.value`, `box.map`, and every method until the value dies. No method re-infers it unless it declares its own parameter.

**What problem it solves / history** — per-call-only thinking produced containers that forgot: `set<T>(x: T)` on a non-generic class stored `unknown` and `get<T>()` let the *reader* guess the type — a `string` in, a `number` out, with a cast papering over the lie. Hoisting `<T>` to the container (`Store<T>`) made the stored type part of the value's identity: `Store<string>` and `Store<number>` are incompatible, and the checker rejects cross-type reads at the assignment, not at the crash.

**Modern guidance** — as of TypeScript 5.9 era, hoist `<T>` to the container when the type must survive between calls — stores, caches, builders, registries (`KVCache<K, V>`, `Builder<T>`, `Registry<T>`). Methods then use the fixed `T` directly; a method declares its own `<U>` only for *additional* per-call flexibility (`getOrElse<U>(fallback: U): T | U`). Constructor functions infer class `T` from arguments (`new Store("hi")` → `Store<string>`) without explicit brackets.

**Runnable example** — fixed `T` across calls (good vs bad, `tsc --strict`):

```typescript
// good — T fixed at construction, enforced on every member
class KVCache<K, V> {
  private m = new Map<K, V>();
  set(k: K, v: V): void { this.m.set(k, v); }
  get(k: K): V | undefined { return this.m.get(k); }
}
const ages = new KVCache<string, number>();
ages.set("ada", 36);
// ages.set("ada", "old"); // error TS2345 — V stayed number
console.log(ages.get("ada")?.toFixed(0) ?? "missing"); // 36

// good — method-level <U> adds per-call flexibility on top of fixed T
class Bag<T> {
  constructor(private items: T[]) {}
  firstOr<U>(fallback: U): T | U { return this.items[0] ?? fallback; }
}
console.log(new Bag([1, 2]).firstOr("none")); // number | string

// bad — generic methods on a non-generic container forget between calls
class LooseBag {
  private items: unknown[] = [];
  add<T>(x: T): void { this.items.push(x); } // T dies with the call
  at<T>(i: number): T | undefined { return this.items[i] as T | undefined; }
}
const lb = new LooseBag();
lb.add("hi");
console.log(lb.at<number>(0)?.toFixed(1)); // compiles via as, undefined behavior at runtime
// fix — Bag<T>: hoist the parameter to the class so add and at share it
```

**Common confusion** — "methods of `KVCache<K, V>` each need `<K, V>`" — they inherit the fixed parameters; redeclaring shadows them (and the shadow is a *different* `K`). "`new KVCache()` without arguments infers `K, V`" — with no constructor site it falls back (`unknown`) — annotate (`new KVCache<string, number>()`) or seed via constructor args. "per-value means immutable" — fixed type, not frozen value: `ages.set("ada", 37)` changes the *value* while `V` stays `number`.

**Performance note** — per-value generics share emit across instantiations (`KVCache<string, number>` and `KVCache<number, string>` emit one class). The checker caches one instantiation per distinct argument tuple — a codebase with 300 `KVCache<string, X>` variants holds 300 cached types (small, structural). Prefer reusing a named instantiation (`type AgeCache = KVCache<string, number>`) over repeating the argument list — one cache entry, one hover rendering.

**Mentor note** — contrast `map<T>` (two calls, two `T`s) with `ages: KVCache<string, number>` (fifty calls, one `V`) on adjacent lines and ask which `T` survives a second call. Then show `at<T>` guessing and ask who chose `number` — the reader, with no evidence — which is why hoisting is a safety fix, not a style nit. Review gate: generic methods on non-generic classes require a comment justifying why the parameter is per-call.

### 3) **Declaration-site choice** (generic function vs container vs alias — pick by lifetime)

**Definition** — three shapes cover every generic API: generic *function* (`<T>` per call — transforms), generic *container* (`<T>` per value — stores), generic *alias* (`<T>` per reference — computes shapes like `Result<T>`, `Dict<T>`). The site decides when `T` is chosen (call, construction, or reference) and how long it lives.

**What problem it solves / history** — mismatched sites caused the two classic generic bugs: a store modeled as a generic function (forgot between calls — `at<T>` guessing) and a transform modeled as a generic container (forced callers to annotate a throwaway value — `new Mapper<string>().run("hi")` instead of `run("hi")`). Naming the three sites turns the choice into a one-question test — "when should `T` be chosen?" — instead of a refactor after the bug.

**Modern guidance** — as of TypeScript 5.9 era, ask the lifetime question first: chosen fresh on every call → function (`parse<T>`, `map<T, U>`); chosen once per stored value → interface/class (`Store<T>`, `Cache<K, V>`); chosen per type reference to compute a shape → alias (`type Api<T> = { data: T; etag: string }`). Aliases compose best (`Api<Box<T>>`); containers enforce lifetimes best; functions infer best. `static` factory methods on generic classes declare their own `<U>` and *return* the instantiated container (`static of<U>(x: U): Store<U>`).

**Runnable example** — three sites, three lifetimes (good vs bad, `tsc --strict`):

```typescript
// good — alias computes a shape per reference
type Api<T> = { data: T; etag: string };
const r: Api<number> = { data: 7, etag: "abc" };
console.log(r.data.toFixed(0)); // 7

// good — function infers per call, container remembers per value
function run<T>(x: T): T { return x; }
class Holder<T> { constructor(public value: T) {} }
console.log(run("hi").toUpperCase()); // HI — no annotation
console.log(new Holder("hi").value.toUpperCase()); // HI — fixed at new

// good — static factory bridges per-call inference into per-value storage
class Box2<T> {
  private constructor(public value: T) {}
  static of<U>(x: U): Box2<U> { return new Box2(x); } // own <U>, returns fixed Box2<U>
}
console.log(Box2.of("hi").value.toUpperCase()); // HI — inferred once, stored after

// bad — container where a function belongs: annotation tax on every call
class Runner<T> { run(x: T): T { return x; } }
// const out = new Runner<string>().run("hi"); // works but forces a throwaway value
const out = run("hi"); // fix — per-call behavior wants a generic function
console.log(out.toUpperCase()); // HI
```

**Common confusion** — "aliases are just shorthand, scope does not matter" — `Api<T>` fixes `T` per *reference* (`Api<string>` vs `Api<number>` are distinct types), which is why `Api<Box<T>>` nesting works — each reference instantiates independently. "static `of` can reuse class `T`" — no `T` exists until `new` fixes it; the factory's `<U>` *becomes* the instance's `T` through the return type. "one site fits all" — forcing transforms into containers (or stores into functions) always costs either annotations or safety — pick by lifetime, not habit.

**Performance note** — alias instantiation is lazy and cached: `Api<number>` computes once and reuses. Deep alias nesting (`Api<Box<Cache<string, number>>>`) checks inside-out with one cache entry per level — keep nesting under ~5 levels in public signatures or hover/checker latency grows linearly with depth. Functions infer fastest (local sites); containers verify cheapest (fixed argument reused across members).

**Mentor note** — give the one-question test as a review stamp: "when is `T` chosen — per call, per value, or per reference?" If the author cannot answer in one sentence, the site is wrong. Exercise: rewrite `Runner<T>` as `run<T>` and `LooseBag` as `Bag<T>`, then ask which rewrite deleted annotations and which deleted a cast — functions delete annotations, containers delete casts.
