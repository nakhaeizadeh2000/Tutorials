## 1.1. Type parameters — declaration, instantiation and erasure

### 1) **What `<T>` declares** (a compile-time parameter filled per use — erased before emit)

**Definition** — a type parameter is a placeholder listed in angle brackets at a declaration — `function identity<T>(x: T): T` declares `T`, and each use *instantiates* it with a concrete type — `identity<string>("hi")` fills `T = string` for that call only. The parameter exists purely in the checker's world: after `tsc` emits, no trace of `T` remains.

**What problem it solves / history** — before generics (TypeScript 0.9, 2013), reusable containers had two bad options: duplicate per type (`StringBox`, `NumberBox`) or fall back to `any` (`class Box { value: any }`) and lose every check at the boundary. Type parameters gave one declaration with per-use precision — `Box<string>` and `Box<number>` share the implementation but keep disjoint contracts, and the checker enforces each instantiation separately.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), declare `<T>` whenever the same shape works for many types and the relationship between input and output matters — `function first<T>(xs: T[]): T | undefined`, `interface Box<T> { value: T }`. Name single parameters `T` (`U`, `V` for more); use descriptive names (`TItem`, `TKey`) when a signature carries three or more. All generic syntax erases (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**Runnable example** — one declaration, many instantiations (good vs bad, `tsc --strict`):

```typescript
// good — one generic box, precise per use
interface Box<T> { value: T; }
const sBox: Box<string> = { value: "hi" };
const nBox: Box<number> = { value: 42 };
// sBox.value.toFixed(2); // error TS2339 — string has no toFixed; precision kept
console.log(sBox.value.toUpperCase(), nBox.value.toFixed(1)); // HI 42.0

// good — input/output relationship preserved
function first<T>(xs: T[]): T | undefined { return xs[0]; }
console.log(first(["a", "b"])); // a (string | undefined)
console.log(first([1, 2])); // 1 (number | undefined)

// bad — any box erases the contract instead of parameterizing it
interface AnyBox { value: any; }
const b: AnyBox = { value: "hi" };
console.log(b.value.toFixed(2)); // compiles (any), crashes at runtime
// fix — parameterize: Box<string> keeps .toUpperCase and blocks .toFixed
```

**Common confusion** — "`<T>` is a runtime argument" — it is compile-time only; you cannot `console.log(T)` or branch on `T` at runtime (see [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>)). "`Box<string>` creates a new class at runtime" — one implementation serves all instantiations; the checker distinguishes them, emit does not. "`T` defaults to `any`" — unconstrained `T` defaults to `unknown` for inference fallback, not `any` (see [2.1. any the escape hatch](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>)).

**Performance note** — generics cost checker time, not runtime time: each instantiation is checked separately (O(instantiations × body)), but emit is shared and allocation-identical. A generic called with 50 distinct `T`s costs 50 check passes and one emitted function — keep hot generic bodies small so the multiplicative check cost stays flat; measure with `tsc --extendedDiagnostics`, never by guessing emit size.

**Mentor note** — teach `<T>` as "a function argument, but for types" — draw `identity<string>` next to `greet("hi")` and ask which world each argument lives in. Exercise: give `AnyBox` and ask students to break it with `.toFixed` on a string, then fix by parameterizing — the crash-to-error conversion sells generics in one minute. Review gate: ban `any`-valued containers where a `<T>` would preserve the relationship.

### 2) **Where generics may appear** (function, alias, interface, class — scope follows the site)

**Definition** — `<T>` may be declared on four sites: function (`function f<T>(x: T)`), type alias (`type Pair<T> = [T, T]`), interface (`interface Box<T> { value: T }`), and class (`class Store<T> { item!: T }`). Scope follows the site: a function parameter is fresh per call; an interface/class parameter is fixed per value for its whole lifetime.

**What problem it solves / history** — early generic teaching showed only functions, so developers parameterized the wrong site — a per-value container modeled as a generic function re-inferred on every method call and lost the stored type between calls. Declaring `<T>` on the container (`Store<T>`) instead of on each method (`get<T>()`) fixed the lifetime: the type is chosen once at construction and threaded through every member without re-inference.

**Modern guidance** — as of TypeScript 5.9 era, pick the site by lifetime: per-call behavior → generic function (`map<T, U>`); per-value container → generic interface/class (`Box<T>`, `Map<K, V>`); reusable shape computation → generic alias (`Result<T> = Ok<T> | Err`). `static` members cannot reference the class's `T` (no value exists to fix it) — give the static method its own `<U>` instead.

**Runnable example** — site determines lifetime (good vs bad, `tsc --strict`):

```typescript
// good — per-value scope: T fixed at construction, shared by all members
class Store<T> {
  private item: T | undefined;
  set(x: T): void { this.item = x; }
  get(): T | undefined { return this.item; }
}
const ss = new Store<string>();
ss.set("hi");
console.log(ss.get()?.toUpperCase()); // HI — T stayed string between calls

// good — per-call scope: fresh T on every invocation
function wrap<T>(x: T): { value: T } { return { value: x }; }
console.log(wrap("a").value.toUpperCase()); // A
console.log(wrap(1).value.toFixed(1)); // 1.0 — independent instantiation

// bad — generic method on a non-generic container loses the stored type
class LooseStore {
  private item: unknown;
  set<T>(x: T): void { this.item = x; } // T forgotten after the call
  get<T>(): T | undefined { return this.item as T | undefined; } // caller guesses T
}
const ls = new LooseStore();
ls.set("hi");
console.log(ls.get<number>()?.toFixed(1)); // compiles via as, lies at runtime
// fix — Store<T>: the class (not the method) owns the parameter
```

**Common confusion** — "a generic method and a generic class are interchangeable" — the method re-instantiates per call (forgets between calls); the class fixes `T` per value (remembers). "`static` can use the class `T`" — it cannot (`TS2302`: static side has no instance to fix `T` from) — declare `static of<U>(x: U)` with its own parameter. "type aliases and interfaces scope identically" — both fix per value, but only interfaces merge and extend nominally (see [1.3. Interfaces vs type aliases](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)).

**Performance note** — site choice has no emit cost either way — `Store<string>` and `Store<number>` share one emitted class. The checker cost differs: per-call functions re-solve `T` at each call site (cheap, local), while generic classes thread `T` through every member access (each `ss.get()` re-checks against the fixed argument). Neither allocates at runtime — the decision is purely about lifetime semantics, not speed.

**Mentor note** — draw two timelines: function `<T>` (born and dies within one call arrow) vs class `<T>` (born at `new`, lives as long as the value). Ask "should the type be allowed to change between these two calls?" — yes → generic function; no → generic container. Review checklist: flag `get<T>()` methods on non-generic classes — they almost always want the parameter hoisted to the class.

### 3) **Erasure proof** (`Box<string>` and `Box<number>` emit identical JavaScript)

**Definition** — generic instantiation is fully erased: `const a: Box<string> = { value: "x" }` and `const b: Box<number> = { value: 1 }` emit the same object literals — the `<string>` / `<number>` arguments exist only while `tsc` checks. No runtime registry maps values back to their `T`; `instanceof` cannot distinguish instantiations of the same generic.

**What problem it solves / history** — developers coming from reified generics (C#, Java with bridge methods) expected `T` to be inspectable at runtime — `if (x instanceof Box<string>)` or `typeof T === "string"` inside the body. TypeScript kept the C++-template/erasable philosophy instead: the body may only use what the constraint guarantees, and any runtime branching must go through an explicit value-level tag (discriminant, `kind` field, or a passed-in predicate) rather than the erased parameter.

**Modern guidance** — as of TypeScript 5.9 era, never branch on `T` at runtime — thread a value alongside the type: `function parse<T>(input: string, schema: (raw: unknown) => T): T` (the `schema` function is the runtime half of erased `T`). When a boundary needs the type name at runtime (logging, metrics), pass it explicitly (`entityName: string`) instead of trying to recover `T`. Generics stay safe under `--erasableSyntaxOnly` — no `enum`/`namespace` trap here.

**Runnable example** — erasure means no runtime `T` (good vs bad, `tsc --strict`):

```typescript
// good — runtime behavior comes from values, types only check
function parse<T>(input: string, decode: (raw: unknown) => T): T {
  return decode(JSON.parse(input));
}
const n = parse("42", (raw) => Number(raw));
console.log(n.toFixed(1)); // 42.0 — T = number proven at compile time, Number() runs it

// good — discriminant carries the runtime half when T alone cannot
type Load<T> = { status: "ok"; data: T } | { status: "err"; error: string };
function show<T>(r: Load<T>, render: (v: T) => string): string {
  return r.status === "ok" ? render(r.data) : `err ${r.error}`;
}
console.log(show({ status: "ok", data: 7 }, (v) => `#${v}`)); // #7

// bad — trying to inspect the erased parameter at runtime
function tagBad<T>(x: T): string {
  // return typeof T === "string" ? "str" : "other"; // error TS2693: 'T' only refers to a type
  return typeof x === "string" ? "str" : "other"; // fix — inspect the VALUE, not the parameter
}
console.log(tagBad("hi"), tagBad(7)); // str other
```

**Common confusion** — "`Box<string>` and `Box<number>` are different runtime classes" — identical emit; only the checker distinguishes them. "`instanceof` can test `T`" — `instanceof` tests constructor functions (values), never type arguments. "erasure means generics are free" — free at runtime, not at check time: each instantiation is verified separately, and recursive/variadic generics can measurably slow `tsc` (see [3.2. Recursive generics](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>)).

**Performance note** — emit delta of adding `<T>` to a declaration is zero bytes — verify with `tsc --emit` and diff. The check-time cost is per-instantiation: a generic helper instantiated with 200 distinct literal `T`s (route tables, event maps) creates 200 cached instantiations — each cheap alone, but hover/completion over the union can feel slow in the IDE. Prefer one generic over a literal-union instantiation per call site when the body does not depend on the literal.

**Mentor note** — prove erasure live: compile `Box<string>` vs `Box<number>` with `tsc` and `diff` the `.js` — identical output ends the "which is faster at runtime?" debate permanently. Then ask how `show()` knows which branch it is in — answer is the `status` value, never `T` — cementing the type/value split. Link forward to `infer` (see [2.3. infer](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>)) as the compile-time way to *compute* from `T` without runtime access.
