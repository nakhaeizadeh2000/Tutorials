## 1.1. Type parameters — declaration instantiation and erasure

A type parameter names a relationship that a declaration can preserve for different type choices. For example, a box's value type can be string in one use and number in another, while one implementation supplies the behavior. The type argument is checking information; actual inputs and callbacks still determine runtime results.

These independent examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under its filename in a scratch directory without tsconfig.json. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Activate each commented negative independently and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **What a type parameter declares**

`T` in `interface Box<T>` is a type parameter. `string` in `Box<string>` is the supplied type argument. The value member is checked using that choice. In `first<T>`, the parameter relates the array's element type to its possible result; the return also includes undefined because an empty array has no first element.

Save as `relationships.ts`.

```typescript
interface Box<T> { value: T }
const words: Box<string> = { value: "hello" };
const numbers: Box<number> = { value: 42 };
console.log(words.value.toUpperCase(), numbers.value.toFixed(1));
// words.value.toFixed(1); // TS2551: the member remains string
// const wrong: Box<number> = words; // TS2322: incompatible value member
function first<T>(values: readonly T[]): T | undefined { return values[0]; }
const word = first(["a", "b"]);
const number = first([1, 2]);
console.log(word, number, first<string>([]));
// const required: string = first<string>([]); // TS2322: empty result remains possible
// function assumeLength<T>(value: T): number { return value.length; } // TS2339

interface AnyBox { value: any }
const unchecked: AnyBox = { value: "hello" };
try { unchecked.value.toFixed(1); }
catch (error) { console.log(error instanceof TypeError ? "unchecked value: TypeError" : "unexpected error"); }
```

The output is `HELLO 42.0`, `a 1 undefined`, then `unchecked value: TypeError`. The generic boxes retain useful restrictions; the any-valued box permits a method call that its string value cannot perform. A generic body cannot assume an unconstrained input has length merely because one caller passes a string. The [primary generics explanation](https://www.typescriptlang.org/docs/handbook/2/generics.html#working-with-generic-type-variables) describes that obligation. If a body needs a capability, express it through the parameter's structure or an appropriate constraint; [constraints](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) develops the choice.

Use a parameter when a relationship helps the API. A one-off length reader can accept `{ length: number }` directly if it does not need to preserve the caller's input type. The [original Golden Rule discussion](https://effectivetypescript.com/2020/08/12/generics-golden-rule/) asks what a parameter relates, including inferred result positions. Treat that as a design question, not a mechanical ban based on counting letters. [Function-level generics](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) owns the full mapper, constraint, default and decoder introduction; [inference control](<./1.2. Inference from arguments and explicit type arguments.md>) owns how arguments select a choice.

### 2) **Where generics may appear**

Functions and methods can declare type parameters for their calls. Interfaces, aliases and classes can declare parameters used by their members or type structure. A generic container can also have a method with its own parameter. Placement determines which relationship a caller is choosing; it is not limited to four isolated keywords.

Save as `sites.ts`.

```typescript
type Pair<T> = readonly [T, T];
interface Box<T> { value: T }
function pair<T>(value: T): Pair<T> { return [value, value]; }
const names: Pair<string> = pair("Ada");
const numeric: Box<number> = { value: 3 };
console.log(names.join(","), numeric.value);
// const mismatched: Pair<string> = ["Ada", 3]; // TS2322

class Cell<T> {
  value: T;
  constructor(value: T) { this.value = value; }
  map<U>(transform: (value: T) => U): Cell<U> {
    return new Cell(transform(this.value));
  }
  static of<U>(value: U): Cell<U> { return new Cell(value); }
  // static shared: T; // TS2302: static members cannot refer to the class parameter
}
const text = Cell.of("hello");
const count = Cell.of(42);
console.log(text.value.toUpperCase(), count.value.toFixed(0));
console.log(text.map(value => value.length).value);
console.log(text.constructor === count.constructor, text instanceof Cell, count instanceof Cell);
// text.value = 42; // TS2322: this view's member is string
```

The output is `Ada,Ada 3`, `HELLO 42`, `5`, then `true true true`. Pair describes a tuple type and Box describes a structural member contract; neither creates a runtime tuple or box by declaration alone. The actual literals and function calls create the values. Cell is a runtime class, and both instances share its constructor. Their member types differ because their type arguments differ.

Cell's instance parameter T connects its constructor input, value and map callback input. Each map call can select a new U for the resulting cell. Its static factory has its own U: a shared static member cannot use an instance's T to create a separate slot for each type choice. The [primary generic-class guidance](https://www.typescriptlang.org/docs/handbook/2/generics.html#generic-classes) states that static-side limitation. [Static members and generics](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>) owns the runtime/static comparison, and [generic scope](<./1.3. Generic scope per-call vs per-value and declaration sites.md>) deepens parameter placement. Interfaces and aliases are structural contracts here; interface extension does not make them nominal types.

### 3) **Prove erasure without confusing type and value changes**

Different type arguments do not inherently require different JavaScript implementations. But replacing a string literal with a numeric literal *does* change the runtime program. To isolate erasure, compare two accepted files that differ only in a type annotation while keeping the same runtime expression.

Save as `emit.ts`.

```typescript
interface Box<T> { value: T }
function identity<T>(value: T): T { return value; }
const box: Box<string> = { value: "same" };
console.log(identity(box.value));
```

Compile and run it: the output is `same`. Copy this source to `emit-unknown.ts` and change **only** `Box<string>` to `Box<unknown>` on the box annotation. Compile that file with the same command and run it: the output is also `same`. Run `diff -u dist/emit.js dist/emit-unknown.js`: it produces no differences for these options and sources. Inspect either output: the interface, type parameter, type argument and annotations disappear, while the identity function, object creation and console call remain.

The two source contracts still differ: a string method through box.value is available in emit.ts and rejected through the unknown view. Byte-identical runtime output does not imply identical checking information. Conversely, the two Cell instances above allocate actual objects holding different values; erasure does not eliminate those allocations.

A type parameter is also not a runtime binding you can inspect. Pass the runtime operation or evidence the generic needs. Save as `runtime.ts`.

```typescript
function render<T>(value: T, format: (value: T) => string): string {
  return format(value);
}
console.log(render(42, value => value.toFixed(1)));
console.log(render({ name: "Ada" }, value => value.name.toUpperCase()));
function category<T>(value: T): string {
  // return typeof T; // TS2693: T exists only in type space
  return typeof value;
}
console.log(category("hello"), category(42));
// render(42, (value: string) => value.toUpperCase()); // TS2345
```

The output is `42.0`, `ADA`, then `string number`. The callback actually formats the supplied value; T only connects the callback's accepted input to that value. A boundary decoder follows the same principle: a runtime function must establish the result, not a caller-selected type argument alone. Reuse the [checked decoder example](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) rather than treating coercion such as Number(raw) as full shape validation. [Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) owns the broader source/emit distinction.

### 4) **Common confusion**

A type argument chooses a static contract; it is not a second runtime constructor or an automatically checked input value. Generic declarations also differ from any: the checker retains the relationship and rejects operations that the admitted choices do not support. An unconstrained T is not permission to access arbitrary members.

There is no universal “T defaults to any” or “T always becomes unknown” rule. Inference evidence, constraints, defaults and contextual results matter; the adjacent inference owner supplies worked contrasts. Also, changing the type argument cannot be used as a runtime instanceof test for a particular payload type. A shared constructor can recognize its instances without knowing whether a cell holds a string or number.

### 5) **Performance note**

The emit comparison establishes that these type-only differences add no runtime code. The actual object literals, new Cell calls, array construction and callbacks still execute. It does not establish that every generic API has zero allocation or that two differently implemented programs have equal runtime cost.

This example also supplies no checker-cost formula or count of generic-body rechecks. A type-argument count is not evidence that a body is checked or emitted once per call. For a measured checking slowdown, use [extended diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) and preserve the relationship during any simplification.

### 6) **Mentor note**

Ask the learner to mark each declaration-site parameter, each supplied type argument and each runtime argument. Then have them predict the rejected AnyBox-style method call when the value is exposed through Box<string>. A sound explanation names the preserved member type, not an imagined runtime generic check.

For the emit drill, keep the value literal unchanged and compare string versus unknown annotations. Explain both the unchanged JavaScript and the different accepted operations. Finally, ask which real value render uses to choose its formatting operation and why a bare T could not provide it. This ties the static relationship to concrete runtime behavior.
