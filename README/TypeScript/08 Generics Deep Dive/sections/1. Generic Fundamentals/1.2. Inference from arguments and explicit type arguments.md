## 1.2. Inference from arguments and explicit type arguments

A generic call relates the supplied values to a type parameter. Inference may preserve a literal, reflect an already widened source, use an expected result context or gather candidates from more than one argument. Diagnose the actual signature and call before choosing an explicit type argument.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Save each named file in a new directory without a `tsconfig.json`. Run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir out FILE.ts`, then `node out/FILE.js`, substituting inference, evidence, noinfer or decoder. All four compile and run as shown. For an intentional rejection, uncomment only its indicated line and check with the same flags plus `--noEmit` instead of `--outDir out`.

### 1) **Observe the inferred type before fixing it**

For this identity signature, the call with hi produces the literal type `"hi"`. The constrained invoke call similarly preserves `"get"`. A let-bound source has already widened to string, so invoke receives that broader type. Writing identity<string> deliberately chooses string rather than restoring lost precision. The type-equality checks below make those predictions executable at checking time.

Save `inference.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function identity<T>(value: T): T { return value; }
function invoke<M extends string>(method: M, url: string): M { return method; }
const literal = identity("hi");
const numberLiteral = identity(42);
const method = invoke("get", "/u");
let mutableMethod = "get";
const widened = invoke(mutableMethod, "/u");
const explicitString = identity<string>("hi");
type Literal = Expect<Equal<typeof literal, "hi">>;
type NumberLiteral = Expect<Equal<typeof numberLiteral, 42>>;
type Method = Expect<Equal<typeof method, "get">>;
type Widened = Expect<Equal<typeof widened, string>>;
type ExplicitString = Expect<Equal<typeof explicitString, string>>;
console.log("values:", literal, numberLiteral, method, widened, explicitString);
// const forced = invoke<"get">(mutableMethod, "/u"); // uncomment: TS2345
```

The live assertions compile and runtime prints `values: hi 42 get get hi`. The same runtime string can have different static contracts. Uncomment forced to observe TS2345: an explicit `"get"` argument does not make a string-typed input satisfy that singleton. Narrow the input through evidence or preserve the literal where it is created. Do not assert a specific method simply because its current initializer happens to be get.

This is a result for these declarations, rather than a rule that every generic preserves every literal. Return shape, constraints, mutable object properties and contextual typing can affect inference. The [function generics reference](https://www.typescriptlang.org/docs/handbook/2/functions.html#generic-functions) explains relating input/output types; [widening and contextual typing](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>) owns the source-level model. Matt Pocock's original [NoInfer explanation](https://www.totaltypescript.com/noinfer) also starts with the literal identity result, before changing the inference site.

### 2) **No argument evidence, contextual results and empty arrays**

An unconstrained factory with no argument or expected result supplying T falls back to unknown here. An explicit number argument can give an empty collection its element contract. A contextual number-or-undefined annotation can guide the return-only make call; the function still returns undefined at runtime. The expected type is checking information rather than a value-producing mechanism.

Save `evidence.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function make<T>(): T | undefined { return undefined; }
const noContext = make();
const contextual: number | undefined = make();
function empty<T>(): T[] { return []; }
const noElementEvidence = empty();
const numbers = empty<number>();
numbers.push(1);
function head<T>(values: readonly T[]): T | undefined { return values[0]; }
const emptyHead = head([]);
const typedHead = head<number>([]);
type NoContext = Expect<Equal<typeof noContext, unknown>>;
type NoElements = Expect<Equal<typeof noElementEvidence, unknown[]>>;
type EmptyHead = Expect<Equal<typeof emptyHead, undefined>>;
type TypedHead = Expect<Equal<typeof typedHead, number | undefined>>;
console.log("factory:", noContext, contextual, numbers.length); // undefined undefined 1
console.log("head:", emptyHead, typedHead); // undefined undefined
// console.log(noContext.toFixed()); // uncomment: TS18046
// numbers.push("oops"); // uncomment: TS2345
```

The equality checks pass, and the two output lines are `factory: undefined undefined 1` and `head: undefined undefined`. Empty<T>() has no element inference site, so its bare call returns unknown[]. By contrast, head([]) infers never for the empty literal's element type in this call and reduces the return to undefined. An explicit number element contract makes typedHead number-or-undefined; it cannot create a first element.

Uncomment the unknown operation to observe TS18046, or the string push to observe TS2345. An annotated empty collection is useful when later writes must obey its element contract. Do not diagnose every empty array as never[]: local evolving-array behavior has its own [verified pitfall explanation](<../../../03 Basic Types and Annotations/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by basic type misunderstandings.md>).

### 3) **NoInfer: choose which argument supplies the candidates**

Sometimes one argument should define a permitted set and another should be checked against it. If both contribute candidates, an invalid initial choice can expand the inferred set. Built-in NoInfer, introduced in [TypeScript 5.4](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-4.html#the-noinfer-utility-type), excludes its wrapped position from candidate inference while still checking that argument against the resulting type.

Save `noinfer.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function chooseLoose<C extends string>(choices: readonly C[], initial: C): C {
  if (!choices.includes(initial)) throw new RangeError("initial is not a choice");
  return initial;
}
function choose<C extends string>(choices: readonly C[], initial: NoInfer<C>): C {
  if (!choices.includes(initial)) throw new RangeError("initial is not a choice");
  return initial;
}
const choices = ["red", "green"] as const;
const picked = choose(choices, "red");
console.log("picked:", picked); // red
type Picked = Expect<Equal<typeof picked, "red" | "green">>;
// const rejected = choose(choices, "blue"); // uncomment: TS2345

function tryInvalidLoose(): void {
  try {
    const accepted = chooseLoose(choices, "blue"); // checker accepts expanded C
    type Expanded = Expect<Equal<typeof accepted, "red" | "green" | "blue">>;
    console.log(accepted);
  } catch (error: unknown) {
    console.log("loose:", error instanceof RangeError ? "RangeError" : "other");
  }
}
tryInvalidLoose();
const widenedChoices: string[] = ["red", "green"];
try {
  choose(widenedChoices, "blue"); // C is string; NoInfer cannot restore lost literals
} catch (error: unknown) {
  console.log("widened:", error instanceof RangeError ? "RangeError" : "other");
}
```

The output is `picked: red`, `loose: RangeError` and `widened: RangeError`. The loose call is accepted statically because blue joins the union; its live Expanded assertion checks that result type even though the runtime membership check throws before returning. With NoInfer on initial, the readonly literal choices supply `"red" | "green"`. Uncomment rejected to observe TS2345 for blue. Remove NoInfer from that parameter and the same call checks successfully again.

NoInfer does not install the includes check; both functions explicitly implement it. If choices is already string[], C becomes string and a blue argument passes the static contract. The runtime membership check still rejects it. This distinction matters for data loaded or mutated at runtime. Choose NoInfer when one parameter genuinely owns inference, retain another useful source of evidence, and test both an accepted input and a rejected competing candidate. It is not a general speed annotation or a substitute for parsing. The [utility reference](https://www.typescriptlang.org/docs/handbook/utility-types.html#noinfertype) documents its inference role; the worked owner is this lesson.

### 4) **Explicit arguments do not validate data**

An explicit argument supplies or constrains a type parameter. It remains subject to the value parameter's checks and adds no runtime decoder. Prefer a signature that relates the returned T to a real decoding function when consuming parsed data.

Save `decoder.ts`:

```typescript
export {};
function parseAs<T>(text: string, decode: (raw: unknown) => T): T {
  const raw: unknown = JSON.parse(text);
  return decode(raw);
}
function decodeAge(raw: unknown): number {
  if (typeof raw !== "number" || !Number.isFinite(raw) || raw < 0) {
    throw new TypeError("expected a finite nonnegative age");
  }
  return raw;
}
const age = parseAs("42", decodeAge); // decoder return infers number
console.log("age:", age.toFixed(1)); // 42.0
for (const text of ['"42"', '-1', 'null']) {
  try { parseAs<number>(text, decodeAge); }
  catch (error: unknown) {
    console.log("invalid:", error instanceof TypeError ? "TypeError" : "other");
  }
}
```

The output is `age: 42.0` followed by three `invalid: TypeError` lines. The successful call infers number from decodeAge's return. The invalid calls explicitly request number but still fail the decoder's checks. That failure comes from the implementation, rather than the angle brackets. This fixture chooses a finite nonnegative-number contract; a more specific age range would require additional checks. Full boundary parsing belongs in [validation](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>).

Use inference when the supplied evidence captures the intended contract. Use an explicit argument when the call needs a chosen element/result type or an intentionally broader contract. Use NoInfer when one competing parameter should be checked without contributing candidates. Explain the choice in terms of the API's relationship, rather than applying a fixed quota of explicit arguments.

### 5) **Common confusion**

A literal identity result does not mean every generic return is a literal. An explicit type argument cannot narrow a genuinely string-typed input without evidence or populate an empty array. NoInfer suppresses candidates at a position rather than disabling checking there. Finally, knowing T is number does not make JSON data numeric: follow the runtime decoder as well as the static relationship.

### 6) **Performance note**

Type arguments, equality probes and NoInfer are erased. The implementations still execute membership scans, JSON parsing and decoder checks. No checker or runtime speed comparison was measured here; neither fewer angle brackets nor adding NoInfer establishes an optimization. Investigate slow inference with the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) and preserve the tested API relationship when changing a signature.

### 7) **Mentor note**

Have the learner predict identity's literal, the let source's string type and the two different empty-call results before checking the equality probes. Then ask which choose parameter should own C, remove NoInfer and activate blue. A sound answer explains why the candidate union grows and why the runtime membership rejection remains. Finish by asking why parseAs<number> still rejects a JSON string containing digits.
