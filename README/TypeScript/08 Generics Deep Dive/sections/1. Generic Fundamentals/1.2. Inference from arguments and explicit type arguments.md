## 1.2. Inference from arguments and explicit type arguments

### 1) **Inference from arguments** (the checker fills `T` from what you pass)

**Definition** — when you call `identity("hi")` without writing `<string>`, TypeScript *infers* `T = string` from the argument — the parameter `x: T` becomes an inference site, and the checker solves `T` from the value flowing into it. No annotation needed at the call site; the return type follows (`T` → `string`).

**What problem it solves / history** — explicit type arguments on every call (`identity<string>("hi")`, `map<string, number>(xs, f)`) made generics feel like Java 5 ceremony — correct but noisy, so developers fell back to `any` helpers to avoid writing them. Inference (present since generics landed in TS 0.9) removed the tax for the common case: the 90% of calls where the argument determines `T` need zero angle brackets, and explicit arguments remain only for the ambiguous 10%.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), rely on inference by default — `first(["a"])`, `wrap(42)`, `map(users, u => u.id)` — and read the hover when the result surprises you. Inference flows from *value positions* (arguments, array elements); it cannot invent a type from nothing — a parameter with no inference site falls back to its constraint or `unknown`. Preserve literals deliberately (see [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>)) instead of fighting widening after the fact.

**Runnable example** — inference in action (good vs bad, `tsc --strict`):

```typescript
// good — T solved from the argument, return follows
function identity<T>(x: T): T { return x; }
const s = identity("hi"); // T = string, s: string
console.log(s.toUpperCase()); // HI
const n = identity(42); // T = number, independent instantiation
console.log(n.toFixed(1)); // 42.0

// good — multi-site inference picks the common supertype
function pair<F, S>(f: F, s: S): [F, S] { return [f, s]; }
const p = pair("a", 1); // [string, number]
console.log(p[0].toUpperCase(), p[1].toFixed(0)); // A 1

// bad — nothing to infer from: T falls back, precision lost
function make<T>(): T | undefined { return undefined; }
const v = make(); // T = unknown — no argument constrained it
// console.log(v.toFixed(1)); // error TS18046 — unknown, not number
// fix — give the checker a site: pass an argument or write the argument explicitly (next promise)
function makeFrom<T>(fallback: T): T { return fallback; }
console.log(makeFrom(7).toFixed(1)); // 7.0 — inferred from fallback
```

**Common confusion** — "inference reads the return type backwards" — inference flows *into* `T` from arguments and *out* through the return; the expected return context can guide it (contextual typing, see [3.2. Inference and widening](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>)), but a bare `make()` with no sites has nothing to solve. "`T` was inferred as `string`, so the literal `"get"` is gone" — widening: string literals widen to `string` at mutable inference sites unless `as const` or a literal constraint keeps them (handled in unit 2.1/3.3 patterns). "hover shows `{}` so `T` is object" — `{}` is the pre-`unknown` fallback in old code; modern fallback is `unknown` — treat either as "no inference happened."

**Performance note** — inference is local and cheap: solving `T` from one argument is O(argument type size), with no cross-file graph walk. Cost grows with *candidate count*: a 5-parameter generic called with object-literal arguments infers 5 sites per call — still microseconds. The measurable slowdown comes from inference over huge literal unions (route tables with 500 members) — each call re-solves against all members; extract the union to a named type so the solver caches once.

**Mentor note** — demo inference by hovering `identity("hi")` and showing `T = string` inline — students see the invisible argument become visible. Exercise: call `make()` and ask why `v` is `unknown` — answer is "no value ever flowed into `T`." Follow with `makeFrom(7)` to show the fix is a site, not a cast. Review gate: flag explicit `<string>` arguments where inference already produces `string` — redundant arguments rot when the value type changes.

### 2) **Explicit type arguments** (writing `<T>` when inference cannot or should not decide)

**Definition** — an explicit type argument pins `T` at the call site — `identity<string>("hi")`, `empty<number[]>()`, `fetchAs<User>("/me")` — overriding or supplying what inference would compute. Required when there is no inference site (factory with only a return type), and chosen when inference picks too wide a type (widened `string` instead of `"get"`).

**What problem it solves / history** — inference-only generics left two gaps: factories (`create<T>(): T`, `parse<T>(s: string): T`) had no argument to infer from and collapsed to `unknown`, and widened literals (`"get"` → `string`) silently lost the precision downstream exhaustiveness needed. Explicit arguments close both: they supply the missing input and narrow the widened one — the caller, who knows the intent, decides instead of the solver guessing.

**Modern guidance** — as of TypeScript 5.9 era, write explicit arguments in exactly three situations: no inference site (`useState<string>("")` on first render with `undefined` initial), literal precision (`invoke<"get">("/users")` where inference would widen), and intent documentation at critical boundaries (`parse<User>(raw)` where the schema — not the string — determines `T`). Everywhere else, let inference work — redundant arguments desynchronize from values during refactors.

**Runnable example** — when to write `<T>` (good vs bad, `tsc --strict`):

```typescript
// good — no inference site: explicit argument supplies T
function empty<T>(): T[] { return []; }
const nums = empty<number>(); // number[] — usable immediately
nums.push(1);
console.log(nums.length); // 1

// good — literal precision: explicit narrows what inference widens
function invoke<M extends string>(method: M, url: string): M { return method; }
const m1 = invoke("get", "/u"); // M = string (widened — exhaustiveness lost)
const m2 = invoke<"get">("get", "/u"); // M = "get" (pinned — switch stays exhaustive)
console.log(m1, m2); // get get

// bad — redundant argument rots when the value changes type
function echo<T>(x: T): T { return x; }
const a = echo<string>("hi"); // ok today...
// const b = echo<string>(42); // error TS2345 after refactor — argument lies
const c = echo(42); // fix — inference tracks the value: T = number
console.log(c.toFixed(0)); // 42

// good — boundary documentation: schema determines T, not the string
function parseAs<T>(text: string, decode: (raw: unknown) => T): T {
  return decode(JSON.parse(text));
}
const age = parseAs<number>("42", Number); // T pinned by decode's return
console.log(age.toFixed(1)); // 42.0
```

**Common confusion** — "explicit `<string>` and inferred `string` differ" — identical instantiations; explicit only *chooses* what inference would compute. "explicit arguments are checked against parameters" — yes: `echo<string>(42)` errors because `42` is not a `string` — the argument constrains the value, not the other way around. "`fetch<User>()` validates the response is a `User`" — no runtime validation; the argument only labels the compile-time contract — validate with a guard/schema (see [2.2. unknown the type-safe top type](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>)).

**Performance note** — explicit arguments *reduce* check cost: the solver skips inference and verifies assignability directly (O(1) sites instead of O(sites)). The saving is trivial per call but real across generated code (1000 `invoke<"get">` calls skip 1000 widening computations). No emit difference — `<"get">` and inferred `"get"` emit identically.

**Mentor note** — teach the three-situation rule as a checklist at the call site: "is there an argument flowing into `T`? did inference widen my literal? does the reader need the intent spelled out?" If none — delete the brackets. Exercise: widen `invoke("get", …)` then ask why the exhaustive switch stopped failing — fix with `<"get">` and watch the `never` sink re-arm. Lint: flag explicit arguments identical to the inferred hover — they are comments that compile.

### 3) **Inference failure modes** (reading the hover when `T` is not what you meant)

**Definition** — three fallbacks signal failed inference: `unknown` (no site constrained `T`), widened `string`/`number` (a literal flowed through a mutable site), and `never[]` (an empty array gave element inference nothing to generalize). Each has a distinct hover signature and a distinct fix — none requires `as`.

**What problem it solves / history** — silent fallbacks were the top generic support question for years: `const x = first([])` typed `undefined`, `useState()` typed `unknown`, and route helpers widened `"get"` to `string` — all compiled, all broke exhaustiveness or autocomplete downstream. Naming the three modes turned "generics feel random" into a diagnostic skill: read the hover, match the mode, apply the fix (explicit argument, `as const`, or a seed element).

**Modern guidance** — as of TypeScript 5.9 era, diagnose in order: hover shows `unknown` → add an inference site or explicit argument; hover shows widened `string` where you wrote `"get"` → pin with `as const` / explicit `<"get">` / literal constraint; hover shows `never[]` → seed the array or annotate `string[]`. Enable `strict` (especially `strictNullChecks` + `noImplicitAny`) so failures surface as errors at the generic boundary instead of `any` leaks downstream.

**Runnable example** — three modes, three fixes (good vs bad, `tsc --strict`):

```typescript
// mode 1 — unknown fallback: no site constrained T
function head<T>(xs: T[]): T | undefined { return xs[0]; }
const h = head([]); // T = never, h: undefined — seed or annotate
const h2 = head<string>([]); // fix — explicit: string | undefined
const h3 = head(["a"]); // fix — seed element: string | undefined
console.log(h2 ?? "empty", h3 ?? "empty"); // empty a

// mode 2 — widened literal: mutable site widens "get" to string
function methodOf<M extends string>(m: M): M { return m; }
const w = methodOf("get"); // M inferred "get" here (constrained site keeps literal)
let mut = "get";
const w2 = methodOf(mut); // M = string — widened at the SOURCE (let), not the generic
console.log(w, w2); // get get
const pinned = methodOf("get" as const); // fix — const-source keeps literal

// mode 3 — never[] trap: empty array infers element never
const xs: number[] = []; // fix — annotate instead of inferring from nothing
xs.push(1);
console.log(head(xs)?.toFixed(0)); // 1

// bad — silencing the signal with as instead of fixing the site
const forced = head([]) as string | undefined; // compiles, hides the empty-source bug
// fix — head<string>([]) or head(["seed"]): the TYPE now documents the intent
```

**Common confusion** — "`unknown` means the generic is broken" — `unknown` means *no evidence reached `T`* — the generic is honest; the call site starved it. "`as const` fixes every widening" — `as const` fixes the *source* (`let` → literal); it cannot narrow a genuinely `string`-typed variable — use an explicit argument or constraint there. "`never[]` is an error" — it is the correct inference from zero elements; annotate the array instead of blaming the generic.

**Performance note** — failure modes cost *developer* time, not checker time — `unknown`/`never` fallbacks check fastest (nothing to verify). The expensive mode is widen-then-narrow churn: inferring `string` then intersecting back to `"get" | "post"` at every call site re-checks the union per call — pin the literal once at the source and downstream checks collapse to O(1).

**Mentor note** — make a "hover reading" drill: show `unknown`, `string` (from `"get"`), and `never[]` hovers side by side and ask for mode + fix before compiling — builds the diagnostic reflex that replaces `as` with sites. Review gate: any `as` applied directly to a generic call result (`head([]) as string`) must justify why the site could not be fixed instead.
