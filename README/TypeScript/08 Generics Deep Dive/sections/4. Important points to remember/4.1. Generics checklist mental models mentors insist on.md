## 4.1. Generics checklist — mental models mentors insist on

Review a generic API by following the relationship from its inputs to its output, then examining the JavaScript that implements it. A type parameter describes a relationship; it supplies no runtime validator, stored value, retry policy or timer. Use these four questions after studying the domain's full explanations.

### 1) **What survives compilation and establishes runtime evidence?**

Find the runtime value or operation responsible for the result. A decoder callback can inspect data; writing parseText<User> cannot inspect it. A generic class uses its actual constructor, rather than a new runtime class for each type argument. Compare the [declaration and erasure examples](<../1. Generic Fundamentals/1.1. Type parameters declaration instantiation and erasure.md>) when this distinction is unclear.

Type-only edits can emit identical JavaScript, but changing a runtime argument from a string to a number changes the emitted expression. An emit comparison must hold the values constant to isolate the type change. Use ordinary tsc compilation to inspect emitted files; there is no tsc --emit switch. The [erasure owner](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) separates erased declarations from retained statements.

### 2) **Which choices are admitted, inferred or defaulted?**

A constraint states what choices the declaration accepts and what operations its body may use. It is neither runtime validation nor a promise that every transformation returns the supplied subtype. Ask why the API needs its bound, including domain restrictions beyond member access. Use [constraints](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) for the body and subtype obligations.

A default fills an omitted type argument when appropriate; it does not create a missing runtime value. Choose a default with a useful contract, rather than choosing any merely to suppress errors. If a source was already widened, an explicit literal argument cannot recover missing evidence. Consult [defaults](<../2. Constraints Defaults and Inference Control/2.2. Defaults and optional type parameters.md>) and [inference and NoInfer](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) for those separate decisions.

### 3) **Who selects the parameter and which value does it describe?**

A generic function allows fresh choices at calls. A particular container view can fix the type of its stored values while a method introduces a fresh result type. A generic call signature inside an interface can also be callable for several types; the interface keyword alone does not fix a single choice. Review [generic scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>) before moving a parameter mechanically.

Look for an output-only reader that lets the caller choose a type unrelated to storage. An assertion may make it compile while allowing a string to be requested as a number. Conversely, a configured generic container can legitimately support many operations over its fixed element type. Ask which relationship the implementation actually preserves.

### 4) **Does extraction or forwarding preserve the promised contract?**

An infer pattern computes a type from a matching shape; it does not inspect a runtime value. A tuple-rest wrapper can preserve required argument positions, while a bare any[] rest can hide missing arguments. Neither form automatically implements the behavior suggested by a name such as retry or debounce. Use [infer matching](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) and [actual composition and retry](<../3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>) for the full examples.

For recursive types, ask whether the declaration describes a shape or performs type-level computation, and what happens when a stopping policy is reached. A runtime cycle, a recursive declaration and a TS2589 failure are distinct observations; [recursive generics](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) demonstrates them separately.

Run this small review drill with TypeScript 7.0.2 and Node.js 20.20.2. Save it as review.ts, compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist review.ts`, then run `node dist/review.js`. Check each commented negative separately using the same flags with --noEmit instead of --outDir dist.

```typescript
function makeLookup<T>(values: readonly T[]): (index: number) => T | undefined {
  return index => values[index];
}
function forward<Args extends unknown[], Result>(fn: (...args: Args) => Result): (...args: Args) => Result {
  return (...args) => fn(...args);
}
const lookup = forward(makeLookup([10, 20]));
console.log(lookup(1), lookup(9));
// lookup("1"); // TS2345
// lookup(); // TS2554
const numbers: readonly number[] = [10, 20];
// const textLookup = makeLookup<string>(numbers); // TS2345

type Envelope<T = unknown> = { payload: T };
const incoming: Envelope = { payload: JSON.parse('"20"') as unknown };
// console.log(incoming.payload.toFixed(0)); // TS18046
if (typeof incoming.payload === "number") console.log(incoming.payload.toFixed(0));
else console.log("numeric payload rejected");

type ElementOf<T> = T extends readonly (infer Item)[] ? Item : never;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Stored = Expect<Equal<ReturnType<typeof lookup>, number | undefined>>;
type Extracted = Expect<Equal<ElementOf<readonly [1, 2]>, 1 | 2>>;
// const missing: Envelope = {}; // TS2741
// type Unsupported = Expect<Equal<ElementOf<readonly [1, 2]>, number>>; // TS2344
```

The output is `20 undefined`, then `numeric payload rejected`. The closure stores the supplied array reference and lookup preserves possible absence. The wrapper forwards its required numeric index. Envelope's default limits unchecked use of the parsed value; it does not replace that string with a number. The two live type probes check the return contract and readonly tuple extraction. No timer or validator is implemented by the generic parameters themselves.

### 5) **Common confusion**

Fewer written type arguments, casts or diagnostics do not by themselves prove a better API. An any default can remove a diagnostic by removing protection. An explicit unknown result may preserve the need for a real check. Likewise, a helper can have excellent tuple inference while its body fails to perform its advertised operation. Review both the accepted calls and observed behavior.

### 6) **Performance note**

Type parameters, aliases and probes erase; the example retains a closure, array indexing, function calls and a runtime typeof branch. No runtime work arises directly from choosing a default or tuple label. No universal checking-cost formula or cache benefit follows from these review questions. Measure an actual problem through [compiler diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before recommending a performance rewrite.

### 7) **Mentor note**

Ask the learner to explain why lookup(9) can be undefined, why an explicit string argument cannot reinterpret numbers, and which line rejects the parsed string. A good answer follows evidence rather than naming syntax alone.

As an exercise, create a checkedLookup wrapper that requires an integer index and a present element, returning T or throwing RangeError. Keep makeLookup's existing contract. A solution reads the result once, rejects a noninteger or undefined result, and returns the narrowed value. For these number inputs, index 1 returns 20, while 9 and 0.5 throw. Explain that this policy also rejects an intentionally stored undefined value; supporting that case requires a different presence contract.
