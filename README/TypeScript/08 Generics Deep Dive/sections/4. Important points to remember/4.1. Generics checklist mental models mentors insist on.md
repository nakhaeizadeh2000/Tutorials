## 4.1. Generics checklist — mental models mentors insist on

### 1) **Parameters erase — contracts do not leak to runtime** (prove with emit before reaching for runtime checks)

**Definition** — every `<T>` in this domain vanishes at emit: `Box<string>`, `parse<User>`, `debounce<T>` all run as unparameterized JavaScript. The checklist habit is proving it once per generic (`tsc --emit`, diff two instantiations) instead of assuming reified behavior and branching on `T` at runtime.

**What problem it solves / history** — runtime-branch-on-`T` bugs (`typeof T`, `instanceof Box<string>`) compiled in editors without red squiggles (the error appears only at `tsc`) and shipped as `undefined` behavior — caught in QA, not in the IDE. The emit-proof habit moves the lesson earlier: developers who have *seen* identical `.js` for two instantiations never write the runtime branch again.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), pair every generic with its runtime half explicitly: erased `T` + value tag (`kind`), schema function (`decode`), or discriminant — never bare `T` at runtime. See [1.1. Type parameters and erasure](<../1. Generic Fundamentals/1.1. Type parameters declaration instantiation and erasure.md>).

**Runnable example** — emit proof plus value-side tag (good vs bad, `tsc --strict`):

```typescript
// good — runtime half travels as a value; T stays compile-time
function decode<T>(text: string, run: (raw: unknown) => T): T {
  return run(JSON.parse(text));
}
console.log(decode("7", Number).toFixed(0)); // 7 — Number() is the runtime half of T = number

// bad — branching on the erased parameter instead of a value
function kindOfBad<T>(x: T): string {
  // return typeof T; // error TS2693 — T only refers to a type
  return typeof x; // fix — inspect the value
}
console.log(kindOfBad("hi"), kindOfBad(7)); // string number
```

**Common confusion** — "emit proof is a one-time trick" — it is a per-generic review step: any generic whose author cannot show identical emit for two instantiations is hiding a runtime assumption. See [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>).

**Performance note** — zero emit delta per instantiation — the checklist's performance content is check-time: each instantiation verifies separately, so keep generic bodies small and instantiations cached under named aliases.

**Mentor note** — run the emit diff live in reviews for first-time generic authors — one `diff` ends the runtime-`T` debate permanently. Gate: any `typeof T` / `instanceof T<U>` in a PR must be rewritten to value inspection before merge.

Type erasure what survives compilation.md>); type/value split → [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. ### 2) **Constrain minimally, default generously** (the body needs little; callers appreciate the fallback)

**Definition** — constraints answer "what does the *body* touch?" (one member, not the world); defaults answer "what do *most callers* want?" (the 80% instantiation). Minimal bounds admit primitives and edge shapes; generous defaults silence the common reference. Both live on the same parameter without conflict (`T extends { length: number } = string`).

**What problem it solves / history** — maximal-constraint/minimal-default APIs (`T extends object`, no default) taxed every call site twice: valid primitive callers rejected, common references bracketed — and each rejection was "fixed" with `as`, spreading laundering outward. The minimal/generous pair reverses both taxes at the declaration, once.

**Modern guidance** — as of TypeScript 5.9 era, audit each parameter with two questions: "which member does the body read?" (that member *is* the constraint) and "which argument repeats most?" (that argument *is* the default). If no member is read, drop the constraint; if no majority exists, drop the default. See [2.1. Constraints](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) + [2.2. Defaults](<../2. Constraints Defaults and Inference Control/2.2. Defaults and optional type parameters.md>).

**Runnable example** — minimal bound admits, generous default silences (good vs bad, `tsc --strict`):

```typescript
// good — body reads .length only; callers omit the common string case
function show<T extends { length: number } = string>(x?: T): number {
  return (x ?? "hi").length;
}
console.log(show(), show("hello"), show([1, 2, 3])); // 2 5 3

// bad — object bound plus no default: rejects strings, taxes every reference
function showBad<T extends object>(x: T & { length: number }): number { return x.length; }
// showBad("hi"); // error TS2345 — valid caller rejected; no default to omit either
// fix — show: { length: number } bound admits strings; = string default silences them
```

**Common confusion** — "minimal constraints are loose" — they are *precise*: the exact member used, nothing more — looseness is `any`, precision is the touched member. "generous defaults hide information" — hovers display the instantiated default, so readers see it — unwritten is not hidden. See [2.2. unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) for the honest `= unknown` envelope default.

**Performance note** — minimal constraints shrink solver search (fewer members per candidate); shared default instantiations cache once — both directions of the pair *reduce* check cost while admitting more callers.

**Mentor note** — stamp PRs with the two questions ("body reads what? callers repeat what?") — unanswered means unreviewed. Exercise: convert one `extends object` + no-default API and count deleted `as` casts plus deleted brackets — the pair's ROI in two numbers.

### 3) **Scope follows the declaration** (per-call function vs per-value container — pick before writing `<T>`)

**Definition** — the lifetime question ("when is `T` chosen?") precedes the syntax: per *call* → generic function; per *value* → generic interface/class; per *reference* → generic alias. Correct scope deletes annotations (functions infer) or deletes casts (containers remember); wrong scope adds one of them back at every use.

**What problem it solves / history** — scope mismatches were the most expensive generic bugs because they compounded: `at<T>` guessing corrupted every read (casts everywhere), `Runner<T>` containers taxed every call (annotations everywhere) — and both looked locally reasonable until the usage count multiplied the workaround. Asking the lifetime question first prevents the multiplication.

**Modern guidance** — as of TypeScript 5.9 era, write the answer in the declaration's doc comment (`/** T fixed per value at construction. */`) so the next author preserves it. Static factories bridge scopes (`of<U>(x: U): Store<U>` — per-call inference producing per-value storage). See [1.3. Generic scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>).

**Runnable example** — scope prevents workarounds (good vs bad, `tsc --strict`):

```typescript
// good — function scope: no annotation, fresh per call
function first<T>(xs: T[]): T | undefined { return xs[0]; }
console.log(first(["a"])?.toUpperCase(), first([1])?.toFixed(0)); // A 1

// good — container scope: no cast, fixed per value
class Slot<T> { constructor(public value: T) {} }
const slot = new Slot("hi");
console.log(slot.value.toUpperCase()); // HI — remembered, not re-guessed

// bad — scopes crossed: generic method guesses, generic runner taxes
class GuessBox {
  private v: unknown;
  set<T>(x: T): void { this.v = x; }
  get<T>(): T | undefined { return this.v as T | undefined; } // reader guesses
}
const gb = new GuessBox();
gb.set("hi");
console.log(gb.get<number>()?.toFixed(1)); // compiles via as — lies at runtime
// fix — Slot<T>: hoist to the container; first<T>: keep transforms per call
```

**Common confusion** — "one scope covers both" — a parameter has exactly one lifetime; mixed needs (per-value storage *plus* per-call flexibility) compose (`Bag<T>` + method `<U>`), never collapse into one parameter. See [3.1. Static members and generics](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>) for the `static`-side exclusion.

**Performance note** — scope choice is check-cost-neutral at small scale; at scale, per-value caching (one instantiation per container type) beats per-call re-solving for hot stored types — another reason stores belong on containers.

**Mentor note** — the one-sentence test ("when is `T` chosen?") belongs on a review stamp — no answer, no merge. Exercise: fix `GuessBox` and `Runner` in opposite directions (hoist one, flatten the other) — proves scope is a choice, not a default.

### 4) **Extract with `infer`, compose with tuples** (name the piece, thread it through)

**Definition** — `infer` names what the checker solved (element, return, payload, head); tuples thread named pieces through wrappers (capture, concat, pipe) without flattening. Together they replace per-shape helpers and `any[]` forwarding: extract once with a pattern, compose everywhere with a tuple.

**What problem it solves / history** — pre-pattern code hand-rolled both halves: `StrElem`/`NumElem` per wrapper plus `any[]` forwarding per helper — N×M helpers for N wrappers and M forwarders. Two patterns (`Array<infer U>`, `<T extends unknown[]>`) replaced the matrix: extractors compose with forwarders (`timed<Elementwise<T>>` reads naturally) because both preserve structure instead of flattening it.

**Modern guidance** — as of TypeScript 5.9 era, memorize four `infer` patterns (return, element, head, payload) and one forwarding shape (`<T extends unknown[]>(...args: T) => R`) — the pair covers stdlib reading plus wrapper authoring. Prefer stdlib names at call sites (`ReturnType`, `Awaited`); write patterns only for project-specific wrappers. See [2.3. infer](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) + [3.3. Variadic tuples](<../3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>).

**Runnable example** — extract then forward, fully checked (good vs bad, `tsc --strict`):

```typescript
// good — ElemOf extracts, timed forwards: composition stays transparent
type ElemOf<T> = T extends Array<infer U> ? U : never;
function timed<T extends unknown[], R>(fn: (...args: T) => R): (...args: T) => R {
  return (...args) => fn(...args);
}
const first = timed(<T>(xs: T[]): T | undefined => xs[0]);
const f = first([["a"], ["b"]]); // string[] | undefined — ElemOf not even needed here
console.log(f?.[0]?.toUpperCase() ?? "empty"); // A
type E = ElemOf<string[]>; // string — extraction when the wrapper (not the call) needs it
const e: E = "hi";
console.log(e.toUpperCase()); // HI

// bad — any forwarding plus per-shape extraction: opacity compounded
function timedBad<R>(fn: (...args: any[]) => R): (...args: any[]) => R {
  return (...args) => fn(...args);
}
// fix — timed<T extends unknown[], R> + ElemOf<T>: structure in, structure out
```

**Common confusion** — "`infer` and tuples solve the same problem" — `infer` *decomposes* (wrapper → piece), tuples *compose* (pieces → signature) — opposite directions, used together. "stdlib covers everything, patterns are academic" — project wrappers (telemetry, retry, validation) need the forwarding shape regardless of stdlib coverage. Full catalog lives in [09 Utility Types](<../09 Utility Types and Type Transformations/README.md>).

**Performance note** — extraction caches per instantiation; forwarding checks per call site — composed cost is additive, not multiplicative, as long as each layer preserves structure (no `any` forcing downstream re-verification).

**Mentor note** — the composition demo (`timed` wrapping a generic `first`) is the capstone exercise: students who predict the hover (`<T>(xs: T[]) => T | undefined` preserved) have internalized both halves. Review gate: new wrappers must forward tuples; new extractors must use `infer` — no per-shape helpers, no `any[]` rest.
