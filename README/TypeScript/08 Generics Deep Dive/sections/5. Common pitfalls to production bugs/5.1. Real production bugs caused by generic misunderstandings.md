## 5.1. Real production bugs caused by generic misunderstandings

### 1) **`any` fallback from failed inference reached a price calculation** (untyped fetch generic returned `any`; arithmetic silently produced `NaN`)

**Definition** — a `fetchJson<T>(url: string): Promise<T>` helper without inference site or default fell back per call: most callers annotated (`fetchJson<Price>`) but one passed the result straight into arithmetic unannotated — `T` resolved `unknown`, a local `as Price` silenced it, and a malformed payload turned `total.toFixed(2)` into a `TypeError` behind an `any`-shaped hole that `strict` never saw because the cast pre-empted inference.

**What problem it solves / history** — the incident review found three compounding choices: no constraint (body assumed `.items`), no default (omission meant `unknown`), and a caller-side `as` (hid the fallback instead of fixing the site). Any one of this domain's disciplines — `T extends { items: unknown[] }`, `= unknown` default forcing narrowing, or an explicit argument — would have moved the failure to compile time.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), fetch-shaped generics always carry three guards: a constraint bounding the body (`T extends object`), an `unknown`-ish default making omission narrowable, and a ban on `as` at call sites (explicit argument or narrowing instead). See [1.2. Inference failure modes](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) + [2.2. unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>).

**Runnable example** — the bug and the three guards (good vs bad, `tsc --strict`):

```typescript
export {}; // module marker for top-level await in this runnable snippet
// bad — unannotated call plus as: fallback hidden, malformed payload crashes
async function fetchJson<T>(url: string): Promise<T> {
  return JSON.parse(await Promise.resolve('{"total":"oops"}')) as T;
}
async function totalBad(): Promise<string> {
  const data = (await fetchJson("u")) as { total: number }; // as hides unknown fallback
  return data.total.toFixed(2); // compiles — crashes: "oops".toFixed is not a function
}

// good — constraint + unknown default + narrowing instead of as
async function fetchJsonSafe<T extends object = Record<string, unknown>>(url: string): Promise<T> {
  void url;
  return JSON.parse('{"total":"oops"}') as T;
}
async function totalGood(): Promise<string> {
  const data = await fetchJsonSafe<{ total: unknown }>("u"); // explicit: no fallback
  return typeof data.total === "number" ? data.total.toFixed(2) : "invalid"; // narrowed
}
console.log(await totalGood()); // invalid — handled, not crashed
```

**Common confusion** — "`as T` inside the helper validates" — `as` asserts without checking; only a schema/guard validates — the helper's cast is contained plumbing, never proof. "one `as` at the call site is harmless" — it disabled exactly the fallback signal (`unknown`) that would have forced the `typeof` check. See [3.3. Unsound spots](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>).

**Performance note** — the `typeof` narrow costs one branch per boundary crossing — negligible against the network call it guards. The incident's cost was downtime plus a refund run — orders of magnitude above any check-time saving from skipping the annotation.

**Mentor note** — post-mortem drill: replay the unannotated call, hover the `unknown`, and ask "what did `as` cost us here?" — the answer (a compile-time error traded for a production crash) generalizes to every `as`-on-generic-call in the codebase. Gate: `as` applied to a generic call result requires a linked justification comment.

Inference from arguments and explicit type arguments.md>); unknown → [2.2. unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>); any infection → [2.1. any](<../../../03 Basic Types and Annotations/sections/2. ### 2) **Over-constrained `T extends object` rejected valid primitive IDs** (checkout broke for numeric SKUs the constraint never allowed)

**Definition** — a `normalize<T extends object>(id: T): string` helper written for object-shaped IDs rejected the numeric SKU path added a quarter later — `normalize(42)` errored TS2345, the checkout team "fixed" it with `normalize(42 as unknown as object)`, and the laundering hid a `toString` vs `toFixed` formatting divergence that charged one cent per unit wrong for six hours.

**What problem it solves / history** — the constraint described the *first* caller's shape, not the *body's* need (string conversion — primitives qualify). Minimal-bound discipline (`T extends string | number` or unconstrained + `String(id)`) would have admitted SKUs without laundering; the incident instead paid the over-constraint tax twice (rejected caller, then hidden formatting bug).

**Modern guidance** — as of TypeScript 5.9 era, constrain to the member used (`String(x)` needs nothing — leave `T` unconstrained; `.length` needs `{ length: number }`). Audit every `extends object` for primitive callers before release. See [2.1. Over-constraining cost](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>).

**Runnable example** — bound admits SKUs without laundering (good vs bad, `tsc --strict`):

```typescript
// bad — object bound rejects the numeric SKU the body could handle
function normBad<T extends object>(id: T): string { return String(id); }
// normBad(42); // error TS2345 — number not assignable to object
// const sku = normBad(42 as unknown as object); // laundering hides the rejection (and the review signal)

// good — unconstrained: String() accepts everything, no caller rejected
function norm<T>(id: T): string { return String(id); }
console.log(norm(42), norm("u-1")); // 42 u-1 — primitives welcome, no casts
```

**Common confusion** — "widening the constraint weakens safety" — `String(id)` is total over `T` — the bound added rejections without adding checks. "the `as unknown as` was temporary" — laundering at a generic boundary is never temporary; it disables the exact check the next SKU-shaped caller needs. See [1.1. Structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>).

**Performance note** — zero runtime delta (`String()` either way); the cost was all correctness — rejected valid input, then hid valid-but-divergent formatting behind the cast.

**Mentor note** — grep `extends object` quarterly and demand one primitive-caller test per instance — the SKU class of bug dies to a single `normalize(42)` assertion. Exercise: write the failing call *before* the helper (TDD the bound) so the constraint is evidence-driven, not assumed.

Constraints extends narrowing inside the body.md>); any laundering → [2.1. any](<../../../03 Basic Types and Annotations/sections/2. ### 3) **Missing `as const` widened a literal through a generic boundary** (route table lost `"get"` precision; exhaustive switch stopped failing)

**Definition** — a `register<T extends string>(method: T, path: string)` helper inferred `T = string` from a `let`-sourced `"get"` (widened at the mutable source, not the generic) — the route table typed `string`, the exhaustive `switch (route.method)` with its `never` sink went silent, and a `"delete"` handler shipped without auth because no branch was required to exist.

**What problem it solves / history** — widening-at-source is invisible at the generic boundary (the hover shows `string`, honestly — the damage happened earlier at `let`). The fix pair — `as const` at the source plus literal-preserving `M` returns (see 2.1 promise 2) — restores the chain: source keeps `"get"`, generic preserves `"get"`, switch re-arms.

**Modern guidance** — as of TypeScript 5.9 era, declare route/method/event tables `as const`, type registration helpers `<M extends string>(m: M): M` (return the parameter), and keep a `never`-sink switch over the table — three links, each verified independently. See [1.2. Inference failure modes](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) + [3.2. Exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>).

**Runnable example** — source precision restored end to end (good vs bad, `tsc --strict`):

```typescript
// bad — let widens before the generic ever sees the literal
let mBad = "get";
function reg<M extends string>(m: M): M { return m; }
const rBad = reg(mBad); // M = string — switch below cannot exhaust
function handleBad(m: string): string { return m; } // widened: no literal union to exhaust

// good — const source plus M-preserving helper keeps "get"
const mGood = "get" as const;
const rGood = reg(mGood); // M = "get"
function handle(m: "get" | "post"): string { return m === "get" ? "G" : "P"; }
console.log(handle(rGood), handleBad(rBad)); // G get
```

**Common confusion** — "the generic widened my literal" — the `let` widened it; the generic faithfully inferred `string` from a `string` — blame the source, fix the source. "`as const` everywhere fixes routing" — `as const` on genuinely dynamic input (user input, parsed JSON) lies — pin with explicit `<"get">` or validate-then-narrow there instead.

**Performance note** — literal preservation costs one instantiation per literal (cached, tiny) and saves exhaustive-switch verification downstream — the auth-missing-handler class of bug costs incident response, not check time.

**Mentor note** — trace the widening backwards from the silent switch (hover `string` → hover the `let` → add `as const` → watch `never` re-arm) as a live debugging narrative — students learn to read hovers upstream, not patch downstream. Gate: route tables without `as const` or explicit literal types fail review.

**Cross-links** — inference/widening → [1.2. Inference](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>); literals → [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>); exhaustiveness → [3.2. Exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>).

### 4) **Unbounded recursive type hit TS2589 in CI only** (deep config generic compiled locally but timed out the build checker)

**Definition** — an unbounded `DeepFreeze<T>` over the app config compiled against the small local fixture (depth 4) but the monorepo's generated schema (depth 12, 800 keys) blew the instantiation budget in CI — `TS2589` on main, green on the PR's narrowed `include`, forty minutes of build-queue forensics to connect the two.

**What problem it solves / history** — the utility lacked a depth cap and a large-input test — both standard since this domain's budget rule (see [3.2. Depth budget](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>)). Capping (`Seen`-tuple counter defaulting to 3–5) plus a CI fixture pinning the largest real schema turned a queue-blocking mystery into a local error with a documented repair.

**Modern guidance** — as of TypeScript 5.9 era, ship every recursive utility with a cap and test it against the largest real input in the repo — not the unit fixture. Prefer scoping (freeze the owned subtree, reference pre-computed aliases for generated ones) over raising budgets. See [3.2. Recursive generics](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) + [19 Performance](<../../../19 Performance Project References and Scaling/README.md>).

**Runnable example** — capped utility plus scoped application (good vs bad, `tsc --strict`):

```typescript
// good — capped: overflow degrades to T instead of timing out the build
type Capped<T, D extends number = 3, Seen extends 0[] = []> = Seen["length"] extends D
  ? T
  : T extends object ? { readonly [K in keyof T]: Capped<T[K], D, [...Seen, 0]> } : T;
type Owned = { db: { host: string } };
const o: Capped<Owned> = { db: { host: "h" } };
console.log(o.db.host.toUpperCase()); // H

// bad — unbounded over an unbounded input (kept shallow here so the doc compiles;
// the same shape over the 800-key generated schema tripped TS2589 in CI)
// type DeepAny<T> = T extends object ? { [K in keyof T]: DeepAny<T[K]> } : T;
// fix — Capped (counter) for libraries; scope-narrowing (freeze owned subtree only) for apps
```

**Common confusion** — "CI-only means flaky infra" — depth failures are input-dependent (largest schema in the program), and CI builds the whole program while local `include` narrows it — deterministic, not flaky. "capping loses correctness" — overflow falls back to the *unfrozen* (still sound) type — strictly better than a timed-out build shipping nothing.

**Performance note** — the cap bounds check memory linearly (D levels × keys) — the incident's unbounded run consumed gigabytes before aborting; capped runs stay flat. Measure with `tsc --extendedDiagnostics` on the largest schema after any recursive-utility change.

**Mentor note** — pin the largest-schema fixture in CI *for* recursive utilities (not just the feature PRs) — the fixture is the budget's test. Post-mortem action template: cap + fixture + doc comment stating D and overflow behavior — three lines preventing the next queue outage.
