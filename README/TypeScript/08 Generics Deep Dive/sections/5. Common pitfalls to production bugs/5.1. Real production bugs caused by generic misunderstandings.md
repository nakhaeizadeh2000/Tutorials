## 5.1. Real production bugs caused by generic misunderstandings

These are minimal local reproductions of failure patterns, not reports of verified external incidents. Each separates the compiler's contract from the JavaScript operation that actually runs. Follow the linked owners for the full generic mechanics.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename, compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Check each commented negative separately with those flags and --noEmit instead of --outDir dist.

### 1) **An explicit result argument bypassed the missing validation**

A helper that reads JSON and asserts T lets its caller choose a result contract without checking the payload. Calling it without useful inference evidence can expose unknown; explicitly selecting a result type hides that warning without adding validation. Neither an object constraint nor a default fixes the body.

Save as boundary.ts.

```typescript
function readUnchecked<T>(text: string): T { return JSON.parse(text) as T; }
const noEvidence = readUnchecked('{"total":"oops"}');
// console.log(noEvidence.total); // TS18046
function readConstrained<T extends object = Record<string, unknown>>(text: string): T {
  return JSON.parse(text) as T;
}
const claimed = readConstrained<{ total: number }>('{"total":"oops"}');
try { console.log(claimed.total.toFixed(2)); }
catch (error) { console.log(error instanceof TypeError ? "explicit contract: TypeError" : "unexpected error"); }

function totalText(text: string): string {
  const raw: unknown = JSON.parse(text);
  if (typeof raw !== "object" || raw === null || !("total" in raw)) return "invalid";
  const total = raw.total;
  return typeof total === "number" && Number.isFinite(total) ? total.toFixed(2) : "invalid";
}
console.log(totalText('{"total":"oops"}'), totalText('{"total":12.5}'), totalText("null"));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Fallback = Expect<Equal<typeof noEvidence, unknown>>;
```

The output is `explicit contract: TypeError`, then `invalid 12.50 invalid`. The selected type satisfies the helper's constraint and compiles, but the field is still a string. The repair checks the actual value before formatting. Invalid JSON syntax still throws from JSON.parse; this example checks the parsed shape and numeric field rather than implementing a complete parsing-error policy.

The static fallback is unknown in this example, not an automatic any fallback. See [inference and decoder evidence](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) for the honest generic callback relationship, and [unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) for boundary checks.

### 2) **An accidental object bound concealed the identifier contract**

If an identifier API accepts strings and numbers, an object bound rejects legitimate inputs. Removing that bound does not mean every JavaScript value should become a valid identifier. Unrestricted string conversion can collapse unrelated inputs to the same representation. State the intended domain independently of which operations the body happens to use.

Save as identifiers.ts.

```typescript
function objectOnly<T extends object>(id: T): string { return String(id); }
// objectOnly(42); // TS2345
function normalizeId(id: string | number): string { return String(id); }
console.log(normalizeId(42), normalizeId("u-1"));
// normalizeId({ id: 42 }); // TS2345
function unrestricted(id: unknown): string { return String(id); }
console.log(unrestricted({}), unrestricted("[object Object]"));
console.log(unrestricted({}) === unrestricted("[object Object]"));
```

The output is `42 u-1`, `[object Object] [object Object]`, then `true`. A conversion-only return type does not need a generic parameter. The narrower input domain rejects the accidental object without asserting a primitive is an object. A different API can legitimately require object inputs; its domain, operations and desired guarantees determine that choice. Nor is String a universal guarantee against exceptions from arbitrary user-defined coercion hooks.

Use [constraints and body obligations](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) to reason about the bound. Do not repair a rejected legitimate input with an assertion that disguises the mismatch.

### 3) **The source widened, but the real exhaustiveness check still complained**

A mutable string source can lose literal precision before a generic receives it. A switch that sends the remaining string to a never sink reports an error; it does not silently become exhaustive. A permissive fallback can accept everything, but that is a different implementation with a different contract.

Save as methods.ts.

```typescript
function register<M extends string>(method: M): M { return method; }
let mutableMethod = "get";
const widened = register(mutableMethod);
const fixedMethod = "get";
const preserved = register(fixedMethod);
function unexpected(value: never): never { throw new Error(`unexpected method: ${String(value)}`); }
function openMethod(method: string): string {
  switch (method) {
    case "get": return "G";
    case "post": return "P";
    default:
      // return unexpected(method); // TS2345: method remains string
      return "unsupported";
  }
}
const routes = [{ method: "get", path: "/" }, { method: "post", path: "/save" }] as const;
type Method = typeof routes[number]["method"];
function handle(method: Method): string {
  switch (method) {
    case "get": return "G";
    case "post": return "P";
    default: return unexpected(method);
  }
}
console.log(handle(preserved), openMethod(widened), routes.map(route => handle(route.method)).join(","));
// handle(widened); // TS2345
// register<"get">(widened); // TS2345: explicit arguments cannot reinterpret string evidence
// const recovered = widened as const; // TS1355: variable references are not literal expressions
function handleInput(value: unknown): string {
  return value === "get" || value === "post" ? handle(value) : "invalid method";
}
console.log(handleInput("get"), handleInput("delete"));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Wide = Expect<Equal<typeof widened, string>>;
type Precise = Expect<Equal<typeof preserved, "get">>;
```

The output is `G G G,P`, then `G invalid method`. The const string binding already preserves get without as const. The table uses a const assertion on its literal expression; that is different from applying it later to a variable. The [primary const-assertion caveats](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html#caveats-1) describe the permitted expressions. Runtime input needs a real check before entering handle.

A literal-returning registration helper does not itself create authentication or complete routing behavior. Use [source inference](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) and [exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) to inspect those independent guarantees.

### 4) **A cap changed the transform's promise**

A recursive mapped shape alone does not establish that a compiler will exceed its limits. Reproduce the actual failure before changing a transform. A depth cap can deliberately stop transforming, but its unchanged remainder may still be mutable. Calling that remainder deeply frozen would overstate the resulting contract.

Save as stopping.ts. The limited mapped example below concerns ordinary record-shaped data; function and built-in-container policies need the [full transform owner](<../../../09 Utility Types and Type Transformations/README.md>).

```typescript
type Unwrap<T> = T extends PromiseLike<infer Item> ? Unwrap<Item> : T;
type Loop = PromiseLike<Loop>;
// type Runaway = Unwrap<Loop>; // TS2589

type Depth = 0 | 1 | 2;
type Previous = [0, 0, 1];
type Capped<T, D extends Depth = 1> = D extends 0 ? T
  : T extends object ? { readonly [K in keyof T]: Capped<T[K], Previous[D]> } : T;
type Config = { db: { host: string } };
const shallow: Capped<Config> = { db: { host: "initial" } };
shallow.db.host = "cap stopped"; // Accepted: the nested object is the unchanged remainder.
// shallow.db = { host: "replacement" }; // TS2540
const deeper: Capped<Config, 2> = { db: { host: "h" } };
// deeper.db.host = "changed"; // TS2540
// type Unsupported = Capped<Config, number>; // TS2344
console.log(shallow.db.host, Object.isFrozen(shallow));
console.log(deeper.db.host);
```

The output is `cap stopped false`, then `h`. Activating Runaway produces TS2589 on this toolchain; the positive example does not pretend that a small mapped config has the same failure. Neither depth choice freezes a runtime object. The closed literal-depth set makes supported stopping choices explicit instead of accepting a broad number that can silently stop at the wrong level.

The [recursive generics lesson](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) owns shape versus computation and finite cap results. [Instantiation budgets](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) owns measurement and budget investigation. No universal safe depth, largest-schema threshold or memory formula follows from these fixtures.

### 5) **Common confusion**

Explicit arguments choose a static contract; they do not prove JSON obeys it. A constraint can intentionally describe a domain, even when the body could mechanically accept more. A widened source can fail a never check, and a const binding can preserve a string literal without a const assertion. These are different causes and need different repairs.

A cap can make a partial transformation usable while changing the guarantee at its boundary. The unchanged remainder is not evidence that every intended deep-readonly property is protected. Document that policy as part of the API instead of treating compilation success as the entire result.

### 6) **Performance note**

JSON parsing, field checks, conversions and actual calls remain at runtime; type arguments and mapped types erase. No network latency, external incident cost, checking speed or memory consumption was measured here. A cap's checking effect depends on the input and computation shape; changing its contract is observable even without a performance measurement. Compare genuine problematic projects with diagnostics and traces before claiming a speed improvement.

### 7) **Mentor note**

Ask which observation disproves each proposed repair: a malformed payload through an explicit result argument, a rejected numeric identifier, the residual string at the never sink, or a writable field below a cap. Require the learner to identify both the evidence and the owner of the underlying mechanism.

For practice, extend Method's table with delete before editing handle. Compilation must reject the remaining method at unexpected. Then add an explicit delete branch and extend handleInput's actual value check. A complete solution preserves get/post behavior, returns D for delete, and still rejects an unrelated value such as patch. Merely asserting the dynamic input is Method does not meet the exercise.
