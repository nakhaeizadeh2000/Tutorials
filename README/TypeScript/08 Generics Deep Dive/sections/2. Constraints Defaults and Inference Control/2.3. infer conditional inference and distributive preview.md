## 2.3. infer — conditional inference and distributive preview

Infer names a type captured by matching a conditional type's pattern. It does not read a runtime wrapper or produce a value. Choose the pattern and the non-match result from the contract you want: array elements, a guaranteed tuple head and an awaited result are related questions with different boundaries.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent TypeScript fence under its filename and compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`. Run `node dist/FILE.js`. Activate commented negatives individually and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **What infer extracts**

In `T extends ReadonlyArray<infer Element> ? Element : never`, the checker tries to match T against an array pattern and captures its element type. The captured name is available in the true branch. A readonly-array pattern accepts both mutable arrays and const tuples; a mutable Array pattern does not match every readonly input.

Save as `extraction.ts`.

```typescript
type ElementOf<T> = T extends ReadonlyArray<infer Element> ? Element : never;
type MutableElement<T> = T extends Array<infer Element> ? Element : never;
type ReturnOf<F> = F extends (...args: never[]) => infer Result ? Result : never;
type ReturnWithAny<F> = F extends (...args: any[]) => infer Result ? Result : never;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ArrayElement = Expect<Equal<ElementOf<string[]>, string>>;
type TupleElement = Expect<Equal<ElementOf<readonly ["a", 1]>, "a" | 1>>;
type ReadonlyMismatch = Expect<Equal<MutableElement<readonly ["a", 1]>, never>>;
type NeverArgsReturn = Expect<Equal<ReturnOf<(text: string) => number>, number>>;
type AnyArgsReturn = Expect<Equal<ReturnWithAny<(text: string) => number>, number>>;
type NonFunction = Expect<Equal<ReturnOf<string>, never>>;
const element: ElementOf<readonly string[]> = "hello";
const result: ReturnOf<(text: string) => number> = element.length;
console.log(element.toUpperCase(), result);
// type Outside = infer Result; // TS1338: infer must be in a conditional's extends clause
// type WrongScope<T> = T extends ReadonlyArray<infer E> ? E : E; // TS2304: E not in false-branch scope
// type InvalidBuiltin = ReturnType<string>; // TS2344: the standard utility rejects this input
```

The output is `HELLO 5`. Six live assertions establish element matching, non-matching readonly inputs and function return extraction. Both ignored-argument patterns capture number here; using any in the pattern does not automatically turn that result into any. Neither pattern authorizes calling a real function with arbitrary arguments. [Callable constraints](<./2.1. Constraints extends narrowing inside the body.md>) demonstrates that separate runtime error.

The [primary conditional-type explanation](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html#inferring-within-conditional-types) introduces this matching mechanism. Our ReturnOf deliberately returns never for a non-function; the standard ReturnType instead constrains its input and reports an error. Prefer a standard utility when its contract fits, and define a custom pattern when you need a different match or fallback. Full utility implementation belongs to [infer pipelines](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>).

### 2) **Infer positions and their boundaries**

A tuple pattern with a required first element asks whether that element is guaranteed by the type. An array element lookup asks a different question. An unbounded array may be empty, and an optional tuple head can be absent, so neither matches a required-head pattern just because some runtime examples contain a first value.

Save as `tuples.ts`.

```typescript
type Head<T> = T extends readonly [infer First, ...unknown[]] ? First : never;
type Tail<T> = T extends readonly [unknown, ...infer Rest] ? Readonly<Rest> : never;
type IndexedFirst<T extends readonly unknown[]> = T[0];
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Guaranteed = Expect<Equal<Head<readonly ["a", "b", 1]>, "a">>;
type Rest = Expect<Equal<Tail<readonly ["a", "b", 1]>, readonly ["b", 1]>>;
type EmptyHead = Expect<Equal<Head<[]>, never>>;
type EmptyIndex = Expect<Equal<IndexedFirst<[]>, undefined>>;
type OptionalHead = Expect<Equal<Head<[string?]>, never>>;
type OptionalIndex = Expect<Equal<IndexedFirst<[string?]>, string | undefined>>;
type ArrayHead = Expect<Equal<Head<string[]>, never>>;
// type DirectOutOfBounds = [][0]; // TS2493: direct indexing of this known empty tuple is invalid
// const manufactured: Head<[]> = undefined; // TS2322: no normal undefined inhabitant of never

function first<T>(values: readonly T[]): T | undefined { return values[0]; }
console.log(first(["a", "b"] as const), first<string>([]));
const tail: Tail<readonly ["a", "b", 1]> = ["b", 1];
console.log(tail.join(","));
// tail[0] = "b"; // TS2540: this helper deliberately publishes a readonly tail
```

The output is `a undefined`, then `b,1`. Generic IndexedFirst<[]> computes undefined without an error; it is not the same operation as directly writing `[][0]` in a type expression. Head<[]> returns never because its pattern does not match. Casting undefined to never would only conceal that mismatch and still produce undefined at runtime; it would establish no valid head.

The actual first function has a runtime absence contract and returns undefined for the empty fixture. The type helpers do not execute that read. Tail explicitly applies Readonly to the captured remainder, so its readonly result is a chosen output policy, not an assumed consequence of using infer. [Tuple forwarding](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>) and [recursive generics](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) own the deeper tuple and recursion applications.

Promise extraction also depends on the pattern. A single Promise match is not a substitute for the standard Awaited contract, which models recursive awaiting and supports thenable shapes. Save as `awaiting.ts`.

```typescript
type PromisePayload<T> = T extends Promise<infer Value> ? Value : never;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
const thenable = { then(resolve: (value: number) => unknown) { resolve(7); } };
type Shallow = Expect<Equal<PromisePayload<Promise<Promise<number>>>, Promise<number>>>;
type Recursive = Expect<Equal<Awaited<Promise<Promise<number>>>, number>>;
type ThenableMismatch = Expect<Equal<PromisePayload<typeof thenable>, never>>;
type ThenableResult = Expect<Equal<Awaited<typeof thenable>, number>>;
async function main(): Promise<void> {
  console.log(await thenable, await Promise.resolve(9));
}
void main().catch(error => { console.log("unexpected failure", error); });
```

The output is `7 9`. The nested Promise types are static matching probes, not a claim that the runtime constructs nested promises without assimilation. The actual await handles the shown thenable and promise. The [primary Awaited reference](https://www.typescriptlang.org/docs/handbook/utility-types.html#awaitedtype) states its recursive purpose; its full pattern and edge cases belong to the utility owner. A hand-written recursive matcher also needs a termination policy for its admitted inputs, rather than assuming every recursive wrapper must eventually end.

### 3) **Distributive preview**

A conditional with a bare type parameter on the checked side distributes over that parameter's union members. Wrapping the checked side, as in `[T] extends [string]`, asks about the whole union instead. The results are types, not a runtime filtering pass.

Save as `distribution.ts`.

```typescript
type Strings<T> = T extends string ? T : never;
type Whole<T> = [T] extends [string] ? T : never;
type BadEmpty<T> = T extends never ? true : false;
type IsEmpty<T> = [T] extends [never] ? true : false;
type RightOnly<T> = T extends [string] ? 1 : 2; // T is still bare on the checked side.
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Distributed = Expect<Equal<Strings<"a" | 1 | "b">, "a" | "b">>;
type WholeUnion = Expect<Equal<Whole<"a" | 1>, never>>;
type EmptyTrap = Expect<Equal<BadEmpty<never>, never>>;
type EmptyFixed = Expect<Equal<IsEmpty<never>, true>>;
type StillDistributed = Expect<Equal<RightOnly<[string] | number>, 1 | 2>>;
const value: Strings<"a" | 1> = "a";
const empty: IsEmpty<never> = true;
console.log(value.toUpperCase(), empty);
// const whole: Whole<"a" | 1> = "a"; // TS2322
// const number: Strings<"a" | 1> = 1; // TS2322
```

The output is `A true`. Whole rejects the mixed union as a unit; Strings keeps the matching members. BadEmpty distributes over an empty union and produces never rather than true. Wrapping T gives the whole-type emptiness check. Wrapping only the right-hand pattern does not stop distribution, as RightOnly demonstrates.

Use this preview to recognize the mechanism. The full rules and utilities live in [conditional types](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>); [union/intersection distribution](<../../../07 Unions Intersections and Narrowing/sections/2. Intersection Types/2.3. Unions and intersections distributive behavior and primitive intersections.md>) distinguishes that algebra from conditional member selection. No member ordering or runtime array mutation follows from a union type.

### 4) **Common confusion**

Infer captures checking information; it is not a runtime extractor or a new caller-chosen parameter. The pattern must express what the input guarantees, and the false branch defines the non-match contract. Returning never, passing the original type through and reporting a constrained-input error are different API choices.

A readonly input, an optional element and a possibly empty array can require different patterns. Similarly, matching Promise once and awaiting a thenable are different contracts. Do not manufacture a never value with an assertion or print a constant boolean as proof of an unexecuted type computation; use live type assertions and separately observe runtime behavior.

### 5) **Performance note**

Infer and conditional types erase. Runtime indexing, joins, promise awaiting and callbacks remain. These examples establish no four-level chain limit, tuple-length cost formula or cache-entry count. A required-head pattern can fail because of the contract even for a tiny input, not because the checker ran out of time. For actual checking costs, use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) and the recursion owner's stopping-policy guidance.

### 6) **Mentor note**

Ask the learner to name the checked type, the pattern, the captured name and the non-match result before simplifying an alias. Compare Head<[]>, IndexedFirst<[]> and Head<string[]>; a sound answer distinguishes an empty tuple, a generic indexed lookup and a type that does not guarantee nonemptiness. Then switch the literal input to readonly and explain which pattern still matches.

For an exercise, derive the last element type of a nonempty readonly tuple with a pattern ending in an inferred Last. Return never when the tuple does not guarantee a last element. Verify a singleton, a mixed tuple, an empty tuple and an unbounded array. The matching operation is type-level; a runtime last function still needs an absence policy for arrays.
