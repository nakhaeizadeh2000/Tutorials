## 2.3. `infer` — conditional inference and distributive preview

### 1) **What `infer` extracts** (naming the piece the checker solved for)

**Definition** — `infer U` inside a conditional type declares a placeholder the checker *solves* by matching: `T extends Array<infer U> ? U : never` matches `T` against `Array<U>`, binds `U` to the element type, and returns it — `string[]` yields `string`. `infer` appears only in the `extends` branch of a conditional type, never standalone.

**What problem it solves / history** — before `infer` (TS 2.8, 2018), extracting a nested type required indexing tricks that only worked for known shapes (`T[number]` for arrays, `T[K]` for objects) and failed for return types, promise payloads, and tuple heads — each needed its own hand-rolled helper. `infer` unified them: one syntax names whatever the pattern captures, so `Element<T>`, `Return<T>`, and `Awaited<T>` are all the same three-line shape with different patterns.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), reach for `infer` when you hold a wrapper and need the wrapped type — array → element, function → return, `Promise` → payload, tuple → head. Write the pattern (`Array<infer U>`, `(...args: never[]) => infer R`, `Promise<infer V>`), return the placeholder in the true branch, and `never` in the false branch. Full utility-transform treatment lives in [09 Utility Types](<../09 Utility Types and Type Transformations/README.md>) — this leaf owns the extraction mechanic.

**Runnable example** — one shape, many wrappers (good vs bad, `tsc --strict`):

```typescript
// good — element extraction: pattern captures, branch returns
type ElemOf<T> = T extends Array<infer U> ? U : never;
const e: ElemOf<string[]> = "hi"; // string
console.log(e.toUpperCase()); // HI

// good — return and payload extraction share the shape
type Ret<F> = F extends (...args: never[]) => infer R ? R : never;
type Payload<P> = P extends Promise<infer V> ? V : never;
const r: Ret<() => number> = 7;
const v: Payload<Promise<string>> = "done";
console.log(r.toFixed(0), v.toUpperCase()); // 7 DONE

// bad — hand-rolled per-shape helpers instead of one infer pattern
type StrArrElem = string[] extends Array<infer _U> ? string : never; // overfit to one shape
// type NumElem = ... // second helper for number[] — multiplied per wrapper
// fix — ElemOf<T>: the pattern (not the example) is the reusable unit
const n: ElemOf<number[]> = 3;
console.log(n.toFixed(0)); // 3 — same helper, new wrapper
```

**Common confusion** — "`infer U` declares a generic like `<U>`" — `infer` binds *by matching* inside one conditional branch; `<U>` is supplied or inferred per call — different mechanisms, different positions. "`infer` works outside `extends`" — it is only legal in the matched pattern (`T extends P<infer U> ? …`); elsewhere it errors. "the false branch does not matter" — it defines the failure contract (`never` for "no match" vs `T` for "pass through") — pick deliberately, because callers branch on it.

**Performance note** — `infer` matching is structural and cached per instantiation (`Element<string[]>` computes once). Chained extraction (`Payload<Ret<F>>`) nests one cache entry per level — keep chains under ~4 levels in public signatures or hover text balloons while check cost stays linear.

**Mentor note** — teach `infer` as "destructuring for types" — draw `const [head] = arr` next to `Array<infer U>` and ask what `U` binds. Exercise: implement `ElemOf`, then `Ret`, then `Payload` without looking — the third one proves the pattern transferred. Review gate: hand-rolled per-wrapper element helpers (`StrElem`, `NumElem`) must be replaced by one `infer` alias.

### 2) **`infer` positions** (return, element, head, payload — the four daily sites)

**Definition** — four patterns cover daily extraction: return (`F extends (...args: never[]) => infer R`), element (`T extends Array<infer U>`), tuple head/tail (`T extends [infer H, ...infer Rest]`), payload (`T extends Promise<infer V>`). Each names the captured piece; the true branch decides whether to return it bare, wrap it, or recurse over it.

**What problem it solves / history** — each position previously needed bespoke syntax knowledge: `ReturnType` was magic, tuple splitting required length arithmetic, and promise unwrapping nested `.then` types by hand. The four `infer` patterns replaced four mental models with one — match the wrapper shape, name the hole, return the name — so reading any stdlib utility (`Awaited`, `Parameters`, `ReturnType`) became pattern recognition instead of memorization.

**Modern guidance** — as of TypeScript 5.9 era, memorize the four patterns, not the stdlib list: need the return → `(...args: never[]) => infer R`; the element → `Array<infer U>`; the head → `[infer H, ...unknown[]]`; the payload → `Promise<infer V>`. Use `never[]` for ignored function args (accepts any arity) and `unknown[]` for ignored tuple tails (accepts any length). Prefer stdlib names (`ReturnType`, `Awaited`) at call sites; write `infer` only when the stdlib lacks your wrapper.

**Runnable example** — four sites, one mechanic (good vs bad, `tsc --strict`):

```typescript
// good — head/tail splitting drives recursion without index arithmetic
type Head<T> = T extends [infer H, ...unknown[]] ? H : never;
type Tail<T> = T extends [unknown, ...infer Rest] ? Rest : never;
const h: Head<["a", "b", 1]> = "a";
const t: Tail<["a", "b", 1]> = ["b", 1];
console.log(h.toUpperCase(), t.length); // A 2

// good — payload unwrapping without chaining .then types
type Deep<V> = V extends Promise<infer U> ? Deep<U> : V;
const d: Deep<Promise<Promise<number>>> = 7;
console.log(d.toFixed(0)); // 7 — unwrapped twice by recursion

// bad — index-arithmetic extraction that infer replaces
type FirstBad<T extends unknown[]> = T[0]; // crashes on [] (no element), blind to tuples
// const x: FirstBad<[]> = ... // error — T[0] on empty tuple
// fix — Head<T>: the conditional returns never on mismatch instead of erroring
const safe: Head<[]> = undefined as never; // never — honest "no head" contract
console.log(safe); // (never — uninhabited, proves the empty case handled)
```

**Common confusion** — "`(...args: any[]) => infer R` is equivalent" — `any[]` args make the pattern match loosely and leak `any` into inference; `never[]` matches any arity while keeping args uninhabited-precise. "`Head` and `T[0]` are interchangeable" — `T[0]` errors on empty tuples and widens unions; `Head` returns `never` on mismatch — different failure contracts, choose by intent. "recursive `Deep` loops forever" — each level unwraps one `Promise`; non-promises hit the false branch and terminate — recursion needs a shrinking input (see next promise and [3.2. Recursive generics](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>)).

**Performance note** — tuple `infer` on long tuples (100+ elements) costs O(length) per match — fine occasionally, expensive inside mapped types over every row. Prefer `Head`/`Tail` single splits over full tuple destructuring in hot utility types; cache the result in a named alias instead of re-matching per property.

**Mentor note** — drill the four patterns as flashcards: show the wrapper (`Promise<X>`, `(a) => Y`, `[A, ...]`, `T[]`) and ask for the `infer` line before revealing it — recall beats recognition for utility authoring. Exercise: implement `Tail`, then use it to write a 3-line `Last` via recursion — proves composition, not just matching.

### 3) **Distributive preview** (naked `T` maps over unions member-by-member)

**Definition** — a conditional over a *naked* type parameter distributes: `T extends U ? X : Y` with `T = A | B` evaluates as `(A extends U ? X : Y) | (B extends U ? X : Y)` — each member decides independently, results reunite in a union. Wrapping `T` (`[T] extends [U]`) disables distribution and tests the whole union at once.

**What problem it solves / history** — filtering unions (`Exclude`, `Extract`, "all strings in this mixed union") requiredihan manual per-member overloads before distributive conditionals (TS 2.8): every new member meant a new branch. Distribution turned the conditional into a map: one line filters any present or future member, and adding a variant to the union automatically flows through existing filters without edits.

**Modern guidance** — as of TypeScript 5.9 era, use naked-`T` distribution for member-wise filtering (`T extends string ? T : never` keeps strings, drops the rest) and the `[T]` wrapper when the whole union matters (`[T] extends [never]` tests emptiness). Full distributive law, `Exclude`/`Extract` implementations, and non-distributive escapes live in [09 Utility Types](<../09 Utility Types and Type Transformations/README.md>) — this promise teaches recognition (distributed vs whole), not the catalog.

**Runnable example** — distributed vs whole-union test (good vs bad, `tsc --strict`):

```typescript
// good — naked T distributes: each member filtered independently
type Strings<T> = T extends string ? T : never;
type S = Strings<"a" | 1 | "b" | true>; // "a" | "b" — members decided one by one
const s: S = "a";
console.log(s.toUpperCase()); // A

// good — wrapped [T] tests the whole union at once (no distribution)
type IsEmpty<T> = [T] extends [never] ? true : false;
const e1: IsEmpty<never> = true;
const e2: IsEmpty<string | never> = false; // string | never = string — not empty
console.log(e1, e2); // true false

// bad — expecting distribution from a non-naked check
type Whole<T> = [T] extends [string] ? T : never;
type W = Whole<"a" | 1>; // never — the WHOLE union (not string) failed at once
// const w: W = "a"; // error — correctly never; author wanted Strings<T> (naked)
// fix — naked T distributes; [T] does not: pick by intent
const ok: Strings<"a" | 1> = "a"; // "a" — distributed survivor
console.log(ok.toUpperCase()); // A
```

**Common confusion** — "every conditional distributes" — only naked-`T` (`T extends …`) distributes; `Array<T>`, `[T]`, `Box<T>` wrappers test whole. "`Exclude` is magic" — `Exclude<T, U> = T extends U ? never : T` is one naked-conditional line — distribution does the work. "distribution preserves order/duplicates" — results reunite as a union (order-free, deduped) — member *sequence* is lost, member *set* is kept.

**Performance note** — distribution multiplies check cost by member count (N-member union × conditional body) — a 200-member literal union through a nested distributive filter checks 200 branches per reference. Prefer pre-filtered named unions over re-filtering the same large union at 50 call sites — filter once, reference the result.

**Mentor note** — the naked-vs-wrapped contrast is the whole lesson: write both lines, instantiate with `"a" | 1`, and ask why one yields `"a"` and the other `never` — the brackets are the only difference. Exercise: implement `Exclude` from memory (one line), then break it with `[T]` and explain the `never` — proves distribution understood, not memorized. Forward-link the catalog to 09 explicitly so students do not camp on this preview.
