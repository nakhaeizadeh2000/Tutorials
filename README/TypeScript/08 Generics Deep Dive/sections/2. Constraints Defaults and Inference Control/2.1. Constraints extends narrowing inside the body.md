## 2.1. Constraints — extends narrowing inside the body

A constraint states which type choices a generic declaration admits. It gives the body capabilities it can rely on while preserving a relationship with the chosen parameter. It does not convert the argument, validate external input or permit constructing an arbitrary value of the caller's more specific type.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent TypeScript fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Activate commented negatives one at a time and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **What a constraint promises**

`T extends { length: number }` admits types with a numeric length. The body may read that member and return one of its supplied T values. An unconstrained T does not supply length, and an array of T supplies the array's length rather than necessarily each element's length. This distinction follows the [primary generic-variable guidance](https://www.typescriptlang.org/docs/handbook/2/generics.html#working-with-generic-type-variables).

Save as `capabilities.ts`.

```typescript
function longest<T extends { length: number }>(left: T, right: T): T {
  return left.length >= right.length ? left : right;
}
const word = longest("abcd", "xy");
const array = longest([1, 2, 3], [9]);
console.log(word.toUpperCase(), array.join(","));
function elementCount<T>(values: readonly T[]): number { return values.length; }
function lengthOf(value: { length: number }): number { return value.length; }
console.log(elementCount(["a", "bb"]), lengthOf("hello"));
// function assumed<T>(value: T): number { return value.length; } // TS2339
// function firstLength<T>(values: readonly T[]): number { return values[0].length; } // TS2532 and TS2339
// longest(3, 5); // TS2345

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Word = Expect<Equal<typeof word, "abcd" | "xy">>;
type ArrayResult = Expect<Equal<typeof array, number[]>>;
const unchecked: any = 42; // Deliberate bypass of the static input contract.
const claimed: number = lengthOf(unchecked);
console.log("unchecked length:", claimed); // Runtime undefined despite the declared return.
try { claimed.toFixed(0); }
catch (error) { console.log(error instanceof TypeError ? "unchecked input: TypeError" : "unexpected error"); }
```

The output is `ABCD 1,2,3`, `2 5`, `unchecked length: undefined`, then `unchecked input: TypeError`. ElementCount counts elements; lengthOf reads one value's length. They answer different questions. FirstLength is rejected both because the indexed value can be absent and because T has no promised length. Add an element constraint and an absence policy if the intended operation really is the first element's length; do not replace it with an array count and call that the same repair.

The two live type assertions establish this longest call's local literal-union and number-array results. The word is one of the two supplied literals, while its runtime selection is abcd. They are not literal-preservation guarantees for every generic signature. The unchecked input also demonstrates why neither a structural parameter nor a generic constraint replaces [runtime boundary checks](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>). Adding NonNullable or another type operator cannot validate an any value at runtime.

### 2) **Preserve a relationship when the implementation can honor it**

Returning the original T can preserve information beyond its constraint. Returning the bound instead intentionally exposes only that bound. Neither is intrinsically wrong: an identity-style operation can preserve a caller's subtype, while a transformation may change its value and need a different result contract.

Save as `precision.ts`.

```typescript
function keepMethod<M extends string>(method: M): M { return method; }
function uppercase(method: string): string { return method.toUpperCase(); }
const exact = keepMethod("get");
let source = "get";
const broad = keepMethod(source);
const changed = uppercase("get");
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Exact = Expect<Equal<typeof exact, "get">>;
type Broad = Expect<Equal<typeof broad, string>>;
type Changed = Expect<Equal<typeof changed, string>>;
console.log(exact, broad, changed);
// keepMethod<"get">(source); // TS2345: explicit argument cannot recover a widened source
// function dishonest<M extends string>(method: M): M { return method.toUpperCase(); } // TS2322

function keepNamed<T extends { name: string }>(value: T): T { return value; }
const input = { name: "Ada", admin: true };
const kept = keepNamed(input);
console.log(kept.admin, kept === input);
// function replace<T extends { name: string }>(value: T): T { return { name: value.name }; } // TS2322
```

The output is `get get GET`, then `true true`. The literal call retains get, the already widened source stays string, and the uppercase operation correctly returns a general string. A generic implementation claiming to return the same M after changing the string is rejected: M could be the literal get, whose uppercase spelling is not get.

KeepNamed returns the same object and retains admin. A replacement containing only name meets the constraint but may fail the caller's T. This is the [primary constrained-values distinction](https://www.typescriptlang.org/docs/handbook/2/functions.html#working-with-constrained-values). Use the type parameter for a relationship the implementation actually preserves, rather than choosing a narrower return type to make consumers happy. [Inference control](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) owns source precision and competing evidence; [generic functions](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) introduces the full relationship.

### 3) **Choose bounds and argument relationships from the operation**

An unnecessary object-only bound can exclude a primitive string even when the body only needs length. A mutable-array bound can exclude a readonly tuple even when the body does not mutate. Arrays are structural types too; their rejection is about the required contract, not a nominal class distinction or arbitrary tuple arity.

Save as `bounds.ts`.

```typescript
function lengthOf(value: { length: number }): number { return value.length; }
function objectLength<T extends object>(value: T & { length: number }): number {
  return value.length;
}
function mutableLength<T extends string[]>(value: T): number { return value.length; }
const readonlyWords = ["a", "b"] as const;
console.log(lengthOf("hi"), lengthOf(readonlyWords), lengthOf({ length: 10 }));
console.log(mutableLength(["a", "b", "c"]), objectLength({ length: 4 }));
// objectLength("hi"); // TS2345: object requirement excludes this primitive
// mutableLength(readonlyWords); // TS4104: readonly source cannot fulfill mutable-array contract
```

The output is `2 2 10`, then `3 4`. The simple structural parameter fulfills this read-only operation; no generic parameter is needed when the caller needs only a number result. An object or mutable-array requirement can be justified for other operations, so remove it only after checking what the implementation must do. The [Golden Rule discussion](https://effectivetypescript.com/2020/08/12/generics-golden-rule/) uses relationship questions to examine unnecessary generic parameters; [object contracts](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) owns readonly behavior.

A callable constraint also needs care: being compatible with a broad callable shape does not prove that the caller supplied the concrete arguments the implementation requires. Save as `calling.ts`.

```typescript
function unsafeInvoke<F extends (...args: never[]) => unknown>(fn: F): unknown {
  return fn(); // Accepted, but no concrete argument has been supplied.
}
const requiresText = (value: string): string => value.toUpperCase();
try { unsafeInvoke(requiresText); }
catch (error) { console.log(error instanceof TypeError ? "missing argument: TypeError" : "unexpected error"); }
function invoke<Args extends unknown[], Result>(
  fn: (...args: Args) => Result, ...args: Args
): Result {
  return fn(...args);
}
console.log(invoke(requiresText, "Ada"));
console.log(invoke((left: number, right: number) => left + right, 2, 3));
// invoke(requiresText); // TS2554: required forwarded argument missing
// invoke(requiresText, 42); // TS2345: wrong argument type
```

The output is `missing argument: TypeError`, `ADA`, then `5`. The never-array callable shape admits requiresText, but unsafeInvoke then calls it without its required string. The repaired signature relates the actual argument tuple to the callback's parameters and forwards those arguments. This is a concrete application of the relationship taught in [tuple forwarding](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>); it is not a reason to call every function matching a constraint with zero arguments.

### 4) **Common confusion**

A bound is not the complete identity of T. The caller may require additional members, literals or invariants that a replacement meeting only the bound would discard. Conversely, a declared string result is honest when the implementation transforms its input instead of preserving its exact literal.

Constraints also do not always add useful restrictions. In these .ts signatures, extends unknown or extends any would not narrow the admitted type choices. Choose the needed capability or relationship rather than adding a bound for the appearance of safety. Actual runtime checks remain necessary when unchecked data can enter.

### 5) **Performance note**

Bounds and type relationships erase. Property reads, comparisons, calls, argument forwarding and string conversion methods remain. The examples show differences in admitted values and runtime correctness; they establish no universal rule that a smaller constraint speeds the solver or that literal preservation saves a certain number of checks. Measure real checker issues using [extended diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) while preserving the API's intended relation.

### 6) **Mentor note**

Ask what the body may read and what it must preserve in its return. KeepNamed may read name, but its T return requires retaining the more specific input. Uppercase changes the value and cannot promise the same arbitrary string subtype. Require the learner to explain both rejected replacement implementations without appealing to a vague “generic error.”

For a repair exercise, implement `firstLength` for readonly arrays of values with numeric length, returning undefined when the array is empty. A suitable signature relates an element constraint to `number | undefined`; the body checks the indexed value before reading length. Verify an empty array, strings and readonly arrays as elements, and rejection of numeric elements. The absence policy and member guarantee are separate obligations.
