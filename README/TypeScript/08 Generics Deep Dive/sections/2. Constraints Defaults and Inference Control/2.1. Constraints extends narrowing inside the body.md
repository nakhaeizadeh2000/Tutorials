## 2.1. Constraints — `extends` narrowing inside the body

### 1) **What `T extends` promises** (the constraint is the body's only assumption)

**Definition** — `function f<T extends C>(x: T)` constrains `T` to subtypes of `C`: inside the body, the checker treats `T` as `C` (so `C`'s members are accessible), while callers keep their precise subtype (`"get"` stays `"get"`, not widened to `string`). The constraint is an upper bound, not a conversion.

**What problem it solves / history** — unconstrained bodies could assume nothing — `x.length` on bare `T` errored because `T` might be a `number` — so developers either duplicated helpers per shape or cast through `any`. Constraints (since TS 0.9) gave the body a provable minimum: `T extends { length: number }` unlocks `.length` once, while every caller still passes its own narrow type and gets its own narrow result back.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), constrain exactly what the body touches — needs `.length` → `T extends { length: number }`; needs a key lookup → `K extends keyof T`; needs a string method → `T extends string`. Callers preserve literals through constraints (a `"get"` argument with `M extends string` can still infer `M = "get"` at a literal-friendly site). Function-level basics live in [2.2. Generic functions](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) — this leaf owns the inside-the-body contract.

**Runnable example** — constraint unlocks the body, preserves the caller (good vs bad, `tsc --strict`):

```typescript
// good — body uses .length (guaranteed), caller keeps string[] (precise)
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
const w = longest("abcd", "xy"); // T = string, w: string
console.log(w.toUpperCase()); // ABCD
console.log(longest([1, 2, 3], [9]).length); // 3 — arrays qualify too

// good — keyof constraint threads lookup precision
function get<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
const cfg = { host: "h", port: 8080 };
console.log(get(cfg, "port").toFixed(0)); // 8080 — T[K] = number
// get(cfg, "missing"); // error TS2345 — K constrained to "host" | "port"

// bad — unconstrained body reaches for members it cannot prove
function firstLenBad<T>(xs: T[]): number {
  // return xs[0].length; // error TS18048/TS2339 — T might lack .length
  return xs.length; // fix option A — use what the SITE guarantees (arrays have .length)
}
function firstLen<T extends { length: number }>(x: T): number {
  return x.length; // fix option B — constrain the ELEMENT contract instead
}
console.log(firstLenBad(["a", "bb"]), firstLen("hello")); // 2 5
```

**Common confusion** — "the constraint widens the caller's type to `C`" — the caller keeps its subtype; the constraint only widens what the *body* may assume. "`T extends string` accepts `any`" — `any` is assignable both ways (unsound escape, see [3.3. Unsound spots](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)) — constrain plus `NonNullable`/validation at boundaries. "constraints run at runtime" — purely checker-side; a `T extends { length: number }` call with a number argument fails *before* emit, never in production.

**Performance note** — constraints *narrow* the solver's search: `K extends keyof T` restricts inference candidates to the key union instead of all strings — faster checks and better errors. Over-broad constraints (`T extends unknown` — no restriction) add zero value; over-narrow ones (`T extends string`) reject valid callers. Zero emit delta either way.

**Mentor note** — teach "the body sees `C`, the caller keeps `T`" as the one sentence — then prove it by hovering `w` (`string`, not `{ length: number }`). Exercise: remove the constraint and ask what breaks first — the `.length` access, not the call — showing constraints serve the *implementation*, inference serves the *caller*. Review gate: bodies casting `x as C` where `T extends C` would prove it — the cast is a constraint-shaped hole.

### 2) **Constraining without erasing use** (callers keep literal and subtype precision)

**Definition** — a well-placed constraint preserves the argument's narrowness through the call: `identity<M extends string>(m: M): M` returns `"get"` for `"get"`, not `string`. The constraint bounds *admissibility* (what may be passed) without collapsing *identity* (which subtype was passed).

**What problem it solves / history** — developers feared constraints would "widen everything to the bound" and wrote overloads per literal instead (`onGet()`, `onPost()`) — doubling APIs to preserve what a single `M extends string` already preserved. Understanding that `M` (not `C`) flows to the return type collapsed those overload sets back into one generic and re-armed downstream exhaustiveness.

**Modern guidance** — as of TypeScript 5.9 era, return the *parameter* (`M`), never the *constraint* (`string`): `function f<M extends string>(m: M): M` preserves; `function f(m: string): string` widens. Combine with `as const` sources and explicit `<"get">` pins (see 1.2) when the *source* already widened — the constraint cannot recover precision the argument never carried.

**Runnable example** — precision survives the bound (good vs bad, `tsc --strict`):

```typescript
// good — M flows to the return; literal survives
function method<M extends string>(m: M): M { return m; }
const g = method("get"); // M = "get"
function handle(m: "get" | "post"): string { return m === "get" ? "G" : "P"; }
console.log(handle(g)); // G — still assignable to the literal union

// good — subtype identity survives: caller passes Dog, gets Dog
interface Animal { name: string; }
interface Dog extends Animal { barks: boolean; }
function keep<T extends Animal>(x: T): T { return x; }
const d = keep({ name: "r", barks: true }); // T = the literal object type
console.log(d.barks); // true — not widened to Animal

// bad — returning the constraint widens every caller
function methodBad(m: string): string { return m; }
const g2 = methodBad("get"); // string — exhaustiveness dead downstream
// handle(g2); // error TS2345 — string not assignable to "get" | "post" (correctly!)
// fix — return M (the parameter), not string (the bound)
```

**Common confusion** — "`M extends string` means the return is `string`" — the return is `M` (the inferred subtype); only an explicit `: string` return annotation widens. "`keep(dog)` returns `Animal`" — it returns the *argument's* type (`Dog`-shaped literal) — the constraint is invisible in the result. "narrowing the constraint narrows callers" — tightening `C` rejects more callers but never narrows accepted ones — precision comes from inference, not from `C`.

**Performance note** — returning `M` instead of `C` costs one extra cached instantiation per distinct argument (each literal gets its type) — trivial. The saving is downstream: literal-preserving calls keep discriminated-union narrowing O(variants) instead of falling back to `string`-wide `if/else` chains the checker cannot verify.

**Mentor note** — hover-compare `method("get")` (`"get"`) vs `methodBad("get")` (`string`) side by side — one screen kills the "constraints widen" myth. Exercise: feed both into `handle()` and ask which compiles — then delete the overloads the team wrote to work around the widened one. Rule of thumb for review: any generic returning its *constraint* instead of its *parameter* is suspicious.

### 3) **Over-constraining cost** (minimal bounds admit the most callers)

**Definition** — an over-narrow constraint rejects valid callers: `T extends object` blocks primitives, `T extends string[]` blocks tuples of the wrong arity, `T extends { id: string }` blocks every type without `id`. The cheapest constraint that unlocks the body admits the most callers — prefer structural minimums (`{ length: number }`) over nominal ones (`Array<string>`).

**What problem it solves / history** — defensive constraints (`extends object`, `extends Record<string, unknown>`) were added "for safety" and then rejected numbers, strings, and branded primitives at real call sites — checkout IDs, SKU numbers, locale strings — forcing `as` laundering at every boundary. Minimal constraints (the exact member the body reads) reopened those call sites without touching the implementation.

**Modern guidance** — as of TypeScript 5.9 era, constrain to the *member used*, not the *kind assumed*: reads `.length` → `{ length: number }`; reads `[key]` → `K extends keyof T` pattern; calls the value → `(...args: never[]) => unknown` shape. Avoid `extends object` (blocks primitives silently) and `extends any`/`extends unknown` (no constraint at all — drop it). When nothing is touched, leave `T` unconstrained — the honest signature.

**Runnable example** — minimal bounds admit more callers (good vs bad, `tsc --strict`):

```typescript
// good — structural minimum: anything with .length qualifies
function lenOf<T extends { length: number }>(x: T): number { return x.length; }
console.log(lenOf("hi"), lenOf([1, 2]), lenOf({ length: 10 })); // 2 2 10

// bad — object-only bound rejects primitives the body never excluded
function lenObj<T extends object>(x: T & { length: number }): number { return x.length; }
// lenObj("hi"); // error TS2345 — string not assignable to 'object': the bound rejects a valid caller
// const s: string = "hi"; lenObj(s); // same error in the wild — T extends object blocks string callers
// fix — lenOf: the { length: number } bound alone admits strings, arrays, and shapes
console.log(lenOf("hi")); // 2 — minimal bound admits the string caller

// good — unconstrained when nothing is touched: identity needs no bound
function id<T>(x: T): T { return x; }
console.log(id(42).toFixed(0), id("x").toUpperCase()); // 42 X — primitives welcome
```

**Common confusion** — "`extends object` means any non-primitive" — it excludes primitives *including* the strings/arrays-with-methods callers actually pass; `object` is narrower than newcomers expect. "`extends unknown` adds safety" — it constrains nothing (`unknown` is the top) — delete it and say what you mean. "constraints validate at runtime" — rejected callers fail at `tsc`, never in production; runtime validation still needs guards/schemas.

**Performance note** — minimal constraints check fastest (fewer members to verify per candidate) and produce shorter error messages (one missing member vs a deep `object` mismatch). No emit effect — constraint strictness is purely a call-site admissibility filter.

**Mentor note** — audit every `extends object` in the codebase and ask "which primitive caller does this reject, and does the body actually exclude them?" Most fail the test — replace with the touched member. Exercise: pass a `string` to `lenObj`-style bound and read the error — then to `lenOf` — the contrast teaches structural-minimum thinking in one compile.
