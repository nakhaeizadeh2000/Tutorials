## 2.2. Defaults and optional type parameters

A generic default supplies a type choice when the relevant argument is omitted and inference does not choose another candidate. It is not a runtime initializer, a constraint or a promise that an empty collection contains a default element. Choose it as part of the API's omitted-type contract.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent TypeScript fence under its filename and compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`. Run `node dist/FILE.js`. Activate each commented negative separately and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **What defaults fill**

In a type reference, Envelope means Envelope<string> when its parameter defaults to string. An explicit number still chooses number. At a generic call, argument evidence can select a candidate before the default is needed. An optional type parameter also does not make a required runtime argument optional. The [primary default rules](https://www.typescriptlang.org/docs/handbook/2/generics.html#generic-parameter-defaults) distinguish these choices.

Save as `choices.ts`.

```typescript
type Envelope<T = string> = { data: T };
const legacy: Envelope = { data: "ok" };
const numeric: Envelope<number> = { data: 7 };
console.log(legacy.data.toUpperCase(), numeric.data.toFixed(0));
function boxed<T = string>(value: T): { value: T } { return { value }; }
const inferred = boxed(42); // Input evidence selects number despite the string default.
function empty<T = string>(): T[] { return []; }
const defaulted = empty();
const selected = empty<number>();
function optional<T = string>(value?: T): T | undefined { return value; }
function runtimeFallback(value = "fallback"): string { return value; }
console.log(inferred.value, defaulted.length, selected.length);
console.log(optional(), runtimeFallback());
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Inferred = Expect<Equal<typeof inferred.value, number>>;
type Defaulted = Expect<Equal<typeof defaulted, string[]>>;
type Selected = Expect<Equal<typeof selected, number[]>>;
// boxed(); // TS2554: the value argument is still required
// defaulted.push(42); // TS2345: chosen element contract is string
// type WrongOrder<T = string, U> = [T, U]; // TS2706

type Pair<First, Second = string> = [First, Second];
const pair: Pair<number> = [1, "tail"];
console.log(pair.join(","));
```

The output is `OK 7`, `42 0 0`, `undefined fallback`, then `1,tail`. Empty uses string when there is no input evidence, but it still returns an empty array. Optional returns undefined when no value is supplied; only runtimeFallback contains the JavaScript initializer that supplies a string value. Pair demonstrates leaving out the optional trailing type argument. There is no blank type-argument slot that skips First while explicitly choosing Second.

Do not generalize a bare function call to mean “always use its default.” An explicit argument, an inference candidate or context may matter. In particular an empty array passed as evidence can infer never instead of triggering a string default. [Inference control](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) and [the function introduction](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) own those worked contrasts.

### 2) **Defaults with constraints**

A default must satisfy its parameter's constraint. It can also depend on an earlier type parameter. These are type-level checks; they do not manufacture a matching runtime object or repair an unsafe any choice.

Save as `bounds.ts`.

```typescript
type WithId<T extends { id: string } = { id: string }> = { data: T };
const ordinary: WithId = { data: { id: "u1" } };
const richer: WithId<{ id: string; name: string }> = { data: { id: "u2", name: "Ada" } };
console.log(ordinary.data.id, richer.data.name);
// type Invalid<T extends { id: string } = number> = T; // TS2344: default fails its bound
// const missing: WithId = { data: {} }; // TS2741: default type does not supply a runtime id

type Batch<Item = string, Items extends readonly Item[] = readonly Item[]> = { items: Items };
const words: Batch = { items: ["a"] };
const numbers: Batch<number> = { items: [1, 2] };
console.log(words.items.join(","), numbers.items.join(","));
// type WrongItems = Batch<number, readonly string[]>; // TS2344

type LengthDefault<T extends { length: number } = []> = T;
const empty: LengthDefault = []; // [] is an empty tuple, not a nonempty value.
console.log("tuple length:", empty.length);
// const populated: LengthDefault = ["x"]; // TS2322: the selected default is exactly []
type EmptyShapeDefault<T = {}> = { data: T };
const primitive: EmptyShapeDefault = { data: 42 }; // {} admits non-nullish primitives.
console.log("empty shape:", primitive.data);
// const nullish: EmptyShapeDefault = { data: null }; // TS2322

type Unsafe<T extends { length: number } = any> = { data: T };
const unchecked: Unsafe = { data: 42 };
console.log("any default:", unchecked.data.length); // Runtime undefined; the bound did not validate it.
```

The output is `u1 Ada`, `a 1,2`, `tuple length: 0`, `empty shape: 42`, then `any default: undefined`. The id default still requires an id in each value. Batch's omitted Items depends on the selected Item, so Batch<number> uses a readonly number-array contract. The empty tuple is a legal length-bearing type and admits zero elements. The meaning of `{}` remains non-nullish values when it is a default; its syntactic position does not turn it into an object-only runtime validator.

An any default can satisfy a bound while suppressing useful checks, as the final example shows. Prefer a default whose exposed operations fit the intended omitted-type contract. Unknown is often appropriate for an unexamined payload because it requires evidence before use; it is not automatically a valid default for every bound. [Constraints](<./2.1. Constraints extends narrowing inside the body.md>) owns admission/body guarantees, and [unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) owns boundary use.

### 3) **When defaults pay**

Choose a default when the omitted spelling has a useful, documented meaning. A response envelope might mean unknown data; a builder might start with no known filter keys. A library may instead require a type argument to make a domain decision explicit. Reference counts or a majority percentage do not decide whether a default is sound.

A default does not implement a builder's state changes. Save this deliberately broken reproduction as `phantom.ts`.

```typescript
class PhantomQuery<T = {}> {
  where<K extends string>(_key: K, _value: unknown): PhantomQuery<T & Record<K, unknown>> {
    return this as unknown as PhantomQuery<T & Record<K, unknown>>;
  }
  build(): T { return {} as T; }
}
const claimed = new PhantomQuery().where("name", "ada").where("age", 36).build();
console.log(Object.keys(claimed).length, Object.hasOwn(claimed, "name"));
```

The output is `0 false`. Accumulating keys in a return type did not store either input. The assertions concealed the mismatch. A working implementation must keep runtime state corresponding to the contract it publishes.

Save the following small filter builder as `builder.ts`. Its default never means no known key before a filter is added. It returns a map snapshot, with unknown values, rather than claiming a fully typed result object or executing a database query.

```typescript
class Query<Keys extends string = never> {
  private filters: Map<Keys, unknown>;
  constructor(entries: readonly (readonly [Keys, unknown])[] = []) {
    this.filters = new Map(entries);
  }
  where<Key extends string>(key: Key, value: unknown): Query<Keys | Key> {
    return new Query<Keys | Key>([...this.filters, [key, value]]);
  }
  build(): ReadonlyMap<Keys, unknown> { return new Map(this.filters); }
}
const empty = new Query().build();
const query = new Query().where("name", "ada").where("age", 36);
const snapshot = query.build();
const changed = query.where("age", 37).build();
console.log(empty.size, snapshot.size, snapshot.get("name"), snapshot.get("age"));
console.log("snapshots:", snapshot.get("age"), changed.get("age"), changed.size);
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Empty = Expect<Equal<typeof empty, ReadonlyMap<never, unknown>>>;
type Snapshot = Expect<Equal<typeof snapshot, ReadonlyMap<"name" | "age", unknown>>>;
// snapshot.get("missing"); // TS2345: not one of this view's known keys
// snapshot.set("name", "Grace"); // TS2339: published ReadonlyMap view
```

The output is `0 2 ada 36`, then `snapshots: 36 37 2`. The builder copies its state for each new step and returns a new map snapshot. Repeating a key replaces its value rather than inventing a second key or an impossible field intersection. Unknown deliberately makes no promise about each value's shape; a get result still needs examination before numeric or string operations. ReadonlyMap is the published static view, not a runtime freeze of the map.

The default supports a real initial state, while the method's additional key parameter reflects an actual operation. [Generic scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>) owns those two parameter lifetimes; [Map semantics](<../../../10 Arrays Tuples and Collections/sections/3. Collections and Selection/3.1. Map and Set typing generics over collections.md>) owns storage/overwrite behavior. Marius Schulz's [original defaults article](https://mariusschulz.com/blog/generic-parameter-defaults-in-typescript) explains trailing optional type parameters in its TypeScript 2.3 context. Its historical React any defaults are context, not a recommendation for this unknown-valued builder or every current payload API.

Changing a published default can affect every consumer omitting that argument. For a migration drill, change only Envelope's default in choices.ts from string to unknown. The existing legacy.data.toUpperCase call then fails with TS18046 until the consumer checks the value or explicitly selects string. Explicit Envelope<number> remains numeric. Replacing Envelope<unknown> with bare Envelope when unknown is already its default preserves that contract; it does not create new safety by itself.

### 4) **Common confusion**

A default, a bound and a value initializer answer different questions: which type choice is omitted, which choices are admitted, and which value is produced at runtime. A parameter may have both a bound and default, but an unsafe any choice can still defeat meaningful checking. Empty tuple and never defaults describe types; neither populates runtime storage.

Omitting trailing type arguments also differs from skipping required runtime arguments. Boxed's T default cannot make its value parameter optional. Defaults may simplify some overload declarations, but they do not encode every arity-dependent or variant-dependent return relationship an overload might represent.

### 5) **Performance note**

Generic defaults erase. The optional value argument, JavaScript fallback expression, array creation, builder copies and maps remain. The builder here copies filters when extending and building a snapshot; that work is implemented explicitly. No cache-entry count or checker-speed comparison follows from spelling a type argument explicitly versus accepting its default. Measure actual checking issues through [the measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before optimizing the declaration.

### 6) **Mentor note**

Ask what happens separately to the type and runtime value for optional(), empty() and boxed(42). A sound answer predicts undefined, an empty array and a number while identifying why the type default is used or bypassed. Then ask how the id example can require a value field despite having a default type.

For the builder, inspect both the type and actual map before and after the repeated age filter. Require an explanation of why the old snapshot stays 36 and the new one becomes 37. A passing key-union probe alone would not catch the phantom builder's missing storage. Finish with the Envelope migration drill and explain why changing an omitted-type contract is an API decision.
