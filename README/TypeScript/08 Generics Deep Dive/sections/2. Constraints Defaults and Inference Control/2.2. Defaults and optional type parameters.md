## 2.2. Defaults and optional type parameters

### 1) **What defaults fill** (omitted arguments fall back instead of erroring)

**Definition** — `type Response<T = string> = { data: T }` gives `T` a default: `Response` means `Response<string>`, while `Response<number>` still overrides. Function generics accept defaults too (`function f<T = string>(x?: T)`), but required parameters must precede defaulted ones (`<T, U = string>` ok, `<T = string, U>` errors without the required-then-optional order).

**What problem it solves / history** — wrapper types (`ApiResponse<T>`, `Paginated<T>`, `Store<T>`) had one dominant instantiation (string payloads, default page size) yet forced every reference to spell it — `ApiResponse<string>` repeated hundreds of times, and changing the common case meant editing every call site. Defaults (TS 2.3) made the common case silent: references write the argument only when they diverge, and the default lives in exactly one declaration.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default the parameter 80%+ of callers want — `Response<T = unknown>` for fetch wrappers, `Config<T = DefaultTheme>` for theming, `Paginated<T, N extends number = 20>` for paging. Keep required parameters first; document the default at the declaration (`/** Defaults to string for legacy endpoints. */`). Defaults erase like all generics (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**Runnable example** — common case silent, divergence explicit (good vs bad, `tsc --strict`):

```typescript
// good — default carries the common case
type Api<T = string> = { data: T; etag: string };
const legacy: Api = { data: "ok", etag: "a" }; // Api<string> — no brackets
const typed: Api<number> = { data: 7, etag: "b" }; // override where needed
console.log(legacy.data.toUpperCase(), typed.data.toFixed(0)); // OK 7

// good — function default fills un-inferrable positions
function withFallback<T = string>(x?: T): T | string {
  return x ?? "fallback";
}
console.log(withFallback(), withFallback(42)); // fallback 42

// bad — no default: every reference repeats the obvious
type Verbose<T> = { data: T; etag: string };
const v1: Verbose<string> = { data: "ok", etag: "a" }; // tax on every line
const v2: Verbose<string> = { data: "yes", etag: "b" };
// fix — Api<T = string>: write the argument only when it diverges
```

**Common confusion** — "the default constrains what may be passed" — defaults fill *omissions*; constraints bound *admissions* — `Api<number>` is legal regardless of `= string`. "defaults apply per member" — the default applies per *reference* (`Api` → `Api<string>` everywhere in that annotation), not per use of `T` inside. "function defaults replace overloads" — defaults fill un-inferred positions; overloads model *different arities* (see [2.1. Function overloads](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>)).

**Performance note** — defaults add one cached instantiation per omitted reference (`Api` → shared `Api<string>` entry) — cheaper than N distinct explicit spellings. No emit delta; check cost identical to writing the argument out.

**Mentor note** — grep the codebase for the most-repeated single type argument (`ApiResponse<string>` × 200) — that repetition *is* the default waiting to be declared. Exercise: add `= string` and delete 200 brackets, then change the default once to watch the common case migrate in one edit. Review rule: a wrapper referenced 10+ times with the same argument needs a default or a comment explaining why not.

### 2) **Defaults with constraints** (the default must satisfy the bound)

**Definition** — `type R<T extends object = {}>` pairs both: callers may pass any `object` subtype, and omissions fall back to `{}` — but `{}` itself must satisfy `object`, or the declaration errors (`TS2344`). The default is checked against the constraint once, at the declaration; every instantiation is checked again at the reference.

**What problem it solves / history** — unconstrained defaults (`T = any`) silently widened the fallback beyond what the body assumed — the default `any` flowed into `.length` accesses the constraint was supposed to guard. Requiring the default to satisfy the constraint closed the hole at the declaration: an illegal fallback fails where it is written, not in 50 downstream references that omitted the argument.

**Modern guidance** — as of TypeScript 5.9 era, always read the pair together: `T extends { length: number } = []` (never-empty default for length users), `K extends keyof T = keyof T` (whole-object default for pickers), `T extends string = "get"` (literal default preserving exhaustiveness). If no single value satisfies the constraint honestly, the parameter should have no default — force callers to choose instead of supplying a lying fallback.

**Runnable example** — default obeys the bound (good vs bad, `tsc --strict`):

```typescript
// good — default satisfies the constraint: omissions stay legal
function firstLen<T extends { length: number } = string>(x?: T): number {
  return (x ?? "hi").length;
}
console.log(firstLen(), firstLen("hello"), firstLen([1, 2, 3])); // 2 5 3

// good — literal default keeps exhaustiveness when callers omit
type Route<M extends string = "get"> = { method: M; path: string };
const r: Route = { method: "get", path: "/a" }; // Route<"get"> — switch stays exhaustive
console.log(r.method.toUpperCase()); // GET

// bad — default violates the constraint: declaration itself fails
// type Bad<T extends { length: number } = number> = T; // error TS2344 — number lacks .length
// fix — pick a default inside the bound (= string, = [], = {}) or drop the default
type Fixed<T extends { length: number } = []> = T;
const f: Fixed = []; // [] satisfies { length: number }
console.log(f.length); // 0
```

**Common confusion** — "`= {}` means any object" — `{}` as a *default value type* is the empty-object type (satisfies `object`); `{}` as an *inference fallback* is the old top-like — same syntax, different role; read which position it occupies. "the default narrows future inference" — explicit arguments and inference override the default entirely; the default only fires on omission. "constraint + default = two sources of truth" — one contract: the constraint bounds, the default exemplifies — keep them consistent or drop the default.

**Performance note** — declaration-time check of default-vs-constraint runs once per generic declaration — negligible. Omitted references share the default instantiation cache entry — 100 `Route` references (no argument) check as one `Route<"get">`.

**Mentor note** — when reviewing `T extends C = D`, ask "is `D` a `C`?" out loud and hover-verify — the checker already asked, but saying it builds the pair-reading habit. Exercise: write the `Bad` alias, read TS2344, then fix with `= []` — students learn the declaration is itself checked, not just its uses.

### 3) **When defaults pay** (config, response, and builder wrappers)

**Definition** — defaults pay where one instantiation dominates: response envelopes (`Api<T = unknown>`), theme/config objects (`Theme<T = DefaultPalette>`), and builders (`Query<T = {}>`) where callers start generic and narrow as they chain. The default removes the argument from the common path while keeping the escape hatch for the rare one.

**What problem it solves / history** — early generic APIs forced a choice between precision and ergonomics: precise wrappers taxed every call site with brackets, so teams either ate the tax (200 `ApiResponse<string>` spellings) or dropped the parameter (back to `any` envelopes). Defaults broke the trade-off: the envelope stays precise *and* the common reference stays bare — divergence (not conformity) costs brackets.

**Modern guidance** — as of TypeScript 5.9 era, default when three conditions hold: a clear majority instantiation exists, the default satisfies the constraint, and overriding stays one bracket away. Response/config/builder wrappers almost always qualify; domain-model generics (`Store<T>`, `Cache<K, V>`) rarely do — no honest default exists for a store's content, so force the argument instead of inventing one.

**Runnable example** — builder narrows from the default (good vs bad, `tsc --strict`):

```typescript
// good — builder starts at the default, narrows as it chains
class Query<T = {}> {
  where<K extends string>(key: K, value: unknown): Query<T & Record<K, unknown>> {
    return this as unknown as Query<T & Record<K, unknown>>;
  }
  build(): T { return {} as T; }
}
const q = new Query().where("name", "ada").where("age", 36).build();
console.log(Object.keys(q).length); // 2 — T accumulated per chain link

// good — response envelope: bare for unknown, explicit for known
type Envelope<T = unknown> = { data: T; ok: boolean };
const e1: Envelope = { data: JSON.parse("42"), ok: true }; // unknown — forces narrowing
if (typeof e1.data === "number") console.log(e1.data.toFixed(0)); // 42
const e2: Envelope<number> = { data: 7, ok: true };
console.log(e2.data.toFixed(0)); // 7

// bad — forced argument where a default belongs: noise on every line
type Noisy<T> = { data: T; ok: boolean };
const n1: Noisy<unknown> = { data: 1, ok: true }; // tax without precision gain
// fix — Envelope<T = unknown>: bare means unknown, explicit means known
```

**Common confusion** — "every generic deserves a default" — stores/caches with no majority instantiation get *less* safe with defaults (`new Store()` silently `Store<{}>` instead of erroring for the missing content type). "defaults hide the type" — hovers still show the instantiated default (`Envelope<unknown>`), so readers see the fallback — nothing is hidden, only unwritten. "builder chaining needs `any`" — the `T & Record<K, unknown>` accumulation above stays fully checked; the single `as unknown as` cast is the sanctioned escape inside the library (documented, contained), not a caller-side habit.

**Performance note** — chained builder instantiations (`Query<{}>` → `Query<A>` → `Query<A & B>`) create one cached type per link — a 10-link chain holds 10 entries (small). Prefer accumulating intersections over rebuilding mapped types per link — intersections cache structurally, mapped types recompute per instantiation.

**Mentor note** — the three-condition test ("majority? satisfies constraint? one bracket to override?") fits on a review stamp — apply it to every new generic parameter. Exercise: take a `Noisy<T>` codebase, add `= unknown`, delete the repeated `<unknown>` spellings, and watch which call sites *gain* errors (they were relying on `any`-shaped silence) — those are the bugs the default just surfaced.
