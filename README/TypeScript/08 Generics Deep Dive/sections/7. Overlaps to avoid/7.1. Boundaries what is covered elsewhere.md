## 7.1. Boundaries — what is covered elsewhere

Generics describe relationships among types selected at a declaration or use. This domain deepens type-parameter scope, inference, constraints, defaults, extraction, variance and recursive/tuple patterns. It relies on earlier callable, object and class models, and supplies prerequisites for later transformations. Use those owners when the missing step is outside the type-parameter relationship itself.

The routes below distinguish an input/output contract, a transformed type and the runtime work performed by a program. They use published lessons and the current TypeScript 7 learning route. Navigation is an aid to investigation; it is not evidence that every linked implementation or host integration has been checked.

### 1) **Function-level generic basics**

Start with [generic functions](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) when the question is how to relate a function's input, callback and returned result. That owner now checks literal versus widened inference, minimal constraints, defaults and per-call versus fixed contracts with complete examples. This domain's [inference and NoInfer owner](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) then explores missing evidence, competing candidates and explicit choices in more depth.

For a choice between several public call signatures and one generic relationship, use [overloads](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>). For forwarding a typed argument list through a wrapper, begin with [callable tuple rest](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>), then use this domain's [variadic generic patterns](<../3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>). Keep the full signature comparison in its owner rather than repeating it in each generic example.

### 2) **Utility types and mapped/conditional transforms**

This domain's [infer and distribution preview](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) introduces how a conditional type names an extracted piece and how a type parameter can distribute over alternatives. [Conditional types](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) develops that behavior fully. [Mapped types](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) owns rebuilding members from a key set.

Use the [library-utility explanation](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>) to choose among union filters and object-member projections. Recognizing a type parameter in Exclude does not make generic syntax alone the answer to choosing the right utility. The learner needs to know whether the input represents alternatives, keys or object members. Briefly remind them of the parameter mechanism, then follow the canonical transform explanation.

### 3) **Object composition and class containers**

A generic object still has member requirements. Use [object shapes](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) and [optional/readonly/index contracts](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) when an initializer, alias or property access violates those requirements. Use [composition](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) and [declaration merging](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>) when several shapes or declarations must be combined.

Use [class duality](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>) for instance versus constructor-value questions and [generic class members](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>) for the static/instance distinction. Return to [generic declaration scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>) to choose where a container's type argument is fixed and where a method needs a new result parameter. Parameterizing a shape does not remove its required fields or construct a runtime instance.

### 4) **Union algebra and live narrowing**

[Union/intersection modeling](<../../../07 Unions Intersections and Narrowing/README.md>) explains alternatives and combined requirements. This domain parameterizes over those types; transformations can select named alternatives, while [live narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) determines which members a value operation may use on a branch. A conditional type is not an if statement executed against that value.

For recursive inputs, [recursive object graphs](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.1. Recursive object types and self-referential structures.md>) distinguishes recursive descriptions from finite cyclic identities. [Deep transforms](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) owns transform policies. The [measured instantiation-budget lesson](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) shows that a type-depth cap also changes the resulting contract. Do not substitute a guessed universal depth limit for the observed failure and the intended semantics.

### 5) **Compiler configuration and current tool interfaces**

[Configuration](<../../../13 Configuration and Compiler Options/README.md>) owns option selection. [The bounded erasable-toolchain contract](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) explains what the syntax/import checks cover and what still belongs to the resolver and runtime. Erased type parameters do not imply that every accompanying construct, import graph or host operation is supported by a source-execution tool.

Use the [current learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>) for configuration migration, compiler/API boundaries and artifact assessment. Take an unsupported option or missing tool interface to the relevant configuration/tool owner. Take an unexpected inferred type to the actual signature and its evidence sites. Neither case is resolved by adding more generic parameters indiscriminately.

### 6) **Practice: choose the missing evidence**

Consider an identity call whose source is already string, an invalid blue choice accepted after two inputs expand a candidate union, and a capped deep transform whose remaining nested fields stay required. The first calls for the [literal/source inference probes](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>); an explicit singleton cannot make a broad input meet that contract. The second calls for the same owner's NoInfer comparison and runtime membership check. The third calls for the [depth-cap contract and measured reproduction](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>), not simply a request for a larger compiler budget.

Finally, if parseText<User> receives a numeric name, inspect the [decoder's actual checks](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>). A selected type argument is not the missing runtime proof. These answers name both the owner and the next observation; no separate implementation is needed in a routing lesson.

### 7) **Common confusion**

A generic result, a runtime-created value and validation of external input are distinct. A container's fixed parameter can coexist with a method's fresh parameter; neither placement is universally correct for every callable. Distribution filters types, while a branch narrows a value. A depth cap is a transform policy with a visible stopping result, rather than a promise that the compiler performs less work without changing the contract.

### 8) **Performance note**

Following an owner link does not change program performance. Type arguments and transforms are erased, while collection traversal, construction, parsing and checking performed by their implementations remain. No performance measurement ran for this navigation lesson, and there is no additive-cost formula or cache guarantee established by its domain boundaries. Use the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) to investigate an actual slow compiler workload.

### 9) **Mentor note**

For each practice case, ask the learner to name the inference site or runtime check and predict the result before following the link. A strong answer distinguishes an already widened input, a competing candidate, a transform's stopping policy and an unverified parsed value. If the answer is only "use generics" or "enable strict," ask which operation that change would actually affect and what evidence would confirm it.
