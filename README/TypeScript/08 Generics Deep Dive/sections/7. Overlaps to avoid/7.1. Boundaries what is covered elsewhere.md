## 7.1. Boundaries — what is covered elsewhere

### 1) **Function-level generic basics** (per-call inference, overloads vs generics) — [05 Functions and Callable Types](<../../../05 Functions and Callable Types/README.md>)

**Definition** — call signatures, overload lists, per-call `<T>` inference on functions, `this` parameters, and callback variance live in 05 — this domain deepened them (constraints, `infer`, `in`/`out`, recursion, variadic tuples) without re-teaching them.

**What problem it solves / history** — 05 owns "how do I type this function?"; 08 owns "how do type parameters behave everywhere?" — the split keeps overload-vs-generic judgment (05/2.1) and method-vs-class scope (08/1.3) each in one place.

**Modern guidance** — for function-typing questions start at [2.2. Generic functions](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>); come here for declaration-site mechanics, `infer`, variance annotations, and recursive/variadic patterns.

**Runnable example** — 05 owns the signature, 08 the parameter mechanic (`tsc --strict`):

```typescript
// 05-style: overload vs generic judgment for one function
function totalFee(fee: number): number;
function totalFee(fee: string): string;
function totalFee(fee: string | number): string | number { return fee; }
// 08-style: the parameter mechanic behind the generic alternative
function totalFeeG<T extends string | number>(fee: T): T { return fee; }
console.log(totalFee(7).toFixed(0), totalFeeG("7").toUpperCase()); // 7 7
```

**Common confusion** — "08 replaces 05/2.2" — 08 *builds on* it; function-call ergonomics (overloads, `this`, contextual typing) stay in 05.

**Performance note** — no overlap means no duplicated check-cost guidance — each domain measures its own sites.

**Mentor note** — route "how do I type this callback?" to 05 and "why does `<T>` behave this way?" here — the question's verb (type vs behave) picks the domain.

**Cross-links** — generic functions → [2.2. Generic functions](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>); overloads → [2.1. Function overloads](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>).

### 2) **Utility types and mapped/conditional transforms** (`Partial`/`Pick`/`Exclude`, `keyof` mapping) — [09 Utility Types and Type Transformations](<../../../09 Utility Types and Type Transformations/README.md>)

**Definition** — the stdlib catalog (`Partial`, `Required`, `Pick`, `Omit`, `Exclude`, `Extract`, `ReturnType`, `Awaited`) plus mapped-type (`{ [K in keyof T]: … }`) and conditional-type authoring live in 09 — this domain supplied the prerequisites (`infer` extraction, naked-`T` distribution, `DeepRO` recursion shape) without building the catalog.

**What problem it solves / history** — teaching `Exclude` inside generics would duplicate 09's distributive-law treatment; teaching it only in 09 would leave 2.3's preview dangling — the forward link resolves both: preview here, source of truth there.

**Modern guidance** — use 08 patterns to *read* utilities (`Exclude<T, U> = T extends U ? never : T` is naked-`T` distribution from 2.3); go to 09 to *author* mapped/conditional transforms and to pick the right stdlib name.

**Runnable example** — 08 pattern recognizes the 09 utility (`tsc --strict`):

```typescript
// 08 gave the mechanic (naked-T distribution); 09 will own the catalog
type MyExclude<T, U> = T extends U ? never : T; // preview — full law in 09
type S = MyExclude<"a" | 1 | "b", number>; // "a" | "b"
const s: S = "a";
console.log(s.toUpperCase()); // A
```

**Common confusion** — "`infer`/distributive are 09 topics misplaced here" — mechanics (how `infer` binds, when `T` distributes) belong to parameters; the *catalog* (which utility when) belongs to 09 — mechanism vs selection differ.

**Performance note** — distribution cost guidance here (O(members) per filter) composes with 09's catalog guidance (filter once, reference) — read both for large unions.

**Mentor note** — tell students "you can now *read* every utility; 09 teaches *choosing* among them" — sets the expectation that 09 is selection, not re-teaching.

**Cross-links** — infer preview → [2.3. infer](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>); utility home → [09 Utility Types](<../../../09 Utility Types and Type Transformations/README.md>).

### 3) **Object-type composition and class hierarchies** (`&` vs `extends`, `implements`, mixins) — [04 Objects, Interfaces and Type Aliases](<../../../04 Objects Interfaces and Type Aliases/README.md>) + [06 Classes and Object-Oriented Types](<../../../06 Classes and Object-Oriented Types/README.md>)

**Definition** — object shape composition (`&` vs `extends`, declaration merging, `keyof` queries) lives in 04; class-side generics (parameter properties, `abstract` factories, mixins, `InstanceType`) live in 06 — this domain referenced both (scope sites, `KVCache`, `Box2.of`) without re-teaching them.

**What problem it solves / history** — generic containers sit *atop* object/class mechanics: `Store<T>` needs 04's freshness/optional rules and 06's duality/instantiation rules to be usable — linking (not copying) keeps each rule in its home domain.

**Modern guidance** — design the container shape in 04/06 first (freshness-safe, constructible), then parameterize it here (scope, constraint, default) — shape before parameter, always.

**Runnable example** — shape from 04/06, parameter from 08 (`tsc --strict`):

```typescript
// 04/06 shape (structural container, constructible) + 08 parameter (scope + default)
interface Shelf<T = string> { items: T[]; label?: string }
class ShelfBox<T> { constructor(public shelf: Shelf<T>) {} }
const b = new ShelfBox({ items: ["a"], label: "x" });
console.log(b.shelf.items[0]?.toUpperCase()); // A
```

**Common confusion** — "generic containers need no object rules" — freshness, `readonly`, and `implements` all still apply *inside* `T`'s instantiation — parameters add a layer, they do not replace the shape layer.

**Performance note** — shape checks (04) and instantiation checks (08) compose additively — keep shapes small *and* instantiations cached.

**Mentor note** — review containers in two passes (shape pass per 04/06, parameter pass per 08) — mixed passes miss one layer's bugs.

**Cross-links** — object model → [04 Objects](<../../../04 Objects Interfaces and Type Aliases/README.md>); class model → [06 Classes](<../../../06 Classes and Object-Oriented Types/README.md>).

### 4) **Union/intersection algebra and narrowing** (distributivity in practice, discriminants) — [07 Unions, Intersections and Narrowing](<../../../07 Unions Intersections and Narrowing/README.md>)

**Definition** — `|`/`&` set algebra, discriminated-union design, and control-flow narrowing (`typeof`/`in`/`never`-sink exhaustiveness) live in 07 — this domain used them (distributive preview, `Strings<T>` filter, `never` false branches) without re-teaching them.

**What problem it solves / history** — `Exclude`/`Extract` are *applications* of 07's algebra via 08's distribution mechanic — each domain owns its layer (algebra, mechanism, catalog) so the three compose instead of repeating.

**Modern guidance** — model alternatives in 07 (discriminants, exhaustiveness), parameterize over them here (`Strings<T>`, `ElemOf<T>`), transform them in 09 — alternative → parameter → transform, in that order.

**Runnable example** — 07 algebra through the 08 mechanic (`tsc --strict`):

```typescript
// 07: discriminated union + exhaustive sink; 08: generic filter over it
type Ev = { kind: "click"; x: number } | { kind: "key"; k: string };
type Clicks<T> = T extends { kind: "click" } ? T : never;
function assertNever(x: never): never { throw new Error(`unhandled ${String(x)}`); }
function handle(e: Ev): string {
  if (e.kind === "click") return `x=${e.x}`;
  if (e.kind === "key") return `k=${e.k}`;
  return assertNever(e); // 07 exhaustiveness — never sink
}
const c: Clicks<Ev> = { kind: "click", x: 1 }; // 08 distribution over the 07 union
console.log(handle(c)); // x=1
```

**Common confusion** — "distribution *is* narrowing" — distribution filters *types* at compile time; narrowing refines *values* along control flow — related, not identical; 07 owns the latter.

**Performance note** — filtered unions (08) feed narrower switches (07) — filter once upstream so every downstream `switch` checks fewer members.

**Mentor note** — teach the pipeline order explicitly (model → parameterize → transform → narrow) — students who sequence the four domains stop building filters before modeling the union.

**Cross-links** — unions/narrowing → [07 Unions](<../../../07 Unions Intersections and Narrowing/README.md>); exhaustiveness → [3.2. Exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>).

### 5) **Compiler strictness flags** (`strict`, `strictFunctionTypes`, `--erasableSyntaxOnly`) — [13 Configuration and Compiler Options](<../../../13 Configuration and Compiler Options/README.md>)

**Definition** — `strict` (including `strictNullChecks`, `noImplicitAny`), `strictFunctionTypes`/`strictPropertyInitialization`/`noImplicitOverride`, and `--erasableSyntaxOnly`/`isolatedDeclarations` verification commands live in 13 — this domain cited their effects (fallbacks surfacing, variance strictness, erasable generics) without owning them.

**What problem it solves / history** — flag semantics belong with the compiler-options reference (13), not scattered across 20 domains — one home keeps `tsconfig` advice consistent when defaults evolve (as they did through TS 5.x).

**Modern guidance** — develop this domain under `strict` + `erasableSyntaxOnly` (all examples verified so); take flag questions (which combination surfaces `unknown` fallbacks? does `erasableSyntaxOnly` affect generics?) to 13 when it lands — until then, the per-leaf verification notes (`tsc --strict` + flag where relevant) are authoritative.

**Runnable example** — flags change what the same generic reports (`tsc --strict`):

```typescript
// strictNullChecks ON: T | null forces narrowing (this domain assumes it throughout)
function nameOf<T extends { name: string } | null>(x: T): string {
  return x === null ? "(none)" : x.name; // narrow required — strict surfaces the fallback
}
console.log(nameOf(null), nameOf({ name: "ada" })); // (none) ada
```

**Common confusion** — "generics need special flags" — they need `strict` (like everything) plus nothing else; `--erasableSyntaxOnly` already passes for all-generic syntax (no `enum` trap in this domain).

**Performance note** — `strict` adds check-time precision at zero emit cost — the performance guidance here (cache instantiations, cap recursion) assumes `strict` on.

**Mentor note** — standardize team `tsconfig` on `strict: true` before teaching generics — unstrict generics teach `any`-shaped habits that `strict` later punishes.
