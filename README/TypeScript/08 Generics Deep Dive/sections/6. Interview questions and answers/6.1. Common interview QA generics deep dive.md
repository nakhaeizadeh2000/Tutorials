## 6.1. Common interview QA — generics deep dive

### 1) **Where can `<T>` appear and what scope does each site give?** (function vs interface vs class vs alias)

**Definition** — four sites, three lifetimes: function `<T>` is fresh per call (`map<T, U>` re-solves every invocation); interface/class `<T>` is fixed per value (`KVCache<K, V>` chosen at construction, shared by all members); alias `<T>` is fixed per reference (`Api<T>` instantiates where written). `static` members cannot see class `T` — no value fixes it yet.

**What problem it solves / history** — interviewers ask this to separate template-users from lifetime-thinkers: candidates who answer "on functions and classes" describe syntax; candidates who add "per call vs per value" predict the `at<T>`-guessing bug and the `Runner<T>` annotation tax before writing them — the difference between using generics and designing with them.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer with the lifetime test ("when is `T` chosen?") plus one example per site, then volunteer the `static` exclusion — it signals production experience. Full treatment in [1.1. Declaration and erasure](<../1. Generic Fundamentals/1.1. Type parameters declaration instantiation and erasure.md>) + [1.3. Scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>).

**Runnable example** — three lifetimes in nine lines (`tsc --strict`):

```typescript
function perCall<T>(x: T): T { return x; } // fresh per call
class PerValue<T> { constructor(public v: T) {} } // fixed per value
type PerRef<T> = { data: T }; // fixed per reference
console.log(perCall("a").toUpperCase(), new PerValue(1).v.toFixed(0));
const r: PerRef<boolean> = { data: true };
console.log(r.data);
class WithStatic<T> {
  constructor(public v: T) {}
  static make<U>(x: U): WithStatic<U> { return new WithStatic(x); } // own <U>, not T
}
console.log(WithStatic.make("hi").v.toUpperCase()); // HI
```

**Common confusion** — "generic methods inherit class `T` automatically" — they do (no redeclaration needed); redeclaring `<T>` on the method *shadows* the class parameter with a fresh one — the shadowing bug behind several "why did my type change?" incidents.

**Performance note** — all sites erase to identical emit — scope is a checking-lifetime choice with zero runtime cost; per-value caching reuses instantiations across members.

**Mentor note** — strong answers name the `static` exclusion unprompted — probe with "can a static method use the class's `T`?" when candidates skip it. Hiring signal: lifetime-first reasoning predicts API-design quality.

Static members](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>).

### 2) **What does `T extends { length: number }` unlock — and what does it preserve?** (constraint vs precision)

**Definition** — the constraint unlocks `.length` inside the body (the only assumption the implementation may use) while the *parameter* `T` preserves the caller's subtype end to end (`"hello"` in, `string` out — never widened to `{ length: number }`). Body sees the bound; caller keeps the identity.

**What problem it solves / history** — the "constraints widen" myth produced overload-per-literal APIs (`onGet`, `onPost`) that a single `M extends string` returning `M` already covered — interviewers probe this to see whether candidates delete code (one generic) or multiply it (N overloads) when precision matters.

**Modern guidance** — as of TypeScript 5.9 era, return the parameter (`M`), never the constraint (`string`); constrain the member touched, nothing more. Full treatment in [2.1. Constraints](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>).

**Runnable example** — bound unlocks, parameter preserves (`tsc --strict`):

```typescript
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b; // body uses .length (bound's gift)
}
const w = longest("abcd", "xy"); // T = string — caller's identity kept
console.log(w.toUpperCase()); // ABCD — still a string, not { length: number }
function keep<M extends string>(m: M): M { return m; }
function handle(m: "get" | "post"): string { return m; }
console.log(handle(keep("get"))); // compiles — "get" survived the bound
```

**Common confusion** — "returning `T` leaks the constraint" — the constraint never appears in the result; hovering `w` shows `string`. "tighter constraints narrow results" — constraints filter *admissibility*, inference decides *identity* — tightening rejects callers without narrowing survivors.

**Performance note** — constraints shrink solver search (fewer candidates per site) — the precise signature checks faster than the `any`-shaped alternative while preserving more information.

**Mentor note** — ask candidates to hover-compare `longest("a","bb")` (`string`) against a version returning `{ length: number }` — the prediction ("which hover?") separates constraint-understanders in seconds. Follow-up: "when would you return the constraint instead?" (never for precision-preserving APIs; only when intentionally normalizing).

**Cross-links** — constraints → [2.1. Constraints](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>); literals → [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>).

### 3) **When is an explicit type argument required?** (no site, widened literal, `never[]` fallback)

**Definition** — three situations: no inference site (`empty<number>()` — nothing flows into `T`), widened literal (`invoke<"get">` — inference would keep `string` from a `let` source), and empty-collection fallback (`head<string>([])` — zero elements infer `never`). Everywhere else, inference suffices and explicit arguments rot.

**What problem it solves / history** — blanket-explicit (`identity<string>("hi")` everywhere) and blanket-inferred (`make()` hoping for magic) both fail — one rots on refactor, the other falls back to `unknown`. The three-situation rule from [1.2. Inference](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) gives the interview answer structure: site-missing, precision-lost, evidence-empty.

**Modern guidance** — as of TypeScript 5.9 era, diagnose via hover (`unknown` → add site/argument; `string`-from-`"get"` → `as const`/explicit; `never[]` → seed/annotate), then choose the cheapest fix in that order. Redundant explicit arguments are review debt — flag them.

**Runnable example** — three situations, three one-line fixes (`tsc --strict`):

```typescript
function empty<T>(): T[] { return []; }
function head<T>(xs: T[]): T | undefined { return xs[0]; }
function reg<M extends string>(m: M): M { return m; }
const a = empty<number>(); // required: no site
const b = reg<"get">("get"); // precision: pin the literal
const c = head<string>([]); // fallback: name the element
console.log(a.length, b.toUpperCase(), c ?? "empty"); // 0 GET empty
const d = head(["x"]); // inference suffices — no brackets
console.log(d?.toUpperCase()); // X
```

**Common confusion** — "explicit arguments are always safer" — stale arguments (`echo<string>(42)` after refactor) error *against* the value — inference tracks refactors, brackets freeze them. "the compiler should infer from return context alone" — it uses return context (contextual typing) but cannot invent from nothing — `empty()` with no site and no context stays `unknown`.

**Performance note** — explicit arguments skip inference (verify-only, cheaper per call) — prefer them in generated code with thousands of identical calls; prefer inference in hand-written code where values evolve.

**Mentor note** — pose the hover-reading drill ("hover says `unknown` — mode and fix?") — candidates who answer "no site → explicit or seed" diagnose production generics; candidates reaching for `as` do not. Strong follow-up: "which fix for a `let`-widened literal — `as const` or explicit?" (source fix vs call fix — either, but source scales).

**Cross-links** — inference → [1.2. Inference](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>); widening → [3.2. Widening](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>).

### 4) **What does `infer U` do inside `T extends Array<infer U> ? U : never`?** (naming the solved piece)

**Definition** — `infer U` binds `U` by *pattern-matching*: the checker matches `T` against `Array<U>`, solves for the hole (`string[]` → `U = string`), and the true branch returns the binding. Legal only in the `extends` pattern of a conditional; the false branch (`never`) defines the no-match contract.

**What problem it solves / history** — before `infer` (TS 2.8), each wrapper needed bespoke extraction (`T[number]`, `ReturnType` magic, manual tuple indexing) — interviewers ask this to check whether candidates see the *one* mechanism (match → name → return) behind `Element`, `ReturnType`, `Awaited`, and `Head` alike.

**Modern guidance** — as of TypeScript 5.9 era, memorize four patterns (return, element, head, payload) and prefer stdlib names at call sites — write `infer` only for project-specific wrappers. Full treatment in [2.3. infer](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>).

**Runnable example** — one shape, three wrappers (`tsc --strict`):

```typescript
type ElemOf<T> = T extends Array<infer U> ? U : never;
type Ret<F> = F extends (...args: never[]) => infer R ? R : never;
type Head<T> = T extends [infer H, ...unknown[]] ? H : never;
const e: ElemOf<number[]> = 1;
const r: Ret<() => string> = "hi";
const h: Head<["a", 1]> = "a";
console.log(e.toFixed(0), r.toUpperCase(), h.toUpperCase()); // 1 HI A
```

**Common confusion** — "`infer` declares a callable generic" — it binds by matching within one conditional evaluation, not per call. "false branch is filler" — it is the failure contract (`never` vs passthrough) that callers branch on — always chosen deliberately.

**Performance note** — matches cache per instantiation; chains (`Payload<Ret<F>>`) nest one entry per level — fine under ~4 levels, hover-heavy beyond.

**Mentor note** — "destructuring for types" (`const [h] = arr` ↔ `[infer H, ...unknown[]]`) lands the concept in one analogy. Ask for `Tail` after `Head` — composition on the spot proves transfer.

**Cross-links** — infer → [2.3. infer](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>); utility catalog → [09 Utility Types](<../../../09 Utility Types and Type Transformations/README.md>).

### 5) **`in T` vs `out T` — what breaks in the wrong position?** (variance enforcement)

**Definition** — `out T` promises production-only (using `T` as a parameter errors TS2378); `in T` promises consumption-only (returning `T` errors). The annotation converts a consumer-side assignment mystery into an author-side declaration error — wrong-position use fails where written, not three packages away.

**What problem it solves / history** — unannotated two-way `T` produced invariant interfaces whose assignment errors blamed the consumer ("why won't my `Cell<Cat>` assign?") instead of the `write` method causing invariance. Annotations move the error to the design moment — interviewers use this to test API-design thinking over syntax recall.

**Modern guidance** — as of TypeScript 5.9 era, annotate public one-direction interfaces (`Provider<out T>`, `Handler<in T>`); leave two-way internals unannotated (honest invariance). Fix TS2378 by design (method-level `<U>` or dropped annotation), never with `any`. Full treatment in [3.1. Variance](<../3. Variance and Advanced Generic Patterns/3.1. Variance in out annotations and generic positions.md>).

**Runnable example** — direction enforced at the declaration (`tsc --strict`):

```typescript
interface Source<out T> { read(): T; }
interface Sink<in T> { write(x: T): void; }
// interface Liar<out T> { write(x: T): void; } // error TS2378 — consumed under out
interface Fixed<out T> { read(): T; parse<U>(x: U, f: (u: U) => T): T; } // method <U> for input
const s: Source<string> = { read: () => "hi" };
console.log(s.read().toUpperCase()); // HI
```

**Common confusion** — "annotations change assignability rules" — they declare intent the checker *verifies*; measurement (inferred variance) already assigned the same way — annotations add speed plus early errors, not new semantics. "methods respect `out` strictly" — methods stay bivariant; property-style callbacks are strict — annotation does not rewrite method checking.

**Performance note** — declared direction skips per-member variance measurement (O(members) saved per comparison) — meaningful on library-surface interfaces compared hundreds of times.

**Mentor note** — ask "who is TS2378 for — author or consumer?" (author, months early) — the answer reveals design-moment thinking. Hiring signal: candidates who split `Cell` into `Source`/`Sink` unprompted design separable abstractions.

Variance core](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>).
