## 6.1. Common interview QA — generics deep dive

A useful answer explains who chooses a type, which evidence supports it, and what the implementation must do. These questions synthesize the domain; use the linked lessons for the complete mechanisms. Follow-ups change an assumption so an answer cannot rely on memorized syntax alone.

All programs use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts` and run `node dist/FILE.js`. Activate negatives separately and use the same flags with --noEmit instead of --outDir dist.

### 1) **Where can a parameter appear and when is it selected?**

Functions, methods, classes, interfaces and aliases can declare type parameters at supported sites. A generic call signature allows fresh choices at calls. A particular Reader<number> view fixes its read result to number. An interface can itself contain a generic call signature, so the keyword interface does not by itself mean a single fixed callable choice.

An instance method can use its class parameter or introduce a separate parameter. A static method cannot use the instance-side class parameter; it can declare its own. Do not turn these static relationships into a claim that JavaScript creates a specialized class for each argument. See [declarations and erasure](<../1. Generic Fundamentals/1.1. Type parameters declaration instantiation and erasure.md>) and [scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>).

For a follow-up, compare Reader<T> with a nongeneric interface containing a generic call signature. A sound answer identifies which declaration owns T and whether one stored value is being promised or multiple calls can choose independently.

### 2) **What does a constraint allow without proving the result?**

T extends { length: number } allows length access and restricts admitted arguments. If a function promises to return T, its body must honor the actual supplied subtype, not merely construct something satisfying the bound. A transforming function can honestly return string instead of promising the original literal. Constraints and inference interact; do not guess the local result from the bound alone.

In choices.ts below, longest returns one of its supplied values and its live probe establishes the local literal union. An object containing only length would not satisfy every possible T. Ask the learner to explain that distinction using an input with an additional required member. The [constraint owner](<../2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) demonstrates that body obligation.

### 3) **When should a caller supply an explicit argument?**

Use one when it expresses the intended contract and available inference or context does not express it adequately. A factory can also infer from a return context. An empty array's inference depends on its position and context; avoid a universal rule that every empty expression has the same type. An explicit argument must still accept the runtime arguments, and cannot reinterpret an already widened string as a specific literal.

Save as choices.ts.

```typescript
interface Universal { <T>(value: T): T; }
const identity: Universal = value => value;
interface Reader<T> { read: () => T; }
const reader: Reader<number> = { read: () => 7 };
class Stored<T> {
  value: T;
  constructor(value: T) { this.value = value; }
  static of<U>(value: U): Stored<U> { return new Stored(value); }
  // static invalid(value: T): void {} // TS2302
}
console.log(identity("a").toUpperCase(), identity(1).toFixed(0), reader.read());
console.log(Stored.of("hi").value.toUpperCase());

function longest<T extends { length: number }>(left: T, right: T): T {
  return left.length >= right.length ? left : right;
}
const word = longest("abcd", "xy");
console.log(word.toUpperCase());
// longest(1, 2); // TS2345
// function counterfeit<T extends { length: number }>(): T { return { length: 0 }; } // TS2322
function empty<T>(): T[] { return []; }
const noContext = empty();
const contextual: number[] = empty();
const explicit = empty<string>();
let widened = "get";
function keep<M extends string>(value: M): M { return value; }
// keep<"get">(widened); // TS2345
console.log(noContext.length, contextual.length, explicit.length, keep("get"));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Word = Expect<Equal<typeof word, "abcd" | "xy">>;
type Unselected = Expect<Equal<typeof noContext, unknown[]>>;
type FromContext = Expect<Equal<typeof contextual, number[]>>;
```

The output is `A 1 7`, `HI`, `ABCD`, then `0 0 0 get`. The same universal callable handles string and number calls. The three empty arrays have equal runtime lengths while their static element contracts differ. A declared contextual type is one valid route; an explicit argument is another. Neither creates an element. See [inference, explicit arguments and NoInfer](<../1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) for evidence and competing-candidate cases.

For a follow-up, pass an unchecked parsed value through a selected result argument. The answer must explain that the argument supplies no runtime validation and identify the missing decoder or value check.

### 4) **What does infer bind and what happens on a non-match?**

Inside a conditional extends pattern, infer names a captured part for use in the true branch. The false branch is an intentional result contract, such as never. A mutable-array pattern does not match every readonly input, and a required-head tuple pattern does not match a possibly empty array. Neither extraction nor never creates a runtime element.

Save as patterns.ts.

```typescript
type ElementOf<T> = T extends readonly (infer Item)[] ? Item : never;
type Head<T> = T extends readonly [infer First, ...unknown[]] ? First : never;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type E = Expect<Equal<ElementOf<readonly number[]>, number>>;
type H = Expect<Equal<Head<readonly ["a", 1]>, "a">>;
type Empty = Expect<Equal<Head<[]>, never>>;
type Open = Expect<Equal<Head<string[]>, never>>;
const element: ElementOf<readonly number[]> = 1;
const first: Head<readonly ["a", 1]> = "a";
console.log(element.toFixed(0), first.toUpperCase());
// const fabricated: Head<[]> = undefined; // TS2322
// type Invalid = infer Item; // TS1338
```

The output is `1 A`; the four probes also compile. For a follow-up, ask for the last item of a readonly tuple and its empty/non-tuple policy. A complete explanation chooses a pattern and non-match result, rather than asserting that an empty tuple contains a never value. The [infer owner](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) includes head, tail and Awaited distinctions; [variadic composition](<../3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>) covers actual argument forwarding.

### 5) **What can variance annotations establish and where do they stop?**

A producer is covariant when its result can safely widen; a consumer is contravariant when it can accept the broader input wherever a narrower input is required. Annotations describe intended directions for supported generic declarations. A wrong function-property direction can produce TS2636. Method parameters retain their compatibility exception, so not every consuming method under out is rejected.

Save as directions.ts.

```typescript
interface Animal { name: string; }
interface Cat extends Animal { meow: () => string; }
interface Source<out T> { read: () => T; }
interface Sink<in T> { write: (value: T) => void; }
const cats: Source<Cat> = { read: () => ({ name: "Milo", meow: () => "meow" }) };
const animals: Source<Animal> = cats;
const anyAnimal: Source<Animal> = { read: () => ({ name: "animal" }) };
// const wrongSource: Source<Cat> = anyAnimal; // TS2322
const animalSink: Sink<Animal> = { write: value => console.log(value.name) };
const catSink: Sink<Cat> = animalSink;
catSink.write(cats.read());
console.log(animals.read().name);
const onlyCats: Sink<Cat> = { write: value => console.log(value.meow()) };
// const wrongSink: Sink<Animal> = onlyCats; // TS2322
// interface WrongOut<out T> { write: (value: T) => void; } // TS2636
interface MethodOut<out T> { write(value: T): void; } // Accepted; the annotation is not a complete soundness proof.
```

The output is Milo on two lines. The reverse assignments fail. The accepted MethodOut declaration and rejected property declaration are different fixtures; do not report the rejected property result as proof that the method form failed.

Annotations have limits for instantiation-based comparisons and do not force their direction on every structural comparison. They are optional in ordinary APIs, and a fresh method parameter does not automatically repair remaining outer input/output relationships. The [annotation owner](<../3. Variance and Advanced Generic Patterns/3.1. Variance in out annotations and generic positions.md>) demonstrates these limits with runtime counterexamples, supported by the [primary current guidance](https://www.typescriptlang.org/docs/handbook/2/generics.html#variance-annotations).

For a follow-up, ask whether a mutable field container is automatically invariant. A strong answer distinguishes the intended mutation safety from TypeScript's actual accepted assignments and proposes a stricter function-property contract when appropriate; see [variance foundations](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>).

### 6) **Common confusion**

Generic keywords do not determine scope by themselves; the parameter's declaration and uses determine the relationship. A constraint does not manufacture an arbitrary T, an explicit argument does not repair invalid evidence, and an infer pattern's never result does not inhabit an empty runtime position. A variance annotation is also not a runtime guard or a guarantee that every unsafe method use is rejected.

No universal speed advantage follows from explicit arguments, small constraints or direction annotations; no hover-depth threshold or per-comparison savings was measured here. ### 8) **Mentor note**

Ask for a prediction, a reason and a changed-assumption follow-up. Evaluate whether the explanation accounts for the program's actual result and rejection, rather than rewarding an unprompted term or a guessed editor display.

As a small design exercise, add map<U>(fn: (value: T) => U): Stored<U> to Stored. Implement it by applying fn to this.value and constructing a new Stored. Mapping Stored.of(7) with n => n.toFixed(1) must produce a string container containing 7.0; the original container still holds 7. Reject a boolean value assigned through that result's string field. The fresh U and fixed T serve different relationships in one class.
