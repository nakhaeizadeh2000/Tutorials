## 3.1. Variance — in out annotations and generic positions

Variance annotations describe a generic parameter's assignment relationship at its declaration. They are not use-site casts, runtime guards or a way to turn structural types into nominal identities. Start with the structural producer/consumer contract, then use an annotation only when you have a specific reason and understand the comparisons where it applies.

[Variance foundations](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>) establishes assignment direction and mutable-field/method exceptions. This leaf owns the optional annotations and their diagnostic/comparison limits. Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under its filename and compile independently with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate each commented negative separately and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **What in and out declare**

Out describes covariance: a Cat-producing source can fulfill an Animal-producing contract. In describes contravariance: a consumer accepting any Animal can fulfill a Cat-consumer contract. In out describes invariance. The function-property cell below has opposing input and output requirements, so neither related instantiation can substitute for the other under the declared strict checking.

Save as `directions.ts`.

```typescript
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
interface Source<out T> { read: () => T }
interface Sink<in T> { write: (value: T) => void }
interface Cell<in out T> { read: () => T; write: (value: T) => void }
const cat: Cat = { name: "Mira", meow: () => "meow" };
const other: Animal = { name: "Other" };
const catSource: Source<Cat> = { read: () => cat };
const animalSource: Source<Animal> = catSource;
const animalSink: Sink<Animal> = { write: value => console.log("accepted", value.name) };
const catSink: Sink<Cat> = animalSink;
console.log(animalSource.read().name);
catSink.write(cat);
const onlyCats: Sink<Cat> = { write: value => console.log(value.meow()) };
const onlyAnimals: Source<Animal> = { read: () => other };
// const wrongSink: Sink<Animal> = onlyCats; // TS2322
// const wrongSource: Source<Cat> = onlyAnimals; // TS2322
function cell<T>(value: T): Cell<T> {
  return { read: () => value, write: next => { value = next; } };
}
const cats = cell<Cat>(cat);
const animals = cell<Animal>(other);
console.log(cats.read().meow(), animals.read().name);
// const wider: Cell<Animal> = cats; // TS2322
// const narrower: Cell<Cat> = animals; // TS2322
```

The output is `Mira`, `accepted Mira`, then `meow Other`. All three annotations agree with the relationships represented by these function-property members. The [primary 4.7 introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#optional-variance-annotations-for-type-parameters) gives the feature's version and input/output examples. The keywords erase; they do not change which objects these functions actually return or accept.

### 2) **Read the actual variance diagnostic and member syntax**

An identifiably incompatible annotation can produce TS2636 at the declaration. For example, an output annotation on a strict function-property consumer contradicts its input requirement. Method parameters retain the compatibility exception, however, so a method-shaped consuming use under out need not produce that diagnostic.

Save as `diagnosis.ts`.

```typescript
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
// interface WrongOut<out T> { write: (value: T) => void } // TS2636
// interface WrongIn<in T> { read: () => T } // TS2636
// interface WrongParser<out T> { parse: <Input>(raw: Input, decode: (raw: Input) => T) => T } // TS2636

interface MethodOut<out T> { write(value: T): void } // Accepted; not a complete safety guarantee.
const catOnly: MethodOut<Cat> = { write(value) { console.log(value.meow()); } };
const widened: MethodOut<Animal> = catOnly;
try { widened.write({ name: "Other" }); }
catch (error) { console.log(error instanceof TypeError ? "annotated method: TypeError" : "unexpected error"); }

type Decoder<out Result> = (raw: unknown) => Result;
const numberDecoder: Decoder<number> = raw => {
  if (typeof raw !== "number") throw new TypeError("number required");
  return raw;
};
console.log(numberDecoder(42).toFixed(1));
try { numberDecoder("42"); }
catch (error) { console.log(error instanceof TypeError ? error.message : "unexpected error"); }
// function unsupported<out T>(value: T): T { return value; } // TS1274: not this declaration site
```

The output is `annotated method: TypeError`, `42.0`, then `number required`. WrongParser still uses T in the decoder parameter's return and in its own result. Moving only the raw input to a fresh Input did not remove that opposing relationship. Reconsider the intended contract rather than mechanically renaming an input parameter. Decoder represents a different, honest contract: it accepts unknown and produces one chosen result type, with actual runtime checks in its implementation.

The method example accepts an unsafe widened consumer and then fails on an ordinary Animal. A keyword did not make that method input strict. Use a function-property consumer with an implementation that accepts the intended inputs, as in Sink, when that is the API contract. Dropping an annotation also does not automatically make a method-based read/write shape invariant. The full [method exception](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) explains why syntax matters.

An annotation is written on a supported generic declaration, such as these interfaces or the function type alias. It is not permitted on the generic function declaration shown in the negative. [Generic scope](<../1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>) owns which parameter a method should relate, while [boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) owns fuller decoder evidence.

### 3) **Know when the annotation participates**

The annotation can participate when comparing instantiations of a generic type. It does not rewrite ordinary structural comparisons. To make that distinction visible, the following program deliberately overstates a producer's variance. This is a diagnostic experiment, not a recommended declaration to publish.

Save as `comparisons.ts`.

```typescript
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
const cat: Cat = { name: "Mira", meow: () => "meow" };
interface ForcedInvariant<in out T> { make: () => T } // Deliberately stronger than the structure needs.
const cats: ForcedInvariant<Cat> = { make: () => cat };
// const named: ForcedInvariant<Animal> = cats; // TS2322: generic-instantiation comparison
const structural: ForcedInvariant<Animal> = { make: (): Cat => cat }; // Accepted structural comparison.
console.log(structural.make().name);

interface Producer<out T> { make: () => T } // Matches the actual output-only relation.
const honestCats: Producer<Cat> = { make: () => cat };
const honestAnimals: Producer<Animal> = honestCats;
console.log(honestAnimals.make().name);
```

The output is `Mira`, then `Mira`. The rejected named assignment and accepted object literal show why a stronger annotation cannot be used to force nominal invariance across all structural inputs. Restore the producer's actual relation instead of relying on that inconsistency. The [current primary guidance](https://www.typescriptlang.org/docs/handbook/2/generics.html#variance-annotations) documents the comparison boundary and warns that the checker may choose comparison strategies differently across versions. These local results are evidence for the declared compiler, not an API technique for exploiting that choice.

Use inferred variance for ordinary declarations. Temporary annotations can help investigate a specific relationship, and a carefully validated annotation may address a demonstrated problem in a complex type. Public visibility or a one-way-looking name is not enough to justify annotating every parameter. Before retaining one, verify its structural relation, method/property syntax and relevant assignments. The declaration-site diagnostic is useful evidence, but acceptance alone is not proof of every desired safety property.

### 4) **Common confusion**

An annotation being accepted does not mean that every use of T is checked according to a simple input/output slogan. Method bivariance remains relevant. Similarly, in out can be accepted as a stronger annotation without changing the structure of an anonymous value supplied to that target.

Changing an input to a fresh method parameter changes the API's relationship. It is not a general variance repair: other parameter or callback positions may still use the outer T. Preserve the intended behavior and check the full signature, rather than treating TS2636 as an instruction to add another letter.

### 5) **Performance note**

Variance annotations erase, and the functions, writes, guards and throws remain. No checking-speed improvement was measured in these examples. TypeScript already infers variance; it does not necessarily redo a full member walk for each unannotated assignment. The primary guidance allows a possible small benefit for carefully profiled complex types when variance inference itself is the bottleneck. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before making such a claim or changing a public contract for speed.

### 6) **Mentor note**

Ask the learner to predict the four rejected direction assignments, then explain the accepted method annotation and its TypeError. A sound answer distinguishes a function-property input from a method parameter and keeps runtime producer behavior separate from the annotation.

For a diagnostic exercise, turn WrongOut into an honest function-property consumer and supply an implementation accepting every Animal. Verify that it can fill a Cat sink, while a Cat-only implementation cannot fill the Animal sink. Then explain why changing only an annotation on MethodOut would not by itself validate the runtime inputs. Finish with the named-versus-anonymous producer comparison and identify why the deliberately forced annotation should be removed.
