## 3.1. Variance — `in` / `out` annotations and generic positions

### 1) **What `in` / `out` declare** (use-site direction the checker verifies)

**Definition** — `interface Source<out T> { read(): T }` marks `T` as *produced* (covariant: `Source<Cat>` assignable to `Source<Animal>`), while `interface Sink<in T> { write(x: T): void }` marks `T` as *consumed* (contravariant: `Sink<Animal>` assignable to `Sink<Cat>`). Unannotated parameters get *inferred* variance; the annotation makes the intent explicit and machine-checked (TS 4.7+).

**What problem it solves / history** — inferred variance silently accepted interfaces whose `T` flowed both ways, then rejected assignments with inscrutable "not assignable" errors far from the cause — library authors could not state "this container only produces `T`" and have misuse fail at the declaration. Explicit annotations (TS 4.7) turned intent into a checked contract: using `T` in the wrong position errors where it is written (`TS2378`), not in a consumer three packages away.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), annotate one-direction `T` in public library interfaces — producers (`Reader`, `Provider`, `Factory`) get `out`, consumers (`Writer`, `Handler`, `Validator`) get `in`. Leave internal two-way containers (`Box<T>` with get *and* set) unannotated — inferred invariance is the honest answer. Foundations live in [3.1. Variance](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>); callable specifics in [3.2. Callback variance](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>).

**Runnable example** — direction decides assignability (good vs bad, `tsc --strict`):

```typescript
// good — producer is covariant: Cat source serves where Animal source expected
interface Animal { name: string; }
interface Cat extends Animal { meows: boolean; }
interface Source<out T> { read(): T; }
const catSrc: Source<Cat> = { read: () => ({ name: "m", meows: true }) };
const animalSrc: Source<Animal> = catSrc; // ok — producing Cats satisfies Animal readers
console.log(animalSrc.read().name); // m

// good — consumer is contravariant: Animal sink serves where Cat sink expected
interface Sink<in T> { write(x: T): void; }
const animalSink: Sink<Animal> = { write: (a) => console.log(a.name) };
const catSink: Sink<Cat> = animalSink; // ok — accepting any Animal handles Cats
catSink.write({ name: "m", meows: true });

// bad — two-way T is invariant: neither direction assigns
interface Cell<T> { read(): T; write(x: T): void; }
// const c: Cell<Animal> = null as unknown as Cell<Cat>; // error TS2416 — invariant
// fix — split into Source<out T> + Sink<in T> when directions genuinely separate
```

**Common confusion** — "annotating `out` makes assignment *more* permissive" — it makes the *declared* direction assignable and the *opposite* use an error — stricter at the declaration, clearer at the use. "`in`/`out` change runtime behavior" — purely checker-side; emit identical with or without annotations. "methods are always checked strictly" — methods are *bivariant* (unsound escape for ergonomics); property-style callbacks are strict — annotation does not change method bivariance (see [3.2. strictFunctionTypes](<../../../02 The Type System Core/sections/3. Soundness and variance/3.2. Function variance and strictFunctionTypes.md>)).

**Performance note** — variance annotations *speed up* checks: the checker trusts the declared direction instead of measuring each member's position (O(members) per comparison saved). Large generic interfaces compared in hot paths (collections, streams) check measurably faster annotated — one keyword, linear saving per assignment.

**Mentor note** — teach with arrows: `out T` (values flow *out* of the interface toward readers — Cat-out serves Animal-out), `in T` (values flow *in* from callers — Animal-in serves Cat-in). Exercise: remove `out` and ask what still compiles (inference agrees), then misuse `T` as a parameter and compare errors — annotated fails fast at the interface, unannotated fails late at the consumer.

### 2) **Reading variance errors** (wrong-position use fails fast at the declaration)

**Definition** — `interface Bad<out T> { write(x: T): void }` errors `TS2378: Type 'T' is declared here but used as a parameter` — the annotation caught `T` consumed where only production was promised. The fix is one of two: widen the annotation (drop `out`, accept invariance) or move the use (accept the value through a method-level generic instead of the class parameter).

**What problem it solves / history** — without annotations, direction mistakes surfaced as assignment errors at *consumer* sites — "why can't I assign my `Cell<Cat>` to `Cell<Animal>`?" with no pointer to the `write` method causing invariance. Declaration-site errors invert the diagnosis: the author learns at authoring time that the interface cannot honestly promise `out`, and consumers never see the confusion.

**Modern guidance** — as of TypeScript 5.9 era, treat TS2378 as a design question, not a syntax error: does this interface *really* only produce `T`? If yes, move the consuming use to a method-level `<U>` (`parse<U>(x: U): T` — input is per-call, not the class parameter). If no, drop the annotation and document invariance. Never silence with `any` — the annotation was protecting a real consumer.

**Runnable example** — error at the declaration, fix by design (good vs bad, `tsc --strict`):

```typescript
// good — consuming use moved to a method-level parameter: class T stays out-only
interface Parser<out T> {
  parse<U>(input: U, decode: (raw: U) => T): T;
}
const p: Parser<number> = { parse: (input, decode) => decode(input) };
console.log(p.parse("42", Number).toFixed(0)); // 42

// good — honest invariance: reads and writes share T, no annotation claimed
interface RW<T> { read(): T; write(x: T): void; }
const rw: RW<string> = { read: () => "hi", write: (s) => console.log(s) };
console.log(rw.read().toUpperCase()); // HI

// bad — annotation lies about direction (kept as commented error demo)
// interface Liar<out T> { write(x: T): void; } // error TS2378 — T consumed under out
// fix — Parser<out T> (method-level <U> for input) or RW<T> (drop annotation, own invariance)
```

**Common confusion** — "TS2378 means variance is broken" — TS2378 means the *annotation* caught a real two-way use — the interface was never one-directional. "method-level `<U>` weakens the interface" — it strengthens it: the class parameter keeps its honest direction while the method stays flexible per call. "dropping the annotation loses safety" — dropping a *lying* annotation restores the checker's measured variance — honesty over aspiration.

**Performance note** — declaration-site errors cost one check pass at authoring time and save every consumer comparison after — the cheapest error location in the pipeline. No emit or runtime effect.

**Mentor note** — show the `Liar` error live and ask "who is this error *for* — the author or the consumer?" — the author, months before any consumer exists. That reframes annotations as API-design tests, not type gymnastics. Exercise: fix `Liar` both ways (method-level `<U>` vs dropped annotation) and state which contract each fix promises — proves the error was a design fork, not a typo.

### 3) **When to annotate** (public one-direction interfaces; internals rely on inference)

**Definition** — annotate when three conditions hold: the interface is *public* (consumers compare instantiations across package boundaries), `T` flows *one way* (all members produce or all consume), and the promise is *stable* (future members will respect the direction). Otherwise, inferred variance already answers correctly — the annotation would add ceremony without information.

**What problem it solves / history** — blanket-annotation drives (`out` everywhere "for performance") produced lying interfaces that broke when the next PR added a consuming member — every consumer's assignment flipped from ok to error overnight, with the annotation (not the new member) blamed. Selective annotation — public, one-way, stable — kept the signal trustworthy: annotated means *guaranteed*, unannotated means *measured*.

**Modern guidance** — as of TypeScript 5.9 era, annotate stdlib-shaped abstractions (`Reader<out T>`, `Writer<in T>`, `Handler<in T>`, `Provider<out T>`); skip domain containers that genuinely go both ways (`Store<T>`, `KVCache<K, V>`), internal helpers (consumers are in-repo and errors stay local), and evolving interfaces (direction not yet settled — annotate when it stabilizes, not before).

**Runnable example** — annotate the stable abstraction, skip the evolving one (good vs bad, `tsc --strict`):

```typescript
// good — stable public abstraction: direction is the contract
interface Provider<out T> { get(): T; }
interface Consumer<in T> { accept(x: T): void; }
const numP: Provider<number> = { get: () => 7 };
const numC: Consumer<number> = { accept: (n) => console.log(n.toFixed(0)) };
console.log(numP.get()); // 7
numC.accept(7); // 7.0 logged

// good — evolving internal container: inference measures, no promise made
interface Draft<T> { read(): T; stage(x: T): void; } // two-way today; direction may change
const d: Draft<string> = { read: () => "v1", stage: (s) => console.log(s) };
console.log(d.read().toUpperCase()); // V1

// bad — premature annotation on an evolving interface invites the next-PR break
// interface Draft2<out T> { read(): T; stage(x: T): void; } // TS2378 today, not next quarter
// fix — Draft<T>: annotate when the direction stabilizes into a public promise
```

**Common confusion** — "unannotated means unknown variance" — unannotated means *measured* variance (the checker computes it per comparison) — always correct, just slower and implicit. "annotations are required for correctness" — correctness comes from measurement; annotations add speed plus a design promise — skip them where neither pays. "internal code should match public style" — internal errors stay in-repo and cheap; public errors cross package boundaries and expensive — annotate at the boundary.

**Performance note** — annotation value scales with comparison count: a public `Provider<T>` compared at 500 consumer sites saves 500 variance measurements; an internal helper compared twice saves two. Annotate where the multiplication pays (library surface), skip where it does not (two-use internals).

**Mentor note** — the three-condition checklist ("public? one-way? stable?") fits a review comment — three yeses → annotate; any no → measure. Exercise: take an internal two-way container, annotate `out`, read TS2378, then decide (drop vs split into Source/Sink) — the decision, not the keyword, is the lesson. Link to API-design guidance: annotations are promises to strangers, not notes to self.
