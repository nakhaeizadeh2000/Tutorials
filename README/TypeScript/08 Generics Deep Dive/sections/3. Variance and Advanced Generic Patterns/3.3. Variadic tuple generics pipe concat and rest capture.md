## 3.3. Variadic tuple generics — pipe, concat and rest capture

### 1) **Labeled tuple rest** (arity plus names survive through the generic)

**Definition** — `function f<Args extends unknown[]>(...args: Args)` captures the *whole argument list* as one tuple type — arity, order, element types, and (with labels) parameter names. Labels (`...args: [first: string, count: number]`) flow into tooltips and apply/fill order, so the generic boundary preserves the call signature, not just the value types.

**What problem it solves / history** — pre-variadic generics (before TS 3.0/4.0) typed rest as `any[]` or fixed arities via overload lists — wrappers (`debounce`, `memoize`, `bind`) either flattened every argument to `any` or repeated 5 overloads per helper. Variadic tuples made the wrapper transparent: `debounce<T extends unknown[]>(fn: (...args: T) => void, ms: number): (...args: T) => void` forwards the exact signature with zero per-function overloads.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), type every forwarding helper with `<T extends unknown[]>` rest capture — never `any[]`, never fixed overloads for arity alone. Label tuple positions that carry meaning (`[url: string, init?: RequestInit]`); constrain with `unknown[]` (admits everything, preserves each element) rather than `never[]` (admits nothing) or `any[]` (admits everything but flattens checking). Rest/tuple foundations live in [2.3. Rest and tuples](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>).

**Runnable example** — transparent forwarding (good vs bad, `tsc --strict`):

```typescript
// good — debounce forwards the exact signature: arity, types, and labels survive
function debounce<T extends unknown[]>(fn: (...args: T) => void, _ms: number): (...args: T) => void {
  return (...args) => fn(...args);
}
const save = debounce((id: string, retries: number) => console.log(id, retries), 200);
save("u1", 3); // (id: string, retries: number) — hover shows both
// save("u1"); // error TS2554 — arity preserved through the generic

// good — labeled tuple documents each position
type Endpoint = [url: string, init?: { method: string }];
function call(...[url, init]: Endpoint): string { return `${init?.method ?? "GET"} ${url}`; }
console.log(call("/a", { method: "POST" })); // POST /a

// bad — any[] rest flattens the signature: arity and element types lost
function debounceBad(fn: (...args: any[]) => void, _ms: number): (...args: any[]) => void {
  return (...args) => fn(...args);
}
const saveBad = debounceBad((id: string, _r: number) => console.log(id), 200);
saveBad("u1"); // compiles (any) — missing retries slips to runtime
// fix — <T extends unknown[]>: the tuple (not any[]) is the forwarding unit
```

**Common confusion** — "`T extends unknown[]` accepts anything, so it is `any`" — `unknown[]` *admits* any argument list but *preserves* each element type; `any[]` admits and then *forgets* them — admission vs memory differ. "labels affect assignability" — labels are documentation-only; `[a: string, b: number]` and `[string, number]` assign identically — label for readers, constrain for the checker. "rest capture handles `this` too" — `this` needs its own explicit parameter (`this: Ctx`) — rest covers trailing arguments only (see [3.1. this parameter](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>)).

**Performance note** — tuple capture costs O(arity) per call site (each argument checked once) — identical to checking the unwrapped call. Long tuples (20+ args) render slowly in hovers but check linearly — prefer options-bags past ~5 parameters for readability, not speed.

**Mentor note** — hover `save` and `saveBad` side by side: one shows `(id: string, retries: number)`, the other `(...args: any[])` — the invisible signature becomes the lesson. Exercise: forward a 3-arg function through both helpers and count which call-site errors survive — `any[]` keeps zero. Review gate: `...args: any[]` in a generic helper is a defect, not a shortcut.

### 2) **Concat and pipe composition** (`[...A, ...B]` builds typed pipelines)

**Definition** — tuple types spread inside other tuples: `[...A, ...B]` concatenates, `[H, ...T]` prepends, `[...T, Last]` appends — all at the type level, all arity-preserving. Pipes compose stage signatures (`Pipe<A, B>`, `Pipe<B, C>` → `Pipe<A, C>`) so each stage's output type-checks against the next stage's input without manual threading.

**What problem it solves / history** — middleware chains (Express, validation pipelines, ETL stages) were typed as `any[]` chains or N-deep overload nests — adding a stage meant editing the chain type by hand, and a stage returning the wrong shape failed at the *end* of the pipe instead of at the guilty link. Tuple concat expresses the chain as data: stages declare input/output, the pipe type zips them, and mismatches error at the miswired joint.

**Modern guidance** — as of TypeScript 5.9 era, model fixed pipelines as tuple-chained stages: `pipe<A, B, C>(ab: (a: A) => B, bc: (b: B) => C): (a: A) => C` for two links; extend with `[...Steps]` tuples for N links. Keep chains short in public signatures (2–4 stages read well); extract named stage aliases past that. Prefer explicit stage functions over clever recursive pipe types — the readable chain beats the general one in every review.

**Runnable example** — mismatch errors at the joint (good vs bad, `tsc --strict`):

```typescript
// good — two-stage pipe: B is the contract both stages share
function pipe<A, B, C>(ab: (a: A) => B, bc: (b: B) => C): (a: A) => C {
  return (a) => bc(ab(a));
}
const job = pipe(
  (s: string) => s.length, // string => number
  (n: number) => n > 2, // number => boolean (joint matches: B = number)
);
console.log(job("hello")); // true

// good — tuple concat threads arity through prepend/append
type Prepend<H, T extends unknown[]> = [H, ...T];
type P = Prepend<string, [number, boolean]>;
const p: P = ["a", 1, true];
console.log(p[0]?.toUpperCase(), p[1]?.toFixed(0)); // A 1
// const bad: P = [1, "a", true]; // error TS2322 — order preserved, not just membership

// bad — any-chained pipe defers the mismatch to runtime
function pipeBad(ab: (a: any) => any, bc: (b: any) => any): (a: any) => any {
  return (a) => bc(ab(a));
}
const jobBad = pipeBad(
  (s: string) => s.length,
  (b: boolean) => !b, // joint broken: number fed to boolean — silent via any
);
console.log(jobBad("hello")); // false — wrong, and no compile error pointed at the joint
// fix — pipe<A, B, C>: the shared B makes the joint a checked contract
```

**Common confusion** — "concat reorders or dedupes" — `[...A, ...B]` preserves order and duplicates exactly (tuples, not sets) — `[1, "a"]` and `["a", 1]` are different types. "pipe infers stages backwards" — inference flows forward (arguments determine `A`, then `B`, then `C`); annotate the *first* stage's input when the chain starts from nothing. "N-stage recursive pipes are always better" — 2–4 explicit overloads read better than one recursive type in every real codebase — generality has a review cost.

**Performance note** — concat instantiations cache per tuple pair (`Prepend<string, [number, boolean]>` computes once). Recursive N-stage pipes cost O(stages) instantiations per composition — fine for short chains, budget-capped for generated ones (see [3.2. Recursive generics](<../3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>)).

**Mentor note** — break the joint deliberately (`(b: boolean) => !b` after a number stage) in both `pipe` and `pipeBad` and compare: one errors at the comma between stages, the other logs a wrong boolean. Ask "which error would you rather debug at 2am?" — the joint error wins every time. Exercise: extend to three stages and watch `B`/`C` joints each enforce independently.

### 3) **Generic rest capture vs `any`** (preserve each element or flatten them)

**Definition** — `<T extends unknown[]>` with `...args: T` captures the argument list *as a tuple* (each position keeps its type); `...args: any[]` accepts the same calls but types every position `any`. Capture is transparent (errors and autocomplete survive); `any` is opaque (both die at the boundary).

**What problem it solves / history** — logging/metrics/telemetry wrappers (`withTiming`, `withRetry`, `trace`) wrapped every function in the codebase — typed `any[]`, they laundered the entire call graph through `any` and disabled checking program-wide; typed `<T extends unknown[]>`, they forward perfectly and the wrapped function checks exactly as the original. One keyword at the wrapper fixed every call site without touching any of them.

**Modern guidance** — as of TypeScript 5.9 era, the rule is absolute: generic forwarding helpers capture (`<T extends unknown[]>` + `...args: T` + return the same `T` shape); only leaf helpers that genuinely consume arguments (formatters reading `args[0]` as `unknown` and narrowing) may touch the elements — and even those start from the captured tuple, not `any[]`.

**Runnable example** — wrapper transparency (good vs bad, `tsc --strict`):

```typescript
// good — timing wrapper: signature in, same signature out
function timed<T extends unknown[], R>(fn: (...args: T) => R): (...args: T) => R {
  return (...args) => fn(...args);
}
const add = timed((a: number, b: number) => a + b);
console.log(add(2, 3).toFixed(0)); // 5 — R = number, arity enforced
// add(2); // error TS2554 — missing b caught through the wrapper

// good — retry wrapper preserves async signatures too
function retry<T extends unknown[], R>(fn: (...args: T) => Promise<R>, _n: number): (...args: T) => Promise<R> {
  return (...args) => fn(...args);
}
const fetchAge = retry(async (id: string) => ({ id, age: 36 }), 3);
void fetchAge("u1").then((u) => console.log(u.age.toFixed(0))); // 36

// bad — any wrapper launders the whole call graph
function timedBad<R>(fn: (...args: any[]) => R): (...args: any[]) => R {
  return (...args) => fn(...args);
}
const addBad = timedBad((a: number, b: number) => a + b);
console.log(addBad(2)); // NaN — missing b slipped through any; R alone cannot save arity
// fix — timed<T extends unknown[], R>: capture the tuple, forward the tuple
```

**Common confusion** — "capturing `T` still needs per-element constraints" — the tuple *is* the constraint: each position carries its own type from the wrapped function — no extra bounds needed. "`R` alone preserves the signature" — `R` preserves the return; only `T` preserves the parameters — wrappers need both. "wrappers add runtime overhead worth avoiding" — the types erase; the one extra closure call is the wrapper's *purpose* (timing/retry) — type-level transparency costs zero bytes beyond the closure itself.

**Performance note** — capture-vs-`any` has zero emit difference (both emit rest/spread); check cost favors capture (each argument checks once against its known type) over `any` (arguments check trivially but every *use* of the result re-verifies from scratch downstream). Transparent wrappers keep errors at the call site (cheap, local) instead of downstream (expensive, scattered).

**Mentor note** — audit every `...args: any[]` in the repo and convert one high-traffic wrapper (`withTiming`, `trace`) live — the error count *dropping* across call sites (as `any` leaks close) sells the pattern better than any slide. Rule: wrappers forward tuples; only endpoints consume elements — and endpoints narrow from `unknown`, never assume from `any`.
