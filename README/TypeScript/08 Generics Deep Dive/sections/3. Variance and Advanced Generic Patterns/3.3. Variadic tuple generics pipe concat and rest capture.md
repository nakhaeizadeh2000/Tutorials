## 3.3. Variadic tuple generics — pipe concat and rest capture

A generic rest parameter relates a whole argument list to another call. Variadic tuple types can also compute ordered combinations of tuple contracts. Those types do not automatically implement timing, debouncing, retrying or a pipeline; the JavaScript body must perform the behavior its name promises.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent TypeScript fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate commented negatives separately and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **Labeled tuple rest and forwarding**

A wrapper can capture its callback's positional arguments and result as separate parameters. Labels help readers identify positions but do not change assignability or create runtime argument names. Call this implementation forward: it invokes its callback immediately and does not pretend to debounce or measure it.

Save as `forwarding.ts`.

```typescript
function forward<Args extends unknown[], Result>(
  fn: (...args: Args) => Result
): (...args: Args) => Result {
  return (...args) => fn(...args);
}
const save = forward((id: string, retries: number): string => `${id}:${retries.toFixed(0)}`);
console.log(save("u1", 3));
// save("u1"); // TS2554
// save("u1", "3"); // TS2345

type Endpoint = [url: string, options?: { method: string }];
function requestLabel(...[url, options]: Endpoint): string {
  return `${options?.method ?? "GET"} ${url}`;
}
console.log(requestLabel("/a"), requestLabel("/a", { method: "POST" }));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Arguments = Expect<Equal<Parameters<typeof save>, [id: string, retries: number]>>;
type Result = Expect<Equal<ReturnType<typeof save>, string>>;
type LabelsAreNotIdentity = Expect<Equal<[url: string], [string]>>;
```

The output is `u1:3`, then `GET /a POST /a`. The live probes establish parameter positions and the result. They do not prove an editor's displayed labels; tuple equality also succeeds without the labels. Missing or wrongly typed arguments remain errors through this particular wrapper.

These examples use ordinary receiver-independent callables. A parameter/result wrapper does not automatically preserve every overload, generic relationship, constructor signature, attached property or receiver requirement. [Rest and tuple foundations](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>) owns forwarding basics; [receiver typing](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) owns that separate call contract.

### 2) **Execute concat and check pipeline joints**

`[...Left, ...Right]` concatenates positional types, preserving their order and repeated elements. A runtime implementation must still construct the result. Readonly input tuples can be spread into a newly created mutable result tuple. Open arrays instead produce open array positions; generic spreading does not invent a fixed length they never promised. The [primary variadic-tuple notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-0.html#variadic-tuple-types) introduce these relationships.

Save as `composition.ts`.

```typescript
function concat<Left extends readonly unknown[], Right extends readonly unknown[]>(
  left: Left, right: Right
): [...Left, ...Right] {
  return [...left, ...right];
}
const joined = concat(["a", 1] as const, [true, "a"] as const);
const openNumbers = concat([1, 2], [3]);
console.log(joined.join(","), openNumbers.join(","));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Positions = Expect<Equal<typeof joined, ["a", 1, true, "a"]>>;
type Unbounded = Expect<Equal<typeof openNumbers, number[]>>;
// const wrongOrder: typeof joined = [1, "a", true, "a"]; // TS2322

function pipe<Input, Middle, Output>(
  first: (value: Input) => Middle, second: (value: Middle) => Output
): (value: Input) => Output {
  return value => second(first(value));
}
const textLength = (text: string): number => text.length;
const job = pipe(textLength, (count: number) => `count:${count}`);
console.log(job("hello"));
// pipe(textLength, (text: string) => text.toUpperCase()); // TS2345: incompatible intermediate contract
function unsafePipe(first: (value: any) => any, second: (value: any) => any): (value: any) => any {
  return value => second(first(value));
}
const unsafe = unsafePipe(textLength, (text: string) => text.toUpperCase());
try { unsafe("hello"); }
catch (error) { console.log(error instanceof TypeError ? "pipeline joint: TypeError" : "unexpected error"); }
```

The output is `a,1,true,a 1,2,3`, `count:5`, then `pipeline joint: TypeError`. Concat creates an array; the tuple type describes its positional contract. The checked pipe connects number output to number input. The unsafe helper accepts a string-requiring second stage, then actually passes it a number and fails.

Inference can obtain information from multiple positions; it is not a universal one-way sequence through the written stages. Check the resulting contract and the diagnostic instead of promising a particular error location between two arguments. More stages, asynchronous stages and overloaded inputs need their own supported relationships. An arbitrary stage-count preference is not a type-system rule; keep the form that makes the actual operation clear.

### 3) **Generic capture differs from a bare array annotation**

A named Args parameter can preserve positions even when its constraint is any[]. A non-generic rest parameter written any[] instead exposes an open bag and loses the original positional call contract. Unknown[] is a useful bound when the generic body should not assume each element has arbitrary members, but it is not the sole cause of tuple inference.

Save as `capture.ts`.

```typescript
function captureUnknown<Args extends unknown[]>(...args: Args): Args { return args; }
function captureAny<Args extends any[]>(...args: Args): Args { return args; }
const unknownBound = captureUnknown("Ada", 30);
const anyBound = captureAny("Ada", 30);
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type UnknownBound = Expect<Equal<typeof unknownBound, [string, number]>>;
type AnyBound = Expect<Equal<typeof anyBound, [string, number]>>;
console.log(unknownBound.join(","), anyBound.join(","));
// function inspect<Args extends unknown[]>(...args: Args): void { args[0].toUpperCase(); } // TS2571

function unsafeForward<Result>(fn: (...args: any[]) => Result): (...args: any[]) => Result {
  return (...args) => fn(...args);
}
const add = unsafeForward((left: number, right: number) => left + right);
console.log(add(2)); // Accepted but the missing right value produces NaN.
```

The output is `Ada,30 Ada,30`, then `NaN`. Both generic captures retain the tuple in these calls. The unknown-bound body cannot use a string method without evidence; any would suppress that restriction. The non-generic any rest in unsafeForward loses arity even though Result still tracks the declared output. Closing such a hole may reveal previously hidden call errors; it does not guarantee that a project's diagnostic count decreases.

The next wrapper performs an actual asynchronous retry operation while retaining its supplied argument/result relationship. Save as `retry.ts`. MaxAttempts includes the first attempt, and shouldRetry decides whether a failure qualifies for another one. The loop has no delay, cancellation or network integration. Use repeated operations only when their effects permit the chosen retry policy; this example uses deterministic local functions.

```typescript
function retry<Args extends unknown[], Result>(
  fn: (...args: Args) => Promise<Result>, maxAttempts: number,
  shouldRetry: (error: unknown) => boolean
): (...args: Args) => Promise<Result> {
  if (!Number.isInteger(maxAttempts) || maxAttempts < 1) throw new RangeError("positive attempt count required");
  return async (...args) => {
    let failures = 0;
    while (true) {
      try { return await fn(...args); }
      catch (error) {
        failures++;
        if (failures >= maxAttempts || !shouldRetry(error)) throw error;
      }
    }
  };
}
const transient = (error: unknown): boolean => error instanceof Error && error.message === "temporary";
async function main(): Promise<void> {
  let attempts = 0;
  const fetchAge = retry(async (id: string) => {
    attempts++;
    if (attempts === 1) throw new Error("temporary");
    return { id, age: 36 };
  }, 3, transient);
  // fetchAge(); // TS2554: wrapped argument remains required
  // fetchAge(42); // TS2345
  const user = await fetchAge("u1");
  console.log(user.id, user.age, attempts);

  let failures = 0;
  const exhausted = retry(async () => { failures++; throw new Error("temporary"); }, 2, transient);
  try { await exhausted(); }
  catch { console.log("exhausted", failures); }
  let permanentAttempts = 0;
  const permanent = retry(async () => { permanentAttempts++; throw new TypeError("invalid input"); }, 3, transient);
  try { await permanent(); }
  catch { console.log("not retried", permanentAttempts); }
  try { retry(async () => 1, 0, transient); }
  catch (error) { console.log(error instanceof RangeError ? "invalid attempt count" : "unexpected error"); }
}
void main().catch(error => { console.log("unexpected failure", error); });
```

The output is `u1 36 2`, `exhausted 2`, `not retried 1`, then `invalid attempt count`. The first call actually fails once and succeeds on the second attempt; the second stops at its limit, and the third's error predicate denies a retry. The same captured id argument is forwarded on each permitted attempt. A wrapper that only returns fn(...args) once would preserve a signature but implement none of these behaviors. [Async types](<../../../18 Async Types and Standard Library/README.md>) owns the broader asynchronous contract and operation policies.

### 4) **Common confusion**

A generic array constraint and a published open-array parameter are different declarations. Both captureUnknown and captureAny preserve the shown tuple, while unsafeForward exposes any[] and permits a missing argument. Judge the whole input/output relationship rather than treating the word unknown as a magic precision switch.

Tuple labels are documentation, and tuple spreads compute ordered contracts. Neither implements scheduling or retries. Verify the actual attempts, returned value and rejection policy separately from the wrapper's accepted arguments. This lesson's helpers also do not bind a receiver or promise to preserve every overloaded callable.

### 5) **Performance note**

The generic types and live assertions erase. Rest/spread, array construction, function calls, awaits and repeat attempts remain. Retry can repeat the underlying operation, so its operational cost depends on actual attempts and that operation; the example counts them without measuring latency. No tuple-size threshold, call-site checking formula or capture-versus-any speed ranking was measured. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a genuine checking problem.

### 6) **Mentor note**

Ask which signature preserves parameters and which implementation performs the named behavior. Require the learner to predict both generic capture types before running them, then explain unsafeForward's NaN. For retry, ask why maxAttempts counts the initial invocation and what stops the permanent error after one attempt.

For a composition exercise, chain another checked pipe after job that reads the resulting string's length. Verify the final result for hello, then replace that final stage with a boolean-only input and observe rejection. Explain why a working two-stage composition can be used twice without claiming a fully general recursive pipeline type or a fixed stage-count rule.
