## 3.2. Recursive generic types and self-referential patterns

### 1) **The wrapped rule** (recursion must pass through a member)

**Definition** — a recursive generic must reference itself through a property, array, union, or mapped layer — `type J<T> = T | J<T>[]` is legal (self-reference wrapped in an array member); bare `type X<T> = X<T>` never terminates and errors. The wrapper gives the checker a finite unfolding per level: each nesting adds one structural layer the checker can count.

**What problem it solves / history** — direct self-reference (`type X = X`) hung or errored opaquely in early TypeScript, and generic recursion inherited the confusion — developers wrote `type Deep<T> = Deep<T>` expecting "nested T" and got circularity errors (TS2456). The wrapped rule names the fix: recursion describes *nesting* (a tree node holding child nodes, a JSON value holding arrays of JSON), so the self-reference must sit inside the container that creates the next level.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), always wrap: objects (`{ children: Node<T>[] }`), arrays (`(T | Nested<T>)[]`), unions (`T | Wrapper<T>`). Non-generic recursion mechanics live in [3.1. Recursive objects](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.1. Recursive object types and self-referential structures.md>) — this leaf owns the *parameterized* layer (how `T` threads through each level).

**Runnable example** — wrapped terminates, bare does not (good vs bad, `tsc --strict`):

```typescript
// good — self-reference wrapped in array/property: each level adds structure
type JsonVal = string | number | boolean | null | JsonVal[] | { [k: string]: JsonVal };
const j: JsonVal = { a: [1, "x", { b: null }] };
console.log(JSON.stringify(j)); // {"a":[1,"x",{"b":null}]}

// good — generic parameter threads through every level
interface TreeNode<T> { value: T; children: TreeNode<T>[]; }
const root: TreeNode<string> = { value: "r", children: [{ value: "c", children: [] }] };
console.log(root.children[0]?.value.toUpperCase()); // C

// bad — bare self-reference: no wrapper, no termination (kept as commented error)
// type Loop<T> = Loop<T>; // error TS2456 — type alias circularly references itself
// fix — wrap the reference: type Loop2<T> = { next: Loop2<T> | null; payload: T }
type Chain<T> = { payload: T; next: Chain<T> | null };
const c: Chain<number> = { payload: 1, next: { payload: 2, next: null } };
console.log(c.next?.payload.toFixed(0)); // 2
```

**Common confusion** — "generic recursion is a different feature from object recursion" — same rule, one extra thread: the wrapper terminates, the parameter specializes (`TreeNode<string>` children are `TreeNode<string>`, not `TreeNode<unknown>`). "wrapping in a union is enough" — `type X<T> = X<T> | T` still references bare `X<T>` as a member — the *alias itself* must not appear unwrapped at the top level; `T | Wrapper<T>` (reference through a *different* shape) is the legal form. "recursion depth is unlimited" — the checker caps instantiation depth (next promise but one).

**Performance note** — each nesting level is one cached instantiation (`TreeNode<string>` at depth 3 holds 3 entries) — linear and cheap. Cost explodes with *branching* recursion (mapped types recursing over every property per level — see promise 3) — keep the fan-out narrow or cap the depth explicitly.

**Mentor note** — draw one level ("a node holds an *array of* nodes — the array is the wrapper") before showing syntax — students who see the container first never write bare `Loop<T>`. Exercise: fix `Loop<T>` three ways (array, property, union member) and state what each wrapper models (list, chain, choice). Review gate: any new recursive alias must name its wrapper in the PR description.

### 2) **Generic recursion sites** (Json, DeepReadonly, linked nodes)

**Definition** — three sites use parameterized recursion daily: data shapes (`JsonVal`, `TreeNode<T>` — `T` is the payload), deep transforms (`DeepReadonly<T>` — `T` is rebuilt per level), and linked structures (`Chain<T>`, comment threads — `T` is the node content). In each, the parameter appears both at the current level (payload) and inside the wrapped reference (next level's payload).

**What problem it solves / history** — shallow helpers (`Readonly<T>`, one-level `Flatten`) silently stopped at depth 1 — nested config objects stayed mutable, nested arrays stayed wrapped — and teams layered manual per-level types (`Config`, `ConfigL2`, `ConfigL3`) that rotted on the fourth nesting. Recursive generics compute *all* levels from one declaration: `DeepReadonly<Config>` freezes the leaves the author never enumerated.

**Modern guidance** — as of TypeScript 5.9 era, write deep transforms as conditional + recursion: `type DeepRO<T> = T extends object ? { readonly [K in keyof T]: DeepRO<T[K]> } : T` — objects recurse per property, primitives terminate. Linked structures recurse through the node type directly (`Chain<T>` above). Stop conditions matter: every branch must reach a non-recursive base (primitive, `null`, empty tuple) or the checker diverges.

**Runnable example** — one declaration, all depths (good vs bad, `tsc --strict`):

```typescript
// good — deep transform recurses to the leaves
type DeepRO<T> = T extends object ? { readonly [K in keyof T]: DeepRO<T[K]> } : T;
type Cfg = { db: { host: string; ports: number[] }; tag: string };
const cfg: DeepRO<Cfg> = { db: { host: "h", ports: [1] }, tag: "t" };
console.log(cfg.db.host.toUpperCase(), cfg.tag.toUpperCase()); // H T
// cfg.db.host = "x"; // error TS2542 — readonly at depth 2, not just depth 1

// good — linked thread: parameter is the content, recursion is the structure
interface Msg<T> { body: T; replies: Msg<T>[]; }
const thread: Msg<string> = { body: "hi", replies: [{ body: "yo", replies: [] }] };
console.log(thread.replies[0]?.body.toUpperCase()); // YO

// bad — manual per-level types rot at the next nesting
interface CfgL1 { db: { host: string; ports: number[] }; tag: string; } // depth-1 frozen?
// interface CfgL2 { db: { host: string; ports: readonly number[] }; ... } // second copy for depth 2
// fix — DeepRO<Cfg>: the recursion (not the author) enumerates the levels
```

**Common confusion** — "`DeepRO` loops on primitives" — the false branch (`: T`) terminates: strings/numbers are not `object`, so recursion stops exactly at the leaves. "`T extends object` matches arrays and functions too" — yes: arrays recurse per element (desired), functions recurse per property (usually harmless, occasionally surprising — exclude with `T extends (...args: never[]) => unknown ? T : …` when functions must stay intact). "mapped-type recursion needs `infer`" — mapped types recurse by indexing (`DeepRO<T[K]>`), `infer` recurses by matching — different tools for different wrappers (see [2.3. infer](<../2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>)).

**Performance note** — deep transforms cost O(properties × depth) instantiations — a 50-key config nested 4 deep creates ~200 cached mapped types (fine). The cliff is *wide + deep* (1000-key generated schema × 6 levels) — flatten or `DeepRO` only the subtree that needs it. Full scaling treatment lives in [19 Performance](<../../../19 Performance Project References and Scaling/README.md>).

**Mentor note** — trace `DeepRO<Cfg>` one level on a whiteboard (`Cfg` → per-key `DeepRO<…>`) and stop — students extrapolate the rest. Exercise: add a `Date` field and watch it recurse into object properties (surprise!) — then fix with a `T extends Date ? T : …` carve-out — teaches stop conditions through a real casualty. Review rule: every recursive transform names its base cases in a comment.

### 3) **Depth budget** (TS2589 — cap depth before the checker gives up)

**Definition** — the checker aborts runaway instantiation with `TS2589: Type instantiation is excessively deep and possibly infinite` — the signal that recursion (or distributive mapping over a huge union) exceeded its budget. The fix is structural, not a flag: cap the depth (`Depth extends [0,1,2,…]` counter), flatten the input, or narrow the recursion to the subtree that needs it.

**What problem it solves / history** — unbounded `DeepX` over generated schemas (OpenAPI, GraphQL codegen with 1000+ types) compiled on small services and timed out in the monorepo — CI-only failures with no local repro, because depth depends on the *largest* input in the program. The budget error (plus explicit depth counters) turned "works on my machine" into a local, citable diagnostic with a standard repair kit.

**Modern guidance** — as of TypeScript 5.9 era, budget defensively: library-published deep transforms take a depth counter (`DeepRO<T, D extends number = 5>` decrementing per level to a base fallback); application code recurses over owned (small) types and references pre-computed aliases for generated (large) ones. Never raise the budget via compiler internals — restructure so the largest real input stays under it, and record the cap in the type's doc comment.

**Runnable example** — capped depth terminates by construction (good vs bad, `tsc --strict`):

```typescript
// good — depth counter: tuple length tracks depth, D caps it, overflow falls back to T
type CappedRO<T, D extends number = 3, Seen extends 0[] = []> = Seen["length"] extends D
  ? T
  : T extends object ? { readonly [K in keyof T]: CappedRO<T[K], D, [...Seen, 0]> } : T;
type Small = { a: { b: { c: string } } };
const s: CappedRO<Small> = { a: { b: { c: "x" } } };
console.log(s.a.b.c.toUpperCase()); // X

// simpler production pattern — cap by narrowing scope, not arithmetic:
type ShallowRO<T> = { readonly [K in keyof T]: T[K] }; // depth 1 by design
const sh: ShallowRO<Small> = { a: { b: { c: "x" } } };
console.log(sh.a.b.c.toUpperCase()); // X — outer frozen, inner intentionally live

// bad — unbounded deep transform over an unbounded input (illustrative; kept small so it compiles)
// type DeepAny<T> = T extends object ? { [K in keyof T]: DeepAny<T[K]> } : T;
// type Huge = { a: { b: { c: { d: { e: { f: string } } } } } };
// const h: DeepAny<Huge> = ... // fine at 6 levels; the same shape at 60 generated levels trips TS2589
// fix — CappedRO (counter) or ShallowRO (scope): budget is a design input, not an error to suppress
```

**Common confusion** — "TS2589 means the code is wrong" — it means the *instantiation* exceeded budget on some input — the code may be correct but too ambitious for the largest schema; cap or narrow. "raising the limit fixes it" — deeper budgets move the cliff (and slow every check) — restructure instead. "small examples prove unbounded is safe" — depth failures depend on program-wide inputs (codegen size) — test deep transforms against the largest real schema, not the unit fixture.

**Performance note** — the budget *is* the performance system: each instantiation level costs memory and check time, so the cap bounds both. Measured rule: keep application deep transforms under depth ~5 over owned types; library transforms ship an explicit counter defaulting to 3–5 with the overflow behavior documented (`D = 0` → `T` passthrough).

**Mentor note** — reproduce TS2589 deliberately once (deep fixture + unbounded mapped recursion) so the team recognizes the number, then fix by scoping — the scar tissue prevents future "just add depth" PRs. Review gate: new recursive utilities over non-owned (generated) inputs must ship with a depth cap or a written reason the input stays small.
