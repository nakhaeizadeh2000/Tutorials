## 4.1. Production checklist — mental models mentors insist on

### 1) **Identify the artifact, selected checks and enforced decision**

A release needs evidence for its actual support contract. Name the source/revision, compiler and dependency state, built candidate and consumers. Run checks that cover selected static contracts, package layout/resolution and relevant behavior, preserving each failure. A particular tool count is not a completeness criterion. The [release collector](<../1. Production Checklist/1.1. Pre-release type gates all green.md>) checks one identified tarball through health tools and fresh typed ESM/CommonJS consumers.

Its subtraction candidate passes layout, resolution and typing but fails behavior. Its missing-declaration candidate fails layout before consumer execution. Changing producer source without repacking leaves the old tarball green with the same digest. Therefore retain the relationship between the intended revision, build inputs and reviewed artifact; a passing hash identifies checked bytes, not whether the newest source was built. A gate also needs actual workflow enforcement before claiming a failed local command blocks hosted publication. No such hosting configuration is supplied by the collector.

Inspect the effective options and selected source/probes of relevant commands. The [configuration audit](<../1. Production Checklist/1.2. Strictness and configuration audits.md>) reproduces a child that inherits strict but disables null checking, and another that becomes green by omitting an incorrect probe. Shared inheritance reduces duplication; it does not guarantee identical contracts. Intentional check/emit or host differences can be correct when their inputs and purpose are explicit.

### 2) **Choose a migration unit and verify the complete target**

For source conversion, choose a reviewable unit from dependencies and affected callers, not a universal one-file rule. The [mixed-language exercise](<../2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) builds JavaScript, checked JSDoc and a typed conversion while preserving selected runtime cases. Its numeric annotations narrow checked callers but do not remove historical JavaScript coercion. A renamed-file count alone would miss that boundary.

For stricter checking, distinguish an option dependency from an organization's chosen order. The [strictness exercise](<../2. Migration Playbooks/2.3. Loose to strict sequencing.md>) independently exposes implicit any and unsafe function parameters; initialization checking needs null checking, and noImplicitOverride requires an explicit setting outside strict. The repaired full target and runtime cases matter more than reciting one order. A fallback, optional chain or widened return changes a decision or API; review the intended meaning.

For a version change, use the [actual three-compiler upgrade](<../2. Migration Playbooks/2.2. TypeScript version upgrades without flag-days.md>) to separate source acceptance, declarations, emitted behavior, tool API and installed-consumer evidence. The old accepted source still fails on empty input. CLI acceptance also cannot certify an imported API or editor integration. A staged transition can help isolate these contracts; a coherent project-wide conversion can also be appropriate. Neither strategy guarantees a schedule or eliminates follow-up type quality work.

### 3) **Keep uncertain boundaries honest**

A declaration is a claim about a provider. The [installed untyped dependency](<../3. Interop and Portable Code/3.3. Declaration-first consumption of untyped JavaScript.md>) demonstrates a false precise shim whose local type pin passes while the real value crashes. Returning unknown and projecting a checked own string property rejects the malformed numeric/null cases. Bundled types later replace the local shim, but still return unknown; maintenance provenance does not discharge runtime validation.

Inspect declaration inclusion and context when changing providers. An included script-style ambient module can hide a bundled contract rather than defer to it. A top-level import can make a declaration an augmentation. Remove or reconcile the old shim deliberately, then check actual resolution and consumers; there is no universal lookup ladder or automatic deletion-on-arrival rule.

A [checked JavaScript provider](<../3. Interop and Portable Code/3.1. allowJs checkJs and JSDoc-typed JavaScript.md>) has a related boundary: disabling its body diagnostics can let a false string annotation reach a green typed caller. JSDoc or TypeScript syntax can support maintained contracts, but neither substitutes for checking the provider and exercising its behavior. Track exceptions by context/identity as well as counts; replacing one accepted error with another can leave a total unchanged.

### 4) **Test host and lifecycle behavior at the boundary used**

A report interface does not redact strings. The [observability/lifecycle exercise](<../1. Production Checklist/1.3. Observability hooks error reporting and health.md>) tests a fixed-field projection that omits synthetic secret messages/causes. Its readiness model makes local decisions, while real probe transport and orchestration remain separate. A JSON state alone does not change deployment routing.

The same exercise sends actual SIGTERM with owned work pending, stops new admission and distinguishes a completed drain from a deadline child failure. Waiting until work finishes before calling shutdown would not test the drain. A timeout ends the fixture's waiting; it does not cancel an arbitrary operation, undo effects or prove distributed consistency. Identify all real resources and their cleanup policies before expanding that claim.

The [portable storage application](<../3. Interop and Portable Code/3.2. Environment-portable code node browser edge.md>) runs selected sequential behavior in Node and actual Chrome. A browser-only empty-value bug passes checking and leaves Node green, but fails Chrome. A matching interface or fake cannot certify an unexecuted host adapter. For an edge provider, add its actual implementation, supported APIs/settings and host-specific evidence before declaring support.

### 5) **Common confusion**

Green is scoped to an operation and its inputs. A source check, package analyzer, installed runtime entry, typed probe and actual signal test answer different questions. Their failures can overlap, and their successes do not combine into proof of every application path.

Counts and snapshots focus review but do not choose compatibility policy automatically. A changed declaration may preserve old calls, a stable declaration may hide new behavior, and an unchanged diagnostic total may hide a replacement defect. Read the contract and observed consumer outcomes rather than updating expectations solely to restore green.

### 6) **Performance note**

This checklist introduces no new executable fixture, deployment or benchmark. It synthesizes the linked actual observations. Gate costs depend on setup, dependency order, selected programs and resource contention; parallel wall time is not generally just the slowest command. No fixed validation cost, migration throughput or incident-prevention payoff follows from these recommendations.

### 7) **Mentor note**

Present four cases: a green old tarball after source changed, a type pin over a false shim, a browser adapter whose Node fake is green, and a shutdown invoked after all work finished. Ask what each observation establishes and which boundary remains untested. Strong answers identify artifact identity, actual provider values, the real host and overlap with admitted work.

For a proposed release or migration, ask the learner to name the support contract, failing counterexample, preservation evidence and remaining integration limits. A useful checklist guides that reasoning; it does not replace it with a universal tool quota, flag order or cadence.
