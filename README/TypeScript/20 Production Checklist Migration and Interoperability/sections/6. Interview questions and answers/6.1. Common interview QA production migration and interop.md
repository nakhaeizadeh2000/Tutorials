## 6.1. Common interview QA — production migration and interop

These questions assess decisions and evidence. The linked owners contain complete actual fixtures; this interview leaf introduces no new executable project or benchmark. Explain which contract an observation establishes before recommending a tool or policy.

### 1) **What evidence would gate a TypeScript package release?**

Name the supported consumers, source/revision and build inputs, then identify the candidate artifact. Check selected static API contracts, actual packed files/resolution and relevant runtime behavior. Tool suites can overlap; a fixed five-tool quota is not completeness. Preserve statuses and connect the local result to actual workflow enforcement before saying a failure blocks publication.

The [release collector](<../1. Production Checklist/1.1. Pre-release type gates all green.md>) runs health tools and fresh typed ESM/CommonJS consumers against one tarball. Its subtraction implementation passes structural/type steps but fails behavior. Its missing-declaration candidate fails early. The report identifies the tarball and digest; it does not sign it or prove the latest source was built.

**Follow-up:** source changed, but the old tarball's report is green. What can be released? The evidence belongs to the old bytes. Rebuild/repack the intended revision, rerun its checks and review that identified candidate. Also inspect configuration scope: a child can omit a failing type probe or disable an individual strict check while inheriting strict. A green source check only covers its actual selected inputs/options.

For a running application, add relevant lifecycle and deployment evidence. The [real SIGTERM exercise](<../1. Production Checklist/1.3. Observability hooks error reporting and health.md>) tests pending owned work and admission, not every HTTP/database/telemetry integration. A report type does not redact strings, and a readiness union does not configure an orchestrator.

### 2) **How would you choose a JavaScript migration strategy?**

Establish the current execution path, module/build constraints, consumers and areas where checking can improve a useful contract. A mixed program can introduce allowJs, reporting controls and checked JSDoc or deliberate TypeScript conversions. Choose reviewable dependency-coherent units; a unit can span files. Maintained typed JavaScript can also be appropriate. Historical project-wide automation is another strategy with follow-up type-quality work, not an automatically inferior approach.

The [actual migration stages](<../2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) expose any parameters from JavaScript, add numeric JSDoc and then require TypeScript annotations after a rename. Their runtime verifier checks listed numeric and coercing calls. The declared API narrows checked callers without adding runtime validation.

**Follow-up:** a project is now all .ts and compiles; is migration complete? Inspect the intended contracts, explicit any/suppressions, selected type probes, imports, artifacts and relevant behavior. File counts alone do not answer. A typed addition implementation can violate the original multiplication contract while checking successfully. For strictness, honor genuine option dependencies and verify the full target; there is no universal nullability-first rule that guarantees completion or a fixed delivery schedule.

### 3) **How would you evaluate a compiler-version upgrade?**

Read the changes relevant to the actual program and formulate a reproducible comparison. Separate checking, emission/declarations, tool APIs, editor integration and installed consumers. Use isolated outputs and known executable versions. An advisory comparison can collect migration evidence, but promotion needs a deliberate decision about which contract that interface now must pass.

The [three-compiler exercise](<../2. Migration Playbooks/2.2. TypeScript version upgrades without flag-days.md>) compares 5.5.4, 5.6.3 and current 7.0.2. The old checker accepts an iterator value read that throws on empty input. Newer checking exposes possible undefined, and the repaired completion guard produces a deliberate RangeError while preserving the declared string return. Installed consumers assert both ordinary output and required empty-input rejection. CLI success also leaves an old imported compiler API incompatible in the native comparison.

**Follow-up:** can rollback be one compiler pin? Only if that accurately restores the tested operational state. Source, lockfile, configuration, emitted artifacts and other changes may need restoration together. The fixture rehearses a bounded old-compiler fallback; it does not undo a published API or data change. Choose an upgrade window from actual support constraints rather than a universal weeks-per-minor rule or a claim that lag multiplies effort predictably.

### 4) **How do you defend a local declaration for an untyped dependency?**

Describe only the surface needed and supported by evidence, but do not confuse minimality with truth. Keep uncertain results unknown, establish the fields the application needs and test actual provider behavior. A local type equality pin over the same declaration cannot establish that the JavaScript implementation agrees.

The [installed provider exercise](<../3. Interop and Portable Code/3.3. Declaration-first consumption of untyped JavaScript.md>) has a false precise shim and passing local pin, followed by a runtime TypeError. An unknown-returning declaration and own-data string projection accept the valid result and reject the provider's numeric/null cases. This is a bounded Item contract, not a complete schema or a sandbox.

**Follow-up:** the dependency now ships types; can the shim and parser be deleted? Inspect the selected declarations, remove/reconcile the included local shim and run relevant consumers. An ambient declaration can hide a bundled signature. Even correctly selected bundled types may still return unknown, as the actual update does, so projection remains necessary. Upstream provenance and a TODO do not prove runtime values or enforce a removal schedule. Maintaining local types can be a deliberate choice when ownership and compatibility are clear.

### 5) **What would support a Node, browser and edge portability claim?**

Identify actual APIs, loaders, permissions and operational behavior for each promised host. A shared interface and a fake establish selected shapes/model behavior, not all adapters. Use independent checking programs with deliberate ambient inputs, then run relevant behavior through each actual supported host. A runtime-name global or typeof guard does not confer API support or guarantee bundler pruning.

The [portable cache exercise](<../3. Interop and Portable Code/3.2. Environment-portable code node browser edge.md>) checks an isolated shared program and runs the same selected sequential contract in Node memory and real Chrome localStorage. Replacing the browser's nullish miss mapping with a truthy mapping compiles, leaves Node green and fails Chrome on a stored empty string. An explicit process leak also fails shared/browser checking while Node accepts it; environment mistakes need not fail every consumer identically.

**Follow-up:** does that green Node/Chrome matrix establish a named edge service? No. Add its actual adapter, appropriate types, compatibility settings/bindings and relevant host evidence. An asynchronous key/value interface can fit a remote provider while its consistency, errors and persistence differ. The verified cases do not promise atomic creation or deduplication under concurrent misses. Choose abstractions for needed contracts, without mandating a fixed number of seams or claiming negligible indirection cost.

### 6) **Common confusion**

Successful process status has a scope. A health analyzer can omit a consumer mode by policy; a source check can omit a probe; an old artifact can remain correct after source changes. Interpret the selected work before inferring a cause or approval to promote a different candidate.

Static and runtime evidence can disagree consistently: a false provider declaration gives a green caller, readonly permits direct JavaScript mutation, and a deadline can exit without completing pending work. Diagnose the boundary rather than assuming compiler nondeterminism or treating a type annotation as an implementation.

### 7) **Performance note**

These answers establish no new timing, conversion throughput, validation budget or gate-speed formula. Extra compilers, programs and hosts add setup, checking and maintenance work. Scheduling and dependency order affect wall time; benchmark representative successful work when comparing costs. A stronger support claim needs relevant evidence even if a smaller local test is faster.

### 8) **Mentor note**

Ask for a prediction before revealing each follow-up's actual result. Have the learner identify the checked artifact/program/provider/host and a meaningful counterexample. Strong answers explain the missing evidence and the preserved contract instead of reciting a tool count, flag order or migration cadence.

For a senior discussion, propose a different absence or compatibility policy and ask which declarations, callers, tests and release notes change. Assess that reasoning against the role. A bounded answer with an explicit untested integration is more useful than an unsupported promise of universally safe shipping.
