## 6.1. Common interview QA — production migration and interop

### 1) **What gates a TypeScript release — and which are advisory vs blocking?**

**Definition** — the gate answer (1.1): five blocking (whole-program `noEmit`, surface `tsd`/typecheck, behavior unit, tarball `attw`+`publint`, baseline diffs) + two audits (flag signoff with expiring overrides, exemption inventories holding-or-shrinking) + parity (dev/CI/prod configs identical). Advisory on *none* (pressure proceduralized — break-glass + postmortem the sole exception path).

**What problem it solves / history** — advisory-gate incidents (5.1 incident 1 — warnings shipped, `any` everywhere): the interview probes release discipline (blocking sets enumerated — pressure withstood structurally, exceptions proceduralized).

**Modern guidance** — answer shape: enumerate 5+2+1, state none-advisory with the break-glass exception, cite incident 1's epitaph ("packaging warnings are blockers"). As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS).

**Runnable example** — gates enumerated (good vs bad, `tsc --strict`):

```typescript
// good — gate set recited with rationale (each gate's regression class named — blocking justified per class)
export {}; // module marker (consistent module scope across fences)
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends (<T>() => T extends Y ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
export function gated(): number { return 1; } // release API (gates: statics pinned below, behavior asserted, packaging/baselines in CI)
assertType<Equal<ReturnType<typeof gated>, number>>(); // gate representation (statics blocking — widening red at the cut)
console.log(gated()); // 1 — gates evidenced (enumeration with rationale — discipline, not ritual)
// bad — "tests green, ship it" (statics/surfaces/packaging/baselines unmentioned — release discipline unknown)
// fix — 5+2+1 enumeration (gates + audits + parity — none advisory, break-glass proceduralized)
```

**Common confusion** — "more gates slower releases" — parallel gates ≈ slowest (seconds-to-minutes — incidents costing days; net velocity positive per 1.1). "hotfix exemptions" — break-glass + postmortem (exceptions proceduralized — casual exemptions rejected like skipped tests).

**Performance note** — gate enumeration free (recitation); gate execution parallel-cheap (slowest-dominates — insurance arithmetic decisive).

**Mentor note** — hiring signal: candidates stating none-advisory unprompted (pressure-proofing designed — senior instinct).

### 2) **How do you migrate a large JS codebase — without stopping feature work?**

**Definition** — the playbook answer (2.1): bridge (`allowJs` mixed programs — behavior unchanged), inventory (JS-file backlog ratcheting), loops (rename-tighten-test-merge per file — independence total), JSDoc halfway (safety now — graduation mechanical), dashboards (counts plotted — stalls flaggable). Features shipping throughout (velocity with safety — 5.1 incident 2's inverse).

**What problem it solves / history** — flag-day framing (freezes stalling — quarters vaporized): the interview probes incremental design (bridges + loops + halfway — momentum compounding, stalls structurally prevented).

**Modern guidance** — answer shape: bridge → inventory → loops → JSDoc → dashboards (five steps, velocity throughout); cite loop independence (one file, one PR — reviewable, revertable); close with the metric (JS-file ratchet — progress evidenced).

**Runnable example** — loops evidenced (good vs bad, `tsc --strict`):

```typescript
// good — loop shape demonstrated (rename-tighten-test-merge — independence total, momentum compounding)
export {}; // module marker (consistent module scope across fences)
export function looped(s: string | number): string {
  return `v:${String(s)}`; // tightened (implicit made explicit — 2.1 loop shape in miniature)
}
console.log(looped(3)); // v:3 — file loops (features shipping throughout — velocity with safety, always)
// bad — "freeze and rewrite" (flag-days stalling — 5.1 incident 2 attached as counter-evidence)
// fix — playbook recitation (bridge → loops → JSDoc → dashboards — increments daily, momentum compounding)
```

**Common confusion** — "loops too slow at scale" — loops steady (daily files × engineers — big-bangs stalling at month three with zero shipped; duration-to-done favoring loops). "JSDoc delays conversion" — JSDoc *values* holdouts (safety now — graduation mechanical later; untyped churn the actual delay).

**Performance note** — loops minutes-to-hours per file (steady throughput — quarters productive vs quarters frozen).

**Mentor note** — follow-up: "stalled mid-migration — diagnose?" (backlog flat + no loops merging — playbook deviation, not migration impossibility).

### 3) **How do you upgrade TypeScript versions — without a flag-day?**

**Definition** — the upgrade answer (2.2): changelog triage (breaking lists short — effort proportional to actuals), branch builds (new `tsc` on branch — class-ordered fixes per 13/4.1), dual pipelines (old required + new advisory→required — disagreements reviewed, rollbacks one-line), ecosystem gating (support matrices — blockers first, TS within windows).

**What problem it solves / history** — version-freeze folklore ("upgrades break everything" — one traumatic jump generalizing): the interview probes upgrade procedure (triage → branch → dual → gate — jumps proceduralized, lag interest unpaid).

**Modern guidance** — answer shape: triage cadence (minors within weeks — 16/3.3), branch pattern (class-ordered fixes), dual windows (comparison baselines), gating (support matrices — stages green in order).

**Runnable example** — triaged upgrades (good vs bad, `tsc --strict`):

```typescript
// good — version-tolerant idioms (stable across versions — dual runs agreeing trivially)
export {}; // module marker (consistent module scope across fences)
export function upgradeProof(xs: unknown): string {
  if (!Array.isArray(xs)) throw new Error("array-only"); // narrowing idioms (stable — triaged upgrades finding nothing here)
  return `n:${xs.length}`;
}
console.log(upgradeProof([1])); // n:1 — tolerant code (breaking lists short — effort proportional to actuals, never feared)
// bad — "pin forever" (frozen majors — lag compounding breaks multiplicatively, jumps traumatic eventually)
// fix — triage cadence (weeks per minor — lag interest unpaid, jumps proceduralized)
```

**Common confusion** — "upgrades need freezes" — upgrades need *branches* (isolated variables — mainline shipping throughout; freezes confusing coordination with cessation). "dual pipelines double cost" — dual bounded by windows (promotion closing old — cost temporary, surprises prevented permanent).

**Performance note** — triage minutes per minor (lists short); frozen jumps weeks (compounded — lag interest multiplicative per 2.2 part 1).

**Mentor note** — cadence question: "last upgrade lag?" (weeks-healthy — quarters-frozen indicating folklore debt, triage prescribed).

### 4) **How do you consume untyped JS safely — and when do shims graduate?**

**Definition** — the interop answer (3.3): minimal shims (used names — tracker-linked, deletion-on-arrival); progressive precision (shim → parsed-boundary → precise types — trust earned per rung); exits (fork-PR-replace — sunsets dated). Graduation when: precision needs (hot paths), upstream arrival (bundled/`@types` published — shims deleted same-PR), or replace evaluation favoring typed alternatives.

**What problem it solves / history** — hopeful-`any` permanence (5.1 incident 3 — payloads widening silently for weeks): the interview probes trust procedure (bounds → ladders → exits — hope unrepresentable, precision progressing).

**Modern guidance** — answer shape: shim-minimal + tracker (honesty), parse-boundaries (validation discharging — 15/3.3), rungs quarterly (precision deepening), exits dated (sunsets — residence justifying like `any`).

**Runnable example** — laddered consumption (good vs bad, `tsc --strict`):

```typescript
// good — runged trust (shim → parse → proven — upgrades loud at shims, never silent at call sites)
export {}; // module marker (consistent module scope across fences)
declare function legacyPing(host: string): unknown; // rung-1 (unknown-honest — ignorance stated)
export function ping(host: string): string {
  const r: unknown = legacyPing(host); // boundary (validation next — assumption never per 3.3 part 2)
  if (typeof r !== "string") throw new Error("string-only"); // rung-2 (parsed — proven, not cast)
  return r;
}
console.log(ping("h")); // h — trust earned (rungs scheduled — precision progressing quarterly)
// bad — "declare module any and move on" (hopeful permanence — widening silent, incidents analyst-discovered)
// fix — ladders + exits (bounds scheduled — trust earned per rung, sunsets dated)
```

**Common confusion** — "shims are debt" — *unplanned* shims debt (planned with trackers/exits are transitions — 3.3 part 1 restated). "parsing duplicates vendors" — parsing *validates* vendors (boundaries proving — duplication-as-detection per 17/1.3).

**Performance note** — validation microseconds per boundary (hopeful-any costing analyst-discovered weeks — asymmetry decisive per 3.3 part 2).

**Mentor note** — dependency question: "which rung, exit when?" (rungs stated, sunsets dated — interop honest by procedure).

### 5) **What makes code portable across Node/browser/edge — and how do you prove it?**

**Definition** — the portability answer (3.2): guards centralized (`env.ts` typeof-detection — branches reviewed together); lib splits (three-plus-one `tsconfig`s — shared bare `ESNext`, leaks red at authoring); seams injected (storage/clock/network interfaced — runtimes implementing, fakes proving per 17/2.2 behavesLike). Proof = lib-split compilation (all four green) + behavesLike suites per runtime (identical assertions, N implementations).

**What problem it solves / history** — unportable "shared" code (environment globals smuggled — browser builds failing, edge crashing): the interview probes portability construction (guards + splits + seams — proof by compilation and contract suites, not by hope).

**Modern guidance** — answer shape: guards (detection centralized), splits (leaks loud), seams (capabilities interfaced) + proofs (four-way green, behavesLike per runtime).

**Runnable example** — portability proven (good vs bad, `tsc --strict`):

```typescript
// good — seamed portability (capabilities interfaced — runtimes implementing, fakes proving)
export {}; // module marker (consistent module scope across fences)
export interface RNG { bytes(n: number): number[] } // seam (capability interfaced — 3.2 pattern in miniature)
class FakeRNG implements RNG { bytes(n: number): number[] { return Array(n).fill(7); } } // fake proving (substitutability tested — 17/2.2 economics)
export function token(rng: RNG): string { return rng.bytes(2).join("-"); } // portable (seam consumed — environment names absent)
console.log(token(new FakeRNG())); // 7-7 — proof by contract (suites asserting — portability tested, not hoped)
// bad — "runs on my runtime" (environment globals direct — portability hoped, builds failing elsewhere)
// fix — guards + splits + seams (proof by compilation-four-way and behavesLike — portable by construction)
```

**Common confusion** — "portability restricts APIs" — portability *seams* capabilities (5–6 interfaces — domain logic untouched, edges adapted per 3.2 part 3). "four-way CI overkill" — four small programs parallel-cheap (faster than one mega-program per 19/2.3 — proof affordable).

**Performance note** — seams nanoseconds per call (indirections inlinable — proof costs test-time; unportable builds costing runtimes, asymmetry decisive).

**Mentor note** — portability bar: four-way green + behavesLike per seam (compilation proving, contracts proving — hope unrepresentable).
