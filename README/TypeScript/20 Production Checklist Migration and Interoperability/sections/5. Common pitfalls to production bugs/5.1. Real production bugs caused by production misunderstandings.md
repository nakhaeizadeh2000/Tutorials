## 5.1. Real production bugs caused by production misunderstandings

These patterns can affect production releases, integrations and shutdowns. The evidence below comes from **local reproductions in complete linked fixtures**, not documented customer outages. No lost-payment count, multi-quarter rewrite or telemetry-delivery incident is claimed. Each case identifies the observation, diagnosis and limits of its remedy.

### 1) **Green packaging analysis is mistaken for correct released behavior**

The [release collector](<../1. Production Checklist/1.1. Pre-release type gates all green.md>) checks a calc-kit tarball with health tools, a fresh installation, strict ESM/CommonJS consumers and runtime assertions. A subtraction implementation retains the number-to-number declaration and valid package paths. Its first four steps pass, but ESM behavior fails and the collector exits 1. A source snippet with a numeric signature would not expose that defect.

For a separate artifact failure, packing only JavaScript omits declarations that remain present in the working directory. The collector fails at publint before any consumer step. The [health-tool owner](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.3. publint attw and package health checks.md>) also observes this attw version exiting 0 while reporting that the package contains no types. Interpret each tool's scope and output; do not infer a typed consumer contract from one successful process status.

A missing explicit types condition is not automatically an any leak. The publishing owner demonstrates matching adjacent declarations being found through extension substitution, while actually missing declarations produce strict consumer errors. Inspect the packed files and resolved paths before diagnosing “any everywhere.” Choose the support matrix deliberately and test it.

Changing producer source without rebuilding/repacking leaves the old tarball's behavior and digest unchanged. Its green report belongs to those old bytes. Relate the intended source/revision and build inputs to the identified candidate, and keep the checked artifact stable. Finally verify the real release workflow preserves the failed status before claiming publication is blocked. No registry operation or hosted enforcement is exercised here.

### 2) **A migration is declared complete from filenames or caller checks**

The [mixed-source migration](<../2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) initially exposes any parameters from an actual JavaScript dependency to a strict TypeScript caller. Checked JSDoc then supplies numeric parameter contracts; renaming that file without TypeScript annotations still reports implicit-any errors. A renamed-file total would conceal the unfinished contract work.

The same fixture preserves selected runtime cases, including an existing coercing string call from JavaScript after the checked API is narrowed to numbers. This is not a contradiction: annotations did not add runtime validation. Review the static API change and the intended runtime policy separately. Changing multiplication to addition passes checking and fails its behavior verifier, so a green converted source is insufficient on its own.

A related [JSDoc provider experiment](<../3. Interop and Portable Code/3.1. allowJs checkJs and JSDoc-typed JavaScript.md>) returns a number under a string return annotation. Disabling JavaScript body diagnostics lets the typed caller build, then its toUpperCase call fails. Repair the provider or its honest contract; suppressing its checking only changes reporting.

Choose a coherent reviewable migration unit and verify the complete target, including imports, outputs and affected callers. File-by-file work can help, while the original maintainer experience linked from the migration playbook also documents project-wide automation with follow-up typing. Neither approach guarantees feature velocity, a fixed completion schedule or behavior preservation from renaming alone.

### 3) **A shim's type pin is mistaken for provider verification**

The [untyped dependency exercise](<../3. Interop and Portable Code/3.3. Declaration-first consumption of untyped JavaScript.md>) packs and installs a real local CommonJS provider. Its wrong result contains numeric id, but an inaccurate shim promises a string id. The local equality pin passes because it reads that same declaration. Runtime then fails when the consumer treats the number as a string.

The remedy in the fixture returns unknown at that uncertain boundary and checks an own string data property before constructing the used Item. Valid input works; the provider's numeric/null cases are rejected. This is a bounded projection, not proof of every business invariant or protection from a hostile dependency. The load parameter declaration still makes a claim about supported calls and needs its own evidence.

A later local version adds bundled declarations. Removing the included ambient shim and inspecting the actual index.d.cts verifies the new selected type contract. Its return remains unknown, so runtime projection is still necessary. Do not automatically delete validation merely because a dependency gains types. Conversely a stale included shim can hide a bundled signature; declaration context and inclusion matter more than an assumed priority ladder.

### 4) **A timeout or sequential example is mistaken for a tested drain**

Calling serve to completion and then calling shutdown cannot show whether pending work survives a termination signal. The [actual lifecycle fixture](<../1. Production Checklist/1.3. Observability hooks error reporting and health.md>) starts an owned task blocked on an input gate, waits for the child's ready message and sends real SIGTERM on Linux. It then checks draining readiness and refusal of new admission before releasing the original task. The child logs work completion before drained and exits 0.

In a second process the parent withholds completion. The child stops waiting at its deadline, closes the fixture's owned stdin handle and exits 1. The verifier treats that as an expected failed-drain result, not successful completion. A timeout has not cancelled the task or undone effects. The unresolved promise alone does not keep this particular process running once its owned handles are gone.

For real application shutdown, inventory admission paths and resources, define completion/cancellation/error policy, and test the actual signal route and deployment integration. A local single-task test cannot certify HTTP response completion, database consistency, remote retries or telemetry delivery. Reporting projection and readiness payload tests likewise do not configure an orchestrator or prove messages were delivered. Keep those missing integrations visible rather than claiming all work is lossless.

### 5) **Common confusion**

A false declaration and a missing declaration are different failures. A semantic implementation bug can pass both declarations and packaging analysis. A disabled diagnostic can make the same false provider description reach a typed consumer. Each diagnosis needs the actual selected contract and runtime observation.

The [Node/Chrome storage exercise](<../3. Interop and Portable Code/3.2. Environment-portable code node browser edge.md>) supplies another false green: a browser-only empty-string mapping defect passes checking and leaves the Node memory contract green, while the real browser fails. A fake or another host checks its modeled behavior, not every adapter.

### 6) **Performance note**

These local failure patterns establish selected correctness and lifecycle observations. They provide no outage-cost estimate, validation microsecond budget, migration throughput or universal gate-speed formula. Expanding a consumer or host matrix adds setup and maintenance work; choose it from the support contract and measure relevant costs separately. A faster green result caused by omitted inputs is weaker coverage, not an equivalent optimization.

### 7) **Mentor note**

Give a learner the passing type pin, green old tarball, number-returning JSDoc provider and deadline child exit. Ask what each result says and what it does not establish. Good answers identify self-referential declaration evidence, old artifact identity, suppressed provider checking and failed completion respectively.

For a proposed remedy, request the failing counterexample and the exact restored contract. Reject a response that merely adds a cast, renames a file, prints a green label or promises a schedule. Follow the complete fixture and preserve the distinction between local tests and unexecuted deployment behavior.
