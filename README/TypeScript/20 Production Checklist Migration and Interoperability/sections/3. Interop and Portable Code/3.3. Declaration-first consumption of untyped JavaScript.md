## 3.3. Declaration-first consumption of untyped JavaScript

### 1) **Test a declaration against an actual provider**

An ambient declaration supplies a checker contract. It does not implement the package, validate a return value or prove a third-party version agrees. A narrow declaration can still be false. Tests that compare a shim's type with the same asserted signature only confirm the local description; they do not inspect the JavaScript implementation.

Use TypeScript **7.0.2**, Node **20.20.2** and npm **10.8.2**, verified 2026-10-17. This disposable exercise creates a real local CommonJS package, packs it and installs it into a separate consumer. It is not a downloaded SDK or a published contribution. Create legacy, artifacts and consumer/src, plus consumer/shims. Save `legacy/package.json`:

```json
{"name":"legacy-kit","version":"1.0.0","main":"./index.cjs","files":["index.cjs"]}
```

Save `legacy/index.cjs`:

```javascript
exports.load = id => id === "valid" ? { id: "item:1" } : id === "wrong" ? { id: 17 } : null;
exports.extra = "outside the reviewed shim";
```

Save `consumer/package.json`:

```json
{"name":"legacy-consumer","version":"1.0.0","private":true,"type":"module"}
```

Save `consumer/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true
  },
  "include": ["src/**/*.mts", "shims/**/*.d.ts"]
}
```

Save this deliberately inaccurate `consumer/shims/legacy.d.ts`:

```typescript
declare module "legacy-kit" {
  export function load(id: string): { id: string };
}
```

It is a script-style declaration file: do not add export {} or a top-level import while intending to declare this otherwise untyped module. External-module context can make the same block an augmentation; the [ambient module owner](<../../../12 Modules Namespaces and Declaration Files/sections/2. Namespaces and Ambient Contexts/2.3. Ambient modules declare module wildcards.md>) demonstrates that distinction and why included shims can hide bundled types.

Save `consumer/src/main.mts`:

```typescript
import { load } from "legacy-kit";
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type LocalPin = Expect<Equal<ReturnType<typeof load>, { id: string }>>;
console.log(load("wrong").id.toUpperCase());
```

From the disposable root, run each independently:

```bash
npm pack ./legacy --ignore-scripts --pack-destination ./artifacts
npm install --prefix ./consumer --ignore-scripts --no-audit --no-fund --package-lock=false ./artifacts/legacy-kit-1.0.0.tgz
tsc -p consumer/tsconfig.json
node consumer/dist/main.mjs
```

Packing, installation and checking exit 0, including LocalPin. Execution deliberately exits 1 with TypeError: the actual wrong result has a numeric id. The pin merely restated the false shim. Removing the installed package would create a different runtime-resolution failure; the declaration is no substitute for that provider either.

### 2) **Keep uncertain results unknown and project the used contract**

Replace the declaration with:

```typescript
declare module "legacy-kit" {
  export function load(id: string): unknown;
}
```

Checking the old main now fails: its local equality assertion no longer matches, and property access cannot proceed on unknown. This is useful uncertainty, not a missing promise to invent. Replace main.mts with this complete boundary exercise:

```typescript
import { load } from "legacy-kit";
interface Item { id: string }
function getItem(id: string): Item {
  const raw: unknown = load(id);
  const descriptor = typeof raw === "object" && raw !== null
    ? Object.getOwnPropertyDescriptor(raw, "id") : undefined;
  if (!descriptor || !("value" in descriptor) || typeof descriptor.value !== "string") {
    throw new TypeError("invalid legacy item");
  }
  return { id: descriptor.value };
}
const item = getItem("valid");
let rejected = 0;
for (const id of ["wrong", "missing"]) {
  try {
    getItem(id);
    throw new Error("invalid item accepted");
  } catch (error) {
    if (!(error instanceof TypeError)) throw error;
    rejected++;
  }
}
console.log(item.id.toUpperCase(), "rejected", rejected);
```

Build and run again. Both exit 0; output is `ITEM:1 rejected 2`. The wrapper accepts an own string data property and constructs the used output shape. It rejects the provider's numeric and null cases. It does not claim an arbitrary input is a complete business object or sandbox a hostile package; proxy descriptor operations and provider calls can themselves throw. The [parsing owner](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) supplies fuller boundary/schema reasoning. This small projection applies it specifically to the consumed legacy operation.

A shorthand declaration granting any would permit unchecked operations again. unknown requires the caller to establish what it uses, but the load parameter signature still makes a claim about supported calls; test and review that as well. Only load is described here even though the actual provider has extra. An undeclared runtime export is outside this local static surface, not physically private or nonexistent. Do not infer security or complete library coverage from a minimal shim.

As a negative probe, temporarily add `const guessed: string = load("valid").id;` to the final main. Checking fails TS2571 because that result is unknown. Restore it and verify the working wrapper again. A static probe is useful for the boundary contract; actual provider and invalid-result behavior tests remain separate evidence.

### 3) **Replace a local shim with tested upstream declarations**

To model a typed-provider update locally, change legacy's version to 1.0.1, add `"types": "./index.d.cts"` and expand files to include index.d.cts. Save `legacy/index.d.cts`:

```typescript
export function load(id: string): unknown;
export const extra: string;
```

Pack the new local tarball and install that exact filename into the consumer. Remove consumer/shims/legacy.d.ts from the selected program, then run:

```bash
npm pack ./legacy --ignore-scripts --pack-destination ./artifacts
npm install --prefix ./consumer --ignore-scripts --no-audit --no-fund --package-lock=false ./artifacts/legacy-kit-1.0.1.tgz
tsc -p consumer/tsconfig.json --traceResolution
tsc -p consumer/tsconfig.json
node consumer/dist/main.mjs
```

All commands exit 0; runtime remains `ITEM:1 rejected 2`, and the trace identifies the installed index.d.cts. The new provider declarations still return unknown, so the projection remains useful. “Bundled types” is not evidence that every return value is a valid Item. Also check an extra import now resolves without the local shim if that newly supported surface matters to the application.

Do not assume a fixed hierarchy always chooses bundled types over local declarations. The ambient owner demonstrates an included stale shim hiding a real signature. Inspect actual resolution, declaration context and accepted calls, then remove or deliberately reconcile the old declaration. Physical presence on disk and program inclusion are different.

For a real dependency, local maintenance, an upstream/DefinitelyTyped contribution or replacement are possible choices. Evaluate supported versions, license/maintenance constraints, consumer impact and actual runtime contracts. A tracker and owner can make follow-up visible; a comment, age threshold or quarterly schedule does not automatically enforce removal. A permanent maintained declaration can be reasonable, and an upstream arrival still needs compatibility checks. No PR, publication or dependency replacement was performed by this exercise.

### 4) **Common confusion**

A type equality assertion over a declaration can pass while the implementation violates it. A minimal return shape is not automatically honest; use unknown where uncertainty remains and validate the required boundary. The tests here distinguish those layers with an actual installed provider.

Community or bundled declarations transfer maintenance responsibility, not proof of runtime validity. Local ambient declarations can also remain active after new types appear. Verify which contract is selected before deleting wrappers or claiming the migration is complete.

### 5) **Performance note**

Ambient declarations execute no validation. The provider call, descriptor inspection, string operation and output construction still run. No boundary latency, resolver speed or maintenance-payoff benchmark was measured; validation cost depends on the data and policy. Keep the projection appropriate to the consumed contract rather than promising universally negligible checks or a fixed schedule for every dependency.

### 6) **Mentor note**

Give the learner the passing LocalPin and failing runtime call. Ask what the pin actually inspected and which additional observation could establish the provider result. Then switch to unknown and ask why the projection is stronger evidence than replacing it with an assertion.

For the typed update, have the learner show the resolved index.d.cts and demonstrate the two invalid provider results still being rejected. Ask whether a lingering ambient shim could change that evidence. A sound answer discusses selected declarations and actual behavior, without treating a package's popularity or a TODO as a guarantee.
