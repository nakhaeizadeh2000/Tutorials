## 3.1. allowJs checkJs and JSDoc-typed JavaScript

### 1) **Separate participation, reporting and consumption**

allowJs admits JavaScript inputs into a compiler program. checkJs enables reporting of JavaScript semantic diagnostics across the selected JavaScript; it is not restricted to annotated files. A leading ts-check directive can opt a file into checking, while ts-nocheck suppresses its checking diagnostics. JavaScript still contributes inferred and JSDoc types to checked callers when its own body diagnostics are disabled. Reporting control is not a proof that a declaration tells the truth.

JavaScript checking also has language-specific behavior. The [JavaScript checking reference](https://www.typescriptlang.org/docs/handbook/type-checking-javascript-files.html) describes open-ended inferred object literals and parameter optionality rules, among other differences. JSDoc annotations can make particular contracts more precise; do not infer that every unannotated JS form behaves exactly like a TypeScript equivalent. The [migration exercise](<../2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) shows actual unannotated-parameter diagnostics and a rename that needs explicit TypeScript annotations. Here we focus on maintained typed JavaScript and its declarations.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. Create src in a disposable directory. Save `package.json`:

```json
{"name":"checked-javascript","version":"1.0.0","private":true,"type":"module"}
```

Save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "allowJs": true,
    "checkJs": true,
    "declaration": true,
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true
  },
  "include": ["src/**/*"]
}
```

Save `src/contract.mts`:

```typescript
export interface Config { mode: "fast" | "safe"; retries: number }
```

### 2) **Write actual JSDoc contracts and check a real caller**

Save this **JavaScript**, `src/api.js`:

```javascript
/** @import { Config } from "./contract.mjs" */
/** @typedef {{ id: string }} User */
/**
 * @param {User} user
 * @returns {string}
 */
export function label(user) { return user.id; }
/**
 * @template T
 * @param {readonly T[]} values
 * @returns {T | undefined}
 */
export function head(values) { return values[0]; }
/** @satisfies {Config} */
export const settings = { mode: "fast", retries: 2 };
/** @template T @typedef {{ readonly [K in keyof T]: T[K] }} Snapshot */
/** @type {Snapshot<{ count: number }>} */
export const snapshot = { count: 1 };
```

The typedef names an object shape; param and returns describe a callable contract. Template preserves head's element relationship, including the declared empty-array possibility. Type annotates the snapshot binding. Satisfies checks settings against Config without replacing the result with a Config annotation; the checked consumer below observes the retained fast literal. The mapped alias also works in this supported JSDoc type syntax, so mapped types alone do not force a .ts conversion. General mapped-type semantics remain at their [canonical owner](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>).

The [JSDoc reference](https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html) documents these TypeScript-supported tags and syntax. This is not a promise that every generic JSDoc documentation generator interprets them. Its import tag brings Config into comment type expressions, not JavaScript value scope. No runtime module import is created by the tag. A real value needs its own JavaScript implementation and import.

Save `src/main.mts`:

```typescript
import { label, head, settings, snapshot } from "./api.js";
const text: string = label({ id: "u:1" });
const first: number | undefined = head([1, 2]);
const mode: "fast" = settings.mode;
console.log(text.toUpperCase(), first, mode, snapshot.count);
```

Save `verify.mjs` in the root:

```javascript
import assert from "node:assert/strict";
import { label, head, settings, snapshot } from "./src/api.js";
assert.equal(label({ id: "u:1" }), "u:1");
assert.equal(head([7]), 7);
assert.equal(head([]), undefined);
assert.equal(settings.mode, "fast");
snapshot.count = 2;
assert.equal(snapshot.count, 2);
console.log("JavaScript behavior verified");
```

Run:

```bash
tsc -p tsconfig.json --listFilesOnly
tsc -p tsconfig.json
node dist/main.mjs
node verify.mjs
tsc -p tsconfig.json --emitDeclarationOnly --outDir type-dist
```

All commands exit 0. The emitted consumer prints `U:1 1 fast 1`; the separate direct-JavaScript process prints `JavaScript behavior verified`. The latter executes src/api.js on Node 20 without loading the TypeScript contract module: comment imports have no runtime edge. Its snapshot mutation succeeds because readonly is a checking contract, not Object.freeze. The root verifier is deliberately JavaScript runtime code outside the selected src program.

Inspect dist/api.d.ts and type-dist/api.d.ts. They describe label's string result, head<T>'s T | undefined result, settings and the mapped snapshot contract. Declaration-only output also includes contract.d.mts and main.d.mts, but creates no JavaScript provider there. Normal dist includes the emitted/copied implementations. This is declaration generation from actual JavaScript, not a hand-written TS stand-in; [declaration authoring](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>) owns the implementation-provider boundary. Publishing those declarations needs its own complete package/consumer check.

### 3) **Expose lies and choose the maintenance form deliberately**

In a disposable copy, change label's return expression to `user.id.length`, retaining its string return comment. Checking fails TS2322. Build with `--checkJs false`: it succeeds because the JavaScript body diagnostic is disabled, while main still sees the documented string result. Running emitted main fails TypeError at toUpperCase; the direct verifier also rejects the wrong value. A typed caller does not repair an incorrect provider annotation.

Add `// @ts-check` as the first line of the modified api.js and repeat with checkJs false: TS2322 returns. Instead use `// @ts-nocheck` with checkJs true: the body diagnostic is suppressed and the incorrect provider can again pass checking. These directives control reporting; they do not fix the implementation. Restore the original file, build and run both entries again.

For independent static failures, append `snapshot.count = 2;` to main.mts: the compiler rejects the readonly write with TS2540. Restore it, then append `const wrong: string = head([1, 2]);`: TS2322 rejects the generic/absence mismatch. Restore it. Finally try appending `console.log(Config);` to api.js. TS2693 reports type-only Config being used as a value; the comment import did not define it. Restore and rerun the original checks.

Keep JavaScript when its checked contracts, build path and contributor workflow work well. Choose TypeScript syntax when it improves readability, required constructs or tool support enough to justify conversion. Declaration output and a simple generic are not automatic graduation thresholds. Conversely a compiling JSDoc contract can still be false, and verbose type expressions can deserve extraction or redesign in either language. Review real errors and consumer contracts rather than applying a universal complexity or contributor-count rule.

### 4) **Common confusion**

A JSDoc import is a type dependency, not a runtime import. A readonly mapped type does not freeze the object. A declared string result can still be a number at runtime if provider checking is disabled or otherwise escaped. These are different boundaries, exposed by the actual negative cases above.

Type checking JavaScript can be useful permanently. Renaming to .ts adds no runtime validation, and broad claims of identical checking overlook JavaScript-specific inference rules. No declaration package or editor navigation result was established merely by this local mixed program.

### 5) **Performance note**

The comments/types here do not implement runtime checks. Normal JavaScript bodies still allocate and execute their actual operations. Compiler work depends on program membership and type relationships; no rule that JavaScript checking is cheaper or proportional to annotation density was measured. This exercise establishes declared and observed behavior, not an 80/20 payoff, editor latency or conversion-effort estimate.

### 6) **Mentor note**

Show the false string return and ask why disabling JavaScript diagnostics makes a typed consumer green. Require the learner to trace the declaration used by main and the actual number returned by the implementation. Then ask which directive restores or suppresses that diagnostic and why neither is a behavior fix.

Have the learner compare the static readonly rejection with the direct JavaScript mutation, and explain the absent runtime Config binding. A sound maintenance recommendation discusses the actual contracts and tools, rather than assuming that a particular type expression mandates a new file extension.
