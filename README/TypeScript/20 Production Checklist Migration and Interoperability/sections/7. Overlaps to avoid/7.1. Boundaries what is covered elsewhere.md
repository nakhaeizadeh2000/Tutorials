## 7.1. Boundaries — what is covered elsewhere

A release or migration decision combines several kinds of evidence. Keep each check attached to the contract it actually exercises: configuration, source checking, tool compatibility, runtime behavior and consumed artifacts. This domain applies that evidence to a concrete change; the neighboring owners explain how the underlying checks and mechanisms work.

The verified return lesson accepts an async callback at a void boundary, then shows an ignoring host completing before its task and an awaiting host propagating completion. If release code relies on a drain or cleanup, test the actual host's lifecycle and failure path. The callback's assignability alone cannot supply that evidence. The observability fixture now sends real SIGTERM while an owned task is pending, rejects new admission and compares completed drain with a deadline child failure. Its fixed-field reporting projection and local readiness states do not prove remote delivery or orchestration behavior.

The [portable storage application](<../3. Interop and Portable Code/3.2. Environment-portable code node browser edge.md>) runs a selected sequential contract in actual Node and Chrome. A browser-only empty-value defect passes checking and leaves Node green, while the browser fails. Likewise, a bounded type transform may improve checking completion while changing its accepted contract. The measured budget and recursive-object owners make that trade-off explicit. Runtime completion tests and compiler measurements should both preserve the behavior the migration needs, but a result from one does not replace the other.

### 6) **Common confusion**

A compiler pass, a runtime test, a lint result and a fresh-consumer build are different observations. A declared helper is not an executed test tool. Type-only contracts do not install runtime values or complete pending work. A historical version index is navigation, while a migration assessment checks an actual change. Select evidence from the failure and intended consumer rather than assuming every green command proves the release.

### 7) **Performance note**

This navigation lesson adds no runtime operation or benchmark. Running additional gates can require real checking, I/O or application work; their cost is not divided into independent domain totals. Use comparable compiler/build measurements for checking concerns and appropriate application measurements for runtime concerns. Do not trade away a required contract just to lower a counter or shorten a release command.

### 8) **Mentor note**

Review three cases. First, source and runtime checks pass but an installed consumer cannot resolve types: route to the artifact assessment and inspect declarations in the tarball. Second, a task is accepted at a void callback boundary but shutdown code reports completion early: route to the observed callback-host contrast, then test the actual lifecycle. Third, the native source check succeeds while a tool calls an absent compiler API: route to the compatibility fixture and preserve a supported pairing.

For each case require the owner, the actual failing operation and a check that could establish the repair. A sound explanation keeps configuration, execution, tool interfaces and artifacts distinct while connecting them to the same release decision. A slogan that all gates must be green is insufficient without identifying what the gates exercised.
