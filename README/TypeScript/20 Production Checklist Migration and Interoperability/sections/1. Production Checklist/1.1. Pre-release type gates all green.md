## 1.1. Pre-release type gates all green

### 1) **Choose gates from the release contract**

A release gate is a check whose failure the release workflow preserves as a failure. Select gates for the promised source, static API, artifact layout and runtime behavior; there is no mandatory number of tools or jobs. An ordinary compiler project can include alias-only type assertions. A dedicated type-test suite adds value when it checks another contract, not merely because it adds another green label. The [gate composition owner](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>) demonstrates static-only and behavior-only failures, plus a false green from excluding a probe.

For a package, build and pack before checking the artifact consumers install. Test supported module/resolver paths with actual consumers. Health tools add useful analysis but do not execute every supported host or validate arbitrary implementation behavior. A local collector's nonzero exit also does not configure hosted merge or publication protection. Connect the command to the real workflow and verify that failure prevents the intended action. These examples perform no publication.

### 2) **Run release checks on one identified tarball**

Start with the complete [calc-kit publishing project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) through sections 1–2. It creates producer, artifacts and consumer directories and a local dual-format tarball. Add the pinned tools from [package health checks](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.3. publint attw and package health checks.md>): publint **0.3.25** and @arethetypeswrong/cli **0.18.5** in sibling tools. Use native TypeScript **7.0.2**, Node **20.20.2** and npm **10.8.2**, verified 2026-10-17.

Save this additional `verify-release.mjs` in the disposable root, alongside producer/tools/artifacts. It uses POSIX tool launchers, as tested on Linux. It checks an already built tarball rather than silently repacking inside each gate. Each fresh temporary consumer is owned and removed by this script; it does not reuse the earlier consumer's installation or emitted files.

```javascript
import { spawnSync } from "node:child_process";
import { createHash } from "node:crypto";
import { readFileSync, writeFileSync, mkdtempSync, rmSync } from "node:fs";
import { resolve, join } from "node:path";
const root = process.cwd();
const supplied = process.argv[2];
if (!supplied) throw new Error("pass one local tarball path");
const artifact = resolve(supplied);
const digest = () => createHash("sha256").update(readFileSync(artifact)).digest("hex");
const report = { artifact, sha256: digest(), steps: [], ok: false };
let consumer;
function step(name, command, args, cwd = root) {
  const result = spawnSync(command, args, { cwd, encoding: "utf8" });
  const output = `${result.stdout ?? ""}${result.stderr ?? ""}`;
  const status = result.status ?? 1;
  report.steps.push({ name, command, args, status, output });
  if (result.error) throw result.error;
  if (status !== 0) throw new Error(`${name} failed (${status})`);
}
try {
  step("package layout", join(root, "tools/node_modules/.bin/publint"), [artifact, "--strict"]);
  step("resolution analysis", join(root, "tools/node_modules/.bin/attw"), [artifact, "--profile", "node16"]);
  consumer = mkdtempSync(join(root, ".release-consumer-"));
  writeFileSync(join(consumer, "package.json"), JSON.stringify({ name: "release-consumer", version: "1.0.0", private: true }));
  writeFileSync(join(consumer, "esm.mts"), `
import { add, format } from "calc-kit";
import { mean } from "calc-kit/stats";
const selected: "esm" = format;
const total: number = add(2, 3);
if (selected !== "esm" || total !== 5 || mean([2, 4]) !== 3 || mean([]) !== undefined) throw new Error("ESM contract");
console.log("ESM verified");
`);
  writeFileSync(join(consumer, "cjs.cts"), `
import api = require("calc-kit");
import stats = require("calc-kit/stats");
const selected: "cjs" = api.format;
const total: number = api.add(2, 3);
if (selected !== "cjs" || total !== 5 || stats.mean([2, 4]) !== 3 || stats.mean([]) !== undefined) throw new Error("CJS contract");
console.log("CJS verified");
`);
  step("fresh install", "npm", ["install", "--ignore-scripts", "--no-audit", "--no-fund", "--package-lock=false", artifact], consumer);
  step("consumer types", "tsc", ["--strict", "--target", "es2022", "--module", "nodenext", "--moduleResolution", "nodenext", "--noEmitOnError", "--outDir", "dist", "esm.mts", "cjs.cts"], consumer);
  step("ESM behavior", process.execPath, ["dist/esm.mjs"], consumer);
  step("CJS behavior", process.execPath, ["dist/cjs.cjs"], consumer);
  if (digest() !== report.sha256) throw new Error("artifact changed during checks");
  report.ok = true;
} catch (error) {
  report.error = error instanceof Error ? error.message : String(error);
  process.exitCode = 1;
} finally {
  if (consumer) rmSync(consumer, { recursive: true, force: true });
  writeFileSync("release-report.json", JSON.stringify(report, null, 2));
}
```

Run from that root:

```bash
node --check verify-release.mjs
node verify-release.mjs artifacts/calc-kit-1.0.0.tgz
```

Both commands exit 0 for the original package. release-report.json records six successful steps, the absolute tarball path and its SHA-256 digest. The runtime steps capture `ESM verified` and `CJS verified`. The consumer assignments check the chosen declaration branch, while the assertions check selected behavior. The digest identifies the bytes checked; it is not a signature, authenticity proof or protection against arbitrary concurrent writers. Keep artifacts stable during verification and use the identified artifact for any later authorized release.

The [attw reference](https://github.com/arethetypeswrong/arethetypeswrong.github.io/blob/main/packages/cli/README.md) distinguishes a positional tarball from `--pack`, which packs a directory. Its node16 profile ignores legacy node10 failures; it does not establish that unsupported mode. The [publint CLI](https://publint.dev/docs/cli) documents tarball inputs and strict warning handling. Retain the chosen profiles and actual tool output in the release evidence.

### 3) **Prove rejection and review deliberate changes**

In a disposable producer copy, change add to subtraction in **both** module implementations, build and pack into a separate artifact directory. Run the collector against that tarball. Package layout, resolution analysis, installation and type checking pass, but ESM behavior fails with `ESM contract`; the collector exits 1 and does not run CJS behavior after the failure. The same number-to-number signature does not prove addition. Restore both implementations, rebuild and repack before continuing.

For an independent artifact failure, change only the producer files field to select dist/*.mjs and dist/*.cjs, leaving declarations on disk but out of the new tarball. The collector fails at publint and records that failure without testing an old consumer. The health owner separately shows that this attw version can exit 0 for a package it reports as containing no types. Therefore an exit code must be interpreted with the command's actual purpose and supported consumer checks; it is not automatically a certificate for an intended typed package.

An already packed tarball is unchanged when source changes. Verify the old tarball after modifying producer source but before rebuilding/repacking: it retains the same digest and old passing behavior. That green result belongs to the old artifact. Rebuilding and repacking changed implementation bytes produces a different identified candidate with its own outcome. A release record needs the relationship between the intended revision, build inputs and checked artifact as well as the artifact identity; a hash alone does not prove the latest source was built.

Review public declaration/API changes against supported uses and compatibility commitments. A strict signature snapshot may change when an optional parameter is added even though existing calls still work; [installed surface tests](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) demonstrate that distinction. A baseline diff focuses review but does not automatically choose a version number. Likewise diagnostic totals can stay constant while one accepted error is replaced by a new error, and performance counters need a comparable compiler/workload. Do not treat automatically updated snapshots as approval of a contract change.

### 4) **Common confusion**

The source program and installed consumer are different programs. The latter tests exports, packed declarations and actual runtime files for selected paths. It does not promise every consumer mode, bundler or deployment host. Add evidence when expanding the support matrix.

Required status checks and publication conditions are workflow settings outside this local script. Document which failed contracts prevent release and how any explicitly accepted exception is owned and reviewed. A printed green label or policy comment does not enforce that decision.

### 5) **Performance note**

This collector runs dependent steps sequentially and stops at the first failure. It measures no latency or incident-prevention payoff. Parallel work may require separate installations, isolated outputs and artifact dependencies; wall time is not generally just the slowest command. Retaining one tarball across checks provides consistent input identity here, not a measured universal speedup.

### 6) **Mentor note**

Give a learner the passing original, typed subtraction and missing-declaration artifacts. Ask which step rejects each, then inspect the report and identify which later steps did not run. A sound answer distinguishes static layout/resolution, declaration contracts and implementation meaning.

Then change source without repacking and ask what a green old-tarball report proves. Require the learner to name the artifact digest and missing build-to-revision evidence. Finish by asking what additional integration would be necessary before claiming hosted publication is blocked.
