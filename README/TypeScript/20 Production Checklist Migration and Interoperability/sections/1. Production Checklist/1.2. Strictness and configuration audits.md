## 1.2. Strictness and configuration audits

### 1) **Audit effective checks and selected inputs**

A configuration audit asks what a real command checks, with which compiler/options, and why that scope matches the release contract. Reading `strict: true` in a base file is insufficient: a child can disable individual strict-family options. Strict also permits explicit any and does not eliminate every unsound operation. The [strict reference](https://www.typescriptlang.org/tsconfig/strict.html) documents individual overrides and potential new checks across compiler versions. The [configuration checklist](<../../../13 Configuration and Compiler Options/sections/4. Important points to remember/4.1. Configuration checklist mental models mentors insist on.md>) owns the broader option decisions.

Choose syntax/import gates for the actual pipeline. The erasable trio can be useful where a stripping path needs its restrictions; it is not a universal requirement for every emitted TypeScript library. Module settings must match the supported loader/bundler. Inspect effective options and actual membership for each intended command, including type tests and build-only tools. An unselected file or an intentionally disabled check remains outside that result.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. In a disposable directory create src and test-d. Save `tsconfig.base.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": ".",
    "noEmitOnError": true
  },
  "include": ["src/**/*.mts", "test-d/**/*.mts"]
}
```

Save `tsconfig.dev.json`:

```json
{"extends":"./tsconfig.base.json","compilerOptions":{"noEmit":true}}
```

Save `tsconfig.release.json`:

```json
{"extends":"./tsconfig.base.json","compilerOptions":{"outDir":"dist"}}
```

Save `src/app.mts`:

```typescript
export function integer(n: number): number {
  if (!Number.isInteger(n)) throw new RangeError("integer required");
  return n;
}
console.log(integer(3));
try {
  integer(1.5);
  throw new Error("fraction accepted");
} catch (error) {
  if (!(error instanceof RangeError)) throw error;
  console.log("fraction rejected at runtime");
}
```

Save `test-d/api.mts`:

```typescript
import type { integer } from "../src/app.mjs";
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Result = Expect<Equal<ReturnType<typeof integer>, number>>;
```

This alias-only probe checks a selected return contract without calling an ambient helper. Run:

```bash
tsc -p tsconfig.dev.json --showConfig
tsc -p tsconfig.release.json --showConfig
tsc -p tsconfig.dev.json --listFilesOnly
tsc -p tsconfig.release.json --listFilesOnly
tsc -p tsconfig.dev.json
tsc -p tsconfig.release.json
node dist/src/app.mjs
```

All commands exit 0. Both programs select app.mts and api.mts; the intentional difference is checking without output versus emitting into dist. Runtime prints `3` and `fraction rejected at runtime`. The number parameter accepts 1.5 statically; the implementation enforces integrality dynamically.

### 2) **Reproduce overrides and missing-probe false greens**

In a disposable copy, add `const sample: number = null;` to app.mts and set `strictNullChecks: false` in release's compilerOptions. Dev checking fails TS2322 while release checking succeeds. Release still inherits `strict: true`, but its explicit nullability override changes the check. Inspect showConfig to see the effective difference. Restore the source and option before the next contrast. No runtime validation is installed by either setting.

Now change only api.mts's expected return from number to string. Both configs reject the probe with TS2344. Add `"include": ["src/**/*.mts"]` to the release config. Release checking becomes green because its root selection no longer includes api.mts; dev remains red. Inspect release membership to confirm the omitted probe. Restore its include and the correct expected return, then run both checks and the emitted entry again.

The [extends reference](https://www.typescriptlang.org/tsconfig/extends.html) explains that child files/include/exclude fields replace their base counterparts and relative paths are interpreted where they originate. It also notes that references are not inherited. Sharing a base reduces duplication; it does not make overrides or missing coverage impossible. This exercise performs an actual comparison, but implements no automatic organization-wide configuration-diff gate.

Intentional differences between checking, emitting, tests and host-specific programs can be correct. Review those differences against supported inputs and outputs rather than requiring byte-identical configurations. The same config also does not imply the same compiler, dependencies, environment, open editor content or deployed loader. Record those when investigating a local/CI discrepancy.

### 3) **Review exceptions as contracts, not just counts**

An inventory can help find explicit any, assertion escapes, directives and lint disables, but each occurrence needs context. A type-test rejection directive and an application suppression serve different purposes; a reason comment alone proves neither is correct. An expected-error directive requires some diagnostic on its following line, not one particular diagnostic. The [negative-test owner](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>) demonstrates unused and wrong-diagnostic limits with actual checks.

For this fixture, temporarily put `// @ts-expect-error` immediately above `integer(1.5)`. Checking fails with TS2578: there was no static error to expect. Remove the directive and instead append `integer("wrong");` as a separate experiment. Checking fails with TS2345. Restore the file afterward; no failing calls belong in the final runnable entry.

Track the reason, owner, affected operation and removal condition for an accepted migration exception. A date can help review an agreement, but it does not implement enforcement. A raw count cannot tell whether one old error was fixed while a new error replaced it, or whether a directive now suppresses an unrelated diagnostic. The [gate/baseline owner](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>) explains identity-aware comparison and scope limits. No automatic scanner, shrinking-error ratchet or expiry scheduler is implemented here.

### 4) **Common confusion**

A base strict flag is a default for its family, not an immutable policy over all children. A shared base also does not merge include arrays or prove parity of selected tests. Inspect effective results from the exact commands that matter.

A runtime integer restriction is not expressed by the TypeScript number type. An unused expectation on 1.5 is therefore evidence of a mistaken test, not missing compiler enforcement. Likewise fewer suppression comments can accompany weaker checking if their source files were excluded.

### 5) **Performance note**

Configuration loading, input discovery and extra checks have costs, but no timing or savings benchmark was run here. Sharing a base improves maintainability without promising zero configuration cost. A smaller program can be faster because it omitted a necessary probe; preserve intended coverage before interpreting such a change as an improvement. Choose audit scope from the actual release rather than a fixed ceremony or universal option checklist.

### 6) **Mentor note**

Show the inherited strict flag alongside the explicit nullability override and ask the learner to predict each command. Then remove the failing probe through a child include and ask why green is now weaker evidence. A sound answer inspects effective checks and selected files rather than blaming nondeterminism.

For exception review, ask what diagnostic the directive was intended to test and how that contract could silently change. Require an actual negative check when appropriate. For parity review, ask which differences are intentional and which remaining environment inputs the configuration comparison cannot establish.
