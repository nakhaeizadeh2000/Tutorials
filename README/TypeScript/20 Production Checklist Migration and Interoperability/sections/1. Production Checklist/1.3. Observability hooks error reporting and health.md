## 1.3. Observability hooks error reporting and health

### 1) **Make a reporting projection explicit**

TypeScript can describe a report without controlling the values copied into it. A string field named cause can still contain an access token or user data. Decide which information a reporting boundary needs, construct that projection deliberately and inspect the actual serialized result. Error messages, stacks and causes need separate handling where collected; a type annotation does not redact them. [Custom error/cause mechanics](<../../../15 Strictness Errors and Validation/sections/2. Error Values and Hierarchies/2.2. Custom error classes cause and stacks.md>) owns bounded cause traversal and runtime identity.

The local model below emits only fixed classification fields and a cause-presence boolean. It deliberately omits messages and cause values. This verifies a small projection, not a complete telemetry SDK, arbitrary-object sanitizer or delivery guarantee. Choose sampling, grouping and retention from the information needed and the destination's actual policy; no universal percentage or fingerprint tuple fits every system.

### 2) **Distinguish readiness from liveness and transport policy**

Readiness asks whether to admit the relevant traffic or work. Liveness asks whether a process should be restarted under the configured supervision policy. A missing dependency can make a process unready while the process itself remains responsive. Model states that support the real decision; a boolean can be sufficient for a single external readiness decision, while an internal tagged result can explain its reason.

The [Kubernetes probe reference](https://kubernetes.io/docs/concepts/workloads/pods/probes/) distinguishes probe mechanisms and their consequences. Its HTTP probe evaluates the status code, not an arbitrary JSON health union. A typed payload therefore does not by itself tell an orchestrator to restart or shed traffic. Implement and test the actual transport mapping and deployment configuration when those are part of the contract. No Kubernetes cluster, HTTP health endpoint or real dependency probe is exercised here.

The following project uses native TypeScript **7.0.2**, Node **20.20.2**, npm **10.8.2** and @types/node **20.19.43**, verified on Linux 2026-10-17. It tests a local reporting/readiness model and actual process lifecycle behavior. Save `package.json` in a disposable directory:

Save `src/model.mts`:

```typescript
export interface Report {
  kind: "error" | "non-error";
  site: "worker";
  hasCause: boolean;
}
export function toReport(error: unknown): Report {
  return {
    kind: error instanceof Error ? "error" : "non-error",
    site: "worker",
    hasCause: error instanceof Error && Object.hasOwn(error, "cause")
  };
}
export type Readiness =
  | { state: "ready"; ready: true }
  | { state: "dependency-unavailable"; ready: false }
  | { state: "draining"; ready: false };
export function readiness(requiredDependencyUp: boolean, stopping: boolean): Readiness {
  if (stopping) return { state: "draining", ready: false };
  return requiredDependencyUp
    ? { state: "ready", ready: true }
    : { state: "dependency-unavailable", ready: false };
}
```

These booleans are supplied observations, not a network check or a timeout implementation. Cause presence does not inspect the cause's value or prove it is an Error. The report likewise treats a cross-realm Error outside this realm's instanceof result as non-error; it is an intentionally small classification policy.

### 3) **Exercise stop, drain and deadline with a real signal**

A shutdown test must overlap with accepted work. Calling shutdown only after serve has returned tests no drain. The child below registers one pending owned task, announces readiness, then waits for input to complete it. On SIGTERM it stops admission before taking the drain snapshot. A parent controls when to finish the task or deliberately withholds completion.

Save `src/child.mts`:

```typescript
import { readiness } from "./model.mjs";
let stopping = false;
let failed = false;
let shutdownTask: Promise<void> | undefined;
const tasks = new Set<Promise<void>>();
const log = (event: string, extra = {}) => console.log(JSON.stringify({ event, ...extra }));
function admit(job: () => Promise<void>): boolean {
  if (stopping) return false;
  const task = Promise.resolve().then(job).catch(() => { failed = true; });
  tasks.add(task);
  void task.then(() => { tasks.delete(task); });
  return true;
}
let finish!: () => void;
const gate = new Promise<void>(resolve => { finish = resolve; });
process.stdin.once("data", () => { finish(); });
admit(async () => { await gate; log("work done"); });
async function shutdown(): Promise<void> {
  stopping = true;
  log("draining", { readiness: readiness(true, stopping), newAccepted: admit(async () => {}) });
  let timer: ReturnType<typeof setTimeout> | undefined;
  const deadline = new Promise<false>(resolve => {
    timer = setTimeout(() => resolve(false), process.argv[2] === "deadline" ? 50 : 5000);
  });
  const completed = await Promise.race([Promise.all([...tasks]).then(() => true), deadline]);
  clearTimeout(timer);
  log(completed && !failed ? "drained" : "deadline or task failure");
  process.stdin.destroy();
  process.exitCode = completed && !failed ? 0 : 1;
}
process.on("SIGTERM", () => { shutdownTask ??= shutdown(); });
log("ready", { readiness: readiness(true, false) });
```

The deadline ends this fixture's waiting and closes its owned stdin handle; it does not cancel a running job or undo its effects. In the withheld-completion case, the unresolved promise alone does not keep Node running after the owned handle and timer are gone. Real sockets, workers, files and telemetry exporters need their own close/cancellation policy. A synchronous event-loop stall can also delay a timer; this is not a hard wall-clock guarantee.

[Node's signal documentation](https://nodejs.org/download/release/v20.20.2/docs/api/process.html#signal-events) explains that a listener removes SIGTERM's default exit behavior on non-Windows platforms. The application must finish its lifecycle. SIGKILL cannot run cleanup, and Windows signal behavior differs. This fixture sets exitCode and releases its owned resources rather than calling process.exit before output has flushed.

Save `verify.mjs` in the project root:

```javascript
import assert from "node:assert/strict";
import { spawn } from "node:child_process";
import { createInterface } from "node:readline";
import { once } from "node:events";
import { toReport, readiness } from "./dist/model.mjs";
const projected = toReport(new Error("synthetic-secret", { cause: new Error("secret-cause") }));
assert.deepEqual(projected, { kind: "error", site: "worker", hasCause: true });
assert.equal(JSON.stringify(projected).includes("secret"), false);
assert.deepEqual(toReport(17), { kind: "non-error", site: "worker", hasCause: false });
assert.deepEqual(readiness(true, false), { state: "ready", ready: true });
assert.deepEqual(readiness(false, false), { state: "dependency-unavailable", ready: false });
assert.deepEqual(readiness(true, true), { state: "draining", ready: false });
for (const mode of ["complete", "deadline"]) {
  const child = spawn(process.execPath, ["dist/child.mjs", mode], { stdio: ["pipe", "pipe", "inherit"] });
  const closed = once(child, "close");
  const events = [];
  const watchdog = setTimeout(() => child.kill("SIGKILL"), 10000);
  try {
    for await (const line of createInterface({ input: child.stdout })) {
      const value = JSON.parse(line);
      events.push(value.event);
      if (value.event === "ready") child.kill("SIGTERM");
      if (value.event === "draining") {
        assert.equal(value.readiness.state, "draining");
        assert.equal(value.readiness.ready, false);
        assert.equal(value.newAccepted, false);
        if (mode === "complete") child.stdin.write("finish\n");
      }
    }
    const [code, signal] = await closed;
    assert.equal(signal, null);
    assert.equal(code, mode === "complete" ? 0 : 1);
    assert.deepEqual(events, mode === "complete"
      ? ["ready", "draining", "work done", "drained"]
      : ["ready", "draining", "deadline or task failure"]);
    console.log(mode, "verified");
  } finally {
    clearTimeout(watchdog);
    child.stdin.destroy();
    if (child.exitCode === null && child.signalCode === null) child.kill("SIGKILL");
    await closed;
  }
}
```

Run from that root:

```bash
npm install --ignore-scripts --no-audit --no-fund
tsc -p tsconfig.json
node --check verify.mjs
node verify.mjs
```

All commands exit 0. The final command prints `complete verified` and `deadline verified`; the latter verifies an expected child exit 1, not successful work completion. The parent waits for the child's actual ready message before signaling, avoiding a guessed startup sleep. Its watchdog is a test cleanup bound, not the child's successful shutdown path.

For meaningful contrasts, replace `stopping = true` with `stopping = false`, rebuild and run the verifier. It rejects newAccepted/readiness behavior despite successful compilation. Restore that assignment. Independently add a message field copying an Error message in toReport's returned object, leaving the declared Report return type: checking rejects the excess field. If the Report interface is also widened to allow the field, checking succeeds but the serialized-object assertions fail. Restore the original model, rebuild and verify again. These failures distinguish a declared shape from a deliberately tested projection.

### 4) **Common confusion**

A union does not cause an orchestrator to read it, and a reporter interface does not scrub values copied into it. Transport adapters and serialization policy are executable boundaries. This local fixture tests fixed fields and readiness decisions, without claiming remote delivery, live dependency health or deployed routing.

A timeout can stop waiting without cancelling work. A successful local drain of one owned job also says nothing about an untracked background task, database commit, HTTP response or distributed retry. The [async completion owner](<../../../18 Async Types and Standard Library/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by async misunderstandings.md>) supplies different actual fetch/body and detached-task experiments; timer types alone are not a shutdown implementation.

### 5) **Performance note**

Reporting serialization, queueing, exporting and dependency checks have workload-dependent costs; none was benchmarked here. Sampling reduces selected records but can also hide evidence, so choose and verify a policy with operational needs in mind. Drain time includes admitted work, cleanup and scheduling, not merely the slowest idealized operation. These tests observe bounded fixture outcomes and ordering, without a universal latency, data-consistency or lossless-shutdown promise.

### 6) **Mentor note**

Ask the learner to identify exactly what the synthetic-secret assertion proves and which fields intentionally disappeared. Then present a typed message string containing the same sentinel: the annotation alone is no redaction. Ask what deployment action a JSON readiness state causes without a transport mapping; the answer should identify the missing integration.

For lifecycle review, require work to be pending before the real signal, refusal of new admission, completion ordering and the noncompletion result. Ask what resources remain outside the tracked set and how a real host could force termination. A sound answer distinguishes successful drain from a deadline that abandons waiting.
