## 2.2. TypeScript version upgrades without flag-days

### 1) **Changelog-triaged upgrades**

A compiler upgrade changes several contracts: which source is accepted, which JavaScript and declarations are emitted, and which tools can use the compiler. A green source check answers only the first question. Plan a small comparison that can reveal a real difference, fix its cause, then test the artifacts that consumers receive.

This lesson uses the historical **5.5.4 → 5.6.3** transition because it exposes an ordinary library-type change without requiring a framework. It also checks the repaired project with the track's current **7.0.2** baseline, verified 2026-10-13. These older pins are laboratory inputs, not a recommended production baseline. For the native transition's configuration, compiler API and Unicode differences, follow the [7.0 migration assessment](<../../../25 Update TypeScript 7.0/sections/5. Migration Assessment/5.1. Assess a complete native compiler migration.md>).

Start by reading breaking changes relevant to your code and recording a hypothesis. Here the [5.6 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-6.html#strict-builtin-iterator-checks-and---strictbuiltiniteratorreturn) describe stricter built-in iterator return checking under strict mode. Our hypothesis is that reading an iterator's value without testing completion can now fail checking. This is a source/library-type difference, not evidence that the runtime's Set implementation changed.

Use a focused branch or small reviewable changes according to your team's workflow. The [VS Code team's migration account](https://code.visualstudio.com/blogs/2026/06/26/iterating-faster-with-ts-7) describes adopting checking, emission and editor use in stages. Its historical preview rollout illustrates why separate gates help; its timing and speed results are not estimates for this fixture. Decide upgrade order from actual dependency constraints: a blocking tool may need attention before the compiler, while an independent CLI check can be piloted earlier.

### 2) **Dual-pipeline verification**

Use **Node 20.20.2 / npm 10.8.2**, the tested environment. Create a disposable `upgrade-tags` directory and `src` inside it. Save `package.json` below. The aliases and explicit executable paths avoid depending on which package last installed a `tsc` shim.

```json
{
  "name": "tutorial-upgrade-tags",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "files": [
    "dist"
  ],
  "scripts": {
    "check:old": "node node_modules/ts-old/bin/tsc -p tsconfig.json --noEmit",
    "check:new": "node node_modules/ts-new/bin/tsc -p tsconfig.json --noEmit",
    "check:current": "node node_modules/ts-current/bin/tsc -p tsconfig.json --noEmit",
    "build:old": "node node_modules/ts-old/bin/tsc -p tsconfig.json --outDir dist-old",
    "build:new": "node node_modules/ts-new/bin/tsc -p tsconfig.json --outDir dist",
    "build:current": "node node_modules/ts-current/bin/tsc -p tsconfig.json --outDir dist-current"
  },
  "devDependencies": {
    "ts-old": "npm:typescript@5.5.4",
    "ts-new": "npm:typescript@5.6.3",
    "ts-current": "npm:typescript@7.0.2"
  }
}
```

Save `tsconfig.json`. An explicit source root, library set and global-type list keep the comparison's inputs stable. Separate output directories prevent one compiler from overwriting another's evidence. `noEmitOnError` stops a failing build from creating new output; it does not delete old artifacts.

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": [
      "es2022"
    ],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "declaration": true,
    "noEmitOnError": true
  },
  "include": [
    "src/**/*.ts"
  ]
}
```

Save this initial `src/index.ts`:

```typescript
export function firstTag(tags: readonly string[]): string {
  const item = new Set(tags).values().next();
  return item.value.toUpperCase();
}
```

The function promises a string, but an empty Set has no first yielded string. Install the pinned tools and run each command independently:

```bash
npm install --ignore-scripts --no-fund
node node_modules/ts-old/bin/tsc --version
node node_modules/ts-new/bin/tsc --version
node node_modules/ts-current/bin/tsc --version
npm run check:old
npm run check:new
npm run check:current
npm run build:old
node --input-type=module -e 'import {firstTag} from "./dist-old/index.js"; console.log(firstTag(["green"]));'
node --input-type=module -e 'import {firstTag} from "./dist-old/index.js"; firstTag([]);'
```

The final command intentionally fails; do not append deployment commands to it. Actual results:

| Observation | Result | What it establishes |
|---|---|---|
| Executable versions | 5.5.4, 5.6.3, 7.0.2 | The comparison ran the intended compilers. |
| Old source check/build | Exit 0 | Old acceptance did not prove the empty-input contract. |
| Candidate source check | TS18048, exit 2 | `item.value` can be undefined under this library/type configuration. |
| Current source check | TS18048, exit 1 | Current checking also detects this unsafe access. |
| Old emitted code, nonempty input | `GREEN`, exit 0 | One ordinary runtime case works. |
| Old emitted code, empty input | TypeError, exit 1 | The unchecked access has a real runtime consequence. |

Diagnostic codes and process exits are recorded separately; a nonzero exit is the gate, and its explanation is the diagnostic. Do not disable strictness or assert away the undefined value merely to equalize results. Decide the function's empty-input contract. Here we retain its string return and deliberately replace an accidental TypeError with a documented RangeError. Replace `src/index.ts` with:

```typescript
export function firstTag(tags: readonly string[]): string {
  const item = new Set(tags).values().next();
  if (item.done) throw new RangeError("At least one tag is required");
  return item.value.toUpperCase();
}
```

Testing `item.done` distinguishes a completed iterator from a yielded value. This small example motivates the upgrade decision; general iterator/generator mechanics belong to [AsyncIterable and generators](<../../../18 Async Types and Standard Library/sections/3. Standard Library in Practice/3.2. AsyncIterable generators and for-await.md>) and the JavaScript iterable lessons.

Save `compare.mjs`:

```javascript
import { readFileSync } from "node:fs";
import { firstTag as oldFirst } from "./dist-old/index.js";
import { firstTag as newFirst } from "./dist/index.js";
import { firstTag as currentFirst } from "./dist-current/index.js";
for (const first of [oldFirst, newFirst, currentFirst]) {
  if (first(["green", "blue"]) !== "GREEN") throw new Error("Result changed");
  let rejected = false;
  try { first([]); } catch (error) { rejected = error instanceof RangeError; }
  if (!rejected) throw new Error("Missing empty-input contract");
}
const declarations = ["dist-old", "dist", "dist-current"].map(directory =>
  readFileSync(`${directory}/index.d.ts`, "utf8"));
if (!declarations.every(text => text === declarations[0])) {
  throw new Error("Review declaration differences");
}
console.log("three builds: GREEN; empty input rejected; declarations match");
```

Run:

```bash
npm run check:old
npm run check:new
npm run check:current
npm run build:old
npm run build:new
npm run build:current
node compare.mjs
```

All six compiler commands exit 0. The comparison prints `three builds: GREEN; empty input rejected; declarations match`. It exercises all three emitters and compares this package's declaration bytes. It does not prove equivalence of every compiler feature. Equal declaration text also cannot describe the newly deliberate exception behavior: document and review that change separately.

For a meaningful regression check, temporarily remove the `item.done` guard and run `npm run check:new`. TS18048 returns with exit 2. Restore the guard and rerun; exit 0. In a real upgrade, maintain an evidence table for each changed error class and add application-specific runtime cases. Promotion means the candidate becomes a required gate for the promises assigned to it; an advisory job needs an owner and a decision date.

### 3) **Ecosystem lag gating**

Identify whether each dependent tool calls the CLI, imports a compiler API, reads declarations, or integrates with an editor service. Those interfaces can have different support windows. Save `api.mjs`:

```javascript
import * as oldTs from "ts-old";
import * as newTs from "ts-new";
import * as currentTs from "ts-current";
console.log(oldTs.version, typeof oldTs.createProgram);
console.log(newTs.version, typeof newTs.createProgram);
console.log(currentTs.version, typeof currentTs.createProgram);
```

`node api.mjs` exits 0 and prints:

```text
5.5.4 function
5.6.3 function
7.0.2 undefined
```

We also executed `createProgram` through 5.6.3 on the repaired source and obtained zero diagnostics. Calling that old entry point through the 7.0.2 import throws TypeError. Successful native CLI checks above therefore do not establish compatibility for a tool that imports the old API. The [current tool/API lesson](<../../../25 Update TypeScript 7.0/sections/2. Editor and Tool Compatibility/2.1. Editor and tool API compatibility.md>) owns the tested native/compatibility arrangement; use it instead of assuming an arbitrary alias automatically rewires a linter.

The [typescript-eslint support page](https://typescript-eslint.io/users/dependency-versions/) lists a TypeScript API window of `>=4.8.4 <6.1.0` when consulted on 2026-10-13. Both historical compiler inputs fall within that published range; 7.0.2 does not. That is documentation evidence, not a lint run for this package. Framework, editor, bundler and deployment integrations are untested here. Record their actual versions and run their gates in your own project before promotion.

| Component | Evidence required before promotion |
|---|---|
| CLI checking | Actual executable version and candidate diagnostics on the selected project. |
| Emit and declarations | Isolated build output, reviewed public surface and runtime tests. |
| Imported compiler API | Support documentation plus the dependent tool's real command. |
| Framework/editor integration | Its declared compatibility and observed integration behavior. |
| Package consumption | The packed artifact installed in a fresh consumer, with checking and execution. |

Keep an operational fallback explicit. The repaired fixture builds with the old compiler and passes the same small runtime contract, providing a local fallback rehearsal. A production rollback may also require restoring source, lockfile, configuration and artifacts together. Changing one compiler pin cannot undo unrelated changes, data migrations or a published API contract. Version-keyed build caches help isolate inputs; they do not replace a rollback test.

### 4) **Verify a built consumer and defend the decision**

From `upgrade-tags`, run `npm pack --ignore-scripts --json`. The tested tarball is `tutorial-upgrade-tags-1.0.0.tgz`; its file list contains `dist/index.js`, `dist/index.d.ts` and `package.json`. `private: true` prevents accidental publication but still allows this local pack. Source files and development dependencies are not part of this package's exports.

Create `consumer` inside `upgrade-tags`. Save `consumer/package.json`:

```json
{
  "name": "tutorial-tags-consumer",
  "private": true,
  "type": "module",
  "dependencies": {
    "tutorial-upgrade-tags": "file:../tutorial-upgrade-tags-1.0.0.tgz"
  }
}
```

Save `consumer/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": [
      "es2022",
      "dom"
    ],
    "types": [],
    "rootDir": ".",
    "outDir": "out",
    "noEmitOnError": true
  },
  "include": [
    "consumer.ts"
  ]
}
```

Save `consumer/consumer.ts`:

```typescript
import { firstTag } from "tutorial-upgrade-tags";
console.log(firstTag(["green", "blue"]));
try { firstTag([]); } catch (error: unknown) {
  if (!(error instanceof RangeError)) throw error;
  console.log(error.message);
}
```

From `consumer`, run:

```bash
npm install --ignore-scripts --no-fund ../tutorial-upgrade-tags-1.0.0.tgz
npm ci --ignore-scripts --no-fund
node ../node_modules/ts-old/bin/tsc -p tsconfig.json
node out/consumer.js
node ../node_modules/ts-new/bin/tsc -p tsconfig.json
node out/consumer.js
node ../node_modules/ts-current/bin/tsc -p tsconfig.json
node out/consumer.js
```

All eight commands exit 0. Each runtime run prints `GREEN` then `At least one tag is required`. The consumer resolves the exported declaration and executes the packed JavaScript. It does not import the library source or rely on an editor's workspace mapping. `npm ci` replays the consumer lockfile; retain both producer and consumer lockfiles with reproducible project evidence. CI should install from the producer lockfile too rather than resolve dependencies afresh on every run.

**Exercise:** write a short upgrade decision using the observed evidence. Explain why the old green check was insufficient, why the completion guard preserves the declared return type, what exception behavior changed, and which components can adopt the candidate. State what remains unverified before moving a real application.

**Explained solution:** 5.6's built-in iterator types exposed an empty-input possibility previously hidden by a broad return type. The guard implements a deliberate contract and passes old, candidate and current checking. Separate builds and installed-consumer runs provide bounded artifact evidence. An API-dependent tool still needs its compatible compiler interface and actual integration test, so CLI promotion does not imply an editor/linter/framework promotion. Reject a decision that merely says “latest compiles”; it omits the behavioral change and support boundaries.

### 5) **Common confusion**

An upgrade does not require changing every tool in one step, nor does “compiler first” work for every dependency graph. Choose an independently testable interface, then honor the blockers of the next stage. A stable release can tighten checking or change library declarations; consult the actual release rather than inferring compatibility from a version label.

Two successful checks do not imply identical runtime behavior or interchangeable compiler APIs. This fixture's source checks, emit comparison, API probe and packed consumer answer different questions. Historical pins are useful for reproducing a known transition; they are not a reason to freeze a production project indefinitely.

### 6) **Performance note**

Running additional compilers adds installation, checking and storage work during the migration window. The elapsed cost depends on job scheduling, project size, caches and the compiler; it is not necessarily twice the wall time. No timing benchmark or upgrade-effort estimate was measured here. Keep build outputs and caches keyed to their real inputs, measure representative clean and warm jobs, and retire redundant comparison jobs once their migration purpose is complete. The [native measurement lesson](<../../../25 Update TypeScript 7.0/sections/3. Native Build and Watch/3.1. Native builds watch and measurement.md>) provides a measured method without promising a universal speed ratio.

### 7) **Mentor note**

Ask the learner to predict the empty-input run before showing the candidate diagnostic. Then ask which evidence would still be missing if all source checks passed. A sound answer identifies runtime behavior, public artifacts and tool interfaces. During review, require each proposed workaround to explain the application invariant it preserves; a cast that only silences TS18048 has no such explanation.

Have a senior learner propose a different empty-input contract and identify its declaration, consumer and compatibility consequences. This tests design judgment beyond reproducing the guard. Have the reviewer rehearse the stated fallback using isolated outputs rather than treating a pin revert as an automatic recovery guarantee.
