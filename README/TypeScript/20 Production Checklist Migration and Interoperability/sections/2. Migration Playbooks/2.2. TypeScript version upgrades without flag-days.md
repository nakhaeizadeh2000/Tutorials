## 2.2. TypeScript version upgrades without flag-days

### 1) **Changelog-triaged upgrades** (breaking vs feature vs fix, branch builds, error classes)

**Definition** — *triage*: reading each TS release's breaking-change notes first (stricter generics, lib reshapes, flag defaults — the short list that actually bites), building on a branch (`tsc` new-version run — error classes ordered: nullability/any/variance per 13/4.1, fixed class-by-class), merging when green (errors zero or baselined per 17/3.3 — upgrade as normal PR, never flag-day).

**What problem it solves / history** — version-freeze (TS pinned for years — "upgrades break everything" folklore from one traumatic jump): triaged upgrades converting jumps into class-ordered fixes (breaking list short — most releases zero-touch; effort proportional to actual breaks, not feared ones).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), upgrade within weeks per minor (triage cheap — breaking lists short; lag compounding breaks multiplicatively); branch-build pattern (new `tsc` on a branch — fixes class-ordered, reviewable); pin exact in apps (lockfile-pinned — upgrades deliberate PRs, never floating ranges per 16/3.3).

**Runnable example** — triaged upgrades (good vs bad, `tsc --strict`):

```typescript
// good — version-tolerant code (stable idioms — upgrades zero-touch by construction)
export {}; // module marker (consistent module scope across fences)
export function upgradeSafe(input: string | null): string {
  return input ?? "fallback"; // idiomatic narrowing (stable across versions — triaged upgrades finding nothing here)
}
console.log(upgradeSafe(null)); // fallback — zero-touch code (idioms stable — breaking lists rarely touching plain narrowing)
// bad — version-frozen repos (TS 4.x in 2026 — lag compounding breaks, jumps traumatic, folklore self-fulfilling)
// fix — triaged upgrades (weeks per minor — breaking lists short, effort proportional to actuals)
```

```text
// good — upgrade branch pattern (class-ordered fixes — reviewable, revertable, normal PRs)
// $ npm i -D typescript@5.9 --branch upgrade/ts59 (labeled CLI doc — branch build, new tsc)
// $ tsc --noEmit (labeled CLI doc — errors class-ordered: nullability → any → variance per 13/4.1)
// (green or baselined → merge as normal PR — upgrades proceduralized, never flag-days)
```

**Common confusion** — "minor versions break" — minors *rarely* break user code (breaking lists short — majors/betas carrying risk; triage reading, not fearing). "upgrade everything at once" — upgrade TS *first* (isolated variable — framework/editor upgrades following per 16/3.3 ecosystem windows, sequenced not bundled). "pinning prevents upgrades" — pinning *schedules* upgrades (deliberate PRs — floating ranges upgrading accidentally, pinned ranges upgrading intentionally).

**Performance note** — triage minutes per minor (breaking lists short); frozen jumps weeks (compounded breaks — lag interest compounding multiplicatively).

**Mentor note** — upgrade cadence: minors within weeks (triage cheap — lag expensive; frozen repos thawing via 2.3-style sequencing applied to versions).

### 2) **Dual-pipeline verification** (old plus new tsc in CI during migration)

**Definition** — *dual pipelines*: CI running both TS versions during upgrade windows (old pinned + new branch — behavior compared, error diffs reviewed — drift caught where versions disagree; rollbacks clean (pin revert — one-line downgrade, caches keyed per version per 19/2.2 part 3).

**What problem it solves / history** — upgrade surprises in prod (new-version emit/behavior differing — discovered post-merge without comparison baseline): dual runs converting surprises into diffs (versions compared pre-merge — disagreements reviewed, rollbacks one-line).

**Modern guidance** — dual-run during windows (old required, new advisory-then-required — promotion explicit, never silent); diff error sets (new-errors-only reviewed — pre-existing baselined per 17/3.3, deltas attributed); roll back by pin (downgrade one line — caches version-keyed per 19/2.2, no poisoning).

**Runnable example** — version comparison (good vs bad, `tsc --strict`):

```text
// good — dual-pipeline shape (old required, new tracked — promotion explicit)
// ci.yml (labeled config doc — matrix over TS versions):
// jobs: { check-ts58: { run: "tsc --noEmit" }, check-ts59: { run: "tsc59 --noEmit", advisory: true } }
// (new-errors-only reviewed — promotion flipping advisory→required with evidence, never silently)
```

```typescript
// good — version-agnostic idioms (stable across versions — dual runs agreeing trivially)
export {}; // module marker (consistent module scope across fences)
export function dualSafe<T>(xs: T[]): T | undefined {
  return xs[0]; // plain indexing (idioms stable — version diffs empty here by construction)
}
console.log(dualSafe([1])); // 1 — agnostic code (dual pipelines agreeing — disagreements reserved for genuine breaks)
// bad — single-pipeline upgrades (new-version surprises post-merge — no comparison baseline, rollbacks tangled)
// fix — dual windows (old + new compared — disagreements reviewed pre-merge, rollbacks one-line)
```

**Common confusion** — "dual pipelines double CI cost" — dual runs *temporarily* (windows, not forever — promotion closing the old pipeline; cost bounded by window length). "advisory-new is theater" — advisory-new *collects* (error diffs accumulating — promotion evidenced, theater only if never promoted; windows timeboxed). "rollbacks need reverts" — rollbacks need *pin changes* (one-line downgrades — version-keyed caches per 19/2.2 making downgrades clean).

**Performance note** — dual runs 2× check-time during windows (bounded — promotion closing; surprises prevented post-merge incidents — insurance arithmetic favorable).

**Mentor note** — upgrade-window review: "old required, new diffed, promotion dated?" (three states — windows timeboxed, promotions evidenced).

### 3) **Ecosystem lag gating** (framework editor linter windows, staged upgrades)

**Definition** — *lag gating*: upgrading past what the ecosystem supports staged (framework TS ranges, editor bundled-TS, typescript-eslint/Prettier compat matrices — support windows checked per dependency, upgrades sequenced: TS last or first per constraint graph, never jumped blindly). Windows: each dependency declaring supported TS ranges (peerDeps, compat docs — ranges read, not assumed).

**What problem it solves / history** — ecosystem breakage post-upgrade (framework types incompatible, editor features missing, lint rules erroring — TS green, toolchain red): gating sequencing upgrades past support (constraints graphed — TS moving within supported ranges, blockers upgraded first, TS following).

**Modern guidance** — read support ranges pre-upgrade (framework/editor/linter matrices — constraints graphed); sequence blockers first (incompatible deps upgraded before TS — TS following, not leading, where constrained); stage jumps (TS → toolchain → flags — ordered, each green before next, see 16/3.3 lag management).

**Runnable example** — sequenced upgrades (good vs bad, `tsc --strict`):

```typescript
// good — range-respecting code (supported idioms — ecosystem agreeing across the window)
export {}; // module marker (consistent module scope across fences)
export function ecoSafe(value: unknown): string {
  if (typeof value !== "string") throw new Error("string-only"); // narrowing idioms (stable across TS + toolchain versions — support windows overlapping here)
  return value.toUpperCase();
}
console.log(ecoSafe("ok")); // OK — supported shapes (windows overlapping — upgrades sequenced within support, never past it)
// bad — blind TS jumps (toolchain red post-upgrade — framework types incompatible, lint erroring, editors stale)
// fix — range reading + sequencing (constraints graphed — blockers first, TS within support, stages green in order)
```

```text
// good — support-matrix check (ranges read — upgrades sequenced, never jumped)
// pre-upgrade checklist (labeled doc — constraints graphed):
// framework: supports TS 5.5–5.9 (range read — jump to 5.9 inside, 6.0-beta staged after framework majors)
// editor: bundled TS 5.9 (features present — no staleness)
// lint: typescript-eslint 8.x ↔ TS 5.9 (matrix green — rules running, not erroring)
// (all green → upgrade proceeds; any red → blockers first, TS following)
```

**Common confusion** — "latest TS always safe" — latest safe *within support windows* (ranges constraining — beta/RC past framework ranges staged, never jumped). "ecosystem follows TS" — ecosystem *lags* TS (weeks-to-months — gating respecting lag; leading-edge repos pinning betas deliberately with fallback plans). "staging slows upgrades" — staging *de-risks* upgrades (ordered greens — blind jumps rolling back wholesale, staged jumps rolling back per stage).

**Performance note** — gating costs checklist-minutes (matrix reads — cheapest upgrade insurance; blind-jump rollbacks hours-to-days across toolchain).

**Mentor note** — upgrade-PR attachment: support matrix (ranges evidenced — jumps reviewed against constraints, never against enthusiasm).
