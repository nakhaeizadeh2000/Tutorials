## 2.1. JavaScript to TypeScript file by file

### 1) **Bridge a real JavaScript dependency**

An incremental migration keeps a working execution path while improving selected static contracts. `allowJs` admits JavaScript into the configured program; `checkJs` controls reporting of JavaScript checking errors. JavaScript can still contribute inferred or JSDoc types to TypeScript callers when its own semantic diagnostics are not enabled. Neither flag validates external values or guarantees a build preserves runtime behavior. The [migration handbook](https://www.typescriptlang.org/docs/handbook/migrating-from-javascript.html) motivates separating input/output directories and introducing mixed inputs; use the actual current module/output strategy rather than copying its older ES5 and bundler examples as defaults.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. Create src in a disposable directory. Save `package.json`:

```json
{"name":"mixed-migration","version":"1.0.0","private":true,"type":"module"}
```

Save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "allowJs": true,
    "checkJs": false,
    "declaration": true,
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true
  },
  "include": ["src/**/*"]
}
```

Save the actual JavaScript dependency `src/scale.js`:

```javascript
export function scale(value, factor) { return value * factor; }
```

Save `src/main.mts`:

```typescript
import { scale } from "./scale.js";
const result: number = scale(3, 2);
console.log(result);
```

Save `verify.mjs` in the root. This is a JavaScript runtime verifier; it intentionally checks an existing coercing call as well as numeric calls:

```javascript
import assert from "node:assert/strict";
import { scale } from "./dist/scale.js";
assert.equal(scale(3, 2), 6);
assert.equal(scale(0, 8), 0);
assert.equal(scale(-2, 3), -6);
assert.equal(scale("3", 2), 6);
console.log("selected behavior preserved");
```

Run:

```bash
tsc -p tsconfig.json --listFilesOnly
tsc -p tsconfig.json
node dist/main.mjs
node verify.mjs
```

All exit 0; main prints 6 and the verifier prints `selected behavior preserved`. The file list includes both real source languages. The output directory contains copied/transformed JavaScript alongside emitted main.mjs and their declarations. Inspect dist/scale.d.ts: scale has any parameters and a number return inferred from multiplication. Consequently replacing main's first argument 3 with `"3"` also checks and runs at this stage. Restore main afterward. A strict caller has not repaired the unchecked parameter boundary.

This example is an emitted-only Node path. The import names scale.js, which exists in dist; it does not claim native Node 20 execution of main.mts. Separate outputs prevent overwriting source. Keep package metadata/module format with the actual deployed output arrangement.

### 2) **Add checked contracts before or during a rename**

Turn checkJs to true and check again. Both unannotated JavaScript parameters produce TS7006. This contradicts the idea that checkJs only checks already annotated files. Replace scale.js with this actual JSDoc form:

```javascript
/** @param {number} value @param {number} factor @returns {number} */
export function scale(value, factor) { return value * factor; }
```

Build, run main and run the verifier again: all pass with the original observed results. dist/scale.d.ts now exposes number parameters. Changing main to call scale with `"3"` fails TS2345; restore it. The JavaScript runtime verifier still accepts that coercing call because comments did not implement validation. The static API is now narrower than the previous any boundary, a deliberate change for checked callers.

For a TypeScript conversion, rename scale.js to scale.ts without changing main's output-extension import. In this environment the checker resolves that import to the TypeScript source, and emission still creates dist/scale.js. The existing JSDoc parameter comments do not supply TypeScript parameter annotations: checking the merely renamed file reports TS7006. Replace its contents with:

```typescript
export function scale(value: number, factor: number): number { return value * factor; }
```

Build and rerun both entries. They pass with the same selected behavior. Inspect the declaration to confirm the intended numeric contract. Remove the old JavaScript source when renaming; do not keep competing same-stem inputs and infer which one a tool chose. This small rename happens to preserve output names, but moving to a different module format or source-extension execution requires its own import and host checks.

As a meaningful negative, temporarily change multiplication to addition in the typed implementation. Checking succeeds because the numeric signature is unchanged, while verify.mjs fails. Restore multiplication and rerun. The passing tests support the listed cases, not equivalence over every JavaScript input, exceptional value or consumer. If the desired policy is to reject coercion at runtime, implement and test that separately rather than attributing it to annotations.

### 3) **Choose a migration unit and a completion criterion**

A small independent dependency is often a useful first unit because its callers expose a manageable contract. Other migrations need a coherent group of files, module-format changes or tooling work together. File-by-file is a strategy for reviewable progress, not a rule that every file is independent or needs one separate merge. Check actual callers, build artifacts and relevant behavior before promoting a unit. Preserve a way to restore the prior revision and its dependency/configuration state when necessary.

JSDoc-checked JavaScript can be a maintained destination as well as a bridge. Choose TypeScript syntax where its expression and contributor workflow improve maintainability; declaration output alone does not require converting every JavaScript source. The [JavaScript/JSDoc owner](<../3. Interop and Portable Code/3.1. allowJs checkJs and JSDoc-typed JavaScript.md>) owns the broader checking and annotation vocabulary. Conversion may require reorganizing types and imports rather than a mechanical one-to-one translation.

[Airbnb's original migration account](https://medium.com/airbnb-engineering/ts-migrate-a-tool-for-migrating-to-typescript-at-scale-cd23bfeb5cc) describes choosing project-wide automated conversion with follow-up type improvement. Its [maintainer README](https://github.com/airbnb/ts-migrate) explicitly notes remaining any and suppression work after a compiling result. That historical experience shows why incremental file conversion is not universally superior and why a renamed-file count is not a type-quality measure. It does not establish compatibility of that tool with this native compiler; ts-migrate was not run here.

A practical progress record names converted contracts, remaining unchecked boundaries, relevant probes and accepted exceptions. A falling JavaScript count can accompany widespread any or lost coverage. Review that evidence alongside counts, and keep feature and migration changes separable when doing so improves diagnosis. No universal conversion throughput, percentage payoff or guaranteed delivery schedule follows from the strategy.

### 4) **Common confusion**

allowJs admits JavaScript; it does not mean every JavaScript diagnostic is reported or every inferred parameter is safe. checkJs applies to selected JavaScript beyond JSDoc annotations. Per-file directives can also change reporting; the detailed owner explains those controls.

Annotations can narrow checked callers without rejecting the same inputs at runtime. In this exercise the historical string coercion still executes from JavaScript after the numeric TypeScript API is introduced. Decide and document that boundary rather than calling all type-only changes behavior validation.

### 5) **Performance note**

This exercise observes checking, declaration output and selected runtime behavior. It measures no editor latency, migration throughput or relative JS/TS checking speed. Program cost depends on selected files and type relationships, not simply annotation density or file-extension count. Keep the work being checked and emitted comparable when investigating migration-related build changes.

### 6) **Mentor note**

Ask the learner to show the declaration before and after JSDoc, then explain why the JavaScript string-coercion assertion still passes. A sound answer separates inferred any, checked contract and runtime implementation. Next ask why a plain rename can report errors even though the comments already describe numbers.

For a migration proposal, require the execution path, chosen reviewable unit and evidence of contract improvement. Ask what a green source check would miss: output routing, unchecked callers, lost type-test selection and runtime behavior are plausible answers. Reward a stated limit rather than a promise that renaming all files completes safety.
