## 7.1. Boundaries — what is covered elsewhere

Class typing draws on runtime objects, callable contracts and configuration. Use the failing operation to choose an owner: a field appears in JavaScript output, a shape assignment fails, a stored method loses its receiver, a union needs narrowing, or a decorator needs the correct configured program. This page connects those questions without repeating their full examples. The current compiler baseline and support boundaries live in the [current learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>); individual owners declare their tested environment.

### 1) **Runtime mechanics and static class views**

JavaScript owns constructor execution, prototype delegation, field order, runtime private names and descriptor behavior. TypeScript adds instance/constructor-side types, member access checks, class compatibility, abstract/override declarations, generic class relationships and constructor queries. Ask which statement executes before deciding whether a type annotation can change its outcome.

For field evaluation and the constructor versus instance storage boundary, use [runtime class fields and statics](<../../../../JavaScript/07 Prototypes and Classes/sections/3. Class syntax/3.4. Static members static blocks and class field order.md>). For class syntax and inheritance prerequisites, use the [JavaScript class index](<../../../../JavaScript/07 Prototypes and Classes/README.md>). The local [class duality owner](<../1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>) names the two type views; [constructor queries](<../3. Advanced Class Patterns/3.3. Class type queries InstanceType and constructor signatures.md>) deepens their extraction.

A checker annotation is not runtime validation, and a syntax gate is not a universal source-execution guarantee. Use the already verified [bounded erasable pipeline](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) and [runner comparison](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) when the failure belongs to processing or resolution.

### 2) **Object contracts and class-specific extensions**

A class instance participates in object-shape checking. [Object shapes and excess properties](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) owns the ordinary member contract, while [modifiers and dictionaries](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) owns property optionality, readonly views and index signatures. Do not reintroduce those rules under a new class name.

Stay in this domain for [class extends/implements](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) and [access modifiers](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>). For plain object inheritance versus intersection, use [object composition](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>). For same-name declaration/augmentation behavior, use [merging](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.2. Declaration merging and module augmentation.md>). The declaration's name alone does not supply a runtime object or validate its input.

### 3) **Callable contracts and method invocation**

A method is a callable whose actual invocation may supply or lose a receiver. The [receiver owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) compares implicit body inference, explicit call requirements and real bind/arrow remedies. A callback type without an explicit receiver requirement does not automatically reject every extracted method. A this:void target does not prohibit outer lexical capture or prove every implicit method safe.

The [callback variance owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) owns supplied-input substitution and the method exception. [Overloads](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>) owns public signatures versus implementation bodies; [generic callables](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) owns call-level evidence.

Stay here for [class override and polymorphic this](<../2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>) and [generic class/static relationships](<../3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>). Runtime binding itself belongs in [call/apply/bind](<../../../../JavaScript/05 Functions Deep Dive/sections/3. this binding/3.3. call apply bind and bound functions.md>). A parameter/result forwarding type does not bind a receiver.

### 4) **Union narrowing and runtime evidence**

Class values can appear as union members, but the full narrowing catalog belongs in [built-in narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.1. Union Types/1.2. Discriminated unions the tagged pattern that scales.md>); class heritage does not automatically choose a complete domain model.

Use [callable predicates and assertions](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) for explicit/inferred predicate signatures and successful assertion continuation. Use [unknown boundaries](<../../../03 Basic Types and Annotations/sections/2. ### 5) **Decorator configuration and composition ownership**

The class domain owns members, inheritance, abstract/override checks and [mixins](<../3. Advanced Class Patterns/3.2. Mixins and class composition without inheritance.md>). The decorator domain owns decorator signatures, evaluation/application and configured transformation. Use the [actual standard-versus-legacy programs](<../../../14 Decorators and Metadata/sections/2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) before borrowing a wrapper into a framework or changing its flags. Use the [metadata owner](<../../../14 Decorators and Metadata/sections/2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) for initialization/inheritance/read boundaries, and the [DI lifecycle owner](<../../../14 Decorators and Metadata/sections/3. Patterns in Practice/3.3. Dependency injection with decorators.md>) for its tested local container relationships.

These topics are already published; there is no need to wait for a future decorator track. For application-oriented backend work, the [root curriculum](<../../../../../README.md>) retains NestJS with the Fastify adapter as the vehicle and names the prerequisite sequence. A local class or container fixture does not establish framework integration or authorize authoring that planned track.

### 6) **Common confusion**

Class syntax does not absorb all object, function and runtime behavior into one type-system rule. A modifier can affect checking while the underlying operation still executes. A method's inferred body receiver is not automatically an extraction restriction; a declaration supplies no runtime data by itself. Locate the actual object, function and call before deciding which owner answers the failure.

### 7) **Performance note**

Navigation and type annotations have no direct runtime performance effect. Construction, stored callbacks, decorators and runtime checks can execute real work, but this routing lesson measures none of it. A compiler budget or runtime allocation problem needs its own evidence; use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) rather than inferring a speed improvement from rearranged documentation or changed type syntax.

### 8) **Mentor note**

Give the learner three reports and require the owner plus the next observation. A parameter-property file accepted by ordinary checking but rejected by an erasable gate belongs to the processing/constructor syntax boundary: inspect the consumed source and declared tool configuration. A queued method that compiles and loses its receiver belongs to the callable invocation boundary: compare the actual call with bind or an arrow wrapper. A decorator reading no route metadata belongs to the metadata/configuration boundary: inspect symbol initialization and the store/read channel before changing the class's public shape. The linked owners contain the actual observed contrasts; this routing exercise requires a justified diagnostic plan, not a claimed new execution.
