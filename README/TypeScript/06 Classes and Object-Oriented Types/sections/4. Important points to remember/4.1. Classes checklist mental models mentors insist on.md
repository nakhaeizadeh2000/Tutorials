## 4.1. Classes checklist — mental models mentors insist on

### 1) **Class is both type and value** (the name lives in two declaration spaces — instance type vs constructor value)

**Definition** — `class User` is two symbols: `User` (instance) in type space and `typeof User` (constructor+statics) in value space — never conflate `User` with `typeof User`.

**What problem it solves** — JS `new User()` and `User.static()` share the name — duality lets `let u: User` (instance) and `typeof User` (factory param) be distinct without renaming.

**Modern guidance** — as of TypeScript 5.9 era, use `User` for instances, `typeof User` for Ctors, `InstanceType<typeof User>` only when bridging from a value.

**Runnable example** — duality checklist (good vs bad, `tsc --strict`):

```typescript
class User { constructor(public id: string) {} static kind = "user" as const; }
let u: User = new User("u1"); // instance side
let Ctor: typeof User = User; // constructor side
type Inst = InstanceType<typeof User>; // == User
// const bad: typeof User = new User("u1"); // error — instance ≠ constructor
```

```typescript
// good — construct signature type as alternative to typeof
class User2 { constructor(public id: string) {} }
type CtorSig = new (id: string) => User2;
function build(C: CtorSig): User2 { return new C("u1"); }
build(User2); // ok
```

**Common confusion** — "`class` is nominal" — structural unless `private`/`#private` present.

**Performance note** — dual symbol is checker-only — one class emits once.

**Mentor note** — ask "what is `User` in `let x: User` vs `x = User`?" — instance vs value.

**Cross-links** → [1.1. Class as type and value duality](<../1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>).

### 2) **extends is inheritance; implements is a check** (structural assignability survives either — only private/#private adds nominal separation)

**Definition** — `extends` inherits prototype + types; `implements` only checks shape at declaration; structural assignability determines runtime passing regardless.

**What problem it solves** — prevents coupling to base just for a shape guarantee; lets same-shaped classes from different bundles interoperate.

**Modern guidance** — use `extends` for *is-a* + shared logic; `implements` for *has-shape* adapter; add `private __brand` for domain separation where same shape would leak (`User` vs `Order`).

**Runnable example** — check vs inherit (good vs bad, `tsc --strict`):

```typescript
interface Logger { log(msg: string): void; }
class Base { constructor(protected table: string) {} }
class UserRepo extends Base implements Logger {
  constructor() { super("users"); }
  log(msg: string): void { console.log(msg); }
}
class LooseLogger implements Logger { log(msg: string): void {} } // no extends, still Logger

// structural leak without brand
class User { constructor(public id: string) {} }
class Order { constructor(public id: string) {} }
function deleteUser(u: User): void {}
declare let order: Order;
// deleteUser(order); // compiles — same shape → leak
// fix: private brand
class SafeUser { private __u = true; constructor(public id: string) {} }
class SafeOrder { private __o = true; constructor(public id: string) {} }
// deleteUserSafe(new SafeOrder("o1")); // error — brand blocks
```

```typescript
// good — implements error at class site, not call site
// class BadLog implements Logger {} // error — missing log — local
```

**Common confusion** — "`implements` changes assignability" — no, structure does.

**Performance note** — `implements` erases; `extends` adds one prototype link.

**Mentor note** — remove `implements` and show assignability still holds — ask what was lost (local check).

**Cross-links** → [2.1. Extends implements](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>).

### 3) **abstract ships, interface describes** (choose by whether subclasses should share runtime and construction control)

**Definition** — `interface` is shape-only (erases); `abstract class` ships shared helpers, constructor logic, and `abstract` enforcement; evolution via abstract can add defaults without breaking implementers.

**What problem it solves** — library evolution: adding `perimeter()` to `interface Shape` breaks every implementer; adding it with default to `abstract class Shape` doesn't.

**Modern guidance** — `interface` for data/adapter contracts; `abstract class` when subclasses share runtime (`describe()`, `super` validation, registry).

**Runnable example** — evolution (good vs bad, `tsc --strict`):

```typescript
abstract class Shape {
  abstract area(): number;
  perimeter(): number { return 0; } // default
  describe(): string { return `area=${this.area()}`; }
}
class Circle extends Shape {
  constructor(public r: number) { super(); }
  area(): number { return Math.PI * this.r * this.r; }
}
// interface variant would break Circle if area/perimeter added

abstract class Entity {
  protected constructor(public id: string) {} // construction control
}
class UserE extends Entity { constructor(id: string, public name: string) { super(id); } }
// new Entity("e1"); // error — abstract + protected
```

```typescript
// bad — duplicating shared logic per class because interface chosen
interface HasDescribe { describe(): string; }
// class A implements HasDescribe { describe(){ /* duplicate */ } } // shared helper lost
```

**Common confusion** — "`abstract class` cannot have constructor logic" — it can and should via `super()`.

**Performance note** — abstract helpers are single prototype method, not per-instance.

**Mentor note** — add a new method to both an `interface` and an `abstract class` and count breakage.

**Cross-links** → [2.2. Abstract classes](<../2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>).

### 4) **override + this preserve the chain** (override proves polymorphism; this return keeps subclass identity without re-casting)

**Definition** — `override` (TS 4.3+, `noImplicitOverride`) proves a member overrides a base; `method(): this` makes the return track the actual receiver (polymorphic this), preserving subclass type through base methods.

**What problem it solves** — rename of `Base.save()` to `Base.persist()` orphaned every `Sub.save()` silently before `override`; `clone(): Base` lost subclass type and needed casts before `this`.

**Modern guidance** — enable `noImplicitOverride` and mark every override; use `(): this` for chainable/fluent, `clone(): this`, `static create(): this` via `this` param.

**Runnable example** — override + this (good vs bad, `tsc --strict --noImplicitOverride`):

```typescript
class Repo {
  save(item: string): void { console.log(item); }
}
class UserRepo2 extends Repo {
  override save(item: string): void { console.log(`user ${item}`); super.save(item); }
  // override handel(): void {} // error — not in base — catches typo
}

class Fluent {
  protected x = 0;
  setX(v: number): this { this.x = v; return this; }
}
class SubFluent extends Fluent { private y = 0; setY(v: number): this { this.y = v; return this; } }
const s = new SubFluent().setX(1).setY(2); // this keeps SubFluent

// bad — base return loses subclass
class BaseBad {
  clone(): BaseBad { return new BaseBad(); }
}
class SubBad extends BaseBad {}
// const sb = new SubBad().clone(); // BaseBad — lost SubBad
```

```typescript
// good — explicit this param vs arrow
class Clicker {
  count = 0;
  incMethod(): void { this.count++; }
  incArrow = (): void => { this.count++; }; // captured — safe when detached
}
const cl = new Clicker();
const a = cl.incArrow; a(); // ok — arrow captured
// const m = cl.incMethod; // m() would lose this
```

**Common confusion** — "`override` changes dispatch" — only validates; "`this` needs generics" — it is generic over self already.

**Performance note** — `override` erases; `this` return is reference return, monomorphic.

**Mentor note** — rename demo: rename `Base.save` and show `override`-less subclass silently diverges vs `override` errors immediately.
