## 4.1. Classes checklist — mental models mentors insist on

A class review asks several independent questions: what value is constructed, what contract the checker sees, where behavior comes from and which instance a method returns. Keep those questions separate. A familiar class name, an implements clause or a fluent return annotation cannot substitute for the evidence needed by another operation.

This checklist consolidates the preceding owners through one small job API. Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save `class-review.ts` in a fresh directory without tsconfig.json. Build and run:

```bash
tsc --strict --noImplicitOverride --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist class-review.ts
node dist/class-review.js
```

For an intentional rejection, activate just one commented line in a separate copy and replace `--outDir dist` with `--noEmit`. Do not run rejected source.

```typescript
export {};
interface Runnable { run(): string }
abstract class Job {
  static category = "job";
  name: string;
  constructor(name: string) { this.name = name; }
  abstract run(): string;
  describe(): string { return this.name + ": " + this.run(); }
}
class EmailJob extends Job implements Runnable {
  recipient = "unset";
  setRecipient(value: string): this { this.recipient = value; return this; }
  run(): string { return "email to " + this.recipient; }
}
class AuditedEmailJob extends EmailJob {
  override run(): string { return "audited " + super.run(); }
  auditId = "a1";
}
function create<T extends Job>(Ctor: new (name: string) => T, name: string): T {
  return new Ctor(name);
}
const Ctor: typeof AuditedEmailJob = AuditedEmailJob;
const job: AuditedEmailJob = create(Ctor, "welcome");
const configured = job.setRecipient("Ada");
console.log("views:", Ctor.category, typeof Ctor, typeof job);
console.log("receiver:", configured === job, configured.auditId);
console.log(job.describe());
const adapter: Runnable = { run: () => "adapter" };
console.log("shape:", adapter.run(), adapter instanceof Job);
// const wrongSide: typeof AuditedEmailJob = job; // Instance cannot supply this constructor.
// class MissingJob extends Job {} // Missing required run hook.
// create(Job, "base"); // Abstract input cannot meet a concrete constructor requirement.
// class StaleJob extends Job { override send(): string { return "old"; } run(): string { return "ok"; } }
// class MissingOverride extends EmailJob { run(): string { return "replacement"; } }
// class InvalidCopy { copy(): this { return new InvalidCopy(); } }
```

Both positive commands exit 0. Output is:

```text
views: job function object
receiver: true a1
welcome: audited email to Ada
shape: adapter false
```

### 1) **Identify the instance view and the constructor value**

`job: AuditedEmailJob` describes the instance. `Ctor: typeof AuditedEmailJob` describes the constructor value, including its public construction contract and statics. The type-position typeof query is checker syntax; the `typeof Ctor` expression printed at runtime is a JavaScript operation. The class name supplies both an instance type and a value; typeof is how a type annotation describes that value, not another runtime constructor.

The first line shows a constructor function and an instance object. The inherited static category is read from Ctor, not from job. Activate wrongSide to see TS2739: the instance lacks the constructor-side requirements. In review, name the operation first: passing an existing job needs its instance contract; constructing one needs a constructor value with suitable arguments. [Class duality](<../1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>) owns static receivers, default instanceof behavior and custom hooks; [class queries](<../3. Advanced Class Patterns/3.3. Class type queries InstanceType and constructor signatures.md>) owns InstanceType and ConstructorParameters.

### 2) **Separate implementation inheritance from contract compatibility**

The extends chain supplies Job.describe and dispatches its run call to the audited subclass. The implements clause checks EmailJob against Runnable at its declaration; it does not install run. The plain adapter also satisfies Runnable, despite not inheriting Job. Its false instanceof result is compatible with its successful type assignment.

Removing implements leaves the same methods and accepted assignments here, while losing the explicit declaration-site completeness check. Removing extends would remove inherited behavior unless another implementation supplied it. Neither operation is a general refactoring recipe. Check actual callers, constructors and runtime relationships before changing inheritance.

Public shapes can match across unrelated classes. Private and **protected** members also impose declaration-origin requirements; sibling classes inheriting the same protected member can remain compatible, whereas unrelated declarations with the same spelling do not establish a shared origin. The [primary compatibility guide](https://www.typescriptlang.org/docs/handbook/type-compatibility.html#private-and-protected-members-in-classes) and [inheritance owner](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) develop that distinction. For meaningfully different IDs or entities, choose a deliberate domain contract from the [branding owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>); a cast is not a runtime identity check.

### 3) **Require concrete construction and meaningful shared behavior**

Job supplies describe and constructor initialization. Its abstract run states an obligation for concrete subclasses. Activate MissingJob to observe TS2515; activate create(Job, ...) instead to observe TS2345. The factory's concrete new signature is the evidence its body needs to construct T. Abstract constructor signatures are useful for inspection or queries, where construction is not performed.

Inspect dist/class-review.js: the interface, abstract hook, type queries and generic signatures are absent. The Job class, name assignment, describe implementation and extends relationships remain. Abstract is checker enforcement, not a runtime prohibition against new; the [abstract owner](<../2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>) demonstrates the controlled failure from forcing construction. Ordinary private or protected constructors provide separate checker access restrictions without requiring abstract.

Choose an interface when callers need a capability such as run without an inheritance requirement. Choose a base class when inherited behavior and the extension contract are useful. A default implementation added to a base can preserve source compatibility yet violate behavior; returning a fictitious perimeter of zero is not a safe evolution strategy. Test what consumers depend on. Constructor initialization and access belong in [constructors](<../1. Class Type Fundamentals/1.2. Constructors parameter properties and instance creation.md>); privacy mechanisms belong in [access modifiers](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>).

### 4) **Check override intent and the actual returned receiver**

EmailJob supplies the abstract run hook without an override marker; the declared noImplicitOverride setting accepts that abstract implementation. AuditedEmailJob replaces a concrete body, so it carries override. Activate MissingOverride for TS4114, or StaleJob for TS4113 because send does not exist in Job. The marker checks a member relationship. It does not change dispatch or prove that replacement behavior is correct. The [option reference](https://www.typescriptlang.org/tsconfig/noImplicitOverride.html) explains the rename problem; test the contract's behavior separately.

setRecipient returns its actual receiver. That is why configured equals job and still exposes auditId. The [this-type guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#this-types) shows how such instance self types preserve the subtype. A copy is different: activate InvalidCopy for TS2322, since a newly created base object cannot satisfy every possible subclass this type. Give copying an explicit construction/state contract instead of casting this.constructor to a guessed signature.

A static factory also needs its own constructor receiver contract; static create(): this is not the instance self-return mechanism. These cases and callback detachment are worked through in [override and polymorphic this](<../2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>). Returning this neither binds a detached method nor validates a fresh instance.

### 5) **Common confusion**

Compatibility, inheritance and construction are different checks. The adapter runs without being a Job; a concrete subclass can be constructed through the matching signature; the abstract base can be named in a type query without being a valid factory input. The fact that abstract and implements erase does not mean that the whole class or its runtime helpers disappear.

Private/protected origin requirements are not universal nominal typing for every projection. A consumer that requests only a public capability may accept more values. Runtime #private access is a separate enforcement mechanism from a TypeScript private modifier. Use the linked owners to decide which contract an actual boundary needs.

### 6) **Performance note**

The interface, implements/override/abstract modifiers, type queries and annotations add no emitted runtime operations. The sample still allocates instances, initializes fields and calls methods through an inherited chain. Returning this reuses an existing reference; copying would perform whatever allocation and state work its implementation contains. No method speed, allocation size, hierarchy threshold or checker-cost formula was measured here. Inspect emitted code to identify work, then use an appropriate profiler for a demonstrated runtime concern; the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) addresses compiler checking separately.

### 7) **Mentor note**

Ask the learner to predict the output before running it, then remove implements and explain what is lost. A sound answer preserves the adapter assignment and inherited behavior while identifying the removed local completeness check. Next, activate create(Job, ...) and explain why an inspection helper could accept Job while this factory cannot.

For review practice, replace setRecipient's return with a new EmailJob. The checker should reject it as a self return; even a cast would fail the sample's identity expectation. Finally, rename a concrete base member with a marked subclass replacement still present. Require both the compiler diagnostic and an explanation of the intended dispatch. These checks test reasoning rather than keyword recall.
