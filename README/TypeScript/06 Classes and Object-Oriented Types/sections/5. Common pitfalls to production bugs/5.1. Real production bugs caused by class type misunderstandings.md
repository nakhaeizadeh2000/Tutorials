## 5.1. Real production bugs caused by class type misunderstandings

The following local reproductions model failure patterns; they are not accounts of measured external incidents. Each connects a checked contract to the operation that actually runs. The remedies address different boundaries: domain meaning, serialization, mutation and dispatch. One modifier cannot solve all four.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save each named program in a fresh directory without tsconfig.json. Build with `tsc --strict --noImplicitOverride --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. All positive programs exit 0. Activate one marked negative in a separate copy and use `--noEmit` instead of `--outDir dist` to observe the checker failure. Runtime failures are caught; all stored data is local demonstration data.

### 1) **A public shape does not establish domain identity**

Two classes with matching public members can satisfy the same instance contract. If an operation interprets id specifically as a user ID, accepting a same-shaped order can select the wrong record. The following intentionally uses an identical string in both stores so that the consequence is visible rather than just logging a misleading operation name.

Save `domains.ts`:

```typescript
export {};
class User { id: string; constructor(id: string) { this.id = id; } }
class Order { id: string; constructor(id: string) { this.id = id; } }
const users = new Map([["shared", "Ada"]]);
const orders = new Map([["shared", "book"]]);
function deleteUser(user: User): void { users.delete(user.id); }
const order = new Order("shared");
deleteUser(order); // Accepted: the public instance shape matches.
console.log("wrong domain:", users.has("shared"), orders.has("shared"), order instanceof User);

class SafeUser {
  private brand = "user";
  id: string;
  constructor(id: string) { this.id = id; }
}
class SafeOrder {
  private brand = "order";
  id: string;
  constructor(id: string) { this.id = id; }
}
function userId(user: SafeUser): string { return user.id; }
console.log("checked user:", userId(new SafeUser("u1")));
// userId(new SafeOrder("o1")); // TS2345: different private declaration origins.
const forced = new SafeOrder("o1") as unknown as SafeUser;
console.log("assertion accepted:", userId(forced));
const publicView: Pick<SafeUser, "id"> = new SafeOrder("o2");
console.log("public projection:", publicView.id);
```

Output is `wrong domain: false true false`, `checked user: u1`, `assertion accepted: o1`, then `public projection: o2`. The wrong operation removed the user while leaving the order. Type compatibility did not test the runtime prototype chain or the meaning of the ID.

The private member separates the complete SafeUser/SafeOrder contracts at checked call sites. The marked call fails with TS2345, exit 1. The double assertion still compiles and the public projection deliberately asks for less evidence. Neither validates a user identity. Use a checked domain factory/contract where identities must remain distinct, keep its evidence through the consuming API, and validate external values at their actual boundary. The [branding owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) develops those choices. [Inheritance compatibility](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) also covers shared protected origins; separation is not limited to two private keywords.

### 2) **Checker-private data can appear in serialization**

A TypeScript private modifier limits checked member access; it does not remove the runtime property. Ordinary enumeration, spread and JSON serialization can therefore expose it. A runtime private name is a different member representation. The [primary privacy caveats](https://www.typescriptlang.org/docs/handbook/2/classes.html#caveats) explain this distinction.

Save `serialization.ts`:

```typescript
export {};
class SoftSession {
  userId: string;
  private token = "demo-secret";
  constructor(userId: string) { this.userId = userId; }
}
const soft = new SoftSession("u1");
console.log("soft key:", Reflect.get(soft, "token"));
console.log("soft keys:", Object.keys(soft).join(","));
console.log("soft JSON:", JSON.stringify(soft));
console.log("soft spread:", Reflect.get({ ...soft }, "token"));
// soft.token; // TS2341: ordinary checked private access.
class HardSession {
  userId: string;
  #token = "demo-secret";
  constructor(userId: string) { this.userId = userId; }
  masked(): string { return this.#token.slice(0, 2) + "***"; }
}
const hard = new HardSession("u1");
console.log("hard keys:", Object.keys(hard).join(","));
console.log("hard JSON:", JSON.stringify(hard));
console.log("hard spread:", Object.keys({ ...hard }).join(","));
console.log("ordinary lookups:", Reflect.get(hard, "token"), Reflect.get(hard, "#token"));
console.log("public result:", hard.masked());
```

The output is:

```text
soft key: demo-secret
soft keys: userId,token
soft JSON: {"userId":"u1","token":"demo-secret"}
soft spread: demo-secret
hard keys: userId
hard JSON: {"userId":"u1"}
hard spread: userId
ordinary lookups: undefined undefined
public result: de***
```

The direct private access is rejected, while the reflection operations are accepted and execute against ordinary keys. Neither string lookup on hard addresses its lexical private name. The private member is absent from these ordinary serialization operations, but a public method or custom serializer can still deliberately return its value. Review the intended output surface, not just the field spelling. Do not send a secret-bearing instance to a general logger and assume its checker type removes internal data.

The [access-modifier owner](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>) supplies private-name parsing/access failures and native ES2022 versus transformed ES2015 artifacts. The tested output here retains native #token. A claim that every private field is always implemented as a WeakMap would confuse one compilation target with a language requirement.

### 3) **Readonly, getter-only and frozen are different mutation boundaries**

A readonly annotation does not make an ordinary field's descriptor unwritable. Another compatible writable view can mutate it without an assertion. A getter-only public property and Object.freeze affect runtime operations, but neither implies recursive immutability of every referenced object.

Save `mutation.ts`:

```typescript
export {};
class Config {
  readonly host: string = "localhost";
  readonly nested = { port: 5432 };
}
const defaults = new Config();
const alias: { host: string } = defaults;
alias.host = "changed";
console.log("alias:", defaults.host);
// defaults.host = "blocked"; // TS2540 through the readonly view.
Object.freeze(defaults);
defaults.nested.port = 443;
try { alias.host = "blocked"; }
catch (error: unknown) {
  console.log(error instanceof TypeError ? "frozen write: TypeError" : "unexpected error");
}
console.log("shallow:", defaults.host, defaults.nested.port, Reflect.set(defaults, "host", "other"));
class GetterConfig {
  #host = "localhost";
  get host(): string { return this.#host; }
}
const getter = new GetterConfig();
try { (getter as unknown as { host: string }).host = "blocked"; }
catch (error: unknown) {
  console.log(error instanceof TypeError ? "getter write: TypeError" : "unexpected error");
}
console.log("getter:", getter.host, Object.hasOwn(getter, "host"), Reflect.set(getter, "host", "other"));
console.log("still extensible:", Reflect.set(getter, "note", "allowed"));
// getter.host = "blocked"; // TS2540: getter-only checked view.
```

Output is `alias: changed`, `frozen write: TypeError`, `shallow: changed 443 false`, `getter write: TypeError`, `getter: localhost false false`, then `still extensible: true`. The strict emitted assignment to the inherited getter without a setter fails; it does not create an own host property. Reflect.set returns false without throwing. The [ordinary setter algorithm](https://tc39.es/ecma262/2026/multipage/ordinary-and-exotic-objects-behaviours.html#sec-ordinarysetwithowndescriptor) accounts for this accessor failure.

Freeze blocks the immediate host write, while the referenced nested object remains mutable. GetterConfig's backing state stays unchanged through the attempted public assignment, but the instance still permits another ordinary property. Choose the exact mutation policy required by the data model, including referenced state and intentional update methods. Type-level readonly utilities do not recursively freeze existing runtime objects. The [object modifier owner](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) owns the broader view/integrity contrasts.

### 4) **A renamed base method can leave a stale subclass method**

After a base API changes from save to persist, an unmarked subclass save can remain as a separate method. Calling persist then uses the inherited implementation. The old method has not become an overload of the new name. Test the path the caller actually invokes.

Save `rename.ts`:

```typescript
export {};
class RenamedBase {
  persist(item: string): string { return "base " + item; }
}
class LegacySub extends RenamedBase {
  save(item: string): string { return "legacy " + item; }
}
const legacy = new LegacySub();
const baseView: RenamedBase = legacy;
console.log("after rename:", baseView.persist("u1"), legacy.save("u1"));
class RepairedSub extends RenamedBase {
  override persist(item: string): string { return "user -> " + super.persist(item); }
}
console.log("repaired:", new RepairedSub().persist("u1"));
// class MarkedStale extends RenamedBase { override save(item: string): string { return item; } } // TS4113.
// class UnmarkedReplacement extends RenamedBase { persist(item: string): string { return item; } } // TS4114.
```

Output is `after rename: base u1 legacy u1`, then `repaired: user -> base u1`. This program uses noImplicitOverride, yet LegacySub.save is accepted because no current base save exists. The flag cannot recover historical intent from an unmarked new member. A retained explicit override would reject the stale name with TS4113; an actual concrete replacement missing the marker is rejected with TS4114. Reconnect the intended operation and test its behavior rather than merely deleting an error-producing keyword.

The [override owner](<../2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>) covers the accepted abstract-hook exception, self returns and callback detachment. The marker erases and does not alter JavaScript dispatch. Instance self returns and captured callbacks solve separate problems; neither repairs a renamed method relationship.

### 5) **Common confusion**

A brand restricts the checked target that carries it; a public projection can intentionally drop it. An assertion changes checker acceptance without installing validation, private state or a new prototype chain. Checker-private fields remain ordinary runtime properties, while private names are outside ordinary own-key serialization. Readonly checking, an accessor without a setter and shallow freeze reject different operations. Finally, noImplicitOverride checks current relationships rather than remembering a deleted base method.

### 6) **Performance note**

The private modifier erases, but `private brand = "user"` still has a real field initializer. Native private fields, getter calls, Maps, serialization, spread and freeze all perform runtime work. A type-only brand and an initialized class field are not the same emitted pattern. This lesson measured no fixed field bytes, WeakMap overhead, freeze complexity or fastest-access ranking. Choose a mechanism that enforces the required boundary, inspect the actual output, then measure a demonstrated cost in the deployed workload.

### 7) **Mentor note**

Have the learner explain the first reproduction using both the accepted assignment and the two Map states. Then predict the soft/hard JSON output and identify the exact serialization mechanism. An answer based only on the word private is incomplete.

For mutation, ask why the alias write succeeds before freeze, why the nested port still changes afterward and why the getter assignment cannot create an own host property. Finally, show LegacySub under noImplicitOverride and ask why it still compiles. Require a proposed repair and an observed call through the consumer's base view. These questions connect the compiler's evidence to the operation whose behavior matters.
