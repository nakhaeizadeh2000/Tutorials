## 5.1. Real production bugs caused by class type misunderstandings

### 1) **Structural class leak** (a Dog instance passed where a Cat was expected — same shape, no private brand — mutated missing field at runtime)

**Definition** — incident: `function adoptCat(c: Cat)` received a `Dog` (both `{ name: string }`) — structural assignability allowed it, runtime mutated `c.whiskerLength` that `Dog` didn't have — `undefined` propagated to snapshot.

**What problem it solves** — exposes that class names are not nominal — same public shape → assignable without heritage.

**Modern guidance** — as of TypeScript 5.9 era, brand domain classes that must not mix (`User` vs `Order`) via `private __brand` or `#private`.

**Runnable example** — leak and fix (good vs bad, `tsc --strict`):

```typescript
// bad — same shape, no brand → leak
class User { constructor(public id: string) {} }
class Order { constructor(public id: string) {} }
function deleteUser(u: User): void { console.log(`delete ${u.id}`); }
declare let order: Order;
deleteUser(order); // compiles — shape leak → deleted order by mistake

// good — private brand blocks leak
class SafeUser { private __u = true; constructor(public id: string) {} }
class SafeOrder { private __o = true; constructor(public id: string) {} }
declare let safeOrder: SafeOrder;
// deleteUserSafe(safeOrder); // error — brand mismatch
function deleteUserSafe(u: SafeUser): void { console.log(u.id); }
deleteUserSafe(new SafeUser("u1")); // ok

// good — #private also brands + hides at runtime
class HardUser { #brand = "User"; constructor(public id: string) {} }
class HardOrder { #brand = "Order"; constructor(public id: string) {} }
// const bad: HardUser = new HardOrder("o1") as unknown as HardUser; // error
```

```typescript
// bad — expecting instanceof to have prevented leak (structural, not nominal)
// if (order instanceof User) deleteUser(order as unknown as User); // instanceof false, but direct pass still leaked
```

**Common confusion** — "class name prevents mix" — only `private`/`#private` do.

**Performance note** — private brand is one extra field check at compile time — zero runtime if `private`, `WeakMap` slot if `#private`.

**Mentor note** — demo `User = Order` assignability then add brand — show error appears.

### 2) **private vs #private runtime leak** (private hid at compile time but was readable via obj["field"] at runtime — #private would have thrown)

**Definition** — incident: `class TokenStore { private token = "secret" }` logged via `JSON.stringify(store)` or `store["token"]` — `private` emitted as `.token` and leaked to logs; `#token` would have been absent and throws outside.

**What problem it solves** — hard privacy for secrets vs checker-only privacy for ergonomic helpers.

**Modern guidance** — as of TypeScript 5.9 era, use `#private` for token/key/secret/PII — not copyable by spread, not enumerable, not serialized; use `private` for internal helpers where cross-instance reads and test introspection are desired.

**Runnable example** — leak via private vs hard (good vs bad, `tsc --strict`):

```typescript
// bad — private leaks to serializer
class TokenStore {
  private token = "secret";
  constructor(public userId: string) {}
}
const store = new TokenStore("u1");
console.log((store as any).token); // "secret" — leaked to serializer
console.log(Object.keys(store as any)); // ["userId","token"] — token present
console.log(JSON.stringify(store as any)); // {"userId":"u1","token":"secret"} — leak

// good — #private hidden
class TokenStoreHard {
  #token = "secret";
  constructor(public userId: string) {}
  get masked(): string { return this.#token.slice(0,2)+"***"; }
}
const hard = new TokenStoreHard("u1");
// console.log((hard as any).token); // undefined
console.log(Object.keys(hard as any)); // ["userId"] — #token absent
console.log(JSON.stringify(hard as any)); // {"userId":"u1"} — not leaked
console.log({ ...(hard as any) }); // #token not copied

// good — protected vs #private for subclass invariants
class BaseCounter {
  protected count = 0; // subclass can set count = -999
  inc(): void { this.count++; }
}
class SafeCounter {
  #count = 0; // subclass cannot touch — invariant holds even against evil subclass
  inc(): void { this.#count++; }
  get value(): number { return this.#count; }
}
```

```typescript
// bad — expecting private to be absent after spread
// const copy = { ...store }; // token still there — spread copies private-emitted field
```

**Common confusion** — "`private` is hard privacy" — only `#private` is.

**Performance note** — `#private` costs WeakMap/slot indirection — small per-instance; measure hot loops with millions of secret fields.

**Mentor note** — show `Object.keys(privateStore)` vs `Object.keys(hashPrivateStore)` — visible leak vs hidden.

**Cross-links** → [1.3. Access modifiers](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>).

### 3) **readonly without freeze** (readonly silenced a write at compile time but a shared DEFAULTS instance was still mutated through an alias)

**Definition** — incident: `class Config { readonly host: string; } const DEFAULTS = new Config("localhost"); (DEFAULTS as any).host = "evil"` mutated shared singleton via alias — `readonly` had erased, no runtime `freeze`.

**What problem it solves** — `readonly` is checker-only — shared defaults need `Object.freeze` or `#private` + getter for runtime immutability.

**Modern guidance** — as of TypeScript 5.9 era, pair `readonly` on shared singletons with `Object.freeze` or expose via `#private` + getter; `readonly` alone suffices for per-request instances where alias mutation is not a bug.

**Runnable example** — readonly leak vs freeze (good vs bad, `tsc --strict`):

```typescript
// bad — readonly alone leaks via alias
class Config2 {
  constructor(public readonly host: string) {}
}
const DEFAULTS = new Config2("localhost");
// DEFAULTS.host = "evil"; // error — checker blocks typed write
(DEFAULTS as any).host = "evil"; // runtime write succeeds — DEFAULTS.host now "evil" for all users

// good — freeze shared singleton (one-time O(n))
class ConfigFrozen {
  constructor(public readonly host: string) {}
}
const DEFAULTS_FROZEN = Object.freeze(new ConfigFrozen("localhost"));
// (DEFAULTS_FROZEN as any).host = "evil"; // in strict mode TypeError: Cannot assign to read only property

// good — #private + getter when mutation must be impossible even via alias
class ConfigHard {
  #host: string;
  constructor(host: string) { this.#host = host; }
  get host(): string { return this.#host; }
}
const DEFAULTS_HARD = new ConfigHard("localhost");
// (DEFAULTS_HARD as any).host = "evil"; // writes a new property 'host', does not change #host — getter still "localhost"
console.log(DEFAULTS_HARD.host); // "localhost"
```

```typescript
// bad — expecting readonly to be deep
class Nested {
  constructor(public readonly nested: { x: number }) {}
}
const n = new Nested({ x: 1 });
// n.nested.x = 2; // ok — readonly is shallow — nested object still mutable
// fix — as const or ReadonlyDeep for deep
```

**Common confusion** — "`readonly` is `freeze`" — `freeze` is runtime non-extensible + throws; `readonly` is erased.

**Performance note** — `Object.freeze` is O(fields) once — freeze shared defaults at module init, not per-request.

**Mentor note** — demo `(as any).host =` leak with `readonly` then freeze — show checker vs runtime guard gap.

**Cross-links** → [1.3. Access modifiers](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>).

### 4) **Missing override hid a rename** (base method renamed; subclass silently became an overload instead of an override — no error until runtime dispatch missed)

**Definition** — incident: `Base.save()` renamed to `Base.persist()` — `class UserRepo extends Base { save() {} }` without `override` became a separate method, not an override — callers via `Base` reference invoked `Base.save()` (no longer exists) and missed `UserRepo.save()` — `persist` path never called subclass logic.

**What problem it solves** — `override` + `noImplicitOverride` turns rename into compile error at subclass site, not silent dispatch miss.

**Modern guidance** — as of TypeScript 5.9 era, enable `noImplicitOverride` and annotate every override — misspelling or rename becomes checker error.

**Runnable example** — missing override leak (good vs bad, `tsc --strict --noImplicitOverride`):

```typescript
// good — override catches rename
class RepoB {
  save(item: string): void { console.log(`base save ${item}`); }
}
class UserRepoB extends RepoB {
  override save(item: string): void { console.log(`user save ${item}`); super.save(item); }
}
// rename Base: save → persist
// class RepoRenamed { persist(item: string): void {} }
// class UserRepoRenamed extends RepoRenamed {
//   override save(item: string): void {} // error TS4113 — save not in base — rename caught here
//   override persist(item: string): void { console.log(item); } // fix — now correct override
// }

// bad — without override (noImplicitOverride off), rename silently orphans
class BadBase {
  save(item: string): void { console.log(item); }
}
class BadSub extends BadBase {
  override save(item: string): void { console.log(`sub ${item}`); } // with flag on, must have override — with flag off, missing override would silently orphan on rename
}
// With flag on, this without override would error TS4114 — must add override

// good — polymorphic this vs base return after rename still preserved
class FluentB {
  protected x = 0;
  setX(v: number): this { this.x = v; return this; }
}
class SubFluentB extends FluentB {
  setY(v: number): this { return this; }
}
// rename does not affect this-return — chain still typed via this
```

```typescript
// bad — arrow vs method confusion hides this loss after rename
class ClickerB {
  count = 0;
  incMethod(): void { this.count++; }
  incArrow = (): void => { this.count++; };
}
// const m = new ClickerB().incMethod; // detached m() loses this
// const a = new ClickerB().incArrow; a(); // arrow preserves
```

**Common confusion** — "`override` is a decorator" — keyword, checker-only, erases.

**Performance note** — `override` erases — zero runtime; `this` return is single reference.

**Mentor note** — rename `Base.save` live and show `override`-less subclass becomes orphan vs `override` errors — teach "every override must say override".
