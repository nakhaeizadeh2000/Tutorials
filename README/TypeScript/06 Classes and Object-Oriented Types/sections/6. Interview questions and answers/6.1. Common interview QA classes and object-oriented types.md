## 6.1. Common interview QA — classes and object-oriented types

A strong answer identifies the operation, states what the checker guarantees and predicts the runtime result. The questions below are short diagnostic exercises. Follow the linked owners for full implementation guidance rather than memorizing a rule that drops its conditions.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save each named program in a separate fresh directory without tsconfig.json. Build with `tsc --strict --noImplicitOverride --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then execute `node dist/FILE.js`. For a marked negative, activate only that line in a separate copy and replace `--outDir dist` with `--noEmit`. All positive programs exit 0; the intentional negatives exit 1.

### 1) **What does a class name mean in a type annotation and in an expression?**

**Answer:** User names an instance type in `user: User` and a constructor value in `new User(...)` or `const Ctor = User`. The type query `typeof User` describes that constructor value, including its static side. The JavaScript expression `typeof User` instead returns a runtime string. A class does not by itself supply a namespace for qualified type members; a merged namespace is a separate declaration. The [declaration-spaces owner](<../../../02 The Type System Core/sections/2. The type vs value separation/2.2. Declaration spaces type value and namespace.md>) explains the distinction.

Save `views.ts`:

```typescript
export {};
class User {
  id: string;
  constructor(id: string) { this.id = id; }
  greet(): string { return "hi " + this.id; }
  static kind = "user";
}
const Ctor: typeof User = User;
const args: ConstructorParameters<typeof User> = ["u1"];
const user: InstanceType<typeof User> = new Ctor(...args);
function create<T extends User>(C: new (id: string) => T, id: string): T {
  return new C(id);
}
console.log(user.greet(), Ctor.kind, typeof Ctor, typeof user);
console.log(create(User, "u2").greet());
// const wrongSide: typeof User = user; // TS2739: instance lacks constructor-side requirements.
// User.greet(); // TS2339: greet is on instances.
// const wrongArgs: ConstructorParameters<typeof User> = [42]; // TS2322.
```

Output is `hi u1 user function object`, then `hi u2`. ConstructorParameters checks an argument tuple; InstanceType computes the constructed instance type. Neither creates a runtime value. The factory receives actual construction evidence through a concrete signature instead of asserting that an instance type is constructible. See [duality](<../1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>) and [class queries](<../3. Advanced Class Patterns/3.3. Class type queries InstanceType and constructor signatures.md>).

**Follow-up:** Why would `C extends User` alone be insufficient for a parameter which the function intends to invoke with new? It describes an instance contract, whereas construction needs a constructor contract.

### 2) **Does implements inherit behavior, and what changes if it is removed?**

**Answer:** Implements checks the instance contract at the class declaration. It neither supplies members nor changes the emitted inheritance chain. Removing it from an otherwise unchanged, valid class preserves its members and accepted structural assignments here, while losing the explicit declaration-site completeness check. That observation is not a guarantee that every larger API refactor is harmless. Extends actually establishes inheritance and can supply methods or constructor behavior.

Save `contracts.ts`:

```typescript
export {};
interface Reader { read(): string }
class CheckedReader implements Reader { read(): string { return "checked"; } }
class PlainReader { read(): string { return "plain"; } }
class BaseReader { read(): string { return "base"; } }
class InheritedReader extends BaseReader {}
function read(reader: Reader): string { return reader.read(); }
console.log(read(new CheckedReader()), read(new PlainReader()), read(new InheritedReader()));
console.log(new PlainReader() instanceof BaseReader, new InheritedReader() instanceof BaseReader);
// class Missing implements Reader {} // TS2420: missing member at declaration.
// read({}); // TS2741: missing member at use site.
```

Output is `checked plain base`, then `false true`. Removing only CheckedReader's implements clause leaves that output and the accepted calls unchanged. It removes the declaration's stated check, not the read body. The [primary class guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#implements-clauses) describes that checking role.

**Follow-up:** Are all same-shaped class instances interchangeable? Public shape is not the whole rule when private or protected declaration origins matter. A complete contract can require an origin shared by inherited members; a public projection can deliberately require less. Use [inheritance compatibility](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) for the accepted sibling and rejected unrelated-origin cases.

### 3) **When is an abstract class useful instead of an interface?**

**Answer:** An interface can describe a capability implemented independently by classes or ordinary objects. An abstract class can supply runtime helpers around hooks required from concrete subclasses. Choose according to the behavior and extension relationship, rather than treating abstract as a runtime construction guard or as universally better reuse. Constructor access restrictions are a separate option on ordinary classes too.

Save `abstract.ts`:

```typescript
export {};
interface HasArea { area(): number }
abstract class Shape implements HasArea {
  abstract area(): number;
  describe(): string { return "area=" + this.area(); }
}
class Square extends Shape {
  side: number;
  constructor(side: number) { super(); this.side = side; }
  area(): number { return this.side ** 2; }
}
const square = new Square(2);
const adapter: HasArea = { area: () => 9 };
console.log(square.describe(), adapter.area(), square instanceof Shape);
// class MissingShape extends Shape {} // TS2515: missing required hook.
// new Shape(); // TS2511: checked abstract construction.
```

Output is `area=4 9 true`. The adapter satisfies the interface without inheriting describe. The class helper and extends relationship remain in JavaScript; interface/abstract annotations and the bodyless area hook erase. [Abstract classes](<../2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>) demonstrates concrete construction contracts, forced-construction failure and ordinary restricted constructors.

**Follow-up:** Is adding a default perimeter returning zero a safe way to evolve Shape? It might preserve compilation yet return a meaningless perimeter for existing subclasses. Evaluate consumer behavior as well as source compatibility; add a required hook when subclasses must supply their own meaningful operation.

### 4) **What does override catch, and does noImplicitOverride require every abstract implementation to say it?**

**Answer:** Override checks that a corresponding base member exists and the replacement is compatible. NoImplicitOverride requires markers for the concrete replacements below; an implementation of an abstract hook is accepted without one. Neither the marker nor the flag changes dispatch or proves the replacement's behavior. The [option reference](https://www.typescriptlang.org/tsconfig/noImplicitOverride.html) describes the rename motivation; the examples make the abstract/concrete distinction explicit.

Save `overrides.ts`:

```typescript
export {};
class Repo { save(item: string): string { return "base " + item; } }
class UserRepo extends Repo {
  override save(item: string): string { return "user -> " + super.save(item); }
}
abstract class Job { abstract run(): string; }
class ReadyJob extends Job { run(): string { return "ready"; } }
class Animal { get label(): string { return "animal"; } }
class Dog extends Animal { override get label(): string { return "dog"; } }
console.log(new UserRepo().save("u1"), new ReadyJob().run(), new Dog().label);
// class Typo extends Repo { override saev(item: string): string { return item; } } // TS4113.
// class Unmarked extends Repo { save(item: string): string { return item; } } // TS4114.
```

Output is `user -> base u1 ready dog`. A base rename can make an explicit old-name override fail. An unmarked stale method can remain a separate method after the rename, because the current base no longer contains that name; the compiler does not remember historical intent. The [class pitfalls](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by class type misunderstandings.md>) traces that actual dispatch path.

**Follow-up:** Does returning this prove an arbitrary clone is correct? It can preserve the actual fluent receiver's type, but copying needs an honest construction/state contract. Static factories and detached callbacks need separate receiver reasoning. See [override and polymorphic this](<../2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>).

### 5) **How do private and private names differ after emission?**

**Answer:** The TypeScript private modifier erases, while an initialized private field remains an ordinary runtime property. A JavaScript private name such as #count has runtime private-access semantics and is outside ordinary own-key enumeration. ES2022 emission retains native private syntax here; the tested ES2015 output uses WeakMap support. Neither representation establishes a universal speed or memory ranking.

Save `privacy.ts`:

```typescript
export {};
class SoftCounter {
  private count = 0;
  inc(): void { this.count++; }
  equals(other: SoftCounter): boolean { return this.count === other.count; }
}
class HardCounter {
  #count = 0;
  inc(): void { this.#count++; }
  equals(other: HardCounter): boolean { return this.#count === other.#count; }
}
const soft = new SoftCounter(); soft.inc();
const otherSoft = new SoftCounter(); otherSoft.inc();
const hard = new HardCounter(); hard.inc();
const otherHard = new HardCounter(); otherHard.inc();
console.log("soft:", Reflect.get(soft, "count"), Object.keys(soft).join(","));
console.log("hard:", Reflect.get(hard, "count"), Reflect.get(hard, "#count"), JSON.stringify(hard));
console.log("same-class reads:", soft.equals(otherSoft), hard.equals(otherHard));
// soft.count; // TS2341.
// hard.#count; // TS18013: lexical private access is not an ordinary string lookup.
```

Output is `soft: 1 count`, `hard: undefined undefined {}`, then `same-class reads: true true`. Both forms permit same-class cross-instance reads inside their declaring methods. HardCounter's count is not an ordinary string-keyed property. Inspect the ES2022 output, then compile privacy.ts again with `--target es2015 --outDir legacy` and run `node legacy/privacy.js`: the output is identical in this fixture while the implementation representation differs. The [primary privacy caveats](https://www.typescriptlang.org/docs/handbook/2/classes.html#caveats) and [access-modifier owner](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>) explain checked access, runtime private names and serialization boundaries.

**Follow-up:** Does hiding a private member from JSON prove no method can expose its value? No. Review the public methods and actual serialization contract. Choose an access boundary from its requirements, rather than a blanket rule that one keyword is always for caches and another always for secrets.

### 6) **Common confusion**

A constructor type is not an instance type, and the type query typeof is not the runtime typeof operation. An accepted structural assignment does not require instanceof to be true. Abstract and override provide checker obligations while class bodies still execute. A private modifier's erasure does not erase its field initializer, and native private names are not ordinary keys with a # character in the string.

### 7) **Performance note**

The interface, implements/abstract/override modifiers, type queries and generic signatures erase. Constructors, field initialization, inherited method calls and private-access implementations remain. Inspect the declared target's artifact before discussing cost. No bundle measurement, method timing, field-byte count or engine optimization result was obtained in these exercises. The [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) concerns checking cost, which must also be kept separate from runtime allocation and dispatch.

### 8) **Mentor note**

For an initial answer, require a correct prediction and the operation behind it. For deeper reasoning, change one condition: remove implements, pass an abstract base to a constructing factory, rename the base member, or change the private-field target. Ask what the checker accepts and what the emitted program does separately.

A strong candidate names the limit of the evidence: public shape does not prove domain meaning, default behavior does not prove behavioral compatibility, an override does not repair a business contract, and two observed emit targets do not establish every runtime's storage strategy. Use the follow-ups to reveal a misconception and route it to its owner, rather than penalizing a learner for not recalling an internal term.
