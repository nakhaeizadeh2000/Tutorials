## 6.1. Common interview QA — classes and object-oriented types

### 1) **What does one class declaration put in each declaration space?** (type vs value vs namespace — and how typeof Class reaches the constructor)

**Definition** — `class User` creates two bindings: in type space `User` is instance `{ id; greet }`, in value space `User` is the constructor object (`new`, `static`) — `typeof User` reaches constructor; namespace space empty for classes (only `enum`/`namespace` populate it).

**What problem it solves** — interview trap: "`class` is a value — can I use it as type?" — yes, duality lets `let u: User` (instance) and `let C: typeof User` (ctor) share name but differ.

**Modern guidance** — as of TypeScript 5.9 era, answer with two columns — instance vs static — and utilities `InstanceType<typeof C>` / `ConstructorParameters<typeof C>` bridging them.

**Runnable example** — spaces (good vs bad, `tsc --strict`):

```typescript
class User {
  constructor(public id: string) {}
  greet(): string { return this.id; }
  static kind = "user" as const;
}
let u: User = new User("u1"); // type space — instance
let C: typeof User = User; // value space — constructor
type Inst = InstanceType<typeof User>; // User
type Params = ConstructorParameters<typeof User>; // [id: string]
type Static = typeof User; // has kind + new
// const bad: typeof User = new User("u1"); // error — instance ≠ constructor
// User.greet(); // error — greet on instance, not static
```

```typescript
// bad — confusing value vs type in generic constraint
class UserB { constructor(public id: string) {} static kind = "user" as const; }
// function bad<C extends UserB>(Ctor: C) {} // UserB is instance type, not constructible — need typeof or new sig
function good<C extends typeof UserB>(Ctor: C): InstanceType<C> { return new Ctor("u") as InstanceType<C>; }
```

**Common confusion** — "`class` is nominal" — structural except private/#private.

**Performance note** — dual symbol is checker-only — emit single class.

**Mentor note** — ask "what does `User` mean in `let x: User` vs `x = User`?" — instance vs value — then ask how `InstanceType` bridges.

### 2) **extends vs implements — is removing implements a breaking change?** (no for assignability; yes for the check — the structural nuance)

**Definition** — `implements` only checks shape at class declaration; assignability is structural, so `LoosePoint {x,y}` is still assignable to `PointLike {x,y}` without `implements` — removal does not change runtime or type flow, but loses local missing-method error.

**What problem it solves** — interview trap: "does `class C implements I` affect `C = I` assignability?" — answer: no, shape does — `implements` is documentation + early error.

**Modern guidance** — as of TypeScript 5.9 era, keep `implements` for contracts you care to verify locally; `extends` when you need runtime inheritance.

**Runnable example** — breaking change? (good vs bad, `tsc --strict`):

```typescript
interface PointLike { x: number; y: number; }
class Point implements PointLike { constructor(public x: number, public y: number) {} }
class LoosePoint { constructor(public x: number, public y: number) {} } // no implements
let p: PointLike = new LoosePoint(1,2); // ok — shape

// removing implements still assignable, but missing method surfaces later
interface Logger { log(msg: string): void; }
class Forgot implements Logger { log(msg: string): void {} } // error if missing appears here
class NoCheck { /* forgot log */ }
// declare function useLogger(l: Logger): void;
// useLogger(new NoCheck()); // error appears at call site — less local — same type effect, worse DX
```

```typescript
// good — extends is breaking (prototype chain), implements is not
class Base { table = "base"; }
class Child extends Base {}
// instanceof changes with extends, not with implements
```

**Common confusion** — "`implements` inherits" — never runtime.

**Performance note** — `implements` erases — zero cost; `extends` adds prototype.

**Mentor note** — remove `implements` live and show `LoosePoint` still assignable — ask "what was lost?" — local check.

### 3) **When does abstract class beat interface?** (shared runtime + construction control vs shape-only contracts)

**Definition** — `interface` is shape-only (erases, no runtime, mergeable); `abstract class` ships shared implementation (`describe()`, constructor validation), abstract enforcement (`abstract speak()`), and `protected constructor` control.

**What problem it solves** — evolution: add default `perimeter()` to `abstract class Shape` without breaking subclasses; add it to `interface Shape` breaks every implementer.

**Modern guidance** — `interface` for data/adapter across modules; `abstract class` when subclasses share runtime helpers or need `super()` ordering and protected construction.

**Runnable example** — decision (good vs bad, `tsc --strict`):

```typescript
abstract class Shape {
  abstract area(): number;
  perimeter(): number { return 0; } // default — add without break
  describe(): string { return `area=${this.area()}`; }
}
class Circle extends Shape {
  constructor(public r: number) { super(); }
  area(): number { return Math.PI*this.r*this.r; }
}
// interface variant:
// interface ShapeI { area(): number; }
// interface ShapeI { area(): number; perimeter(): number; } // breaks Circle

abstract class Entity {
  protected constructor(public id: string) {} // only subclasses construct
}
class UserE2 extends Entity { constructor(id: string, public name: string){ super(id);} }
// new Entity("e1"); // error — abstract + protected
```

```typescript
// bad — using interface where shared logic would duplicate
// interface HasDescribe { describe(): string; } // every class must reimplement describe
```

**Common confusion** — "`abstract class` is Java nominal" — still structural in TS.

**Performance note** — abstract helper is one prototype method — not per-instance.

**Mentor note** — add a new method to both `interface` and `abstract class` and count breakage.

**Cross-links** → [2.2. Abstract classes](<../2.%20Inheritance%20and%20Polymorphism/2.2.%20Abstract%20classes%20and%20members%20when%20abstract%20beats%20interface.md>).

### 4) **Why does override exist and what does it catch?** (base rename/misspelling — the "forgot-override" bug)

**Definition** — `override` (keyword, TS 4.3+, `noImplicitOverride` flag) marks intent to override; checker verifies matching base member exists — rename/misspelling becomes error at subclass, not silent new method.

**What problem it solves** — before `override`, rename `Base.save→persist` orphaned `Sub.save` silently — `Sub` became a new method, dispatch via `Base` missed it.

**Modern guidance** — enable `noImplicitOverride` and annotate every override — erases, zero runtime.

**Runnable example** — catches (good vs bad, `tsc --strict --noImplicitOverride`):

```typescript
class Repo { save(item: string): void {} }
class UserRepo extends Repo {
  override save(item: string): void { console.log(item); super.save(item); }
  // override handel(): void {} // error TS4113 — not in base — catches typo
}
// rename base:
// class Repo2 { persist(item: string): void {} }
// class UserRepo2 extends Repo2 {
//   override save(item: string): void {} // error — save not in base — caught
//   override persist(item: string): void {} // fix
// }

// bad — without override (flag off) rename silently orphans
class BadRepo2 extends Repo { override save(item: string): void {} } // with flag on, must have override — flag off would silently orphan without it
```

```typescript
// good — override on getters
class Animal { get label(): string { return "animal"; } }
class Dog2 extends Animal { override get label(): string { return "dog"; } }
```

**Common confusion** — "`override` changes dispatch" — only validates.

**Performance note** — erases — no emit.

**Mentor note** — rename `Base.save` live and show `override` error vs silent orphan.

**Cross-links** → [2.3. Override and polymorphic this typing](<../2.%20Inheritance%20and%20Polymorphism/2.3.%20Override%20and%20polymorphic%20this%20typing.md>).

### 5) **private vs #private — which has runtime cost?** (checker-only erasure vs WeakMap field — performance vs hard privacy)

**Definition** — `private` is checker-only (emits as normal field, readable via `(obj as any).field`, spreads/copies, enumerable); `#field` is ES2022 hard private (WeakMap slot, not reachable by string key, not enumerable, not serialized, not copied by spread).

**What problem it solves** — secrets (token, key, PII) need hard privacy where `private` leak via `obj["private"]` is a vulnerability; `private` needed for cross-instance helpers (`equals(other: This)` needs `other.private`).

**Modern guidance** — as of TypeScript 5.9 era: `private` for internal helpers/test-visible; `#private` for secrets/PII/non-serializable internals; `#private static` via `static {}` for static secrets.

**Runnable example** — cost vs privacy (good vs bad, `tsc --strict`):

```typescript
class CounterA2 {
  private count = 0;
  inc(): void { this.count++; }
  equals(other: CounterA2): boolean { return this.count === other.count; } // cross-instance ok
}
const ca = new CounterA2(); ca.inc();
console.log((ca as any).count); // "leak" — still there — zero cost

class CounterB2 {
  #count = 0;
  inc(): void { this.#count++; }
  get value(): number { return this.#count; }
  equals(other: CounterB2): boolean { return this.#count === other.#count; }
}
const cb = new CounterB2(); cb.inc();
console.log((cb as any).count); // undefined — hard private — not as string
console.log(Object.keys(cb as any)); // [] — not enumerated
console.log(JSON.stringify(cb as any)); // "{}" — not serialized

// choose: token → #private (hard), cache → private (ergonomic)
class TokenHard {
  #token = "secret";
  get masked(): string { return this.#token.slice(0,2)+"***"; }
}
```

```typescript
// bad — expecting private to survive spread as absent
class Priv { private x = 1; constructor(public y: number) {} }
const priv = new Priv(2);
console.log({ ...(priv as any) }); // { x:1, y:2 } — private spread
// vs #private: spread would be { y:2 } only
```

**Common confusion** — "`private` is hard" — only `#private` is.

**Performance note** — `private` zero cost; `#private` adds slot indirection — small per-instance, measure hot loops with millions.

**Mentor note** — `Object.keys(private)` vs `Object.keys(hashPrivate)` demo — leak visible.
