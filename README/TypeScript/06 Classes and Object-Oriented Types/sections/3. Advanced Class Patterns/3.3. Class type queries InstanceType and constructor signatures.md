## 3.3. Class type queries — InstanceType and constructor signatures

A constructor value, the type of that constructor and the type of its instances are different views. Type queries let a factory or public contract derive information from a constructor without duplicating its parameter tuple. They do not construct an object or prove that an abstract input can safely be invoked.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noImplicitOverride --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. Activate one marked negative in a separate copy and replace --outDir dist with --noEmit to check its rejection. The removeComments option makes JavaScript inspection easier; it does not change the type contracts.

### 1) **From constructor value to instance and argument types**

UserValue is an actual value referring to the User constructor. In a type position, typeof UserValue captures that constructor's type. InstanceType extracts its instance result; ConstructorParameters extracts its argument tuple. The [utility reference](https://www.typescriptlang.org/docs/handbook/utility-types.html#constructorparameterstype) documents these operations. They apply to construct signatures rather than ordinary call signatures.

Save `queries.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
class User {
  static kind = "user";
  id: string;
  name: string;
  constructor(id: string, name: string) { this.id = id; this.name = name; }
  greet(): string { return this.name; }
}
const UserValue = User;
type UserConstructor = typeof UserValue;
type UserInstance = InstanceType<UserConstructor>;
type UserArguments = ConstructorParameters<UserConstructor>;
type InstanceMatches = Expect<Equal<UserInstance, User>>;
type ArgumentsMatch = Expect<Equal<UserArguments, [id: string, name: string]>>;
type ConstructorMatches = Expect<Equal<UserConstructor, typeof User>>;
type ConcreteConstructor = new (...args: any[]) => object;
type Factory<C extends ConcreteConstructor> =
  (...args: ConstructorParameters<C>) => InstanceType<C>;
const makeUser: Factory<typeof User> = (...args) => new User(...args);
const user: UserInstance = makeUser("u1", "Ada");
console.log(user.greet(), UserValue.kind, user instanceof UserValue);
// makeUser("u1"); // TS2554: name argument is required.
// makeUser("u1", 42); // TS2345: name must be string.
// user.kind; // TS2576: static member is on the constructor.
// UserValue.greet(); // TS2339: instance method is not on the constructor.
// type WrongInput = InstanceType<User>; // TS2344: instance type is not a constructor type.
```

The output is `Ada user true`. Three equality probes pin the extracted contracts. The concrete factory is checked against those derived arguments and result, while its body constructs a known User without a constructor assertion. The broad constructor bound in Factory is a type-level utility constraint; the particular typeof User supplies the actual call-site tuple.

Use the query when deriving a wrapper or registry contract from an existing constructor prevents drift. It does not mean that every public API must expose a class's entire instance surface. A deliberately narrower interface can be useful when a consumer needs only one capability. The [inheritance compatibility owner](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) distinguishes that structural contract from runtime inheritance.

### 2) **Concrete construction and abstract query acceptance**

A concrete subclass remains concrete even when its base is abstract. The factory below accepts Dog because its constructor can be invoked with a name; it rejects Animal because the base is abstract. Abstract signatures remain useful for non-instantiating operations and type queries. InstanceType<abstract new () => Animal> is valid and computes Animal without needing a runtime concrete constructor value.

Save `construction.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
abstract class Animal {
  name: string;
  constructor(name: string) { this.name = name; }
  abstract speak(): string;
}
class Dog extends Animal { speak(): string { return "woof"; } }
type AbstractResult = Expect<Equal<InstanceType<abstract new () => Animal>, Animal>>;
type AbstractArgs = Expect<Equal<ConstructorParameters<typeof Animal>, [name: string]>>;
function build<A extends unknown[], T>(Ctor: new (...args: A) => T, ...args: A): T {
  return new Ctor(...args);
}
const dog: Dog = build(Dog, "Rex");
console.log(dog.name, dog.speak());
// build(Animal, "base"); // TS2345: abstract input cannot meet concrete construction.
// build(Dog); // TS2554: name is required.
function inspect(Ctor: abstract new (name: string) => Animal): string {
  // new Ctor("base"); // TS2511: abstract-accepting signature cannot authorize construction.
  return Ctor.name;
}
console.log(inspect(Animal), inspect(Dog));

type AnimalConstructor = new (name: string) => Animal;
class Registry {
  private constructors = new Map<string, AnimalConstructor>();
  register(key: string, Ctor: AnimalConstructor): void { this.constructors.set(key, Ctor); }
  create(key: string, name: string): Animal | undefined {
    const Ctor = this.constructors.get(key);
    return Ctor ? new Ctor(name) : undefined;
  }
}
const registry = new Registry();
registry.register("dog", Dog);
console.log(registry.create("dog", "Milo")?.speak(), registry.create("missing", "x"));
// registry.register("base", Animal); // TS2345: abstract constructor.
class NeedsCollar extends Animal {
  collar: string;
  constructor(name: string, collar: string) { super(name); this.collar = collar; }
  speak(): string { return this.collar.toUpperCase(); }
}
// registry.register("collared", NeedsCollar); // TS2345: requires another argument.
```

The output is `Rex woof`, `Animal Dog` and `woof undefined`. The generic build body uses a concrete construct signature with a correlated argument tuple and result. The registry uses one explicit public constructor contract; it does not claim to create every possible Animal subclass. NeedsCollar requires a different contract or an adapter factory that deliberately supplies its collar.

The installed standard-library definitions of both utilities accept abstract constructor constraints. Query acceptance does not weaken the separate restriction on new. The [abstract-class owner](<../2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>) provides the full distinction between construction and inspection, including ordinary private/protected constructor access. These utilities describe public constructor signatures; they are not an access bypass.

The danger in an abstract-accepting instantiating registry can be observed directly. Save `forced-registry.ts`:

```typescript
export {};
abstract class Animal { abstract speak(): string; }
class Dog extends Animal { speak(): string { return "woof"; } }
const constructors = new Map<string, abstract new () => Animal>([["base", Animal], ["dog", Dog]]);
function forcedCreate(key: string): Animal | undefined {
  const Ctor = constructors.get(key);
  return Ctor ? new (Ctor as new () => Animal)() : undefined;
}
console.log(forcedCreate("dog")?.speak());
const base = forcedCreate("base");
if (base) {
  console.log(base instanceof Animal, typeof base.speak);
  try { base.speak(); }
  catch (error: unknown) {
    console.log(error instanceof TypeError ? "missing hook: TypeError" : "unexpected error");
  }
}
```

This prints `woof`, `true undefined` and `missing hook: TypeError`. Registering the abstract base is permitted by that broad storage type. The assertion discards the restriction and JavaScript constructs its emitted class, leaving the abstract hook absent. The earlier registry fixes the construction contract at registration and invocation rather than guessing that an abstract-typed entry will happen to be concrete.

### 3) **Inspect JavaScript and declarations for different purposes**

The queries and construct-signature annotations erase. Field initialization, constructor assignments and method bodies execute. A declaration-only build describes a public type surface; it does not show what JavaScript was emitted. To verify erasure, inspect actual JavaScript as well as executing its retained value operations.

Save `emit.ts`:

```typescript
export {};
export class UserQ {
  static kind = "user";
  id: string;
  constructor(id: string) { this.id = id; }
  greet(): string { return this.id; }
}
type Instance = InstanceType<typeof UserQ>;
type Arguments = ConstructorParameters<typeof UserQ>;
type AbstractInstance<C extends abstract new (...args: any[]) => object> = InstanceType<C>;
const user: Instance = new UserQ("u1");
console.log(UserQ.kind, user.greet());
// class Restricted { constructor(public id: string) {} } // TS1294 under erasableSyntaxOnly.
```

The normal build/run prints `user u1`. Inspect dist/emit.js: it contains UserQ, its field/constructor/method code and the call, without the three aliases. Add unused aliases in a separate copy and the emitted JavaScript remains unchanged under the stated removeComments setup; that observation says nothing about a universal checker-time cost.

For a separate declaration artifact, run the same compiler flags with `--declaration --emitDeclarationOnly --outDir types emit.ts` instead of --outDir dist. This produces types/emit.d.ts and no JavaScript in that fresh types directory. Keep these outputs separate so a stale JavaScript file cannot be mistaken for the result of declaration-only emission. The [source/emit owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) covers consumed file graphs, and the [toolchain gate owner](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) explains why parameter properties reject this example's erasable-syntax restriction.

### 4) **Common confusion**

InstanceType expects a constructor type, so class User's instance type is not the same input as typeof User. An abstract constructor can participate in a type query without being invoked. A concrete Dog does not become abstract merely because Animal is abstract. Deriving a constructor tuple cannot prove that a cast will construct a valid object. Finally, declaration output and JavaScript output answer different inspection questions.

### 5) **Performance note**

The aliases add no runtime construction or reflection after erasure. The factories and registry still allocate instances and perform ordinary lookups/calls. Type queries can require checking work; this lesson establishes no per-class linear formula, cache guarantee or negligible timing delta. The unused-alias comparison checks emitted bytes, not compilation speed. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) if a real program has a checker bottleneck.

### 6) **Mentor note**

Start from the UserValue binding and ask the learner to derive its constructor, instance and argument types. Then give them Dog and Animal: both support queries, but only Dog meets the concrete factory's construction requirement. Add NeedsCollar and require a review of the registry's actual arguments rather than an instanceof check. Finally, compare a declaration-only artifact with the JavaScript artifact and identify which observation establishes erasure. The forced-registry result explains why a cast is insufficient evidence for any of these construction decisions.
