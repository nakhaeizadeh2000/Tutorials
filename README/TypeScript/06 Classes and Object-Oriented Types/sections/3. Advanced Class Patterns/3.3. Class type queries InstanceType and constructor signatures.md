## 3.3. Class type queries — InstanceType and constructor signatures

### 1) **Querying the two sides** (InstanceType<typeof Class> recovers the instance; ConstructorParameters peels the new signature)

**Definition** — `InstanceType<typeof Class>` unwraps the constructor to its instance type (`InstanceType<typeof User>` → `User`); `ConstructorParameters<typeof Class>` extracts the `constructor` parameter tuple (`[id: string]`); `ReturnType` analog does not apply to `new` — use these instead. They are built-in utility types that index the construct signature.

**What problem it solves / history** — factories and DI containers start from the *value* (`User` class object) but need the *instance* type for return/members. Without queries, teams duplicated `type UserInstance = { id: string }` alongside `class User`, which drifted.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), always derive instance/params from `typeof Class` where possible — single source, erases. Keep `ConstructorParameters` for generic factories that forward args (`function create<C extends abstract new (...a: any[]) => any>(Ctor: C, ...args: ConstructorParameters<C>)`).

**Runnable example** — querying both sides (good vs bad, `tsc --strict`):

```typescript
// good — queries derive from typeof
class User {
  constructor(public id: string, public name: string) {}
  greet(): string { return this.name; }
}
type UInst = InstanceType<typeof User>; // User
type UParams = ConstructorParameters<typeof User>; // [id: string, name: string]
type UCtor = typeof User; // constructor side

function makeUser(...args: UParams): UInst {
  return new User(...args);
}
const u = makeUser("u1", "Ada"); // checks id+name

// generic factory via queries
function build<C extends abstract new (...args: any[]) => any>(
  Ctor: C,
  ...args: ConstructorParameters<C>
): InstanceType<C> {
  return new (Ctor as unknown as new (...args: any[]) => InstanceType<C>)(...args);
}
const u2 = build(User, "u2", "Bob"); // inferred User

// bad — duplicating tuple manually (drifts when constructor changes)
// function makeUserBad(id: string, name: string): User { return new User(id, name); } // manual — needs update on param add
// function buildBad(Ctor: typeof User, id: string, name: string): User { return new Ctor(id, name); } // not generic — only User
```

```typescript
// good — static side query plus instance query together
class Repo {
  static kind = "repo" as const;
  constructor(public table: string) {}
}
type RepoCtor = typeof Repo; // has kind + new
type RepoInst = InstanceType<RepoCtor>; // Repo instance (table)
```

**Common confusion** — "`InstanceType<typeof C>` is the same as `C`" — for `class C` yes, but for factory params `C extends abstract new` it unwraps whatever was passed — `InstanceType<C>` is the pattern. "`ConstructorParameters` includes return type" — no, only params; `InstanceType` is return.

**Performance note** — utilities are checker-only, erase, no emit or allocation — one instantiation per distinct `typeof Class`, cached.

**Mentor note** — teach as "value → type" bridge: start from `User` value, `typeof` reaches constructor, `InstanceType` reaches instance. Exercise: given `const UserValue = User`, ask how to get `[id, name]` tuple without looking at definition.

### 2) **Abstract construct queries** (abstract new vs new — why a factory for abstract bases must use abstract new construct sig)

**Definition** — `abstract new (...args) => T` matches constructors that may be abstract; `new (...args) => T` matches only concrete. Query `ConstructorParameters<C>` works with either, but `InstanceType<C>` requires `C extends abstract new` to accept abstract-typed Ctors.

**What problem it solves / history** — typing a factory as `new () => Animal` rejected `typeof Dog` where `Dog extends Animal` but `Animal` was `abstract` — forcing casts. `abstract new` unioned the two worlds without allowing `new Animal()` at value level.

**Modern guidance** — as of TypeScript 5.9 era, use `abstract new` in generic constraints for any factory that should accept subclasses/abstract bases; keep concrete `new` for factories that must guarantee instantiation without cast.

**Runnable example** — abstract new generic (good vs bad, `tsc --strict`):

```typescript
abstract class Animal { constructor(public name: string) {} abstract speak(): string; }
class Dog extends Animal { speak(): string { return "woof"; } }

// good — abstract new accepts Dog (concrete extends abstract base)
type AbstractCtor<T = any> = abstract new (...args: any[]) => T;
function adoptAnimal<C extends AbstractCtor<Animal>>(Ctor: C, ...args: ConstructorParameters<C>): InstanceType<C> {
  return new (Ctor as unknown as new (...args: any[]) => InstanceType<C>)(...args);
}
const d = adoptAnimal(Dog, "Rex"); // ok — Dog extends Animal

// bad — concrete new rejects abstract-typed helpers in generic position
type ConcreteCtor<T = any> = new (...args: any[]) => T;
function adoptConcrete<C extends ConcreteCtor<Animal>>(Ctor: C, ...args: ConstructorParameters<C>): InstanceType<C> {
  return new (Ctor as unknown as new (...args: any[]) => InstanceType<C>)(...args);
}
void adoptConcrete; void d;
// adoptConcrete(Dog, "Rex"); // still ok for Dog, but a helper typed as AbstractCtor<Animal> wouldn't match ConcreteCtor

// good — mixing InstanceType + abstract new for registration table
class Registry {
  static map = new Map<string, AbstractCtor<Animal>>();
  static register(key: string, ctor: AbstractCtor<Animal>): void { Registry.map.set(key, ctor); }
  static create(key: string, name: string): Animal | undefined {
    const Ctor = Registry.map.get(key);
    return Ctor ? new (Ctor as new (name: string) => Animal)(name) : undefined;
  }
}
Registry.register("dog", Dog);
```

```typescript
// bad — expecting abstract to be directly constructable via query
// type Bad = InstanceType<abstract new () => Animal>; // no — still need concrete Ctor value at runtime
// new Animal("x"); // error TS2511 — abstract not newable as value
```

**Common confusion** — "`abstract new` makes `new Animal()` legal" — no, value-level still fails — only the *type parameter* widens. "`ConstructorParameters` fails on abstract new" — it succeeds for both.

**Performance note** — abstract vs concrete is checker-only distinction, no emit difference — one `new` call regardless.

**Mentor note** — teach as column: `abstract new` = accepts more *types*, `new` = accepts fewer — value-level `new` check unchanged. Exercise: write `function instantiate<C extends AbstractCtor<Animal>>(Ctor: C): InstanceType<C>` and ask which `Ctor` values it accepts.

### 3) **Zero-emit erasure** (every query and utility on classes erases — like object type queries, no runtime cost)

**Definition** — `InstanceType`, `ConstructorParameters`, `typeof Class`, `abstract new` and all type positions on classes leave *no* emit — they are erased at compilation (see [Type erasure](<../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20TypeScript%20doesnt%20execute/2.1.%20Type%20erasure%20what%20survives%20compilation.md>)). Only the `class` value itself emits as JS.

**What problem it solves / history** — typing `InstanceType` without erasure would require runtime `Type` objects and reflection — TypeScript chose erasure so class-heavy code pays nothing for rich static queries.

**Modern guidance** — as of TypeScript 5.9 era, rely on erasure to liberally query classes — `InstanceType` chains, mapped over arrays of constructors, do not bloat bundle. Verify by inspecting `tsc --emitDeclarationOnly` or built `.js` — only `class` declarations remain.

**Runnable example** — erasure proof (good vs bad, `tsc --strict --erasableSyntaxOnly`):

```typescript
// good — all query forms erase
class UserQ {
  constructor(public id: string) {}
  greet(): string { return this.id; }
  static kind = "user" as const;
}
type Inst = InstanceType<typeof UserQ>; // erased
type Params = ConstructorParameters<typeof UserQ>; // erased
type CInst<T extends abstract new (...a: any[]) => any> = InstanceType<T>; // erased
const u = new UserQ("u1"); // only this line emits — class + new remain

// bad — expecting runtime Type object
// const t: Inst = UserQ; // error TS2739 — Inst is UserQ instance, not constructor

// good — emit inspection (pseudo): built.js contains `class UserQ { constructor(id){this.id=id} greet(){...} UserQ.kind="user" }` — no InstanceType trace
// npx tsc existingFile.ts --target es2022 --module commonjs && cat existingFile.js shows only value side
```

```typescript
// bad — trying to use InstanceType as value without typeof
// const x: InstanceType<UserQ> = new UserQ("u1"); // error — UserQ instance type, not constructor value; need typeof UserQ

// good — erasable check: `class` modifiers remain erasable (private/abstract/override all allowed under flag)
class ErasableUser {
  private x = 1;
  readonly y = 2;
  constructor(public id: string) {}
  greet(): string { return this.id; }
}
type EInst = InstanceType<typeof ErasableUser>; // still erasable
```

**Common confusion** — "utilities have runtime `Type` objects" — never — they are type operators, no value. "`typeof Class` keeps types at runtime" — `typeof` in type position erases; only `typeof` as JS `typeof` at value position remains.

**Performance note** — checker instantiation cache for `InstanceType<typeof Class>` is per distinct `Class` — linear in distinct classes, trivial; no heap/emit impact. Prefer `InstanceType<C>` over manual duplicate interfaces that double maintenance.

**Mentor note** — teach by running `cat dist/File.js` after a file heavy with `InstanceType` — students see zero artifacts, which cements erasure mental model. Exercise: add 10 `InstanceType` aliases and measure `tsc --extendedDiagnostics` before/after — delta near zero vs adding 10 `enum`s that would fail erasable check.
