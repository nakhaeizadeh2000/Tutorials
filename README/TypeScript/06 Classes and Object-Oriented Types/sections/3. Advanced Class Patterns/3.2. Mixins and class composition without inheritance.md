## 3.2. Mixins and class composition without inheritance

A class-expression mixin is a function that accepts a base constructor and returns a subclass adding a capability. The capability can be applied to different bases, while each application still uses ordinary single inheritance. The title's composition does not mean that the runtime prototype chain disappears.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noImplicitOverride --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. Activate one marked negative in a separate copy and replace --outDir dist with --noEmit to check its rejection. Ordinary constructor assignments avoid parameter-property restrictions under this gate.

### 1) **Concrete subclass factories preserve useful inference**

The generic B retains the particular base constructor's contract. Stamped adds stamp and stampText, while Named adds a method requiring name. Their inferred results preserve the original constructor arguments and the public static kind. There is no need to assert a replacement static side merely to access that inherited static member.

Save `stack.ts`:

```typescript
export {};
type Constructor<T extends object = object> = new (...args: any[]) => T;
function Stamped<B extends Constructor>(Base: B) {
  return class extends Base {
    stamp = "ready";
    stampText(): string { return this.stamp; }
  };
}
function Named<B extends Constructor<{ name: string }>>(Base: B) {
  return class extends Base {
    describe(): string { return "name=" + this.name; }
  };
}
class UserBase {
  static kind = "user";
  name: string;
  constructor(name: string) { this.name = name; }
}
const StampedUser = Stamped(UserBase);
const CompleteUser = Named(StampedUser);
const user = new CompleteUser("Ada");
console.log(CompleteUser.kind, user.name, user.stampText(), user.describe());
console.log("ancestry:", user instanceof UserBase, user instanceof StampedUser,
  user instanceof CompleteUser);
// new CompleteUser(); // TS2554: original name argument is still required.
// user.missing(); // TS2339: unrelated member is not supplied.
// Named(class MissingName {}); // TS2345: required name capability is absent.

const First = Stamped(UserBase);
const Second = Stamped(UserBase);
const first = new First("Grace");
console.log("separate application:", First === Second, first instanceof Second);
console.log("method identity:", first.stampText === new First("Lin").stampText,
  first.stampText === new Second("Lin").stampText);
```

The output is `user Ada ready name=Ada`, `ancestry: true true true`, `separate application: false false` and `method identity: true false`. The final object inherits through both actual mixin applications to UserBase. An object created through First does not inherit through the separately created Second. Store a composed constructor when its identity matters rather than calling the factory again and assuming it returns the same class.

The any[] in the constructor helper is the conventional broad construct-signature bound used by the [primary mixin guide](https://www.typescriptlang.org/docs/handbook/mixins.html#how-does-a-mixin-work). B still carries the specific argument/member information used at the call site. Avoid widening a composed constructor to the broad helper when consumers need that information. The [inheritance owner](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) explains shape checking and member origins separately.

### 2) **Abstract inputs leave abstract obligations**

A factory that accepts abstract constructor inputs must allow inherited hooks to remain unimplemented. When extending a generic value constrained by an abstract constructor, declare the returned subclass abstract too. A later concrete subclass supplies the hooks. The [4.2 feature explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-2.html#abstract-construct-signatures) describes this obligation.

Save `abstract-mixin.ts`:

```typescript
export {};
type AbstractConstructor = abstract new (...args: any[]) => object;
function Stamped<B extends AbstractConstructor>(Base: B) {
  abstract class StampedClass extends Base { stamp = "ready"; }
  return StampedClass;
}
abstract class Job { abstract run(): string; }
const StampedJob = Stamped(Job);
class ConcreteJob extends StampedJob { run(): string { return "done"; } }
const job = new ConcreteJob();
console.log(job.run(), job.stamp, job instanceof Job);
// new StampedJob(); // TS2511: returned class remains abstract.
// class MissingHook extends StampedJob {} // TS2515: missing run.
// function Bad<B extends AbstractConstructor>(Base: B) { return class extends Base {}; } // TS2797.
```

This prints `done ready true`. The final concrete class can be instantiated and carries the added field. Activating Bad instead shows why simply changing the first example's bound from new to abstract new is insufficient: its anonymous concrete subclass is not allowed to pretend that every possible base's abstract hooks are implemented.

The generated constructor and fields are still runtime values. Abstract annotations erase, as shown in the [abstract-class owner](<../2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>); they do not make an instantiating factory safe through a cast. For transformations that need only a constructor's types, use the [query owner](<./3.3. Class type queries InstanceType and constructor signatures.md>).

### 3) **Choose inheritance composition or an explicit collaborator**

A mixin fits when a reusable capability should become part of a class's instance contract and inheritance behavior. An explicit collaborator fits when behavior should be supplied or replaced through an ordinary value. Neither choice is determined by a universal maximum mixin count. Review the constructor contract, required base capabilities, method-name interactions and how callers will identify or substitute the result.

Save `collaborator.ts`:

```typescript
export {};
interface Formatter { format(name: string): string }
const friendly: Formatter = { format(name) { return "Hello " + name; } };
const compact: Formatter = { format(name) { return name.toUpperCase(); } };
class Report {
  name: string;
  formatter: Formatter;
  constructor(name: string, formatter: Formatter) { this.name = name; this.formatter = formatter; }
  describe(): string { return this.formatter.format(this.name); }
}
const report = new Report("Ada", friendly);
console.log(report.describe());
report.formatter = compact;
console.log(report.describe());
// new Report("Ada", { format: 42 }); // TS2322: collaborator must implement its contract.
```

The output is `Hello Ada` and `ADA`. This design replaces a collaborator without generating another subclass. Choose from the behavior the application needs: a stable class capability, a replaceable strategy, shared state or per-instance state. A type intersection by itself installs none of those runtime implementations; it only expresses requirements on the resulting value.

Justin Fagnani's original [subclass-factory explanation](https://justinfagnani.com/2015/12/21/real-mixins-with-javascript-classes/) is useful for distinguishing a mixin definition from an application and reasoning about the final chain. Its historical preferences and runtime optimization claims are not a performance result for this program.

Decorators are another mechanism with their own configured checking and emission path. They can replace runtime methods or return a subclass with extra runtime state; they are not metadata-only. Their effect on the statically exposed class type is a separate question. Use the [configured decorator comparison](<../../../14 Decorators and Metadata/sections/2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) and [class decorator owner](<../../../14 Decorators and Metadata/sections/1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>) for that implementation rather than using decorators as an interchangeable spelling of a mixin factory.

### 4) **Common confusion**

The inferred mixin result can retain inherited statics and constructor arguments. The final instance can match both its original base and the actual mixed constructor. A separate evaluation of the same factory produces another class identity. An abstract input does not remove required hooks from the final concrete subclass. Finally, a type intersection, a generated subclass and a supplied collaborator are distinct ways of describing or assembling behavior.

### 5) **Performance note**

The emitted stack.js contains one Stamped function with one stampText method definition, even though the program calls Stamped several times. Each call evaluates a class expression, producing a distinct class and method value; instances of one application share that prototype method. Runtime allocation is different from duplicating source text at every application site. No bundler/minifier size, dispatch latency, memory quantity or depth threshold was measured. Keep expensive composition out of an often-repeated path when it can be reused, and measure the actual workload before attributing a bottleneck to inheritance depth or a hover type.

### 6) **Mentor note**

Ask the learner to predict CompleteUser.kind, the constructor argument and all three ancestry checks before running stack.ts. Then compare First and Second and explain the observed method identities. A sound explanation follows the actual generated classes rather than an informal label such as stamped. For abstract composition, require the learner to identify which class still owes run and why adding a cast would not implement it. Finish by choosing between the Report collaborator and a mixin for a replaceable formatting policy, explaining the substitution the caller needs.
