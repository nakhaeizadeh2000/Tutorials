## 3.2. Mixins and class composition without inheritance

### 1) **Mixin as class expression** (function Timestamped<B extends Constructor>(Base: B) — generic constraint that returns an anonymous class extending Base)

**Definition** — a *mixin* is a function that takes a base `Constructor` (`abstract new (...args: any[]) => any`) and returns an anonymous `class extends Base` with extra members — composition over single `extends`. Typed as `function M<B extends Constructor>(Base: B): B & Constructor<Added>`.

**What problem it solves / history** — JS single `extends` cannot express cross-cutting concerns (timestamp, logging, validation) shared across otherwise unrelated hierarchies — duplication or diamond inheritance. Mixins (Handbook: Mixins, TS 2.2+ class expressions) give `Timestamped(Loggable(User))` without linear hierarchy.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), model mixins as branded functions with clear `Constructor` constraint; keep each mixin small (one concern) — large mixins bloat hover types and duplicate method emission per composition.

**Runnable example** — class expression mixin (good vs bad, `tsc --strict`):

```typescript
// good — Constructor helper + mixin
type Constructor<T = {}> = new (...args: any[]) => T;

function Timestamped<B extends Constructor>(Base: B) {
  return class extends Base {
    createdAt = new Date();
    ageMs(): number { return Date.now() - this.createdAt.getTime(); }
  };
}
function Loggable<B extends Constructor>(Base: B) {
  return class extends Base {
    log(msg: string): void { console.log(`[${new Date().toISOString()}] ${msg}`); }
  };
}
class UserBase {
  constructor(public name: string) {}
}
const TimestampedUser = Timestamped(UserBase);
const LoggableTimestampedUser = Loggable(Timestamped(UserBase)); // stacked
const u = new LoggableTimestampedUser("Ada");
console.log(u.createdAt);
u.log("hello");
console.log(u.ageMs());
console.log(u.name); // from UserBase — mixin preserved base members

// bad — mixin that forgets Constructor constraint loses base typing
// function BadMixin(Base: any) { return class extends Base {} } // any — no base inference
```

```typescript
// bad — expecting mixin to preserve static side automatically
type ConstructorStatic<T = {}> = new (...args: any[]) => T;
function TimestampedStatic<B extends ConstructorStatic>(Base: B) {
  return class extends Base { createdAt = new Date(); };
}
class WithStatic {
  static kind = "base" as const;
  constructor(public x: number) {}
}
const MixedStatic = TimestampedStatic(WithStatic);
// MixedStatic.kind; // error — mixin's return type does not carry statics unless explicitly typed — need & typeof
```

**Common confusion** — "mixins extend prototype chain linearly" — they do, but each `Timestamped(Base)` is a new anonymous class — `instanceof` checks need the mixed constructor, not original `UserBase`. "mixin's `this` is the mixed class" — `this` inside mixin methods is the final instance including later mixin members.

**Performance note** — each mixin creates a new anonymous class — one extra prototype per composition; stacking 5 mixins creates 5 prototypes — still O(mixins) at class evaluation, not per instance. Methods are shared per mixed class, not per instance — same cost as normal methods.

**Mentor note** — teach with two-function vs hierarchy comparison: show `class Dog extends Animal` vs `Loggable(Timestamped(Dog))` — ask which repeats `log` if `Cat` also needs it. Exercise: write `Activatable` mixin that adds `isActive: boolean` + `activate()`.

### 2) **Intersection on the instance** (stacking mixins Timestamped(Loggable(User)) is & on the instance side and extends on the constructor side)

**Definition** — `Timestamped(Loggable(User))` at type level is `InstanceType<typeof User> & { createdAt: Date } & { log(msg: string): void }` (instance `&`) while the constructor side is chained `extends` — `new` of mixed class produces the intersection instance.

**What problem it solves / history** — before intersection-aware mixins, stacked mixins' type was only the last mixin's members — earlier members lost. Intersection preserves *all* mixed members for hover/intellisense without manual `type Mixed = User & Timestamped & Loggable` alias.

**Modern guidance** — as of TypeScript 5.9 era, treat mixed instance type as intersection — expect hover to show long `&` chain; extract a named `type MixedUser = InstanceType<typeof LoggableTimestampedUser>` for readability where hover explodes.

**Runnable example** — intersection instance (good vs bad, `tsc --strict`):

```typescript
type Constructor2<T = {}> = new (...args: any[]) => T;
function withMeta<B extends Constructor2>(Base: B) {
  return class extends Base {
    meta = "meta" as const;
  };
}
function withId<B extends Constructor2>(Base: B) {
  return class extends Base {
    id = Math.random().toString(36);
  };
}
class Entity {
  constructor(public name: string) {}
}
const MetaIdEntity = withId(withMeta(Entity));
const e = new MetaIdEntity("test");
// e is Entity & { meta: ... } & { id: string } — all members present
console.log(e.name, e.meta, e.id);

// good — named alias for hover
type MetaIdEntityInst = InstanceType<typeof MetaIdEntity>; // Entity & {meta...} & {id...}
declare function handle(x: MetaIdEntityInst): void;

// bad — expecting single inheritance chain to hold both mixins without mixing
// class Single extends Entity {} // only Entity members — need mixin composition
```

```typescript
// good — checking intersection via satisfies
type Constructor2b<T = {}> = new (...args: any[]) => T;
function withMetaB<B extends Constructor2b>(Base: B) { return class extends Base { meta = "meta" as const; }; }
function withIdB<B extends Constructor2b>(Base: B) { return class extends Base { id = Math.random().toString(36); }; }
class EntityB { constructor(public name: string) {} }
const MetaIdEntityB = withIdB(withMetaB(EntityB));
const inst = new MetaIdEntityB("hi") satisfies EntityB; // also has meta/id — satisfies EntityB without widening
```

**Common confusion** — "mixin intersection is nominal" — still structural — `InstanceType<typeof Mixed>` is assignable to any shape matching all intersected members. "constructor side also `&`" — constructor side is `B & Constructor<Added>` — `new Mixed()` still checks original constructor args plus mixin args if mixin adds ctor params.

**Performance note** — intersection `&` at type level is checker-only — no extra runtime dispatch; instance is normal object with extra fields — one allocation per instance plus each mixin's fields — same as manual `extends`.

**Mentor note** — show hover for `MetaIdEntity` — explain the `&` chain is the type-level view of prototype chain. Exercise: stack three mixins and ask which `instanceof` checks hold (`e instanceof Entity`, `e instanceof MetaIdEntity`).

### 3) **When mixins beat extends** (cross-cutting concerns without diamond inheritance — trade-off is longer hover types and duplicate declaration emitted)

**Definition** — choose *mixin* when a concern cuts across unrelated subtrees (`Timestamped` for `User`, `Order`, `Event`); choose *extends* when subclasses form a single semantic hierarchy (`Animal → Dog → GuardDog`).

**What problem it solves / history** — diamond-like need for `A extends B, C` (not possible — JS single prototype) was solved by mixins — one linear chain that composes orthogonal traits without duplicating trait code in each leaf.

**Modern guidance** — as of TypeScript 5.9 era:
| Scenario | Use | Why |
|---|---|---|
| Single lineage (LSP holds) | `extends` | Simple hierarchy, `instanceof` chain, one prototype |
| Cross-cutting (time, log, retry, valid) | Mixins | Reusable trait, no duplicate code per leaf |
| Assembly-time concern (decorators) | Decorators (domain 14) | Metadata, not runtime members |

Mixin trade-offs: hover types longer (`&` chain), `instanceof` needs mixed ctor, emitted JS repeats trait methods per mixed class (one per composition site).

**Runnable example** — choosing (good vs bad, `tsc --strict`):

```typescript
// good — extends for single lineage (LSP)
abstract class AnimalX { constructor(public name: string) {} abstract speak(): string; }
class DogX extends AnimalX { speak(): string { return "woof"; } }
class GuardDog extends DogX { guard(): void { console.log("guarding"); } }

// good — mixin for cross-cutting
type Ctor3<T = {}> = new (...args: any[]) => T;
function Retryable<B extends Ctor3>(Base: B) {
  return class extends Base {
    async retry<T>(fn: () => Promise<T>, n = 3): Promise<T> {
      let last: unknown;
      for (let i = 0; i < n; i++) { try { return await fn(); } catch (e) { last = e; } }
      throw last;
    }
  };
}
class UserRepoX { constructor(public id: string) {} }
class OrderRepoX { constructor(public id: string) {} }
const RetryUserRepo = Retryable(UserRepoX);
const RetryOrderRepo = Retryable(OrderRepoX);
// both get retry without duplicating retry() per repo or forcing common base

// bad — forcing common base just for retry
abstract class RetryBase { // now every repo must extend RetryBase — couples lineage
  async retry<T>(fn: () => Promise<T>): Promise<T> { return fn(); }
}
// class UserRepoY extends RetryBase {} // works but now cannot also extend Entity without diamond
// class OrderRepoY extends RetryBase {} // lineage pollution

// bad — mixin for single-lineage where extends suffices (over-engineered)
function DogMixin<B extends Ctor3>(Base: B) { return class extends Base { speak(): string { return "woof"; } }; }
// const MixedDog = DogMixin(AnimalX as Ctor3<AnimalX>); // verbose vs `class Dog extends Animal`
```

```typescript
// good — limit mixins to 2–3 per composition; beyond, extract trait objects instead of stacking 6
```

**Common confusion** — "mixins are decorators" — decorators (domain 14) add metadata/transform at class definition; mixins add concrete members via class expression — different phases. "more mixins always better for DRY" — stacking 6 mixins produces unreadable hover, duplicate emit, and fragile `super` ordering — prefer trait objects or composition fields beyond 3.

**Performance note** — `extends` is one prototype per subclass; mixin also one per composition — equal per-instance cost (fields added). Deeply stacked mixins still O(depth) prototype walk for `instanceof`; prefer flat composition (2–3 mixins) over 6-deep chains for JIT-friendly monomorphic dispatch.

**Mentor note** — ask "does `Dog` *is-a* `Animal` or does `UserRepo` *has-retry*?" — *is-a* → `extends`, *has-* → mixin/trait. Review PRs for `class Foo extends Bar` where `Bar` is only a capability trait — suggest mixin.
