## 3.1. Static members — generics and static blocks

### 1) **Static side is separate** (statics live on `typeof Class` — `Generic<T>` type params are instance-only; static members cannot see `T`)

**Definition** — `class Box<T> { static kind = "box"; static make<U>(v: U): Box<U> { ... } }` — `T` is *per-instance* (different per `new Box<number>` vs `new Box<string>`), while `static kind` and `static make` live on `typeof Box` once, shared across all instances. A `static` member cannot reference `T` directly — it must declare its own `<U>`.

**What problem it solves / history** — JS static fields (`Box.kind`) are singleton per class, not per instance. Typing them as instance members would make `box.kind` check but `Box.kind` fail. Split sides keep instance generic `T` from leaking into the shared constructor.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), keep statics stateless or cache-only — stateful statics that see instance data suggest instance methods. When a static needs the instance type, give it its own generic `<U>` and return `Box<U>`.

**Runnable example** — static cannot see instance T (good vs bad, `tsc --strict`):

```typescript
// good — static side separate from instance T
class Box<T> {
  constructor(public value: T) {}
  static kind = "box" as const; // lives on typeof Box
  static of<U>(value: U): Box<U> { return new Box(value); } // own U, not T
  // static bad(): T {} // error TS2302: Static members cannot reference class type parameters
}

const n = Box.of(42); // inferred Box<number>
const s = Box.of("hi"); // inferred Box<string>
console.log(Box.kind); // "box"
// n.kind; // error — kind not on instance

// bad — trying to store instance-specific state in static
class Counter<T> {
  static total = 0; // shared across all Counter<number> and Counter<string>
  constructor(public v: T) { Counter.total++; }
}
new Counter<number>(1);
new Counter<string>("x");
console.log(Counter.total); // 2 — not per-T, shared — document this
```

```typescript
// good — static generic bridges instance generic
class Repo<T> {
  constructor(private items: T[]) {}
  static fromArray<U>(items: U[]): Repo<U> { return new Repo(items); }
}
const r = Repo.fromArray([1, 2, 3]); // Repo<number>
```

**Common confusion** — "`class Foo<T> { static x: T }` should check" — checker rejects — `T` is instance-only. "`typeof Foo` includes `T`" — no, `typeof Foo` is the static side, no instance type param.

**Performance note** — statics are one property on the constructor function — one allocation per class, not per instance; lookup is monomorphic (single class). Keep statics small — large static maps retained for process lifetime.

**Mentor note** — draw two boxes: Instance side (per `new`, has `T`) vs Static side (`typeof Box`, shared) — illustrate why `static of<U>` needs its own `<U>`.

### 2) **Generic classes** (class Box<T> — one T per instance construction; how inference flows through new Box(42) vs new Box<string>("hi"))

**Definition** — `class Box<T> {}` introduces a type param `T` that varies *per instance construction*: `new Box(42)` infers `Box<number>` from the constructor argument, `new Box<string>("hi")` fixes `T` explicitly. `T` scopes over instance members (`value: T`, `get(): T`) but not statics.

**What problem it solves / history** — before generics, typed containers (`Array`, `Map`, `Promise`) were `any` — generic classes (TS 0.9+) let `Box<number>` reject `Box<string>` at assignment without runtime checks.

**Modern guidance** — as of TypeScript 5.9 era, prefer `new Box(42)` inference for literals, explicit `<string>` only when inference widens undesirably (e.g., `new Box(null)` → `Box<null>` vs `Box<string | null>`). Keep constraints minimal — `class Repo<T extends { id: string }>` only when body *needs* `id`.

**Runnable example** — inference and constraints (good vs bad, `tsc --strict`):

```typescript
// good — inference from constructor arg
class Box2<T> {
  constructor(public value: T) {}
  map<U>(fn: (v: T) => U): Box2<U> { return new Box2(fn(this.value)); }
}
const a = new Box2(42); // Box2<number> inferred
const b = a.map(x => x.toString()); // Box2<string>
const c = new Box2<string>("hi"); // explicit when inference not enough

// good — constraint guarantees inside body
class Repo2<T extends { id: string }> {
  constructor(private items: T[]) {}
  find(id: string): T | undefined { return this.items.find(x => x.id === id); } // ok — T has id
}
// new Repo2([{ id: "1", name: "x" }]); // ok — satisfies constraint
// new Repo2([{ name: "x" }]); // error — missing id

// bad — over-constraining loses utility
class Over<T extends { id: string; name: string; email: string }> {
  constructor(public v: T) {}
}
// new Over({ id: "1", name: "x" }); // error — missing email — too strict for generic container
// fix — constraint only what you need: <T extends { id: string }>
```

```typescript
// bad — expecting inference to narrow union without help
class Box2c<T> { constructor(public value: T) {} }
// const ambiguous = new Box2c(null); // inferred Box2c<null> — not Box2c<string | null>
// fix — explicit type or union arg
const amb = new Box2c<string | null>(null); // ok
```

**Common confusion** — "generic class static can use `T`" — never; `T` is instance. "inference needs explicit `<T>` everywhere" — usually infers from args — explicit only when widening.

**Performance note** — generic classes cause one extra type instantiation per distinct `<T>` at construction — compile-time cost O(distinct `T` count); keep `Box<number>` vs `Box<string>` reuses instantiation cache. Runtime cost zero — `T` erases, emit is plain `class`.

### 3) **Static blocks** (static { } — ES2022 initialization that runs once at class evaluation; ordering relative to field initializers)

**Definition** — `static { ... }` (ES2022, TS 4.4+ emit) is a block that runs *once* when the class is evaluated, after static fields and before any `new`. It has `this` as the class constructor, can initialize `#private static` fields, and can do try/catch around static initialization.

**What problem it solves / history** — before static blocks, complex static initialization needed IIFEs (`static x = (()=>{...})()`) or external `init()` calls — ordering was implicit and exceptions unhandled. Static blocks made initialization explicit, lexically ordered, and exception-safe.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 LTS supports static blocks natively — emit as `static {}` when target ≥ ES2022, downlevels to helper otherwise), use `static {}` to wire registries, validate static invariants, or hydrate `#private static` — keep them short and synchronous (no top-level `await` inside without `async` helper).

**Runnable example** — static block ordering and error handling (good vs bad, `tsc --strict --target es2022`):

```typescript
// good — static block runs once, can access private static
class Config {
  static DEFAULT_PORT: number = 0;
  static #secret = "init";
  static get secret(): string { return Config.#secret; }
  static {
    // runs after DEFAULT_PORT declaration, before any new Config()
    try {
      Config.DEFAULT_PORT = 5432;
      Config.#secret = "loaded";
    } catch (e) {
      Config.DEFAULT_PORT = 3000;
    }
    console.log(`Config initialized: ${Config.DEFAULT_PORT}`);
  }
  constructor(public port: number = Config.DEFAULT_PORT) {}
}
console.log(Config.secret); // "loaded" — block already ran at class evaluation

// ordering — static fields before block, instance fields after
class Ordered {
  static a = 1;
  static { Ordered.a = 2; } // overwrites 1 → 2
  // static b = Ordered.a + 1; // would be 3 if declared here — ordering matters
}

// bad — expecting instance field in static block
class BadStatic {
  instanceField = 1;
  static {
    // this.instanceField; // error TS2339 — static block's this is the class, not instance
  }
}
```

```typescript
// good — registry via static block (self-registration)
class Base {
  static registry: Map<string, typeof Base> = new Map();
}
class User extends Base {
  static { Base.registry.set("user", User); }
}
class Order2 extends Base {
  static { Base.registry.set("order", Order2); }
}
console.log(Base.registry.has("user")); // true
```

**Common confusion** — "static block runs per instance" — never — once per class evaluation. "static block can use `super`" — `super` not available — use `Base.registry` explicitly.

**Performance note** — static block is one execution at class evaluation — negligible; ordering defines which `static` fields are visible (forward reference before `static { }` may be `undefined`).
