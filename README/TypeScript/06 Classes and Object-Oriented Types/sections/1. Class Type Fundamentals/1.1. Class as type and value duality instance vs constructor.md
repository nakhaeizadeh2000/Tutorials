## 1.1. Class as type and value duality — instance vs constructor

The name of a class can refer to its constructor value or describe its instances in a type position. Use the surrounding operation to tell which view you need: constructing an object, reading a static member and checking an instance member are different operations. A type annotation does not create another runtime class.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. For an intentional rejection, activate one marked line in a separate copy and replace --outDir dist with --noEmit. Ordinary fields and constructor assignments satisfy this syntax gate; runtime failures are caught deliberately.

### 1) **One class name, instance and constructor views**

In an annotation, User describes an instance with id, name and greet. In a type position, typeof User captures the constructor's type, including its new signature and public statics. In an expression, User is the actual constructor value. InstanceType can recover the instance result when you start from that constructor type.

Save `duality.ts`:

```typescript
export {};
class User {
  static kind = "user";
  id: string;
  name: string;
  constructor(id: string, name: string) { this.id = id; this.name = name; }
  greet(): string { return "hi " + this.name; }
}
const user: User = new User("u1", "Ada");
const UserConstructor: typeof User = User;
const second = new UserConstructor("u2", "Bob");
type UserInstance = InstanceType<typeof UserConstructor>;
const third: UserInstance = new UserConstructor("u3", "Cara");
console.log(user.greet(), second.greet(), third.greet());
console.log(UserConstructor.kind, UserConstructor === User);
console.log("runtime typeof:", typeof User, typeof user);
// user.kind; // TS2576: static member belongs to the constructor.
// User.greet(); // TS2339: instance method is not a static member.
// const wrongSide: typeof User = user; // TS2739: instance lacks constructor-side members.
// User("u4", "Dan"); // TS2348: class constructor requires new.
```

The output is `hi Ada hi Bob hi Cara`, `user true` and `runtime typeof: function object`. The type-position typeof query erases. The JavaScript typeof expressions on the last line execute and produce runtime strings. UserConstructor is another reference to the same constructor, not another generated class.

Use the class's instance type when consumers should depend on its full instance contract. A narrower interface can still be appropriate when a consumer needs only one capability or should accept another implementation. The [object-shape owner](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.1. Object types structural shape and excess property checks.md>) and [class compatibility owner](<../2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>) explain public shape and private/protected origin constraints. Full declaration-space rules belong in [type/value spaces](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>).

### 2) **Static methods have a constructor receiver**

A static method called as Base.who receives Base as its runtime receiver; the inherited call Derived.who receives Derived. Its body can infer the constructor-side this type without an explicit annotation. An explicit this parameter can add a checked call requirement, but it does not create the receiver or bind the method. The [static-member guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#static-members) establishes constructor-side members and inheritance.

Save `receivers.ts`:

```typescript
export {};
class Base {
  static label = "base";
  static who(): string {
    // return this.missing; // TS2339: body this is the constructor side.
    return this.label;
  }
  static explicit(this: typeof Base): string { return this.label; }
}
class Derived extends Base { static override label = "derived"; }
console.log(Base.who(), Derived.who());
const detached = Base.who;
try { detached(); }
catch (error: unknown) {
  console.log(error instanceof TypeError ? "detached: TypeError" : "unexpected error");
}
console.log("bound:", detached.bind(Base)(), Base.who.call(Derived));
const explicit = Base.explicit;
// explicit(); // TS2684: checked call lacks the required constructor receiver.
```

The output is `base derived`, `detached: TypeError` and `bound: base derived`. Extracting the implicit static method is accepted, but its receiverless invocation fails in the emitted strict program. Binding it or supplying a receiver with call fixes this particular invocation. Extracting the explicit method is also legal; calling it without a receiver is rejected.

The [callable receiver owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) owns the full call/apply/bind rules. The [static/generic owner](<../3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>) adds shared constructor state and independent static type parameters. Static does not mean receiverless, nor does it make an instance member available on the constructor.

### 3) **Construction evidence and runtime instance relations**

A concrete construct signature permits a particular new operation. A broader abstract construct signature accepts abstract constructor values for operations that do not instantiate them. It cannot justify calling new through an assertion. The [abstract construct-signature guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#abstract-construct-signatures) distinguishes the factory that can instantiate a concrete subclass from one that accepts an abstract base.

Save `constructors.ts`:

```typescript
export {};
abstract class Animal {
  name: string;
  constructor(name: string) { this.name = name; }
  abstract speak(): string;
}
class Dog extends Animal { speak(): string { return "woof"; } }
function create<T>(Ctor: new (name: string) => T, name: string): T {
  return new Ctor(name);
}
function createMany<T>(Ctor: new (name: string) => T, names: readonly string[]): T[] {
  return names.map(name => new Ctor(name));
}
console.log(create(Dog, "Rex").speak(), createMany(Dog, ["Rex", "Milo"]).length);
// create(Dog, 42); // TS2345: required argument type.
// create(Animal, "base"); // TS2345: abstract constructor cannot satisfy concrete new.
// new Animal("base"); // TS2511: abstract construction is rejected by the checker.
function inspect(Ctor: abstract new (name: string) => Animal): string {
  // new Ctor("base"); // TS2511: signature permits abstract input.
  return Ctor.name;
}
console.log(inspect(Animal), inspect(Dog));

// Deliberately unsafe: removes exactly the construction restriction the helper needs.
function forced(Ctor: abstract new (name: string) => Animal): Animal {
  return new (Ctor as new (name: string) => Animal)("forced");
}
const base = forced(Animal);
console.log("constructed:", base.name, base instanceof Animal, typeof base.speak);
try { base.speak(); }
catch (error: unknown) {
  console.log(error instanceof TypeError ? "missing hook: TypeError" : "unexpected error");
}
```

The output is `woof 2`, `Animal Dog`, `constructed: forced true undefined` and `missing hook: TypeError`. The safe factory accepts Dog and rejects Animal. The forced helper allows the abstract base and JavaScript constructs its emitted class. The failure occurs later when the absent hook is called. Abstract is a checker restriction, not an emitted constructor guard. The [abstract owner](<../2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>) and [query owner](<../3. Advanced Class Patterns/3.3. Class type queries InstanceType and constructor signatures.md>) develop the full construction, inspection and utility-query contracts.

Instance assignment and instanceof also answer different questions. Save `relations.ts`:

```typescript
export {};
class Base { value = 1; }
class Derived extends Base {}
class Similar { value = 1; }
const child = new Derived();
const structural: Base = new Similar();
console.log("chain:", child instanceof Base, Object.getPrototypeOf(child) === Base.prototype);
console.log("shape only:", structural.value, structural instanceof Base);
function read(value: unknown): string {
  if (value instanceof Base) return "base:" + value.value;
  return "other";
}
console.log(read(child), read(structural));
class Sentinel {
  static [Symbol.hasInstance](value: unknown): boolean { return value === "sentinel"; }
}
const marker: unknown = "sentinel";
console.log("custom relation:", marker instanceof Sentinel);
```

The output is `chain: true false`, `shape only: 1 false`, `base:1 other` and `custom relation: true`. Derived's immediate prototype differs from Base.prototype, but the default relation finds Base.prototype farther along its chain. Similar satisfies the public instance shape and does not share that chain. The read function uses a runtime branch to narrow its unknown input. Sentinel's custom hook demonstrates why the relation need not even mean the ordinary chain test.

The [OrdinaryHasInstance algorithm](https://tc39.es/ecma262/2026/multipage/abstract-operations.html#sec-ordinaryhasinstance) walks prototypes repeatedly. [InstanceofOperator](https://tc39.es/ecma262/2026/multipage/ecmascript-language-expressions.html#sec-instanceofoperator) consults Symbol.hasInstance. Use the relation appropriate to the data and constructor identity available to the application. It is not general validation of external object fields or constructor invariants. Full runtime behavior belongs in the [JavaScript reflection owner](<../../../../JavaScript/07 Prototypes and Classes/sections/5. Type checks and reflection/5.1. instanceof isPrototypeOf Symbol.hasInstance and cross-realm failures.md>).

### 4) **Common confusion**

User in an instance annotation differs from typeof User in a constructor annotation. A static method has a runtime call receiver even without an explicit this parameter. Concrete construction requirements differ from abstract query/inspection acceptance. Structural assignment is not an instanceof test, and the default instanceof relation is not immediate-prototype equality. An assertion changes none of these runtime operations.

### 5) **Performance note**

Type annotations and construct signatures erase; the class, constructors, fields, calls and runtime instance tests remain. A custom Symbol.hasInstance executes its own code. This lesson measures neither lookup speed, a typical hierarchy depth nor a per-class checker cost. Changing an annotation does not remove runtime initialization or attach a missing method. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a checking bottleneck and a suitable runtime profiler for actual instance operations.

### 6) **Mentor note**

Ask the learner to sort new UserConstructor, user.greet and UserConstructor.kind by the view each needs. Then compare Base.who, Derived.who and the detached call, explaining who supplies this. For construction, require the learner to name when the forced example fails: the base is constructed first, and the missing hook fails later. Finish with child and structural: a sound answer separates the accepted type assignment, chain relation and direct-prototype comparison, and qualifies custom hooks.
