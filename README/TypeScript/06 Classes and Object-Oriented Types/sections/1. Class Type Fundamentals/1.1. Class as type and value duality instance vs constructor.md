## 1.1. Class as type and value duality — instance vs constructor

### 1) **Dual declaration** (one `class User` creates two things — instance type vs constructor value across declaration spaces)

**Definition** — `class User {}` declares *two* bindings with the same name in two declaration spaces (see [Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>)): in type space `User` is the *instance* type (`{ id: string }` plus methods), in value space `User` is the *constructor* object (`typeof User` — callable via `new` and holding statics). This duality is unique to `class` (and `enum`) — `interface` and `type` exist only in type space.

**What problem it solves / history** — JavaScript already had `class` sugar over prototypes (ES2015) — `new User()` and `User.staticMethod()` coexist on one name. TypeScript needed to type *both* sides without inventing two names. Its solution: let the checker treat `class` as a *type* when used as annotation (`let u: User`) and as a *value* when used as expression (`new User()`). Before this, typing constructors required manual `interface UserConstructor { new(): User }` boilerplate.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to writing `let u: User` for instances and `typeof User` for constructors. Use `InstanceType<typeof User>` only when you start from the constructor value. Never duplicate the instance shape as a separate `interface UserShape` — the class already *is* its instance type and erases like every type (see [Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**Runnable example** — dual spaces (good vs bad, `tsc --strict`):

```typescript
// good — instance type vs constructor value
class User {
  constructor(public id: string, public name: string) {}
  greet(): string { return `hi ${this.name}`; }
  static kind = "user" as const;
}

// instance side — annotation uses instance type
const u: User = new User("u1", "Ada");
u.greet(); // ok — greet lives on instance side
// u.kind; // error TS2339 — kind is on static side, not instance

// constructor side — typeof reaches the value
const UserCtor: typeof User = User;
const u2 = new UserCtor("u2", "Bob"); // ok — typeof User is newable
console.log(UserCtor.kind); // "user" — static side

// bridging — InstanceType recovers instance from constructor value
type UInst = InstanceType<typeof User>; // same as User
const u3: UInst = new User("u3", "Cara");

// bad — confusing the two sides
// const bad: typeof User = new User("x", "y"); // error TS2739 — instance not assignable to constructor
// User.greet(); // error TS2339 — greet is not static
```

```typescript
// bad — duplicating shape as separate interface (unnecessary ceremony)
interface UserShape { id: string; name: string; greet(): string; }
class UserDup implements UserShape {
  constructor(public id: string, public name: string) {}
  greet(): string { return this.name; }
}
// works but UserDup already IS its shape — prefer class directly unless you need a shape without construction
```

**Common confusion** — "`User` and `typeof User` are the same" — no, `User` is the instance, `typeof User` is the constructor (+ statics); `User` appears in annotation position, `typeof User` in value/constructor position. "`class` is nominal so structural checks don't apply" — still structural except for `private`/`#private` brand (see [1.3. Access modifiers](<./1.3. Access modifiers and encapsulation public private protected readonly.md>)).

**Performance note** — duality has zero runtime cost — both sides erase to one `class` emit (type side gone, constructor value remains). Checker cost is one extra symbol per class (instance + constructor) — trivial; 10k classes still <1ms in `tsc --extendedDiagnostics` typeCheck.

**Mentor note** — teach by asking "what does `User` mean in `let x: User` vs `x = User`?" — answer is *instance vs value*. Review exercise: give `function make(Ctor: typeof User)` and ask what `InstanceType<typeof Ctor>` evaluates to.

### 2) **Instance side vs static side** (instance members on `User`, statics and `new` on `typeof User` — bridging with utilities)

**Definition** — the *instance side* is members accessed on an instance (`u.id`, `u.greet()`); the *static side* is members accessed on the constructor (`User.kind`, `User.create()`, `new User()`). TypeScript keeps their type graphs separate — instance generics do not leak to statics, statics do not pollute instances. Utilities `InstanceType`, `ConstructorParameters`, `ReturnType` bridge the gap.

**What problem it solves / history** — JavaScript let classes carry both `this.name` (per-instance) and `User.tableName` (per-class). Typing them as one flat object would conflate `u.tableName` with `User.name` and lose the `new` signature. Split sides keep `new` checkable (`new User()` vs `User()`) and let `static` factory methods be typed without instance noise.

**Modern guidance** — as of TypeScript 5.9 era, treat the split literally: instance methods read/write `this`; static methods receive no `this` (or explicit `this: typeof Class` if they use `this` polymorphically). Keep statics narrow — heavy static state suggests a separate namespace or module. All modifiers on either side erase — safe under `--erasableSyntaxOnly` (see [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

**Runnable example** — split sides and bridging (good vs bad, `tsc --strict`):

```typescript
class Repo<T> {
  constructor(private items: T[] = []) {}
  add(item: T): void { this.items.push(item); }
  static label = "repo" as const;
  static of<U>(items: U[]): Repo<U> { return new Repo(items); }
}

const r: Repo<number> = new Repo([1, 2]);
r.add(3);
// Repo.add(3); // error TS2339 — add is instance-only
console.log(Repo.label); // "repo" — static-only
// r.label; // error — label not on instance

// bridging utilities
type RInst = InstanceType<typeof Repo>; // Repo<unknown> — instance side recovered
type RParams = ConstructorParameters<typeof Repo>; // [items?: unknown[]]
type RStatic = typeof Repo; // static side — has label + of

// bad — expecting static member on instance
// const badLabel: string = r.label; // error TS2339
// bad — expecting instance generic on static side
// function staticUsesT(x: typeof Repo): Repo<string> { return x.of(["hi"]); } // ok via static method, but T not visible on typeof side
```

```typescript
// good — factory that returns correctly typed instance via static method
class Repo2<T> {
  constructor(private items: T[] = []) {}
  add(item: T): void { this.items.push(item); }
  static of<U>(items: U[]): Repo2<U> { return new Repo2(items); }
}
const nums = Repo2.of([10, 20, 30]); // inferred Repo2<number>
nums.add(40);

// bad — trying to call class without new (construct signature requires new)
class Point { constructor(public x: number, public y: number) {} }
// const p = Point(1, 2); // error TS7009: 'new' expression, whose target lacks a construct signature, cannot be invoked without 'new'
```

**Common confusion** — "`static` members are inherited by instances" — never; `instance.staticMember` is always an error. "`Repo<T>` static can see `T`" — no, `T` is instance-only; a static method must declare its own `<U>` (see [3.1. Static members, generics and static blocks](<../3. Advanced Class Patterns/3.1. Static members generics and static blocks.md>)).

**Performance note** — statics are plain properties on the constructor function — one allocation per class, not per instance; lookup is monomorphic after first access (V8 inline cache). Overusing statics as a global store increases retained memory per class — measure heap if you keep thousands of class-level caches.

**Mentor note** — draw two columns — Instance side | Static side — and sort every member. Review check: given `class C { x=1; static y=2; m(){ } static n(){ } }` ask which of `C.x`, `C.m`, `new C().y`, `new C().n` type-check — answer is none.

### 3) **Construct signatures** (writing `new (x: string) => T` and `abstract new` — why `instanceof` narrows but assignment checks shape)

**Definition** — a *construct signature* is the type of the constructor itself: `new (id: string) => User` or `abstract new (id: string) => Base`. It says "callable with `new` and returns `T`". A class's static side implicitly has one; standalone construct types let you accept any constructor without hard-coding the class name. `instanceof` is the runtime guard that narrows `unknown` into the instance side.

**What problem it solves / history** — before construct signatures, factories had to take `Function` or untyped `any` and cast after `new`. Construct signatures let `function create<T>(Ctor: new (...args: any[]) => T): T` stay typed end-to-end. `abstract new` (TS 4.2+) lets you accept *either* abstract or concrete constructors without losing `abstract` intent.

**Modern guidance** — as of TypeScript 5.9 era, prefer `new (x: X) => T` or `abstract new` in factory parameters over `typeof Class` when the factory should accept *any* matching constructor (subclasses, test doubles). Keep `instanceof` as the narrowing companion to `new` — `if (x instanceof User)` narrows `x` to `User` even across module boundaries (prototype identity, not structural). Both signatures erase.

**Runnable example** — factories with construct sigs and `instanceof` (good vs bad, `tsc --strict`):

```typescript
class User { constructor(public id: string) {} }
class Order { constructor(public id: string) {} }

type Ctor<T> = new (id: string) => T;
function build<T>(Ctor: Ctor<T>, id: string): T { return new Ctor(id); }

const u = build(User, "u1"); // inferred User
const o = build(Order, "o1"); // inferred Order

// abstract construct — accepts abstract or concrete bases
abstract class Animal { constructor(public name: string) {} abstract speak(): string; }
class Dog extends Animal { speak(): string { return "woof"; } }
type AbstractCtor = abstract new (name: string) => Animal;
function adopt(Ctor: AbstractCtor, name: string): Animal {
  // abstract new allows passing abstract bases as types; runtime still needs concrete Ctor
  return new (Ctor as new (name: string) => Animal)(name);
}
adopt(Dog, "Rex"); // ok
// adopt(Animal, "x"); // still constructable via type, but runtime new Animal fails — checker allows abstract new, runtime guard needed

// instanceof narrowing
function handle(x: unknown): string {
  if (x instanceof User) return x.id; // narrowed to User
  if (x instanceof Animal) return x.speak(); // narrowed to Animal
  return "unknown";
}

// bad — factory typed as () => T loses construction check
// function badBuild<T>(Ctor: () => T): T { return Ctor(); } // not newable — classes require new
// badBuild(User, "u1"); // error — User not callable without new
```

```typescript
// good — structural assignability still governs the instance side
class A { constructor(public x: number) {} }
class B { constructor(public x: number) {} }
declare let b: B;
const a: A = b; // ok — shapes match (instance side structural); construct side not compared
```

**Common confusion** — "`instanceof` is structural" — no, it checks prototype chain identity (`Object.getPrototypeOf(x) === User.prototype`); two structurally identical classes are *not* `instanceof` each other. "`new () => T` and `typeof Class` are identical" — `typeof Class` also carries statics; `new () => T` carries only the construct signature.

**Performance note** — `instanceof` is a prototype walk — O(depth of hierarchy), typically 1–3 steps; no allocation. Construct signatures add no emit or runtime cost. Prefer `instanceof` over property sniffing (`"id" in x`) when the class has `private`/`#private` identity that structurally identical shapes would fake.

**Mentor note** — teach construct signatures as "the type of `new`". Exercise: ask students to write `createMany(Ctor: new (n: string)=>T, ids: string[]) => T[]` without using `typeof`.
