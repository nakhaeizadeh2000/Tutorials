## 1.2. Constructors — parameter properties and instance creation

A constructor implementation initializes an instance. Its declaration accepts typed parameters but cannot have a return-type annotation. The class's construct signature describes the result of new. Parameter properties combine a constructor parameter with a field and initialization; a private parameter restricts that field, while a private constructor restricts creation through checked external new calls. Neither replaces runtime validation.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a fresh directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with parameters, manual, initialization or patterns. The first and last fixtures contain parameter properties and require transformation; do not add erasableSyntaxOnly to those files and expect a pass. Manual and initialization can also be checked with that gate. Activate one commented failure at a time and replace `--outDir dist` with `--noEmit` for its diagnostic.

### 1) **Constructor declarations and generated parameter-property fields**

User declares id, email and token through constructor parameters. Public/private/readonly on those parameters describe the resulting members. New User supplies the ordinary three arguments; it returns a User instance whose methods can use those initialized fields.

Save `parameters.ts`:

```typescript
export {};
class User {
  constructor(public id: string, public readonly email: string, private token: string) {}
  reveal(): string { return this.token.slice(0, 2) + "***"; }
}
const user = new User("u1", "ada@example.com", "secret");
console.log(user.id, user.email, user.reveal());
console.log(JSON.stringify(user)); // private field is still an ordinary enumerable runtime property
// user.token; // uncomment: TS2341
// user.email = "other@example.com"; // uncomment: TS2540
// class WrongLocation { method(private value: string) {} } // uncomment: TS2369
// class WrongAnnotation { constructor(): void {} } // uncomment: TS1093
```

The output is `u1 ada@example.com se***` followed by `{"id":"u1","email":"ada@example.com","token":"secret"}`. Reading token directly fails with TS2341, and assigning email fails with TS2540. The private visibility restriction is checker information; the serialized local fixture confirms that token remains an ordinary runtime property. [Parameter-property documentation](https://www.typescriptlang.org/docs/handbook/2/classes.html#parameter-properties) explains this field-producing form.

A method parameter cannot be a parameter property (TS2369). A constructor declaration cannot have a return annotation, even void (TS1093). Use a construct signature to describe new's result when accepting a constructor value; do not write a result annotation on the constructor body declaration. [Primary constructor guidance](https://www.typescriptlang.org/docs/handbook/2/classes.html#constructors) keeps those roles separate.

For an erasable-source pipeline, write the field declarations and assignments explicitly. Save the separate `manual.ts`:

```typescript
export {};
class User {
  id: string;
  readonly email: string;
  private token: string;
  constructor(id: string, email: string, token: string) {
    this.id = id; this.email = email; this.token = token;
  }
  reveal(): string { return this.token.slice(0, 2) + "***"; }
}
const user = new User("u1", "ada@example.com", "secret");
console.log(user.id, user.email, user.reveal());
console.log(JSON.stringify(user));
```

Its two output lines are identical for this case. Both programs retain actual field initialization and ordinary private-property serialization. Adding --erasableSyntaxOnly rejects parameters with TS1294 but accepts manual. The manual form is also useful when initialization performs multiple steps. Choose syntax from the consuming pipeline and clarity of the initialization, rather than assuming parameter-property shorthand is always the right default. [Bounded syntax/processing contracts](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) owns the complete gate; [access modifiers](<./1.3. Access modifiers and encapsulation public private protected readonly.md>) owns runtime-private alternatives.

### 2) **Initialization evidence, optional fields and trusted assertions**

StrictPropertyInitialization checks that a required field has initialization evidence. A field initializer or constructor assignment can supply it. An optional field permits absence and makes reads account for undefined. A definite assignment assertion tells the checker to trust an initialization promise; it does not assign a value or install a runtime check.

Save `initialization.ts`:

```typescript
export {};
class Config {
  host = "localhost";
  port: number;
  constructor(port: number) { this.port = port; }
}
const config = new Config(5432);
console.log(config.host, config.port);
class Lazy {
  value!: string; // external initialization promise; no runtime guard
  init(value: string): void { this.value = value; }
}
const lazy = new Lazy();
try { console.log(lazy.value.toUpperCase()); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
lazy.init("ready");
console.log(lazy.value.toUpperCase());
class Session { token?: string; }
const session = new Session();
console.log(session.token?.toUpperCase() ?? "missing");
session.token = "token";
console.log(session.token.toUpperCase());
// class Missing { value: string; } // uncomment: TS2564
// function unchecked(session: Session): string { return session.token.toUpperCase(); } // uncomment: TS18048
```

The output is `localhost 5432`, `TypeError`, `READY`, `missing` and `TOKEN`. Config establishes host and port before use. Lazy is accepted even before init, and its first string operation fails because no value was supplied. Init then makes that operation work. Session's optional value is handled explicitly before it exists and can be used after assignment. Required Missing.value fails with TS2564; the unchecked optional read fails with TS18048.

Prefer constructor injection when a dependency must exist from the start, or model an optional/lifecycle state when absence is real. Use a definite assertion only with an actual producer and first-use guarantee, then verify that path. A comment describing hydration does not execute it. An initializer must also run in the appropriate order; the [JavaScript field-order owner](<../../../../JavaScript/07 Prototypes and Classes/sections/3. Class syntax/3.4. Static members static blocks and class field order.md>) covers that runtime prerequisite. [Initialization configuration](<../../../13 Configuration and Compiler Options/sections/1. Strictness Family/1.3. strictFunctionTypes strictPropertyInitialization noImplicitOverride.md>) owns the switch alongside its other independent checks.

### 3) **Factories, builders and cached construction have different contracts**

A private constructor can make a checked caller use an approved class entry point. Its factory still needs to enforce the intended value contract. The following LoginAddress accepts exactly a string containing @; that bounded illustrative rule is not full email validation, deliverability or account identity. Public new remains available on RawUser despite its private email field.

Save `patterns.ts`:

```typescript
export {};
class LoginAddress {
  readonly value: string;
  private constructor(value: string) { this.value = value; }
  static create(raw: unknown): LoginAddress {
    if (typeof raw !== "string" || !raw.includes("@")) throw new Error("expected string containing @");
    return new LoginAddress(raw);
  }
}
const address = LoginAddress.create("ada@example.com");
console.log(address.value);
for (const input of [42, "bad"]) {
  try { LoginAddress.create(input); } catch (error: unknown) { console.log(error instanceof Error ? "rejected address" : "other"); }
}
class Query {
  readonly table: string;
  readonly limit: number | undefined;
  constructor(table: string, limit?: number) { this.table = table; this.limit = limit; }
  static builder(table: string): QueryBuilder { return new QueryBuilder(table); }
}
class QueryBuilder {
  private lim: number | undefined;
  private readonly table: string;
  constructor(table: string) {
    if (!table.trim()) throw new Error("table required");
    this.table = table;
  }
  limit(value: number): this {
    if (!Number.isInteger(value) || value <= 0) throw new RangeError("positive integer required");
    this.lim = value; return this;
  }
  build(): Query { return new Query(this.table, this.lim); }
}
const query = Query.builder("users").limit(10).build();
console.log(query.table, query.limit, Query.builder("users").build().limit);
try { Query.builder("users").limit(0); } catch (error: unknown) { console.log(error instanceof RangeError ? "rejected limit" : "other"); }
class Singleton {
  private static instance: Singleton | undefined;
  readonly id: string;
  private constructor(id: string) { this.id = id; }
  static get(id: string): Singleton { return Singleton.instance ??= new Singleton(id); }
}
const first = Singleton.get("a");
const second = Singleton.get("b");
console.log(first === second, second.id);
class RawUser { constructor(private email: string) {} }
console.log(new RawUser("bad") instanceof RawUser); // private parameter restricts field, not construction
// new LoginAddress("bad"); // uncomment: TS2673
// address.value = "other"; // uncomment: TS2540
// Query.builder("users").limit("10"); // uncomment: TS2345
```

The output is `ada@example.com`, two `rejected address` lines, `users 10 undefined`, `rejected limit`, `true a` and `true`. An external new LoginAddress fails with TS2673. Its factory rejects the two malformed inputs before returning. The final RawUser construction is accepted: placing private on the parameter did not make its constructor private. Private constructor checking also does not create a runtime security boundary after annotations erase.

QueryBuilder accumulates an optional positive integer limit and then creates a Query snapshot. The constructor's optional argument is separate from Query.limit's explicit number-or-undefined property; this matches build's actual explicit undefined call under exactOptionalPropertyTypes. A wrong string limit yields TS2345, while zero reaches the runtime range check. This small example illustrates staged construction; a single options object may be simpler when the configuration does not benefit from fluent accumulation. Builder use does not automatically validate a public Query constructor's inputs.

Singleton returns the first cached instance, so calling get with b after a still gives the instance whose id is a. That is a cache contract, not construction parameter reuse or an automatic multi-tenant lifetime policy. Prefer explicit creation/lifetime ownership when independent instances matter. The [DI lifecycle example](<../../../14 Decorators and Metadata/sections/3. Patterns in Practice/3.3. Dependency injection with decorators.md>) owns the tested container-specific identity distinction. [Boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) owns broader input validation, and [checked brands](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) owns domain evidence beyond this simple factory rule.

### 4) **Common confusion**

A construct signature describes new's result; a constructor implementation cannot annotate that result. Parameter properties transform into member initialization and do not pass every erasable-source gate. A private parameter restricts a field, while private constructor restricts checked external construction. Definite assignment is a trusted promise, optionality permits absence, and neither makes an unset value safe to use. A factory, builder or cache only enforces the conditions its body actually checks.

### 5) **Performance note**

Visibility, readonly and initialization annotations are checker information. Field creation/assignment, factory validation, builder objects and static cache retention are runtime work. Parameter-property transformation and manual assignments produce the observed matching values, but no allocation or execution benchmark was measured. Do not infer monomorphic lookup, an automatic speed ranking or universal cache savings from the class's syntax. Measure the actual creation/lifetime workload when performance matters.

### 6) **Mentor note**

Ask the learner to move private from RawUser's parameter onto its constructor and predict which check changes.
