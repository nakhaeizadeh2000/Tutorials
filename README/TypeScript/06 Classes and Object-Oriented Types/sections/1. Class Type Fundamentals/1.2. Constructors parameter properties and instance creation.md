## 1.2. Constructors — parameter properties and instance creation

### 1) **Constructor is not the type** (why `new User()` returns `User`, how parameter properties sugar declaration+assignment)

**Definition** — the `constructor` is the initializer called by `new`; its *return type* is implicitly the instance (`User`), not `void`. Parameter properties — `constructor(private id: string)` or `constructor(public readonly name: string)` — declare *and* initialize a field in one token (equivalent to `field; constructor(field) { this.field = field; }`). They exist only on `constructor` params, not on regular methods.

**What problem it solves / history** — pre-parameter-property classes repeated `this.x = x` for every field — noisy, error-prone. Parameter properties (since TS 1.x) collapsed that boilerplate and let the constructor signature itself document required fields. They also keep initialization provably local for `strictPropertyInitialization`.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), prefer parameter properties for data carriers (DTOs, entities) and explicit fields for logic-heavy classes where initialization is non-trivial. Avoid `private` params for fields needed by serializers — they still serialize at runtime but are hidden from type-check reads.

**Runnable example** — parameter properties vs manual (good vs bad, `tsc --strict --strictPropertyInitialization`):

```typescript
// good — parameter properties collapse field + assignment
class User {
  constructor(
    public id: string,
    public readonly email: string,
    private token: string,
  ) {}
  reveal(): string { return this.token.slice(0, 3) + "***"; }
}
const u = new User("u1", "ada@example.com", "secret");
console.log(u.id, u.email); // ok
// console.log(u.token); // error TS2341 — private

// good — manual equivalent (when you need custom logic)
class Account {
  public id: string;
  private token: string;
  constructor(id: string, token: string) {
    if (!id) throw new Error("id required");
    this.id = id;
    this.token = token;
  }
}

// bad — forgetting this assignment (strictPropertyInitialization catches it)
class Bad {
  // name: string; // error TS2564: Property 'name' has no initializer and is not definitely assigned
  name!: string; // bypass — but now unsafe until assigned before use
  constructor(name: string) { this.name = name; } // ! silenced the check — prefer param property
}
```

```typescript
// bad — parameter property on non-constructor (syntax error)
// class Foo {
//   method(private x: string) {} // error TS1270: parameter property only in constructor
// }
```

**Common confusion** — "`constructor` return type can be annotated" — no need and rarely correct; let it infer `this` instance. "`private` constructor param makes the value private at runtime" — only at type level unless combined with `#private` (see [1.3. Access modifiers](<./1.3. Access modifiers and encapsulation public private protected readonly.md>)).

**Performance note** — parameter properties emit as normal `this.x = x` assignments — same as manual; no extra allocation. V8 treats classes with only param-property assignments as monomorphic constructors after first instantiation — keep assignment order stable across construction paths.

**Mentor note** — teach with desugar: show param-property class and its desugared `this.id = id` form side-by-side. Review check: ask which members survive at runtime after erasure (all `public`/`private` annotations gone, assignments remain).

### 2) **`strictPropertyInitialization`** (the initialization contract `tsc` proves — `!`, `?`, and definite assignment)

**Definition** — `--strictPropertyInitialization` (part of `--strict`) requires every instance property to be initialized in the constructor or with a field initializer. `prop!` (definite assignment assertion) tells the checker "trust me, initialized before use"; `prop?` makes it optional/`undefined` until set.

**What problem it solves / history** — JavaScript lets `this.x` be set after construction (e.g., `init()` called later) — a classic source of `undefined` reads. Initialization checking (TS 2.7+) flags `this.x` reads that might occur before assignment without runtime cost.

**Modern guidance** — as of TypeScript 5.9 era, keep `strictPropertyInitialization` on; use `!` only when initialization is *provably* external (ORM hydration, `Object.assign` in constructor wrapper) and document the proof in a comment. Prefer `readonly` + initializer for invariant fields, `?` for truly optional, and factory `static create` that does validation before returning.

**Runnable example** — initialization contract (good vs bad, `tsc --strict`):

```typescript
// good — initialized inline or via constructor
class Config {
  host: string = "localhost";
  port: number;
  constructor(port: number) { this.port = port; }
}
new Config(5432); // both initialized

// bad — missing initialization flagged
class Lazy {
  // value: string; // error TS2564 — not initialized
  value!: string; // ok to checker, but runtime undefined until set — risky
  init(v: string): void { this.value = v; }
}
const lazy = new Lazy();
// console.log(lazy.value.toUpperCase()); // runtime TypeError — value still undefined

// good — optional vs definite
class Session {
  token?: string; // undefined until login
  id!: string; // set by hydrate — narrowed after
  hydrate(id: string): void { this.id = id; }
}
```

```typescript
// bad — silencing with ! then forgetting to hydrate
class UserRepo {
  db!: { query(s: string): void };
  find(id: string): void {
    // this.db.query("select…"); // runtime crash if hydrate not called — ! hid the error
  }
}
// fix — use constructor injection instead of !
class UserRepoFixed {
  constructor(private db: { query(s: string): void }) {}
  find(id: string): void { this.db.query(id); } // safe
}
```

**Common confusion** — "`!` proves initialization at runtime" — no, it only silences the checker; no emit, no runtime guard — the `undefined` still reads. "`?` is the same as `!`" — `?` makes the type `T | undefined` and forces callers to handle it; `!` keeps `T` and hides the gap.

**Performance note** — initialization checks are compile-time only; field initializers emit as `this.field = ...` in the constructor — one write per field; ordering matters for JIT (keep initializer order consistent with construction hot path).

**Mentor note** — demo the three states — `= value`, `!`, `?` — and ask "which one still throws at runtime?" Repeat that `!` is a promise *you* make — checker trusts it blindly. Review checklist: every `!` on a field must have an adjacent comment showing where it is assigned before first read.

### 3) **Construction patterns** (factory `static create`, builder, and `private constructor` singletons — typing `new` without exposing it)

**Definition** — construction patterns hide raw `new` behind a typed entry point: `static create()` validates before returning, `private constructor` prevents external `new`, builder accumulates fields before a final `build()`.

**What problem it solves / history** — raw `new User(raw)` lets invalid shapes reach the instance (e.g., `email` not validated, `id` not branded). Factories enforce invariants once and keep construction sites narrow — fewer `new` call sites = fewer `undefined` leaks. `private constructor` singletons (and `static` registries) predate TS but gain static safety with `private`/`#private`.

**Modern guidance** — as of TypeScript 5.9 era, default to `static create(payload: unknown): User` at module boundaries — parse/validate with `zod`/`valibot` inside `create`, return a branded instance; keep `constructor` `private` or `private` param properties to force callers through `create`. For expensive construction, add a `static` cache behind `#private static`.

**Runnable example** — factory and private constructor (good vs bad, `tsc --strict`):

```typescript
// good — private constructor + factory validates before construction
class Email {
  private constructor(public readonly value: string) {}
  static create(raw: string): Email {
    if (!raw.includes("@")) throw new Error("bad email");
    return new Email(raw);
  }
}
// new Email("x@y.com"); // error TS2673: Constructor of 'Email' is private — only within class
const e = Email.create("ada@example.com");

// good — builder for many optional fields
class Query {
  constructor(
    public readonly table: string,
    public readonly limit?: number,
  ) {}
  static builder(table: string) { return new QueryBuilder(table); }
}
class QueryBuilder {
  private lim?: number;
  constructor(private table: string) {}
  limit(n: number): this { this.lim = n; return this; }
  build(): Query { return new Query(this.table, this.lim); }
}
const q = Query.builder("users").limit(10).build();

// bad — public constructor lets invalid instance slip
class RawUser {
  constructor(public email: string) {} // no validation — caller can new RawUser("not-an-email")
}
new RawUser("bad"); // compiles — invalid at runtime
```

```typescript
// good — singleton with private constructor and static cache
class Singleton {
  private static inst: Singleton | undefined;
  private constructor(public id: string) {}
  static get(id: string): Singleton {
    if (!Singleton.inst) Singleton.inst = new Singleton(id);
    return Singleton.inst;
  }
}
const s1 = Singleton.get("a");
const s2 = Singleton.get("b");
console.log(s1 === s2); // true — same instance
```

**Common confusion** — "`private constructor` makes the class un-instantiable" — only *outside* the class; statics inside can still `new` it. "`static create` is inheritance-friendly" — factories that return `this` need polymorphic `this` (see [2.3. Override and polymorphic this](<../2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>)), otherwise subclasses get base type.

**Performance note** — factories add one call and one allocation — negligible; builder chain keeps `this` return monomorphic (same builder prototype) — JIT inlines well. `private constructor` has zero emit cost (erases), only a checker restriction.

**Mentor note** — teach construction as invariant enforcement — every `new` is a proof obligation. Exercise: give a `class User { constructor(public email: string) }` with no validation and ask students to add `private constructor` + `static create` that brands `UserId` (see [3.2. Branded and opaque patterns](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>)).
