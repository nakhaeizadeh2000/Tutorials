## 1.3. Access modifiers and encapsulation — public private protected readonly and #private

### 1) **Three modifiers plus #private** (public/protected/private are type-level; #field is runtime-hard WeakMap — emit, compatibility, erasableSyntaxOnly)

**Definition** — `public` (default, visible everywhere), `protected` (visible inside class + subclasses), `private` (visible only inside declaring class) are *checker-only* — they erase and emit as normal fields. `#field` (ECMAScript 2022) is a *runtime* private field backed by `WeakMap`/internal slot — inaccessible via `obj["#field"]` or `Object.keys` and throws outside.

**What problem it solves / history** — `private` gave early TypeScript (1.x) a way to mark intent without runtime cost, but `obj["privateField"]` still leaked. TC39 `#private` (supported TS 4.4+ emit) closed the hole — hard privacy that survives `as any` probing. Teams needed both: checker-only for ergonomic cross-instance reads, hard for security/encapsulation where leak is a bug.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to `private` for internal fields where the leak cost is low (tests can still introspect), `#private` where leak is a vulnerability or where the field must not appear in `JSON.stringify`/`Object.keys`. Both `private` and `#private` erase type-wise — `private` erases to normal field, `#private` emits as `#field` (still allowed under `--erasableSyntaxOnly` — `enum` is the only blocked syntax, not `#private`).

**Runnable example** — modifier vs #private (good vs bad, `tsc --strict`):

```typescript
// good — checker-only private (leakable at runtime)
class CounterA {
  private count = 0;
  inc(): void { this.count++; }
  get value(): number { return this.count; }
  // cross-instance read is allowed inside class — useful for equals/compare
  equals(other: CounterA): boolean { return this.count === other.count; } // ok — private visible inside class
}
const ca = new CounterA();
ca.inc();
// ca.count; // error TS2341 — checker blocks
console.log((ca as any).count); // 1 — runtime leak (field is still "count")

// good — hard private (not leakable, not enumerable)
class CounterB {
  #count = 0;
  inc(): void { this.#count++; }
  get value(): number { return this.#count; }
  equals(other: CounterB): boolean { return this.#count === other.#count; } // ok — #count visible inside class
}
const cb = new CounterB();
cb.inc();
// console.log((cb as any)["#count"]); // undefined — #count not as string key
// console.log((cb as any).count); // undefined — no leak
console.log(Object.keys(cb as any)); // [] — #count does not appear

// bad — assuming private is hard
class TokenStore {
  private token = "secret";
}
const ts = new TokenStore();
console.log((ts as any).token); // "secret" — leaked to serializer/logs
// fix — use #private for tokens
class TokenStoreHard {
  #token = "secret";
  reveal(): string { return this.#token.slice(0, 2) + "***"; }
}
```

```typescript
// protected vs private inheritance
class Base {
  protected id = "base";
  private secret = "s";
}
class Child extends Base {
  show(): string { return this.id; } // ok — protected visible in subclass
  // getSecret(): string { return this.secret; } // error TS2341 — private not visible in subclass
}
```

**Common confusion** — "`private` fields are hidden at runtime" — no, they emit as `this.privateField`; only `#field` is hidden. "`#private` can be accessed via `obj['#field']`" — never; it throws `SyntaxError` when parsed outside class. "`private` vs `#private` affect structural assignability" — both add nominal brand: two classes with same public shape but different `private`/`#private` are not assignable.

**Performance note** — `private` has zero runtime cost (erases). `#private` has small cost: engine stores value in an internal `PrivateName` slot/`WeakMap` — per-instance overhead ~ 16 bytes + indirection, lookup is slightly slower but monomorphic after warm-up. For hot paths with millions of instances, `private` is faster; for security, pay the `#private` cost.

**Mentor note** — teach with `Object.keys` + `(as any)` probe: students who see the leak stop trusting `private` for secrets. Review rule: any field containing a token, key, or PII must be `#private` — lint for `private token|secret|password`.

### 2) **readonly at the type level** (prevents type-checked writes but emits no freeze — contrast with Object.freeze and #private)

**Definition** — `readonly prop: T` marks a member as type-checked read-only — checker rejects `this.prop = ...` outside the constructor/field initializer. It emits as normal writable field (`this.prop = ...`) and does *not* freeze the object; alias mutations and runtime writes still land.

**What problem it solves / history** — JavaScript `const` does not apply to object members; `readonly` (TS 2.0+) brought assignment-checking to fields, constructor params, and mapped types (`readonly` operator) — needed for immutable DTOs and to make `as const` objects `readonly` deeply without `Object.freeze` cost.

**Modern guidance** — as of TypeScript 5.9 era, use `readonly` for invariant data (ids, config, injected deps) and pair with `Object.freeze` only when runtime mutation must also be prevented (shared `DEFAULTS`, cross-worker messages). In classes, `readonly` fields must be set in constructor or inline — `strictPropertyInitialization` enforces it. `readonly` erases — safe under `--erasableSyntaxOnly`.

**Runnable example** — readonly vs freeze (good vs bad, `tsc --strict`):

```typescript
// good — readonly checked, freeze frozen
class Config {
  constructor(public readonly host: string, public readonly port: number) {}
}
const cfg = new Config("localhost", 5432);
// cfg.host = "other"; // error TS2540 — readonly

// bad — readonly alone does not freeze at runtime
const DEFAULTS = { host: "localhost", port: 5432 } as const; // deeply readonly at type level
// (DEFAULTS as any).host = "evil"; // runtime mutation still writes if not frozen
Object.freeze(DEFAULTS);
// (DEFAULTS as any).host = "evil2"; // now silent fail in strict mode or throw in strict — runtime guard

// class-level readonly without freeze leak
class User {
  constructor(public readonly id: string) {}
}
const u = new User("u1");
(u as any).id = "hacked"; // runtime write succeeds — readonly did not prevent
// fix — #private + getter when mutation must be impossible
class UserHard {
  #id: string;
  constructor(id: string) { this.#id = id; }
  get id(): string { return this.#id; }
}
const uh = new UserHard("u1");
// (uh as any).id = "hacked"; // writes a new property, does not change #id — uh.id still "u1"
```

```typescript
// good — readonly via parameter property + mapped
type Mutable = { x: number; y: number };
type Frozen = Readonly<Mutable>; // mapped type — same fields as readonly
const p: Frozen = { x: 1, y: 2 };
// p.x = 3; // error TS2540
```

**Common confusion** — "`readonly` makes the object immutable at runtime" — no, only the checker rejects *typed* writes; `(as any).prop = ...` or aliased `obj` writes still mutate. "`readonly` implies deep immutability" — only shallow; nested `readonly` requires `as const` or `ReadonlyDeep` utility.

**Performance note** — `readonly` has zero emit cost; `Object.freeze` is a one-time O(n) over own properties and marks the object non-extensible — subsequent writes become slow-path throws/type-errors in JIT. Freeze shared defaults once at module init, not per-request.

**Mentor note** — demo `readonly` leak via `(as any).prop =` to break the "immutable" mental model. Review checklist: every `public readonly` on a shared singleton must be accompanied by `Object.freeze` or `#private` if runtime mutation is a bug (see [5.1. Real production bugs](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by class type misunderstandings.md>)).

### 3) **Encapsulation design** (when private is enough, when #private pays for hard privacy, and when protected leaks to subclasses)

**Definition** — encapsulation chooses the weakest visibility that prevents misuse: `public` when callers should read/write, `protected` when only subclasses should extend, `private`/`#private` when only the class itself should touch the field. Choice trades ergonomics (cross-instance helpers, tests) against leak risk (logs, serializers, subclass override).

**What problem it solves / history** — JavaScript classes started with only `public` fields; conventions (`_private`) were not enforced. TypeScript added checker encapsulation early, but frameworks (React, ORMs) introspected private fields via strings, causing silent coupling. `#private` gave libraries a way to hide internals from both consumers and serializers (e.g., `JSON.stringify` skips `#private`).

**Modern guidance** — as of TypeScript 5.9 era:
| Need | Use | Why |
|---|---|---|
| Internal helpers, test-visible state | `private` | Ergonomic, zero cost, allow `equals(other: This)` cross-instance |
| Secrets, tokens, invariants that must not leak/serialize | `#private` | Runtime hidden, not copied by spread/`Object.assign`, not serialized |
| Extension hook for subclasses | `protected` | Subclass can override but outsiders cannot; pair with `override` (see [2.3. Override](<../2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>)) |
| Public API field | `public` / `public readonly` | Document mutability intent; prefer `readonly` for invariants |

**Runnable example** — choosing visibility (good vs bad, `tsc --strict`):

```typescript
// good — protected for extension point, private for internals
class Repo {
  protected table = "users";
  private cache = new Map<string, unknown>();
  #secret = "internal";
  find(id: string): unknown { return this.cache.get(id); }
  // subclass may override table but not reach #secret
}
class UserRepo extends Repo {
  protected table = "user_rows"; // ok — protected allows subclass override
  debug(): string { return this.table; } // ok
  // leak(): string { return (this as any).cache; } // still reachable via private leak — prefer #private for cache if leak is bug
}

// bad — public mutable leaks to every caller
class BadRepo {
  constructor(public cache: Map<string, unknown>) {} // caller can .clear() externally
}
const br = new BadRepo(new Map());
br.cache.clear(); // mutated outside — invariant broken

// good — #private for non-serializable internals (not copied by spread)
class Session {
  #token: string;
  constructor(public userId: string, token: string) { this.#token = token; }
  get masked(): string { return this.#token.slice(0, 2) + "***"; }
}
const sess = new Session("u1", "secret");
console.log(JSON.stringify(sess)); // {"userId":"u1"} — #token absent, private would have leaked as "token":"secret" if enumerable
console.log({ ...sess as any }); // #token still absent
```

```typescript
// bad — protected leak lets subclass bypass invariant
class BaseCounter {
  protected count = 0; // subclass can set count = -999
  inc(): void { this.count++; }
}
class Evil extends BaseCounter {
  hack(): void { this.count = -999; } // allowed — protected
}
// fix — #private when invariant must hold even against subclasses
class SafeCounter {
  #count = 0;
  inc(): void { this.#count++; }
  get value(): number { return this.#count; }
}
```

**Common confusion** — "`protected` is safe encapsulation" — only against outsiders; subclasses can still violate invariants — use `#private` when subclasses must not touch the field. "`#private` prevents subclass `override`" — correct, `#private` is not visible to subclass at all, so it cannot be overridden — intentional for invariant.

**Performance note** — `private`/`protected` have no emit cost; `#private` adds `WeakMap`/slot lookup — small but measurable for fields on hot inner loops (tight loops over millions of instances). Keep hot numeric fields `private` for speed, cold secrets `#private`.

**Mentor note** — teach with `JSON.stringify(new ClassWithPrivate)` vs `new ClassWithHashPrivate` — visible leak vs hidden. Exercise: given a `class User { private token }` that gets logged via `logger.info(JSON.stringify(user))`, ask what leaks and which modifier fixes it.
