## 1.3. Access modifiers and encapsulation — public private protected readonly and #private

Class modifiers describe who may use a member through checked code. Runtime private names and property descriptors provide different behavior after emission. Readonly, a private backing field, a getter-only public view and a frozen object are separate mechanisms. Choose the one that matches the actual access or mutation boundary, then verify what emitted JavaScript does.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a fresh directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with privacy, origins, readonly or extension. For a commented checking failure, activate that line alone and replace `--outDir dist` with `--noEmit`. Intentional runtime failures are caught. A separate ES2015 emission contrast is described below; no runtime cost ranking is inferred from the target.

### 1) **Checker visibility, private names and compatibility origins**

A public member is available through the checked public contract. A private member is restricted through ordinary member access in checked code, but remains an ordinary runtime property. A protected member supplies a checked subclass access boundary, discussed in part3. A #private name is a separate runtime private member; the string "#count" is an ordinary property key, not that private name.

Save `privacy.ts`:

```typescript
export {};
class SoftCounter {
  private count = 0;
  inc(): void { this.count++; }
  get value(): number { return this.count; }
  same(other: SoftCounter): boolean { return this.count === other.count; }
}
const soft = new SoftCounter(); soft.inc();
console.log("soft:", soft.value, soft["count"], Object.keys(soft).join(","), JSON.stringify(soft));
class HardCounter {
  #count = 0;
  inc(): void { this.#count++; }
  get value(): number { return this.#count; }
  same(other: HardCounter): boolean { return this.#count === other.#count; }
}
const hard = new HardCounter(); hard.inc();
console.log("hard:", hard.value, Reflect.get(hard, "#count"), Object.keys(hard).length, JSON.stringify(hard));
Reflect.set(hard, "#count", 99); // creates an ordinary string-keyed property
console.log("string key:", Reflect.get(hard, "#count"), "private:", hard.value);
try { eval("hard.#count"); }
catch (error: unknown) { console.log(error instanceof SyntaxError ? "SyntaxError" : "other"); }
const other = new HardCounter(); other.inc();
console.log("same:", hard.same(other));
try { hard.same({ value: 1 } as HardCounter); } // assertion cannot install private field state
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
// soft.count; // uncomment: TS2341
// hard.#count; // uncomment: TS18013
```

The six output lines are `soft: 1 1 count {"count":1}`, `hard: 1 undefined 0 {}`, `string key: 99 private: 1`, `SyntaxError`, `same: true` and `TypeError`. Soft's dot access to count fails with TS2341, while its bracket access is accepted and the ordinary property appears in enumeration/JSON. Hard's private member does not appear as the ordinary #count key. Adding that string property does not change its private state. Eval safely catches parsing a private-name access outside the class's lexical declaration; a direct checked access gives TS18013. The [primary privacy caveats](https://www.typescriptlang.org/docs/handbook/2/classes.html#caveats) distinguish these operations.

Both classes permit same-class cross-instance access in their own methods. Hard.same cannot read private state from the asserted plain object; the assertion does not create that state and the runtime access throws TypeError. This does not make every assertion or external object trustworthy.

ES2022 output retains native #count syntax. Compile privacy.ts again with --target es2015 and --outDir legacy, then run `node legacy/privacy.js`: this fixture produces the same six lines, but its emitted private implementation uses WeakMap support/helpers. Those are tested target-specific representations, not a universal description of every engine's private-field storage. Both syntax variants are allowed by the erasable gate here; parameter properties are a different transformed form covered in [constructors](<./1.2. Constructors parameter properties and instance creation.md>).

Private members also affect class compatibility. Save `origins.ts`:

```typescript
export {};
class First {
  private token = 1;
  read(): number { return this.token; }
}
class Second {
  private token = 1;
  read(): number { return this.token; }
}
const first = new First();
const another: First = new First();
const publicView: { read(): number } = first;
console.log(first.read(), another.read(), publicView.read());
// const wrongOrigin: First = new Second(); // uncomment: TS2322
// const missingPrivate: First = { read: () => 1 }; // uncomment: TS2741
```

The output is `1 1 1`. Another First shares the declaration origin. A public read-only capability can expose read without exposing the class's private member. Second's separately declared private token prevents assignment to First (TS2322), while a plain object lacking that required member fails TS2741. Merely giving public shapes different class names would not create this separation. [Structural compatibility](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>) and [checked class/brand patterns](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) own the broader origin/evidence rules.

### 2) **Readonly views, getters and shallow runtime freeze**

Readonly rejects writes through that checked view. It does not make an ordinary data property's runtime descriptor unwritable. A getter-only inherited accessor instead lacks a setter. Object.freeze affects the immediate object's own properties; it does not recursively freeze the nested objects those properties reference.

Save `readonly.ts`:

```typescript
export {};
class Config {
  readonly host = "localhost";
  readonly nested = { port: 5432 };
}
const config = new Config();
const writableView: { host: string } = config;
writableView.host = "changed"; // accepted structural view; readonly is not a runtime descriptor
console.log("alias:", config.host);
Object.freeze(config);
config.nested.port = 443; // shallow freeze leaves nested object mutable
try { writableView.host = "blocked"; }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
console.log("frozen:", config.host, config.nested.port, Reflect.set(config, "host", "other"));
class UserHard {
  #id: string;
  constructor(id: string) { this.#id = id; }
  get id(): string { return this.#id; }
}
const user = new UserHard("u1");
try { (user as unknown as { id: string }).id = "hacked"; }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
console.log("getter:", user.id, Object.hasOwn(user, "id"), Reflect.set(user, "id", "other"));
console.log("extensible:", Reflect.set(user, "note", "allowed"), Reflect.get(user, "note"));
// config.host = "other"; // uncomment: TS2540
// user.id = "other"; // uncomment: TS2540
```

The output is `alias: changed`, `TypeError`, `frozen: changed 443 false`, `TypeError`, `getter: u1 false false` and `extensible: true allowed`. The writable structural view changes Config.host before freezing. Freeze then blocks the ordinary host assignment in strict JavaScript, while the nested port still changes. Reflect.set reports false without throwing for the blocked write. Writing host through the original readonly view fails checking with TS2540.

UserHard's public id is getter-only, so an ordinary assignment to it throws in this strict environment. It does not create a new own id property or replace #id. Reflect.set also returns false, and the original value remains u1. A new ordinary note property can still be added, demonstrating that a getter/private backing field does not freeze the whole object. Checked id assignment yields TS2540. The [2026 ordinary setter algorithm](https://tc39.es/ecma262/2026/multipage/ordinary-and-exotic-objects-behaviours.html#sec-ordinarysetwithowndescriptor) rejects an inherited accessor write with no setter; the [primary getter guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#getters--setters) explains its checked readonly view.

Use a readonly view to communicate mutation permissions to checked consumers. Use an actual descriptor/accessor/freeze mechanism when the specified runtime write must fail, and decide separately what should happen to nested mutable references. Do not treat private backing state as a complete immutability guarantee. [Object modifier/integrity contrasts](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) owns the wider alias/shallow-freeze cases.

### 3) **Encapsulation follows ownership and supported extension**

Protected exposes a field to checked subclass implementations; it does not enforce that every subclass mutation preserves an invariant. Private is useful for checked implementation boundaries; #private retains runtime private access rules after emission and keeps that private member outside ordinary own-key serialization/spread. These are language behaviors, not an automatic validation or authorization policy.

Save `extension.ts`:

```typescript
export {};
class BaseCounter {
  protected count = 0;
  read(): number { return this.count; }
}
class ChildCounter extends BaseCounter {
  setUnchecked(value: number): void { this.count = value; }
}
const child = new ChildCounter();
child.setUnchecked(-1);
console.log("protected:", child.read());
class BoundedCounter {
  #count = 0;
  inc(): void { this.#count++; }
  get value(): number { return this.#count; }
}
const counter = new BoundedCounter(); counter.inc();
console.log("owned:", counter.value);
class Session {
  userId: string;
  #token: string;
  constructor(userId: string, token: string) { this.userId = userId; this.#token = token; }
  get masked(): string { return this.#token.slice(0, 2) + "***"; }
}
const session = new Session("u1", "secret");
console.log(session.masked, JSON.stringify(session));
console.log(Object.keys({ ...session }).join(","));
// child.count; // uncomment: TS2445
// class WrongChild extends BaseCounter { readToken(): string { return this.secret; } } // uncomment: TS2339
```

The output is `protected: -1`, `owned: 1`, `se*** {"userId":"u1"}` and `userId`. ChildCounter is allowed to write the inherited protected count, including -1; the type does not express a nonnegative-number invariant. Outside child.count is rejected with TS2445. A member absent from the base does not become available merely because the code is in a subclass (TS2339 in WrongChild).

BoundedCounter's private state is accessed by its own operation, while Session intentionally exposes userId and a masked result without putting its private token into ordinary JSON/spread. The private field's absence there follows the member representation; a method or serializer that deliberately returns token could still expose its value. Choose a public API from the operations callers need, a protected extension point when subclasses should participate, and an implementation boundary whose runtime behavior meets the actual requirement. Avoid making every field hard-private or public by a keyword quota.

### 4) **Common confusion**

The string key #count is not the lexical private name #count. A checker-private property can remain enumerable, while a private member's emitted representation depends on target. Readonly is a checked view, a getter-only write can fail through an inherited accessor, and a shallow freeze leaves referenced nested objects mutable. Protected allows subclass access without proving the mutation valid. Identify the exact access or write before deciding which mechanism controls it.

### 5) **Performance note**

Public/private/protected/readonly annotations do not install runtime validation or freeze. Native private fields and the tested ES2015 WeakMap/helpers have real runtime implementations, as do accessors and freeze. This lesson measured no field memory overhead, engine lookup speed, freeze complexity or hot-path ranking. Do not trade away a needed access boundary because of an invented fixed byte count or speed claim; measure the actual target/runtime/workload through the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>).

### 6) **Mentor note**

Ask the learner to predict three writes: Reflect.set(hard, #count string, 99), writableView.host before freeze, and a forced user.id assignment through a writable view. A sound answer distinguishes an ordinary key from private state, an ordinary mutable data descriptor from readonly checking, and an inherited accessor with no setter. Then explain why Session's token is absent from JSON and why ChildCounter can still set a negative count. Evaluate the mechanism and the intended public/extension contract, rather than a universal modifier rule.
