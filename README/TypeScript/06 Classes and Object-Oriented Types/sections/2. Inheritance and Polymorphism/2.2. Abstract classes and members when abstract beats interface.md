## 2.2. Abstract classes and members — when abstract beats interface

### 1) **abstract contract** (abstract class cannot be instantiated; abstract method must be implemented — emit is a normal class)

**Definition** — `abstract class Animal { abstract speak(): string; }` declares a class that cannot be directly instantiated (`new Animal()` is an error) and may contain `abstract` members (methods, getters, properties) with no body. Subclasses must implement every `abstract` member to become concrete — otherwise they remain abstract.

**What problem it solves / history** — interfaces describe shapes without runtime; abstract classes describe shapes *plus* shared implementation (`constructor` validation, helper methods). Before `abstract` (added TS 1.6), teams duplicated base logic via mixins or runtime checks `if (this instanceof Animal)`.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), choose `abstract class` when subclasses should share runtime logic or a constrained construction path; emits as normal `class` (abstract is erased — safe under `--erasableSyntaxOnly`). Mark every inherited abstract member implemented in subclass — checker enforces it.

**Runnable example** — abstract contract (good vs bad, `tsc --strict`):

```typescript
// good — abstract base with shared logic + abstract hook
abstract class Animal {
  constructor(public name: string) {
    if (!name) throw new Error("name required");
  }
  // shared runtime helper
  describe(): string { return `${this.name} says ${this.speak()}`; }
  abstract speak(): string;
}
class Dog extends Animal { speak(): string { return "woof"; } }
class Cat extends Animal { speak(): string { return "meow"; } }
const dog = new Dog("Rex");
console.log(dog.describe()); // "Rex says woof"
// const a = new Animal("x"); // error TS2511: Cannot create an instance of an abstract class
// class Bad extends Animal {} // error TS2515: Non-abstract class 'Bad' does not implement inherited abstract member 'speak'

// abstract properties
abstract class Repo {
  abstract table: string;
  find(id: string): string { return `select * from ${this.table} where id=${id}`; }
}
class UserRepo extends Repo { table = "users"; } // ok — implements abstract property
```

```typescript
// bad — forgetting abstract forces runtime check that checker would have caught
class BaseNoAbstract {
  speak(): string { throw new Error("override me"); } // runtime throw, not checker error
}
class Kitten extends BaseNoAbstract {}
new Kitten().speak(); // throws at runtime — abstract would have errored at class declaration
// fix — use abstract
```

**Common confusion** — "`abstract` methods have emit" — no, abstract members leave no JS; concrete helper methods emit. "`abstract class` cannot have constructor logic" — it can and should; subclasses call it via `super()` — construction still validated.

**Performance note** — `abstract` adds zero emit/runtime cost (erased). Shared helper `describe()` is one function on prototype, not per-instance — same cost as normal method.

**Mentor note** — teach with error demo: try `new Animal` and missing `speak` — checker errors are immediate, unlike `throw` that fires only at call site. Review check: ask "what does `abstract` buy over `throw`?" Answer: declaration-site vs call-site failure.

### 2) **abstract vs interface with implementation** (interfaces shape-only; abstract classes ship shared runtime and construction constraints)

**Definition** — `interface Shape { area(): number; }` is *only* a type (erases, no runtime, no constructor). `abstract class Shape { abstract area(): number; perimeter(): number { ... } }` is both a type and a value (has prototype, constructor, shared helpers). Construction control (`protected constructor`, `private` brand) is possible only with `abstract class`.

**What problem it solves / history** — library authors needed to publish contracts that could evolve with default implementations without breaking consumers — abstract classes let you add `perimeter()` with a default body; interfaces require every implementer to add it.

**Modern guidance** — as of TypeScript 5.9 era:
| Need | Use | Why |
|---|---|---|
| Shape only (data holder, adapter) | `interface` | Purely structural, mergeable, no runtime coupling |
| Shared runtime/helpers + shape | `abstract class` | One implementation inherited by all subclasses |
| Cross-cutting without hierarchy | `interface` + mixins | Avoid diamond inheritance |

All three erase except abstract's runtime helpers which emit normally.

**Runnable example** — evolution (good vs bad, `tsc --strict`):

```typescript
// good — interface evolution breaks implementers
interface ShapeI { area(): number; }
// adding method breaks all implementers:
// interface ShapeI { area(): number; perimeter(): number; } // every implementer must add perimeter

// good — abstract with default lets evolution without break
abstract class ShapeA {
  abstract area(): number;
  perimeter(): number { return 0; } // default — subclasses inherit without change
  describe(): string { return `area=${this.area()}`; }
}
class Circle extends ShapeA {
  constructor(public r: number) { super(); }
  area(): number { return Math.PI * this.r * this.r; }
  // perimeter inherited as 0 — can override later without forcing immediate change
}

// construction constraint only abstract can do
abstract class Entity {
  protected constructor(public id: string) {} // protected → only subclasses construct
}
class User extends Entity {
  constructor(id: string, public name: string) { super(id); }
}
// new Entity("e1"); // error — abstract + protected constructor

// bad — using interface when shared logic duplicates
interface HasDescribe { name: string; describe(): string; }
// every class re-implements describe() — duplicated
```

```typescript
// good — abstract registry pattern
abstract class BaseRepo2 {
  abstract table: string;
  static registry: Map<string, BaseRepo2> = new Map();
  register(): void { BaseRepo2.registry.set(this.table, this); }
}
```

**Common confusion** — "`interface` can have implementation" — never at runtime; default members are `abstract class` feature. "`abstract class` is like Java abstract" — structurally still checked, not nominal like Java/C#.

**Performance note** — interface has zero runtime (erases); abstract helpers add one prototype method per helper — negligible. Construction via `super(...)` is one extra call — JIT inlines small bases.

**Mentor note** — teach by adding a new method to both an `interface` and an `abstract class` and counting how many consumers break. Review checklist: if you foresee shared helpers or `super` control, start with `abstract class`; if you need pure shape contracts across modules, start with `interface`.

### 3) **Abstract construct signatures** (abstract new ... => T — typing factories that accept any subclass constructor)

**Definition** — `abstract new (args) => T` is the construct signature that matches *either* abstract or concrete constructors; `new (args) => T` matches only concrete ones. Factories that should accept any subclass (including abstract-typed parameters) must use `abstract new` to avoid rejecting abstract bases at the type level.

**What problem it solves / history** — factories typed as `new () => Animal` rejected `abstract class Animal` and test fakes that were typed as abstract; `abstract new` (TS 4.2+) closed that gap while keeping `new Animal()` still an error at call sites — type-level vs value-level split.

**Modern guidance** — as of TypeScript 5.9 era, prefer `abstract new` in generic factories (`function create<T>(Ctor: abstract new (...args: any[]) => T)`) when the factory does not itself call `new AbstractClass`; keep `new` concrete when the factory *must* guarantee concrete instantiation.

**Runnable example** — abstract construct for factories (good vs bad, `tsc --strict`):

```typescript
abstract class Animal2 { constructor(public name: string) {} abstract speak(): string; }
class Dog2 extends Animal2 { speak(): string { return "woof"; } }
class Cat2 extends Animal2 { speak(): string { return "meow"; } }

// good — factory accepts any concrete subclass via abstract new
type AbstractCtor<T> = abstract new (...args: any[]) => T;
function makeAnimal2(Ctor: AbstractCtor<Animal2>, name: string): Animal2 {
  // inside, we know Ctor is concrete at call site (Dog2/Cat2) — cast to concrete for new
  return new (Ctor as new (name: string) => Animal2)(name);
}
const d = makeAnimal2(Dog2, "Rex");
const c = makeAnimal2(Cat2, "Milo");

// bad — new-only factory rejects abstract-typed helpers
type ConcreteCtor<T> = new (...args: any[]) => T;
function makeConcrete<T>(Ctor: ConcreteCtor<T>): T { return new Ctor(); }
// makeConcrete(Animal2 as unknown as ConcreteCtor<Animal2>); // awkward cast — prefer AbstractCtor

// good — utility bridging
type CtorParams<T extends AbstractCtor<any>> = ConstructorParameters<T>; // works with abstract new
type CtorInst<T extends AbstractCtor<any>> = InstanceType<T>;
type DogParams = CtorParams<typeof Dog2>; // [name: string]

// bad — expecting abstract to be directly constructable
// new Animal2("x"); // error TS2511 — abstract cannot be instantiated even though its construct sig exists
```

```typescript
// good — concrete-only factory when guarantee matters
class Concrete {
  constructor(public id: string) {}
}
function makeConcreteOnly(Ctor: new (id: string) => Concrete): Concrete {
  return new Ctor("id-1"); // guaranteed concrete — no cast needed
}
makeConcreteOnly(Concrete); // ok
// makeConcreteOnly(Animal2 as unknown as new (name: string) => Animal2); // forces concrete contract
```

**Common confusion** — "`abstract new` means you can `new` the abstract class" — no, you still cannot `new Animal2(...)` — the signature only widens *what you can pass as a Ctor value*, not what you can instantiate. "`new` vs `abstract new` differ at emit" — no difference, both erase.

**Performance note** — construct signatures are checker-only, no emit or runtime indirection beyond the single `new` call.

**Mentor note** — draw two columns: Type-level (what can be *passed* as Ctor) vs Value-level (what can be *new'd*). Exercise: write `function clone<T extends Animal2>(obj: T): T` vs `function recreate(Ctor: AbstractCtor<T>)` and ask which needs `abstract new`.
