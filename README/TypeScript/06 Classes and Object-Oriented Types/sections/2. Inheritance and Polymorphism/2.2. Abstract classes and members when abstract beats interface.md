## 2.2. Abstract classes and members — when abstract beats interface

An abstract class can provide shared executable behavior while leaving named operations for concrete subclasses to implement. Choose it when that inheritance relationship is useful. Shape checking, constructor access and reusable runtime behavior are separate needs; an abstract class is one way to combine them.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named file in a fresh directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. For intentional rejections, activate one marked line in a separate copy and replace --outDir dist with --noEmit. The forced-construction failure is caught so the rest of its program can run.

### 1) **Abstract hooks and shared executable behavior**

Animal.describe is a real method that calls the speak hook. Dog and Cat supply different hook bodies while inheriting the helper. A non-abstract subclass must implement the inherited abstract members; directly constructing the abstract base is rejected. These are checker obligations. The abstract modifier and bodyless hook are absent from the emitted JavaScript, while the constructor and describe implementation remain. The [class guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#abstract-classes-and-members) develops that contract.

Save `hooks.ts`:

```typescript
export {};
abstract class Animal {
  name: string;
  constructor(name: string) {
    if (name.length === 0) throw new Error("name required");
    this.name = name;
  }
  abstract speak(): string;
  describe(): string { return this.name + " says " + this.speak(); }
}
class Dog extends Animal { speak(): string { return "woof"; } }
class Cat extends Animal { speak(): string { return "meow"; } }
console.log(new Dog("Rex").describe());
console.log(new Cat("Milo").describe());
// new Animal("base"); // TS2511: direct abstract construction.
// class Missing extends Animal {} // TS2515: missing inherited abstract hook.

abstract class Repo {
  abstract table: string;
  describe(): string { return "table=" + this.table; }
}
class UserRepo extends Repo { table = "users"; }
console.log(new UserRepo().describe());
// class MissingTable extends Repo {} // TS2515: abstract property not implemented.

class ThrowingBase { speak(): string { throw new Error("override me"); } }
class SilentChild extends ThrowingBase {}
try { new SilentChild().speak(); }
catch (error: unknown) {
  console.log(error instanceof Error ? error.message : "unexpected error");
}
```

The output is `Rex says woof`, `Milo says meow`, `table=users` and `override me`. The first three lines use real subclass implementations. The last demonstrates a different contract: ThrowingBase already has a concrete speak, so SilentChild is accepted and only fails when that body executes. Use an abstract hook when omitting the operation should be a declaration error. Use a concrete throwing body only when throwing is itself deliberate behavior.

Constructor checks such as the empty-name rejection remain ordinary JavaScript checks. TypeScript's string annotation alone does not validate external input. Also avoid invoking a subclass hook from a base constructor when it relies on fields initialized later; the [constructor owner](<../1. Class Type Fundamentals/1.2. Constructors parameter properties and instance creation.md>) covers initialization evidence.

### 2) **Choose shape, construction access and implementation separately**

An interface is useful when a consumer needs a public capability without a required inheritance chain. An abstract class is useful when subclasses should inherit a helper around required hooks. Ordinary classes can also restrict construction: private and protected constructors do not require abstract. A runtime mixin function returning a class supplies executable implementation too; its type annotations erase, but its function and returned class remain.

Save `choices.ts`:

```typescript
export {};
interface Named { name: string }
interface Described { describe(): string }
function render(value: Described): string { return value.describe(); }
const plain = { describe(): string { return "plain adapter"; } };
console.log(render(plain));

class FactoryOnly {
  private constructor() {}
  static create(): FactoryOnly { return new FactoryOnly(); }
}
class ExtendOnly { protected constructor() {} }
class ConcreteChild extends ExtendOnly { constructor() { super(); } }
console.log("restricted:", FactoryOnly.create() instanceof FactoryOnly,
  new ConcreteChild() instanceof ExtendOnly);
// new FactoryOnly(); // TS2673: private constructor.
// new ExtendOnly(); // TS2674: protected constructor.

class Person { name = "Ada"; }
function described(Base: new () => Named) {
  return class extends Base {
    describe(): string { return "name=" + this.name; }
  };
}
const DescribedPerson = described(Person);
const person = new DescribedPerson();
console.log(render(person), person instanceof Person);

abstract class Shape {
  abstract area(): number;
  abstract perimeter(): number;
  describe(): string { return "area=" + this.area(); }
}
class Square extends Shape {
  side = 2;
  area(): number { return this.side * this.side; }
  perimeter(): number { return 4 * this.side; }
}
console.log(new Square().describe(), new Square().perimeter());
```

The output is `plain adapter`, `restricted: true true`, `name=Ada true` and `area=4 8`. Both the plain adapter and the generated class satisfy Described. The restricted ordinary classes establish construction access independently of abstract hooks. The [historical protected-constructor example](https://www.typescriptlang.org/docs/handbook/classes.html#understanding-protected) illustrates ordinary constructor control; the current diagnostics above verify it on the declared compiler.

The [mixin guide](https://www.typescriptlang.org/docs/handbook/mixins.html#how-does-a-mixin-work) explains class-expression composition. This small example only composes a zero-argument named base; the [mixin owner](<../3. Advanced Class Patterns/3.2. Mixins and class composition without inheritance.md>) owns generic forwarding and stacking. A mixin can itself use extends internally, as described does here. It is not an erased alternative to all runtime inheritance.

Adding a default perimeter that returns zero could preserve source compatibility for an existing Circle subclass while producing the wrong perimeter. Square instead implements the meaningful operation explicitly. When evolving a base contract, test both compilation and the behavior clients depend on. A default implementation is useful only when its meaning is valid for the inheriting subclasses; adding a required hook deliberately requires those subclasses to supply behavior.

### 3) **Constructors you may inspect versus constructors you may invoke**

A concrete construct signature such as new (name: string) => T permits construction with that argument contract. An abstract construct signature accepts abstract or concrete constructors, but does not authorize invoking them. Use the broader form for a helper that only inspects the constructor or applies a type query. Use the concrete form for a factory that actually constructs. The [construct-signature discussion](https://www.typescriptlang.org/docs/handbook/2/classes.html#abstract-construct-signatures) shows why an instantiating helper must reject an abstract base.

Save `constructors.ts`:

```typescript
export {};
abstract class Animal {
  name: string;
  constructor(name: string) { this.name = name; }
  abstract speak(): string;
}
class Dog extends Animal { speak(): string { return "woof"; } }
function make<T extends Animal>(Ctor: new (name: string) => T, name: string): T {
  return new Ctor(name);
}
const dog = make(Dog, "Rex");
console.log(dog.name, dog.speak());
// make(Animal, "base"); // TS2345: abstract constructor cannot meet concrete new.

function inspect(Ctor: abstract new (name: string) => Animal): string {
  // new Ctor("base"); // TS2511: this signature allows abstract constructors.
  return Ctor.name;
}
console.log(inspect(Animal), inspect(Dog));
type BaseArguments = ConstructorParameters<typeof Animal>;
type BaseInstance = InstanceType<typeof Animal>;
const args: BaseArguments = ["Milo"];
const instance: BaseInstance = new Dog(...args);
console.log(instance.name, instance.speak());

// Deliberately unsafe: this assertion discards the abstract-constructor restriction.
function forced(Ctor: abstract new (name: string) => Animal): Animal {
  return new (Ctor as new (name: string) => Animal)("forced");
}
const base = forced(Animal);
console.log("forced base:", base instanceof Animal, typeof base.speak);
try { base.speak(); }
catch (error: unknown) {
  console.log(error instanceof TypeError ? "missing hook: TypeError" : "unexpected error");
}
```

This prints `Rex woof`, `Animal Dog`, `Milo woof`, `forced base: true undefined` and `missing hook: TypeError`. The safe factory constructs Dog; passing Animal is rejected. Inspection accepts both because it does not instantiate either. ConstructorParameters and InstanceType also work with this abstract class without creating a value themselves.

The final factory deliberately recreates the old mistake. Its parameter type explicitly allows Animal. The assertion cannot establish that the caller chose a concrete subclass. JavaScript constructs the emitted Animal, and the missing hook fails later. Keep concrete construction evidence in the signature instead of using a cast to silence precisely the restriction the factory needs. Constructor access restrictions are an additional consideration: the signature above describes publicly constructible classes, not a way around a private or protected constructor.

### 4) **Common confusion**

Abstract does not install a runtime guard against new. Its checker restriction and required hooks disappear during emission; concrete bodies remain. Constructor visibility is a separate checker restriction available on ordinary classes too. An interface describes members but does not install their implementations. A mixin's declarations may erase while its actual function, class and calls execute. Finally, accepting an abstract constructor for inspection is different from having evidence that it can safely be instantiated.

### 5) **Performance note**

The abstract modifiers and construct signatures add no runtime operation after erasure. Shared helpers, constructor checks, mixin calls and generated classes still run. Calling described creates a class; constructing DescribedPerson creates an instance. There is no measured cost ranking among interfaces, abstract bases and mixins here, and no general promise of inlining or negligible overhead. Choose the required behavior first; investigate actual checking or runtime costs with the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) and an appropriate runtime profiler.

### 6) **Mentor note**

Give a learner three changes to review. First, replace the required perimeter hook with a zero default: compilation may succeed while geometric behavior is wrong. Second, change make's concrete constructor parameter to abstract new: direct invocation must now be rejected. Third, silence that error with the forced assertion: the observed missing-hook failure explains what evidence was discarded. Ask them to justify each result and propose the smallest contract that permits the intended operation. A good answer preserves an actual implementation or a concrete constructor requirement instead of adding casts.
