## 2.1. Extends implements and structural class compatibility

### 1) **extends vs implements** (extends inherits runtime + types; implements only checks structural satisfaction — removing it doesn't change assignability)

**Definition** — `class Dog extends Animal` inherits *both* runtime prototype chain and type members; `class Dog implements AnimalLike` only *checks* that `Dog` has the members of `AnimalLike` — no runtime inheritance, no prototype link. Removing `implements` does not change whether an instance is assignable (structure governs), only whether the checker verifies completeness at the declaration site.

**What problem it solves / history** — JavaScript only has `extends` (prototype chain). TypeScript added `implements` to let a class claim compliance with `interface`/`type` contracts without inheriting implementation — enabling "implements capability, not heritage" (e.g., `class User implements Serializable`). Early TS teams misused `implements` as inheritance; the distinction clarified in Handbook § Classes.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), use `extends` when you need `super` and shared logic; use `implements` when you need a shape guarantee (adapter, repository contract) without coupling to a base class. Prefer `interface` for the `implements` target — it gives clearer error messages than type aliases.

**Runnable example** — extends vs implements (good vs bad, `tsc --strict`):

```typescript
interface Logger { log(msg: string): void; }
class BaseRepo {
  constructor(protected table: string) {}
  query(sql: string): void { console.log(`[${this.table}] ${sql}`); }
}

// good — extends inherits behavior + type
class UserRepo extends BaseRepo implements Logger {
  constructor() { super("users"); }
  log(msg: string): void { this.query(`-- log: ${msg}`); }
}
const ur = new UserRepo();
ur.query("select *");
ur.log("hi");
console.log(ur instanceof BaseRepo); // true — runtime chain

// good — implements only checks shape, no runtime link
interface Serializable { serialize(): string; }
class Order implements Serializable {
  constructor(public id: string) {}
  serialize(): string { return JSON.stringify({ id: this.id }); }
}
const o: Serializable = new Order("o1"); // ok — shape matches
// Order does NOT extend anything — Order.prototype is not linked to Serializable (interface has no runtime)

// bad — expecting implements to inherit
// class Bad implements BaseRepo { // error — BaseRepo is a value, not just a type, but implements only checks shape
//   // must re-declare query/super logic manually — better extends
// }

// bad — removing implements hides missing method until use-site
// class ForgotLogger implements Logger {}
// error TS2420: Class incorrectly implements interface 'Logger' — missing log — caught at declaration
// without implements, the omission would surface only where Logger is expected — later and noisier
class ForgotLoggerNoCheck { /* forgot log */ }
declare function useLogger(l: Logger): void;
// useLogger(new ForgotLoggerNoCheck()); // error appears here instead of at class — less local
```

```typescript
// good — structural assignability survives without implements
interface PointLike { x: number; y: number; }
class Point implements PointLike { constructor(public x: number, public y: number) {} }
class LoosePoint { constructor(public x: number, public y: number) {} } // no implements
const p: PointLike = new LoosePoint(1, 2); // ok — shape, not declaration, matters
```

**Common confusion** — "`implements` creates inheritance" — never at runtime; it is a *check* only, erases. "`extends` is required for assignability" — no, two classes with same shape are assignable regardless of `extends` (unless `private`/`#private` present).

**Performance note** — `extends` adds one prototype link — monomorphic dispatch after warm-up; deep hierarchies (>5 levels) add O(depth) `instanceof` cost. `implements` has zero emit/runtime cost (checker only).

**Mentor note** — teach by removing `implements` and showing assignability still holds — then ask "what did `implements` buy?" Answer: local error at class vs distant error at call site. Review exercise: give `class C implements I` missing one method and ask where the error appears.

### 2) **Structural compatibility of classes** (two classes with same shape assignable regardless of heritage — private/#private is the only nominal escape)

**Definition** — TypeScript checks classes *structurally* like objects: `class A { x: number }` and `class B { x: number }` are mutually assignable even though they never share lineage. Only `private` or `#private` members add a nominal brand — two classes with mismatched private fields are incompatible even if public shapes match.

**What problem it solves / history** — JS libraries often produce same-shaped classes from different factories (e.g., two `User` classes from different bundles). Structural typing lets them interoperate without explicit hierarchy — nominal would force casting everywhere.

**Modern guidance** — as of TypeScript 5.9 era, treat class assignability as shape until you need domain separation — then add `private __brand` or `#private` (see [1.3. Access modifiers](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>) and [1.3. Nominal typing](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)). Never rely on class name for separation — expose a branded `UserId` type instead.

**Runnable example** — structural vs branded (good vs bad, `tsc --strict`):

```typescript
// good — same public shape → assignable despite different declarations
class Dog { constructor(public name: string) {} bark(): string { return "woof"; } }
class Cat { constructor(public name: string) {} meow(): string { return "meow"; } }
const dog: Dog = new Dog("Rex");
// const cat: Cat = dog; // error TS2741? Actually bark vs meow mismatch — not assignable because method sets differ
// But public-shape-only classes with same members ARE assignable:

class A { constructor(public x: number, public y: number) {} }
class B { constructor(public x: number, public y: number) {} }
let a: A = new B(1, 2); // ok — same public shape

// branded via private — same public shape but NOT assignable
class UserId { private __brand = "UserId"; constructor(public id: string) {} }
class OrderId { private __brand = "OrderId"; constructor(public id: string) {} }
declare let uid: UserId;
declare let oid: OrderId;
// const bad: UserId = oid; // error TS2322 — private brand mismatch (nominal separation)
// #private also brands
class HardUserId { #brand = "UserId"; constructor(public id: string) {} }
class HardOrderId { #brand = "OrderId"; constructor(public id: string) {} }
// const bad2: HardUserId = new HardOrderId("o1") as unknown as HardUserId; // still error structurally

// good — function accepting either A or B by shape
function dist(p: A): number { return Math.hypot(p.x, p.y); }
dist(new B(3, 4)); // ok — B shape satisfies A
```

```typescript
// bad — assuming nominal separation without private (production leak)
class User { constructor(public id: string) {} }
class Order { constructor(public id: string) {} }
function deleteUser(u: User): void { console.log(u.id); }
declare let order: Order;
deleteUser(order); // compiles — same shape, no brand — deletes order by mistake
// fix — add brand
class SafeUser { private __u = true; constructor(public id: string) {} }
class SafeOrder { private __o = true; constructor(public id: string) {} }
// deleteUserSafe(new SafeOrder("o1")); // error — brand prevents leak
```

**Common confusion** — "class heritage makes types compatible" — heritage is *sufficient* but not *necessary*; shape governs. "`private` name matters" — only that *some* private exists per class with matching declaration; same private name with different types still checks.

**Performance note** — structural check rescans members per assignment — O(members), compile-time only; adding `private` brand adds one member to check, negligible. Runtime `instanceof` still walks prototype — stricter than assignability (see [1.1. Construct signatures](<../1. Class Type Fundamentals/1.1. Class as type and value duality instance vs constructor.md>)).

**Mentor note** — demo `A = B` assignability then add `private` to both and show break. Ask "which one protects `deleteUser(order)`?" Exercise: brand `UserId` vs `OrderId` with `private` and show the checker now rejects the leak.

### 3) **implements with interfaces vs type aliases** (why implements prefers interface and how & composes outside the class)

**Definition** — `implements` accepts `interface` or `type` alias that describes an object shape; for `interface` the checker reports missing members with interface-member wording, for `type` it may show expanded `&`/`|`. Both erase; `&` (intersection) is the out-of-class composition alternative (`type Combined = A & B` vs `class C extends A`).

**What problem it solves / history** — early codebases used `type` unions for `implements` (`implements A & B`) which produced opaque error messages. Handbook now recommends `interface` for `implements` targets — clearer diffs ("Property 'x' is missing") and merges cleanly for augmentation.

**Modern guidance** — as of TypeScript 5.9 era, prefer `interface` for any type you `implement` or `extend` from a class; reserve `type` for unions/conditionals/mapped that `interface` cannot express. When a class needs multiple contracts, `implements A, B` is clearer than `implements A & B` — assignability is the same.

**Runnable example** — interface vs type alias for implements (good vs bad, `tsc --strict`):

```typescript
interface HasId { id: string; }
type HasIdType = { id: string; }
class UserI implements HasId { constructor(public id: string) {} } // preferred — interface target
class UserT implements HasIdType { constructor(public id: string) {} } // also ok

// multiple contracts — comma form preferred
interface Timestamped { createdAt: Date; }
interface Loggable { log(): void; }
class AppEvent implements Timestamped, Loggable {
  createdAt = new Date();
  log(): void { console.log(this.createdAt); }
}

// bad — opaque & in implements (same check, worse message)
type Combo = HasId & Timestamped;
// class Event2 implements Combo { // error would show expanded intersection — harder to read
// }

// good — & outside class composes without implements
type WithMeta = UserI & { meta: string };
const withMeta: WithMeta = { id: "u1", meta: "admin" } as unknown as WithMeta;
// class need not implement WithMeta — structural check suffices at use-site
```

```typescript
// bad — expecting type-only union/mapped to be implementable
// interface Bad implements string {} // error — string is primitive, not object shape
type Wrap<T> = { value: T };
// class NumberWrap implements Wrap<number> {} // ok — generic type alias is object shape, allowed
class NumWrap implements Wrap<number> { constructor(public value: number) {} }
```

**Common confusion** — "`implements` can implement any `type`" — only object-shape `type` aliases; `string | number`, primitives, or unions with non-object members are not object shapes to implement. "`interface` and `type` behave identically under `implements`" — largely, but interface merging and error phrasing differ.

**Performance note** — both `interface` and `type` targets erase; `implements` list length is checker-only — 1 vs 5 interfaces is negligible. Composition via `&` outside class does not affect class emit.

**Mentor note** — show error messages: `implements HasId` missing `id` vs `implements HasId & Timestamped` missing — second message expands intersection and is noisier. Exercise: convert `implements A & B` to `implements A, B` and compare hover.
