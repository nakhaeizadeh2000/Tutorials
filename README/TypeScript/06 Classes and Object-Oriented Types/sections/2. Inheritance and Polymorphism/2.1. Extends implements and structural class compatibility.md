## 2.1. Extends implements and structural class compatibility

Inheritance supplies implementation through a runtime class chain. An implements clause checks an instance contract at the class declaration. Assignment asks whether the source satisfies the target type. These questions often have the same answer for a subclass, but an adapter can satisfy a contract without inheriting its implementation.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named file in a fresh directory without tsconfig.json. Build the three positive programs with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. For a commented negative, activate only that line in a separate copy and replace --outDir dist with --noEmit. Check bad-syntax.ts separately with --noEmit; it is deliberately invalid and must not be run.

### 1) **Inheritance supplies behavior; implements checks a contract**

UserRepo inherits query and the protected table member from BaseRepo. Its constructor calls super to initialize the inherited state. Its own log method meets Logger. The class target in the next example is also legal: PublicRepo names an instance type as well as a constructor value. Adapter supplies its own query body and implements that public instance contract without extending PublicRepo.

Save `heritage.ts`:

```typescript
export {};
interface Logger { log(message: string): void }
class BaseRepo {
  protected table: string;
  constructor(table: string) { this.table = table; }
  query(sql: string): string { return this.table + ": " + sql; }
}
class UserRepo extends BaseRepo implements Logger {
  constructor() { super("users"); }
  log(message: string): void { console.log(this.query("log " + message)); }
}
const users = new UserRepo();
console.log(users.query("select"));
users.log("hi");
console.log("chains:", Object.getPrototypeOf(UserRepo) === BaseRepo,
  Object.getPrototypeOf(UserRepo.prototype) === BaseRepo.prototype);

class PublicRepo { query(): string { return "base"; } }
class Adapter implements PublicRepo { query(): string { return "adapter"; } }
const repo: PublicRepo = new Adapter();
console.log(repo.query(), repo instanceof PublicRepo);

interface PointLike { x: number; y: number }
class LoosePoint { x = 3; y = 4; }
const point: PointLike = new LoosePoint();
console.log("distance:", Math.hypot(point.x, point.y));
function useLogger(logger: Logger): void { logger.log("used"); }
class MissingLogger {}
// class CheckedMissing implements Logger {} // TS2420: missing log at declaration.
// useLogger(new MissingLogger()); // TS2741: missing log at use site.
// users.missing(); // TS2339: inheritance does not supply an absent member.
```

The output is `users: select`, `users: log hi`, `chains: true true`, `adapter false` and `distance: 5`. Both prototype links exist for UserRepo. Adapter has a usable query but no PublicRepo prototype inheritance. LoosePoint needs no implements clause to satisfy PointLike.

Use implements when the declaration itself should be checked against a named contract. Removing it removes that local completeness check; it does not remove members from the class or create a new nominal identity. Activate CheckedMissing to see the declaration error, then instead activate useLogger to see the use-site error. The [class guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#implements-clauses) describes implements as a check on the class, rather than an inherited method provider. It also does not contextually fill in missing parameter annotations in your implementation.

### 2) **Public shape and member origins**

For public members, matching class names are unnecessary. For private or protected members, compatibility also considers their declaration origin. Two sibling subclasses can inherit the same protected declaration and remain compatible. Two unrelated classes that each declare a protected member with the same name do not share that origin. The [compatibility guide](https://www.typescriptlang.org/docs/handbook/type-compatibility.html#private-and-protected-members-in-classes) explicitly covers both private and protected members.

Save `origins.ts`:

```typescript
export {};
class PublicUser { id = "u1"; }
class PublicOrder { id = "o1"; }
function displayUser(user: PublicUser): string { return user.id; }
console.log("public shape:", displayUser(new PublicOrder()));

class ProtectedBase { protected marker = 0; id = "shared"; }
class Left extends ProtectedBase {}
class Right extends ProtectedBase {}
class Other { protected marker = 0; id = "other"; }
const sibling: Left = new Right();
console.log("shared origin:", sibling.id);
// const unrelated: Left = new Other(); // TS2322: different protected origins.
// class OtherImplementation implements ProtectedBase { protected marker = 0; id = "other"; } // TS2720.

class PrivateUser { private marker = true; id = "u1"; }
class PrivateOrder { private marker = true; id = "o1"; }
// const privateMismatch: PrivateUser = new PrivateOrder(); // TS2322.
const forced = new PrivateOrder() as unknown as PrivateUser;
console.log("assertion bypass:", forced.id);

class HardUser { #marker = true; id = "u1"; read(): boolean { return this.#marker; } }
class HardOrder { #marker = true; id = "o1"; read(): boolean { return this.#marker; } }
// const hardMismatch: HardUser = new HardOrder(); // TS2322.
const forcedHard = new HardOrder() as unknown as HardUser;
try {
  console.log(HardUser.prototype.read.call(forcedHard));
} catch (error: unknown) {
  console.log(error instanceof TypeError ? "private access: TypeError" : "unexpected error");
}
```

The output is `public shape: o1`, `shared origin: shared`, `assertion bypass: o1` and `private access: TypeError`. The first call is accepted because the public shapes match. In a real operation where user and order IDs have different meaning, this is a reason to introduce a checked domain contract, rather than assume the class name separates them.

Activate unrelated to see TS2322. The OtherImplementation declaration instead produces TS2720: its independently declared protected marker cannot implement the protected member from ProtectedBase. The cause is the member origin, not a prohibition on class types in implements. Extend the intended base when inheriting its protected extension contract is appropriate; otherwise depend on a deliberately public capability contract.

The private mismatch is rejected even though both classes spell their marker identically. A double assertion bypasses that check; it does not validate identity or reconstruct state. HardOrder has its own lexical private marker. Invoking the HardUser method against that object fails even after an assertion. The [access-modifier owner](<../1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>) explains private names, ordinary string keys and emitted representations in full. The [branding owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) develops checked domain factories and projection limits.

### 3) **Legal contract composition**

An interface, a concrete object alias, a named intersection and a mapped type with known keys can supply a class contract. A comma-separated implements list checks each listed contract. Direct A & B syntax in that list is a grammar error. A union of alternatives is also unsuitable as one statically known set of members to implement; that semantic restriction differs from the parser error.

Save `contracts.ts`:

```typescript
export {};
interface HasId { id: string }
type Labeled = { label: string };
type Combined = HasId & Labeled;
class Named implements Combined { id = "u1"; label = "Ada"; }
class Comma implements HasId, Labeled { id = "u2"; label = "Grace"; }
type Permissions = { [K in "read" | "write"]: boolean };
class Policy implements Permissions { read = true; write = false; }
type Wrap<T> = { value: T };
class NumberWrap implements Wrap<number> { value = 42; }
console.log(new Named().label, new Comma().label);
console.log(new Policy().read, new Policy().write, new NumberWrap().value);
// class MissingPolicy implements Permissions { read = true; } // TS2420: missing write.
type Alternative = HasId | Labeled;
// class UnionTarget implements Alternative { id = "u3"; label = "Lin"; } // TS2422.
```

This prints `Ada Grace` and `true false 42`. MissingPolicy fails at its declaration with TS2420; UnionTarget fails with TS2422 even though its body happens to provide both public fields. Choose an explicit combined contract if the class must provide both. Choose separate implementations and a union at the consuming boundary if alternatives are intended.

Save the separate, intentionally rejected `bad-syntax.ts`:

```typescript
export {};
interface A { a: string }
interface B { b: number }
class Bad implements A & B { a = "a"; b = 1; }
```

Checking this file produces two TS1005 parser diagnostics. Use a named intersection or `implements A, B` as in the working program. Neither fix automatically supplies the fields. The [composition owner](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) covers compatible utility parents, conflicts and exact optional properties. Interface-versus-alias choices should follow capabilities such as declaration merging, not an unverified guarantee that one always produces better diagnostics.

### 4) **Common confusion**

An accepted assignment does not prove prototype inheritance. An implements clause can name a class instance type without inheriting its methods. Conversely, matching public fields do not settle every class assignment when protected or private origins matter. Check the target's complete contract and the declaration that introduced each restricted member before adding assertions. A mapped type is not automatically excluded from heritage: the concrete known-key Permissions example is accepted.

### 5) **Performance note**

The implements clauses, aliases and assertions erase. Constructors, field initializers, prototype inheritance and the explicit method calls still execute. Replacing extends with implements requires providing the behavior through some other runtime code; erasing a clause does not erase that work. No dispatch speed, hierarchy-depth threshold or checker member-count formula was measured here. For a real checking bottleneck, use the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) while preserving the required contract.

### 6) **Mentor note**

Ask the learner to predict three independent results: Adapter assigned to PublicRepo succeeds, its instanceof PublicRepo is false, and Other assigned to Left fails. A sound explanation identifies public shape, runtime chain and protected origin respectively. Then ask why adding a double assertion changes checker acceptance but not the HardUser private-access result. Finally, diagnose Bad in two steps: repair its grammar, then check whether the required members exist. These questions reveal whether the learner is reasoning about the operation or merely recognizing a keyword.
