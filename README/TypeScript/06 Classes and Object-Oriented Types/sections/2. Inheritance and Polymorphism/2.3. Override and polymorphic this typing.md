## 2.3. Override and polymorphic this typing

### 1) **override keyword** (TS 4.3+ — override proves you actually override a base member; missing base becomes error not silent overload)

**Definition** — `override` (keyword, not decorator) marks a subclass member that intentionally overrides a base member; with `noImplicitOverride` on, every overriding member *must* have `override`, and with `override` present the checker verifies a matching base member exists — misspelling or renamed base becomes an error.

**What problem it solves / history** — before `override`, renaming `Base.save()` to `Base.persist()` silently orphaned every `Sub.save()` — subclasses became separate overloads, not overrides, and runtime dispatch missed them (silent bug). `override` (TS 4.3, `noImplicitOverride` flag) turned that into a compile error at the subclass declaration site.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta), enable `noImplicitOverride` in `tsconfig.json` and mark every overriding member with `override`. The keyword erases (zero runtime), safe under `--erasableSyntaxOnly`.

**Runnable example** — override catches renames (good vs bad, `tsc --strict --noImplicitOverride`):

```typescript
// good — override proves intent and catches rename
class Repo {
  save(item: string): void { console.log(`save ${item}`); }
}
class UserRepo extends Repo {
  override save(item: string): void { console.log(`user save ${item}`); super.save(item); }
}

// bad — without override, rename silences (noImplicitOverride off would allow this silently)
class BadRepo extends Repo {
  override save(item: string): void { console.log(item); }
  // if noImplicitOverride were off, `save` without `override` would have silently orphaned on Base rename
}

// good — misspelling caught by override
class Base2 {
  handle(): void {}
}
class Child2 extends Base2 {
  // override handel(): void {} // error TS4113: This member cannot have an 'override' modifier because it is not declared in the base class
  override handle(): void { console.log("handled"); } // ok — matches base
}

// good — override on getters/setters and with types
class Animal3 {
  get label(): string { return "animal"; }
  speak(): string { return "..."; }
}
class Dog3 extends Animal3 {
  override get label(): string { return "dog"; }
  override speak(): string { return "woof"; }
}
```

```typescript
// bad — adding override where no base exists misleads readers even without flag
class Standalone {
  // override foo(): void {} // error when override present but no base — easy to catch
}
```

**Common confusion** — "`override` is a decorator/metadata" — no, it is a contextual keyword that only affects checking, no emit, no reflector. "`override` changes dispatch" — never at runtime; it only validates static intent.

**Performance note** — `override` has zero emit/runtime cost (erases). Benefit is fewer silent dispatch misses, which at scale avoids debugging megacross-heap call-graph issues in monorepos.

**Mentor note** — teach with rename demo: rename `Base.save` to `Base.persist` and show `BadRepo.save` becomes a new method without `override`, but `UserRepo override save` errors immediately. Review rule: every PR that adds a class member touching a base name must include or remove `override` so reviewers see intent.

### 2) **Polymorphic this as return** (clone(): this — the return type that tracks the subclass, not the base)

**Definition** — `method(): this` means "return the same concrete type as the *receiver*" — `new Dog().clone()` returns `Dog`, `new Cat().clone()` returns `Cat`, even when `clone` is declared only in `Animal`. Unlike `Animal` return, `this` parameterizes the return over the subclass without generics.

**What problem it solves / history** — fluent APIs (`builder.setX().setY().build()`) and prototype `clone`/`copy` needed subclass-preserving returns without casting at every call. Generics `class Box<T>` parametrized the *container*, not the *self* — `this` solved self-type for `extends` chains.

**Modern guidance** — as of TypeScript 5.9 era, use `(): this` for chainable setters, `clone(): this`, and `static create(): this` (polymorphic statics via `this` param on static). Prefer `this` over `Self extends Base` generics — `this` stays accurate through any depth without manual type arguments.

**Runnable example** — polymorphic this (good vs bad, `tsc --strict`):

```typescript
// good — this preserves subclass through base method
class Fluent {
  protected x = 0;
  setX(v: number): this { this.x = v; return this; }
}
class SubFluent extends Fluent {
  private y = 0;
  setY(v: number): this { this.y = v; return this; }
}
const s = new SubFluent().setX(1).setY(2); // ok — setX returns this (SubFluent), so setY visible
// const bad = new Fluent().setX(1).setY(2); // error — Fluent has no setY, as expected

// good — clone with this
class Animal4 {
  constructor(public name: string) {}
  clone(): this {
    const Ctor = this.constructor as new (name: string) => this;
    return new Ctor(this.name);
  }
}
class Dog4 extends Animal4 { bark(): void { console.log("woof"); } }
const d4 = new Dog4("Rex").clone(); // inferred Dog4
d4.bark(); // ok — this preserved Dog4 via clone()

// bad — using base type loses subclass
class BaseBad {
  clone(): BaseBad { return new BaseBad(); } // returns BaseBad, not subclass
}
class SubBad extends BaseBad {}
const sb = new SubBad().clone(); // inferred BaseBad — lost SubBad members
// (sb as SubBad).extra; // would need cast

// good — polymorphic this in static via this param
class Model {
  static create<T extends Model>(this: new () => T): T { return new this(); }
}
class UserModel extends Model { user = "u"; }
const um = UserModel.create(); // inferred UserModel
```

```typescript
// bad — expecting this to narrow without this return
class Counter {
  count = 0;
  inc(): void { this.count++; } // void, not chainable — chain breaks
}
// new Counter().inc().inc(); // error — inc returns void
```

**Common confusion** — "`this` return is the same as `Base` return" — `Base` fixes return to base even on subclass receivers; `this` tracks the *actual* receiver. "`this` needs generics" — it is already generic over self — no `<T>` needed.

**Performance note** — `this` return is checker-only (erases); emitted JS still returns `this` value (one reference, no allocation beyond the usual `return this`). Chain `setX().setY()` keeps monomorphic `this` across fluent calls — JIT optimizes well.

**Mentor note** — demo `Sub.clone(): Sub` vs `Base.clone(): this` — show that `Sub` case duplicates `clone` per subclass while `this` declares it once. Exercise: convert a `copy(): Base` to `copy(): this` and ask what breaks without `this`.

### 3) **this in methods vs arrows** (method this is late-bound and checkable via explicit this param; arrow this is lexically captured and immune to variance)

**Definition** — *Method* `m() { console.log(this); }` binds `this` at call time (depends on receiver) and is subject to `strictFunctionTypes` variance; *arrow field* `m = () => { console.log(this); }` captures `this` lexically at construction (same `this` forever) and is an instance property, not a prototype method.

**What problem it solves / history** — callbacks (`arr.forEach(obj.method)`) lost `this` when methods were detached — arrow fields fixed that by capturing, but cost per-instance allocation vs prototype sharing. TypeScript needed to let checkers prove or forbid `this` loss (`this: void`, `noImplicitThis`).

**Modern guidance** — as of TypeScript 5.9 era, prefer methods for normal members (prototype-shared, cheaper), arrow fields when the member is *passed* as callback without binding (event handlers, React `onClick = () => {}`). Annotate detached callbacks with `this: void` to prove no `this` reliance (see [3.1. this parameter](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>)), and keep `strictFunctionTypes` aware of method bivariance.

**Runnable example** — method vs arrow (good vs bad, `tsc --strict`):

```typescript
// good — method (prototype) vs arrow field (captured)
class Clicker {
  count = 0;
  // method — needs correct this at call site
  incMethod(): void { this.count++; }
  // arrow — this captured at construction, safe when detached
  incArrow = (): void => { this.count++; };
}
const cl = new Clicker();
// detached method loses this
const m = cl.incMethod;
// m(); // runtime TypeError or NaN — this undefined (strict mode)
// cl.incMethod.call(cl); // ok with explicit this
const a = cl.incArrow;
a(); // ok — arrow captured cl as this
console.log(cl.count); // 1 — arrow worked

// good — explicit this param on method proves requirement
class Repo2 {
  table = "users";
  find(this: Repo2, id: string): string { return `${this.table}:${id}`; }
  findLoose(this: void, id: string): string { return `loose:${id}`; } // guarantees no this use
}
function useRepo(cb: (id: string) => string): void { cb("u1"); }
const repo2 = new Repo2();
useRepo(repo2.findLoose); // ok — this:void proves detach-safe
// useRepo(repo2.find); // error TS2345 — find needs Repo2 this, not void

// bad — arrow field per-instance cost hidden
class Heavy {
  // 10 arrow fields = 10 closures per instance — prototype methods would share one function
  a = () => {};
  b = () => {};
  c = () => {};
}
// for 1M instances, 3M closures vs 3 prototype functions — measurable heap
```

```typescript
// good — choosing: method + bind vs arrow
class EventHandler {
  onEvent(this: EventHandler, e: string): void { console.log(this, e); }
}
const h = new EventHandler();
// element.addEventListener("click", h.onEvent.bind(h)); // bind solves detach for methods
// element.addEventListener("click", () => h.onEvent("click")); // arrow wrapper also safe
```

**Common confusion** — "arrow methods are cheaper — no bind" — per-call cheaper but per-instance more expensive (one closure per instance vs one prototype function). "methods and arrows are interchangeably typed" — methods are bivariant for compatibility, arrow fields are strict-function property-checked.

**Performance note** — method: one function per class (prototype), dispatched monomorphically; arrow field: one closure per instance (constructor allocation, `WeakMap` for `#private`-like if needed). For 100k instances with 2 arrow handlers, ~200k closures vs 2 prototype functions — profile in `Chrome DevTools` heap if arrow-heavy classes dominate.

**Mentor note** — demo detach loss with `setTimeout(obj.method, 0)` breaking `this`, then fix with arrow vs `bind` vs `this:void` annotation. Exercise: ask students to convert `onClick = () => { this.setState(...) }` to a method plus `bind` and discuss the threshold where arrow pays (callbacks stored long-term vs hot render loops).
