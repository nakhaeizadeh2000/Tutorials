## 2.3. Override and polymorphic this typing

An override annotation checks a subclass relationship. A self return type preserves the receiver's type through a method call. Neither proves that an implementation preserves behavior or that an arbitrary subclass can be reconstructed from the base constructor's arguments. Review the member relationship, returned value and construction contract separately.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named program in a fresh directory without tsconfig.json. Run `tsc --strict --noImplicitOverride --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. For intentional rejections, activate one marked line in a separate copy and replace --outDir dist with --noEmit. Runtime failures below are caught deliberately.

### 1) **Override intent and the abstract-hook exception**

The noImplicitOverride option requires an override annotation when replacing a concrete base implementation in the cases below. Implementing an abstract hook without that annotation is accepted. An explicit override still checks that a base member exists. The [option reference](https://www.typescriptlang.org/tsconfig/noImplicitOverride.html) explains rename drift; these local probes distinguish the abstract case from its concrete example.

Save `overrides.ts`:

```typescript
export {};
class Repo {
  save(item: string): string { return "base " + item; }
}
class UserRepo extends Repo {
  override save(item: string): string { return "user -> " + super.save(item); }
}
console.log(new UserRepo().save("Ada"));
// class MissingOverride extends Repo { save(item: string): string { return item; } } // TS4114.
// class Typo extends Repo { override saev(item: string): string { return item; } } // TS4113.

abstract class Job { abstract run(): string; }
class ConcreteJob extends Job { run(): string { return "done"; } }
console.log(new ConcreteJob().run()); // Accepted without override under this flag.

class RenamedRepo { persist(): string { return "persist"; } }
class StaleRepo extends RenamedRepo {
  save(): string { return "old save"; }
}
const stale = new StaleRepo();
console.log(stale.persist(), stale.save());
// class CheckedStale extends RenamedRepo { override save(): string { return "old save"; } } // TS4113.
```

The output is `user -> base Ada`, `done` and `persist old save`. Uncomment MissingOverride to observe TS4114 and Typo or CheckedStale to observe TS4113. StaleRepo.save is simply a separate method after the base rename. It is not an overload of persist. Calling persist therefore uses the inherited body, even though the old save still exists.

As another check, rename Repo.save to persist in a separate copy without changing UserRepo. Its explicit override is rejected; its super.save call also references a missing member. A keyword check cannot decide whether a valid new implementation preserves persistence, validation or error behavior. Test those semantic obligations separately.

### 2) **Fluent self returns and explicit copying contracts**

Returning the actual receiver is a straightforward way to fulfill a self return type. In the following fluent API, setName returns the same DogBuilder object, so its subclass method remains available. A fixed Base return would expose only Base members at the call site. The [self-type guide](https://www.typescriptlang.org/docs/handbook/2/classes.html#this-types) introduces this subclass-preserving relationship.

Copying is a different operation. The unsafe example casts this.constructor to a one-argument constructor although a subclass requires a collar too. Correct runtime constructor identity cannot supply that missing argument. The remedy below assigns copying to a concrete class whose required state is known.

Save `self-and-copy.ts`:

```typescript
export {};
class Builder {
  name = "";
  setName(value: string): this { this.name = value; return this; }
}
class DogBuilder extends Builder {
  collar = "";
  setCollar(value: string): this { this.collar = value; return this; }
}
const builder = new DogBuilder();
const configured = builder.setName("Rex").setCollar("red");
console.log("fluent:", configured === builder, configured.name, configured.collar);
// new Builder().setName("Rex").setCollar("red"); // TS2339: no subclass member.
// class InvalidSelf { copy(): this { return new InvalidSelf(); } } // TS2322: arbitrary subclass this.

class UnsafeAnimal {
  name: string;
  constructor(name: string) { this.name = name; }
  clone(): this {
    const Ctor = this.constructor as new (name: string) => this;
    return new Ctor(this.name);
  }
}
class UnsafeDog extends UnsafeAnimal {
  collar: string;
  constructor(name: string, collar: string) { super(name); this.collar = collar; }
  describe(): string { return this.collar.toUpperCase(); }
}
const broken = new UnsafeDog("Rex", "red").clone();
console.log("asserted copy:", broken instanceof UnsafeDog, broken.name, broken.collar);
try { broken.describe(); }
catch (error: unknown) {
  console.log(error instanceof TypeError ? "missing collar: TypeError" : "unexpected error");
}

abstract class Copyable { abstract copy(): Copyable; }
class Dog extends Copyable {
  name: string;
  collar: string;
  constructor(name: string, collar: string) { super(); this.name = name; this.collar = collar; }
  override copy(): Dog { return new Dog(this.name, this.collar); }
  describe(): string { return this.name + ":" + this.collar.toUpperCase(); }
}
const original = new Dog("Rex", "red");
const copy = original.copy();
console.log("explicit copy:", copy !== original, copy.describe());
// class MissingCopy extends Copyable {} // TS2515.
```

The output is `fluent: true Rex red`, `asserted copy: true Rex undefined`, `missing collar: TypeError` and `explicit copy: true Rex:RED`. The invalid self-return probe fails with TS2322: an arbitrary subclass receiver may have additional state, so a newly constructed base instance cannot meet every possible this type.

Dog.copy honestly returns Dog and supplies both constructor arguments. It does not promise to preserve an unknown further subclass. If another subclass adds required state, give it an explicit copying contract or factory and verify that state too. An abstract hook makes the obligation visible; its type alone still cannot prove correct copying behavior. For complex state decide deliberately which references are shared or copied, rather than describing any new instance as a deep clone.

### 3) **Static factories use a constructor receiver contract**

The special instance this type is not valid as a direct static create(): this return annotation. A generic static method can instead declare an explicit constructor receiver and return that constructor's result type. Its new () => T requirement matters: a subclass requiring arguments cannot use this zero-argument factory unchanged.

Save `static-factory.ts`:

```typescript
export {};
// class InvalidStatic { static create(): this { return new this(); } } // TS2526.
class Model {
  static create<T extends Model>(this: new () => T): T { return new this(); }
}
class UserModel extends Model { user = "u"; }
const user: UserModel = UserModel.create();
console.log(user.user, user instanceof UserModel);
class NeedsName extends Model {
  name: string;
  constructor(name: string) { super(); this.name = name; }
}
// NeedsName.create(); // TS2684: constructor receiver requires an argument.
```

This prints `u true`. The static method constructs through its runtime receiver; the explicit this parameter constrains that receiver for checking and erases. The method's generic T is independent of any class-level instance parameter. Static create(): this is a different, rejected spelling, not shorthand for the generic contract. Keep factories aligned with the arguments and invariants their target constructors require.

### 4) **Class callbacks: invocation and capture**

An ordinary method uses the receiver supplied by its call. An arrow field captures the instance when its initializer runs. An explicit method this parameter can require a receiver at checked call sites; it does not bind the function. The [receiver owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) develops call, apply, bind and standard-host limits; this example applies those distinctions to class members.

Save `receivers.ts`:

```typescript
export {};
class Counter {
  count = 0;
  implicit(): number { return ++this.count; }
  explicit(this: Counter): number { return ++this.count; }
  captured = (): number => ++this.count;
}
function invoke(callback: (this: void) => number): number { return callback(); }
const counter = new Counter();
try { invoke(counter.implicit); } // Accepted; the implicit method requirement is not enforced here.
catch (error: unknown) {
  console.log(error instanceof TypeError ? "detached: TypeError" : "unexpected error");
}
const explicit = counter.explicit; // Extraction alone is legal.
// explicit(); // TS2684: receiverless invocation.
// invoke(counter.explicit); // TS2345: explicit Counter requirement conflicts with void receiver.
console.log("remedies:", invoke(counter.captured), invoke(counter.explicit.bind(counter)),
  invoke(() => counter.explicit()));
const other = new Counter();
console.log("function identity:", counter.implicit === other.implicit,
  counter.captured === other.captured);
```

The output is `detached: TypeError`, `remedies: 1 2 3` and `function identity: true false`. A captured arrow, a bound method and a wrapper all preserve the intended instance here. The original method remains shared through the prototype; these two instances have different captured function values.

Receiver handling and parameter variance answer different questions. Under strictFunctionTypes, function-property parameter checking differs from method compatibility; arrows are not immune to variance. A this:void callback may still log or capture mutable outer state. For the full assignment-direction and method exception examples, use [callback variance](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>).

### 5) **Common confusion**

Override is erased and does not change runtime dispatch. A self return annotation does not bind this, construct a subclass or validate a copy. A fluent method can satisfy its contract by returning its actual receiver; an arbitrary constructor assertion cannot prove the same result. Static construction needs a constructor contract of its own. Finally, extracting an implicit method can be accepted even when its eventual invocation lacks the receiver it needs.

### 6) **Performance note**

The override keyword, explicit this parameters and return annotations erase. Returning this preserves an existing reference; the copy methods allocate and initialize objects. Prototype methods can share one function value across instances, while the arrow fields in the example produce different function values. Bound callbacks and wrappers also create callable values. No allocation sizes, speed ranking or optimization threshold was measured; choose the required lifetime and receiver behavior, then profile if function storage or copying is a demonstrated cost.

### 7) **Mentor note**

Ask why ConcreteJob compiles without override while MissingOverride fails, then rename a concrete base member and explain the resulting errors. For copying, add a required field to the subclass and require an observed value in the copy; instanceof alone is insufficient. Finally, distinguish extraction from invocation when reviewing explicit, implicit and captured callbacks. A sound review names both the checking contract and the operation that supplies the actual value.
