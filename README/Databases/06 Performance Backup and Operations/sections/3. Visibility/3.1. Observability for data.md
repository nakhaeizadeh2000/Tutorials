# 3.1. Observability for data

Watching databases with evidence: four signals on one dashboard, `pg_stat_*` views over guesses, and alerts firing on approach instead of arrival. Junior read: four queries, one dashboard, thresholds at 80%. Expert read: which signal predicts which incident, and why approach-alerts beat arrival-pages.

## 1) Four signals, one dashboard

### 1) **Definition** (the vital quartet)

*Bloat* (dead-tuple ratios per hot table — [1.2](<../1. Performance at scale/1.2. Vacuum and bloat.md>)); *cache* (buffer hit ratio — memory serving vs disk fetching); *connections* (counts by state — pool health vs leak signature); *slow queries* (threshold-logged shapes ranked by total time — [1.1](<../1. Performance at scale/1.1. EXPLAIN at scale.md>)). One dashboard, four panels — every data incident announcing itself in exactly one of them first.

### What problem it solves (history)

Single-signal monitoring (slow-query logs only — bloat/connection/cache incidents arriving unannounced: pool exhaustion discovered at "too many clients", cache collapse discovered at latency cliffs, bloat discovered at quarter-end slowdowns) left three incident classes permanently surprising (unwatched signals failing unwarned — pages without precursors, triage without baselines). Four signals cover the incident space (each major class announcing in its panel quarters early — precursors, not postmortems).

### Modern guidance

Dashboard all four per production database (panels built at provisioning — observability day-one, not post-incident); review weekly (trend walk per signal — stable vs climbing decided on history, never snapshots); extend per workload (replication lag where replicas exist, WAL growth where archiving runs, lock waits where contention concentrates — quartet plus topology-specific extras).

### Runnable example (good — all four signals, read live)

```bash
docker exec dbprobe psql -U postgres -tAc "SELECT round(100.0*sum(blks_hit)/NULLIF(sum(blks_hit+blks_read),0),1) || '% hit' FROM pg_stat_database;"
# 99.3% hit
docker exec dbprobe psql -U postgres -c "SELECT state, count(*) FROM pg_stat_activity GROUP BY state ORDER BY 2 DESC;"
#  state  | count
# --------+-------
#          |     5
#  active |     1
docker exec dbprobe psql -U postgres -tAc "SELECT relname, n_dead_tup FROM pg_stat_user_tables ORDER BY n_dead_tup DESC NULLS LAST LIMIT 3;"
# outbox|2
# racers|1
# bookings|1
```

Verified (PostgreSQL 16.15, docker): cache 99.3% (memory serving — healthy); connections 5 idle + 1 active (pool-shaped, no leak signature — total-below-max, idle-present); bloat top-3 named (outbox 2, racers 1, bookings 1 — small numbers, watchable trends). Slow-query signal rides threshold logs ([1.1](<../1. Performance at scale/1.1. EXPLAIN at scale.md>)'s funnel entry — logged shapes, ranked weekly). Four queries, full vital picture, thirty seconds.

### Common confusion

- **"four dashboards, one per signal"** — one dashboard, four panels (incident correlation needs adjacency — bloat climbing *while* cache ratio falls *while* slow queries multiply tells one story (growth outpacing maintenance); four separate dashboards tell four anecdotes. Correlation requires co-location — adjacency is the feature, consolidation the discipline).
- **"more signals, more safety"** — signals beyond the quartet pay diminishing returns (per-index hit rates, per-function timings — interesting occasionally, noisy always: alert fatigue desensitizing *all* signals including the vital four). Quartet mandatory (every database, day one); extras justified per incident-pattern (added after the second same-shaped surprise — evidence-gated instrumentation, never anticipatory).

### Performance note

Monitoring cost per signal (catalog queries per minute — microseconds each, negligible; dashboard storage per quarter — megabytes, lifecycle-managed); unmonitored-signal cost (incidents per class — hours with misdirection each, quarters of archaeology for trendless classes). Four signals cost minutes to build, pennies to run, incidents to prevent — fund permanently, staff rotationally.

### Mentor note

Onboarding dashboard tour (four panels, narrated per signal — "this climbs before slowdowns, this pages before exhaustion" — thirty minutes): mentees inheriting on-call with toured dashboards triage from baselines immediately (oriented, not searching); untoured successors discover panels mid-incident (navigation under pager pressure — worst classroom, highest tuition). Tour before rotation, always.

## 2) `pg_stat_*` over guesses

### 2) **Definition** (catalog evidence per symptom)

`pg_stat_user_tables` (per-table bloat/insert/update/delete/vacuum history — growth and maintenance truth); `pg_stat_database` (buffer hits, transactions, conflicts — instance truth); `pg_stat_activity` (per-backend state/query/wait — live truth: what runs *now*, waiting on *what*); `pg_stat_user_indexes` (index scans — usage truth from [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)). Symptoms map to views (slow → activity+statements; bloat → user_tables; connections → activity counts; cache → database ratios) — evidence per symptom, always guesses never.

### What problem it solves (history)

Guess-driven triage ("restart the database" as first response — unmeasured restarts clearing caches (warming penalties post-restart — slower after "fixing"), masking blockers (lock holders recycled, root cause unexamined — recurrence scheduled), destroying evidence (pg_stat_activity reset — forensic state wiped by the remedy)) mistook motion for progress (action-visible, information-destroying). Catalog-first triage reads state *before* acting (activity shows blockers — terminate *them*; stats show bloat — vacuum *it*; counts show leaks — fix *them*): action targeted, evidence preserved.

### Modern guidance

Read catalogs before acting (symptom → view → evidence → action — order fixed: guesses after evidence, never before); snapshot catalogs per incident (pg_stat_activity full dump at triage start — forensic baseline preserved past restarts; stats deltas across the incident — rates, not points); know the gaps honestly (`pg_stat_statements` absent here — shared_preload_libraries empty on dbprobe, verified in research: slow-query evidence via threshold logs instead — gap named, alternative wired, never hand-waved).

### Runnable example (good — symptom-to-view mapping, applied live)

```markdown
# "queries slowed over months" → pg_stat_user_tables (dead ratios per table — bloat evidenced: see part-1 probe)
# "too many clients" → pg_stat_activity counts by state (total-max + idle-zero + queue = leak signature, per [04/4.1])
# "cache collapse" → pg_stat_database hit ratio trend (99.3% now — falling trend pages before cliffs)
# "which query burns most?" → threshold logs ranked ([1.1] funnel — pg_stat_statements where installed, logs here)
```

### Common confusion

- **"pg_stat resets make history useless"** — stats reset on restart/crash (cumulative counters restarting — deltas across resets meaningless *unless* snapshotted externally: metrics pipelines scraping per minute — history in Prometheus/Datadog, not in Postgres). Scrape continuously (per-minute deltas — rates surviving restarts); read instant values for triage (now-state, always fresh). History external, triage internal — both, layered.
- **"pg_stat_statements is mandatory"** — statements extension is *valuable* (per-query stats — top-N by total time, server-side); threshold logging is *sufficient* (log-derived tallies — same ranking, log-shipped effort). Mandatory where query volume justifies extension ops (shared_preload + restart — change-managed); sufficient elsewhere (logs ranked weekly — zero server changes). Honest gap analysis per environment (absent here — named, alternative wired — the S6-research verdict, restated where it governs).

### Performance note

Catalog-read cost per query (microseconds — views over shared memory, non-blocking); metrics-scrape cost per minute (negligible — established practice fleet-wide); guess-triage cost per incident (wrong fixes applied — restarts, rewrites, scaling: motion without evidence, priced in downtime + data risk). Read first (free), act second (targeted) — order fixed permanently.

### Mentor note

Live-triage drills with catalogs open (slow query injected → mentee reads pg_stat_activity first — blocker named before action proposed): mentees evidencing-before-acting internalize catalog-first triage permanently (state before strategy — the senior sequence). Untrained triage acts first (restart-shaped reflexes — evidence destroyed with the symptom). Drill state-first quarterly; reflexes follow evidence.

## 3) Alerts on approach, not arrival

### 3) **Definition** (80% thresholds, paged precursors)

Alerts fire at 80% of danger (dead-ratio climbing toward impact, connections toward caps, cache ratio falling toward cliffs, disk toward full — precursors paged, arrivals prevented); pages name the trajectory (climbing-for-weeks vs spiking-now — trend-attached alerts route correctly: gradual → tune scheduled; spike → incident now); arrival alerts retained as backstops (100% still pages — defense in depth: approach primary, arrival secondary, never arrival-only).

### What problem it solves (history)

Arrival-only alerting (disk-full pages, connection-cap pages, bloat-impact pages — alerts coinciding with outages: responders starting behind (damage occurring *as* paged — recovery racing harm, mitigation simultaneous with diagnosis); no precursor history (trendless alerts — "when did this start?" unanswerable, prevention unplannable)) made every page an incident (alerts arriving with damage, not before). Approach alerts convert pages to tasks (precursor acknowledged in daylight — tuned calmly, never paged).

### Modern guidance

Threshold at 80% per finite resource (dead ratios, connection counts, disk, WAL volume, replication lag — approach values, reviewed per table/service); attach trends to pages (climbing-since timestamps — responders distinguishing gradual (schedule tune) from spike (incident now) at glance); retain arrival backstops (100% pages — secondary safety nets, rarely firing *because* approach alerts work — silence proving the system, not the monitoring).

### Runnable example (good — threshold shapes, stated)

```markdown
# approach alerts (precursors — tasks, not incidents):
# dead_ratio > 20% sustained 1h → tune vacuum (task — daylight, scheduled)
# connections > 80% of max → audit pools (task — arithmetic reviewed, per [04/1.1])
# cache hit < 98% trending down → investigate workload shift (task — plan review)
# disk > 80% → expand/clean (task — capacity planned, never surprised)
# arrival backstops (100% — incidents, rarely reached *because* approach works)
```

### Common confusion

- **"more alerts, more safety"** — alert volume desensitizes (fatigued responders acknowledging blindly — real pages missed among noise: safety *decreasing* past the attention budget). Approach alerts replace arrival noise (fewer, earlier, actionable — signal-to-noise *improved* by earlier firing: precursors investigated calmly beat outages paged frantically). Alert budgets per team (pages-per-week reviewed — noisy alerts tuned-or-removed quarterly).
- **"approach alerts fire too early"** — early firing *is* the design (precursors acknowledged in daylight — tuning scheduled calmly); mistuned early firing (flapping thresholds — noise without trajectory) gets tuned (hysteresis + trend-windows — firing on sustained approach, never blips). Early-and-right pages prevent; early-and-noisy pages fatigue — tune the discriminator, never silence the signal.

### Performance note

Alert-config cost (thresholds + trends per signal — minutes per quarter); approach-page cost (daylight tasks — scheduled, calm); arrival-page cost (incidents — downtime + trust + archaeology per occurrence). Approach alerting trades minutes-quarterly for incidents-never (asymmetric trade funding itself permanently — cheapest reliability practice after gates).

### Mentor note

Review alert history quarterly (pages per signal — approach-vs-arrival ratios: rising approach share means maturing observability (precursors caught); arrival-dominated history means threshold debt (tune earlier, add precursors). Ratios trend the *monitoring* itself (meta-observability — watching the watchers, cheaply, quarterly). Unreviewed alerting rots into noise or silence — review prevents both.
