# 4.1. Operations checklist (habits mentors insist on)

The three habits that keep database operations boring: measure before touching, prove recovery instead of backups, and observe the four signals. Junior read: extend the gate with three operations stages. Expert read: which incident each stage names, and why operations checks belong in CI rather than in runbooks nobody runs.

## 1) Measure before touching

### 1) **Definition** (evidence-gated changes)

Index, rewrite, and tuning changes land with before/after receipts (EXPLAIN plans, ANALYZE actuals, dead-ratio deltas — attached to the commit, reviewed as first-class content); unreceipted changes wait (pending-index files failing gate stage 60 — evidence absent where performance is claimed). Receipts precede merges; measurements precede prescriptions — always, no exceptions for seniority.

### What problem it solves (history)

Unmeasured performance work (indexes added on intuition — maintenance without benefit, net-negative shipped confidently; rewrites deployed on theory — new shapes, unknown plans, occasionally slower; tunables flipped on advice — global anxiety settings, fleet-wide side effects) optimized predictions instead of executions (effort spent, latency unchanged-or-worse, confidence unearned). Evidence gating converts performance work from hope to accounting (receipts per change — improvement proven or change reverted, no third state).

### Modern guidance

Attach receipts per change (before/after EXPLAIN for indexes — [1.1](<../1. Performance at scale/1.1. EXPLAIN at scale.md>)'s verified 250→1 pattern; dead-ratio deltas per vacuum tuning — [1.2](<../1. Performance at scale/1.2. Vacuum and bloat.md>)'s witnessed 9→0); gate unreceipted shapes (pending-index files failing stage 60 — structure reviewed before speed claimed); review receipts first (numbers before narrative — approvers reading plans before prose, every performance PR).

### Runnable example (good — the operations gate, verified)

```bash
#!/bin/bash
# operations gate: receipted indexes + restore proof + four signals
if ls gateops/pending-index.sql >/dev/null 2>&1; then exit 60; fi
grep -q "src:.*dst:" gateops/restore-proof.txt 2>/dev/null || exit 61
[ $(grep -c "" gateops/signals.md 2>/dev/null) -ge 4 ] || exit 62
echo OPS-GREEN
```

```bash
./gate6.sh; echo "exit=$?"
# exit=60        (gateops/pending-index.sql: unreceipted CREATE INDEX — evidence absent)
# (pending file receipted into plan-receipt.md and removed →)
# OPS-GREEN
# exit=0
```

Verified: stage 60 fires on the unreceipted index change (evidence absent — the gate as review assistant, not replacement); green when receipted-and-removed (plan-receipt.md carries before/after — the 769.59→4.31 shape from [1.1](<../1. Performance at scale/1.1. EXPLAIN at scale.md>), filed where future droppers read it).

### Common confusion

- **"gates slow performance work"** — gates *sequence* it (receipts attached — minutes per change; unreceipted work returned with the gate number, not debated). Slow is unmeasured rework cycles (deploy → doubt → revert → rethink — weeks per loop); gated work lands once (proven, attributed, trusted). Gates accelerate net velocity (fewer reversions) while appearing to tax gross velocity (receipts per change) — net wins, always.
- **"small indexes skip receipts"** — small indexes skip *ceremony* (lightweight before/after — two EXPLAIN lines, not full reports); no index skips *evidence* (receipts scale with change size — one line per small change, full analysis per structural one). Evidence proportional, never absent — the standard scales, never waives.

### Performance note

Gate cost per run: file checks (milliseconds) — cheapest stages after version prints. Unreceipted-change cost: net-negative indexes (maintenance without benefit — taxed writes, unsped reads, shipped confidently); unmeasured rewrites (unknown plans — possibly slower, deployed hopefully). Receipts cost minutes per change (attached once); reversions cost quarters (archaeology per regret — when was this added? why? — unanswerable without receipts).

### Mentor note

Require receipts in every performance PR ("show me before/after" — two EXPLAIN outputs, thirty seconds to verify): mentees internalize evidence-first tuning when reviewers ask consistently (three PRs and authors attach plans unprompted — the habit that ends hope-based optimization permanently). Receipts in commits also document *why* each structure exists (future droppers read before dropping — archaeology with answers).

## 2) Prove recovery, not backups

### 2) **Definition** (round-trip assertions)

Recovery proven per backup (dump → fresh target → restore → counts match — [2.1](<../2. Survival/2.1. Backups that restore.md>)'s verified 1/1 + 4/4): gate stage 61 asserts the proof artifact exists (restore-proof counts present — recovery evidenced, not hoped); RTO printed per rehearsal (dump-to-serving minutes — budgets evidenced against SLOs); unproven backups failing loudly (stage 61 red — missing proof attributed, not debated).

### What problem it solves (history)

Backup-green/restore-never pipelines (dumps accumulating — success measured in files written; first restore attempted at disaster — corrupt dumps, version skew, missing roles discovered under pager pressure: recovery latency unknown until needed most (RTO discovered live — hours vs assumed minutes); partial restores accepted blindly (counts unchecked — missing tables noticed by customers)) mistook backup existence for recovery capability (files ≠ recoverability — the theater [2.1](<../2. Survival/2.1. Backups that restore.md>) exists to close). Proof asserts capability (restored counts — recoverability witnessed per backup).

### Modern guidance

Assert proof artifacts per backup (restore-proof counts committed — stage 61 greens only on matched source/destination tallies); print RTO per rehearsal (minutes, trended — budgets evidenced against SLOs, drift visible); rehearse per tier (nightly automated round trips; weekly/monthly sampled + checksummed — coverage proportional to criticality, per [2.1](<../2. Survival/2.1. Backups that restore.md>) part 2).

### Runnable example (good — stage 61 asserting the verified round trip)

```bash
# restore-proof.txt (committed artifact of the verified [2.1] round trip):
# src:1 dst:1 src-orders:4 dst-orders:4
grep -q "src:.*dst:" gateops/restore-proof.txt 2>/dev/null || exit 61
```

Stage 61 greens on matched tallies (proof present — recovery evidenced this backup cycle); reds on absence (no proof committed — recovery hoped, build red until proven). The artifact outlives the session (committed per backup cycle — provenance queryable: which backup proved which counts, when).

### Common confusion

- **"dump logs prove backups"** — dump logs prove *dumping* (bytes written — necessary); restore proofs prove *recovery* (bytes reloadable + counts matching — sufficient). Necessary ≠ sufficient (the theater gap exactly — logs green, restores red on first attempt). Assert sufficiency (restore-proof counts), monitor necessity (dump-job health) — both layers, distinct stages.
- **"staging restores prove prod recovery"** — staging restores prove *procedure* (commands work — valuable); production restores need *production-shaped* rehearsals (volumes, sizes, versions matching — procedure *plus* scale). Procedure proven in staging (weekly); scale proven per tier (quarterly full-size rehearsals where RTO matters — RTO scales with size, small-proven ≠ large-proven).

### Performance note

Proof-artifact cost per backup (counts file — bytes, committed); rehearsal cost (reload minutes — automated, off-peak); unproven-backup cost (first-restore-at-disaster — hours with misdirection + data-loss windows per corrupt/partial backup). Proof cheap (committed counts), hope dear (disaster tuition) — assert per backup, rehearse per tier, sleep per night.

### Mentor note

Pair the first proof-failure deliberately (delete restore-proof.txt — watch stage 61 redden the build): mentees witnessing proof-absence block merges trust round trips permanently (absence visible beats absence assumed — evidence over exhortation, again). Unproven backups are wishes — teach wishing vs proving early, with the gate as examiner.

## 3) Observe the four signals

### 3) **Definition** (dashboarded vitals, gated presence)

Four signals dashboarded (bloat, cache, connections, slow queries — [3.1](<../3. Visibility/3.1. Observability for data.md>)): gate stage 62 asserts the signals *document* exists (four lines minimum — dashboard presence, not dashboard quality: existence gated mechanically, quality reviewed humanly); thresholds reviewed quarterly (80% approach values — tuned per table/service, never defaulted blindly); trends walked weekly (stable vs climbing decided on history — part of on-call handoff, not extra credit).

### What problem it solves (history)

Undashboarded databases (signals queryable but unviewed — `n_dead_tup` available, nobody looking; hit ratios computable, uncomputed; connection counts visible, unwatched; slow logs written, unread) failed unwarned in all four classes (bloat slowdowns, cache collapses, pool exhaustions, query regressions — each preceded by quarters of visible-if-watched trends, each discovered at impact). Presence-gating plus weekly walks converts unwatched-availability into watched-trends (incidents preceded by acknowledged precursors — tasks, not pages).

### Modern guidance

Document signals per database (four lines minimum — names, queries, thresholds: stage 62 asserts presence); dashboard from day one (panels built at provisioning — observability coeval with service, never retrofitted post-incident); walk weekly (trend review in on-call handoff — stable/climbing decided per signal per week; climbing triggers tuning tasks with dates, not pages with adrenaline).

### Runnable example (good — stage 62 asserting presence, verified)

```bash
# gateops/signals.md (four lines — the dashboard document, committed):
# bloat: n_dead_tup watched
# cache: 99.3% hit
# connections: counts by state
# slow: threshold logs ranked
[ $(grep -c "" gateops/signals.md 2>/dev/null) -ge 4 ] || exit 62
```

Verified: four lines present → stage greens (presence asserted — the document exists with all four signals named); fewer → red (signals undocumented — dashboard debt visible as build status, not discovered mid-incident). Quality reviewed humanly (thresholds sane? trends walked? — presence gated mechanically, wisdom reviewed culturally).

### Common confusion

- **"dashboards replace gates"** — dashboards *display* (trends visible — humans interpret); gates *enforce* (presence asserted — machines verify). Undashboarded gates pass blindly (stages green, nobody watching trends — proof without practice); ungated dashboards rot (panels unwatched — decoration, not observability). Presence-gated *and* trend-walked (machines + humans, each doing what the other can't).
- **"four signals suffice forever"** — quartet covers *classes* (bloat/cache/connections/slow — the vital signs); topology adds signals (replication lag, WAL growth, lock waits — per architecture, justified per incident-pattern). Quartet mandatory always (every database, day one); extras evidence-gated (added after the second same-shaped surprise — instrumentation earned, never anticipated).

### Performance note

Presence-gate cost per run (line counts — milliseconds); dashboard cost (panels built once, data flowing — pennies); trend-walk cost (minutes weekly — on-call handoff ritual). Unobserved-signal cost (incidents per class — hours with misdirection each, quarters of archaeology for trendless classes). Presence cheap, walks cheap, blindness dear — fund all three permanently.

### Mentor note

The graduation exercise for this domain: hand the mentee an unwatched database (no dashboard, no gates, no rehearsals) and gates 1–6. One hour to observed-everywhere: four signals dashboarded, proof artifacts committed, thresholds proposed with dates — each artifact citing its leaf. Fluency demonstrated, operations internalized, incidents prepaid for the team.
