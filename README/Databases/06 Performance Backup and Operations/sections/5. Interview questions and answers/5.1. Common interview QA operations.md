# 5.1. Common interview QA: operations

Canonical answers for the three operations questions every backend interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their numbers. Expert read: each answer runs evidence (verified plans, counts, gates) before conclusions — prediction first, output as confirmation.

## 1) "Queries slowed over months" — diagnose it

### 1) **Definition** (the three-suspect screen)

Gradual slowdown over months — screens for trend thinking: hires enumerate three suspects (bloat: dead ratios climbing; statistics: estimates rotted post-bulk; growth: data volume outgrowing plans), evidence each in order (n_dead_tup trends, ANALYZE-dated plans, row-count growth), and fix the evidenced one (vacuum/tune, ANALYZE, index — receipts attached per fix).

### What problem it solves (hiring signal)

Slowdown triage without trend data devolves to folklore (rewrites, restarts, scaling — motion without evidence, priced in downtime + data risk): candidates answering with suspect-enumeration-plus-evidence-per-suspect demonstrate measurement-first operations (months-scale thinking — trends, not snapshots); candidates answering with a favorite fix demonstrate heroics (occasionally right, usually wasteful).

### Modern guidance

Answer as differential diagnosis with the verified exhibits (bloat: 9 dead → VACUUM → 0 — witnessed; stats: 250→1 estimates + Bitmap→Index plan change, zero code — witnessed; growth: 50k-row fixture shape — volume named): suspect, evidence, fix, receipt — per suspect, in likelihood order (bloat first where updates churn, stats first post-bulk-loads, growth first where counts climbed).

### Runnable example (good — the differential, quoted)

```bash
# suspect 1 — bloat (verified live): txn_demo|9 → VACUUM → txn_demo|0
# suspect 2 — stats (verified live): rows=250 → ANALYZE → rows=1, cost 323.72 → 4.31
# suspect 3 — growth (verify per candidate: row counts over months — trend, not snapshot)
```

A hire narrates "bloat, stats, or growth — check dead ratios, check estimate-vs-actual, check row counts over time" before touching anything; the interviewer hears process, not prescription. Follow-up ("all three clean?"): connection/pool shape (checkout waits — [04/1.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/1. Drivers/1.1. pg Pool that serves.md>)) then cache shape (hit-ratio trend — [3.1](<../3. Visibility/3.1. Observability for data.md>)) — differential continued, never abandoned.

### Common confusion (in candidates)

- **"add indexes" as first move** — red flag: unevidenced indexing (writes taxed per index, storage doubled — net-negative additions shipped confidently). Strong candidates EXPLAIN first (naming the node), measure second (ANALYZE actuals), prescribe third (index *or* vacuum *or* ANALYZE per evidence). Sequence, not enthusiasm — always.
- **"months-long means data growth"** — yellow flag as sole theory: growth is *one* suspect (row counts confirm — trivially checkable); bloat and stats rot are time-correlated too (dead accumulating, distributions shifting — same timescale, different fixes). Single-suspect answers reveal impatience; differential answers reveal method.

### Performance note

Slowdown answers need the receipt habit (before/after numbers per fix — cost ratios, dead counts, actuals — committed with the change): numbers volunteered with sources (769.59→4.31, 9→0 — quoted above) beat numbers recited; ranges beat points. Evidence volunteered with sources beats evidence extracted.

### Mentor note

Mock with "p99 doubled since spring" — demand the three-suspect enumeration before any prescription ("bloat? stats? growth? — evidence per suspect, in that order"): mentees graduate when differentials precede prescriptions without prompting. Differential-first thinking transfers to every slow system (caches, queues, APIs — same method, different signals).

## 2) "Restore from last night" — walk it

### 2) **Definition** (the recovery screen)

"Primary died at 9am — walk me through restore from last night's backup" — screens for rehearsed recovery: hires narrate dump → fresh target → restore → counts-match (verified 1/1 + 4/4 this session), state RTO from rehearsal (minutes, measured — never estimated), and name PITR for intraday gaps (WAL replay to 08:59 — RPO priced honestly, never zero-claimed).

### What problem it solves (hiring signal)

Recovery narration separates rehearsed operators (round trips performed — counts quoted, RTO stated, gaps named: calm under pager pressure, steps ordered) from policy reciters ("nightly dumps, 30-day retention" — files undescribed, restores unwitnessed: confidence unbacked, first-restore-at-disaster guaranteed). The screen predicts on-call recovery quality directly.

### Modern guidance

Answer as the round trip with numbers (148KB dump → `restorecheck` → 1/1 + 4/4 → cleaned — quoted verbatim below), state RTO measured (rehearsal-timed minutes — budgeted against SLOs), extend to PITR for intraday loss (base + WAL replay to minute-precision — RPO seconds-to-minutes, honestly priced). Close unprompted with the schedule (nightly automated round trips — recovery proven within hours of taking, never hoped).

### Runnable example (good — the round trip, quoted)

```bash
# pg_dump -Fc → /tmp/shop.dump (148435 bytes)
# CREATE DATABASE restorecheck → pg_restore → counts:
# src:1 / dst:1  +  src-orders:4 / dst-orders:4  (matched — recovery proven)
# DROP DATABASE restorecheck + rm dump (hygiene — verified artifacts, cleaned fixtures)
```

A hire walks dump→target→restore→counts→clean without notes (rehearsed shape — practiced, not memorized); the interviewer hears procedure internalized (steps ordered, evidence per step, hygiene closed). Follow-up ("counts mismatch?"): stop the rollout (mismatch investigated — roles? versions? partial dump? — recovery blocked loudly, never shipped hopefully).

### Common confusion (in candidates)

- **"restore to production directly"** — red flag: restores land on *fresh* targets (isolated — production untouched until verified: counts matched, application smoke green, traffic cut over deliberately). Direct-overwrite restores gamble the only good copy remaining (failed restore onto live data — recovery destroying recoverability: the cardinal restore sin, never committed, never excused).
- **"RTO estimated from dump size"** — yellow flag: RTO measured per rehearsal (dump-to-serving stopwatch — timed, trended, budgeted); size-derived estimates ignore restore-phase variance (role creation, index rebuilds, WAL replay — unmeasured phases dominating real RTOs). Measured RTOs only (rehearsal-timed — estimates labeled as such, never quoted as budgets).

### Performance note

Recovery answers need RTO/RPO numbers (RTO minutes-measured, RPO seconds-priced — quoted per rehearsal, budgeted per SLO); round-trip counts (1/1, 4/4 — matched tallies, witnessed). Numbers volunteered with provenance (rehearsal-timed — this session's round trip) beat numbers recited; honesty about gaps (PITR unrehearsed-here — named, not hidden) outscores false completeness.

### Mentor note

Rehearse restores live per cohort (dump → scratch → counts — thirty minutes, recovery witnessed): mentees performing round trips trust backups structurally thereafter (proven, not hoped — the habit that generalizes to every backup system they'll ever own). Unwitnessed backups are wishes — teach wishing vs proving early, with the round trip as examiner.

## 3) "Postgres in Docker for prod?" — answer honestly (plus rapid-fire)

### 3) **Definition** (the container screen)

"Would you run Postgres in Docker in production?" — screens for honest trade-offs: hires answer yes-with-conditions (named volumes — addressable persistence, witnessed orphan lesson; files-plus-env config — reviewed deltas; `pg_isready` healthchecks — proof-based routing; backups off-host — volumes ≠ backups). Absolutists ("never" / "always") fail; conditionals pass with receipts.

### What problem it solves (hiring signal)

Container absolutism (never-Docker dogma from pre-volume eras, always-Docker enthusiasm from dev-compose comfort) reveals unexamined positions (defaults defended without evidence — production posture by fashion). Conditional answers reveal operated understanding (volumes named, orphans witnessed, healthchecks proven — production Docker *practiced*, not theorized).

### Modern guidance

Answer yes-with-three-conditions (named volumes — data addressable across recreates; config versioned — deltas reviewed, secrets environmental; healthchecks proving — isready-gated dependents, no sleeps); cite the witnessed lessons (anonymous orphans accumulating — named from day one; data+config co-located on volume — S5 settings surviving via PGDATA); close with backups-off-host (volumes persist lifecycles — dumps recover disasters: both mandatory, neither substituting).

### Runnable example (good — the evidence trio, quoted)

```bash
# volumes: anonymous orphans witnessed (7+ unnamed — named from day one thereafter)
# config: /var/lib/postgresql/data/postgresql.conf (auditable location — settings grep-able)
# health: pg_isready exit=0 (/var/run/postgresql:5432 - accepting connections — proof, not port)
```

### Rapid-fire drills (with answers)

1. **Seq Scan on 50k rows — verdict?** Check selectivity first (small result → index missing, add with receipts; full-table intent → scan correct) ([1.1. EXPLAIN](<../1. Performance at scale/1.1. EXPLAIN at scale.md>)).
2. **n_dead_tup climbing on hot table — action?** Tune per-table vacuum factors + confirm no long transactions pinning (evidence-ordered) ([1.2. Vacuum](<../1. Performance at scale/1.2. Vacuum and bloat.md>)).
3. **Dump exists, never restored — verdict?** Wish (round trip now — counts or it didn't happen) ([2.1. Backups](<../2. Survival/2.1. Backups that restore.md>)).
4. **`docker volume ls` full of hex names — meaning?** Anonymous orphans (name volumes; prune verified-unreferenced only) ([2.2. Containers](<../2. Survival/2.2. Postgres in containers.md>)).
5. **Cache hit 99%→91% in a week — action?** Workload-shift investigation (new shapes? eviction pressure? — trend-driven, not yet paging) ([3.1. Observability](<../3. Visibility/3.1. Observability for data.md>)).
6. **Gate exits 60 vs 61 vs 62 — meaning?** 60: unreceipted index (evidence); 61: unproven restore (capability); 62: undocumented signals (presence) ([4.1. Operations checklist](<../4. Important points to remember/4.1. Operations checklist habits mentors insist on.md>)).

### Common confusion (in candidates)

- **"managed Postgres ends this discussion"** — managed moves *execution* (patching, failover, snapshots automated — toil bought away); retention *verification* stays yours (restore tests scheduled, RTO asserted — [2.1](<../2. Survival/2.1. Backups that restore.md>)'s round trip against managed dumps, per quarter). Managed-unverified fails identically at restore time (provider green, recovery unproven — outsourcing execution, never assurance).
- **"containers are dev-only"** — containers are *lifecycle* tools (reproducible environments — dev *and* prod with named volumes + proven restores + isready gates); managed services are *toil* tools (outsourced operations — orthogonal axis). Dev-only vs prod-ready decided by volumes/backups/healthchecks (present → prod-worthy; absent → dev-only regardless of orchestrator).

### Performance note

Container answers need the co-location footnote (compute-near-data for latency — same host/AZ as apps; cross-AZ database traffic priced per GB per month — cloud bills read topology). Candidates volunteering placement economics (volume locality, AZ affinity, backup egress) show production thinking beyond configuration (topology *and* settings — the complete answer).

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly ops-health check. Drills 3 and 6 separate wishers (dumps, undocumented signals) from provers (round trips, gated presence); ask those first when time is short.
