# 2.1. Backups that restore

Proving recovery instead of hoping for it: dump/restore round trips with matching counts, rehearsed restores with measured RTO, and PITR named honestly with priced RPO. Junior read: back up, restore somewhere else, compare counts. Expert read: what "tested" means (RTO measured, not estimated), and where dumps end and WAL archiving begins.

## 1) Dump, restore, verify — the round trip

### 1) **Definition** (recovery proven, not taken)

`pg_dump -Fc` (custom-format logical backup — compressed, restorable selectively); `pg_restore` into a *fresh* database (never over live — restore target isolated, production untouched); row-count comparison per table (source vs restored — counts matching, content spot-checked: recovery *proven* per run, not assumed per schedule). The round trip is the unit: dumped, restored, verified — or it didn't happen.

### What problem it solves (history)

Backup theater (dumps scheduled, files accumulating, restores never attempted — success measured in files written, not recoveries proven) failed at the only moment backups matter (primary dead, restore attempted first time under pager pressure: corrupt dumps (unnoticed for months), version-mismatched restores (dump from 16, restore tool from 14 — format surprises), missing roles/extensions (restored schema referencing absent owners — half-recovered databases serving confusion)). Round-trip verification converts theater to recovery (each backup proven restorable within hours of taking, failures fixed calmly, never paged).

### Modern guidance

Dump per schedule (nightly full minimum — frequency from RPO math, per part 3); restore per backup (automated round trip into scratch — counts compared, mismatches paging *before* disaster, never during); retain per policy (grandfather-father-son or equivalent — retention documented, restores tested per tier, oldest tier verified readable, not merely present).

### Runnable example (good — the round trip, verified live)

```bash
docker exec dbprobe pg_dump -U postgres -Fc -f /tmp/shop.dump postgres
# -rw-r--r--  1 root  148435  /tmp/shop.dump   (148KB custom-format dump)
docker exec dbprobe psql -U postgres -tAc "CREATE DATABASE restorecheck;"
# CREATE DATABASE
docker exec dbprobe pg_restore -U postgres -d restorecheck /tmp/shop.dump
docker exec dbprobe psql -U postgres -tAc "SELECT 'src:' || count(*) FROM probe_items;"
# src:1
docker exec dbprobe psql -U postgres -tAc "SELECT 'dst:' || count(*) FROM probe_items;" -d restorecheck
# dst:1
docker exec dbprobe psql -U postgres -tAc "SELECT 'src-orders:' || count(*) FROM demo_orders;"
# src-orders:4
docker exec dbprobe psql -U postgres -tAc "SELECT 'dst-orders:' || count(*) FROM demo_orders;" -d restorecheck
# dst-orders:4
```

Verified (PostgreSQL 16.15, docker): dumped (148KB), restored into fresh `restorecheck` (isolated — production untouched), counts matching per table (1/1 probe_items, 4/4 demo_orders — recovery proven, not hoped). Scratch database dropped + dump removed after (hygiene — verified artifacts, cleaned fixtures: `DROP DATABASE restorecheck`, `rm /tmp/shop.dump` — CLEANED).

### Common confusion

- **"dump success means recoverable"** — dump success means *bytes written* (serializable snapshot taken — necessary); restorability means *bytes reloadable* (parseable by restore tools, roles/extensions present, version-compatible — sufficient, verified only by restoring). Bytes-written without reload-proof is the theater this leaf exists to close (round trip per backup — proof, not hope, always).
- **"custom format overcomplicates"** — custom (`-Fc`) enables selective restore (single tables — surgical recovery without full reloads), parallel jobs (`-j` — faster restores, RTO-relevant), and compression (smaller transfers — cheaper retention). Plain SQL dumps restore serially-or-nothing (all-or-nothing reloads — recovery granularity lost). Format choice is recovery-optionality choice — custom by default, plain where tooling demands text.

### Performance note

Dump cost per run (sequential read of live data — I/O competing with queries: off-peak scheduled, replica-sourced where available — primary impact minimized structurally); restore cost per rehearsal (scratch-database reload — minutes, automated); unverified-backup cost (first-restore-at-disaster — hours with misdirection *plus* data-loss window per corrupt/partial backup — unbounded, per occurrence). Round trips cost minutes per backup (automated); theater costs disasters (priced in downtime + data).

### Mentor note

Schedule the first restore rehearsal *with* the mentee present (dump, restore to scratch, compare counts — thirty minutes, recovery witnessed): mentees performing round trips trust backups structurally thereafter (proven, not hoped — the habit that generalizes to every backup system they'll ever own: files, snapshots, replicas — all unproven until restored). Unwitnessed backups are wishes — teach wishing vs proving early.

## 2) Untested backups are wishes

### 2) **Definition** (rehearsal as proof)

Restore rehearsal: scheduled, automated round trips (frequency matching backup frequency — every backup proven within hours, not quarters); RTO measured per rehearsal (dump-to-serving minutes, timed — recovery budgets evidenced, not estimated); failures fixed calmly (mismatched counts, missing roles, version skew — found in rehearsal logs, fixed in daylight, never paged). Tested means rehearsed-with-numbers (RTO printed per run — recovery proven on a schedule, not hoped on a policy).

### What problem it solves (history)

Policy-proven backups ("nightly dumps, 30-day retention" — documented, audited, green-checkmarked — restored never, RTO unknown, roles untested) failed first-restore under pressure (missing extensions aborting reloads midway — half-restored databases serving confusion; RTO discovered live (4 hours vs assumed 30 minutes — downtime quadrupling past SLOs mid-incident); partial restores accepted blindly (counts unchecked — missing tables noticed by customers, not operators). Rehearsals convert policy into proof (each backup restorable *demonstrably* — RTO known *numerically*).

### Modern guidance

Rehearse per backup tier (nightly → daily round trip automated; weekly/monthly → restore sampled + checksummed — coverage proportional to tier criticality); measure RTO per rehearsal (dump-to-serving stopwatch — RTO printed, trended, budgeted against SLOs); alarm rehearsal failures distinctly (backup-job red vs restore-job red — different severities, different owners: unwritten vs unrestorable — both paged, differently).

### Runnable example (good — the rehearsal shape, mirrored from the verified round trip)

```bash
# nightly rehearsal job (shape — commands verified above, schedule added here):
# 1. pg_dump -Fc → artifact (148KB-class for small DBs — size trended per run)
# 2. CREATE DATABASE restore_probe_$(date +%F) (fresh target per rehearsal — isolation)
# 3. pg_restore → probe (reload proven — version compatibility witnessed per run)
# 4. counts compare per table (1/1, 4/4 — mismatches paging before disaster)
# 5. DROP DATABASE + rm artifact (hygiene — verified artifacts, cleaned fixtures)
# 6. log RTO minutes (trended — budgets evidenced, SLOs honest)
```

### Common confusion

- **"restore tests risk production"** — rehearsals target *scratch* databases (fresh `restorecheck`-class targets — production untouched by construction: restores write to isolated namespaces, never live ones). Risk-free by topology (separate database — blast radius zero by design); risk*ful* is skipping (first-restore-at-disaster — blast radius unbounded, timing worst-case). Isolate targets, rehearse freely — safety structural, not careful.
- **"quarterly rehearsals suffice"** — rehearsal frequency matches *backup* frequency (nightly backups → nightly round trips — unproven windows measured in hours, never quarters; quarterly spot-checks supplement (oldest-tier readability — retention integrity), never substitute (fresh backups proven fresh). Provenance per backup (each dump restorable *demonstrably* within hours of taking).

### Performance note

Rehearsal cost per backup (reload + counts — minutes, automated, off-peak scheduled); unrehearsed cost per disaster (first-restore latency unknown — RTO discovered live: hours vs assumed minutes, plus partial-restore confusion per untested gap). Rehearsal economics overwhelmingly favor automation (minutes per backup, machines unattended) over hope (hours per disaster, humans paged).

### Mentor note

Pair the first rehearsal failure deliberately (corrupt a scratch dump — watch the round trip catch it calmly): mentees witnessing catches-in-daylight trust rehearsals permanently (proof beats policy — evidence over exhortation, again). Uncaught-by-rehearsal incidents get postmortemed as rehearsal gaps (coverage extended — the system learning, not blaming).

## 3) PITR named, not mythologized

### 3) **Definition** (honest point-in-time recovery)

PITR: base backup + continuous WAL archiving = restore to *any* moment (accidental `DROP TABLE` at 14:32 → restore to 14:31 — granularity per WAL segment, not per dump schedule). RPO priced honestly (WAL shipping lag — seconds-to-minutes of potential loss, measured, never zero-claimed); RTO measured per rehearsal (base-restore + WAL-replay time — timed, budgeted). Named components (base cadence, archive health, replay procedure — each monitored, each rehearsed), never mythology ("we have PITR" untested — hope wearing an acronym).

### What problem it solves (history)

Dump-only recovery (nightly snapshots — intraday work unrecoverable: 23 hours of orders lost per midnight failure, discovered per disaster; "PITR configured" untested (archive commands failing silently for months — WAL gaps discovered at replay time: recovery halting mid-history, unresumable, data ending at the gap)) mistook components for capability (archiving *configured* ≠ recovery *possible* — replay untested, gaps invisible, RPO fictional). Named-and-rehearsed PITR converts acronym to capability (replay proven per quarter — gaps alarmed per segment, RPO honest per measurement).

### Modern guidance

Archive continuously (`archive_command` shipping WAL per segment — gaps alarmed: unarchived segments paging within minutes, never discovered at replay); base regularly (weekly full minimum — replay distance bounded: recovery time proportional to WAL volume since base); rehearse PITR quarterly (restore-to-point on scratch — timestamp-targeted recovery proven, RTO/RPO printed per rehearsal); price RPO honestly (archive lag measured — seconds-to-minutes stated, zero never claimed).

### Runnable example (good — the components, named with honest scope)

```markdown
# PITR stack (named — components monitored, replay rehearsed; full replay drill owned by
# platform runbooks + Domain 06-adjacent ops practice, mechanism summarized honestly here):
# base: weekly pg_basebackup (full snapshot — replay start point, retained per policy)
# WAL: continuous archive_command shipping (per-segment — gaps alarmed within minutes)
# replay: restore base + replay to timestamp (accident at 14:32 → target 14:31 — granularity per segment)
# RPO: archive-lag seconds-to-minutes (measured, stated — zero never claimed)
# RTO: base-restore + replay minutes (timed per rehearsal — budgeted against SLOs)
```

Honest scope note: full PITR replay drills (archive setup + timed point-recovery) belong to platform runbooks with dedicated staging — this leaf names components, prices RPO/RTO, and prescribes rehearsal cadence; the *mechanism* beyond naming (this track teaches *usage*, and PITR operation at scale is platform depth — named here, rehearsed per runbook, never mythologized as "configured therefore capable").

### Common confusion

- **""PITR configured" means safe"** — configured-means-nothing-unrehearsed (archive gaps silent for months — the classic PITR-shaped outage: "we had archiving on" beside unrecoverable history). Safety means *replayed* (quarterly point-recoveries proven — gaps would have failed rehearsal loudly, fixed calmly). Configuration is intent; rehearsal is capability — audit capability, never intent.
- **"dumps plus WAL equals overkill"** — dumps (coarse recovery — nightly granularity, simple reloads) plus WAL (fine granularity — intraday precision, replay complexity) cover different loss windows (last-night vs last-minute — RPO tiers, priced separately). Either alone leaves a window uncovered (dumps: intraday loss; WAL-only: base fragility). Tiered recovery (dumps nightly + WAL continuously + rehearsals quarterly) covers both — priced per tier, never duplicated blindly.

### Performance note

WAL-archiving cost steady-state (segment shipping bandwidth — modest, monitored; archive storage growth — retained per policy, lifecycle-managed); replay cost per rehearsal (base-restore + log-replay minutes — quarterly scheduled); unarchived-gap cost (history ending at the gap — data unrecoverable past it, priced in permanent loss + trust). Archive continuously (cheap), rehearse quarterly (bounded), price RPO honestly (measured) — fund all three permanently.

### Mentor note

Whiteboard PITR as timeline (base snapshot → WAL segments → accident mark → recovery target — drawn per onboarding): mentees seeing time-as-recoverable-medium grasp RPO intuitively (loss window = accident-to-target distance, priced in minutes). Follow with "prove it" (quarterly replay drill scheduled before the whiteboard erases — naming without rehearsing is mythology with diagrams).
