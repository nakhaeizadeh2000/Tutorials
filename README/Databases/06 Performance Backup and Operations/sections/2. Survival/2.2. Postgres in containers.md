# 2.2. Postgres in containers

Running PostgreSQL under Docker honestly: named volumes for data, files-plus-env for config, and `pg_isready` healthchecks proving serving. Junior read: volume for data, env for secrets, healthcheck for routing. Expert read: what anonymous volumes taught this track twice, and why `pg_isready` beats TCP checks.

## 1) Data lives in volumes, never layers

### 1) **Definition** (persistence outside the container lifecycle)

PGDATA on a Docker volume (named: `pgdata:/var/lib/postgresql/data` — stable identity across recreates; never container layers: layered writes die with the container, copy-on-write penalizing database I/O patterns doubly). Image holds binaries + config defaults; volume holds the cluster (data, WAL, config overlays — everything irreplaceable, nothing rebuildable).

### What problem it solves (history)

Layer-stored databases (data inside writable container layers — `docker rm` deleting production: unrecoverable by design, discovered per cleanup; layer drivers slowing random writes 2–10× (copy-on-write per modified page — database I/O patterns, the worst case for overlay filesystems)) made every container operation a data operation (restarts safe, removals fatal — lifecycle confusion with permanent consequences). Volumes separate lifecycles (containers cattle — recreated freely; data pet — persisted deliberately).

### Modern guidance

Named volumes always (`pgdata` — stable names across recreates, backups targeting known sources, `docker volume ls` readable); never rely on anonymous volumes (auto-created per container — unnamed orphans accumulating per recreate, unmappable to services — this track's own lesson, witnessed below); never bind-mount PGDATA casually (host permission/SELinux/ownership pitfalls — named volumes dodge the userid-mapping class entirely; bind-mounts where backup tooling demands host paths, deliberately).

### Runnable example (good — this track's own volume lesson, verified live)

```bash
docker inspect dbprobe --format='mounts: {{json .Mounts}}'
# mounts: [{"Type":"volume","Name":"afc158ea...","Destination":"/var/lib/postgresql/data",...}]
docker volume ls | head -8
# local  9d719304...   (orphans — prior containers' anonymous volumes, unmappable)
# local  8529ac0b...   (each recreate minted another — unnamed accumulation, witnessed)
# local  afc158ea...   (current dbprobe's — live data, anonymous name)
```

Verified: the postgres image declares its `VOLUME` (auto-created per container — data survived *restarts* all track long: S1's restart-proof); container *removal* orphaned prior volumes (S4's disappearance lost the working set — new container, new anonymous volume, reseed required: removal without `-v` keeps bytes no service can find). Named volumes would have made recovery `docker run -v pgdata:...` (one flag — data reattached, no reseed). Anonymous volumes persist bytes; named volumes persist *addressability* — operations needs the latter.

### Common confusion

- **"volumes are backups"** — volumes are *persistence* (surviving container lifecycle — necessary); backups are *recovery points* (dumped, tested, retained off-host — [2.1](<./2.1. Backups that restore.md>)'s round trips: volume loss (host disk death — volumes die with hosts) needs backups, not more volumes). Persist with volumes (lifecycle); recover with backups (disaster) — different mechanisms, different moments, both mandatory.
- **"bind mounts perform better"** — modern volume drivers match bind performance (same kernel paths — the overlay penalty applies to *layers*, never to volumes-or-binds); binds win only tooling convenience (host-side backup agents, file inspection — deliberate choices, not performance). Choose volumes by default (permissions + portability), binds by tooling need (documented per mount).

### Performance note

Volume I/O ≈ host I/O (local driver — near-baremetal for database patterns); layered I/O degrades (copy-on-write per first-touch page — random writes multiplying I/O, the database-hostile shape). Anonymous-vs-named performs identically (same driver — the difference is operational (addressability), never mechanical); orphans cost disk silently (accumulating per recreate — `docker volume prune` scheduled with row-level care: prunes *unreferenced* volumes — verify references first, prune second, never automated blindly).

### Mentor note

Show `docker volume ls` on any long-lived Docker host together (orphan graveyard — unnamed volumes from forgotten containers): the authors of each orphan "knew" their data was "in Docker somewhere" (addressability absent — bytes present, services unable). Named volumes from day one (convention enforced in review — every database service names its volume, no exceptions): addressability designed, orphans never born.

## 2) Config ships as files and env

### 2) **Definition** (reviewable, versioned database configuration)

PostgreSQL settings travel as mounted config files (`postgresql.conf` deltas — versioned beside the Dockerfile, reviewed per change) plus environment (`POSTGRES_PASSWORD` at init, `PG*` vars per client tooling — secrets via secret managers in production, env files locally gitignored per [01/1.2](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.2. Connecting from Node.md>)). Tunables that mattered this track (`max_prepared_transactions = 10` via `ALTER SYSTEM` — [05/3.1](<../../../05 Transactions Consistency and Integrity/sections/3. Distribution/3.1. Distributed honesty 2PC and sagas.md>)'s witnessed enablement) live in versioned files, never in tribal runbooks.

### What problem it solves (history)

Console-tuned databases (`ALTER SYSTEM` + reload, unrecorded — settings drifting per host: staging tuned, production default (or vice versa); restarts reverting to image defaults silently (ephemeral config layered over persistent data — tuning evaporating per recreate, rediscovered per incident)) made configuration unrepeatable (works-tuned-here mysteries — settings present nowhere reviewable). Files-plus-env makes configuration convergent (same files, every deploy — drift detectable as diff, fixable by commit).

### Modern guidance

Mount config deltas (custom `.conf` over image defaults — deltas minimal, commented with rationale + measured effect); env for secrets-and-per-deploy values (passwords, hosts, ports — never baked into images: images portable, secrets environmental); `ALTER SYSTEM` sparingly (persists into PGDATA — survives recreates sharing the volume (useful), invisible to review (dangerous): record every ALTER SYSTEM in the versioned config with the same values — dual-recorded or eventually divergent).

### Runnable example (good — config located, verified live)

```bash
docker exec dbprobe psql -U postgres -tAc "SHOW data_directory;" -tAc "SHOW config_file;"
# /var/lib/postgresql/data
# /var/lib/postgresql/data/postgresql.conf
docker exec dbprobe psql -U postgres -tAc "SHOW max_prepared_transactions;"
# 10   (S5's ALTER SYSTEM persisted in PGDATA — present because the volume survived restarts;
#       reviewable nowhere in the repo — the dual-recording gap this leaf exists to close)
```

Verified: data + config co-located on the volume (surviving restarts — S5's setting intact across this session's operations); config file path known (auditable location — settings grep-able per incident). The gap named honestly: volume-persisted settings need repo mirrors (config files versioned — dual-recorded, reviewed; ALTER SYSTEM alone is console-tuning with extra steps).

### Common confusion

- **"env configures everything"** — env covers *a subset* (documented `POSTGRES_*` init vars + client `PG*` — a few dozen settings); `postgresql.conf` covers *everything* (hundreds of tunables — vacuum costs, planner constants, WAL behavior: files for depth, env for secrets-and-per-deploy). Env-only tuning plateaus early (the tunables that matter live in files — know both surfaces, use each for its scope).
- **"config in the image is reproducible"** — baked config is reproducible *until rebuilt* (Dockerfile edits → new layers → same values, verifiable); mounted config is reproducible *and reviewable per deploy* (same image, varying mounts — environment deltas visible without rebuilds). Mount deltas (reviewable), bake bases (stable) — split by change cadence (per-deploy vs per-release).

### Performance note

Config-file hygiene costs review minutes per change (deltas commented, effects measured); console-tuning costs drift incidents (unrecorded settings diverging per host — performance differing inexplicably across "identical" environments: hours per occurrence, misattributed to queries). Tunables with receipts (setting + measured effect + review) compound (fleet-wide improvements from one verified change); untracked tunables decay (restart roulette per host).

### Mentor note

Audit database config per quarter (dump effective settings — `SHOW ALL` diffed across environments: drift visible as text, fixed as commits): mentees performing config diffs learn environment-parity thinking permanently (identical-where-it-matters, varying-where-designed — parity as reviewed property, not hoped state). Drift found quarterly beats drift found paged — schedule the audit, skip the incident.

## 3) Healthchecks prove serving

### 3) **Definition** (routing on proof)

`pg_isready` in `HEALTHCHECK` (exit 0 accepting connections — schedulers route *on proof*, not on process existence); container `healthy` status gating dependents (app containers starting after db-healthy — ordering by readiness, not by sleep timers); liveness vs readiness split (process alive vs serving queries — distinct probes, distinct responses: unready sheds traffic, dead restarts).

### What problem it solves (history)

Sleep-ordered startups (`depends_on` without conditions + `sleep 10` — databases still initializing when apps connect: crash-loops on fresh deploys, green on restarts (timing-dependent correctness — works eventually, fails initially, flakes in CI); TCP-checked routing (port open ≠ serving — Postgres accepting sockets during crash recovery, refusing queries: traffic routed to unready backends — errors with healthy-looking targets). Proof-based routing (isready green → traffic flows) removes timing from correctness (ready means serving — verified, not hoped).

### Modern guidance

`pg_isready -U <user>` in HEALTHCHECK (interval 10s, timeout 3s, retries 3 — fast failure detection without flapping); dependents condition on healthy (compose `condition: service_healthy` — ordering declared, not slept); separate readiness from liveness (isready for routing; deeper query-probe for liveness where recovery differs — unready sheds, dead restarts: distinct signals, distinct automation).

### Runnable example (good — proof green, verified live)

```bash
docker exec dbprobe pg_isready -U postgres; echo "pg_isready exit=$?"
# /var/run/postgresql:5432 - accepting connections
# pg_isready exit=0
```

Verified: accepting connections (socket *and* server state — isready performs the handshake, not just the TCP dial: proof, not port-check). App containers gating on this signal start once — no sleeps, no crash-loop roulette, no CI flakes from boot races.

### Common confusion

- **"depends_on orders startup"** — plain `depends_on` orders *creation* (containers born in sequence — readiness unaddressed: database born, uninitialized, app connecting instantly — race preserved, merely sequenced). `condition: service_healthy` orders *readiness* (traffic/dependents gated on proof — race eliminated structurally). Creation order comforts; readiness order works — condition, never bare depends.
- **"TCP check suffices"** — TCP-open during crash recovery accepts-then-refuses (sockets up, queries down — routed traffic erroring against healthy-seeming targets: the gap between port and service, measured in 500s). `pg_isready` performs protocol handshake (server *answering*, not merely listening — proof depth matched to routing consequence).

### Performance note

Healthcheck cadence costs a handshake per interval (microseconds per 10s — negligible); sleep-based ordering costs boot latency per deploy (fixed sleeps — seconds wasted per start, crash-loops on slow boots — tail latency of deploys, unbounded); proof-based ordering costs nothing extra (checks already running — routing consumes existing signals). Readiness-gated starts are *faster* on average (no sleeps) *and* reliable (no races) — strictly dominant, adopt unconditionally.

### Mentor note

Ban `sleep` in compose files on sight ("what are we waiting for? — name the readiness signal" — sleeps replaced with conditions per instance): mentees internalize proof-based ordering when reviewers ask consistently ("prove ready, don't pause hopefully"). Sleep-free compose files read as engineering (signals wired); sleep-laden ones read as superstition (hopes timed) — review accordingly.
