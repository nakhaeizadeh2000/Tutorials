# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for operations. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the operations-vs-mechanics split that keeps ops knowledge in exactly one place per question.

## 1) Query, transaction, and access foundations (neighbor domains own the mechanics)

### 1) **Definition** (the ops/mechanics split)

*Query mechanics* (joins, plans, indexes — Domain 02, assumed readable), *transaction models* (lifecycles, levels, snapshots — Domain 05, assumed wired), *access mechanics* (pools, checkouts, migrations — Domain 04, assumed disciplined), *first contact* (CRUD, choosing, gates — Domain 01, assumed fluent). This domain *operates* what those domains *built*: plans sustained, versions vacuumed, dumps restored, containers run, signals watched.

### The assignments (with the exact targets)

- Foundations (CRUD/choosing/proving) → [01 Database Foundations](<../../../01 Database Foundations and Mental Model/README.md>). Every probe here assumes handshakes, parameters, and witnesses — no re-teaching, ever.
- Query depth (joins, aggregates, plans) → [02 Postgres Deep Dive](<../../../02 Postgres Deep Dive/README.md>). Operations sustains measured shapes; depth discovers them.
- Document depth (pipelines, modeling, writes) → [03 MongoDB Deep Dive](<../../../03 MongoDB Deep Dive/README.md>). Ops patterns transfer (funnel, vacuum-analogues, gates) with document spellings adapted per target.
- Access (pools, checkouts, migrations, retries) → [04 Access](<../../../04 Node.js Data Access Drivers and Pooling/README.md>). Gates 1–4 prove construction; gate6 proves operation — lineage, not duplication.
- Integrity models (ACID, levels, snapshots, distribution) → [05 Transactions Consistency](<../../../05 Transactions Consistency and Integrity/README.md>). Recovery replays committed state; durability tiers price standby survival — models assumed, operations added.
- Naming level (vacuum/backup/health as words) → [IT Vocabulary 05](<../../../../ITVocabulary/05 Data Databases and AI Vocabulary/sections/1. Data words/1.2. Database table query and index.md>) (words owned there; operations owned here).

### Common confusion

- **"operations subsumes mechanics"** — operations *sustains* mechanics (measured shapes kept fast, versions vacuumed, dumps restored — stewardship over time); mechanics *enable* operations (shapes to sustain, versions to vacuum, dumps to restore — capability at a point). Stewardship without capability is process without substrate (gates asserting nothing executable); capability without stewardship decays (unmeasured drift, untested restores — entropy, scheduled). Sustain what mechanics enables — both layers, always.
- **"one ops domain covers all stores"** — patterns transfer (funnel, gates, round trips — method portable); mechanics differ per store (vacuum vs compaction, WAL vs oplog, pg_dump vs mongodump — each verified per engine, never assumed across). Method once, mechanics per store — MongoDB-ops depth lands in its own right (future work named, not claimed).

### Mentor note

Teach mentees to read this page as a router: "mechanics" questions go to 01–05, "operations" questions stay here. The distinction resolves half of all ops debates before they start — most are mechanics-questions asked in ops-rooms ("which index?" during a backup-schedule review), or the reverse.

## 3) Design and mapping (planned siblings own the ends)

### 3) **Definition** (the ops/design/map split)

*Operations* (this domain: sustaining, recovering, containing, watching Postgres services) vs *modeling* (Database Design track: normal forms, capacity modeling, growth planning — planned sibling) vs *mapping* (ORM track: migration runners, query builders, observability hooks — planned sibling). Operations assumes modeled schemas (measured shapes exist to sustain) and precedes mapping judgment (raw operational literacy before generated-operations trust).

### The assignments

- Schema modeling (normalization, capacity models, growth plans) → Database Design track (planned sibling per root README — textual forward, no dead link by design).
- Object mapping (entities, migration runners, query telemetry) → ORM track (planned sibling per root README — textual forward, no dead link by design).
- Repository seams (operated stores behind policy) → [DesignPatterns 06/1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>) (seam owned there — sustained stores run behind it).

### Common confusion

- **"ops tooling belongs here"** — ops *discipline* belongs here (funnel, rehearsals, gates, thresholds — method); vendor *tooling* belongs to platforms (managed consoles, proprietary monitors — venues, not method). Method transfers across vendors (funnel anywhere — evidence per step); tooling varies per venue (console per provider — learned per job). Teach method (durable); reference tooling (perishable, versioned, linked never taught).
- **"sibling tracks duplicate this domain"** — siblings *consume* it (modeled schemas worth sustaining — design quality determining ops burden; mapped queries worth watching — generated shapes measured like hand-written). Quality upstream reduces toil downstream (modeled well → sustained cheaply; mapped observably → tuned evidently). Tracks compose (usage → design → mapping → operations sustained throughout).

### Mentor note

The one-sentence router for operations: "Mechanics questions go back (01–05), judgment waits (07), models live in siblings, *sustaining* stays here." Funnel/rehearsal/container/signal — the operations layer with its own craft, its own checklist, its own interview.
