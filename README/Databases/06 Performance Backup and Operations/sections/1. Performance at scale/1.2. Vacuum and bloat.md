# 1.2. Vacuum and bloat

Reclaiming dead tuples before they slow scans: bloat observed per table, autovacuum trusted generally and tuned per hot table, alarms set quarters before impact. Junior read: dead rows accumulate, vacuum cleans, watch the counter. Expert read: what stats snapshots hide, and which knobs turn per churn profile.

## 1) Dead tuples are deferred work

### 1) **Definition** (versions awaiting reclamation)

UPDATE appends new versions ([05/2.1](<../../../05 Transactions Consistency and Integrity/sections/2. Mechanisms/2.1. MVCC snapshots not locks.md>)); superseded versions linger as dead tuples (invisible to new snapshots, occupying pages — deferred cleanup, not free storage); vacuum reclaims (dead marked reusable — space recycled in-table, scans skipping freed pages thereafter). Bloat is *scheduled* cleanup (work deferred by design — MVCC's price, vacuum's job), never corruption.

### What problem it solves (history)

Vacuum-fearing operations (maintenance windows "too risky to touch" — dead tuples accumulating for quarters: sequential scans slowing per dead row, tables 3× live size, transaction-ID wraparound halting writes at the 2B-transaction limit unvacuumed — the doomsday the daemon prevents silently) mistook background maintenance for danger (action feared, inaction fatal). Routine vacuum converts bloat from incident to housekeeping (reclaimed continuously, monitored casually).

### Modern guidance

Watch `n_dead_tup` per hot table (witnessed below — dead counts queryable, trendable, alarmable); VACUUM deliberately where autovacuum lags (manual runs post-mass-operations — explicit reclamation, receipted); never disable autovacuum (unvacuumed tables bloat unboundedly *and* approach wraparound-halt — the daemon is load-bearing infrastructure wearing background-process clothes).

### Runnable example (good — bloat witnessed, reclaimed, verified live)

```bash
docker exec dbprobe psql -U postgres -tAc "SELECT relname, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'txn_demo';"
# txn_demo|9
docker exec dbprobe psql -U postgres -tAc "VACUUM txn_demo;" -tAc "SELECT relname, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'txn_demo';"
# VACUUM
# txn_demo|0
```

Verified (PostgreSQL 16.15): 9 dead tuples observed (update churn on `txn_demo` across this track's probes — versions superseded, awaiting reclamation); manual VACUUM reclaims to 0 (space reusable — scans skipping freed pages thereafter). Honest snapshot note: `pg_stat` counters update asynchronously (a same-second UPDATE showed 9→9 — stats snapshots lag real-time churn; trends over minutes, not point reads per statement, drive decisions).

### Common confusion

- **"dead tuples mean corruption"** — dead tuples mean *history* (superseded versions awaiting reclamation — normal MVCC operation: every UPDATE creates one by design). Corruption reads wrong answers (checksums failing, constraint violations on valid writes — integrity breaks, pages 0-7-0-0); bloat reads slowly (correct answers, more pages — performance degrades, integrity intact). Bloat alarms performance reviews; corruption pages integrity — different severities, different responses.
- **"VACUUM locks tables"** — plain VACUUM runs *concurrently* (reads/writes proceeding — brief locks at start/end only, production-safe routinely); VACUUM FULL rewrites under exclusive lock (downtime-shaped — space returned to OS at access cost: reserved for one-time reclaims post-mass-delete, per [05/2.1](<../../../05 Transactions Consistency and Integrity/sections/2. Mechanisms/2.1. MVCC snapshots not locks.md>) part 2). Routine vacuum never blocks; FULL always does — choose per occasion, never by habit.

### Performance note

Bloat cost per scan (dead tuples read-and-discarded — sequential scans slowing linearly with dead fraction: 3×-bloated tables scanning 3× pages for live rows); vacuum cost (I/O + CPU background — throttled by cost settings, pausable, schedulable — pennies per reclaimed page); unvacuumed cost (bloat unbounded + wraparound halt at 2B unvacuumed transactions — writes stopping fleet-wide: the doomsday vacuum prevents silently). Reclaim routinely (daemon + deliberate runs); alarm early (dead-ratio thresholds — part 3).

### Mentor note

Show `n_dead_tup` live per cohort (query before/after a bulk UPDATE + VACUUM — three commands, bloat witnessed appearing and vanishing): version-churn made visible converts vacuum from background mystery to foreground habit (touched once, understood permanently). Follow with "which of *our* tables churn hottest?" (their service's write patterns — monitoring targets chosen, not assigned).

## 2) Autovacuum tuned per hot table

### 2) **Definition** (daemon defaults plus per-table deltas)

Autovacuum daemon on (verified `on` below — background workers triggering per scale factors: `autovacuum_vacuum_scale_factor = 0.2` (vacuum past 20% dead + threshold), `autovacuum_analyze_scale_factor = 0.1` (analyze past 10% churn)); per-table storage parameters overriding (hot tables: lower factors — aggressive cleanup where churn concentrates; cold tables: defaults — daemon economics preserved). Defaults for the fleet, deltas for the hot.

### What problem it solves (history)

One-size vacuum (defaults for 10-row config tables *and* 10M-row event streams — hot tables outrunning daemon triggers (bloat accumulating between too-rare runs — the 20% of millions is hundreds of thousands of dead tuples per cycle); cold tables vacuumed pointlessly (churn-free maintenance I/O — harmless but noisy in logs/monitoring)) mistook uniformity for simplicity (same settings everywhere — simple to state, wrong per workload). Per-table deltas right-size cleanup (hot aggressive, cold default — maintenance proportional to churn, never uniform).

### Modern guidance

Trust defaults initially (daemon on, factors standard — verified below; sized for general workloads — overrides earned, not anticipated); tune hot tables on measured bloat (`n_dead_tup` trends per table — scale factors lowered where dead accumulates between runs: `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.05)` with the trend attached as justification); never globally aggressive (fleet-wide low factors — vacuum I/O competing with queries continuously: tuning is per-table triage, not global anxiety).

### Runnable example (good — daemon verified, knobs named)

```bash
docker exec dbprobe psql -U postgres -tAc "SHOW autovacuum;" -tAc "SELECT name, setting FROM pg_settings WHERE name IN ('autovacuum_vacuum_scale_factor','autovacuum_analyze_scale_factor');"
# on
# autovacuum_analyze_scale_factor|0.1
# autovacuum_vacuum_scale_factor|0.1
```

Verified: daemon on (background maintenance running — the default protecting every table silently); factors 0.2/0.1 (vacuum past 20% dead, analyze past 10% churn — thresholds naming exactly when the daemon acts). Hot-table delta shape (documented, applied where trends demand): `ALTER TABLE hot_events SET (autovacuum_vacuum_scale_factor = 0.05)` — aggressive where churn concentrates, justified by trend, reviewed per quarter.

### Common confusion

- **"autovacuum causes load spikes"** — autovacuum *throttles* itself (cost-based delays — `autovacuum_vacuum_cost_delay/limit` pacing I/O: background by construction, pausable, schedulable); unthrottled manual VACUUMs spike harder (foreground I/O unpaced — the cure worse than the daemon). Spikes trace to manual full vacuums or cost-limit misconfiguration (tuned per evidence — daemon blamed rarely, correctly almost never).
- **"disable autovacuum on bulk loads"** — disabling *delays* cleanup (bloat accumulating through the load — then demanding catch-up vacuum anyway, plus wraparound-age advancing unopposed); tuning *schedules* it (cost limits relaxed off-peak — faster background cleanup without foreground contention). Disable never (wraparound riskNearby uncompromising — 2B-transaction halt); tune always (knobs exist precisely for load-shaped maintenance).

### Performance note

Daemon overhead steady-state (throttled background I/O — single-digit percent, pausable); per-table deltas cost review minutes quarterly (trend-attached justifications — tuning with receipts); disabled-daemon cost (bloat unbounded + wraparound halt — fleet-stopping, boarding-pass-priced). Defaults + deltas + reviews: free baseline, cheap tuning, no doomsdays — fund all three permanently.

### Mentor note

Review autovacuum settings per schema review (defaults verified on, hot tables justified deltas attached — two checks, seconds): mentees internalize maintenance-as-design when reviewers ask consistently ("churn profile? — show me the factors"). Background daemons stay background *because* someone reviews their settings — attention scheduled, incidents unscheduled.

## 3) Bloat alarms before impact

### 3) **Definition** (dead-ratio thresholds)

Alarm on dead-tuple ratio (dead ÷ (live + dead) per hot table — 20%+ warning, higher paging — visibility quarters before slowdown); trend over snapshots (point reads lie — stats async per part-1 note; weekly ratios revealing growth *rates*: stable ratios (vacuum keeping pace — healthy), climbing ratios (vacuum outpaced — tune or investigate long transactions pinning cleanup)).

### What problem it solves (history)

Threshold-less bloat (monitored nowhere — discovered via slowdown: sequential scans degrading per dead row over quarters, "queries slowed over months" incidents with quarters of archaeology (when did it start? — unknowable without history)) priced diagnosis in quarters (trendless alerts firing only at impact — too late for cheap fixes, perfectly timed for expensive ones). Ratio alarms with history convert impact-discovery into trend-observation (quarters of warning, minutes of tuning).

### Modern guidance

Alarm dead-ratio per hot table (20% warning / 40% page starter — tuned per table criticality); retain ratio history (weekly samples — growth rates visible: stable vs climbing decided on trends, never snapshots); pair with long-transaction alarms (`idle_in_transaction` age — snapshot-pinning blockers surfaced distinctly from churn-bloat: different causes (open transactions vs write storms), different fixes (kill/fix holders vs tune vacuum)).

### Runnable example (good — the ratio query, reusable)

```sql
-- dead-ratio per table (shape — run weekly, trend the output):
SELECT relname, n_live_tup, n_dead_tup,
  round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables ORDER BY dead_pct DESC NULLS LAST;
-- witnessed live shape: txn_demo|…|9 (dead present — reclaimed to 0 above via VACUUM)
```

### Common confusion

- **"alarm absolute dead counts"** — absolute counts mislead across sizes (9 dead on a 2-row table: 82% bloat, alarming; 9 dead on 50k rows: noise). Ratios normalize (dead ÷ total — size-independent severity); absolutes contextualize (total dead bytes for capacity planning — different question, different metric). Ratio alarms, absolute reports — each metric its job.
- **"one threshold fleet-wide"** — hot tables tolerate less bloat (heap scans per query — ratio directly taxing hot paths: tighter thresholds); cold/archival tables tolerate more (rarely scanned — bloat harmless until touched). Thresholds per table criticality (hot tight, cold loose — reviewed with the table, not the fleet).

### Performance note

Monitoring cost per table (one catalog query weekly — free); threshold tuning cost (minutes per hot table quarterly — reviewed with trends); unmonitored-bloat cost (slowdown discovered at impact — quarters of archaeology + emergency vacuum windows + trust repair). Visibility quarters-early for minutes-quarterly — the cheapest observability in data operations, funded permanently.

### Mentor note

Assign bloat-watch per service (dead-ratio dashboard panel per hot table — owned, reviewed weekly): mentees owning panels learn maintenance cadence kinesthetically (trends watched, tunes proposed, alarms acknowledged — operations as gardening, not firefighting). Unowned panels rot (dashboards nobody reads — decoration, not observability); ownership converts decoration to discipline.
