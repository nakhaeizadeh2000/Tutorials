# 1.1. EXPLAIN at scale

Keeping queries fast as tables grow: the slow-query funnel, statistics freshness, and worst-first prioritization. Junior read: log slow queries, EXPLAIN the top one, fix, re-measure. Expert read: where estimates rot and how ANALYZE resurrects them, with a live 250-to-1 correction.

## 1) Slow-query pipeline, not slow-query heroics

### 1) **Definition** (the ordered funnel)

Slow-query handling as pipeline (log → rank by total time → EXPLAIN top query → index-or-rewrite → re-measure with ANALYZE): each stage feeding the next, evidence flowing one direction. Log identifies candidates (`log_min_duration_statement` — thresholded query logging, per [3.1](<../3. Visibility/3.1. Observability for data.md>)); ranking prioritizes (total time = mean × calls — frequency-weighted pain, not slowest-single); EXPLAIN diagnoses; fixes land with receipts; re-measurement closes the loop.

### What problem it solves (history)

Heroic query tuning (senior called in, favorite query rewritten from experience, shipped unmeasured — occasionally faster, sometimes slower, always unattributed) optimized anecdotes (loudest complaint, not costliest query — attention allocated by volume of voice, not volume of time). The funnel allocates attention by total time (measured pain ranked — worst first, always): heroics become process (any engineer runs the funnel; juniors fix senior-slowed queries with receipts).

### Modern guidance

Log beyond a threshold (`log_min_duration_statement = 100ms` starter — slower than OLTP, faster than reports — tuned per workload); rank weekly (total-time top-10 reviewed — new entries investigated, known entries tracked); funnel per candidate (EXPLAIN → fix → ANALYZE-prove — no stage skipped: un-EXPLAINed fixes are guesses wearing confidence, unproven fixes are hopes wearing commits).

### Runnable example (good — the funnel stages, named)

```markdown
# funnel per slow shape (the discipline — live receipts in parts 2–3):
# log: log_min_duration_statement flags p99-breaching shapes ([3.1] owns the threshold)
# rank: total-time top-N (frequency × mean — worst first, always)
# diagnose: EXPLAIN (+ ANALYZE actuals — [02/2.2] method, applied at scale here)
# fix: index-or-rewrite with before/after receipts (committed with the change)
# re-measure: ANALYZE-proven improvement (loop closed — funnel drained, next candidate)
```

### Common confusion

- **"one slow query, drop everything"** — single slow queries matter by *total time* (rare-slow: deprioritized behind frequent-moderate — total-time ranking, not max-latency ranking). Loudest single incident ≠ costliest query (outage-shaped slowness triaged as incidents — [track triage habits]; funnel-shaped slowness triaged as process — this leaf). Triage shapes differ; runbooks differ accordingly.
- **"funnel too slow for startups"** — funnel stages scale down freely (threshold + eyeball top-3 + EXPLAIN one query — fifteen minutes weekly): the pipeline is proportionate by construction (effort per candidate constant, candidates ranked so effort lands where pain lives). Skipping the funnel saves minutes and spends quarters (unmeasured drift compounding silently — small teams discover at scale-up, painfully).

### Performance note

Funnel economics per quarter (hourly reviews + per-fix receipts — bounded process cost) against drift economics (unmeasured slowing compounding per deploy — latency creeping per quarter, discovered at SLO breach with quarters of archaeology). Process cost linear and small; drift cost superlinear and unbounded — fund the funnel permanently, staff it rotationally.

### Mentor note

Run the funnel live per cohort (slowest query on staging — log, rank, EXPLAIN, fix, prove — one hour, end to end): mentees performing the full loop internalize measurement-first tuning permanently (evidence per step beats heroics per incident — culture formed by witnessed payoff, not policy). Quarterly funnel reviews thereafter (top-N walked together — team-wide latency literacy, compounding).

## 2) Estimates rot, statistics refresh

### 2) **Definition** (planner truth maintenance)

The planner decides from statistics (value distributions sampled by `ANALYZE` — estimates per predicate: rows=250 predicted); data evolves past samples (bulk loads, purges, distribution shifts — estimates rotting while data moves); `ANALYZE` refreshes (re-sample → estimates corrected → plans re-chosen: maintenance, not optimization). Rotten estimates misplan (Bitmap Heap Scan where Index Scan suffices — cost 323 vs 4, same query, stale truth).

### What problem it solves (history)

Stale-statistics incidents (bulk-loaded tables planned on empty-table samples — sequential scans chosen for indexed shapes, bitmaps where plain seeks win: performance cliffs appearing *without code changes* (deploy green, data shifted — "nothing changed" incidents with everything different underneath)) misdiagnosed as code regressions (queries rewritten, indexes added blindly — fixes for a statistics problem wearing query costumes). `ANALYZE` after bulk operations prevents the class (samples current — plans correct — no code touched, nothing "fixed" because nothing broke).

### Modern guidance

ANALYZE after bulk loads/purges/backfills (explicit statement post-job — statistics current before traffic meets new data, never after); trust autovacuum's auto-analyze generally (daemon refreshing on churn thresholds — background maintenance, monitored not managed); refresh manually where autovacuum lags (massive single-shot loads outpacing daemon triggers — explicit ANALYZE in the job, receipted in its logs).

### Runnable example (good — 250-to-1 correction, verified live)

```bash
# before ANALYZE (fresh 50k-row load, stale samples — recreated fixture, PG 16.15):
docker exec dbprobe psql -U postgres -tAc "EXPLAIN SELECT * FROM perf_events WHERE kind = 'purchase';"
#  Bitmap Heap Scan on perf_events  (cost=6.23..323.72 rows=250 width=44)
#    Recheck Cond: (kind = 'purchase'::text)
#    ->  Bitmap Index Scan on perf_events_kind_idx  (cost=0.00..6.17 rows=250 width=0)

docker exec dbprobe psql -U postgres -tAc "ANALYZE perf_events;"
# ANALYZE
docker exec dbprobe psql -U postgres -tAc "EXPLAIN SELECT * FROM perf_events WHERE kind = 'purchase';"
#  Index Scan using perf_events_kind_idx on perf_events  (cost=0.29..4.31 rows=1 width=18)
#    Index Cond: (kind = 'purchase'::text)
```

Verified: estimates 250 → 1 (truth restored — one purchase exists, planner now knows); plan shape Bitmap Heap → plain Index Scan (simpler access, cost 323.72 → 4.31 — two orders of magnitude on paper, sub-millisecond both in practice at this scale); zero code changed (no query rewritten, no index added — statistics maintenance as the *entire* fix).

### Common confusion

- **"ANALYZE optimizes queries"** — ANALYZE *informs* the planner (samples refreshed — decisions improved where data shifted); it optimizes nothing directly (no indexes built, no queries rewritten — truth maintenance, not tuning). Expecting speedups from ANALYZE misunderstands the mechanism (correct plans, not faster plans — speed follows correctness of choice, occasionally dramatically as above, incidentally not causally).
- **"autovacuum covers bulk loads"** — autovacuum triggers on *churn thresholds* (inserts/updates/deletes counted — massive single transactions tripping analysis late or post-traffic: new data queried under old samples meanwhile). Bulk jobs ANALYZE explicitly (job step, receipted — deterministic freshness beats daemon heuristics for step-function data changes, always).

### Performance note

ANALYZE cost per table (sample scan — seconds on millions of rows, scheduled off-peak or post-job); stale-statistics cost (misplanned queries per second until refresh — 323-vs-4 cost ratios executing continuously: compute burned per query, latency taxed per request). Refresh economics overwhelmingly favor explicitness (seconds per bulk job vs elevated cost per query until daemon catches up — fund the statement, skip the incident).

### Mentor note

The before/after ANALYZE demo (stale plan → ANALYZE → corrected plan — three commands, cost collapsing live): mentees watching statistics maintenance fix performance without touching code recalibrate "optimization" permanently (truth maintenance as performance work — unglamorous, decisive). Add "ANALYZE after bulk ops" to every data-job template (one line preventing the class structurally).

## 3) Worst query first, always

### 3) **Definition** (total-time prioritization)

Optimization ordered by total time (mean latency × call frequency — costliest shape first, tail curiosities last): the top-ranked query earns engineering (EXPLAIN → fix → prove — full funnel); rank 50 earns nothing (opportunity cost exceeding conceivable gain — attention finite, ranked allocation optimal). Worst-first is resource allocation (engineering hours where time burns), not perfectionism (every query fast — unbounded cost, diminishing returns).

### What problem it solves (history)

Tail-chasing optimization (exotic 0.1% queries tuned lovingly — engineers optimizing interesting problems while the top-3 shapes burn 90% of database time: toil theaters with flamegraphs, latency unchanged quarter after quarter) misallocated the scarcest resource (engineering attention — spent where curiosity led, not where time burned). Total-time ranking redirects attention structurally (funnel order, not fascination order — boredom-tolerant process beating curiosity-driven heroics).

### Modern guidance

Rank by total time weekly (pg_stat_statements where available — else log-derived tallies: threshold logs aggregated — method varies, ranking invariant); fix top-1 fully before glancing at top-2 (completed improvements compound — half-fixed top-3s sum to nothing measurable); re-rank post-fix (ranks shift as winners improve — the funnel re-sorted per cycle, attention following pain dynamically, never statically).

### Runnable example (good — the ranking habit, narrated)

```markdown
# weekly review (shape — tooling per [3.1], judgment here):
# 1. checkout_total p50 40ms × 2M calls/day = 22h/day DB time → EXPLAIN → missing compound → fix → prove
# 2. nightly_report 90s × 1 call/day = 90s/day → scheduled, bounded, accepted (not fixed — ranked below #1 by 880×)
# 3. exotic_geo 800ms × 12 calls/day = 10s/day → ignored deliberately (documented ignore — attention finite)
# fixed #1 fully (22h → 3h/day) before glancing at #2 (ranking honored — heroics declined, process won)
```

### Common confusion

- **"slowest query first"** — slowest *single* (max latency — often rare/edge: pathological inputs, cold caches — fixing helps outliers, not totals); costliest *total* (mean × frequency — where time actually burns). Max-latency ranking optimizes anecdotes (dramatic, unrepresentative); total-time ranking optimizes bills (boring, decisive). Rank totals, triage maxes as incidents (outlier spikes paged, not funneled).
- **"everything must be fast"** — everything must be *bounded* (timeouts, budgets — worst cases contained); speed investment follows rank (top shapes optimized, tail accepted with bounds). Unbounded perfectionism (every query tuned — cost infinite, returns diminishing past rank ~5) vs bounded adequacy (top fixed, rest budgeted — finite cost, decisive returns). Budget tails, fix heads.

### Performance note

Prioritization ROI per cycle (top-1 fix ROI typically 10–100× tail-fix ROI — attention allocated by rank pays superlinearly); re-ranking cost (minutes weekly — tally review, order refreshed). Unranked optimization ROI (effort scattered — mean return per hour a fraction of ranked — heroics taxing teams in opportunity cost, invisible on any balance sheet except velocity).

### Mentor note

Publish the weekly top-N with owners (ranked list, named improvers, receipts attached — latency accountability made visible): teams internalize total-time thinking when rankings are public (nobody wants their query topping the board two weeks running — social accountability compounding process discipline). Celebrate rank-drops (top-1 fixed → parade the receipt — improvement culture, visibly rewarded).
