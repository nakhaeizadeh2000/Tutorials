# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for Postgres depth. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the query-depth vs operation-vs-theory split that keeps SQL knowledge in exactly one place per question.

## 1) Foundations and drivers (neighbor domains own the ends)

### 1) **Definition** (the depth sandwich)

*First contact* (CRUD, parameters, witnesses, choosing — Domain 01, assumed fluent) below; *drivers and pooling* (pg pools, checkout discipline, migrations — Domain 04, planned) above. This domain owns the *middle*: query depth (joins, aggregates), protected shapes (schema, constraints, indexes), and atomic units (transactions basis). Questions about first queries go back; questions about pools go forward; questions about depth stay here.

### The assignments (with the exact targets)

- Foundations (CRUD/params/witnesses/choosing/gates) → [01 Database Foundations](<../../../01 Database Foundations and Mental Model/README.md>). Every probe here assumes the handshake, bound parameters, and witness-reading — no re-teaching, ever.
- Drivers and pooling (pool sizing, checkout binding at scale, migration discipline) → [Domain 04: Node.js Data Access Drivers and Pooling](<../../../04 Node.js Data Access Drivers and Pooling/README.md>).
- Naming level (join/transaction/index as words) → [IT Vocabulary 05](<../../../../ITVocabulary/05 Data Databases and AI Vocabulary/README.md>) (words owned there; mechanics owned here).

### Common confusion

- **"this domain should teach pooling"** — pooling *uses* transactions (checkout-bound units — [3.1](<../3. Atomicity/3.1. Transactions basis.md>) part 3's lifecycle) without *being* transactions. Mechanics compose across the boundary (binding here, sizing there); teaching both in one place fuses what production separates (pool config vs unit discipline — different files, different owners, different incidents).
- **"depth without drivers is academic"** — depth *precedes* drivers pedagogically (joins/aggregates/indexes/transactions understood against one connection — variables isolated); drivers *apply* depth (same queries through pools — composition, not re-learning). Learn deep on one client, scale through pools after — order matters, both matter.

### Mentor note

Teach mentees to read this page as a router: "first-contact" questions go to 01, "pooling" questions wait for 04, "depth" questions stay here. The distinction resolves half of all SQL debates before they start — most are driver-questions asked in depth-rooms ("is the pool slow?" during an unindexed-query incident), or the reverse.

## 3) Design and mapping (planned siblings own the ends)

### 3) **Definition** (the depth/design/map split)

*Depth* (this domain: querying, shaping, speeding, transacting Postgres directly) vs *modeling* (Database Design track: normal forms, key strategy, evolution — planned sibling) vs *mapping* (ORM track: entities, query builders, migrations via abstraction — planned sibling). Depth assumes workable schemas (queries run against designed tables) and precedes mapping (raw SQL literacy before generated-SQL trust — you cannot evaluate an ORM without reading its output).

### The assignments

- Schema modeling (normalization, keys, constraints as design discipline) → Database Design track (planned sibling per root README — textual forward, no dead link by design).
- Object mapping (entities, repositories via ORM, generated migrations) → ORM track (planned sibling per root README — textual forward, no dead link by design).
- Repository seams (policy surviving store swaps) → [DesignPatterns 06/1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>) (seam owned there — depth queries run behind it).

### Common confusion

- **"depth means design"** — depth *queries* designed schemas (incidental shapes serving lessons — minimal tables per probe); design *produces* schemas (normal forms, evolution strategy — systematic, not incidental). Incidental shapes teach SQL; systematic design teaches modeling — different jobs, different homes.
- **"ORM users skip this domain"** — ORM users need this domain *most* (generated SQL debugged via plans, N+1 recognized via join semantics, migrations reviewed via constraint literacy — every ORM failure mode is a depth question in disguise). Abstraction without foundation is magic; magic breaks quarterly — learn depth, then abstract consciously.

### Mentor note

The one-sentence router for Postgres: "First queries go back (01), pools wait (04), models live in siblings, *depth* stays here." Joins/aggregates/schema/indexes/transactions — the depth layer with its own craft, its own checklist, its own interview.
