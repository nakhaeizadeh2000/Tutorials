# 4.1. Postgres checklist (habits mentors insist on)

The three habits that keep PostgreSQL work boring: deliberate joins with explicit aggregates, early constraints with evidenced indexes, and transacted multi-writes. Junior read: extend the gate with three Postgres stages. Expert read: which incident each stage names, and why shape-checks belong in CI rather than in reviewers' memories.

## 1) Join deliberately, aggregate explicitly

### 1) **Definition** (the shape habit)

Every join names its type (`INNER`/`LEFT` written, never defaulted — intent visible); every aggregate names its grain (`GROUP BY` keys listed — per-what stated); every filter sits in its clause (keys in `ON`, questions in `WHERE`, group thresholds in `HAVING` — [1.1](<../1. Query depth/1.1. Joins across tables.md>) part 3's split, enforced). Shape decisions visible in text; reviewers verify placement, not intent.

### What problem it solves (history)

Shape drift (bare `JOIN` defaulting INNER silently, `SELECT *` across joins colliding `id` columns in drivers, HAVING-less thresholds computed client-side from full group dumps) produced wrong-membership reports and colliding fields — each invisible in green test suites (small fixtures masking fan-out, single-row groups hiding grain errors). Explicit shape makes membership reviewable (counts predicted per query — [1.1](<../1. Query depth/1.1. Joins across tables.md>)'s count-prediction exercise, enforced).

### Modern guidance

Write join types always (even INNER — explicitness costs five characters, saves LEFT-refactor incidents); list group keys beside every aggregate (grain stated — reviewers match grain to question); predict counts before running unfamiliar joins (2 customers × 1 order → INNER yields 1 — prediction recorded in scratch, confirmed by output).

### Runnable example (good — the discipline, witnessed)

```bash
# deliberate join (verified S-probes): type named, columns explicit, keys in ON
# SELECT c.name, o.total FROM demo_customers c INNER JOIN demo_orders o ON o.customer_id = c.id;
# explicit aggregate (verified): grain listed, groups witnessed
# SELECT c.name, COUNT(o.id) AS orders ... GROUP BY c.name;  →  ann 3 | bo 1
```

### Common confusion

- **"explicitness is verbosity"** — explicitness is *reviewability* (types/grains/clauses visible — reviewers verify in seconds); verbosity is *noise* (redundant aliases, decorative parens — removed freely). `INNER` and `GROUP BY c.name` carry information (type, grain); noise carries none — keep signal, cut noise, never confuse them.
- **"small queries don't need this"** — small queries *grow* (today's two-table lookup becomes tomorrow's five-table report — shape habits formed small transfer large; shape sloppiness formed small compounds). Discipline scales down freely (five characters per query); incidents scale up dearly.

### Performance note

Shape discipline costs nothing at runtime (keywords, not operations) and prevents the dearest query incidents (fan-out multiplications, cross joins from missing ON — full products materialized: rows² transferred, memory flooded). Explicit shapes fail review-fast (misplacement visible in text); implicit shapes fail production-slow (membership wrongness discovered downstream).

### Mentor note

Review joins mechanically (type? columns? ON-keys-only? grain-listed? — four checks, seconds): mentees internalize shape discipline when reviewers ask consistently ("which join type? — show me"). Mechanical checks beat explanations for placement rules — ask thrice, habit forms permanently.

## 2) Constrain early, index on evidence

### 2) **Definition** (the two-timings rule)

Constraints at design time (types, NOT NULL, UNIQUE, CHECK, FK — declared with the table, before the first row); indexes at EXPLAIN time (created for observed slow shapes — plan attached to the commit, per [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)). Never reversed (indexes guessed at design — unqueried maintenance; constraints bolted post-incident — garbage already stored, deduplication scheduled).

### What problem it solves (history)

Reversed timing produced both failure classes at once: unconstrained early tables (duplicates/orphans/nonsense stored from week one — cleanup migrations forever after) plus unevidenced early indexes (every column indexed "for performance" — writes taxed, storage doubled, zero plans attached). Timing discipline assigns each mechanism its moment: rules before rows, speed after measurement.

### Modern guidance

Constrain with the CREATE (every table ships with types/not-nulls/uniques/checks/FKs decided — schema review gates merges, per [2.1](<../2. Shape and speed/2.1. Schema and constraints that protect.md>)); index per plan (slow query → EXPLAIN → index → before/after ANALYZE in the commit — evidence chain unbroken); audit quarterly (unused indexes dropped via `pg_stat_user_indexes` zeros; missing constraints proposed via incident patterns — both directions, scheduled).

### Runnable example (good — FK indexed on evidence, verified live)

```bash
docker exec dbprobe psql -U postgres -tAc "SELECT indexname FROM pg_indexes WHERE tablename = 'demo_orders';"
# demo_orders_pkey          ← declaration-built (PK carries its index — [2.1] part 1)
# (customer_id unindexed — join probe paid full scans silently until now)

docker exec dbprobe psql -U postgres -c "CREATE INDEX IF NOT EXISTS demo_orders_customer_id_idx ON demo_orders (customer_id);"
# CREATE INDEX
# demo_orders_pkey + demo_orders_customer_id_idx  ← evidenced (join column, measured joins)
```

Verified: FK column carried *no* index until this session (Postgres builds none automatically — the declaration gap [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>) part 1 warned about); created on join evidence; catalog now shows both. Declaration provides integrity (FK refuses orphans); evidence provides speed (index serves joins) — each mechanism at its timing, both present now.

### Common confusion

- **"migrations add constraints later fine"** — later constraints validate *history* (existing violations block the migration — cleanup first, then constrain: downtime-shaped work); early constraints prevent history (violations never stored — zero cleanup, ever). Migrate constraints in when missed (necessary); prefer declaring at CREATE (sufficient, cheaper by the cleanup avoided).
- **"EXPLAIN per index is ceremony"** — EXPLAIN per index is *receipt* (before/after actuals — improvement proven, regressions caught); ceremony is process without payoff (this pays per avoided mis-index). Receipt-per-index also documents *why* each index exists (future droppers read the commit — archaeology with answers, per [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>) part 3).

### Performance note

Timing discipline *is* performance strategy (constrained-early: validity free per write; indexed-on-evidence: speed where measured, zero tax elsewhere). Reversed timing inverts both (unconstrained: incidents; unevidenced indexes: taxed writes, unsped reads). Two timings, two mechanisms, zero overlap — schedule each correctly once, benefit per query forever.

### Mentor note

Schema reviews check constraints (column-by-column intent — [2.1](<../2. Shape and speed/2.1. Schema and constraints that protect.md>)'s rite); index PRs check plans (before/after ANALYZE attached — [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)'s receipt). Two review rituals, distinct triggers (CREATE vs slow-query), same spirit (evidence over assertion). Ritualize both; performance follows process.

## 3) Wrap multi-writes in transactions

### 3) **Definition** (the unit rule, gated)

Two writes, one fate: BEGIN/COMMIT around related statements, ROLLBACK on any error, one connection throughout ([3.1](<../3. Atomicity/3.1. Transactions basis.md>)'s lifecycle — acquired, opened, worked, published-or-abandoned, released). Gated by shape review (multi-statement paths without transaction keywords flagged — grep for consecutive `query(` awaits without BEGIN, triaged humanly, never auto-failed: heuristics assist, reviewers decide).

### What problem it solves (history)

Unwrapped pairs (verified live in [3.1](<../3. Atomicity/3.1. Transactions basis.md>) part 2: `partial` persisting after its sibling's `23505` — half-intent stored, cleanup manual) ship partial states on every mid-sequence failure (constraint hits, crashes, deploys mid-flight — each leaving half-executed intent for the next reader to misinterpret). Wrapped pairs fail totally and loudly (nothing stored, error surfaced — debugging starts from truth, not half-truth).

### Modern guidance

Gate the shape (unfiltered-write grep in gate2 stage 20 below — unwrapped *destructives* caught mechanically; transaction *presence* reviewed humanly — heuristics flag, humans judge); wrap per user intent (one fate per action — transfer/debit-credit, order/items, multi-table mutations from one request); keep units tight (statements only between BEGIN/COMMIT — no external awaits inside, per [3.1](<../3. Atomicity/3.1. Transactions basis.md>) part 1).

### Runnable example (good — the postgres gate, verified)

```bash
#!/bin/bash
# postgres gate: filtered writes + FK indexed, non-zero names the stage
if grep -rEn '^(UPDATE|DELETE)[^;]*;' gatesql/ 2>/dev/null | grep -v WHERE; then exit 20; fi
docker exec dbprobe psql -U postgres -tAc "SELECT count(*) FROM pg_indexes WHERE tablename = 'demo_orders' AND indexdef LIKE '%(customer_id)%';" | grep -q "[1-9]" || exit 21
echo PG-GREEN
```

```bash
./gate2.sh; echo "exit=$?"
# gatesql/dirty.sql:1:UPDATE ledger SET balance = 0;
# exit=20
# (dirty file removed →)
# PG-GREEN
# exit=0
```

Verified: stage 20 fires on the planted unfiltered `UPDATE` (filename + line as evidence), silent when clean; stage 21 asserts the FK index exists (catalog proof — the evidence from part 2, gated). Honest boundary: stage 20 is a single-line heuristic (multiline statements evade — reviewers cover what grep can't; heuristics assist, humans judge).

### Common confusion

- **"gates replace transaction review"** — gates catch *shapes* (unfiltered destructives — mechanical); reviewers catch *units* (unwrapped pairs — semantic: two writes, one fate, no keywords — needs judgment). Shape-gates plus unit-review cover both halves; either alone halves coverage. Automate shapes, review units — the split from [01/4.1](<../../../01 Database Foundations and Mental Model/sections/4. Important points to remember/4.1. Data checklist habits mentors insist on.md>)'s unification thinking, applied.
- **"two gates are one too many"** — merge freely (gate1 + gate2 → one script, stages 10/11/20/21, distinct exits — pedagogy splits per domain, operations unifies per repo, per [01/4.1](<../../../01 Database Foundations and Mental Model/sections/4. Important points to remember/4.1. Data checklist habits mentors insist on.md>)).

### Performance note

Gate cost per run: greps (milliseconds) + catalog query (milliseconds) — cheapest stages after version prints. Unwrapped-pair cost: partial-state incidents (hours with misdirection, per occurrence — symptoms far from the unwrapped writes). Unfiltered-destructive cost: table-wide locks + mass mutation (seconds of contention + data repair — the dearest typo class in SQL). Gate cheaply, sleep soundly.

### Mentor note

The graduation exercise for this domain: hand the mentee a repo with four planted faults (unfiltered UPDATE, missing FK index, unwrapped transfer pair, unmapped trace) and gates 1–2. Thirty minutes, four exit codes/stages, four fixes — each fix citing its leaf. Fluency demonstrated, not described — incidents prepaid for the team.
