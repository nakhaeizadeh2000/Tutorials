# 1.1. Joins across tables

Answering cross-entity questions where the data lives: `INNER JOIN` for matches, `LEFT JOIN` for the lonely, `ON` for matching and `WHERE` for restricting. Junior read: two join types, one rule separating them. Expert read: where filtered joins misreport, and why join shape decides store choice.

## 1) INNER JOIN answers cross-entity questions

### 1) **Definition** (the match combiner)

`INNER JOIN ... ON` pairs rows whose keys match, emitting one combined row per match: customers × orders becomes (ann, 19.98) — non-matching rows on either side dropped silently. The product relational stores sell: questions spanning entities answered in one query, at the planner's speed, with integrity the foreign key guarantees.

### What problem it solves (history)

Pre-relational assembly (application-side loops: fetch customers, fetch orders, nest in code — N+1 queries, network per entity, integrity unenforced between fetches) scaled as the product of table sizes in round trips. Joins collapsed it to one round trip with planner-optimized access (hash/merge/nested-loop chosen per statistics — Domain 06 owns plan reading; the mechanism assumed here).

### Modern guidance

Join on declared foreign keys (integrity enforced — orphans rejected at write time, per [2.1](<../2. Shape and speed/2.1. Schema and constraints that protect.md>)); select explicit columns (never `SELECT *` across a join — duplicate `id` columns collide in drivers, widths multiply); alias tables (`c`, `o` — readable at a glance, mandatory past two tables).

### Runnable example (good — matched rows combined, verified live)

```bash
docker exec dbprobe psql -U postgres -c "SELECT c.name, o.total FROM demo_customers c INNER JOIN demo_orders o ON o.customer_id = c.id;"
#  name | total
# ------+-------
#  ann  | 19.98
# (1 row)
```

Verified on PostgreSQL 16.15: two tables, one query, matched pair combined. The `INNER` keyword is optional (`JOIN` ≡ `INNER JOIN` — write it anyway: explicit join type per review checklist in [4.1](<../4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)).

### Common confusion

- **"JOIN duplicates data"** — joins *combine* (one row per match — the product of matches, not of tables); duplication complaints trace to fan-out (one-to-many matches multiplying left rows — correct behavior misread: per-order customer rows repeat the customer *because each pair is a distinct answer*). Expect fan-out on 1:N; aggregate it away ([1.2](<./1.2. Aggregates and grouping.md>)) when per-parent singles are wanted.
- **"comma joins are equivalent"** (`FROM a, b WHERE a.id = b.a_id` — antique theta syntax: equivalent results, inferior readability, WHERE-clause conflation inviting the bug part 3 dissects). Modern `JOIN ... ON` separates matching from restricting structurally — syntax steering correctness, again.

### Performance note

Join cost follows the smaller input + index availability (indexed FK lookups: nested-loop cheap; unindexed: hash/merge with scans — `EXPLAIN` decides per query in [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)). Missing-FK-index joins degrade superlinearly (full scan per outer row — the N+1's server-side twin). Index foreign keys by default (the rule [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>) enforces with plans attached).

### Mentor note

Teach joins with Venn diagrams once (inner = overlap — then discard the diagrams: real join thinking is *match tables*, not shaded ovals). The lasting exercise: predict row counts before running (2 customers × 1 order → inner yields 1 — every correct prediction internalizes match-semantics; every wrong one teaches fan-out or loneliness concretely).

## 2) LEFT JOIN keeps the lonely

### 2) **Definition** (absence-reporting join)

`LEFT JOIN` emits every left row, matched or not — unmatched rights arrive as NULLs (`bo | (null)`): absence reported as data, not hidden by the join. The loneliness query (`WHERE o.id IS NULL` — left rows with no match) answers "which customers never ordered?" — the negative question INNER JOIN cannot ask (it drops exactly those rows).

### What problem it solves (history)

Absence-blind reporting (inner-joined dashboards showing only active customers — churned/never-ordered segments invisible, growth math wrong by construction) misled product decisions for years: retention computed over survivors (survivorship bias in SQL clothing). LEFT JOIN + IS NULL reports the missing as first-class answers — churn lists, orphan audits, onboarding funnels, all negative-space questions.

### Modern guidance

Default LEFT when the question tolerates absence ("customers *with their* orders" — keep the orderless); reserve INNER for match-required questions ("orders *with* customer names" — orphans impossible by FK anyway); filter loneliness with `IS NULL` on the *right* key (never `= NULL` — three-valued logic: NULL never equals, only `IS NULL` matches — the classic empty-result mystery).

### Runnable example (good — the lonely reported, verified live)

```bash
docker exec dbprobe psql -U postgres -c "SELECT c.name, o.total FROM demo_customers c LEFT JOIN demo_orders o ON o.customer_id = c.id ORDER BY c.name;"
#  name | total
# ------+-------
#  ann  | 19.98
#  bo   |
# (2 rows)

docker exec dbprobe psql -U postgres -c "SELECT c.name FROM demo_customers c LEFT JOIN demo_orders o ON o.customer_id = c.id WHERE o.id IS NULL;"
#  name
# ------
#  bo
# (1 row)
```

Verified: `bo` (orderless customer, inserted this session) survives LEFT (NULL total) and is *found* by the IS NULL loneliness query — absence as answer, not accident. INNER on the same tables yields 1 row (bo dropped — correct for match-questions, wrong for census-questions).

### Common confusion

- **"NULL total means zero"** — NULL means *absent* (no order — unknown, not zero; `SUM` skips NULLs, `COUNT(total)` skips them too — aggregates treat absence as non-participation, never as zero). Coalesce explicitly (`COALESCE(o.total, 0)` — absence rendered as zero *by decision*, visible in the query, reviewable).
- **"RIGHT JOIN for symmetry"** — RIGHT JOIN mirrors LEFT (keeps right rows) — valid, rarely needed (swap table order instead: every RIGHT is a LEFT rewritten — conventions prefer LEFT-only codebases for grep-ability). FULL JOIN keeps both lonelies (reconciliation queries — rare, legitimate, named explicitly when used).

### Performance note

LEFT JOIN costs ≥ INNER (superset of rows + NULL-extension per miss — marginally more I/O, same plan shapes). Loneliness filters (`IS NULL` on right keys) use indexes where present (anti-join plans — `NOT EXISTS` equivalent, planner's choice per statistics). Absence reporting is never the slow part (the join dominates; the filter is a scan over its output — measure the join, not the predicate).

### Mentor note

The `bo` exercise (insert orderless parent → INNER hides → LEFT shows → IS NULL finds — four commands, one narrative): mentees predicting each count correctly own join semantics; wrong predictions pinpoint the gap (fan-out vs loneliness — different confusions, different remedies). Run it per onboarding cohort; counts don't lie about comprehension.

## 3) Join on keys, filter with WHERE

### 3) **Definition** (ON matches, WHERE restricts)

`ON` declares *how tables relate* (key equality — the relationship, stable across queries); `WHERE` declares *which combined rows survive* (predicates — the question, varying per query). Conflating them (filter predicates smuggled into `ON` of an INNER JOIN — harmless there, corrupting under LEFT: filtered rights vanish *before* NULL-extension, silently converting LEFT to INNER behavior).

### What problem it solves (history)

ON-cluttered queries (business filters embedded in join conditions — "it works" under INNER, breaks on the LEFT refactor that business inevitably requests) produced the subtlest wrong-result class in SQL: correct row *shape*, wrong row *membership* (missing rows nobody counts — absence unnoticed is worse than errors). Separation (relationships in ON, questions in WHERE) makes LEFT-refactors safe by construction.

### Modern guidance

ON holds key equality only (plus genuinely relationship-scoped predicates — dated validity ranges on slowly-changing dimensions, the documented exception); WHERE holds every question predicate (status filters, thresholds, date windows — visible, movable, testable per query); review ON clauses for non-key conditions (each one a LEFT-trap armed — disarm or document with the reason inline).

### Runnable example (good — the discipline, verified pair)

```bash
# WHERE restricts combined rows (verified live — empty set, honestly empty):
docker exec dbprobe psql -U postgres -c "SELECT c.name, o.total FROM demo_customers c JOIN demo_orders o ON o.customer_id = c.id WHERE o.total > 100;"
#  name | total
# ------+-------
# (0 rows)
```

```sql
-- bad: filter smuggled into ON (works under INNER today…)
SELECT c.name, o.total FROM demo_customers c JOIN demo_orders o
  ON o.customer_id = c.id AND o.total > 100;
-- …breaks under LEFT tomorrow (bo vanishes entirely — not even NULL-extended:
-- the ON predicate rejects before extension, LEFT degrades to INNER silently)
```

Why it hurts: identical output under INNER (indistinguishable in tests — the trap arms invisibly), divergent under LEFT (rows missing, no error — production census silently wrong). Fix: ON for keys, WHERE for questions — the refactor-proof split (LEFT-swaps change nothing when predicates already live in WHERE).

### Common confusion

- **"ON vs WHERE is stylistic"** — stylistic under INNER (same results — the equivalence lulling teams), semantic under OUTER (different membership — the divergence biting later). Style-today/semantics-tomorrow constructs deserve rules, not taste: keys in ON always, questions in WHERE always.
- **"extra ON conditions optimize"** — the planner optimizes predicates identically wherever placed (predicate pushdown is location-independent — EXPLAIN proves it per query in [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)). Placement serves *correctness under refactor* (membership stability), never performance — optimize with indexes, stabilize with placement.

### Performance note

No performance dimension (planner-normalized — identical plans for ON/WHERE-placed INNER predicates, verifiable via EXPLAIN). The cost axis is correctness durability (refactor-safe membership — LEFT conversions preserving census). Free to place correctly (zero runtime delta); dear to place cleverly (silent row loss per future refactor).

### Mentor note

Code-review ON clauses mechanically (keys-only? — every non-key predicate gets "move to WHERE or justify inline"): two weeks of mechanical review converts a team permanently (placement discipline becomes authoring habit — reviewers stop finding violations because authors stop writing them). Mechanical checks beat explanations for placement rules.
