# 1.2. Aggregates and grouping

Summarizing data where it lives: five aggregate functions, `GROUP BY` per-group rows, and `HAVING` filtering groups after `WHERE` filters rows. Junior read: count, sum, average in one row. Expert read: where grouping misleads (fan-out inflation), and why HAVING-after-WHERE ordering is semantic, not stylistic.

## 1) Five functions summarize anything

### 1) **Definition** (whole-table answers)

`COUNT` (rows), `SUM` (total), `AVG` (mean), `MIN`/`MAX` (extremes) collapse a result set into one row: questions about *collections* answered without fetching them. Aggregates ignore NULLs (except `COUNT(*)` — the row itself always counts); empty sets yield `COUNT 0`, `SUM NULL` (absence vs zero, again — [1.1](<./1.1. Joins across tables.md>) part 2's NULL discipline, applied).

### What problem it solves (history)

Application-side summarization (fetch all rows, loop in code — full table over the wire per dashboard number) scaled as data volume in transfer and memory, failing exactly as dashboards mattered most (month-end reports over millions of rows — minutes per number, timeouts per quarter-close). Server-side aggregates move computation to data (one row back — bytes constant regardless of table size).

### Modern guidance

Summarize in SQL by default (counts, sums, averages — the store's home turf); fetch rows only to *display* rows (lists, details — presentation needs); mind the empty set (`COUNT` → 0, `SUM` → NULL — `COALESCE(SUM(x), 0)` where zero is meant, decided visibly per query).

### Runnable example (good — one row answering five questions, verified live)

```bash
docker exec dbprobe psql -U postgres -c "SELECT COUNT(*), SUM(total), AVG(total), MIN(total), MAX(total) FROM demo_orders;"
#  count |  sum  |         avg         | min  |  max
# -------+-------+---------------------+------+-------
#      4 | 74.73 | 18.6825000000000000 | 5.00 | 42.50
# (1 row)
```

Verified on PostgreSQL 16.15 (4 seeded rows): five answers, one row, zero application code. Note `AVG`'s full precision (`18.6825...` — NUMERIC exactness, not float drift — the type choice from [2.1](<../2. Shape and speed/2.1. Schema and constraints that protect.md>) paying off visibly).

### Common confusion

- **"`AVG` of integers averages wrong"** — integer division truncates *in expressions* (`SUM(x)/COUNT(x)` on ints — cast first: `AVG(x::NUMERIC)`); the `AVG()` aggregate itself promotes correctly (verified `18.68...` above, exact). Expression arithmetic vs aggregate semantics — different rules, same query — cast deliberately in hand-rolled ratios.
- **"aggregates need GROUP BY"** — bare aggregates collapse *everything* (one row, no groups — the simplest summary); `GROUP BY` multiplies the summary per key (part 2). Ungrouped answers "how many orders?"; grouped answers "how many *per customer*?" — different questions, different clauses, chosen per question asked.

### Performance note

Aggregates scan (full or index-assisted — plans in [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)): cost scales with rows scanned, not rows returned (one row back, millions read — the bargain). Approximate variants exist where exactness is negotiable (percentiles, distinct-counts at scale — Domain 06 owns HyperLogLog-class trade-offs); exact first, approximate on measured pain.

### Mentor note

The dashboard-number exercise (every KPI on the team's dashboard rewritten as one aggregate query — count per step): mentees discovering their loop-and-sum code replaced by single rows internalize server-side thinking permanently. Review application-side summarization as a finding ("why isn't this an aggregate?") until the codebase stops containing any.

## 2) `GROUP BY` summarizes per group

### 2) **Definition** (one row per key)

`GROUP BY c.name` partitions rows by key, aggregating within each partition: per-customer order counts and spend — the GROUPed twin of part 1's whole-table collapse. With LEFT JOIN, empty groups survive the summary (`COUNT(o.id)` 0, `SUM` NULL — absence inside the aggregate, per the COUNT-twins probe below).

### What problem it solves (history)

Per-group questions answered per-group queries (loop over customers, query each — N+1 summarization, the aggregation twin of application-side joins) scaled as groups × latency — dashboards with hundreds of groups timing out serially. GROUP BY answers all groups in one pass (single scan, hash/sort grouping — planner's choice per statistics).

### Modern guidance

Group by the question's grain (per-customer, per-day, per-status — the grain *is* the question; wrong grain, wrong answers); select grouped keys + aggregates only (bare columns beside GROUP BY are indeterminate — Postgres *rejects* them by default, rightly: which row's value? — unanswerable is an error, not a guess); LEFT JOIN + GROUP for census groups (empty groups reported with zeros/NULLs — absence in the summary, per [1.1](<./1.1. Joins across tables.md>) part 2).

### Runnable example (good — per-group summary, verified live)

```bash
docker exec dbprobe psql -U postgres -c "SELECT c.name, COUNT(o.id) AS orders, SUM(o.total) AS spent FROM demo_customers c LEFT JOIN demo_orders o ON o.customer_id = c.id GROUP BY c.name ORDER BY c.name;"
#  name | orders | spent
# ------+--------+-------
#  ann  |      3 | 67.48
#  bo   |      1 |  7.25
# (2 rows)
```

Verified: per-customer counts and spend in one pass (ann: 3/67.48, bo: 1/7.25). Note `COUNT(o.id)` (non-null order ids — counts *orders*) vs `COUNT(*)` (counts *rows* — identical here, divergent under LEFT with unmatched groups: `COUNT(*)` counts the NULL-extended row, `COUNT(o.id)` doesn't — the part-1 NULL discipline applied to grouping).

### Common confusion

- **"GROUP BY with JOIN double-counts"** — fan-out inflates pre-grouped joins (1:N matches multiplying left rows *before* grouping — SUM over fanned rows counts matches, not parents). Aggregate *before* joining (subquery/CTE per side, then join summaries) when fan-out distorts — or accept fan-out deliberately (per-order-per-customer rows are the correct grain there). Grain awareness, always.
- **"ORDER BY inside groups"** — `ORDER BY` sorts *output rows* (post-grouping — group order); in-group ordering needs window functions or array_agg with ORDER (Domain 02-adjacent depth, named once: `array_agg(x ORDER BY y)` — per-group sequenced lists, rare, legitimate).

### Performance note

Grouping cost: sort or hash over the input (memory-bounded — `work_mem` spills to disk past it, gracefully slower — Domain 06 owns tuning); indexed group keys accelerate (ordered scans skipping sorts — plans in [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)). Dashboard-group counts in the hundreds group in milliseconds; millions of groups need approximate or pre-aggregated strategies (Domain 06 — measured pain first).

### Mentor note

The fan-out trap demo (SUM over a 1:N join vs SUM over pre-aggregated CTE — different numbers, same data): one divergent pair teaches grain awareness faster than any GROUP BY tutorial. Run it per cohort; ask "which is right?" (both — different grains); follow with "which answers the question?" (grain must match the question — the lesson, restated until reflex).

## 3) `HAVING` filters groups

### 3) **Definition** (post-grouping restriction)

`HAVING SUM(o.total) > 10` keeps groups passing the predicate (ann: 67.48 stays; bo: 7.25 goes) — evaluated *after* grouping over aggregate values. `WHERE` filters *rows before* grouping (which rows participate); `HAVING` filters *groups after* (which summaries survive). Same English ("only big spenders"), different stages, different answers.

### What problem it solves (history)

Pre-HAVING workarounds (subquery wrapping: `SELECT * FROM (GROUPed...) WHERE ...` — verbose, opaque to planners of the era) made grouped filtering second-class: written rarely, read painfully. HAVING (SQL-92 standard, universal) promotes it to first-class: intent visible (filter *on the summary*), planners optimizing across the boundary (predicate pushdown into grouping where valid).

### Modern guidance

WHERE for row participation (status filters, date windows — narrows input, the planner's favorite kind); HAVING for group survival (thresholds on summaries — "spent > 10", "orders ≥ 5" — undecidable pre-grouping by construction); never HAVING on bare columns (group-key predicates belong in WHERE — earlier filtering, smaller groups, cheaper grouping).

### Runnable example (good — groups filtered, verified live)

```bash
docker exec dbprobe psql -U postgres -c "SELECT c.name, SUM(o.total) AS spent FROM demo_customers c JOIN demo_orders o ON o.customer_id = c.id GROUP BY c.name HAVING SUM(o.total) > 10;"
#  name | spent
# ------+-------
#  ann  | 67.48
# (1 row)
```

Verified: bo's 7.25 group computed then excluded (HAVING evaluates post-aggregation — the group *existed*, then failed the predicate). Contrast WHERE (`WHERE o.total > 10` pre-grouping: excludes *rows* under 10 first — different input, different sums, different question entirely).

```bash
# the NULL-counting twin (verified live — COUNT(*) vs COUNT(col)):
# SELECT COUNT(*), COUNT(total) FROM (VALUES (1, 5.00), (2, NULL)) AS v(id, total);
#  count | count
# -------+-------
#      2 |     1
```

`COUNT(*)` counts rows (2 — presence); `COUNT(total)` counts values (1 — NULL skipped). In HAVING terms: `HAVING COUNT(*) > 1` vs `HAVING COUNT(total) > 1` ask different questions (rows present vs values known) — choose per question, witness the difference once, remember forever.

### Common confusion

- **"HAVING without GROUP BY"** — valid (whole result as one implicit group — `HAVING SUM(x) > 0` filters the single summary row: present or empty result). Rare, legitimate (threshold-gated singleton reports); confusing to readers (GROUP-less HAVING scans as typo — comment the intent where used).
- **"WHERE SUM(x) > 10"** — invalid (aggregates unavailable pre-grouping — the engine rejects: aggregates compute *from* groups, WHERE runs *before* them). The error is the teacher (stage order enforced by syntax — read errors as curriculum, per this track's habit).

### Performance note

HAVING-after-WHERE ordering is also the *performance* order (WHERE narrows input first — fewer rows grouped; HAVING prunes output after — cheap filter on summaries). Predicate placement across the boundary changes work done (filter early, aggregate less — same principle as part-1's server-side summarization, applied within the query). EXPLAIN shows the order ([2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>) reads it); trust but verify per hot query.

### Mentor note

The WHERE-vs-HAVING swap exercise (same predicate, both clauses, compare outputs — different rows, different counts, different questions): two runs teach stage order permanently (pre-group vs post-group as *execution* order, not just syntax position). Follow with "which is cheaper?" (WHERE-first — narrower input — the performance dividend of correct placement, free with understanding).
