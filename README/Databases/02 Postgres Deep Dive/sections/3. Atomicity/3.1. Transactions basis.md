# 3.1. Transactions basis

Making multi-statement writes all-or-nothing: `BEGIN`/`COMMIT` atomicity, `ROLLBACK` as planned undo, and one-client-per-transaction discipline. Junior read: wrap related writes, or partial states escape. Expert read: where autocommit ends and transactions begin, and why pooling meets atomicity at checkout time.

## 1) BEGIN/COMMIT make all-or-nothing

### 1) **Definition** (the atomic unit)

`BEGIN` opens a transaction (subsequent statements on *this connection* stage, invisible to others); `COMMIT` publishes all of them atomically (all visible at once — no observer ever sees the middle); anything between without commit is provisional (other sessions see pre-state until commit lands). One transaction, one fate — the unit multi-statement correctness is built from.

### What problem it solves (history)

Multi-statement writes without transactions partially applied on mid-sequence failures (debit posted, credit lost — money destroyed by a crash between statements; the classic transfer anomaly that named the problem): each statement individually atomic (single-statement autocommit holds), the *sequence* unprotected (no unit spanning statements). Transactions extend atomicity from statements to sequences — the missing unit, supplied.

### Modern guidance

Wrap related writes (transfer legs, order+items, multi-table mutations from one user action — one fate per user intent); keep transactions short (open late, commit early — locks held per duration, contention scaling with length); never user-think inside transactions (no API calls, no prompts, no awaits on external I/O between BEGIN and COMMIT — lock-holding while the world responds is how deadlocks and pileups are manufactured).

### Runnable example (good — transfer atomic, verified live)

```javascript
// pg 8.23.0, single client, PostgreSQL 16.15 (docker, this session)
await c.query('BEGIN');
await c.query('UPDATE ledger SET balance = balance - 30 WHERE owner = $1', ['ann']);
await c.query('UPDATE ledger SET balance = balance + 30 WHERE owner = $1', ['bo']);
await c.query('COMMIT');
// committed: [{"owner":"ann","balance":70},{"owner":"bo","balance":80}]
```

Verified: 100→70 and 50→80 (conservation holds — money moved, none created or destroyed). Concurrent observers see either (100, 50) or (70, 80) — never (70, 50): the middle state exists only inside the transacting connection, invisible by construction.

### Common confusion

- **"single statements need transactions"** — single statements are *already* atomic (autocommit wraps each — all-or-nothing per statement, free). Transactions begin where *sequences* need unity (two+ statements, one fate — wrapping singles adds lock-hold for zero benefit). Wrap sequences, never singles.
- **"COMMIT always succeeds"** — COMMIT can fail (serialization conflicts, constraint checks deferred to commit, connection loss mid-commit — ambiguous outcome: applied or not *unknown*). Ambiguous commits need idempotent retry (same operation safely repeatable — keys and dedup designed in, per Domain 05's integrity patterns) — commit-and-hope is not a strategy.

### Performance note

Transaction overhead per unit: BEGIN/COMMIT round trips (two extra — pipelined, negligible) + lock-hold duration (contention scaling with length × concurrency — short transactions contend linearly, long ones superlinearly). Keep units tight (statements only, no awaits between — the hot path stays contention-free); batch independent units separately (one giant transaction serializes what parallel small ones wouldn't).

### Mentor note

The transfer demo (debit+credit with a kill between — in txn: nothing applied; without: half applied — verified pair below in part-2-adjacent prose) converts atomicity from vocabulary to mechanism in one run. Mentees predicting both outcomes correctly own transactions; wrong predictions reveal autocommit-blindness (remedy: part 2's contrast, immediately).

## 2) ROLLBACK is the undo you plan

### 2) **Definition** (explicit abandonment)

`ROLLBACK` discards the staged unit (provisional writes vanish — as if never issued); error paths roll back *explicitly* (catch → ROLLBACK → rethrow/report — the undo planned beside the attempt, never assumed); connection release without commit/rollback aborts implicitly (drivers roll back on `end()` mid-transaction — safety net, not strategy: explicit beats implicit, always).

### What problem it solves (history)

Unwound failures (catch-log-continue without ROLLBACK — connection returned to the pool *inside a failed transaction*: subsequent queries on it failing "current transaction is aborted," poisoning pooled clients one by one — the cascading pool-poisoning incident class) stemmed from treating errors as *handled* while the transaction stayed *open*. Explicit ROLLBACK closes both: error handled, unit abandoned, connection clean for return.

### Modern guidance

Catch-rollback-rethrow per transacted unit (three lines, no exceptions — the pattern below, copy it); ROLLBACK on *any* error (constraint violations included — aborted transactions accept only ROLLBACK/COMMIT-which-rolls-back: querying further inside aborts with `25P02`, the in-transaction-ignored error); verify abandonment where it matters (re-read post-rollback in tests — absence asserted, not assumed).

### Runnable example (good — abandonment verified, plus the unwrapped contrast)

```javascript
await c.query('BEGIN');
await c.query("INSERT INTO ledger (owner, balance) VALUES ('zed', 10)");
await c.query('ROLLBACK');
const r = await c.query("SELECT count(*)::int AS n FROM ledger WHERE owner = 'zed'");
// rolled-back absent: true
```

```javascript
// bad: two writes, no transaction, second violates (verified live — 23505):
await c.query("INSERT INTO ledger (owner, balance) VALUES ('partial', 5)");   // applied
await c.query("INSERT INTO ledger (owner, balance) VALUES ('ann', 5)");       // 23505 duplicate
// no-txn partial persists: true — 'partial' stored, intent half-executed, no error surfaced for the FIRST write
await c.query("DELETE FROM ledger WHERE owner = 'partial'");                  // manual cleanup (verified)
```

Verified pair: wrapped-and-rolled-back vanishes (`zed` absent — undo complete); unwrapped-and-failed persists (`partial` stored — half-intent live, cleanup manual). The contrast is the lesson: unwrapped sequences fail *partially and silently*; wrapped sequences fail *totally and loudly*. Prefer loud totality.

### Common confusion

- **"ROLLBACK on success paths"** — ROLLBACK *abandons* (test teardowns, dry runs — legitimate abandonment contexts); success paths COMMIT (persistence intended). Test-then-rollback (seed → assert → rollback — database-clean tests without fixtures) is ROLLBACK's finest legitimate use — abandonment as hygiene, not failure.
- **"implicit rollback suffices"** — driver-abort-on-release *rescues* (connection recycled clean — safety net holding); explicit ROLLBACK *declares* (intent visible, errors surfaced, timing controlled — strategy). Nets catch falls; strategies prevent them — write the ROLLBACK, keep the net.

### Performance note

ROLLBACK cost: staged writes discarded (I/O already spent — wasted, necessarily: the alternative is wrong data, infinitely dearer); aborted-transaction queries rejected (`25P02` until ROLLBACK — fail-fast, cheap). Lingering open transactions cost locks + bloat (idle-in-transaction connections blocking vacuum — connection hygiene per Domain 04: release-or-rollback promptly, monitor `idle_in_transaction`).

### Mentor note

Require catch-rollback-rethrow shape in review for every transacted unit (three lines present? — mechanical check, two seconds): mentees internalize abandonment planning when reviewers ask once ("where's the ROLLBACK?"). Pair with the pool-poisoning story (one missing ROLLBACK cascading through pooled clients — narrative scar tissue, administered kindly).

## 3) One client, one transaction

### 3) **Definition** (connection-scoped atomicity)

Transactions live on *connections*, not clients-in-abstract: `BEGIN` binds the issuing connection (all subsequent statements on *that* object participate); a second client sees pre-commit state (isolation working — concurrency unaffected); pool checkouts carry transactions (checked-out connection = transacted unit in flight — release only after COMMIT/ROLLBACK). Atomicity follows the connection object through every API.

### What problem it solves (history)

Connection-confused transactions (BEGIN on client A, writes on client B — "transaction not working," silently autocommitted halves; pool-released mid-transaction — next borrower inheriting open state, failing mysteriously) produced the "transactions don't work" folklore that was always connection misuse. Binding discipline (one object, open-to-close, never shared mid-unit) dissolves the folklore: transactions always worked — handles wandered.

### Modern guidance

One checked-out connection per transacted unit (acquire → BEGIN → work → COMMIT/ROLLBACK → release — lifecycle unbroken, object never shared mid-flight); never pool-share mid-transaction (concurrent use of one transacted connection interleaves foreign statements into the unit — corruption by sharing, excluded structurally); helper functions receive the client (pass `c` explicitly — ambient/global clients hide binding, explicit parameters declare it).

### Runnable example (good — the lifecycle, named)

```javascript
// the discipline (shape — pooling mechanics in Domain 04, binding here):
const c = await pool.connect();          // acquire: one object, exclusively held
try {
  await c.query('BEGIN');                // open on THIS object
  await c.query('UPDATE ... WHERE ...'); // work on THIS object only
  await c.query('COMMIT');               // publish from THIS object
} catch (e) {
  await c.query('ROLLBACK');             // abandon from THIS object
  throw e;                               // report (never swallow — callers decide)
} finally {
  c.release();                           // return clean (committed or rolled back — never open)
}
```

### Common confusion

- **"transactions span pools"** — transactions span *one connection* (pool is a lender, not a participant — checkout binds, release unbinds; the unit never outlives its checkout). Cross-connection atomicity needs distributed protocols (2PC/sagas — Domain 05 names them, systems reach for them deliberately, never accidentally).
- **"helpers can grab their own clients"** — helpers grabbing connections *inside* a transacted unit break atomicity (their writes land outside the unit — committed separately, rolled back never). Pass the transacted client down (explicit parameter — the seam [DesignPatterns 06/1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>) would approve: seams carry the unit).

### Performance note

Binding discipline costs parameter-passing (explicit `c` through call chains — style, free) against connection-confusion incidents (half-committed units, poisoned pools — hours with misdirection, per occurrence). Checkout-hold duration equals transaction length (short units release fast — pools stay fluid; long units starve borrowers — keep units tight, per part 1).

### Mentor note

Review transacted code for the five-line lifecycle (acquire/BEGIN/work/COMMIT-or-ROLLBACK/release — each present, ordered, on one object): missing lines named in review ("no ROLLBACK path" — two seconds to spot, permanent habit to form). Lifecycle reviews teach atomicity faster than isolation theory — mechanics before models, always (models arrive in Domain 05).
