# 5.1. Common interview QA: Postgres

Canonical answers for the three Postgres questions every backend interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their codes. Expert read: each answer runs evidence (verified plans, codes, gates) before conclusions — prediction first, output as confirmation.

## 1) "INNER vs LEFT JOIN?" — answer with NULLs

### 1) **Definition** (the absence-reporting screen)

"What's the difference, and when does it matter?" — screens for match-vs-census thinking: hires answer with NULLs (INNER drops the unmatched; LEFT keeps them NULL-extended), demonstrate with the loneliness query (`IS NULL` finds the orderless — `bo`, verified), and warn about silent census corruption (INNER where LEFT belonged — missing rows, no error, worst failure shape).

### What problem it solves (hiring signal)

Join choice is the highest-frequency SQL judgment (every multi-table query) with the quietest failure mode (wrong membership, green logs): candidates answering in row-counts (2 customers → INNER yields 1, LEFT yields 2 — predicted before running) prove model-driven querying; candidates answering in syntax prove recitation. The question predicts reporting correctness directly.

### Modern guidance

Answer with the verified pair (inner 1 row / left 2 rows with NULL — quoted), the loneliness follow-up (`WHERE o.id IS NULL` → `bo` — absence as answer), and the NULL-vs-zero warning (`COALESCE` by decision — [1.1](<../1. Query depth/1.1. Joins across tables.md>) part 2). End unprompted with ON-vs-WHERE (keys in ON, questions in WHERE — refactor-proof placement): completeness signals, not just correctness.

### Runnable example (good — the pair, quoted verbatim)

```bash
# INNER (matched only):
#  name | total
# ------+-------
#  ann  | 19.98
# (1 row)
# LEFT (lonely kept):
#  name | total
# ------+-------
#  ann  | 19.98
#  bo   |
# (2 rows)
# loneliness:
#  bo
# (1 row)
```

A hire narrates *before* running ("INNER drops bo — no match; LEFT keeps her NULL-extended; IS NULL finds exactly the unmatched") — prediction first, confirmation second. Interviewers: ask "count customers from each" before revealing (1 vs 2 — the count question exposes census thinking instantly).

### Common confusion (in candidates)

- **"LEFT is safer, use always"** — LEFT where INNER belongs hides integrity breaks (orphans that FKs should have prevented — INNER's disappearance *is* the alarm; LEFT's tolerance masks it). Match-required questions use INNER deliberately (disappearance diagnosed); census questions use LEFT deliberately (absence reported). Deliberate per question — never default per habit.
- **"NULL total equals zero"** — red flag adjacent: NULL is absent (aggregates skip — `COUNT(total)` vs `COUNT(*)` diverge, verified 1-vs-2 in [1.2](<../1. Query depth/1.2. Aggregates and grouping.md>)). Candidates coalescing explicitly (`COALESCE(o.total, 0)` — decided, visible) pass; candidates equating pass nothing.

### Performance note

Join-type answers need no numbers (membership question, not speed) — except the follow-up volunteer (FK indexes serve joins — created on evidence this session; unindexed FKs degrade superlinearly — [2.2](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>) part 1). Membership first, mechanics volunteered — the ordering interviewers score.

### Mentor note

Mock with counts covered ("how many rows from each variant?" — demanded before output): mentees graduate when predictions precede results two sessions running. Count-prediction is the join-comprehension instrument — use it per mock, per onboarding, per review of reporting code.

## 2) "This query is slow — what now?" — read the plan

### 2) **Definition** (the measurement-sequence screen)

"Production query takes seconds — walk me through it" — screens for ordered optimization: hires EXPLAIN first (plan attached before theorizing), index second (before/after ANALYZE quoted), rewrite third (only with plan evidence). Tool-first candidates ("add an index") fail the sequence; evidence-first candidates pass before naming any fix.

### What problem it solves (hiring signal)

Slow-query work without discipline optimizes cold code (rewrites unmeasured, indexes unproven — effort uncorrelated with latency) or ships regressions disguised as fixes (untested index slowing writes net-negative). The plan→index→rewrite sequence converts complaints into arithmetic — and arithmetic into the cheapest effective fix, usually one index with receipts.

### Modern guidance

Answer as a procedure with the verified receipts: EXPLAIN (Seq Scan cost 769.59 — the diagnosis), index (CREATE INDEX — the prescription), ANALYZE (Bitmap Index Scan 323.72, actual 1 row, 0.073ms — the proof). Each step measured before the next is taken (no skipping to rewrite, no combining index+rewrite in one deploy — isolated changes, attributed deltas).

### Runnable example (good — the sequence with this track's numbers)

```bash
# step 1 — read (50k rows, PG 16.15):
# Seq Scan on perf_events  (cost=0.00..769.59 rows=180 width=44)
# step 2 — index:
# CREATE INDEX perf_events_kind_idx ON perf_events (kind);
# step 3 — prove (ANALYZE, TIMING OFF):
# Bitmap Index Scan ... (cost=0.00..6.17 rows=250 width=0) (actual rows=1 loops=1)
# Execution Time: 0.073 ms
```

A hire quotes direction *and* caveat (estimates 250 vs actual 1 — stale statistics post-bulk-load, `ANALYZE` reconciles — honesty about divergence signals seniority louder than the speedup). Interviewers: ask "estimates say 250, actual 1 — problem?" (no — direction right; refresh stats; re-verify — measured response beats alarmed response).

### Common confusion (in candidates)

- **"add indexes until fast"** — red flag: unevidenced indexing (writes taxed per index, storage doubled — net-negative additions shipped confidently). Strong candidates EXPLAIN first (naming the node), index second (prescribing for the node), prove third (ANALYZE attached) — sequence, not enthusiasm.
- **"rewrite in the ORM"** — yellow flag as a *first* move: rewrites without plans optimize blind (new shape, unknown plan — possibly worse). Plan first (current cost named), then decide the lever (index? rewrite? both, ordered, attributed). Rewrites are third in the sequence for a reason.

### Performance note

The numbers *are* the answer (769.59 → 323.72 → 0.073ms actual — quoted above, re-measured per repo). Strongest form: "plan names the node, index serves the node, ANALYZE proves the serving — receipts per change, committed with the index." Evidence volunteered with sources beats evidence extracted; ranges beat points.

### Mentor note

Mock with "this query takes four seconds" — demand the plan command before any prescription ("EXPLAIN first — what does it show?"). Mentees graduate when step 1 is always the plan, step 2 the index, step 3 the proof — fashion-proof performance judgment in three steps (same drill as TSNode 04/5.1's loop profiling — method transfers across stacks).

## 3) "Transfer money safely" — transact it (plus rapid-fire)

### 3) **Definition** (the atomicity drill)

"Move $30 from ann to bo — make it safe" — screens for unit thinking: hires wrap (BEGIN/debit/credit/COMMIT), plan abandonment (catch → ROLLBACK → rethrow), and bind one connection (acquire-to-release lifecycle, never shared mid-unit). Single-statement answers ("one UPDATE... somehow") fail the unit; lifecycle answers pass before discussing isolation levels.

### What problem it solves (hiring signal)

Money movement is the canonical multi-statement hazard (partial application destroys conservation — value created or annihilated by crashes): engineers reaching for transactions reflexively protect every multi-write unit in the codebase (orders+items, multi-table mutations per action); engineers reaching per-incident protect none proactively. The drill predicts data-integrity culture directly.

### Modern guidance

Answer as the lifecycle (acquire → BEGIN → work → COMMIT → release; catch → ROLLBACK → rethrow — [3.1](<../3. Atomicity/3.1. Transactions basis.md>) part 3's five lines), quote conservation proof (70/80 post-commit — verified), name the contrast (unwrapped `partial` persisting after sibling `23505` — verified pair), and defer isolation theory honestly ("READ COMMITTED default suffices here; SERIALIZABLE on measured anomaly evidence — Domain 05 owns the models").

### Runnable example (good — the transfer, quoted conserved)

```bash
# BEGIN; UPDATE ann -30; UPDATE bo +30; COMMIT;
# committed: [{"owner":"ann","balance":70},{"owner":"bo","balance":80}]
# ROLLBACK probe: zed absent post-abort (undo complete)
# unwrapped contrast: partial persists after 23505 (half-intent live — the exhibit against hope)
```

### Rapid-fire drills (with answers)

1. **`UPDATE` matches zero rows — error?** No error, `rowCount: 0` (assert counts — silent no-op otherwise) ([01/2.1](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.1. First Postgres queries.md>)).
2. **Duplicate email insert — code?** `23505` + named constraint (branch on code, report constraint) ([2.1. Schema](<../2. Shape and speed/2.1. Schema and constraints that protect.md>)).
3. **Orphan order insert — allowed?** Refused (FK violation named — orphans structurally impossible) ([2.1. Schema](<../2. Shape and speed/2.1. Schema and constraints that protect.md>)).
4. **Cost 769 vs actual 1 row — worry?** No (direction right; refresh stats; re-verify — measured calm) ([2.2. Indexes](<../2. Shape and speed/2.2. Indexes and EXPLAIN.md>)).
5. **Gate exits 20 vs 21 — meaning?** 20: unfiltered destructive (shape); 21: FK index missing (evidence) ([4.1. Postgres checklist](<../4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)).
6. **Connection released mid-transaction — outcome?** Implicit abort (safety net — explicit ROLLBACK remains the strategy) ([3.1. Transactions](<../3. Atomicity/3.1. Transactions basis.md>)).

### Common confusion (in candidates)

- **"transactions are slow, avoid"** — transactions cost round trips + lock-hold (short units: negligible; the verified transfer commits in milliseconds); unwrapped sequences cost partial states (hours with misdirection, per occurrence). Price per unit, not per keyword — short transacted beats long unwrapped on every axis including speed (contention scales with length, not with BEGIN).
- **"isolation level first"** — basis before models (BEGIN/COMMIT/ROLLBACK/binding correct — 99% of application correctness; isolation levels tune the remaining anomalies — measured, rarely). Candidates leading with SERIALIZABLE reveal theory-first instincts; candidates leading with the lifecycle reveal production-first ones.

### Performance note

Transfer answers need the tight-unit footnote (statements only between BEGIN/COMMIT — no external awaits inside; lock-hold minimized — contention linear, never superlinear). Candidates volunteering unit-tightness unprompted show production awareness beyond correctness (correct *and* contention-safe — the complete answer).

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly data-health check. Drills 1 and 5 separate witness-readers (counts, exit codes) from hope-runners; ask those first when time is short.
