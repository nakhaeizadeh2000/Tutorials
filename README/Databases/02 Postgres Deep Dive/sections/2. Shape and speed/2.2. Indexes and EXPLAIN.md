# 2.2. Indexes and EXPLAIN

Making reads fast and proving it: indexes trading writes for reads, `EXPLAIN` narrating plans, and `EXPLAIN ANALYZE` measuring actuals. Junior read: index the filtered column, watch scans become seeks. Expert read: what estimates vs actuals diverge on, and which indexes earn their maintenance.

## 1) Indexes trade writes for reads

### 1) **Definition** (the maintenance bargain)

`CREATE INDEX ... ON perf_events (kind)` builds a lookup structure (B-tree by default — ordered keys to row pointers): filtered reads seek instead of scanning (the verified pair below: Seq Scan → Bitmap Index Scan); every write pays maintenance (index entries inserted/updated/deleted alongside rows — slower writes, larger storage). Reads fund the bargain per query; writes pay it per row.

### What problem it solves (history)

Unindexed growth (tables fast at hundreds of rows — every query a full scan nobody notices — then seconds at millions, discovered at peak traffic) produced the classic "database is slow" incident with a one-line fix outstanding for months. Indexes convert scan-shaped queries to seek-shaped (cost proportional to matches, not table size); the bargain holds wherever reads outnumber writes per row (almost everywhere outside append-only logs).

### Modern guidance

Index filtered/joined/ordered columns first (WHERE predicates, FK columns, ORDER BY keys — the shapes queries actually use, discovered via EXPLAIN in part 2, never guessed); measure write impact where writes dominate (bulk loaders, event ingestion — index maintenance per row, benchmarked); drop unused indexes quarterly (`pg_stat_user_indexes` scans showing zero — maintenance without readers, pure cost).

### Runnable example (good — 50k rows, scan then seek, verified live)

```bash
docker exec dbprobe psql -U postgres -c "INSERT INTO perf_events (kind) SELECT 'click' FROM generate_series(1, 50000);"
# INSERT 0 50000
docker exec dbprobe psql -U postgres -c "EXPLAIN SELECT * FROM perf_events WHERE kind = 'purchase';"
#  Seq Scan on perf_events  (cost=0.00..769.59 rows=180 width=44)
#    Filter: (kind = 'purchase'::text)

docker exec dbprobe psql -U postgres -c "CREATE INDEX perf_events_kind_idx ON perf_events (kind);"
# CREATE INDEX
docker exec dbprobe psql -U postgres -c "EXPLAIN SELECT * FROM perf_events WHERE kind = 'purchase';"
#  Bitmap Heap Scan on perf_events  (cost=6.23..323.72 rows=250 width=44)
#    Recheck Cond: (kind = 'purchase'::text)
#    ->  Bitmap Index Scan on perf_events_kind_idx  (cost=0.00..6.17 rows=250 width=0)
```

Verified on PostgreSQL 16.15: cost 769.59 → 323.72 (less than half before execution even runs), access method Seq Scan → Bitmap Index Scan. The planner chose *bitmap* (many matches expected — estimates said 250) over plain index scan — plan shapes vary per statistics; reading them (part 2) beats predicting them.

### Common confusion

- **"index every column"** — each index taxes every write (N indexes × maintenance per row — bulk inserts slowing linearly with index count) and storage (indexes rival table size on wide keys). Index *queried* shapes (evidence from plans/slow logs); every unqueried index is pure overhead wearing preparedness.
- **"primary keys need indexes"** — PKs/UNIQUEs build indexes automatically (declaration carries the structure — [2.1](<./2.1. Schema and constraints that protect.md>)'s constraints already index identity). Manual duplicates (`CREATE INDEX ... ON t(id)` where `id` is PK — redundant twin, maintenance doubled, benefit zero). Know what declarations already built before adding.

### Performance note

Index payoff scales with table size (hundreds of rows: noise; 50k: halved cost verified above; millions: scan-seconds vs seek-milliseconds — orders of magnitude). Write tax scales linearly (each index ~constant per-row maintenance — bulk-load windows measure it per index added). The bargain equation: reads-saved × read-frequency vs writes-taxed × write-frequency — computed per table, revisited per growth spurt.

### Mentor note

The 50k-row demo (seed → EXPLAIN scan → CREATE INDEX → EXPLAIN seek — five commands): run it per cohort and watch index-skeptics convert (cost numbers halving live beat theory permanently). Follow with "which columns get indexes *here*?" (their service's slow queries — EXPLAIN-driven, never guessed — the habit that generalizes).

## 2) `EXPLAIN` shows the plan

### 2) **Definition** (the database narrating itself)

`EXPLAIN <query>` prints the planner's chosen access path without executing: node types (Seq Scan, Index/Bitmap Index Scan, Nested Loop, Hash Join — *how*), costs (startup..total in abstract units — *relative*, not milliseconds), row estimates (planner statistics — *predictions*, actuals in part 3), widths (bytes per row — I/O shape). Reading plans precedes theorizing slowness — always, no exceptions (IT Vocabulary 05/1.2's thirty-minute rule, linked).

### What problem it solves (history)

Blind query tuning (rewriting SQL by folklore — "subqueries are slow," "joins are slow," "add DISTINCT" — each rewrite unmeasured, most neutral or harmful) burned optimization budgets on cold code while real costs (missing index here, fan-out there, stale statistics everywhere) sat one EXPLAIN away. Plan-first tuning aims effort (the costliest node named, with its share) before spending any.

### Modern guidance

EXPLAIN before theorizing (every "slow query" claim arrives with its plan or gets sent back for one); read top-down-costly-first (highest cost node — the bottleneck candidate; access methods — scan-vs-seek verdict per table); learn five node types deeply (Seq/Index/Bitmap scans, Nested Loop/Hash/Merge joins — 95% of plans composed from these; exotic nodes looked up per encounter, not memorized).

### Runnable example (good — the plan, read aloud, verified)

```bash
# Seq Scan on perf_events  (cost=0.00..769.59 rows=180 width=44)
#   Filter: (kind = 'purchase'::text)
# reading: full-table scan (Seq Scan), cost 769.59 total, ~180 rows ESTIMATED
# (actual: 1 — estimates vs actuals diverge; part 3 measures why it still matters)
```

```bash
# Bitmap Heap Scan ... (cost=6.23..323.72 rows=250 width=44) (actual rows=1 loops=1)
#   Recheck Cond: ... -> Bitmap Index Scan on perf_events_kind_idx
# reading: index-driven bitmap (which pages), heap fetch (which rows),
# cost less than half, actual 1 row — plan and reality agreeing directionally
```

Costs are *relative units* (compare within a plan version — 769 vs 323 meaningful; across versions/configurations — meaningless without ANALYZE actuals). Estimates (`rows=180/250` vs actual 1 — stale statistics on freshly loaded data: `ANALYZE perf_events` refreshes them — the maintenance part 3 prescribes).

### Common confusion

- **"cost is milliseconds"** — cost units are planner-internal (derived from `seq_page_cost`/`random_page_cost` settings — tunable, versioned, hardware-blind by default). Compare costs *relatively* (before/after index on the same box — direction and ratio meaningful); measure milliseconds with ANALYZE (part 3 — actuals, not estimates).
- **"Seq Scan means missing index"** — small tables scan *correctly* (planner prefers sequential under ~page-count thresholds — index overhead exceeding scan savings); selective predicates on big tables scan *wrongly* (the missing-index case). Scan-vs-seek verdicts need table size context (rows + selectivity — the plan shows both; read both before prescribing).

### Performance note

EXPLAIN itself costs planning only (milliseconds — safe anywhere, including production replicas for read-only queries; never EXPLAIN ANALYZE writes blindly — part 3's caution). Plan-reading skill compounds (five node types → every slow query triaged in minutes — the highest-leverage reading skill in data work, per ITV's thirty-minute rule).

### Mentor note

Onboarding rite: one slow-query plan read together (junior narrates nodes, mentor corrects — thirty minutes, per ITV 05/1.2): graduates read plans before theorizing forever after; the unguided read plans never (theorizing first is the default human setting — only guided practice overrides it). Highest-ROI thirty minutes in backend onboarding — schedule it week one.

## 3) Measure with EXPLAIN ANALYZE

### 3) **Definition** (proof over hope)

`EXPLAIN (ANALYZE, TIMING OFF)` executes the query and annotates each node with *actuals* (`actual rows=1 loops=1` — observed, not estimated) plus wall times (`Planning Time`, `Execution Time` — milliseconds, real). Estimates predict; actuals convict: estimate/actual divergence diagnoses stale statistics (refresh with `ANALYZE`), misplanning (cost settings vs hardware), and row-count surprises (data shaped unlike assumptions).

### What problem it solves (history)

Estimate-only tuning (plans read, indexes added, "should be faster" shipped — unmeasured, occasionally slower: misestimated selectivity choosing worse plans post-index) optimized predictions instead of executions. ANALYZE closes the loop (before/after actuals per change — improvement proven in milliseconds, regressions caught pre-merge). Hope deploys; proof merges.

### Modern guidance

ANALYZE per change (index added? plan altered? — before/after actuals quoted in the commit, the receipt habit from this track's gates); `TIMING OFF` where overhead matters (timing per-node perturbs micro-measurements — off for comparisons, on for absolute budgets); never ANALYZE mutating statements blindly (it *executes* — `INSERT/UPDATE/DELETE` analyzed actually write: wrap in transactions + `ROLLBACK` for dry runs, or analyze on staging clones).

### Runnable example (good — actuals convicting, verified live)

```bash
docker exec dbprobe psql -U postgres -c "EXPLAIN (ANALYZE, TIMING OFF) SELECT * FROM perf_events WHERE kind = 'purchase';"
#  Bitmap Heap Scan on perf_events  (cost=6.23..323.72 rows=250 width=44) (actual rows=1 loops=1)
#    Recheck Cond: (kind = 'purchase'::text)
#    Heap Blocks: exact=1
#    ->  Bitmap Index Scan on perf_events_kind_idx  (cost=0.00..6.17 rows=250 width=0) (actual rows=1 loops=1)
#          Index Cond: (kind = 'purchase'::text)
#  Planning Time: 0.031 ms
#  Execution Time: 0.073 ms
```

Verified: estimated 250 rows, actual 1 (statistics stale post-bulk-load — direction right, magnitude off: `ANALYZE perf_events` would reconcile); execution 0.073ms (sub-millisecond indexed fetch over 50k rows — the bargain's receipt in the only currency that matters). Planning (0.031ms) vs execution separated — optimize the larger (execution here, overwhelmingly; planning dominates only in pathological prepared-statement churn).

### Common confusion

- **"ANALYZE is safe anywhere"** — ANALYZE *executes* (reads run — safe on replicas; writes *write* — `EXPLAIN ANALYZE DELETE...` deletes, genuinely). Dry-run discipline (transaction-wrap + rollback, or staging data — never production writes "just to see the plan"). Read-only ANALYZE freely; mutating ANALYZE deliberately.
- **"actuals replace estimates"** — actuals describe *this* execution (data as-is, cache as-is — warm-cache actuals flatter cold reality); estimates describe the planner's *model* (used for every future planning decision — stale models misplan tomorrow's queries). Tune on actuals (what happened), maintain estimates (ANALYZE tables — what the planner believes), both, always.

### Performance note

Measurement cost: one execution per ANALYZE (the query runs — production reads fine on replicas; production writes never). Unmeasured-tuning cost: index additions that slow (maintenance without benefit — net negative, shipped confidently). Receipt-per-change (before/after actuals in commits) is the cheapest performance governance available — seconds per change, incidents prevented per quarter.

### Mentor note

Require before/after ANALYZE in every index PR ("show me 769→323 with actuals" — evidence, not assertion): two review cycles and teams self-serve (authors attach plans unprompted — the habit that ends "add index, hope" culture permanently). Plans in commits also document *why* the index exists (future droppers read the receipt before dropping — archaeology with answers).
