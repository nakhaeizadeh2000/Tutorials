# 2.1. Schema and constraints that protect

Declaring shape as contract: intent-revealing types, `NOT NULL` by decision, and `UNIQUE`/`CHECK`/`FOREIGN KEY` refusals with named errors. Junior read: constraints reject bad data with the reason attached. Expert read: why store-enforced invariants outlive every client, and what drivers surface per violation.

## 1) Types and NOT NULL declare intent

### 1) **Definition** (shape as contract)

Column types (`TEXT`, `INT`, `NUMERIC`, timestamps — chosen per meaning, not convenience) plus `NOT NULL` (presence required — decided per column, never defaulted blindly) declare what the data *is*: the schema as the executable specification every writer obeys regardless of language, driver, or era. `SERIAL PRIMARY KEY` adds store-owned identity (sequences, never app counters — [01/1.1](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.1. What databases are and are not.md>)'s durability applied to identity).

### What problem it solves (history)

Permissive shapes (all-nullable `TEXT` columns — "flexible" storage accepting garbage uniformly: ages of `'old'`, emails of `NULL`, totals of `'TBD'`) pushed validation entirely into application code (duplicated per client, skipped per deadline, drifted per language) — garbage in, garbage *stored*, garbage joined for years. Declared types reject at the boundary closest to the data: every client inherits correctness, none reimplements it.

### Modern guidance

Type per meaning (`NUMERIC` for money — exact, never float drift; `TIMESTAMPTZ` for instants — zones explicit; `TEXT` with `CHECK` for formatted values — pattern plus presence); `NOT NULL` by decision (nullable only where absence is meaningful — optional fields, genuinely unknown values; everything else `NOT NULL` — presence as contract); defaults where sensible (`status DEFAULT 'new'` — the store fills intent, clients omit innocently).

### Runnable example (good — declared shape, verified live)

```sql
-- shape as contract (PostgreSQL 16.15, docker, this session):
CREATE TABLE guarded_users (id SERIAL PRIMARY KEY, email TEXT NOT NULL UNIQUE, age INT CHECK (age >= 0));
CREATE TABLE guarded_orders (id SERIAL PRIMARY KEY, user_id INT NOT NULL REFERENCES guarded_users(id), total NUMERIC NOT NULL CHECK (total >= 0));
-- CREATE TABLE × 2 — intent executable: identity, presence, uniqueness, range, reference
```

### Common confusion

- **"`TEXT` for everything is pragmatic"** — `TEXT`-everywhere defers meaning to readers (is `age` numeric? parseable? — unknown until runtime failure); typed columns answer statically (clients, validators, and planners all see intent). Pragmatism that hides meaning bills interest per query — type once, benefit per read.
- **"NULL means missing, fine everywhere"** — NULL means *unknown* (three-valued logic: `NULL = NULL` is NULL, not true — [1.1](<../1. Query depth/1.1. Joins across tables.md>) part 2's discipline). Nullable-by-default columns infect every predicate with unknown-semantics (filters silently dropping rows — absence mishandled as false). Nullable by decision (meaningful absence only), `NOT NULL` otherwise.

### Performance note

Typed columns index and plan better (integer comparisons beat text casts; `NOT NULL` enables planner simplifications — nullability narrows row-width estimates and join selectivity). Permissive shapes cost per query (casts, null-checks, misestimated plans — death by a thousand planner pessimisms). Declaration is index-adjacent performance wearing a correctness costume ([2.2](<./2.2. Indexes and EXPLAIN.md>) measures it).

### Mentor note

Review schemas column-by-column ("why nullable? why TEXT? — decide aloud per column"): thirty seconds per column converts permissive habits to contract thinking within one review cycle. Mentees defending each nullability choice learn intent-declaration permanently; the schema becomes documentation no wiki maintains separately.

## 2) UNIQUE, CHECK, and FOREIGN KEY refuse

### 2) **Definition** (three refusals, three guarantees)

`UNIQUE` (no duplicates — identity per value, enforced), `CHECK (age >= 0)` (range validity — nonsense rejected with the rule named), `FOREIGN KEY ... REFERENCES` (referential integrity — orphans impossible, joins trustworthy). Each refusal arrives as a *named* error (constraint name + SQLSTATE code — machine-routable, human-readable): violations diagnosed, never debugged.

### What problem it solves (history)

Application-only validation (uniqueness checked via SELECT-before-INSERT — racing under concurrency: two writers, both see absent, both insert, duplicates stored; ranges checked in code — bypassed by every other client, script, and console) failed exactly under the conditions validation matters most (concurrency, multiplicity, time). Store constraints hold under all three (atomic checks at write time — race-free by construction, client-agnostic by position).

### Modern guidance

Constrain duplicables (`UNIQUE` on emails, slugs, natural keys — duplicates rejected, races closed); constrain ranges (`CHECK` on ages, totals, enums-as-text — nonsense named at write time); reference everything related (`FOREIGN KEY` per relationship — orphans structurally impossible, joins trustworthy by construction). Name constraints explicitly where teams read errors (`CONSTRAINT sane_age CHECK ...` — greppable names beat generated ones in incident channels).

### Runnable example (good — four refusals, verified live with exact errors)

```bash
docker exec dbprobe psql -U postgres -tAc "INSERT INTO guarded_users (email, age) VALUES ('ann@x.io', 40);"
# ERROR:  duplicate key value violates unique constraint "guarded_users_email_key"
docker exec dbprobe psql -U postgres -tAc "INSERT INTO guarded_users (email, age) VALUES ('bo@x.io', -3);"
# ERROR:  new row for relation "guarded_users" violates check constraint "guarded_users_age_check"
docker exec dbprobe psql -U postgres -tAc "INSERT INTO guarded_users (email) VALUES (NULL);"
# ERROR:  null value in column "email" of relation "guarded_users" violates not-null constraint
docker exec dbprobe psql -U postgres -tAc "INSERT INTO guarded_orders (user_id, total) VALUES (999, 5.00);"
# ERROR:  insert or update on table "guarded_orders" violates foreign key constraint "guarded_orders_user_id_fkey"
```

Verified: each refusal names its constraint (`guarded_users_email_key`, `_age_check`, not-null column, `_user_id_fkey`) — diagnosis complete without opening application code. Drivers surface codes structurally (verified via pg 8.23.0: `e.code '23505'` + `e.constraint 'guarded_users_email_key'` — branch on code, report the constraint, retry or abort by policy).

### Common confusion

- **"constraints slow writes"** — uniqueness checks cost an index probe per write (microseconds — the price of race-freedom); check constraints cost expression evaluation (nanoseconds — the price of validity). Unconstrained writes cost duplicate-resolution incidents (dedupe scripts, customer merges, downtime — priced in days). Micro-payments vs incident bills — constrain, always.
- **"FKs prevent scaling"** — foreign keys constrain *writes* (checked per insert — indexed probes, cheap); reads join identically with or without declared FKs (the planner doesn't need the declaration to join — it needs it to *trust*). Sharding stories complicate FKs (cross-shard references unenforceable — genuine limit, named explicitly when reached); single-database services have no such story (constrain freely until sharding evidence arrives).

### Performance note

Constraint overhead per write: NOT NULL (free — width bit), CHECK (expression eval — nanoseconds), UNIQUE (index probe — microseconds), FK (indexed lookup — microseconds). Incident overhead per missing constraint: duplicates/fan-out/orphans discovered downstream (dedupe labor + wrong reports + trust repair — unbounded). Constrain by default; measure before removing any (EXPLAIN-backed removal proposals only — evidence-gated relaxation, never fashion).

### Mentor note

The four-refusals demo (insert each violation live, read each named error aloud — five minutes): mentees watching the store defend itself stop treating constraints as ceremony and start treating them as tests. Follow with "which of these did your last project enforce in code?" (silence, then resolve — constraints added that week, incidents prevented that quarter).

## 3) Constraints are the cheapest tests

### 3) **Definition** (store-enforced invariants)

A constraint is a test the store runs on every write, in every environment, for every client, forever — costing its declaration once (one DDL line) and paying per violation prevented (each refused write a test passing silently). Application test suites cover paths they execute; constraints cover paths *nobody* executes (ad-hoc consoles, new clients, midnight hotfixes — the writes tests never see).

### What problem it solves (history)

Client-tested invariants (uniqueness asserted in CI — green suite, raced production; ranges validated in forms — bypassed by API clients; references checked in code — skipped by scripts) held exactly where tests ran and nowhere else (production writes arriving through untested paths — consoles, migrations, integrations — violating freely). Store tests hold at the only choke point all writes share: the write itself.

### Modern guidance

Constrain invariants, test behaviors (uniqueness/ranges/references in DDL — logic flows in suites — each layer owning what it sees best); assert constraints in CI (migration tests attempting violations — refused as expected, codes asserted: `23505` et al. — the refusal itself regression-tested); document the rule set per table (constraint inventory beside the schema — reviewers audit rules, not just columns).

### Runnable example (good — the refusal as regression test, verified shape)

```javascript
// migration test (shape — runs in CI against a scratch database):
// attempt duplicate email → expect code 23505 + named constraint (verified live above:
// driver-sees: 23505 | constraint: guarded_users_email_key)
// attempt orphan order → expect 23503-class refusal (verified live above — FK violation named)
// green suite = store still defending (refusals regression-tested, not merely declared)
```

### Common confusion

- **"constraints replace tests"** — constraints replace *invariant* tests (uniqueness/range/reference assertions migrate to DDL + refusal-tests); behavior tests stay in suites (flows, calculations, permissions — logic the store can't see). Layers, not substitutes: store tests invariants, suites test behaviors, gates assert both ([4.1](<../4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>) carries the pair).
- **"too many constraints brittle the schema"** — *wrong* constraints brittle it (over-strict CHECKs blocking legitimate evolution — relaxed via migration, priced visibly); *right* constraints stabilize it (invalid states unrepresentable — Tony Hoare's billion-dollar lesson, enforced per write). Review constraints for correctness (right rules), not count (fewer rules ≠ better schema — *true* rules do).

### Performance note

Constraint-suite cost: declarations (bytes of DDL) + refusal-tests (milliseconds per CI run — violation attempts are cheap writes). Unconstrained-invariant cost: application re-checks per client (duplicated logic, drifted rules — N implementations of one truth) + violation incidents (unbounded, per occurrence). Centralize invariants where writes converge (the store); distribute behaviors where logic lives (the suite).

### Mentor note

Frame constraints as "tests that outlive the test suite" (running for consoles, scripts, future clients — coverage no suite achieves): mentees graduate from test-counting (coverage %) to invariant-placing (which truths hold regardless of caller?) — the senior shift from verifying paths to guaranteeing states. Ask per schema review: "what does this table guarantee to *any* writer?" (answers become constraints; silence becomes findings).
