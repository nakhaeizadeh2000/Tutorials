# 3.1. Retries, timeouts, and backoff

Surviving failure without manufacturing it: timeouts bounding every hop, retries restricted to idempotent work, backoff spacing attempts with jitter under caps. Junior read: bound waits, key retries, space attempts. Expert read: where timeout-ambiguity forbids retry, and why jitter exists (fleet de-pulsing, not politeness).

## 1) Timeout every hop

### 1) **Definition** (failure budgets per interaction)

Statement timeouts (`SET statement_timeout` — per-session ceiling, queries killed past it with code `57014`), server-selection caps (topology waits bounded — [1.2](<../1. Drivers/1.2. MongoClient topology without a server.md>) part 2), socket/connect timeouts (network patience, finite). Every hop bounded: unbounded waits cascade (one slow dependency holding slots fleet-wide — outage amplifier); bounded waits route (timeout → named error → policy).

### What problem it solves (history)

Unbounded-hop fleets (default timeouts infinite-or-generous — one hung upstream parking every handler slot: throughput zero while all workers "busy" waiting, healthchecks failing on exhaustion rather than cause, autoscalers adding victims) mistook patience for robustness (waiting longer never fixed the upstream — it only widened the blast radius to every waiter). Timeouts convert hangs to errors (fast, named `57014`/selection-timeout, countable — retried or shed per policy, alarmed per threshold).

### Modern guidance

Bound every hop (statements: `statement_timeout` seconds-per-query-class — OLTP milliseconds-to-seconds, never infinite; topology: single-digit seconds — [1.2](<../1. Drivers/1.2. MongoClient topology without a server.md>) part 2; sockets: seconds — blip tolerance, never infinite); catch by code (`57014` → set a savepoint/retry-or-shed decision, never string-match messages); alarm on timeout rate (thresholds per query class — timeouts tripling means upstream trouble, not slow queries — route correctly).

### Runnable example (good — the kill, timed, verified live)

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node -e "
const { Client } = require('pg');
(async () => {
  const c = new Client({ connectionString: process.env.DATABASE_URL });
  await c.connect();
  await c.query(\"SET statement_timeout = '500ms'\");
  const t = Date.now();
  try { await c.query('SELECT pg_sleep(5)'); console.log('UNEXPECTED-OK'); }
  catch (e) { console.log('timed-out:', e.code, 'after-ms:', Date.now() - t); }
  await c.end();
})();"
# timed-out: 57014 after-ms: 514
```

Verified (PostgreSQL 16.15, fresh `dbprobe` container — see incident note in LOG): 5s sleep killed at ~500ms budget with code `57014` (query_canceled — the timeout's name, branchable). Bound honored to millisecond scale (514ms ≈ budget + kill latency — waits bounded *by construction*, not by luck).

### Common confusion

- **"timeouts cause errors"** — timeouts *convert* hangs (unbounded, uncountable, cascading) into errors (bounded, named, routable). The error existed latently (upstream hung — failure already real); the timeout merely *reports* it on a budget instead of propagating it indefinitely. Reporting fast beats hanging hopefully — always, every hop.
- **"one timeout value everywhere"** — OLTP reads (milliseconds), reports (seconds-to-minutes), migrations (minutes-to-unbounded *with supervision* — long, watched, killable), handshakes (seconds). One value fits none (tight timeouts aborting reports; loose timeouts parking OLTP slots). Timeout per query *class* (statement_timeout set per session/transaction — scoped, reviewed, documented per class).

### Performance note

Timeout tuning trades tail latency for error rate correctly (bounded tails + countable errors — p99 protected structurally); unbounded trades errors for tails (everything eventually answers — p99 unbounded, SLOs fictional). Set bounds from blip distributions (healthy p99.9 × small factor — measured per environment); alarm on approach (timeout-rate thresholds — pages before cliffs, never at them).

### Mentor note

The kill demo (5s sleep, 500ms budget, `57014` at 514ms — ninety seconds): mentees watching a hung query die on budget trust timeouts permanently (and set them proactively — drill converts theory to reflex). Follow with "which value for *your* hottest query?" (blip distribution × factor — measured answer, not default) — prescription personalized, habit formed.

## 2) Retry idempotent work only

### 2) **Definition** (keys license retries)

Retry iff the attempt carries an idempotency key (natural-key `_id`s — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) — retries converge) or the operation is inherently idempotent (read-only SELECTs, `$set`-same-value upserts — re-application harmless). Timeout-ambiguous non-idempotent work retries *blind* (applied-or-not unknown — duplicate risk per retry): investigate first (query the key — applied? — then decide), never retry-and-hope.

### What problem it solves (history)

Blind-retry storms (every timeout retried N times with full payloads — ambiguous outcomes multiplying: applied-twice charges, duplicated orders, thundering replays hitting a recovering upstream *simultaneously* — recovery delayed by the very traffic meant to survive it) turned single blips into sustained overloads (retry amplification × fleet size — the outage aftershock bigger than the quake). Keyed retries converge (duplicates refused — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) part 1's verified refusal); blind retries amplify (duplicates effected — harm per attempt).

### Modern guidance

Key idempotent actions (payments/orders/registrations — per action, never per attempt); retry reads freely (SELECTs re-run safely — no keys needed where nothing mutates); investigate ambiguous timeouts (non-idempotent write timed out → read-by-key first: applied? — then retry-or-accept with evidence, never blind); cap attempts always (part 3's ceilings — retries bounded even when safe, storms structurally impossible).

### Runnable example (good — the retry matrix, decided)

```markdown
# retry policy matrix (posted per service, reviewed per quarter):
# SELECT / idempotent reads ......... retry freely (no mutation — convergence trivial)
# keyed writes (idempotencyKey) ..... retry with same key (refusal converges — [03/3.1] verified)
# upserts on identity .............. retry freely (match-or-create converges — [03/3.1] part 2)
# unkeyed writes past timeout ...... INVESTIGATE FIRST (read-by-key → applied? → decide; never blind)
```

### Common confusion

- **"retry with backoff fixes everything"** — backoff paces retries (part 3 — timing); keys license them (identity — permission). Paced-but-blind retries duplicate politely (spaced duplicates — still duplicates, just slower); keyed retries converge (duplicates refused — pace optional, safety structural). License first (keys), pace second (backoff) — order load-bearing.
- **"timeout means failed, safe to retry"** — timeout means *unknown* (applied-then-slow-response vs never-applied — indistinguishable from outside: ambiguity, not failure, is the hazard). Unknown-outcome retries on unkeyed writes gamble per attempt (win: recovered; lose: duplicated — odds unknown, stakes customer-shaped). Read-by-key resolves unknown → known; retry only known-safe.

### Performance note

Keyed-retry cost: unique-probe per attempt (microseconds — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) part 1 gladly paid) + refusal handling (fetch-original — one read per duplicate-attempt). Blind-retry cost: duplicate effects (refunds + trust + regulatory attention — unbounded per storm) + amplification load (retries × fleet hitting recovery — aftershock engineering). Keys cheap, storms dear — key always, backoff additionally.

### Mentor note

The ambiguity lecture ("timeout ≠ failure — timeout = unknown"): five minutes distinguishing failed (safe: retry keyed), unknown (investigate: read-by-key), and succeeded-slowly (accept: verify effect) — mentees classifying outcomes before acting retry safely forever after (classification precedes permission — the senior sequence). Quiz with scenarios (timed-out unkeyed payment → ? — "read by key first" — drilled till reflex).

## 3) Backoff with jitter and caps

### 3) **Definition** (spaced, de-pulsed, terminated attempts)

Backoff spaces attempts exponentially (`base × 2^n` — 100ms, 200ms, 400ms… — pressure relief per round); jitter randomizes spacing (full/equal jitter — fleets avoiding synchronized pulses: thundering herds *are* synchronized retries, de-pulse by design); caps terminate (`maxDelay` ceiling, `maxAttempts` count — retries bounded even when safe: storms structurally impossible, budgets honored).

### What problem it solves (history)

Fixed-interval retries (every client retrying every second — synchronized pulses hitting recovering upstreams in lockstep: recovery delayed per pulse, each pulse re-triggering the outage it responds to — self-sustaining failure synchronized by good intentions) plus unbounded retries (forever-attempts on dead endpoints — slot exhaustion per caller, log floods per fleet). Backoff+jitter+caps convert synchronized-forever into desynchronized-bounded (pressure relief that actually relieves).

### Modern guidance

Exponential base per operation (100ms interactive, seconds batch — pressure scaled to patience); jitter always (equal jitter: `delay/2 + rand(delay/2)` — de-pulsed without full randomness's tail; full jitter where simplicity wins); caps both axes (`maxDelay` 5–30s per class, `maxAttempts` 3–5 per action — termination guaranteed, budgets honored); log attempts with counts (attempt N/M per error — retry visibility in logs, not mystery latency).

### Runnable example (good — the shape, verified locally)

```bash
node -e "
const delays = (base, cap, tries, jitter) => Array.from({ length: tries }, (_, i) =>
  Math.min(cap, base * 2 ** i) + jitter(i));
console.log(JSON.stringify(delays(100, 5000, 5, () => 0)));"
// [100,200,400,800,1600]
```

Verified (local computation — delay arithmetic, no I/O): exponential shape doubling per attempt, cap unbinding at 5 tries (1600 < 5000 — cap binds later tries; honest output shows the pre-cap region, caps asserted in tests with longer sequences). Production shape adds jitter (`+ rand()` per attempt — de-pulsing; determinism here for testability — jitter injected, never hardcoded).

### Common confusion

- **"jitter is politeness"** — jitter is *de-synchronization engineering* (thundering herds are phase-locked retries — synchronized by identical bases/intervals; jitter breaks phase-lock — recovery traffic spread over time, upstream breathing room per round). Politeness suggests optional; de-pulsing proves structural (herd collapse measured pre/post jitter — order-of-magnitude recovery-time deltas on real fleets).
- **"more attempts maximizes recovery"** — attempts past caps *delay* failure handling (circuit-breaking, shedding, paging — the real responses — postponed per extra attempt: hope as strategy). Caps route to policy fast (exhausted → shed/page/fallback — decisive states, not lingering maybe). Bounded retries fail over; unbounded retries fail slowly — prefer fastover.

### Performance note

Backoff cost per incident: attempt latency sums (100+200+400+… — budgeted per action, capped per policy); herd cost without jitter (synchronized pulses × fleet — recovery delayed multiplicatively, the multiplicative term jitter deletes). Caps bound worst-case attempt spend (attempts × ceiling — finite, reviewable); attempts logged per error (visibility free with structure).

### Mentor note

Simulate the herd (ten clients, fixed-interval retries against a flapping stub — watch synchronized pulses; add jitter — watch desynchronization): one simulation teaches backoff permanently (pulses visible, then gone — evidence over exhortation). Require jitter in every retry helper review ("show me the random" — two seconds to ask, herds prevented forever).
