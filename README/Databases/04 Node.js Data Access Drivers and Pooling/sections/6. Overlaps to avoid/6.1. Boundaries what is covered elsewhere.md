# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for data access. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the access-vs-mechanics split that keeps driver knowledge in exactly one place per question.

## 1) Foundations and depth (neighbor domains own the ends)

### 1) **Definition** (the access sandwich)

*First contact* (handshakes, secrets, CRUD, choosing — Domain 01, assumed fluent) below; *depth* (joins, aggregates, indexes, transactions, documents — Domains 02–03, assumed readable) beside. This domain owns the *access*: pools, topology, checkouts, migrations, retries. Questions about queries go back/sideways; questions about holding databases from Node stay here.

### The assignments (with the exact targets)

- Foundations (URLs, handshakes, secrets, gates) → [01 Database Foundations](<../../../01 Database Foundations and Mental Model/README.md>). Every probe here assumes proven connections and bound parameters — no re-teaching, ever.
- Postgres depth (joins, plans, constraints, transactions basis) → [02 Postgres Deep Dive](<../../../02 Postgres Deep Dive/README.md>). Pool sizing serves measured queries; checkout binding carries transacted units — depth assumed, access added.
- MongoDB depth (pipelines, modeling, indexes, idempotent writes) → [03 MongoDB Deep Dive](<../../../03 MongoDB Deep Dive/README.md>). Topology options declare behavior drivers execute; idempotency keys license retries — depth assumed, access added.
- Naming level (pool/topology/migration as words) → [IT Vocabulary 05](<../../../../ITVocabulary/05 Data Databases and AI Vocabulary/sections/1. Data words/1.2. Database table query and index.md>) (words owned there; mechanics owned here).

### Common confusion

- **"access subsumes depth"** — access *consumes* depth (pools serve measured queries — unmeasured queries pooled are unmeasured at scale; checkouts carry transacted units — unwitnessed units carried blindly). Consuming without understanding misattributes (pool blamed for plan failures — the misrouting this split prevents). Depth first (02–03), access second (here) — order matters, both matter.
- **"driver docs replace this domain"** — driver docs specify *APIs* (signatures, options, defaults — reference); this domain teaches *discipline* (sizing, binding, versioning, retrying — judgment). APIs without discipline misconfigure correctly-called functions (valid calls, wrong values — the incident class discipline prevents). Reference the docs; practice the discipline — different jobs, different homes.

### Mentor note

Teach mentees to read this page as a router: "query" questions go to 01–03, "holding" questions stay here. The distinction resolves half of all data-access debates before they start — most are depth-questions asked in access-rooms ("is the pool slow?" during an unindexed-query incident), or the reverse.

## 3) Design and mapping (planned siblings own the ends)

### 3) **Definition** (the access/design/map split)

*Access* (this domain: holding databases from Node — pools, checkouts, migrations, retries) vs *modeling* (Database Design track: normal forms, key strategy, migration *planning* — planned sibling) vs *mapping* (ORM track: entities, query builders, migration *tooling* — planned sibling). Access executes versioned migrations; siblings plan and abstract them. Usage assumes modeled schemas; mapping assumes driver literacy (this domain's graduates evaluate ORMs by reading generated SQL — literate choice, never magic).

### The assignments

- Schema modeling (normalization, keys, migration strategy) → Database Design track (planned sibling per root README — textual forward, no dead link by design).
- Object mapping (entities, repositories via ORM, migration runners) → ORM track (planned sibling per root README — textual forward, no dead link by design).
- Repository seams (policy surviving store swaps) → [DesignPatterns 06/1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>) (seam owned there — accessed clients pass through it).

### Common confusion

- **"migration runners belong here"** — runner *tools* belong to siblings (Flyway/Liquibase/ORM CLIs — evaluated there); migration *discipline* belongs here (versioned files, expand/contract, prove-before-mutate — [2.2](<../2. Discipline/2.2. Migrations basis.md>)). Tools automate discipline; discipline precedes tools (unphased migrations run by excellent runners still flag-day — mechanism without method, same outage, faster tooling).
- **"access complete without ORM evaluation"** — access completes at drivers (pools/checkouts/migrations/retries — this domain, fully); ORM *evaluation* completes judgment (reading generated SQL per [02-adjacent N+1 literacy] — the [01/6.1](<../../../01 Database Foundations and Mental Model/sections/6. Overlaps to avoid/6.1. Boundaries what is covered elsewhere.md>) usage→design→mapping order). Evaluate ORMs from driver literacy (graduation exercise, not prerequisite).

### Mentor note

The one-sentence router for access: "Query questions go back/sideways (01–03), theory waits (05–07), models live in siblings, *holding* stays here." Pools/topology/checkouts/migrations/retries — the access layer with its own craft, its own checklist, its own interview.
