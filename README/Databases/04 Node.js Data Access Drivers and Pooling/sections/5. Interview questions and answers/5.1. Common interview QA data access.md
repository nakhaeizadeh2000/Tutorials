# 5.1. Common interview QA: data access

Canonical answers for the three data-access questions every backend interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their numbers. Expert read: each answer runs evidence (verified counts, codes, gates) before conclusions — prediction first, output as confirmation.

## 1) "Pool size 10 — why?" — price it

### 1) **Definition** (the sizing screen)

"Your service sets `max: 10` — justify it" — screens for arithmetic over defaults: hires derive from slots (Little's-law concurrency needing simultaneous connections — burst ÷ latency, headroom ×1.5) capped by server share (`max_connections` ÷ pools connecting — replicas × services). Default reciters ("pg defaults to 10") fail; pricers pass before naming a number.

### What problem it solves (hiring signal)

Pool sizing is the most common unexamined configuration in data-backed services (defaults everywhere — connection counts scaling with topology, not load): engineers answering from arithmetic size deliberately (reviewed, maintained, re-derived per growth); engineers answering from defaults inherit quiet-hours pages (topology-scaled counts, 3 a.m. timing). The question predicts operational ownership directly.

### Modern guidance

Answer with the two-sided derivation (slots-needed from concurrency math, server-share cap from `max_connections` ÷ total pools — the smaller governs), quote the burst evidence (20 queries through max-5 in 218ms — queueing designed, peak held — verified this session), and name the re-derivation trigger (traffic doubling, replica changes, new services on the server — arithmetic re-runs per growth, never set-and-forget).

### Runnable example (good — the derivation, quoted)

```bash
# burst evidence (verified live, pg 8.23.0 + PG 16.15):
# per-query connects: 143 ms for 10  (~14ms handshake each — the unamortized tax)
# pooled burst 20x50ms max5: 218 ms  (≈4 waves — queueing by design, peak held at 5)
# pool peak: 5 idle-after: 5 → drained total: 0  (held, shared, emptied — observably)
```

A hire narrates "14ms per handshake argues pooling; 4 waves argue slots; peak-5-held argues caps work; drained-0 argues hygiene" — four numbers, four arguments, one `max`. Interviewers: ask "traffic 10×s — what moves?" (re-derive: slots first, server-share second, max moves deliberately with both cited).

### Common confusion (in candidates)

- **"bigger is safer"** — red flag: oversubscribed servers contend internally (throughput peaks then falls — the pool-size knee, measured per workload). Safety lives at the knee (latency flat while growing — stop before the rise), not at the maximum. Bigger-is-safer reveals unmeasured thinking; knee-seeking reveals profiles.
- **"defaults are tuned"** — defaults encode *tutorial topology* (one service, one database — pg's `max: 10` guesses reasonably there and wrong everywhere else: ten services × default = 100 baseline connections). Tuned-for-whom is the follow-up that separates (singularity vs fleet — topology named, default judged accordingly).

### Performance note

Sizing answers need the queueing footnote (checkout-wait histograms — p99 wait vs p99 query: wait-dominated grows max server-permitting; query-dominated indexes per [02/2.2](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.2. Indexes and EXPLAIN.md>)). Numbers volunteered with sources (burst timings quoted above) beat numbers recited; ranges beat points.

### Mentor note

Mock with "justify this max" pointing at an un-commented pool config (no arithmetic attached): mentees graduate when the answer starts "I can't — no derivation present" (reviewing the absence, not inventing numbers). Sizing comments demanded per review thereafter ("sized from what?" — [track habit], asked thrice, formed permanently).

## 2) "Mid-transaction pool release" — diagnose it

### 2) **Definition** (the binding screen)

"Connection released mid-transaction — what breaks?" — screens for object-lifecycle thinking: hires trace the unit (BEGIN bound to checkout A; release returns A open; borrower B inherits open transaction — B's queries joining A's unit, A's ROLLBACK abandoning B's work, pool poisoning cascading borrower-to-borrower). Object-tracers pass; pool-abstraction reciters ("the pool handles it") fail before the second sentence.

### What problem it solves (hiring signal)

Transaction/pool interplay is the least интуитивно understood data mechanic (invisible binding — no syntax marks which connection carries the unit; failures presenting as *other* borrowers' mysteries — borrower B's queries failing inside borrower A's abandoned unit). Engineers tracing object lifecycles diagnose in minutes; engineers trusting pool magic debug for hours across the wrong borrowers.

### Modern guidance

Answer as object-trace (checkout → BEGIN binds → release *after* COMMIT/ROLLBACK only — the lifecycle from [2.1](<../2. Discipline/2.1. Checkout discipline.md>), quoted with counts: 1/0 held, 1/1 released — verified); name the poison path (early release → open unit lent → borrower joins → originator rolls back → borrower loses work — cascade narrated stepwise); prescribe construction (try/finally release — every path returns; leak monitors on counts — drift paged distinctly from slowness).

### Runnable example (good — the lifecycle counts, quoted)

```bash
# verified live (pg Pool, this session):
# checked-out: total 1 idle 0   (exclusively held — one unit, one object)
# unit-committed (70→65/50→85 — conserved on the checkout)
# released: total 1 idle 1      (returned clean — committed, never open)
```

A hire narrates "held 1/0 (mine), committed (conserved), released 1/1 (clean)" — counts witnessing binding at each step. Interviewers: ask "release *before* COMMIT — who breaks?" (next borrower inherits open unit — poison path narrated stepwise; then the fix: finally-release, counts monitored).

### Common confusion (in candidates)

- **"pool.query sequences transact"** — red flag (each `pool.query` may borrow differently — BEGIN on A, writes on B/C autocommitted, COMMIT theater on A — [2.1](<../2. Discipline/2.1. Checkout discipline.md>) part 1's verified exhibit). Candidates asserting pool.query-transactions reveal untested mental models (never watched the scatter — the lifecycle demo from [2.1](<../2. Discipline/2.1. Checkout discipline.md>) converts in one run).
- **"release is cleanup, order flexible"** — release *position* is semantics (pre-COMMIT release = abandonment-by-lending; post-COMMIT release = clean return; finally release = total coverage). Order flexible nowhere (sequence load-bearing — acquire/BEGIN/work/COMMIT-or-ROLLBACK/release, unbroken). Flexibility claimed here reveals lifecycle blindness — probe with "release inside try before COMMIT?" and watch.

### Performance note

Binding answers need the hold-duration footnote (checkout-hold equals transaction length — short units release fast, pools stay fluid; tight units from [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>) part 1, pooled spelling). Candidates volunteering hold-awareness show production thinking beyond correctness (correct *and* contention-safe — the complete answer).

### Mentor note

Whiteboard the poison path with boxes (borrower A opens, releases early, borrower B inherits, A rolls back — arrows per step, victims labeled): mentees tracing object flow across borrowers own binding permanently (lifecycles visualized once, internalized forever). Box-tracing beats paragraph-reading for lifecycle mechanics — draw, don't describe.

## 3) "Migration locked prod" — prevent it (plus rapid-fire)

### 3) **Definition** (the evolution drill)

"Deploying a column rename locked production — walk me through prevention" — screens for phased-evolution thinking: hires answer expand/contract (additive first, backfill, enforce last — [2.2](<../2. Discipline/2.2. Migrations basis.md>) part 2's verified sequence), prove-before-mutate (handshake + pending-list + backup check — part 3), and versioned files (numbered, tracked, rerun-safe — part 1). Flag-day narrators ("just rename in one deploy") fail the drill regardless of seniority claimed.

### What problem it solves (hiring signal)

Schema evolution under rolling deploys is the highest-blast-radius data operation most teams perform routinely (instant DDL × gradual code = incompatibility windows sized as rollouts): engineers answering in phases prevent flag-day outages structurally; engineers answering in single deploys schedule them. The drill predicts deploy-incident rates directly.

### Modern guidance

Answer as the three phases with the verified receipts (expand nullable + backfill `UPDATE 1` → contract `ALTER TABLE` enforced → versions `001/002` tracked — all verified live this session); name the reversed-order failure (SET NOT NULL against NULLs errors — witnessed verbatim: "column contains null values" — later-constraints-validate-history, priced); close with proof-before-mutate (handshake, pending-list, `ON_ERROR_STOP` — context proven per run, never assumed).

### Runnable example (good — the phased receipts, quoted)

```bash
# expand: ALTER TABLE + UPDATE 1 (backfilled) → tracked 001_add_tier
# contract: ALTER TABLE (enforced, post-backfill) → tracked 002_tier_not_null
# versions: 001_add_tier + 002_tier_not_null (history queryable — drift detectable as unapplied)
# reversed-order failure (witnessed): column "tier" contains null values (history validated, loudly)
```

### Rapid-fire drills (with answers)

1. **Per-query Client in a handler — verdict?** Finding (unamortized handshakes — pool it; 143ms/10 measured) ([1.1. pg Pool](<../1. Drivers/1.1. pg Pool that serves.md>)).
2. **30s selection timeout in request path — verdict?** Finding (bound single-digit — failover patience, never default) ([1.2. MongoClient](<../1. Drivers/1.2. MongoClient topology without a server.md>)).
3. **`pool.query('BEGIN')` sequences — verdict?** Finding (scattered units — checkout explicitly) ([2.1. Checkout](<../2. Discipline/2.1. Checkout discipline.md>)).
4. **Console ALTER in prod — verdict?** Finding (unfiled evolution — version it; prove target first) ([2.2. Migrations](<../2. Discipline/2.2. Migrations basis.md>)).
5. **Unkeyed write timed out — retry?** Investigate first (read-by-key — unknown ≠ failed) ([3.1. Retries](<../3. Resilience/3.1. Retries timeouts and backoff.md>)).
6. **Gate exits 40 vs 41 vs 42 — meaning?** 40: bare pool (unsized); 41: scattered unit (unbound); 42: unbounded retry (unterminated) ([4.1. Access checklist](<../4. Important points to remember/4.1. Access checklist habits mentors insist on.md>)).

### Common confusion (in candidates)

- **"migrations are DBA work"** — migrations are *authored* by developers (phased files — expand/contract thinking per change) and *operated* with DBA discipline (proved runs, backup checks — rite per run). Unowned middle (developers writing unphased DDL, operators running unproven files) fails at 3 a.m. with no owner. Author phases, operate rites — ownership per layer, explicit.
- **"small tables skip phases"** — small tables skip *ceremony* (lightweight files, fast review — proportionate process), never *phases* (expand-before-contract holds at every size — lockstep renames break single-instance deploys too, given replicas or replicas-to-come). Phase-skipping justified by topology (proven single-instance atomic restarts), never by table size.

### Performance note

Evolution answers need the lock-conscious footnote (long validations split `NOT VALID` + `VALIDATE` where supported; backfills batched with LIMIT loops — hot-table etiquette, per [2.2](<../2. Discipline/2.2. Migrations basis.md>) part 1). Candidates volunteering lock-awareness show production thinking beyond correctness (evolution without contention — the complete answer).

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly data-health check. Drills 1 and 6 separate witness-readers (timings, exit codes) from hope-runners; ask those first when time is short.
