# 2.1. Checkout discipline

Binding transactions to pooled connections: acquire, transact, release — never shared mid-unit, leak-checked by counts. Junior read: `pool.connect()`, work, `release()` in finally. Expert read: why checkout-hold equals transaction length, and what idle/total counts prove per review.

## 1) Acquire, transact, release

### 1) **Definition** (the pooled lifecycle)

`pool.connect()` checks out one connection exclusively; BEGIN/work/COMMIT-or-ROLLBACK executes the unit on it ([02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>)'s lifecycle, pooled spelling); `release()` returns it (clean — committed or rolled back, never open). Five lines, unbroken order, one object throughout — the unit rule from 02/3.1 applied at pool scale.

### What problem it solves (history)

Pool-naive transactions (`pool.query('BEGIN')` — BEGIN on *whatever connection the pool hands per call*: subsequent statements landing on *different* connections (each `pool.query` re-borrows — the unit scattered across connections, atomicity voided silently) plus the pool believing all checkouts returned (nothing checked out — nothing to leak, nothing transacted either). Binding discipline (explicit checkout holding the unit) restores the object the lifecycle requires.

### Modern guidance

Checkout per transacted unit (explicit `pool.connect()` — never `pool.query` sequences for multi-statement units); lifecycle on the checkout (BEGIN→work→COMMIT/ROLLBACK→release — [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>) part 3 verbatim, pooled); single statements stay on `pool.query` (no checkout needed — autocommit suffices, per 02/3.1 part 1: wrap sequences, never singles).

### Runnable example (good — the pooled lifecycle, verified live)

```javascript
// pg 8.23.0 Pool, PostgreSQL 16.15 (docker, this session)
const c = await pool.connect();
// checked-out: total 1 idle 0
try {
  await c.query('BEGIN');
  await c.query('UPDATE ledger SET balance = balance - 5 WHERE owner = $1', ['ann']);
  await c.query('UPDATE ledger SET balance = balance + 5 WHERE owner = $1', ['bo']);
  await c.query('COMMIT');
  // unit-committed
} catch (e) { await c.query('ROLLBACK'); throw e; }
finally { c.release(); }
// released: total 1 idle 1
// rows: [{"owner":"ann","balance":65},{"owner":"bo","balance":85}]
```

Verified: checkout observed (total 1, idle 0 — exclusively held), unit conserved (65/85 — prior 70/80 moved by 5, books balanced), release observed (idle 1 — returned clean). Counts witness the lifecycle the way rowCounts witness writes ([01/2.1](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.1. First Postgres queries.md>) part 3's habit, connection spelling).

### Runnable example (bad — pool.query sequences, the scattered unit)

```javascript
// bad: each pool.query may borrow a DIFFERENT connection (unit scattered, atomicity void)
await pool.query('BEGIN');
await pool.query('UPDATE ledger SET balance = balance - 5 WHERE owner = $1', ['ann']);
await pool.query('UPDATE ledger SET balance = balance + 5 WHERE owner = $1', ['bo']);
await pool.query('COMMIT');
// BEGIN bound connection A; UPDATEs ran on B and C (autocommitted singles!); COMMIT committed nothing on A.
```

Why it hurts: silently autocommitted halves (each statement atomic alone — the unit unprotected while appearing transacted); COMMIT as theater (committing an empty unit on a borrowed connection — green logs, unguarded writes); error paths worse (ROLLBACK on yet another connection abandons nothing — partial states persist *despite* the error handling). Fix: checkout once (explicit object — the lifecycle needs a home, pools lend homes per checkout).

### Common confusion

- **"pool.query is transactional enough"** — `pool.query` is *statement*-safe (autocommit per call — correct for singles); *unit*-unsafe (no cross-call binding — sequences scatter). Statement safety ≠ unit safety (the category error behind every scattered-unit incident — name the unit, bind the unit, never assume the pool binds for you).
- **"checkout per request is wasteful"** — checkout per *transacted unit* (writes needing unity — minority of traffic); plain `pool.query` per single (reads and singles — majority, checkout-free). Waste would be checking out for everything (idle-held connections under read load — pool starvation by over-binding); precision binds transacted units only (binding where unity matters, borrowing elsewhere).

### Performance note

Checkout-hold duration equals transaction length (short units release fast — pools stay fluid; the tight-unit rule from [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>) part 1, pooled spelling). Pool sizing interacts (long-held checkouts shrink effective pool — max derived *including* transacted hold times, not just query counts — sizing arithmetic from [1.1](<../1. Drivers/1.1. pg Pool that serves.md>) part 2 extended with hold profiles).

### Mentor note

Review transacted code for the checkout line first ("where's the `pool.connect()`?" — absent means scattered, present means traceable): one question routing every transaction review (binding verified before logic read). Mentees internalize checkout-first thinking when reviewers ask consistently ("show me the object the unit lives on" — homes for units, always).

## 2) Never share mid-transaction

### 2) **Definition** (exclusive-hold rule)

A checked-out transacted connection serves exactly one unit (no concurrent use — no parallel queries on it, no passing to parallel branches, no shared helper pools mid-unit): interleaved foreign statements join the unit (committed or rolled back *with* it — corruption by sharing, structurally excluded by exclusivity). Helpers receive the client *sequentially* (awaited chains sharing `c` — ordered, never parallel).

### What problem it solves (history)

Shared-transaction concurrency (`Promise.all` over queries on one transacted client — statements interleaving mid-unit: helper B's read seeing helper A's uncommitted writes (phantom reads inside the unit — logic deciding on provisional data); error attribution impossible (which branch failed the unit? — interleaved, unknowable); rollback abandoning everyone's work (one branch's error discarding all branches' writes — blast radius by sharing). Exclusivity converts concurrency bugs into sequencing (await chains — slower per unit, correct always).

### Modern guidance

Await chains on transacted clients (sequential statements — order explicit, attribution trivial); parallelize *across* units (concurrent checkouts per independent unit — pool parallelism, unit isolation preserved); pass `c` down call chains (explicit parameter — ambient/global clients hide sharing; explicit parameters expose it to review).

### Runnable example (good — sequential sharing, contrasted)

```javascript
// good: sequential use of one checkout (ordered, attributable)
await c.query('UPDATE ledger SET balance = balance - 5 WHERE owner = $1', ['ann']);
await c.query('UPDATE ledger SET balance = balance + 5 WHERE owner = $1', ['bo']);
// order explicit (debit before credit — readable, auditable); failure attributable (which line threw).
```

```javascript
// bad: parallel use of one checkout (interleaved, unattributable)
await Promise.all([
  c.query('UPDATE ledger SET balance = balance - 5 WHERE owner = $1', ['ann']),
  c.query('UPDATE ledger SET balance = balance + 5 WHERE owner = $1', ['bo']),
]);
// pg protocol serializes per connection anyway (no true parallelism — false concurrency:
// all of sharing's hazards (interleaving, unattribution) with none of its speed).
```

Why parallel-on-one hurts *and* helps nothing: node-postgres multiplexes poorly per connection (protocol-level serialization — parallel calls queue opaquely, errors unattributable, ordering undefined). Exclusivity costs nothing measurable (sequential awaits on one connection — same wire time, defined order); sharing gains nothing (no parallelism exists to exploit — the hazard without the payoff, worst trade available).

### Common confusion

- **"parallel is faster, always parallelize"** — parallelize across *connections* (independent units on separate checkouts — true concurrency, pool-mediated); serialize within *one transacted connection* (protocol reality — false concurrency excluded structurally). Parallelism's home is the pool (many units, many checkouts); sequence's home is the unit (one checkout, ordered statements).
- **"helpers need their own checkouts"** — helpers *within* a unit share the unit's checkout (passed `c` — participating correctly); helpers *outside* units check out independently (own lifecycle — own fate). Checkout scope follows unit scope (same unit → same object; different units → different objects — scope alignment, reviewed per call).

### Performance note

Sequential-per-unit costs nothing vs false-parallel (same wire serialization — wall time identical, attribution gained free); parallel-across-units scales with pool size (true concurrency — throughput linear to knee, per [1.1](<../1. Drivers/1.1. pg Pool that serves.md>) part 2). Misplaced parallelism (within-unit) pays hazard without speed; placed parallelism (across-units) pays speed without hazard — position, not presence, decides.

### Mentor note

The `Promise.all`-on-one-client grep (`Promise.all` + shared `c` in transacted scopes — hits triaged live per review): mentees watching one shared-client incident (unattributable failure, rolled-back innocents) serialize thereafter permanently. Review parallel database calls for checkout scope first ("same unit or separate?" — scope question routing every concurrency review).

## 3) Leak-checked by construction

### 3) **Definition** (counts as proof)

Pool counts prove hygiene (`totalCount`/`idleCount` witnessed per lifecycle — checked-out 1/0, released 1/1, drained 0 — [1.1](<../1. Drivers/1.1. pg Pool that serves.md>) part 3's numbers, applied per unit); `try/finally` release guarantees return (every path — success, error, early-return — releases: construction, not vigilance); leak monitors alarm drift (`totalCount` growing unboundedly == checked-out-never-released accumulating — the metric paging before exhaustion).

### What problem it solves (history)

Leaked checkouts (early returns skipping `release()`, thrown errors bypassing it, forgotten awaits leaving checkouts dangling — pool draining over hours: `totalCount` at max, `idleCount` at 0, new checkouts queueing forever — the slow strangulation incident, misdiagnosed as database slowness for its first half-life) stemmed from release-as-afterthought (remembered on happy paths, forgotten on all others). `try/finally` construction makes leaking *unwritable* in the normal shape (release attached to acquisition syntactically — paths can't diverge past it).

### Modern guidance

`try/finally` every checkout (no bare acquire-release pairs — construction enforced in review: acquire without adjacent finally is a finding); monitor counts (total/idle/waiting dashboarded — drift alarms before exhaustion: total-at-max + idle-zero + queue-growing = leak signature, paged distinctly from slowness); timeout checkouts where supported (acquire ceilings — checkout waits bounded, never infinite — queue discipline per resilience habits in [3.1](<../3. Resilience/3.1. Retries timeouts and backoff.md>)).

### Runnable example (good — counts witnessing hygiene, verified live)

```bash
# from the verified lifecycle above:
# checked-out: total 1 idle 0   (held — exclusively, observably)
# released: total 1 idle 1      (returned — clean, observably)
# drained total: 0              ([1.1] part 3 — emptied, observably)
```

```javascript
// bad: release on happy path only (leak on every error — the strangulation shape)
const c = await pool.connect();
await c.query('BEGIN');
await c.query('...');        // throws → release skipped → checkout leaks
c.release();                 // happy-path-only release (errors bypass — pool drains over hours)
// Fix: try { ... } finally { c.release(); } — every path returns (construction, not vigilance).
```

Why happy-only hurts on a delay (leaks accumulate per error — error *rate* setting drain speed: quiet services take weeks (mystery slowness, misdiagnosed), error-prone services take hours (outage with a misleading shape — pool exhaustion presenting as database failure). Fix structurally (finally — one keyword, total coverage) and monitor counts (drift visible quarters before impact).

### Common confusion

- **"leaks crash loudly"** — leaks strangle quietly (gradual pool exhaustion — latency climbing as queueing grows, errors only at full starvation: symptoms mimicking database slowness for most of the incident's life). Quiet degradation misroutes triage (database blamed — indexes added, queries rewritten — while checkouts leak unattended). Monitor counts (leak signature distinct from slowness — total-max + idle-zero + queue — read the signature, not the symptom).
- **"GC collects leaked clients"** — unreleased checkouts stay *referenced* (pool registry holds them — reachable, uncollectable by design: the pool must track its own). GC collects garbage (unreachable); pools retain members (reachable registry entries — leaks by construction, collectable never). Release explicitly — the registry obeys code, not collectors.

### Performance note

Finally-release costs nothing (one call per unit — unconditional, microseconds); leak monitoring costs one dashboard (counts already exposed — observability free with the driver). Leaked-checkout incidents cost strangulation-hours (misdiagnosed as slowness — wrong fixes applied: indexes, rewrites, scaling — while checkouts drain unattended). Construction + counts: free prevention, free detection — fund both permanently.

### Mentor note

Require try/finally in review for every checkout ("show me the finally" — two seconds to ask, permanent habit to form): mentees internalize release-construction when reviewers ask thrice (third PR arrives finally-blocked unprompted). Pair with the counts habit (witness total/idle per lifecycle test — observability alongside construction, both permanent).
