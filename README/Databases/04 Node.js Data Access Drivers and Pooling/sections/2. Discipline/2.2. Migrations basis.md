# 2.2. Migrations basis

Evolving schemas without breaking running code: versioned migration files, expand-before-contract discipline, and proof-before-mutation runs. Junior read: numbered files, applied in order, tracked in a table. Expert read: why expand/contract ordering prevents deploy coupling, and what rerun-safety demands per statement.

## 1) Schema changes are versioned files

### 1) **Definition** (evolution with history)

Migrations are ordered, reviewable SQL files (`000_init.sql`, `001_add_tier.sql`, `002_tier_not_null.sql` — applied once each, recorded in `schema_migrations(version)`): schema evolution with the same properties as code evolution (diffs, reviews, history, rollback story). Ad-hoc `ALTER TABLE` in consoles leaves no record (unreviewed, unrepeatable, untraceable — archaeology for the next engineer).

### What problem it solves (history)

Console-evolved schemas (DBAs and developers ALTERing production directly — changes unrecorded, environments diverging: staging missing columns prod has, restores resurrecting dropped tables, new hires onboarding onto undocumented shapes) produced environment drift as the default state (each database a snowflake — "works in staging" meaningless, restores untrustworthy). Versioned files make environments converge (same files, same order, every database — drift detectable as unapplied versions, fixable by running them).

### Modern guidance

One file per change (atomic review units — DDL diffs readable, revertible individually); ordered names (numeric prefixes — application order unambiguous, no timestamps wars); tracked application (`schema_migrations` or tool equivalent — applied versions recorded *in the database*: truth about truth, queryable); rerun-safe statements (`IF NOT EXISTS`, idempotent backfills — re-running applied migrations no-ops instead of erroring, per the verified rerun below).

### Runnable example (good — versioned evolution, verified live)

```bash
cat > mig/001_add_tier.sql <<'EOF'
ALTER TABLE guarded_users ADD COLUMN IF NOT EXISTS tier TEXT;
UPDATE guarded_users SET tier = 'basic' WHERE tier IS NULL;
EOF
docker exec -i dbprobe psql -U postgres -v ON_ERROR_STOP=1 -f - < mig/001_add_tier.sql
# ALTER TABLE
# UPDATE 1
docker exec dbprobe psql -U postgres -tAc "INSERT INTO schema_migrations (version) VALUES ('001_add_tier') ON CONFLICT DO NOTHING;"
# INSERT 0 1
```

```bash
# rerun safety (same file, second run — verified live):
# ALTER TABLE  (NOTICE: column already exists, skipping — no error)
# UPDATE 1     (backfill idempotent — already-'basic' rows rewritten identically)
```

Verified on PostgreSQL 16.15: applied once (tracked), re-runnable without error (`IF NOT EXISTS` + convergent backfill — rerun converges, never corrupts). `ON_ERROR_STOP=1` aborts the file on first failure (partial-file application refused — file-level atomicity of *attempt*, distinct from transactional DDL, honestly noted).

### Common confusion

- **"migration tools are overkill early"** — *files* are the minimum (numbered SQL + tracking table — thirty lines of discipline, zero dependencies); *tools* (Flyway/Liquibase/node-pg-migrate/Prisma Migrate — ORM track territory) automate later (checksums, locks, rollbacks — earned at scale). Files first day one (unskippable); tools when files chafe (measured friction, not anticipated).
- **"down migrations for every change"** — down scripts rot (untested reversals — destructive, lossy, never run except in disasters where untested code is the last thing wanted); forward-only with expand/contract (part 2 — roll forward, never back: old code tolerates new schema, new code requires it — deploys decoupled, rollbacks rereleases). Down scripts documented as aspirational; forward compatibility engineered as real.

### Performance note

Migration cost per deploy: file application time (DDL locks brief per statement — seconds; backfill UPDATEs scale with rows — large backfills batched with `LIMIT` loops, lock-friendly); tracking overhead zero (one row per version — metadata, not data). Unversioned-evolution cost: drift incidents (environments disagreeing — debugging across snowflakes, hours per occurrence) plus restore roulette (backups of undocumented shapes — recovery untrustworthy). Files cheap, drift dear — version from the first ALTER.

### Mentor note

Require migration files from the second schema change onward (first CREATE is scaffolding; second change starts history — "where's the file?" asked once, answered forever): mentees versioning early never experience drift (environments converging by construction); console-ALTER veterans convert after one drift incident (scar tissue, administered kindly — pair the story with the fix, not the shame).

## 2) Expand before contract

### 2) **Definition** (decoupled evolution)

*Expand*: additive changes only (new nullable columns, new tables, new indexes — old code unaffected: unknown columns ignored, new tables unreferenced). *Migrate*: backfill + dual-write (data moved, both shapes populated — running code straddling versions safely). *Contract*: removal cheapest last (old columns dropped, NOT NULL enforced, old code retired — only after zero readers of the old shape remain). Three phases, two deploys minimum (expand ships vN-compatible; contract ships after vN retires).

### What problem it solves (history)

Lockstep migrations (column renamed in one deploy — old code reading `tier`, new schema without it: rolling deploys serving mixed versions failing halfway (vN pods crashing on vN+1 schema, vN+1 pods missing vN columns — the deploy that can only succeed atomically across a fleet that deploys gradually): each migration a flag day, each flag day an incident with a schedule. Expand/contract decouples (schema compatible with both code versions throughout — deploys independent, rollbacks rereleases, never reversals).

### Modern guidance

Additive first, always (nullable columns, new tables — deploys that old code survives by ignorance); backfill explicitly (UPDATE per row-set — batched at scale, verified by counts); enforce last (`SET NOT NULL`, drops, renames — only after readers/writers of the old shape reach zero, verified by code search + traffic observation); keep phases in separate files (001 expand, 002 contract — reviewable independently, deployable independently).

### Runnable example (good — expand, backfill, contract, verified live)

```bash
# expand (001, verified above): nullable tier added + backfilled to 'basic'
# contract (002, verified live):
docker exec -i dbprobe psql -U postgres -v ON_ERROR_STOP=1 -f - < mig/002_tier_not_null.sql
# ALTER TABLE
docker exec dbprobe psql -U postgres -tAc "SELECT email, tier FROM guarded_users;"
# ann@x.io|basic
docker exec dbprobe psql -U postgres -tAc "SELECT version FROM schema_migrations ORDER BY version;"
# 001_add_tier
# 002_tier_not_null
```

Verified: contract enforced *after* backfill populated (order load-bearing — the reversed order failed live in this session's probe: `SET NOT NULL` against NULL-containing column errors, the "later constraints validate history" lesson from [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>) witnessed verbatim). Expand→backfill→contract: sequence as correctness, not ceremony.

### Runnable example (bad — the flag-day rename, narrated)

```sql
-- bad: single-deploy rename (atomicity assumed across a gradual fleet)
ALTER TABLE guarded_users RENAME COLUMN tier TO plan;
-- rolling deploy: vN pods SELECT tier → error (column gone); vN+1 pods expect plan early in rollout (present —
-- but vN crash-loops until fully replaced). Mixed-version window = guaranteed partial outage.
-- Fix: expand (ADD plan nullable) → dual-write/backfill → contract (DROP tier after vN retires).
```

Why lockstep hurts: fleet deploys are gradual (mixed versions coexist for minutes-to-hours — any deploy moment has both readers); schema changes are instant (one ALTER — single moment). Instant schema × gradual code = incompatibility window sized as the rollout. Expand/contract makes every intermediate state compatible (old code tolerates new schema *and* vice versa — windows safe by construction).

### Common confusion

- **"small teams skip expand/contract"** — small teams skip it *until the first rolling deploy* (single-instance deploys tolerate lockstep — atomic restarts, no mixed window; second instance/replica introduces gradualism — the discipline becomes load-bearing exactly when growth arrives). Learn the shape on small fleets (cheap rehearsal); depend on it before scaling (expensive absence).
- **"contract phase is optional"** — uncontracted expands accumulate (nullable columns nobody fills, dead tables nobody drops, dual-writes nobody removes — schema archaeology billing every future reader). Contract scheduled per expand (ticket filed with the expand PR — "remove tier-nullability after vN retires, dated"): expansion without contraction is debt with a vague promise; dated contraction is hygiene.

### Performance note

Expand-phase cost: nullable columns (near-free — metadata only); backfill cost (UPDATE per row — batched at scale, off-peak scheduled); contract cost: constraint validation scans (table-wide check per enforcement — lock-conscious on hot tables: `NOT VALID` + `VALIDATE` split where supported, per Postgres docs). Lockstep-rename cost: outage window per deploy (downtime priced in availability + trust). Phased evolution trades small planned work for zero unplanned outages — always take the trade.

### Mentor note

Rehearse expand/contract on a toy table per onboarding (add-nullable → backfill → enforce — three files, one narrative): mentees performing the sequence once apply it forever (phased thinking internalized kinesthetically, not theoretically). Review schema PRs for phase-labels ("expand or contract?" — every migration file labeled, mixed-phase files split on sight).

## 3) Migrations prove before mutating

### 3) **Definition** (the pre-mutation rite)

Migration runs prove first (handshake `SELECT 1` — right host/database, per [01/1.2](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.2. Connecting from Node.md>); pending-versions listed — what's unapplied, reviewed before running; backup freshness confirmed — restorable *before* mutating, never assumed after). Mutations follow proof (migrate only through proven connections against backed-up databases — the rite from [01/4.1](<../../../01 Database Foundations and Mental Model/sections/4. Important points to remember/4.1. Data checklist habits mentors insist on.md>), migration spelling).

### What problem it solves (history)

Blind migrations (files run against assumed databases — wrong-host writes landing in staging-as-prod or prod-as-staging: the "oops heard across the office" with DDL permanence; unbacked-up mutations — failed migrations with no restore point: forward-fix under pressure as the only option, chosen poorly at 3 a.m.) combined permanence (DDL is hard to unring) with unverified context (wrong place, no safety net). Proof-before-mutation makes context explicit and recovery possible *before* irreversibility.

### Modern guidance

Prove connection per run (URL echoed redacted + `SELECT 1` green — wrong-database writes structurally prevented, not hopefully avoided); list pending first (`SELECT version FROM schema_migrations` vs files present — unapplied set reviewed, surprise files investigated); confirm backup recency (last successful backup timestamp + last restore *test* date — tested restores, not assumed dumps); run with `ON_ERROR_STOP` (first failure aborts the file — partial-file application refused, per the verified invocations above).

### Runnable example (good — the pre-mutation sequence, verified shape)

```bash
# prove (connection + identity — verified pattern from 01/1.2, migration spelling):
docker exec dbprobe psql -U postgres -tAc "SELECT 1;"                    # connection proven
docker exec dbprobe psql -U postgres -tAc "SELECT version FROM schema_migrations ORDER BY version;"
# 001_add_tier                                                           # applied set known
# 002_tier_not_null
# mutate (only after proof — -v ON_ERROR_STOP=1 on every invocation above):
docker exec -i dbprobe psql -U postgres -v ON_ERROR_STOP=1 -f - < mig/002_tier_not_null.sql
# ALTER TABLE                                                            # (idempotent rerun — NOTICE + success, verified)
```

### Common confusion

- **"CI proves enough"** — CI proves *migration correctness* (files apply cleanly against scratch — syntax, ordering, constraint validity); pre-mutation proof proves *target suitability* (right database, backed up, expected versions — context, not content). Content proven in CI (merge gate); context proven per run (deploy rite). Both gates, different moments — content-green never implies context-safe.
- **"read-only preview suffices"** — dry-run listings (pending versions — informative) without connection proof (handshake — substantive) verify intent, not target (correct files, wrong database — the failure mode that matters). Preview *and* prove (list pending *then* handshake *then* mutate — three beats, always in that order).

### Performance note

Proof cost per run: handshake + version query + backup check (seconds, mostly human-readable output — negligible beside migration runtime); unproven-mutation cost: wrong-database DDL (recovery measured in restore windows — RTO priced in downtime + trust). Seconds of proof vs hours of recovery — the most asymmetric trade in operations; prove always, mutate after.

### Mentor note

Require the three-beat prelude in every migration runbook (prove → list → mutate — printed at the runbook's top, executed per run): mentees internalizing prelude-first thinking extend it everywhere (deploys proved, rollbacks listed, deletes confirmed — caution as habit, not fear). Caution distinguished from fear explicitly (fear avoids action; caution verifies context then acts decisively — teach the difference by modeling it).
