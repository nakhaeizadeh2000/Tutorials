# 1.2. MongoClient topology without a server

Declaring MongoDB client behavior without a live server: topology options as intent, bounded waits as policy, and one shared client per process. Junior read: options in code, timeouts finite, single client. Expert read: what each option buys under failover, and why client-per-request is a connection storm wearing convenience.

## 1) Topology options declare intent

### 1) **Definition** (behavior versioned in code)

`new MongoClient(url, { maxPoolSize, serverSelectionTimeoutMS, retryWrites, ... })` declares pool bounds, wait budgets, and retry policy where reviewers see them (code, not tribal runbooks): `maxPoolSize` caps connections (server kindness, per [1.1](<./1.1. pg Pool that serves.md>) part 2's sizing, document spelling); `serverSelectionTimeoutMS` bounds topology waits (failover patience, finite); `retryWrites` opts into driver-retried writes (idempotent-shaped operations retried once, automatically).

### What problem it solves (history)

Default-shaped clients (unbounded pools, 30s selection timeouts, retry behavior assumed) met failovers badly (primary steps down → driver waits half a minute per operation *by default* → cascading timeouts fleet-wide before topology settles) and success quietly (defaults working = behavior unexamined = first failover a surprise curriculum). Declared options convert topology behavior from default to decision (reviewed, versioned, tested per environment).

### Modern guidance

Declare the three always (`maxPoolSize` sized — server-share arithmetic per [1.1](<./1.1. pg Pool that serves.md>) part 2; `serverSelectionTimeoutMS` at seconds-single-digit (failover patience, never 30s defaults in request paths); `retryWrites: true` where operations are idempotent-shaped (inserts with `_id`s, idempotent updates — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) — retries safe *because keys exist*, never as hope). URL vs code split: environment-varying in URL (hosts, credentials), behavior in code (reviewed options, tested values).

### Runnable example (good — options echoed back, verified driver-local)

```bash
node -e "
const { MongoClient } = require('mongodb');
const c = new MongoClient('mongodb://app:x@mongo-primary:27017/shopdb?retryWrites=true', { maxPoolSize: 10, serverSelectionTimeoutMS: 5000 });
console.log('pool:', c.options.maxPoolSize, '| timeout:', c.options.serverSelectionTimeoutMS, '| retryWrites:', c.options.retryWrites);
c.close();"
# pool: 10 | timeout: 5000 | retryWrites: true
```

Verified (mongodb driver, no server — construction and option resolution are local computation): declared values resolve exactly (URL flag + code options merged, readable back — configuration *witnessed*, not hoped). Server round-trips of these options are documented from the 8.3 manual (labeled per scope note from [01/1.2](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.2. Connecting from Node.md>)).

### Common confusion

- **"options are tuning, later"** — timeout options are *correctness-adjacent* (30s default waits convert failovers into fleet-wide cascading timeouts — behavior, not speed: bounded waits route failures fast, unbounded waits propagate them). Pool sizes tune performance; timeouts govern failure shape — set timeouts at authoring time (correctness), sizes at measurement time (performance).
- **"URL carries everything"** — URL carries *environment* (hosts/credentials/database — per-deploy values); code carries *behavior* (pool bounds, timeouts, retry policy — reviewed logic). All-in-URL strings bloat per environment (behavior duplicated across env files, drifting); all-in-code loses environment flexibility (hosts hardcoded — undeployable elsewhere). Split by variance axis: varying → URL, decided → code.

### Performance note

Option costs: `maxPoolSize` bounds throughput ceiling (too small queues client-side — checkout waits; too large pressures server — same knee as [1.1](<./1.1. pg Pool that serves.md>) part 2, document spelling); timeouts bound tail latency (failover waits capped — p99 protected structurally, not hopefully). Options priced per environment (staging values ≠ production values — reviewed per deploy, never copied blindly).

### Mentor note

Require the three options in every MongoClient construction review ("pool? timeout? retries? — show me"): two review cycles and teams declare topology deliberately forever after (defaults become the exception requiring justification, not the rule requiring discovery). Defaults-as-findings beats defaults-as-fate — ask thrice, habit forms.

## 2) Fail-fast and bounded waits

### 2) **Definition** (failure budgets per hop)

Every server interaction carries a bound: `serverSelectionTimeoutMS` (topology discovery patience — failover windows, measured in seconds), socket/connect timeouts (per-hop patience — network blips vs outages, distinguished by budget), and operation-level ceilings where supported (slow operations aborted, not awaited forever). Unbounded waits cascade (one slow dependency holding slots fleet-wide — the outage amplifier); bounded waits route (timeout → named error → retry-or-shed policy).

### What problem it solves (history)

Default-timeout fleets (30s selections, infinite sockets — "generous" settings encoding hope) converted single-host blips into fleet incidents (requests piling behind dead topology — slots exhausted waiting, healthchecks failing on exhaustion rather than cause, autoscalers adding victims to the pile). Bounded waits convert blips to errors (fast, named, countable — retried or shed per policy, alarmed per threshold).

### Modern guidance

Bound every hop (selection single-digit seconds — failover patience, never 30; sockets seconds — blip tolerance, never infinite; statements per [02-adjacent timeout habits](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>) — unbounded database waits cascade identically across stores); catch by name (`MongoServerSelectionError` → topology path: retry-with-backoff or shed-per-policy — [3.1](<../3. Resilience/3.1. Retries timeouts and backoff.md>) owns the policy); alarm on timeout rate (thresholds per operation — timeouts tripling means topology trouble, not slow queries — route correctly).

### Runnable example (good — bounded failure, timed, verified)

```bash
node -e "
const { MongoClient } = require('mongodb');
(async () => {
  const t = Date.now();
  const c = new MongoClient('mongodb://localhost:27018/?serverSelectionTimeoutMS=2000');
  try { await c.connect(); } catch (e) { console.log('bounded-fail:', e.name, 'after-ms:', Date.now() - t); }
  finally { await c.close(); }
})();"
# bounded-fail: MongoServerSelectionError after-ms: 2024
```

Verified (no server listening — the bound honored anyway): named error at ~2000ms (budget respected to the millisecond-scale — waits bounded *by construction*, not by luck). Contrast the 30s default (fifteen times the patience, fifteen times the slot-holding per blip — fleet arithmetic that pages at 3 a.m.).

### Common confusion

- **"short timeouts cause flakiness"** — short timeouts *reveal* flakiness fast (named errors, countable, alarmable — blips visible as blips); long timeouts *hide* it as latency (p99 climbing mysteriously — cause laundered into "slow database"). Visibility beats comfort (fast named errors route correctly; slow mystery latency routes nowhere). Tune bounds to blip distributions (p99.9 of healthy handshake × small factor — measured, per environment).
- **"retry on timeout always"** — retry *idempotent* work on timeout (keys exist — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) — safe); timeout-ambiguity on non-idempotent work retries *blind* (applied-or-not unknown — duplicate risk per retry). Timeout ≠ safe-to-retry (ambiguity, not failure, is the hazard — [3.1](<../3. Resilience/3.1. Retries timeouts and backoff.md>) owns the policy matrix).

### Performance note

Bounded waits trade tail latency for error rate correctly (timeouts converting unbounded tails into countable errors — p99 protected structurally); unbounded waits trade error rate for tails incorrectly (everything eventually answers — p99 unbounded, SLOs fictional). Tail-latency work *starts* with bounds (budgeted hops — then optimize the bounded path, never the unbounded hope).

### Mentor note

The timeout-fire drill (kill the database process, watch bounded errors arrive in ~2s with names — then restore, watch recovery): mentees witnessing fast named failure trust bounds permanently (and set them proactively — drill converts theory to reflex). Unbounded-default codebases get the drill first (evidence before prescription — show the 30s pileup, then bound it).

## 3) Single shared client per process

### 3) **Definition** (one topology view per process)

One `MongoClient` per process per deployment (module-singleton — created at boot, shared everywhere): single topology monitor (server discovery running once — failover observed coherently, not per-request rediscovered); single pool set (connections shared — server kindness, per [1.1](<./1.1. pg Pool that serves.md>) part 2's arithmetic, document spelling); single close point (shutdown drains once — [1.1](<./1.1. pg Pool that serves.md>) part 3's discipline, document spelling).

### What problem it solves (history)

Client-per-request code (MongoClient constructed per handler — topology rediscovery per request, connection storms per burst: servers counting hundreds of connections from one process, monitoring drowning in hello traffic) scaled control-plane load with request rate (linearly, unboundedly — the document twin of connect-per-request, same page different driver). Singleton clients fix control-plane cost per process (constant — discovery once, pools shared).

### Modern guidance

Singleton per deployment URL (module scope — created at boot with the handshake proof from [01/1.2](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.2. Connecting from Node.md>)); databases/collections accessed per operation (`client.db("shopdb").collection("orders")` — cheap handles, never new clients); close once at shutdown (drain discipline — [1.1](<./1.1. pg Pool that serves.md>) part 3, document spelling: stop accepting → close client → exit numbered).

### Runnable example (good — singleton shape, contrasted)

```javascript
// good: one client, many operations (module singleton — boot-once, share-everywhere)
const client = new MongoClient(process.env.MONGO_URL, { maxPoolSize: 10, serverSelectionTimeoutMS: 5000 });
await client.connect();  // once, at boot, with proof query
const orders = client.db("shopdb").collection("orders");  // handle per use, client shared
// ... thousands of operations, one topology monitor, one pool set ...
await client.close();    // once, at shutdown
```

```javascript
// bad: client-per-request (topology storm in request clothing)
async function getOrder(id) {
  const client = new MongoClient(process.env.MONGO_URL);  // discovery + pool per CALL
  await client.connect();
  const doc = await client.db("shopdb").collection("orders").findOne({ _id: id });
  await client.close();
  return doc;
}
// N concurrent requests → N topology monitors + N pool sets → server hello-storm + connection churn.
```

Why per-request hurts: control-plane multiplication (discovery traffic × requests — servers spending cycles on hellos, not queries); connection churn (pools built and torn per request — handshake latency per call, the unamortized tax from [1.1](<./1.1. pg Pool that serves.md>) part 1, document edition); close-race hazards (in-flight ops on closing clients — error surface per request, not per process). Singleton converts all three to constants.

### Common confusion

- **"singleton hinders testing"** — singleton hinders *unstructured* testing (hardcoded global — untestable); injectable singletons test cleanly (module exporting a creator + default shared instance — tests inject fakes/scratch clients, production shares one). Singleton-by-default with injection seams (constructor/factory parameters — testability designed, not sacrificed).
- **"multi-tenant needs multi-client"** — multi-tenant needs multi-*deployment* clients (one per distinct URL/credential set — keyed registry, bounded count); per-*request* clients even multi-tenant (tenant-keyed pool map, shared per tenant — cardinality bounded by tenants, never by requests). Bound cardinality by deployments, never by traffic.

### Performance note

Singleton control-plane cost per process: one monitor + bounded pools (constant — traffic-independent); per-request cost: full discovery + pool churn per call (traffic-linear — the storm curve). Request-rate growth converts per-request patterns from wasteful to outage-shaped (connection storms tripping server limits — the 3 a.m. page with a code-shape cause). Singleton at authoring time (free); storms debugged at scale (dear).

### Mentor note

Grep per-request constructions in review (`new MongoClient` / `new Pool` / `new Client` inside handlers — each hit a finding until proven singleton-or-justified): two review cycles and teams construct-once permanently (factories at module scope, handles per use — the shape that scales). Construction-site review (where objects are born) beats incident review (where storms land) — earlier, cheaper, kinder.
