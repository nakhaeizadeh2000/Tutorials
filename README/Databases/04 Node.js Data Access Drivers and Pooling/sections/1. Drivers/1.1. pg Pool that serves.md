# 1.1. pg Pool that serves

Sharing PostgreSQL connections across a Node.js process: pools amortizing handshakes, sized from arithmetic, drained on shutdown. Junior read: one Pool, queries through it, `end()` at exit. Expert read: what burst timing proves about queueing, and why pool size is capacity math, not configuration taste.

## 1) Pool amortizes handshakes

### 1) **Definition** (persistent-connection reuse)

`new Pool({ connectionString, max })` holds open server connections; `pool.query()` borrows one, runs, returns it — handshake paid once per connection lifetime, not per query. Per-query `Client` connects pay TCP+auth per request ([01/1.2](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.2. Connecting from Node.md>)'s handshake, repeated wastefully); pooled queries pay microseconds of checkout. Amortization is the entire pattern.

### What problem it solves (history)

Connect-per-request services (client constructed per handler — handshake latency added to every response, server connection counts exploding per replica: the "too many clients" page arriving with traffic) scaled handshake cost with request rate (linearly, unboundedly). Pools cap it structurally (fixed connections, shared across requests — handshake cost constant per process, query cost per request only).

### Modern guidance

One `Pool` per process per database (module-singleton — created at boot, shared everywhere, never per-request); queries via `pool.query()` for single statements (borrow-run-return invisibly — the common path); checked-out clients only for transactions (explicit `pool.connect()` — [2.1](<../2. Discipline/2.1. Checkout discipline.md>) owns the lifecycle). Per-query `Client` construction in request paths is a finding, not a style.

### Runnable example (good — the amortization, measured live)

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node -e "
const { Client, Pool } = require('pg');
(async () => {
  let t = Date.now();
  for (let i = 0; i < 10; i++) {
    const c = new Client({ connectionString: process.env.DATABASE_URL });
    await c.connect(); await c.query('SELECT 1'); await c.end();
  }
  console.log('per-query connects:', Date.now() - t, 'ms for 10');
  const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 5 });
  t = Date.now();
  await Promise.all(Array.from({ length: 20 }, () => pool.query('SELECT pg_sleep(0.05)')));
  console.log('pooled burst 20x50ms max5:', Date.now() - t, 'ms');
  await pool.end();
})();"
# per-query connects: 143 ms for 10
# pooled burst 20x50ms max5: 218 ms
```

Verified (pg 8.23.0, PostgreSQL 16.15 local docker): ~14ms handshake per connect (local — hundreds of ms cloud, the unamortized tax at scale); 20×50ms sleeps through 5 slots in 218ms (≈4 sequential waves — queueing visible in wall time: 20 queries / 5 connections, no more parallelism than slots, exactly as designed).

### Common confusion

- **"pool.query opens connections"** — `pool.query` *borrows* (checkout invisible — idle connection reused, or new one created up to `max`); only pool creation and growth open sockets (lazily — first queries warm the pool, verified `totalCount` climbing in part 2's probe pattern). Borrowing is microseconds; opening is milliseconds — the distinction the whole pattern exists to exploit.
- **"one pool per module"** — pools per *database* (one object, process-wide — modules import the shared pool, never construct: per-module pools multiply connections per feature (N modules × max — server caps hit by architecture, not traffic). Singleton by database URL (keyed registry where multi-tenant — one pool per distinct URL, never per call site).

### Performance note

Amortization ratio per process: handshakes-per-boot vs queries-per-lifetime (long-lived services: thousands-to-one — handshake cost vanishing; serverless/edge: worse ratios — pool *outside* the function (RDS Proxy/pgbouncer — pooled past the process boundary) where per-invocation pools can't amortize). Measure handshake share once (`time` cold boot vs steady query p50 — the ratio decides pooling architecture, not fashion).

### Mentor note

The burst-timing demo (20 sleeps through max-5 → ~4 waves in wall time): mentees watching queueing appear in milliseconds own pools permanently (slots as parallelism ceiling — intuitive forever after). Follow with "what if max were 20?" (no queueing, 20 server connections — the sizing question part 2 answers with arithmetic, not instinct).

## 2) Size from arithmetic, not default

### 2) **Definition** (slots math vs server caps)

`max` derives from two numbers: application concurrency (Little's-law slots needing simultaneous connections — burst ÷ per-query latency) bounded above by server capacity (`max_connections` ÷ pools connecting — replicas × services sharing one Postgres). Default `max: 10` is pg's guess (fine for one service on a dedicated server — wrong everywhere else: ten services × default = 100 connections before traffic exists).

### What problem it solves (history)

Default-sized fleets (every service `max: 10`, N services per database — connection counts growing with *deployments*, not *load*: "too many clients" pages during quiet hours, caused by a deploy adding replicas, not users) confused capacity with configuration (connections as settings, not resources). Arithmetic restores the resource view (slots needed × services sharing ÷ server cap = per-pool max, written down, reviewed per growth).

### Modern guidance

Compute per service (concurrent slots from [track-agnostic Little's law: rps × hold-time] — headroom ×1.5, then cap by server share: `max_connections` ÷ total pools); set explicitly in config (env `PGPOOL_MAX` — reviewed, never defaulted); re-derive per growth spurt (traffic doubles → arithmetic re-runs → max moves deliberately, with the server-cap check attached).

### Runnable example (good — the burst proving slots, verified)

```bash
# from the verified probe above: 20 concurrent queries through max: 5
# pooled burst 20x50ms max5: 218 ms  (≈4 waves — queueing, designed)
# pool peak: 5 (never exceeded max — the cap holding under burst)
```

```javascript
// bad: defaults everywhere (the quiet-hours page, narrated)
// 8 services × max: 10 (default) = 80 baseline connections on a max_connections=100 server
// + deploy surge (new replicas connecting before old drain) → "too many clients" at 3 a.m.
// Fix: max per arithmetic (slots × headroom, capped by server share) + deploy-aware headroom.
```

Why defaults hurt: connection counts scale with *topology* (services × replicas × pools) while defaults assume *singularity* (one service, one database — the tutorial topology every default encodes). Fleet reality violates the assumption on day two (second service, first autoscale). Arithmetic per service, capped per server — the two-line fix preventing the 3 a.m. page.

### Common confusion

- **"bigger pools are faster"** — bigger pools queue less *client-side* while pressuring the *server* (connections consume server memory/locks — oversubscribed Postgres contends internally: throughput *peaks then falls* with connection count — the pool-size knee, measured per workload, never assumed). Size to the knee (latency flat while growing, rising after — stop before the rise), not to impatience.
- **"`max: 1` serializes safely"** — serializes *everything* (one connection — full utilization per query, queueing per burst: latency linear in concurrency — correct only for migrations/scripts, never services). Floor for services: slots-derived (part-1 arithmetic — headroom included); ceiling: server-share-capped. Between floor and ceiling lies engineering; outside lies incident.

### Performance note

Pool-size tuning is the highest-leverage DB performance knob most teams never turn (default-shaped latency accepted as database-shaped — misattributed slowness budgets spent on query rewrites while queueing dominates). Measure queueing directly (checkout-wait histograms — pg exposes via events/timing; p99 wait vs p99 query — wait-dominated means grow max (server permitting); query-dominated means index (Domain 02), not pool).

### Mentor note

Demand the sizing comment beside every `max` (`max: 8 // 60 slots ÷ ... server share 100/12 pools — ADR-00X`): un-commented maxes get challenged ("sized from what?" — [track review habit]); commented maxes get maintained (numbers refreshed per growth — arithmetic living with the code). Two review cycles and teams size deliberately forever after.

## 3) Drain on shutdown

### 3) **Definition** (clean pool death)

`pool.end()` closes idle connections and waits for in-flight queries (drain, not kill — running work completes); post-`end()` queries reject (pool closed — fail-fast, never hang); process exit follows (event loop emptied — no socket keeping Node alive "mysteriously"). Shutdown sequence: stop accepting → drain pool → exit 0 (graceful, numbered, tested).

### What problem it solves (history)

Abrupt exits (SIGTERM → `process.exit()` with pool alive — in-flight queries severed mid-write: half-applied intent from the *application* side (database sees disconnected mid-transaction — rolls back, but the caller already counted success); sockets holding exits open (un-`end()`ed pools delaying shutdown past orchestrator grace — SIGKILL finishing what SIGTERM should have: unclean, unnumbered). Draining converts exits from amputation to completion.

### Modern guidance

Handle SIGTERM explicitly (stop server → `await pool.end()` → `process.exit(0)` — the sequence, in code, tested with signals); `end()` before exit always (even in scripts — one-shot jobs leaking pools hang "done" processes for seconds: mystery latency with a one-line fix); timeout the drain (grace budget — in-flight past N seconds gets logged, then forced: bounded grace beats infinite hang, per track resilience habits).

### Runnable example (good — drained to zero, verified live)

```bash
# from the verified probe: pool peak: 5 idle-after: 5 → await pool.end() →
# drained total: 0
```

Verified (`pool.totalCount`/`idleCount` witnessed): 5 live mid-burst, 5 idle after, 0 after `end()` — the pool emptied observably (counts, not hope). Un-`end()`ed twin hangs (sockets holding the loop — "done but won't exit" mystery, one line away from clean).

### Common confusion

- **"`end()` kills queries"** — `end()` *drains* (in-flight complete — graceful; idle close immediately). Killing needs explicit `pool.end()` racing termination (or `client.release(err)` per errored checkout — poisoned connections evicted, never reused). Drain-first is the default precisely because killing loses work — choose kill only past grace budgets, loudly.
- **"scripts don't need draining"** — scripts need it *most* (short-lived processes where pool-hang dominates runtime — 5s script + 30s socket-hang = 6× slowdown blamed on "Node startup"). One `await pool.end()` per script (finally-blocked — success and error paths alike drain).

### Performance note

Drain cost per shutdown: in-flight completion time (bounded by grace — seconds worst case, milliseconds typical); un-drained cost: orchestrator SIGKILL past grace (unclean kills mid-write — data risk, not just untidiness) plus mystery hang time (operators waiting on "stuck" deploys — minutes per rollout). Drain deliberately (coded sequence), exit numbered (0 clean — supervisors read what you return).

### Mentor note

Test shutdowns like features (SIGTERM the service under load — zero dropped queries, numbered exit, bounded duration — the drain test from service checklists): mentees watching graceful exits under kill signals trust shutdown code permanently (and write it — untested shutdown paths rot exactly like untested features). Kill-test quarterly; grace configured, not hoped.
