# 1.2. Isolation levels and anomalies

What concurrent transactions may and may not observe: read-committed defaults, priced anomalies, and serializable adopted on evidence. Junior read: dirty reads impossible, repeats unrepeatable, increments losable — all witnessed. Expert read: which anomaly each level permits, and what measured evidence justifies escalation.

## 1) Read committed: the default that suffices

### 1) **Definition** (no dirty reads, non-blocking readers)

PostgreSQL's default (`SHOW default_transaction_isolation` → `read committed`, verified on dbprobe): statements see committed data as of statement start (never uncommitted — dirty reads structurally impossible); writers never block readers (snapshots serve reads — [2.1](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>) owns the mechanism); each statement in a transaction sees a *fresh* snapshot (re-reads observe intervening commits — the non-repeatability part 2 prices).

### What problem it solves (history)

Locking-read engines (readers blocked behind writers — throughput collapsing under mixed workloads: reporting queries queuing behind OLTP writes, dashboards timing out per deploy window) traded correctness visibility for simplicity (one lock model, every reader waiting). Read-committed MVCC decoupled them (snapshots for readers, locks only for conflicting writers — mixed workloads flowing: reports concurrent with writes, neither starving).

### Modern guidance

Default everywhere initially (dirty-read-free + non-blocking reads — the 99% application correctness, per [02/5.1](<../../../02 Postgres Deep Dive/sections/5. Interview questions and answers/5.1. Common interview QA Postgres.md>)'s lifecycle-first rule); verify the default per environment (`SHOW default_transaction_isolation` in runbooks — assumed defaults drift per managed provider, printed beats hoped); escalate per anomaly evidence only (part 3's rule — measured non-repeatables/phantoms/skew in *your* workload, never theory).

### Runnable example (good — dirty read impossible, verified with concurrent clients)

```javascript
// pg 8.23.0, two clients, PostgreSQL 16.15 (docker, this session)
await a.query('BEGIN');
await a.query("UPDATE txn_demo SET balance = 999 WHERE owner = 'ann'");  // uncommitted
const dirty = await b.query("SELECT balance FROM txn_demo WHERE owner = 'ann'");
// dirty-read-blocked, B sees: 100   (committed truth — 999 invisible, structurally)
await a.query('ROLLBACK');
```

Verified: B reads 100 while A's 999 sits uncommitted (dirty reads impossible — no level, no flag, no luck involved: MVCC snapshots exclude uncommitted versions by construction). The 999 never existed for any observer (rolled back — aborted work leaves no trace readable at any level).

### Common confusion

- **"read committed means repeatable reads"** — committed *per statement* (each SELECT a fresh snapshot — re-reads observe intervening commits: 100 → 50 verified below). Repeatability needs *repeatable read* (snapshot per transaction — part 2's priced upgrade) or *application re-read discipline* (read-once-then-decide — often cheaper than escalation). Name-vs-behavior gap closed by demonstration, never documentation.
- **"default varies, check nothing"** — defaults *do* vary (managed providers, ORMs, drivers setting per-session levels — assumption drift per environment). `SHOW` per runbook (printed default — one line defeating a whole class of "works here, anomalies there" mysteries). Verify floors, then reason atop them — always.

### Performance note

Read-committed costs snapshot-per-statement (cheap — version visibility checks per row, index-assisted) with zero reader-writer blocking (concurrency maximal for the guarantee level). Stronger levels cost predicate tracking + abort rates (repeatable-read serialization failures, serializable conflict aborts — contention per level, priced in part 3). Default performance is the baseline (pay for observed anomalies only — upgrades evidence-gated, never speculative).

### Mentor note

The dirty-read demo (uncommitted 999 invisible to B — thirty seconds, two clients): mentees watching invisibility trust the default structurally thereafter (guarantees witnessed beat guarantees lectured). Follow with "what *can* B see across re-reads?" (committed changes — part 2's non-repeatable demo, immediately after: impossibility then possibility, paired).

## 2) Anomalies priced per level

### 2) **Definition** (three leaks, three prices)

*Non-repeatable read*: re-read observes committed change (100 → 50 verified — allowed at read committed; forbidden at repeatable read+). *Phantom*: re-query gains/loses rows (range membership shifting under concurrent inserts — allowed below serializable). *Lost update*: read-modify-write clobbers concurrent modification (110 not 120 verified — allowed at read committed; prevented by locking reads, atomic updates, or serializable). Each anomaly a level boundary (permitted below, forbidden above — priced per level, adopted per evidence).

### What problem it solves (history)

Anomaly folklore ("transactions are isolated" — unqualified, therefore false at every level for some anomaly: code correct under serial assumptions failing under read-committed reality — balance checks passing pre-write, overdrafts materializing post-commit) misled generations into assuming the strongest semantics at default cost. Priced anomalies replace folklore with a menu (each leak named, demonstrated, gated to its level — choose per measured need, pay per strength).

### Modern guidance

Demonstrate per workload (concurrent-client probes like below — anomalies reproduced *in your shapes* before escalation debates); fix at the cheapest sufficient level (lost update → atomic `UPDATE ... SET x = x + 10` or `SELECT FOR UPDATE` first — statement-level fixes before level escalation; phantom → predicate locking or serializable — evidence-gated); document the chosen level per service (default unless the anomaly register says otherwise — register kept: anomaly, reproduction, level, receipt).

### Runnable example (good — non-repeatable and lost update, verified live pair)

```bash
# non-repeatable read (allowed at read committed — verified):
# B reads 100 ... A commits 50 ... B re-reads 50
# nonrepeatable: 100 -> 50
```

```bash
# lost update (allowed at read committed — verified):
# A reads 100, B reads 100; A writes 110, commits; B writes 110, commits
# both-added-10-from-100, final: 110 (lost-update: true)   (expected 120 — 10 destroyed)
```

Verified pair (concurrent pg clients, same session): re-reads observe commits (100→50 — non-repeatable, permitted); read-modify-write clobbers (110≠120 — lost, permitted). Three fixes priced: atomic update (`SET balance = balance + 10` — no read, no loss — cheapest), locking read (`SELECT ... FOR UPDATE` — [2.1](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>) part 3), serializable (part 3 — retries included in the price).

### Common confusion

- **"lost update is a bug in Postgres"** — lost update is *permitted behavior* at read committed (each statement correct in isolation — read saw 100 truly, wrote 110 truly; the *sequence* assumed stability no level below serializable-plus-locking provides). Blaming the engine misroutes the fix (toward version upgrades — useless) from the application (atomic updates/locking reads — effective). Permitted ≠ correct-for-you (levels bound interference; applications own their assumptions).
- **"phantoms equal non-repeatables"** — non-repeatable: *same rows, changed values* (re-read divergence); phantom: *changed row membership* (re-query gaining/losing rows — range inserts/deletes between reads). Different shapes, different fixes (values → locking/atomic; membership → predicate locks/serializable). Conflating them mis-prescribes (locking rows doesn't stop range inserts — phantom needs predicate-level protection, named explicitly).

### Performance note

Anomaly economics per fix: atomic updates (free — statement shape, no level change); locking reads (row-lock contention — hot-row serialization, measured per workload); repeatable-read (snapshot-per-txn + serialization failures retried — abort rates per contention); serializable (conflict detection + retries — strongest guarantee, highest contention cost). Escalate cheapest-first (statement → lock → level — evidence per step, never theory-first).

### Mentor note

The anomaly zoo demo (dirty-blocked, nonrepeatable-allowed, lost-verified — three probes, one session, all green/red as predicted): mentees predicting each outcome before running own isolation permanently (prediction-then-output per anomaly — the method from this track's gates, applied to theory). Wrong predictions pinpoint the gap (which leak surprised? — that level's model re-taught immediately).

## 3) Serializable on measured evidence

### 3) **Definition** (strongest level, priced admission)

`SERIALIZABLE`: transactions behave *as if* serially ordered (predicate tracking + conflict detection — anomalies structurally impossible; conflicts abort with `40001` serialization_failure — retried by the application, budgeted in design). Admission priced: abort-and-retry rates under contention (hot workloads aborting percents — throughput paid per conflict), implementation burden (every transacted path retry-safe — idempotency per unit, per [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>)).

### What problem it solves (history)

Blanket serializable (strongest level everywhere — "safest," unmeasured: contention aborting percents of transactions on hot rows — throughput collapsing precisely where traffic concentrates; retry logic absent — aborts surfacing as user errors) traded unobserved anomalies for observed outages (correctness maximal, availability damaged — the cure priced above the disease it prevented). Evidence-gated serializable (proven anomaly → level + retries, scoped to affected units) pays strength only where leaks are witnessed.

### Modern guidance

Reproduce first (concurrent-client anomaly probes *in your shapes* — parts 1–2 pattern, per service); fix cheapest first (atomic/locking before levels — part 2's ladder, evidence per rung); escalate scoped (affected units serializable — `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` per transaction, never database-wide by default); retry by design (40001 handlers with backoff + idempotency keys — aborts are *expected control flow* at serializable, not errors: budgeted, logged, retried).

### Runnable example (good — the escalation ladder, decided)

```markdown
# anomaly evidence → cheapest sufficient fix (ladder, climbed on receipts):
# lost update witnessed → atomic UPDATE (SET x = x + 10 — no level change, verified shape)
# + hot-row contention measured → SELECT FOR UPDATE (locking read — contention priced per workload)
# + phantom/range anomaly reproduced → SERIALIZABLE scoped to the unit + 40001-retry with keys
# each rung evidenced (probes green/red as predicted); skipping rungs prohibited (theory-first escalation).
```

### Common confusion

- **"serializable means no retries needed"** — serializable *requires* retries (aborts are the mechanism working — conflicts detected, victims chosen, `40001` returned: application retries with backoff + idempotency, budgeted from day one of escalation). Unretried serializable converts detected conflicts into user errors (guarantee kept, usability broken — half-adopted strength worse than honest read-committed + locking).
- **"default serializable is safest"** — default-serializable serializes *throughput* (contention aborting under load — availability damaged fleet-wide for anomalies most workloads never exhibit). Safety measured per anomaly (reproduced? — escalate; theorized? — lifecycle + locks suffice). Safest is evidence-matched strength, never maximum strength by default.

### Performance note

Serializable pricing: abort rates (contention-proportional — hot rows aborting single-digit percents typically, double-digits pathologically); retry multipliers (attempts × unit cost — budgeted per action, capped per [04/3.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/3. Resilience/3.1. Retries timeouts and backoff.md>)'s ceilings); throughput ceiling (serial-equivalent ordering — concurrency bounded by conflict rate, measured per workload). Price before adopting (contention probes *first* — levels second, always in that order).

### Mentor note

Forbid theory-first escalation in review ("reproduce it here first" — concurrent-client probe or it didn't happen; "cheapest fix attempted?" — ladder rungs evidenced bottom-up): two blocked escalations teach evidence-gated levels permanently (strength earned by demonstration, never by anxiety). Anxiety-driven levels (serializable "to be safe") get the contention bill attached post-hoc — education via invoice, kindly administered.
