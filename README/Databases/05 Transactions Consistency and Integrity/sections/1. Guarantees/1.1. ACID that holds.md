# 1.1. ACID that holds

What transactions guarantee, witnessed live: atomic all-or-nothing, consistency as constraint preservation, durability across process death — with isolation previewed for [1.2](<./1.2. Isolation levels and anomalies.md>). Junior read: four letters, three live proofs. Expert read: which letter each mechanism carries, and where guarantees end and models begin.

## 1) Atomicity and Durability, witnessed

### 1) **Definition** (units and survival)

*Atomicity*: multi-statement units apply totally or not at all (BEGIN→work→COMMIT publishes everything; any failure abandons everything — [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>)'s lifecycle, witnessed again here). *Durability*: committed writes survive process death (restart the server — rows remain, proven below, not asserted). Two letters, one mechanism each (atomicity: the unit protocol; durability: write-ahead logging flushing before COMMIT acknowledges).

### What problem it solves (history)

Pre-transactional stores (early files, then auto-commit-only engines) offered statement granularity: multi-step business operations (transfer, order+items, migrate-with-backfill) failing mid-sequence left half-applied intent (money destroyed, orders itemless — unrecoverable except by compensating heroics, invented per incident). Atomic units plus durable commits moved partial failure from *normal* to *impossible-by-construction* (for single-system units — distribution reopens the question honestly in [3.1](<../3. Distribution/3.1. Distributed honesty 2PC and sagas.md>)).

### Modern guidance

Transact business units (one fate per user intent — transfers, multi-table mutations per action — never bare statement sequences for related writes); trust committed durability (WAL-flushed commits survive crashes — design recovery *around* committed state (replay from it), never *against* partial states (which cannot exist)); verify per environment (atomicity + durability probes in CI against scratch databases — guarantees asserted, not release-noted).

### Runnable example (good — atomic unit, then survival, verified live)

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node -e "
const { Client } = require('pg');
(async () => {
  const c = new Client({ connectionString: process.env.DATABASE_URL });
  await c.connect();
  await c.query('BEGIN');
  await c.query('UPDATE txn_demo SET balance = balance - 30 WHERE owner = \$1', ['ann']);
  await c.query('UPDATE txn_demo SET balance = balance + 30 WHERE owner = \$1', ['bo']);
  await c.query('COMMIT');
  console.log('atomic:', JSON.stringify((await c.query('SELECT owner, balance FROM txn_demo ORDER BY owner')).rows));
  await c.end();
})();"
# atomic: [{"owner":"ann","balance":70},{"owner":"bo","balance":80}]
```

```bash
docker restart dbprobe
docker exec dbprobe psql -U postgres -tAc "SELECT owner, balance FROM txn_demo ORDER BY owner;"
# ann|70
# bo|80
```

Verified (PostgreSQL 16.15, docker): conservation holds through the unit (100+50 = 70+80 — moved, never created/destroyed); committed state survives full container restart (process death — durability witnessed, second restart-proof in this track after S1's `probe_items`). Atomicity witnessed per unit ([02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>)'s transfer, re-proven); durability witnessed per restart (rows outliving processes — the guarantee backups extend, Domain 06 owns).

### Common confusion

- **"COMMIT means stored"** — COMMIT means *durably recorded* (WAL-flushed — survives crashes with default settings); *synchronous replication* decides standby survival (async standbys lag — committed-but-unreplicated writes lost on primary death: durability *tiers*, not absolutes — synchronous_commit settings trade latency for standby-durability per deploy, reviewed deliberately).
- **"atomicity means instant"** — atomicity means *indivisible visibility* (all-or-nothing to observers — never half-applied *seen*); intermediate states exist transiently (inside the unit, invisible by isolation — which is why isolation ([1.2](<./1.2. Isolation levels and anomalies.md>)) completes atomicity: units indivisible *and* interference-bounded).

### Performance note

Atomicity costs lock-hold duration (contention scaling with unit length — tight units from [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>) part 1, applied); durability costs fsync latency per commit (milliseconds — group commit batching concurrent commits into shared flushes: throughput preserved under concurrency, latency floored per commit). Synchronous replication adds network round trips (standby acknowledgment — latency for survival-across-boxes, priced per deploy, never defaulted blindly).

### Mentor note

Pair the two witnesses (transfer-conservation + restart-survival) as the ACID onboarding demo (five minutes, both green): mentees watching units conserve *and* survive trust transactions structurally thereafter (guarantees witnessed beat guarantees lectured — evidence over exposition, again). Follow with "which letter constrains *concurrent* units?" (isolation — previewed, modeled next in [1.2](<./1.2. Isolation levels and anomalies.md>)).

## 2) Consistency as constraint preservation

### 2) **Definition** (valid-to-valid transitions)

*Consistency*: every committed transaction moves the database from one valid state to another (validity defined by constraints — CHECK/UNIQUE/FK/NOT NULL from [02/2.1](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.1. Schema and constraints that protect.md>): violating writes refused *inside* the unit (aborting it — invalid states uncommittable, not merely discouraged). The C is the constraints' letter (declared rules carrying consistency — application code needn't (and can't reliably) hold it alone).

### What problem it solves (history)

Constraint-free consistency (validity enforced in application code — every client reimplementing rules, consoles bypassing all of them: negative balances stored, orphan rows accumulating, duplicates racing in) decayed per writer (each new client a new validity dialect — states valid-nowhere agreed upon nowhere). Constraint-carried consistency centralizes validity (one rule set, enforced at the choke point all writes share — states valid by construction, regardless of writer).

### Modern guidance

Declare validity in DDL (CHECK ranges, UNIQUE identity, FK references, NOT NULL presence — the rule set from [02/2.1](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.1. Schema and constraints that protect.md>), reviewed per table); test refusals in CI (violation attempts asserting codes — `23514` et al. — the refusal regression-tested, per [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)); never "validate later" (deferred validity is stored invalidity — cleanup migrations forever after: constrain at CREATE, per [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)'s two-timings rule).

### Runnable example (good — invalid transition refused, state preserved, verified live)

```bash
# attempt: negative balance through the unit (violates CHECK (balance >= 0)):
# consistency-refuses: 23514
# still-valid: {"n":2,"s":150}   (2 rows, total 150 — unchanged: refusal preserved validity)
```

Verified (same session, same table): `23514` names the violated CHECK; post-refusal state identical (n=2, s=150 — conservation intact: the invalid transition never happened, not "happened then fixed"). Consistency witnessed as *preservation under assault* (attempted invalidity refused — validity observable in what *didn't* change).

### Common confusion

- **"consistency means correct data"** — consistency means *rule-abiding* states (constraints satisfied — validity, not truth: a `balance: 70` obeying every rule may still mismatch reality (unrecorded cash payment — truth lives outside databases; validity lives inside). Databases guarantee validity (rules hold); applications pursue truth (reconciliation, audits, domain processes pursue it). Validity necessary, truth pursued — different owners, different mechanisms.
- **"application validation suffices"** — application validation *duplicates* (per client, per language — drifting dialects of validity); constraints *centralize* (one rule set at the choke point — every writer held, including consoles). Validate in apps for UX (fast feedback, friendly messages); enforce in stores for truth (refusals, codes, preservation). UX validates; stores guarantee — layered, never substituted.

### Performance note

Constraint-checking costs expression evaluation per write (nanoseconds — CHECK; microseconds — UNIQUE/FK probes, per [02/2.1](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.1. Schema and constraints that protect.md>) part 2's pricing) against invalid-state incidents (dedupe labor, wrong reports, trust repair — unbounded, per occurrence). Validity checking is the cheapest per-write work available (cents) preventing the dearest incidents (dollars) — constrain by default, measure before removing any.

### Mentor note

Frame consistency as "the database refusing to lie about itself" (invalid states uncommittable — lies structurally impossible, not carefully avoided): mentees graduate from test-counting (coverage %) to invariant-placing (which truths hold regardless of caller?) — the senior shift from verifying paths to guaranteeing states ([02/2.1](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.1. Schema and constraints that protect.md>) part 3's lesson, model-level restatement here).

## 3) Isolation previewed, modeled next

### 3) **Definition** (interference bounds, preview)

*Isolation*: concurrent units observing bounded interference (dirty reads? non-repeatable reads? phantoms? — each a named way one unit's in-flight work leaks into another's view). Preview verdict, models in [1.2](<./1.2. Isolation levels and anomalies.md>): PostgreSQL's `read committed` default (verified `SHOW default_transaction_isolation` → `read committed` on dbprobe) forbids dirty reads structurally (uncommitted data invisible — always); higher levels bound the subtler leaks (repeatability, phantoms, skew — priced per level, adopted on measured anomaly evidence).

### What problem it solves (history, previewed)

Unisolated concurrency (read-uncommitted engines, lock-free wishful stores — transactions observing half-written peers: balances read mid-transfer (70+80 momentarily 70+50 — conservation apparently violated *in the observer*, not the store), decisions made on provisional data (overbooking, double-spend approvals — real money on phantom reads)) produced incidents diagnosed as logic bugs (code correct, views corrupt — the layer misattributed). Isolation models bound observer corruption per level (readers see committed snapshots — MVCC in [2.1](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>), never half-units).

### Modern guidance

Default `read committed` suffices initially (dirty-read-free + writers-never-block-readers — the 99% application correctness, per [02/5.1](<../../../02 Postgres Deep Dive/sections/5. Interview questions and answers/5.1. Common interview QA Postgres.md>)'s lifecycle-first rule); escalate on measured anomalies (reproduced non-repeatable reads/phantoms/skew in *your* workload — [1.2](<./1.2. Isolation levels and anomalies.md>) demonstrates each live; SERIALIZABLE adopted on receipts, never on theory); never escalate by default (serializable everywhere serializes throughput — contention per level, priced in [1.2](<./1.2. Isolation levels and anomalies.md>)).

### Runnable example (good — the default, verified, models next)

```bash
docker exec dbprobe psql -U postgres -tAc "SHOW default_transaction_isolation;"
# read committed
```

Verified: the floor this track's probes run on (every concurrent behavior witnessed hereafter executes under `read committed` unless a leaf states otherwise — assumptions printed, never ambient). Anomaly demonstrations live in [1.2](<./1.2. Isolation levels and anomalies.md>) (concurrent clients, verified pair per anomaly — preview ends here, models there).

### Common confusion

- **"ACID means serializable"** — ACID's I spans *levels* (isolation guaranteed *to the chosen level's definition* — read-committed databases are fully ACID *at read committed*: atomic, consistent, durable, plus no-dirty-reads). Serializable is the *strongest* level, not the *defining* one (conflating them over-prescribes — serializable-everywhere serializes throughput for anomalies workloads never exhibit).
- **"isolation replaces transactions"** — isolation *qualifies* concurrent transactions (interference bounds between units); transactions *create* units (atomicity/durability per unit — [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>)). Units first (lifecycle correct — 99%), levels second (interference bounded — evidence-driven): order load-bearing, per [02/5.1](<../../../02 Postgres Deep Dive/sections/5. Interview questions and answers/5.1. Common interview QA Postgres.md>)'s lifecycle-first rule.

### Performance note

Isolation costs scale with strength (read-committed: snapshot-per-statement — cheap; repeatable-read: snapshot-per-transaction + predicate tracking; serializable: full conflict detection with abort-and-retry — contention per level, priced in [1.2](<./1.2. Isolation levels and anomalies.md>)). Default-level performance is the baseline (pay for observed anomalies only — upgrades evidence-gated, never speculative).

### Mentor note

Teach ACID as "A+D witnessed, C constrained, I previewed" (two proofs + one rule + one pointer — five minutes): mentees holding the four letters as *mechanisms* (unit protocol, WAL, constraints, levels) instead of *initialisms* reason about guarantees permanently (letters as vocabulary decay; mechanisms as mental models endure). Mechanisms, not mnemonics — always.
