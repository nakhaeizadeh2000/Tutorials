# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for consistency. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the lifecycle-vs-model split that keeps integrity knowledge in exactly one place per question.

## 1) Lifecycle and access (neighbor domains own the mechanics)

### 1) **Definition** (the model/mechanics split)

*Transaction lifecycle* (BEGIN/COMMIT/ROLLBACK/binding — [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>), assumed wired) and *pool access* (checkouts, drains, counts — [04/2.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/2. Discipline/2.1. Checkout discipline.md>), assumed disciplined) are mechanics this domain models atop: guarantees constrain lifecycles, levels qualify pooled units, anomalies reproduce through checkouts. Questions about wiring go back; questions about models stay here.

### The assignments (with the exact targets)

- Foundations (CRUD, choosing, gates) → [01 Database Foundations](<../../../01 Database Foundations and Mental Model/README.md>). Every probe here assumes handshakes, parameters, and witnesses — no re-teaching, ever.
- Lifecycle mechanics (units, abandonment, binding) → [02/3.1. Transactions basis](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>) (this track — five-line lifecycle owned there).
- Access mechanics (pools, checkouts, drains) → [04/2.1. Checkout discipline](<../../../04 Node.js Data Access Drivers and Pooling/sections/2. Discipline/2.1. Checkout discipline.md>) (this track — pooled lifecycle owned there).
- Naming level (ACID/isolation as words) → [IT Vocabulary 05](<../../../../ITVocabulary/05 Data Databases and AI Vocabulary/sections/1. Data words/1.2. Database table query and index.md>) (words owned there; models owned here).

### Common confusion

- **"models replace lifecycles"** — models *qualify* lifecycles (interference bounds atop wired units — levels meaningless over scattered `pool.query` sequences: nothing to isolate where no unit exists). Lifecycle first ([02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>)), models second (here) — order load-bearing, per [02/5.1](<../../../02 Postgres Deep Dive/sections/5. Interview questions and answers/5.1. Common interview QA Postgres.md>)'s lifecycle-first rule, restated at the boundary.
- **"theory needs no prerequisites"** — isolation theory without lifecycle fluency misattributes (anomaly symptoms read as logic bugs — models applied to unwired units: correct theory, absent substrate). Prerequisites gate comprehension (wired units → bounded interference → named distribution — sequence, not suggestion).

### Mentor note

Teach mentees to read this page as a router: "wiring" questions go to 02/3.1+04/2.1, "model" questions stay here. The distinction resolves half of all consistency debates before they start — most are lifecycle-questions asked in model-rooms ("isolation broken?" during unwired units), or the reverse.

## 3) Design and mapping (planned siblings own the ends)

### 3) **Definition** (the model/design/map split)

*Models* (this domain: guarantees, levels, snapshots, distributed honesty) vs *modeling* (Database Design track: normal forms *with* integrity reasoning — planned sibling) vs *mapping* (ORM track: transactions via abstractions — planned sibling). Models assume designed schemas (constraints declared per design) and precede mapping (raw transaction literacy before generated-transaction trust — you cannot evaluate an ORM's unit handling without having wired units by hand).

### The assignments

- Schema modeling (normalization, keys, integrity-by-design) → Database Design track (planned sibling per root README — textual forward, no dead link by design).
- Object mapping (entities, unit-of-work, transaction runners) → ORM track (planned sibling per root README — textual forward, no dead link by design).
- Repository seams (units carried through policy) → [DesignPatterns 06/1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>) (seam owned there — modeled units pass through it).

### Common confusion

- **"ORM transactions suffice"** — ORM runners *script* lifecycles (begin/commit wrappers — convenient); understanding *owns* them (levels chosen, anomalies reproduced, races shut — judgment this domain teaches). Scripted lifecycles without models misconfigure confidently (serializable-by-default ORM settings — contention accepted blindly; unwired runners — units scattered behind abstraction). Literacy before abstraction — always.
- **"models are academic"** — models *route* incidents (anomaly vocabulary diagnosing production behavior — "non-repeatable, escalate locking" vs "logic bug, rewrite handler": different fixes, model-chosen). Unmodeled triage guesses (symptoms matched to folklore — right fixes occasionally, by luck). Models pay per incident avoided — academic only to those who never paged.

### Mentor note

The one-sentence router for integrity: "Wiring questions go back (02/3.1+04/2.1), theory waits nowhere (here), models live in siblings, *guarantees* stay here." ACID/levels/snapshots/constraints/distribution — the integrity layer with its own craft, its own checklist, its own interview.
