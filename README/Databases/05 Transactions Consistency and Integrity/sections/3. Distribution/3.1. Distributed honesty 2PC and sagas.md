# 3.1. Distributed honesty 2PC and sagas

Staying honest across systems: two-phase commit coordinating rarely, sagas compensating stepwise, and the transactional outbox bridging honestly. Junior read: single-system transactions end at the system boundary; beyond it, compensate or coordinate explicitly. Expert read: what 2PC prices in availability, and why outbox-plus-idempotent-handlers beats both for most teams.

## 1) 2PC coordinates, rarely

### 1) **Definition** (prepare/commit across systems)

Two-phase commit: phase one (`PREPARE TRANSACTION` — each participant durably staging its unit, reporting ready); phase two (`COMMIT PREPARED` — coordinator directing commit after *all* reported ready, or abort after any failure). Atomicity across systems (all commit or all abort — the single-system guarantee extended past the boundary); priced in availability (participants blocked holding prepared state until the coordinator decides — coordinator failure stalls everyone) and latency (two network rounds + forced WAL per phase).

### What problem it solves (history)

Cross-system writes without coordination (debit here, credit there, best-effort ordering — partial states across system boundaries: money left one ledger, never arriving at the other — unrecoverable except by reconciliation heroics discovering the gap days later) made distributed business operations lotteries (each participant deciding alone — atomicity void across the only boundary that matters). 2PC supplies cross-system atomicity (coordinated commit — all-or-nothing past the boundary, proven below).

### Modern guidance

Reach for 2PC almost never (single-system transactions + outbox (part 3) + idempotent handlers cover the overwhelming majority — 2PC's availability price (blocking coordinator — CAP's C-at-A's-expense, explicitly) exceeds most business needs); enable deliberately where used (`max_prepared_transactions` nonzero — *disabled by default*, verified below: the platform itself votes "rarely" via defaults); monitor prepared age (orphaned prepared units holding locks indefinitely — coordinator crashes mid-protocol leave participants blocked: prepared-age alarms + operator `COMMIT/ROLLBACK PREPARED` runbooks, rehearsed).

### Runnable example (good — prepare/commit witnessed, plus the default that votes rarely)

```bash
# attempt on defaults (verified live — the platform voting "rarely"):
# PREPARE TRANSACTION 'demo2pc'
# error: prepared transactions are disabled  (code 55000)
# hint: Set max_prepared_transactions to a nonzero value.
docker exec dbprobe psql -U postgres -tAc "ALTER SYSTEM SET max_prepared_transactions = 10;"
docker restart dbprobe   # postmaster-level setting — restart applies (durability re-proven: data survives)
# SHOW max_prepared_transactions;  →  10
```

```bash
DATABASE_URL=... node -e "
  await c.query('BEGIN');
  await c.query(\"INSERT INTO outbox (aggregate, payload) VALUES ('order-7', '{\\\"status\\\": \\\"paid\\\"}')\");
  await c.query(\"PREPARE TRANSACTION 'demo2pc'\");
  // prepared-durable: true   (pg_prepared_xacts lists gid — staged, crash-surviving)
  await c.query(\"COMMIT PREPARED 'demo2pc'\");
  // committed-visible: 1     (unit published — prepare/commit, both witnessed)"
# prepared-durable: true
# committed-visible: 1
```

Verified (PostgreSQL 16.15, this session): disabled-by-default (`55000` + hint — configuration as opinion: the engine ships uncoordinated, coordination opt-in); enabled via `ALTER SYSTEM` + restart (postmaster setting — applied, verified `10`); prepare durable (`pg_prepared_xacts` listing — crash-surviving staged state); commit published (row visible — two phases, one atomic outcome).

### Common confusion

- **"2PC is the distributed transaction"** — 2PC is *a* distributed protocol (blocking, coordinator-centric — one family); saga/outbox/idempotent-handler patterns are the *pragmatic* family (non-blocking, compensation-based — parts 2–3). "Distributed transaction" names the *problem* (cross-system atomicity); 2PC/saga/outbox name *solutions* with opposed price tags (availability vs eventuality). Name the problem, price the solutions, choose per business need — never default to 2PC by vocabulary.
- **"prepared means committed"** — prepared means *staged-and-durable* (survives crashes — recoverable by coordinator direction *either way*: commit *or* abort follows). Staged work is *pending*, not done (queries don't see it; only `pg_prepared_xacts` lists it). Recovery complexity lives exactly here (crashed coordinators leaving prepared units — operator runbooks exist for this state, rehearsed per part-1 guidance).

### Performance note

2PC costs per unit: two forced-WAL phases (durability twice — latency doubled vs single commit); blocking holds (locks/versions held from prepare to coordinator decision — contention window spanning *networks*, not statements: coordinator latency + failure windows billed per participant); orphan risk (crashed coordinators — manual resolution latency unbounded without runbooks). Price per cross-system unit (latency ×2, availability coupled, operations burdened); compare against saga/outbox totals (eventual, non-blocking, handler-idempotent — cheaper nearly always, per parts 2–3).

### Mentor note

The disabled-by-default demo (attempt → `55000` + hint → enable → restart → prepare → commit — ten minutes): mentees watching the platform itself vote "rarely" internalize 2PC's price permanently (defaults as design opinions — read them as curriculum, not obstacles). Follow with "when *would* you?" (genuinely atomic cross-system money movement with coordinator HA — rare, real, named explicitly when reached).

## 2) Sagas compensate stepwise

### 2) **Definition** (forward steps, backward inverses)

Saga: a business operation as ordered local transactions (reserve → charge → ship — each committing independently, immediately visible), each step paired with a compensating inverse (cancel-reservation → refund → recall-shipment — semantic undo, business-meaningful, not storage-rollback). Failures trigger backward compensation (completed steps inverted in reverse — eventual consistency via explicit business logic, not atomicity via protocol).

### What problem it solves (history)

Cross-service atomicity wishes (distributed BEGIN/COMMIT fantasies — single mental model stretched past system boundaries: services blocking on shared coordinators, availability coupling every participant to the slowest, outages correlating fleet-wide by design) failed availability-first businesses precisely when availability mattered (peak traffic + coordinator hiccup = global stall — correctness maximal, business halted). Sagas trade atomicity for availability-with-convergence (each step durable locally *now*; failures compensated explicitly *soon*; business invariants restored by design, not by protocol).

### Modern guidance

Step with inverses (every forward step ships its compensator in the same PR — uncompensatable steps rejected in review: "how does this undo?" asked per step, answered per step); orchestrate explicitly (orchestrator service driving steps — state machine visible, retries per step, timeouts per hop — or choreography via events with saga-aware consumers — DesignPatterns 06/5.1's vocabulary, linked); make steps idempotent (keys per step-attempt — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) — retried steps converge, compensated steps stay compensated).

### Runnable example (good — the saga narrative, enumerated)

```markdown
# order saga (steps with inverses — narrated, each locally transacted):
# 1. reserve inventory (inverse: release reservation)
# 2. charge payment    (inverse: refund — idempotency-keyed, per [03/3.1])
# 3. book shipment     (inverse: cancel booking)
# failure at 3 → compensate 2 (refund) → compensate 1 (release) → order marked FAILED with ledger
# each step commits independently (visible immediately — no blocking); failures converge backward (explicitly)
```

```markdown
# bad: distributed BEGIN fantasy (the wish, priced)
# BEGIN-across-services → reserve → charge → ship → COMMIT-across-services
# (coordinator stalls mid-protocol → all three services blocked holding prepared state —
#  availability coupled fleet-wide; the 2PC price from part 1, paid in production this time)
```

Why sagas win *for most businesses*: availability preserved (no cross-service blocking — steps commit locally, failures compensate asynchronously); invariants restored (compensations designed per step — business-meaningful undo, not storage rollback); progress observable (saga state queryable per step — "failed at shipment, refunded, awaiting release" — operators narrate, customers informed). Atomicity sacrificed knowingly (intermediate states *visible* — designed for (idempotent readers, tolerant UX), never accidental).

### Common confusion

- **"sagas are eventually consistent, therefore sloppy"** — sagas are *explicitly* consistent (convergence designed per failure path — compensated states enumerated, tested per step-failure: rigor relocated from protocol to business logic, not abandoned). Sloppy is *uncompensated* multi-step writes (failures unhandled — partial states permanent, discovered by customers). Explicit compensation is rigor wearing business clothes — review it like protocol code (paths enumerated, inverses tested).
- **"compensation equals rollback"** — rollback restores *storage* state (versions discarded — as-if-never-happened, invisible); compensation creates *new business* state (refund recorded — audit-visible, customer-meaningful: money moved twice, ledger showing both). Audited businesses *prefer* compensation traces (regulators read ledgers, not the absence of rows — visible undo beats invisible unhappening, always).

### Performance note

Saga cost per operation: N local commits (each fast — single-system units, no cross-system blocking) + compensation readiness (inverse code paths maintained — authoring cost, one-time per step); failure cost per step-failure (compensations executed — bounded, enumerated, tested). 2PC cost per operation (blocking holds + double WAL + coordinator risk — per part 1, recurring). Sagas trade authoring (inverses written) for runtime (never blocked) — pay once in code, save per incident forever.

### Mentor note

Design-review sagas step-by-step ("forward? inverse? tested failure at *this* step?" — per-step interrogation, three questions each): mentees surviving the interrogation design compensable systems habitually (inverses authored with forwards — uncompensatable steps extinct within a quarter). Uncompensatable steps rejected in review regardless of schedule pressure — the rule that prevents incident-debt at its source.

## 3) Outbox bridges honestly

### 3) **Definition** (transactional messaging without distributed transactions)

Outbox pattern: business write + message intent in *one local transaction* (order row + outbox row committed atomically — single-system guarantee, no coordination); relay process publishes outbox rows to the broker (marks relayed — at-least-once delivery); consumers handle idempotently (keys dedup — [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) — repeats converge). Exactly-once *effects* from at-least-once *delivery* + transactional *recording* — honesty assembled from three boring parts.

### What problem it solves (history)

Dual-write failures (database committed, broker publish crashed between — state changed, nobody notified (orders paid, unshipped — discovered by customers asking); or broker-first ordering — notified, uncommitted (phantom events for rolled-back work — downstream acting on fiction)) made "write DB + publish event" the most incident-dense two lines in backend code (two systems, no shared atomicity — partial outcomes structurally routine). Outbox fuses recording atomically (one transaction — both-or-neither recorded) and relays separately (delivery retried to success — at-least-once, honestly).

### Modern guidance

Relay-table per publishing aggregate (outbox rows: aggregate id, payload, relayed flag — transactional with business writes, always); relay process separate (poller/publisher — crash-safe resumption via unrelayed scan, ordered per aggregate where causality matters); consumers idempotent (keys per message — duplicates refused, originals returned — the [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) contract at the consuming end); monitor relay lag (unrelayed age alarmed — delivery latency visible, stuck relays paged distinctly from business errors).

### Runnable example (good — record + relay, verified live)

```bash
DATABASE_URL=... node -e "
  await c.query('BEGIN');
  await c.query(\"INSERT INTO outbox (aggregate, payload) VALUES ('order-7', '{\\\"status\\\": \\\"paid\\\"}')\");
  await c.query(\"PREPARE TRANSACTION 'demo2pc'\");   // (2PC phase-1 shown in part 1 — here: plain COMMIT suffices)
  ...
# committed-visible: 1
# relayed: {"n":1}   (UPDATE ... WHERE relayed = false — relay marking, witnessed)"
```

Verified (same session, same table): business intent + relay intent committed atomically (one unit — dual-write failure structurally impossible: no between-state exists); relay marking witnessed (`relayed: {n:1}` — published-then-marked, resumable on crash: unrelayed scan redelivers, idempotent consumers converge). The 2PC detour in part 1's probe was illustrative (prepare/commit witnessed); production outbox commits plainly (single-system atomicity — no coordinator, no blocking — honesty without ceremony).

### Common confusion

- **"outbox needs 2PC with the broker"** — outbox *avoids* broker coordination (relay is at-least-once delivery + idempotent consumption — no atomicity spanning DB×broker, ever: the design insight is precisely that coordination is unnecessary (recorded atomically + delivered eventually + consumed idempotently = honest end-to-end without a single distributed transaction).
- **"polling the relay table is wasteful"** — polling costs indexed scans on small unrelayed sets (partial index `WHERE NOT relayed` — constant-time-ish, cheap); alternatives (logical-decoding/CDC tailing — lower latency, higher machinery: Debezium-class infrastructure, operated separately). Poll-first (minutes of latency acceptable — most domains), CDC on measured lag pain (sub-second needs with receipts — machinery earned, never anticipated).

### Performance note

Outbox cost per business write (one extra row in-transaction — negligible beside business I/O); relay cost (poll cadence × unrelayed scan — indexed, cheap; delivery at broker speed — normal producer throughput); consumer cost (idempotency probes per message — microseconds, [03/3.1](<../../../03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>) gladly paid). End-to-end latency genres: poll-relay (seconds — fine for most); CDC-relay (sub-second — priced machinery). Latency budgeted per domain (seconds acceptable → poll; sub-second required → CDC with receipts).

### Mentor note

The dual-write autopsy ("DB committed, publish crashed — narrate the customer impact" — then outbox-redesign the same two lines together): mentees converting dual-writes to outbox-relays stop producing the densest incident class in backend code within a quarter (two lines made honest — highest incident-density reduction per diff in data work). Review every DB+publish pair for outbox shape ("where's the relay row?" — asked per pair, answered per pair).
