# 5.1. Common interview QA: consistency

Canonical answers for the three consistency questions every backend interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their codes. Expert read: each answer runs evidence (verified probes, codes, gates) before conclusions — prediction first, output as confirmation.

## 1) "Dirty reads in Postgres?" — answer no, then why

### 1) **Definition** (the default screen)

"Can a transaction read uncommitted data?" — screens for default-model thinking: hires answer no *with the mechanism* (read-committed floor + MVCC snapshots — uncommitted versions invisible structurally, verified: B saw 100 during A's uncommitted 999), then name what *is* observable (committed changes per re-read — non-repeatable, permitted) and where models deepen ([1.2](<../1. Guarantees/1.2. Isolation levels and anomalies.md>)'s ladder, cited unprompted).

### What problem it solves (hiring signal)

Default-model questions separate engineers who *operate* defaults (verified floor, witnessed guarantees — production behavior predicted) from engineers who *assume* them (documentation recited — behavior surprising under concurrency). The screen predicts incident competence directly: evidence-grounded defaults vs folklore defaults, one question apart.

### Modern guidance

Answer in three beats with the verified probe (default printed: `read committed` — floor named; dirty blocked: B-sees-100 — guarantee witnessed; non-repeatable permitted: 100→50 — boundary stated): mechanism (snapshots, [2.1](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>)), boundary (re-reads observe commits — permitted, priced), escalation (repeatable-read on measured need — ladder, never theory).

### Runnable example (good — the probe, quoted)

```bash
# A: BEGIN + UPDATE balance = 999 (uncommitted)
# B: SELECT → 100  (dirty-read-blocked — committed truth, structurally invisible 999)
# A: ROLLBACK (999 never existed for any observer — aborted work traceless at every level)
```

A hire narrates *before* running ("B sees 100 — snapshots exclude uncommitted; ROLLBACK erases 999 from all possible views") — prediction first, confirmation second. Interviewers: ask "what does B see *after* A commits 999?" (999 — committed visibility, immediate — then "and before?" (100 — the pair proving snapshot semantics both directions)).

### Common confusion (in candidates)

- **"Postgres has dirty reads at read-uncommitted"** — PostgreSQL *treats* READ UNCOMMITTED as READ COMMITTED (documented behavior — requesting the weakest level silently upgrades: no dirty reads at any setting, ever). Candidates asserting dirty-read scenarios reveal engine-agnostic recitation (true elsewhere — SQL Server permits them; Postgres structurally cannot). Engine-specific truth volunteered unprompted signals depth.
- **"snapshot means stale"** — snapshots mean *moment-pinned* (statement/transaction start — freshness bounded by start latency, not versions): read-committed re-reads see latest-committed (staleness measured in statement time — current to milliseconds). Stale-implying answers reveal cache-thinking applied to snapshots (different invalidity models — pinned vs expired, never conflated by strong candidates).

### Performance note

Default-model answers need the non-blocking footnote (2ms concurrent read witnessed — [2.1](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>) — readers never wait on writers: throughput implication stated unprompted shows production thinking). Numbers volunteered with sources (2ms, 100/50/110 — quoted above) beat numbers recited; ranges beat points.

### Mentor note

Mock with the two-client script open but unrun ("predict B's three reads: during, after-commit, after-rollback"): mentees graduate when all three predictions land (100/999/100 — invisibility, visibility, erasure — the snapshot lifecycle in three numbers). Prediction-then-output per anomaly — the method from this track's gates, applied to theory.

## 2) "Lost update, two writers" — demonstrate it

### 2) **Definition** (the clobber screen)

"Two writers increment concurrently — final value?" — screens for read-modify-write hazard thinking: hires demonstrate the loss (100 +10 +10 → 110, verified — one increment destroyed), name the permission (allowed at read committed — each statement correct in isolation), and price three fixes (atomic update: free; locking read: contention-priced; serializable: abort-budgeted — cheapest sufficient first).

### What problem it solves (hiring signal)

Lost-update blindness (read-then-write code reviewed as correct — sequential reasoning applied to concurrent execution: green suites, corrupt production — load-correlated wrongness invisible to single-threaded tests) is the most common concurrency defect in application code (counters, balances, inventories — read-modify-write everywhere). Demonstration ability predicts concurrent-code review quality directly.

### Modern guidance

Answer as the demo (two clients, same read, sequential commits, 110 witnessed — loss exhibited, not described), then the ladder (atomic `SET x = x + 10` first — no read, no loss; `SELECT FOR UPDATE` second — contention priced; serializable third — evidence-gated, per [1.2](<../1. Guarantees/1.2. Isolation levels and anomalies.md>) part 3). Never theory-first (levels named without demo — unanchored abstractions, instantly forgettable, never hirable).

### Runnable example (good — the loss, quoted)

```bash
# A reads 100, B reads 100; A writes 110, commits; B writes 110, commits
# both-added-10-from-100, final: 110 (lost-update: true)   (expected 120 — 10 destroyed)
```

A hire narrates the destruction mechanism per line (B's write based on stale read — clobber, not merge — then names all three fixes with prices). Interviewers: ask "fix without changing isolation" (atomic update — `SET balance = balance + 10` — no read, no loss, no level touched — the cheapest sufficient answer, first).

### Common confusion (in candidates)

- **"transactions prevent lost update"** — transactions *scope* units (atomicity per unit — both writers' units committed perfectly: A-unit correct, B-unit correct, combined wrong). Loss lives *between* units (stale-read basis shared — units individually flawless, jointly destructive). Transactional correctness ≠ concurrent correctness (units vs interference — different layers, [1.2](<../1. Guarantees/1.2. Isolation levels and anomalies.md>)'s menu covers both).
- **"ORMs handle concurrency"** — ORMs expose *optimistic locking* (version columns, update-where-version — opt-in per entity, not default: unversioned entities race identically under ORMs). Candidates citing version columns unprompted (with the write-skipped-on-mismatch + retry shape) show framework-plus-fundamentals (either alone insufficient — ORM feature plus lost-update model, both).

### Performance note

Fix pricing is the answer's core (atomic: free — statement shape; locking: contention per hot row — measured per workload; serializable: abort rates + retries — budgeted per action). Candidates pricing all three unprompted (free/contention/abort-budget — economics per rung) outscore single-fix answers regardless of rung chosen. Price, then prescribe — always.

### Mentor note

Live-demo lost update per cohort (two terminals, narrated reads/writes, 110 witnessed — jaws drop reliably: sequential intuition visibly violated). Then fix live three ways (atomic → locking → level — ladder climbed on receipts). Demo-then-ladder teaches concurrency permanently (witnessed loss + priced fixes — scar tissue plus toolbox, one session).

## 3) "Pay across services" — saga it (plus rapid-fire)

### 3) **Definition** (the distribution drill)

"Charge here, ship there, one failure — design it" — screens for explicit-coordination thinking: hires reject distributed-BEGIN fantasy (priced: blocking holds + double WAL + coordinator risk — [3.1](<../3. Distribution/3.1. Distributed honesty 2PC and sagas.md>) part 1's witnessed `55000`-by-default), narrate saga steps with inverses (reserve/charge/ship + release/refund/recall — compensated, tested per step-failure), and bridge with outbox (transactional relay rows — verified committed-visible + relayed).

### What problem it solves (hiring signal)

Cross-service atomicity wishes (BEGIN-across-services fantasies — availability coupled fleet-wide, coordinator as single point of stall) reveal distributed-systems immaturity instantly (coordination unpriced — hope as protocol). Saga/outbox answers reveal production-grade distribution thinking (explicit coordination per boundary — priced, reviewed, rehearsed). The drill predicts distributed-incident rates directly.

### Modern guidance

Answer as the rejection-then-pattern (2PC priced-and-declined for most businesses — availability coupled; saga narrated stepwise with inverses; outbox relaying with idempotent consumers — [3.1](<../3. Distribution/3.1. Distributed honesty 2PC and sagas.md>) parts 1–3 in order). Quote the witnessed receipts (prepared-durable + committed-visible + relayed `{n:1}` — verified this session). Name the exception honestly (genuinely atomic cross-system money with HA coordinators — rare, real, named explicitly when reached).

### Runnable example (good — the saga sketch, narrated)

```markdown
# "charge + ship, ship fails":
# saga: reserve ✓ → charge ✓ → ship ✗ → compensate charge (refund, keyed) → compensate reserve (release)
#   → order FAILED with ledger (visible, auditable, customer-informed — converged, not atomic)
# outbox: each step's intent relayed transactionally (committed-visible 1, relayed {n:1} — verified shape)
# 2PC declined with price (blocking coordinator — availability coupled fleet-wide for atomicity rarely needed)
```

### Rapid-fire drills (with answers)

1. **ACID letters in one breath?** Atomicity (units), Consistency (constraints), Isolation (levels), Durability (WAL+restart — witnessed all) ([1.1. ACID](<../1. Guarantees/1.1. ACID that holds.md>)).
2. **Default isolation on dbprobe?** `read committed` (SHOW-verified — dirty-free, non-blocking) ([1.1. ACID](<../1. Guarantees/1.1. ACID that holds.md>)).
3. **Readers block writers?** Never (snapshots — 2ms witnessed concurrent read) ([2.1. MVCC](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>)).
4. **Lock wait unbounded — code?** `55P03` at budget (504ms witnessed — queue patience honored) ([2.1. MVCC](<../2. Mechanisms/2.1. MVCC snapshots not locks.md>)).
5. **Two racers, one unique — outcome?** Exactly one + `23505` (TOCTOU shut — verified pair) ([2.2. Constraints](<../2. Mechanisms/2.2. Constraints as integrity.md>)).
6. **Gate exits 50 vs 51 — meaning?** 50: ROLLBACK-less unit (wiring); 51: default drift (floor) ([4.1. Integrity checklist](<../4. Important points to remember/4.1. Integrity checklist habits mentors insist on.md>)).

### Common confusion (in candidates)

- **"saga means no consistency"** — sagas deliver *business* consistency (compensated end-states enumerated — converged explicitly, audited visibly) instead of *storage* atomicity (all-or-nothing invisibility). Consistency redefined per boundary (single-system: atomic; cross-system: convergent — different guarantees, honestly named). Unnamed-distribution candidates promise atomicity past boundaries (fantasy); saga candidates promise convergence with ledgers (contract).
- **"outbox is over-engineering"** — outbox is one table + one relay (trivial mechanism — verified in minutes this session: committed-visible + relayed) preventing the densest incident class in backend code (dual-write partials — hours with misdirection, per occurrence). Mechanism-trivial, incident-dense-covered — the best ROI shape in distributed data work (minutes to build, incidents retired permanently).

### Performance note

Distribution answers need price tags (2PC: 2× WAL + blocking holds + coordinator risk; saga: N local commits + inverse authorship; outbox: one row + relay poll — priced per pattern, chosen per business need). Candidates pricing all three unprompted (latency/availability/authoring per pattern) outscore single-pattern answers regardless of pattern chosen. Price, then pattern — always.

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly data-health check. Drills 1 and 6 separate acronym-reciters (letters without mechanisms) from guarantee-operators (witnesses per letter, exit codes per gate); ask those first when time is short.
