# 2.1. MVCC snapshots not locks

How PostgreSQL serves concurrent readers without blocking writers: snapshot visibility, row versions with vacuum cleanup, and explicit row locks where snapshots stop. Junior read: reads never wait on writes; writes queue politely with timeouts. Expert read: what xmin/xmax prove per row, and why `SELECT FOR UPDATE` exists despite snapshots.

## 1) Readers never block writers

### 1) **Definition** (snapshot visibility)

Each statement (read committed) or transaction (repeatable read+) reads a *snapshot*: the set of row versions committed as of a moment. Concurrent uncommitted writes are invisible (other versions, not locks, mediate — readers proceed without waiting, writers proceed without blocking readers). Visibility rules, not lock queues, arbitrate read/write concurrency — locks reserved for write/write contention (part 3).

### What problem it solves (history)

Locking-read engines (shared locks per SELECT — readers queuing behind writers: reporting queries timing out per deploy window, dashboards serializing behind OLTP writes, read scaling capped by write rate) coupled read throughput to write latency inversely. MVCC decoupled them (versions appended, never overwritten in place — readers pinned to committed snapshots, writers appending new versions concurrently: both proceed, neither waits).

### Modern guidance

Rely on snapshot reads by default (reporting concurrent with OLTP — no read locks to manage, none to tune); verify non-blocking where it matters (concurrent read-during-write probes per critical report — witnessed below, not assumed); never add read locks "for safety" (shared locks reintroduce the coupling MVCC removed — safety lives in snapshots, not in locks taken hopefully).

### Runnable example (good — unblocked read, verified live)

```javascript
// pg 8.23.0, two clients, PostgreSQL 16.15 (docker, this session)
await a.query('BEGIN');
await a.query("UPDATE txn_demo SET balance = 111 WHERE owner = 'ann'");  // uncommitted
const t = Date.now();
const r = await b.query("SELECT balance FROM txn_demo WHERE owner = 'ann'");
// reader-unblocked-ms: 2 | sees-committed: 110
await a.query('ROLLBACK');
```

Verified: B's read completes in 2ms *during* A's open write (unblocked — no waiting, no timeout, no queue); sees committed 110 (snapshot truth — 111 invisible, structurally). Contrast lock-based engines (B would wait for A's COMMIT/ROLLBACK — read latency coupled to longest open write — the coupling MVCC deletes).

### Common confusion

- **"snapshots mean stale reads"** — snapshots mean *committed-as-of-moment* reads (freshness bounded by statement/transaction start — read-committed statements see the latest committed per statement: staleness measured in statement latency, not versions). Stale means *arbitrarily old* (cache without TTL — unbounded); snapshots mean *moment-pinned* (bounded by start time — current to milliseconds). Pinned, not stale — vocabulary matters here.
- **"no locks anywhere"** — MVCC removes *read* locks (the throughput win); *write* locks persist (row-level on conflicting writers — part 3's queueing, honestly measured). "No locks" overclaims (write/write contention locks genuinely — second writer waits or times out); "no read locks" claims exactly (readers never queue — verified above at 2ms).

### Performance note

Snapshot-read cost: version visibility checks per row (xmin/xmax compared against snapshot — index-assisted, microseconds); lock-based read cost: lock acquisition + queueing behind writers (milliseconds-to-seconds under write load — coupling priced per report). Mixed-workload throughput multiplies under MVCC precisely where locking engines serialize (reports × writes concurrently — the production shape snapshots serve best).

### Mentor note

The 2ms demo (read during open write — timed, witnessed): mentees watching unblocked reads trust snapshots structurally thereafter (concurrency without coordination anxiety — the mental model that replaces lock-thinking). Follow with "when *do* readers wait?" (never on writers — only on *each other's* exotic locks (advisory, DDL) — boundaries named, model complete).

## 2) Versions, not overwrites

### 2) **Definition** (row versioning + vacuum)

UPDATE appends a new row version (stamped `xmin`/`xmax` transaction ids — old version retained for concurrent snapshots still pinned to it); DELETE marks dead (invisible to new snapshots, space unreclaimed until vacuum); autovacuum reclaims (dead-tuple cleanup + statistics refresh — background, tunable, monitored). Storage churns versions; vacuum compacts; snapshots select among them per visibility rules.

### What problem it solves (history)

In-place-update engines (overwriters destroying old values — concurrent readers needing locks (part 1's coupling) or reading torn states (half-written rows — corruption by concurrency); no time-travel (flashback queries, audit trails, logical replication all reimplemented per need)) traded simplicity for coupling and amnesia. Versioning buys non-blocking reads *and* history (concurrent snapshots + change streams + point-in-time recovery — one mechanism, three payoffs).

### Modern guidance

Expect version churn on hot rows (update-heavy tables accumulating dead tuples — bloat monitored via `pg_stat_user_tables.n_dead_tup` — thresholds alarmed, not feared); trust autovacuum defaults initially (sized for general workloads — tuned per hot table only on measured bloat: scale factors, thresholds, costs); never disable vacuum (unvacuumed tables bloat unboundedly — transaction-ID wraparound halting writes at 2B transactions unvacuumed: the doomsday vacuum prevents, silently, until disabled loudly).

### Runnable example (good — version stamps exist, verified live)

```bash
docker exec dbprobe psql -U postgres -tAc "SELECT xmin, xmax, balance FROM txn_demo WHERE owner = 'ann';"
# versions: {"xmin":"759","xmax":"760","balance":110}
```

Verified: rows carry version stamps (`xmin` creator, `xmax` expirer-or-abort-marker — MVCC metadata visible per row, not theoretical). Concurrent snapshots select versions by stamp comparison (visibility rules — part 1's 2ms read chose the committed version structurally, stamps deciding). Details of stamp lifecycle (abort markers, freeze ages) belong to engine internals — usage needs stamps-exist + vacuum-runs, both witnessed here.

### Common confusion

- **"bloat means broken vacuum"** — bloat means *outpaced* vacuum (write rate exceeding cleanup rate — hot tables, long transactions pinning old snapshots (open transactions blocking cleanup — the `idle_in_transaction` villain from [04/3.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/3. Resilience/3.1. Retries timeouts and backoff.md>)), aggressive autovacuum settings pending). Diagnose per cause (long xacts? write storms? disabled autovacuum? — three distinct fixes, one symptom).
- **"VACUUM FULL routinely"** — `VACUUM FULL` rewrites tables under exclusive lock (downtime-shaped maintenance — space returned to OS, access blocked meanwhile); routine autovacuum reclaims *for reuse* (space recyclable in-table — sufficient nearly always). FULL reserved for one-time reclaims post-mass-delete (scheduled, announced, measured) — routine FULL is downtime scheduled as hygiene.

### Performance note

Version-churn cost per hot row (dead tuples per update — bloat linear in update rate until vacuumed); vacuum cost (I/O + CPU background — throttled by cost settings, pausable, schedulable); unvacuumed cost (bloat unbounded — sequential scans slowing per dead tuple, wraparound halting writes at the limit). Monitor `n_dead_tup` per hot table (alarm thresholds — bloat visible quarters before impact, per Domain 06 observability).

### Mentor note

Show `xmin`/`xmax` live once per cohort (one row's stamps, then update, then stamps changed — versions witnessed, not theorized): version-thinking replaces overwrite-thinking permanently (updates append — readers pin — vacuum cleans — the three-beat model of Postgres storage). Three beats recited cold beats chapters skimmed — drill the beats.

## 3) Locks where snapshots stop

### 3) **Definition** (write-write queuing with bounds)

Conflicting writers queue (second writer on a locked row waits — lock *queues*, honestly: order preserved, progress guaranteed on committer/rollbacker action); waits bounded by `lock_timeout` (queue patience — `55P03` on expiry, named and routable); `SELECT ... FOR UPDATE` declares intent early (lock at read time — write intent visible to the queue *before* the write executes, ordering contention deterministically).

### What problem it solves (history)

Unbounded lock waits (second writer hanging forever on a forgotten open transaction — application threads parked indefinitely, pools draining one stuck checkout at a time, incidents presenting as total hangs with zero errors) mistook patience for robustness (waiting longer never resolves holder-side abandonment — only bounds convert hangs to errors). Bounded queues plus declared intent convert lock contention from hang-shaped to error-shaped (named, timed, retried-or-shed per policy).

### Modern guidance

Bound lock waits per session/class (`lock_timeout` seconds — queue patience, never infinite; statement timeouts adjacent but distinct — lock-wait vs execution budgets, both set); declare write intent early (`FOR UPDATE` on read-modify-write rows — contention ordered deterministically, lost-update class shrunk structurally); handle `55P03` as retry-or-shed (bounded-wait expiry — transient contention (retry with backoff + keys) vs hot-row pathology (redesign: smaller units, less contention) — error code routing, per [04/3.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/3. Resilience/3.1. Retries timeouts and backoff.md>)).

### Runnable example (good — queue then bound, verified live pair)

```bash
# A holds row lock in open txn; B attempts same lock with 500ms budget:
# lock-queues-then-fails: 55P03 after-ms: 504
# both-closed (A rolled back, both clients ended cleanly — no leaks, no hangs)
```

Verified (concurrent pg clients, this session): B queued (waited — lock ordering real, not theoretical), then failed *named* at budget (`55P03 lock_timeout` — queue patience honored to millisecond scale), both connections closed cleanly (no leaked lock-holders — hygiene witnessed post-contention).

```javascript
// bad: SET LOCAL outside a transaction (the unbounded-wait trap — witnessed live this session)
await b.query("SET LOCAL lock_timeout = '500ms'");   // outside BEGIN — WARNING only, setting IGNORED
await b.query("SELECT ... FOR UPDATE");               // waits FOREVER (no budget applied — hang)
// process hung past tool timeout (60s, zero output — the shape unbounded waits take in production:
// silent, total, misdiagnosed as "slow database"). Fix: SET (session-level) or BEGIN first.
```

Why the trap bites: `SET LOCAL` warns instead of erroring (subtle log line, easily missed — setting silently absent while code reads bounded); the subsequent wait inherits infinity (default — unbounded by configuration, not by intent). Prefer session-level `SET` (applies immediately, visibly) or transaction-scoped discipline (BEGIN → SET LOCAL → work — ordered, reviewed as a unit).

### Common confusion

- **"locks mean contention problems"** — locks *serialize* contention (ordered progress — correctness under concurrency); *unbounded* locks mean hang exposure (patience without budget — availability risk). Queueing is healthy (work ordered); unbounded queueing is not (work parked). Bound queues (timeouts set) preserve the ordering benefit while deleting the hang exposure — keep the mechanism, budget the wait.
- **"FOR UPDATE everywhere is safe"** — locking reads serialize *more* (readers-turned-waiters — throughput reduced where plain snapshot reads sufficed: reads needing no write-intent locked "just in case" — contention manufactured, not managed). Lock intentfully (write-following reads — read-modify-write rows only); snapshot everything else (free concurrency, per part 1).

### Performance note

Lock-queue cost per contention event (wait duration — bounded by timeout: milliseconds configured, never hang-shaped); hot-row serialization cost (throughput ceiling at one-writer-at-a-time per row — contended counters/sequences redesigned: sharded counters, advisory batching — architecture responding to measurement, per Domain 06 patterns). Queue-then-bound is the cheapest contention posture (ordering free, bounds cheap, hangs impossible).

### Mentor note

The two-run lock lab (unbounded hang first — feel the silence; bounded `55P03` second — hear the name): contrast teaches bounds permanently (hang-shaped vs error-shaped failure — experienced back-to-back, never confused again). Run the hang with a stopwatch visible (seconds of nothing — the production shape of unbounded waits, safely witnessed); then the bound (named error at budget — relief audible in the room).
