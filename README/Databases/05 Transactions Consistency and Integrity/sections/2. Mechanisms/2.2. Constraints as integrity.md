# 2.2. Constraints as integrity

Constraints beyond the basics: deferred checks spanning statements, exclusion for non-overlapping ranges, and application-check races shut structurally. Junior read: rules can wait until commit, forbid overlaps, and beat application checks. Expert read: where immediate checking fails legitimately, and what exclusion expresses that UNIQUE cannot.

## 1) Deferred constraints check at commit

### 1) **Definition** (cross-statement rules)

`DEFERRABLE INITIALLY DEFERRED` foreign keys (and deferrable UNIQUE/CHECK/EXCLUDE) validate at COMMIT, not per statement: child-before-parent inserts within one transaction succeed (order-independent authoring — migration scripts, seed loaders, circular references), violations still abort the commit (deferred ≠ waived — invalid *final* states refused identically, valid intermediates tolerated).

### What problem it solves (history)

Immediate-only checking forced insert ordering (parents before children, always — seed scripts topologically sorted by hand; circular references uninsertable without deferral gymnastics: insert-null-then-update, constraint-dropping migrations — ceremony per cycle); bulk loads crawled (per-row FK probes on unordered dumps — reordering dumps to satisfy immediate checks, ETL shaped by constraint timing instead of data flow). Deferral decouples authoring order from validity (any order within the unit — validity judged on the final state, where it belongs).

### Modern guidance

Defer genuinely cyclic/out-of-order writes (seed data with cycles, bulk loads in arrival order, multi-table units authored child-first for readability); keep immediate default elsewhere (violations surfacing at the offending statement — error locality beats commit-time attribution for routine writes); never defer to *hide* violations (deferred-invalid still aborts — deferral reorders checking, never waives it: final-state validity identical, intermediate tolerance the only delta).

### Runnable example (good — child-first commit, verified live)

```bash
docker exec dbprobe psql -U postgres -c "CREATE TABLE defer_parent (id INT PRIMARY KEY);"
docker exec dbprobe psql -U postgres -c "CREATE TABLE defer_child (id INT PRIMARY KEY, pid INT NOT NULL REFERENCES defer_parent(id) DEFERRABLE INITIALLY DEFERRED);"
docker exec dbprobe psql -U postgres -c "BEGIN; INSERT INTO defer_child VALUES (1, 1); INSERT INTO defer_parent VALUES (1); COMMIT;"
# BEGIN
# INSERT 0 1
# INSERT 0 1
# COMMIT
docker exec dbprobe psql -U postgres -tAc "SELECT count(*) FROM defer_child;"
# 1
```

Verified (PostgreSQL 16.15): child referencing a not-yet-existing parent *succeeds* inside the unit (immediate checking would abort at the first INSERT — order enforced); commit validates the final state (parent present — valid, committed). Reverse the final state (parent absent at COMMIT — abort with FK violation, nothing stored): deferred checks, undeferred standards.

### Common confusion

- **"deferred means unchecked"** — deferred means *commit-checked* (violations abort COMMIT with the same codes/names — `23503` et al. — timing shifted, strictness identical). Unchecked would commit invalid states (never happens — final validity enforced unconditionally). Timing vs strictness confused most often under deadline pressure ("make it pass" reaching for DEFERRABLE as suppression — suppression it is not: invalid finals still abort).
- **"defer everything for flexibility"** — blanket deferral degrades error locality (violations attributed to COMMIT, not the offending statement — debugging per abort instead of per line) for flexibility rarely needed (acyclic writes gain nothing — immediate errors pinpoint better). Defer per constraint with cyclic/out-of-order justification (named in the DDL comment — rationale beside the mechanism); immediate everywhere else.

### Performance note

Deferred checking costs commit-time validation sweeps (batched checks per deferred constraint — fewer, larger validations vs per-statement probes: bulk loads measurably faster deferred, routine OLTP indifferent); immediate checking costs per-statement probes (microseconds each — the steady-state price of error locality). Bulk/etl paths defer deliberately (measured win); OLTP paths stay immediate (locality win) — timing per workload, never global.

### Mentor note

The child-first demo (insert child, insert parent, commit green — then drop the parent insert, watch COMMIT abort): two runs teach deferral completely (tolerance without laxity — order-free authoring, validity-guaranteed finals). Mentees reaching for DEFERRABLE thereafter justify per constraint ("which cycle/out-of-order justifies this?" — rationale required, fashion refused).

## 2) Exclusion beyond unique

### 2) **Definition** (non-overlap as constraint)

`EXCLUDE USING gist (room WITH =, during WITH &&)`: no two rows sharing `room` whose `during` ranges overlap (`&&` — range overlap operator; `=` — equality per room). UNIQUE forbids *equal* values (one dimension, equality); exclusion forbids *conflicting* predicates (multi-column, operator-expressed — overlaps, adjacencies, containment). Double-booking structurally impossible (overlapping reservations unrepresentable — refused with a named constraint, not detected by audit).

### What problem it solves (history)

Application-side overlap checks (query-existing → none-overlapping → insert — racing under concurrency: two bookings checked clean simultaneously, both inserted overlapping (the TOCTOU from part 3, calendar edition); plus every non-checking writer bypassing entirely — consoles, scripts, integrations) failed exactly when rooms mattered (peak season concurrency — overlaps discovered at check-in, apologies issued in person). Exclusion closes the race structurally (overlap checked atomically at write time — concurrent overbookings serialized into refusal).

### Modern guidance

Exclude overlapping reservations (rooms × time, seats × shows, capacity × windows — conflict-shaped domains); model ranges natively (`TSRANGE`/`DATERANGE` with `&&`/`@>`/`<@` — range types + GiST, the purpose-built pair); name the constraint (`bookings_room_during_excl` — refused writes diagnosed per name, routed per policy); combine with application UX (availability *previews* queried (readable calendars), exclusion *enforces* (writable truth) — previews guide, constraints decide).

### Runnable example (good — overlap refused with both keys named, verified live)

```bash
docker exec dbprobe psql -U postgres -tAc "CREATE EXTENSION IF NOT EXISTS btree_gist;"
# CREATE EXTENSION
docker exec dbprobe psql -U postgres -c "CREATE TABLE bookings (room INT, during TSRANGE, EXCLUDE USING gist (room WITH =, during WITH &&));"
# CREATE TABLE
docker exec dbprobe psql -U postgres -c "INSERT INTO bookings VALUES (101, '[2026-10-01, 2026-10-07)');"
# INSERT 0 1
docker exec dbprobe psql -U postgres -c "INSERT INTO bookings VALUES (101, '[2026-10-03, 2026-10-07)');"
# ERROR:  conflicting key value violates exclusion constraint "bookings_room_during_excl"
# DETAIL:  Key (room, during)=(101, ["2026-10-03 00:00:00","2026-10-07 00:00:00")) conflicts with existing key (room, during)=(101, ["2026-10-01 00:00:00","2026-10-05 00:00:00")).
```

Verified: overlapping reservation refused with *both* conflicting keys quoted (room 101, both ranges — diagnosis complete in the error: which room, which overlap, against what). Adjacent ranges (`[10-01,10-03)` + `[10-03,10-05)` — bounds touching, not overlapping) commit cleanly (`&&` semantics — adjacency permitted, overlap refused: boundary precision, not approximated).

### Common confusion

- **"UNIQUE(room, during) suffices"** — UNIQUE forbids *identical* pairs (same room + same exact range — distinct-but-overlapping ranges pass freely: `[10-01,10-05)` + `[10-03,10-07)` differ textually, conflict actually). Equality ≠ non-overlap (the category error behind every double-booking-on-UNIQUE incident — constraint present, conflict class uncovered). Overlap-shaped rules need exclusion (operator-expressed conflicts — UNIQUE covers equality only).
- **"exclusion needs an extension, skip it"** — `btree_gist` ships with PostgreSQL (CREATE EXTENSION, one line — verified above, no packages, no restarts); GiST powers the operator classes (&&, =, <@ — indexed conflict detection, not sequential scans per insert). Extension-aversion here costs double-bookings (priced in refunds + reputation); one-line extension costs nothing measurable.

### Performance note

Exclusion-check cost per insert (GiST probe — logarithmic, like all indexed checks); application-overlap-check cost (query-then-insert round trips + race window — slower *and* wrong under concurrency). Overlapping-domain throughput scales with exclusion (concurrent non-conflicting inserts proceed — predicate-level granularity, finer than table locks); application checks serialize correctly only under serializable-plus-luck (levels + hope — exclusion instead, structurally).

### Mentor note

The double-booking demo (insert overlapping live, read the DETAIL aloud — room, both ranges, existing key quoted): mentees watching refusal-with-diagnosis stop writing overlap checks in application code permanently (store-enforced conflicts with named errors beat hand-rolled queries-plus-hope every time). Follow with "which of our domains overlap-shape?" (inventory per codebase — reservations, schedules, allocations — each a candidate exclusion, reviewed quarterly).

## 3) Application checks race; constraints don't

### 3) **Definition** (TOCTOU shut structurally)

Time-of-check-time-of-use races (check-absent → act-present-changed: two writers checking simultaneously, both seeing clear, both acting — duplicates/overbooks/overdrafts stored "correctly" per check, wrongly per reality) close *only* where check and act are atomic (UNIQUE refusal, exclusion predicate, FK existence, SERIALIZABLE predicate tracking — store-atomic check-act, no window). Application checks sequence (check, *then* act — window between, race inside); constraints fuse (check *is* the act — windowless by construction).

### What problem it solves (history)

Check-then-act code (SELECT-for-exists → INSERT-if-absent — the universal application pattern, racing universally: concurrent doubles under load spikes *precisely when correctness matters most* (flash sales, registration rushes, retry storms — load-correlated races, incident-shaped by definition)) failed load-dependently (quiet correctness, loud corruption — race windows widening with concurrency, incidents arriving with traffic). Constraint fusion removes the window (atomic check-act — concurrency-independent correctness: quiet *and* loud both correct).

### Modern guidance

Fuse check-act per invariant (UNIQUE per identity, EXCLUDE per conflict-shape, FK per reference, SERIALIZABLE predicates per range-anomaly — mechanism per invariant class, reviewed per table); keep application pre-checks as UX (fast-fail friendly errors — user experience, not correctness: pre-checks guide, constraints decide); test races concurrently (two-client probes asserting single-survivor — verified below, committed in suites per [4.1](<../4. Important points to remember/4.1. Integrity checklist habits mentors insist on.md>)).

### Runnable example (good — the race run and shut, verified live)

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node -e "
const { Client } = require('pg');
(async () => {
  const a = new Client({ connectionString: process.env.DATABASE_URL });
  const b = new Client({ connectionString: process.env.DATABASE_URL });
  await a.connect(); await b.connect();
  const appCheckThenInsert = async (c, who) => {
    const r = await c.query('SELECT count(*)::int AS n FROM racers WHERE email = \$1', ['race@x.io']);
    if (r.rows[0].n === 0) { await c.query('INSERT INTO racers (email) VALUES (\$1)', ['race@x.io']); return who + '-inserted'; }
    return who + '-skipped';
  };
  const [ra, rb] = await Promise.allSettled([appCheckThenInsert(a, 'A'), appCheckThenInsert(b, 'B')]);
  // A: 23505 | B: B-inserted
  // rows: 1
})();"
# A: 23505 | B: B-inserted
# rows: 1
```

Verified (concurrent pg clients, same session): both checked absent simultaneously (race entered — both saw 0), both inserted (race executed), exactly one survived (UNIQUE refused the loser with `23505` — race *shut* structurally: application checks raced (both passed), constraint decided (one stored). Outcome order-independent (A-or-B wins per timing; exactly-one holds per constraint — nondeterministic winner, deterministic count).

### Common confusion

- **"our traffic is too low to race"** — races need *two* concurrent writers (deployments double connections, retries double attempts, cron overlaps jobs — concurrency arrives via operations, not traffic: low-traffic races strike during deploys/retries/cron (the worst moments — recovery windows, exactly when correctness matters most). Race-proofing costs one constraint (declared once); race incidents cost per occurrence (duplicates discovered downstream — unbounded, traffic-independent).
- **"serializable closes all races"** — serializable closes *predicate* races (range anomalies — predicate tracking + aborts); unique/exclusion/FK races close *cheaper* (constraints without level escalation — no abort rates, no retries). Right mechanism per race class (identity → UNIQUE; conflict-shape → EXCLUDE; reference → FK; range-anomaly → serializable): escalation ladder, cheapest sufficient first ([1.2](<../1. Guarantees/1.2. Isolation levels and anomalies.md>) part 3's ladder, applied).

### Performance note

Constraint-fusion cost per write (index probes — microseconds, like all uniqueness); application-race cost per incident (duplicates stored — dedupe labor + customer harm + trust repair, unbounded per occurrence, traffic-independent). Race-proofing *before* traffic (constraints at CREATE — [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)'s two-timings rule) beats race-proofing *after* incidents (cleanup migrations + retrofitted constraints + validation backfills — downtime-shaped work).

### Mentor note

The concurrent-racer demo (two clients, same millisecond, one survivor + one `23505` — five minutes): mentees watching application checks race-then-lose while constraints decide stop writing check-then-act permanently (evidence over exhortation, again). Require concurrent-race tests per unique/exclusion constraint ("prove the race shut" — two-client probes committed beside the DDL — race coverage, not just refusal coverage).
