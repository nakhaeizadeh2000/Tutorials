# 3.1. Choosing Postgres or MongoDB

Deciding between the stores by access pattern: relations and joins point relational, shape variance points document, and one store serves until measured pain says otherwise. Junior read: default Postgres, justify MongoDB. Expert read: where the default fails honestly, and what "measured pain" concretely means.

## 1) Access pattern decides

### 1) **Definition** (questions-first selection)

List the workload's most frequent questions *before* naming the store: cross-entity questions ("orders with customer names" — joins) point Postgres; nested-entity questions ("order with its items" — single fetch) point MongoDB; key lookups point cache (elsewhere). The questions decide; preferences, resumes, and conference talks don't vote.

### What problem it solves (history)

Hype-driven selection (document stores for tabular billing data — application-side joins forever; relational for shape-shifting catalogs — migration per attribute) produced the regret migrations both directions are famous for: replatforming under load with data disagreements (which store is truth *during* the move? — unanswerable mid-migration, answered in downtime). Questions-first selection prevents the migration by preventing the mismatch.

### Modern guidance

Write the top five queries per workload (frequency + shape: join/nest/lookup — the selection evidence); prototype both where genuinely ambiguous (same data, same five questions, timed — hours of prototyping vs months of regret); re-decide per service (one workload's answer never generalizes — polyglot across services, monoglot within, per part 3).

### Runnable example (good — the join question answered relationally, verified live)

```sql
-- the cross-entity question (PostgreSQL 16.15, docker, this session):
CREATE TABLE demo_customers (id SERIAL PRIMARY KEY, name TEXT);
CREATE TABLE demo_orders (id SERIAL PRIMARY KEY, customer_id INT REFERENCES demo_customers(id), total NUMERIC);
INSERT INTO demo_customers (name) VALUES ('ann');
```

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node -e "
const { Client } = require('pg');
(async () => {
  const c = new Client({ connectionString: process.env.DATABASE_URL });
  await c.connect();
  await c.query(\"INSERT INTO demo_orders (customer_id, total) VALUES (1, 19.98)\");
  const r = await c.query('SELECT c.name, o.total FROM demo_customers c JOIN demo_orders o ON o.customer_id = c.id');
  console.log('joined:', JSON.stringify(r.rows[0]));
  await c.end();
})();"
# joined: {"name":"ann","total":"19.98"}
```

Verified: enforced reference (`REFERENCES` — orphan orders rejected at write time), one query answering across entities, no application-side assembly. The document twin (embedded customer subdocument — [2.2](<../2. First queries/2.2. First MongoDB operations.md>)) answers *its* shape in one fetch; the join answers *this* shape in one query — each cheap at home, dear away.

### Common confusion

- **"we might need flexible schema later"** — speculative flexibility (paying document costs — weak joins, app-side integrity — for variance that never arrives) vs priced migration (relational now, `jsonb` columns absorbing variance later, full move only on measured pain). Speculation bills daily; migration bills once *if* ever. Default boring, migrate on evidence.
- **"benchmarks say X is faster"** — vendor benchmarks answer *their* questions on *their* hardware (write-heavy micro-ops favoring LSM trees; join-heavy analytics favoring planners — each true, each partial). Your five questions on your hardware decide; benchmarks shortlist candidates, never crown winners.

### Performance note

Selection performance is workload-relative (joins cheap relationally, nesting cheap in documents — each 10–100× dearer cross-shape at scale). Mis-selection costs compound (application-side joins = N+1 at scale; migration-every-field = DDL queue forever). Prototype-timing both candidates (hours) against mis-selection (quarters) — the cheapest performance insurance in data work.

### Mentor note

Demand the five-questions list in every store-choice review ("show me the questions" — before opining on answers): mentees producing questions first decide correctly without seniority; mentees defending preferences produce migrations later. Questions-first is the transferable skill (search/graph/time-series evaluations reuse it verbatim).

## 2) Relational by default

### 2) **Definition** (the default with an exit)

Postgres unless the questions say otherwise: enforced schemas (bad data rejected at write time — integrity as a store guarantee, not app hope), real joins (cross-entity questions answered where the data lives), transactions with teeth (multi-statement atomicity — Domain 05 owns the mechanics), and `jsonb` absorbing document-shaped variance (GIN-indexed nesting *inside* relations — the escape hatch making the default safe). Defaults need exits; this one has a documented hatch.

### What problem it solves (history)

The 2010s document-default wave (loose shapes for tabular data — joins reimplemented per service, integrity reimplemented per app, transactions wished for) relearned per team what the industry relearned collectively: most application data relates (users have orders have payments — the relational shape of business itself), and reimplementing relations in application code is slower, buggier, and unportable versus the planner doing it. Defaults encode collective tuition; pay attention to tuition already paid.

### Modern guidance

Start Postgres (solitary default — team fluency compounds on one store: tooling, reviews, incidents all share vocabulary); absorb variance with `jsonb` first (document-shaped *columns* before document-shaped *stores* — nesting per column, relations per table, both queryable); exit to MongoDB on measured document-dominance (nest-reads dwarfing joins *with numbers* — access logs, not instincts — plus shape variance defeating `jsonb` ergonomics).

### Runnable example (good — variance absorbed without leaving, described)

```sql
-- products with per-category attributes: relational core, document edge
CREATE TABLE products (id SERIAL PRIMARY KEY, name TEXT NOT NULL, attrs JSONB NOT NULL DEFAULT '{}');
-- queries both shapes: SELECT * FROM products WHERE category_id = $1 (relational)
--   AND attrs->>'color' = 'red' (document path — GIN-indexable, Domain 02/06 own mechanics)
```

Described shape (mechanics in Domains 02/06 — `jsonb` operators and GIN there, never here): relations where data relates, documents where it varies, one engine answering both. The exit stays open (full document store when variance dominates *with receipts*); the default holds until receipts arrive.

### Common confusion

- **"`jsonb` means Postgres does everything"** — `jsonb` covers *variance within relations* (attributes, configs, payloads — nested but attached); document-dominant workloads (shape *is* the data, joins rare, scale-out writes) still favor MongoDB (purpose-built distribution, driver-native documents). Hatch ≠ replacement (escape valves relieve pressure; they don't change the engine's center of gravity).
- **"default means forever"** — defaults start decisions (best prior for unknown workloads — tuition-encoded); measurements continue them (access logs per quarter — join-vs-nest ratios drifting document-ward trigger re-evaluation). Default-forever is dogma wearing prudence; default-with-exits is engineering.

### Performance note

Relational-default performance compounds operationally (one store's indexes tuned, one planner understood, one backup story tested — depth beats breadth in on-call fluency). Split stores double operational surface (two backup stories, two failure vocabularies, two tuning disciplines — paid per incident in unfamiliarity). Consolidation is operational performance wearing a simplicity costume — split on measured pain (part 3), never on forecast.

### Mentor note

Teach the default as tuition ("the industry paid for this default in regret migrations — accept the gift, spend your novelty budget elsewhere"): juniors defaulting relationally inherit decades of incident wisdom free. Exits taught alongside (jsonb hatch, MongoDB criteria) prevent default-calcification — defaults with documented exits stay engineering, never dogma.

## 3) One store per service to start

### 3) **Definition** (monoglot services, polyglot systems)

Each service starts on one store (operational surface minimal — one backup story, one failure vocabulary, one tuning discipline); systems go polyglot service-by-service (billing relational, catalog document, sessions cached — each workload's answer, independently chosen). Splits happen on measured pain (growth or shape evidence per service), never on architecture diagrams drawn before traffic exists.

### What problem it solves (history)

Day-one polyglot (Postgres *and* Mongo *and* Redis per service "for flexibility" — three failure modes, three backup stories, zero traffic) taxed every deploy with unneeded operational surface while teaching nothing (no workload yet to inform any choice — flexibility purchased before knowing what must flex). Measured splits convert flexibility from upfront tax to earned response (pain names the second store precisely when it arrives).

### Modern guidance

One store per service at launch (the access-pattern answer from part 1 — nothing more); split criteria written in advance (what measurement triggers the second store — join pain quantified? nest dominance logged? — thresholds in the ADR, not vibes); shared-nothing between splits (each store owns its entities — dual-writes minimized, sync jobs explicit and monitored — distributed consistency priced before adopted).

### Runnable example (good — the split that never happened yet, narrated)

```markdown
# shop service, month 1: Postgres only (orders+customers relational — verified join above)
# month 6: product-attribute variance explodes → jsonb attrs (hatch, same engine, no new store)
# month 14: catalog reads 100:1 nest-shaped, joins ~0 → MongoDB for catalog reads (measured:
#   access logs show 99.2% single-key nest fetches; join queries 0.01% — receipts, not forecast)
# each split earned by numbers; operational surface grew with revenue, never before it
```

```markdown
# bad: day-one polyglot (three stores, zero traffic, full surface)
# Postgres (empty) + MongoDB (empty) + Redis (empty) — three backup stories untested,
# three failure vocabularies unlearned, consistency questions unanswerable (which is truth
# for what? — undecided, undeployed, unneeded). Flexibility theater with on-call admission.
```

Why it hurts: operational surface without workload (backups untested per store — restore failures discovered per incident; failure modes unlearned — every page a tutorial; consistency undecided — dual-write bugs from week one). Fix: monoglot launch (one store, fully operated), splits earned (thresholds in ADRs, pain measured, second store onboarded deliberately).

### Common confusion

- **"microservices need polyglot persistence"** — services *may* differ (polyglot across services — each workload's answer); services *needn't* differ (monoglot per service until pain — uniformity where workloads agree). "Need" smuggles day-one complexity as principle; the principle is per-workload choice, exercised per service on evidence.
- **"migrating later costs more"** — migrating *without* the seam costs more (SQL in policy code — DesignPatterns 06/1.2's warning, linked); migrating *behind* repository seams costs a second implementation plus parity suites (bounded, planned, proven pattern). Seam-first architecture makes later splits cheap — invest in seams (certain payoff), not second stores (speculative).

### Performance note

Single-store performance focuses tuning (one planner, one index discipline, one connection story — depth per incident avoided); multi-store performance fragments attention (three shallow understandings — each incident a context-switch across failure vocabularies). Operational focus is on-call performance (right diagnosis first try — fluency depth deciding, not tool count).

### Mentor note

The split-threshold ADR ("we add MongoDB when nest-reads exceed 95% for a quarter" — written at launch, reviewed quarterly): mentees learn evidenced architecture fastest by writing thresholds that later fire (or don't — untriggered thresholds teach restraint equally). Thresholds convert philosophy into instrumentation — architecture as hypotheses with expiration dates.
