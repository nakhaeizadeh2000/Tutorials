## 3) Design and mapping (planned siblings own the ends)

### 3) **Definition** (the usage/design/map split)

*Usage* (this track: connecting, querying, choosing, proving against live stores) vs *modeling* (Database Design track: normal forms, keys, migration strategy — planned sibling) vs *mapping* (ORM track: entities, query builders, unit-of-work — planned sibling). Usage assumes modeled schemas (queries run against designed tables) and precedes mapping (raw drivers before abstractions — you cannot evaluate an ORM without having felt the driver).

### The assignments

- Schema modeling (normalization, keys, constraints as design, migration planning) → Database Design track (planned sibling per root README — textual forward, no dead link by design).
- Object mapping (entities, repositories via ORM, migrations via ORM) → ORM track (planned sibling per root README — textual forward, no dead link by design).
- Learn in order: usage (this track — feel the driver) → design (model deliberately) → mapping (abstract consciously). Skipping usage produces ORM users who can't read generated SQL (debugging blind at the first slow query); skipping design produces users with unmodelled schemas (every query a workaround).

### Common confusion

- **"ORM first is faster"** — faster to first demo (scaffolds generate CRUD — velocity visible), slower to first incident (generated N+1, lazy-load traps, migration conflicts — understanding owed with interest). Driver-first engineers evaluate ORMs (reading generated SQL — literate choice); ORM-first engineers inherit them (magic boxes — surprised quarterly). Learn bottom-up, abstract top-down.
- **"design belongs in this track"** — design *examples* appear here (declared tables per leaf — minimal shapes serving the lesson); design *discipline* lives in its track (normal forms, key strategy, evolution — systematic, not incidental). Incidental shapes teach syntax; systematic design teaches modeling — different jobs, different homes.

### Mentor note

The one-sentence router for data: "Usage questions stay here, modeling questions go to Database Design, mapping questions go to ORM, *naming* questions go to IT Vocabulary, *seam* questions go to DesignPatterns." Five homes, no overlap, every question housed — that sentence is worth more than any single leaf.
