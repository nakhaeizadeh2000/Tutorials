# 5.1. Common interview QA: database foundations

Canonical answers for the three data questions every backend interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their prices. Expert read: each answer runs evidence (verified probes, error codes, gate stages) before conclusions — prediction first, output as confirmation.

## 1) "SQL vs NoSQL — which and why?" — answer with access patterns

### 1) **Definition** (the shape-choice screen)

"When would you choose SQL vs NoSQL?" — screens for questions-first selection: hires list access patterns (join-heavy → Postgres; nest-heavy → MongoDB; key lookups → cache), default relational (tuition-encoded), and price the alternative (split stores double operational surface — [3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>)). Preference answers ("I like documents") fail; pattern answers pass before naming a product.

### What problem it solves (hiring signal)

Store choice is the highest-blast-radius data judgment (every query, every migration, every incident flows through it) — engineers deciding by fashion import fashion's failure modes (application-side joins at scale, migration-per-field paralysis). The question predicts whether data decisions will be measured or mimicked.

### Modern guidance

Answer in three beats: questions (top-five workload queries, join/nest/lookup classified), default (relational — data relates until proven otherwise, `jsonb` absorbing variance), exit criteria (nest-dominance *with numbers* earns MongoDB — access logs, not instincts). End unprompted with monoglot-start (one store per service until measured pain — [3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>) part 3): judgment, not just selection.

### Runnable example (good — the evidence behind the answer, quoted)

```bash
# relational evidence (verified live, PG 16.15): enforced FK + one-query join
# joined: {"name":"ann","total":"19.98"}
# document evidence (verified shape): nested fetch, zero joins, local ObjectId identity
# hex24: true | unique: true | has-time: true
```

A hire cites both receipts (join answered relationally, nest fetched documentarily) then chooses per *the interviewer's* workload questions ("for *your* orders-with-customers shape: Postgres — the join above is the exhibit"). Choosing for the stated workload (not reciting a favorite) is what interviewers score.

### Common confusion (in candidates)

- **"NoSQL scales, SQL doesn't"** — red flag: both scale (read replicas, partitioning, managed fleets — scaling is architecture, not category); they scale *different shapes* cheaply (write-fanout vs join locality). Scale claims without shape analysis reveal slogan-driven design — probe with "scale *which questions*?" and watch the recovery.
- **"we'll need flexible schema"** — yellow flag without evidence: speculative flexibility bills daily (weak joins, app-side integrity — paid per query); priced migration bills once *if* ever ([3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>) part 1). Strong candidates ask "which fields vary?" before blessing variance.

### Performance note

Selection answers need workload-relative numbers (join cost vs nest cost *for the stated questions* — measured in prototypes, quoted as ranges); vendor benchmarks cited as shortlists (never verdicts — [3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>) part 1's rule). Numbers volunteered with provenance outscore adjectives; humility about unmeasured corners outscores false precision.

### Mentor note

Mock with two workloads (billing-with-customers vs event-firehose-with-evolving-payloads) demanding opposite answers with the same method (five questions → default → exit check): mentees graduate when both answers land in five minutes each — method held constant, verdicts varying correctly. Method constancy is the skill; verdicts are its outputs.

## 2) "How does your app connect?" — trace the wiring

### 2) **Definition** (the wiring-trace screen)

"Walk me through this repo's database connection" — screens for compositional reasoning: hires name URL (five facts), driver (`pg` 8.23.0 / `mongodb`), handshake (`SELECT 1` / `ping` — quoted green), secrets path (env → process, `.env` gitignored), and close discipline (`end()`/`close()` — no leaked slots). Component namers pass partially; composers (all five, in data-flow order) pass fully.

### What problem it solves (hiring signal)

Connection wiring is the most-forked infrastructure in backend repos (hardcoded URLs *and* env vars *and* config files, disagreeing) — engineers who can *trace* a working wiring can *repair* a broken one and *review* a proposed one. The question predicts data-infrastructure ownership, the least glamorous and most load-bearing kind.

### Modern guidance

Answer as a trace (URL → driver → handshake → secrets → close), cite the single wiring (env var name, driver version, proof query — no alternatives mentioned unless asked), and name the gates (proof stage + secret grep — [4.1](<../4. Important points to remember/4.1. Data checklist habits mentors insist on.md>) stages 10/11). Follow-ups welcomed ("pooled?" — Domain 04; "replica?" — read/write split with lag policy; "secret rotation?" — env-scoped, independent per environment).

### Runnable example (good — the trace, quoted green)

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node handshake.js
# handshake: {"ok":1}
# closed clean
```

"URL names protocol/user/host/port/database (parsed via stdlib — five facts witnessed); `pg` connects; `SELECT 1` proves working-not-merely-reachable; env provides the secret (`.env` gitignored — `git check-ignore` match verified); `client.end()` frees the slot. Failure shape honored too: dead MongoDB port fails fast `MongoServerSelectionError`, bounded 3s, closed clean." One breath, five components, two proofs (green path + failure path) — the complete answer.

### Common confusion (in candidates)

- **"connection pooling" as the handshake** — pools *amortize* handshakes (many queries per connection — Domain 04 owns the mechanics); the handshake *proves* the path (one query, deterministic answer). Pooling answers before proving is premature (unproven paths pooled are unproven at scale — prove first, pool second, always in that order).
- **"ORM handles connections"** — ORMs *manage* pools atop drivers (same URLs, same handshakes, same secrets — one layer up); the wiring questions persist unchanged (URL facts, proof queries, secret paths — ORM or raw, identical). Candidates hiding behind the ORM reveal unexamined infrastructure — probe beneath ("what URL does it read?").

### Performance note

Wiring-trace answers need one number (handshake latency — milliseconds local, tens cloud — quoted to show cost-awareness) plus the pooling implication (per-query connects cost handshake-per-request — hundreds of ms at scale, the Domain-04 argument stated numerically in advance). Composition questions need economics, not just topology.

### Mentor note

Mock wiring-traces against the candidate's *own* repo (not a toy): "trace prod's connection, five facts, no looking." Fluency on home turf predicts on-call orientation speed directly (location-aware engineers triage in minutes — [4.1](<../4. Important points to remember/4.1. Data checklist habits mentors insist on.md>) part 3's four facts, recited cold). Home-turf tracing is the interview; terrain quizzes are the training.

## 3) "Show me injection and its fix" — demonstrate live (plus rapid-fire)

### 3) **Definition** (the sibling-demonstration screen)

"Break it, then fix it — live" — screens for security-as-mechanism (not slogans): hires concatenate (watch `42601` die on `O'Reilly`), bind (watch the identical surname store intact), then name the sibling (operator injection via request-spread — `{ $ne: null }` shape, allowlist fix). Slogan reciters ("always sanitize inputs") fail; mechanism demonstrators pass before the fix lands.

### What problem it solves (hiring signal)

Injection remains OWASP #1-adjacent decades in because developers *know about it* without *feeling its mechanism* (knowledge without scar tissue — bypassed under deadline pressure: "just this once, it's internal"). Live demonstration proves scar tissue (watched it die, fixed it structurally); sibling-naming proves transfer (SQL *and* NoSQL shapes — one rule, two spellings).

### Modern guidance

Demo in the verified pair order (break → fix → sibling): concatenate `O'Reilly` (dies `42601` — verified), bind it (stores intact — verified), spread `{ $ne: null }` as password (matches without secret — documented shape), fix with fetch-then-compare + allowlist. Close with the gate (stage 11 grep — structural enforcement, vigilance retired): demonstration convinces, automation sustains.

### Runnable example (good — the pair, quoted verbatim)

```bash
# break (verified live, PG 16.15):
# INSERT INTO shop_users (name) VALUES ('O'Reilly')
# interpolation dies: 42601 - syntax error at or near "Reilly"
# fix (verified live, same table, same surname):
# inserted: {"id":1,"name":"O'Reilly"} | rowCount: 1
```

A hire narrates the *mechanism* per line (concatenation parses data as code; placeholders exclude data from parsing) before the output confirms it — prediction first, confirmation second. Interviewers: ask "what would `OR '1'='1` do in each version?" before answering — prediction separates models from memories.

### Rapid-fire drills (with answers)

1. **Restart the DB process — data survives?** Yes, if committed (verified `docker restart` → row present — durability, not luck) ([1.1](<../1. Database identity and setup/1.1. What databases are and are not.md>)).
2. **`UPDATE` matches zero rows — error?** No error, `rowCount: 0` (the silent no-op — assert counts) ([2.1](<../2. First queries/2.1. First Postgres queries.md>)).
3. **MongoDB query with string `_id` misses — why?** Type-strict identity (cast `ObjectId()` at boundaries) ([2.2](<../2. First queries/2.2. First MongoDB operations.md>)).
4. **Gate exits 10 vs 11 — meaning?** 10: store unproven (handshake/witness); 11: interpolation present (boundary unbound) ([4.1](<../4. Important points to remember/4.1. Data checklist habits mentors insist on.md>)).
5. **`.env` committed — verdict?** Finding (rotate credentials, purge history, gitignore — secrets never in source) ([1.2](<../1. Database identity and setup/1.2. Connecting from Node.md>)).
6. **Two stores on day one — verdict?** Finding (monoglot start — split on measured pain, seam-first) ([3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>)).

### Common confusion (in candidates)

- **"sanitization fixes injection"** — sanitization *reduces* instances (escapers, denylists — bypassable per dialect/version/context); parameterization *removes* the class (unparseable data — nothing to bypass). Class-removal vs instance-reduction is the distinction interviewers probe — answer in those terms, unprompted.
- **"NoSQL has no injection"** — operator injection is the sibling (structure, not syntax — `{ $ne: null }` needs no quotes to betray). Candidates claiming immunity reveal half-model thinking; candidates naming the sibling unprompted reveal transfer ([2.2](<../2. First queries/2.2. First MongoDB operations.md>) part 2 owned there).

### Performance note

Demonstration answers need the plan-cache footnote (placeholders enable server-side plan reuse — safety *and* speed, volunteered unprompted shows depth); rapid-fire needs instantaneity (ten seconds per drill — retrieval, not reasoning). Evidence volunteered with sources beats evidence extracted; ranges beat points.

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly team health-check. Drills 2 and 4 separate witness-readers (counts, exit codes) from hope-runners; ask those first when time is short.
