# 1.1. What databases are and are not

A database is durable, shared, queryable state — three properties plain files lack, each verified live below. Junior read: the store keeps your data after restarts, serves every client the same truth, and answers questions about it. Expert read: which property each confused tool drops, and why the shape choice (tables vs documents) precedes every other decision.

## 1) Durable shared queryable state

### 1) **Definition** (the three properties)

*Durable*: committed writes survive process death (restart the server — rows remain). *Shared*: concurrent clients observe one truth (two sessions count the same row — no per-process copies). *Queryable*: ask by content (`WHERE name = 'missing'` → `0`), not by file offset. A system with all three is a database; missing any one, it is something else wearing the name.

### What problem it solves (history)

Application state lived in memory (fast, lost on restart), then in files (durable, unshared — concurrent writers corrupt; unqueryable — full scans per question). Databases fused the three: write-ahead logging for durability, MVCC/locking for sharing, indexes and query languages for questions. Every backend exists because these three stopped being trade-offs.

### Modern guidance

Reach for a database the moment state must outlive the process *and* serve more than one client *and* answer content questions — all three together, the conjunction matters. Files serve one property each (durable *or* fast, never shared-and-queryable); the store serves the conjunction. As of September 2026 the default pair for Node.js services is PostgreSQL 18 (Current; 17/16 supported — probes here run 16.15) and MongoDB 8.3 (stable).

### Runnable example (good — all three properties, verified live)

```sql
-- durable + shared setup (PostgreSQL 16.15, docker postgres:16-alpine):
CREATE TABLE IF NOT EXISTS probe_items (id SERIAL PRIMARY KEY, name TEXT);
INSERT INTO probe_items (name) VALUES ('durable') RETURNING id, name;
--  id |  name
------+---------
--   1 | durable
```

```bash
# shared: two separate sessions count the same row
docker exec dbprobe psql -U postgres -tAc "SELECT count(*) FROM probe_items;"
# 1
docker exec dbprobe psql -U postgres -tAc "SELECT count(*) FROM probe_items;"
# 1

# queryable: ask by content, get an answer (not a file offset)
docker exec dbprobe psql -U postgres -tAc "SELECT count(*) FROM probe_items WHERE name = 'missing';"
# 0

# durable: kill the process entirely, the row survives
docker restart dbprobe && docker exec dbprobe psql -U postgres -tAc "SELECT name FROM probe_items WHERE id = 1;"
# durable
```

Verified: shared (1/1 across sessions), queryable (`0` for absent content), durable (`durable` after full container restart). No application code involved — the properties belong to the store, proven at its own CLI before Node ever connects ([1.2](<./1.2. Connecting from Node.md>) performs the handshake from the other side).

### Common confusion

- **"the ORM is the database"** — the ORM translates (objects ↔ rows/documents); the store guarantees (durability, sharing, questions). Confusing them outsources the three properties to a library that provides none — the ORM track (planned sibling, see [6.1](<../6. Overlaps to avoid/6.1. Boundaries what is covered elsewhere.md>)) owns translation; this track owns the guarantees underneath.
- **"restart proved persistence"** — restart proved *durability within one container filesystem* (sufficient for the property demo; production durability additionally needs volumes, replicas, and backups — owned by Domain 06, planned, see LOG). Properties compose: process-survival here, disk-failure survival there, region-failure survival later.

### Performance note

Each property has a price: durability costs fsync latency per commit (milliseconds — batched by group commit); sharing costs concurrency control (locks/MVCC overhead per transaction); queryability costs index maintenance (writes pay for reads' speed). The prices are the *reason* for the confused tools below (each dodges one price by dropping its property) — choose properties first, pay knowingly.

### Mentor note

Run the restart demo live in front of every mentee (insert → restart → select — thirty seconds): watching a row survive process death converts "database" from vocabulary to mechanism instantly. Mentees who witnessed durability reason about backups and volumes correctly later; mentees who memorized the word don't.

## 2) Postgres vs MongoDB in one paragraph each

### 2) **Definition** (the two shapes)

*PostgreSQL*: relational tables with enforced schemas and relations — rows in `orders` reference `customers.id` by foreign key, joins answer cross-table questions, constraints reject bad data at write time. Consistency and joins are the product. *MongoDB*: document collections with flexible shape — nested JSON-like records (`{ customer: { name, tags: [...] } }`), queries as structured objects, schema enforced by application discipline. Flexibility and scale-shape are the product.

### What problem it solves (history, condensed)

Business data *is* relational (orders have customers have payments — decades of relational dominance). The 2010s web-scale wave (loose shapes, huge writes, global distribution) birthed document stores — then the industry relearned that most apps still want joins, while modern Postgres absorbed half the document use-case (`jsonb`). Fashion cycles; the shape question stays — full treatment in [3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>).

### Modern guidance

Default relational (Postgres — your data almost certainly relates); document for genuinely shape-shifting records (fields varying per record, nested reads dominating); key-value (Redis) for cache/session speed — different track's territory, named here once. "MongoDB for scale we don't have" is the most common regret migration in both directions — choose by access pattern ([3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>)), never by hype.

### Runnable example (good — the same fact, both shapes)

```sql
-- relational: shape enforced, relations explicit
CREATE TABLE customers (id SERIAL PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE orders (id SERIAL PRIMARY KEY, customer_id INT REFERENCES customers(id), total NUMERIC);
```

```javascript
// document: shape flexible, nesting inline (MongoDB shell spelling — verified in 2.2)
db.orders.insertOne({ customer: { name: "ann" }, items: [{ sku: "a1", qty: 2 }], total: 19.98 });
```

Same order, two philosophies: enforced foreign keys vs embedded subdocuments. Neither is "simpler" — simplicity lives at the query pattern (join-heavy → tables; nest-heavy → documents), decided per workload in [3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>).

### Common confusion

- **"NoSQL means no schema"** — it means *flexible/enforced-elsewhere* schema (IT Vocabulary 05/1.2's verdict, linked not restated). Schemaless stores without application-level shape discipline become swamps with faster writes — flexibility is a design burden moved, not removed.
- **"Postgres can't do documents"** — `jsonb` stores, indexes, and queries nested documents inside the relational engine (GIN indexes, `->` operators — Domain 02 owns the mechanics). "Can't" is outdated by a decade; "should it for *your* workload" is the live question ([3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>) decides per access pattern).

### Performance note

Shape performance follows queries, not stores (join-heavy on documents = application-side joins, slow; nest-heavy on tables = wide rows or N+1, slow). Benchmark the *workload's* questions per candidate store (same data, same questions, timed) — store benchmarks without workload questions measure marketing. Measure yours; the shape that answers fastest wins.

### Mentor note

Teach the shape choice with one question per workload ("show me the three most frequent questions this data must answer"): join-shaped answers point relational; nest-shaped point document. Mentees answering from questions instead of preferences make portable decisions — the habit transfers to every store they will ever evaluate (search, graph, time-series included).

## 3) Not spreadsheets, not caches, not queues

### 3) **Definition** (three impostors, three missing guarantees)

*Spreadsheets* (CSV/Sheets): durable-ish, single-writer, unqueryable at scale — drop sharing (concurrent edits fork) and questions (filters aren't indexes). *Caches* (Redis-as-primary): shared and fast, non-durable by design (eviction is the feature — restart empties) — drop durability deliberately for speed. *Queues* (message brokers): durable transit, not state (consumed messages vanish — retention is the bug, not the feature) — drop queryable rest-state by architecture.

### What problem it solves (history)

Every team inherits a spreadsheet-that-became-a-database (concurrent editors forking versions, "querying" with eyeballs — integrity gone by row 10,000), a cache-treated-as-truth (eviction deleting the only copy — the outage named "but Redis had it"), or a queue-queried-as-state (replaying logs to answer "what's the balance?" — O(history) per question). Naming the impostor routes the data to its real store before the incident names it.

### Modern guidance

Spreadsheet on day zero → Postgres by first concurrent writer (migrate at the fork, not after); cache *in front* of the store (cache-aside with TTL — stale briefly beats absent totally; the store remains truth); queues *between* services (transit with retention policies — state lives in a store at rest, never in flight). Each tool excellent inside its guarantees, catastrophic outside — boundaries are the skill.

### Runnable example (good — the routing table, applied)

```markdown
# needs durability + sharing + questions → database (Postgres/MongoDB — this track)
# needs speed over survival → cache in front (Redis — TTL'd, store behind stays truth)
# needs delivery between services → queue between (retention + ack — state rests in a store)
# needs eyeballs on 200 rows once → spreadsheet (migrate when writers multiply)
```

```bash
# bad: cache as the only copy (verified shape of the incident, not executed — never execute data loss)
# redis SET session:abc "{...}" EX 3600  →  restart/evict  →  session gone, no store behind
# the fix is architectural (store behind cache), never operational (bigger cache, longer TTL)
```

Why the bad hurts: eviction (the cache's *correct* behavior) reads as data loss (the application's *catastrophe*) — correctness and catastrophe sharing one mechanism, distinguished only by architecture. Fix the architecture (truth in the store, speed in the cache), not the knob (TTL tuning postpones, never prevents).

### Common confusion

- **"Redis persists, so it's a database"** — persistence options (RDB/AOF) make Redis *durable-ish*; the data model (no relations, no ad-hoc queries, eviction-first design) still drops queryability and sharing semantics databases guarantee. Durable cache ≠ database (one property ≠ three) — use each for its guarantees.
- **"our queue retains, so it stores"** — retained logs answer replay questions (event sourcing *built atop* logs with snapshots and projections — architecture, not default); raw queues answer "what's current?" at O(history) per ask. Retention is transit insurance, not state — build state stores from streams deliberately (projected, indexed, queryable), never by querying the broker.

### Performance note

Right-tool performance is order-of-magnitude (cache lookups microseconds vs store milliseconds — the gap that justifies two systems, not one); wrong-tool performance is cliff-shaped (spreadsheet scans, queue replays, eviction storms — each degrading superlinearly past its design envelope). Operate each tool inside its envelope (sizes, TTLs, retention reviewed); migrate across tools at envelope edges (the routing table above, revisited per growth spurt).

### Mentor note

The impostor quiz ("we keep X in Y — which guarantee are we betting against?") converts architecture reviews from taste to guarantees-talk in one question. Mentees answering in properties (durable/shared/queryable per tool) route data correctly for life; mentees answering in products ("we use Postgres for everything") route by habit until the incident reteaches them.
