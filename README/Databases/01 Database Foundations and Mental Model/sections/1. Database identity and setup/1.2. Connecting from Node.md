# 1.2. Connecting from Node

How a Node.js program reaches a database: connection strings naming five facts, the connect-prove-close handshake, and secrets kept out of source. Junior read: one URL, one client, one probe query. Expert read: what each URL slot controls, why handshakes belong in scripts, and the credential discipline reviewers enforce.

## 1) Connection strings name everything

### 1) **Definition** (the five-fact URL)

`postgres://app:s3cret@db-primary:5433/shopdb` names protocol (`postgres:` — driver and dialect), credentials (`app:s3cret` — who, proven how), host (`db-primary` — where), port (`5433` — which program on the machine; 5432 Postgres default, 27017 Mongo), and database (`shopdb` — which namespace inside the server). MongoDB's twin adds query options (`mongodb://app:s3cret@mongo-primary:27017/shopdb?retryWrites=true` — driver behavior flags in the URL itself).

### What problem it solves (history)

Scattered connection config (host here, password there, port assumed) produced "works on my machine" as a service: five facts in four places, each environment differing in one. The URL concentrates all five in one string — diffable per environment, printable (redacted) in diagnostics, parseable by every driver identically.

### Modern guidance

One URL per environment (`DATABASE_URL` for the primary store; named siblings `MONGO_URL`, `REPLICA_URL` where they exist — never positional ambiguity); ports explicit always (defaults assumed are defaults forgotten — the next refactor changes them silently); options in the URL for driver behavior (`retryWrites`, `sslmode` — behavior versioned with the string, not tribal knowledge).

### Runnable example (good — parse both URLs, five facts each, verified)

```bash
node -e "
const u = new URL('postgres://app:s3cret@db-primary:5433/shopdb');
console.log('protocol:', u.protocol, '| user:', u.username, '| host:', u.hostname, '| port:', u.port, '| database:', u.pathname.slice(1));"
# protocol: postgres: | user: app | host: db-primary | port: 5433 | database: shopdb

node -e "
const u = new URL('mongodb://app:s3cret@mongo-primary:27017/shopdb?retryWrites=true');
console.log('protocol:', u.protocol, '| user:', u.username, '| host:', u.hostname, '| port:', u.port, '| database:', u.pathname.slice(1), '| opts:', u.search);"
# protocol: mongodb: | user: app | host: mongo-primary | port: 27017 | database: shopdb | opts: ?retryWrites=true
```

Verified with Node v20.20.2 built-in `URL` (no driver needed to *read* the string — parsing is stdlib; connecting is the driver's job, part 2). Quote the redacted URL (password masked) in bug reports — the five facts minus the secret diagnose most connection failures outright.

### Common confusion

- **"port is optional"** — omittable, never absent (drivers default 5432/27017 — the default holds until the environment overrides it: Docker-mapped ports, managed instances, sidecars). Explicit ports survive environment changes; defaulted ports break silently at the first remap. Write the port.
- **"`/` path means filesystem"** — the path is the *database name* (`/shopdb` — namespace inside the server, not a directory). Connecting to the wrong database (default `postgres` vs app `shopdb`) is the quietest misconfiguration: queries run, tables "missing" — always verify the fifth fact, not just the host.

### Performance note

URL parsing costs microseconds once per process (parsed at client construction — never per query). Connection *establishment* costs milliseconds-to-seconds (TCP + TLS + auth handshake — the reason part 2's handshake and Domain 04's pooling exist). Parse cheaply, connect deliberately, pool persistently.

### Mentor note

Make mentees recite the five facts for their service's URL from memory (protocol/user/host/port/database — thirty seconds): anyone who can't name the port or database will misdiagnose the next connection failure as a code bug. URL literacy is connection-debugging literacy — drill it on day one.

## 2) Connect, prove, close

### 2) **Definition** (the handshake rite)

Open a client from the URL → run a proof query (`SELECT 1` / `ping`) → close cleanly. The proof query distinguishes *connected* (socket open) from *working* (server answering): firewalls and proxies open sockets to black holes — only an answered query proves the path end to end. Every script, service boot, and CI job performs it first.

### What problem it solves (history)

"Connected successfully" logs preceding total query failure (proxies accepting TCP then dropping, wrong-database connections answering trivially, auth passing but permissions denying) taught the industry that sockets lie and only answers tell truth. The proof query (one round trip, deterministic answer) converts connection hope into connection evidence — thirty seconds that prevent hours of app-vs-network ambiguity.

### Modern guidance

Handshake per entry (service boot fails fast on proof failure — crash-looping visibly beats serving blindly); handshake per script (migrations and seed jobs prove before mutating — never write through an unproven connection); close explicitly (`client.end()` / `close()` — leaked clients exhaust server connection caps, the finite resource behind every "too many clients" page).

### Runnable example (good — live handshake, verified)

```javascript
// handshake.js — pg 8.23.0 against PostgreSQL 16.15 (docker, this session)
const { Client } = require('pg');
(async () => {
  const client = new Client({ connectionString: process.env.DATABASE_URL });
  await client.connect();
  const r = await client.query('SELECT 1 AS ok');
  console.log('handshake:', JSON.stringify(r.rows[0]));
  await client.end();
  console.log('closed clean');
})().catch(e => { console.error('FAIL', e.message); process.exit(1); });
```

```bash
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node handshake.js
# handshake: {"ok":1}
# closed clean
```

Verified: answered (`{"ok":1}` — server working, not merely reachable), closed (`closed clean` — no leaked connection server-side). The MongoDB twin (`new MongoClient(url)` → `ping` → `close`) follows the identical rite — driver spelling differs, evidence discipline doesn't. Honest scope note: no MongoDB server executes in this session's probe lab (v8 image refuses kernel 6.19 per SERVER-121912, verified in daemon logs; v7.0 pull blocked by registry auth EOF ×3) — Mongo *URL parsing* above and the fail-fast probe below are verified; server-round-trip snippets in [2.2](<../2. First queries/2.2. First MongoDB operations.md>) are documented from the MongoDB 8.3 manual and labeled per snippet.

### Runnable example (failure shape — the driver fails fast and names it, verified)

```bash
node -e "
const { MongoClient } = require('mongodb');
(async () => {
  const client = new MongoClient('mongodb://localhost:27018/?serverSelectionTimeoutMS=3000');
  try { await client.connect(); console.log('UNEXPECTED-UP'); }
  catch (e) { console.log('fails-fast:', e.name); }
  finally { await client.close(); console.log('closed clean'); }
})();"
# fails-fast: MongoServerSelectionError
# closed clean
```

Verified (mongodb driver, no server listening): named error (`MongoServerSelectionError` — topology, not code), bounded wait (`serverSelectionTimeoutMS` — never the 30s default in scripts), clean close regardless. Failure behavior this explicit is a feature: catch by name, retry or abort by policy, never string-match messages.

### Common confusion

- **"`connect()` succeeding means queries work"** — `connect()` proves TCP+auth (the socket half); the proof query proves the working half (permissions, database existence, server health). Both, in that order — the rite has two beats because failures have two halves.
- **"close is optional at process exit"** — unclosed clients delay exit (sockets hold the event loop — Node hangs "mysteriously" after main completes) and consume server slots meanwhile (finite cap shared across replicas — leaks compound fleet-wide). Close explicitly, always — one line preventing two incident classes.

### Performance note

Handshake cost per process boot (one round trip — milliseconds local, tens of ms cloud) — negligible against service lifetime, load-bearing at boot (fail-fast beats boot-blind). Per-query connections (open-proof-close per query) cost the handshake *per query* — hundreds of ms per request at scale, the performance argument for pooling (Domain 04) stated numerically in advance.

### Mentor note

Require the handshake as the first lines of every database script in review ("prove before mutate" — the rule that prevents migrations running against wrong databases). Mentees internalize it fastest by breaking it once: point a seed script at the wrong database *with* the proof (fails loudly, zero writes) vs without (writes somewhere surprising) — the contrast teaches permanently.

## 3) Secrets never in source

### 3) **Definition** (the credential boundary)

Connection strings carry passwords — therefore they never appear in source files, diffs, logs, or bug reports unredacted. They live in environment (`DATABASE_URL` per environment — shell, container env, secret manager), loaded at runtime, gitignored at rest (`.env` + `.env.*` in `.gitignore` — committed never). The boundary: code reads `process.env`, platforms provide values, repos contain neither.

### What problem it solves (history)

Committed credentials (URLs in source, dumps in fixtures, passwords in Slack threads) leak durably (git history remembers — rotation required, not deletion) and widely (every clone carries the secret — ex-employees, forks, breaches). Env-based secrets leak narrowly (one environment, rotatable independently) and briefly (revoke + rotate, no history surgery). The boundary converts credential incidents from repo-wide to environment-scoped.

### Modern guidance

`.env` locally (gitignored — verified below), secret manager in shared environments (never copy-paste between them — each environment mints its own credentials); `process.env` exclusively in code (no config files carrying passwords — reviewed by grep: `grep -ri "postgres://.*:" src/` must return nothing); redacted diagnostics (log host/database, never userinfo — `new URL(str).password = "***"` before printing).

### Runnable example (good — ignored and loaded, verified)

```bash
printf 'DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres\n' > .env
printf '.env\nnode_modules\n' > .gitignore
git check-ignore -v .env
# .gitignore:1:.env	.env
DATABASE_URL=$(grep DATABASE_URL .env | cut -d= -f2-) node -e "
const { Client } = require('pg');
(async () => {
  const client = new Client({ connectionString: process.env.DATABASE_URL });
  await client.connect();
  console.log('env-handshake:', JSON.stringify((await client.query('SELECT 1 AS ok')).rows[0]));
  await client.end();
})();"
# env-handshake: {"ok":1}
```

Verified: ignore rule matches (`.env` invisible to git — the boundary enforced by tooling, not memory), env-loaded URL handshakes green. The rite from part 2 composed with the boundary: prove *through* the secret path actually used (env), never a hardcoded twin (which proves a different configuration than production runs).

### Common confusion

- **"`.env.example` with real values helps onboarding"** — examples carry *shape* (keys + placeholders + comments — `DATABASE_URL=postgres://user:pass@host:5432/db`), never *values* (real passwords in examples commit the very secret the file exists to avoid). Shape documented, values minted per developer — onboarding that stays secure past day one.
- **"tests need embedded credentials"** — tests need *injected* credentials (CI secrets → env → same `process.env` path — identical code path, environment-provided values). Embedded test passwords commit real access (test databases get promoted, credentials persist) — inject, never embed, at every fidelity.

### Performance note

Secret loading costs one env read per boot (free) — against committed-credential incidents (rotation across history: filter-repo surgery + forced rotation + audit — days of toil per occurrence). The cheapest security practice in this domain by two orders of magnitude: one gitignored file, zero committed secrets, forever.

### Mentor note

Audit every repo's history once (`git log -p | grep -i "postgres://[^ ]*:[^ ]*@"` — committed URLs surface immediately): findings become the rotation ticket *and* the onboarding story ("this is why we gitignore"). Mentees who watched a real rotation never commit a secret twice — scar tissue as curriculum, administered kindly.
