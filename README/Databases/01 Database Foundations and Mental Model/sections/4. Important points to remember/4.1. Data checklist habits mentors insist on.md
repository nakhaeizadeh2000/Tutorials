# 4.1. Data checklist (habits mentors insist on)

The three habits that keep database work boring: prove the store, bind every boundary, and know where the data lives. Junior read: a copy-paste gate script. Expert read: which incident each stage names, and why data checks belong in CI rather than memory.

## 1) Prove the store before trusting it

### 1) **Definition** (the 30-second rite)

Per environment, before any real work: handshake (`SELECT 1` / `ping` — the rite from [1.2](<../1. Database identity and setup/1.2. Connecting from Node.md>)), throwaway write + read-back (insert probe row, select it, delete it — witnesses from [2.1](<../2. First queries/2.1. First Postgres queries.md>)), and version print (server version logged — behavior varies per major, assumptions end here). Thirty seconds per environment; run on setup, on bump, on move, on doubt.

### What problem it solves (history)

Unproven environments failed in the worst ways (migrations against wrong databases — writes landing somewhere surprising; version-skewed behavior — features assumed, absent; network-adjacent black holes — sockets open, answers never): each a "code bug" investigated for hours that a thirty-second rite names in seconds. The rite converts environment trust from assumption to observation, per environment, per change-event.

### Modern guidance

Rite after setup, after every server/driver bump, after moving entries between environments, and inside CI (proof stage asserting the test database answers — green rite or red build, never blind suites). Keep the probe row namespaced (`__rite_probe__` — unmistakable in audits, deletable without thought); log the version per run (version drift between environments is the silent behavior fork — printed versions make it visible).

### Runnable example (good — the gate stages, verified)

```bash
#!/bin/bash
# data gate: prove store + witness write + parameter discipline
DATABASE_URL=postgres://postgres:probe@localhost:5433/postgres node -e "
const { Client } = require('pg');
(async () => {
  const c = new Client({ connectionString: process.env.DATABASE_URL });
  await c.connect();
  const r = await c.query('SELECT 1 AS ok');
  if (r.rows[0].ok !== 1) process.exit(10);
  const w = await c.query('SELECT count(*)::int AS n FROM probe_items');
  if (w.rows[0].n < 1) process.exit(11);
  await c.end();
})().catch(() => process.exit(10));" || exit 10
! grep -rn 'query(`' gatesample/ 2>/dev/null || exit 11
echo DATA-GREEN
```

Verified: stage 10 (handshake + witness read of the `probe_items` row surviving since unit 4), stage 11 (interpolation grep fires on the planted file, silent when clean). Exit codes narrate the failure: 10 unproven store, 11 unbound boundary — the on-call engineer reads the number before opening a log.

### Common confusion

- **"CI passing means the store is fine"** — CI suites often run against fakes/mocks (fast, deterministic — DesignPatterns 06's prescription, linked) while staging runs the real store unproven. The rite belongs where the *store* runs (dev, staging, prod deploys — each environment proven, not just the code tested).
- **"one rite per repo lifetime"** — the rite expires on every server/driver/URL change (yesterday's proof describes yesterday's topology). Re-run per change-event; automate per pipeline (proof stage in CI — asserted per merge, not per memory).

### Performance note

Thirty seconds per rite (handshake + write + read + version), triggered on change-events — against multi-hour app-vs-environment ambiguity per incident. Automate it (postinstall, predeploy, CI stage) and the cost drops to zero human seconds; the payoff stays step-function per caught drift.

### Mentor note

Onboard every mentee with the rite live (their machine, their first handshake, witnessed): anyone who proved the store once distrusts unproven environments forever. The habit generalizes (unproven caches, queues, APIs — same rite shape, different proof query) — teach the pattern, not just the database instance.

## 2) Parameters on every boundary

### 2) **Definition** (the grep-gate rule)

All external data crosses into queries bound (`$1` / BSON values / allowlisted fields — never concatenated, never spread): enforced by grep in review (`query(\`` hits triaged) and by gate in CI (stage 11 above — interpolation present fails the build). The rule covers *both* stores (SQL placeholders *and* MongoDB field allowlists — [2.2](<../2. First queries/2.2. First MongoDB operations.md>) part 2's sibling class rides the same gate philosophy).

### What problem it solves (history)

Reviewed-away injection (human eyes catching concatenation most of the time — the misses reaching production on schedule) upgraded to gated-away injection (machines catching every instance — misses structurally impossible to merge). Review vigilance tires per PR; gates don't tire per commit. The rule moves injection defense from attention (finite) to automation (constant).

### Modern guidance

Gate stage per repo (grep patterns per stack: backtick-queries, `+`-built filters, `find(req.*)` spreads — each pattern a stage with an exit code); review hits as findings (every grep hit either parameterized or allowlisted with a comment — no bare suppressions); extend per store (SQL concatenation *and* NoSQL operator-spread — both shapes gated, neither trusted to eyeballs).

### Runnable example (good — the gate catching, verified above)

```bash
# planted: gatesample/dirty.js → stage 11 fires with the filename (evidence, not suspicion)
# cleaned: file removed → DATA-GREEN (the gate as merge signal, not decoration)
```

Pair with [2.1](<../2. First queries/2.1. First Postgres queries.md>) part 2's live pair (concatenation dies `42601`, placeholders hold) and [2.2](<../2. First queries/2.2. First MongoDB operations.md>) part 2's sibling (operator injection via request-spread): three evidences, one rule — boundaries bind, everywhere, always.

### Common confusion

- **"linters cover this"** — security linters flag *known* patterns (heuristic, versioned, bypassable — `eval`-grade cleverness evades); the gate asserts *absence of the concatenation shape* in query calls (simpler, stricter, fewer false negatives). Both (linter breadth + gate strictness), never either/or — defense in depth, not in duplication.
- **"internal queries are exempt"** — internal callers change (today's cron becomes tomorrow's endpoint — trust boundaries move per refactor, never per audit). Exemptions rot (the "internal-only" query exposed via a new route, unbound, unreviewed). No exemptions: bind everything, the uniformity *is* the safety.

### Performance note

Gate cost per run: one grep (milliseconds) — the cheapest CI stage after version prints. Interpolation incidents cost breach response (rotation, disclosure, forensics — priced in six figures and trust). Asymmetry funds the gate permanently — cheapest stage, highest blast-radius exclusion.

### Mentor note

First review comment on every data PR: "show me the binds" (parameters per external value, allowlist per spread field — two seconds to ask, permanent habit to form). Mentees internalize boundary discipline when reviewers ask thrice; the fourth PR arrives pre-bound. Questions beat lectures — ask, don't preach.

## 3) Know where the data lives

### 3) **Definition** (the four facts, recited)

Host, port, database name, backup story — recited per environment without looking: `db-primary:5433/shopdb`, nightly dumps + WAL archive, restore tested last quarter. The facts live in runbooks (linked from alerts), in onboarding (week-one recitation), and in incident channels (stated at triage start — "which database are we talking about?" answered before theorizing).

### What problem it solves (history)

Location-ambiguous incidents ("the database is slow" — which cluster? which database? primary or replica? prod or staging-that-looks-like-prod?) burned the first twenty minutes per page on orientation (messages pinged, dashboards guessed, wrong clusters investigated). Stated location focuses instantly (right host, right database, right backup status — triage starting from facts, not search).

### Modern guidance

Runbook per environment (host:port/db, topology, backup/restore status with dates — reviewed quarterly, stale runbooks worse than none); recite on onboarding (new engineers state the four facts unaided by week two — IT Vocabulary 02's map exercise, linked); announce at triage ("shopdb on db-primary:5433, replica lag 0, last restore test Aug" — thirty seconds focusing every responder).

### Runnable example (good — the facts, stated)

```markdown
# shopdb, production (stated, not searched):
# host: db-primary (managed, multi-zone) · port: 5433 · database: shopdb
# backups: nightly dump + continuous WAL · restore tested: 2026-08 (32 min, documented)
# replica: shopdb-ro (lag < 1s typical) · failover: manual, runbook p.3
```

### Common confusion

- **"connection strings document this"** — strings name three facts (host/port/database — [1.2](<../1. Database identity and setup/1.2. Connecting from Node.md>) part 1) but never the fourth (backup/restore story — operational, not addressable). Addresses locate; backup status reassures (recovery possible, tested, timed). Both stated, neither assumed.
- **"managed means unbothered"** — managed moves backup *execution* to the provider (patches, snapshots, failover automated); retention *verification* stays yours (restore tests scheduled, RTO/RPO asserted — IT Vocabulary 02's warning, linked). Unverified managed backups fail at restore time with provider status pages green — verify, per schedule, forever.

### Performance note

Recitation costs seconds (stated facts); orientation-search costs tens of minutes per incident ( Dashboards guessed, channels asked). Runbook maintenance costs minutes quarterly; stale-runbook incidents cost hours (wrong facts worse than no facts — quarterlies keep them true). Facts are triage performance wearing an administrative costume.

### Mentor note

Quiz the four facts cold per 1:1 monthly (host/port/database/backup-date — thirty seconds): mentees answering instantly own their terrain; mentees searching own a todo (read the runbook this week). Terrain ownership predicts on-call performance more reliably than query fluency — quiz terrain, teach queries alongside.
