# 2.1. First Postgres queries

The complete first hour with PostgreSQL: tables, the four statements, bound parameters, and reading your own results. Junior read: copy these five commands and data moves. Expert read: why placeholders are structural (not careful), and what row counts plus `RETURNING` prove per write.

## 1) Tables, rows, and four statements

### 1) **Definition** (the relational first hour)

`CREATE TABLE` declares shape (columns, types, constraints — enforced at write time); `INSERT` adds rows; `SELECT` asks by content (`WHERE` filters, never file offsets); `UPDATE`/`DELETE` change or remove by the same filters. Four statements plus one declaration cover most application I/O — everything else (joins, indexes, transactions) composes them, owned by Domain 02.

### What problem it solves (history)

Ad-hoc persistence (JSON files per entity, in-memory maps "until we need a database" — schema drifting per writer, queries as full scans, concurrent writes corrupting) collapses the week concurrent writers arrive. Declared tables convert drift to contract (one shape, enforced), scans to indexed questions, and concurrent writes to transactions — the three properties from [1.1](<../1. Database identity and setup/1.1. What databases are and are not.md>) made concrete per statement.

### Modern guidance

Declare types that mean it (`TEXT NOT NULL` over nullable-by-default — nullability is a decision, not an accident; `SERIAL PRIMARY KEY` for surrogate identity — sequences owned by the store, never the app); filter deliberately (`WHERE` on every `UPDATE`/`DELETE` — unfiltered writes are the "oops" heard across the office); verify live per environment (the handshake from [1.2](<../1. Database identity and setup/1.2. Connecting from Node.md>) precedes every session below).

### Runnable example (good — full CRUD cycle, verified live)

```sql
-- shape first (PostgreSQL 16.15, docker, this session):
CREATE TABLE shop_users (id SERIAL PRIMARY KEY, name TEXT NOT NULL, status TEXT NOT NULL DEFAULT 'new');
-- CREATE TABLE
```

```javascript
// pg 8.23.0 — insert/select/update/delete, each reporting (DATABASE_URL env, per 1.2)
const ins = await c.query("INSERT INTO shop_users (name, status) VALUES ($1, $2) RETURNING id, name", ["O'Reilly", "new"]);
// inserted: {"id":1,"name":"O'Reilly"} | rowCount: 1
const sel = await c.query("SELECT id, name, status FROM shop_users WHERE status = $1", ["new"]);
// selected: 1 {"id":1,"name":"O'Reilly","status":"new"}
const upd = await c.query("UPDATE shop_users SET status = $1 WHERE name = $2", ["active", "O'Reilly"]);
// updated: 1
const del = await c.query("DELETE FROM shop_users WHERE status = $1", ["active"]);
// deleted: 1
```

Verified end to end: declared shape, apostrophe-bearing name stored intact, filtered reads, counted writes, clean delete — the relational first hour with receipts per statement.

### Common confusion

- **"`SELECT *` is fine to start"** — `SELECT *` couples queries to column order and width (schema additions silently widen every consumer — payload bloat, deserialization surprises); explicit columns document intent and survive migrations. Prototypes tolerate `*`; anything committed names its columns.
- **"DDL belongs in migrations, not here"** — true at scale (Domain 04 owns migration discipline); false for learning (hand-written `CREATE TABLE` teaches types/constraints faster than any migration abstraction). Learn DDL by hand, ship DDL via migrations — in that order, always.

### Performance note

First-hour performance is correctness-shaped (right rows, right filters — speed comes later via indexes in Domain 02/06). One habit with immediate payoff: `WHERE`-filtered writes (unfiltered `UPDATE`/`DELETE` lock whole tables — seconds of contention per accident, the most expensive typo in SQL). Filter first, execute second — every statement, every time.

### Mentor note

Pair the first CRUD with the row-count narration ("inserted 1, selected 1, updated 1, deleted 1 — each number witnessed"): mentees who read counts catch silent no-ops (UPDATE matching zero rows "succeeds" — the count is the only witness) from day one. Counts are the cheapest assertion in SQL — teach them before `WHERE` subtleties.

## 2) Parameters, never interpolation

### 2) **Definition** (structural injection immunity)

`$1, $2` placeholders separate *code* (the statement text, parsed once) from *data* (bound values, never parsed): `O'Reilly` arrives as a value the parser never inspects — quoting, escaping, and attacker-crafted syntax all inert by construction. Interpolation concatenates data *into* code (parsed together — every quote a potential breakout). Parameters don't avoid injection carefully; they remove the mechanism entirely.

### What problem it solves (history)

String-built SQL (`` `... '${name}' ...` `` — the JS 11 template-literal shape this track links) produced injection as an industry (Bobby Tables → breaches → OWAsps #1 for a decade): each fixup (escaping functions, denylists, WAFs) patched instances while concatenation preserved the class. Placeholders killed the class: unparseable data cannot break out of a query it was never part of.

### Modern guidance

Bind every value from outside the statement text (user input, config, upstream responses — *all* external data, no exceptions for "trusted" sources — trust boundaries move, placeholders don't care); keep identifiers static (table/column names can't parameterize — allowlist them in code, never from input); review by grep (`grep -n "query(\`" src/` — every template-literal query is a finding until proven static).

### Runnable example (good — the break and the hold, verified pair)

```bash
# interpolation breaks on a surname (verified live — and this is the GENTLE case):
# INSERT INTO shop_users (name) VALUES ('O'Reilly')
# interpolation dies: 42601 - syntax error at or near "Reilly"
```

```javascript
// placeholders hold the identical value (verified live, same session):
await c.query("INSERT INTO shop_users (name, status) VALUES ($1, $2) RETURNING id, name", ["O'Reilly", "new"]);
// inserted: {"id":1,"name":"O'Reilly"} | rowCount: 1
```

Verified pair: same surname, same table — concatenated dies `42601` (accidental breakage today, exploitable breakout tomorrow — `' OR '1'='1` needs no invitation where quotes concatenate), bound stores intact. The error code is the lesson: `42601` syntax error is injection's fingerprint at its politest.

### Common confusion

- **"escaping equals parameters"** — escaping is *careful* (correct per dialect, per version, per context — three axes of drift); parameters are *structural* (no parsing, nothing to get right). Careful fails on the axis nobody checked (second-order injection — stored values re-concatenated later — defeats escapers routinely). Structure has no axes to drift on — prefer it absolutely.
- **"ORMs handle this, raw SQL is the risk"** — ORMs parameterize *their generated* SQL (safe); raw fragments inside ORMs (`.where("status = '" + s + "'")` — the escape hatch every ORM provides) concatenate identically. The risk is concatenation, not rawness — parameterized raw SQL beats concatenated ORM fragments every time.

### Performance note

Parameterized statements enable server-side plan caching (parse once, execute many with different binds — measurable on hot paths: planning overhead eliminated per repeat). Interpolation defeats the cache (every concatenation a novel statement — parsed, planned, and cached separately until the cache churns). Safety *and* speed from one mechanism — the rare free lunch, eaten via `$1`.

### Mentor note

The `O'Reilly` demo converts skeptics in ninety seconds (concatenate → `42601`; bind → stored — same surname, opposite outcomes): run it live per onboarding cohort, then grep the repo together (`query(\`` hits triaged on the spot). Developers who watched interpolation die on a surname never concatenate again — scar tissue, administered kindly.

## 3) Read your own results

### 3) **Definition** (counts and `RETURNING` as witnesses)

Every write reports: `rowCount` (rows affected — the affected-set witness) and `RETURNING` (the written values back — the content witness). `UPDATE` matching zero rows "succeeds" (no error — the count `0` is the *only* signal the target didn't exist); `INSERT ... RETURNING id` hands back the generated key (no second `SELECT` — no race between write and re-read). Results read per statement; silence trusted never.

### What problem it solves (history)

Fire-and-forget writes (unread results — "it didn't throw, so it worked") hid no-op updates (stale IDs, wrong filters — zero rows touched, green logs), lost generated keys (re-`SELECT` by non-unique columns — wrong row under concurrency), and masked constraint surprises (defaults applied silently — assumed values vs stored values diverging). Reading results converts "no error" (weak evidence) into "one row, this content" (strong evidence) per write.

### Modern guidance

Assert counts where cardinality matters (update-one flows: `rowCount === 1` or throw — stale-target updates fail loudly, never silently); `RETURNING` generated values always (ids, timestamps, defaults — read back what the store decided, never assume); log counts on bulk writes (migrated N, deleted M — operations narrate their blast radius in numbers).

### Runnable example (good — witnesses per statement, verified)

```bash
# from the verified cycle above — every statement reported:
# inserted: {"id":1,"name":"O'Reilly"} | rowCount: 1   (content + count)
# selected: 1 {...}                                    (count + content)
# updated: 1                                           (count — target existed)
# deleted: 1                                           (count — removed exactly one)
```

```javascript
// bad: unread results (the silent no-op — same API, zero witnesses)
await c.query("UPDATE shop_users SET status = $1 WHERE id = $2", ["active", 999999]);
// rowCount: 0 — no error, nothing updated. Unread, this "succeeds."
// Fix: if (upd.rowCount !== 1) throw new Error("user 999999 missing — stale write refused");
```

Why unread hurts: the application proceeds on false premises (updated state assumed, stored state unchanged — downstream reads contradict the write the logs claim succeeded). The count is a one-line assertion away; skip it and debugging starts from a lie ("but the update succeeded").

### Common confusion

- **"`RETURNING` costs a round trip"** — `RETURNING` rides the write's round trip (same statement, same latency — the values come back with the acknowledgement). A follow-up `SELECT` costs the *extra* round trip (plus the race — concurrent modification between write and re-read). `RETURNING` is faster *and* more correct — the follow-up SELECT is pure cost with negative correctness.
- **"counts suffice, content is luxury"** — counts witness *cardinality* (how many); `RETURNING` witnesses *content* (which values — defaults, generated ids, trigger-modified rows). Defaults surprise most (assumed `status: 'new'` vs stored `'pending_review'` — content witness catches what counts can't). Both witnesses, per write, always.

### Performance note

Witness-reading costs nothing extra (counts and `RETURNING` arrive with the write's response — bytes already transferred). Unwitnessed writes cost incident-hours per silent no-op (stale-target updates discovered downstream — the most misdirected debugging shape in data code: symptoms far from the unwitnessed write). Free evidence vs dear ambiguity — read, always.

### Mentor note

Require count-assertions in review for update/delete paths ("show me the `rowCount` check" — two seconds to ask, permanent habit to form): mentees internalize witness-reading when reviewers ask thrice. The question generalizes (MongoDB's `matchedCount`/`modifiedCount` in [2.2](<./2.2. First MongoDB operations.md>) get the same treatment — one habit, both stores).
