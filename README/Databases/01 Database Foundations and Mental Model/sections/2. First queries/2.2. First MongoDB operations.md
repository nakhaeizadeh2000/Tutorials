# 2.2. First MongoDB operations

The complete first hour with MongoDB: collections, the four operations, object-shaped queries, and the `_id` contract. Junior read: insert, find, update, delete — same arc as 2.1, document spelling. Expert read: where object-queries move injection (not remove it), and what `_id` guarantees across a cluster.

## 1) Collections, documents, and four operations

### 1) **Definition** (the document first hour)

`db.orders.insertOne(doc)` adds a nested record; `find(filter)` matches by structured query; `updateOne(filter, { $set })` patches fields; `deleteOne(filter)` removes. Collections (loose record groups — no declared schema) hold documents (JSON-like values — nested freely). Four operations mirroring [2.1](<./2.1. First Postgres queries.md>)'s arc, document spelling throughout.

### What problem it solves (history)

Shape-shifting records (product catalogs with per-category attributes, event logs with evolving payloads, user profiles with optional everything) fought relational schemas per change (migrations per field, nullable sprawl, EAV contortions). Documents absorb shape variance without migration: new fields appear per record, queries address nested paths directly, the schema lives in application discipline (flexible — and burdened — elsewhere).

### Modern guidance

Use the operation matching intent (`insertOne` vs `insertMany` — singular/plural honesty; `updateOne` vs `updateMany` vs `replaceOne` — patch vs wholesale, named deliberately); filter every mutating op (unfiltered `deleteMany({})` empties collections — the all-caps twin of SQL's missing `WHERE`, same office "oops"); read result witnesses (`acknowledged`, `matchedCount`/`modifiedCount`/`deletedCount` — [2.1](<./2.1. First Postgres queries.md>) part 3's habit, document spelling).

### Runnable example (good — the document CRUD arc)

```javascript
// MongoDB shell / mongosh spelling (MongoDB 8.3 manual — server round-trip
// documented-not-executed on this floor: no mongod runs here per 1.2's scope
// note — kernel 6.19 vs SERVER-121912 + registry EOF. API spelling per manual.)
db.orders.insertOne({ customer: { name: "ann" }, items: [{ sku: "a1", qty: 2 }], total: 19.98, status: "new" });
// { acknowledged: true, insertedId: ObjectId("...") }
db.orders.find({ status: "new" }).toArray();
// [{ _id, customer: { name: "ann" }, items: [...], total: 19.98, status: "new" }]
db.orders.updateOne({ _id: id }, { $set: { status: "shipped" } });
// { acknowledged: true, matchedCount: 1, modifiedCount: 1 }
db.orders.deleteOne({ status: "shipped" });
// { acknowledged: true, deletedCount: 1 }
```

```javascript
// bad: unfiltered mass mutation (the "oops", document edition)
db.orders.deleteMany({});
// { acknowledged: true, deletedCount: 41207 } — acknowledged AND catastrophic.
// Fix: filter always (deleteMany({ status: "test", obsolete: true }) — intent in the filter),
// plus a read-back count before destructive ops (find(filter).count() first — witness, then act).
```

Why unread hurts identically here: `matchedCount: 0` "succeeds" (stale `_id`, wrong filter — green logs, untouched data); `modifiedCount` < `matchedCount` whispers schema drift (filter matched, `$set` changed nothing — already-that-value or path typo). Witnesses per operation, both stores — one habit, two spellings.

### Common confusion

- **"collections need declaring"** — collections materialize on first write (no `CREATE` — implicit creation is the feature *and* the typo-hazard: `db.odrers.insertOne` silently births `odrers`). Typos become collections, not errors — list collections after writes (`show collections` / `db.getCollectionNames()`) until the habit forms, and prefer explicit `db.createCollection` where the driver supports declaring intent.
- **"`find()` returns an array"** — `find()` returns a *cursor* (lazy, batched — `.toArray()` materializes, `.limit()` bounds, iteration streams). Unbounded `.toArray()` on million-record matches OOMs the client exactly like unfiltered `SELECT *` floods it — cursor discipline (limit/project/iterate) is the document twin of column discipline.

### Performance note

First-hour performance is shape-shaped (embed vs reference decisions dominate later query cost — nesting reads in one fetch, referencing joins in application code; Domain 03 owns the mechanics). One habit with immediate payoff: filtered mutations (unfiltered writes lock/scan broadly — same contention shape as SQL's missing `WHERE`, same office acoustics).

### Mentor note

Teach 2.1 and 2.2 as one arc in two spellings (same four operations, same witness habit, same unfiltered-"oops" — different syntax): mentees completing both stop asking "which store is easier" (comparable first hours) and start asking "which questions does each answer cheaply" (the shape question from [3.1](<../3. Choosing/3.1. Choosing Postgres or MongoDB.md>) — the upgrade from syntax to judgment in one pairing).

## 2) Queries are objects, not strings

### 2) **Definition** (structured query shape)

`{ status: "shipped", total: { $gt: 100 } }` — field paths mapped to match expressions (`$gt`, `$in`, `$regex`, `$and` combinators), parsed as *data* by the driver (BSON-encoded, never concatenated into a statement string). No statement text exists to break out of: the injection surface moves from *syntax breakout* (SQL's class) to *operator injection* (untrusted keys/operator objects reaching the query — distinct shape, same vigilance).

### What problem it solves (history)

String-query injection (SQL concatenation — [2.1](<./2.1. First Postgres queries.md>) part 2's `42601`) has no document equivalent *for values* (BSON carries types — a string stays a string through any nesting). But naive query-building (`find(req.query)` — client-controlled *keys* like `{"$gt": ""}` smuggled as values) reopens a sibling class: operators arriving where values were expected (auth bypass via `{ password: { $ne: null } }` — the canonical NoSQL-injection shape, real incidents, real CVEs).

### Modern guidance

Values from anywhere (BSON-typed — safe by construction); *keys and operators from code only* (never spread request objects into filters — pick listed fields explicitly: `{ status: req.query.status }` with an allowlist, never `find(req.query)`); validate operator-bearing inputs (sort/filter DSLs parsed against grammars — validated structure, not passed-through objects).

### Runnable example (good — values safe, keys guarded)

```javascript
// good: values flow, operators stay in code (documented spelling, 8.3 manual)
db.users.find({ username: "ann" });                    // value — BSON-typed, inert
db.orders.find({ total: { $gt: 100 } });               // operator — authored, static
db.users.find({ username: req.query.u });              // STILL SAFE for values (typed string)

// bad: request-shaped queries (operator injection — the sibling class)
db.users.find({ username: req.body.username, password: req.body.password });
// attacker posts { "username": "ann", "password": { "$ne": null } }
// → filter becomes { username: "ann", password: { $ne: null } } → matches without the password.
// Fix: compare hashes in code (never query on secrets), allowlist fields explicitly.
```

Why it hurts: authentication bypass without a single quote (quote-filters and WAFs watching for SQL syntax see nothing — the payload is valid JSON with honest intent). Fix at the architecture (secret comparison outside queries — fetch by username, compare hash in code), not the syntax (no escaping exists for structure — only allowlisting).

### Common confusion

- **"BSON means injection-proof"** — BSON immunizes *values* (typed, unparseable-as-code); operator *structure* stays attacker-reachable wherever requests shape filters. "No SQL → no injection" is the dangerous half-truth (half the mechanism gone, half remaining — guard the remaining half with allowlists, not confidence).
- **"Mongoose validates, so we're safe"** — schema validation types *values* (helpful, insufficient — `{ $ne: null }` can typecheck as "any" where schemas are loose, and validation runs before operator-position analysis it doesn't perform). Validate shapes *and* fix query construction (allowlisted fields, code-side secret comparison — defense in the query builder, not just the schema).

### Performance note

Object queries serialize to BSON once per operation (microseconds — structure cost trivial); operator-rich filters plan like SQL predicates (index use per field — `{ status: 1 }` index serves equality, range operators scan without compound support — Domain 03/06 own index mechanics). Query *shape* decides indexability (equality-first, sorts-last — same selectivity logic as `WHERE` ordering, different syntax).

### Mentor note

Demo operator injection against a scratch collection (post `{ $ne: null }` as password, watch it match — jaws drop faster than any SQL lecture achieves): the sibling class lands hardest on engineers who believed BSON ended the story. Follow immediately with the fix (fetch-then-compare + allowlist) — scare then suture, in one session.

## 3) The `_id` contract

### 3) **Definition** (automatic unique identity)

Every document carries `_id` (ObjectId by default — 12 bytes: timestamp + random + counter — globally unique without coordination, roughly time-ordered); missing `_id` on insert auto-generates (never null, never duplicated — the store refuses identity-less records); custom `_id` allowed (natural keys, UUIDs — uniqueness still enforced). Identity without sequences, without round trips, without single points of generation.

### What problem it solves (history)

Distributed identity (multi-writer inserts needing unique keys without a central sequence — the bottleneck single-row counters and UUID-generation debates) resolved structurally: ObjectId mints uniqueness locally (timestamp + randomness + counter — collision-impossible in practice, coordination-free always). No sequence table, no lock, no network — identity as a local computation with global guarantees.

### Modern guidance

Accept default ObjectIds unless a natural key dominates access (URLs keyed by slug, idempotency keys — `_id` as the dedup mechanism: duplicate insert fails loudly, exactly once enforced); reference by `_id` across collections (manual refs — store the ObjectId, `$lookup`/application-join at read — reference mechanics owned by Domain 03); never mutate `_id` (immutable — rewrites are delete+insert with new identity, history forked deliberately or never).

### Runnable example (good — identity minted locally, verified live via driver)

```bash
node -e "
const { ObjectId } = require('mongodb');
const a = new ObjectId(), b = new ObjectId();
console.log('hex24:', /^[0-9a-f]{24}$/.test(a.toHexString()), '| unique:', !a.equals(b), '| has-time:', a.getTimestamp() instanceof Date);"
# hex24: true | unique: true | has-time: true
```

Verified (mongodb driver, no server needed — generation is local computation): 24-hex shape, pairwise unique, timestamp embedded (rough ordering free — creation time readable from the id itself). Server round-trips above are documented from the 8.3 manual (labeled per snippet); identity mechanics execute anywhere — proven on this floor with zero infrastructure.

### Common confusion

- **"`_id` is a string"** — `_id` is ObjectId-typed (12 bytes, BSON type — queries with the *string* form miss: `{ _id: "68..." }` ≠ `{ _id: ObjectId("68...") }` — the most common "phantom missing document" in MongoDB work). Cast at boundaries (driver `ObjectId()` on input ids — validated, never trusted raw), store typed, compare typed.
- **"auto-ids are random, order is lost"** — timestamp-first bytes make ObjectIds *roughly* time-ordered (creation-sortable for practical purposes — recent-first pagination by `_id` works); randomness guards uniqueness, timestamp orders. Not a clock replacement (counter/random low bits — same-second collisions ordered arbitrarily), but free recency ranking no sequence provides.

### Performance note

ObjectId generation costs nanoseconds locally (no I/O — vs sequence round trips per insert: network + lock + contention at scale). Index cost identical to any unique key (B-tree per `_id` — mandatory, maintained per write). Monotonic-ish inserts cluster (recent writes co-locate — hot-page friendly, unlike UUIDv4 scatter): identity choice shapes write locality — ObjectId wins hot paths, UUIDs win merge-everywhere topologies.

### Mentor note

The string-vs-ObjectId phantom ("document exists but find misses") is the ideal first MongoDB debugging exercise (reproduce: insert, query with string form, miss; cast, hit — five minutes): type-strict identity learned through one phantom beats documentation chapters. Add "cast boundary ids" to the review checklist permanently ([4.1](<../4. Important points to remember/4.1. Data checklist habits mentors insist on.md>) carries it).
