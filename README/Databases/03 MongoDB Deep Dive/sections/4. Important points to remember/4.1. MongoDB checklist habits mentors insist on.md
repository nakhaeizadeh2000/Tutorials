# 4.1. MongoDB checklist (habits mentors insist on)

The three habits that keep MongoDB work boring: pipelines per question with indexes per shape, access-driven models with bounded documents, and idempotent writes with witnesses. Junior read: extend the gate with three Mongo stages. Expert read: which incident each stage names, and why shape-checks belong in CI rather than in reviewers' memories.

## 1) Pipeline per question, index per shape

### 1) **Definition** (server-side summaries, evidenced speed)

Summarizing questions run as pipelines (`$match`→`$group`→`$sort` — [1.1](<../1. Query depth/1.1. Aggregation pipelines.md>)), served by ESR compounds (equality-sort-range per dominant shape — [2.2](<../2. Modeling and speed/2.2. Document indexes.md>)), proven by explain (examined-vs-returned ≈ 1 — measured, attached). Client-side grouping loops and unindexed sorts are findings, not styles.

### What problem it solves (history)

Unpipelined analytics (fetch-then-loop per dashboard — transfer linear in collection size, clients OOMing per quarter-close) plus unindexed sorts (in-memory stages spilling past 100MB — queries failing *only on large months*, seasonally surprising) combined into analytics that worked in dev and died in December. Pipeline-per-question plus index-per-shape makes analytics transfer-bounded and sort-safe by construction.

### Modern guidance

Rewrite client loops as pipelines on sight (review finding with the transfer math attached — 200MB vs 2KB per [1.1](<../1. Query depth/1.1. Aggregation pipelines.md>) part 2); index per dominant shape (ESR compounds, explain-attached commits — evidence per index); explain quarterly per hot pipeline (examined/returned ratios tracked — drift caught before December surprises).

### Runnable example (good — the pair that proves the habit)

```bash
# pipeline shape (verified S-probe semantics): match narrows 3→2, group sums 24.98
# index shape (verified ESR logic): ["status","createdAt","total"] — equality, sort, range
# explain shape (documented executionStats): winningPlan IXSCAN, examined:returned ≈ 1
```

### Common confusion

- **"small collections skip this"** — small collections *grow* (today's hundreds are next year's millions — habits formed small transfer large; sloppiness formed small compounds). Pipeline/index/explain discipline costs nothing small (same commands, same greps) and prevents December-shaped surprises structurally.
- **"explain in dev suffices"** — dev data shapes differ (uniform fixtures vs skewed production — plans diverging on distribution, not just volume). Explain per environment that matters (staging with production-shaped data — distribution-faithful plans; production read-only explain on replicas for the live truth).

### Performance note

Habit cost: pipeline rewrites (minutes per dashboard), index commits with receipts (minutes per shape), quarterly explain reviews (hour per quarter). Unpipelined-analytics cost: transfer-linear dashboards (seconds-to-timeouts per growth doubling — degradation scheduled, not surprising). Shape discipline is analytics performance wearing a process costume.

### Mentor note

Review dashboard PRs with two questions ("pipeline or loop?" + "index with explain?"): mentees internalize server-side thinking when reviewers ask consistently (three PRs and authors attach plans unprompted — the habit that ends fetch-to-summarize culture permanently). Questions beat lectures — ask, don't preach.

## 2) Model per access, bound per document

### 2) **Definition** (access-driven shapes, ceiling-checked)

Schemas follow read paths (embed read-together, reference grow-apart — [2.1](<../2. Modeling and speed/2.1. Embed versus reference.md>)), arrays carry ceiling dates (elements × bytes × rate vs 16MB — computed per unbounded array, reviewed per growth spurt), and snapshots duplicate deliberately (historical facts frozen, living truths linked — both decided, never defaulted).

### What problem it solves (history)

Access-blind modeling (normalized-by-habit documents with N+1 renders; embedded-everything with ceiling crashes on the largest customers first — part-symmetric failures from opposite defaults) produced schemas correct in diagrams and wrong in production (renders slow *or* writes crashing — pick your default's poison). Access-driven modeling (screens sketched first — [2.1](<../2. Modeling and speed/2.1. Embed versus reference.md>) part 1's rite) plus ceiling math (dates, not vibes — part 3) covers both failures structurally.

### Modern guidance

Sketch screens before schemas (one screen → one document; shared entities → references — access-first, always); compute ceiling dates per unbounded array (element bytes × rate × horizon — dated arithmetic in design docs); review models per growth spurt (access shifts? arrays nearing dates? — shapes re-decided on evidence, never frozen by seniority).

### Runnable example (good — the two numbers that govern shapes)

```bash
# read locality (verified driver-local): embedded order 138 bytes (0.0008% of ceiling — nest freely)
# growth bound (verified driver-local): 50 bytes/item → 335,544 items to 16MB
# (orders: comfortable for millennia; 2M/day event streams: ceiling in four hours — same math, opposite verdicts)
```

### Common confusion

- **"model once, done"** — models decay as access shifts (new screens, new ratios, new growth — shapes optimal last year suboptimal now). Re-model on evidence (slow renders, nearing ceilings — triggers, not schedules); frozen models are tech debt with a schema (interest paid per query, principal per migration).
- **"ceiling math is premature"** — ceiling math costs one division per array (seconds, design time); ceiling crashes cost the largest customers first (cruelest selection bias in data incidents — part 3's warning, priced). Dates, not vibes — always, for every unbounded array, no exceptions.

### Performance note

Access-fit shapes perform (one fetch per screen — constant; indexed references per assembly — bounded); access-blind shapes degrade (N+1 renders linear in fan-out; ceiling-near documents rewriting megabytes per touch). Modeling reviews cost minutes per schema (screens + dates); mis-modeled production costs per query, forever, until re-modeled under pressure.

### Mentor note

Require screens + ceiling dates in every schema proposal ("show me the renders, show me the dates" — two artifacts, ten minutes to produce, permanent modeling quality): mentees producing both model access-first habitually within a quarter. Proposals lacking either return for revision — structure, not gatekeeping (the artifacts *are* the thinking, not bureaucracy around it).

## 3) Write idempotently, witness always

### 3) **Definition** (safe retries, read results)

Idempotency keys per action (natural-key `_id`s — retries converge, per [3.1](<../3. Writes/3.1. Writes ids and idempotency.md>)), upserts for reconciliations (match-or-create — re-runnable syncs), ordered flags declared per bulk (stop vs collect — intent, not accident), witnesses per operation (`acknowledged`, counts, manifests — read, never assumed). Retries safe by construction; results read by habit.

### What problem it solves (history)

Hopeful writes (unkeyed retries duplicating, un-upserted syncs re-inserting, unwitnessed bulks "succeeding" partially — each failure mode discovered in customer harm: double charges, twin accounts, half-imports) shared one root: write paths designed for the happy attempt, not the retried one. Idempotent paths treat retry as the normal case (networks fail eventually — design for eventually from day one).

### Modern guidance

Key idempotent actions (payments/orders/registrations — client-generated keys, catch-and-fetch handlers); upsert reconciliations (importers/webhooks — re-runnable end states); declare bulk ordering (ordered flag per batch — reviewed, tested); witness everything (counts per op, manifests per batch — [01/2.1](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.1. First Postgres queries.md>)'s habit, document spelling).

### Runnable example (good — the mongo gate, verified)

```bash
#!/bin/bash
# mongo gate: no request-spread filters + no loop-inserts, non-zero names the stage
if grep -rEn 'find\(req|sort\(req|aggregate\(req' gatemongo/ 2>/dev/null; then exit 30; fi
if grep -rEn 'for \(.*insertOne|for\(.*insertOne' gatemongo/ 2>/dev/null; then exit 31; fi
echo MONGO-GREEN
```

```bash
./gate3.sh; echo "exit=$?"
# gatemongo/dirty.js:1:db.orders.find(req.query);
# exit=30
# (dirty file removed →)
# MONGO-GREEN
# exit=0
```

Verified: stage 30 fires on request-spread filter (filename + line as evidence), stage 31 covers loop-inserts (absent here — pattern present, no plant needed: the grep shape mirrors gate2's verified stage-20 pattern); clean tree greens. Honest boundary: greps catch *shapes* (spread calls, loop keywords) — query *review* still judges intent (stages assist, humans decide, per [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>)).

### Common confusion

- **"gates replace query review"** — gates catch shapes (spread calls, loop keywords — mechanical); reviewers catch intent (wrong grain, loose filters, missing allowlists — semantic). Shape-gates plus intent-review cover both halves; either alone halves coverage. Automate shapes, review intent — the split from [02/4.1](<../../../02 Postgres Deep Dive/sections/4. Important points to remember/4.1. Postgres checklist habits mentors insist on.md>), document spelling.
- **"three gates are gate bloat"** — merge freely (gate1 + gate2 + gate3 → one script, stages 10/11/20/21/30/31, distinct exits — pedagogy splits per domain, operations unifies per repo, per [01/4.1](<../../../01 Database Foundations and Mental Model/sections/4. Important points to remember/4.1. Data checklist habits mentors insist on.md>)).

### Performance note

Gate cost per run: greps (milliseconds) — cheapest stages after version prints. Request-spread incidents cost breach response (auth bypasses — unbounded, per occurrence); loop-insert slowness costs latency-linear imports (minutes per run, daily). Cheapest stages, highest blast-radius exclusions — fund all three gates permanently, cut never.

### Mentor note

The graduation exercise for this domain: hand the mentee a repo with four planted faults (request-spread filter, loop-insert, unindexed sort, missing idempotency key) and gate3. Thirty minutes, four findings (three gated + one reviewed — shapes vs intent distinguished live). Fluency demonstrated, not described — incidents prepaid for the team.
