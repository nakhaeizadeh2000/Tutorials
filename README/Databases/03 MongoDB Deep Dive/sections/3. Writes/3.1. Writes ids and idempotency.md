# 3.1. Writes, ids, and idempotency

Writing exactly once under at-least-once attempts: natural-key `_id`s refusing duplicates, upserts completing match-or-create, and ordered bulk writes witnessed per batch. Junior read: retry safely by keying writes. Expert read: where idempotency lives (keys, not hopes), and what ordered-vs-unordered chooses per batch.

## 1) `_id` as the dedup mechanism

### 1) **Definition** (identity-keyed exactly-once)

Natural-key `_id` (idempotency keys, slugs, deterministic hashes — identity *meaningful* to the operation): first insert stores; duplicate insert fails loudly (duplicate-key error — the refusal *is* the mechanism); retry handler catches refusal and fetches the original (same effect, repeated attempts — exactly-once effect from at-least-once delivery). Keys carry idempotency; code carries the catch-and-fetch.

### What problem it solves (history)

Retry-duplicated writes (network timeouts retried blindly — client uncertain, server re-executing: double charges, duplicate orders, twin accounts — each retry a gamble settled in customer harm) plagued every at-least-once transport (which is every network, eventually). Identity keys convert gambles to lookups (retry repeats the key — store answers "already have it" with the original — uncertainty resolved structurally, not hopefully).

### Modern guidance

Key idempotent operations (payments, orders, registrations — client-generated keys per attempt: UUID per user action, never per retry); catch duplicates explicitly (11000 → fetch-by-key → return original — the retry path, tested, not hoped); never key by hope (timestamps, randoms per retry — distinct keys per attempt defeat dedup by construction: same action, different identities, duplicates stored "correctly").

### Runnable example (good — retry simulation, verified locally)

```bash
node -e "
// idempotency-key retry simulation: duplicate key refuses, fetch returns original
const store = new Map();
const insertPayment = (key, amount) => {
  if (store.has(key)) return { outcome: 'duplicate-refused', payment: store.get(key) };
  const doc = { key, amount, status: 'charged' };
  store.set(key, doc);
  return { outcome: 'stored', payment: doc };
};
console.log(JSON.stringify(insertPayment('pay-42', 19.98)));
console.log(JSON.stringify(insertPayment('pay-42', 19.98)));"
// {"outcome":"stored","payment":{"key":"pay-42","amount":19.98,"status":"charged"}}
// {"outcome":"duplicate-refused","payment":{"key":"pay-42","amount":19.98,"status":"charged"}}
```

Verified (local Map standing in for the unique index — refusal semantics identical: second identical key returns the original, never a twin): stored once, refused once, original returned. Server spelling (`_id` or unique-indexed `idempotencyKey` + 11000-catch — [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) part 2, documented from the 8.3 manual) enforces the same refusal atomically under concurrency — simulation teaches the shape, the index enforces it.

### Common confusion

- **"retries are safe with transactions"** — transactions make attempts *atomic* (all-or-nothing per try — Domain 05 owns the models); idempotency keys make *retries* safe (repeated tries converge — keys, not transactions, deduplicate). Atomic retry without keys retries cleanly into duplicates (each attempt a fresh identity — perfectly atomic twins). Both mechanisms, different jobs — transact the unit, key the attempt.
- **"UUIDs solve duplicates"** — random UUIDs *per retry* defeat dedup (distinct identities per attempt — duplicates stored "uniquely," correctly, harmfully); deterministic keys *per action* enable it (same action → same key → refusal). Randomness placement decides (per action: dedup; per retry: duplicates) — key by action, never by attempt.

### Performance note

Dedup cost per write: unique-probe (microseconds — [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) part 2's probe, gladly paid) + key generation client-side (nanoseconds). Duplicate-incident cost: double-charges (refunds + trust + regulatory attention — unbounded per occurrence). Keys cost nothing measurable; twins cost businesses — key every idempotent operation, no exceptions.

### Mentor note

The double-submit demo (post twice, one key — second refused, original returned — five minutes, from [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) part 2's exercise): mentees watching exactly-once emerge from refusal design retry-safe systems thereafter (keys per action, catch-and-fetch per handler — reflex, not policy). Demo per cohort; retry safety follows refusal-witnessing, never precedes it.

## 2) Upserts complete the idempotent write

### 2) **Definition** (match-or-create atomically)

`updateOne(filter, { $set }, { upsert: true })`: matching document updates in place; absent match inserts (filter + update merged — created with both); race-free by construction (match-and-create atomic at write time — concurrent upserts converge on one document, never twins). The idempotent write completed: retries re-match (updating idempotently) instead of re-inserting (duplicating).

### What problem it solves (history)

Find-then-insert races (check existence → absent → insert — concurrent twins racing the check: both see absent, both insert, duplicates stored — the TOCTOU hole unique indexes also close, differently) plus sync-job re-runs (nightly imports re-inserting history — duplicates per run, dedup scripts per morning). Upserts collapse check+write into one atomic operation (match-or-create — no window, no race, re-runnable freely).

### Modern guidance

Upsert syncs and reconciliations (importers, webhooks, reconcilers — re-runnable by design: run N times, same end state); `$set` idempotent fields (statuses, timestamps, counters via `$inc` — re-application converges: same values rewritten, counters incremented *once per logical event* only with dedup keys — counters need keys, sets don't); filter on the identity (upsert filter = the dedup key — `_id` or unique field — match precision decides correctness: loose filters merge distinct entities, tight filters miss matches).

### Runnable example (good — upsert shape, verified locally)

```bash
node -e "
// upsert shape: match-or-create in one operation (documented server spelling below)
const upsert = (filter, update) => ({ updateOne: [filter, { \$set: update }, { upsert: true }] });
console.log('upsert-shape:', JSON.stringify(upsert({ idempotencyKey: 'pay-42' }, { status: 'charged' })));"
// upsert-shape: {"updateOne":[{"idempotencyKey":"pay-42"},{"$set":{"status":"charged"}},{"upsert":true}]}
```

```javascript
// server spelling (MongoDB 8.3 manual — documented-not-executed on this floor):
db.payments.updateOne({ idempotencyKey: "pay-42" }, { $set: { status: "charged" } }, { upsert: true });
// first run: inserts (filter + $set merged — created with both halves)
// retry: matches (updates status idempotently — same end state, no twin)
```

Verified shape locally (filter/update/options positions — the call contract as data); server semantics documented (match-or-create atomicity per manual). Re-runs converge (same filter → same document — sync jobs re-runnable without dedup scripts; webhook retries harmless by construction).

### Common confusion

- **"upsert replaces unique indexes"** — upserts need *match precision* (filter hitting exactly the intended document — loose filters merging strangers is corruption with a mechanism); unique indexes *enforce* precision (duplicates refused even when filters err — backstop independent of query quality). Upsert for convenience (one operation), unique for guarantee (structural refusal) — both, layered (upsert *on* unique-keyed filters — belt, suspenders, and tailoring).
- **"`$setOnInsert` vs `$set` confusion"** — `$set` applies always (match updates *and* inserts — re-application rewrites: idempotent for same values, divergent for timestamps); `$setOnInsert` applies on insert only (creation metadata — createdAt set once, never rewritten by retries). Retry-varying fields (`updatedAt: now()`) belong in `$set` deliberately (freshness per attempt — intended divergence); creation facts belong in `$setOnInsert` (stability across retries — intended convergence).

### Performance note

Upsert cost: match probe + write (identical to update-then-fallback-insert, minus the round trip — one operation vs two); race-window elimination free (atomicity structural — no lock management, no retry loops). Sync-job economics transform (re-runnable imports: run nightly without dedup passes — operational toil deleted structurally, not automated away).

### Mentor note

Teach upserts as "find-or-create without the race" (the shape every sync job wants, most hand-roll badly): mentees reaching for upsert-first on reconciliation tasks skip an entire generation of TOCTOU bugs (check-then-act instincts retired per codebase). Review sync code for hand-rolled match-then-insert (each instance an upsert candidate — convert with filter-precision review).

## 3) Ordered bulk for all-or-most

### 3) **Definition** (batch intent declared)

Bulk writes declare ordering: `ordered: true` (default — stop at first error, preceding ops applied: all-or-nothing-*so-far*, sequential semantics); `ordered: false` (unordered — continue past errors, per-operation results collected: most-or-all with a failure manifest). Witnesses per batch (`insertedCount`, `matchedCount`, `modifiedCount`, `deletedCount`, plus per-error details — bulk results read like single-op witnesses, aggregated).

### What problem it solves (history)

Loop-inserted batches (per-document round trips — latency linear in batch size, partial failures mid-loop with client-side bookkeeping reinventing bulk semantics badly) scaled as round trips (thousands of documents × network latency — minutes per import) and failed opaquely (which succeeded? — client-tracked, drift-prone). Bulk operations move batching server-side (one round trip — latency constant-ish; server-tracked witnesses — authoritative per operation).

### Modern guidance

Ordered for dependent sequences (migrations with FK-ish ordering, event replays preserving causality — stop-on-error preserves sequence invariants); unordered for independent bulk (imports, backfills — maximize throughput, collect the failure manifest, retry failures selectively); witness every batch (counts asserted per batch — inserted N expected? — manifests reviewed, failures retried by key, never blindly).

### Runnable example (good — both orderings, contrasted)

```javascript
// ordered (default): stops at first error — preceding applied (documented spelling, 8.3 manual):
db.orders.insertMany([{ _id: 1 }, { _id: 1 }, { _id: 2 }], { ordered: true });
// → first stored, second errors (duplicate), third NEVER ATTEMPTED (sequence halted — all-or-nothing-so-far)

// unordered: collects results past errors:
db.orders.insertMany([{ _id: 1 }, { _id: 1 }, { _id: 2 }], { ordered: false });
// → first + third stored, second errors (manifest lists it — most-or-all with named failures)
```

```javascript
// bad: client-side loop pretending at bulk (latency + witness debt)
for (const doc of docs) await db.orders.insertOne(doc);
// N round trips (latency linear), client-tracked witnesses (drift-prone), first error aborts
//   the loop (unplanned ordered-semantics — accidental, not designed). Bulk deliberately.
```

Why loop-inserts hurt: latency (N trips — imports taking minutes server-side-takes-seconds), witness drift (client counts vs server truth diverging on partial failure — unreconciled), accidental ordering (abort-on-throw mimicking ordered:true without declaring it — semantics by accident). Bulk declares intent (ordered flag — reviewed, tested); loops hope (whatever the loop does under failure — unexamined until examined in production).

### Common confusion

- **"unordered means unreliable"** — unordered means *per-operation reporting* (each op witnessed individually — failures named per document, successes counted exactly): reliability *improves* (partial outcomes visible precisely — retry the manifest, not the batch). Ordered aborts hide later outcomes (unattempted ≠ failed — unknown status per remaining doc). Visibility per operation beats blanket abort for independent bulk.
- **"bulk bypasses validation"** — bulk validates identically (schema/constraints per document — same rules, batched transport): batching changes *delivery* (one round trip), never *correctness* (per-document rules enforced). Validation errors arrive per document in the manifest (named, routable — retry-after-fix per failure, not per batch).

### Performance note

Bulk economics: one round trip vs N (latency collapsed — imports minutes→seconds, the dominant win); server-side batching vs client loops (throughput multiplied — connection-slot efficiency per batch). Ordered bulk serializes server-side (sequence preserved — throughput secondary to order); unordered parallelizes internally (throughput maximal — order unguaranteed). Intent declares performance profile — choose per batch, witness per result.

### Mentor note

Ban loop-inserts in review ("bulk or justify" — per-document awaits in import paths flagged mechanically): mentees converting loops to bulks learn batch thinking permanently (round trips as budget — spent deliberately, never per-iteration). The ordered-flag question ("stop or collect on error?") teaches intent-declaration alongside — two habits per review comment.
