# 1.2. Query operators and projections

Expressing intent in document queries: comparison/membership/pattern operators, projections narrowing transfers, and operator-bearing input kept in code where it belongs. Junior read: `$gt` compares, projections trim, requests never shape filters. Expert read: where BSON-typed values end and operator-structure risk begins, and why projection discipline compounds with indexes.

## 1) Operators express intent

### 1) **Definition** (structured match vocabulary)

Operators name comparisons (`$gt/$gte/$lt/$lte` — ranges; `$eq` implicit in plain values), membership (`$in`/`$nin` — sets), patterns (`$regex` — text shapes), logic (`$and`/`$or`/`$nor`/`$not` — combinations), and existence (`$exists` — presence vs value). `{ total: { $gt: 100 } }` reads as intent (totals above one hundred — reviewable); driver BSON-encodes it typed (numbers stay numbers — no parsing, no breakout surface for values).

### What problem it solves (history)

String-built document queries (JSON stringified with concatenated values — early drivers accepting strings, tutorials demonstrating interpolation) recreated SQL injection in document spelling (quotes breaking out, operators smuggled as text). Object-shaped queries with BSON typing closed the value half permanently: structure parsed as data, values typed as values — syntax breakout structurally impossible, per [01/2.2](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.2. First MongoDB operations.md>) part 2.

### Modern guidance

Plain values for equality (`{ status: "new" }` — simplest shape, BSON-typed); operators for the rest (`$gt` ranges, `$in` sets, `$regex` patterns — intent-named, reviewable); combinators for composition (`$and`/`$or` explicit — nested logic visible, never string-glued). Every operator in a query traceable to a code literal (grep-able intent — dynamic operator *names* from input are the finding part 3 gates).

### Runnable example (good — BSON round-trip, verified driver-local)

```bash
node -e "
const { BSON } = require('mongodb');
const filter = { status: 'new', total: { \$gt: 100 } };
const rt = BSON.deserialize(BSON.serialize(filter));
console.log('bson-roundtrip:', JSON.stringify(rt));"
# bson-roundtrip: {"status":"new","total":{"$gt":100}}
```

Verified (mongodb driver, no server — serialization is local computation): operator structure survives BSON round-trip typed (`$gt` operator intact, `100` numeric — structure and types preserved exactly). Server execution of this filter shape is documented from the 8.3 manual (labeled): matched documents returned, transfer bounded by matches.

### Common confusion

- **"`$where` for complex logic"** — `$where` executes JavaScript per document server-side (full scans + JS sandbox overhead — slowest predicate class, injection-adjacent surface for string-built functions). Expressible-with-operators logic belongs in operators (indexed, bounded, reviewable); `$where` reserved for genuinely inexpressible predicates (rare — justify per use, measure per query, remove on sight in reviews).
- **"operators need indexes to work"** — operators *function* without indexes (correctness independent — full scans answer truly); operators *perform* with indexes (compound ESR shapes — [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) owns the mechanics). Correctness first (operators express), speed second (indexes serve) — never conflate the two axes in review.

### Performance note

Operator cost follows selectivity (equality-first shapes use indexes directly; leading `$or`/`$regex` without anchors scan — shape decides plan, per [2.2](<../2. Modeling and speed/2.2. Document indexes.md>)). `$regex` anchored (`^prefix`) indexes; unanchored scans (full collection per query — the document twin of `LIKE '%x%'`). Operator choice *is* performance choice at scale — review operators with plans, not preferences.

### Mentor note

The operator-vocabulary drill (translate five English questions to filters aloud — "shipped orders over 100" → `{ status: "shipped", total: { $gt: 100 } }`): mentees translating fluently query intentionally; stumblers reveal SQL-thinking (WHERE-translation word-by-word — valid bridge, then native shapes). Five questions, thirty seconds each — fluency audible instantly.

## 2) Projections return only what's needed

### 2) **Definition** (transfer narrowing)

Projections select fields (`{ secret: 0 }` excluding, `{ name: 1, total: 1 }` including — never mixed except `_id`): matched documents trimmed before transfer (narrow payloads, fast wire, minimal exposure). Default returns everything (full documents — convenient, wasteful, leaky); production queries project deliberately (needed fields named — transfer budgeted per query).

### What problem it solves (history)

Full-document fetching (every query returning secrets, blobs, histories — payloads 10–100× needed bytes) taxed wire, memory, and exposure simultaneously (slow lists, OOMing aggregations, secret fields reaching clients that log them). Projections convert fetching from wholesale to retail (fields named per consumer — transfer proportional to need, exposure proportional to naming).

### Modern guidance

Exclude secrets always (`{ secret: 0, hash: 0 }` — exposure reduced structurally, not hopefully); include narrowly for lists (list views name 3–5 fields — payloads predictable, rendering fast); cover with indexes where hot (covered queries served from index alone — [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) owns the mechanics; projection+index composed deliberately).

### Runnable example (good — match then trim, verified locally)

```bash
node -e "
const docs = [
  { _id: 1, status: 'new', total: 150, secret: 'x' },
  { _id: 2, status: 'new', total: 50, secret: 'y' },
  { _id: 3, status: 'shipped', total: 200, secret: 'z' }
];
// filter { status: 'new', total: { \$gt: 100 } } + projection { secret: 0 } →"
// matched-projected: [{"_id":1,"status":"new","total":150}]
```

Verified (local filter+project mirroring server semantics): 3 docs in, 1 out, secret field absent from the survivor. Server spelling (`db.orders.find(filter, { secret: 0 })` — documented from the 8.3 manual) performs the same trim pre-transfer: wire carries the survivor only, never the scanned.

### Common confusion

- **"projection secures secrets"** — projection *reduces* exposure (unnamed fields absent from *this* response); allowlists + access control *secure* (unauthorized callers never reach the query — projection is narrowing, not authorization). Defense in depth (authz outside, projection inside — both, never either/or): projected secrets still leak to authorized-but-logging clients (audit what leaves, per [4.1](<../4. Important points to remember/4.1. MongoDB checklist habits mentors insist on.md>)).
- **"include and exclude mix freely"** — mixing (include `a` + exclude `b`) errors, except `_id` (excludable alongside includes — the single documented exception). The restriction prevents ambiguous shapes (projected documents unpredictable — drivers refuse rather than guess). Pick one direction per query (include-lists for narrow views, exclude-lists for secret-trimming).

### Performance note

Projection payoff scales with document width (narrow docs: marginal; blob-adjacent docs: 10–100× transfer reduction — measured per collection, applied per hot query). Covered-query composition (projection ⊆ index — served without document fetch) multiplies the win (index-only reads — the document twin of index-only scans, [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) owns the proof). Project deliberately on hot paths; default fully on cold ones.

### Mentor note

Audit one hot endpoint's payload together (log response bytes, list fields, strike unneeded — watch kilobytes become hundreds of bytes): mentees witnessing 10× transfer cuts project habitually thereafter. Payload audits quarterly (fields accrete per feature — trimming scheduled, not hoped) — transfer hygiene compounds like all hygiene.

## 3) Operator-bearing input stays in code

### 3) **Definition** (the structural allowlist rule)

Request data supplies *values* (typed strings/numbers — BSON-safe by construction); code supplies *operators and keys* (static literals — `$gt`, field names, sort directions — never from input). Spreading request objects into filters (`find(req.query)`) or sorts (`sort(req.query.sort)`) hands operator *structure* to clients — the sibling injection class from [01/2.2](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.2. First MongoDB operations.md>) part 2, gated here.

### What problem it solves (history)

Request-shaped queries (convenience APIs passing `req.query` straight to `find()` — filter DSLs without grammars, sort endpoints without allowlists) admitted operator payloads (`{ "$gt": "" }` as values, `password: { $ne: null }` as auth — verified shape in 01/2.2) that quote-filters and SQL-trained WAFs never see (valid JSON, honest intent-looking). Allowlisting (picked fields, validated structure) closes the structural hole SQL-era tooling cannot see.

### Modern guidance

Pick fields explicitly (`{ status: req.query.status }` — listed, typed, bounded); validate sort/filter DSLs against grammars (allowed keys + allowed directions enumerated — validated structure, never passed-through objects); compare secrets in code (fetch by username, hash-compare locally — secrets never inside queries, per 01/2.2's fix).

### Runnable example (good — picked vs spread, contrasted)

```javascript
// good: values flow, structure stays (allowlisted fields, code-owned operators)
const allowedSorts = { newest: { createdAt: -1 }, oldest: { createdAt: 1 } };
db.orders.find({ status: req.query.status }).sort(allowedSorts[req.query.sort] || allowedSorts.newest);

// bad: request shapes the query (operator injection — 01/2.2's verified sibling shape)
db.users.find({ username: req.body.username, password: req.body.password });
// posts { "username": "ann", "password": { "$ne": null } } → matches without the secret.
// Fix: fetch-then-compare (by username only) + allowlisted fields (structure in code, values from requests).
```

### Common confusion

- **"validation libraries prevent this"** — validators type *values* (Joi/Zod shapes — helpful, insufficient where schemas permit objects: `{ $ne: null }` validates as "object" where objects are allowed). Validation *plus* construction discipline (picked fields, code-owned operators — the query builder never spreads requests) covers both halves. Validate inputs, construct queries — two jobs, two mechanisms.
- **"GET query strings can't carry operators"** — query strings parse to *strings* (flat — `?status[$gt]=` shapes depend on parser nesting: `qs` extended syntax builds objects from brackets — parser-configured structure, attacker-influenced). Parser settings are security settings (simple parser where objects unneeded — depth limits where needed — reviewed like auth code, not utility config).

### Performance note

Allowlisting costs a lookup per request (microseconds — field pick + enum check); request-spread costs incident response (auth bypasses, data exfiltration — unbounded, per occurrence). Validation grammars cost design time once (enumerated keys/directions — documented, tested); unvalidated DSLs cost breach-shaped surprises forever. Structure cheap, incidents dear — allowlist always.

### Mentor note

The spread-hunt grep (`find(req`, `sort(req`, `aggregate(req` — hits triaged live per review): mentees watching one spread become an auth bypass stop spreading forever (scar tissue via grep, administered kindly). Add the patterns to the review checklist permanently ([4.1](<../4. Important points to remember/4.1. MongoDB checklist habits mentors insist on.md>) carries them) — checklist beats memory, again.
