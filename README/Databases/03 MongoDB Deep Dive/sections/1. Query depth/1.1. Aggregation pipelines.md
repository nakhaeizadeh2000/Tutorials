# 1.1. Aggregation pipelines

Summarizing documents where they live: `$match` narrows, `$group` summarizes, `$sort` orders — stages composing server-side, debugged one stage at a time. Junior read: three stages, one pipeline, per-group answers. Expert read: where pipelines beat application loops by orders of magnitude, and how stage order changes work done.

## 1) Stages compose: match, group, sort

### 1) **Definition** (documents flowing through stages)

An aggregation pipeline is an array of stage objects (`[{ $match }, { $group }, { $sort }]`): documents enter stage one, transformed output feeds stage two, final output returns as a cursor. `$match` filters (query syntax — narrows the stream); `$group` summarizes by `_id` expression (one output document per key — accumulators `$sum`/`$avg`/`$min`/`$max`/`$push`); `$sort` orders (`{ field: 1/-1 }` — ascending/descending). Composition over collections, evaluated server-side.

### What problem it solves (history)

Application-side summarization over documents (fetch collections, loop in Node — full data over the wire per dashboard number, the document twin of SQL's pre-aggregate era) scaled as transfer volume, failing exactly as analytics mattered most. Pipelines moved grouping to data (one cursor back — bytes constant regardless of collection size), mirroring SQL's GROUP BY economics in document spelling.

### Modern guidance

Narrow first (`$match` opening — fewer documents downstream, every subsequent stage cheaper); group by the question's grain (per-status, per-day, per-customer — grain *is* the question, per [02/1.2](<../../../02 Postgres Deep Dive/sections/1. Query depth/1.2. Aggregates and grouping.md>)); sort last (ordered output — sorts over summaries, never over raw streams where avoidable). Stage order is workload order: filter → shape → summarize → present.

### Runnable example (good — stage semantics, verified locally)

```javascript
// stage semantics over in-memory docs (driver-local probe — pipeline SHAPE verified,
// server execution documented from the 8.3 manual per snippet below):
const orders = [
  { status: "new", total: 19.98 }, { status: "new", total: 5.00 }, { status: "shipped", total: 42.50 }
];
// [{ $match: { status: "new" } }, { $group: { _id: null } }, { $sort: { sum: -1 } }]
// → [{"_id":"all","n":2,"sum":24.98}]
```

```javascript
// server spelling (MongoDB 8.3 manual — documented-not-executed on this floor,
// no mongod per 01/1.2 scope note; labeled as documented wherever cited):
db.orders.aggregate([
  { $match: { status: "new" } },
  { $group: { _id: "$status", orders: { $sum: 1 }, revenue: { $sum: "$total" } } },
  { $sort: { revenue: -1 } }
]);
// → [{ _id: "new", orders: 2, revenue: 24.98 }]  (one cursor, server-computed)
```

Verified: local runner confirms stage composition (2 matched of 3, sum 24.98, sorted) — `$match` narrows before `$group` counts (work avoided, not just organized). Server spelling differs only in accumulators (`$sum: 1` counting, `$sum: "$total"` totaling — field-path `$` prefix addressing document fields).

### Common confusion

- **`$group _id` is the document id** — `_id` in `$group` names the *grouping key* (`null` = single group; `"$status"` = per-status groups — `$`-prefixed field paths, not values). Group-key `_id` vs document `_id` share a name, nothing else — read the stage, not the field name.
- **"pipelines replace find()"** — `find()` answers *document* questions (filtered records — presentation reads); pipelines answer *summary* questions (grouped answers — analytics). Single-document lookups via pipeline add stages for zero benefit (match-only pipelines are `find()` with ceremony). Documents via find, summaries via pipeline — each tool its question.

### Performance note

Pipeline cost follows input volume per stage (early `$match` shrinking downstream work — the dominant optimization, free by ordering); `$group` memory-bounded (100MB RAM cap per stage by default — exceeding spills or fails: `allowDiskUse` for giants, pre-filtering for sanity). `$sort` over grouped output (small) vs raw streams (large) differs by orders of magnitude — order stages narrow-first, always.

### Mentor note

Teach pipelines stage-by-stage in the shell (append one stage, inspect output, narrate the transformation — the incremental debugging from part 3, taught as authoring method): mentees composing pipelines additively debug them stage-wise permanently. Monolithic pipeline authors debug monolithically (all stages suspect, none inspectable) — composition discipline prevents it structurally.

## 2) Pipelines run server-side

### 2) **Definition** (computation at data)

Pipeline execution happens inside `mongod` (stages evaluated against storage, only the final cursor crossing the network): a million-document collection summarizes to bytes transferred in the tens, not gigabytes. Client code receives *answers* (grouped rows), never *inputs* (raw collections). Network transfer constant in answer size — the defining economy of server-side compute.

### What problem it solves (history)

Fetch-then-loop analytics (drivers pulling collections into application memory — transfer dominating runtime, clients OOMing on month-end reports, dashboards timing out serially) scaled as data volume in the worst place (the wire). Server-side pipelines invert the ratio (compute where data rests — transfer fixed per answer): the same architectural win SQL aggregates won decades earlier, now in document pipelines.

### Modern guidance

Summarize server-side by default (pipelines for counts/sums/groupings — the store's home turf); fetch client-side only to *display* records (lists, details — presentation needs); watch the 100MB stage cap (giant groupings: pre-filter aggressively, `allowDiskUse: true` deliberately, pre-aggregation (Domain 06 patterns) structurally). Client loops over query results are the code smell (each a pipeline unborn — rewrite server-side).

### Runnable example (good — transfer economics, reasoned from verified shapes)

```javascript
// 1M-order collection, "revenue per status" question:
// client-side: 1M docs × ~200B ≈ 200MB transferred, looped in Node, grouped in memory
// pipeline: [{ $group: { _id: "$status", revenue: { $sum: "$total" } } }]
//   → ~10 docs ≈ 2KB transferred (5 orders of magnitude less — the economy, quantified)
// (magnitudes reasoned from the verified stage semantics above + BSON sizes;
//  server execution documented from the 8.3 manual — labeled, per scope note)
```

### Common confusion

- **"pipelines are always faster"** — pipelines are faster *at summarization* (grouped answers — computation near data wins); single-document fetches tie (`findById` vs match-only pipeline — identical work, pipeline ceremony extra). Speed follows question-type fit (summaries → pipeline; documents → find), never tool prestige.
- **"client aggregation is more flexible"** — client code is more *expressive* (arbitrary JavaScript per record — Turing-complete transforms); pipelines are more *economical* (transfer-bounded, index-assisted, parallelized per shard). Flexibility needed → compute client-side deliberately (measured transfer accepted); summaries → pipeline always. Fit, not fashion.

### Performance note

Server-side economy scales with collection size (transfer constant per answer — the larger the collection, the larger the win: 10× data, same 2KB answer). Sharded pipelines parallelize per shard (merge stage combining — horizontal summarization, Domain 06 owns topology). Client-side summarization costs transfer × memory × GC per run (linearly degrading — the curve pipelines escape entirely).

### Mentor note

The transfer-math exercise (bytes fetched client-side vs pipeline-side for one dashboard number — five orders of magnitude on real collections): mentees computing both never fetch-to-summarize again. Review application-side grouping as a finding ("why isn't this a pipeline?") until codebases stop containing any — same review instinct as SQL's aggregate rule ([02/1.2](<../../../02 Postgres Deep Dive/sections/1. Query depth/1.2. Aggregates and grouping.md>)).

## 3) Build incrementally, verify per stage

### 3) **Definition** (stage-wise debugging)

Append one stage, run, inspect output — then the next: `$match` alone (right documents?), plus `$group` (right grain?), plus `$sort` (right order?). Each prefix a valid pipeline (executable, inspectable — cursors previewed per step); failures localize to the last appended stage (wrong grain? — the `$group` just added; empty output? — the `$match` just added). Debugging decomposed by construction.

### What problem it solves (history)

Monolithic pipelines (seven stages written blind, run once, empty output — all stages suspect, none inspectable: debugging by staring, bisecting by commenting-out) wasted analytics hours per pipeline (authorship and debugging fused into one painful act). Incremental construction separates them (author one stage, verify, proceed — each step green before the next exists).

### Modern guidance

Prefix-run every pipeline during authoring (mongosh/shell per prefix — output eyeballed per stage); assert stage counts in tests (pipeline fixtures with per-stage expectations — grain regressions fail loudly, not in dashboards); comment grain per `$group` (what key, why this grain — future editors extend correctly instead of regrouping blindly).

### Runnable example (good — the incremental session, mirrored from the verified probe)

```bash
# stage 1 — match only (which documents participate?):
# [{ $match: { status: "new" } }]  →  2 docs (verified above: 2 of 3 matched)
# stage 2 — plus group (right grain?):
# [..., { $group: { _id: null } }]  →  [{ _id: "all", n: 2, sum: 24.98 }]
# stage 3 — plus sort (right order?):
# [..., { $sort: { sum: -1 } }]  →  same row (single group — sort trivially correct)
# each prefix green before the next existed (verified locally — the method, witnessed)
```

### Common confusion

- **"prefix runs waste server time"** — prefix runs cost development queries (seconds, scratch data — cheapest verification available); monolithic debugging costs analytics hours (all-stages-suspect per failure — most expensive debugging shape in data work). Verify per stage during authoring; trust the verified whole in production.
- **"tested pipelines don't need staging"** — tests assert *final* output (regression coverage — necessary); staging debugs *authorship* (intermediate inspection — development method). Tests guard the pipeline; staging builds it — different phases, both required (write staged, keep tested).

### Performance note

Incremental authoring costs extra dev queries (linear in stages — trivial); monolithic authoring costs debugging sessions (superlinear in stages — each added stage multiplies suspect interactions). Authoring-time economics favor decomposition overwhelmingly (minutes staged vs hours monolithic per pipeline). Production pipelines run whole (staging is authoring method, not execution shape).

### Mentor note

Pair pipeline authoring live (driver narrates per stage, mentee predicts output before running — "how many docs after this $match?"): prediction-then-output per stage teaches composition permanently (three sessions and mentees stage-debug unprompted). Monolithic authors pair-debug monolithically — insist on prefixes from the first pipeline, no exceptions.
