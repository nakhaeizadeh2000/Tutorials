# 5.1. Common interview QA: MongoDB

Canonical answers for the three MongoDB questions every backend interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their numbers. Expert read: each answer runs evidence (verified probes, documented shapes, gate stages) before conclusions — prediction first, output as confirmation.

## 1) "Embed or reference?" — answer with access

### 1) **Definition** (the modeling screen)

"Customer with orders — nest or link?" — screens for access-driven modeling: hires ask the read path first (one screen → embed; shared entity → reference; unbounded growth → reference with ceiling math), cite the measured shapes (138-byte order at 0.0008% vs 335k-items-to-ceiling arithmetic — both verified driver-local), and name the axis (snapshot-duplicate historical facts; reference living truths).

### What problem it solves (hiring signal)

Document modeling is the highest-blast-radius MongoDB judgment (shapes persist for years — migrations under ceiling pressure are the dearest kind): engineers deciding by access (screens sketched, growth dated) model sustainably; engineers deciding by default (embed-everything or normalize-everything) inherit one failure family wholesale. The question predicts schema longevity directly.

### Modern guidance

Answer with the snapshot-vs-truth question first ("will this fact change after write? — frozen: embed; living: reference"), the ceiling math second (elements × bytes × rate vs 16MB — dated, per array), and the read path third (one screen → one fetch — locality designed, not hoped). End unprompted with the mixed shape (priceAtPurchase embedded + productId referenced — historical snapshot beside living link, per [2.1](<../2. Modeling and speed/2.1. Embed versus reference.md>) part 2).

### Runnable example (good — the numbers behind the answer, quoted)

```bash
# embedded order (verified driver-local): 138 bytes (0.0008% of 16MB — nest freely)
# ceiling math (verified driver-local): 50 bytes/item → 335,544 items to 16MB
# verdict for orders: embed (bounded, read-together, five orders of headroom)
# verdict for 2M/day event streams: reference (ceiling in four hours — same math, opposite answer)
```

A hire quotes both numbers then decides per *the interviewer's* growth rate ("at your 2M/day: reference with time-partitioning — the arithmetic says four hours to ceiling"). Numbers first, verdict second, growth-rate question unprompted — the complete modeling answer.

### Common confusion (in candidates)

- **"embed for performance, always"** — red flag: embedding optimizes *reads* (one fetch) while taxing *writes* (whole-document rewrites) and risking ceilings (unbounded arrays). Performance answers need direction (read-heavy + bounded → embed; write-heavy/shared/unbounded → reference). Unconditional embedding reveals one-sided thinking — probe with "shared catalog entity?" and watch the recovery.
- **"reference for cleanliness"** — yellow flag: normalization nostalgia (relational habits in document stores — N+1 renders, assembly per screen). Cleanliness measured in fetches per screen (one excellent, N+1 poor), not in duplication absence. Duplication of *snapshots* is correct duplication — the distinction candidates must state unprompted.

### Performance note

Modeling answers need the read/write asymmetry quantified (99%-path shaped first — dominant direction decides; minority direction accommodated). Strongest form: "embed for the 99% read path (one fetch), reference the shared/unbounded remainder (bounded writes) — asymmetry priced, both directions served." Asymmetry analysis outscores symmetric rules.

### Mentor note

Mock with two workloads (order-with-items vs clickstream-at-2M/day) demanding opposite answers with the same method (access → ceiling → snapshot/truth): mentees graduate when both answers land in five minutes each — method constant, verdicts varying correctly. Method constancy is the skill; verdicts are its outputs.

## 2) "This aggregation is slow — what now?" — explain it

### 2) **Definition** (the pipeline-measurement screen)

"Pipeline takes seconds — walk me through it" — screens for ordered optimization: hires inspect per stage (which stage balloons? — stage-wise debugging from [1.1](<../1. Query depth/1.1. Aggregation pipelines.md>) part 3), explain the slow shape (examined-vs-returned ratio — [2.2](<../2. Modeling and speed/2.2. Document indexes.md>) part 3's fraction), then prescribe (early `$match`, ESR compound, pre-filtered input — ordered by evidence, never enthusiasm).

### What problem it solves (hiring signal)

Aggregation slowness without discipline attracts stage-blind fixes (allowDiskUse as first resort — masking unfiltered inputs; `$sort` reordering by superstition — unmeasured shuffles) that cost more than the slowness (masked problems grow into outages; superstitious orders rot). The measurement sequence converts complaints into arithmetic — stage identified, index evidenced, receipt attached.

### Modern guidance

Answer as a procedure with the verified shapes: inspect per stage (prefix-run — the ballooning stage named), explain it (executionStats: examined vs returned — ratio diagnoses), prescribe in order (early-match narrowing, ESR compound, pre-filtered giants — cheapest effective first). Each step measured before the next (no skipping to rewrite, no combining fixes in one deploy — isolated changes, attributed deltas).

### Runnable example (good — the procedure with this track's shapes)

```bash
# step 1 — inspect per stage (verified local semantics): match 3→2, group sums 24.98
# step 2 — explain the slow shape (documented executionStats vocabulary):
#   COLLSCAN, examined 50001 : returned 1 → missing/misshaped index (the 02/2.2 Seq Scan twin)
#   vs IXSCAN, examined 3 : returned 3 → serving exactly (healthy shape)
# step 3 — prescribe (ESR compound ["status","createdAt","total"] — verified ordering logic)
# step 4 — prove (before/after stats in the commit — receipt habit from [02/2.2])
```

### Common confusion (in candidates)

- **"allowDiskUse fixes slow pipelines"** — yellow flag as a *first* move: `allowDiskUse` permits spilling (100MB+ stages completing slowly instead of failing fast — masking unfiltered inputs with disk). Strong candidates narrow first (early `$match` — less work), index second (ESR — faster work), spill last (allowDiskUse for legitimately giant groupings — measured, deliberate). Order matters; spilling is last resort, never first.
- **"rewrite as find() loops"** — red flag: abandoning server-side compute for client loops (transfer-linear degradation — the architecture [1.1](<../1. Query depth/1.1. Aggregation pipelines.md>) part 2 exists to prevent). Slow pipelines get *narrowed and indexed*, never *downloaded* — direction of fix reveals model soundness instantly.

### Performance note

Pipeline answers need the ratio (examined:returned — quoted per shape; ≈1 healthy, ≫1 sick) plus the receipt habit (before/after stats committed with the index). Strongest form: "ratio diagnoses, ESR prescribes, stats prove — three artifacts, one slow pipeline, zero guesswork." Evidence volunteered with sources beats evidence extracted.

### Mentor note

Mock with "this pipeline takes nine seconds" — demand stage inspection before any prescription ("which stage balloons? — prefix-run it"). Mentees graduate when step 1 is always inspection, step 2 always explain, step 3 prescription with receipts — fashion-proof performance judgment in three steps (same drill as 02/5.1's slow-query screen — method transfers across stores).

## 3) "Double-charge on retry" — prevent it (plus rapid-fire)

### 3) **Definition** (the exactly-once drill)

"Network timeout, client retries, customer charged twice — design so it can't happen" — screens for key-based idempotency: hires key per action (idempotency keys as `_id`/unique — retries converge), catch duplicates explicitly (11000 → fetch original → return it — the retry path, tested), and complete with upserts (match-or-create — re-runnable syncs). Hope-based answers ("transactions" alone, "disable retries") fail the drill; key-based answers pass before discussing isolation.

### What problem it solves (hiring signal)

Retry-safety is the most customer-visible correctness property in payments/orders/registrations (duplicates charge real money — harm measured in refunds + trust + regulatory attention): engineers designing keys-per-action prevent the class structurally; engineers hoping transports behave debug duplicates per incident. The drill predicts harm-prevention directly.

### Modern guidance

Answer as the mechanism (key per action → duplicate refused → fetch original → return it — [3.1](<../3. Writes/3.1. Writes ids and idempotency.md>) part 1's verified simulation), extend to syncs (upserts re-run safely — part 2), and bound the bulk (ordered flags declared — part 3).Transactions named as complement (atomic units — Domain 05), never substitute (atomic retries without keys duplicate atomically — the distinction stated unprompted scores independently).

### Runnable example (good — the refusal, quoted)

```bash
# first attempt: {"outcome":"stored","payment":{"key":"pay-42","amount":19.98,"status":"charged"}}
# retry:        {"outcome":"duplicate-refused","payment":{"key":"pay-42","amount":19.98,"status":"charged"}}
# (verified locally — same key, original returned, never a twin)
```

### Rapid-fire drills (with answers)

1. **Pipeline stage order — rule?** Narrow first (`$match` opening — downstream work minimized) ([1.1. Aggregation](<../1. Query depth/1.1. Aggregation pipelines.md>)).
2. **Compound key order — rule?** ESR (equality, sort, range — verified ordering logic) ([2.2. Document indexes](<../2. Modeling and speed/2.2. Document indexes.md>)).
3. **String `_id` query misses — why?** Type-strict identity (cast `ObjectId()` at boundaries) ([01/2.2](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.2. First MongoDB operations.md>)).
4. **Unbounded comments array — verdict?** Reference with ceiling date (growth math vs 16MB — dated, reviewed) ([2.1. Embed vs reference](<../2. Modeling and speed/2.1. Embed versus reference.md>)).
5. **Gate exits 30 vs 31 — meaning?** 30: request-spread filter (structure); 31: loop-insert (batching) ([4.1. MongoDB checklist](<../4. Important points to remember/4.1. MongoDB checklist habits mentors insist on.md>)).
6. **Upsert filter too loose — risk?** Entity merging (strangers fused — precision + unique backstop) ([3.1. Writes](<../3. Writes/3.1. Writes ids and idempotency.md>)).

### Common confusion (in candidates)

- **"idempotency means no duplicates ever"** — idempotency means *same effect* across repeats (refused twin + returned original = one effect, two attempts — duplicates *attempted*, never *effected*). Attempt-counting observability stays honest (retries visible in metrics — refused, not hidden); effect-counting stays exact (one charge — the guarantee). Attempts may repeat; effects converge.
- **"keys replace transactions"** — keys deduplicate *attempts* (retry convergence — single-document scope); transactions unify *units* (multi-statement atomicity — Domain 05 scope). Keyed retries without transactions duplicate *units* atomically (each attempt internally consistent, mutually duplicated); transacted attempts without keys duplicate *wholes* (consistent twins — worse). Both mechanisms, different jobs — key attempts, transact units.

### Performance note

Idempotency answers need the cost footnote (unique-probe microseconds per write — gladly paid; duplicate incidents unbounded — never risked). Rapid-fire needs instantaneity (ten seconds per drill — retrieval, not reasoning). Evidence volunteered with sources beats evidence extracted; ranges beat points.

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly data-health check. Drills 3 and 5 separate witness-readers (casts, exit codes) from hope-runners; ask those first when time is short.
