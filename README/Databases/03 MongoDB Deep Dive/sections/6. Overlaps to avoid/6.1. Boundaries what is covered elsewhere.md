# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for MongoDB depth. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the document-vs-relational-vs-theory split that keeps MongoDB knowledge in exactly one place per question.

## 1) Foundations and relational twins (neighbor domains own the ends)

### 1) **Definition** (the depth sandwich, document edition)

*First contact* (CRUD, objects, `_id`, operator-injection sibling — Domain 01, assumed fluent) below; *relational twins* (joins, GROUP BY, plan reading — Domain 02, assumed readable) beside. This domain owns the *document depth*: pipelines, operators, modeling, document indexes, idempotent writes. Questions about first operations go back; questions about SQL twins go sideways; questions about document depth stay here.

### The assignments (with the exact targets)

- Foundations (CRUD/objects/ids/injection-sibling/gates) → [01 Database Foundations](<../../../01 Database Foundations and Mental Model/README.md>). Every probe here assumes the handshake, BSON literacy, and witness-reading — no re-teaching, ever.
- Relational twins (join semantics, aggregate grain, plan discipline) → [02 Postgres Deep Dive](<../../../02 Postgres Deep Dive/README.md>). Each document mechanic cites its SQL twin (match tables, grain discipline, plan-first tuning) — twins linked, never re-derived.
- Naming level (aggregation/index/idempotency as words) → [IT Vocabulary 05](<../../../../ITVocabulary/05 Data Databases and AI Vocabulary/sections/1. Data words/1.2. Database table query and index.md>) (words owned there; mechanics owned here).

### Common confusion

- **"document depth needs no SQL"** — document mechanics *rhyme* with relational ones (pipelines↔GROUP BY, ESR↔compound-column-order, explain↔EXPLAIN — same measurement sequences, both stores). SQL-illiterate document engineers reinvent grain discipline and plan reading per store (tuition repaid unnecessarily); twin-literate engineers transfer method instantly (learn once, apply twice).
- **"twins mean duplication"** — twins mean *referenced* parallels (one-line links per rhyme — "same economy, document spelling" — never restated mechanics). Duplication would re-teach GROUP BY inside `$group`; referencing teaches the delta only (accumulators, stage order — genuinely new). Deltas, not copies — the DRY law applied per leaf.

### Mentor note

Teach mentees to read this page as a router: "first-contact" questions go to 01, "SQL-twin" questions go to 02, "document-depth" questions stay here. The distinction resolves half of all MongoDB debates before they start — most are foundation-questions asked in depth-rooms ("how do I insert?" during an aggregation review), or the reverse.

## 3) Design and mapping (planned siblings own the ends)

### 3) **Definition** (the depth/design/map split, document edition)

*Depth* (this domain: querying, modeling, speeding, writing documents directly) vs *modeling* (Database Design track: document schema patterns as design discipline — planned sibling) vs *mapping* (ORM track: ODMs, entity mapping — planned sibling). Depth assumes workable shapes (pipelines run against modeled collections) and precedes mapping (driver literacy before ODM trust — you cannot evaluate an ODM without reading its queries).

### The assignments

- Schema modeling (document patterns, key strategy, evolution) → Database Design track (planned sibling per root README — textual forward, no dead link by design).
- Object-document mapping (ODMs, entities, generated migrations) → ORM track (planned sibling per root README — textual forward, no dead link by design).
- Repository seams (policy surviving store swaps) → [DesignPatterns 06/1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>) (seam owned there — depth queries run behind it).

### Common confusion

- **"ODM users skip this domain"** — ODM users need this domain *most* (generated pipelines debugged via explain, N+1 recognized via modeling literacy, bulk semantics reviewed via write literacy — every ODM failure mode is a depth question in disguise). Abstraction without foundation is magic; magic breaks quarterly — learn depth, then abstract consciously.
- **"modeling examples here duplicate Design"** — examples *serve lessons* (minimal shapes per probe — incidental, serving the leaf); discipline *lives* in its track (patterns systematic — deliberate, serving careers). Incidental shapes teach mechanics; systematic patterns teach modeling — different jobs, different homes.

### Mentor note

The one-sentence router for MongoDB: "First operations go back (01), SQL twins go sideways (02), drivers wait (04), models live in siblings, *depth* stays here." Pipelines/operators/modeling/indexes/writes — the depth layer with its own craft, its own checklist, its own interview.
