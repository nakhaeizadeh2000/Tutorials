# 2.2. Document indexes

Speeding document queries with evidence: ESR-ordered compounds, uniqueness where identity lives, and `explain` measured plans. Junior read: index equality fields, prove with explain. Expert read: why key order decides index usefulness, and what uniqueness guarantees beyond speed.

## 1) Index the queried shape

### 1) **Definition** (ESR compound discipline)

Compound indexes order keys Equality → Sort → Range (`{ status: 1, createdAt: -1, total: 1 }` serving `status = ? ORDER BY createdAt` with `total` ranged): equality prefixes navigate (exact key seeks), sort keys order (no in-memory sort stage), range tails filter (bounded scans). Field order *is* the index (reordered keys serve different shapes — one compound per dominant shape, not per query).

### What problem it solves (history)

Single-field index sprawl (every queried field indexed alone — compound queries using one index plus in-memory stages for the rest: sorts spilling, ranges scanning post-match) paid full maintenance per index for partial speedups (each query half-served — planner picking the least-bad single). ESR compounds serve whole shapes (equality navigates, sort orders, range bounds — one index per dominant question, maintenance earning its keep).

### Modern guidance

Order keys ESR per dominant query (equality fields first — highest cardinality leftmost among equals; sort field next — direction matching (`-1` for newest-first); range last — bounded tail scans); one compound per shape (dominant questions enumerated — access logs, not guesses); sort-direction fidelity (`createdAt: -1` serves newest-first sorts — reversed sorts need reversed keys or in-memory stages).

### Runnable example (good — ESR ordering, verified locally)

```bash
node -e "
// ESR check: equality fields first, sort second, range last — executable ordering rule
const orderKey = (pred) => [
  ...pred.filter(p => p.op === 'eq').map(p => p.field),
  ...pred.filter(p => p.op === 'sort').map(p => p.field),
  ...pred.filter(p => p.op === 'range').map(p => p.field)
];
console.log('esr-order:', JSON.stringify(orderKey([
  { field: 'total', op: 'range' }, { field: 'status', op: 'eq' }, { field: 'createdAt', op: 'sort' }
])));"
// esr-order: ["status","createdAt","total"]
```

```javascript
// server spelling (MongoDB 8.3 manual — documented-not-executed on this floor):
db.orders.createIndex({ status: 1, createdAt: -1, total: 1 });
// serves: db.orders.find({ status: "new", total: { $gt: 100 } }).sort({ createdAt: -1 })
// (equality navigates → sort orders from the key → range bounds the tail — whole shape, one index)
```

Verified: ordering logic executable locally (predicates sorted ESR deterministically — the rule as code, not prose); server creation/usage documented from the 8.3 manual (labeled per scope note). Key order wrong (`{ total: 1, status: 1 }` for the same query — range-first poisons equality navigation: full range scanned, status filtered after — shape mismatch, measurable).

### Common confusion

- **"more indexes, more speed"** — each index taxes every write (maintenance per insert/update/delete — N indexes × per-row cost, measured in bulk-load windows) while serving only its shapes (unqueried indexes: pure overhead wearing preparedness). Index *shapes* (dominant questions, enumerated), not fields (queried somewhere, sometime) — evidence per index, drop quarterly per [4.1](<../4. Important points to remember/4.1. MongoDB checklist habits mentors insist on.md>).
- **"sort direction doesn't matter"** — direction decides sort-service (matching direction: index-ordered output, no stage; reversed: in-memory sort stage — memory-bounded, spill-prone). Newest-first applications index `-1` deliberately (direction as design, not default); bidirectional sorts need bidirectional thinking (compound per direction, or bounded in-memory sorts — chosen, never accidental).

### Performance note

Compound payoff scales with collection size (small: noise; large: seek-vs-scan orders of magnitude — same bargain as [02/2.2](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.2. Indexes and EXPLAIN.md>), document spelling); write tax scales linearly per index (bulk windows measure per addition — additions gated on read evidence). ESR ordering maximizes payoff per index (whole shapes served — few indexes, full coverage) — ordering discipline *is* index economy.

### Mentor note

The ESR whiteboard (predicates classified eq/sort/range, keys ordered aloud — thirty seconds per query): mentees ordering keys correctly unprompted index deliberately forever after. Review index PRs with "which shape does this serve?" (dominant question named, or the index doesn't land — evidence-gated additions, per [4.1](<../4. Important points to remember/4.1. MongoDB checklist habits mentors insist on.md>)).

## 2) Uniqueness where identity lives

### 2) **Definition** (dedup as index property)

`{ unique: true }` on natural-key indexes (slugs, emails, idempotency keys — identity-valued fields): duplicates refused at write time with duplicate-key errors (named index, machine-routable code — the write-side twin of `_id`'s automatic uniqueness from [01/2.2](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.2. First MongoDB operations.md>)). Uniqueness enforced where identity lives (the store — race-free, client-agnostic), never where it's convenient (application pre-checks — racy, bypassable).

### What problem it solves (history)

Check-then-insert dedup (query-for-exists → insert-if-absent — racing under concurrency: two writers, both see absent, both insert, duplicates stored; plus every non-checking client bypassing entirely — consoles, scripts, integrations) failed exactly under the conditions dedup matters (concurrent double-submits, retry storms — duplicates precisely when uniqueness is load-bearing). Unique indexes close the race structurally (atomic check-and-insert at write time — second writer refused, loudly).

### Modern guidance

Unique-index natural keys (slugs, idempotency keys, emails — identity semantics → unique enforcement, one mechanism per meaning); catch duplicate-key errors explicitly (code 11000 — branch to fetch-existing (idempotent retry path) vs abort (genuine conflict) — error codes routed, never string-matched); compound uniqueness where scoped (per-user slugs: `{ userId: 1, slug: 1 }` unique — identity scoped, duplicates meaningful only within scope).

### Runnable example (good — dedup shape, documented spelling + local twin)

```javascript
// server spelling (MongoDB 8.3 manual — documented-not-executed on this floor):
db.payments.createIndex({ idempotencyKey: 1 }, { unique: true });
db.payments.insertOne({ _id: new ObjectId(), idempotencyKey: "pay-42", amount: 19.98 });
// retry posts identical idempotencyKey → duplicate-key error 11000 (refused, loudly)
// handler: catch 11000 → fetch existing by key → return it (exactly-once effect, at-least-once attempts)
```

```javascript
// local twin of the guarantee (verified driver-local — code 11000 shape asserted structurally):
// const err = { code: 11000, keyPattern: { idempotencyKey: 1 } };
// err.code === 11000 → fetch-by-key path (idempotent retry); else → abort path (genuine conflict).
```

Why unique-not-precheck: pre-check races (TOCTOU between check and insert — concurrency's classic hole); unique refuses atomically (check *is* the insert — no window, no race). Retry storms meet refusal (loud, routable) instead of duplicates (silent, compounding) — the exactly-once effect from at-least-once attempts, per [3.1](<../3. Writes/3.1. Writes ids and idempotency.md>).

### Common confusion

- **"unique slows hot inserts"** — uniqueness checks cost an index probe per write (microseconds — the price of race-freedom); duplicate incidents cost dedupe labor + customer harm (unbounded, per occurrence). Hot paths with identity semantics pay probes gladly (measured once, beneficial forever); identity-free hot paths skip uniqueness (nothing to enforce — no index, no tax).
- **"sparse vs partial vs unique confusion"** — sparse skips *missing* fields (legacy — partial indexes supersede: `partialFilterExpression` scoping precisely); partial scopes *which documents* (active-only uniqueness — `{ active: true }`-scoped slugs, archived duplicates allowed); unique enforces *all indexed* (full-scope dedup). Three modifiers, three scopes — compose deliberately (partial-unique for scoped identity — the common production shape).

### Performance note

Unique-probe cost per write (index lookup — microseconds, like all uniqueness); duplicate-incident cost (dedupe scripts, customer merges, trust repair — days per occurrence). Hot-insert paths measure probe overhead once (bulk windows — acceptable nearly always); identity semantics decide presence (meaning, not speed, governs). Enforce where identity lives; measure where heat lives.

### Mentor note

The double-submit demo (post twice with one idempotency key — second refused 11000, fetch returns original — five minutes): mentees watching exactly-once emerge from refusal stop fearing retries and start designing for them (retry-safe by construction — the senior shift from hope to mechanism). Demo per cohort; exactly-once understanding follows refusal-witnessing, never precedes it.

## 3) Measure with explain

### 3) **Definition** (document plan proof)

`db.orders.find(filter).explain("executionStats")` returns the winning plan with measured stats (stages, keys examined, docs returned, ms elapsed — proof, not estimates): `IXSCAN` + low examined-to-returned ratio (index serving — healthy); `COLLSCAN` on large collections (full scan — index missing or unusable); `SORT` stage with spills (in-memory sort overflowing — index the sort or bound the input). Plans read before theorizing — the document twin of [02/2.2](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.2. Indexes and EXPLAIN.md>)'s rule.

### What problem it solves (history)

Blind document tuning (index-per-field sprawl, ESR-violating compounds, sort-stage surprises — each unmeasured, most neutral-or-harmful) burned optimization budgets on cold shapes while real costs (missing compounds, unindexed sorts, scanned millions) sat one explain away. Plan-first tuning aims effort (examined-vs-returned ratio names waste precisely — 50k examined / 1 returned screams missing index in one line).

### Modern guidance

Explain per slow shape (every "slow query" claim arrives with executionStats or returns for one); read examined-vs-returned first (ratio ≈ 1: indexed serving; ratio ≫ 1: scan or misshaped index — the single most informative fraction in document performance); attach plans to index commits (before/after stats — improvement proven, regressions caught — receipt habit from [02/2.2](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.2. Indexes and EXPLAIN.md>) part 3, document spelling).

### Runnable example (good — the ratio that diagnoses, described precisely)

```javascript
// healthy (shape — documented executionStats vocabulary, 8.3 manual):
// winningPlan: IXSCAN on { status: 1 } → totalKeysExamined: 3, totalDocsExamined: 3,
//   nReturned: 3, executionTimeMillis: 0
// → ratio 1:1 (every examined document returned — index serving exactly)

// sick (shape — the twin to diagnose):
// winningPlan: COLLSCAN → totalDocsExamined: 50001, nReturned: 1
// → ratio 50001:1 (full collection scanned per answer — the 02/2.2 Seq Scan twin,
//   verified live there at cost 769.59: same disease, relational spelling)
```

Described shapes (server execution documented — labeled per scope note): the ratio diagnoses without running (examined ≫ returned = missing/misshaped index, always). Relational twin verified live ([02/2.2](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.2. Indexes and EXPLAIN.md>) cost 769.59 → 323.72 with actuals) — same measurement sequence, both stores: plan, index, prove.

### Common confusion

- **"explain() output is self-evident"** — verbosity obscures (allPlansConsidered, rejected plans, shard spans — noise around the signal): read winningPlan + examined/returned + ms (three fields answering health — rest consulted per anomaly, never scanned routinely). Three-field reading triages in seconds; full-output reading drowns in minutes.
- **"queryPlanner mode suffices"** — `queryPlanner` shows *chosen* plans without executing (estimates — the hope half); `executionStats` executes and measures (actuals — the proof half). Planning questions (which index?) suit the former; performance questions (how slow?) demand the latter. Mode matches question — proof mode for speed claims, always.

### Performance note

Explain cost: queryPlanner mode (planning only — safe anywhere); executionStats executes (reads run — replicas fine; writes never explained blindly — same caution as SQL ANALYZE). Unmeasured-tuning cost: mis-index additions (maintenance without benefit — net negative, shipped confidently). Receipt-per-index (before/after stats in commits) is the cheapest document-performance governance — seconds per change, incidents prevented per quarter.

### Mentor note

Require executionStats in every slow-query report ("no plan, no triage" — the rule that ends folklore-based tuning in a quarter): mentees attaching plans unprompted within weeks (habit formed by requirement, sustained by payoff — plans that name fixes teach faster than mentors can). Plans in commits document *why* each index exists (future droppers read receipts before dropping).
