# 2.1. Embed versus reference

Deciding document shape by access: nest what reads together, link what grows apart, and let the 16MB ceiling break ties. Junior read: embed for one-fetch reads, reference for shared or unbounded data. Expert read: where embedding becomes a write-amplification trap, and how growth math (measured, not hoped) decides before production does.

## 1) Embed what reads together

### 1) **Definition** (read-locality nesting)

Embed subdocuments/arrays read with their parent (order with its items — one fetch, zero joins, snapshot-consistent by construction): the read path that dominates (order display, 99% of accesses) served in a single document fetch. Embedded data versions with its parent (one write updates the unit — no cross-collection coordination); embedded reads never join (no `$lookup`, no application assembly — locality complete).

### What problem it solves (history)

Over-normalized documents (orders referencing items referencing products — three collections for one screen, application-joined per render: N+1 in document clothing) reimplemented relational shape without relational joins (worst of both: no planner, no locality — fetch fan-out per render, latency linear in nesting depth). Embedding restores locality (read-unit shaped as stored-unit — one fetch per screen, by design).

### Modern guidance

Embed bounded, co-read data (order+items, user+preferences, post+comments-small — read together, written together, sized together); keep embedded arrays small-and-slow-growing (tens of elements, bounded domains — statuses, line items per order, addresses per user); version embedded units atomically (single-document writes are atomic — embedded updates never half-apply, per the write unit Domain 05 formalizes).

### Runnable example (good — the embedded unit, measured, verified driver-local)

```bash
node -e "
const { BSON, ObjectId } = require('mongodb');
const order = { _id: new ObjectId(), customer: { name: 'ann' }, items: [{ sku: 'a1', qty: 2, price: 9.99 }], total: 19.98, status: 'new' };
const bytes = BSON.calculateObjectSize(order);
console.log('embedded-order bytes:', bytes, '| of 16MB:', (bytes / (16*1024*1024) * 100).toFixed(4) + '%');"
# embedded-order bytes: 138 | of 16MB: 0.0008%
```

Verified (mongodb driver, local BSON computation — sizing is client-computable, no server needed): a realistic order occupies 138 bytes — 0.0008% of the ceiling. Embedding headroom measured in *five orders of magnitude* for this shape: nest confidently, monitor structurally (part 3's ceiling math generalizes the check).

### Common confusion

- **"embed everything, joins are legacy"** — embedding everything nests *shared* entities per user (product details copied into ten thousand orders — stale copies diverging, updates fanning out to thousands of documents). Embed read-units (order snapshots — point-in-time truth, correctly duplicated); reference shared-truth (product catalog — one copy, linked). Snapshot vs truth is the axis — not embed-vs-reference as fashion.
- **"embedded writes are free"** — embedded updates rewrite the *document* (whole-document write amplification on large embeds — 15MB document touched per 50-byte field change: I/O billed per document, not per field). Small embeds: negligible; large embeds: rewrite tax per touch (part 3's ceiling math doubles as the amplification warning — measure bytes per update path).

### Performance note

Embedded reads cost one fetch (constant — document size bounded, transfer predictable); referenced reads cost 1+N fetches or one `$lookup` (assembly cost per read — application joins linear in fan-out, `$lookup` server-side per pipeline). Read-path dominance decides (99%-path shaped first — optimize the common read, accept the rare write's shape): locality for readers, links for writers, measured per workload.

### Mentor note

The read-path question ("show me the screen this data renders on") settles most embed/reference debates in one sketch (one screen → one document; three screens sharing one entity → reference): mentees sketching screens before schemas model access-first permanently. Schema-first modelers produce elegant diagrams with N+1 renders — screens first, always.

## 2) Reference what grows apart

### 2) **Definition** (links for shared and unbounded)

Reference by `_id` where entities evolve independently (products shared across orders — one truth, linked) or grow unboundedly (comment threads, event streams — arrays that never stop — capped only by the ceiling they will eventually hit). Reads assemble (`$lookup` server-side, application-join client-side — explicit joins, chosen per query); writes stay independent (update product once — every reference reads current; append events freely — no document rewrite per event).

### What problem it solves (history)

Embedded-everything at scale (product details duplicated per order — price corrections fanning out to millions of documents, partial updates leaving price-history soup; unbounded arrays growing per event — documents swelling toward the ceiling, then *crashing through it* in production) failed on shared-truth staleness and growth ceilings simultaneously. References isolate evolution (shared entities versioned once; unbounded streams appended forever — each shape in its structure).

### Modern guidance

Reference shared entities (catalogs, users, configs — single truth, many readers); reference unbounded growth (events, comments-at-scale, audit trails — append-only collections, time-ordered by ObjectId); join explicitly per read (`$lookup` for server-side assembly — documented from the 8.3 manual; application-join for cross-shard or shaped assembly — Domain 06 owns topology implications). Duplication only for point-in-time snapshots (order-line product names *at purchase* — historical truth, correctly frozen).

### Runnable example (good — the reference shape, contrasted)

```javascript
// orders reference products (shared truth — one copy, linked):
// orders:  { _id, customer: {...}, items: [{ productId: ObjectId("..."), qty: 2, priceAtPurchase: 9.99 }], total }
// products:{ _id, sku: "a1", name: "...", price: 9.99 }   ← current truth lives HERE only
// read assembles: db.orders.aggregate([{ $match: {...} }, { $lookup: { from: "products", localField: "items.productId", foreignField: "_id", as: "catalog" } }])
// (server spelling documented from the 8.3 manual — labeled per scope note)
```

```javascript
// bad: embedded shared truth (staleness by design)
order.items[0] = { sku: "a1", name: "Old Name", price: 8.99 };  // product renamed + repriced since
// ten thousand embedded copies disagree with the catalog — which price is true? (unanswerable post-hoc)
// Fix: embed priceAtPurchase (historical snapshot — frozen correctly) + reference productId (current truth — linked).
```

Why it hurts: duplicated shared-truth diverges silently (no constraint spans documents — staleness undetectable except by audit; price corrections fanning out partially — some copies updated, rest stale, revenue computed over disagreement). Fix by axis (snapshot-duplicate historical facts; reference living truths — both deliberately, never by default).

### Common confusion

- **"references are just slow joins"** — references are *explicit* joins (chosen per read — `$lookup` or application assembly, indexed both sides, measured): slow only where unindexed or over-fetched (same discipline as SQL joins — [02/1.1](<../../../02 Postgres Deep Dive/sections/1. Query depth/1.1. Joins across tables.md>) part 1's shape thinking, document spelling). Unindexed-reference N+1 deserves its reputation; indexed, deliberate references perform fine.
- **"DBRefs solve referencing"** — DBRefs (driver-assisted `{ $ref, $id }` links — resolved client-side per reference, N+1 by construction) automate the slow path (convenience-shaped N+1 — each resolved individually, no batching). Manual refs + `$lookup`/batched application-join outperform structurally (set-based assembly — one round trip per side). Prefer manual refs (explicit, batchable); treat DBRefs as legacy convenience (documented, avoided).

### Performance note

Reference cost per read: join assembly (one `$lookup` stage or batched fetch — constant-ish per query, indexed); embedded-duplicate cost per write: fan-out updates (copies × write cost — linear in duplication factor, unbounded over time). Read-heavy shared data references cheaply (assemble per read, update once); write-heavy snapshots embed cheaply (write once, read frozen). Dominant direction decides — measured per collection, reviewed per growth spurt.

### Mentor note

The snapshot-vs-truth question ("will this fact change after write? — yes: reference; no: embed") resolves most modeling debates in one sentence: mentees asking it model temporally (facts with lifecycles — historical vs living), not just structurally. Temporal modeling is the senior shift (shapes *over time*, not shapes *at rest*) — teach the question, the answers follow.

## 3) The 16MB ceiling decides ties

### 3) **Definition** (the hard bound)

16,777,216 bytes per document, enforced (oversized writes rejected — `BSONObjectTooLarge`, no override, no negotiation): the only absolute in document modeling. Growth math per array (`bytesPerElement × expectedCount` vs ceiling — computed, per part's probe pattern); unbounded growth references *always* (no projection survives infinity — the ceiling is a matter of *when*, priced per growth rate).

### What problem it solves (history)

Ceiling crashes (comment arrays, event logs, audit trails embedded "temporarily" — growing silently for years, then one insert crossing 16MB in production: writes failing *only for the largest customers* (longest histories hit first — the most valuable accounts breaking first, the cruelest selection bias in data incidents). Growth math at design time (elements × bytes vs ceiling, with dates) converts crashes into planned references.

### Modern guidance

Compute growth per unbounded array at design (element bytes × rate × horizon vs 16MB — dated arithmetic in the design doc, reviewed per growth spurt); reference beyond 12–24 month projections (margin before the ceiling — migrations under ceiling pressure are the dearest kind); monitor document sizes in production (max/avg per collection tracked — growth visible quarters before impact, per Domain 06 observability).

### Runnable example (good — the ceiling math, verified driver-local)

```bash
node -e "
const { BSON } = require('mongodb');
const perItem = BSON.calculateObjectSize({ sku: 'a1-xxxxxxxx', qty: 2, price: 9.99 });
const maxItems = Math.floor((16*1024*1024) / perItem);
console.log('bytes/item:', perItem, '| items-to-16MB:', maxItems);"
# bytes/item: 50 | items-to-16MB: 335544
```

Verified: 50 bytes/item → 335,544 items to the ceiling (comfortable for orders — alarming for event streams at millions/day: 335k ÷ 2M/day = ceiling in *four hours*). Same arithmetic, opposite verdicts per growth rate — math decides, hope doesn't. Cap unbounded arrays structurally (capped collections for rolling windows, time-partitioned collections for history — bounded by construction, never by optimism).

### Common confusion

- **"16MB is plenty"** — plenty for *bounded* shapes (orders, profiles, configs — thousands of elements max); nothing for *unbounded* ones (event-per-click streams, IoT telemetry, audit-everything — millions per day eat 16MB for breakfast). "Plenty" is growth-rate-relative (divide by rate before opining — the arithmetic above, per array, per review).
- **"GridFS extends documents"** — GridFS stores *blobs* (files chunked across documents — binary payloads, not model growth: PDFs, images, exports). Array-growth pressure needs *modeling* (reference/time-partition — structural), not blob storage (different problem — large values, not many elements). Right tool per pressure: GridFS for blobs, references for growth.

### Performance note

Near-ceiling documents cost per touch (multi-MB rewrite I/O per field update — write amplification maximized; working-set eviction per large read — cache pollution per fetch). Right-sized documents (KBs — the 138-byte order from part 1) touch cheaply (single pages, cache-resident). Size discipline *is* write performance for documents (bytes per touch, not query cleverness) — measure per update path, bound per array.

### Mentor note

Require ceiling math in every document-model review ("largest array: elements × bytes × rate = ceiling date?" — three numbers, one date): mentees computing dates model temporally (shapes *over time* — the senior shift from part 2, reinforced); reviewers asking thrice make growth-math reflexive team-wide. Dates, not vibes — ceiling dates in design docs, always.
