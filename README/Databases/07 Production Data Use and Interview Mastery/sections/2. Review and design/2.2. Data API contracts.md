# 2.2. Data API contracts

Designing data boundaries services consume: versioned shapes, keyset pagination, and errors naming data remedies. Junior read: envelope every response, paginate every list, version before breaking. Expert read: why keyset beats offset under concurrent writes, and what remedy-bearing data errors save in support load.

## 1) Shapes versioned, never broken silently

### 1) **Definition** (additive evolution with announcements)

API shapes evolve additively (new fields optional, new endpoints versioned — old clients unaffected: unknown fields ignored, known fields stable); breaking changes versioned explicitly (`/v2/` paths or version headers — announced, migrated, then old removed after traffic reaches zero); removals dated (sunset headers + changelogs — breaking scheduled, never sprung). Silent breaks (renamed fields, dropped values, restructured envelopes — clients discovering via 500s) rejected in review regardless of schedule pressure.

### What problem it solves (history)

Silent shape breaks (renamed `total` to `amount` Friday — three clients red Monday, none warned: integration failures discovered per consumer, fixed per fire-drill, trust taxed per incident) made every API change a potential multi-team outage (producers deploying confidently, consumers breaking silently — versioning absent, coordination accidental). Versioned evolution converts breaks into migrations (announced → dual-served → measured-zero → removed: consumers moving deliberately, producers waiting verifiably).

### Modern guidance

Additive by default (optional fields, new endpoints — old clients immune by construction); versioned when breaking (path/header versions — explicit, greppable, sunsetting); envelope uniformly (`{ ok, data } | { ok: false, error: { code, remedy } }` — verified below: clients branch on `ok`, never on status-text-sniffing); sunset by traffic (old-version usage metered — removal only at measured zero, never calendar-guessed).

### Runnable example (good — the envelope, verified live via node)

```bash
node -e "
const env = (ok, data, code, remedy) => ok ? { ok: true, data } : { ok: false, error: { code, remedy } };
console.log(JSON.stringify(env(true, { id: 7 })));
console.log(JSON.stringify(env(false, null, 'RATE_LIMITED', 'Retry after 30s')));"
# {"ok":true,"data":{"id":7}}
# {"ok":false,"error":{"code":"RATE_LIMITED","remedy":"Retry after 30s"}}
```

Verified (Node v20.20.2): success and failure share one shape (branch on `ok` — machines route, humans read remedy). Data errors carry codes *and* remedies (constraint violations surfaced as actionable errors — `23505` inside becomes `DUPLICATE_SLUG, "slug taken — choose another"` outside: store codes translated, never leaked raw).

### Common confusion

- **"versioning can wait for v2"** — unversioned v1 *is* the versioning decision (every change breaking by default — no path/header to evolve under). Version from day one (cost: one path segment; benefit: every future change has somewhere to go but breaking). Retrofit versioning is a migration (clients coordinated, URLs rewritten — quarters of work); initial versioning is a prefix (minutes, once).
- **"envelopes waste bytes"** — envelopes cost one discriminant field per response (bytes, single-digit percent on small payloads — negligible beside I/O); unenveloped errors cost client-branching chaos (status-text sniffing per consumer — brittle, unversionable, untestable). Uniformity priced in bytes (cheap); uniformity absent priced in integration incidents (dear).

### Performance note

Envelope overhead per response (one field — negligible); versioning overhead per breaking change (dual-serve window — old + new shapes served during migration: storage/compute doubled briefly, bounded by sunset date); sunset discipline pays continuously (old versions retired at measured zero — surface area shrinking, maintenance concentrating). Versioned evolution costs bytes transiently, saves incidents permanently.

### Mentor note

Review API PRs contract-first (spec diff before handler diff — shapes, codes, versions decided before implementation reviewed): implementation follows contract, never precedes it. Mentees designing APIs start with the envelope + error table (one page), then handlers — contract-driven development, one page at a time.

## 2) Pagination where lists grow

### 2) **Definition** (bounded lists, stable pages)

Lists paginate (bounded page sizes — whole-table responses refused structurally); keyset pagination preferred (`WHERE id > $last ORDER BY id LIMIT n` — stable under concurrent writes: inserts shifting offsets don't duplicate/skip keyset pages); offset pagination tolerated for static/small sets only (page N as rows N×size — concurrent inserts shifting every subsequent page: duplicates and gaps under write load, by construction).

### What problem it solves (history)

Unbounded list endpoints (`GET /orders` returning all rows — payload linear in table size: responses growing per quarter (KB→MB→timeouts), clients OOMing on big accounts, databases serializing millions of rows per dashboard load) plus offset-under-write pages (concurrent inserts shifting page boundaries mid-pagination — items duplicated across pages, items skipped entirely: clients seeing ghosts and holes, support tickets blaming "missing data" that exists) made lists the slowest-growing liability per service. Bounded keyset pages fix both (transfer capped per page, stability under writes by key ordering).

### Modern guidance

Keyset by default (`id`/cursor-ordered — stable pages, bounded transfers); offset only where data is static (admin exports, small reference tables — documented exception, revisited per growth); page sizes capped server-side (`LIMIT min(requested, 100)` — clients requesting millions get hundreds: bounds enforced, never negotiated); total counts separated (counts via dedicated endpoint/query — never bundled with pages: counting scans while paging seeks, different costs, different caches).

### Runnable example (good — keyset pages, verified live)

```bash
DATABASE_URL=... node -e "
  const page1 = await c.query('SELECT id FROM demo_orders ORDER BY id LIMIT 2');
  // page1: [1,2]
  const last = 2;
  const page2 = await c.query('SELECT id FROM demo_orders WHERE id > \$1 ORDER BY id LIMIT 2', [last]);
  // page2-keyset-after-2: [3,4]"
# page1: [1,2]
# page2-keyset-after-2: [3,4]
```

Verified (PostgreSQL 16.15, `pg` 8.23.0): keyset pages stable and complete ([1,2] then [3,4] — no overlap, no gap). Concurrent-insert an id-0 row mid-pagination and offset pages shift (duplicates/gaps — the failure keyset structurally avoids: position by *key*, never by *count*).

### Common confusion

- **"offset is simpler"** — offset is simpler to *write* (`OFFSET N` — one clause) and wrong under writes (shifting boundaries — duplicates/gaps per concurrent insert: simplicity billing correctness). Keyset is marginally more code (cursor threading — one extra parameter) and correct under writes (key-ordered stability — structural, not hopeful). Simplicity measured end-to-end (authoring + correctness), never authoring-only.
- **"clients need total pages"** — clients need *progress* (next-cursor presence — "more" boolean, not page 7-of-4000 arithmetic); totals cost full scans per request (COUNT(*) over filtered millions — the most expensive number on list endpoints, recomputed per page-load). Totals separated (cached counts endpoint, refreshed periodically — expensive number computed rarely, displayed approximately).

### Performance note

Keyset cost per page (indexed range scan — constant-ish, cursor-positioned); offset cost per deep page (`OFFSET 100000` — scans-and-discards 100k rows per request: linear degradation with depth, the deep-page cliff). Unbounded-list cost (full serialization per request — linear in table size, unbounded). Page by key (constant), cap sizes (bounded), separate counts (cached) — three rules, linear costs nowhere.

### Mentor note

Demo offset-skew live (insert mid-pagination, show duplicate/gap — ninety seconds): witnesses convert faster than warnings (keyset adopted on sight, offset defended never again). Review list endpoints for the three rules (keyset? capped? counts-separated? — mechanical checks, seconds): lists stay bounded and stable by review habit, not hope.

## 3) Errors name data remedies

### 3) **Definition** (actionable data failures)

Data errors carry machine codes + human remedies (`DUPLICATE_SLUG` / "slug taken — choose another"; `FK_VIOLATION` / "referenced record missing — create it first"; `RATE_LIMITED` / "Retry after 30s" with `Retry-After`): callers branch on code (programmatic), humans follow remedies (operational), support joins on request ids (correlatable). Raw store codes translated at the boundary (23505 inside → DUPLICATE_* outside — information discipline, per [part-1-adjacent error hygiene]).

### What problem it solves (history)

Remedy-less data errors (500 "Internal error" on unique violations — clients retrying identically (guaranteed repeat failure — retry storms on deterministic errors); support tickets per duplicate (humans bridging the remedy gap — reading code, asking engineers, waiting)) converted every data failure into a support interaction (humans as error-decoders — load scaling with failure rate instead of novelty). Remedy-bearing errors convert repeats into self-service (first occurrence: ticket + remedy added; subsequent: clients follow the remedy — support load scaling with novelty only).

### Modern guidance

Codify per data error (table: store code → API code → status → remedy → retryable — reviewed like API shapes); translate, never leak (23505 → DUPLICATE_*, never raw SQLSTATE/constraints client-side — schema details are internal vocabulary); test remedies (assert `remedy` field presence per error code — contract tests covering the interface, not just the happy shape); flag retryability (boolean — callers back off correctly instead of hammering deterministic failures).

### Runnable example (good — remedies verified in the envelope probe above)

```bash
# from the verified probe: {"ok":false,"error":{"code":"RATE_LIMITED","remedy":"Retry after 30s"}}
# caller branches on code (machine), follows remedy (human), no ticket filed (team) — the full payoff in one line
```

### Common confusion

- **"remedies leak internals"** — remedies describe *caller action* (retry, reduce, wait, contact — external vocabulary), never *system internals* (constraint names, query shapes, hostnames — redacted). Actionable ≠ transparent: "slug taken" helps without exposing; `guarded_users_email_key` exposes without helping (and couples clients to schema internals — renaming constraints breaking clients: leakage with interest). Remedy outward, investigate inward.
- **"codes freeze the API"** — codes *version* with the API (new codes added freely — additive, non-breaking; removals versioned — same policy as fields). Uncoded messages freeze harder (clients sniffing text break on rewording — every copy-edit a breaking change). Codes liberate wording; messages without codes imprison it.

### Performance note

Remedy fields cost bytes per error (tens of bytes — errors are rare paths; payload cost negligible). Retryable flags save thundering herds (non-retryable errors shed load — callers back off correctly instead of hammering; retry storms are unbounded-error consequences). Error design is load-shedding design wearing an API costume (flags priced in averted storms, remedies priced in averted tickets).

### Mentor note

Audit any API's data errors in ten minutes (list codes, check remedies, verify retryable flags — gaps filed as findings with support-ticket counts attached): the audit converts abstract "better errors" into counted load (N tickets/month answerable by remedies). Teams seeing the count prioritize the error table immediately — support metrics sell error design better than any style argument.
