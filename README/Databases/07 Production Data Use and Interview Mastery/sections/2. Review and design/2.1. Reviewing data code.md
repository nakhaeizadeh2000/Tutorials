# 2.1. Reviewing data code

The gates-first review order for data work: mechanical findings before taste, evidence before approval, failure paths before happy paths. Junior read: run the gates, read the exits, then opine on style. Expert read: why review order determines incident rates, and what "approve" certifies beyond the diff.

## 1) Gates before taste

### 1) **Definition** (mechanical-first review order)

Review in layers: gates (unbound parameters? unwitnessed writes? unversioned DDL? unreceipted indexes? — grep + gate scripts decide), then correctness (logic, shapes, boundaries), then taste (naming, structure, elegance). Mechanical findings block; correctness findings discuss; taste findings suggest. Order enforced per PR via templates (gate output pasted before human review begins — no output, no review).

### What problem it solves (history)

Taste-first reviews (naming debates atop concatenated SQL, elegance discourse over unwitnessed writes — incidents shipped beautifully formatted) approved structurally broken data code with polished prose (well-named variables in injectable queries — style green, security red). Gates-first ordering inverts the waste: machines judge machines (greps, gates — instant, objective), humans judge what machines can't (design, trade-offs, readability).

### Modern guidance

Every data PR runs gates 1–6 (or the merged pre-flight — green required, stage numbers quoted on red); reviewers open with gate output (red → request changes with the stage number, no further reading until green); taste comments wait for green (style on red code is churn — the code will change anyway). Gate lists live in [01/4.1](<../../../01 Database Foundations and Mental Model/sections/4. Important points to remember/4.1. Data checklist habits mentors insist on.md>) through [06/4.1](<../../../06 Performance Backup and Operations/sections/4. Important points to remember/4.1. Operations checklist habits mentors insist on.md>) — six checklists, one review order.

### Runnable example (good — all gates green, verified in one pass)

```bash
./gate1.sh; echo "gate1=$?"
# DATA-GREEN
# gate1=0
./gate2.sh; echo "gate2=$?"
# PG-GREEN
# gate2=0
./gate4.sh; echo "gate4=$?"
# ACCESS-GREEN
# gate4=0
```

Verified (all gates, this session): data handshake proven, Postgres shaped, access bound — the mechanical review of three domains in three commands. A reviewer pasting this output approves the *structure*; logic review follows on green, never before. (Gate3/Gate5/Gate6 shapes verified in their sessions — same pattern, distinct stages.)

### Common confusion

- **"gates replace reviewers"** — gates replace *vigilance*, not judgment (mechanical properties checked; design decisions still human — [1.1](<../1. Production judgment/1.1. Capacity judgment under constraints.md>)'s ADRs need readers, not runners). Reviewers freed from grep-work spend attention on architecture — gates upgrade review, never automate it away.
- **"small PRs skip gates"** — small PRs skip *slow* gates never (grep stages: milliseconds — cheap gates run always); large suites gate per schedule (full profiles per merge, not per push — cost-proportioned, per [04-adjacent clock discipline]). Size scales scheduling, never exemption.

### Performance note

Review throughput rises when machines go first (mechanical red in seconds vs human-found-in-days; taste discussion only on green code that survives). Review *quality* rises simultaneously (attention unspent on greppable defects concentrates on design). Gates-first is review performance (faster merges, fewer escapes) wearing a process costume.

### Mentor note

Enforce with PR templates (gate-output section first, human-review sections after — structure beats exhortation): contributors paste green outputs before requesting review; reviewers check the paste before reading code. Two quarters of template-enforced order and teams internalize it (templates teach until habits form, then guard the habit).

## 2) Ask for the evidence

### 2) **Definition** (priced-constant review)

Every constant, claim, and shape in the diff justifies itself with evidence: pool sizes (arithmetic from [04/1.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/1. Drivers/1.1. pg Pool that serves.md>)), timeouts (blip distributions from [04/3.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/3. Resilience/3.1. Retries timeouts and backoff.md>)), index additions (before/after plans from [02/2.2](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.2. Indexes and EXPLAIN.md>)), thresholds (distributions from [1.2](<../1. Production judgment/1.2. Growth planning without panic.md>)). Unpriced numbers get challenged ("sized from what?") — not hostility, but because unpriced constants are guesses wearing literal syntax.

### What problem it solves (history)

Magic-constant data code (timeout 30s "seems safe," pool 10 "default," retries 5 "standard," threshold 80% "round" — each unmeasured, each load-bearing) failed mysteriously at scale (30s timeouts cascading, 10-pools starving, 5-retries storming, 80% misfiring — each failure unattributable: which constant? sized for what load?). Priced constants fail diagnosably (threshold known, arithmetic attached, deviation measurable) — and get resized correctly on first evidence instead of third incident.

### Modern guidance

Challenge every unexplained literal in data paths (timeouts, sizes, counts, TTLs, thresholds — "source?" per number); accept measurements, derivations, and explicit guesses-with-review-dates (honest estimates beat silent defaults — "guess, revisit March" is honorable); record prices beside the constant (comment with the arithmetic or ADR link — prices live with code, not in chat history).

### Runnable example (good — priced vs unpriced, contrasted)

```javascript
// good: every number sourced
const TIMEOUT_MS = 600; // p99 200ms × 3, measured 2026-09 (blip distribution × factor)
const POOL_MAX = 8;     // 60 slots ÷ ... server share capped (sizing in [04/1.1], ADR-00X)
const RETRIES = 2;      // blast radius: 3× traffic worst case, within headroom (ADR-00X)
```

```javascript
// bad: literals without lineage
const TIMEOUT_MS = 30000; // (nothing — 30s of cascading hang per slow upstream)
const POOL_MAX = 10;      // (nothing — default-shaped, load-unshaped)
const RETRIES = 5;        // (nothing — 6× amplification, storms at the second failure)
```

Why unpriced hurts: unpriced numbers resist tuning (change 30s to what? — no model answers) and hide coupling (timeout × retries × pool = worst-case load multiplier — unknowable without prices). Fix: price on introduction (three comments, one minute) or on first challenge (reviewer asks once, author measures, comment lands with the fix).

### Common confusion

- **"asking slows reviews"** — asking *accelerates* reviews over time (priced codebases answer before asked — comments carry prices; unpriced codebases re-litigate per PR). First month slower (habit forming); every month after faster (evidence accumulated). Invest the month.
- **"estimates don't count as prices"** — dated estimates count fully ("guess 600ms, revisit March" — falsifiable, scheduled, honest). What doesn't count: silence (no number to revisit, no date to revisit on). Falsifiability is the standard, not accuracy — wrong fast beats vague forever.

### Performance note

Priced constants are performance documentation (timeouts bound tails, pools bound concurrency, thresholds bound growth — the p99 story told per constant). Unpriced constants are performance debt (tails unexplained, capacity unplanned, incidents undiagnosable). Review-time pricing converts debt to documentation at one comment per number — the cheapest performance practice after bounding.

### Mentor note

Model the question kindly ("help me understand the 600 — measured or estimated?") until the team asks it of itself — tone determines adoption (curiosity spreads, interrogation stalls). Celebrate first pricings publicly (the comment that sourced a timeout is a team asset — say so). Culture first, checklist second, gates last — in that order, always.

## 3) Approve the failure paths

### 3) **Definition** (happy-paths-necessary-insufficient)

Approval certifies failure behavior, not just feature behavior: constraint violations routed (typed, mapped, actionable — [02/2.1](<../../../02 Postgres Deep Dive/sections/2. Shape and speed/2.1. Schema and constraints that protect.md>)), rollbacks planned (catch-rollback-rethrow — [02/3.1](<../../../02 Postgres Deep Dive/sections/3. Atomicity/3.1. Transactions basis.md>)), restores proven (round-trip counts — [06/2.1](<../../../06 Performance Backup and Operations/sections/2. Survival/2.1. Backups that restore.md>)). Happy paths necessary; failure paths decisive — merge when both convince.

### What problem it solves (history)

Happy-path approvals (demo works, tests green, screenshots lovely) shipped services whose first error was also their first untested path (unmapped constraint errors, unplanned rollbacks, unproven restores — each unreviewed failure mode an incident scheduled). Failure-path review converts first-errors from incidents into handled cases (routed, mapped, drained — each verified pre-merge, each boring in production).

### Modern guidance

Per PR: name the failure modes changed (new constraint? new transaction? new backup dependency? — author lists them in the description); prove each handled (refusal test asserting the code, rollback test asserting abandonment, restore test asserting recovery — evidence per mode); approve only when failures convince equally (reviewer asks "show me it failing correctly" — the demo that matters).

### Runnable example (good — failure-path review checklist, applied)

```markdown
# PR review (failure paths): new unique constraint on slug
# - violation path: duplicate → 23505 + named constraint (test asserts code — [02/2.1] shape)
# - transaction path: multi-row backfill → wrapped, ROLLBACK tested ([02/3.1] lifecycle)
# - restore path: rollback plan = forward-fix migration (expand/contract — [04/2.2]), dumps current ([06/2.1])
# verdict: failures approved — happy path was already convincing.
```

### Common confusion

- **"failure review doubles review time"** — failure review *front-loads* incident time (minutes in review vs hours paged — same work, cheaper venue, calmer participants). Total engineering time falls (fewer incidents, faster triage when they come — mapped, drained, routed by construction). Pay in review or pay in incidents, with interest.
- **"small changes can't fail interestingly"** — small changes fail in foreign paths (one-line constraint addition locking hot tables for hours — DDL on millions of rows; one-flag change dropping maps — observability lost silently). Interesting failures hide in boring diffs — review the blast radius, not the diff size.

### Performance note

Failure-path review costs minutes per PR (modes listed, evidence linked) against incident hours per escape (diagnosis + fix + retro + trust repair). The highest-leverage review minutes available: each approved failure path is an incident that arrives handled (boring page, known remedy) instead of novel (confusing page, cold diagnosis).

### Mentor note

Pair-review failure paths with juniors explicitly ("let's list what can fail here" — before reading what succeeds): the habit forms fastest as a spoken ritual (senior models enumeration, junior internalizes the lens). Three sessions of spoken failure-listing and juniors review failure-first unprompted — the lens transfers permanently.
