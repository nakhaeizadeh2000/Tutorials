# 1.1. Capacity judgment under constraints

Sizing data layers from constraints: traffic and SLOs first, stores second, boring wins ties, capacity from numbers. Junior read: list inputs before naming stores. Expert read: where fleet arithmetic overrules per-service math, and what EXCEEDS verdicts demand next.

## 1) Constraints first, stores second

### 1) **Definition** (inputs before outputs)

Traffic shape (rps, read/write mix, growth rate), SLOs (p99 latency, RPO/RTO, availability), team size (operators per system — complexity budget), floor (managed vs self-hosted, regions) are the *inputs*; stores and topologies (Postgres/MongoDB, replicas, pools, caches) are *outputs* of the decision tree, never defaults. Name inputs in writing; derive outputs from them.

### What problem it solves (history)

Store-first systems (MongoDB-everywhere startups, Postgres-forever enterprises — defaults defended by identity rather than arithmetic: workloads mismatched for years (joins reimplemented, ceilings crashed, pools exhausted — each mismatch discovered in production, priced in incidents)) mistook familiarity for fitness (known tools assumed suitable — suitability unmeasured). Constraints-first ordering makes fitness decidable (inputs written, outputs derived — mismatches visible *before* production, in review).

### Modern guidance

Write constraints per service (traffic/SLO/team/floor — design-doc header, reviewed like code); derive stores per workload ([01/3.1](<../../../01 Database Foundations and Mental Model/sections/3. Choosing/3.1. Choosing Postgres or MongoDB.md>)'s five-questions list — questions first, stores second); revisit per growth spurt (constraints expire — traffic doubles invalidate derivations: re-derive quarterly, re-decide on evidence, never on tenure).

### Runnable example (good — fleet arithmetic overruling service math, verified locally)

```bash
node -e "
const rps = 800, holdS = 0.025;
const slots = Math.ceil(rps * holdS);
const perPool = Math.ceil(slots * 1.5);
const serverCap = 100, pools = 6;
console.log('slots:', slots, '| per-pool max:', perPool, '| fleet-total:', perPool * pools, '| server-cap:', serverCap, '| verdict:', perPool * pools <= serverCap ? 'FITS' : 'EXCEEDS - resize');"
// slots: 20 | per-pool max: 30 | fleet-total: 180 | server-cap: 100 | verdict: EXCEEDS - resize
```

Verified (local arithmetic — Little's-law slots × headroom vs server cap): per-service math says 30 (sensible alone); fleet math says 180 vs 100 cap (EXCEEDS — resize demanded: smaller pools, fewer pools per server, bigger server, or read replicas shedding load). Service-local sizing passes; fleet-global sizing governs — arithmetic at *both* levels, verdicts honest at each.

### Common confusion

- **"capacity planning is premature for startups"** — planning is *proportionate* (ten-minute arithmetic per service — slots, pools, caps written down; triggers dated — review when doubled): premature is *provisioning* (buying headroom years early — money burned), never *planning* (math done — free, clarifying). Plan early (cheap), provision on triggers (timed), never provision on vibes.
- **"managed removes capacity work"** — managed removes *provisioning* toil (instance classes, failover, patching — bought away); *sizing* stays yours (workload slots, pool counts, growth triggers — managed providers bill by size chosen: unexamined sizes billed monthly, examined sizes justified quarterly). Outsource operations, never arithmetic.

### Performance note

Capacity arithmetic costs minutes per service per quarter (slots, pools, triggers — reviewed with traffic deltas); unplanned capacity costs incidents (exhaustion pages — connection caps, disk-full, pool starvation: hours with misdirection each) plus over-provision waste (idle headroom billed monthly — money burned quietly). Minutes quarterly vs hours-plus-dollars continuously — fund the arithmetic permanently.

### Mentor note

Demand constraint headers in every data design doc ("traffic/SLO/team/floor — four lines before any store named"): two review cycles and teams derive stores instead of defaulting them (derivation visible — reviewers audit inputs, not tastes). Constraint-first thinking transfers to every architecture decision (caches, queues, services — same method, different inputs).

## 2) Boring wins ties

### 2) **Definition** (novelty budgeted, not assumed)

Between architectures meeting SLOs, choose fewest moving parts (single Postgres over Postgres+Mongo+Redis-unproven; managed over self-hosted-unstaffed; synchronous simplicity over clever async where latency budgets allow). Novelty budgeted per decision (each exotic component justified with measured need — dated, reviewed); ties broken toward boring *explicitly* (verdict recorded with the rejected alternatives named — ADRs per [track habit]).

### What problem it solves (history)

Resume-driven data architecture (sharded Mongo for thousands of rows — operational surface without workload; multi-region active-active for single-region users — consistency puzzles unsolicited; bespoke storage engines for CRUD — novelty as identity) accumulated failure modes no incident needed (each exotic piece interacting with every future piece — debuggability dividing per component, on-call fluency fragmenting per novelty). Boring-wins converts elegance from default to defendant (justify or remove — novelty on trial, simplicity presumed innocent).

### Modern guidance

Count moving parts per proposal (stores, replicas, caches, queues, coordinators — listed); challenge each with "what breaks if we delete it?" (nothing measurable → delete); spend novelty where boring demonstrably fails (measured gap — not theorized elegance: sharding on write-wall evidence, never on forecast); re-audit yearly (boring alternatives improve — managed offerings maturing, Postgres absorbing use-cases: yesterday's exotic need may be today's default feature).

### Runnable example (good — the deletion test, narrated)

```markdown
# proposal: Postgres + MongoDB + Redis + Kafka for a 500-rps CRUD service
# deletion test per component:
# - MongoDB: no document-shaped workload named → DELETE (Postgres + jsonb covers variance)
# - Kafka: no cross-service events named → DELETE (direct writes + outbox later if needed)
# - Redis: p99 reads measured 12ms vs 50ms SLO → DELETE (unneeded speed, unneeded surface)
# verdict: single Postgres, managed — boring wins 3-0, novelty budget unspent for real needs
```

### Common confusion

- **"boring means outdated"** — boring means *fewest parts meeting SLOs with margin* (Postgres 18 + managed + pools — thoroughly modern, zero exotic). Outdated means failing SLOs or drowning in toil — different axis entirely. Conflating them lets novelty pose as progress (shiny components, unmeasured needs — fashion cycles billed as engineering).
- **"budgeting novelty slows innovation"** — budgeting *directs* it (spend where boring demonstrably fails — the constraint that earns the experiment gets the experiment). Undirected novelty spends everywhere and learns nowhere (no measurement, no comparison — motion without learning). Budgets accelerate learning by forcing comparison (boring baseline vs novelty delta — experiments with controls, not vibes).

### Performance note

Boring architectures profile cleanly (fewer layers between symptom and cause — plans, counts, gates all standard); exotic stacks compound diagnostic surface (per-component failure vocabularies — triage translating across systems per incident). Boring is operational performance wearing a simplicity costume (fluency depth per incident avoided — on-call hours, the true currency).

### Mentor note

Keep a team novelty ledger (component, justification, measurement, review date — one table): additions append rows, yearly reviews prune them. Mentees proposing additions learn to argue in ledger terms (numbers, not adjectives); reviewers gain a memory longer than the quarter. Ledgers turn taste into governance without bureaucracy.

## 3) Capacity from numbers

### 3) **Definition** (budgets × traffic = resources)

Per-query budgets (p50/p99 ms per shape — measured) × traffic (rps per shape — projected) = slots, connections, sizes, headroom (derived — Little's law for concurrency, growth rates for storage, pool math for connections). Numbers sourced (measured, projected, dated — never inherited from blog posts or other companies' architectures); triggers dated (review when doubled — thresholds with calendar entries, not vibes).

### What problem it solves (history)

Vibes-based provisioning ("three replicas should do it" — for every service, every load) produced twin failures: idle over-provision (money burned quietly — unexamined headroom compounding monthly) and cliff under-provision (noon traffic collapsing midnight-sized services — the incident [5.1](<../5. Interview questions and answers/5.1. Common interview QA judgment synthesis.md>) rehearses). Arithmetic replaces vibes (slots from law, pools from slots, triggers from growth — numbers at every step, hope at none).

### Modern guidance

Size per service (budgets measured on artifacts — never on hopes: profiled p99 per shape, projected rps per route); headroom explicit (burst factor × N+1 — written in the ADR, reviewed with traffic deltas); re-size on evidence (profile deltas, traffic growth, emit changes — numbers expire, re-measure per quarter); trigger on thresholds (rows doubling, dead-ratio climbing, pool-wait rising — dated numbers firing planned responses, per the verified trigger line in part-1's probe).

### Runnable example (good — triggers dated, verified output)

```bash
# from the verified probe: review-trigger: rows > 2x last quarter OR dead-ratio > 20% OR pool-wait p99 rising
# (thresholds with teeth — each firing a planned response: re-derive capacity, tune vacuum, grow pools)
```

### Common confusion

- **"autoscaling replaces sizing"** — autoscaling reacts to thresholds sizing defines (target CPU/concurrency/latency — all derived from budgets) with scale-up latency sizing must cover (cold starts × instance count — arithmetic, not magic). Unsized autoscaling oscillates (thrashing on noise — thresholds unmoored) or lags (cold starts exceeding SLO before warm — latency unbudgeted). Size first, scale second — autoscalers execute arithmetic, they don't invent it.
- **"load tests give capacity"** — load tests *validate* arithmetic (confirm slots, find the real bottleneck — usually downstream, not compute); they don't replace it (untargeted load-testing without expected numbers produces graphs without verdicts). Predict (arithmetic), then test (confirm or learn), never test blind — expected numbers first, graphs second.

### Performance note

Capacity math costs one profiling session per service per quarter (budgets measured under representative load — [06/3.1. Observability](<../../../06 Performance Backup and Operations/sections/3. Visibility/3.1. Observability for data.md>) applied) against continuous over-provision (money) or cliff incidents (downtime). The highest-ROI arithmetic in operations: three lines preventing both tails (idle waste *and* collapse — bounded both directions by numbers).

### Mentor note

Demand the three numbers (slots, pools+headroom, triggers) in every production-readiness review — no numbers, no launch. Mentees learn capacity thinking fastest by sizing their own dev service first (small numbers, same method): predict, deploy, watch dashboards confirm. Arithmetic habit formed small transfers large.
