# 1.2. Growth planning without panic

Growing data layers deliberately: thresholds triggering planned responses, reads scaling before writes, migrations staying phased under growth pressure. Junior read: numbers trigger actions, panic triggers nothing. Expert read: where read/write scaling asymmetries live, and why phased evolution matters more (not less) as growth accelerates.

## 1) Thresholds trigger, vibes don't

### 1) **Definition** (dated numbers firing planned responses)

Growth thresholds (row-count multiples, dead ratios, pool-wait percentiles — values with dates and responses attached): crossing fires the *planned* response (re-derive capacity, tune vacuum, grow pools — calm tasks, scheduled), never panic (emergency rewrites, unmeasured scaling, flag-day migrations — adrenaline architectures). Thresholds reviewed quarterly (still the right numbers? — recalibrated per traffic, retired per architecture change).

### What problem it solves (history)

Vibes-driven scaling ("feels slow, add replicas" — unmeasured responses to unmeasured problems: over-provisioned money pits *and* under-provisioned cliffs, simultaneously possible across services: feelings scaling infrastructure in both wrong directions at once) mistook motion for management (acting visibly — scaling ceremonies, war rooms — without numbers to steer by). Thresholds convert feelings to triggers (crossed values firing planned plays — response quality independent of responder adrenaline).

### Modern guidance

Threshold the vital few (row growth, dead ratios, pool waits, cache trends — [06/3.1](<../../../06 Performance Backup and Operations/sections/3. Visibility/3.1. Observability for data.md>)'s quartet, dated); attach responses per threshold (crossed → named play: re-derive/tune/grow — planned, not improvised); review triggers quarterly (thresholds expire as architectures evolve — recalibrated or retired, never fossilized).

### Runnable example (good — the evaluator, verified locally + live counts)

```bash
node -e "
const signals = [
  { name: 'rows-qoq', value: 1.4, watch: 1.5, act: 2.0 },
  { name: 'dead-ratio', value: 0.12, watch: 0.2, act: 0.4 },
  { name: 'pool-wait-p99ms', value: 8, watch: 50, act: 200 },
];
for (const s of signals) {
  const verdict = s.value >= s.act ? 'ACT' : s.value >= s.watch ? 'WATCH' : 'ok';
  console.log(s.name + ':', s.value, '->', verdict);
}"
# rows-qoq: 1.4 -> ok
# dead-ratio: 0.12 -> ok
# pool-wait-p99ms: 8 -> ok
docker exec dbprobe psql -U postgres -tAc "SELECT count(*) FROM perf_events;"
# 50001
```

Verified (local evaluator: deterministic thresholds → verdicts; live row count 50001 anchoring the growth signal to a real table): signals evaluated mechanically (ok/watch/act — no judgment per reading, judgment per *threshold design*), growth witnessed numerically (50k rows — the table this track grew deliberately across sessions, S2→S6).

### Common confusion

- **"thresholds replace judgment"** — thresholds *trigger* judgment (crossed values paging humans *with context*: which signal, what trend, which playbook — decided response, not automated action for non-trivial crossings). Auto-remediation suits known-safe responses (vacuum runs, cache clears — bounded, reversible); judgment suits the rest (re-architecture, resharding, migration — irreversible, reviewed). Trigger mechanically, decide humanly — split, never conflated.
- **"more thresholds, more safety"** — threshold count tracks *vital* signals (growth, bloat, waits, cache — the quartet plus topology extras, per [06/3.1](<../../../06 Performance Backup and Operations/sections/3. Visibility/3.1. Observability for data.md>)); threshold sprawl desensitizes (dozens of limits, most unowned — alert fatigue muting the vital few). Thresholds budgeted like attention (finite — spent on vitals, reviewed quarterly, pruned ruthlessly).

### Performance note

Threshold evaluation costs microseconds per signal (comparisons — free); threshold *design* costs measurement sessions (distributions per signal — blip vs trend separation, per environment). Untriggered growth costs incidents (exhaustion pages — connection caps, disk-full, pool starvation: hours with misdirection each) plus over-provision waste (idle headroom billed monthly). Design once quarterly, evaluate continuously, sleep nightly.

### Mentor note

Review thresholds with mentees per quarter ("still the right numbers? — show me the trends"): mentees calibrating thresholds learn growth thinking kinesthetically (numbers *moving* toward lines — anticipation, not reaction). Panic-free growth is a skill with a curriculum (thresholds, plays, rehearsals — taught explicitly, never absorbed by osmosis).

## 2) Scale reads first, writes deliberately

### 2) **Definition** (asymmetric scaling order)

Reads scale horizontally first (replicas absorbing fan-out — routine, low-risk: read-only copies, lag-monitored, promotable); writes scale deliberately (bigger primaries, sharding, or workload splits — each evidenced, never anticipated: write scaling changes consistency/writes-paths (single-writer simplicity traded knowingly), read scaling preserves them). Order load-bearing: premature write-scaling complicates; delayed read-scaling merely slows (tolerable, reversible — asymmetry favoring reads-first always).

### What problem it solves (history)

Write-first scaling (sharded day-one clusters — cross-shard joins impossible, transactions bounded per shard, operational surface tripled — for workloads single primaries serve for years) paid distribution prices before earning distribution needs (complexity without traffic — consistency puzzles unsolicited, toil without users). Reads-first scaling defers distribution until write walls *measured* (replicas absorbing growth meanwhile — cheap, reversible, sufficient for read-heavy majorities).

### Modern guidance

Replicate reads at measured pressure (replica lag monitored — sub-second typical; stale-tolerance declared per query (session reads own writes where freshness matters — read-your-writes routing, explicit); shard writes on evidenced walls (single-primary limits reached *with numbers*: write throughput capped, hot partitions proven — sharding designed from measurements, never forecasts); split workloads before sharding stores (read/write service separation — cheaper than distributed writes, reversible unlike them).

### Runnable example (good — the scaling order, narrated with honest scope)

```markdown
# growth ladder (each rung evidenced before climbing):
# rung 1: bigger primary (vertical — simplest, first: headroom until metrics say otherwise)
# rung 2: read replicas (horizontal reads — lag-monitored, stale-tolerance declared per query)
# rung 3: workload splits (read/write services separated — cheaper than distribution)
# rung 4: sharding (write walls measured — cross-shard costs accepted explicitly, last resort)
# (ladder logic — single-primary operations witnessed all track (dbprobe); replica/shard
#  mechanics belong to platform practice + Database Design siblings — named here, detailed there)
```

### Common confusion

- **"replicas solve writes"** — replicas absorb *reads* (fan-out served — write load untouched: primaries still serialize every write — write walls persist identically under ten replicas). Write pressure needs write answers (bigger primaries, workload splits, sharding — each evidenced). Replica-for-writes is category error (read solution, write problem — mismatched axes, persistent wall).
- **"sharding is just partitioning"** — partitioning *organizes* (time/range splits within one system — pruning, archival — routine); sharding *distributes* (independent systems with cross-shard costs — joins bounded, transactions scoped, operations multiplied). Partition early (cheap, reversible); shard deliberately (evidenced, committed — point of architectural no-return, entered with numbers or not at all).

### Performance note

Reads-first scaling costs replica lag (milliseconds typical — freshness budgeted per query: stale-tolerant reads anywhere, fresh reads routed primary); writes-deliberate costs decision latency (quarters of measurement before sharding — patience priced against premature-distribution incidents). Premature sharding costs permanently (cross-shard everything — joins, transactions, operations: complexity interest compounding per feature, forever).

### Mentor note

The scaling-ladder whiteboard (four rungs, evidence per climb — "what number moves us up?"): mentees internalizing rung-order resist premature distribution permanently (forecasts don't climb ladders — measurements do). Review scaling proposals rung-by-rung ("prove rung 3 exhausted before rung 4" — evidence-gated ascent, always).

## 3) Migrations under growth stay phased

### 3) **Definition** (expand/contract at scale)

Phased evolution under growth pressure (expand additive → backfill batched → contract dated — [04/2.2](<../../../04 Node.js Data Access Drivers and Pooling/sections/2. Discipline/2.2. Migrations basis.md>)'s sequence, growth-sized): backfills batched with `LIMIT` loops (lock-friendly chunks — hot tables migrated without contention storms); contracts dated post-growth-review (old shapes retired only after readers reach zero *at current traffic* — verification scaled with load, not assumed from quiet hours).

### What problem it solves (history)

Growth-blind migrations (backfills as single UPDATEs over millions of rows — hours-long locks, replication lag spiking, deploys stalling mid-migration: maintenance windows blown by unbatched ambition; contracts enforced pre-verification (NOT NULL against NULLs at scale — validation scans locking hot tables during peak) mistook small-table manners for all-scale manners (works on thousands, wounds on millions — scale as a phase change, not a multiplier). Phased-and-batched migrations scale manners with table size (chunks bounded, locks brief, verification sampled).

### Modern guidance

Batch backfills (`LIMIT`-looped chunks with sleeps — lock footprint bounded per chunk, progress resumable per batch); verify contracts by sampling pre-enforcement (NULL counts, violation scans — enforcement only after clean sampling, at scale doubly so); date contracts post-traffic-review (readers-at-zero verified under *current* load — quiet-hour verification lies about peak behavior: verify at pressure, contract after proof).

### Runnable example (good — the batched shape, described with receipts nearby)

```sql
-- batched backfill (shape — small-table twin verified live in [04/2.2]: UPDATE 1, tracked 001):
-- UPDATE guarded_users SET tier = 'basic' WHERE tier IS NULL AND id BETWEEN $1 AND $2;
-- (chunks of 10k, sleeps between — lock footprint bounded per chunk, resumable per batch id)
```

### Common confusion

- **"online DDL removes phasing"** — concurrent index builds and friends remove *locking* (access preserved during build — genuine progress); phasing removes *incompatibility* (mixed-version readers/writers coexisting — expand/contract about *code*, not locks). Orthogonal advances (both adopted — non-locking builds *within* phased evolution: speed and compatibility composed, never substituted).
- **"growth postpones contracts"** — growth *schedules* contracts (dated, traffic-reviewed — enforcement timed deliberately); postponement *indefinite* accumulates debt (nullable columns nobody fills, dead tables nobody drops — schema archaeology billing every future reader). Date contracts (enforcement with calendar entries — debt with repayment plans, never open-ended).

### Performance note

Batched-migration cost (chunk loops + sleeps — elapsed longer, locks briefer: total time traded for contention safety — the right trade at scale, wrong trade on tiny tables where single statements finish in milliseconds); unbatched-migration cost (hours-long locks — contention storms, replication lag, deploy stalls: scale- blind manners priced in incidents). Manner matched to size (single statements small, batches large — sized per table, reviewed per migration).

### Mentor note

Rehearse phased migrations on staging-with-volume (production-shaped row counts — backfill batches timed, locks observed, contracts verified under load): mentees performing phased evolution at scale internalize growth-sized manners permanently (small-table habits explicitly re-examined per order of magnitude). Scale changes manners — rehearse per magnitude, not per theory.
