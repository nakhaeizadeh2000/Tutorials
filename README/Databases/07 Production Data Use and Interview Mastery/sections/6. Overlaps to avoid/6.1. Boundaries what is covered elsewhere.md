# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for data mastery. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the judgment-vs-mechanics split that keeps capstone knowledge in exactly one place per question.

## 1) **Mechanics in 01–06**

**Definition** — this domain judges and assembles; every technique references its owning domain and is never re-taught here. Foundations (handshakes, CRUD, choosing, gates) → [Domain 01](<../../../01 Database Foundations and Mental Model/README.md>). Postgres depth (joins, plans, constraints, transactions basis) → [Domain 02](<../../../02 Postgres Deep Dive/README.md>). MongoDB depth (pipelines, modeling, writes) → [Domain 03](<../../../03 MongoDB Deep Dive/README.md>). Access (pools, checkouts, migrations, retries) → [Domain 04](<../../../04 Node.js Data Access Drivers and Pooling/README.md>). Integrity models (ACID, levels, snapshots, distribution) → [Domain 05](<../../../05 Transactions Consistency and Integrity/README.md>). Operations (plans-at-scale, restores, containers, signals) → [Domain 06](<../../../06 Performance Backup and Operations/README.md>). Judgment questions route in one line each.

- **What problem it solves**: capstone bloat (mechanics re-derived in synthesis leaves — copies drifting at the track's summit; the longest leaves teaching the least new). Reference discipline keeps the capstone lean (links per technique — judgment per leaf; new content only where assembly creates insight). Readers navigate by need (mechanics rusty — the link names the refresher; judgment ready — the leaf delivers).
- **Modern guidance** — when a capstone question reduces to mechanics, link out in one line (never re-derive — "pairs: [02/2.1]" then continue with the judgment). When a 01–06 reader arrives here, the prerequisites (domain index §0) tell them what's assumed — no surprise dependencies. Propose mechanics corrections upstream (errors in 01–06 fixed there — never patched by local restatement, least of all here).

## 2) **Frameworks and platform**

**Definition** — this track stops at the data layer's edge deliberately: service frameworks (HTTP routing, middleware, validation — their tracks), ORMs/ODMs as products (entities, migrations runners, telemetry — ORM track), clouds and vendors (managed databases, IAM, networking, bills — platform docs). Production judgment here is *data* judgment (store-shaped trade-offs — the track's home turf); platform judgment lives on platforms.

- **Why it matters (scope)**: track sprawl (framework tutorials inside a data track — competing with dedicated tracks, losing to both; platform guides aging with vendor APIs — unmaintainable beside data stability). Clean edges learn faster (data complete here — frameworks next with mechanics assumed; platforms referenced, never re-taught). Each venue authoritative in its own track (updates land once — DRY across the repo, not just the track).
- **Modern guidance** — finish data before frameworks (this track complete — mechanics assumed downstream; framework code then reads as automation, not magic). Reference platforms, never re-teach (links to current docs — versions drift; local copies rot). Judge data questions here (store-shaped trade-offs — the track's home turf; platform trade-offs — home turf elsewhere).

## 3) **Words and careers**

**Definition** — meeting vocabulary (what to *call* these things — isolation level, bloat, backoff as professional language) → the [IT Vocabulary track](<../../../../ITVocabulary/README.md>) (naming owned there; mechanism owned here). Growth beyond data (staff engineering, system design at scale, mentoring as craft) → the mentor paths later in this repo (System Design, Mentor Capstone — named as next steps when those tracks land; see root README mentor-path order). This track graduates engineers fluent in data (hirable, promotable, on-callable); careers continue elsewhere, referenced here.

- **Why it matters (growth)**: vocabulary poverty (correct mechanics, unintelligible meetings — influence capped by language; words learned alongside, interviews and incidents both graded on clarity). Track-terminal thinking (Databases complete — learning stops; stores evolve, systems widen; graduation is commencement, not conclusion). Referenced next steps keep momentum (System Design for scale — Mentor Capstone for craft; paths named, not hidden).
- **Modern guidance** — borrow vocabulary deliberately (IT Vocabulary for review/incident phrasing — precise words make precise diagnoses). Name the next track per engineer (scale-hungry → System Design track when it lands; craft-hungry → Mentor Capstone; framework-hungry → service tracks — guidance, not gates). Keep career questions out of data reviews (promotion packets cite impact — built on these mechanics; mechanics enable, impact argues).
