# 5.1. Common interview QA: judgment and synthesis

Canonical answers for the three capstone questions every data interview asks, plus rapid-fire drills across all seven domains. Junior read: memorize the narrations. Expert read: each answer synthesizes verified receipts from 01–06 — systems, incidents, and teaching, priced and standarded throughout.

## 1) Design a reviews service, data edition

### 1) **Definition** (the systems screen)

"Design reviews for a shop: 500 rps reads, 50 rps writes, 5-year retention" — screens for constraint-first data design: hires open with inputs (traffic shape, SLOs, team — [1.1](<../1. Production judgment/1.1. Capacity judgment under constraints.md>)), choose stores per workload (reviews relational — joins with orders; counts aggregated — GROUP BY; shapes versioned — additive evolution), wire access (pools sized, checkouts bound, migrations filed), prove operations (gates green, restores rehearsed, signals watched).

### What problem it solves (hiring signal)

Systems answers reveal data judgment wholesale (constraints handled? capacity priced? failure designed? observability shipped?) — the single highest-signal interview hour available. Candidates narrating end-to-end with numbers predict production ownership; candidates reciting components predict integration tickets. The screen hires owners, not assemblers.

### Modern guidance

Answer as a walk: constraints → stores → shapes → access → integrity → operations (six domains in traversal order — the [3.1](<../3. Full-system synthesis/3.1. One write every layer.md>) narration applied to a green field). Quote receipts per choice (Little's-law slots, ESR compounds, gate stages — all verified this track); name the boring alternative rejected per exotic kept (novelty budgeted — [1.1](<../1. Production judgment/1.1. Capacity judgment under constraints.md>) part 2); close with review posture (gates-first, priced, failure-approved — [2.1](<../2. Review and design/2.1. Reviewing data code.md>)).

### Runnable example (good — the answer skeleton, filled)

```markdown
# "reviews: 500rps reads, 50rps writes, 5y retention, team of 5, PG 18 floor"
# constraints: read-heavy 10:1, p99 100ms, RPO minutes (dumps nightly + WAL), team small → boring wins
# stores: Postgres (reviews join orders/users — relational; counts via GROUP BY — server-side)
# shapes: reviews (UNIQUE(user,product) — one review each, duplicates refused 23505),
#   versioned API (additive fields, keyset pages — [2.2] contracts)
# access: pool max 8 (slots math), checkouts bound (transacted writes), migrations filed (expand/contract)
# integrity: FKs enforced, exclusion on (product, daterange) promos, read-committed + atomic increments
# ops: EXPLAIN-verified hot paths, nightly round-trip restores, 4-signal dashboard, thresholds dated
# gates: 1–6 green blocking merge; ADR records this with review date ([1.1] part 3)
```

A hire narrates this in five minutes with numbers; the interviewer hears six domains compiled into one decision. Follow-up ("reviews 100× overnight?"): capacity arithmetic re-run (slots → pools → replicas for reads; sharding only on measured write walls — [1.2](<../1. Production judgment/1.2. Growth planning without panic.md>) ladder).

### Common confusion (in candidates)

- **"starts with the framework"** — red flag: framework choice is application architecture (their tracks); data design is storage architecture (this track). Starting with Express/NestJS answers a different interview — redirect kindly ("frameworks aside — where does a review live, and how do readers find it?").
- **"one database for everything"** — yellow flag without justification: monoglot-start is *principled* (measured pain earns splits — [01/3.1](<../../../01 Database Foundations and Mental Model/sections/3. Choosing/3.1. Choosing Postgres or MongoDB.md>) part 3), not dogmatic (reviews + analytics + sessions in one store unexamined — workload questions unasked). Principled monoglot names its split triggers; dogmatic monoglot has none.

### Performance note

Design answers need numbers (slots, pools, bytes, budgets — quoted above, re-derived per scenario); ranges beat points ("50–100 slots" honest vs "exactly 73" fabricated); sources beat memory ("S4 pool probe" cited vs "I recall"). Numbers volunteered with provenance outscore numbers recited; humility about variance outscores false precision.

### Mentor note

Mock the systems question monthly (new constraints each time — traffic shapes, floors, teams varied): mentees graduate when every answer opens with inputs, prices every choice, and closes with an ADR shape — five minutes, no tooling, pure judgment. The mock doubles as architecture training (constraints-first thinking transfers to every design review).

## 2) "Writes doubled overnight" — scale it live

### 2) **Definition** (the incident screen)

"Write traffic 2× at midnight, pool waits climbing, p99 degrading — walk me through it" — screens for staged triage under pressure: hires read signals first (pool-wait p99, dead ratios, connection counts — [06/3.1](<../../../06 Performance Backup and Operations/sections/3. Visibility/3.1. Observability for data.md>)), price levers (pool growth vs server caps vs write shaping — [1.1](<../1. Production judgment/1.1. Capacity judgment under constraints.md>) arithmetic), and act reversibly (pool +2 with cap check — measured, reverted if flat; never blind doubling).

### What problem it solves (hiring signal)

Incident response is the least trainable-on-the-job skill that matters most at 3 a.m. (everyone learns eventually; the team pays tuition per incident until they do). Simulated incidents measure the pre-trained state: signals-first reading, priced levers, reversible actions — the exact behaviors correlating with short MTTR in production postmortems.

### Modern guidance

Answer in stages with narration ("pool-wait p99 first — queueing or queries? checkout histogram decides; counts second — total-max + idle-zero + queue means leak, else load; server third — caps and CPU honest?"); act smallest-reversible-first (pool +2 within cap — minutes, revertible; never max-doubling blindly — unpriced jumps risk server contention); close the loop (receipt: waits flat post-change — measured, committed; threshold updated — learned permanently).

### Runnable example (good — the staged narration, compressed)

```markdown
# "writes 2×, pool-wait p99 8→120ms, p99 latency climbing"
# stage 1 (signals): pool-wait climbing + counts below max + idle>0 → queueing from load, not leak
#   (leak signature absent: total<max — [04/4.1] distinction, applied live)
# stage 2 (levers priced): pool 8→12 within server share (cap math re-run — fits) vs query rewrite
#   (EXPLAIN shows indexed seeks — queries innocent, capacity guilty — evidence per lever)
# stage 3 (act reversibly): max 12, watch 15min → waits flat at 9ms (receipt — kept + threshold updated)
# close: ADR updated (new arithmetic), game-day scheduled for 3× (rehearsed, not hoped)
```

### Common confusion (in candidates)

- **"scale the database first"** — yellow flag as a *first* move: vertical scaling buys headroom (valid mitigation — do it in parallel where trivially available) but diagnoses nothing (unmeasured spend, unlearned lesson — the incident recurs with bigger bills). Strong candidates mitigate *and* diagnose concurrently (pool lever now, EXPLAIN during, ADR after — two tracks, stated explicitly).
- **"restart the pool"** — red flag as diagnosis: restarts clear evidence (counts reset, queues drained, wait histograms zeroed — the crime scene cleaned before forensics) and mask leaks (draining-then-refilling looks healthy for hours — recurrence scheduled). Restart to *mitigate* documented pool corruption (explicit, timestamped); never to *investigate* (evidence first — counts, histograms, traces — then restart if needed).

### Performance note

Incident answers need the receipt habit (before/after waits quoted — "120ms → 9ms, histogram attached" — falsifiable, transferable); postmortem quality predicted by staging discipline (staged responders write timelines with evidence per stage; random responders write narratives with conclusions per hunch). Hire the stagers; train the rest with game-days ([4.1](<../4. Important points to remember/4.1. Mastery checklist habits mentors insist on.md>) part 2's rehearsal).

### Mentor note

Run live-fire mocks (degraded pool, candidate screensharing, narrate-while-diagnosing): score staging (signals→levers→action order held?), reversibility (smallest change first?), receipts (measured before/after?). Graduates hold order under simulated pressure; near-misses layer-hop (coach with the game-day prescription — [4.1](<../4. Important points to remember/4.1. Mastery checklist habits mentors insist on.md>) part 2). Pressure reveals training; training removes pressure.

## 3) Teach transactions in five minutes (plus rapid-fire)

### 3) **Definition** (the mentoring screen)

"Teach me transactions — five minutes, whiteboard" — screens for compiled, transferable understanding: hires narrate lifecycle (BEGIN/COMMIT/ROLLBACK, one client — two minutes, transfer demo), levels (read-committed default + anomaly menu — two minutes, lost-update demo), and close with the boundary (models atop wired units — lifecycle first, one sentence). Five minutes, two demos, zero jargon unexplained — teaching *is* the mastery proof ([4.1](<../4. Important points to remember/4.1. Mastery checklist habits mentors insist on.md>) part 3).

### What problem it solves (hiring signal)

Senior hires teach constantly (onboarding, reviews, incidents — knowledge transfer is the job above a level); teaching skill predicts multiplier impact directly (narrators grow teams; hoarders bottleneck them). The five-minute lesson compresses pedagogy into an observable: structure (simple→deep), evidence (demos, not claims), responsiveness (questions routed, not deflected).

### Modern guidance

Teach in traversal order (lifecycle → levels → snapshots → close with boundary — the [05-chapter order](<../../../05 Transactions Consistency and Integrity/README.md>), compressed); demo per beat (transfer-conserved, lost-update 110, snapshot-read 2ms — every claim witnessed); invite interruption (questions routed to domains — "great question — that's MVCC, thirty seconds?" — responsiveness scored). Close with the one sentence that matters ("transactions wire units; levels bound interference; snapshots free readers — lifecycle first, models on evidence").

### Runnable example (good — the four-beat lesson, timed)

```markdown
# beat 1 (lifecycle, 90s): BEGIN/debit/credit/COMMIT → 70/80 conserved; unwrapped partial persists
# beat 2 (levels, 90s): dirty-blocked 100, nonrepeatable 100→50, lost-update 110 — menu priced
# beat 3 (snapshots, 60s): 2ms concurrent read, xmin/xmax stamps, 55P03 at budget — mechanisms witnessed
# beat 4 (boundary, 60s): lifecycle first, levels on evidence ([02/5.1]'s rule — judgment, not theory)
# close (60s): questions — each routed to its domain, live
```

All four demos verified across S2/S4/S5 (conservation, anomalies, snapshots, locks — this track's probe corpus). A hire teaching this cold demonstrates retention; the interviewer learns transactions *and* evaluates simultaneously — the lesson is the assessment.

### Rapid-fire drills (with answers — all seven domains)

1. **Handshake proves what?** Working-not-merely-reachable (answers, not sockets — `{"ok":1}`) ([01/1.2](<../../../01 Database Foundations and Mental Model/sections/1. Database identity and setup/1.2. Connecting from Node.md>)).
2. **Interpolation breaks on what name?** `O'Reilly` (`42601` — then bind it) ([01/2.1](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.1. First Postgres queries.md>)).
3. **INNER vs LEFT in row counts?** 1 vs 2 on demo data (loneliness kept — `bo`) ([02/1.1](<../../../02 Postgres Deep Dive/sections/1. Query depth/1.1. Joins across tables.md>)).
4. **String `_id` query misses — why?** Type-strict identity (cast `ObjectId()` at boundaries) ([01/2.2](<../../../01 Database Foundations and Mental Model/sections/2. First queries/2.2. First MongoDB operations.md>)).
5. **Checkout released mid-unit — outcome?** Poisoned borrower (bind lifecycle — try/finally) ([04/2.1](<../../../04 Node.js Data Access Drivers and Pooling/sections/2. Discipline/2.1. Checkout discipline.md>)).
6. **Estimates say 250, actual 1 — action?** ANALYZE the table (stale statistics — plan corrected without code: 250→1 witnessed) ([06/1.1](<../../../06 Performance Backup and Operations/sections/1. Performance at scale/1.1. EXPLAIN at scale.md>)).
7. **Gate exits 60 vs 61 vs 62 — meaning?** Unreceipted index / unproven restore / undocumented signals ([06/4.1](<../../../06 Performance Backup and Operations/sections/4. Important points to remember/4.1. Operations checklist habits mentors insist on.md>)).

### Common confusion (in candidates)

- **"teaching means covering everything"** — teaching means *routing* everything (four beats live, every question routed to its domain — coverage via pointers, not recitation). Completists run overtime listing levels; teachers finish early with questions answered. Brevity with pointers outscores exhaustive recitation.
- **"rapid-fire tests trivia"** — rapid-fire tests *compiled judgment* (ten seconds permits retrieval, never derivation — answers present iff the model is compiled). Trivia fails under follow-up ("why?" breaks reciters); judgment survives it (every drill above routes to a leaf with the full story). Drill, then probe — the pair separates cleanly.

### Performance note

Teaching answers need timing (four beats, five minutes — pace evidenced); rapid-fire needs instantaneity (ten seconds per drill — retrieval, not reasoning). Candidates managing the clock unprompted signal seniority more reliably than any single answer (time-awareness is the meta-skill: paced lessons, snappy drills, conversational follow-ups).

### Mentor note

The five-minute lesson is the onboarding gift every senior owes (record once, replay per hire — then live-teach quarterly to keep it sharp). Timed rapid-fire runs the quarterly health-check (seven drills, seventy seconds, team-wide gaps surfaced). Teaching infrastructure compounds: lessons recorded, drills repeated, gaps closed — mastery scaled beyond individuals.
