# 2.2. Mutations and subscriptions shaping live

## 1. Mutations sequencing (writes serializing — inputs validating — payloads returning)

**Definition** — mutation discipline: writes serialized through validated inputs returning rich payloads (writes serializing — intents ordering (effects sequencing — races declining (serializing proving — interleaving refusing); inputs validating — shapes proving (garbage declining — handlers assuming (validating funding — trusting declining); payloads returning — affected stating (errors listing — clients reconciling (returning owning — void declining).

**What problem it solves** — the mutation trio: *mutations querying* (writes reading — sides returning (effects confusing — audits blurring (querying billing — sequencing declining); *inputs trusting* (shapes hoping — garbage entering (validity bluffing — corruption arriving (trusting charging — proving declining); *payloads voiding* (results hiding — errors silencing (clients guessing — reconciliations failing (voiding billing — transparency declining). Sequenced mutations converting querying to serializing (writes ordering — inputs proving (payloads stating — races declining); reviewers finding input/payload pairs per mutation (sequencing proving → verifiable; querying → returned).

**Modern guidance** — the sequencing lines per mutation (review-enforced): *writes serializing* (intents ordering — effects sequencing (races declining — parallel conflicting-ending (serializing proving — interleaving refusing (order owning — chaos declining); *inputs validating* (shapes proving — garbage declining (handlers assuming — trusting declining (validating funding — hoping ending (checks owning — corruption preventing); *payloads returning* (affected stating — errors listing (clients reconciling — void declining (returning owning — hiding refusing (transparency funding — guessing declining).

```typescript
// GOOD: mutations sequencing — validated inputs, rich payloads, errors listed (compiled + run live).
interface PlaceInput { // inputs validating — shapes proving, trusting declining
  item: string;
  qty: number;
}
interface PlacePayload { // payloads returning — affected stating, void declining
  ok: boolean;
  id?: string;
  errors?: string[];
}
function place(input: PlaceInput): PlacePayload { // writes serializing — intents ordering, races declining
  const errors: string[] = [];
  if (input.item.length === 0) errors.push('item required');
  if (input.qty <= 0) errors.push('qty positive required');
  if (errors.length > 0) return { ok: false, errors };
  return { ok: true, id: `o-${input.item.length}-${input.qty}` };
}
const good = place({ item: 'book', qty: 2 });
const bad = place({ item: '', qty: -1 });
console.log(good.ok && good.id === 'o-4-2' && !bad.ok && bad.errors?.join(',') === 'item required,qty positive required' ? 'mutations sequence' : 'writes query');
```

**Common confusion** — *"mutations are POST endpoints (verbs equating)."* POST creating resources (subordinates adding — unsafe owning (non-idempotent proving (creating serving — replacing declining); mutations sequencing writes (intents ordering — inputs validating (payloads returning — races declining (sequencing proving — querying declining). "POST" describing transport (resources creating — HTTP serving); mutations describing writes (intents sequencing — payloads stating). Create resources (POST owning — subordinates adding); sequence mutations (writes ordering — payloads returning).

**Performance note** — sequencing economics: ordering costing serials (intents sequencing — races declining (parallel conflicting-ending — chaos declining); queried equivalents costing confusion (effects confusing — audits blurring (validity bluffing — trust eroding). Sequence cheaply (writes — serials); query never (mutations — reads).

**Mentor note** — teach "input, validate, payload" (juniors sequencing one mutation per input-pair design query-proof writes on first hearing; void mutations interrogated ("which payload?" — sequencing demanding per mutation). Sequence one write once (intents ordering — payloads returning tangible (querying ending — sequencing proving permanently). Validate inputs; state payloads — sequencing discipline in three habits, reviewed per mutation.

## 2. Subscriptions streaming (events pushing — clients listening — polls declining)

**Definition** — subscription streaming: server-pushed events filtered per client (events pushing — facts emitting (streams owning — polls declining (pushing proving — pulling ending); clients listening — interests subscribing (filters scoping — firehoses taming (listening funding — polling declining); polls declining — intervals ending (loads sparing — freshness earning (declining proving — hammering ending).

**What problem it solves** — the polling trio: *clients polling* (intervals hammering — loads wasting (freshness lagging — servers straining (polling billing — pushing declining); *firehoses streaming* (events flooding — clients drowning (filters missing — relevance declining (flooding charging — attention dying); *filters missing* (subscriptions unscoped — inboxes overflowing (relevance hoping — storms arriving (missing costing — survival bluffing). Streaming subscriptions converting polling to pushing (events emitting — clients filtering (polls ending — freshness earning); reviewers finding filter args per subscription (streaming proving → verifiable; polling → returned).

**Modern guidance** — the streaming lines per subscription (review-enforced): *events pushing* (facts emitting — streams owning (polls declining — pulling ending (pushing proving — hammering refusing (servers owning — clients waiting); *clients listening* (interests subscribing — filters scoping (firehoses taming — polling declining (listening funding — flooding ending (attention owning — drowning declining); *polls declining* (intervals ending — loads sparing (freshness earning — hammering ending (declining proving — polling refusing (push funding — pull ending). Transport streaming (sockets owning — frames funding) belongs to the future Socket.IO track — this leaf owns filter mechanics, never the transport.

```typescript
// GOOD: subscriptions streaming — filtered hub delivering matches, unsubscribing cleanly (compiled + run live).
interface Note { // events pushing — facts emitting, polls declining
  topic: string;
  seq: number;
}
class Hub { // clients listening — interests subscribing, polling declining
  private subs = new Map<number, (n: Note) => boolean>();
  private next = 0;
  subscribe(want: string, inbox: string[]): number {
    const id = this.next;
    this.next += 1;
    this.subs.set(id, (n) => { // filters scoping — firehoses taming, storms surviving
      if (n.topic === want) inbox.push(`${n.topic}#${n.seq}`);
      return true;
    });
    return id;
  }
  unsubscribe(id: number): void { this.subs.delete(id); }
  publish(n: Note): void {
    for (const f of this.subs.values()) f(n);
  }
}
const hub = new Hub();
const inbox: string[] = [];
const sub = hub.subscribe('orders', inbox);
hub.publish({ topic: 'orders', seq: 1 });
hub.publish({ topic: 'billing', seq: 2 });
hub.unsubscribe(sub);
hub.publish({ topic: 'orders', seq: 3 });
console.log(inbox.join(',') === 'orders#1' ? 'subscriptions stream' : 'clients poll');
```

"Sockets" describing transport (frames flowing — delivery funding); subscriptions describing selection (interests filtering — events pushing). Filter interests (clients scoping — firehoses taming); transport frames (sockets owning — delivery funding).

**Performance note** — streaming economics: pushing costing filters (interests scoping — firehoses taming (loads sparing — freshness earning); polled equivalents costing hammer (intervals hitting — loads wasting (servers straining — freshness lagging). Push cheaply (events — filters); poll never (intervals — hammer).

**Mentor note** — teach "subscribe with filters" (juniors scoping one interest per subscription design firehose-proof streams on first hearing; filterless subscriptions interrogated ("which topics?" — streaming demanding per subscription). Stream one interest once (events pushing — clients filtering tangible (polling ending — streaming proving permanently). Emit facts; tame firehoses — streaming discipline in three habits, reviewed per subscription.

## 3. Live shaping (filters scoping — backpressure bounding — storms surviving)

**Definition** — live shaping: bounded live queries surviving storms (filters scoping — interests bounding (firehoses taming — relevance owning (scoping proving — flooding declining); backpressure bounding — rates capping (queues shedding — producers slowing (bounding funding — overflowing declining); storms surviving — bursts absorbing (outcomes steadying — capacity budgeting (surviving owning — collapsing declining).

**What problem it solves** — the unbounded-live trio: *queries unbounding* (selections opening — streams flooding (clients drowning — servers crushing (unbounding billing — relevance declining); *backpressure missing* (rates uncapped — queues overflowing (producers flooding — consumers failing (missing charging — collapse scheduling); *storms collapsing* (bursts arriving — uniques recomputing (outcomes spiking — capacity dying (collapsing billing — survival bluffing). Shaped liveness converting flooding to bounding (filters bounding — rates capping (storms absorbing — outcomes steadying); reviewers bounding rates per live query (shaping proving → verifiable; flooding → returned).

**Modern guidance** — the shaping lines per live query (review-enforced): *filters scoping* (interests bounding — firehoses taming (relevance owning — flooding declining (scoping proving — opening refusing (bounds owning — drowning declining); *backpressure bounding* (rates capping — queues shedding (producers slowing — overflowing declining (bounding funding — missing refusing (limits owning — collapse declining); *storms surviving* (bursts absorbing — outcomes steadying (capacity budgeting — collapsing declining (surviving owning — dying preventing (absorption funding — cascade declining).

```typescript
// GOOD: live shaping — bounded streams delivering scoped subsets, overflow shed (compiled + run live).
function live(source: number[], wantEven: boolean, cap: number): { kept: number[]; shed: number } {
  const kept: number[] = []; // filters scoping — interests bounding, flooding declining
  let shed = 0;
  for (const n of source) {
    if (wantEven && n % 2 !== 0) continue;
    if (kept.length >= cap) { shed += 1; continue; } // backpressure bounding — rates capping, overflowing declining
    kept.push(n);
  }
  return { kept, shed }; // storms surviving — bursts absorbing, collapsing declining
}
const r = live([1, 2, 3, 4, 5, 6], true, 2);
console.log(r.kept.join(',') === '2,4' && r.shed === 1 ? 'live shapes' : 'streams flood');
```


**Common confusion** — *"shaping limits realtime (bounds delaying)."* Shaping bounding relevance (filters scoping — rates capping (storms surviving — outcomes steadying (bounding proving — flooding declining); limiting delaying delivery (queues buffering — latencies growing (waits funding — freshness declining (limiting charging — realtime ending). "Limiting" describing delay (queues buffering — latencies growing); shaping describing survival (filters bounding — storms absorbing). Bound relevance (filters scoping — firehoses taming); delay never (queues buffering — latencies growing).

**Performance note** — shaping economics: bounding costing filters (interests bounding — rates capping (storms surviving — outcomes steadying); flooded equivalents costing collapse (bursts arriving — capacity dying (outcomes spiking — trust eroding). Bound cheaply (filters — caps); flood never (streams — storms).

**Mentor note** — teach "filter, cap, shed" (juniors shaping one live query per bound design flood-proof streams on first hearing; unbounded subscriptions interrogated ("which cap?" — shaping demanding per stream). Shape one stream once (filters scoping — rates capping tangible (flooding ending — shaping proving permanently). Scope interests; shed overflow — shaping discipline in three habits, reviewed per stream.
