# 4.1. gRPC checklist mentors insist on

## 1. Every contract protoing (services stating — messages typing — fields numbering)

**Definition** — the proto gate: each service stated, message typed, field numbered (services stating — methods declaring (streams marking — deadlines bounding-later (stating proving — guessing ending); messages typing — fields numbering (types owning — meanings holding (typing funding — any declining); fields numbering — tags assigning (wire ordering — evolution enabling (numbering proving — naming declining).

**What problem it solves** — the unprotoed trio: *services guessing* (methods unmapped — contracts unowned (implementations assuming — behaviors bluffing (guessing billing — owning declining); *messages anying* (values untyped — numbers floating (precision missing — overflows scheduling (anying charging — safety declining); *numbers reusing* (tags recycling — meanings colliding (old reading-new — corruption arriving (reusing billing — compatibility breaking). The gate converting guessing to stating (services declaring — messages typing (fields numbering — evolution enabling); mentors asking one question per service ("which proto?" — protoing demanding per RPC).

**Modern guidance** — the gate commands (run per service, enforced in review):

```typescript
// GOOD: contracts gated — services stating, messages typing, fields numbering (checklist shape).
// 1. Service proof (methods declaring — streams marking):
//    every RPC in IDL — unary defaulting, streams justifying, deadlines bounding-later.
// 2. Message proof (fields numbering — types owning):
//    every message typed with numbered fields — any declining, meanings holding.
// 3. Number proof (tags assigning — wire ordering):
//    removals reserved, numbers never reused — breaks declining, callers serving.
// State services; type messages; number fields.)
```

```typescript
// BAD: contracts unprotoed — services guessing, numbers reusing (real unprotoed shape).
// // "JSON over POST, trust us." (shapes hoping — clients discovering — trust eroding).
// // Recycled tags (meanings colliding — corruption arriving). State protos; type messages; reserve numbers.)
```

**Common confusion** — *"gates slow proto work (process throttling)."* Gates preventing drift (services stating — messages typing (evolution enabling — incidents preventing (preventing funding — throttling declining); missing gates slowing debugging (shapes hoping — numbers missing (clients discovering — support ticketing (missing charging — writing declining). "Throttling" describing ceremony (approvals queuing — value missing); gates describing leverage (proof reusing — drift preventing). Gate contracts (services stating — fields numbering); ship faster (evolution enabling — incidents preventing).

**Performance note** — proto economics: stating costing IDL lines (services declaring — messages typing (evolution enabling — incidents preventing); guessed equivalents costing discovery (shapes hoping — clients discovering (trust eroding — support ticketing). State cheaply (protos — services); guess never (JSON — conventions).

**Mentor note** — demand "proto link in the PR" (juniors stating one service per proto design guess-proof contracts on first hearing; protoless services interrogated ("which IDL?" — protoing demanding per service). State one service once (methods declaring — fields numbering tangible (guessing ending — stating proving permanently). Declare methods; number tags — protoing discipline in three habits, reviewed per service.

## 2. Every call bounding (shapes choosing — deadlines stating — errors mapping)

**Definition** — the bounding gate: each call choosing shapes, stating deadlines, mapping errors (shapes choosing — latencies weighing (complexities pricing — needs matching (choosing proving — defaulting declining); deadlines stating — times bounding (chains propagating — waits limiting (stating funding — hanging ending); errors mapping — statuses classifying (trailers carrying — clients branching (mapping proving — defaulting declining).

**What problem it solves** — the unbounding trio: *shapes defaulting* (bidi assuming — states owning (complexity hiding — simplicity missing (defaulting billing — matching declining); *deadlines missing* (budgets unstated — waits hanging (limits absenting — liveness bluffing (missing costing — reliability declining); *errors defaulting* (UNKNOWN answering — kinds blurring (semantics missing — handling guessing (defaulting charging — classifying declining). The gate converting defaulting to bounding (shapes matching — deadlines numbering (errors classifying — hangs declining); mentors asking one question per call ("which shape, which budget?" — bounding demanding per RPC).

**Modern guidance** — the gate commands (run per call, enforced in review):

```typescript
// GOOD: calls gated — shapes choosing, deadlines stating, errors mapping (checklist shape).
// 1. Shape proof (latencies weighing — complexities pricing):
//    every RPC on its shape — unary defaulting, streams justifying, needs matching.
// 2. Deadline proof (times bounding — chains propagating):
//    every call carrying a deadline — waits limiting, hangs declining, cascades preventing.
// 3. Error proof (statuses classifying — trailers carrying):
//    every failure mapped to codes — clients branching, retries judging, guesses ending.
// Choose shapes; state deadlines; map errors.)
```

```typescript
// BAD: calls unbounding — shapes defaulting, deadlines missing (real unbound shape).
// // Bidi everywhere (states owning — debugs multiplying — simplicity missing).
// // No deadlines (waits hanging — resources pinning). Choose per need; bound waits; classify failures.)
```

**Common confusion** — *"gates over-engineer RPCs (checks bureaucratizing)."* Gates evidencing discipline (shapes choosing — deadlines stating (proof reusing — judgment focusing (evidencing funding — slowing declining); bureaucratizing padding ceremony (forms multiplying — value missing (swaps unnamed — comprehension taxing (padding charging — judgment absenting). "Bureaucratizing" describing ceremony (forms multiplying — value missing); gates describing evidence (discipline proving — trust earning). Evidence discipline (shapes choosing — deadlines stating); pad never (forms multiplying — value missing).

**Performance note** — bounding economics: choosing costing decisions (latencies weighing — complexities pricing (needs matching — defaulting declining); defaulted equivalents costing states (channels opening — debugs multiplying (simplicity missing — maintenance growing). Choose cheaply (shapes — needs); default never (bidi — cases).

**Mentor note** — demand "shape, budget, code per call" (juniors bounding one call per triple design default-proof RPCs on first hearing; unbound calls interrogated ("which deadline?" — bounding demanding per RPC). Bound one call once (shapes choosing — deadlines stating tangible (defaulting ending — bounding proving permanently). Match shapes; map codes — bounding discipline in three habits, reviewed per call.

## 3. Every stream backpressuring (rates capping — consumers keeping — storms surviving)

**Definition** — the backpressure gate: each stream capping rates, keeping consumers, surviving storms (rates capping — flows limiting (producers slowing — overflow declining (capping proving — flooding declining); consumers keeping — readers pacing (buffers draining — lags bounding (keeping funding — dropping declining); storms surviving — bursts absorbing (outcomes steadying — capacity budgeting (surviving owning — collapsing declining).

**What problem it solves** — the unpressured trio: *streams flooding* (rates uncapped — consumers drowning (servers crushing — clients buffering (flooding billing — relevance declining); *consumers dropping* (readers lagging — buffers overflowing (messages losing — completeness bluffing (dropping charging — keeping declining); *storms collapsing* (bursts arriving — capacity dying (outcomes spiking — trust eroding (collapsing billing — survival bluffing). The gate converting flooding to capping (rates limiting — consumers pacing (storms absorbing — outcomes steadying); mentors asking one question per stream ("which cap?" — pressuring demanding per flow).

**Modern guidance** — the gate commands (run per stream, enforced in review):

```typescript
// GOOD: streams gated — rates capping, consumers keeping, storms surviving (checklist shape).
// 1. Rate proof (flows limiting — producers slowing):
//    every stream capped — overflow shedding, floods declining, relevance owning.
// 2. Consumer proof (readers pacing — buffers draining):
//    consumers keeping up or shedding explicitly — lags bounding, drops owning, silent loss declining.
// 3. Storm proof (bursts absorbing — outcomes steadying):
//    bursts budgeted — capacity planning, collapses declining, survival proving.
// Cap rates; keep consumers; survive storms.)
```

```typescript
// BAD: streams unpressuring — rates uncapping, consumers dropping (real unpressured shape).
// subscribe('*'); // rates uncapped — consumers drowning, servers crushing.
// // Slow readers (buffers overflowing — messages losing). Cap flows; pace readers; budget bursts.)
```

**Common confusion** — *"gates throttle throughput (caps limiting)."* Gates bounding abuse (rates capping — consumers keeping (storms surviving — outcomes steadying (bounding funding — flooding declining); throttling capping value (flows limiting — users waiting (waits funding — freshness declining (throttling charging — performance declining). "Throttling" describing caps (flows limiting — users waiting); gates describing survival (rates bounding — storms absorbing). Bound abuse (rates capping — consumers keeping); throttle never (flows limiting — users waiting).

**Performance note** — pressuring economics: capping costing bounds (flows limiting — consumers pacing (storms surviving — outcomes steadying); flooded equivalents costing collapse (bursts arriving — capacity dying (outcomes spiking — trust eroding). Cap cheaply (bounds — rates); flood never (streams — storms).

**Mentor note** — demand "cap per stream" (juniors capping one rate per flow design flood-proof streams on first hearing; uncapped streams interrogated ("which bound?" — pressuring demanding per flow). Cap one stream once (rates limiting — consumers pacing tangible (flooding ending — pressuring proving permanently). Limit flows; pace readers — pressuring discipline in three habits, reviewed per stream.
