## 3.1. Reflog: the seatbelt under everything

### 1) **Reflog remembers every move**

**Definition** — the reflog is a local journal of where your `HEAD` and branch tips *pointed*: every commit, amend, reset, rebase, merge, and checkout appends an entry (`HEAD@{n}`) with the action that moved it. Verified shape on Git 2.53.0: after resets, reverts, and amends, `git reflog` reads `16e80b4 HEAD@{0}: reset: moving to HEAD / 16e80b4 HEAD@{1}: reset: moving to HEAD~1 / daed2b7 HEAD@{2}: revert: Revert "B amended" / 16e80b4 HEAD@{3}: commit (amend): B amended / 5e3a9cd HEAD@{4}: commit: B` — the full movement history including the orphaned pre-amend hash. Entries expire after 90 days by default (`gc.reflogExpire`) and never leave your machine (never fetched, never pushed).

- **What problem it solves**: every destructive operation in this domain — `--hard` resets, rebases, amended-away tips, deleted branches — moves pointers, and moved-from positions are otherwise unrecoverable (no branch, no tag, `log --all` finds nothing). The reflog keeps the old positions: recovery is one command away for three months. Without it, "deleted branch" means "deleted work"; with it, deletion means "unlabelled, still reachable via the journal."
- **Modern guidance** — reach for `git reflog` first in every "it's gone" moment: deleted branch, bad reset, aborted-then-regretted rebase, amended-away commit. Read the action column (`commit:`, `reset: moving to`, `rebase finished:`, `checkout: moving from`) to find the movement that lost your work — the hash on *its* line is your recovery target. Never `gc --prune` a repo you're actively rescuing from (expiry is what finally deletes orphans; don't hurry it).

```bash
# GOOD: the journal answers "where was it?" — verified entries
git reflog
#  16e80b4 HEAD@{0}: reset: moving to HEAD
#  16e80b4 HEAD@{1}: reset: moving to HEAD~1
#  daed2b7 HEAD@{2}: revert: Revert "B amended"
#  16e80b4 HEAD@{3}: commit (amend): B amended     (orphaned tip — still listed)
#  5e3a9cd HEAD@{4}: commit: B                    (pre-amend hash — still listed)
# BAD: `git gc --prune=now` during a rescue "to clean up" —
# expiry is the only thing that deletes orphans; pruning mid-rescue deletes the patient
```

### 2) **Recover by naming the lost tip**

**Definition** — recovery is re-labeling: `git branch <rescue-name> <hash-from-reflog>` (or `git reset --hard <hash>` if the current branch *is* the right home) re-attaches a label to the orphaned commit, making it reachable again. Verified end-to-end: after deleting branch `doomed` holding `641ca87 DOOMED valuable work`, `git log --all --oneline | grep DOOMED` returns **0** (unreachable from every ref) — yet `git branch rescued 641ca87` succeeds, and `git log rescued --oneline` shows `641ca87 DOOMED valuable work` on top. Deletion removed the label; the journal kept the position; re-labeling restored the work.

- **Why it matters (correctness)**: panic is the destructive part of data loss — the `--hard` reset to "fix" a bad reset, the re-clone that wipes the reflog along with the repo (Domain 04 §2.1: re-cloning destroys rescue history). The recovery procedure is three calm steps: `reflog` (find the hash), re-label (branch or reset `--hard` to it — the tree is safe to overwrite *now* because the target is known-good), verify (`log`, `status`, tests). Nothing is urgent for 90 days; haste is the only expiry that matters.
- **Modern guidance** — prefer a rescue *branch* over resetting the current line (branching can't destroy; resetting can — leaf 1.1's area rules apply mid-rescue too). Verify recovered work before deleting the rescue branch (diff against expectations, run the tests). After recovery, keep the story honest: if the loss affected shared lines, say so in the standup — "recovered via reflog, no shared history touched" closes incidents faster than silence.

```bash
# GOOD: calm recovery — journal, re-label, verify — verified
git branch -D doomed                    # Deleted branch doomed (was 641ca87). — label gone
git log --all --oneline | grep DOOMED   # 0 matches — unreachable from every ref
git reflog | head -n 3
#  7357274 HEAD@{0}: checkout: moving from doomed to main
#  641ca87 HEAD@{1}: commit: DOOMED valuable work   (the lost position — journal kept it)
git branch rescued 641ca87
git log rescued --oneline | head -n 2   # 641ca87 DOOMED valuable work — restored
# BAD: re-cloning "to fix" a lost branch — the fresh clone has no reflog,
# so the rescue history dies with the old directory
```

### 3) **Reflog is local and finite**

**Definition** — two boundaries that define when the seatbelt works: *local* (reflog lives in `.git/logs/`, never transferred — clones start empty, pushes send nothing) and *finite* (entries expire: 90 days for reachable tips, 30 for unreachable ones by default; `git gc` eventually deletes expired orphans). Recovery works on the machine where the movement happened, within the window. After expiry, orphaned objects are garbage-collected and truly gone.

- **Why it hurts when missing (correctness, maintainability)**: the engineers who lose work permanently fall into exactly these two gaps — "I deleted the branch on my laptop, can you recover it from the server?" (no: the server never had your reflog) or "that was six months ago" (expired, collected). Both are predictable: the seatbelt covers local mistakes promptly, not remote archaeology eventually. For the gaps, the protections are different tools — pushed branches (server keeps refs, not reflogs), tags for milestones, backups for machines (Domain 07 touches policy; the habit is yours).
- **Modern guidance** — internalize the coverage map: lost it here, recently → reflog (this leaf). Lost it here, long ago → check remote refs and tags first, reflog second (expiry may have taken it). Lost it elsewhere → the other machine's reflog, or the pushed refs. And the meta-habit that widens every window: push private branches early (even WIP) — a pushed ref survives laptop loss, expiry, and `gc` alike. The reflog is the seatbelt; pushed refs are the insurance.

```bash
# GOOD: know the coverage before you need it
git log --all --oneline | grep -c .     # reachable universe — reflog can restore the rest (recently, locally)
git branch -r --contains <sha>          # did it ever reach the server? (pushed refs outlive reflog)
# BAD: assuming the forge, a teammate's clone, or a six-month-old laptop directory
# holds your reflog — local and finite means local and finite
```

### 4) **Common confusion**

- "Reflog shows all commits" — it shows *movements* (pointer positions over time), not commits. A commit never checked out, reset to, or rebased appears only via its own `commit:` entry on the branch that created it — and `log --all` already covers reachable ones. Reflog's value is the *unreachable* positions.
- "`log --all` replaces reflog" — `--all` covers all *labels*; reflog covers *former* label positions. The verified rescue proves the gap: count 0 in `log --all`, present in reflog.
- "Expired reflog entries are archived somewhere" — expiry plus `gc` deletes the objects. No archive, no trash bin. The 90/30-day windows are generous but real.
- "Reflog works on bare/server repos the same way" — servers record pushes in reflogs too (if enabled), but you can't rely on another machine's journal. Push refs, not hope.

### 5) **Performance note**

Reflog appends one line per HEAD movement — bytes, never a bottleneck at any repo size. `git reflog` reads a local text file (instant); expiry runs inside routine `gc` (amortized). The cost that matters is *attention*: engineers who don't know the journal exists pay re-implementation hours for recoverable losses. This leaf is the cheapest insurance in the track — one command to learn, three months of coverage per use.

### 6) **Mentor note**

Run the verified rescue as a live drill for every junior: create `doomed`, delete it, show `log --all` count 0 (let the panic register), then `reflog`, re-label, verify. The emotional arc — loss, proof-of-loss, recovery — teaches faster than any diagram, and graduates never re-clone in panic again. Follow with the boundary quiz: "teammate's laptop died with unpushed work?" (their reflog died with it — push early is the lesson); "branch deleted last year?" (expired — tags and pushes are the lesson). Watch for the gc-pruner ("cleaning up" during incidents — fix by banning `gc --prune` outside maintenance windows) and the reflog-denier ("Git lost my work" without ever running `reflog` — fix with the three calm steps). Review check: every incident report mentions the reflog step explicitly, even when the answer was "checked, not there" — the check is the habit.
