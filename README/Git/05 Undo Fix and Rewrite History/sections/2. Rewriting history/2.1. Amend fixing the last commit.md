## 2.1. Amend: fixing the last commit

### 1) **Amend replaces the tip**

**Definition** — `git commit --amend` folds staged changes into `HEAD` (and/or rewrites its message), producing a *replacement* commit: same position in the line, new hash, old tip orphaned. Verified on Git 2.53.0: amending `B` (`5e3a9cd`) yields `B amended` (`16e80b4`) — the subject changed, the hash changed with it, the parent (`A`) didn't move. Three uses, all tip-scoped: fix the message, add the forgotten file, fold the just-staged hunk that belongs with the tip.

- **What problem it solves**: without amend, every tip fix costs a second commit — "fix typo," "actually add the file," "oops the message" — and private-branch history fills with noise that reviewers must read around (Domain 02 §1.2: messages are contracts; noise is breach). Amend keeps the unit atomic *after the fact*: the tip becomes what it should have been, and review reads one clean commit instead of a commit plus its apologies.
- **Modern guidance** — amend freely while the commit is private (unpushed, or pushed only to your own PR branch). Stage first, then `--amend` (optionally `--no-edit` to keep the message when only adding files). Never amend to smuggle unrelated work into an old commit — the tip should become what it *should have been*, not what is merely convenient. Message-only fixes need no staging at all.

```bash
# GOOD: the tip becomes what it should have been — verified hash replacement
git log --oneline -2   # 5e3a9cd B / 1793b36 A
git add forgotten.txt
git commit --amend -m "B amended"
git log --oneline -2   # 16e80b4 B amended / 1793b36 A (same position, new hash 5e3a9cd -> 16e80b4)
# BAD: "fix typo in B" as a second commit on a private branch —
# reviewers read two commits where one clean tip would do (noise, not history)
```

### 2) **Amended commits are new commits**

**Definition** — amend doesn't edit — it *replaces*: the old tip object remains in the store (reachable via reflog, leaf 3.1) but nothing points at it anymore. Consequences follow from replacement, not editing: any branch, tag, or teammate referencing the old hash now references an abandoned object; the new tip needs pushing as if new (because it is). On private lines this is bookkeeping; on shared lines it is breakage — the same rule as rebase (next leaf), because amend *is* a one-commit rebase.

- **Why it matters (correctness)**: the "just a small amend" framing kills shared lines — a teammate who pulled `5e3a9cd` and then fetches your amended `16e80b4` holds both, and their next push is refused (diverged mirrors of the "same" commit). The fix (their rebase onto your tip) is easy but mandatory for *every* holder, scaling pain with collaborators. Replacement semantics make the rule obvious once stated: you didn't change a commit, you orphaned one and published another.
- **Modern guidance** — ask "who else has this hash?" before every amend: nobody (unpushed) → amend freely; only my PR reviewers (pushed to my branch) → amend, then `--force-with-lease` (next section's spelling); anyone else (main, shared, tagged) → don't amend — `revert` (leaf 1.2) or a follow-up commit. When in doubt, `git status -sb` plus `branch -r --contains <sha>` answers "who else" mechanically instead of by memory.

```bash
# GOOD: replacement-aware amend — check visibility first
git branch -r --contains HEAD   # anyone else holding this tip? (empty on private lines)
git commit --amend -m "feat(cart): reject negative quantities"
git push --force-with-lease     # PR branch only — lease refuses if a reviewer pushed meanwhile
# BAD: amending a commit already merged to main and force-pushing —
# replacement orphans every copy downstream; the "small fix" breaks the whole team
```

### 3) **After amend comes lease-push**

**Definition** — pushing a replaced tip is necessarily non-fast-forward (the remote holds the orphaned hash), so the push needs `--force-with-lease`: overwrite *only if* the remote tip is exactly what you last fetched. The lease is a compare-and-swap on the remote ref — if a teammate pushed meanwhile, the lease fails and your overwrite is refused. Bare `--force` skips the check: it overwrites whatever is there, seen or unseen.

- **Why it hurts when missing (correctness, maintainability)**: bare `--force` on a PR branch discards reviewers' pushes (their fixup commits, their rebase resolutions) silently — the exact data loss the lease exists to prevent. The failure mode is invisible: your push succeeds, their commits vanish from the line, and discovery waits until someone asks "where did my commit go?" The lease converts that silence into a refusal plus a re-read — fetch, inspect their addition, re-apply yours on top.
- **Modern guidance** — make `--force-with-lease` the only force spelling in your fingers (alias it if needed; never alias bare `--force`). After amending a pushed PR branch: fetch first (is the lease still valid?), lease-push, confirm CI re-runs. If the lease refuses, someone moved — read their change before replaying yours over it. Teams serious about this enforce it server-side (protected branches + "require linear history" + dismissed-stale-reviews, Domain 06/07) so no one's fingers decide alone.

```bash
# GOOD: the only force spelling — compare-and-swap, not overwrite
git push --force-with-lease origin feat/x
#  + ea9f556...c671bf6 feat/x -> feat/x (forced update, lease held — remote was as fetched)
#  lease refused? → fetch, read their push, replay yours on top, lease-push again
# BAD: `git push --force` on anything — skips the check, discards unseen commits silently
```

### 4) **Common confusion**

- "Amend edits history in place" — replacement, not editing: new object, orphaned old tip, reflog entry (leaf 3.1) pointing at the orphan. The DAG never mutates — pointers just move.
- "Amending before push is always safe" — safe *for others* (nobody holds the hash), but the orphan still exists locally until gc. Safety here means no collaborator impact, not no trace.
- "`--force-with-lease` without arguments is vague" — the lease defaults to the upstream tracking ref (leaf: Domain 04 §1.2's pairing) — it checks exactly the line you're pushing to. Explicit `--force-with-lease=<ref>:<expected-sha>` exists for scripts; humans use the bare form.
- "Two amends need two force-pushes" — amend as many times as you like locally; push once when the tip is right. The lease covers the final replacement, not each draft.

### 5) **Performance note**

Amend costs one commit object (same as any commit) plus orphaning one — negligible at every scale. Lease-push costs one fetch-equivalent check server-side — same round trip as a normal push. The performance that matters is review latency: amended-then-lease-pushed PRs re-run CI per push, so batch your tip fixes (message + files + hunks in one amend) instead of amend-push-amend-push churning the pipeline.

### 6) **Mentor note**

Drill replacement semantics until "amend = orphan + publish" is reflex: amend in scratch, show both hashes in reflog, recover the orphan (leaf 3.1 preview). Then stage the shared-line accident in a paired scratch (two clones, one amends-and-force-pushes main) and have the other clone diagnose the divergence — reading `status -sb` and choosing rebase-over-recovery. That ten-minute exercise does more for golden-rule internalization than any warning paragraph. Watch for the amend-everything reflex (rewriting shared tips for cosmetics — fix with "who else has this hash?") and the force-without-lease muscle memory (fix by removing bare `--force` from aliases and history). Review check: amends only on private tips, lease-only pushes, bodies explaining *why* on the final message.
