## 2.2. Rebase and cherry-pick: replaying commits

### 1) **Rebase replays onto a new base**

**Definition** — `git rebase <new-base>` takes your branch's commits (those not reachable from the new base), resets your line to the base, then re-applies each commit in turn — new hashes, same diffs, linear result. Verified on Git 2.53.0: rebasing a two-commit line already sitting on its base prints `Successfully rebased and updated refs/heads/oldfeat.` with the line reading `F2 / F1 / A` — and rebasing a branch with nothing to replay prints `Current branch feat/sync-demo is up to date.` (`rc=0`): Git says so instead of manufacturing empty commits.

- **What problem it solves**: diverged private lines otherwise join with noise — a two-commit feature rebased-merge style produces a merge commit recording a "collaboration" between you and yourself three hours apart. Replay keeps private history linear: your commits float onto the fresh base as if written there, review reads a straight line, and `bisect` steps through causes instead of joins. The base moves daily (Domain 04 §3.1); replay is how private lines track it without accumulating self-merges.
- **Modern guidance** — rebase private lines only (unpushed, or pushed solely to your own PR branch — Domain 04 §3.1's rule). Fetch first, `rebase origin/main` (or `upstream/main`), resolve any conflicts per-commit (each replayed commit may stop once — `add`, then `continue`; `--abort` restores the pre-rebase line whenever doubt wins), then `--force-with-lease` to your PR branch. Never rebase lines others pulled — their copies reference pre-replay hashes, and every holder pays recovery costs (leaf 2.1's replacement semantics, scaled to N commits).

```bash
# GOOD: private line floats onto the fresh base — verified
git fetch --all
git switch feat/guest-checkout
git rebase origin/main
#  Successfully rebased and updated refs/heads/feat/guest-checkout.
git push --force-with-lease   # PR branch only — lease checks, bare force doesn't
# BAD: rebasing `main` (or any line teammates pulled) "for a clean log" —
# every holder's copy now references orphaned hashes; cleanliness for you, breakage for all
```

### 2) **Interactive rebase edits the story**

**Definition** — `git rebase -i <base>` opens your line's commits as an editable script — `pick`, `reword` (message), `squash`/`fixup` (fold into previous), `drop`, `reorder` — and replays per your edits. Verified non-interactively with `GIT_SEQUENCE_EDITOR=true git rebase -i <base>`: `Successfully rebased and updated refs/heads/oldfeat.` — the machinery runs headless; the editor is just the script's author. This is private-branch cleanup before review: ten "wip" commits become three atomic ones with contract-grade messages (Domain 02 §1.1–1.2).

- **Why it matters (correctness)**: review quality tracks commit quality — reviewers reading "wip," "fix," "actually fix," "FINAL fix" must reconstruct intent the author already had and discarded. Interactive rebase moves that reconstruction to where it's cheapest (the author's machine, pre-review): squash the apologies, reword the vague, drop the dead ends, order the story so each commit builds on the last. The published line then reads as argument, not diary.
- **Modern guidance** — rewrite only unmerged private history (same golden rule — interactive or not, replay is replay). Common script shapes: `fixup` for "oops" commits (message discarded), `squash` for combining with message merge (edit the combined message), `reword` for contract-grade subjects, `drop` for debug scaffolding. Keep the result atomic: each surviving commit builds and passes tests alone (`exec` lines can enforce per-commit CI). After rewriting a pushed PR branch: lease-push, and note that every rewrite dismisses prior approvals (configure "dismiss stale reviews" — Domain 07) — which is correct, since the reviewed code no longer exists.

```bash
# GOOD: diary becomes argument — squash the apologies, reword the vague
git rebase -i origin/main
#  pick a1b2c3 feat(cart): guest checkout core
#  fixup d4e5f6 oops missing guard      (message discarded into previous)
#  reword g7h8i9 stuff                 (rewrite subject to contract grade)
#  drop j0k1l2 debug scaffolding       (never belonged in review)
# BAD: interactive-rebasing a merged line to "clean up history" —
# the commits are already ancestors everywhere; replay orphans every downstream copy
```

### 3) **Cherry-pick plucks single commits**

**Definition** — `git cherry-pick <sha>` replays exactly one commit onto your current line — new hash (different parents), same diff. Verified: picking `HOTFIX rate limit` onto `main` prints `[main 7357274] HOTFIX rate limit` — the change lands without its original line. And the honest edge, also verified: picking a change already present yields `The previous cherry-pick is now empty, possibly due to conflict resolution` — Git detects the no-op instead of duplicating it (commit with `--allow-empty` only if the empty marker itself carries meaning).

- **Why it hurts when missing (correctness, maintainability)**: without cherry-pick, urgent single fixes travel with their whole line — hotfixing production means merging a feature branch (with unfinished work) or hand-copying diffs (losing authorship, message, and traceability). Cherry-pick moves the *commit* — author, message, and diff intact — onto release lines (Domain 06), backports, or a colleague's branch, with the new hash recording the new context. The uses that justify it: hotfixes, backports to supported releases, rescuing one good commit from an abandoned line.
- **Modern guidance** — cherry-pick sparingly and traceably: one commit, one reason, with `-x` (appends `(cherry picked from commit <sha>)` to the message) when crossing repositories or long-lived lines so future archaeologists (Domain 02 §2.2) can find the original. Prefer merging whole lines when the line is the unit (features → PRs, Domain 04); prefer cherry-pick when the *commit* is the unit (hotfix → release). After picking, verify the surrounding line still builds — the commit was tested in its original context, not this one.

```bash
# GOOD: one commit, new context, traceable — verified
git switch main
git cherry-pick -x <hotfix-sha>
#  [main 7357274] HOTFIX rate limit   (new hash; message records origin with -x)
#  empty result? → "The previous cherry-pick is now empty" — already present, no duplicate made
# BAD: cherry-picking whole features commit-by-commit instead of merging the line —
# N replays where one join belongs (loses the join metadata reviewers and reverts need)
```

### 4) **Common confusion**

- "Rebase is just merge with cleaner output" — different contracts: merge preserves both histories (join metadata, revertible as a unit — leaf 1.2), rebase rewrites yours (linearity at the cost of new hashes). "Cleaner" describes private lines; on public lines it's destructive.
- "Interactive rebase can fix shared history safely" — interactivity changes the *script*, not the visibility rule. Rewording a shared commit still orphans every copy. The golden rule doesn't grade on interactivity.
- "Cherry-pick duplicates code" — it duplicates *commits* (new hashes, same diff) across lines by design; the duplication is tracked (hashes differ, `-x` records origin) and each copy evolves independently. Duplicated *uncommitted* code is the smell; cherry-picked commits are the procedure.
- "Aborted rebase loses my commits" — `--abort` restores the pre-rebase line exactly (original hashes, reflog entry to prove it — leaf 3.1). Replay either completes or never happened.

### 5) **Performance note**

Replay cost scales with commits × conflicting hunks — trivial for weekly private lines (seconds), painful for quarterly ones (hours of per-commit conflict resolution — another argument for short-lived branches, Domain 03 §1.2). Interactive scripts add editor latency, not compute. Cherry-pick is one commit — constant cost. The real budget is CI: every lease-push after replay re-runs the pipeline, so batch replay + amend + push into one verification cycle instead of three.

### 6) **Mentor note**

Teach replay with the DAG visible: draw base, old tip, and replayed tip as three labels, then run `rebase` in scratch and watch the old hashes orphan (reflog proves it — leaf 3.1 preview). Have every junior resolve one per-commit conflict during replay (`add` + `continue`) and abort one deliberately — the two halves of replay confidence. Watch for the public-rebaser (replays shared lines for aesthetics — fix with "who else has these hashes?") and the cherry-pick-everything reflex (N picks where one merge belongs — fix with "is the commit the unit or is the line?"). Review check: rebases only on private lines, interactive scripts leave atomic contract-grade commits, cherry-picks carry `-x` across lines, lease-only pushes after every replay.
