## 1.2. Revert: the public undo

### 1) **Revert adds, never removes**

**Definition** — `git revert <commit>` creates a *new* commit whose diff is the inverse of the target — the old commit stays in history, everyone's copies keep working, the effect is undone. Verified on Git 2.53.0: reverting the tip produces `[main daed2b7] Revert "B amended"` and `git log --oneline` reads `daed2b7 Revert "B amended" / 16e80b4 B amended / 1793b36 A` — three commits, net effect of the middle one cancelled, no hash rewritten.

- **What problem it solves**: shared history is a contract — teammates' branches, tags, CI, and deploys reference commits by hash. Removing a commit (`reset`, `rebase`) breaks every reference downstream of it; everyone's next fetch sprouts duplicates or refusals. Revert keeps the contract append-only: the mistake and its correction are both visible, `blame` tells the true story ("added here, reverted there, re-landed later"), and no colleague's copy ever disagrees with yours about what exists.
- **Modern guidance** — default to revert for every commit that left your machine (pushed, merged, pulled by anyone). Name reverts well: the default `Revert "<subject>"` plus a body line explaining *why* (link the incident). When the reverted work must return later, `revert` the revert — history stays honest instead of pretending the first revert never happened.

```bash
# GOOD: public mistake, public correction — append-only, verified
git revert --no-edit HEAD
#  [main daed2b7] Revert "B amended"
git log --oneline   # daed2b7 Revert "B amended" / 16e80b4 B amended / 1793b36 A
# BAD: `git reset --hard HEAD~1` + force-push to "remove" a pushed mistake —
# every teammate holding the old tip now diverges, and their next push is refused
```

### 2) **Reverting a merge names its parent**

**Definition** — a merge has two parents, so reverting one must say which line counts as "the main line": `git revert -m 1 <merge>` keeps parent #1 (the branch you merged *into*) and undoes the *join* — the incoming side's effect vanishes while both lines' commits remain. Verified: after `Merge made by the 'ort' strategy`, `git revert -m 1 --no-edit HEAD` prints `[main 8f0e483] Revert "Merge featx"` — the revert commit undoes the resolution state, which is exactly the granularity rollbacks need (Domain 03 §2.1: the join commit is the unit of revert for the integration decision).

- **Why it matters (correctness)**: release rollbacks almost always target merges ("un-merge Thursday's deploy but keep the commits for a clean retry"). Reverting without `-m` fails outright (Git refuses: "commit is a merge but no -m option was given") — and guessing the parent wrong reverts the *main line's* history instead of the feature's. Parent #1 is the line you were standing on during the merge (`main` in `git merge feat` from `main`) — first-parent history (`log --first-parent`) shows you exactly that line.
- **Modern guidance** — revert merges with `-m 1` unless you can articulate why the other parent is the main line (exotic flows: merging `main` *into* a feature to test — then the feature is #1). After a merge-revert, remember the trap: re-merging the same branch later silently does nothing (the original commits are already ancestors — Git sees "already merged"). The fix is `revert` the revert first, then merge the fixed line — documented in Pro Git and worth rehearsing before release night.

```bash
# GOOD: undo the join, keep both lines — verified
git merge --no-ff -m "Merge featx" featx   # Merge made by the 'ort' strategy.
git revert -m 1 --no-edit HEAD
#  [main 8f0e483] Revert "Merge featx"   (join undone; featx commits intact for retry)
# BAD: `git revert <merge>` without -m — refused outright; `-m 2` by guesswork —
# undoes your main line instead of the feature (read --first-parent before choosing)
```

### 3) **Revert conflicts resolve like merges**

**Definition** — when later commits built on the reverted code, the inverse diff collides — and the resolution is the familiar loop from Domain 03 §2.2: read the markers, decide per hunk (keep the later work, drop the reverted part, or blend), test, `add`, commit. Reverting *is* joining, backwards: the same three-way machinery, the same `UU` states, the same `--abort` escape. No new skill required — only recognition.

- **Why it hurts when missing (correctness, maintainability)**: teams that fear revert conflicts reach for destructive undo instead ("reset and force-push will be cleaner") — trading a resolvable, reviewable conflict for history surgery on a shared line. Or they abandon the revert halfway (`--quit` without cleanup, or committed markers), leaving the tree worse than the mistake. The loop is mechanical and safe: every hunk is a question with the later code on one side and the inverse on the other, and `--abort` restores the pre-revert state whenever doubt wins.
- **Modern guidance** — resolve revert conflicts exactly like merge conflicts (edit → test → `add` → commit), then verify the *net effect* (`diff` against the pre-mistake state where applicable) rather than just the absence of markers. If the conflict is large, that's information: the code moved far since the mistake, and the revert deserves the same review rigor as the original change — open it as a PR (Domain 04 §2.2), don't push it direct.

```bash
# GOOD: the same loop, backwards — markers, decision, test, stage, commit
git revert --no-edit <sha>     # CONFLICT (content): Merge conflict in f.txt — familiar UU state
#  ... edit hunks (later work wins where it built on the mistake; inverse wins elsewhere) ...
git add f.txt && git commit    # the revert lands as one reviewable unit
git merge --abort 2>/dev/null; git revert --abort   # doubt? abort restores pre-revert state
# BAD: abandoning a conflicted revert mid-tree, or "fixing" it with reset --hard —
# the tree now holds half a revert nobody can read; abort or finish, never linger
```

### 4) **Common confusion**

- "Revert deletes the commit" — the commit stays; its *effect* is cancelled by a new commit. `log` shows both — that visibility is the feature (auditability), not clutter.
- "Reverting twice is a mistake" — revert-of-revert is the standard re-landing pattern (merge-revert trap above). History narrates: merged, reverted, reverted-the-revert, merged-again — each step reviewable.
- "`-m 1` means revert one commit" — `-m` selects the *mainline parent* of a merge, not a count. On non-merges it is an error; on merges it is mandatory.
- "Small mistakes don't deserve revert commits" — on shared lines they do: one honest commit beats one rewritten history. Reserve_amend_-style cleanup for private lines (next section).

### 5) **Performance note**

Revert is one commit — same cost as any commit (one tree, one diff, no network until push). Conflicted reverts cost reviewer attention proportional to how far the code moved since the mistake — which is why fast reverts (hours, not quarters) resolve cleanly. The expensive alternative is history surgery on shared lines: every teammate pays re-clone/rebase costs. Revert is the cheapest correct undo at every scale.

### 6) **Mentor note**

Make juniors revert in scratch until the append-only shape is boring: revert a tip (clean), revert a merge with `-m 1` (read `--first-parent` first), revert into a conflict (resolve with the Domain 03 loop). Then stage the trap: revert a merge, try re-merging the fixed branch, watch Git say "already up to date" — and fix it with revert-of-revert. That single exercise teaches more about DAG reachability than a week of diagrams. Watch for the reset-instead-of-revert reflex on pushed mistakes (fix with the golden-rule question: "who else can see this commit?") and the `-m` guesser (fix with `log --first-parent` before every merge-revert). Review check: every revert names *why* in the body; every merge-revert names its parent deliberately; no force-push appears in shared-line incident reports.
