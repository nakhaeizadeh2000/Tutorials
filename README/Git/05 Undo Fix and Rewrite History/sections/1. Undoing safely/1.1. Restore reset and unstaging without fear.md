## 1.1. Restore, reset, and unstaging without fear

### 1) **Unstage, don't unmake**

**Definition** — `git restore --staged <path>` copies the file from `HEAD` back into the index, moving staged work to the working tree — the composition changes, nothing is lost. Verified on Git 2.53.0: after staging a tweak to `a.txt`, `git restore --staged a.txt` leaves `git status --short` showing ` M a.txt` (unstaged modification, work intact). The pre-2.23 twin `git reset HEAD -- <path>` does the same thing; `restore` is the taught spelling since 2.23 because it names the *direction* (out of staging) instead of overloading `reset`.

- **What problem it solves**: staging is composition (Domain 02 §1.1) — you stage hunks to build one idea per commit, and composition means changing your mind. Without a fearless unstage, every mis-staged hunk becomes a dilemma: commit the wrong shape, or perform surgery. `restore --staged` removes the dilemma: uncompose freely, recompose deliberately. The working tree is never touched, so the operation cannot destroy work — only rearrange it.
- **Modern guidance** — reach for `restore --staged` first for every "wrong shape" moment: wrong file staged, hunk staged that belongs in the next commit, whole `git add .` that swept in experiments. Alias it (`unstage` per Domain 02 §3.2) so the safe path is also the short path. Never use `reset --hard` or `checkout -- <path>` for unstaging — those target different areas (next sections) and destroy what `--staged` preserves.

```bash
# GOOD: staged the wrong shape? uncompose, keep the work — verified
git add a.txt                      # staged a tweak that belongs in the NEXT commit
git restore --staged a.txt
git status --short                 # " M a.txt" — unstaged, intact, recompose freely
# BAD INSTINCT: `git reset --hard` to "unstage" — targets the working tree too,
# discarding the very work --staged would have preserved
```

### 2) **Discard deliberately, never casually**

**Definition** — two commands destroy uncommitted work, and both deserve a pause: `git restore --source HEAD -- <path>` (working-tree file back to committed state — the file's uncommitted edits vanish) and `git reset --hard <commit>` (index *and* working tree back to that commit — all uncommitted work everywhere vanishes). Neither appears in the reflog as recoverable *work* (the reflog records the HEAD move, not the file contents — leaf 3.1 owns that boundary). There is no undo for discarded uncommitted edits.

- **Why it matters (correctness)**: these are the only common Git commands that destroy data without committing anything first. Every "Git ate my code" story that isn't a misunderstood checkout traces here — usually `--hard` typed to fix a staging confusion that `--staged` would have solved. The rule is proportional: uncommitted work has no snapshot backing it, so discarding it is deletion, not undo. Treat both commands like `rm -rf`: correct sometimes, casual never.
- **Modern guidance** — before either command: `git status` (know exactly what dies), and for `--hard`, create a bookmark branch first (`git branch backup-<date>`) — one label that converts destruction into recoverable abandonment. Prefer the narrowest destruction that solves the problem: one file → `restore --source HEAD -- <path>`; whole tree → `reset --hard` only when you can name every change being discarded. If you can't name them, `stash` (Domain 06) instead — shelving beats deleting.

```bash
# GOOD: deliberate discard — status first, bookmark for --hard, narrowest scope
git status --short                 # read what dies BEFORE destroying it
git branch backup-before-cleanup   # one label: destruction becomes abandonment (recoverable via leaf 3.1)
git restore --source HEAD -- a.txt # one file back to committed state — rest of tree untouched
# BAD: `git reset --hard` as a first resort for confusion —
# uncommitted edits vanish with no snapshot, no reflog entry holding their contents
```

### 3) **Know which area you're targeting**

**Definition** — every undo names one of the three areas from Domain 01 §2.1, and the command follows the area: working tree only → `restore --source` (index and HEAD untouched); index only → `restore --staged` (tree and HEAD untouched); HEAD position (committed line) → `reset --soft|--mixed|--hard` (what moves *with* HEAD differs: `--soft` keeps index+tree, `--mixed` resets index but keeps tree, `--hard` resets both). Verified shape: `git reset --soft HEAD~1` moves HEAD back one commit while `git status` still shows the changes staged (`M  a.txt`, `D  b.txt` — index preserved, history pointer moved).

- **Why it hurts when missing (correctness, maintainability)**: area confusion is the root of most undo disasters — `--hard` used where `--staged` belonged (work destroyed instead of uncomposed), `--soft` expected to clean the tree (it never touches files), `restore` without `--staged`/`--source` flags doing something surprising. The three areas are the addressing scheme for all undo: name the area, the flag follows. Developers who point at the area first pick correctly; developers who memorize flags without areas gamble.
- **Modern guidance** — say the area aloud before the command: "unstage this file" (index → `restore --staged`), "discard this file's edits" (tree → `restore --source HEAD`), "move the branch pointer back but keep everything staged" (HEAD, keep index → `reset --soft`), "uncommit but keep edits unstaged" (HEAD, reset index → `reset --mixed`, the default), "abandon everything uncommitted" (all areas → `reset --hard`, bookmarked first). The table is complete — every undo in this domain is one row of it.

```bash
# GOOD: area first, flag follows — verified soft shape
git reset --soft HEAD~1   # HEAD back one; index+tree kept
git status --short        # M  a.txt / D  b.txt (staged) — history moved, work staged
#  --mixed HEAD~1 would unstage too (tree kept); --hard would discard all (bookmark first!)
# BAD: flag-first undo ("I always use reset --hard for everything") —
# one flag cannot address three areas, so it destroys two you didn't mean
```

### 4) **Common confusion**

- "`reset` and `restore` are interchangeable" — `restore` targets files in tree/index (never moves HEAD); `reset` moves the branch pointer (with `--soft/mixed/hard` controlling collateral). Since 2.23, use `restore` for files, `reset` for pointers — the split exists so you stop overloading one command.
- "`--hard` is fine because reflog saves everything" — reflog records HEAD *moves*, not uncommitted file *contents*. Committed-then-abandoned work is recoverable (leaf 3.1); never-committed edits discarded by `--hard` are gone. The seatbelt covers passengers (commits), not luggage (unstaged edits).
- "Unstaging loses the staged snapshot" — the staged blob objects linger as dangling objects, but more usefully: the work itself sits intact in your tree. Nothing was snapshotted *as a commit*, but nothing was deleted either.

### 5) **Performance note**

All three commands are local file-and-pointer operations — instant at any repo size (no network, no object transfer). `--hard` on a giant tree rewrites many working files (I/O-bound, seconds on monorepos) but never touches the object store. Cost discipline is about *data*, not speed: the cheap commands (`--staged`, `--soft`) preserve work; the fast-looking one (`--hard`) is the expensive one in the only currency that matters.

### 6) **Mentor note**

Drill areas before flags: show the three-area diagram, point at each, and have juniors name the command *and flag* for five scenarios (unstage a file, discard a file's edits, uncommit keeping staged, uncommit keeping unstaged, abandon all). Do not proceed until all five are instant. Watch for the two failure postures: the hard-resetter (every confusion ends in `--hard` — fix with the area question: "which area are you targeting?") and the never-discarder (hoards doomed edits across weeks — fix with bookmark-then-discard: destruction with a label is just abandonment). Review check: `restore --staged` used for unstaging, `--hard` always preceded by `status` plus a bookmark branch, no `checkout -- <path>` in new muscle memory.
