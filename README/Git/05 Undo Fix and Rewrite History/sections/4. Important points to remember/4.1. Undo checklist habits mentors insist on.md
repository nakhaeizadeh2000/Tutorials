## 4.1. Undo checklist (habits mentors insist on)

### 1) **Public lines append, private lines may rewrite**

**Definition** — the golden rule in one sentence: commits others can see are undone by *adding* (`revert`); commits only you can see may be *replaced* (`amend`, `rebase`). Visibility is the whole rule — the commands differ because the audience differs. `branch -r --contains <sha>` answers "who else?" mechanically; memory never has to.

- **What problem it solves**: every history disaster in team Git is a visibility error — rewrite applied where append belonged. The rule collapses five leaves of mechanics into one pre-action question, asked before every undo: "who else can see this commit?" Unpushed → your call. PR branch → amend/rebase plus lease-push. Shared (`main`, merged, tagged, pulled) → revert or follow-up commit, always. No other judgment required at the keyboard.
- **Modern guidance** — print the question on the team wiki and in onboarding: *who else can see this commit?* Juniors should answer it aloud before touching undo commands for their first quarter. Seniors enforce it in review: any incident involving rewritten shared history gets the same retro question, blamelessly asked, until the rule is cultural rather than personal.

```bash
# GOOD: visibility first, command second
git branch -r --contains HEAD   # who else holds this tip? (empty → private; listed → shared)
#  private → amend / rebase + --force-with-lease (your line, your rewrite)
#  shared  → revert / follow-up commit (their copies must keep working)
# BAD: choosing undo by convenience ("reset is faster than revert") —
# speed on shared lines is just breakage with less waiting
```

### 2) **Destructive commands get a status first**

**Definition** — `reset --hard`, interactive rebase, lease-push, and `restore --source` all destroy or orphan something — so each gets `git status` (what dies?) plus a bookmark (`git branch backup-<date>`) before running. The bookmark converts destruction into abandonment: one label that keeps every orphan reachable via `log` instead of only via reflog archaeology. Seconds to create, hours to miss.

- **Why it matters (correctness)**: bookmarks are the cheapest insurance in Git (one ref, zero objects) and the most skipped — post-incident reviews invariably find the engineer "was sure" about the tree state. `status` plus a branch removes certainty from the equation: the pre-image is labeled regardless of what you believed. Combined with the reflog (leaf 3.1), this gives two independent recovery paths for every destructive act — belt and suspenders, both free.
- **Modern guidance** — make it ritual, not judgment: *every* `--hard`, every interactive script, every force-push gets status-plus-bookmark, including the "obvious" ones. Obviousness is uncorrelated with correctness under deadline pressure — which is exactly when destructive commands get typed. Delete backup branches in the weekly prune (Domain 04 §2.2's `branch -d` + `fetch --prune` hygiene); a graveyard of month-old backups is clutter, but clutter beats loss.

```bash
# GOOD: status plus bookmark — destruction becomes abandonment
git status --short && git branch backup-before-rebase
git rebase -i origin/main   # worst case: originals labeled backup-before-rebase AND in reflog
# BAD: "I'm sure the tree is clean" followed by --hard —
# certainty is not a backup strategy; labels are
```

### 3) **Lease, never force; reflog before panic**

**Definition** — two half-rules that close the loop: pushes after replay use `--force-with-lease` exclusively (the lease checks the remote is as-fetched; bare `--force` overwrites unseen work silently — leaf 2.1), and every "it's gone" moment starts with `git reflog` (leaf 3.1's three calm steps: journal, re-label, verify — never re-clone, never `gc --prune` mid-rescue).

- **Why it hurts when missing (correctness, maintainability)**: bare force and panicked re-cloning are the two ways engineers convert recoverable situations into permanent ones — the first discards colleagues' pushes, the second discards your own rescue history. Both feel decisive; both destroy the evidence that would have enabled recovery. The checklist exists because pressure inverts judgment: lease and reflog are the pre-committed correct responses for moments when thinking clearly is hardest.
- **Modern guidance** — remove bare `--force` from your vocabulary (no alias, no history shortcut — let it be awkward to type). Teach the panic drill alongside fire drills: "work vanished → reflog → re-label → verify → breathe." Teams that rehearse recovery never improvise it — and post-incident reviews should verify the lease was held and the reflog consulted, the same way aviation checks the checklist was *read*, not just known.

```bash
# GOOD: the two pre-committed responses under pressure
git push --force-with-lease origin feat/x   # lease held → overwrite is safe; refused → fetch and re-read
git reflog | head                            # gone? → journal first, re-label second, panic never
# BAD: `git push --force` ("faster") and `rm -rf` + re-clone ("cleaner") —
# both destroy the evidence recovery needs, fastest and cleanest toward permanent loss
```

### 4) **Common confusion**

- "The golden rule has exceptions for small fixes" — visibility doesn't grade on size. A one-character amend on `main` orphans exactly as many copies as a hundred-commit rebase. Smallness speeds the mistake, not the pardon.
- "Bookmarks are clutter" — unlabeled orphans are recoverable (reflog) but invisible (`log --all` shows nothing — verified in leaf 3.1). Labels make recovery *findable*; the prune pass (weekly) bounds the clutter.
- "Lease always succeeds on my branch" — the lease fails precisely when it matters (teammate pushed meanwhile). Treat refusal as a message, not an obstacle: fetch, read, replay on top.

### 5) **Performance note**

The whole checklist (visibility check + status + bookmark + lease/reflog) adds under a minute to any undo — against incident costs measured in hours (diverged teammates, lost pushes, re-implementation). Highest-leverage minute in the undo workflow; the only Git habit with a better ratio is fetch-before-reason (Domain 04 §4.1).

### 6) **Mentor note**

Convert this leaf into the team's undo runbook: golden-rule question first, status-plus-bookmark before destruction, lease-only pushes, reflog-first rescues. Drill it as incidents, not lessons — stage a bad reset, an amended shared tip (scratch pair), a deleted branch, and have juniors recover each using only this checklist. Grade procedure adherence, not speed. Watch for checklist decay under deadlines (the exact moments it matters most — fix with server-side guards: protected branches, lease requirements, stale-review dismissal per Domains 06–07, so the checklist has mechanical backup). Review check: incident reports cite visibility, bookmark, lease, and reflog steps explicitly — "checked, not there" counts; skipped silently doesn't.
