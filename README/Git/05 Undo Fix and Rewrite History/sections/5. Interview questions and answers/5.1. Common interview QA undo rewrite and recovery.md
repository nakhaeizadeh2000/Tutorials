## 5.1. Common interview QA: undo, rewrite, and recovery

### 1) **Committed to the wrong branch — now what?**

**Definition** — the workflow trap that tests area-and-pointer thinking: commits `X, Y` sit on `main` but belong on `feat/x`. Expected answer moves them without redoing: bookmark or create the right branch at the current tip (`git branch feat/x` / `switch -c`), return `main` to where it belongs (`reset --hard origin/main` — bookmarked first per leaf 4.1, and safe here because the commits survive on the new label), verify both lines. No work redone, no history rewritten that anyone saw.

- **What a good answer sounds like**: "Branches are labels — I label the current tip as the feature branch, move `main` back to its upstream position, and verify. The commits never move; only pointers do." Strong candidates mention the bookmark/safety variant for non-trivial cases and note the shared-line exception (if the wrong-branch commits were already pushed to `main`, the fix is `revert` on `main` plus the branch — pointers already escaped). Bonus: `cherry-pick`/`rebase --onto` for moving a *subset* rather than the whole tip run.
- **Modern guidance** — grade the model (labels move, commits don't) over the spelling: `branch`+`reset`, `switch -c`+`reset`, and `rebase --onto` for partial moves are all full marks. Red flags: "delete and recommit" (destroys authorship and hashes for a pointer problem), "`reset --hard` without mentioning the commits' survival" (may work, proves nothing), any force-push to shared `main` as step one.

```bash
# The trap, solved with pointers (safe: new label first, move second)
git branch feat/x               # label the tip — X, Y now live on feat/x regardless of what follows
git reset --hard origin/main    # main back to its mirrored position (bookmarked by the new label)
git log --oneline main..feat/x  # X, Y — verify the move before celebrating
#  pushed-to-shared variant: revert on main + keep the branch (pointers already escaped — leaf 1.2)
```

### 2) **Reset vs revert vs restore — which and when?**

**Definition** — the judgment question covering the whole domain's command map: `restore` targets files (tree/index, never moves HEAD — leaf 1.1), `reset` moves the branch pointer (with `--soft/mixed/hard` collateral — leaf 1.1), `revert` adds an inverse commit (shared lines, append-only — leaf 1.2). The decision inputs are *area* (which of the three?) and *visibility* (who else sees it?) — the two questions from leaves 1.1 and 4.1.

- **What a good answer sounds like**: a two-question decision tree, not three definitions: "First — who else can see it? Shared means revert, full stop. Private means choose by area: wrong staging → `restore --staged`; wrong files → `restore --source`; wrong tip → `reset` with the collateral flag that matches (`--soft` keep staged, `--mixed` unstage, `--hard` discard, bookmarked). Rebase/amend are `reset`-family (replacement) for multi-commit/single-tip cases." Seniors add the lease-push coda and the reflog seatbelt without prompting.
- **Modern guidance** — listen for *inputs* (area + visibility) before *outputs* (commands): candidates who start from the situation ("pushed to main? revert. Staged wrong file? restore --staged.") demonstrate judgment; candidates who recite flag tables demonstrate memory. Instant fail: recommending `reset --hard` for pushed mistakes, or any answer where visibility never appears. Follow-up that separates mid from senior: "your reset --hard just ate uncommitted work — go" (reflog won't hold file contents — honest answer names the boundary, then prevention: stash/bookmark/status-first).

```bash
# The decision tree, executable
git branch -r --contains HEAD   # visibility: shared → revert (leaf 1.2); private → continue
git status --short              # area: staged-shape → restore --staged; tree-edits → restore --source
git reset --soft HEAD~1         # pointer, keep staged (verified leaf 1.1 shape)
```

### 3) **You force-pushed main — walk me through recovery**

**Definition** — the incident answer that tests honesty under pressure: the old tip is orphaned but (recently, locally) in your reflog and possibly in teammates' clones/remote reflogs. Expected path: stop everyone from fetching the damage (announce immediately — silence spreads orphans), find the last-good hash (your reflog's pre-push entry, a teammate's un-fetched clone, CI's recorded SHA, the forge's reflog/activity), re-label (`reset --hard <last-good>` on a fresh fetch of agreement, or push the rescued tip back), verify with the team (`log` agreement across clones), then retro the prevention (protected branches, no-force rules — Domains 06–07).

- **What a good answer sounds like**: communication *before* commands — "I announce in the team channel first: nobody fetch/pull until I say so." Then parallel recovery paths ranked by freshness (my reflog → teammate's clone → CI SHA → forge history), re-labeling (never re-implementing), team-wide verification, and a prevention ending (branch protection so fingers can't decide alone). Seniors mention that every fetcher between damage and announcement now holds the orphan and needs the same re-label — recovery scales with silence duration, which is why announcement is step zero.
- **Modern guidance** — grade calm and completeness over speed: the candidate who says "first I stop the bleeding, then I check three places for the hash, then I verify across the team, then we protect the branch" passes; the candidate who jumps to `reset --hard ORIG_HEAD` and stops therefails the team dimension. Red-flag instant-fail: "revert the force-push" (can't revert a pointer move — nothing was committed), "re-clone and start over" (destroys the local reflog holding the answer), hiding the incident.

```bash
# Recovery sketch (principles; hashes from YOUR reflog at incident time)
git reflog                       # pre-push entry: the last-good position (e.g. HEAD@{1}: push line)
git branch rescue-main <last-good-sha>   # re-label first — verify before moving shared pointers
#  ... announce: nobody fetch/pull ... verify rescue tip with team/CI ...
git push --force-with-lease origin rescue-main:main  # restore the line (then protect it — Domain 07)
```

### 4) **Common confusion**

- Candidates who answer every undo question with one favorite command (usually `reset --hard` or `rebase -i`) — single-tool answers to area-and-visibility questions reveal memorization without model.
- "ORIG_HEAD always saves you" — `ORIG_HEAD` records only the *last* HEAD-moving operation (merge/reset), overwritten by the next one. The reflog is the journal; `ORIG_HEAD` is a sticky note that gets reused.
- Treating the force-push scenario as purely technical — half the recovery is communication (freeze fetches, coordinate verification, retro prevention). Seniors lead with the channel message; juniors lead with the command.

### 5) **Performance note**

Interview answers here should be compact: wrong-branch (60 seconds — labels move, commits don't, plus the shared exception), reset/revert/restore (90 seconds — two-question tree with one example each), force-push recovery (two minutes — announce, three hash sources, re-label, verify, protect). Candidates who narrate procedures without the model (area + visibility) take longer and prove less — structure is speed.

### 6) **Mentor note**

Use Q1 as the pointer-model screen (every hire must move labels without moving work), Q2 as the judgment screen (every hire must pick undo by area + visibility), Q3 as the incident screen (every hire must communicate first and recover with reflog + team verification). Rubric: junior — correct commands in order; mid — model language (labels, areas, visibility) plus lease/reflog coda; senior — prevention (protection, policy, retro) and honest boundaries (reflog won't restore uncommitted discards). Keep a scratch pair ready and make finalists demonstrate Q1 live — watching pointers move teaches interviewers as much as candidates. Red-flag fails: hard-reset for pushed mistakes, force as first resort, re-clone as rescue, silence as incident response.
