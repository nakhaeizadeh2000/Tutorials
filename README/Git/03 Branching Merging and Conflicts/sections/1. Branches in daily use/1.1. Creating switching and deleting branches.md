## 1.1. Creating, switching, and deleting branches

### 1) **Create and switch in one move**

**Definition** — `git switch -c <name>` creates a branch pointing at `HEAD` and moves `HEAD` onto it in a single command: you are on the new line the moment it exists. `git checkout -b <name>` is the legacy twin — identical result, older spelling from before `switch`/`restore` split `checkout`'s jobs in Git 2.23.

- **What problem it solves**: the two-step dance (`branch` then `checkout`) leaves a gap where the next commit lands on the wrong line. Engineers create the branch, answer a message, then commit — on `main`, not the feature. The single command removes the gap: there is no moment where the branch exists but you are not on it.
- **Modern guidance** — teach and type `switch -c` (and `switch` for moving) in everything new; read `checkout -b` in old scripts and docs without rewriting them. Verified on Git 2.53.0: `switch -c feat/x` prints `Switched to a new branch 'feat/x'`, and `git status -sb` confirms `## feat/x` immediately.

```bash
# GOOD: one move — branch exists and you are on it, no gap
git switch -c feat/cart-guest-checkout
#  Switched to a new branch 'feat/cart-guest-checkout'
git status -sb   # ## feat/cart-guest-checkout — confirmed before editing
# LEGACY TWIN (read it, don't teach it first): git checkout -b feat/cart-guest-checkout
```

### 2) **Switching moves HEAD, never work**

**Definition** — `git switch <branch>` repoints `HEAD` at another line; your uncommitted edits travel with you. When the target line does not touch the same paths, the switch succeeds and the dirt carries over (verified: `carry rc=0`). When switching would overwrite your edits — the target committed a different version of a file you also modified — Git refuses and tells you to commit or stash first (verified exact refusal: `error: Your local changes to the following files would be overwritten by checkout: file.txt / Please commit your changes or stash them before you switch branches.`).

- **Why it matters (correctness)**: the two failure postures are both expensive. The timid engineer commits half-done work "just to switch" and pollutes history with checkpoint noise; the bold one assumes switching is always safe and is then surprised by the refusal mid-context-switch. Knowing the rule — *carries when paths don't collide, refuses when they would* — turns both into a calm decision: commit the finished idea, or carry the scratch deliberately.
- **Modern guidance** — before hopping, run `git status --short`: clean tree switches freely, dirty tree carries-or-blocks per the rule above. Never switch to "check something quickly" with a dirty tree unless you can state which outcome you expect. `git switch -` jumps back to the previous branch — the two-branch toggle for review-then-resume loops.

```bash
# GOOD: know the tree state before hopping — clean switches freely
git status --short    # empty: clean — switch anywhere
git switch main
# DIRTY BUT SAFE: target doesn't touch your paths — edits carry over (rc=0)
# DIRTY AND BLOCKED: target touched the same file — Git refuses, commit or stash first
git switch main
#  error: Your local changes ... would be overwritten by checkout
git switch -   # back to the previous branch — the review toggle
# BAD: committing "wip stuff" just to earn a switch — checkpoint noise in permanent history
```

### 3) **Delete merged with `-d`, unmerged with intent**

**Definition** — `git branch -d <name>` deletes only when the branch's commits are reachable from its upstream or the current line (fully merged); otherwise it refuses with `error: the branch 'feat/y' is not fully merged` (verified `rc=1`). `git branch -D` overrides the check and deletes regardless — the bypass you type deliberately, never by habit.

- **Why it hurts when missing (correctness)**: `-d`'s refusal is the last guard before orphaning commits. Engineers who alias deletion to `-D` "to skip the nag" throw away the only check standing between a typo (`feat/cart` vs `feat/carts`) and unreferenced work that only `reflog` can still find. The refusal is information — it says "this line contains commits nothing else points to." Read it before overriding it.
- **Modern guidance** — default to `-d`; when it refuses, inspect first (`git log --oneline main..<name>` — is the "unmerged" work real or already cherry-picked elsewhere?), then either merge or `-D` with a stated reason. Delete promptly after merge (leaf 1.2 owns the habit); remote-tracking cleanup is `git push origin --delete <name>` plus `git fetch --prune` — local `-d` never touches the remote, a Domain 04 topic, not this leaf.

```bash
# GOOD: the guard works — merged deletes, unmerged refuses, intent overrides
git branch -d feat/cart-guest-checkout   # merged: Deleted branch ... — rc=0
git branch -d feat/abandoned             # unmerged: error: the branch ... is not fully merged — rc=1
git log --oneline main..feat/abandoned   # inspect: is the unmerged work real?
git branch -D feat/abandoned             # deliberate: intent stated, bypass earned
# BAD: aliasing deletion to -D globally — the guard never fires, typos orphan work
```

### 4) **Common confusion**

- "`checkout` and `switch` are interchangeable" — same result for these two moves, different teaching: `switch` cannot touch files (no `-- <path>` form), so it cannot destroy work the way `checkout -- <path>` can. Teach the tool that refuses the dangerous shape.
- "Deleting a branch deletes its commits" — deleting removes the *label*; commits survive while anything points at them (the merge target does — that is exactly what `-d` checked). Unmerged `-D` orphans commits into `reflog`-only reach, expiring with it (Domain 05 owns that rescue).
- "I should delete the branch before merging" — backwards: merge first, then `-d` verifies reachability as it deletes. Deleting first destroys the evidence `-d` needs.
- "Remote branches delete with `-d`" — local `-d` never touches the remote. `push --delete` plus `fetch --prune` is the remote half (Domain 04).

### 5) **Performance note**

Branch creation and switching are O(HEAD-move), not O(tree-copy): a branch is a 41-byte ref file, and switching updates the index plus only files differing between the two tips. Creating branches is therefore free — the performance argument always favors *more, smaller* branches (leaf 1.2), never reusing one long-lived line "to save time." The genuinely slow operation is switching between lines with hugely divergent trees (thousands of files rewritten on disk) — schedule those hops, don't fear branching itself.

### 6) **Mentor note**

Run the gap drill live: have every junior create a branch the two-step way, get interrupted before the checkout, then commit — and watch the commit land on `main`. Then require `switch -c` plus a `status -sb` confirmation before any edit, for a week. Watch for the two failure postures: the gapper (edits before confirming the branch — fix with the `status` reflex) and the `-D` habitualist (force-deletes to skip reading refusals — fix by requiring the `log main..<name>` inspection out loud before any `-D`). Review check: any `checkout -b` in new docs gets rewritten to `switch -c`; any `-D` without a stated reason gets challenged.
