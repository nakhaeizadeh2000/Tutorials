## 1.2. Short-lived branches and the feature-branch habit

### 1) **One branch per idea**

**Definition** — a short-lived branch carries exactly one reviewable idea — a feature, a fix, an experiment — from creation to merge, then dies. Its lifetime is measured in hours to days, not sprints: branch, commit the idea (Domain 02 atomicity), open the review, merge, delete.

- **What problem it solves**: long-lived personal branches become merge-event horizons — weeks of mixed ideas diverging from `main`, unreviewable as a unit, conflicting on every file they touched. The cost compounds silently: each day unmerged is a day of upstream movement the branch doesn't see, so the eventual merge resolves weeks of drift at once, under deadline pressure, by whoever drew the short straw. One idea per branch caps the divergence window at the idea's own size.
- **Modern guidance** — if the branch lives past one review cycle, split the idea, not the branch: land what's done behind the merge, re-branch for the remainder. Long-running *collaboration* needs a shared integration line with a merge cadence (Domain 06 owns branching strategy) — never a private branch aging in silence.

```bash
# GOOD: one idea, one branch, one review — then gone
git switch -c feat/cart-guest-checkout
#  ... three atomic commits, review, merge ...
git switch main && git merge feat/cart-guest-checkout
git branch -d feat/cart-guest-checkout   # merged — label is clutter now
# BAD: feat/cart-work living six weeks, holding a fix + a feature + an experiment
```

### 2) **Name for triage**

**Definition** — branch names follow `<type>/<area>-<what>` — `feat/cart-guest-checkout`, `fix/login-loop`, `exp/search-ranking-v2` — type first for filtering, area second for ownership, ticket where the team tracks it (`feat/cart-4821-guest-checkout`). The name is the first line of the review request: future-you greps history by these.

- **Why it matters (maintainability)**: branches are triaged far more often than they are merged — in `git branch` listings, in CI dashboards, in "which of these twelve lines holds the hotfix?" incidents. `fix/login-loop` answers in one glance; `johns-branch-2` answers nothing and forces archaeology during the incident it's blocking. Naming is the cheapest observability a team can buy.
- **Modern guidance** — agree the type vocabulary once (`feat`, `fix`, `exp`, `chore`, `docs`, `hotfix`) and lint it in review, not in tooling — a naming convention enforced by humans survives; one enforced by hooks gets bypassed with `--no-verify`. Slashes group (`git branch --list 'feat/*'`), hyphens separate words, lowercase always — uppercase and underscores break tab-completion habits across shells.

```bash
# GOOD: triage at a glance — type, area, intent
git branch --list 'fix/*'
#  fix/login-loop
#  fix/cart-negative-qty
git switch -c hotfix/stripe-webhook-5007   # incident line: type + area + ticket
# BAD: johns-branch-2, test-final-v3, stuff — ungreppable during the incident they block
```

### 3) **Delete on merge, not someday**

**Definition** — the merge that lands the idea also retires its label: `git branch -d <name>` immediately after merging, while the context is fresh. The commits are reachable from the target — verified by `-d`'s own guard (leaf 1.1) — so nothing is lost; only the pointer is gone.

- **Why it hurts when missing (correctness, maintainability)**: stale merged branches rot the namespace — `git branch` fills with forty dead lines, tab-completion drowns, and engineers re-branch from `feat/cart-guest-checkout` six months later thinking it's current. Worse, a stale label invites the "helpful" push: someone force-pushes new work onto the old name and two ideas share one line. The audit for staleness is one command (verified on Git 2.53.0: `feat/demo` listed under `--merged main` before deletion, gone after).
- **Modern guidance** — make deletion part of the merge ritual, not a cleanup sprint: merge, `-d`, push, next. Run `git branch --merged main` monthly and delete everything merged — if `-d` refuses, that branch holds unmerged work and deserves a decision, not neglect. Remote halves (`push --delete`, `fetch --prune`) belong to Domain 04.

```bash
# GOOD: merge retires the label — audit monthly, delete merged
git branch --merged main
#  feat/demo        <- merged, reachable — safe to delete
#  * main
git branch -d feat/demo   # Deleted branch feat/demo — commits live on in main
git branch --merged main  # * main — namespace clean
# BAD SIGN: forty lines in git branch, thirty merged months ago — triage is archaeology
```

### 4) **Common confusion**

- "Deleting loses the review trail" — the review lives in the PR (Domain 04), the commits live in the target. The branch label held neither; deleting it removes a pointer, not history.
- "I'll delete in the cleanup sprint" — cleanup sprints never come, and by the time they do nobody remembers which of the forty lines are safe. Delete at merge time when certainty is total.
- "One branch per idea means hundreds of branches" — transiently, yes — and `git branch` with a naming convention handles hundreds; it cannot handle forty *ambiguous* ones. Count is not the problem; ambiguity is.
- "Feature branches are the only strategy" — no: this leaf owns the *mechanic* (small, named, deleted). Which lines are long-lived (`main`, `release/*`) and who merges into them is *policy* — Domain 06.

### 5) **Performance note**

Stale branches cost nothing on disk (41-byte refs) and everything in human bandwidth: every `git branch`, every CI branch dropdown, every "is this still needed?" thread scans the dead. The expensive operation is never creating a branch (O(HEAD-move), leaf 1.1) — it is the *triage* of a polluted namespace during an incident. Deleting on merge keeps the listing proportional to active work, which is the only set anyone ever needs to read quickly.

### 6) **Mentor note**

Enforce the habit mechanically for one month: every merged PR must show its branch deleted before the sprint board card closes — no exceptions, no "I'll do it later." Watch for the two failure postures: the hoarder (forty live branches "in case I need them" — needs the `--merged` audit demo proving the commits survive) and the recycler (reuses one `dev` branch for everything — needs the divergence-window explanation: one idea per line or reviews become unreadable). Review check: any branch older than the sprint it was born in gets asked "what idea is this, and why isn't it merged?" — silence means split or delete.
