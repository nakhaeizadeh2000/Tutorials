## 2.1. Fast-forward vs true merges

### 1) **Fast-forward slides the label**

**Definition** — when the target has not moved since the branch forked (no divergence), `git merge <branch>` simply advances the target label to the branch tip — no new commit, no join recorded. Verified on Git 2.53.0: merging an undiverged `feat` prints `Updating c4f7891..367ed42 / Fast-forward`, and `git log --oneline` shows a straight line (`B`, `A` — no merge commit).

- **What problem it solves**: most feature branches never diverge — nobody commits to `main` underneath a two-day branch. Recording a join commit for a non-join (nothing actually came together) adds graph noise that `log`, `bisect`, and `blame` must all step over forever. Fast-forward keeps the history honest: linear work reads linear.
- **Modern guidance** — let fast-forward happen by default for undiverged branches; it is the common case and the readable one. Reach for the merge flags below only when you need a *decision*, not a habit — the default already does the right thing for the common case.

```bash
# GOOD: no divergence — the label slides, history stays linear
git merge feat/cart-guest-checkout
#  Updating c4f7891..367ed42
#  Fast-forward
git log --oneline   # 367ed42 B / c4f7891 A — straight line, no join commit
# BAD INSTINCT: --no-ff "for visibility" on every merge — graph noise for non-joins
```

### 2) **True merge records the join**

**Definition** — when both lines moved (divergence), the merge creates a two-parent commit joining them — the graph remembers that two lines of work came together, who joined them, and when. Verified: after diverging (`C` on the branch, `D` on `main`), `git merge --no-ff -m "Merge feat2" feat2` prints `Merge made by the 'ort' strategy`, and `log --graph` shows the fork-and-join shape (`* Merge` with `|\` / `|/` arms).

- **Why it matters (correctness)**: the merge commit is the unit of revert for the *integration decision* — `git revert -m 1 <merge>` undoes the joining while keeping both lines' commits intact for a clean retry. Squashed or fast-forwarded-away joins cannot be reverted as joins; teams rediscover this during the release rollback that needs "un-merge Thursdays deploy but keep the commits." The two-parent commit also answers `blame`'s hardest question — "which line brought this hunk into this file?"
- **Modern guidance** — write merge messages that name the joined line (`Merge feat/cart-guest-checkout: guest checkout behind feature flag`), not the default `Merge branch 'x'` — the default names a label that will be deleted (leaf 1.2) and means nothing in six months. First-parent history (`git log --first-parent`) then reads as the integration story: one line per joined idea.

```bash
# GOOD: diverged lines get a join commit with a message that outlives the branch
git merge --no-ff -m "Merge feat/cart-guest-checkout: guest checkout behind flag" feat/cart-guest-checkout
#  Merge made by the 'ort' strategy.
git log --oneline --graph   # * Merge commit with |\ and |/ arms — the join is visible
git log --first-parent --oneline   # integration story: one line per joined idea
# BAD: default "Merge branch 'feat/cart...'" — names a deleted label, says nothing in six months
```

### 3) **Choose deliberately, message honestly**

**Definition** — three merge postures, chosen per situation: default (fast-forward when possible, join when diverged), `--no-ff` (always record the join, even undiverged), `--ff-only` (slide or refuse — never create a join). `--ff-only` on diverged lines aborts with `fatal: Not possible to fast-forward, aborting.` (verified `rc=128`, plus hints suggesting `--no-ff` or `rebase`).

- **Why it hurts when missing (correctness, maintainability)**: teams that never choose get surprised both ways — the "linear history" team wakes up to mystery join commits from diverged merges nobody noticed, and the "always merge commit" team drowns in join commits for branches that never diverged. The failure is silent: nobody notices the wrong shape until `bisect` lands on a join that shouldn't exist or `log` hides a join that should. Choosing per merge — or better, per team policy in Domain 06 — makes the shape intentional and therefore trustworthy.
- **Modern guidance** — the decision table: undiverged + default → slide (common case, do nothing); undiverged + want the join visible (release lines, Domain 06) → `--no-ff`; pulling shared lines where a surprise join means "someone moved underneath me" → `--ff-only`, and treat the refusal as information (rebase or merge deliberately — Domain 05 owns replay-vs-join). `git config pull.ff only` makes `--ff-only` the default for pulls, where surprise joins are most dangerous (Domain 04 owns the pull half).

```bash
# GOOD: posture per situation — slide, record, or refuse
git merge feat/small-fix              # undiverged: slides (default, linear)
git merge --no-ff feat/release-2.4    # undiverged but the join matters: record it
git merge --ff-only feat/risky        # diverged: fatal: Not possible to fast-forward, aborting. (rc=128)
#  ... refusal is information: inspect the divergence, then rebase or join deliberately
# BAD: one global posture for all merges — surprise joins or noise joins, pick your regret
```

### 4) **Common confusion**

- "Fast-forward is a kind of merge commit" — no commit at all is created: the label moves, full stop. That is why there is nothing to revert as a join and nothing for `--first-parent` to show.
- "`--no-ff` is always safer" — it preserves shape at the cost of noise: forty join commits for undiverged two-commit branches make `log` unreadable and `bisect` step over joins that joined nothing. Safety is choosing per case, not maximizing commits.
- "The merge commit duplicates the branch commits" — it contains no new *work*, only the *resolution state* (usually identical to one side) plus the join metadata. Reverting it reverts the resolution, which is exactly the granularity rollbacks need.
- "`--ff-only` failing means something broke" — the refusal is the feature: it detected divergence your workflow didn't expect. Read the graph before overriding.

### 5) **Performance note**

Merge shape has no runtime cost worth measuring — one extra commit object (~200 bytes) either way. The performance that matters is *human*: linear history bisects and reads faster; preserved joins revert faster. Optimize for the operation your team performs most — release teams revert (record joins), library teams bisect (prefer linear) — and encode the choice in policy (Domain 06), not in per-developer improvisation.

### 6) **Mentor note**

Draw the two shapes on a whiteboard before touching flags: two dots in a line (slide) vs a fork with a join dot (true merge). Then have every junior produce both in a scratch repo and read `log --graph` until they can predict the shape before running the merge. Watch for the two failure postures: the never-looker (merges without checking divergence — fix with `git log --oneline main..<branch>` before every merge) and the flag-memorizer (`--no-ff` everywhere "to be safe" — fix with the noise-vs-signal question: "what decision does this join commit record?"). Review check: every merge commit message names the joined *idea*, never just the branch label.
