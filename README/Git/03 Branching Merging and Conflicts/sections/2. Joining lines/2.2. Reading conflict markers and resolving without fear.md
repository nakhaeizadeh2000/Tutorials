## 2.2. Reading conflict markers and resolving without fear

### 1) **Markers are a question, not damage**

**Definition** — when both lines changed the same hunk, Git stops the merge and writes both versions into the file, delimited by markers. Verified on Git 2.53.0 (merge `rc=1`, `Automatic merge failed; fix conflicts and then commit the result.`):

```text
<<<<<<< HEAD
price = 10 * 1.2
=======
price = 12
>>>>>>> feat
```

Top (`<<<<<<< HEAD` … `=======`) is your line — where `HEAD` stood when you merged. Bottom (`=======` … `>>>>>>> feat`) is their line — the branch you named. The markers ask one question per hunk: "these two edits collide — which survives, or what combination?"

- **What problem it solves**: beginners read markers as corruption — the file looks broken, panic sets in, and the fix attempt (`delete everything weird`) destroys one side's work silently. Reading markers as a *question with two quoted answers* reframes the task: each hunk is a small, bounded decision, and `git status --short` shows exactly how many remain (`UU cart.txt` — unmerged, both modified — verified).
- **Modern guidance** — resolve one hunk at a time, top to bottom; never `git add` the file until every marker in it is gone (`grep -n '<<<<<<<' <file>` proves it). `git diff --check` catches leftover whitespace damage from hand-editing the hunk.

```bash
# GOOD: read the question — top is HEAD (yours), bottom is feat (theirs)
git status --short   # UU cart.txt — one unmerged path, both sides modified
#  <<<<<<< HEAD      <- your line: price = 10 * 1.2
#  =======
#  >>>>>>> feat      <- their line: price = 12
grep -n '<<<<<<<' cart.txt   # empty output = no markers left, safe to stage
# BAD: deleting "everything weird" — silently keeps one side, loses the other, no test
```

### 2) **The resolution loop**

**Definition** — edit → test → `add` → commit, one hunk at a time. Edit the hunk into the correct final state (yours, theirs, or a true combination — here `price = 12 * 1.2` honors both), run the relevant test to prove the combination works, stage the resolved file, and complete the merge commit. The loop is mechanical; judgment lives only inside the edit step.

- **Why it matters (correctness)**: every shortcut corrupts a different way. Skipping the test ships combinations neither side ever ran (both sides were green; the *combination* is new code). Staging with markers still present commits the markers as source — a syntax error at best, a silent string change at worst. Committing without `add` leaves the merge unfinished and the tree half-merged. The loop's order exists because each step guards the next: edit decides, test proves, `add` declares, commit records.
- **Modern guidance** — for pure "take one side" hunks say so in the merge message (`Merge feat/pricing: kept main's tax factor, took feat's base price`). For tangled files, `git mergetool` opens a three-way view (local/base/remote) — but learn markers first: tools hide the question, and hidden questions get misanswered. `git log --merge --oneline` during the conflict lists only the commits touching the conflicted paths — the exact context for deciding.

```bash
# GOOD: the loop — decide, prove, declare, record
#  1. edit cart.txt -> price = 12 * 1.2   (both ideas honored, markers removed)
npm test -- cart   # 2. test the COMBINATION — neither side ran this code
git add cart.txt   # 3. declare resolved — UU becomes M
git commit         # 4. record — editor opens with the default merge message, keep it honest
# BAD: edit + commit without testing — ships code no suite ever executed
```

### 3) **Abort is always available**

**Definition** — `git merge --abort` restores the exact pre-merge state: no merge commit, no staged resolutions, working files back to their pre-merge content. Verified: after abort, `status --short` is empty, `cart.txt` holds `price = 10 * 1.2` (the pre-merge `main` content), and `log` shows no trace of the attempt (`main-change`, `base` — the merge never happened).

- **Why it matters (correctness)**: resolution quality collapses under time pressure — the engineer who "must finish this merge now" picks sides at random to unblock the pipeline. Abort converts a crisis into a pause: the merge attempt cost nothing, the conflict will still be there tomorrow, and a rested decision beats a rushed one every time. Teams that normalize aborting get *better* resolutions, not slower ones, because nobody resolves while panicking.
- **Modern guidance** — abort the moment you realize you lack context ("I don't know whose tax factor is right — aborting, asking Priya, merging tomorrow"). Abort only works mid-merge (before the merge commit); once committed, unwinding is `revert`/`reset` territory — Domain 05. If the working tree had unrelated dirt before the merge, abort restores the merge state but your dirt was yours all along — know your `status` before starting (leaf 1.1).

```bash
# GOOD: pausing is professional — the attempt cost nothing
git merge --abort
git status --short   # empty — pre-merge state, cart.txt back to price = 10 * 1.2
git log --oneline | head -3   # main-change / base — the merge never happened
# BAD: force-pushing through a misunderstood conflict at 6pm — random resolution, permanent history
```

### 4) **Common confusion**

- "Conflicts mean someone did something wrong" — conflicts mean two people did something *concurrent*. Short branches (leaf 1.2) make them rarer and smaller; nothing makes them a fault.
- "I must resolve everything before testing anything" — resolve and test per hunk where possible; at minimum test the full file before `add`. The untestable middle state is normal — the finished state must be green.
- "`--abort` loses my resolution work" — abort discards *this attempt's* resolutions, which is the point: they were made without enough context. The branch commits on both sides are untouched — nothing committed is lost.
- "Merge commits from conflicted merges are special" — they are ordinary two-parent commits (leaf 2.1); the only difference is a human chose hunk outcomes. `revert -m 1` unwinds them the same way.

### 5) **Performance note**

Conflicts cost engineer-minutes, never machine-seconds — the merge machinery either succeeds instantly or stops for a human. The variable teams control is *conflict size*, and it is set by branch lifetime (leaf 1.2): a two-day branch conflicts on one hunk; a six-week branch conflicts on forty files. Measure conflict pain in "days since fork," not in tooling — then shorten the fork. `rerere` (leaf 3.1) amortizes repeated identical conflicts, but short branches eliminate them.

### 6) **Mentor note**

Stage a conflict deliberately in week one: two juniors edit the same line on two branches, merge, and read the markers together. The lesson is emotional, not technical — markers must feel like a question, not an alarm. Watch for the two failure postures: the deleter (removes markers without deciding — fix by requiring the "which side and why" sentence before `add`) and the committer (stages with markers present — fix with the `grep '<<<<<<<'` gate as a pre-`add` ritual). Review check: every conflicted merge's message explains each hunk decision in one clause; "resolved conflicts" alone gets sent back.
