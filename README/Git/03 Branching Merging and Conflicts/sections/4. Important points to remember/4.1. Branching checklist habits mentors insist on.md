## 4.1. Branching checklist (habits mentors insist on)

### 1) **Branch small, branch often**

One idea per line, named for triage, deleted on merge — short-lived, well-named, one idea is the unit of safe collaboration ([1.2](<../1. Branches in daily use/1.2. Short-lived branches and the feature-branch habit.md>)). Small branches review fast, merge clean, and revert safely; the divergence window never exceeds the idea's own size.

- **Why it hurts when missing**: long-lived mixed branches become merge-event horizons — unreviewable as a unit, conflicting on every file, resolved under deadline by whoever drew the short straw. Every week unmerged is upstream movement the branch doesn't see.
- **Modern guidance** — the birth ritual: `switch -c <type>/<area>-<what>` ([1.1](<../1. Branches in daily use/1.1. Creating switching and deleting branches.md>)), `status -sb` confirming the line before any edit, atomic commits (Domain 02) while it lives, `-d` at merge. Any branch older than its sprint gets asked what idea it holds and why it isn't merged.

### 2) **Read the graph before joining**

Shape first — fast-forward slide, true join, or conflict waiting — then choose the command ([2.1](<../2. Joining lines/2.1. Fast-forward vs true merges.md>)). Orientation is cheaper than rescue: two seconds of graph-reading prevents the hour-long unwind of a merge run blind.

- **Why it hurts when missing**: blind merges produce both surprise shapes — mystery join commits for the "linear history" team, silent content collisions for everyone. The merge that surprises is the merge that gets reverted badly.
- **Modern guidance** — the pre-merge gate, in order: `git log --oneline main..<branch>` (what joins?) → `git merge-base main <branch>` (where did we fork — how long is the window?) → `git status --short` (is my tree clean enough to merge into?) → choose slide, join, or `--ff-only`-and-inspect. `rerere.enabled` on ([3.1](<../3. Reuse and safety/3.1. Rerere and merge confidence.md>)) so recurrences arrive pre-answered.

```bash
# GOOD: the pre-merge gate — what, where-forked, tree-state, then choose
git log --oneline main..feat/cart-guest-checkout   # what joins? (three commits, one idea)
git merge-base main feat/cart-guest-checkout       # fork point — two days ago, small window
git status --short                                 # clean — merge freely
git merge feat/cart-guest-checkout                 # undiverged: slides (2.1)
# BAD: git merge feat/cart-guest-checkout with no prior read — shape unknown until done
```

### 3) **Resolve calmly, abort freely**

Markers are questions ([2.2](<../2. Joining lines/2.2. Reading conflict markers and resolving without fear.md>)); the loop is mechanical (edit → test → `add` → commit); pausing is professional (`merge --abort` restores everything, verified). Resolution quality collapses under time pressure — aborting converts a crisis into a pause, and a rested decision beats a rushed one.

- **Why it hurts when missing**: engineers who "must finish this merge now" pick sides at random to unblock the pipeline — and random resolutions enter permanent history as deliberate-looking commits. Nobody re-reviews a merged conflict; the guess becomes truth.
- **Modern guidance** — resolve one hunk at a time, test the *combination* (neither side ran it), `grep '<<<<<<<'` before every `add`, name each hunk decision in the merge message. Abort the moment context runs out — the conflict waits, the pipeline can wait, correctness cannot be hurried.

### 4) **Common confusion**

- "The checklist slows experienced developers down" — the three habits total under a minute per branch lifecycle and prevent the failure classes that consume hours. Experience grants speed at the checklist, never exemption from it.
- "Reading the graph is optional for small merges" — small merges are where the habit is built; the unread large merge is where it pays. Skipping the gate "because it's tiny" trains skipping it always.
- "Aborting looks indecisive in front of the team" — aborting with a stated reason ("need Priya's call on the tax factor — merging tomorrow") reads as senior judgment. Force-merging blind reads as junior panic, whatever the title.
- "One of the three matters less" — they compose: small branches without graph-reading still surprise; graph-reading without calm resolution still guesses; calm resolution on six-week branches still drowns. All three, every branch.

### 5) **Mentor note**

Screen with the ten-minute branching drill: a repo with a diverged feature branch, a dirty tree, and a planted same-line conflict — require (a) the pre-merge gate read aloud (what joins, fork point, tree state), (b) the merge executed with the deliberate posture named, (c) the conflict resolved hunk-by-hunk with the combination tested, or aborted with a stated reason and a tomorrow plan. Under ten minutes with all three correct means branching fluency; each hesitation names its drill (window-size → 1.2, shape → 2.1, markers → 2.2). Re-run before granting merge rights on shared lines — these three habits are the cheapest collaboration gate a team can set.
