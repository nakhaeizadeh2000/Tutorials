## 5.1. Common interview QA: branching and merging

### 1) **What happens on `git merge`?**

The fork-check answer — three cases, no hedging. *No divergence* (target unmoved since the fork): the label slides forward, no commit created (fast-forward). *Divergence without collision* (both moved, different hunks): a two-parent join commit records the coming-together. *Divergence with collision* (same hunk, both sides): the merge stops, markers delimit the question, and a human decides ([2.2](<../2. Joining lines/2.2. Reading conflict markers and resolving without fear.md>)).

- **What a good answer shows**: the candidate predicts shape from state — fork point vs tips — instead of reciting flags. Follow up: "how do you know which case you're in *before* merging?" (`log main..<branch>`, `merge-base` — the pre-merge gate from [4.1](<../4. Important points to remember/4.1. Branching checklist habits mentors insist on.md>)).
- **Red flag**: "merge combines the branches" with no mention of the three cases — or calling fast-forward "a merge commit." Shape confusion predicts blind merges.

```bash
# The three cases, demonstrated (all verified on Git 2.53.0 this session)
git merge feat/small        # Updating c4f7891..367ed42 / Fast-forward — no divergence
git merge --no-ff feat/big  # Merge made by the 'ort' strategy — diverged, join recorded
git merge feat/clash        # CONFLICT (content) ... Automatic merge failed — same hunk, human decides
```

### 2) **Fast-forward vs merge commit — which and when?**

The judgment question — linear history vs preserved shape, team policy over dogma ([2.1](<../2. Joining lines/2.1. Fast-forward vs true merges.md>)). Default slide for undiverged work (common case, readable); `--no-ff` where the join itself matters (release lines, integration points worth reverting as units); `--ff-only` where a surprise join means "someone moved underneath me" (shared pulls — Domain 04).

- **What a good answer shows**: trade-off reasoning, not a favorite flag — "who reads this history, and what operation (bisect vs revert) do they perform most?" Bonus: merge messages naming the joined *idea*, never the deleted label.
- **Red flag**: "`--no-ff` always, to be safe" — safety theater that trades noise for signal. Or "fast-forward rewrites history" — it moves one label, touching nothing.

### 3) **Resolve this conflicted hunk**

The practical exercise — hand them the verified hunk from this domain and watch the loop, not just the answer:

```text
<<<<<<< HEAD
price = 10 * 1.2
=======
price = 12
>>>>>>> feat
```

Expected: read top (HEAD/ours) vs bottom (theirs), propose `price = 12 * 1.2` honoring both — or defend picking one side with a reason — then state the loop (test the combination, `add`, commit) and the abort option if context is missing. The decision sentence matters more than the arithmetic: "whose factor, whose base, and how would you verify?"

- **What a good answer shows**: markers read as a question (which side, or what combination, and why) plus the test step for the *combination* — neither side ran that code. Mentioning `grep '<<<<<<<'` before `add` signals scar tissue from staging markers once.
- **Red flag**: deleting one side silently ("take theirs, simpler") with no reason and no test — or freezing ("I'd ask someone else") with no abort-and-plan. Both predict production guesses.

### 4) **Rapid-fire drills**

- "`switch -c` vs `checkout -b`?" — same result; `switch` can't touch files, so teach it first ([1.1](<../1. Branches in daily use/1.1. Creating switching and deleting branches.md>)).
- "Delete a merged vs unmerged branch?" — `-d` guards (refuses unmerged, `rc=1`), `-D` overrides with a stated reason after `log main..<name>` inspection.
- "Dirty tree, need to switch?" — carries when paths don't collide, refuses when it would overwrite; `status` first, commit-or-stash on refusal.
- "Same conflict three merges in a row?" — `rerere`: resolve once (`Recorded resolution`), recurrences arrive pre-filled (`Resolved ... using previous resolution`), verify before `add` ([3.1](<../3. Reuse and safety/3.1. Rerere and merge confidence.md>)).
- "Branch naming that survives triage?" — `<type>/<area>-<what>`: `feat/cart-guest-checkout`, `fix/login-loop` ([1.2](<../1. Branches in daily use/1.2. Short-lived branches and the feature-branch habit.md>)).
- "When do you `merge --abort`?" — the moment context runs out; the attempt cost nothing, the conflict waits ([2.2](<../2. Joining lines/2.2. Reading conflict markers and resolving without fear.md>)).

### 5) **Mentor note**

Grade branching interviews on *prediction*, not recall: can the candidate state the merge shape before running it, the conflict outcome before opening the file, the deletion result before typing `-d`? Recall answers ("`-D` force-deletes") hire hands; prediction answers ("`-d` will refuse here because nothing else points at those commits") hire owners. The whiteboard fork diagram from 2.1's mentor note doubles as the interview prop — draw two dots, ask "merge now, what shape?" — then add a commit to each side and ask again. Candidates who update their answer with the state pass; candidates repeating one posture fail.
