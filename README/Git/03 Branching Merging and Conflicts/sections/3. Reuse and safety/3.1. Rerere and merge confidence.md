## 3.1. Rerere and merge confidence

### 1) **Record, reuse, relax**

**Definition** — `rerere` (reuse recorded resolution) watches your conflict resolutions and replays them: resolve an identical hunk conflict once, and every future occurrence of the same conflict arrives pre-resolved. Verified end-to-end on Git 2.53.0: the first merge conflicts (`rc=1`), resolving + committing prints `Recorded resolution for 'f.txt'`; recreating the same conflict prints `Resolved 'f.txt' using previous resolution.` — and the file already holds the recorded outcome (`v = 5`), still staged as unmerged (`UU`) awaiting your `add`.

- **What problem it solves**: long-lived branches re-conflict on the same hunks every time they sync — the identical `cart.txt` decision, made Tuesday, reappears Thursday and again at final merge. Without `rerere` each recurrence costs a fresh decision (and risks a *different* answer to the same question, which is how Thursday's merge silently contradicts Tuesday's). With it, repetition becomes confirmation: review the replayed hunk, test, `add`, done.
- **Modern guidance** — trust but verify each replay: `rerere` replays text, not intent — if the surrounding code changed since the recording, the replayed hunk can be stale-but-plausible. Read every `Resolved ... using previous resolution` line as "here's what you said last time," run the test, then commit. Never `add` a replayed file blind.

```bash
# GOOD: first resolution teaches, recurrences confirm
git merge side
#  CONFLICT (content): Merge conflict in f.txt   (rc=1 — decide once, carefully)
#  ... edit f.txt, test, add, commit ...
#  Recorded resolution for 'f.txt'.   <- the lesson is stored in .git/rr-cache/
# ... days later, same hunk collides again ...
git merge side
#  CONFLICT (content): Merge conflict in f.txt
#  Resolved 'f.txt' using previous resolution.   <- pre-filled with v = 5
git diff f.txt   # verify the replay still fits TODAY's surrounding code, then add + commit
# BAD: answering the same hunk three times from memory — the third answer drifts
```

### 2) **Train it before you need it**

**Definition** — `rerere` learns only while enabled: `git config --global rerere.enabled true` turns on recording everywhere, starting now. Past resolutions (made while it was off) were never recorded and can never be replayed — the cache has no retroactive memory. Verified: the `rr-cache` directory appears only after a recorded resolution under an enabled config.

- **Why it matters (correctness)**: engineers enable `rerere` mid-crisis — mid-rebase, mid-release — and discover an empty cache exactly when repetition peaks. The tool pays off on the *third* identical conflict, which means the first two had to happen while it watched. Enabling globally today costs nothing (a few kilobytes of `rr-cache` per resolution) and buys the replay exactly when the long-lived branch starts re-hurting.
- **Modern guidance** — enable globally on every machine you merge on, today, as onboarding step zero — alongside `user.name` and `init.defaultBranch`. Pair it with `rerere.autoupdate` (replays stage themselves when the replay is exact, skipping the manual `add` for byte-identical cases) only after the team trusts the verify-before-`add` reflex — autoupdate removes the pause that catches stale replays.

```bash
# GOOD: onboarding step zero — recording starts before the first conflict
git config --global rerere.enabled true
git config --global rerere.autoupdate true   # only after the verify reflex is habit
ls .git/rr-cache/   # 7ce5dacb... — one directory per recorded conflict shape
# BAD: enabling mid-release and expecting the cache to know last month's resolutions
```

### 3) **Shared resolutions need sharing**

**Definition** — `rr-cache` lives in `.git/`, which never pushes, fetches, or clones — every engineer's cache is private. Your recorded resolution helps exactly one person: you, on this machine. Teams that need shared answers must share them through another channel.

- **Why it hurts when missing (correctness, maintainability)**: the senior resolves the gnarly `auth.js` conflict on Monday; the junior hits the identical hunk Wednesday and answers differently — now the same question has two committed answers on two lines, and the final merge conflicts *with itself*. Engineers who assume `rerere` is team-wide stop communicating resolutions ("the tool remembers"), which is precisely backwards: the tool remembers locally, so humans must broadcast deliberately.
- **Modern guidance** — spread resolutions three ways: short branches (leaf 1.2) so the same conflict rarely reaches two people; documented patterns ("tax factor always wins over base price — see merge 9f31ac") for recurring domain decisions; and for chronic re-conflicting long lines, a `rerere-trainable` workflow — one engineer owns the sync merges so one cache sees every recurrence. Never promise juniors that "Git will remember" without the local-only qualifier.

```bash
# GOOD: one owner per long line — one cache sees every recurrence
#  owner syncs release/* weekly, resolves once, rerere replays on later syncs
#  decision log in the merge message: "kept main's tax factor (policy: tax wins)"
# BAD: five engineers syncing the same long branch independently — five caches, five answers
```

### 4) **Common confusion**

- "`rerere` resolves conflicts automatically" — it replays *your recorded answer* into the working file and still stops the merge (`rc=1`, still `UU`): you verify, test, `add`, commit. It removes repetition, not judgment.
- "Enabling it changes merge behavior" — recording is invisible until a recurrence: merges conflict exactly as before, plus one `Recorded resolution` line at commit time. There is no behavior to fear on day one.
- "The cache grows forever" — entries expire with `rerere gc` (60-day default for unresolved, longer for referenced); repos accumulate kilobytes, not megabytes. Never hand-prune `rr-cache`.
- "`rerere` replaces understanding markers" — it sits *atop* leaf 2.2's loop: the first resolution must be a good one, because every replay copies it. A wrong recorded answer is a wrong answer on subscription.

### 5) **Performance note**

`rerere` costs a hash comparison per conflicted hunk — microseconds against the minutes of a human decision. The measurable effect is on *repeat* merges: syncing a long-lived branch drops from N decisions to N confirmations. But the larger performance lever remains branch lifetime (leaf 2.2): `rerere` amortizes repetition, short branches eliminate it. Enable both; credit the branches.

### 6) **Mentor note**

Check `rerere.enabled` in every onboarding review — it takes ten seconds and pays compound interest. Then manufacture the lesson: have the junior create the same conflict twice in a scratch repo and watch the second arrive pre-resolved. The visible `Resolved ... using previous resolution` line is the conviction moment. Watch for the two failure postures: the blind-adder (stages replays without reading — fix with the `git diff` before `add` ritual) and the broadcaster (assumes the team shares the cache — fix by asking "where does `rr-cache` live, and does it push?"). Review check: any recurrence of an identical conflict resolved differently on two lines gets traced to "who replayed what, and did they verify?"
