## 1.1. What Git is and why snapshots win

### 1) **Distributed means every clone is a full backup**

**Definition** — Git is a distributed version control system: every clone contains the complete history of the project, not just the latest files. There is no single computer whose disk failure loses the past — any clone can rebuild the whole story.

- **What problem it solves**: centralized systems (CVS, Subversion) keep history on one server. Server down means no commits, no history, no diffs — and server loss means history loss. Git moves the history to every developer's machine, so committing, branching, and reading history all work offline, on a plane, or during an outage.
- **Modern guidance** — treat hosting (GitHub, GitLab) as *convenience and collaboration*, not as the source of truth's only copy. The source of truth is a social agreement ("`main` on the shared remote is what we ship"), backed by the fact that dozens of clones each hold the full history — as of the September 2026 era (Git 2.55 stable) this is standard practice in every team this track targets.

```bash
# The whole history arrives with the clone — nothing is fetched lazily
git clone https://github.com/example/app.git
cd app
git log --oneline | wc -l   # every commit, available offline from here on
```

### 2) **Snapshots, not diffs**

Each commit records what *every tracked file looked like* at that moment — a full snapshot of the project tree. When you ask what changed between two commits, Git computes the difference on demand. Older systems stored per-file reverse diffs as the primary data; in Git, diffs are a presentation layer over snapshots.

- **History in one paragraph**: Linus Torvalds built Git in 2005 for the Linux kernel after the BitKeeper license was revoked. Kernel history was huge and branching was constant, so the design optimized for cheap branches and instant diffs anywhere in history — snapshots plus content addressing made both trivial, while delta-chains would have made old commits expensive to reconstruct.
- **Modern guidance** — think "which state?" before "what changed?". `git show <commit>` displays a stored state; `git diff A B` computes a view. This reflex pays off in every later domain: checkout moves you between states, revert creates a state that undoes another, and bisect searches states for a fault.

```bash
# BAD mental model: "commit 7 contains 3 changed lines"
# GOOD mental model: "commit 7 is the whole project at 14:02" — diffs are computed views
git show --stat HEAD        # the stored snapshot, summarized
git diff HEAD~1 HEAD        # same two snapshots, rendered as a diff on demand
```

### 3) **Integrity by hash**

**Definition** — every Git object (file blob, directory tree, commit) is stored under the hash of its contents — SHA-1 historically, SHA-256 in repositories created with the modern object format. The name *is* the checksum, so silent corruption is impossible: if a single byte changes, the hash no longer matches and Git reports it.

- **Why it matters (correctness)**: a version control system that can silently return wrong file contents is worse than none — you would ship corruption with confidence. Content addressing turns every read into a verification: checkout, clone, and fetch all re-hash what they receive.
- **Modern guidance** — two practical consequences. First, never edit anything inside `.git/objects` by hand — you would create objects whose names lie about their contents. Second, when a tutorial says "commit IDs are hashes", understand the direction: the ID is *derived from* the content (plus metadata), which is why two identical trees committed with identical metadata hash identically, and why history is tamper-evident.

```bash
# Every object is verifiable on demand
git fsck --full   # re-hashes all objects; reports corruption instead of hiding it
```

### 4) **Common confusion**

- "`git commit` uploads my work" — no, it snapshots locally. Nothing leaves your machine until `push` (Domain 04 owns remotes — the most important boundary in this leaf).
- "Git stores diffs to save space" — the *model* is snapshots; packfiles and delta compression are a storage optimization Git applies behind the scenes. Confusing the two makes `rebase` and `cherry-pick` (Domain 05) seem magical instead of mechanical.
- "The remote is the backup, my clone is disposable" — both directions are true simultaneously: your clone is a full backup of history, and the shared remote is the collaboration point. Losing an unpushed local commit still loses work (only *pushed* history is backed up elsewhere).
- "SHA-1 means Git is broken" — collision attacks on SHA-1 are real in theory, which is why the SHA-256 object format exists; Git also ships collision detection for SHA-1 repos. For everyday engineering this changes nothing about how you commit.

### 5) **Mentor note**

Teach snapshots with a camera, not a ledger: each commit is a photograph of the whole project, and `diff` is laying two photographs side by side. Juniors who picture a ledger ("commit 7 holds 3 lines") stumble on checkout ("where did my files go?") and on revert ("why did it create a *new* commit instead of deleting?"). Photographs answer both instantly: checkout swaps which photo is on the desk; revert takes a new photo that happens to look like an older one. Check understanding with one question: "if I delete a file and commit, is the file's content still in the repo?" (Yes — earlier snapshots still hold it, until history itself is rewritten in Domain 05.)
