## 1.2. The commit DAG: history as a graph

### 1) **Commits point backwards**

**Definition** — each commit stores the ID of its parent commit (or parents, for merges). History is therefore a chain of backwards pointers: from any commit you can walk to every ancestor, but nothing points forward to children. The newest commits are the *tips* you start from; the oldest commit has no parent.

- **What problem it solves**: "what happened before this?" must be answerable forever, even after branches are deleted and remotes disappear. Backwards pointers make ancestry a property of the data itself — `git log` needs no server, no index, no branch list; it just follows parent links from wherever you stand.
- **Modern guidance** — read `git log` output as "start here, walk backwards". `HEAD~3` means "three parent-hops back from here", and every `~`/`^` revision expression is graph navigation, not arithmetic on a list. When a command talks about "reachable" commits (fetch, gc, push), it means "walkable backwards from some tip".

```bash
# History is walked backwards from a tip — try it on any repo
git log --oneline -5          # five hops back from HEAD
git show HEAD --pretty=%P     # parent ID(s) of HEAD — the backwards pointer itself
git log --oneline HEAD~3 -3   # start three hops back, show three more
```

### 2) **Branches are movable labels**

**Definition** — a branch is a lightweight, movable pointer to one commit — a sticky note, not a folder. Creating a branch writes a 41-byte file; switching branches moves `HEAD` to a different sticky note; committing slides the current sticky note forward to the new commit.

- **What problem it solves**: in centralized systems branching copied directories on the server — slow and heavy, so developers avoided it and worked on long-lived shared lines. Making branches nearly free changed team behavior: a branch per feature, per experiment, per fix became the default, because creating and destroying them costs nothing.
- **Modern guidance** — never picture a branch as "containing" commits. Ask instead "which commits are reachable from this label?" — that set changes every time the label moves. This is why deleting a merged branch loses nothing (the commits remain reachable from `main`) while deleting an *unmerged* branch orphans its commits (no label points at them anymore — recovery via `reflog` is Domain 05's territory).

```bash
# BAD mental model: "the feature branch holds my 3 commits"
# GOOD mental model: "the label 'feature' points at my newest commit; main does not reach it yet"
git branch feature            # new sticky note on the current commit — nothing copied
git log --oneline --graph --all -8   # labels (* branch names) sitting on graph tips
```

### 3) **Merges are commits with two parents**

**Definition** — a merge commit is an ordinary snapshot with two (or more) parents instead of one: it records the state where two lines of history join, and its ancestry includes *both* sides. The graph shape — where lines fork and rejoin — is the true structure of your history; timestamps are decoration.

- **Why it matters (correctness, review)**: `git log` in date order can interleave unrelated lines and imply a sequence that never happened. `git log --graph` shows the fork/join shape: which commits came from the feature line, which from `main`, and exactly where they joined. Code archaeology ("which release contains this fix?") is graph reachability (`git branch --contains`, `git tag --contains`), not date comparison.
- **Performance note** — graph walks are proportional to commits visited, and Git's packfiles plus generation-number optimization make even million-commit histories (Linux kernel, Chromium) traversable in milliseconds. If `log --graph` feels slow, you are usually rendering too much (add `-20` or a path filter) — measure by limiting the walk before blaming the repo size.

```bash
# GOOD: read shape, not dates — graph shows the fork and the join
git log --graph --oneline -10
# GOOD: answer "where did this fix land?" with reachability, not timestamps
git branch --contains <commit>   # which labels can walk backwards to this commit
```

### 4) **Common confusion**

- "Branches copy my files" — nothing is copied; a branch is a pointer write. The working tree changes on *checkout* because files are materialized from a different snapshot, not because the branch "holds" them.
- "`main` is special" — `main` is a sticky note like any other; its privilege is purely social (the agreed integration line). Git treats it identically to `feature/login` — every command in this track works the same on both.
- "Merge order in `log` is chronological truth" — date-ordered `log` interleaves parallel lines; only `--graph` (topological) shows what descended from what. Prefer `--graph` whenever more than one line exists.
- "Deleting a branch deletes work" — deleting a label never touches commits; it only removes one way to reach them. Merged work stays reachable from the merge target; unmerged work becomes unreachable-but-present until garbage collection (and recoverable via `reflog` — Domain 05).

### 5) **Mentor note**

Draw the graph before touching commands: three circles in a line (`A ← B ← C`), one label `main` on `C`. Then branch: new label `feature` also on `C`. Then commit on `feature`: new circle `D` with parent `C`, label slides to `D`. Juniors who can draw this sequence understand branching, checkout, fast-forward, and merge before running a single command — and they stop fearing "losing" branches. Review check: ask "after `git branch feature`, how many commits does `feature` contain?" Anyone answering with a count instead of "it points at the same commit as HEAD" needs the sticky-note correction. API-design echo: Git's reference model (labels pointing at immutable objects) is the same shape as tags, remote-tracking branches, and `HEAD` itself — one model, four uses.
