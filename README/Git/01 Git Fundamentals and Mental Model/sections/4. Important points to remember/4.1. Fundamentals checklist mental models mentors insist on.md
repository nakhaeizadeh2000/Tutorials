## 4.1. Fundamentals checklist (mental models mentors insist on)

### 1) **Snapshot reflex**

Ask "which commit shows this state?" before "what changed?" — states are primary, diffs are derived. When a bug report arrives, the first move is locating the state (`log`, `bisect` later) — not reading a diff without knowing which two snapshots it connects.

- **Why it hurts when missing**: developers without the reflex debug the wrong layer — they diff `main` against a stale local branch and "find" changes that never shipped, or they `checkout` a file from the wrong commit and test a state nobody runs. Every wasted hour traces back to an unnamed state.
- **Modern guidance** — make it verbal: narrate "I am on `main` at `a3f9c1`, the bug appeared between `v2.3` and `v2.4`" before touching commands. If you cannot name the states, run `git log --oneline -5` and `git status` until you can — orientation before operation, always.

### 2) **Three-area discipline**

Stage deliberately, commit atomically, check `status` before and after — the double-`status` sandwich from [2.1](<../2. The three areas/2.1. Working tree index HEAD and the file lifecycle.md>) as non-negotiable habit. The sandwich catches the staged debug line, the forgotten new file, and the half-staged edit — the three most common commit defects, all visible in one glance each.

- **Why it hurts when missing**: undisciplined commits are the root cause behind half of Domains 03–06's rescue operations — unmergeable branches (mixed concerns cannot merge cleanly), unrevertable history (one commit does three things), unreviewable PRs (the diff tells no story). Discipline here is prevention; everything later is cure.
- **Modern guidance** — enforce it mechanically until it is reflex: a shell alias or prompt indicator showing branch + dirty state makes skipping `status` harder than running it. In code review, reject commits the author cannot describe in one sentence — the standard this track holds from the first commit onward.

```bash
# The sandwich — memorize the rhythm, not just the commands
git status          # before: what exists in each area?
git add <files>     # compose: claim exactly what belongs together
git diff --staged   # review: read the snapshot you are about to freeze
git commit -m "area: imperative summary"
git status          # after: tree quiet? (catches the half-staged edit)
```

### 3) **Graph literacy**

Read `log --graph` shape — branches as labels, merges as two-parent commits, `HEAD` as "you are here". Before pulling, merging, or asking for help, produce the graph: most Git questions ("why can't I push?", "where did my commits go?", "what will this merge do?") answer themselves once the shape is visible.

- **Why it hurts when missing**: graph-illiterate developers operate blind — they merge without knowing the fork point, push without knowing the remote moved, delete branches without knowing reachability. Every "Git ate my work" story ever told is a graph that was never drawn.
- **Modern guidance** — keep one graph command in muscle memory and use it daily: `git log --graph --oneline --all -15`. Fifteen lines is enough to orient in any workflow; `--all` shows every label so nothing hides. When the shape confuses you, draw it on paper with circles and sticky notes ([1.2](<../1. Thinking in snapshots/1.2. The commit DAG history as a graph.md>)) — the physical model never lies.

```bash
# GOOD: orient in the graph before operating — daily habit
git log --graph --oneline --all -15   # shape first, commands second
# BAD: git pull on a branch whose graph you have never looked at
```

### 4) **Common confusion**

- "Checklists are for beginners" — pilots with ten thousand hours still run checklists, because the failure mode is not ignorance but skipping. The sandwich takes five seconds; the rescue takes an hour.
- "Atomic commits slow me down" — committing often in small units is *faster* to review, revert, and bisect than untangling one large commit later. Speed is measured at review and rescue time, not at `commit` time.
- "I will learn the graph when I need branching" — the graph *is* branching. Domains 03–05 assume you already read shape fluently; arriving without it turns every merge into superstition.

### 5) **Mentor note**

Screen for these three reflexes in every junior's first month with one five-minute exercise: hand them a repo with staged, unstaged, and untracked changes on a detached `HEAD`, and ask for (a) which commit they stand on, (b) what the next commit would contain, (c) how to get back to `main` safely. Correct answers in under two minutes mean the fundamentals stuck; hesitation names exactly which reflex to drill. Re-run the drill before granting merge rights — graph literacy is the cheapest gate a team can set.
