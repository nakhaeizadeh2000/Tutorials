## 3.1. Init, clone, config, and your first commit

### 1) **Init vs clone**

**Definition** — `git init` creates an empty repository in an existing directory (a fresh `.git`, no commits, no remote). `git clone <url>` copies a remote repository — full history plus a working tree — and wires the remote as `origin` automatically. Two births: start-from-nothing vs start-from-shared-history.

- **What problem it solves**: new work and joined work begin differently. A personal script starts as local files that deserve history (`init`); team work starts as someone else's history you continue (`clone`). Using the wrong birth doubles effort — `init` + manual remote wiring when `clone` did it in one step, or `clone` of nothing when `init` was the honest start.
- **Modern guidance** — default branch naming: modern Git (2.28+, and standard ever since) lets you choose with `git init -b main`, and hosting platforms create `main` by default — as of the September 2026 era (Git 2.55) `main` is the expected name in every new repo. For `init`, set it explicitly so the first commit lands on `main` instead of a legacy default you rename later.

```bash
# Birth 1: local files that deserve history
mkdir notes && cd notes
git init -b main              # empty repo, default branch named up front
# Birth 2: continue someone else's history (remote wired as origin for free)
git clone https://github.com/example/app.git
# BAD: git init inside an existing clone — nested repos that fight over your files
```

### 2) **Identity config is a correctness control**

**Definition** — every commit stamps `user.name` and `user.email` into its metadata permanently. `git config` sets them per-repo (default, preferred) or globally (`--global`, your machine-wide identity). Unset identity blocks the first commit — Git refuses to create anonymous history.

- **Why it matters (correctness)**: identity is how `blame`, `log`, and hosting platforms attribute work — wrong email means your commits do not link to your GitHub profile, and a teammate's laptop default means their commits wear your name. Because identity is baked into the commit hash, fixing it later means rewriting history (Domain 05), not editing a field.
- **Modern guidance** — set identity per-repo for work machines (company email here, personal email there), `--global` only for the fallback. Verify with `git config user.email` inside the repo *before* the first commit — ten seconds now saves a history rewrite later. Also set `init.defaultBranch main` globally once, so every future `init` inherits it.

```bash
# GOOD: identity verified before the first commit — per-repo over global
git config user.name "Ada Lovelace"
git config user.email "ada@company.com"
git config user.email            # verify — the value that will be stamped
git config --global init.defaultBranch main   # once per machine, inherited forever
# BAD: committing with a borrowed laptop default, then discovering
# git log shows someone else's name baked into immutable history
```

### 3) **Add, commit, log: the smallest complete loop**

**Definition** — the complete first-commit loop: create or edit files, `git add` the ones that belong (new files are untracked until added — `add` both stages edits and enrolls new files), `git commit -m` with a message describing the change, `git log` to verify the snapshot exists.

- **What problem it solves**: until this loop runs, everything before it is theory — the three areas, the DAG, the snapshots. One real commit makes them concrete: `status` goes quiet, `log` shows your name, and the graph has a second dot. Every workflow in Domains 02–06 is this loop repeated with more deliberation.
- **Modern guidance** — write the message as a summary of the change in the imperative ("add", "fix", "reject" — the convention `git log` history and every changelog tool assume). Verify with `git log --oneline -3` and `git status` (clean tree) — the loop is only complete when the tree is quiet and the log shows your commit on `main`.

```bash
# The smallest complete loop — run it verbatim to make every earlier leaf concrete
echo "# notes" > README.md
git add README.md                          # enroll the new file + stage it
git commit -m "docs: start project notes"  # snapshot with an imperative message
git log --oneline -3                       # your commit on top — history is real now
git status                                 # "nothing to commit, working tree clean" — loop complete
```

### 4) **Common confusion**

- "`git add .` adds everything, that is fine" — `add .` stages all tracked edits *and* enrolls every untracked file under the current directory, including stray credentials, build output, and editor backups. Prefer naming files (or a reviewed `status` first) until `.gitignore` discipline (Domain 02) protects you.
- "The commit message does not matter for now" — messages are the only human-readable index of history; "wip" and "stuff" compound into an unreadable `log` within weeks. One imperative sentence is the cheapest documentation you will ever write.
- "`git log` shows nothing after init" — correct: no commits exist yet, so there is no history to walk. `log` needs at least one snapshot; the loop above creates it.
- "Clone already configured my identity" — clone copies history and remotes, never identity. `user.name`/`user.email` come from your local config or nowhere — verify in every fresh clone on a new machine.

### 5) **Mentor note**

Watch a junior's first commit like a driving test: the sequence `status → add (named files) → status → commit → log → status` performed without prompting is the license. The two failure modes are symmetric — committing blindly without the sandwich (debug lines shipped) and freezing at `add .` anxiety (nothing committed for days). Cure the second with visible practice: five tiny commits in an hour on a scratch repo beats one lecture on atomicity. Review check for this leaf: `git log` shows their name spelled right, their email, `main` as the branch, and a clean `status` — four facts, ten seconds, done.
