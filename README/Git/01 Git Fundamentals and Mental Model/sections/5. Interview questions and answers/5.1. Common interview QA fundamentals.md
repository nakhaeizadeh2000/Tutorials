## 5.1. Common interview QA: fundamentals

### 1) **Git vs centralized VCS**

The classic opener — "why Git instead of Subversion?" Answer in one distributed sentence, then expand: every clone holds full history, so commits, branches, and history reads work offline; branching is a pointer write, so per-feature branches are free; integrity is hashed, so corruption is detected, not silent.

- **What the interviewer is really testing**: whether you understand the architectural trade, not whether you memorized a feature list. Centralized systems optimize for access control and huge binary assets; Git optimizes for offline work, cheap branching, and history integrity. Saying "Git is better" without the trade signals recitation.
- **Modern guidance** — close with the honest caveat: Git is weak at giant binaries (every clone carries every version — LFS or artifact stores cover that, a workflow topic for Domain 06) and has no built-in path-level permissions (hosting platforms add them). Candidates who volunteer the weaknesses get trusted on the strengths.

```bash
# One command that proves the distributed claim — run it with no network
git log --oneline -5   # full history, offline, from your clone alone
```

### 2) **Snapshots vs deltas**

The separator question — "does Git store diffs?" The precise answer: the *model* is snapshots (each commit records every tracked file's full content), while packfiles apply delta compression *as a storage optimization* behind the scenes. `git diff` computes views on demand; nothing in the object model is a delta.

- **What the interviewer is really testing**: model-vs-implementation thinking. Engineers who confuse the two predict wrong behavior — they expect old commits to be "expensive" (wrong: any snapshot materializes directly) or `rebase` to "replay diffs" (wrong direction: it re-applies changes onto new parents — Domain 05's full story).
- **Modern guidance** — answer with the consequence, not just the fact: "because commits are snapshots, `checkout` of any commit costs the same, and `diff` between any two commits is computed, never stored." Then volunteer the packing detail to show you know both layers ([1.1](<../1. Thinking in snapshots/1.1. What Git is and why snapshots win.md>)).

### 3) **The three areas in one breath**

"Walk me through a change from edit to commit" — working tree (you edit), index (you stage with `add`), repository (you freeze with `commit`, `HEAD` advances). Then name the inspection commands: `status` shows all three bands, bare `diff` the unstaged boundary, `diff --staged` the staged boundary ([2.1](<../2. The three areas/2.1. Working tree index HEAD and the file lifecycle.md>), [2.2](<../2. The three areas/2.2. Status diff and seeing what changed.md>)).

- **What the interviewer is really testing**: whether your daily loop is deliberate. Follow-ups go straight at the weak points: "you edited, staged, edited again, then committed — what did the commit capture?" (the staged version only) and "how do you commit only half a file?" (`add -p`). Both are answered correctly only by people who stage intentionally.
- **Modern guidance** — narrate the double-`status` sandwich as your personal discipline, not as theory. Interviewers hire habits: "I read `status` before staging, `diff --staged` before committing, `status` after" beats any definition recital.

### 4) **Rapid-fire drills**

- "What is `HEAD`?" — the pointer to your current commit (usually via a branch label); new commits build on it; detached means it points at a commit with no label.
- "What is a branch, really?" — a movable label on one commit, not a container. Deleting it removes the label, never the commits.
- "What does `git clone` set up that `git init` does not?" — full history copy plus the `origin` remote wiring.
- "Where is your name stored per commit?" — `user.name`/`user.email` baked into commit metadata at creation; fixing it later rewrites history.
- "Staged a file, edited it again, committed — what got committed?" — the staged content; the later edit stays unstaged. (`status` after committing proves it.)
- "How do you see what the next commit contains?" — `git diff --staged`, always, before committing.

### 5) **Mentor note**

Prep juniors with the "one breath, one caveat" format: every fundamentals answer fits in two sentences of model plus one honest limitation. Interviewers promote candidates who bound their own claims ("snapshots as the model — delta compression as the storage detail", "distributed history — weak at giant binaries"). Run mock interviews where the follow-up always asks "when does that break?" — the engineers who survive that follow-up six times in a row pass real loops. And remind them: "I verify with `status`/`log --graph` before operating" is a stronger closing line than any definition.
