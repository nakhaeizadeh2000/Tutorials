## 2.1. Working tree, index, HEAD, and the file lifecycle

### 1) **Three places a change can live**

**Definition** — every change sits in exactly one of three areas. The *working tree* is your files on disk — what you edit. The *index* (staging area) is Git's loading dock — what the next commit will contain. *HEAD* is the pointer to your current commit — what the last snapshot recorded. A change flows working tree → index (`git add`) → repository (`git commit`).

- **What problem it solves**: without a staging step, every commit would sweep up everything you touched — the half-finished experiment alongside the bug fix. The index separates "I edited it" from "I mean it": you compose the next snapshot deliberately instead of photographing a messy desk.
- **Modern guidance** — build the habit in this order: edit, `git status`, stage exactly what belongs together, `git status` again, commit. The double-`status` sandwich (before staging and before committing) is the cheapest correctness control in Git — as of the September 2026 era every senior workflow this track teaches assumes it.

```bash
# Watch a change move through all three areas
echo "fix" >> app.js            # 1. working tree: edited, unstaged
git add app.js                  # 2. index: staged — now part of the next commit
git commit -m "fix: handle empty cart"   # 3. repository: snapshotted, HEAD moves
```

### 2) **Staging is intentional committing**

**Definition** — `git add` copies the current content of a file into the index; `git commit` snapshots *the index*, not the working tree. Edits made after `git add` stay unstaged — the commit contains what you staged, byte for byte, regardless of what the file looks like now.

- **Why it matters (correctness)**: this is the mechanism behind atomic commits — one logical change per snapshot. Fix a typo in file A while building a feature in files A and B? Stage only the feature hunks (`git add -p`), commit, then stage the typo separately. Reviewers, `bisect` (Domain 06), and `revert` (Domain 05) all assume each commit does one thing; staging is how you keep that promise when your editing did two.
- **Modern guidance** — stage at the granularity of the *commit you want*, not the file you touched: whole files for single-purpose edits, `git add -p` (interactive hunk staging) whenever a file mixes concerns. If `git status` after staging shows anything staged you cannot describe in one sentence, unstage and split.

```bash
# GOOD: commit contains exactly what was staged — verify before committing
git add -p app.js     # stage only the fix hunks, leave the experiment unstaged
git status            # confirm: staged = fix, unstaged = experiment
git commit -m "fix: reject negative quantities"
# BAD: git commit -a  # sweeps every tracked edit into one snapshot — atomicity lost
```

### 3) **HEAD is "where I am"**

**Definition** — `HEAD` is the pointer that says which commit (and usually which branch tip) your working tree is built on. Normally `HEAD` points at a branch label ("attached"), and the branch points at a commit — so committing slides the branch forward and `HEAD` follows. After `git checkout <commit>` directly, `HEAD` points at a commit with no branch ("detached") — new commits there have no label to slide.

- **What problem it solves**: Git needs to know what "the current state" means for `diff`, `status`, `commit`, and `merge`. `HEAD` is that anchor: `git diff HEAD` compares disk against the current commit, `git commit` parents the new snapshot on it, and checkout redefines it.
- **Modern guidance** — treat "detached HEAD" as read-only mode: perfect for inspecting old code or building a release tarball, dangerous for new work (commits there are label-less and easy to lose — Domain 05 covers recovery). Day to day, always confirm you are on a branch (`git status` prints it on line one) before writing code.

```bash
# GOOD: know where you stand before you commit
git status            # first line: "On branch main" — or a detached-HEAD warning
git rev-parse HEAD    # the commit ID your next commit will build on
git symbolic-ref HEAD # which branch label HEAD follows (fails when detached — that is the signal)
```

### 4) **Common confusion**

- "`git add` means the change is safe now" — staged is not committed: the index lives in `.git` but has no snapshot protecting it. Only `commit` creates durable history; `add` merely composes it.
- "Committing snapshots my files" — it snapshots the *index*. The classic shock: edit, `add`, edit again, commit — the commit holds the first version, and the second edit is still unstaged. `git status` after every commit catches this in one glance.
- "Detached HEAD destroyed my branch" — nothing was destroyed; `HEAD` just stopped following a label. Your branches and commits are untouched — re-attach with `git switch <branch>` (or `git switch -c new-branch` to keep commits made while detached).
- "`git commit -a` is a shortcut for the same thing" — `-a` stages *all tracked modifications* and commits, skipping the deliberate composition step and sweeping untracked files under the rug (it never adds new files). Convenient for solo throwaway work; a review smell in shared branches.

### 5) **Performance note**

The index is a single binary file (`.git/index`) listing staged entries — `add` and `status` update and scan it in milliseconds even in huge trees, because Git stats files (size, mtime) before hashing contents. If `git status` ever feels slow in a large repo, the cause is almost always untracked-file scanning (build output, `node_modules`) — fix it with `.gitignore` rules (Domain 02 owns ignore patterns), not by avoiding `status`. Never skip the double-`status` sandwich for speed: the seconds it costs are the cheapest insurance in the workflow.

### 6) **Mentor note**

Make the three areas physical: three columns on a whiteboard labeled *disk*, *dock*, *history*, and move sticky notes across them as you `add` and `commit`. Juniors who can point at which column a change is in stop asking "will my commit include this?" — they read `status` instead. Enforce the review rule early: any commit whose staged content the author cannot describe in one sentence gets split before review. That single habit, learned here, prevents the thousand-line "misc fixes" commits that make Domains 03–06 painful.
