## 2.2. Status, diff, and seeing what changed

### 1) **Status answers one question**

**Definition** — `git status` reports what the next commit would contain: staged changes (index vs `HEAD`), unstaged changes (working tree vs index), and untracked files (present on disk, unknown to Git). One command, the complete composition of the pending snapshot.

- **What problem it solves**: every other inspection command shows one boundary; only `status` shows all three areas at once, in words instead of diff hunks. It is the orienting command — run when you sit down, before you stage, before you commit, after you commit, when anything surprises you.
- **Modern guidance** — read `status` in three bands, top to bottom: "Changes to be committed" (staged — this is your next commit, review it), "Changes not staged" (tracked edits you have not claimed yet), "Untracked files" (new files Git ignores until `add`). If the first band ever contains something you cannot describe in one sentence, stop and split before committing ([2.1](<./2.1. Working tree index HEAD and the file lifecycle.md>)).

```bash
# The orienting command — three bands, one pending commit
git status
# Short form for scripts and dense terminal work (same three bands, two columns: staged | unstaged)
git status --short   # "M " staged-modified, " M" unstaged-modified, "??" untracked
```

### 2) **Two diffs for two boundaries**

**Definition** — `git diff` (no flags) shows unstaged changes: working tree vs index. `git diff --staged` (synonym `--cached`) shows staged changes: index vs `HEAD`. Each command shows exactly one edge of the three areas — together they account for every modification.

- **What problem it solves**: "what changed?" is ambiguous with three areas — changed relative to *what*? The two diffs remove the ambiguity by naming the boundary. Pre-commit review is always the staged diff (what you are about to freeze); continued work starts from the unstaged diff (what still needs a decision).
- **Modern guidance** — make the staged diff the last thing you read before every commit: `git diff --staged` is the commit's final draft. If a hunk there surprises you, unstage it (`git restore --staged <file>`) rather than committing "and fixing later" — later never comes, but `git log` remembers forever. Reserve bare `git diff` for the edit loop ("what have I done since I last staged?").

```bash
# GOOD: review the exact snapshot you are about to freeze
git diff --staged     # index vs HEAD — this IS the next commit
# Loop companion: what remains unclaimed
git diff              # working tree vs index — still yours to compose
# BAD: committing without reading the staged diff — the "oops, that debug line shipped" classic
```

### 3) **Read diffs hunks-first**

**Definition** — a unified diff is a list of hunks; each hunk header (`@@ -12,7 +12,9 @@`) names the old and new line ranges, context lines (leading space) anchor you, `-` lines leave, `+` lines arrive. File headers (`diff --git`, `index`, `---`/`+++`) say which files participate; rename detection may collapse a move into `similarity index 92% / rename from/to`.

- **Why it matters (reviews, interviews)**: every code-review tool on GitHub renders these same hunks — reading raw diffs in the terminal trains the exact skill the web UI assumes. Interviewers who paste a diff and ask "what broke?" are testing hunk literacy: find the `-` line that removed the guard, trace which `+` line replaced it.
- **Modern guidance** — scan header → hunks → signs. First the file list (are these the files you intended?), then each hunk's context (where in the file am I?), then the `+`/`-` lines (what actually changed?). For noisy diffs reach for filters, not scrolling: `--stat` for the map, `-U1` for tight context, `-- <path>` to isolate one file, `--word-diff` for prose.

```bash
# GOOD: map first, then read — never scroll a 500-line diff raw
git diff --stat             # which files, how many lines each — the map
git diff -- app.js          # isolate one file — the territory
git diff -U1 -- config.yml  # one context line — dense reading for large files
```

### 4) **Common confusion**

- "`git diff` shows everything I changed" — it shows only *unstaged* changes. Freshly staged work vanishes from bare `diff` (it moved to the other boundary) — the classic "my changes disappeared!" panic. They are in `git diff --staged`.
- "Untracked files appear in diffs" — never. Git diffs only tracked content; new files show in `status` as `??` and enter diffs only after `git add -N` (intent-to-add) or a real `add`. An "empty diff" with a dirty `status` almost always means the work is untracked or fully staged.
- "`--cached` and `--staged` are different commands" — synonyms, same boundary. `--staged` reads better; `--cached` survives in old scripts and muscle memory. Prefer `--staged` in everything you write.
- "More context lines are always better" — default `-U3` suits code; for generated files or minified bundles no context setting helps — exclude them (`.gitattributes`/`--stat` triage is Domain 02 territory) instead of reading noise.

### 5) **Mentor note**

Drill the two-diffs reflex with a live exercise: one file staged, one file half-staged (edit → add → edit again). Ask "show me only what the commit contains" (`--staged`), then "show me only what it does not" (bare `diff`), then "prove the second edit is in neither commit-preview" (`status` shows it unstaged, and it appears in bare `diff` only). Juniors who perform this once never again ask where their changes went. Review rule to install: every PR description should be writable from the staged-diff read-through — if the author cannot narrate the diff hunk by hunk, the change is not review-ready.
