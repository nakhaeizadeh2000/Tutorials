## 5.1. Common interview QA: workflows, tags, and releases

### 1) **Trunk vs GitFlow — which for us?**

**Definition** — the judgment question that tests derivation over fashion: given *this* team's deploy cadence, size, and revert speed, which shape (leaf 1.1) and why? There is no correct answer in the abstract — only a correct *derivation* from the team's reality. Strong candidates ask about reality before answering ("how often do you deploy? who approves? how fast can you revert?") and land where the function points.

- **What a good answer sounds like**: "It depends on three things: deploy frequency, release coordination cost, and revert speed. Daily deploys with flags and minute-scale reverts → trunk (small batches, no tolls). Scheduled versioned releases with stabilization needs → GitFlow (parallel lines absorb the wait). Gated SaaS middle → GitHub Flow. For *your* setup [mirrors what they heard], I'd pick [shape] because [cadence reason], protected as [rules], merging via [policy]. And I'd revisit at 10× growth." Seniors add the migration note (shapes change mechanically; habits are the cost) and the mismatch diagnosis ("Git feels slow" usually means shape fighting cadence).
- **Modern guidance** — grade the *questions asked* as highly as the answer: candidates who interrogate deploy reality before prescribing demonstrate senior judgment; candidates who open with "GitFlow is outdated" or "trunk is modern" demonstrate fashion. Red flags: one-shape-fits-all, protection never mentioned (shape without enforcement is folklore), no revisit criterion (strategy as permanent rather than derived).

```bash
# The derivation, sketched (leaf 1.1's function as interview answer)
#  deploys/day × revert-minutes × team-size → shape:
#  20 × 5min × 8   → trunk + squash + flags (tolls would exceed work)
#  1/month × days × 60 → GitFlow + merge-trains (stabilization absorbs the wait)
```

### 2) **Tag moved after release — what broke?**

**Definition** — the trust exercise: release `v1.5.1` shipped, then the tag was re-pointed (re-tagged, force-pushed `refs/tags/*`). What breaks? Everything that resolved the name: deployed artifacts vs rebuilt artifacts diverge (same version, different bits — undebuggable in production), downstream lockfiles/ranges verify hashes or rebuild from the tag (supply-chain mismatch), audit trails lie (the tag no longer names what shipped), and rollback targets the *new* hash (rolling back to the bug you meant to escape). Verified-adjacent premise from leaf 2.1: consumers resolve tags, not memories — moving the resolution moves everyone's reality silently.

- **What a good answer sounds like**: an enumeration of consumers in blast order — builds (same tag, different bits), deploys (can't reproduce the running artifact), downstream pins (hash mismatches, phantom breakages), audits (provenance destroyed), rollbacks (target corrupted). Then prevention: pattern-protect `v*` on the forge (no moves, no deletes without admin ceremony), tag-and-push as one ritual, `ls-remote --tags` reconciliation — and the recovery honesty: already-moved tags can't be un-seen (caches hold both resolutions), so the fix is a *new* PATCH release plus communication, not a silent move-back.
- **Modern guidance** — listen for immutability as *principle*, not preference: juniors say "don't move tags"; seniors say "tags are the coordinate system releases navigate by — moving one corrupts every chart." Instant fail: "just move it back, nobody will notice" (caches noticed; builds noticed; the lie compounds). Follow-up separating senior: "how do you release the fix then?" (new PATCH version, notes referencing the incident, yank/deprecate markers where the registry supports them — forward motion, never history editing).

```bash
# Prevention and honest recovery (leaf 2.1 mechanics + this leaf's judgment)
git push origin v1.5.1 && git ls-remote --tags origin   # confirm before announcing
#  moved already? → do NOT move back silently: ship v1.5.2 (fix) + notes + deprecate v1.5.1
#  protect: forge rule `v*` — no force-push, no delete (immutability with teeth)
```

### 3) **Design the release pipeline**

**Definition** — the systems answer covering the whole domain: conventional-commit gates at entry (commitlint + PR-title checks), strategy-shaped lines with per-line merge policy (squash on `main`, joins on release trains), CI as merge precondition (build, test, lint green + up-to-date), annotated tags per merge (automation-derived bumps, human-confirmed majors), generated notes (grouped, linked), publish to registries, merge queues past the volume threshold. Eight stages, each from a different leaf — the domain in miniature, drawn as a pipeline.

- **What a good answer sounds like**: a narrated flow with *owners* at each stage — "developers write parseable messages (gated), PRs squash onto protected `main` (policy), CI greens (precondition), semantic-release bumps/tags/notes (derived), humans confirm majors and train timing (judgment), artifacts publish (automation), queues serialize past N PRs/day (correctness at scale)." Seniors add failure handling (stale-green → queue; red main → freeze + revert-forward; moved tag → new PATCH, never move-back) and evolution (revisit thresholds yearly). The answer should name what breaks when each stage is skipped — skipped gates rot versions, skipped queues race greens, skipped tags orphan rollbacks.
- **Modern guidance** — grade architecture (stages with owners and failure modes), not tool names: semantic-release vs alternatives is trivia; gates-before-derivation order is judgment. Red flags: fully-manual releases "for control" at scale (control theater — humans are worse parsers than parsers), no human gates anywhere (breaking changes auto-shipping as surprises), tags as afterthought. Rapid-fire drills that close: squash title vs branch commits — which persists? (title — leaf 3.1); tag vs branch for the deploy source? (tag — leaf 4.1); stash older than a week? (branch it or drop it — leaf 2.2).

```bash
# The pipeline in six lines (domain in miniature)
#  write (gated: commitlint + title) → propose (PR, small) → join (squash, protected, queued)
#  → derive (bump + notes + tag vX.Y.Z) → confirm (human: majors, trains) → publish (registry)
git log v1.5.1..HEAD --pretty=format:'%s' | grep '^feat\|^fix'   # next release, already drafted
```

### 4) **Common confusion**

- Candidates who prescribe strategy without asking about deploy reality — prescription before diagnosis is the fashion failure mode.
- "Tags are just names" — tags are *coordinates*: builds, audits, rollbacks, and downstream pins navigate by them. Moving one corrupts every chart.
- Treating stash as architecture ("developers shelve work for weeks") — stash is interruption-scale (hours); anything bigger is a branch. Seniors time-box the shelf.

### 5) **Performance note**

Interview answers here should be compact: strategy derivation (two minutes — questions, function, prescription, revisit), tag-move (90 seconds — blast order, prevention, honest recovery), pipeline design (three minutes — eight stages with owners and failure modes). Candidates who narrate tools without owners or failure modes take longer and prove less — architecture is answers plus accountability.

### 6) **Mentor note**

Use Q1 as the strategy screen (every hire must derive shape from reality), Q2 as the trust screen (every hire must treat tags as coordinates), Q3 as the systems screen (every hire must design the pipeline with owners and failure modes). Rubric: junior — correct pieces named; mid — pieces connected with reasons (gates-before-derivation, policy-per-line, tags-as-coordinates); senior — failure modes and evolution (stale-green, moved-tag recovery, yearly revisits, human gates preserved). Keep the strategy shapes drawn and one moved-tag postmortem (dated, named) ready — artifacts beat abstractions in interviews. Red-flag fails: one-shape dogma, move-it-back recovery, fully-manual releases at scale, stash-as-storage.
