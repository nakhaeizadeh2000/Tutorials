## 6.1. Boundaries: what is covered elsewhere

### 1) **Mechanics underneath**

**Definition** — this domain decides; Domains 01–05 operate. Joining (slides, joins, conflicts, `rerere`) lives in [Domain 03](<../../../03 Branching Merging and Conflicts/README.md>); proposing (fetch/push, upstream, forks, PR flow, currency) in [Domain 04](<../../../04 Remotes GitHub and Pull Requests/README.md>); undoing and replaying (restore, revert, amend, rebase, reflog) in [Domain 05](<../../../05 Undo Fix and Rewrite History/README.md>); composing (staging, messages, log archaeology) in [Domain 02](<../../../02 Core Workflow Add Commit and Inspect/sections/1. Composing commits/1.1. Partial staging and the atomic commit.md>); the model (snapshots, DAG, areas) in [Domain 01](<../../../01 Git Fundamentals and Mental Model/README.md>). When this domain says "squash onto protected main" or "rebase the PR," the *squash* and the *replay* are links, not paragraphs.

- **Why the boundary matters**: policy questions ("which strategy?") and mechanic questions ("how does squash work?") share a keyboard but different models — decisions vs operations. Re-teaching operations inside policy leaves produces the longest, least re-readable pages in Git pedagogy: half governance, half flag tables, fully skimmable. Keep them split: operate in 01–05, decide here.
- **Modern guidance** — if a passage here needs more than one sentence of join/propose/replay/compose mechanics, stop and link instead. The one-sentence versions: joins slide, record, or resolve (03); proposals branch, push, review, merge-delete (04); undo appends or replaces by visibility (05); commits compose atomically with contracts (02). Everything else here is *policy* (which shape, which join, which gate) and *release mechanics* (tags, stash, derivation).

```bash
# GOOD: one line here, depth behind the link
git merge --squash feat/x   # the squash mechanics are Domain 03/05 territory — the mandate is new
# BAD: re-explaining merge shapes, PR flow, rebase flags, or staging inside policy leaves
```

### 2) **Trust and production gates**

**Definition** — proving authorship (commit/tag signing), keeping secrets out of history (hygiene + response), enforcing gates (hooks, CI, required checks), and conducting review as a team sport belong to Domain 07 (Production Checklist, Security, and Collaboration Mastery) — not here. This domain *sets* policy (which strategy, which join, which gates should exist); 07 *guards* it (signatures prove, hooks enforce, incident response repairs). Policy without guards is a suggestion; guards without policy have nothing to enforce — the handshake between the two.

- **Why the boundary matters**: trust tooling taught inside strategy leaves invites cargo-cult security ("we signed one tag once") without the incident model (what happens when a secret lands, when a key leaks, when CI is bypassed). Domain 07 teaches trust as a disciplined unit with response playbooks; this domain borrows only the conclusions (sign releases, gate merges, protect lines — with forwards). Each side references the other once and stays in its lane.
- **Modern guidance** — memorize the forwards used here and defer the rest: signatures, secret hygiene/response, hooks/CI enforcement, review etiquette → [Domain 07](<../../../07 Production Checklist Security and Collaboration Mastery/README.md>). When trust curiosity strikes mid-policy ("but how do we *prove* the tag?"), follow the link — Domain 07 answers with mechanics plus playbooks, not paragraphs.

```bash
# GOOD: borrow the guard-slot, link the guardbook
#  releases signed + CI-gated + secrets-scanned → Domain 07 owns the how (live link below)
# BAD: GPG setup guides, secret-removal surgery, or hook scripts inside strategy leaves
```

### 3) **Word-level naming**

**Definition** — what strategy words *mean in a meeting* (trunk, spike, train, freeze, rollback as vocabulary) belongs to [IT Vocabulary](<../../../../ITVocabulary/README.md>) — this track never re-teaches definitions those leaves own. Map-style stop-list: model → 01, composition → 02, joining → 03, proposing → 04, operations → 05, policy → here (06), trust → 07, words → IT Vocabulary.

- **Why the boundary matters**: every boundary crossed here is duplication that rots — strategy glossaries copied into policy leaves go stale when industry usage shifts, while the words-track stays current. Single source of truth (PROMPT §5): the concept gets its full treatment once, everywhere else one line plus a link.
- **Modern guidance** — when writing or reviewing Domain 06 content, ask "does a sibling domain or track own this sentence?" If yes, compress to a link. The domain stops at: which shape, which join, which marks, which shelves, which derivations — everything about *how the operations work*, *how trust is proven*, or *what the words mean* lives elsewhere.

### 4) **Common confusion**

- "Policy is where advanced Git lives" — policy is *decisions*; the advanced mechanics concentrate in replay (05) and trust (07). This domain is the governance layer, not the whole stack.
- "Boundaries leaves are filler" — they are the DRY contract made visible: each states what this domain deliberately does *not* teach so neighbors can teach it once.

### 5) **Performance note**

No runtime cost to boundaries — the performance is editorial: one-line links instead of copied sections keep every leaf short, searchable, and single-sourced. When Domain 05 changes lease guidance, one domain updates instead of six.

### 6) **Mentor note**

Quiz: "where does signing live?" (07), "where does rebase live?" (05), "where does squash-vs-merge live?" (here, 06). Correct answers mean the track's architecture landed.
