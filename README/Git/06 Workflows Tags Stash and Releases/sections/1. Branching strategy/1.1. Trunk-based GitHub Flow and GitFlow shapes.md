## 1.1. Trunk-based, GitHub Flow, and GitFlow shapes

### 1) **One long-lived line vs two vs many**

**Definition** — three canonical shapes for persistent lines: *trunk-based* (one long-lived line, `main` — every change branches short and merges within a day or two); *GitHub Flow* (`main` plus deployment-moment branches or environment pointers — same idea, deploy-gated); *GitFlow* (`main` + `develop` + `release/*` + `hotfix/*` — parallel integration, stabilization, and production lines). The shape answers one question: where does unfinished work live while it becomes finished?

- **What problem it solves**: without a named shape, every team invents its own by accident — `main`, `main2`, `main-final`, `develop-old` accumulate as oral tradition, and newcomers learn the map by breaking it. A named strategy converts line-topology from folklore into a one-page document: which lines are long-lived, what each means, who may merge into it, and how long short branches may live. The strategy doesn't prevent divergence (branches still diverge); it makes divergence *legible*.
- **Modern guidance** — default to trunk-based for teams deploying continuously (small batches, feature flags for unfinished paths — flags replace lines). Choose GitHub Flow's deploy-gating when releases need human approval moments. Reserve full GitFlow for scheduled, versioned releases with parallel stabilization (mobile app trains, enterprise quarterly drops) — and accept its cost honestly: long-lived `develop` diverges from `main` for weeks, and every release pays a merge toll. Never adopt GitFlow "to be safe" — parallel lines are risk *storage*, not risk removal.

```bash
# GOOD: the shape visible in labels — trunk (one persistent line, everything else short)
git branch -a   # main (persistent) + feat/* (days, not weeks) — the whole strategy in one listing
#  GitFlow twin: main + develop (persistent) + release/2.4 + hotfix/login-loop (purpose-built)
# BAD INSTINCT: main, develop, staging, preprod, release, release2, test, demo —
# persistent lines nobody can define are not strategy, they are archaeology
```

### 2) **Long-lived means protected**

**Definition** — a long-lived line without rules is a suggestion: branch protection (forge settings on `main`/`develop`/release lines — required PR reviews, green CI, no direct pushes, no force-pushes, linear-history or squash requirements) converts shape into enforcement. Documented per GitHub branch-protection docs (forge-side, no local Git equivalent — the rules live where the shared refs live). Protection answers: who may write here, through which gate, with what evidence?

- **Why it matters (correctness)**: unprotected long-lived lines rot exactly like unreviewed code — direct pushes bypass review, force-pushes rewrite what releases reference, red merges become everyone's base. Every incident in Domains 04–05's cautionary tales (force-pushed `main`, amended shared tips, blind-pull joins) is preventable at this layer: protection makes the dangerous operation *impossible*, not merely discouraged. Culture asks; protection enforces.
- **Modern guidance** — protect every persistent line on day one (before the first incident, not after): require pull requests (no direct pushes), require status checks (CI must pass), require branches be up to date (fresh-base merges only — leaf 1.2's queue extends this), dismiss stale approvals on new pushes (rewritten code re-earns review), block force-pushes entirely on `main`. Short-lived feature branches stay unprotected (flexibility where divergence is cheap); persistent lines stay armored (rigor where divergence is expensive).

```bash
# GOOD: protection as documented checklist (forge settings — GitHub docs "About protected branches")
#  main: [x] Require PR before merging  [x] Require status checks  [x] Dismiss stale approvals
#        [x] Require branches up to date  [x] Block force pushes  [x] No direct pushes
#  feat/*: unprotected — rebase, amend, lease-push freely (Domains 04–05 rules apply)
# BAD: protecting nothing ("we trust each other") until the first rewritten main —
# trust is for people; protection is for 2 AM mistakes, which trust cannot prevent
```

### 3) **Strategy follows deploy reality**

**Definition** — the choice function: continuous deployment (many deploys daily, flags gate features) → trunk-based; human-gated deploys (staging approval, deploy windows) → GitHub Flow (deploy from `main` or short release pointers); scheduled versioned releases (trains, app-store review, contracted versions) → GitFlow (stabilization lines absorb the wait). Team size and revert speed modify, never override: small teams revert fast (trunk wins), large orgs coordinate slowly (explicit lines win).

- **Why it hurts when missing (correctness, maintainability)**: strategy/reality mismatch produces chronic pain misdiagnosed as discipline problems — trunk-based with monthly manual releases means half-flagged features pile in `main` (undeployable trunk); GitFlow with daily deploys means ceremony for every one-line fix (release branches, version bumps, merge tolls — days of process per hour of work). The symptom is always "Git feels slow here" and the cause is always a shape fighting the deploy cadence. Change the shape, not the engineers.
- **Modern guidance** — revisit the choice yearly or at 10× team growth (the shape that served five engineers strangles fifty — and vice versa: process adopted "for scale" prematurely slows the five you have). Migration between shapes is mechanical (delete or add persistent lines, move protection rules, announce once) — the cost is social (habits), never technical. Document the *why* alongside the *what* ("trunk-based because we deploy 20× daily and revert in minutes") so future teams re-derive instead of cargo-culting.

```bash
# GOOD: shape matches cadence — examples, not prescriptions
#  5 engineers, 20 deploys/day, flags everywhere → trunk (main + day-long branches)
#  50 engineers, weekly train, app-store gates     → GitFlow (develop + release/2.4 + hotfix/*)
#  15 engineers, staging-approved SaaS             → GitHub Flow (main + deploy gates)
# BAD: adopting GitFlow "because enterprises do it" for a 3-person side project —
# release tolls on every fix, stabilization lines stabilizing nothing
```

### 4) **Common confusion**

- "More branches means more safety" — persistent lines store divergence risk; they don't remove it. Safety comes from short branches, review, CI, and protection — the shape just organizes them.
- "Trunk-based means committing to main directly" — trunk-based means *short-lived branches* merging to `main` constantly (often via PRs, still reviewed). Direct-to-main is a protection setting (usually off), not a strategy.
- "GitFlow is outdated" — GitFlow is *specialized*: costly where cadence is continuous, correct where releases are scheduled and versioned. "Outdated" is fashion; "mismatched" is diagnosis.
- "Protection slows us down" — protection slows the dangerous operations (direct pushes, red merges, force rewrites) and speeds everything else (fewer incidents, trusted base, confident reverts). Measure incident hours, not gate seconds.

### 5) **Performance note**

Strategy performance is merge latency: trunk-based merges in hours (small diffs, fresh bases, no tolls); GitFlow merges in days-to-weeks per release (stabilization, tolls, coordination). The compute is trivial either way (labels and joins cost nothing); the human pipeline dominates — review queues, CI cycles per long-lived line, conflict resolution on stale branches. Optimize for the bottleneck your deploy reality actually has: trunk optimizes time-to-production, GitFlow optimizes release predictability. Pick the metric first, the shape second.

### 6) **Mentor note**

Draw all three shapes before discussing any: one persistent line with short spurs (trunk), one line with deploy gates (GitHub Flow), the full `main/develop/release/hotfix` lattice (GitFlow). Have juniors place their current team on the drawing — then ask what breaks if the team 10×ed or shipped 10× faster. That question teaches strategy as *derived*, not received. Watch for the fashion-adopter ("everyone uses X" — fix with the deploy-reality function) and the protection-skeptic ("we're disciplined, we don't need rules" — fix with the 2 AM question: "who protects `main` when you're asleep?"). Review check: one-page strategy doc exists, every persistent line is protected in forge settings, juniors can name the shape and its *why*.
