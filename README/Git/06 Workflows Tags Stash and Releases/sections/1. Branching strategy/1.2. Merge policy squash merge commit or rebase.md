## 1.2. Merge policy: squash, merge commit, or rebase

### 1) **Three strategies, three histories**

**Definition** — when a PR joins a protected line, the forge offers three recordings: *squash* (whole PR becomes one commit on the target — branch detail vanishes, target reads one-idea-per-commit); *merge commit* (two-parent join preserved — Domain 03 §2.1's join metadata: who joined what, when, revertible as a unit); *rebase-merge* (commits replayed linearly onto the tip — individual commits preserved, no join recorded). Same code lands three different histories — the policy picks which reader to optimize for.

- **What problem it solves**: without a mandated strategy, history becomes a fossil record of individual taste — squash here, octopus there, rebase-replays beside two-parent joins — and every consumer (bisect, blame, changelogs, reverts) must handle all shapes forever. A single strategy per line makes history *queryable*: `log --first-parent` tells the integration story under merge-commits, `bisect` walks atomic units under squash, `blame` traces authors under rebase. Uniformity is a feature of the log, not aesthetics.
- **Modern guidance** — squash by default for feature PRs onto `main` (PRs are already one idea per Domain 03 §1.2 — one commit each keeps the target bisectable and revertible in one step); merge commits for release integration (the join *is* the event worth recording — who shipped what train when); rebase-merge where commit-level archaeology matters and every commit is independently green (rare — demands per-commit CI). Set it in repo settings (one allowed strategy, or default-plus-discipline), never in per-PR improvisation.

```bash
# GOOD: one strategy per line, set where it can't be improvised (forge settings)
#  main ← feat/* : squash (one idea per commit; revert = one revert)
#  main ← release/2.4 : merge commit (the join records the shipment)
#  log --first-parent main  → integration story under merge; flat story under squash
# BAD: strategy per developer mood — the log becomes mixed-shape,
# and bisect/blame/changelog tooling must handle every shape on every line
```

### 2) **Choose per line, enforce on the forge**

**Definition** — policy lives in forge settings (required merge method, required linear history, required checks, dismiss-stale-reviews), not in wiki requests. Enforcement points, documented per GitHub docs: *allow squash / rebase / merge commits* toggles (remove what the line forbids), *require linear history* (rebase-or-squash only — no join commits, ever), *require status checks + up-to-date branches* (only fresh green lines join), *dismiss stale approvals* (rewritten code re-earns review — Domain 05's lease-push triggers it).

- **Why it matters (correctness)**: unenforced policy is a suggestion engineers follow until deadline pressure — and deadline pressure is exactly when wrong-shape joins do the most damage (mystery merges during release week, unreviewed rewrites during incidents). Enforcement moves the decision from the busiest moment (merging under pressure) to the calmest (configuring the repo once). Teams that "agreed on squash" but allow all three methods discover the agreement was aspirational at the first mixed-shape `bisect`.
- **Modern guidance** — configure the strictest set the team will tolerate on day one (linear or squash-only on `main`, dismiss-stale-reviews everywhere, up-to-date required), then relax deliberately if evidence demands it — tightening later fights entrenched habit. Different lines may differ (release lines allow merge commits recording trains; `main` stays squash-linear) — per-line settings express exactly that. Review the settings yearly alongside the strategy doc (leaf 1.1): policy rots when the team outgrows it silently.

```bash
# GOOD: the enforcement checklist per protected line (forge settings)
#  main: allow [x] squash [ ] merge [ ] rebase + [x] linear history + [x] up-to-date + [x] dismiss stale
#  release/*: allow [x] merge (trains recorded as joins) + [x] up-to-date
# BAD: "we agreed on squash" with all three methods enabled —
# agreement without enforcement is a comment, not a control
```

### 3) **Merge queues for busy mains**

**Definition** — a merge queue serializes joining: PRs enter the queue, the forge re-validates each against the *current* tip (rebase, run CI, confirm green), then joins in order — each PR tested on the base it will actually land on. Without a queue, two PRs green on the same base race: the first joins, the second's green now describes a base that no longer exists (stale-green merge — tested against history, joined onto mystery). Documented per GitHub merge-queue docs (forge-side; local Git has no equivalent — the race is inherently multi-writer).

- **Why it hurts when missing (correctness, maintainability)**: stale-green merges are silent correctness holes — CI certified code X against base T, but X landed on T+1, and the interaction (X breaks under T+1's changed API) ships untested. On busy mains (dozens of PRs daily) the race is constant, and "but CI was green" becomes the epitaph of every such incident. The queue converts parallel optimism into serial certainty: every join certified on its actual base, at the cost of queue latency (minutes per PR — bounded, predictable, automatable).
- **Modern guidance** — enable merge queues when `main` takes more than a handful of PRs daily or when stale-green incidents appear even once (one is enough — the race doesn't self-heal). Keep PRs small and bases fresh (Domains 03–04 discipline shrinks queue time more than any tuning). For quiet mains, required up-to-date branches (previous section) approximates the guarantee without queue latency — upgrade to the queue when "update branch, re-green, race again" becomes the daily loop.

```bash
# GOOD: serialized certainty on busy lines (forge merge-queue settings)
#  PR #41 green on T → queued → rebased on T (still tip?) → CI → joins as T+1
#  PR #42 green on T → queued → rebased on T+1 → CI → joins as T+2 (tested on its real base)
# BAD: parallel merging on a 50-PR/day main with "CI was green" as the defense —
# green described the old base; the join met the new one untested
```

### 4) **Common confusion**

- "Squash loses history" — squash loses *branch-internal* history (wip commits, fixups) and keeps the *idea* as one commit. If the branch was one idea (it should be — Domain 03 §1.2), nothing of value is lost; the apologies were never history.
- "Linear history means no merges ever" — linear means no *join commits on that line*; PRs still review, CI still gates, squash still records. Linearity describes the log shape, not the process rigor.
- "Merge queues are just slower merging" — queues trade bounded latency (minutes, predictable) for a correctness guarantee (every join tested on its base). Unqueued busy mains trade unbounded incident risk for the *feeling* of speed.
- "Small teams don't need merge policy" — small teams need it most: policy set at five engineers is culture; retrofitted at fifty is conflict. One setting now beats one migration later.

### 5) **Performance note**

Merge latency per PR: squash ≈ rebase-merge (one CI cycle on current base) < merge-commit (same plus join verification) < queued (CI per queue position — N× cycles for N queued, but parallelizable across the queue's speculative runs). Stale-green incident cost dwarfs all of them (hours of bisect + revert + re-landing per incident — Domain 05's rescue applied at scale). Optimize for the expensive tail (incidents), not the cheap middle (minutes of queue): policy strictness pays for itself at the first prevented stale-green merge.

### 6) **Mentor note**

Make the three strategies tangible: take one real PR and show its three possible landings (`log --graph` sketches — squash dot, join diamond, replayed line). Have juniors predict `bisect` steps and `revert` commands under each shape — the shape that answers fastest for *your* team's frequent operation wins. That exercise converts policy from received wisdom into derived decision. Watch for the shape-romantic ("merge commits preserve truth" for a squash-shaped team, or vice versa — fix with the reader question: "who reads this log, and what do they ask it?") and the queue-skeptic on a busy main ("CI was green" — fix with one stale-green postmortem, dated and named). Review check: one allowed strategy per protected line in settings (not wiki), dismiss-stale-reviews on, queue enabled past the PR-volume threshold, juniors can state the line's strategy and its *why*.
