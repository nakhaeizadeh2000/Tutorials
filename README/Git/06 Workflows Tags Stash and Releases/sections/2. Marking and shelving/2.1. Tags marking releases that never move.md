## 2.1. Tags: marking releases that never move

### 1) **Annotated tags are release objects**

**Definition** — `git tag -a v0.1.0 -m "Release 0.1.0"` creates a tag *object* (message, tagger, date, optional GPG signature) pointing at a commit — a first-class citizen with authorship and audit trail. Lightweight tags (`git tag v0.1.0` — bare label, no metadata) are bookmarks for scratch use. Verified on Git 2.53.0: `git tag` lists `v0.1.0`, and `git describe --tags` resolves the current line to `v0.1.0` — the release is addressable by name from anywhere downstream (builds, deploys, `blame` context).

- **What problem it solves**: releases identified by branch position ("production is at commit `a1b2c3`… I think") rot the moment anyone asks twice — hashes are unmemorable, branches move, memory lies. Annotated tags freeze a name to a hash with provenance (who tagged, when, why): builds check out tags, changelogs section by tags, rollbacks target tags, auditors read tags. The release becomes a noun the whole organization can point at instead of a hash only Git remembers.
- **Modern guidance** — annotate every release tag (message names the release, body links notes/approvals); sign release tags where supply-chain policy demands it (`-s` — Domain 07 owns the trust story, this leaf owns the mechanics). Reserve lightweight tags for personal bookmarks (test runs, bisect markers) that die within the week. Never reuse a tag name for a different commit — re-tagging rewrites what consumers already resolved (next section's trust exercise covers the breakage).

```bash
# GOOD: releases as objects — annotated, messaged, addressable — verified
git tag -a v0.1.0 -m "Release 0.1.0"
git tag            # v0.1.0
git describe --tags   # v0.1.0 — builds and deploys check out this name, not a hash
# BAD: releases as memory ("prod is… that commit from Tuesday?") or lightweight tags
# for shipped artifacts — no tagger, no date, no message for the auditor who asks next quarter
```

### 2) **Semver gives tags meaning**

**Definition** — Semantic Versioning (`MAJOR.MINOR.PATCH`): MAJOR for incompatible API changes, MINOR for backwards-compatible features, PATCH for backwards-compatible fixes — the number tells consumers what *kind* of change to expect before reading a line. A tag named `v2.4.1` promises: second major line, fourth feature batch, first fix since. The promise is a contract: dependents upgrade PATCH blindly, review MINOR, and schedule MAJOR.

- **Why it matters (correctness)**: version numbers are the API of your release process — consumers automate around them (`^1.4.0` ranges, lockfiles, Renovate rules). A breaking change shipped as MINOR breaks every downstream range silently; a fix shipped as MAJOR makes every consumer schedule unnecessary migration work. Both erode the exact trust automation requires. Semver discipline converts "should I upgrade?" from archaeology into arithmetic.
- **Modern guidance** — bump by content, not calendar: breaking API → MAJOR (and say so loudly in notes); new capability, compatible → MINOR; fix only → PATCH. Pre-1.0 (`0.x.y`) anything may break (document it — consumers pin exactly). Tag names carry the `v` prefix by near-universal convention (`v1.4.2` — tooling from `git describe` to release pipelines expects it). When automation derives bumps from commit types (leaf 3.1), keep the human override: the pipeline proposes, a human confirms breaking-ness.

```bash
# GOOD: numbers that promise — bump by content
#  feat(api): paginated list      → MINOR (v1.4.0 → v1.5.0 — compatible feature)
#  fix(auth): reject empty token  → PATCH (v1.5.0 → v1.5.1 — compatible fix)
#  feat(api)!: drop v1 endpoint   → MAJOR (v1.5.1 → v2.0.0 — the ! marks breaking)
# BAD: "v1.4.2-final2-REAL" or calendar tags for libraries —
# consumers cannot compute upgrade risk from poetry; automation cannot parse it either
```

### 3) **Push tags deliberately**

**Definition** — tags don't follow branches: `git push` sends commits, not tags — release tags travel via `git push origin v1.5.1` (one tag) or `git push --tags` (all unpushed tags). Deleting a remote tag is equally explicit (`git push --delete origin v1.5.1` plus local `git tag -d`). The asymmetry is deliberate: tags mark decisions, and decisions travel on purpose, never as side effects of pushing a branch.

- **Why it hurts when missing (correctness, maintainability)**: the two classic tag incidents both stem from assumed travel — releases "tagged" locally that CI never saw (pipeline watches tags; nothing triggered; the release silently didn't happen), and `--tags` pushes that publish personal bookmark tags (`test-foo`, `wip`) to the shared namespace where automation tries to release them. Explicit push-per-tag keeps the shared tag namespace exactly equal to decided releases — nothing accidental, nothing missing.
- **Modern guidance** — push each release tag by name immediately after creating it (tag-and-push as one ritual, ideally one script or CI job). Reserve `--tags` for deliberate bulk syncs (new mirror, disaster recovery) — never as the daily spelling. Protect release tag patterns on the forge (`v*` — no force-pushing tags, no deleting without admin) so the immutability promise from the interview leaf holds mechanically. Verify after pushing: `git ls-remote --tags origin` shows what the world sees — trust the listing, not your local `git tag`.

```bash
# GOOD: decisions travel on purpose — one tag, one push, one verification
git tag -a v1.5.1 -m "Release 1.5.1" && git push origin v1.5.1
git ls-remote --tags origin   # what the world sees — confirm the release landed there
# BAD: tagging locally and assuming CI noticed, or `git push --tags` as a habit —
# missing releases on one side, bookmark-tag pollution (test-foo, wip) on the other
```

### 4) **Common confusion**

- "Tags move like branches" — tags are *meant* to be immovable (release identity depends on it). Moving a tag re-points every consumer silently — the interview leaf's trust exercise. Branches advance; tags commemorate.
- "Lightweight tags are fine for releases" — fine until the audit: no tagger, no date, no message, no signature. The metadata *is* the release record; lightweight tags skip it.
- "`--tags` is just thorough pushing" — thorough at publishing your scratch bookmarks to shared automation. Explicit beats bulk for anything consumers resolve.
- "Describe works without tags" — `git describe` needs an annotated ancestor to name positions (`v0.1.0-3-gabc1234` = 3 commits past the tag). Tagless lines describe as "no names found" — another reason release lines stay tagged.

### 5) **Performance note**

Tags cost one object (annotated) or one ref line (lightweight) — negligible at every scale; `describe` walks history to the nearest tag (fast on tagged release lines, slow on never-tagged ones — tag regularly and the walk stays short). Push-per-tag transfers one ref update. The expensive resource is human: untagged releases cost archaeology hours per incident ("which commit shipped Tuesday?"); tag discipline pays it back at the first rollback.

### 6) **Mentor note**

Have juniors tag, push-by-name, and `describe` in scratch until the ritual is muscle memory — then stage the moved-tag incident (re-tag locally, watch a consumer resolve the old hash from cache) to teach immutability viscerally. Quiz semver bumps against real commit lists ("breaking? minor? patch?") until the `!` marker and contract language are reflex. Watch for the memory-releaser ("prod is Tuesday's commit" — fix with tag-and-describe ritual) and the bulk-pusher (`--tags` daily — fix with push-by-name plus the bookmark-tag pollution story). Review check: every release tagged annotated with message, pushed by name, pattern-protected on the forge; `ls-remote --tags` matches the release log; juniors can state any shipped version's content from its tag.
