## 4.1. Workflow checklist (habits mentors insist on)

### 1) **Strategy written, not assumed**

**Definition** — one page, linked from onboarding, stating: the shape (trunk / GitHub Flow / GitFlow — leaf 1.1), the persistent lines and what each means, the merge policy per line (leaf 1.2), who may merge, and the protection summary. New hires read it before their first PR; the page answers every "where does this go?" without a senior's time. Unwritten strategy is oral tradition — accurate until the second retelling.

- **What problem it solves**: strategy questions arrive daily ("do we squash here?", "can I push to develop?", "where do hotfixes branch from?") and each costs a senior interruption when undocumented — or worse, gets answered by guessing, producing mixed-shape history the policy was supposed to prevent. The page converts recurring interruptions into a link and recurring guesses into a reference. Teams that write it stop debating mechanics and start debating product.
- **Modern guidance** — keep it to one page (shape diagram + line table + policy table + who-merges + link to protection settings). Review it yearly or at 10× growth (leaf 1.1's revisit rule). Store it in the repo (versioned alongside the code it governs — strategy changes deserve diffs and review like any decision). Test it: any engineer in week two should place any branch and predict its merge path without asking.

```bash
# GOOD: the page exists and the repo matches it
git branch -a   # persistent lines exactly as documented; nothing else long-lived
#  strategy.md: trunk + squash-on-main + protected main + merge queue past 20 PRs/day
# BAD: "ask in chat" as branching strategy — answers vary by who is awake,
# and the log records the variance forever
```

### 2) **Tags mean releases, branches mean work**

**Definition** — the naming invariant: tags commemorate decided releases (annotated, pushed by name, never moved — leaf 2.1); branches carry work-in-progress (created freely, deleted on merge, never released from directly). `git describe` names any commit's distance from the last decision; `git branch -a` lists current intentions. Confusing the two (releasing from a branch tip, working on a tag) breaks every consumer of either.

- **Why it matters (correctness)**: releases resolved by tag are reproducible (same name, same hash, forever — builds, rollbacks, audits); releases resolved by branch are moving targets (Monday's `release` tip differs from Friday's — "works on the release branch" means nothing versioned). Conversely, tags as work markers freeze collaboration (teammates can't advance your tag without violating immutability). The invariant assigns each ref type its job: tags for decisions, branches for motion.
- **Modern guidance** — release pipelines check out tags (never branch tips); humans branch from tags for hotfixes (`switch -c hotfix/x v1.5.1` — the tag names the base precisely). Delete merged branches promptly (Domain 04 §2.2 hygiene); never delete release tags (pattern-protect `v*` on the forge). Audit quarterly: `git ls-remote --tags` reconciled against the release log (every shipment tagged, every tag shipped — no orphans either direction).

```bash
# GOOD: decisions and motion in their places
git checkout -b hotfix/login-loop v1.5.1   # work branches FROM the decision, precisely
git tag -a v1.5.2 -m "Release 1.5.2" && git push origin v1.5.2   # decisions tagged + published
# BAD: deploying branch tips ("ship whatever develop has now") or committing onto tags —
# unversioned releases and frozen collaboration, respectively
```

### 3) **Shelf small, automate the boring**

**Definition** — the daily-hygiene half: stash with messages and pop same-day (leaf 2.2 — pause, don't file), changelogs derived from contracts (leaf 3.1 — never hand-assembled), queues absorbing merge races (leaf 1.2 — never hand-serialized). Each replaces a recurring manual chore (remembering shelf contents, writing notes, timing merges) with a mechanism that works while engineers think about product.

- **Why it hurts when missing (correctness, maintainability)**: manual chores don't just cost time — they fail under pressure (release-night notes written from memory, merge races "resolved" by retrying until green, month-old stashes popped onto moved bases). Mechanisms don't get tired: the queue serializes at 2 AM exactly as at noon, the parser classifies the ugly fix the same as the elegant feature, the named stash pops with its context attached. Reliability comes from removing humans from loops that don't need judgment — keeping them in the ones that do (breaking-change calls, strategy choice, review).
- **Modern guidance** — automate in this order: message gates (cheapest, highest leverage — everything downstream parses), changelog derivation (second release onward), merge queues (past the PR-volume threshold). Keep humans on: breaking-change judgment, release-train timing, review quality, strategy evolution. Audit the automation yearly (parser rules vs actual message shapes, queue latency vs team patience) — mechanisms rot when the workflow outgrows them silently.

```bash
# GOOD: mechanisms handle the boring, humans handle the judgment
git stash list          # short or empty — shelves move daily, not accumulate
git log v1.5.1..HEAD --pretty=format:'%s' | grep -c '^feat\|^fix'   # next notes, already drafted
# BAD: release heroics ("release captain" as a rotating burnout role doing by hand
# what gates, parsers, and queues do deterministically)
```

### 4) **Common confusion**

- "Checklists replace thinking" — checklists replace *remembering* under load; judgment (breaking or not? which train? squash or join?) stays human. The list handles the invariant parts so attention concentrates on the variant parts.
- "Small teams can skip all this" — small teams need *lighter* versions, not zero: one strategy paragraph, tag-per-release, gates on, queue later. Skipping entirely mortgages the migration (culture adopted early is habit; retrofitted is conflict).
- "Automation means no release owner" — automation needs an owner more than manual process did (someone configures, audits, and evolves the pipeline). Ownerless automation rots into confidently-wrong versions.

### 5) **Performance note**

The checklist's total runtime is minutes weekly (branch audit, tag reconciliation, stash-list glance, settings review) against incident costs in hours and release-cycle costs in days. The highest-leverage line item is message gates (seconds per PR, unlocks all downstream automation); the second is the strategy page (one-time write, pays per onboarding and per unasked question forever).

### 6) **Mentor note**

Turn this leaf into the team's workflow runbook: strategy page link, tag/branch invariant, shelf-and-automate hygiene. Quiz juniors on placement ("where does this hotfix branch from? what tags this release? who merges to `main`?") until the answers are environmental, not memorized. Watch for checklist decay (process followed for a sprint, abandoned under pressure — fix with forge enforcement so the checklist has mechanical teeth) and hero culture ("only Alice can release" — fix by automating Alice's knowledge into gates and pipelines). Review check: strategy page current, `v*` protected, gates green-required, queues past threshold, stash lists short, any engineer can release without asking Alice.
