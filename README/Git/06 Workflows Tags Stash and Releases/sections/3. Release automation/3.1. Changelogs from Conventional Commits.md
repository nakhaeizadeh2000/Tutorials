## 3.1. Changelogs from Conventional Commits

### 1) **Parseable messages compound**

**Definition** — Conventional Commits (`type(scope): subject` — `feat:`, `fix:`, `docs:`, `chore:`, with `!` for breaking and footers for links) turn the log into structured data: machines can classify every commit without reading prose. Verified premise on Git 2.53.0: `git log --pretty=format:'%s' | grep '^feat\|^fix'` selects exactly the release-relevant subjects from history — the contract's whole foundation is one grep away. Domain 02 §1.2 taught humans to *write* this way; this leaf spends the accumulated capital.

- **What problem it solves**: hand-written changelogs rot — release notes assembled from memory omit fixes, misstate breaking changes, and arrive days late (or never). And version bumps argued per-release ("is this minor or patch?") re-litigate taxonomy every cycle. Parseable history automates both: types map to sections (features vs fixes vs chores-hidden), `!`/breaking footers map to MAJOR, `feat` to MINOR, `fix` to PATCH. The release notes write themselves from the same commits reviewers already approved — no second source of truth to maintain.
- **Modern guidance** — write every commit message as automation input (type + scope + imperative subject + why-body + ticket footer — Domain 02's contract, now with compound interest). Keep `BREAKING CHANGE:` footers honest and loud (automation trusts them for MAJOR bumps; a silent breaking change ships a lying MINOR). Treat the log as the changelog draft: `git log v1.4.0..v1.5.0 --pretty=format:'%s'` should read as releasable prose before any tool touches it.

```bash
# GOOD: the log already is the changelog draft — verified parseable
git log --pretty=format:'%s' v1.4.0..HEAD | grep '^feat\|^fix'
#  feat(cart): guest checkout behind flag
#  fix(auth): reject negative quantities
#  (feat → MINOR section, fix → PATCH section, ! → MAJOR — automation reads what reviewers wrote)
# BAD: "v1.5: stuff and things" assembled from memory the night before the release —
# omissions, misgraded breaking changes, and archaeology for every downstream consumer
```

### 2) **Release pipelines derive, humans decide**

**Definition** — release automation (semantic-release and its kin, documented per project docs — pipeline-side, configured in repo YAML rather than Git commands): on merge to a release line, the pipeline parses new commits since the last tag, computes the bump (MAJOR/MINOR/PATCH by the type rules), generates notes (grouped sections + links), creates the annotated tag, and publishes. Humans decide strategy (which lines release, what counts as breaking, when to ship); the pipeline derives everything else deterministically.

- **Why it matters (correctness)**: manual releases fail in the boring parts — skipped PATCH bumps ("too small to tag" accumulates into untraceable production states), forgotten tags (shipped but unmarked — leaf 2.1's trust exercise), notes written from fading memory. Automation makes releases *total* (every merge to the line produces exactly one versioned artifact), *ordered* (no skipped numbers, no duplicate tags), and *auditable* (tag → notes → commits, all linked). The pipeline doesn't decide what ships (humans merge); it guarantees every shipment is marked and described.
- **Modern guidance** — adopt semantic-release (or equivalent) on release lines once Conventional Commits discipline holds (automation on unparseable history produces garbage versions — contract first, pipeline second). Configure once: release branches, tag format (`v${version}`), note template, publish targets. Keep the human gates: breaking-change review (a `!` deserves a second pair of eyes before merge — the bump is forever), major-release scheduling (automation proposes MAJOR, humans pick the train per leaf 1.1's strategy). Never hand-edit generated notes without fixing the commits — the log is the source; notes are the view.

```bash
# GOOD: the pipeline contract — commits in, versioned artifact out (repo config, documented)
#  main ← squash "feat(cart): guest checkout" → pipeline: MINOR bump → v1.5.0 tag + notes + publish
#  main ← squash "fix(auth): reject empty"    → pipeline: PATCH bump → v1.5.1 tag + notes + publish
#  main ← squash "feat(api)!: drop v1"        → pipeline: MAJOR proposed → human confirms train → v2.0.0
# BAD: automation on freeform messages ("fixed stuff", "updates") —
# unparseable history yields arbitrary versions; the pipeline amplifies indiscipline, not fixes it
```

### 3) **Enforce the contract at the gate**

**Definition** — commitlint (message-shape linting) in CI plus PR-title checks (for squash merges — the *title* becomes the commit, so the title carries the contract) reject unparseable messages before they reach release lines. The gate converts a writing convention into a merge precondition: red on `fix stuff`, green on `fix(auth): reject empty tokens`. Documented per commitlint/semantic-release docs (config-side: `commitlint.config.js` + CI job + "require conventional PR title" status check).

- **Why it hurts when missing (correctness, maintainability)**: unenforced contracts decay to the median — three disciplined authors and seven "quick fix" committers produce history that parses *mostly*, and "mostly parseable" releases are worse than manual ones (automation confidently generates wrong versions from half-structured input — a MINOR for a breaking change nobody marked). The gate holds the line where culture can't: every merged commit parses, so every derived version is trustworthy. One red check beats ten wiki reminders.
- **Modern guidance** — enforce at both entries: commitlint on pushed commits (catches direct pushes and rebase accidents) *and* PR-title lint (catches squash-merged titles — the title is the future commit). Provide the fast path: PR templates with type/scope placeholders, `commitizen`-style prompting for juniors, and error messages that teach (`"type must be one of feat, fix, docs… — see CONTRIBUTING"` beats `"commitlint failed"`). Grandfather nothing: existing unparseable history stays (rewriting shared lines is worse — Domain 05), but every new commit parses from gate-day forward.

```bash
# GOOD: gates at both entries — unparseable never reaches the release line
#  commitlint CI:  type-enum rule rejects "fixed stuff" with a teaching message
#  PR-title check: squash title "feat(cart): guest checkout" becomes the commit — title IS the contract
# BAD: contract-by-wiki ("please write good messages") with green merges for "wip", "fix", "asdf" —
# automation downstream derives versions from noise, confidently and wrongly
```

### 4) **Common confusion**

- "Automation replaces release judgment" — automation derives versions and drafts notes; humans still judge breaking-ness, train timing, and whether the line is shippable. The pipeline is a scribe, not a release manager.
- "Squash titles don't matter, the branch had good commits" — under squash policy the title *becomes* the commit (leaf 1.2): branch-internal messages vanish, title persists forever. Title lint is commit lint for squash teams.
- "We can adopt semantic-release now and fix messages later" — inverted: garbage in, versioned garbage out. Contract discipline first (Domain 02 + gates), pipeline second. The order is load-bearing.
- "Changelog automation means no human notes" — generated notes cover *what*; humans still write *why-it-matters* (migration guides, deprecation timelines, highlights). Automation drafts; release captains edit.

### 5) **Performance note**

Pipeline cost per release: one parse pass over new commits (milliseconds) + tag + publish (minutes for builds, unrelated to Git). Gate cost per PR: one lint job (seconds, cacheable). The alternative — manual versioning meetings, hand-assembled notes, archaeology per consumer question — costs hours per release cycle. Automation's ROI crosses positive at the second release and compounds with every consumer (each downstream team stops asking "what changed?" because the notes answer first).

### 6) **Mentor note**

Teach this leaf backwards: start from a generated release (tag + notes + bump), trace each line to its commit (`-x` cherry-pick trailers and squash bodies make the mapping visible), then to the contract rule that classified it. Juniors who see derivation end-to-end write parseable messages naturally — the contract stops being bureaucracy and becomes authorship. Watch for the gate-skeptic ("linting messages is pedantic" — fix with one wrong-version postmortem) and the automate-first enthusiast (pipeline before discipline — fix with the garbage-in demonstration: run the parser over freeform history and read the nonsense versions aloud). Review check: commitlint green on every merged PR, squash titles parse, tags appear per merge without human tagging ceremonies, juniors can predict the next bump from the unreleased log.
