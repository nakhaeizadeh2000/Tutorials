## 2.1. Log filtering, formatting, and the questions log answers

### 1) **Ask questions, not dumps**

**Definition** — `git log` without flags dumps everything newest-first; fluency means reaching for the filter that answers your actual question: `--oneline -N` (what happened lately?), `-- <path>` (what touched this file?), `--since/--until` (what landed in this window?), `--grep` (which messages mention this?), `--author` (what did this person ship?).

- **What problem it solves**: undifferentiated log dumps train developers to stop reading history — the answer drowns in hundreds of unrelated commits, so nobody asks. One precise filter returns five lines that answer the question, which teaches the opposite habit: history is a database you query, and querying is cheap.
- **Modern guidance** — memorize five question-shapes and their flags (examples below); everything else is `git log --help` territory. Default to `--oneline` for scanning (one commit per line) and drop it only when you need full messages or diffs. Always bound the walk (`-N`, date range, or path) — unbounded log on a large repo answers slowly and reads never.

```bash
# GOOD: each invocation answers exactly one question
git log --oneline -10              # what happened lately?
git log --oneline -- cart.js       # what touched this file? (-- separates paths from revisions)
git log --oneline --since="2 weeks ago" --until="1 week ago"  # what landed in that window?
git log --oneline --grep="passkey" # which commits mention this? (message search)
git log --oneline --author="ada@"  # what did this person ship?
# BAD: git log | head -200 — unbounded dump, question unasked, answer unread
```

### 2) **Format for the consumer**

**Definition** — `--pretty=format:` renders each commit as exactly the fields the consumer needs (`%h` short hash, `%an` author, `%s` subject, `%cd` date); `--stat` appends per-commit file scope; `--graph --all` renders branch shape; `-p` shows full diffs. Same history, four different documents — pick the format the reader needs.

- **Why it matters (reviews, releases, scripts)**: release notes want subjects and authors, not hashes; incident review wants scope (`--stat`) and shape (`--graph`); automation wants parseable fields (`format:` with a delimiter). Dumping the default format into every consumer wastes everyone's parsing — human or machine.
- **Modern guidance** — three working formats cover ~everything: `--oneline` for eyes, `--pretty=format:'%h %an %s'` (or your team's variant) for notes and scripts, `--graph --oneline --all -20` for shape. Reach for `-p` only on single commits (it explodes on ranges) and `--stat` when scope matters more than content ("how big was that release?").

```bash
# GOOD: format matches the consumer
git log --pretty=format:'%h %an %s' -10        # release-notes raw material
git log --graph --oneline --all -20            # shape — where did lines fork and join?
git log --stat -5                              # scope — how big were these commits?
git log -p -1 a3f9c1                           # full diff, exactly one commit
```

### 3) **Limit the walk**

**Definition** — every `log` invocation walks the graph backwards from its starting points, visiting each reachable commit. Cost scales with commits *visited*, not repo size: `-10` visits ten, `--since` prunes by date, `-- <path>` still walks history but skips display of untouched commits (with `--follow` tracking one file across renames — full story in [2.2](<./2.2. Show blame and archaeology without blame games.md>)).

- **Performance note**: on million-commit histories (kernel, Chromium) an unbounded `git log -- <rare-file>` can take seconds — acceptable interactively, fatal in a hot script loop. Generation numbers make most walks fast, but no index defeats combinatorics: always bound (`-N`, dates, or `--max-count`) in anything automated, and prefer `--oneline` (no diff materialization) when scanning. Measure with `time git log ...` before optimizing; the usual fix is a tighter bound, not a faster machine.
- **Modern guidance** — the habit: every `log` you type gets a bound unless you can say why it needs the whole history. Interactive exploration earns slack; scripts, hooks, and CI get hard limits. A script that runs `git log` unbounded today breaks on the repo's growth tomorrow.

```bash
# GOOD: bounded walks — fast now, fast at 10x history size
git log --oneline -20 -- cart.js
git log --pretty=format:'%h %s' --since="1 month ago" -- CHANGELOG.md
# BAD in automation: git log --pretty=... (no bound — walks to the root commit, every run)
```

### 4) **Common confusion**

- "`-- <path>` shows the file's history" — approximately: it shows commits that touched that path, newest-first, with renames breaking the trail unless `--follow` is added (and `--follow` works for exactly one file). For "when did this *string* change", the pickaxe (`-S`/`-G`) beats path filtering — [2.2](<./2.2. Show blame and archaeology without blame games.md>).
- "`--grep` searches code" — it searches *messages* only. Message search finds decisions ("which commit mentions the incident?"); code search needs `-S`/`-G` pickaxe or a code host's index. Mixing them up wastes both queries.
- "`--author` matching is exact" — it is a regular expression (case-sensitive by default, `--regexp-ignore-case` softens it). `--author="ada"` also matches "adams" — anchor or verify when attributing.
- "Pretty formats change what is shown" — they change *rendering*, never selection. Filtering (`-N`, `--since`, `--grep`, `--author`) chooses commits; formatting (`--pretty`, `--oneline`, `--stat`) displays them. Debug empty output at the filter layer first.

### 5) **Mentor note**

Teach `log` as SQL for history: `SELECT subject FROM commits WHERE path=X AND date>Y LIMIT 10` maps directly onto flags, and developers who already think in queries learn the flags in minutes. The coaching exercise: give five real questions about your own repo ("who last touched payments?", "what shipped Tuesday?", "which commits mention the outage?") and require one command per question — no scrolling, no piping to `grep` (use `--grep`, that is the lesson). Ban `git log | grep` in the same breath: the pipe discards commit structure that flags preserve.
