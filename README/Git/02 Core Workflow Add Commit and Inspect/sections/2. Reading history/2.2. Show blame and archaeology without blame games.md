## 2.2. Show, blame, and archaeology without blame games

### 1) **Show the snapshot**

**Definition** — `git show <commit>` renders one commit completely: metadata (author, date, full message), then the diff it introduced. With no argument it shows `HEAD`. It is the unit operation of archaeology — every "what did this change do?" question bottoms out at one `show`.

- **What problem it solves**: `log` lists, `diff` compares, but neither *presents* a single change with its reasoning attached. `show` binds the message (why) to the hunks (what) in one view — the exact pairing an archaeologist needs when `blame` points at a suspicious line and the next question is "what was this commit thinking?"
- **Modern guidance** — pair `show` with `--stat` first for large commits (decide which files deserve full-diff attention), then `show <commit> -- <path>` to isolate one file's slice. For merge commits add `-m`/`--first-parent` awareness: default `show` on a merge displays a combined diff that confuses beginners — `--first-parent` follows the main line, `-m` splits per parent (merges are Domain 03's full story; here, know the flags exist).

```bash
# GOOD: message + diff in one view — the archaeology atom
git show a3f9c1 --stat        # scope first — which files deserve attention?
git show a3f9c1 -- cart.js   # then one file's slice with its reasoning attached
# CONFUSING default: git show <merge> — combined diff; prefer --first-parent on merges
```

### 2) **Blame lines, not people**

**Definition** — `git blame <file>` annotates every line with the commit (hash, author, date) that last touched it. Read each annotation as "which *change* put this here" — then `show` that commit for the why. The tool names no culprits; only team culture can misuse it that way.

- **Why it hurts when misused (team health, correctness)**: "who wrote this bug?" asked in chat turns archaeology into accusation — authors defend instead of explaining, and the real question ("what reasoning produced this?") goes unasked. Worse, `blame` shows the *last* touch, which is often a formatter, a rename, or a moved block — punishing the messenger while the original decision hides two commits deeper.
- **Modern guidance** — the workflow: `blame` → note the commit → `show` the commit → read its message → if the line moved, re-`blame` the *parent* (`git blame <commit>^ -- <file>`) to walk past cosmetic touches. Ignore whitespace-only churn with `-w`, and moved blocks with `-M`/`-C` detection. Establish the team norm explicitly: blame output is cited as commit IDs, never names, in reviews and incidents.

```bash
# GOOD: annotation -> commit -> reasoning, past cosmetic touches
git blame -w -M cart.js          # ignore whitespace, detect moved lines
git show 7e2b9a                  # the change behind the line — read its message
git blame 7e2b9a^ -- cart.js     # walk past it — what did the line look like before?
# BAD: screenshotting blame with a name circled in team chat
```

### 3) **Follow code across renames**

**Definition** — three tools trace content through moves: `git log --follow -- <file>` tracks one file across renames; `git log -S<string>` (pickaxe) lists commits where the *count* of a string changed; `git log -G<regex>` lists commits where a matching line was added or removed. Path history, string history, line history — pick the dimension you are actually asking about.

- **What problem it solves**: code moves — files renamed, functions relocated, strings reworded. Path filters go blind at renames, `grep` on `HEAD` sees only today, and memory ("I think Ali changed this last spring") does not scale. The pickaxe finds the exact commit where a string appeared or vanished, through every move, because it searches *history*, not the working tree.
- **Modern guidance** — reach order: `--follow` for "this file's story across renames" (one file only — a hard limit), `-S` for "when did this exact string arrive/leave" (fast, count-based, ideal for feature flags and constants), `-G` for "which commits touched lines matching this pattern" (regex-precise, slower, ideal for function-signature hunts). Combine with `log` formatting from [2.1](<./2.1. Log filtering formatting and the questions log answers.md>) — `--oneline` keeps pickaxe output scannable.

```bash
# GOOD: search history, not the working tree
git log --oneline --follow -- src/cart.js   # the file's story, across renames (one file only)
git log --oneline -S"MAX_QTY"               # when did this constant arrive or vanish?
git log --oneline -G"function checkout\("   # which commits touched this signature?
# BAD: grep -r MAX_QTY . — sees today only; the answer is in 2024, three renames back
```

### 4) **Common confusion**

- "`blame` proves who caused the bug" — it proves who last *touched the line*, which is routinely a formatter, a linter migration, or a file move. Causation needs the `show`-and-walk-past workflow, not one annotation.
- "`--follow` works on directories" — one file only, and it must be the last argument. Directory-across-rename history has no single command; narrow to the file first.
- "`-S` and `-G` are interchangeable" — `-S` counts occurrences (finds add/remove of a string, misses rewordings that keep the count); `-G` matches line diffs by regex (finds rewordings, noisier). String appeared/vanished → `-S`; pattern touched → `-G`.
- "`git show` with no argument shows the last change" — it shows `HEAD`, which is the last *commit on your current position*, not necessarily the last thing anyone did. On a stale branch, `show` displays old news with full confidence.

### 5) **Mentor note**

Run the archaeology drill on your own repo: pick a line everyone sees daily, `blame` it live, `show` the commit, read the message aloud, walk past one cosmetic touch. Two lessons land at once — the mechanics, and the visible proof that the "culprit" is usually three refactors removed from the decision. Codify the norm in `CONTRIBUTING.md`: blame output is quoted by commit hash, never by author name, and "who" questions get reframed as "which change and why" before anyone answers. Teams that internalize this debug faster *and* fight less — the rare practice that improves correctness and culture simultaneously.
