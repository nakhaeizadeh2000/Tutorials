## 3.1. Gitignore patterns that keep status fast and secrets out

### 1) **Ignore build outputs and environments**

**Definition** — `.gitignore` lists paths Git must never track: dependency directories (`node_modules/`), build outputs (`dist/`, `*.pyc`, `__pycache__/`), environment files (`.env`), editor and OS droppings (`.vscode/`, `.DS_Store`, `*.swp`). Ignored paths stay out of `status`, out of diffs, and out of commits — permanently, for everyone who clones.

- **What problem it solves**: two pains, one file. Noise: ten thousand `node_modules` entries drown `status` and make the three-area discipline unreadable. Risk: `.env` committed once leaks database passwords and API keys into permanent, replicated history. Ignoring is the single control that fixes both — it keeps the working tree honest and the repository clean.
- **Modern guidance** — commit `.gitignore` on day one of every repo, before the first dependency install. Start from a canonical template ([github/gitignore](https://github.com/github/gitignore) per stack — Node, Python, etc.), then add project specifics (`dist/`, coverage output, local overrides). Review rule: any PR that adds a tool or build step must update `.gitignore` in the same commit — ignore rules age exactly as fast as tooling does.

```bash
# GOOD: committed before the first install — noise and secrets never enter history
cat .gitignore
# node_modules/
# dist/
# .env
# .DS_Store
git status --short   # clean signal — only real source files visible
# BAD: npm install first, gitignore "later" — node_modules staged by accident, .env one add away from a leak
```

### 2) **Patterns, negation, and scope**

**Definition** — ignore syntax: `*.log` ignores by extension, `build/` ignores a directory (trailing slash — files named `build` stay tracked), `/out` anchors to the `.gitignore` level, `!keep.log` re-includes an exception, `*` never crosses `/` while `**` does. Later lines override earlier ones; deeper `.gitignore` files override shallower ones; `$XDG_CONFIG_HOME/git/ignore` (global excludes) covers machine-specific droppings (`.DS_Store`, `*.swp`) across all repos.

- **Why it matters (correctness)**: an overbroad rule silently drops source files a deploy needs (`*~` eating a legitimate template, `build` without slash eating a source file named `build`); an underbroad rule leaks. Debugging "why is this file ignored?" has a dedicated tool — `git check-ignore -v <path>` names the exact file and line responsible — but only engineers who know the precedence rules can fix what it reports.
- **Modern guidance** — three placement rules. Repo `.gitignore`: everything any clone needs ignored (dependencies, outputs, env files) — committed and shared. Global excludes: only machine droppings (editors, OS files) — never project paths, or teammates' checkouts behave differently from yours. Negation sparingly (`!`): one exception per rule maximum; chains of re-inclusion become unreadable within months. Verify every new rule with `check-ignore` before committing it.

```bash
# GOOD: diagnose, don't guess — the exact file and line responsible
git check-ignore -v stray.log
#  .gitignore:4:*.log    stray.log   <- line 4 did it
# Negation: ignore all logs except the one the tests assert on
# *.log
# !fixtures/expected.log
```

### 3) **Secrets need prevention, not cleanup**

**Definition** — a pushed secret is a compromised secret: clones, forks, CI logs, and hosting caches replicate it beyond recall. Prevention is `.gitignore` + `.env` discipline + pre-commit secret scanning (gitleaks, GitHub secret scanning, `git-secrets`); cleanup is rotation plus history surgery — expensive, disruptive, and never guaranteed complete.

- **Why it hurts (security, the one irreversible mistake in this domain)**: removing the file in a later commit does not remove it from history — every clone still holds the secret at the old commit, and scrapers harvest pushed keys within minutes. Real incidents follow the pattern: key committed Friday, discovered Monday, rotated Tuesday, abused Wednesday. The cost is measured in incident response, not keystrokes.
- **Modern guidance** — layer three defenses. First, `.env` in `.gitignore` from the first commit, with `.env.example` (keys, no values) committed so setup stays documented. Second, a secret scanner in pre-commit or CI that rejects commits containing key-shaped strings. Third, the response drill rehearsed before it is needed: revoke/rotate immediately, then purge with `git filter-repo` (the supported surgery tool — `filter-branch` is deprecated) plus hosting-side cache invalidation, then force-push with team coordination (history rewrite rules are Domain 05's territory). Never "just delete the file and push" — that hides the leak from `HEAD` while leaving it in history.

```bash
# GOOD: documented setup without values — the secret never approaches Git
cat .env.example
#  DATABASE_URL=postgres://localhost:5432/app   # shape, not the password
#  STRIPE_KEY=sk_test_...
# Response order on a leak: 1) rotate the credential 2) purge history 3) tell the team
```

### 4) **Common confusion**

- "Ignored files are deleted" — ignoring affects tracking only; files stay on disk untouched. Conversely, ignoring an *already tracked* file does nothing — untrack first (`git rm --cached`, keeps the disk copy) then ignore.
- "`git add -f` on an ignored file is harmless" — `-f` overrides the ignore rule and enrolls the file permanently. It exists for the rare legitimate exception (a fixture that matches an ignore pattern); every `-f` deserves a comment explaining why the rule was bypassed.
- "Global gitignore replaces repo gitignore" — complements, never replaces. Teammates do not share your global file — anything the project needs ignored must live in the committed `.gitignore`, or their checkouts diverge from yours.
- "Cleanup tools make leaks fully reversible" — `filter-repo` rewrites your history, not other people's clones, forks, or scraped copies. Rotation is the fix; surgery is hygiene. Budget for both, promise only rotation.

### 5) **Performance note**

Untracked-file scanning is the dominant cost of `git status` in large repos — every directory walk stats thousands of build artifacts. Correct ignore rules are a performance feature: excluding `node_modules/`, `dist/`, and generated trees turns multi-second `status` into milliseconds (the same mechanism Domain 01's performance note described — stats before hashes, but *skipped* before stats). If `status` is slow despite ignore rules, suspect a missing trailing slash (file-vs-directory matching cost) or an enormous legitimately-untracked tree — then consider sparse checkout (advanced workflow, Domain 06 preview). Measure with `time git status` before and after each rule change.

### 6) **Mentor note**

Audit every new repo's `.gitignore` in its first review — missing `.env` coverage is a launch blocker, not a nit. Keep the team's starter template versioned and referenced from onboarding docs; the engineers who need it most (new hires, new stacks) are the least equipped to write it from scratch. And run the leak drill as a tabletop exercise once: "a production key just hit `main` — what are your first three commands?" Anyone answering "delete the file" before "rotate the credential" needs this leaf re-read. Prevention is culture; rotation order is muscle memory.
