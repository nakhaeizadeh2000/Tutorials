## 1.1. Partial staging and the atomic commit

### 1) **Stage hunks, not files**

**Definition** — `git add -p` (patch mode) walks you through each changed hunk and asks: stage this one? Split it? Skip it? You compose the next commit hunk by hunk instead of file by file — the fix goes in, the experiment stays out, even when both live in the same file.

- **What problem it solves**: real editing sessions mix concerns — the bug fix touches `cart.js` lines 40–44 while the half-done feature touches lines 90–120 of the same file. Whole-file staging forces a choice between a mixed commit (unreviewable, unrevertable) and shelving real progress. Hunk staging removes the dilemma: each commit holds exactly one idea regardless of how the editing happened.
- **Modern guidance** — run `git add -p` whenever `git status` shows a file you touched for two reasons. Answer `y` (stage), `n` (skip), `s` (split smaller), `e` (edit the hunk manually for surgical cases). When every hunk in a file belongs to one idea, whole-file `add` is fine — patch mode is for mixed files, not a ritual for clean ones.

```bash
# GOOD: one idea per commit even from a mixed file
git add -p cart.js
#  Stage this hunk [y,n,s,e,?]? y   <- the fix (lines 40-44)
#  Stage this hunk [y,n,s,e,?]? n   <- the experiment (lines 90-120, stays unstaged)
git commit -m "fix(cart): reject negative quantities"
# BAD: git add cart.js && git commit -m "fix + wip feature" — mixed, unrevertable
```

### 2) **Unstage without fear**

**Definition** — `git restore --staged <path>` (modern spelling; `git reset HEAD <path>` is the legacy synonym) moves staged content back to unstaged — the working tree keeps every edit, only the *composition* changes. Unstaging destroys nothing; it un-claims.

- **Why it matters (correctness)**: staging mistakes are the cheapest mistakes in Git to fix, but only if developers believe that. Engineers who fear unstaging commit whatever got staged ("I'll fix it in the next commit") — and the mixed commit enters permanent history. Knowing restore-by-heart turns every staging error into a five-second redo instead of a permanent scar.
- **Modern guidance** — prefer `git restore --staged` in everything you write (the `restore`/`switch` pair, introduced in Git 2.23, separates "affect files" from "move branches" — `reset` conflates them). Keep `git reset HEAD` readable for old scripts, but never teach it first: `reset`'s other modes (`--hard`) destroy work, and muscle memory should not point at the dangerous twin.

```bash
# GOOD: staged too much? un-claim and recompose — nothing is lost
git restore --staged cart.js   # back to unstaged, all edits intact on disk
git add -p cart.js             # recompose deliberately
# DANGEROUS TWIN: git reset --hard discards working-tree edits — never the unstage tool
```

### 3) **One commit, one idea**

**Definition** — an atomic commit is independently reviewable, revertable, and bisectable: it does one thing, builds, and passes tests on its own. Atomicity is not about size (a rename across 200 files is atomic; a 10-line mixed fix is not) — it is about *coherence*: reverting it undoes exactly one decision.

- **Why it hurts when missing (correctness, maintainability)**: every downstream tool assumes atomicity. `git revert` of a mixed commit resurrects the bug while removing the feature. `git bisect` landing on a mixed commit cannot say which idea broke. Reviewers facing "fix + refactor + formatting" approve on trust, not understanding — and trust does not catch bugs. One sloppy commit taxes every future operation on it.
- **Modern guidance** — the test before every commit: "could I revert this without losing something unrelated?" If no, split (unstage, `add -p`, two commits). The test after: `git show --stat HEAD` should tell a one-sentence story. Format-only churn (prettier, lint fixes) always commits separately — it is the highest-noise, lowest-risk change class, and mixing it into logic commits blinds reviewers to the logic.

```bash
# GOOD: verify atomicity right after committing — the stat tells one story
git show --stat HEAD
#  cart.js | 5 +++--     <- one file, one idea: the fix
# BAD SIGN: cart.js + auth.js + package.json in a "fix" — three ideas, one snapshot
```

### 4) **Common confusion**

- "`add -p` is advanced, beginners should stage whole files" — backwards. Beginners mix concerns *most* (everything happens in one file on day one), so patch mode helps them earliest. Teach `y/n/s` in the first week; reserve `e` (manual hunk edit) for later.
- "`git stash` replaces partial staging" — different tools: stash shelves *all* pending work to switch context; partial staging *composes* the next commit from pending work. Stashing to "split" a commit loses the composition; `add -p` is the splitter, stash is the shelf (Domain 06 owns stashing).
- "Small commits mean slow progress" — commit count is not review cost. Five atomic commits review faster than one mixed commit of the same lines, revert safely, and bisect cleanly. Speed is measured at review and rescue, not at typing `commit`.
- "Unstaging loses the staged version" — nothing is versioned until `commit`, so there is no "staged version" to lose. Unstage returns edits to the working tree byte-identical; only `restore` (without `--staged`) or `reset --hard` touch file contents.

### 5) **Performance note**

Patch-mode staging is interactive and therefore "slow" per invocation — seconds of keystrokes. Measure against the alternative: a mixed commit costs minutes in review confusion and potentially hours in revert/bisect rescue. The expensive operation is never `add -p`; it is the archaeology on commits that should have been two. For genuinely large mechanical changes (codemods touching hundreds of files), stage by path (`git add src/cart/`) rather than hunk-walking — match the staging granularity to the change granularity.

### 6) **Mentor note**

Run the mixed-file drill live: hand every junior a file with a fix and an experiment intermingled, and require two commits — each passing the revert test. Watch for the two failure postures: the stuffer (stages everything, writes "fix + wip") and the freezer (afraid to stage anything, commits nothing for days). The stuffer needs the revert-test question; the freezer needs the unstage-without-fear demo. Install the team rule early: any commit message containing "and", "also", "+", or "misc" gets challenged in review — the conjunction is a confession of non-atomicity.
