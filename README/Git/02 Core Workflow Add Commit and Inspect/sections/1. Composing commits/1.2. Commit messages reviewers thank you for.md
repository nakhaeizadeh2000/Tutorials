## 1.2. Commit messages reviewers thank you for

### 1) **Imperative subject, scoped prefix**

**Definition** — the subject line completes the sentence "this commit will ___": `fix(cart): reject negative quantities`, not `fixed` or `fixes` or `cart stuff`. The scope in parentheses names the area; the verb stays imperative because the commit *is* the action applied to history.

- **What problem it solves**: `git log --oneline` is read hundreds of times per project — during review, bisect, archaeology, release notes. Past-tense, vague, or missing subjects turn that index into noise; imperative scoped subjects turn it into a table of contents. The reader decides in seconds whether a commit matters to their question.
- **Modern guidance** — shape: `type(scope): imperative summary`, ≤72 characters, no trailing period. Types that cover ~every commit: `feat`, `fix`, `docs`, `refactor`, `test`, `chore` (plus `perf`, `ci`, `build` as needed). The scope is the smallest area name the team recognizes (`cart`, `auth`, `ci`) — never a filename path, never omitted on user-facing changes.

```bash
# GOOD: completes "this commit will…" — scannable in log, sortable by scope
git commit -m "fix(cart): reject negative quantities"
git commit -m "docs(git): explain partial staging with hunk example"
# BAD: past tense, no scope, no information — log noise from day one
git commit -m "fixed stuff"
git commit -m "WIP"
```

### 2) **Body explains why, not what**

**Definition** — the diff already shows *what* changed; the body records what the diff cannot: why this approach, what was rejected, which trade was accepted, which ticket or incident motivated it. One blank line after the subject, then short paragraphs (wrapped ~72 columns) a future reader can absorb without opening the code.

- **Why it hurts when missing (maintainability)**: six months later someone finds your line in `blame` and asks "can I change this?" Without the why, they guess — and reintroduce the bug you fixed, remove the guardrail you added for a reason, or "simplify" the workaround for an upstream issue. The body is the only channel from past-you to future-them that survives context loss.
- **Modern guidance** — write the body for the archaeologist, not the reviewer: reviewer has the PR description; the archaeologist has only `git show`. Minimum viable body for any non-trivial commit: the reason (one sentence), the rejected alternative (one clause), the reference (`Refs #1234`, incident ID, spec link). Trivial commits (typo fixes) earn a pass; everything that required a decision earns a body.

```bash
# GOOD: the why survives when the PR page is forgotten
git commit -m "fix(cart): reject negative quantities

Quantities reach checkout as -1 when the stepper is held down (see #1234).
Clamping at the model layer, not the UI, so API clients get the same guard.
Rejected UI-only fix: third-party integrations bypass the stepper entirely."
```

### 3) **Conventional Commits as team contract**

**Definition** — [Conventional Commits v1.0.0](https://www.conventionalcommits.org/) formalizes `type(scope): subject` plus `!` for breaking changes and `BREAKING CHANGE:` footers — a machine-readable contract. Agreed once per repo (documented in `CONTRIBUTING.md`), it powers automated changelogs, semantic version bumps, and release pipelines without human triage.

- **What problem it solves**: release time traditionally means a human reading months of log prose and guessing what is major/minor/patch. With the contract, tooling derives it: `fix:` → patch, `feat:` → minor, `BREAKING CHANGE:` → major. The message stops being prose and becomes structured data that humans also happen to read well.
- **Modern guidance** — adopt the contract at the repo level, not per developer: add the spec link plus your type list to `CONTRIBUTING.md`, enforce with commitlint in CI (warn first month, reject after), and teach `!`/`BREAKING CHANGE:` from day one — breaking changes discovered at release time are the most expensive surprise in the workflow. Domain 06 owns the release-automation side; this leaf owns the writing habit it depends on.

```bash
# GOOD: machine-readable contract — tooling derives semver from these
git commit -m "feat(auth): add passkey login"
git commit -m "feat(api)!: drop v1 endpoints

BREAKING CHANGE: /v1/* removed; migrate to /v2 by 2026-12-01."
# BAD: human-only prose that no tooling can classify — release triage by hand, forever
git commit -m "big auth update, also removed old endpoints!!"
```

### 4) **Common confusion**

- "The PR description covers it, the message can be short" — PR pages rot (repos migrate, forks vanish, squash-merges keep only the commit message). The commit message is the durable record; the PR description is the ephemeral one. Write accordingly.
- "Long messages slow me down" — subjects take seconds; bodies take a minute on decision-commits only. Amortized over every future read of that commit, the body is the highest-ROI writing in engineering.
- "Amend/reword fixes any message" — only before pushing. Once shared, message fixes rewrite history (Domain 05's golden rule) — the pressure to write it right the first time is real, and healthy.
- "Emojis and humor make logs friendly" — they make logs *unparseable*: commitlint rejects them, `log --grep` misses them, non-native speakers stumble on them. Friendliness belongs in chat; the log belongs to tooling and archaeologists.

### 5) **Mentor note**

Review messages with the same rigor as diffs for one month per junior — then the habit sticks for years. The fastest coaching loop: `git log --oneline -10` on their branch in the review, reading subjects aloud. Every mumble ("fixed... stuff?") is a rewrite before merge, not after. Keep a team message guide under ten lines (types, scope rules, body minimum, ticket link) — longer guides go unread. And model it from the top: juniors copy the tech lead's "wip" commits faster than any guide they are given.
