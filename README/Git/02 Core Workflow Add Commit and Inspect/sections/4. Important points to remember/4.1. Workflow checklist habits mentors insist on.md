## 4.1. Workflow checklist (habits mentors insist on)

### 1) **Compose before you freeze**

Hunk-staged, one-idea commits — and the staged diff read every single time. No commit leaves your machine without `git diff --staged` passing your own eyes: each hunk intended, each file belonging, the stat telling a one-sentence story. Composition is the last gate before permanence ([1.1](<../1. Composing commits/1.1. Partial staging and the atomic commit.md>)).

- **Why it hurts when missing**: every mixed, unreviewed commit becomes someone else's archaeology problem — unrevertable, unbisectable, unreviewable. The five seconds of staged-diff review prevent the five-hour rescue. There is no cheaper correctness control in the entire track.
- **Modern guidance** — the pre-commit gate, in order: `status` (what exists?) → stage deliberately → `diff --staged` (what freezes?) → commit → `status` (tree quiet?). Any surprise at any step stops the line. Automate the reminder, never the judgment: hooks can run linters, but only eyes approve composition.

### 2) **Message like the reader is future-you**

Imperative subject with scope, why in the body, ticket linked — written for the archaeologist at 2 AM six months from now, who has only `git show` and no memory of today's standup. That reader is you, and they are tired, and the message is their only lifeline ([1.2](<../1. Composing commits/1.2. Commit messages reviewers thank you for.md>)).

- **Why it hurts when missing**: "fix stuff" in a blame trail ends investigations — nobody can tell whether the line is load-bearing, so they either freeze (dead code lives forever) or guess (live guards get deleted). Vague messages convert every future reader into an archaeologist without a map.
- **Modern guidance** — minimum bar per commit: subject a stranger could triage from, body answering "why this way?" for anything that required a decision, reference (`Refs #1234`) for anything with a ticket. Hold the bar in review for one month per contributor — then it holds itself.

### 3) **Read before you operate**

Graph and status first — orientation is cheaper than rescue. Before pulling, merging, branching, or asking for help: `git status` (where am I, what is pending?) and `git lg` (what shape surrounds me?). Most Git questions answer themselves once both are visible ([2.1](<../2. Reading history/2.1. Log filtering formatting and the questions log answers.md>)).

- **Why it hurts when missing**: blind operation is the root cause of every "Git ate my work" story — merging without knowing the fork point, pulling without seeing the remote moved, deleting without checking reachability. The graph takes two seconds to read; the rescue takes an hour to perform.
- **Modern guidance** — make it environmental: prompt showing branch + dirty state, `lg` aliased to two letters ([3.2](<../3. Ignoring and aliasing/3.2. Aliases and config that compress the daily loop.md>)), `.gitignore` keeping `status` instant ([3.1](<../3. Ignoring and aliasing/3.1. Gitignore patterns that keep status fast and secrets out.md>)). When orientation costs nothing, skipping it becomes inexcusable — and reviewable.

### 4) **Common confusion**

- "Checklists slow experienced developers down" — the three habits total under fifteen seconds per commit and prevent the failure classes that consume hours. Experience does not grant immunity to skipping; it grants speed at the checklist itself.
- "One of the three matters less" — they compose: composition without messages produces clean mysteries; messages without composition produce documented messes; both without orientation produce confident errors. All three, every commit.
- "I will adopt these when the team does" — habits propagate upward faster than downward. One developer's atomic commits with real messages make every review they touch better — and visible practice converts teammates within weeks.

### 5) **Mentor note**

Screen with the five-minute drill from Domain 01's checklist, extended: a repo with staged, unstaged, and untracked changes plus a vague-message history — require (a) position and pending composition named, (b) the next commit composed atomically with a proper message, (c) one history question answered with a single `log` invocation. Under five minutes with all three correct means workflow fluency; each hesitation names its drill. Re-run before granting merge rights — these three habits are the cheapest quality gate a team can set, and the only one that pays off in every later domain.
