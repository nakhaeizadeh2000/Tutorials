## 5.1. Common interview QA: workflow and history

### 1) **Staged, edited again, committed — what got committed?**

The workflow trap question, asked in half of all Git interviews in some form: "you edit a file, `git add` it, edit it again, then commit — what does the commit contain?" Answer: the staged content only — the first version. The commit snapshots the index, not the working tree ([Domain 01 2.1](<../../01 Git Fundamentals and Mental Model/sections/2. The three areas/2.1. Working tree index HEAD and the file lifecycle.md>)).

- **What the interviewer is really testing**: whether you have *lived* the three areas or merely read about them. The guaranteed follow-up — "how would you verify?" (`git status` after committing: the file shows modified again, proving the second edit survived outside the commit) — separates operators from memorizers. A second follow-up often comes: "how do you commit only some hunks of a file?" (`git add -p` — [1.1](<../1. Composing commits/1.1. Partial staging and the atomic commit.md>)).
- **Modern guidance** — answer with the demo, not just the fact: narrate the three commands and their outputs. Interviewers hire demonstrated loops ("I stage, re-edit, commit, then `status` shows the file still modified — that leftover is my proof") over stated facts every time.

```bash
# The proof you narrate in the interview
echo v1 > f.txt && git add f.txt && echo v2 > f.txt
git commit -m "test: stage-then-edit trap"
git show HEAD:f.txt    # v1 — the commit holds the staged version
git status --short     # " M f.txt" — v2 survived, unstaged
```

### 2) **Find when a bug was introduced**

The archaeology answer — "a bug exists today but did not last month; how do you find the commit?" Structure the answer as an escalation ladder: `blame` on the suspicious line → `show` the commit → if unclear, pickaxe (`-S`/`-G`) for the string's arrival → `bisect` across the range for behavioral confirmation ([2.2](<../2. Reading history/2.2. Show blame and archaeology without blame games.md>)).

- **What the interviewer is really testing**: method under uncertainty. Juniors answer with one tool ("I'd use blame"); seniors describe a ladder with exit conditions ("blame if I know the line, pickaxe if I know the string, bisect if I only know the symptom and have a reproduction"). The reproduction-script requirement for `bisect` is the detail that signals real experience — bisect without an automated test is manual labor, not a method.
- **Modern guidance** — close with the workflow payoff: atomic commits make every ladder rung work (bisect lands on one idea, revert removes one decision). Archaeology skill and commit discipline are the same virtue at different times — interviewers who hear that connection promote you one level in their heads.

### 3) **Write a commit message for this diff**

The practical exercise — the interviewer pastes a diff and asks for the message. Perform the ritual live: read the stat (scope?), read the hunks (what?), infer the decision (why?), then write `type(scope): imperative subject` plus a two-line why-body with the reasoning you can defend ([1.2](<../1. Composing commits/1.2. Commit messages reviewers thank you for.md>)).

- **What the interviewer is really testing**: whether your messages serve readers or yourself. The failure modes are visible instantly — describing the diff verbatim ("changed lines 40-44", which the diff already says), past tense, no scope, no why. The pass signal is a message that adds information the diff lacks: the reason, the rejected alternative, the scope for triage.
- **Modern guidance** — think aloud while writing: "the diff shows *what*, so my message will carry *why* — the scope is cart, the type is fix, the body notes the rejected UI-only approach." Narrated reasoning turns a writing test into evidence of review culture. Ask which convention the team uses (Conventional Commits?) — the question itself scores points.

### 4) **Rapid-fire drills**

- "Difference between `git diff`, `git diff --staged`, `git diff HEAD`?" — unstaged boundary, staged boundary, and working-tree-vs-`HEAD` (both boundaries at once — shows everything uncommitted).
- "How do you unstage a file without losing edits?" — `git restore --staged <path>`; nothing on disk changes, only the composition.
- "Ignored file already tracked — what happens?" — nothing: ignore rules apply at enrollment, not retroactively. Untrack first (`git rm --cached`), then the rule takes effect.
- "What does `git blame` actually show?" — the last commit per line — usually worth walking past with `blame <commit>^` and `-w`.
- "When do you use `-S` vs `-G`?" — string appeared/vanished (count-based, fast) vs lines matching a pattern changed (regex, precise).
- "Your `git status` is slow — first suspect?" — untracked-tree scanning (build output, dependencies); fix with `.gitignore`, verify with `time git status`.

### 5) **Mentor note**

Prep with live repos, not flashcards: every question above has a three-command demo, and candidates who perform the demo pass while candidates who recite it wobble at follow-ups. Run mocks where you always ask "how would you verify that?" after the first answer — the verification reflex (`status`, `show`, `check-ignore`) is what interviewers actually score. And teach the meta-answer for workflow questions: "my daily loop is status → compose → staged-diff review → commit → status, so this situation [arises rarely / gets caught at step N]." Discipline narrated as habit beats knowledge narrated as facts.
