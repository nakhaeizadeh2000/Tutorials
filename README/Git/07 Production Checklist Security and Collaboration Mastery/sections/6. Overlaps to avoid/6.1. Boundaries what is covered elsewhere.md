## 6.1. Boundaries: what is covered elsewhere

### 1) **Everything underneath**

**Definition** — this domain guards and masters; Domains 01–06 operate and decide. The model (snapshots, DAG, areas) lives in [Domain 01](<../../../01 Git Fundamentals and Mental Model/README.md>); fluency (staging, messages, log, ignore, aliases) in [Domain 02](<../../../02 Core Workflow Add Commit and Inspect/README.md>); joining (branches, merges, conflicts, `rerere`) in [Domain 03](<../../../03 Branching Merging and Conflicts/README.md>); proposing (fetch/push, upstream, forks, PRs, currency) in [Domain 04](<../../../04 Remotes GitHub and Pull Requests/README.md>); undoing and replaying (restore, revert, amend, rebase, reflog) in [Domain 05](<../../../05 Undo Fix and Rewrite History/README.md>); policy and releases (strategy, merge rules, tags, stash, changelogs) in [Domain 06](<../../../06 Workflows Tags Stash and Releases/README.md>). When this domain says "gated squash onto signed tags" or "bisect the range," the *squash*, the *bisect steps*, and the *tag mechanics* are links, not paragraphs.

- **Why the boundary matters**: mastery questions ("how do we stay safe at scale?") and mechanic questions ("how does this command work?") share incidents but different models — governance vs operations. Re-teaching operations inside mastery leaves produces the capstone that reads like a manual: comprehensive, unfinishable, unusable under pressure. Keep them split: operate and decide in 01–06, guard and master here. Playbooks reference mechanics; they never re-teach them.
- **Modern guidance** — if a passage here needs more than one sentence of join/propose/replay/tag mechanics, stop and link instead. The one-sentence versions: commits compose atomically (02), lines join by policy (03/06), proposals flow through review (04), undo follows visibility (05), releases tag by content (06). Everything else here is *proof* (signatures, scans), *gates* (hooks, checks), *conduct* (review), and *playbooks* (incidents).

```bash
# GOOD: one line here, depth behind the link
git bisect run ./repro.sh   # the search mechanics are leaf 3.1 — the runbook slot is new
# BAD: re-explaining staging, merges, rebases, tags, or PR flow in mastery leaves
```

### 2) **Platform specifics**

**Definition** — forge admin consoles (organization rulesets, SSO/SAML, audit logs), registry publishing (npm, container, artifact flows), deploy systems (pipelines beyond the Git gate), and vendor-specific scanners belong to their vendors' docs — this domain owns the *Git half* (what the repo guarantees: signatures, shapes, hooks config, tag discipline) and links out for the rest. The boundary runs at the repository edge: inside the repo, this track decides; outside it, the platform documents.

- **Why the boundary matters**: platform UIs churn quarterly (button names, settings paths, plan-gated features) while Git mechanics stand for decades — embedding console click-paths in tutorial leaves guarantees rot within a year. Worse, platform specifics vary by vendor (GitHub rulesets vs GitLab push rules vs Bitbucket permissions) while the Git underneath is identical. Teaching the Git half keeps every leaf portable; linking the platform half keeps every leaf current.
- **Modern guidance** — name the control, link the console: "required signatures on release lines (forge: branch protection / rulesets — see vendor docs for current paths)" stays true across UI redesigns; screenshot-driven click-paths don't. When platform curiosity strikes mid-playbook ("where exactly is push protection toggled?"), follow the vendor link — this track answers with Git mechanics plus control names, not navigation.

```bash
# GOOD: control named, console linked (portable across vendors and redesigns)
#  control: required signatures + push protection + up-to-date + dismiss-stale (this track)
#  console: <vendor docs — branch protection / rulesets> (their docs, current paths)
# BAD: "click Settings → Branches → Add rule → …" embedded in tutorial leaves —
# accurate until the next redesign, vendor-locked from birth
```

### 3) **Word-level naming**

**Definition** — what security/process words *mean in a meeting* (CVE, blast radius, SLA, retro, on-call as vocabulary) belongs to [IT Vocabulary](<../../../../ITVocabulary/README.md>) — this track never re-teaches definitions those leaves own. Map-style stop-list (the whole track, final): model → 01, composition → 02, joining → 03, proposing → 04, operations → 05, policy → 06, trust → here (07), words → IT Vocabulary.

- **Why the boundary matters**: every boundary crossed here is duplication that rots — security glossaries copied into mastery leaves go stale when industry usage shifts, while the words-track stays current. Single source of truth (PROMPT §5): the concept gets its full treatment once, everywhere else one line plus a link. This leaf is the map that keeps those lines short — and, as the track's last boundaries leaf, the map of the whole territory.
- **Modern guidance** — when writing or reviewing Domain 07 content, ask "does a sibling domain, track, or vendor own this sentence?" If yes, compress to a link. The domain stops at: proven trust, enforced gates, conducted review, rehearsed incidents — everything about *how the operations work*, *where the console buttons live*, or *what the words mean* lives elsewhere.

```bash
# GOOD: boundary as map — one line per neighbor, then stop (track-complete map)

#  Words (CVE/SLA/retro as vocab)→ IT Vocabulary track

```

### 4) **Common confusion**

- "Mastery is where advanced Git lives" — mastery is *governance*; the advanced mechanics distribute across replay (05), policy (06), and trust (this domain). This leaf maps the summit; the climbs live below.
- "Boundaries leaves are filler" — they are the DRY contract made visible: each states what its domain deliberately does *not* teach so the repo can teach it once. Seven domains, seven maps, zero duplication — that was the design working.

### 5) **Performance note**

No runtime cost to boundaries — the performance is editorial: one-line links instead of copied sections keep every leaf short, searchable, and single-sourced. When vendor consoles redesign, zero leaves update (only vendor links); when Domain 05 changes lease guidance, one domain updates instead of seven.

### 6) **Mentor note**

Use this leaf as the graduation map: hand juniors the seven-domain stop-list and have them place any Git question from their week into exactly one bucket — placement accuracy *is* track mastery (Domain 01's review check, now track-wide). Quiz the full arc: model (01), fluency (02), joining (03), proposing (04), undo (05), policy (06), trust (07). Correct placement across all seven means the learner sees Git as a system, not a command bag — the outcome this track was built to produce.
