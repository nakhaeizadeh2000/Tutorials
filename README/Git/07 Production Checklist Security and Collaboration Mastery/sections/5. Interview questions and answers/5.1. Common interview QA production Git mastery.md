## 5.1. Common interview QA: production Git mastery

### 1) **Secret committed and pushed — exact steps?**

**Definition** — the incident answer that tests ordering under pressure: rotate first (revoke at issuer, mint replacement, update consumers, confirm dead — minutes), clean second (filter-repo surgery with freeze coordination — hours), prevent third (fix the failed layer — retro). The order is load-bearing: pushed means compromised (leaf 1.2's axiom), rotation neutralizes all copies at once, surgery restores hygiene but never exposure. Any answer leading with removal fails the question regardless of technical polish.

- **What a good answer sounds like**: "Minute zero: revoke the credential at the issuer and confirm it's dead — pushed means compromised, copies exist that I'll never enumerate. Then mint the replacement and update consumers through the secret manager, never the repo. Then, and only then: history surgery with a freeze announcement, force-push coordination, and re-clones — plus notification per policy. Then retro: which of the three prevention layers failed, and what changes Monday?" Seniors add blast-radius scoping (public vs private, age of exposure, CI logs as copies) and runbook pointers (issuer links pre-written, owners named).
- **Modern guidance** — grade *sequence*, not tooling: rotation → cleanup → prevention is pass; cleanup → rotation (or rotation never) is fail. Instant fail: "delete the commit" as the whole answer (copies keep the bytes), "it's a private repo so it's fine" (private delays, never prevents), silence about notification (breaches become career events through cover-ups, not leaks). Follow-up separating senior: "the CTO says skip rotation to avoid paperwork?" (refuse professionally — live credentials don't negotiate; offer the fast path: rotate now, document in one paragraph).

```bash
# The answer in order (leaf 1.2's minute-zero sequence as interview response)
#  1. ROTATE: revoke at issuer → confirm dead → mint → update consumers (minutes — bounds everything)
#  2. CLEAN: freeze-announce → filter-repo → verify bytes gone → coordinated force-push → re-clones
#  3. PREVENT: retro the failed layer (.gitignore? hook? review?) → fix that layer this sprint
```

### 2) **Main is red on a Friday deploy — now what?**

**Definition** — the pressure test covering leaf 3.1's drill: freeze merges (announce — nobody joins onto red), diagnose fast (bisect with `run` scripts, or identify the suspect PR), fix forward (revert the culprit — minutes to green — or hotfix train for forward fixes; never shared-history surgery), verify green, unfreeze with announcement, retro the gate gap Monday. Forward-only, coordinated throughout, revert-first by default.

- **What a good answer sounds like**: calm sequencing with explicit communication at each step — "I freeze and announce first, because every merge onto red widens the suspect pool. Then bisect (automated repro if we have one) or revert the prime suspect — revert-first, green in minutes, perfect later. Hotfix train only if the fix must go forward. Unfreeze on green with announcement. Monday: which gate should have caught it, and why the freeze announcement was [fast/slow]." Seniors mention forward-porting (hotfix must land on `main` too), hero-patch refusal (perfect fix while the team waits is the wrong trade), and freeze scope (branches continue; only landings stop).
- **Modern guidance** — listen for communication *density*: candidates who announce at freeze, at fix, and at unfreeze demonstrate incident leadership; candidates who describe only commands demonstrate tooling. Red flags: reset+force-push on shared main (breaks N clones to fix one line), "work late crafting the perfect fix" while red compounds (revert-first exists precisely for Fridays), skipping the retro (the gate gap persists — next Friday repeats). The verified bisect session (leaf 3.1) makes a strong live-demo close: "want me to show the search on a scratch range?"

```bash
# The drill as answer (leaf 3.1, compressed)
#  freeze ("main red — no merges") → bisect run ./repro.sh → revert <culprit> → green → unfreeze → retro gate-gap
git bisect start; git bisect bad HEAD; git bisect good <last-green>   # logarithmic, not archaeological
```

### 3) **Design code review for a 50-engineer org**

**Definition** — the systems answer spanning leaf 2.2's contracts: CODEOWNERS routing (paths → required reviewers, risk-matched approval counts), response SLAs (first review within business hours — stale surfaced mechanically), gates as preconditions (green, fresh, parseable, scanned — leaf 2.1), etiquette as throughput (anchored actionable labeled reviews; author-owned loops), load management (rotation, dashboards, caps — no heroes, no ghosts), and evolution (quarterly contract retros). Six components, each with an owner and a failure mode — the collaboration system, not just its ideals.

- **What a good answer sounds like**: architecture with accountability — "Routing: CODEOWNERS by path, two approvals for auth/payments/migrations, one elsewhere. SLAs: first response <24h business, stale >5d nudged with owner (not shame). Gates: green+fresh+parseable required before human review (reviewers never check shapes). Etiquette: anchored suggestions, blocking-vs-nit labels, author resolves every thread. Load: rotation plus dashboards — reviewers visible, heroes unnecessary. Evolution: quarterly retro on the contract itself (SLA hit rates, bypass trends, load spread)." Seniors add the failure modes each component prevents (rot, burnout, gatekeeping, rubber-stamping) and the small-team seed (paragraph now, routing later — grow with the org).
- **Modern guidance** — grade systems thinking (components × owners × failure modes), not values language ("thorough culture" without routing is vibes). Red flags: no SLAs ("review when free" = rot), no load plan ("seniors review everything" = burnout pipeline), gates-optional (etiquette without enforcement decays), one-size approvals (docs and payments gated identically = friction without safety). Rapid-fire drills that close: squash title vs branch commits — which persists? (title — Domain 06); tag vs branch as deploy source? (tag); stash older than a week? (branch or drop); `--no-verify` in every commit? (hook-speed problem first, then culture).

```bash
# The system in six lines (leaf 2.2 as interview answer)
#  route (CODEOWNERS, risk-matched counts) → time-box (SLA + stale-nudge) → precondition (gates)
#  → conduct (anchored, labeled, kind) → author-closes (resolve + re-request) → sustain (rotation + retro)
```

### 4) **Common confusion**

- Candidates who answer incidents with tools but no communication (rotation without notification, freeze without announcement) — half the recovery is coordination; seniors lead with the channel message.
- "More approvals means safer merges" — approval counts match risk (two for auth/payments, one elsewhere); blanket counts slow everything while missing the point (review *quality* gates safety, counts gate throughput).
- Treating the Friday-deploy scenario as purely technical — timing, communication, and restraint (revert-first over hero-patch) dominate tooling. Pressure inverts judgment; playbooks pre-commit it.

### 5) **Performance note**

Interview answers here should be compact: secret incident (two minutes — order first, then mechanics, then prevention), red-main (two minutes — freeze-to-retro with communication density), review design (three minutes — six components with owners and failure modes). Candidates who narrate playbooks without owners or orders take longer and prove less — incidents are sequences with accountability, and the answer should scan that way.

### 6) **Mentor note**

Use Q1 as the incident-order screen (rotation-first is non-negotiable — fail candidates who clean first), Q2 as the pressure screen (freeze-announce-revert-forward-retro with communication density), Q3 as the systems screen (components × owners × failure modes, grown with the org). Rubric: junior — correct steps named; mid — steps ordered with reasons (copies exist, red compounds, routing distributes); senior — prevention and evolution (runbooks pre-written, gates retro'd, contracts grown, heroes unnecessary). Keep the verified bisect session and one moved-tag/secret postmortem (dated, named) ready as live artifacts — demonstrated mechanics beat recited ones. Red-flag fails: delete-the-commit incident response, force-push on shared main, silence as incident strategy, one-shape-fits-all review, stash-as-storage.
