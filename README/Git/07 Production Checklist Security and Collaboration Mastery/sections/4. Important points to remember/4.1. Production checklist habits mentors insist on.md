## 4.1. Production checklist (habits mentors insist on)

### 1) **Trust is proven, not asserted**

**Definition** — every production claim carries evidence: authorship proven by signatures (leaf 1.1 — `verify-tag` in the deploy path, required signatures on release lines), secrets proven absent by scans (leaf 1.2 — shape-checks in hook + CI, push protection on), quality proven by gates (leaf 2.1 — green builds, fresh bases, required reviews). "Trust us" is not a control; verified artifacts are. The checklist question per claim is always "where's the evidence?" — and the answer is always a check that runs.

- **What problem it solves**: asserted trust fails silently — unsigned release tags nobody verifies, secret policies nobody scans, green-looking mains nobody gated. Each looks controlled in the settings screenshot and operates uncontrolled in practice (Domain 06's bypass-culture warning, now with security consequences). Evidence-based trust fails loudly: missing signatures refuse merges, leaked shapes block pushes, red builds stop the queue. Loud failure is the feature — silence is how breaches and bad releases ship.
- **Modern guidance** — audit the evidence quarterly: release tags signed and verified in pipeline (spot-check one release end-to-end: tag → signature → notes → artifact), secret scans firing in CI (check the logs show runs, not just config), required gates actually required (no admin-bypass habit, bypass rates flat). Rotate the proof alongside the secrets (expired keys re-verified after rotation, scanners extended per new secret shapes). New claims ("we now attest builds with provenance") get gates before announcements — evidence first, press release second.

```bash
# GOOD: evidence at every production claim (quarterly audit ritual)
git verify-tag v1.5.2 && echo PROVEN   # release authorship proven, not asserted
git log --show-signature --oneline -5  # signatures present where policy demands them
#  CI logs: secret-scan ran (not just configured) / gates required (not advisory) / bypass flat
# BAD: "we sign releases" with verify-tag failing, "we scan secrets" with the job disabled —
# asserted controls that operate as decoration
```

### 2) **Gates guard outcomes, humans judge**

**Definition** — the division of labor the whole track converges on: automation enforces invariant outcomes (shapes parse, builds pass, bases fresh, secrets absent, signatures present — leaves 2.1, 1.1–1.2, Domains 04/06), humans judge variant ones (is this the right change? is the breaking flag honest? does the strategy still fit? — leaf 2.2, Domain 06 §1.1). Gates never approve *correctness*; reviewers never check *shapes* by eye. Each side does what it's good at, exclusively.

- **Why it matters (correctness)**: crossed wires fail both ways — humans eyeballing message shapes miss what parsers catch (and burn attention doing it), while gates "approving" logic they can't understand breeds automation complacency (green CI mistaken for correct code — leaf 2.1's core warning). The division keeps each side sharp: gates stay fast and deterministic (their reliability is the product), reviewers stay thoughtful (freed from shape-checking to judge design). Teams that blur it get slow humans *and* blind automation — the worst of both.
- **Modern guidance** — when adding any control, ask "gate or judgment?" first: decidable mechanically (shape, color of CI, freshness count, signature presence) → gate it (required check, no human in the loop); requiring context, trade-offs, or taste (design, breaking-ness honesty, strategy fit) → review it (routed humans, SLAs, severity labels). Revisit the line yearly — today's judgment (novel failure mode) becomes tomorrow's gate (pattern codified after the retro). The track's arc in one sentence: Domains 01–05 teach operations, 06 turns them into policy, this domain splits policy into gates (here, mechanical) and judgment (here, human).

```bash
# GOOD: the split visible in configuration vs calendar
#  gates (mechanical): commitlint, build, secret-scan, verify-tag, up-to-date, approvals-count
#  judgment (human): design review, breaking-ness honesty, strategy fit, incident calls
# BAD: humans checking shapes in review ("missing scope prefix!") while gates stay advisory —
# attention spent where parsers excel, absent where only judgment works
```

### 3) **Incidents follow playbooks**

**Definition** — every incident class in this track has a rehearsed sequence: secret leak → rotate-clean-prevent (leaf 1.2); red main → freeze-bisect-revert-forward (leaf 3.1); force-push damage → announce-freeze-relabel-verify-protect (Domain 05 §5.1); moved tag → new-PATCH-never-move-back (Domain 06 §5.1). Playbooks live in runbooks (issuer links, owners, announcement templates), get drilled as tabletops, and get retro'd into gates after each use. Improvisation is what playbooks replace — pressure inverts judgment, so judgment is pre-committed.

- **Why it hurts when missing (correctness, maintainability)**: unrehearsed incidents expand to fill available panic — rotation ordered after cleanup (live credentials persist), fetches continuing during force-push recovery (orphans spread), re-clones destroying reflogs (evidence dies with the directory). Each failure mode in Domains 05–07's incident leaves traces to *sequence errors under pressure*, not knowledge gaps: the team knew the steps and performed them in the wrong order, or skipped one. Playbooks fix ordering; drills fix skipping. The retro fixes the playbook.
- **Modern guidance** — write the four playbooks now (before the incident — links and owners current, announcement templates ready), tabletop one per quarter (rotate which class; include juniors as drivers, not audience), and retro every real incident into prevention (which gate should have caught it? which step was slow? what changes Monday?). Measure announcement latency and time-to-green as the incident metrics that matter — diagnosis brilliance is optional, coordination speed is not. New hires read the playbooks in week one; veterans re-read them the morning after each incident.

```bash
# GOOD: playbooks pre-committed, drilled, retro'd (runbook index)
#  secret-leak.md: rotate (issuer links) → clean → prevent-gap-fix
#  red-main.md: freeze (template) → bisect/revert-forward → unfreeze → gate-gap-fix
#  force-push.md: announce-freeze → reflog-team-verify → protect → retro
#  moved-tag.md: new-PATCH + deprecate + communicate (never move back)
# BAD: "we'll figure it out" as incident strategy —
# figuring-out under pressure reproduces every sequence error these leaves document
```

### 4) **Common confusion**

- "Production checklists are bureaucracy" — checklists replace *remembering* under load (Domain 05 §4.1's pilots analogy, extended to production). Bureaucracy slows decisions; checklists speed correct ones.
- "Small teams can defer all of this" — small teams need *lighter* versions (one playbook page, gates on, signatures on releases), not zero: deferred trust becomes migrated distrust at exactly the growth moment with least spare attention.
- "Green dashboards mean production safety" — dashboards report checked properties; safety includes judgment quality, drill freshness, and runbook currency. Audit the humans' half as rigorously as the gates'.

### 5) **Performance note**

The production checklist runs minutes weekly (evidence spot-checks, bypass-rate glance, playbook currency) plus quarterly tabletops (hours) — against incident costs in hours-to-days and breach costs unbounded. The most leveraged minute is the bypass-rate check (gate contempt detected early stays cheap); the most leveraged hour is the tabletop (coordination rehearsed stays fast). Prevention spending here has the track's highest return because failures here have the track's highest blast radius.

### 6) **Mentor note**

Make this leaf the graduation exam: juniors who can recite the evidence per claim (where's the proof?), the gate/judgment split per control (who decides?), and the four playbooks in order (what first?) have absorbed the track, not just the commands. Run the exam as scenarios, not questions ("secret in a public push, go" — grade the *order*: rotate first). Watch for checklist decay (production discipline followed until the quiet quarter, then skipped — fix with quarterly audits on the calendar, not in memory) and hero normalization ("Alice handles incidents" — fix with rotation + playbooks until anyone on-call can drive). Review check: evidence current, gates honest, playbooks drilled, retros producing gates — and the mentor's own reviews modeling the etiquette from leaf 2.2. The track ends where it began: Domain 01 taught what Git *is*; this leaf teaches what teams *do* with it under production pressure.
