## 1.1. Signing commits and tags

### 1) **Signatures prove authorship**

**Definition** — `git commit -S` / `git tag -s` attach a GPG/SSH cryptographic signature binding the author's identity to the exact content (message, tree, parents, author fields) — anyone with the public key can verify the commit is byte-identical to what the key-holder signed. Unsigned history *asserts* ("author says t@t.t"); signed history *proves* (only the key-holder could have produced this object). Key setup itself is environment-specific (generate, configure `user.signingKey`, optionally `commit.gpgsign true`) — documented per Git signing docs rather than verified here; the behaviors below are verified on Git 2.53.0.

- **What problem it solves**: author fields are free text — anyone can commit as `ceo@company.com` in seconds, and history happily records the lie. In supply-chain reality (dependencies vendored by hash, releases built from tags, audits tracing provenance), unattributed bytes are untrusted bytes: a forged release tag or a spoofed maintainer commit flows downstream exactly like a genuine one. Signatures convert identity from claim to evidence — the forge shows "Verified," builds gate on it, and forgeries fail loudly instead of blending in.
- **Modern guidance** — sign release tags always (`tag -s` — the release coordinate from Domain 06 §2.1 deserves proof); sign commits on protected lines (configure `commit.gpgsign` or require it server-side so signing is default, not discipline). Prefer SSH keys over GPG for new setups (no keyserver archaeology — GitHub accepts both; SSH matches the keys developers already guard). Never share private keys across machines — one key per machine, revocation playbook ready (next sections' key-hygiene rules).

```bash
# GOOD: releases as proof, not assertion (setup documented per Git signing docs)
git tag -s v1.5.2 -m "Release 1.5.2"   # annotated AND signed — message plus proof
git config --global commit.gpgsign true # signing by default — evidence, not effort
# BAD: release tags and protected-line commits unsigned "because setup takes ten minutes" —
# ten minutes once vs unattributable artifacts forever
```

### 2) **Verify before you trust**

**Definition** — verification reads the proof: `git log --show-signature` annotates each commit (signed → key identity line; unsigned → silence), `git verify-commit <sha>` / `verify-tag` exit 0 on valid, nonzero otherwise. Verified on Git 2.53.0: `log --show-signature --oneline -1` on an unsigned commit prints the bare `d91e28c commit 8` (no signature block — absence visible), and `git verify-commit HEAD` exits `rc=1` with no output. For signed objects the same commands print the `gpg: Good signature from "…"` chain — presence vs absence is machine-readable, which is what gates consume.

- **Why it matters (correctness)**: unverified signatures are decoration — teams that sign but never check gain ceremony without security (a forged *unsigned* commit passes unnoticed among signed ones nobody inspects). Verification belongs at the gates that matter: required-signed status checks on release lines (forge rejects unsigned merges mechanically), `verify-tag` in deploy pipelines (deploy only proven tags), spot `--show-signature` in review for sensitive areas (auth, crypto, permissions). Trust is a check that runs, not a badge that displays.
- **Modern guidance** — enforce "required signatures" on release lines and tags in forge settings (the control from Domain 06 §1.2's enforcement checklist, now with cryptographic teeth). Verify tags in release automation before publishing (one `verify-tag` line in the pipeline — leaf 3.1's pipeline gains a proof step). Teach reviewers the absence pattern: no signature block in `--show-signature` where policy demands one is a blocking finding, not a nit.

```bash
# GOOD: absence is visible, presence is checkable — verified
git log --show-signature --oneline -1   # d91e28c commit 8 (no signature block — unsigned, visibly)
git verify-commit HEAD; echo "rc=$?"    # rc=1 — unsigned fails verification (gates consume this)
#  signed twin: "gpg: Good signature from ..." + rc=0 — pipelines deploy on 0, refuse on nonzero
# BAD: signing commits nobody verifies and requiring nothing —
# proof generated and never read is theater with key-management overhead
```

### 3) **Keys are identity infrastructure**

**Definition** — the key lifecycle: generate per machine (`ssh-keygen` or `gpg --gen-key` — documented per provider docs), register the public half (forge settings, teammates' keyrings), guard the private half (passphrase, hardware key where policy demands), rotate on schedule or suspicion, revoke on loss. Expiry, revocation certificates, and transition statements (old key signs the new) are the unglamorous machinery that keeps "Verified" meaningful across staff turnover and laptop loss.

- **Why it hurts when missing (correctness, maintainability)**: key practices rot exactly like password practices — shared deploy keys nobody can rotate (rotating breaks unknown consumers), departed engineers' keys still trusted (no deprovisioning step), lost laptops with unrevoked keys (signatures still "verify" for an attacker). Each converts the signature system from proof back into assertion with extra steps. The failure is silent until incident: verification passes, trust is misplaced, forensics finds the key should have died a year ago.
- **Modern guidance** — one key per machine per human (blast radius bounded — lose one laptop, revoke one key); expiries under two years (rotation becomes routine, not emergency); revocation runbook written before it's needed (who revokes, where registered keys get removed, how in-flight releases re-verify). Prefer SSH signing for humans (matches existing key hygiene) and scoped deploy keys/tokens for automation (narrowest permission, shortest life, rotated by schedule — Domain 06's pipeline owns its credentials like code). Audit yearly: every trusted key maps to a living human and a current machine — or dies.

```bash
# GOOD: identity with a lifecycle (documented per GitHub SSH-signing docs)
#  generate → register (forge + team keyring) → sign by default → expire <2y → rotate routinely
#  loss? → revoke everywhere registered → releases re-verified → postmortem, not panic
# BAD: one shared team key in a chat message, no expiry, no revocation plan —
# proof that proves nothing about who acted, unkillable when it leaks
```

### 4) **Common confusion**

- "Signed commits can't be altered at all" — signatures cover the commit *object*; rebasing/amending creates new (unsigned-until-signed) objects. Policy must require signing *at merge time* (the commits that land), not just at authorship — otherwise replay strips proof silently.
- "SSH signing is less secure than GPG" — both bind identity to content cryptographically; SSH wins on operations (keys developers already have, no keyserver web-of-trust). Security differences that matter live in key custody (hardware vs disk), not algorithm choice.
- "Verification failures mean attack" — usually they mean process gaps (expired key, unregistered signer, rebased-away signature). Treat failures as blocking *and* investigate proportionally: block the merge, then read the failure before sounding alarms.
- "Small teams don't need signing" — small teams need it most per unit of setup (one afternoon protects every future release coordinate). Unsigned-at-five becomes unsigned-at-fifty with migration costs; signed-at-five is just habit by fifty.

### 5) **Performance note**

Signing costs milliseconds per commit (local crypto); verification costs milliseconds per check (pipeline-negligible). Key operations are human-scale (minutes yearly). The expensive resource is incident forensics without provenance ("who shipped this binary?" unanswerable — hours per question) vs with it (one `verify-tag` — seconds). Highest-ROI cryptography in the development workflow.

### 6) **Mentor note**

Demo the spoof live: commit as `ceo@company.com` in scratch (free-text author, no key), show history recording it straight-faced — then verify (`rc=1`, no signature) and ask "so what did the author field prove?" That thirty-second exercise converts every skeptic; signatures stop being bureaucracy and become the answer to a demonstrated lie. Follow with the gate: require signatures on one scratch release line and watch unsigned merges refuse. Watch for the setup-procrastinator ("ten minutes" perpetually deferred — fix with a team key-signing half-hour, everyone leaves signing) and the verify-never signer (signs religiously, checks never — fix with required-signature gates so verification is mechanical). Review check: release tags signed, protected lines require signatures, `verify-tag` in the deploy path, key inventory current, juniors can explain what a signature proves that an author field doesn't.
