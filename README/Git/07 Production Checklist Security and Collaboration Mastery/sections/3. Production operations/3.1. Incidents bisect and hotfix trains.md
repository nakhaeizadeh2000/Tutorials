## 3.1. Incidents, bisect, and hotfix trains

### 1) **Bisect finds the culprit mechanically**

**Definition** — `git bisect` binary-searches history for the commit that introduced a bug: you mark one bad tip and one known-good ancestor, Git checks out the midpoint, you test and answer `good`/`bad` (or automate with `bisect run <script>`), and the range halves each step — logarithmic commits-to-test instead of archaeological reading. Verified on Git 2.53.0 with 8 linear commits: `bisect start` → `status: waiting for both good and bad commits`; `bisect bad HEAD` → `status: waiting for good commit(s), bad commit known`; `bisect good HEAD~7` → `Bisecting: 3 revisions left to test after this (roughly 2 steps)` with midpoint `commit 4` checked out; `bisect reset` returns to the original tip (`Previous HEAD position was … commit 4`).

- **What problem it solves**: regressions hide in ranges ("worked in v1.4, broken in v1.5" — dozens of commits, any one guilty), and linear reading scales with suspects while memory degrades with distance. Bisect converts the search from O(n) skimming into O(log n) testing: 1,000 commits take ~10 test rounds, each a checkout plus the reproduction script. The guilty commit arrives with its message, author, and diff — the full context for the fix and the retro — instead of a suspect pool nobody has time to drain.
- **Modern guidance** — automate the test step (`git bisect run ./repro.sh` — the script exits 0 for good, nonzero for bad; bisect drives itself to the culprit unattended). Keep history bisectable as team policy (atomic commits that build + pass tests alone — Domains 02/06: a red midpoint poisons the search, "skip" recovers but costs steps). Prefer `run` over manual marking for anything past ~5 steps (attention degrades; scripts don't). Always `bisect reset` when done (the tool parks HEAD mid-history — forgetting strands the tree in 1970s archaeology mode until someone notices).

```bash
# GOOD: logarithmic regression hunting — verified session
git bisect start
#  status: waiting for both good and bad commits
git bisect bad HEAD            # broken tip
#  status: waiting for good commit(s), bad commit known
git bisect good HEAD~7         # last known good
#  Bisecting: 3 revisions left to test after this (roughly 2 steps) — midpoint checked out
git bisect run ./repro.sh      # automated: 0=good, nonzero=bad — walks itself to the culprit
git bisect reset               # Previous HEAD position was 26b36d8 commit 4 — back to your line
# BAD: reading 200 commits of diff to find a regression by eye —
# linear, attention-bound, and abandoned halfway (the bug "fixes itself" in the next refactor)
```

### 2) **Freeze, then fix forward**

**Definition** — the red-main drill: broken protected line → freeze merges first (halt the queue, announce — nobody joins onto red), diagnose (bisect or revert-candidate), fix *forward* (revert the culprit per Domain 05 §1.2, or land the hotfix from leaf §3.2's train — new commits on top, never rewrite of the shared line), verify green, unfreeze. Forward-only under pressure: the incident narrows to "which commit" and "which revert/fix," never "who can rewrite fastest."

- **Why it matters (correctness)**: red main compounds — every merge onto broken multiplies the suspect pool and strands developers (rebase onto red, CI red for unrelated work, bisect ranges widening by the hour). The freeze bounds the incident at its current size; fix-forward keeps every action reviewable and revertible (append-only, Domain 05's golden rule holding exactly when breaking it tempts most). Teams that rewrite shared history during incidents trade one red line for N diverged clones — the rescue (Domain 05 §5.1) dwarfs the original bug.
- **Modern guidance** — codify the drill before needing it (runbook: who declares freeze, where announced, who owns revert-vs-hotfix call, green criteria for unfreeze). Default to revert-forward for suspect commits (one revert, green in minutes — perfection waits for the follow-up PR), hotfix train for forward fixes (next section). Time-box diagnosis (bisect with `run` scripts beats meetings about suspects). Retro every red-main hour: which gate should have caught it (leaf 2.1's gate map grows by one), and why the freeze was late (announcement latency is the metric).

```bash
# GOOD: the drill, in order — freeze, diagnose, forward, verify, unfreeze
#  1. freeze: halt queue + announce "main red — no merges until green" (nobody joins onto red)
#  2. diagnose: git bisect run ./repro.sh (logarithmic) or identify the suspect PR
#  3. fix forward: git revert <culprit> (append-only — Domain 05 §1.2, no shared rewrites ever)
#  4. verify: CI green on the revert → unfreeze with announcement
# BAD: "fixing" red main with reset --hard + force-push under pressure —
# N diverged clones, abandoned tags, and an incident response that needs its own incident response
```

### 3) **Hotfixes ride short trains**

**Definition** — the minimal line that carries the cure: branch from the release tag (`switch -c hotfix/x v1.5.1` — the base named precisely, Domain 06 §2.1), apply the smallest fix (cherry-pick the main-line commit per Domain 05 §2.2, or write the surgical patch directly), review under incident SLA (one qualified approval + green fast-suite — rigor proportional to blast radius, not skipped), tag the release (`v1.5.2` + push by name), forward-port to `main` (merge or cherry-pick back — the fix must exist on the development line too, or the next release reintroduces the bug).

- **Why it hurts when missing (correctness, maintainability)**: hotfix improvisation produces the classics — fixing on `main` and "mense will cherry-pick later" (later never comes; the release line stays broken), branching from a moving tip instead of the tag (the hotfix ships untested companions), skipping forward-port (the bug returns next release wearing a new version number), tagging from memory (unversioned hotfix, undeployable audit). The train is short but complete: tag-base, minimal fix, incident review, release tag, forward-port — five cars, none optional.
- **Modern guidance** — keep hotfix branches shorter-lived than features (hours — the train departs on arrival, no station waiting), narrower in scope (the cure plus its test, nothing adjacent — adjacent improvements ride the normal PR flow), and louder in communication (announce start/merge/tag like the mini-incident it is). Verify the forward-port in CI before closing (the port, not the hotfix, is what future releases inherit). Retro hotfix frequency: occasional trains are operations; daily trains mean the release line or the gates need work (leaf 2.1's map), not more trains.

```bash
# GOOD: the short train — tag base, minimal fix, incident review, release tag, forward-port
git switch -c hotfix/login-loop v1.5.1   # base named precisely — the release, not a moving tip
git cherry-pick -x <main-line-fix>       # or the surgical patch + its test (minimal + proven)
#  ... incident-SLA review + fast-suite green ...
git tag -a v1.5.2 -m "Release 1.5.2" && git push origin v1.5.2
git switch main && git cherry-pick -x <hotfix-sha>   # forward-port — main inherits the cure too
# BAD: hotfixing on main with "we'll backport later" — later is never;
# the release stays broken and the next train ships the same bug with a new number
```

### 4) **Common confusion**

- "Bisect works on any history" — bisect needs *testable midpoints*: non-building commits force `skip` (widening the search) and squash-everything lines hide granularity. Atomic green commits (Domains 02/06 policy) are what make bisect logarithmic in practice, not just theory.
- "Freeze means stop all work" — freeze stops *merging to the red line*; feature work continues on branches (it just can't land until green). Freezing branches too idles the team for a pipeline problem.
- "Hotfixes skip review" — hotfixes skip *queue waiting*, never review: incident-SLA approval (one qualified reviewer, fast) plus green fast-suite is the minimum rigor proportional to production blast radius. Unreviewed hotfixes are how incidents breed.
- "Revert-forward admits defeat" — revert-forward is the fastest correct response (minutes to green, full audit trail, re-landable fix). Treating reverts as failure keeps red lines red while heroes craft perfect patches.

### 5) **Performance note**

Bisect cost is logarithmic in range size (10 rounds per 1,000 commits) times reproduction cost — automate reproduction and the search runs unattended; manual testing makes it attention-bound (the rounds are cheap, the tester is not). Freeze cost is team-throughput per red hour (merges blocked — bounded by fix speed, which is why revert-first beats perfect-later). Hotfix trains cost one incident review plus one fast-suite run — constant, predictable, tiny against incident burn rates (production broken × minutes). Optimize the bottleneck: reproduction automation first, revert-first policy second, train mechanics third.

### 6) **Mentor note**

Drill bisect live (the verified 8-commit session takes five minutes and converts skeptics permanently — logarithmic search demonstrated beats described). Stage a red-main tabletop: announce freeze, assign revert-vs-hotfix, walk the forward-port, retro the gate gap — the team rehearses coordination, not just commands. Quiz hotfix anatomy (tag-base? minimal? reviewed? tagged? ported?) until the five cars are reflex. Watch for the hero-patcher (perfect fix on red main while the team waits — fix with revert-first policy: green now, perfect in the follow-up PR), the silent freezer (freezes without announcing — fix with the announcement template), and the no-port closer ("hotfix done" without forward-port — fix with the reintroduction story). Review check: bisectable history (atomic green commits), freeze runbook posted, hotfix trains tagged + ported, every red hour retro'd into a gate.
