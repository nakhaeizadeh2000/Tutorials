## 2.1. Hooks and CI gates

### 1) **Hooks advise locally, gates enforce remotely**

**Definition** — client hooks (`.git/hooks/` or managed frameworks — `pre-commit`, `pre-push`: lint messages, run fast tests, shape-check secrets) run on the developer's machine and are bypassable by design (`--no-verify` skips them — the escape hatch for emergencies). Server-side gates (required status checks, push rulesets, protected-branch requirements — forge-side, documented per GitHub docs) cannot be skipped by the pusher. The split is architectural: hooks optimize the author's inner loop (fail in seconds, locally); gates protect the shared lines (fail the merge, remotely).

- **What problem it solves**: unenforced conventions decay to the median (Domain 06 §3.1: "mostly parseable" history yields confidently-wrong versions), while enforcement-only workflows punish authors with ten-minute CI round trips for typos catchable in one second locally. Hooks-plus-gates gives both speeds: instant local feedback for the author, unbypassable remote control for the team. Either half alone fails its job — hooks without gates are suggestions under pressure; gates without hooks are latency without learning.
- **Modern guidance** — mirror every gate with a hook (commitlint gate ↔ commit-msg hook; secret shape-check gate ↔ pre-commit hook; fast unit tests ↔ pre-push hook) so authors meet each rule locally before the server does. Keep hooks fast (<30s total — slow hooks get `--no-verify`'d permanently) and honest about bypassability (document when skipping is legitimate: incident hotfixes with follow-up gates, never routine impatience). Version hook configs in the repo (managed frameworks install from config — new clones get the same hooks on setup, not by oral tradition).

```bash
# GOOD: the same rule twice — instant locally, unbypassable remotely
#  .pre-commit-config.yaml → commitlint hook (seconds, local, teaches)
#  CI "lint" job + required status check (minutes, remote, enforces)
git commit -m "fix stuff"     # hook refuses locally with a teaching message — fix in seconds
git commit --no-verify -m ..  # the escape hatch exists (incidents) — the gate still refuses remotely
# BAD: gates without hooks (every typo costs a CI round trip — authors learn to hate the gate)
#   or hooks without gates (deadline week: --no-verify everywhere, history fills with "wip")
```

### 2) **Gate the outcomes that matter**

**Definition** — four gates cover the track's accumulated contracts: message shape (commitlint — Domain 06 §3.1's parseable capital), build health (compile + fast tests green — the merge precondition), freshness (branches up to date before joining — Domain 04 §3.1's rot prevention), and human review (required approvals + dismiss-stale — Domains 04/06). Each maps to a required status check or branch rule; together they define "mergeable" mechanically, so merge decisions stop being judgment calls under pressure.

- **Why it matters (correctness)**: each gate exists because its absence caused a named incident class — unparseable messages (wrong versions shipped), red merges (main broken at midnight), stale-base joins (stale-green correctness holes, Domain 06 §1.2), unreviewed rewrites (force-pushed surprises). The gates convert postmortem lessons into pre-merge impossibilities: the failure that taught the rule cannot recur through the normal path. Teams that gate outcomes spend retros on novel problems; teams that don't re-run the same four incidents quarterly.
- **Modern guidance** — require all four on protected lines from day one (green builds, lint/shape, up-to-date, approvals with stale-dismissal — Domain 06 §1.2's enforcement checklist, applied). Add secret scanning and signature requirements where the risk model demands (leaf 1.1–1.2 — release lines always, feature lines proportionally). Review the gate set yearly: each gate should map to a real incident class (remove gates that never fire — they cost latency without buying safety; add gates for each new postmortem's "never again").

```bash
# GOOD: mergeable defined mechanically (forge required-checks settings)
#  main: [x] build+test green  [x] commitlint  [x] secret-scan  [x] up-to-date
#        [x] 2 approvals  [x] dismiss stale  [x] signed (release lines)
# BAD: "CI is advisory" on protected lines —
# advisory gates advise; incidents arrive anyway, now with green-looking history
```

### 3) **Keep gates fast and honest**

**Definition** — gate latency and reliability are policy features, not infrastructure trivia: slow gates (30-minute suites on every push) train `--no-verify` reflexes and "merge despite red" workarounds; flaky gates (nondeterministic failures) teach contempt ("just retry until green" — green stops meaning tested). Fast means staged (seconds for lint/shape, minutes for unit, longer suites on the merge queue or nightly — Domain 06 §1.2); honest means deterministic (same code, same verdict — quarantine flakes out of required checks into advisory until fixed).

- **Why it hurts when missing (correctness, maintainability)**: bypassed gates are worse than absent ones — the team *believes* it's protected (checks exist!) while operating unprotected (everyone skips/retries). Flaky-required checks are the fastest route there: engineers learn green is luck, red is noise, and judgment replaces both — exactly the improvisation gates were built to remove. Gate contempt, once cultural, survives tooling fixes (the new fast suite inherits the old distrust). Speed and determinism are what keep the control *used*, which is what keeps it a control.
- **Modern guidance** — budget latency explicitly (lint <1min, unit <10min, full suite async/queued — authors wait only for the fast stages); quarantine flakes immediately (move to non-required within the hour, fix or delete within the sprint — a flaky required check is an emergency, not background noise); measure bypass rates (`--no-verify` usage, admin overrides, retry-until-green patterns — rising bypass is the metric that the gates are failing socially). Celebrate gate catches in retros ("the gate caught X" stories build the culture that keeps gates trusted).

```bash
# GOOD: staged honesty — fast required, slow async, flakes quarantined
#  push → lint+shape (1min, required) → unit (8min, required) → full matrix (queue/nightly, advisory-until-green)
#  flaky test? → non-required within the hour → fixed or deleted this sprint
# BAD: 40-minute required suite with 5% flake rate —
# authors bypass, reviewers retry-until-green, protection exists only in settings screenshots
```

### 4) **Common confusion**

- "More gates means more safety" — gates buy safety per *incident class covered*, at latency cost per gate. Gates beyond the incident map cost waiting without protection. Four honest gates beat twelve decorative ones.
- "`--no-verify` is cheating" — bypass is a designed escape hatch (incidents, hook bugs); cheating is *routine* bypass. Track bypass rates; investigate trends, not instances.
- "Hooks work for the whole team automatically" — hooks install per clone (`.git/hooks/` isn't versioned; managed frameworks install from versioned config). Onboarding must run the install — otherwise half the team runs unhooked and discovers rules only at CI.
- "Green CI means correct code" — green means *checked properties hold* (tests pass, shapes parse, scans clear). Correctness beyond checked properties is still review's job (next leaf).

### 5) **Performance note**

Hook latency budgets milliseconds-to-seconds locally (shape checks, lint); gate latency budgets minutes remotely (builds, tests) with async overflow to queues/nightlies. Flake quarantine is measured in hours-to-fix, not compute. The expensive line item is bypass culture (incidents return to pre-gate rates while gate costs persist — paying for protection and operating without it). Fast, honest gates are the cheapest correctness control per dollar in the delivery pipeline.

### 6) **Mentor note**

Audit gates as a system with juniors: list every required check, map each to its incident class ("which postmortem created you?"), time each stage, and find one gate to quarantine-or-remove plus one missing gate to add. That exercise teaches gates as *derived controls*, not received bureaucracy. Watch for the bypass-normalizer ("everyone uses --no-verify" — fix with hook speed first, then bypass-rate visibility) and the gate-collector (twelve required checks, half flaky — fix with the incident-map: no postmortem, no requirement). Review check: every required gate maps to an incident class, staged latency budgets hold, flakes quarantined within the hour, bypass rates flat-or-falling, juniors can name what each gate protects and why skipping it matters.
