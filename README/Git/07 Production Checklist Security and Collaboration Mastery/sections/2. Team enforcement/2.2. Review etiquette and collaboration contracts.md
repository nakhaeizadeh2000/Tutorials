## 2.2. Review etiquette and collaboration contracts

### 1) **Review code, respect humans**

**Definition** — the etiquette that keeps senior reviewers reviewing: comment on *lines* (anchored, quotable, resolvable), propose *edits* (suggested changes the author applies in one click — cheaper than describing the fix in prose), separate *blocking* from *advisory* (request-changes for correctness/safety, comments for style/nits — the author must know what gates merging vs what invites thought), and criticize the *work* in language that never touches the *worker* ("this function drops the error" vs "you forgot").

- **What problem it solves**: review is the team's scarcest attention — senior hours spent reading others' code. Bad etiquette taxes it twice: vague comments ("fix this") force re-reads to decode, and harsh tone makes authors dread (then avoid, then resent) review — the pipeline slows exactly where quality is created. Good etiquette compounds the other direction: precise, kind reviews get fast responses, which gets reviewers volunteering for the next one. Tone is throughput.
- **Modern guidance** — reviewers: lead with what's good (one genuine note — orients the author before the corrections), anchor every finding to a line, propose the edit where you know it (suggestion blocks over "consider refactoring"), label severity explicitly (blocking vs nit — teams that don't label argue about labels instead of code), and batch comments (one review pass, not drip-feed notifications across the day). Authors: assume good intent in text (tone compresses badly — read every comment as technical), respond to every thread (fix, or rebut with reasoning — never silent-dismiss), and thank reviewers publicly (attention is a gift; acknowledge it).

```bash
# GOOD: anchored, actionable, labeled — the review that gets answered today
#  [blocking] auth.js:42 — unauthenticated path returns 200 with the payload; suggest:
#  ```suggestion
#  return res.status(401).json({ error: "token required" });
#  ```
#  [nit] cart.js:17 — consider `totalQty` over `tq` (readability, non-blocking)
# BAD: "this is wrong, fix it" on the PR (no line, no proposal, no severity) —
# the author re-reads the whole diff to decode one sentence, then dreads the next review
```

### 2) **Authors own the loop**

**Definition** — reviewability is produced by the author, not discovered by reviewers: small PRs (Domain 04 §2.2's ~400-line ceiling — review quality collapses past it), green before request (CI as precondition, never "CI will tell us"), self-review first (read your own diff before requesting — catch the debug lines and stray files yourself), every thread resolved (fix or rebut with reasoning), re-request after fixes (stale approvals on new code are theater — Domain 06 §1.2's dismiss-stale rule exists because authors forgot this).

- **Why it matters (correctness)**: reviewers sample; authors guarantee. A reviewer can catch logic errors in readable diffs but cannot reconstruct intent from thousand-line PRs with red CI and twelve unresolved threads — they approve (trusting) or stall (overloaded), and both outcomes ship risk. Author discipline converts review from archaeology into verification: the diff is small, the checks are green, the description argues the *why*, and each comment thread closes visibly. The loop's speed is set at opening, not at review.
- **Modern guidance** — open PRs like you're spending reviewers' money (you are): self-review the diff (catch 80% of nits before anyone else reads), write the description as argument (why this change, what alternatives died, how to verify — Domain 02's why-not-what extended to PRs), keep it small or split it (stacked PRs for dependent ideas — each reviewable alone), respond within a day (review latency is queue latency — stale PRs rot per Domain 04 §3.1), and close the loop explicitly (resolve threads, re-request, confirm merge — never "I think it's done").

```bash
# GOOD: the loop owned end-to-end (author-side ritual)
git diff --stat origin/main...feat/x    # scope check before requesting: reviewable in one sitting?
#  description: WHY (decision + alternatives) / WHAT (files changed) / VERIFY (how to test)
#  after fixes: resolve every thread → push → re-request review → confirm merge + delete branch
# BAD: thousand-line PR, red CI, empty description, "PTAL" —
# asks reviewers to certify the unknown on their own time; the loop stalls on day one
```

### 3) **Contracts beat culture memos**

**Definition** — collaboration expectations written where work happens, not in values decks: response-time SLAs (first review within X business hours — codified, not hoped), approval counts per line risk (one for features, two for auth/payments/migrations), CODEOWNERS routing (paths map to required reviewers — the right eyes automatically), and on-call/review rotation (load shared visibly, not absorbed by the conscientious). Contracts are checkable; memos are vibes — checkable survives turnover, vibes don't.

- **Why it hurts when missing (correctness, maintainability)**: implicit expectations produce the two collaboration failures teams misdiagnose as people problems — PRs rotting for weeks ("I thought someone else was reviewing") and review load concentrating on two seniors ("they're just thorough") until they burn out or gatekeep. Both are routing failures, not character flaws: nobody owned the review, so nobody did it; load wasn't assigned, so it pooled. Written contracts distribute both explicitly — SLAs surface staleness mechanically (stale-bot as backstop, humans as owners), CODEOWNERS distributes load by expertise, rotation prevents heroics.
- **Modern guidance** — write the contract once (SLA hours, approvals-per-risk, CODEOWNERS paths, rotation schedule), enforce it lightly (stale-PR nudges, load dashboards, retro review of the contract itself quarterly), and evolve it with team size (five engineers need a paragraph; fifty need routing plus SLAs plus on-call — grow the contract with the org, never ahead of it). Keep the human override: contracts route and time-box, but any reviewer may dive anywhere (serendipitous review catches what routing misses), and any author may request beyond the minimum (risky changes deserve extra eyes voluntarily).

```bash
# GOOD: expectations as configuration (CODEOWNERS + branch rules — versioned, visible)
#  /auth/  @security-team  (2 approvals required — risk-matched)
#  /docs/  @anyone         (1 approval — friction-matched)
#  SLA: first review < 24h business; stale > 5d gets owner-nudged, not shamed
# BAD: "we have a culture of thorough review" with no routing, no SLA, no counts —
# culture describes; contracts assign — rot and burnout fill the gap between
```

### 4) **Common confusion**

- "Thorough review means many comments" — thorough means *decisive*: blocking findings caught, advisory separated, approval or change-request stated clearly. Fifty nits without a verdict is activity, not review.
- "Self-review is redundant — CI and reviewers will catch it" — self-review catches the author's own debug lines, stray files, and scope creep before spending anyone else's attention. It's the cheapest review pass (context already loaded) and the most skipped.
- "SLAs rush reviewers into rubber-stamping" — SLAs bound *first response*, not approval (acknowledge + triage within hours; thorough review on its own schedule). Unbounded queues rubber-stamp more (approve-to-clear) than time-boxed ones.
- "Etiquette is soft skills, separate from engineering" — etiquette determines review throughput, which determines merge latency, which determines shipping speed. Tone is a delivery metric with feelings attached.

### 5) **Performance note**

Review latency dominates PR cycle time (hours-to-days of queueing vs minutes of reading) — SLAs plus small PRs attack exactly that queue. Suggestion blocks cut round trips (one click vs describe-decode-rewrite cycles). CODEOWNERS cuts routing delay (right reviewer assigned instantly vs broadcast-and-hope). The compute is zero; the throughput gains are multiples: teams with contracts merge in hours what memo-culture teams merge in weeks — same code, same rigor, fraction of the wait.

### 6) **Mentor note**

Model the etiquette in every review you write (juniors copy tone before they copy technique — your suggestion blocks and severity labels become their template). Run a review-dojo: one real PR, the team reviews together, then compare findings (missed blockers surface calibration gaps; nit-floods surface severity-label failures). Teach authorship with the self-review ritual (diff-read before request — make it a checklist item until it's habit). Watch for the drive-by ("LGTM" in seconds on 800 lines — fix with SLA-plus-calibration: fast response, real reading), the ghost (never reviews — fix with routing + load visibility, not shame), and the gatekeeper (review as fiefdom — fix with approval-count caps and rotation). Review check: every PR small, green, described, threaded-to-resolution, re-requested after fixes; contracts current; juniors can both give and receive a blocking finding kindly.
