## 1.1. Fetch, pull, and push

### 1) **Fetch reads, pull reads-and-joins**

**Definition** — `git fetch <remote>` downloads new objects and moves only the remote-tracking labels (`origin/main`) — your branches, index, and working tree are untouched. `git pull` is fetch *plus* a join into your current branch (merge by default, rebase if configured). Verified on Git 2.53.0: a fresh `git fetch origin` exits `rc=0` with no output and no working-tree change; after a new commit lands upstream it prints `32a7da8..1c8f24b  main  -> origin/main` — only the mirror moved.

- **What problem it solves**: before fetch existed in your muscle memory, every sync question was a gamble — "has anyone moved underneath me?" Pull-first workflows answer that question by *joining* before you have looked, so a surprise divergence becomes a surprise merge commit (or conflict) instead of information. Fetch separates *learning* from *deciding*: the read is always safe, and the join happens only after you have seen the shape (Domain 03 §2 owns the join shapes).
- **Modern guidance** — fetch first, read the graph, then choose the join. On a clean, expected-linear pull, `pull --ff-only` is the disciplined default (slides or refuses — refusal is information, verified `fatal: Not possible to fast-forward, aborting.` `rc=128` on diverged lines). Reserve bare `pull` for branches where you have already accepted that a join may appear.

```bash
# GOOD: learn first (safe, read-only), decide second
git fetch origin
#  From /tmp/.../origin-repo
#     32a7da8..1c8f24b  main  -> origin/main   (only the mirror moved)
git log --oneline main..origin/main   # what would join? read before choosing
git pull --ff-only                     # slide if linear, refuse if diverged
# BAD INSTINCT: bare `git pull` on a diverged line "to catch up" — fetches AND
# joins in one step, so the divergence resolves itself as a merge you never chose
```

### 2) **Push publishes your line**

**Definition** — `git push` sends your commits to the remote and advances the remote branch label — but only as a fast-forward by default. If the remote tip moved since you last fetched (someone else pushed), the push is refused rather than overwriting their work. Verified: pushing a behind-`main` prints `! [rejected]  main -> main (non-fast-forward)` with hints to integrate first, `rc=1` — your commits are safe locally, nothing remote changed.

- **Why it matters (correctness)**: the default refusal is the collaboration contract made mechanical — no push silently discards commits you have never seen. Every overwrite of shared history must therefore be a deliberate, separately-spelled act (`--force-with-lease`, Domain 05), never an accident of timing. Teams that learn this trust `push` the way they trust `commit`: boring, predictable, reversible.
- **Modern guidance** — set the upstream once (`git push -u origin feat/x` prints `branch 'feat/x' set up to track 'origin/feat/x'`), then push bare forever — the pairing remembers where this line belongs (leaf 1.2 owns the pairing). When a push is rejected, do not retry louder: fetch, read the divergence (`status -sb`, `log --graph`), then merge or rebase deliberately.

```bash
# GOOD: first push pairs the line, later pushes are bare
git push -u origin feat/x
#  * [new branch]      feat/x -> feat/x
#  branch 'feat/x' set up to track 'origin/feat/x'.
git push   # later: To .../origin-repo / ea9f556..c671bf6  feat/x -> feat/x
# PUSH REFUSED (verified): remote moved underneath you — integrate, don't force
git push
#  ! [rejected]        main -> main (non-fast-forward)
#  hint: Updates were rejected because the tip of your current branch is behind
# BAD: reaching for `--force` on a shared branch to "make it go through" —
# that spelling exists for private-line surgery (Domain 05), not for winning races
```

### 3) **Inspect before you join**

**Definition** — the discipline that ties the two halves together: after every fetch, read `status -sb` (ahead/behind counts) and `log --oneline <yours>..<mirror>` (what exactly would join) *before* running pull, merge, or rebase. Verified: after fetching one upstream commit while holding one local commit, `git status -sb` prints `## main...origin/main [ahead 1, behind 1]` and `git branch -vv` shows `main  e6be30b [origin/main: ahead 1, behind 1]` — the numbers name the divergence before any join exists.

- **Why it hurts when missing (correctness, maintainability)**: blind joins produce the two failure shapes every team recognizes — the mystery merge commit on a line nobody knew diverged, and the conflict resolved without context because the resolver never read the incoming side. Both are cheap to prevent (one fetch plus two read commands) and expensive to repair (history surgery, Domain 05, or a revert nobody can explain). Orientation is cheaper than rescue — Domain 02 §4 states it, this leaf makes it mechanical.
- **Modern guidance** — make it a three-line ritual: `fetch`, `status -sb`, `log --oneline HEAD..origin/<branch>`. If behind is 0, pull freely. If behind is nonzero, read the incoming commits, then choose: `--ff-only` slide, deliberate merge, or rebase of your private commits (Domain 05 owns replay-vs-join). Encode the safe default once: `git config pull.ff only` makes pulls refuse surprise joins everywhere.

```bash
# GOOD: the three-line ritual — fetch, count, read, then choose
git fetch origin
git status -sb          # ## main...origin/main [ahead 1, behind 1] — diverged, look closer
git log --oneline main..origin/main   # exactly what they added — read it first
git pull --ff-only      # diverged: fatal: Not possible to fast-forward, aborting. (rc=128)
#  ... refusal is information: merge or rebase deliberately (Domain 05), don't retry blind
# BAD: `git pull` as a reflex on every context switch — joins what you never read
```

### 4) **Common confusion**

- "`fetch` updates my files" — nothing in your working tree, index, or branches moves. Only `origin/*` mirrors advance. If files changed after a fetch, something else ran.
- "`pull` is just the network version of `fetch`" — pull is fetch *plus a join*. That second half can create commits and conflicts. Seniors who say "never pull blind" mean "never join blind."
- "Rejected push means my commits are lost" — rejected means *nothing moved anywhere*: your commits sit intact locally, their commits sit intact remotely. The refusal preserved both.
- "`--ff-only` failing means the remote is broken" — the refusal detected divergence your workflow didn't expect. Read the graph before overriding — same lesson as Domain 03 §2.1, now across machines.

### 5) **Performance note**

Fetch transfers only objects you lack (negotiation by commit graph — usually kilobytes for a day's work), and `status -sb` reads local labels without network. The expensive operation is the initial clone (full history), never the daily fetch — which is why leaf 2.1 says clone once, fetch forever. `pull --ff-only` costs exactly one fetch plus a label slide; surprise merges cost reviewer hours. Optimize for the human side: fetch often (cheap), join deliberately (rare).

### 6) **Mentor note**

Have every junior produce all three verified states in a scratch pair of repos (a local "remote" plus a clone, as in this leaf's probes): a clean fetch with `.. -> origin/main` output, a `push -u` pairing line, and a `[rejected] (non-fast-forward)` refusal. Make them read `status -sb` aloud before every join until ahead/behind is vocabulary, not output. Watch for the two failure postures: the blind-puller (pulls on every switch — fix with the fetch-first ritual) and the forcer (reaches for `--force` on refusal — fix with the question "whose commits would that discard?"). Review check: no bare `pull` on shared lines without a preceding fetch-and-read; `pull.ff only` set in dotfiles.
