## 1.2. Tracking branches and upstream

### 1) **Upstream is a remembered pairing**

**Definition** — an *upstream* (tracking) relationship pairs one local branch with one remote branch (`feat/x ↔ origin/feat/x`). You set it once with `git push -u origin feat/x` (verified: `branch 'feat/x' set up to track 'origin/feat/x'`), and from then on bare `push`, `pull`, and `status` know which remote line this branch talks to. Without a pairing, bare `push` refuses with instructions instead of guessing: verified `fatal: The current branch no-upstream-demo has no upstream branch. / To push ... use git push --set-upstream origin no-upstream-demo` (`rc=128`).

- **What problem it solves**: before the pairing exists, every sync command needs full coordinates — remote name, local name, remote name again (`git push origin feat/x:feat/x` energy). That verbosity is not just typing: it is a chance, on every invocation, to push the wrong line to the wrong place. The pairing collapses the coordinates to zero — `push`, `pull`, done — and moves the "where does this go?" decision to branch-creation time, when you are actually thinking about it.
- **Modern guidance** — always create the pairing on first push (`-u` / `--set-upstream`), for every branch, no exceptions. If you want it automatic, `git config --global push.autoSetupRemote true` sets the pairing on first push without the flag (the error hint itself suggests it). Never type bare `push` on an unpaired branch twice — the first refusal is the setup reminder.

```bash
# GOOD: pair once, then bare commands just work
git push -u origin feat/x
#  * [new branch]      feat/x -> feat/x
#  branch 'feat/x' set up to track 'origin/feat/x'.
git push   # later: ea9f556..c671bf6  feat/x -> feat/x (no coordinates needed)
# UNPAIRED (verified): Git refuses to guess — follow the hint, don't work around it
git push
#  fatal: The current branch no-upstream-demo has no upstream branch.
#  To push the current branch and set the remote as upstream, use
#      git push --set-upstream origin no-upstream-demo
# BAD: `git push origin HEAD:main` casual spellings to dodge the pairing —
# explicit coordinates on every push reintroduce the wrong-target risk the pairing removes
```

### 2) **Remote-tracking labels are read-only mirrors**

**Definition** — `origin/main` is not "their branch on your machine" — it is a *local label* that records where their branch was the last time you fetched. Only fetch (or a successful push) moves it; you never commit onto it, and `checkout origin/main` gives a detached HEAD, not a work branch. The two labels side by side tell the whole story: `main` (where you are) vs `origin/main` (where they were when you last looked).

- **Why it matters (correctness)**: every "but I already pulled!" confusion traces to treating the mirror as live — it goes stale the moment someone else pushes, and stays stale until your next fetch. Leaf 1.1's fetch-first ritual exists precisely because mirrors lie by omission. Read `origin/main` as "last known position," never "current position," and stale-mirror bugs (merging against yesterday's `main`, reviewing an old tip) disappear as a class.
- **Modern guidance** — never commit on a detached `origin/*` checkout; create a local branch (`switch -c`) if the mirror's state is worth working from. After every fetch, glance at what moved (`git fetch origin` prints `old..new  name -> origin/name` per moved mirror — each line is one upstream line that advanced). If a mirror you care about hasn't moved in weeks, the question is process (is that line dead?), not tooling.

```bash
# GOOD: mirrors are read with log, moved only by fetch
git fetch origin
#  From /tmp/.../origin-repo
#     32a7da8..1c8f24b  main  -> origin/main   (mirror advanced; your main untouched)
git log --oneline main..origin/main   # read the gap between your label and the mirror
# BAD INSTINCT: `git checkout origin/main`, committing, and wondering where the
# branch went — detached HEAD commits belong to no line until you label them
```

### 3) **Divergence reads as ahead/behind**

**Definition** — once a branch has an upstream, `status -sb` and `branch -vv` report the relationship as counts: *ahead N* (your unpublished commits) and *behind M* (their unfetched-into-you commits). Verified on Git 2.53.0 with one commit each side: `git status -sb` prints `## main...origin/main [ahead 1, behind 1]` and `git branch -vv` prints `main  e6be30b [origin/main: ahead 1, behind 1]`. The four states form a complete table: up-to-date (0/0 — pull/push are no-ops), ahead-only (push to publish), behind-only (pull to catch up), diverged (choose the join deliberately).

- **Why it hurts when missing (correctness, maintainability)**: developers who never read ahead/behind treat every sync as "just push" or "just pull" — ahead-only lines get blind pulls (needless joins), behind-only lines get force-pushed attempts (refusals, then confusion), and diverged lines get whichever command was typed first. The counts name the situation in two numbers; ignoring them converts every sync into a guess. This is the cheapest situational awareness Git offers — two integers, zero network.
- **Modern guidance** — read the two numbers before every sync and let them pick the command: ahead-only → `push`; behind-only → `pull --ff-only`; diverged → fetch, read the incoming side, then merge or rebase (Domain 05). Teach juniors the table before teaching any flag: up-to-date, ahead, behind, diverged — four states, four responses, no improvisation.

```bash
# GOOD: two numbers pick the command — no guessing
git status -sb    # ## main...origin/main [ahead 1, behind 1] — diverged: read, then choose
git branch -vv    # main  e6be30b [origin/main: ahead 1, behind 1] C
#   ahead-only [ahead 2]          → git push            (publish)
#   behind-only [behind 3]        → git pull --ff-only  (catch up)
#   diverged [ahead 1, behind 1]  → fetch + read + merge-or-rebase (Domain 05)
# BAD: `git pull` on an ahead-only line or `git push` on a behind-only line
# without reading — the counts already told you which direction to move
```

### 4) **Common confusion**

- "`origin/main` and `main` are the same thing synced" — two labels, two histories. Fetch moves the mirror; only a join moves your branch. The gap between them is the entire subject of this domain.
- "Setting upstream gives others access to my branch" — upstream is a *local reminder* of a pairing, visible only in your repo. Others see your branch when you push it, regardless of your `-u` choices.
- "`-u` must be repeated every push" — once per branch, ever. The pairing persists across fetches, pulls, restarts, and clones of the remote state. Repeating it is harmless but signals the model hasn't landed.
- "Behind means I'm doing something wrong" — behind means *they moved*. It is information about the world, not a grade on your work. Ahead means *you moved*. Diverged means *both* — the normal state of collaboration.

### 5) **Performance note**

Ahead/behind counts are computed locally from the two labels — no network, instant even on huge repos. The pairing itself is one config entry (`branch.<name>.remote` + `branch.<name>.merge`, bytes). Cost discipline lives elsewhere: `fetch` transfers only missing objects, while a stale mirror costs reviewer attention, not CPU. The performance argument for `-u` is keystrokes — bare `push`/`pull` vs full coordinates, fifty times a day, forever.

### 6) **Mentor note**

Make juniors draw the four-label picture before touching `-u`: `main`, `origin/main`, the upstream arrow between them, and the ahead/behind counters as the gap. Then have them produce all four table states in a scratch clone (ahead-only, behind-only, diverged, up-to-date) and predict `status -sb` before running it. Watch for the two failure postures: the coordinate-typer (full `push origin x:y` every time, never sets `-u` — fix with `push.autoSetupRemote` plus the wrong-target question) and the mirror-believer (reads `origin/main` as live truth — fix with "when did you last fetch?"). Review check: every branch in active work has an upstream (`branch -vv` shows no bare entries); dotfiles set `push.autoSetupRemote`.
