## 2.2. Pull-request flow: propose, review, merge

### 1) **Branch → push → propose**

**Definition** — the collaboration unit in three steps: create a short-lived branch (Domain 03 §1.2), push it to your copy with upstream set, open a pull request against the source line. Verified Git-side on 2.53.0: `git push -u origin feat/pr-demo` prints `* [new branch]  feat/pr-demo -> feat/pr-demo` plus the tracking line — at that point the branch is reviewable; the PR itself is a forge action (browser button, or `gh pr create` per GitHub CLI docs — `gh` is not installed in this environment, so treat `gh` lines below as documented, Git-side steps as verified).

- **What problem it solves**: without a proposal step, collaboration degrades into permission roulette — either everyone pushes to `main` (racing, overwriting, unreviewed) or patches travel by chat message (unversioned, untestable, unfindable). The PR inserts the missing stage between *done locally* and *joined upstream*: a URL where CI runs, humans read, and discussion attaches to lines instead of memories. Push publishes; propose invites judgment.
- **Modern guidance** — one branch per PR, pushed early (draft PRs welcome — CI feedback beats private perfection), titled like a commit message (imperative, scoped: Domain 02 §1.2). Target the right base (`main` for features, release lines per Domain 06 policy — wrong-base PRs waste a full review cycle). Never open a PR from `main` itself: the branch is the unit, and `main` must stay pullable.

```bash
# GOOD: the three steps — branch (Domain 03), publish (verified), propose (forge)
git switch -c feat/guest-checkout
#  ... one idea, atomic commits (Domain 02 §1.1) ...
git push -u origin feat/guest-checkout
#  * [new branch]      feat/guest-checkout -> feat/guest-checkout
#  branch 'feat/guest-checkout' set up to track 'origin/feat/guest-checkout'.
gh pr create --base main --title "feat(cart): guest checkout behind flag" --body "Why, not what."
#  (GitHub CLI — documented per `gh` manual; browser "Compare & pull request" is the twin)
# BAD: pushing to `main` on the shared repo "because it's a small fix" —
# small fixes deserve review most (they're the ones nobody re-reads after breaking)
```

### 2) **Review is staged reading**

**Definition** — a review proceeds in layers: the diff (what changed, file by file), the commits (are they atomic and messaged?), the checks (CI green?), then the conversation (comments on lines, requested changes as edits). Approve the *change*; request changes as *specific edits*, not verdicts. GitHub renders each layer separately — Files changed, Commits, Checks, Conversation — because each answers a different question.

- **Why it matters (correctness)**: most review value dies in unstructured reading — the reviewer skims, approves, and the bug ships with two signatures on it. Staged reading forces the failure modes apart: diff-reading catches logic errors, commit-reading catches atomicity rot (Domain 02), checks catch what humans can't (tests, lint, build), and line-anchored comments keep feedback attached to code instead of evaporating in chat. Teams that review in stages find smaller things earlier, when they're cheap.
- **Modern guidance** — reviewers: read the diff before the description (the description argues; the diff testifies), verify CI before approving (green checks are a precondition, not a detail), and phrase change-requests as edits ("extract this guard into `requireCart`, then this reads clean") rather than grades. Authors: keep PRs under ~400 changed lines (small branches, Domain 03 §1.2 — review quality collapses past that), respond to every thread (resolve or rebut, never silent-dismiss), and re-request review after pushing fixes — stale approvals on new code are theater.

```bash
# GOOD: author hygiene that makes staged reading possible
git log --oneline origin/main..feat/guest-checkout   # the commit story reviewers will read
git diff --stat origin/main...feat/guest-checkout    # scope check: small enough to review well?
#  ... 3 files changed, 120 insertions(+), 40 deletions(-) — reviewable in one sitting
# BAD INSTINCT: 2,000-line PRs titled "various fixes" with red CI —
# unreviewable scope plus unverified code asks reviewers to certify the unknown
```

### 3) **Merge the PR, delete the branch**

**Definition** — merging the PR joins the line on the forge (merge, squash, or rebase strategy — team policy, Domain 06 owns the choice), and the feature branch label is deleted immediately after (button offers it; accept). The commits are reachable from the target line forever (Domain 03 §1.2: labels are clutter, commits are safe) — deletion is hygiene, not loss.

- **Why it hurts when missing (correctness, maintainability)**: branches that survive their PR become zombie lines — months later nobody knows if `feat/guest-checkout` is merged, abandoned, or load-bearing, so nobody deletes it, and `branch -a` fills with archaeology nobody trusts. Stale branches also invite the worst accident in this domain: committing fresh work onto a merged line, then opening a PR that re-proposes ancient commits alongside new ones. Delete-on-merge closes the loop the branch opened.
- **Modern guidance** — accept the forge's delete-branch offer every time (enable auto-delete in repo settings so it's default, not a decision). Locally, prune the corpses: `git fetch --prune` drops deleted remote-tracking labels, and `git branch -d feat/done` removes merged locals (the `-d` guard from Domain 03 §1.1 refuses if unmerged — trust it). Which merge strategy (squash vs merge commit vs rebase) is Domain 06 policy — this leaf's rule is strategy-agnostic: whatever joins, the label dies.

```bash
# GOOD: close the loop — merge on the forge, prune locally
git fetch --prune origin     # drop remote-tracking labels the forge already deleted
git branch -d feat/guest-checkout
#  Deleted branch feat/guest-checkout (was 367ed42).   (guard passed: fully merged)
# BAD: merged branches lingering for months — `git branch -a` becomes a graveyard
# where nobody can tell live lines from dead ones, and fresh work lands on corpses
```

### 4) **Common confusion**

- "Opening a PR merges my code" — a PR *proposes*; nothing joins until someone merges (button or command). Unmerged PRs are conversation, not history.
- "Draft PRs look unfinished and weak" — drafts signal "feedback welcome, don't merge yet" and run CI early. Private perfection ships later and breaks bigger.
- " approvals mean the code is correct" — approvals mean reviewers read it and CI passed. Correctness is still the author's job; review is sampling, not proof.
- "Deleting the branch deletes the work" — merged commits live on the target line (reachability, Domain 01 §1.2). The label was scaffolding; the building stands.

### 5) **Performance note**

Small PRs review in minutes; large ones wait days (queueing, context-switching, re-reads) — the dominant cost is *time-to-merge*, not compute. CI per-PR is the parallelizable part (matrix builds, cached deps); human attention is not. Optimize the bottleneck: short branches (Domain 03), green-before-request (CI as precondition), delete-on-merge (branch list stays searchable). A team merging ten 100-line PRs daily outships one merging a 1,000-line PR weekly — same code, fraction of the latency.

### 6) **Mentor note**

Walk every junior through one full loop on a scratch fork before their first real PR: branch, push `-u` (read the tracking line aloud), open the PR, request a review from you, respond to one line comment, merge, delete, prune. Grade the loop, not the code. Watch for the two failure postures: the main-pusher ("it's small" — fix with branch protection rules so the forge refuses, not just you) and the mega-PReg ("I'll split it later" — fix with the 400-line ceiling and draft-PR habit). Review check: every PR has a scoped imperative title, green checks before human review, all threads resolved, branch deleted after merge, local mirrors pruned.
