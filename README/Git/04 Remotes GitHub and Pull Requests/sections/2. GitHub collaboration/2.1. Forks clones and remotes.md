## 2.1. Forks, clones, and remotes

### 1) **Clone copies the repo, fork copies the ownership**

**Definition** — `git clone <url>` downloads the full history plus a working tree and names the source `origin` automatically — one command, ready to work. A *fork* is the same copy made server-side under your account (GitHub button, not a Git command): it exists because you lack push permission on the source, so you need a copy you own. Rule of thumb: can you push to it? Clone. Can't? Fork first, then clone *your fork*.

- **What problem it solves**: beginners either request push access they don't need (widening the blast radius of every mistake) or email patch files around (losing history, review, and CI). Fork-plus-clone gives every contributor — employee on day one, stranger on the internet — an identical starting ritual with zero permission negotiation: your copy, your branches, your pushes, proposed back through review. Open source scales on this shape.
- **Modern guidance** — fork on GitHub, clone your fork (`git clone <your-fork-url>`), then add the source as a second remote (next section). Keep the mental labels sharp: the fork is a *GitHub* concept (ownership, permissions, PR source); the clone is a *Git* concept (history on your disk). The fork without a clone is a bookmark; the clone without a fork is read-only ambition.

```bash
# GOOD: the contributor ritual — fork (browser) → clone yours → add source
git clone <your-fork-url>          # origin → YOUR copy (pushable)
# BAD INSTINCT: cloning the source repo directly when you can't push to it —
# every later `git push` dies with permission denied, and the fix is re-cloning
```

### 2) **Two remotes, two directions**

**Definition** — in a fork workflow your clone carries two remotes with opposite jobs: `origin` (your fork — you fetch *and push* here) and `upstream` (the source — you *fetch* here, never push). Verified in a scratch pair: after `git remote add upstream /tmp/.../source-repo`, `git remote -v` shows four lines (`origin` fetch+push, `upstream` fetch+push), and `git fetch upstream` prints `* [new branch]  main  -> upstream/main` (`rc=0`) — a second mirror family (`upstream/main`) alongside `origin/main`.

- **Why it matters (correctness)**: one remote cannot express "take from here, send there." Developers with a single `origin` pointing at the source either push into the void (permission denied) or — worse — repoint `origin` mid-task and lose track of which remote holds which line. Two named remotes make direction explicit in every command: `fetch upstream` (learn from source), `push origin` (publish to mine), and the graph shows both mirror families side by side (`git branch -r`: `origin/main`, `upstream/main`).
- **Modern guidance** — name them exactly `origin` (yours) and `upstream` (theirs): every tutorial, CI script, and teammate expects those names. Fetch both regularly; push only to `origin`. When a command takes a remote argument, say it out loud — "fetch *upstream*, push *origin*" — until direction is reflex. (Keeping those two lines converged over time is leaf 3.1's job.)

```bash
# GOOD: two remotes, each with one job — verified output
git remote add upstream /tmp/.../source-repo
git remote -v
#  origin    /tmp/.../source-repo (fetch)
#  origin    /tmp/.../source-repo (push)
#  upstream  /tmp/.../source-repo (fetch)
#  upstream  /tmp/.../source-repo (push)
git fetch upstream
#  From /tmp/.../source-repo
#   * [new branch]      main       -> upstream/main   (second mirror family)
git branch -r   # origin/HEAD -> origin/main / origin/main / upstream/HEAD -> upstream/main / upstream/main
# BAD: single-remote fork clones where `origin` points at the source —
# pushes fail (or worse, succeed somewhere unintended) and syncing needs re-cloning
```

### 3) **Clone once, fetch forever**

**Definition** — cloning transfers the entire reachable history (every commit, tree, and blob — the full DAG); every later `fetch` transfers only the objects you lack, negotiated by comparing tips. A 2 GB history clones in minutes and fetches in seconds for months afterward. Deleting and re-cloning "to get fresh" re-pays the full price for what one fetch would deliver incrementally.

- **Why it hurts when missing (correctness, maintainability)**: re-cloners lose everything local — stashes, unpushed branches, reflog rescue history (Domain 05), hook and alias config — in exchange for nothing fetch wouldn't give. Worse, the habit spreads: CI jobs that clone full history on every run instead of fetching, onboarding docs that say "if anything looks odd, re-clone." The odd thing is almost always a stale mirror (leaf 1.2) or a diverged line (leaf 1.1) — both diagnosed locally, both fixed without re-downloading the world.
- **Modern guidance** — clone once per machine; thereafter `fetch` (all remotes: `git fetch --all`) is the refresh. For giant repos where even one clone hurts, shallow-clone (`--depth 1`) or partial-clone (`--filter=blob:none`) at clone time — but treat those as documented exceptions with known costs (shallow boundaries confuse `blame`/`bisect` archaeology, Domain 02 §2.2), not as the default. A healthy clone lives for years.

```bash
# GOOD: refresh incrementally — the clone amortizes over its whole lifetime
git fetch --all          # every remote, only missing objects, seconds
git log --oneline origin/main..upstream/main   # what moved where — read, then act (leaf 3.1)
# BAD: `rm -rf repo && git clone <url>` as a troubleshooting step —
# destroys stashes, unpushed work, and reflog, and re-downloads gigabytes to fix
# what `git fetch` plus two read commands would have diagnosed
```

### 4) **Common confusion**

- "Fork is a Git command" — no Git subcommand creates forks. `clone`, `remote`, `fetch`, `push` are Git (local); fork, pull request, merge button are *forge* concepts (GitHub). The boundary matters when switching forges.
- "`upstream` is a reserved remote name" — pure convention, but universal convention: docs, scripts, and teammates all assume `upstream` means the source. Renaming it `source` works and confuses everyone.
- "I need push access to contribute" — the fork exists so you don't. Push to your copy, propose to theirs (next leaf). Maintainers review PRs from strangers daily without granting a single permission.
- "Two remotes means double the downloads" — fetch is per-remote but incremental per-line: `upstream/main` and `origin/main` share nearly all objects, so the second fetch transfers only the delta. Cheap twice beats expensive once.

### 5) **Performance note**

Clone cost is proportional to reachable history (commits × trees × blobs); fetch cost is proportional to *new* objects since last fetch — typically three orders of magnitude smaller day-to-day. `--all` fetches remotes sequentially but each is incremental; on huge monorepos prefer `--filter=blob:none` clones (missing blobs stream on demand) and accept the first-checkout latency trade. The human performance win is bigger: a long-lived clone accumulates reflog depth (Domain 05 rescue window) and mirror freshness — both free, both lost on re-clone.

### 6) **Mentor note**

Have every junior run the full ritual in scratch before touching a real repo: create a bare "source," clone it as "mine," add "source" as `upstream`, and read `remote -v` plus `branch -r` aloud until both mirror families are vocabulary. Then break it on purpose: push to `upstream` directly and read the permission error (or, locally, notice it *succeeds* — which is exactly why the real forge would refuse, and why direction discipline must be habit, not enforcement). Watch for the two failure postures: the single-remoter (one `origin`, perpetual push confusion — fix by adding `upstream` and re-reading `branch -r`) and the re-cloner (fresh clone for every confusion — fix with the fetch-first ritual from leaf 1.1). Review check: every active clone has the expected remotes (`remote -v` shows `origin`→mine, `upstream`→source); no repo younger than its oldest unpushed branch.
