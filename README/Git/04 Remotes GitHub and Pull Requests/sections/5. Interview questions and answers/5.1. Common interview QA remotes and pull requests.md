## 5.1. Common interview QA: remotes and pull requests

### 1) **Fetch vs pull — which and when?**

**Definition** — the judgment question behind every sync decision: `fetch` only moves remote-tracking mirrors (always safe — verified `rc=0`, nothing local changes); `pull` is fetch plus a join into your branch (creates commits, can conflict). Seniors fetch first and join deliberately; juniors pull blind and debug the resulting joins.

- **What a good answer sounds like**: "I fetch to learn and pull to join — separately. `fetch --all`, read `status -sb` and the incoming `log`, then choose: `--ff-only` slide, deliberate merge, or rebase for private lines. Bare `pull` on a line I haven't read is joining blind." Strong candidates cite the verified refusal (`fatal: Not possible to fast-forward, aborting.`, `rc=128`) as *information*, and name `pull.ff only` as the config that makes pulls safe by default.
- **Modern guidance** — interviewers listen for the *separation of learning from deciding*, not flag trivia. Red flags: "pull is just fetching with extra steps" (misses the join), "I always pull, it just works" (never diverged anything real), "--force when pull fails" (solves joins with overwrites — Domain 05 territory, and wrong there too).

```bash
# The answer, demonstrated (all lines verified on Git 2.53.0 in leaf 1.1)
git fetch origin
#  From ...  32a7da8..1c8f24b  main  -> origin/main
git status -sb          # ## main...origin/main [ahead 1, behind 1] — diverged: choose, don't reflex
git pull --ff-only      # fatal: Not possible to fast-forward, aborting. (rc=128) — information, not failure
```

### 2) **Your push is rejected — what happened?**

**Definition** — the practical exercise: walk the candidate through `! [rejected] main -> main (non-fast-forward)` (verified `rc=1`, both sides intact) to the fix. Expected path: read the refusal (remote moved — your branch is behind), fetch, read the divergence (`status -sb`, `log --oneline HEAD..origin/main`), choose merge vs rebase by the private/public rule, then push. The refusal preserved both histories; the fix joins them deliberately.

- **What a good answer sounds like**: "Non-fast-forward — someone pushed first. My commits are safe locally, theirs are safe remotely. I fetch, read what they added, and either merge it in or rebase my private commits on top, then push. I never `--force` a shared line — lease-only on my own PR branch, and only after checking nobody else pushed." Bonus points for naming `status -sb` ahead/behind counts as the diagnostic and `pull.ff only` as prevention.
- **Modern guidance** — grade the *order* (read → choose → act), not the chosen join: merge and rebase are both defensible on the right lines (leaf 3.1). Instant fail: any variant of "force push and tell the team to re-clone" — that answer deletes colleagues' work and advertises it as process. Follow-up that separates mid from senior: "when *would* you force-push?" (private PR branch, after rebase, with `--force-with-lease` — Domain 05).

```bash
# The exercise, exactly as it presents (verified)
git push
#  ! [rejected]        main -> main (non-fast-forward)
#  hint: Updates were rejected because the tip of your current branch is behind
git fetch origin && git status -sb   # [ahead 1, behind 1]? — diverged: read, then choose
git log --oneline HEAD..origin/main  # what they added — the missing context
```

### 3) **Walk me through your first PR to a new repo**

**Definition** — the process answer covering the whole domain: fork (no push access — fork first), clone your fork (`origin` → yours), add `upstream` (source), branch (`switch -c feat/...`), commit atomically (Domain 02), push `-u` (pair the line — verified tracking output), open the PR (scoped imperative title, why-not-what body), respond to review, merge, delete the branch, prune locally. Eight steps, each from a different leaf — the domain in miniature.

- **What a good answer sounds like**: a narrated sequence with *reasons* at each fork in the road — "I fork because I can't push to source; I add `upstream` so I can fetch their movement; I branch so `main` stays pullable; I push `-u` so later pushes are bare; I keep it small so it reviews in one sitting; I delete the branch because merged labels are clutter." Seniors add freshness ("I fetch `--all` and rebase if review runs long") and CI ("green before requesting review").
- **Modern guidance** — listen for shape, not script: the candidate should adapt (employee with push access skips the fork — clones source, branches, PRs from a branch; stranger follows the full fork ritual). Red flags: PR from `main`, thousand-line first PRs, "I push to main and tell someone to look," no mention of upstream/fetch currency. Rapid-fire drills that close the interview: upstream vs origin? (`theirs` vs `mine` — leaf 2.1); rebase or merge your PR after a week? (rebase private, lease-push — leaf 3.1); branch still listed after merge? (delete it, prune — leaf 2.2).

```bash
# The whole flow in six lines (git-side verified across leaves 2.1–3.1)
git clone <your-fork-url> && git remote add upstream <source-url>
git switch -c feat/first-change && git push -u origin feat/first-change
#  branch 'feat/first-change' set up to track 'origin/feat/first-change'.
# ... open PR (forge), review, merge, then:
git fetch --prune origin && git branch -d feat/first-change
```

### 4) **Common confusion**

- Candidates who conflate `origin` with "the real repo" — `origin` is *your clone's name* for wherever it was cloned from (your fork, in fork flow). The source is `upstream`. Naming reveals model.
- "PRs are a Git feature" — forge concept (GitHub); Git's vocabulary ends at branches, remotes, and joins. Knowing the boundary signals seniority.
- Treating `--force-with-lease` as politeness rather than a correctness check — the lease verifies no one else pushed. Seniors say "check," juniors say "polite."

### 5) **Performance note**

Interview answers cost nothing to compute but everything to structure: the fetch-vs-pull answer should take sixty seconds (safe-read vs read-plus-join, refusal-as-information, config prevention); the rejected-push exercise ninety (read, fetch, diagnose, choose); the PR walkthrough two minutes (eight steps with reasons). Candidates who answer in commands without reasons fail the mentor bar — commands are leaf 1.1, reasons are the domain.

### 6) **Mentor note**

Use Q1 as the sync screen (every hire must separate learning from deciding), Q2 as the incident screen (every hire must join deliberately under pressure), Q3 as the process screen (every hire must narrate the full loop with reasons). Grading rubric: junior — correct commands in order; mid — reasons at each branch plus the private/public rebase rule; senior — prevention (`pull.ff only`, `autoSetupRemote`, protected branches, freshness discipline) and the "when would you force-push" edge answered with lease-only precision. Red-flag instant-fail: force-push as a first resort, PRs from `main`, re-clone as troubleshooting. Keep a scratch repo pair handy and make finalists demonstrate Q2 live — reading real `status -sb` output beats reciting it.
