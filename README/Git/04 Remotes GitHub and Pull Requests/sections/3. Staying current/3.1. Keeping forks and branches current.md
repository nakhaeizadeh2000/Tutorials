## 3.1. Keeping forks and branches current

### 1) **Sync the fork, then the branch**

**Definition** — currency flows downhill in a fixed order: fetch everything (`git fetch --all` — verified: prints `Fetching origin` / `Fetching upstream`, `rc=0`), advance your fork's line to the source (`merge upstream/main` into your `main`), then bring your feature line up (`merge` or `rebase` from your refreshed `main`). Each step reads the previous one's result; skipping ahead joins what you never fetched.

- **What problem it solves**: stale forks are the slow rot of collaboration — PRs opened against a months-old base that conflict everywhere, fail CI on removed APIs, and ask reviewers to evaluate code against a world that no longer exists. The rot is invisible until merge day because nothing *errors* on a stale line; it just diverges quietly. Ordered syncing makes freshness a habit with a fixed sequence instead of a rescue performed the night before the deadline.
- **Modern guidance** — run the sequence weekly on active forks, and always before opening or rebasing a PR: `fetch --all`, merge `upstream/main` into your `main`, then update your feature line. Note the verified gotcha: `git fetch upstream origin` does *not* fetch two remotes (it reads `origin` as a ref pattern on `upstream` — verified `fatal: couldn't find remote ref origin`, `rc=128`). Multiple remotes need `--all` or two separate fetch commands — no shorthand.

```bash
# GOOD: downhill in order — fetch all, advance your main, then your feature line
git fetch --all
#  Fetching origin
#  Fetching upstream
git switch main
git merge upstream/main        # your copy catches the source (fast-forward when clean)
git switch feat/guest-checkout
git merge main                 # ... or rebase (next section) — now against fresh base
# BAD: `git fetch upstream origin` for "both at once" — verified failure:
#  fatal: couldn't find remote ref origin (rc=128) — the second name is a ref pattern, not a remote
```

### 2) **Rebase private, merge public**

**Definition** — *rebase* replays your commits onto a new base (rewriting their hashes); *merge* joins two lines (preserving both). The rule that keeps teams safe: rebase lines only you can see (your unpushed or PR-only branch), merge — never rewrite — lines others already pulled. Verified shape: rebasing a branch already sitting on `main` prints `Current branch feat/sync-demo is up to date.` (`rc=0`) — Git replays zero commits and says so, instead of manufacturing an empty join.

- **Why it matters (correctness)**: rebasing a shared line orphans everyone else's copies — their `origin/feat` still points at the pre-replay hashes, so their next pull sprouts duplicate commits and their next push is refused. The damage scales with collaborators: a rebased PR branch inconveniences one reviewer; a rebased `main` breaks the whole team. The private/public boundary is the only rule you need — everything else (interactive cleanup, Domain 05) refines it.
- **Modern guidance** — your feature branch, not yet merged: `git rebase main` (or `rebase upstream/main`) to float it onto the fresh base — linear, reviewable, conflict-resolving once. Shared lines (`main`, merged PRs, anyone else's branch): merge forward, never rebase backward. After rebasing a *pushed* PR branch, the push needs `--force-with-lease` (lease, never bare `--force` — the lease refuses if a teammate pushed meanwhile; Domain 05 owns the spelling). If that sentence made you nervous, good — it should be a conscious act, not a habit.

```bash
# GOOD: private line floats forward — replay, then lease-push to your own PR branch
git switch feat/guest-checkout
git fetch --all
git rebase main                # replays your commits onto fresh main (hashes change — expected)
git push --force-with-lease origin feat/guest-checkout   # lease: refuses if someone else pushed
# BAD: `git rebase main` run ON main, or rebasing a branch three teammates pulled —
# their mirrors still reference pre-replay hashes; every pull duplicates, every push refuses
```

### 3) **Stale PRs rot visibly**

**Definition** — a PR's *freshness* is the gap between its base at open time and the target line now (`behind N` from leaf 1.2, but against a moving target). GitHub shows it plainly: "This branch is out-of-date with the base branch" plus mergeability (clean / conflicting) plus CI status on the *latest* base. Rot has three symptoms — conflicts (base moved under edited regions), red CI on current APIs (code written against removed behavior), and review drift (comments anchoring to lines that shifted).

- **Why it hurts when missing (correctness, maintainability)**: stale PRs are where merges go to die — the author context-switched months ago, the reviewer must reconstruct intent from archaeology, and the "just merge it, CI will catch problems" pressure peaks exactly when CI is testing the stalest code. Teams that tolerate rot pay in revert rates: fresh PRs revert cleanly (Domain 03 §2.1's join commit), stale ones revert mysteries. Freshness is a leading indicator of merge safety.
- **Modern guidance** — refresh any PR older than a week: fetch, rebase onto the current base, force-with-lease, confirm CI re-runs green. Enable "update branch" discipline (or auto-update in repo settings) so the forge warns before rot compounds. Close PRs that won't merge this quarter — a closed PR with a summary beats a rotting one that blocks the branch list and confuses `git branch -r` readers. Small branches (Domain 03 §1.2) rot slower because they merge sooner; staleness is mostly a scope problem wearing a sync costume.

```bash
# GOOD: weekly freshness pass on every open PR you own
git fetch --all
git status -sb   # ## feat/x...origin/feat/x [behind 12]? — the base moved; refresh now
git rebase origin/main
git push --force-with-lease
# BAD: "This branch is N hundred commits behind — merge anyway, we'll fix forward" —
# forward-fixes on stale bases are how reverts become multi-day incidents
```

### 4) **Common confusion**

- "My fork auto-updates when the source changes" — forks are snapshots; nothing moves until you fetch and join. (GitHub offers a "Sync fork" button — a merge you still must click.)
- "Rebase is just a cleaner merge" — different operations with different contracts: merge preserves both histories, rebase rewrites yours. "Cleaner" is true only for private lines; on public lines it's destructive.
- "`--force-with-lease` is just polite `--force`" — the lease is a *correctness check*: it verifies nobody else pushed before overwriting. Bare `--force` skips the check. On your own PR branch the difference rarely matters — until the once it does.
- "CI passed, so the stale PR is fine" — CI tested the *old base*. Rebase re-runs CI against the new one; that re-run is the point, not bureaucracy.

### 5) **Performance note**

`fetch --all` cost scales with new objects per remote (incremental, seconds); rebase cost scales with your commits × conflicting hunks (usually trivial on weekly cadences, painful on quarterly ones — another reason small branches win). The expensive resource is CI re-runs per refresh (minutes × matrix) — which is why teams batch refreshes weekly rather than per-commit on dormant PRs. Optimize for merge latency: fresh PRs merge in one review cycle; rotten ones consume cycles without merging.

### 6) **Mentor note**

Assign every junior a "stale PR rescue" exercise in scratch: open a PR, advance the base by ten commits (including one conflicting hunk), then have them fetch, read the gap (`log --oneline HEAD..upstream/main`), rebase, resolve once, lease-push, and confirm green. Grade the *order* (fetch → read → replay → verify), not the speed. Watch for the two failure postures: the never-syncer (PR open for a month, "waiting for review" — fix with the weekly freshness pass as calendar habit) and the public-rebaser (replays shared lines for cleanliness — fix with the private/public question: "who else can see this line?"). Review check: no open PR older than two weeks without a freshness comment; `fetch --all` in every sync ritual, never the two-name shorthand.
